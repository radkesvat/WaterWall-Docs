# WireGuard با احراز هویت حساب

با یک حساب WireGuard به سرویس IPv4 مبتنی بر TCP یا UDP دسترسی پیدا کنید.
کلاینت بسته‌های IP را از رابط TUN می‌فرستد. سرور حساب را احراز هویت می‌کند و
برای هر جریان پذیرفته‌شده یک سوکت باز می‌کند. در این حالت فقط کلاینت به TUN
نیاز دارد و سوکت‌های سرور ترافیک را به مقصد می‌رسانند. برای مسیریابی بسته‌های
خام، از جمله ICMP، [WireGuard روی UDP در حالت بسته](./wireguard.mdx) را ببینید.

```text
Client: TunDevice -> WireGuardClient -> UdpConnector
Server: UdpListener -> WireGuardServer (mode=connection) -> TcpUdpConnector
```

سرور به یک سرویس نام‌دار `AuthenticationClient` ارجاع می‌دهد. در این نمونه،
سرویس به `AuthenticationServer` در همان فرایند متصل می‌شود و حساب WireGuard
از `users.json` بارگیری می‌شود. WaterWall گره‌های تبدیل بسته به اتصال و اعمال
سیاست حساب را به‌طور خودکار اضافه می‌کند.

## آماده‌سازی میزبان‌ها {#prepare-the-hosts}

از دو میزبان لینوکس در یک شبکهٔ آزمایشی جداگانه استفاده کنید و روی هر دو
WaterWall نصب کنید. کلاینت به اجازهٔ ساخت رابط TUN نیاز دارد. دسترسی کلاینت به
پورت UDP `51820` سرور را باز کنید. در این نمونه TUN کلاینت و سرویس آزمایشی در
زیرشبکهٔ `10.50.0.0/24` هستند. اگر با مسیر موجود هم‌پوشانی دارد، یک زیرشبکهٔ
آزاد انتخاب کنید.

## پیکربندی دو طرف {#configure-each-side}

فایل‌های زیر را کنار `Waterwall` روی میزبان مربوط ذخیره کنید و WaterWall را از
همان پوشه اجرا کنید. `users.json` را کنار پیکربندی سرور نگه دارید.

| میزبان | فایل‌ها | منبع |
| --- | --- | --- |
| کلاینت | `core.json`، `config.json` | [client](https://github.com/radkesvat/WaterWall/tree/main/tunnels/WireGuardClient/examples/client) |
| سرور | `core.json`، `config.json`، `users.json` | [connection-server](https://github.com/radkesvat/WaterWall/tree/main/tunnels/WireGuardClient/examples/connection-server) |

1. در کلاینت، `127.0.0.1:51820` را در `WireGuardClient.settings.peers[0].endpoint`
   با آدرس IPv4 قابل‌دسترسی و پورت UDP سرور جایگزین کنید. `allowedips` همتا را
   برای سرویس آزمایشی زیر روی `10.50.0.1/32` بگذارید.
2. در سرور، `WireGuardServer.settings.mode` را روی `connection` و
   `auth-client-node-name` را روی `accounts`، یعنی نام گرهٔ `AuthenticationClient`
   در پیکربندی، نگه دارید. `TcpUdpConnector` با `dest_context->address` و
   `dest_context->port` به مقصد هر جریان داخلی متصل می‌شود.
3. در `users.json`، مقدار `wireguard-allowed-ips` حساب نمونه `10.50.0.4/30` است
   و آدرس TUN کلاینت، یعنی `10.50.0.5`، را پوشش می‌دهد. کلید خصوصی کلاینت نمونه
   با همین حساب مطابقت دارد. اعتبارنامه‌های نمونه را فقط در شبکهٔ آزمایشی
   جداگانه به کار ببرید.

برای استفادهٔ عملیاتی، جفت کلید سرور، گذرواژهٔ حساب و رمز مشترک سرویس احراز هویت
را عوض کنید. کلید عمومی تازهٔ سرور را در تنظیمات همتای کلاینت وارد کنید. برای
`privatekey` کلاینت، خروجی SHA-256 گذرواژهٔ تازهٔ حساب را با Base64 رمزگذاری
کنید. سرور کلید عمومی متناظر را از روی حساب به دست می‌آورد. رمز مشترک سرویس
احراز هویت باید در `AuthenticationClient.settings.secret` و ورودی متناظر در
`AuthenticationServer.settings.auth-clients` یکسان باشد.
[تنظیمات WireGuardServer](../../02-noderefs/WireGuardServer.mdx#settings)

## اجرا و بررسی {#run-and-check}

در سرور، به سرویس HTTP آزمایشی یک آدرس محلی در زیرشبکهٔ TUN کلاینت بدهید. فایل
آزمایشی را از یک پوشهٔ جداگانه ارائه کنید تا فقط همان فایل در دسترس باشد. آدرس
داخلی `10.50.0.1` روی رابط `lo` سرور قرار می‌گیرد و آدرس عادی شبکهٔ سرور مقصد
بیرونی UDP است.

```bash
sudo ip addr add 10.50.0.1/32 dev lo
test_dir=$(mktemp -d)
printf '%s\n' 'WireGuard connection mode is working.' > "$test_dir/index.html"
python3 -m http.server 8080 --bind 10.50.0.1 --directory "$test_dir"
```

در یک ترمینال دیگر، WaterWall را روی سرور از پوشهٔ پیکربندی آن اجرا کنید. سپس
کلاینت را از پوشهٔ پیکربندی خودش راه‌اندازی کنید.

```bash title="سرور"
./Waterwall --config:core.json
```

```bash title="کلاینت"
sudo ./Waterwall --config:core.json
```

روی کلاینت، مسیر را بررسی کنید و فایل را درخواست کنید.

```bash
ip -4 route get 10.50.0.1
curl --noproxy '*' --fail http://10.50.0.1:8080/
```

مسیر باید از `ww-client` عبور کند و پاسخ باید
`WireGuard connection mode is working.` باشد. اگر درخواست ناموفق بود، فعال بودن
حساب، پوشش آدرس TUN کلاینت در بازهٔ مجاز حساب و دسترسی سرور به سرویس HTTP را
بررسی کنید. برای بررسی این حالت از TCP یا UDP استفاده کنید، چون این حالت
جریان‌های TCP و UDP روی IPv4 بدون قطعه‌قطعه‌شدن را پردازش می‌کند.

پس از پایان آزمایش، سرویس HTTP را متوقف و آدرس موقت را از رابط `lo` حذف کنید.

```bash
sudo ip addr del 10.50.0.1/32 dev lo
```

برای راه‌اندازی کلاینت SOCKS5 با یک پل بسته درون فرایند به جای رابط TUN،
[ConnectionToPackets](../../02-noderefs/ConnectionToPackets.mdx#typical-placement)
را ببینید.
