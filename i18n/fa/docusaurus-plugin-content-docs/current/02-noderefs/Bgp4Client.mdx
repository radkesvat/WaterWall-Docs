# Bgp4Client {#bgp4client}

## نمای کلی {#overview}

`Bgp4Client` یک تونل جریان بایتی در لایه ۴ است. payload‌های upstream را در فریم‌هایی شبیه BGP قرار می‌دهد و فریم‌های downstream ساخته‌شده توسط `Bgp4Server` را باز می‌کند.

:::warning
`Bgp4Client` مسیریابی واقعی BGP، برقراری BGP peering، تبادل route یا احراز هویت BGP را پیاده‌سازی نمی‌کند. شکل فریم شبیه BGP فقط برای استتار و فریم‌بندی جریان بایتی به کار می‌رود.
:::

گره در `Init` پروتکل TCP را از گزینه‌های مقصد انتخاب می‌کند. خطی که
TCP عرضه نکند بسته می‌شود.

## جایگاه معمول در زنجیره {#typical-placement}

این گره باید با `Bgp4Server` استفاده شود:

```text
client: TcpListener(127.0.0.1:18080) -> Bgp4Client -> TcpConnector(gateway:7443)
server: TcpListener(0.0.0.0:7443) -> Bgp4Server -> TcpConnector(127.0.0.1:8080)
```

connector سمت client به listener مربوط به WaterWall در server روی پورت `7443`
وصل می‌شود؛ connector سمت server سرویس HTTP واقعی روی `127.0.0.1:8080` را
انتخاب می‌کند. برنامه‌ی محلی را به `127.0.0.1:18080` متصل کنید. دو گره نوع BGP
بایت‌ها را فریم و باز می‌کنند؛ HTTP را بازنویسی نمی‌کنند و مقصد را انتخاب نمی‌کنند.

## نمونهٔ کاربردی ساده {#minimal-practical-example}

این‌ها قطعه‌های پیکربندی گره هستند؛ گره‌های همسایهٔ ارجاع‌شده را در پیکربندی پیرامون آن‌ها تعریف کنید.

### نمونهٔ پیکربندی {#configuration-example}

<a id="نمونه-تنظیم"></a>

سمت کلاینت:

```json
{
  "name": "bgp4-client",
  "type": "Bgp4Client",
  "settings": {},
  "next": "transport-out"
}
```

سمت سرور متناظر:

```json
{
  "name": "bgp4-server",
  "type": "Bgp4Server",
  "settings": {},
  "next": "target"
}
```

فیلد `password` برای سازگاری با پیکربندی‌های قدیمی پذیرفته می‌شود، اما منطق فعلی پروتکل از آن برای رمزنگاری یا احراز هویت استفاده نمی‌کند.

## کاربرد و رفع اشکال {#usage-and-troubleshooting}

### محدودیت‌ها {#limits}

<a id="محدودیتها-و-padding"></a>

| محدودیت | مقدار | یادداشت |
| --- | --- | --- |
| حداکثر طول بدنه | `65535` بایت | شامل type یک‌بایتی. |
| حداکثر payload در بدنه عادی | `65534` بایت | مجموع payload و type باید در `65535` بایت جا شود. |
| سقف منطقی ورودی بازگشتی | `2162705` | بایت‌های wire قدیمی به‌علاوهٔ ورودی بازگشتی، شامل سرآیند کش‌شده. |
| سقف هزینهٔ بافرهای ورودی نگه‌داری‌شده | `4325410` | پس از پذیرش بازگشتی و پایان تخلیهٔ بایت‌های آمادهٔ بدنه؛ فشرده‌سازی مفید پیش از رد انجام می‌شود. |
| سقف بایت‌های خروجی فریم‌بندی‌شده در صف | `2162705` | شامل سرآیندهای تولیدشده؛ پیش از callback بررسی می‌شود. |
| سقف هزینهٔ بافرهای خروجی در صف | `8 MiB` | بافرهای خروجی تا هنگام تحویل محاسبه می‌شوند. |
| حداکثر فریم کامل روی مسیر | `65553` بایت | نشانگر، طول، type و بدنه. |
| فضای خالی لازم در سمت چپ | `39` بایت | برای پیشوند فریم و بزرگ‌ترین پیشوند ساختگی OPEN کافی است. |

<span id="splice-فریمبندی-و-کنترل-فشار"></span>

هر دو جهت بافر عادی، بدنهٔ داخل pipe خصوصی و ترکیب این دو را می‌پذیرند.
هر تحویلی که جا شود با استفاده از padding رزروشدهٔ سمت چپ، از جمله پیشوند موجود در حافظه، در همان بافر فریم‌بندی می‌شود؛ بودجهٔ
padding کلاینت ۳۹ و سرور ۱۹ بایت است. ورودی بزرگِ مسیر ارسال پیش از نخستین callback به
یک دستهٔ کامل از فریم‌های مستقل تبدیل می‌شود. شکست ساخت pipe یا پرشدن مقصد
برای همان فریم به بافر عادی با اندازهٔ کافی برمی‌گردد؛ کل ورودی به یک بافر
عادی تجمیع نمی‌شود.

گیرنده سرآیند نوزده‌بایتی را cache می‌کند و بایت‌های آمادهٔ بدنه برنامه را
تدریجی تحویل می‌دهد. سرور ابتدا ۱۰ بایت ثابت OPEN را جمع‌آوری و اعتبارسنجی
می‌کند، سپس حداکثر ۲۵۵ بایت اختیاری را پیش از تحویل دادهٔ برنامه مصرف می‌کند؛
نمایش بقیهٔ دادهٔ برنامه حفظ می‌شود. کلاینت ۳ تا ۱۰ بایت
اختیاری تولید می‌کند و اندازهٔ واقعی آن را از ظرفیت فریم نخست کم می‌کند.
ورودی خالی فریمی تولید نمی‌کند و وضعیت نخستین OPEN را مصرف نمی‌کند.
روی هر line کلاینت دقیقاً یک OPEN پذیرفته می‌شود.

گیرندهٔ مشترکِ فریم با سرآیند ثابت، پیش از بررسی بخش ناقصِ باقی‌مانده، بایت‌های آمادهٔ بدنه را از دستهٔ ورودیِ بدون ورود مجدد (non-reentrant) تخلیه
می‌کند؛ بنابراین اندازهٔ آن دسته می‌تواند از **۲٬۱۶۲٬۷۰۵ بایت**
(`2 MiB + 65,553`) بیشتر باشد. هنگام اجرای callback تحویل، ورودی بازگشتی به‌همراه
بایت‌های wire قدیمیِ نگه‌داری‌شده، شامل سرآیند کش‌شده، باید در همین سقف منطقی
جا شود. سپس ورودی به انتهای FIFO افزوده می‌شود و پیش از بازگشت از پذیرش
بازگشتی، هزینهٔ محاسبه‌شدهٔ بافرهای نگه‌داری‌شده باید حداکثر **۴٬۳۲۵٬۴۱۰ بایت**
باشد. همین سقف هزینه برای باقیماندهٔ ناقص هنگام پایان تخلیه نیز بررسی می‌شود.
ادغام در فضای موجود یا یک‌بار فشرده‌سازیِ مفید می‌تواند پیش از رد ورودی، فضای
اضافی بافرها را آزاد کند. فشرده‌سازی ممکن است بایت‌های داخل pipe را به حافظهٔ
عادی کپی کند؛ سقف هزینه، حسابداری فضای نگه‌داری‌شده را محدود می‌کند، نه کل حافظهٔ
فرایند یا اوج مصرف موقت را. تعداد قطعه‌های ورودی سقف جداگانه‌ای ندارد. پس از
تخلیهٔ بایت‌های آمادهٔ بدنه، باقیماندهٔ ناقص کمتر از ۶۵٬۵۵۳ بایت منطقی است.

خروجی فریم‌بندی‌شده سقف مستقل **۲٬۱۶۲٬۷۰۵ بایت**، شامل سرآیندهای تولیدشده، و
حداکثر **۸ MiB هزینهٔ بافرهای نگه‌داری‌شده** دارد. این سقف‌ها به پروفایل حافظه، pool، ظرفیت واقعی
pipe، پلتفرم یا `misc.splice` وابسته نیستند. حداکثر فریم کامل ۶۵٬۵۵۳ و payload
فریم غیر-OPEN حداکثر ۶۵٬۵۳۴ بایت است.

یک فریم دریافتی ممکن است چند callback از نوع Payload تولید کند؛ مرز فریم، مرز
تحویل دادهٔ برنامه نیست. اگر اتصال وسط فریم بسته شود، پیشوند برنامه که قبلاً
تحویل شده پس گرفته نمی‌شود. هر دو گره از همان line عادی قرض‌گرفته‌شده
استفاده می‌کنند و تمام payloadها را تبدیل می‌کنند؛ بنابراین bypass دائمی ندارند.
Pause و Resume، حتی اگر تکراری باشند، با callbackهای پیش‌فرض در هر دو جهت
شفاف منتقل می‌شوند. بایت‌های آمادهٔ پذیرفته‌شده بدون انتظار برای Resume تخلیه
می‌شوند. محافظ تخلیه در هر جهت ترتیب FIFO را هنگام callbackهای بازگشتی حفظ
می‌کند؛ فریم reader دادهٔ ناقص را نگه می‌دارد و صف محدود خروجی، دسته‌های کامل
فریم‌بندی‌شده را پیش از ورودی بازگشتی ارسال می‌کند. گیرنده هر سرآیند کامل در
ابتدای FIFO را بلافاصله پس از پذیرش، حتی برای ورودی بازگشتی، اعتبارسنجی می‌کند؛
فقط حلقهٔ تخلیهٔ بیرونی بایت‌های برنامه را تحویل می‌دهد. دسته‌های فریم‌بندی‌شدهٔ خروجی
پیش از نخستین callback با سقف بایت و هزینهٔ نگه‌داری بررسی می‌شوند.
دادهٔ نامعتبر، عبور از سقف نگه‌داری یا رد شدن به‌دلیل محدودیت ظرفیت صف
فقط همان اتصال را از طریق مالک line می‌بندد. Finish، بافرها و pipeهای صف‌شده را پیش از
ارسال در جهت دور از فرستنده آزاد می‌کند. این پشتیبانی تضمین zero-copy یا
افزایش throughput بدون اندازه‌گیری نیست.

### نکته‌ها و ملاحظات {#notes-and-caveats}

<a id="نکتهها"></a>

- برای استفاده عملی از `Bgp4Client` باید آن را با `Bgp4Server` جفت کنید.
- در پیاده‌سازی فعلی، `password` قابلیت امنیتی محسوب نمی‌شود.
- فیلد طول در قالب شبیه BGP، بایت‌های نشانگر و length را در نظر نمی‌گیرد.
- اولین فریم OPEN فقط وقتی اولین payload در جهت upstream برسد، فرستاده می‌شود.
- upstream `est` و downstream `init` غیرفعال هستند.
- این گره یک تونل جریان بایتی در لایهٔ ۴ است، نه یک تونل بسته‌ای.

## رفتار پیشرفته {#advanced-behavior}

### قالب فریم {#frame-format}

<a id="فرمت-فریم"></a>

همه payload‌های upstream با این ساختار بسته‌بندی می‌شوند:

```text
16-byte marker | 2-byte body length | 1-byte BGP type | body
```

جزئیات فیلد:

| فیلد | مقدار |
| --- | --- |
| نشانگر | شانزده بایت با مقدار `0xff`. |
| طول بدنه | یک `uint16_t` با ترتیب big-endian؛ شامل بایت type به‌علاوه بایت‌های بدنه. |
| BGP type | مقدار `1` برای نخستین فریم OPEN؛ یکی از مقادیر تصادفی `2` تا `5` برای فریم‌های بعدی payload. |
| بدنه | payload تونل‌شده؛ در نخستین فریم upstream شامل بدنه ساختگی OPEN و سپس payload تونل‌شده است. |

مقادیر نوع پشتیبانی‌شده:

| نوع | نام |
| --- | --- |
| `1` | OPEN |
| `2` | UPDATE |
| `3` | NOTIFICATION |
| `4` | KEEPALIVE |
| `5` | ROUTE-REFRESH |

طول فریم با طول استاندارد پیام BGP یکسان نیست. قالب قدیمی شبیه BGP در WaterWall، طول را برابر بایت type به‌علاوه بایت‌های بدنه در نظر می‌گیرد و نشانگر شانزده‌بایتی و فیلد طول دوبایتی را حساب نمی‌کند.

### نخستین payload در upstream {#first-upstream-payload}

<a id="اولین-upstream-payload"></a>

`Bgp4Client` هنگام `init` فریم OPEN مستقلی نمی‌فرستد. در عوض، نخستین payloadِ upstream را با BGP type برابر `1` فریم می‌کند و پیش از بایت‌های برنامه یک بدنه ساختگی OPEN قرار می‌دهد.

فیلدهای ساختگیِ OPEN:

| فیلد | رفتار |
| --- | --- |
| version | همیشه `4`. |
| AS number | یک `uint16_t` تصادفی که هنگام ساخت نمونه تونل تولید می‌شود. |
| hold time | `90` ثانیه. |
| router id | مقدار تصادفی تولیدشده در هنگام ساخته شدن tunnel نمونه. |
| optional parameter length | طول تصادفی بین `3` تا `10` بایت. |
| optional parameter بایت | بایت‌های تصادفی در بازه `0` تا `199`. |

پس از نخستین فریم، `open_sent` برای line تنظیم می‌شود. payload‌های بعدی upstream بدون پیشوند ساختگی OPEN بسته‌بندی می‌شوند و یک type تصادفی غیر از OPEN می‌گیرند.

از آنجا که `Bgp4Server` انتظار دارد داده تونل‌شده برنامه پس از پیشوند OPEN قرار بگیرد، نخستین فریم OPEN باید بعد از بدنه ساختگی OPEN دارای بایت‌های payload باشد.

### تجزیهٔ downstream {#downstream-parsing}

بایت‌های downstream با `splice_frame_reader_t` مشترک روی یک `splice_stream_t` جمع می‌شوند.

`Bgp4Client` برای هر فریم downstream:

1. سرآیند نوزده‌بایتی را جمع می‌کند و نشانگر، طول و type غیر-OPEN را بررسی می‌کند.
2. طول اعلام‌شده‌ای را که هیچ payload برنامه باقی نمی‌گذارد رد می‌کند.
3. اطلاعات فریم را حذف می‌کند و بایت‌های آمادهٔ payload را به ترتیب، بدون انتظار
   برای باقی فریم، تحویل می‌دهد.
4. طول باقی‌ماندهٔ فریم جاری را تا مصرف آخرین بایت نگه می‌دارد و سپس سرآیند
   بعدی را می‌خواند.

سرآیند ناقص یا بخش نرسیدهٔ بدنه کنترل را تا دریافت ورودی بعدی به worker
برمی‌گرداند. عبور از سقف بایت‌های ورودی بازگشتی یا رد شدن هزینهٔ نگه‌داری،
طبق محدودیت‌های زیر line را می‌بندد.

## جزئیات پیاده‌سازی {#implementation-details}

### عملکرد گره {#what-it-does}

<a id="این-نود-چه-میکند"></a>

- هنگام `init` در جهت upstream، برای هر line یک جریان بایتی خواندن و وضعیت مربوط به اولین فریم را مقداردهی اولیه می‌کند.
- در اولین payloadِ upstream، یک بدنه ساختگی BGP OPEN را پیش از بایت‌های برنامه prepend می‌کند.
- payload‌های upstream را در فریم‌های شبیه BGP قرار می‌دهد.
- یک نوع BGP غیر-OPEN تصادفی برای فریم‌های payload upstream بعدی انتخاب می‌کند.
- فریم‌های شبیه BGP در جهت downstream را از یک جریان بایتی بافر می‌خواند.
- اطلاعات فریم downstream را حذف و payload بازیابی‌شده را به تونل قبلی می‌فرستد.
- در صورت دریافت فریم نامعتبر، هر دو جهت را می‌بندد.

`Bgp4Client` یک تونل جریان بایتی معمولی است. socket شبکه یا line بسته‌ای نمی‌سازد و line بسته‌ای‌ای را نیز آزاد نمی‌کند.

### جریان داده {#data-flow}

<a id="جریان-داده"></a>

جهت upstream:

```text
previous node -> Bgp4Client wraps -> next node
```

جهت downstream:

```text
next node -> Bgp4Client unwraps -> previous node
```

`Bgp4Client` انتظار دارد در سمت مقابل `Bgp4Server` قرار گرفته باشد. هر peer ناسازگاری که فریم مورد انتظار را نسازد، خطای پروتکل ایجاد می‌کند.

### رفتار چرخهٔ عمر {#lifecycle-behavior}

<a id="رفتار-lifecycle"></a>
با دریافت `init` در جهت upstream، `Bgp4Client` وضعیت مربوط به line را مقداردهی اولیه می‌کند و پس از ساخت جریان دریافت، `init` را در همان جهت به تونل بعدی می‌فرستد.

با دریافت `est` در جهت downstream، هر اعلان، حتی تکراری، را به تونل قبلی می‌فرستد.

payload‌های upstream را فریم‌بندی و به تونل بعدی می‌فرستد. payload‌های downstream را بافر و تجزیه می‌کند، فریم را باز می‌کند و داده بازیابی‌شده را به تونل قبلی می‌فرستد.

با دریافت `finish` از هر جهت، وضعیت مربوط به line را از بین می‌برد و `finish` را در همان جهت منتشر می‌کند: در upstream به تونل بعدی و در downstream به تونل قبلی.

در صورت دریافت فریم نامعتبر، `Bgp4Client` وضعیت محلی را از بین می‌برد و هر دو جهت را با ترتیب لازم برای یک تونل میانی می‌بندد: ابتدا finish در upstream و سپس finish در downstream.

Pause و Resume اعلان‌های راهنمای تکرارپذیر هستند. callbackهای پیش‌فرض هر
اعلان را فوراً در همان جهت منتقل می‌کنند؛ وضعیت توقف مصرف‌کننده ذخیره نمی‌شود
و ارسال payload به Resume وابسته نیست:

| callback | مقصد ارسال |
| --- | --- |
| upstream pause/resume | next tunnel upstream |
| downstream pause/resume | previous tunnel downstream |
