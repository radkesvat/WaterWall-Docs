# UserController {#usercontroller}

## نمای کلی {#overview}

`UserController` گره‌ای داخلی و پیشرفته است که محدودیت‌های کاربران احراز هویت‌شده را در زنجیره‌های سرویس‌دهنده اعمال می‌کند.

معمولاً لازم نیست این گره را دستی در زنجیره قرار دهید. گره‌های server-side مانند `Socks5Server`، `TrojanServer` و `VlessServer` در حالت authentication مبتنی بر database، خودشان یک `UserController` داخلی می‌سازند. فقط زمانی سراغ تنظیم دستی بروید که tunnel سفارشی شما `lineAddUser()` را فراخوانی می‌کند و lifecycle مربوط به user handle را می‌شناسد.

<span id="پذیرش-از-cache-محلی" />

### پذیرش از کش و نخستین استفاده {#cached-admission-and-first-use}

lineهای مدیریت‌شدهٔ جدید هنگام قطعی‌های عادی از کش معتبر RAM در AuthenticationClient استفاده می‌کنند؛ وضعیت فعال‌بودن، انقضا، سهمیهٔ ترافیک و رزرو محلی اتصال/IP همچنان اعمال می‌شوند. نبود جدول یا مبنای ساعت اولیه، توقف، شکست نهایی پیوستگی حسابداری یا رد صریح اعتبارنامهٔ خود کلاینت، پذیرش تازه را مسدود می‌کند؛ فقط احراز هویت معتبر این رد را پاک می‌کند. lineهای موجود حسابداری، بررسی انقضا هنگام payload، پیمایش اتصال‌های بیکار و آزادسازی رزروها را ادامه می‌دهند. سهمیه‌های محلی در کلاینت‌های قطع‌شده ممکن است در مجموع از سهمیهٔ کل فراتر بروند؛ تغییرات مدیریتی هنگام تازه‌سازی دریافت می‌شوند.

helper حسابداری AuthenticationClient نخستین ترافیک محلی غیرصفر را حتی در حالت آفلاین یا با مدت انقضای صفر ثبت می‌کند و انقضای نسبی را بی‌درنگ آغاز می‌کند. ورود، رزرو، فراخوانی صفر‌بایتی و تغییر مبنای شمارنده‌ها آغاز استفاده نیستند. سرور زودترین مشاهدهٔ تولیدکنندگان را ادغام می‌کند؛ مبدأها، سن سپری‌شده، وضعیت گزارش/ACK و رزروها با ID پایدار، حتی هنگام تغییر اعتبارنامهٔ همان ID، منتقل می‌شوند. ACK، اتصال مجدد و دریافت بدون تغییر، مدت را از نو آغاز نمی‌کنند. ویرایش صریح مدت و تاریخ مطلق، مؤلفه‌های مستقل را دوباره محاسبه می‌کند؛ زودترین مهلت فعال حاکم است. کپی عمومی و JSON این وضعیت اجرایی را ندارند. برآورد زمان میان ماشین‌ها تأخیر انتقال و رانش ساعت دارد؛ معنای تعلیق ساعت monotonic محلی تغییر نمی‌کند. وضعیت فقط در RAM است و بازیابی پس از خرابی یا تحویل نهایی تضمین نمی‌شود.

<span id="کاری-که-انجام-میدهد" />

### کارهایی که انجام می‌دهد {#what-it-does}

`UserController` پس از گره‌ای قرار می‌گیرد که user را احراز هویت کرده و یک `user_handle_t` معتبر روی line گذاشته است. برای هر line مدیریت‌شده، این گره:

- فعال بودن user را بررسی می‌کند
- تاریخ انقضای user را می‌سنجد
- یک connection slot را رزرو می‌کند
- در صورت وجود source IP، یک IP slot را هم رزرو می‌کند
- بایت‌های upstream و downstream را در آمار ترافیک حساب می‌کند
- اگر user غیرفعال، منقضی، حذف یا over-quota شود line‌های فعال او را می‌بندد
- پس از finish شدن line، connection slot و IP slot را آزاد می‌کند

این گره login protocol را parse نمی‌کند و database اصلی کاربران را هم نگه نمی‌دارد. lookup و accounting از طریق یک `AuthenticationClient` موجود انجام می‌شوند.

## جایگاه معمول در زنجیره {#typical-placement}

<span id="اعمال-محدودیت-روی-سرویس-vmess-مدیریتشده" />

### اعمال محدودیت روی سرویس VMess مدیریت‌شده {#enforce-limits-on-a-managed-vmess-service}

سرویس داده و اتصال کنترل authentication را در زنجیره‌های جدا تنظیم کنید.
`VmessServer` با `auth-client-node-name` به `AuthenticationClient` محلی اشاره می‌کند
و در حالت managed، خودش `UserController` را پیش از connector خروجی قرار می‌دهد.

```text
data:    TcpListener -> TlsServer -> VmessServer -> TcpUdpConnector
control: AuthenticationClient -> TlsClient -> TcpConnector
central: TcpListener -> TlsServer -> AuthenticationServer
```
آدرس و پورت `TcpUdpConnector` را به `dest_context->address` و
`dest_context->port` تنظیم کنید تا مقصد درخواست VMess احراز هویت‌شده دنبال شود.
اعتبارنامه‌های کنترل در AuthenticationClient/Server باید برابر باشند و transport
کنترل راه‌دور از TLS با بررسی هویت server استفاده کند.
[نمونه authentication](../03-examples/api/authentication-users.mdx) ساخت و مدیریت
پایگاه داده را توضیح می‌دهد. serverهای SOCKS5، VLESS، Trojan و HTTP proxy هم در
حالت managed این controller را خودکار اضافه می‌کنند؛ تنظیمات authentication همان
server را به کار ببرید و controller دومی اضافه نکنید.

<span id="نمونههای-دستی-برای-node-احراز-هویت-سفارشی" />

### نمونه‌های دستی برای گره‌های احراز هویت سفارشی {#manual-instances-for-custom-authenticating-nodes}

گره قبلی باید با `lineAddUser()` یک user handle معتبر روی line بگذارد تا controller
بتواند محدودیتی اعمال کند. قطعه تنظیمات پایین مخصوص چنین integrationی است و یک
سرویس authentication مستقل نیست. line بدون user handle معتبر، unmanaged عبور
می‌کند.

در حالت `connection`، ‏`WireGuardServer` مسیر داخلی
`PacketsToConnection -> user binding -> UserController` را پیش از `next` تنظیم‌شده
می‌سازد. PTC مالک lineهای داخلی TCP/UDP است و helper مربوط به binding، کاربر
احرازشده را پیش از Init به آن‌ها اضافه می‌کند. محدودیت‌ها روی همین اتصال‌ها و
payload داخلی اعمال می‌شوند؛ packet lineها و carrier رمزگذاری‌شده وارد controller
نمی‌شوند.

برای گره سفارشی که بعد از Init احراز هویت می‌کند، از
[Programmatic Promotion API](#programmatic-promotion-api) استفاده کنید.
`UserController` هر دو مبدأ line را پشتیبانی می‌کند و upload و download را بر همان
اساس تشخیص می‌دهد؛ [Direction Awareness](#direction-awareness) را ببینید.

## نمونهٔ کاربردی ساده {#minimal-practical-example}

این یک قطعهٔ پیکربندی گره است؛ همسایه‌ها و همتاهای ارجاع‌داده‌شده را در همان استقرار تعریف کنید.

این نمونهٔ دستی برای یک گرهٔ احراز هویت سفارشی است و یک زنجیرهٔ کامل احراز هویت نیست. `auth-client` را تعریف کنید و مطمئن شوید گرهٔ احراز هویت، هویت کاربر را طبق توضیحات پایین روی line ثبت می‌کند یا آن را تحت مدیریت قرار می‌دهد. اگر گرهٔ پروتکل خودش کنترل‌کننده را اضافه می‌کند، از جایگاه مستندشدهٔ پراکسی مدیریت‌شده استفاده کنید.

```json
{
  "name": "user-controller",
  "type": "UserController",
  "settings": {
    "auth-client-node-name": "auth-client",
    "payload-mode": "stream",
    "sweep-interval-ms": 1000,
    "verbose": false
  }
}
```

برای پیش‌فرض‌ها و الزامات مشروط، [پیکربندی](#configuration) و برای مثال‌های کامل و محدودیت‌های عملیاتی، [کاربرد و رفع اشکال](#usage-and-troubleshooting) را ببینید.

## پیکربندی {#configuration}

<span id="فیلدهای-اجباری" />

### فیلدهای الزامی {#required-fields}

| فیلد | نوع | توضیح |
|---|---|---|
| `type` | string | باید `UserController` باشد. |
| `settings` | object | باید object غیرخالی باشد. |
| `settings.auth-client-node-name` | string | نام یک `AuthenticationClient` موجود. نباید به خود `UserController` اشاره کند. |
| `settings.payload-mode` | string | برای instance دستی اجباری است: `stream`، `datagram` یا `dest_context->protocol`. سازندهٔ داخلی resolver تغییرناپذیر می‌دهد. |

<span id="تنظیمات-اختیاری" />

### تنظیمات اختیاری {#optional-settings}

| گزینه | پیش‌فرض | توضیح |
|---|---|---|
| `sweep-interval-ms` | `1000` | فاصله بررسی line‌های مدیریت‌شده روی هر worker، حتی در حالت idle؛ باید `>= 1` باشد. |
| `verbose` | `false` | جزئیات بیشتری در warning مربوط به رد یا بسته شدن line‌های مدیریت‌شده ثبت می‌کند. |

## کاربرد و رفع اشکال {#usage-and-troubleshooting}

<span id="نمونه-تنظیمات" />

### نمونهٔ پایه {#basic-example}

```json
{
  "name": "user-controller",
  "type": "UserController",
  "settings": {
    "auth-client-node-name": "auth-client",
    "payload-mode": "stream",
    "sweep-interval-ms": 1000,
    "verbose": false
  },
  "next": "outbound"
}
```

`auth-client` باید نام یک `AuthenticationClient` در همان config باشد. `UserController` تنها به آن گره اشاره می‌کند و auth client تازه‌ای نمی‌سازد.

<span id="limitهایی-که-enforce-میشود" />

### محدودیت‌های اعمال‌شده {#enforced-limits}

`UserController` محدودیت‌های user را از جدول محلی `AuthenticationClient` می‌خواند.

| محدوده | رفتار |
|---|---|
| `enabled` | user غیرفعال نمی‌تواند line managed جدید باز کند و line‌های موجودش با بررسی payload یا زمان‌سنج پیمایش بسته می‌شوند. |
| expiry زمانی | user منقضی‌شده نمی‌تواند line مدیریت‌شده جدید باز کند و line‌های موجود او بسته می‌شوند. |
| `traffic.up`, `traffic.down`, `traffic.total` | بایت واقعی payload به AuthenticationClient داده می‌شود؛ ضریب `traffic-multiplier` یک بار اعمال و مصرف قابل‌کسر به counterها اضافه می‌شود؛ user over-quota رد یا بسته خواهد شد. |
| `connections-out` | حداکثر تعداد line‌های outbound هم‌زمان برای user. |
| `ips` | حداکثر تعداد source IP‌های هم‌زمان برای user. استفاده دوباره از IP قبلاً شمرده‌شده مجاز است. |

این گره `connections-in` یا occupancy زندهٔ `devices` را اعمال نمی‌کند. فیلدهای ذخیره/صادرشده و gaugeهای
تشخیصی دستگاه حفظ می‌شوند ولی reservation زندهٔ دستگاه را محدود نمی‌کنند. پهنای باند محلی را طبق قرارداد بخش بعد اعمال می‌کند.

نبودن یک limit یا مقدار صفر آن یعنی فیلد مربوطه نامحدود است.

<span id="نکتههای-عملیاتی" />

### نکته‌های عملیاتی {#operational-notes}

- جایگذاری دستی نیازمند گره قبلی است که `lineAddUser()` را با user handle معتبر صدا بزند.
- `Socks5Server`، `TrojanServer` و `VlessServer` در authenticated mode این گره را داخلی می‌سازند؛ در آن حالت یک `UserController` دیگر مستقیم بعد از آن‌ها قرار ندهید.
- `UserController` هیچ‌وقت config user مثل password، enabled state یا limit‌ها را نمی‌نویسد.
- live connection/IP counters state محلی پردازش هستند و از طریق helper‌های `AuthenticationClient` نگه‌داری می‌شوند.
- مصرف قابل‌کسر به stats عادی user اضافه می‌شود. ضریب `traffic-multiplier` روی AuthenticationClient تنظیم می‌شود؛ اندازهٔ واقعی payload، bandwidth و سرعت تغییر نمی‌کنند.
- نخستین ترافیک واقعی حتی با هزینهٔ گرد‌شدهٔ صفر، زمان انقضا را شروع می‌کند. باقی‌ماندهٔ کسری هر جهت با ID پایدار در refresh منتقل و در reconnect حفظ می‌شود؛ این state فقط در حافظه است.
- این گره روی normal line با payload از نوع stream یا datagram کار می‌کند و packet tunnel نیست.

## رفتار پیشرفته {#advanced-behavior}

### پهنای باند و مرزبندی payload {#bandwidth-and-payload-framing}

`limit.bandwidth.u` یا `up` و `.d` یا `down` تعداد بایت منطقی واقعی در ثانیه هستند؛ صفر یعنی نامحدود و کل بازهٔ
unsigned 64-bit معتبر است. همهٔ اتصال‌ها، controllerها و workerهای یک user در همان AuthenticationClient سهم مشترک
دارند؛ userها، جهت‌ها و instanceهای دیگر مستقل‌اند. هماهنگی بین ماشین‌ها وجود ندارد. `traffic-multiplier` فقط
مصرف سهمیه را تغییر می‌دهد؛ نرخ، burst، اندازهٔ صف و ساعت را تغییر نمی‌دهد.

ظرفیت burst عادی برای نرخ `R` برابر `max(1, ceil(R / 10))` بایت است؛ تقریباً ۱۰۰ میلی‌ثانیه با حداقل یک بایت در نرخ
خیلی کم. صف‌های واجد شرایط به نوبت‌های محدود FIFO سرویس می‌گیرند؛ datagram کامل هنگام جمع کردن اعتبار نوبت خود را
نگه می‌دارد، بنابراین fairness تضمین تأخیر برابر نیست. stream
می‌تواند به قطعه‌های دقیق تقسیم شود؛ datagram کامل و به ترتیب ارسال می‌شود. datagram خالی جای خود را در FIFO حفظ
می‌کند و نرخ یا سهمیه مصرف نمی‌کند. بستهٔ بزرگ‌تر از burst ابتدا کل اعتبار خود را جمع می‌کند و سپس یک‌جا می‌رود؛
بنابراین burst لحظه‌ای استثنای یک datagram دارد، حتی با نرخ ۱ بایت در ثانیه. idle پیش از فعال شدن head فقط اعتبار
عادی می‌دهد. لغو یا Pause نوبت head را آزاد و اعتبار قابل انتقال را به ظرفیت عادی محدود می‌کند. سقف datagram برابر
۶۵٬۵۳۵ بایت است؛ سقف کوچک‌تر خود پروتکل همچنان برقرار است.

دادهٔ نگه‌داشته‌شده، قطعه‌های آماده و ورودی‌های صف در مجموع دو جهت، این سقف‌های سخت منابع را به‌اشتراک می‌گذارند:

| محدوده | بایت منطقی | هزینهٔ تخصیص | نوبت‌های صف جهت |
| --- | ---: | ---: | ---: |
| هر line مدیریت‌شده | 1 MiB | 2 MiB | 2 |
| هر کاربر در یک AuthenticationClient | 4 MiB | 8 MiB | 1024 |
| هر AuthenticationClient | 64 MiB | 128 MiB | 16384 |

این‌ها سقف منابع‌اند، نه تنظیم نرخ. رد پذیرش stream، line را می‌بندد و صف را بدون هزینه دور می‌ریزد. overflow
در datagram فقط بستهٔ تازهٔ ردشده را حذف می‌کند و FIFO پذیرفته‌شده سالم می‌ماند. رد timer یا continuation لازم،
line را در هر دو حالت می‌بندد. Pause مصرف‌کننده drain و نوبت آن جهت را متوقف می‌کند؛ Resume پیش از اعلان بیرونی
پیشرفت را برقرار می‌کند. برای stream، فشار محلی و فشار مصرف‌کننده مستقل‌اند. backlog محلی datagram به‌تنهایی
Pause/Resume به تولیدکننده نمی‌فرستد، زیرا تولیدکنندهٔ UDP ممکن است هنگام Pause بسته‌ها را پیش از پر شدن صف این گره
حذف کند. datagram هنگام انتظار برای اعتبار نرخ همچنان وارد صف محدود می‌شود؛ Pause/Resume صریح مصرف‌کننده همچنان
اعمال و به تولیدکننده منتقل می‌شود.

نخستین ورود با طول مثبت، پیش از queue شدن، مشاهدهٔ first-use، گزارش و انقضا را حتی offline و با ضریب تخفیف آغاز
می‌کند. صفر بایت آغاز استفاده نیست. هزینه فقط یک بار، با ضریب، درست پیش از واگذاری مالکیت Payload اعمال می‌شود.
آخرین قطعهٔ مجاز که سهمیه را تمام یا رد می‌کند یک بار تحویل و سپس line زنده بسته می‌شود؛ user از قبل over-quota
grant جدید نمی‌گیرد. دادهٔ صف‌شده یا دورریخته‌شده هزینه ندارد. handoff تأیید تحویل socket نیست.

refresh با ID یکسان، حتی تعویض رمز، اعتبار bucket، کسر refill، timestamp و هویت ticket را حفظ می‌کند. تغییر نرخ
ابتدا اعتبار نرخ قدیم را محاسبه و به ظرفیت تازه محدود می‌کند؛ refresh بدون تغییر burst تازه نمی‌دهد. گذار به نامحدود
FIFO را حفظ و گذار از نامحدود به محدود فقط یک burst عادی ایجاد می‌کند. اتصال مدیریت‌شده در outage عادی یا رد
credential کلاینت اجرای cache را ادامه می‌دهد.

instance دستی همیشه به `payload-mode` صریح نیاز دارد، حتی وقتی userهای فعلی نامحدودند:

| مقدار | رفتار payload |
| --- | --- |
| `stream` | بایت‌ها می‌توانند بین چند تحویل تقسیم شوند. |
| `datagram` | هر payload یک datagram کامل باقی می‌ماند. |
| `dest_context->protocol` | در Init از پیشنهاد مقصد انتخاب می‌شود. TCP جریان بایت و UDP دیتاگرام را انتخاب می‌کند. با پیشنهاد هر دو، TCP برگزیده می‌شود. |

در خط معمولی، حالت‌های ثابت تنها پروتکل خود را می‌پذیرند. کنترل‌کننده انتخاب را پیش
از پذیرش و ارسال Init ثبت می‌کند. پیشنهاد نامعتبر همان خط را می‌بندد.

سازندهٔ داخلی بلافاصله پس از ساخت و پیش از prepare،
`usercontrollerSetPayloadModeResolver(controller, owner, resolver)` را bind می‌کند؛ setting و resolver هم‌زمان
پذیرفته نیستند. resolver پرس‌وجوی خالص metadata روی worker مالک است؛ هر منبع mode در Init هر جهت، پیش از
admission یا forwarding، یک بار تعیین و ذخیره می‌شود. promotion دیرهنگام هم از همان mode استفاده می‌کند و تغییر
destination آن را عوض نمی‌کند. SOCKS/Trojan/VLESS نقش TCP و UDP
remote را از state آماده می‌خوانند؛ HTTP همواره stream است. در مسیر داخلی حالت
`connection` در `WireGuardServer`، ‏TCP داخلی از نوع stream و UDP داخلی از نوع datagram
است. packet lineها و carrier رمزگذاری‌شده وارد UserController نمی‌شوند.

### تشخیص جهت {#direction-awareness}

`UserController` جهت شروع هر line را ذخیره می‌کند و با همان اطلاعات ترافیک را به counter‌های upload یا download نسبت
می‌دهد. «upload» ترافیکی است که از user به سمت دیگر مسیر می‌رود و «download» ترافیکی است که به user برمی‌گردد. user همیشه
در سمتی قرار دارد که line از آن آغاز شده است.

| مبدأ line | آغازکننده | حساب payload در upstream | حساب payload در downstream |
|---|---|---|---|
| از `prev` (upstream `Init`) | یک head/prev adapter، مثلاً `UdpStatelessSocket` در ابتدای زنجیره | upload | download |
| از `next` (downstream `Init`) | سازندهٔ یک normal line در سمت `next` | download | upload |

ردیف اول در serverهای احرازشده و مسیر اتصال‌های داخلی `WireGuardServer` به کار
می‌رود. اگر یک normal line از سمت `next` آغاز شود، حساب upload و download برعکس
می‌شود؛ چرخهٔ اعمال quota در هر دو حالت یکسان است.

## جزئیات پیاده‌سازی {#implementation-details}

<span id="جریان-اجرا" />

### جریان اجرا {#runtime-flow}

در `Init` از هر سمت (upstream `Init` برای line‌ای که از `prev` شروع شده، downstream `Init` برای line‌ای که از `next`
شروع شده):

1. line state آماده و جهت شروع line ذخیره می‌شود؛ payload mode تعیین و ذخیره می‌شود و اگر تعیین نشود حتی line ناشناس رد می‌شود
2. user handle فعلی line خوانده می‌شود
3. line‌های anonymous یا دارای handle نامعتبر بدون اعمال محدودیت عبور می‌کنند و می‌توان بعداً آن‌ها را promote کرد
4. line‌های authenticated از طریق `AuthenticationClient` بررسی می‌شوند
5. برای line‌های پذیرفته‌شده connection/IP slot رزرو می‌شود و line در sweep ثبت خواهد شد
6. line ردشده در همان سمتی که آن را شروع کرده finish می‌شود و سمت مقابل راه نمی‌افتد

ورود با طول مثبت ابتدا شواهد نخستین استفاده را ثبت می‌کند. شکل‌دهنده واجدشرایط‌بودن فعلی را بررسی می‌کند، قطعهٔ دقیق جریان بایتی یا دیتاگرام کامل را آماده می‌کند، سپس درست پیش از واگذاری، پهنای باند را به‌طور اتمی اعطا و طول منطقی خام آن را حساب می‌کند. قطعهٔ نهایی که سهمیه را تمام می‌کند یک بار پیش از بستن ارسال می‌شود. بایت‌های نگه‌داشته‌شده یا کنارگذاشته‌شده مصرف سهمیه ندارند؛ بخش پهنای باند و مرزبندی payload را ببینید.

در `Finish` عادی جریان بایتی، کنترل‌کننده روی همان خط، بایت‌های صف را به‌ترتیب به گیرندهٔ باز
تحویل می‌دهد. برای تحویل نهایی منتظر اعتبار پهنای باند، نوبت کاربر یا `Resume` نمی‌ماند. پیش از
تحویل هر قطعهٔ حداکثر ۱۶ کیبی‌بایتی (16 KiB)، مجاز بودن کاربر را بررسی می‌کند و مصرف همان جهت
ارسال یا دریافت را با ضریب تنظیم‌شده ثبت می‌کند. قطعه‌ای که سهمیه را تمام می‌کند یا از آن می‌گذرد
یک بار تحویل داده می‌شود. با پایان سهمیه یا بسته‌شدن گیرنده، ارسال متوقف می‌شود. رزرو اتصال و IP در
همین فراخوانی آزاد می‌شود. هنگام `Finish` دیتاگرام، دیتاگرام‌های صف بلافاصله آزاد می‌شوند.

### API مدیریت برنامه‌ای line بازشده {#programmatic-promotion-api}

بعضی گره‌ها user را پس از باز شدن line authenticate می‌کنند؛ نمونه‌های آن در بخش [جایگاه رایج](#typical-placement) آمده است. `UserController` برای این گره‌ها تابع زیر را در `interface.h` عمومی در دسترس می‌گذارد:

```c
WW_EXPORT user_admission_result_t usercontrollerTunnelTryManageLine(tunnel_t *t, line_t *l);
```

این تابع همان admission مسیر upstream `Init` را در لحظه اجرا می‌کند: همه limit‌ها بررسی می‌شوند و در صورت پذیرش،
connection slot و IP slot رزرو خواهند شد. گره‌ای که از آن استفاده می‌کند باید:

1. pointer مربوط به instance گره `UserController` را نگه دارد؛ با همان الگویی که `Socks5Server` برای ساخت
   `UserController` داخلی خود با `nodeUserControllerGet()` و `createHandle` به کار می‌برد.
2. peer را authenticate و user را با `lineAddUser()` روی line ثبت کند.
3. تابع `usercontrollerTunnelTryManageLine(user_controller_instance, line)` را فراخوانی کند.

مقدارهای برگشتی:

| نتیجه | معنی |
|---|---|
| `kUserAdmissionOk` | line اکنون managed شده، یا از قبل managed بوده و call idempotent بوده، یا user ندارد و به‌صورت unmanaged passthrough رها شده است. ادامه دادن مجاز است. |
| هر مقدار دیگر `kUserAdmission*` | user پذیرفته نشده است؛ مثلاً disabled یا expired است، quota را رد کرده یا به connection/IP limit رسیده است. line همچنان **بدون مدیریت و بدون تغییر** می‌ماند. |

قرارداد استفاده:

- اگر نتیجه non-OK باشد، این تابع نه `Finish` می‌فرستد و نه line state را از بین می‌برد. **رسیدگی به اتصال ردشده بر عهده caller است**؛ caller باید خودش line را ببندد یا کنار بگذارد و نباید آن را پذیرفته‌شده فرض کند. فراخوانی ناموفق هیچ slotی رزرو نمی‌کند، بنابراین تلاش دوباره در آینده امن است.
- تابع را روی worker مالک line فراخوانی کنید؛ این شرط را با `lineIsOnCurrentWorker(l)` بررسی کنید. line باید یک normal line باشد که پیش‌تر از همین instance گره `UserController` عبور کرده است؛ حالت payload ذخیره‌شده در Init حفظ می‌شود. این API برای packet line نیست.
- وقتی line با این روش تحت مدیریت قرار گرفت، traffic accounting، idle sweep و آزاد شدن slot‌ها در پایان رسیدگی به اتصال درست مانند line‌ای عمل می‌کنند که در `Init` پذیرفته شده است؛ caller به teardown اضافه‌ای نیاز ندارد.

نمونه کد درون گره authenticating، پس از handshake موفق روی `line`:

```c
lineAddUser(line, &resolved_handle, username, password);

user_admission_result_t admission = usercontrollerTunnelTryManageLine(ts->user_controller_tunnel, line);
if (admission != kUserAdmissionOk)
{
    // limits exceeded (for example IP limit): reject this peer / close the line here.
    return;
}
// admitted: continue bringing the peer up.
```

### زمان‌سنج پیمایش {#sweep-timer}

هر worker یک sweep timer دوره‌ای دارد. timer، line‌های مدیریت‌شده را بررسی می‌کند تا user غیرفعال، منقضی، حذف‌شده یا over-quota حتی بدون payload جدید هم قطع شود.

sweep registry تا زمان مدیریت شدن line‌ها reference آن‌ها را نگه می‌دارد. با بسته شدن line یا توقف worker، reference‌ها
آزاد می‌شوند.

### پشتیبانی splice {#splice-support}

payloadهای مدیریت‌نشده و payloadهای نامحدودی که بی‌درنگ تحویل می‌شوند در هر دو جهت بدون بررسی محتوا عبور می‌کنند. صف‌های شکل‌دهی، دیتاگرام را کامل نگه می‌دارند و جریان بایتی را با `sbufMoveRangeTo()` تقسیم می‌کنند؛ این رفتار pipe خصوصی را همراه مسیر جایگزین معمولی نیز پوشش می‌دهد. خروجی آماده تا زمان واگذاری یا کنارگذاشتن در بودجه حساب می‌شود. حسابداری از طول منطقی payload، شامل پیشوندهای مقیم حافظه، استفاده می‌کند و نگاشت معکوس upload/download برای lineهای آغازشده از next حفظ می‌شود. در رد ترافیک، بافر هنوز تحت مالکیت گره بازیافت و بایت‌های pipe خصوصی آن کنار گذاشته می‌شوند؛ سپس line طبق چرخهٔ عمر موجود بسته می‌شود.

buffer‌های عادی در مسیر fallback همچنان پذیرفته می‌شوند. splice زمانی فعال می‌شود که build لینوکس از آن پشتیبانی کند، `misc.splice` فعال باشد، زنجیره هیچ گره از نوع packet نداشته باشد و همهٔ گره‌های زنجیره نهایی پس از گسترش و ادغام از splice پشتیبانی کنند. اعلام flag این قابلیت جای این بررسی‌ها را نمی‌گیرد. بهبود کارایی باید با اندازه‌گیری تأیید شود.
