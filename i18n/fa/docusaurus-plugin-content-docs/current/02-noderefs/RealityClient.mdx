# RealityClient


## نمای کلی {#overview}

`RealityClient` تونل سمت کلاینت Reality v2 است. هر line را با یک دست‌دهی واقعی TLS از طریق `TlsClient` داخلی آغاز می‌کند، مواد کلیدی تازه و مستقل هر جهت را از همان دست‌دهی مشتق می‌کند و سپس کنترل اتصال خامِ برقرارشده را به دست می‌گیرد. در TLS 1.3 ابتدا واگذاری احرازشدهٔ درخواست/تأیید/تأیید نهایی انجام می‌شود؛ TLS 1.2 تحویل‌گرفتن فوری اتصال متناسب با پروفایل را حفظ می‌کند.

زمانی از این گره استفاده کنید که بایت‌های ابتدایی روی شبکه باید شبیه یک نشست عادی کلاینت TLS با دامنهٔ بازدیدکننده باشند، در حالی که دادهٔ پذیرفته‌شدهٔ WaterWall با رمز عبور مشترک Reality محافظت می‌شود.

گره در `Init` پروتکل TCP را از گزینه‌های مقصد انتخاب می‌کند. خطی که
TCP عرضه نکند بسته می‌شود.

## جایگاه معمول در زنجیره {#typical-placement}

<a id="جایگاه-رایج"></a>

پراکسی محلی SOCKS5 برای TCP می‌تواند مقصد درخواست را با VLESS منتقل کند و
برای محافظت از انتقال تا سرور از Reality استفاده کند:

```text
Client: TcpListener -> Socks5Server -> VlessClient -> RealityClient -> TcpConnector
Server: TcpListener -> RealityServer -> VlessServer -> TcpConnector (requested target)
                         |
                         +-> TcpConnector (visitor TLS site)
```

TcpListener محلی را به loopback محدود کنید و روی Socks5Server گزینه‌های
`no-auth: true`، ‏`connect: true` و `udp: false` را بگذارید. در [VlessClient](./VlessClient.mdx#dynamic-destination-example)، ‏UUID
یکسان با سرور، ‏`address: "dest_context->address"`، ‏`port: "dest_context->port"`
و `protocol: "tcp"` قرار دهید. خروجی VlessServer محافظت‌شده یک TcpConnector
مبتنی بر زمینهٔ مقصد است. [شاخه‌های سرور](./RealityServer.mdx#typical-placement) را هم ببینید.

سه آدرس نقش‌های جداگانه دارند:

| مقدار | نقش |
| --- | --- |
| مقصد VlessClient | مقصد اصلی انتخاب‌شده توسط برنامهٔ SOCKS5. |
| آدرس TcpConnector نهایی کلاینت | سرور Reality مربوط به WaterWall، مانند `203.0.113.10:443`. |
| `sni` در RealityClient و شاخهٔ بازدیدکننده سرور | سایت واقعی TLS مانند `www.example.com:443`؛ گواهی آن باید برای این SNI معتبر باشد. |

RealityClient خودش کلاینت TLS داخلی را می‌سازد. شاخهٔ بازدیدکننده سرور مستقیماً به
سایت واقعی TLS وصل می‌شود؛ در این سناریو پیش از RealityServer به TlsServer نیاز نیست.

هر دو همتا باید مقدارهای یکسانی برای `password`، `algorithm`، `salt` و `kdf-iterations`، از جمله پیش‌فرض‌هایشان، داشته باشند و رفتار واگذاری آن‌ها سازگار باشد. سایت بازدیدکننده باید با SNI کلاینت و تأیید گواهی سازگار باشد. مدل استتار، ناظری در مسیر را فرض می‌کند که TLS را خاتمه نمی‌دهد، رمز عبور یا کلیدهای ترافیک TLS را ندارد و مقصد پوششی را کنترل نمی‌کند. این استتار در برابر خاتمهٔ TLS دوام نمی‌آورد و همهٔ رفتارهای زمانی یا کاربردی مرورگر را تضمین نمی‌کند؛ پیش از استقرار [محدودیت‌های امنیتی](#security-model-and-limitations) را بخوانید.

## نمونهٔ کاربردی ساده {#minimal-practical-example}

JSON زیر **قطعهٔ گره** است و پیکربندی کامل نیست. رمز نمونه و نام گره‌های انتقال و بازدیدکننده را جایگزین کنید و شاخه‌های شنونده، همتا و برنامه را مطابق توضیحات بالا تکمیل کنید.

### نمونهٔ پایه {#basic-example}

<a id="نمونه-تنظیمات"></a>

JSONهای زیر بخش‌هایی از گره‌های این سناریو هستند، نه تنظیم کامل. شنونده و گره‌های VLESS توضیح‌داده‌شده را اضافه کنید؛ همهٔ نام‌های `next` باید در پیکربندی وجود داشته باشند.

```json
{
  "name": "reality-client",
  "type": "RealityClient",
  "settings": {
    "sni": "www.example.com",
    "verify": true,
    "password": "replace-with-a-strong-secret",
    "algorithm": "chacha20-poly1305"
  },
  "next": "server-tcp"
}
```

با لایهٔ انتقال TCP معمولی:

```json
{
  "name": "server-tcp",
  "type": "TcpConnector",
  "settings": {
    "address": "203.0.113.10",
    "port": 443
  }
}
```

## پیکربندی {#configuration}

### فیلدهای الزامی {#required-fields}

<a id="فیلدهای-اجباری"></a>

| فیلد | نوع | توضیح |
|---|---|---|
| `type` | رشته | باید `RealityClient` باشد. |
| `next` | رشته | گره‌ای که جریان رکوردهای TLS و Reality را به سمت سرور حمل می‌کند. |
| `settings` | شیء | باید شیء غیرخالی باشد. |
| `settings.sni` | رشته | برای `TlsClient` داخلی الزامی است و نام سرور TLS بازدیدکننده را مشخص می‌کند. |
| `settings.password` | رشته | راز مشترک Reality شامل ۱ تا ۳۲ بایت UTF-8؛ باید با سرور یکسان باشد. |

### تنظیمات {#settings}

<a id="تنظیمات"></a>

`RealityClient` همان شیء تنظیمات را به `TlsClient` داخلی می‌دهد؛ بنابراین رفتار گزینه‌های مرتبط با TLS مانند `sni`، `verify`، `ech-sni-trick`، `x25519mlkem768` و `verbose` تابع `TlsClient` است.

| گزینه | پیش‌فرض | توضیح |
|---|---|---|
| `sni` | اجباری | SNI مربوط به دامنهٔ بازدیدکننده که توسط `TlsClient` داخلی استفاده می‌شود. |
| `verify` | `true` | مقدار بولی مربوط به اعتبارسنجی گواهی برای `TlsClient` داخلی. |
| `ech-sni-trick` | تنظیم نشده | رشته غیرخالی اختیاری که به `TlsClient` داخلی پاس داده می‌شود. |
| `x25519mlkem768` | `true` | مقدار بولی برای فعال/غیرفعال کردن گروه ترکیبی TLS در `TlsClient` داخلی. |
| `verbose` | `false` | مقدار بولی برای فعال‌کردن گزارش بیشتر از وضعیت داخلی TLS. |
| `password` | اجباری | راز مشترک شامل ۱ تا ۳۲ بایت UTF-8 برای مشتق‌سازی کلید. |
| `algorithm` | `chacha20-poly1305` | الگوریتم AEAD؛ یکی از `chacha20-poly1305`، `chacha20poly1305`، `aes-gcm`، `aes-256-gcm` یا `aes256gcm`. |
| `method` | مثل `algorithm` | نام جایگزین برای `algorithm`، وقتی `algorithm` وجود نداشته باشد. |
| `salt` | `waterwall-reality` | نمک برای مشتق‌سازی کلید. مقدار صریح باید شامل ۱ تا ۳۲ بایت UTF-8 باشد و با سرور یکی باشد. |
| `kdf-iterations` | `12000` | تعداد دورهای مشتق‌سازی کلید به‌صورت عدد صحیح در بازه `1` تا `1000000`؛ عدد اعشاری رد می‌شود. |

اگر `aes-gcm` انتخاب شود اما بخش رمزنگاری فعال از AES-GCM پشتیبانی نکند، ساخت تونل شکست می‌خورد.

محدودیت اعتبارنامه برحسب بایت UTF-8 سنجیده می‌شود، نه تعداد نویسه، و همان طولی است که به BLAKE2s داده می‌شود. مقدار پیش‌فرض فقط وقتی اعمال می‌شود که کلید اختیاری وجود نداشته باشد؛ کلید موجود با نوع JSON اشتباه خطای راه‌اندازی است. اگر `algorithm` و `method` هر دو وجود داشته باشند، `algorithm` اولویت دارد و نام جایگزین معتبر، مقدار نامعتبر گزینهٔ اصلی را جبران نمی‌کند. کلید‌های ناشناخته همچنان پذیرفته می‌شوند، چون این شیء با `TlsClient` داخلی مشترک است.

## کاربرد و رفع اشکال {#usage-and-troubleshooting}

### نکته‌های عملیاتی {#operational-notes}

<a id="نکتههای-عملیاتی"></a>

- `RealityClient` به `TlsClient` وابسته است و ساخت باید `INCLUDE_TLS_CLIENT=ON` داشته باشد.
- اولین مرحله یک دست‌دهی واقعی کلاینت TLS است، بنابراین `sni`، رفتار اعتبارسنجی گواهی و گزینه‌های اثر انگشت TLS اهمیت دارند.
- `password`، `salt`، `kdf-iterations` و `algorithm` باید با `RealityServer` یکی باشند.
- واگذاری احرازشده TLS 1.3 با ساخت‌های منتشرنشدهٔ قبلی v2 که در پایان دست‌دهی اصلی کنترل اتصال را می‌گرفتند ناسازگار است. هر دو همتا را هم‌زمان ارتقا دهید؛ چیدمان‌های TLS 1.2 تغییر نکرده‌اند، مسیر جایگزین به v1 یا چیدمان قدیمی وجود ندارد و گزینه منسوخ `max-frame-size` در راه‌اندازی رد می‌شود.
- مقدار مشتق‌شده از رمز عبور یک کلید ریشه است، نه کلید رکورد. هر اتصال واقعی TLS، مواد کلیدی مستقل هر جهت را به‌صورت تازه مشتق می‌کند و چرخش رمز عبور نشست‌های آینده را بدون نیاز به پایگاه دادهٔ تشخیص بازپخش نامعتبر می‌کند.
- این گره تونل جریان بایتی است، نه تونل بسته.

## رفتار پیشرفته {#advanced-behavior}

### مدل امنیتی و محدودیت‌ها {#security-model-and-limitations}

<a id="مدل-تهدید-و-محدودیتهای-امنیتی"></a>

مدل تهدید بررسی‌شده برای استتار، ناظری در مسیر است که TLS را خاتمه نمی‌دهد. این ناظر می‌تواند کل جریان بایتی دوطرفه را ثبت و بازسازی کند؛ نوع، نسخه، طول، جهت، ترتیب، زمان‌بندی، nonce/IV قابل‌مشاهده و رفتار بسته‌شدن رکوردهای TLS را بررسی کند؛ بایت‌ها را دست‌کاری کند؛ و با آگاهی از پیاده‌سازی، اتصال‌های آزمایشی برای شناسایی ایجاد کند. فرض می‌شود این ناظر رمز عبور Reality یا رازهای ترافیک TLS واقعی را نمی‌داند، TLS را خاتمه نمی‌دهد و مقصد پوششی پیکربندی‌شده را کنترل نمی‌کند یا با آن تبانی ندارد. همچنین نمی‌تواند دست‌دهی کامل‌شدهٔ TLS را بدون شکست اعتبارسنجی TLS Finished تغییر دهد.

مواد کلیدی هر نشست Reality به مقادیر تصادفی تازهٔ کلاینت و سرور در دست‌دهی واقعی TLS وابسته‌اند. هیچ چالش مستقل سرور Reality برای تضمین تازگی نشست وجود ندارد. بنابراین محافظت در برابر بازپخش میان اتصال‌ها بر این فرض استوار است که ناظر نمی‌تواند هر دو مقدار تصادفی دست‌دهی را پیش‌بینی یا کنترل کند. مقصد پوششی مخرب یا همدستی که عمداً به بازسازی پیوند رمزنگاری یک دست‌دهی قبلاً مشاهده‌شده کمک کند خارج از این مدل است؛ دفاع در برابر چنین مدل قوی‌تری به یک چالش مستقل و احرازشدهٔ سرور نیاز دارد.

استتار Reality برخی ویژگی‌های عمومی رکوردهای TLS را بازسازی می‌کند؛ از جمله شکل و طول رکورد متناسب با مجموعهٔ رمز، nonce/IV صریح، پیام‌های کنترلی، هشدارها و رفتار بسته‌شدن. با این حال، پس از تحویل‌گرفتن اتصال، رکوردها حاوی متن رمز‌شدهٔ Reality-AEAD هستند، نه متن رمز‌شدهٔ واقعی با کلیدهای ترافیک TLS اتصال پوششی. Reality ادعا نمی‌کند که در برابر خاتمهٔ TLS پنهان می‌ماند یا تمام توزیع‌های زمانی، اندازه‌های نوشتن، الگوهای ارسال دسته‌ای یا معناهای کاربردی سطح بالاتر Chrome را بازسازی می‌کند. ناظری که TLS را خاتمه می‌دهد می‌تواند کلیدهای واقعی ترافیک را روی رکوردهای بعدی آزمایش کند و خارج از محدودهٔ استتار بررسی‌شده است.

## جزئیات پیاده‌سازی {#implementation-details}

### جریان اجرا {#runtime-flow}

<a id="جریان-اجرا"></a>

رویداد `Est` لایهٔ انتقال بلافاصله و فقط یک بار ثبت و منتقل می‌شود و به آمادگی TLS یا Reality وابسته نیست. TlsClient داخلی callback جداگانه‌ای برای پایان دست‌دهی ثبت می‌کند؛ فقط همین callback پیوند رمزنگاری اعتبارسنجی‌شدهٔ دست‌دهی را ثبت و تحویل‌گرفتن اتصال را آغاز می‌کند. نه پایان TLS و نه فعال‌شدن Reality، `Est` دیگری تولید نمی‌کند. دادهٔ برنامه می‌تواند پس از Init و پیش از Est لایهٔ انتقال برسد. FIFO ضروری برای دادهٔ زودهنگام و حفظ ترتیب، با احتساب بافر فعالِ نگه‌داشته‌شده در سر صف، به 2 MiB بایت منطقی و 8 MiB هزینهٔ صف محدود است؛ رسیدن به خود سقف مجاز است. پذیرش به‌صورت تراکنشی انجام می‌شود و سرریز، این line قرض‌گرفته‌شده را از طریق مالکش می‌بندد. تکمیل احرازشده، متن آشکار قدیمی‌تر را به‌ترتیب FIFO و بدون انتظار برای Resume مشورتی تخلیه می‌کند. ورودی بازگشتی نمی‌تواند از سر صف فعلی سبقت بگیرد و دادهٔ برنامه پیش از ACK خصوصی می‌ماند. نخستین بافر متن آشکارِ نگه‌داشته‌شده پیش از درخواست Pause از منبع در صف ثبت می‌شود. وقتی فعال‌سازی احرازشده و تکمیل تخلیهٔ FIFO این توقف محلی را رفع کنند، گره فقط در صورتی Resume می‌فرستد که سمت `next` نیز متوقف نباشد. آخرین Pause/Resume دریافتی و توقف محلیِ متن آشکار دو دلیل مستقل برای توقف منبع هستند؛ هیچ‌کدام دیگری را رفع نمی‌کند. وقتی توقف محلی برقرار نیست، اعلان‌های دریافتی، حتی تکراری، منتقل می‌شوند. این اعلان‌ها مانع خروجی آماده نمی‌شوند. رکوردهای ورودی TLS و واگذاری احرازشده در طول انتظار پروتکل همچنان پیش می‌روند. RealityClient پس از تحویل‌گرفتن اتصال فعال می‌ماند، زیرا باید هر رکورد را رمزنگاری و احراز اصالت کند و شمارهٔ توالی آن را مدیریت کند؛ نمی‌توان آن را برای همیشه از مسیر پردازش کنار گذاشت.

در upstream `Init`، `RealityClient`:

1. وضعیت اختصاصی line خود را مقداردهی اولیه می‌کند
2. `Init` را به `TlsClient` داخلی می‌فرستد
3. منتظر تکمیل دست‌دهی TLS داخلی می‌ماند

دادهٔ upstream که پیش از تکمیل تحویل‌گرفتن اتصال برسد در صف قرار می‌گیرد. وقتی `TlsClient` داخلی پایان دست‌دهی را اعلام کند، `RealityClient` در حالی که شیء SSL هنوز موجود است، نسخهٔ مذاکره‌شدهٔ TLS، مجموعهٔ رمز IANA، مقادیر تصادفی کلاینت و سرور و شماره‌های توالی بعدیِ خواندن و نوشتن رکورد TLS 1.2 را ثبت می‌کند. سپس پروفایل رکورد مشترک را انتخاب می‌کند و کلیدها و IVهای مستقلِ کلاینت به سرور و سرور به کلاینت را از پیوند ثبت‌شده و کلید ریشهٔ مشتق‌شده از رمز عبور می‌سازد. مجموعهٔ رمز پشتیبانی‌نشده، تحویل‌گرفتن اتصال را متوقف می‌کند و به یک قالب عمومی جایگزین متوسل نمی‌شود.

TLS 1.2 وضعیت داخلی TLS را فوراً آزاد می‌کند و شمارنده‌ها و قالب‌های موجود رکورد را حفظ می‌کند. TLS 1.3 در عوض BoringSSL را نگه می‌دارد و `HANDOFF_REQUEST` را با شمارهٔ توالی `0` در جهت کلاینت به سرور می‌فرستد. هنگام انتظار برای `HANDOFF_ACK`، کلاینت فقط ACK مورد انتظار را روی یک کپی از هر رکورد کامل آزمایش می‌کند. اگر احراز اصالت شکست بخورد، رکورد اصلی و شمارهٔ توالی دریافت تغییر نمی‌کنند و رکورد برای پردازش عادی `NewSessionTicket`، `KeyUpdate`، دادهٔ کاربردی پوششی یا هشدار پوششی به BoringSSL داده می‌شود. خروجی پروتکلِ تولیدشده توسط BoringSSL پیش از کنترل‌های بعدی به upstream فرستاده می‌شود. پس از احراز ACK با شمارهٔ توالی `0` در جهت سرور به کلاینت، کلاینت BoringSSL را آزاد می‌کند، `HANDOFF_CONFIRM` را با شمارهٔ توالی `1` در جهت کلاینت به سرور می‌فرستد و دادهٔ برنامهٔ صف‌شده را از شمارهٔ توالی `2` آزاد می‌کند، حتی هنگام Pause مشورتی.

پس از تحویل‌گرفتن اتصال:

| جهت | رفتار |
|---|---|
| دادهٔ upstream | متن آشکارِ گره قبلی رمزنگاری می‌شود، در قالب رکوردهای دادهٔ کاربردیِ شبیه TLS قرار می‌گیرد و به `next` می‌رود. |
| دادهٔ downstream | رکوردهای Reality از `next` تجزیه، احراز اصالت و رمزگشایی می‌شوند و به‌صورت متن آشکار به گره قبلی می‌روند. |

پیش از ACK احرازشدهٔ TLS 1.3، بسته‌شدن یا خطای TLS پوششی، پایان محلی یا ورودی بدساخت باعث بسته‌شدن بدون هشدار مصنوعی Reality می‌شود، زیرا همتا ممکن است هنوز TLS واقعی را پردازش کند. پس از واگذاری، قالب‌بندی نامعتبر، شکست احراز اصالت یا معنای نامعتبرِ دادهٔ احرازشده، در صورت قابل‌نوشتن‌بودن سمت شبکه حداکثر یک هشدار کشندهٔ محافظت‌شدهٔ `bad_record_mac` ایجاد می‌کند و سپس هر دو سمت بسته می‌شوند.

خاتمه به نقش هر سمت وابسته است. `Finish` محلیِ upstream وضعیت Reality را تخریب و فقط `next` را پایان می‌دهد؛ هرگز `close_notify` مصنوعی نمی‌سازد. `close_notify` احرازشدهٔ دریافتی از سرور بدون پاسخ مصرف می‌شود؛ سپس RealityClient فوراً وضعیت خود را تخریب و هر دو سمتِ هنوز باز را می‌بندد. منتظر `Finish` بعدی TCP نمی‌ماند، پس همتای احرازشده نمی‌تواند با نفرستادن FIN اتصال را باز نگه دارد. خطای رکورد احرازشده که به‌صورت محلی تشخیص داده شود تنها مسیر تولید هشدار در کلاینت است و پیش از بستن هر دو سمت حداکثر یک `bad_record_mac` کشنده می‌فرستد. هشدار کشندهٔ دریافتی نیز بدون پاسخ، هر دو سمت را فوراً می‌بندد. `Finish` خام لایهٔ انتقال فقط سمت محلیِ باقی‌مانده را می‌بندد. هیچ گزینهٔ اضافی این رفتار را کنترل نمی‌کند.

### قالب رکورد {#record-format}

<a id="قالب-record"></a>

شکل رکوردهای Reality بر اساس مجموعهٔ رمز مذاکره‌شدهٔ TLS پوششی تعیین می‌شود:

| نسخه و مجموعهٔ رمز TLS پوششی | بدنهٔ قابل‌مشاهدهٔ Reality |
|---|---|
| TLS 1.3 | `Reality-AEAD(payload + encrypted inner type 0x17) + 16-byte tag`؛ بدون nonce/پیشوند قابل‌مشاهده؛ طول بدنه `P + 17` و حداکثر `16401` است. |
| TLS 1.2 ChaCha20-Poly1305 | `Reality-AEAD(payload) + 16-byte tag`؛ بدون nonce/پیشوند قابل‌مشاهده؛ طول بدنه `P + 16` و حداکثر `16400` است. |
| TLS 1.2 AES-GCM | `8-byte explicit nonce + Reality ciphertext + 16-byte tag`؛ حداکثر `16408`. |
| TLS 1.2 AES-CBC/SHA-1 | `16-byte random explicit IV + block-aligned opaque body`؛ حداکثر `16432`. |

در GCM، nonceهای صریح در جهت کلاینت به سرور، شمارهٔ توالی بعدیِ نوشتن TLS را که از BoringSSL ثبت شده است با ترتیب big-endian ادامه می‌دهند. در CBC، طول بدنهٔ تفسیرنشده برابر `round_up(payload + TLS MAC length + 1, block size)` است. فیلد دوبایتیِ رمز‌شدهٔ طول payload و پرکنندهٔ صفر، طول خروجی Reality AEAD را با این مقدار برابر می‌کنند؛ هیچ رمزنگاری CBC یا محاسبهٔ TLS CBC MAC انجام نمی‌شود.

هدر شبیه TLS از این مقادیر استفاده می‌کند:

| فیلد | مقدار |
|---|---|
| نوع محتوا | `0x17`، دادهٔ کاربردی |
| نسخه | `0x0303` |
| طول | طول پیشوند قابل‌مشاهدهٔ پروفایل انتخاب‌شده به‌علاوهٔ طول بدنهٔ تفسیرنشده و احرازشده |

هشدارهای کنترلی شکل قابل‌مشاهدهٔ سازگار با BoringSSL دارند:

| نسخه و مجموعهٔ رمز TLS پوششی | هدر و بدنهٔ هشدار |
|---|---|
| TLS 1.3 | نوع بیرونی `0x17`، نسخهٔ `0x0303` و بدنهٔ 19 بایتی؛ متن آشکاری که رمز می‌شود شامل هشدار دوبایتی و نوع داخلی `0x15` است. |
| TLS 1.2 AES-GCM | نوع بیرونی `0x15`، نسخهٔ `0x0303` و بدنهٔ 26 بایتی با nonce صریح هشت‌بایتی. |
| TLS 1.2 AES-CBC/SHA-1 | نوع بیرونی `0x15`، نسخهٔ `0x0303` و بدنهٔ 48 بایتی با IV تازهٔ 16 بایتی و متن رمز‌شدهٔ هم‌تراز با بلوک. |
| TLS 1.2 ChaCha20-Poly1305 | نوع بیرونی `0x15`، نسخهٔ `0x0303` و بدنهٔ 18 بایتی. |

مقادیر معناییِ رمز‌شده، `01 00` برای `close_notify` و `02 14` برای هشدار کشندهٔ `bad_record_mac` هستند. داده‌ها و هشدارها در هر جهت از یک توالی مشترک و سخت‌گیرانه پیروی می‌کنند. دادهٔ همراه، علاوه بر پروفایل و شکل قابل‌مشاهدهٔ رکورد، نوع معنایی رکورد و نسخهٔ مذاکره‌شدهٔ TLS را نیز به آن پیوند می‌دهد و مانع جایگزینی داده با هشدار یا برعکس می‌شود. این‌ها رکوردهای استتار Reality-AEAD هستند، نه پیام خاتمهٔ واقعی TLS یا هشدارهای رمز‌شده با کلید TLS.

کنترل‌های واگذاری TLS 1.3 از نوع بیرونی `0x17`، نسخهٔ قدیمی `0x0303` و نوع داخلیِ رمز‌شدهٔ دادهٔ کاربردی `0x17` استفاده می‌کنند. متن آشکار نسخه‌دار آن‌ها شامل کد کنترل است که باید با نوع AAD مطابقت داشته باشد؛ padding تولیدشده با CSPRNG نیز احراز اصالت می‌شود و مطابق سیاست مشترک طول قابل‌مشاهده انتخاب می‌شود. طول بدنهٔ TLS به‌طور یکنواخت از بازهٔ <code dir="ltr">22..1172</code> بایت نمونه‌برداری می‌شود (<code dir="ltr">3..1153</code> بایت padding)؛ این بازه در مسیرهای پس از دست‌دهیِ تحت پوشش BoringSSL مشاهده شده است. padding به برنامه تحویل داده نمی‌شود. درخواست، ACK، تأیید نهایی، داده و هشدارها از شمارنده‌های عادی هر جهت استفاده می‌کنند و نمی‌توانند جایگزین یکدیگر شوند. گزینه‌ای در JSON برای تنظیم طول کنترل وجود ندارد.

پیشوند قابل‌مشاهده بخشی از استتار احرازشده است، اما nonce مربوط به AEAD نیست. هر جهت شمارهٔ توالی مستقل Reality دارد که از صفر آغاز می‌شود؛ nonce از IV پایهٔ محرمانهٔ 12 بایتی همان جهت ساخته می‌شود و شمارهٔ توالی Reality با ترتیب big-endian در هشت بایت پایانی آن XOR می‌شود. شمارهٔ توالیِ نمای TLS 1.2 GCM جداگانه رهگیری می‌شود.

دادهٔ همراه، شناسهٔ پروفایل، حوزهٔ رکورد v2، جهت، شمارهٔ توالی Reality، شناسهٔ نشست، هدر TLS، طول پیشوند قابل‌مشاهده و خود پیشوند را به رکورد پیوند می‌دهد. سمت دریافت فقط رکوردی با شمارهٔ توالی دقیقِ بعدی Reality را احراز اصالت می‌کند. بنابراین تکرار، حذف، تغییر ترتیب، بازتاب یا انتقال رکورد میان پروفایل‌ها یا اتصال‌ها باعث شکست احراز اصالت می‌شود. اتصال پیش از سرریز شمارنده‌ها بسته می‌شود.

### نکته‌های بافر و چرخهٔ عمر {#buffer-and-lifecycle-notes}

<a id="نکتههای-buffer-و-lifecycle"></a>

- `RealityClient` به‌ازای هر line یک وضعیت دارد که شامل تجزیه‌گر مربوط به رکورد‌های downstream، داده‌های upstream صف‌شده پیش از دست‌دهی، شناسهٔ نشست، کلید‌ها و IV‌های هر جهت و شمارنده‌های ارسال و دریافت است.
- این گره line معمولی را نه ایجاد می‌کند و نه از بین می‌برد؛ هنگام `Finish` یا زمانی که به‌دلیل خطای Reality هر دو جهت را می‌بندد، فقط وضعیت خودش را پاک می‌کند.
- پیش از فرستادن هشدار کشندهٔ تولیدشده به‌صورت محلی، وضعیت وارد حالت نهایی می‌شود؛ callback‌های بازگشتی مربوط به داده/Pause/Resume/Est بازتاب داده نمی‌شوند، مسیر ارسال مالک پاک‌سازی وضعیت در صورت مرگ line است و پاک‌سازی اضافه متوقف می‌شود.
- این گره `21` بایت فضای خالی لازم در ابتدای بافر (left padding) اعلام می‌کند: `5` بایت برای هدر و در بدترین حالت `16` بایت برای IV صریح CBC.
- بافر خالی داده بدون فرستادن رکورد Reality به مخزن برگردانده می‌شود.
- حداکثر متن آشکار هر قطعه به‌صورت خودکار برابر محدودیت بومی TLS یعنی `16384` بایت است. callback‌های بزرگ‌تر فوراً تقسیم می‌شوند؛ `32768` بایت دقیقاً دو رکورد کامل می‌سازد و buffering بین callback‌ها وجود ندارد.
