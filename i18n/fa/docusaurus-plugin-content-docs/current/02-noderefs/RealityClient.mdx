# RealityClient

`RealityClient` tunnel سمت client برای Reality در واتروال است. این نود هر line را با یک TLS handshake واقعی از طریق `TlsClient` داخلی آغاز می‌کند؛ پس از کامل شدن handshake، کنترل connection خام را تحویل می‌گیرد و payloadهای واتروال را در recordهایی شبیه TLS application-data و محافظت‌شده با AEAD حمل می‌کند.

زمانی از این نود استفاده کنید که بایت‌های ابتدایی روی wire باید برای یک visitor domain شبیه نشست عادی TLS client به نظر برسند، در حالی که payload اصلی واتروال با secret مشترک Reality محافظت می‌شود.

## جایگاه رایج

```text
TcpListener -> RealityClient -> TcpConnector
```

نود `next` مسیر transport به سمت `RealityServer` را فراهم می‌کند. `RealityClient` خودش socket مقصد را باز نمی‌کند؛ بنابراین یک connector یا transport دیگر باید پس از آن قرار بگیرد.

## نمونه تنظیمات

```json
{
  "name": "reality-client",
  "type": "RealityClient",
  "settings": {
    "sni": "www.example.com",
    "verify": true,
    "password": "replace-with-a-strong-secret",
    "algorithm": "chacha20-poly1305"
  },
  "next": "server-tcp"
}
```

با transport TCP معمولی:

```json
{
  "name": "server-tcp",
  "type": "TcpConnector",
  "settings": {
    "address": "203.0.113.10",
    "port": 443
  }
}
```

## فیلدهای اجباری

| فیلد | نوع | توضیح |
|---|---|---|
| `type` | string | باید `RealityClient` باشد. |
| `next` | string | نودی که stream مربوط به TLS و Reality recordها را به سمت server حمل می‌کند. |
| `settings` | object | باید object غیرخالی باشد. |
| `settings.sni` | string | برای `TlsClient` داخلی الزامی است و نام TLS server مربوط به visitor را مشخص می‌کند. |
| `settings.password` | string | secret مشترک و غیرخالی Reality؛ باید با server یکسان باشد. |

## تنظیمات

`RealityClient` همان object تنظیمات را به `TlsClient` داخلی می‌دهد؛ بنابراین رفتار گزینه‌های مرتبط با TLS مانند `sni`، `verify`، `ech-sni-trick` و `x25519mlkem768` تابع `TlsClient` است.

| گزینه | پیش‌فرض | توضیح |
|---|---|---|
| `sni` | اجباری | SNI مربوط به visitor domain که توسط `TlsClient` داخلی استفاده می‌شود. |
| `verify` | `true` | تنظیم certificate verification برای `TlsClient` داخلی. |
| `ech-sni-trick` | تنظیم نشده | گزینه اختیاری TLS client trick که به `TlsClient` داخلی پاس داده می‌شود. |
| `x25519mlkem768` | پیش‌فرض داخلی TLS | فعال/غیرفعال کردن hybrid TLS group در `TlsClient` داخلی در صورت پشتیبانی. |
| `password` | اجباری | secret مشترک برای key derivation. |
| `algorithm` | `chacha20-poly1305` | یکی از `chacha20-poly1305`، `chacha20poly1305`، `aes-gcm`، `aes-256-gcm` یا `aes256gcm`. |
| `method` | مثل `algorithm` | alias برای `algorithm`، وقتی `algorithm` وجود نداشته باشد. |
| `salt` | `waterwall-reality` | salt برای key derivation. باید با server یکی باشد. |
| `kdf-iterations` | `12000` | تعداد roundهای key derivation. بازه معتبر `1` تا `1000000`. |
| `max-frame-size` | `16356` | حداکثر plaintext هر Reality record. بازه معتبر `1` تا `16356`. payload بزرگ‌تر split می‌شود. |

اگر `aes-gcm` انتخاب شود اما crypto backend فعال از AES-GCM پشتیبانی نکند، ساخت tunnel شکست می‌خورد.

## جریان اجرا

در upstream `Init`، `RealityClient`:

1. per-line state خودش را مقداردهی اولیه می‌کند
2. `Init` را به `TlsClient` داخلی می‌فرستد
3. منتظر کامل شدن TLS handshake داخلی می‌ماند

payloadهای upstream که پیش از takeover مربوط به TLS برسند در صف می‌مانند. وقتی `TlsClient` داخلی downstream `Est` را اعلام کند، `RealityClient` state داخلی TLS را بدون بستن connection از بین می‌برد، line را آماده Reality علامت می‌زند، payloadهای صف‌شده را به‌صورت recordهای رمزنگاری‌شده Reality می‌فرستد و سپس downstream `Est` را به نود قبلی اعلام می‌کند.

بعد از takeover:

| جهت | رفتار |
|---|---|
| Upstream payload | cleartext نود قبلی رمزنگاری و در قالب recordهای شبیه TLS application-data به `next` فرستاده می‌شود. |
| Downstream payload | recordهای Reality از `next` parse، احراز اصالت و رمزگشایی می‌شوند و cleartext به نود قبلی می‌رود. |

اگر payload جهت downstream پیش از TLS takeover برسد، record نامعتبر باشد یا احراز اصالت شکست بخورد، هر دو جهت line بسته می‌شوند.

## قالب Record

Reality recordها شکل TLS application-data record دارند:

```text
TLS record header (5 bytes)
nonce             (12 bytes)
ciphertext
AEAD tag          (16 bytes)
```

TLS-like header از این مقادیر استفاده می‌کند:

| فیلد | مقدار |
|---|---|
| Content type | `0x17` application data |
| Version | `0x0303` |
| Length | `12-byte nonce + ciphertext + 16-byte tag` |

TLS record header به‌عنوان associated data مربوط به AEAD احراز اصالت می‌شود. nonce هر record به‌طور مستقل تصادفی است.

## نکته‌های Buffer و Lifecycle

- `RealityClient` به‌ازای هر line یک state دارد که شامل parser مربوط به recordهای downstream، payloadهای upstream صف‌شده پیش از handshake و flag مربوط به TLS-ready است.
- این نود line معمولی را نه ایجاد می‌کند و نه از بین می‌برد؛ هنگام `Finish` یا زمانی که به‌دلیل خطای Reality هر دو جهت را می‌بندد، فقط state خودش را پاک می‌کند.
- این نود `17` بایت required left padding اعلام می‌کند: `5` بایت برای TLS-like record header و `12` بایت برای پیشوند nonce.
- buffer خالی payload بدون فرستادن Reality record به pool برگردانده می‌شود.
- payloadهایی بزرگ‌تر از `max-frame-size` به چند record رمزنگاری‌شده تقسیم می‌شوند.

## نکته‌های عملیاتی

- `RealityClient` به `TlsClient` وابسته است و build باید `INCLUDE_TLS_CLIENT=ON` داشته باشد.
- اولین مرحله یک TLS client handshake واقعی است، بنابراین `sni`، رفتار certificate verification و گزینه‌های TLS fingerprinting اهمیت دارند.
- `password`، `salt`، `kdf-iterations` و `algorithm` باید با `RealityServer` یکی باشند.
- این نود یک stream tunnel است، نه packet tunnel.

## مشخصات نود

| ویژگی | مقدار |
|---|---|
| جایگاه | Middle stream tunnel |
| نیاز به `next` | بله |
| Previous layer | Anything |
| Next layer | Anything |
| Per-line state | دارد |
| ایجاد line | خیر |
| از بین بردن line | خیر |
| Required left padding | `17` |
