# Socks5Client

`Socks5Client` یک tunnel میانی stream است که سمت client پروتکل SOCKS5 را پیاده
می‌کند. این node از transport بعدی برای اتصال به SOCKS proxy استفاده می‌کند،
method negotiation را انجام می‌دهد، در صورت نیاز با username/password احراز هویت
می‌شود و سپس برای مقصد نهایی تنظیم‌شده درخواست `CONNECT` یا `UDP ASSOCIATE`
می‌فرستد.

مقصد نوشته‌شده در تنظیمات `Socks5Client` همان مقصد نهایی داخل درخواست SOCKS
است. آدرس خود SOCKS proxy باید در connector بعدی تنظیم شود؛ معمولاً
`TcpConnector` برای TCP یا `TcpUdpConnector` در حالتی که relay مربوط به UDP لازم
است.

## جایگاه رایج

برای TCP:

```text
TcpListener -> Socks5Client -> TcpConnector
```

برای TCP و UDP از یک SOCKS server:

```text
TcpUdpListener -> Socks5Client -> TcpUdpConnector
```

در چیدمان دوم، connector باید برای control connection از TCP استفاده کند و
relay address برگشتی از `UDP ASSOCIATE` را از طریق UDP در دسترس قرار دهد.

## نمونه پایه

```json
{
  "name": "socks-client",
  "type": "Socks5Client",
  "settings": {
    "address": "dest_context->address",
    "port": "dest_context->port",
    "protocol": "tcp",
    "user": "alice",
    "pass": "secret",
    "dns-behaviour": {"resolve": false},
    "verbose": false
  },
  "next": "proxy-transport"
}
```

`proxy-transport` باید node‌ای باشد که به SOCKS5 server متصل می‌شود؛ برای مثال یک
`TcpConnector` که آدرس و port مربوط به proxy در آن تنظیم شده است.

## پروتکل پویا

اگر line ورودی از قبل protocol مقصد را مشخص کرده است، می‌توانید از
`dest_context->protocol` استفاده کنید تا client همان protocol را دنبال کند.

```json
{
  "name": "socks-client",
  "type": "Socks5Client",
  "settings": {
    "address": "dest_context->address",
    "port": "dest_context->port",
    "protocol": "dest_context->protocol"
  },
  "next": "proxy-transport"
}
```

اگر destination context دقیقاً TCP باشد، `CONNECT` فرستاده می‌شود و اگر دقیقاً
UDP باشد، `UDP ASSOCIATE` انجام خواهد شد. در نبود flag مناسب، در حالت مبهم یا
برای protocolی غیر از TCP/UDP، یک warning ثبت می‌شود و node به TCP برمی‌گردد.

## مقصد ثابت

اگر می‌خواهید مقصد SOCKS را به‌صورت ثابت در JSON بنویسید:

```json
{
  "name": "socks-client",
  "type": "Socks5Client",
  "settings": {
    "address": "example.com",
    "port": 443,
    "protocol": "tcp",
    "dns-behaviour": {"resolve": true, "strategy": "prefer-ipv4"}
  },
  "next": "proxy-transport"
}
```

با فعال بودن resolve محلی domain، `DomainResolver` داخلی پیش از فرستادن درخواست
SOCKS، `example.com` را resolve می‌کند. اگر پاسخ IPv4 موجود باشد، همان آدرس در
درخواست SOCKS قرار می‌گیرد؛ در غیر این صورت fallback مطابق strategy انتخاب‌شده
انجام می‌شود.

## فیلدهای اجباری

| فیلد | نوع | توضیح |
| --- | --- | --- |
| `settings` | object | اجباری است و نباید خالی باشد. |
| `settings.address` / `settings.target-address` / `settings.target` | string | آدرس مقصد نهایی SOCKS. می‌تواند IP ثابت، domain با طول ۱ تا ۲۵۵ بایت، `dest_context->address` یا `line->dest_ctx->address` باشد. domain طولانی‌تر هنگام ساخت node رد می‌شود. |
| `settings.port` | number یا string | پورت مقصد نهایی. عدد `1` تا `65535`، یا `dest_context->port` / `line->dest_ctx->port`. |
| `next` | string | اجباری است و به transport سمت SOCKS proxy اشاره می‌کند. |

## فیلدهای اختیاری

| فیلد | پیش‌فرض | توضیح |
| --- | --- | --- |
| `settings.protocol` / `settings.proto` | `tcp` | مقدارهای مجاز: `tcp`, `connect`, `udp`, `udp-associate`, `dest_context->protocol`, `line->dest_ctx->protocol`. |
| `settings.user` / `settings.username` | تنظیم نشده | نام کاربری SOCKS5. باید همراه `pass` / `password` بیاید. |
| `settings.pass` / `settings.password` | تنظیم نشده | رمز SOCKS5. باید همراه `user` / `username` بیاید. |
| `settings.dns-behaviour` | resolve محلی غیرفعال | کنترل lookup محلی، انتخاب آدرس و انتقال DNS؛ بخش رفتار DNS را ببینید. |
| `settings.verbose` | `false` | log‌های debug بیشتری فعال می‌کند. |

username و password باید غیرخالی باشند و هر کدام حداکثر ۲۵۵ بایت طول داشته
باشند. اگر فقط یکی از آن‌ها تنظیم شود، ساخت node شکست می‌خورد.

## رفتار DNS

resolve کردن نام دامنه یعنی پیدا کردن آدرس IP آن. `Socks5Client` می‌تواند نام دامنهٔ
مقصد نهایی را در درخواست SOCKS5 بفرستد، یا آن را محلی resolve کند و IP انتخاب‌شده
را بفرستد. resolve محلی فقط برای نام دامنهٔ resolve‌نشده و در صورت فعال بودن انجام
می‌شود. IP عددی یا مقصدی که از قبل resolve شده باشد به lookup نیاز ندارد.

این تنظیم مربوط به مقصد نهایی است که از طریق proxy به آن می‌رسید. connector بعدی
آدرس سرور proxy را انتخاب می‌کند و تنظیمات DNS مستقل خودش را دارد. با حذف
`dns-behaviour`، resolve محلی غیرفعال است.

این lookup را با `settings.dns-behaviour` تنظیم کنید:

```json
{"dns-behaviour": {"resolve": true, "mode": "direct", "strategy": "prefer-ipv4", "servers": ["203.0.113.53:53"]}}
```

این IP نمونهٔ مستندات است؛ آن را با سرور خود جایگزین کنید.

| فیلد | معنی |
| --- | --- |
| `resolve` | boolean اجباری: `true` اجازهٔ lookup نام دامنهٔ resolve‌نشده را می‌دهد و `false`، lookup محلی را غیرفعال می‌کند. |
| `mode` | `native` (پیش‌فرض هنگام فعال بودن)، `direct` یا `chain`. |
| `strategy` | یکی از `core-settings`، `accept-dns-returned-order`، `prefer-ipv4`، `prefer-ipv6`، `only-ipv4` یا `only-ipv6`؛ حذف آن اولویت پیش‌فرض آدرس مصرف‌کننده را به کار می‌برد. |
| `servers` | ۱ تا ۳۲ endpoint عددی IP، IP:port یا [IPv6]:port؛ در direct/chain اجباری و در native ممنوع. |
| `dns-next` | نام غیرخالی ورودی DNS، فقط در chain. |

`native` از تنظیمات DNS در core و resolver مشترک worker استفاده می‌کند. هنگام
فعال بودن resolve محلی، این حالت پیش‌فرض انتقال DNS است.

`direct` درخواست‌های DNS را از طریق یک connector خصوصی TCP/UDP در WaterWall به
سرورهایی که مشخص کرده‌اید می‌فرستد.

`chain` درخواست‌های DNS را از chain انتخابی می‌فرستد. برای محافظت از آن‌ها، مسیری
رمزنگاری‌شده مانند VPN خود را انتخاب کنید؛ این حالت به‌تنهایی درخواست‌ها را
رمزنگاری نمی‌کند. مسیر DNS باید هم درخواست‌های UDP و هم fallback روی TCP را حمل
کند. خطای route یا lookup باعث تغییر به DNS بومی یا حالت دیگر نمی‌شود.

در حالت `chain`، با حذف `dns-next` درخواست‌های DNS از همین proxy client و transport
بعد از آن عبور می‌کنند. برای مسیر دیگر، نام یک شاخهٔ DNS جدا را در `dns-next`
بگذارید که از قبل به node دیگری تعلق نداشته باشد. برای استفاده از همین node، فیلد
را ننویسید؛ نام خود node را در آن قرار ندهید.

شکل غیرفعال دقیقاً `"dns-behaviour": {"resolve": false}` است و فیلدهای `mode`، `strategy`، `servers` و `dns-next` را رد می‌کند. object تهی، null، نوع غیرobject، فیلد ناشناخته و strategy عددی رد می‌شوند. نام strategy باید یکی از رشته‌های canonical بالا با حروف کوچک باشد. `core-settings` فقط اولویت آدرس را انتخاب می‌کند و انتقال DNS را تغییر نمی‌دهد.

با `resolve: false`، درخواست proxy در صورت پشتیبانی پروتکل نام دامنه را نگه می‌دارد. connector بعدی مقصد مستقل proxy یا VPN و سیاست DNS خودش را دارد؛ برای bootstrap از IP عددی یا مسیر مستقل استفاده کنید.

مثال‌های native، direct و chain محافظت‌شده و محدودیت گزینه‌های core را در [DomainResolver](./DomainResolver.mdx) ببینید. این سیاست فقط lookupهای متعلق به همین node را کنترل می‌کند؛ fake DNS در PTC، DNS سیستم در TunDevice و همهٔ منابع DNS برنامه را تغییر نمی‌دهد.

## جهت مقداردهی اولیه

line‌های برنامه از طریق `Init` در جهت upstream وارد `Socks5Client` می‌شوند.
`Init` در جهت downstream برای همه نقش‌های line، شامل application، control و relay
در حالت UDP، غیرفعال است؛ دریافت آن یک پیام fatal ثبت می‌کند و با
`abortProgramNow(1)` فرایند را خاتمه می‌دهد. callback‌های downstream برای `Est`
و payload همچنان برای پاسخ‌های proxy و داده‌های relay پشتیبانی می‌شوند.

## رفتار TCP

در حالت TCP، lifecycle به این ترتیب است:

1. upstream `Init`، line state مربوط به `Socks5Client` را مقداردهی اولیه می‌کند و `Init` را به transport بعدی می‌فرستد.
2. transport بعدی اتصال proxy را برقرار می‌کند و `Est` بلافاصله، پیش از مذاکرهٔ SOCKS، به node قبلی می‌رسد.
3. `Socks5Client` greeting مربوط به method‌های SOCKS5 را یک بار ارسال می‌کند. `Est`های تکراری transport به برنامه منتقل می‌شوند، بدون ارسال دوبارهٔ greeting.
4. اگر credential تنظیم شده باشد و server روش username/password را انتخاب کند، درخواست احراز هویت فرستاده می‌شود.
5. node برای مقصد تنظیم‌شده دستور `CONNECT` می‌فرستد.
6. پاسخ موفق، ارسال دادهٔ برنامه را آزاد می‌کند و `Est` دوباره فرستاده نمی‌شود.
7. payload‌های upstream که در انتظار بودند، بدون انتظار برای Resume و با حفظ ترتیب FIFO روی اتصال proxy فرستاده می‌شوند.

در TCP، توقف ناشی از صف دادهٔ برنامه یا تخلیهٔ آن با آخرین Pause/Resume سمت بعدی ترکیب می‌شود.
Resume فقط پس از رفع هر دو علت به منبع می‌رسد؛ Resume مسیر transport صف منتظر مذاکره را آزاد نمی‌کند
و تخلیهٔ صف نیز Pause مسیر transport را پاک نمی‌کند. وقتی توقف محلی وجود ندارد، اعلان‌های تکراری transport عبور می‌کنند.
greeting و خروجی آمادهٔ برنامه یا پاسخ منتظر Resume نمی‌مانند. Pause دریافت، حتی هنگام مذاکره
به adapter بعدی می‌رسد؛ فرستندهٔ آن باید خودش Resume یا بستن اتصال را ترتیب دهد.

پس از موفقیت مذاکرهٔ TCP، تخلیهٔ تمام ورودی و خروجی نگه‌داری‌شده و رفع توقف محلی و فشار transport،
client وضعیت line خود را نابود می‌کند و برای آن line به‌طور دائمی bypass می‌شود.
callbackهای بعدی مستقیماً بین همسایه‌ها عبور می‌کنند. callback در حال اجرا پیش از استفاده از
state که ممکن است در تبادل بازگشتی نابود شده باشد، فعال بودن node را بررسی می‌کند.

اگر پیش از موفق شدن درخواست SOCKS، دادهٔ upstream برسد، در صفی با محدودیت
۲ MiB دادهٔ منطقی و ۸ MiB هزینهٔ حافظهٔ صف نگه داشته می‌شود. حافظهٔ صف فقط هنگام اولین استفاده تخصیص
می‌یابد. محدودیت ۴٬۰۹۶ بایت فقط برای metadata ناقص پاسخ است؛ یک پاسخ کامل
می‌تواند همراه با بدنهٔ بزرگ‌تر برنامه دریافت شود. پردازش بازگشتی پاسخ‌ها
ترتیبی است و دادهٔ پاسخِ نگه‌داری‌شده بودجهٔ مشترک ۲ MiB دادهٔ منطقی و ۸ MiB هزینهٔ حافظهٔ صف در جهت
پایین‌دست دارد. این صف پس از ورودی قدیمی‌تر پاسخ تخلیه می‌شود، حتی در حضور Pause؛
ارسال مستقیم TCP همچنان همگام است. ورودی خالی TCP از پراکسی نادیده گرفته می‌شود و
باقی‌ماندهٔ TCP روی control line مربوط به UDP پس از برقراری ارتباط دور ریخته می‌شود.
line‌های UDP application و relay برای stream مربوط به handshake حافظه تخصیص نمی‌دهند.

اگر proxy همه method‌ها را رد کند، authentication شکست بخورد، پاسخ command
نامعتبر باشد یا command با خطا تمام شود، tunnel آن line را می‌بندد.

## رفتار UDP

در حالت UDP، line اصلی همان مسیر application است و `Socks5Client` دو line داخلی می‌سازد:

| line داخلی | کاربرد |
| --- | --- |
| UDP control line | یک line TCP که به SOCKS proxy وصل می‌شود و `UDP ASSOCIATE` را با مقصد `0.0.0.0:0` می‌فرستد. |
| UDP relay line | یک line UDP که به relay address برگشتی از proxy وصل می‌شود. |

relay line از `BND.ADDR` و `BND.PORT` پاسخ موفق `UDP ASSOCIATE` استفاده می‌کند.
این line، port کنترل TCP را دوباره به‌کار نمی‌برد و endpoint مذاکره‌شده را با
address و port ثابت SOCKS proxy در connector بعدی جایگزین نمی‌کند. بنابراین server
می‌تواند یک relay port موقت و اختصاصی برگرداند؛ policy مربوط به firewall و NAT
باید endpoint برگشتی را اجازه دهد، نه فقط port کنترل TCP را.

این authority مذاکره‌شده از پاک‌سازی metadata مربوط به protocol‌های مشاهده‌شده
توسط `Router` یا sniffer عبور می‌کند. adapter خروجی UDP آن را دقیقاً یک‌بار مصرف
می‌کند و سپس marker داخلی را پاک می‌کند تا روی routing نامرتبط بعدی اثر نگذارد.

Est مربوط به transport کنترل، یک بار به line برنامه منتقل می‌شود. ارسال datagram همچنان
تا آماده شدن control association و relay line منتظر می‌ماند؛ صف آن به ۲ MiB و ۱۰۲۴ buffer محدود است. سپس `Socks5Client` یک header مربوط به SOCKS5 UDP و شامل مقصد نهایی
به ابتدای هر datagram اضافه می‌کند و آن را از relay line می‌فرستد. پاسخ‌های
relay اعتبارسنجی می‌شوند، header از آن‌ها برداشته می‌شود و فقط payload به node
قبلی برمی‌گردد.

fragment‌های SOCKS5 UDP دوباره سرهم نمی‌شوند؛ datagram‌هایی که `FRAG != 0`
دارند برای احتیاط نادیده گرفته می‌شوند.

این مقدار padding اجازه می‌دهد header مربوط به SOCKS5 UDP بدون نقض قرارداد
buffer به ابتدای datagram افزوده شود. اگر buffer ورودی باز هم فضای کافی در سمت
چپ نداشته باشد، tunnel یک buffer جایگزین می‌گیرد و پیش از افزودن header، payload
را در آن کپی می‌کند.

## اشتباه‌های رایج

- آدرس proxy را داخل `settings.address` ننویسید؛ این فیلد مقصد نهایی داخل request SOCKS است.
- حالت UDP را با connector فقط-TCP به کار نبرید؛ این حالت هم control line از نوع TCP و هم relay line از نوع UDP می‌خواهد.
- `dns-behaviour.strategy` روی IP literal اثری ندارد.
- وقتی از `dest_context->address` استفاده می‌کنید، `port` همچنان جداگانه لازم است.

## پشتیبانی از splice

`Socks5Client` از payload‌های TCP مبتنی بر splice پشتیبانی می‌کند. هنگام مذاکرهٔ
روش احراز هویت، اعتبارسنجی و پاسخ command، کل هر ورودی با `sbufEnsureOrdinary()`
پیش از ورود به parser یا صف ورودی بازگشتی به حافظهٔ عادی تبدیل می‌شود. پس از
مذاکره، payload‌های TCP و ورودی‌های لازم در صف FIFO می‌توانند buffer اصلی را حفظ
کنند. محدودیت handshake ناقص از محدودیت backlog برنامه جدا می‌ماند.

line‌های UDP application، TCP control و UDP relay در هر دو جهت خواندن عادی را برای
تمام عمر خود درخواست می‌کنند. آماده‌سازی مقصد UDP این ترجیح را پیش از نگه‌داری
ورودی توسط DNS محلی تنظیم می‌کند. این ترجیح تضمین نوع buffer نیست و به line‌های
مرتبط منتقل نمی‌شود؛ هر datagram همچنان پیش از نگه‌داری، خواندن header یا
قالب‌بندی کاملاً عادی می‌شود. ورودی عادی بدون تغییر عبور می‌کند. line‌های TCP
CONNECT ترجیح خواندن عادی را درخواست نمی‌کنند.

`DomainResolver` داخلی قابلیت splice را حفظ می‌کند. فعال‌شدن واقعی به chain
نهاییِ واجد شرایط و `misc.splice` وابسته است؛ وجود TLS یا node مسدودکنندهٔ دیگر
splice را برای کل chain payload غیرفعال می‌کند.

## متادیتای node {#متادیتای-نود}

متادیتای برگرفته از کد منبع:

| ویژگی | مقدار |
| --- | --- |
| node flags | `kNodeFlagSupportsSplice` |
| `can_have_prev` | `true` |
| `can_have_next` | `true` |
| `layer_group` | `kNodeLayer4` |
| `layer_group_prev_node` | `kNodeLayer4` |
| `layer_group_next_node` | `kNodeLayer4` |

`Est` اتصال transport را اعلام می‌کند، نه موفقیت مذاکرهٔ SOCKS. برای UDP نیز `Est` کنترل TCP یک بار به line برنامه نگاشت می‌شود.
داده پس از Init پذیرفته می‌شود، اما تا آماده شدن پروتکل در صف محدود به ۲ MiB دادهٔ منطقی و ۸ MiB هزینهٔ حافظهٔ صف می‌ماند.
در TCP، greeting و خروجی آمادهٔ برنامه یا پاسخ بدون انتظار برای Resume و با حفظ ترتیب FIFO فرستاده می‌شوند.
اولین دادهٔ نگه‌داری‌شده، منبع خود را Pause می‌کند. Resume پس از تخلیهٔ صف قدیمی‌تر و رفع فشار transport فرستاده می‌شود.
هیچ‌یک از این دو علت توقف نمی‌تواند دیگری را آزاد کند.
Pause دریافت در TCP حتی هنگام مذاکره به adapter بعدی می‌رسد؛ فرستندهٔ آن باید Resume یا بستن اتصال را ترتیب دهد.
در UDP، فشار مسیرهای کنترل و relay تجمیع می‌شود و Resume یکی، Pause دیگری را پاک نمی‌کند.
تخلیهٔ backlog برنامه و greeting خط کنترلِ تحت مالکیت node همچنان این فشار را رعایت می‌کنند؛
فشار دریافت برنامه پس از Init خط relay به همان خط منتقل می‌شود.
line‌های UDP application، control و relay برای قالب‌بندی، مالکیت association و نگاشت فشار فعال می‌مانند.
