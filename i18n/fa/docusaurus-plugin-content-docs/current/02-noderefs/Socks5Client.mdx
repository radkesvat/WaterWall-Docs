# Socks5Client

`Socks5Client` سمت client پروتکل SOCKS5 را داخل یک chain استریم اجرا می‌کند. این نود روی transport بعدی به عنوان
اتصال SOCKS proxy کار می‌کند، method negotiation را انجام می‌دهد، در صورت نیاز username/password می‌فرستد، و سپس برای
مقصد نهایی تنظیم‌شده دستور `CONNECT` یا `UDP ASSOCIATE` می‌فرستد.

مقصدی که در تنظیمات `Socks5Client` می‌نویسید مقصد نهایی داخل درخواست SOCKS است. آدرس خود SOCKS proxy باید در نود بعدی
مثل `TcpConnector` یا، برای UDP، `TcpUdpConnector` تنظیم شود.

## جایگاه رایج

برای TCP:

```text
TcpListener -> Socks5Client -> TcpConnector
```

برای TCP و UDP از یک SOCKS server:

```text
TcpUdpListener -> Socks5Client -> TcpUdpConnector
```

در حالت UDP، نود بعدی باید بتواند هم TCP control connection و هم UDP relay address برگشتی از proxy را مدیریت کند.

## نمونه پایه

```json
{
  "name": "socks-client",
  "type": "Socks5Client",
  "settings": {
    "address": "dest_context->address",
    "port": "dest_context->port",
    "protocol": "tcp",
    "user": "alice",
    "pass": "secret",
    "domain-strategy": "do-not-resolve-domains",
    "verbose": false
  },
  "next": "proxy-transport"
}
```

`proxy-transport` باید نودی باشد که به SOCKS5 server وصل می‌شود؛ مثلا یک `TcpConnector` با آدرس و پورت proxy.

## پروتکل پویا

اگر line ورودی خودش protocol مقصد را مشخص کرده است، می‌توانید از `dest_context->protocol` استفاده کنید.

```json
{
  "name": "socks-client",
  "type": "Socks5Client",
  "settings": {
    "address": "dest_context->address",
    "port": "dest_context->port",
    "protocol": "dest_context->protocol"
  },
  "next": "proxy-transport"
}
```

اگر protocol دقیقا TCP باشد، `CONNECT` ارسال می‌شود. اگر دقیقا UDP باشد، `UDP ASSOCIATE` انجام می‌شود. اگر protocol
نامعتبر، مبهم یا خالی باشد، نود warning می‌دهد و به TCP برمی‌گردد.

## فیلدهای اجباری

| فیلد | نوع | توضیح |
| --- | --- | --- |
| `settings` | object | اجباری است و نباید خالی باشد. |
| `settings.address` / `settings.target-address` / `settings.target` | string | آدرس مقصد نهایی SOCKS. می‌تواند literal، یا `dest_context->address` / `line->dest_ctx->address` باشد. |
| `settings.port` | number یا string | پورت مقصد نهایی. عدد `1` تا `65535`، یا `dest_context->port` / `line->dest_ctx->port`. |
| `next` | string | اجباری است و به transport سمت SOCKS proxy اشاره می‌کند. |

## فیلدهای اختیاری

| فیلد | پیش‌فرض | توضیح |
| --- | --- | --- |
| `settings.protocol` / `settings.proto` | `tcp` | مقدارهای مجاز: `tcp`, `connect`, `udp`, `udp-associate`, `dest_context->protocol`, `line->dest_ctx->protocol`. |
| `settings.user` / `settings.username` | تنظیم نشده | نام کاربری SOCKS5. باید همراه `pass` / `password` بیاید. |
| `settings.pass` / `settings.password` | تنظیم نشده | رمز SOCKS5. باید همراه `user` / `username` بیاید. |
| `settings.domain-strategy` | `do-not-resolve-domains` | تعیین می‌کند domain قبل از درخواست SOCKS به صورت local resolve شود یا نه. |
| `settings.verbose` | `false` | log بیشتر. |

username و password باید غیرخالی و حداکثر 255 بایت باشند. اگر فقط یکی از آنها تنظیم شود، ساخت نود fail می‌شود.

## Domain strategy

`Socks5Client` همیشه یک نود داخلی برای آماده‌سازی مقصد می‌سازد. این مرحله مقصد نهایی SOCKS را داخل `line->dest_ctx`
می‌نویسد و protocol انتخاب‌شده را برای line اصلی نگه می‌دارد.

اگر `domain-strategy` باعث resolve محلی شود، یک `DomainResolver` داخلی هم بین مرحله setup و `Socks5Client` قرار می‌گیرد.
این resolve هم برای domain ثابت در JSON و هم برای domain آمده از `dest_context->address` اعمال می‌شود. IP literal
تغییر نمی‌کند.

| مقدار | رفتار |
| --- | --- |
| `do-not-resolve-domains` | domain همان‌طور داخل request SOCKS5 نوشته می‌شود و سمت SOCKS server resolve می‌شود. |
| `resolve-domains-with-core-settings` | از تنظیم DNS داخل `core.json` استفاده می‌کند. |
| `resolve-domains-and-accept-dns-returned-order` | اولین نتیجه قابل استفاده DNS را می‌گیرد. |
| `resolve-domains-and-prefer-ipv4` | IPv4 را ترجیح می‌دهد و در صورت نبود، IPv6 را استفاده می‌کند. |
| `resolve-domains-and-prefer-ipv6` | IPv6 را ترجیح می‌دهد و در صورت نبود، IPv4 را استفاده می‌کند. |
| `resolve-domains-and-use-only-ipv4` | فقط IPv4؛ اگر نتیجه IPv4 نباشد line بسته می‌شود. |
| `resolve-domains-and-use-only-ipv6` | فقط IPv6؛ اگر نتیجه IPv6 نباشد line بسته می‌شود. |

## رفتار TCP

در حالت TCP، بعد از `DownStreamEst` از transport بعدی، نود greeting SOCKS5 را می‌فرستد. اگر credentials تنظیم شده باشد و
server روش username/password را انتخاب کند، درخواست احراز هویت ارسال می‌شود. سپس برای مقصد تنظیم‌شده دستور `CONNECT`
فرستاده می‌شود.

Payloadهای upstream تا زمان موفق شدن دستور SOCKS نگه داشته می‌شوند. queue اولیه 8 buffer ظرفیت دارد و مجموع payloadهای
queued شده به 1 MiB محدود است. بافر handshake هم حداکثر 4096 بایت است. بعد از جواب موفق proxy، نود `Est` را به سمت
قبلی می‌فرستد و payloadهای queued شده را آزاد می‌کند.

## رفتار UDP

در حالت UDP، line اصلی همان مسیر application است و `Socks5Client` دو line داخلی می‌سازد:

| line داخلی | کاربرد |
| --- | --- |
| UDP control line | یک line TCP که به SOCKS proxy وصل می‌شود و `UDP ASSOCIATE` را با مقصد `0.0.0.0:0` می‌فرستد. |
| UDP relay line | یک line UDP که به relay address برگشتی از proxy وصل می‌شود. |

line اصلی فقط وقتی established می‌شود که هم control association و هم relay line آماده باشند. سپس payloadهای UDP با
هدر SOCKS5 UDP شامل مقصد نهایی wrap می‌شوند و از relay line عبور می‌کنند. پاسخ‌های relay هم validate می‌شوند، هدر
SOCKS5 UDP از آنها حذف می‌شود، و payload خام به سمت نود قبلی برمی‌گردد.

fragmentation مربوط به SOCKS5 UDP reassemble نمی‌شود؛ datagramهایی که `FRAG != 0` دارند محافظه‌کارانه نادیده گرفته
می‌شوند.

## متادیتای نود

| ویژگی | مقدار |
| --- | --- |
| flag | `kNodeFlagNone` |
| previous node | مجاز |
| next node | اجباری |
| layer group | `kNodeLayerAnything` |
| `required_padding_left` | بدترین حالت هدر SOCKS5 UDP: `4 + 1 + 255 + 2` بایت |

این padding برای prepend کردن هدر UDP لازم است. اگر buffer ظرفیت چپ کافی نداشته باشد، نود buffer جدید می‌گیرد و payload
را قبل از اضافه کردن هدر کپی می‌کند.

## اشتباه‌های رایج

- آدرس proxy را داخل `settings.address` ننویسید؛ این فیلد مقصد نهایی داخل request SOCKS است.
- UDP mode را با connector فقط-TCP استفاده نکنید.
- `domain-strategy` روی IP literal اثری ندارد.
- وقتی از `dest_context->address` استفاده می‌کنید، `port` همچنان جداگانه لازم است.
