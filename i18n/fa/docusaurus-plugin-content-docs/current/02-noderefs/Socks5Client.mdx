# Socks5Client

## نمای کلی {#overview}


`Socks5Client` یک تونل میانی جریان بایتی است که سمت کلاینت پروتکل SOCKS5 را پیاده
می‌کند. این گره از مسیر انتقال بعدی برای اتصال به پراکسی SOCKS استفاده می‌کند،
روش SOCKS5 را مذاکره می‌کند، در صورت تنظیم نام کاربری و گذرواژه احراز هویت
می‌شود و سپس برای مقصد نهایی تنظیم‌شده درخواست `CONNECT` یا `UDP ASSOCIATE`
می‌فرستد.

مقصد نوشته‌شده در تنظیمات `Socks5Client` همان مقصد نهایی داخل درخواست SOCKS
است. آدرس خود پراکسی SOCKS باید در گره اتصال بعدی تنظیم شود؛ معمولاً
`TcpConnector` برای TCP یا `TcpUdpConnector` در حالتی که رله مربوط به UDP لازم
است.

<a id="جایگاه-رایج"></a>

## جایگاه معمول در زنجیره {#typical-placement}

برای TCP:

```text
TcpListener -> Socks5Client -> TcpConnector
```

برای TCP و UDP از یک سرور SOCKS:

```text
TcpUdpListener -> Socks5Client -> TcpUdpConnector
```

در چیدمان دوم، گره اتصال باید برای اتصال کنترلی از TCP استفاده کند و
آدرس رلهٔ برگشتی از `UDP ASSOCIATE` را از طریق UDP در دسترس قرار دهد.


## نمونهٔ کاربردی ساده {#minimal-practical-example}

این یک **قطعهٔ پیکربندی گره** برای TCP CONNECT است. `proxy-transport` باید به نقطهٔ اتصال پراکسی SOCKS5 متصل شود؛ مقصد زیر سرویس راه دور درخواستی است.

<a id="مقصد-ثابت"></a>

### نمونهٔ مقصد ثابت {#fixed-target-example}

```json
{
  "name": "socks-client",
  "type": "Socks5Client",
  "settings": {
    "address": "example.com",
    "port": 443,
    "protocol": "tcp",
    "dns-behaviour": {"resolve": true, "strategy": "prefer-ipv4"}
  },
  "next": "proxy-transport"
}
```

با فعال بودن تبدیل محلی نام دامنه به IP، `DomainResolver` داخلی پیش از فرستادن
درخواست SOCKS، آدرس IP مربوط به `example.com` را پیدا می‌کند. اگر پاسخ IPv4 موجود
باشد، همان آدرس در درخواست SOCKS قرار می‌گیرد؛ در غیر این صورت گزینهٔ جایگزین
مطابق راهبرد انتخاب‌شده تعیین می‌شود.


## پیکربندی {#configuration}

<a id="فیلدهای-اجباری"></a>

### فیلدهای اجباری {#required-fields}

| فیلد | نوع | توضیح |
| --- | --- | --- |
| `settings` | شیء | اجباری است و نباید خالی باشد. |
| `settings.address` / `settings.target-address` / `settings.target` | رشته | آدرس مقصد نهایی SOCKS. می‌تواند IP ثابت، دامنه با طول ۱ تا ۲۵۵ بایت، `dest_context->address` یا `line->dest_ctx->address` باشد. دامنه طولانی‌تر هنگام ساخت گره رد می‌شود. |
| `settings.port` | عدد یا رشته | پورت مقصد نهایی. عدد `1` تا `65535`، یا `dest_context->port` / `line->dest_ctx->port`. |
| `next` | رشته | اجباری است و به مسیر انتقال سمت پراکسی SOCKS اشاره می‌کند. |

<a id="فیلدهای-اختیاری"></a>

### فیلدهای اختیاری {#optional-fields}

| فیلد | پیش‌فرض | توضیح |
| --- | --- | --- |
| `settings.protocol` / `settings.proto` | `tcp` | منبع انتخاب فرمان SOCKS. مقدارهای مجاز: `tcp`, `connect`, `udp`, `udp-associate`, `dest_context->protocol`, `line->dest_ctx->protocol`. |
| `settings.user` / `settings.username` | تنظیم نشده | نام کاربری SOCKS5. باید همراه `pass` / `password` بیاید. |
| `settings.pass` / `settings.password` | تنظیم نشده | رمز SOCKS5. باید همراه `user` / `username` بیاید. |
| `settings.dns-behaviour` | resolve محلی غیرفعال | کنترل جست‌وجوی محلی، انتخاب آدرس و انتقال DNS؛ بخش رفتار DNS را ببینید. |
| `settings.verbose` | `false` | ثبت گزارش‌های عیب‌یابی بیشتر را فعال می‌کند. |

نام کاربری و گذرواژه باید غیرخالی باشند و هر کدام حداکثر ۲۵۵ بایت طول داشته
باشند. اگر فقط یکی از آن‌ها تنظیم شود، ساخت گره شکست می‌خورد.

<a id="رفتار-dns"></a>

### رفتار DNS {#dns-behaviour}

resolve کردن نام دامنه یعنی پیدا کردن آدرس IP آن. `Socks5Client` می‌تواند نام دامنهٔ
مقصد نهایی را در درخواست SOCKS5 بفرستد، یا آن را محلی resolve کند و IP انتخاب‌شده
را بفرستد. resolve محلی فقط برای نام دامنهٔ resolve‌نشده و در صورت فعال بودن انجام
می‌شود. IP عددی یا مقصدی که از قبل resolve شده باشد به جست‌وجو نیاز ندارد.

این تنظیم مربوط به مقصد نهایی است که از طریق پراکسی به آن می‌رسید. گره اتصال بعدی
آدرس سرور پراکسی را انتخاب می‌کند و تنظیمات DNS مستقل خودش را دارد. با حذف
`dns-behaviour`، resolve محلی غیرفعال است.

این جست‌وجو را با `settings.dns-behaviour` تنظیم کنید:

```json
{
  "dns-behaviour": {
    "resolve": true,
    "mode": "direct",
    "strategy": "prefer-ipv4",
    "servers": ["203.0.113.53:53"]
  }
}
```

این IP نمونهٔ مستندات است؛ آن را با سرور خود جایگزین کنید.

| فیلد | معنی |
| --- | --- |
| `resolve` | بولی اجباری: `true` اجازهٔ جست‌وجوی نام دامنهٔ resolve‌نشده را می‌دهد و `false`، جست‌وجوی محلی را غیرفعال می‌کند. |
| `mode` | `native` (پیش‌فرض هنگام فعال بودن)، `direct` یا `chain`. |
| `strategy` | یکی از `core-settings`، `accept-dns-returned-order`، `prefer-ipv4`، `prefer-ipv6`، `only-ipv4` یا `only-ipv6`؛ حذف آن اولویت پیش‌فرض آدرس مصرف‌کننده را به کار می‌برد. |
| `servers` | ۱ تا ۳۲ نقطهٔ اتصال عددی IP، `IP:port` یا `[IPv6]:port`؛ در `direct` و `chain` اجباری و در `native` ممنوع. |
| `dns-next` | نام غیرخالی ورودی DNS، فقط در حالت `chain`. |

`native` از تنظیمات DNS در core و resolver مشترک worker استفاده می‌کند. هنگام
فعال بودن resolve محلی، این حالت پیش‌فرض انتقال DNS است.

`direct` درخواست‌های DNS را از طریق یک گره اتصال خصوصی TCP/UDP در WaterWall به
سرورهایی که مشخص کرده‌اید می‌فرستد.

`chain` درخواست‌های DNS را از زنجیرهٔ انتخابی می‌فرستد. برای محافظت از آن‌ها، مسیری
رمزنگاری‌شده مانند VPN خود را انتخاب کنید؛ این حالت به‌تنهایی درخواست‌ها را
رمزنگاری نمی‌کند. مسیر DNS باید هم درخواست‌های UDP و هم fallback روی TCP را حمل
کند. خطای مسیریابی یا جست‌وجو باعث تغییر به DNS بومی یا حالت دیگر نمی‌شود.

در حالت `chain`، با حذف `dns-next` درخواست‌های DNS از همین کلاینت پراکسی و مسیر انتقال
بعد از آن عبور می‌کنند. برای مسیر دیگر، نام یک شاخهٔ DNS جدا را در `dns-next`
بگذارید که از قبل به گره دیگری تعلق نداشته باشد. برای استفاده از همین گره، فیلد
را ننویسید؛ نام خود گره را در آن قرار ندهید.

شکل غیرفعال دقیقاً `"dns-behaviour": {"resolve": false}` است و فیلدهای `mode`، `strategy`، `servers` و `dns-next` را رد می‌کند. شیء تهی، null، نوع غیرشیء، فیلد ناشناخته و strategy عددی رد می‌شوند. نام strategy باید یکی از رشته‌های استاندارد بالا با حروف کوچک باشد. `core-settings` فقط اولویت آدرس را انتخاب می‌کند و انتقال DNS را تغییر نمی‌دهد.

با `resolve: false`، درخواست پراکسی در صورت پشتیبانی پروتکل نام دامنه را نگه می‌دارد. گره اتصال بعدی مقصد مستقل پراکسی یا VPN و سیاست DNS خودش را دارد؛ برای راه‌اندازی اولیه از IP عددی یا مسیر مستقل استفاده کنید.

مثال‌های native، direct و زنجیره محافظت‌شده و محدودیت گزینه‌های core را در [DomainResolver](./DomainResolver.mdx) ببینید. این سیاست فقط جست‌وجوهای متعلق به همین گره را کنترل می‌کند؛ fake DNS در PTC، DNS سیستم در TunDevice و همهٔ منابع DNS برنامه را تغییر نمی‌دهد.


## کاربرد و رفع اشکال {#usage-and-troubleshooting}

<a id="نمونه-پایه"></a>

### نمونهٔ پایه {#basic-example}

این نمونه مقصد ورودی را از `line->dest_ctx` حفظ می‌کند و از پراکسی SOCKS می‌خواهد به همان مقصد متصل شود.

```json
{
  "name": "socks-client",
  "type": "Socks5Client",
  "settings": {
    "address": "dest_context->address",
    "port": "dest_context->port",
    "protocol": "tcp",
    "user": "alice",
    "pass": "secret",
    "dns-behaviour": {"resolve": false},
    "verbose": false
  },
  "next": "proxy-transport"
}
```

`proxy-transport` باید گره‌ای باشد که به سرور SOCKS5 متصل می‌شود؛ برای مثال یک
`TcpConnector` که آدرس و پورت مربوط به پراکسی در آن تنظیم شده است.

<a id="پروتکل-پویا"></a>

### نمونهٔ پروتکل پویا {#dynamic-protocol-example}

اگر line ورودی ممکن است از قبل TCP یا UDP باشد، از
`dest_context->protocol` استفاده کنید تا کلاینت همان پروتکل را دنبال کند.

```json
{
  "name": "socks-client",
  "type": "Socks5Client",
  "settings": {
    "address": "dest_context->address",
    "port": "dest_context->port",
    "protocol": "dest_context->protocol"
  },
  "next": "proxy-transport"
}
```

اگر زمینهٔ مقصد دقیقاً TCP باشد، `CONNECT` فرستاده می‌شود و اگر دقیقاً
UDP باشد، `UDP ASSOCIATE` انجام خواهد شد. در نبود پرچم مناسب، در حالت مبهم یا
برای پروتکلی غیر از TCP/UDP، یک هشدار ثبت می‌شود و گره به TCP برمی‌گردد.

<a id="اشتباههای-رایج"></a>

### اشتباه‌های رایج {#common-mistakes}

- آدرس پراکسی را داخل `settings.address` ننویسید؛ این فیلد مقصد نهایی داخل درخواست SOCKS است.
- حالت UDP را با گره اتصالِ صرفاً TCP به کار نبرید؛ سمت بعدی باید بتواند هم line کنترل TCP و هم line رلهٔ UDP بسازد.
- `dns-behaviour.strategy` روی آدرس IP صریح اثری ندارد؛ فقط بر مقصدهای دامنه‌ای اثر می‌گذارد.
- وقتی از `dest_context->address` استفاده می‌کنید، `port` همچنان جداگانه لازم است.


## رفتار پیشرفته {#advanced-behavior}

<a id="رفتار-tcp"></a>

### رفتار TCP {#tcp-behavior}

در حالت TCP، چرخهٔ عمر به این ترتیب است:

1. upstream `Init`، وضعیت line مربوط به `Socks5Client` را مقداردهی اولیه می‌کند و `Init` را به مسیر انتقال بعدی می‌فرستد.
2. پس از بازگشت `Init` گره بعدی، اگر line هنوز زنده باشد، `Socks5Client` پیام آغازین انتخاب روش SOCKS5 را یک بار می‌فرستد. در زمان برقراری اتصال، `TcpConnector` پیام را تا موفقیت اتصال در صف نگه می‌دارد.
3. اعلان `Est` مسیر انتقال، حتی در صورت تکرار، مستقل از پیام آغازین و مذاکره بلافاصله به سمت برنامه فرستاده می‌شود.
4. اگر اطلاعات ورود تنظیم شده باشد و سرور روش نام کاربری/گذرواژه را انتخاب کند، درخواست احراز هویت فرستاده می‌شود.
5. گره برای مقصد تنظیم‌شده دستور `CONNECT` می‌فرستد.
6. پاسخ موفق، ارسال دادهٔ برنامه را آزاد می‌کند و `Est` دوباره فرستاده نمی‌شود.
7. داده‌های upstream که در انتظار بودند، بدون انتظار برای Resume و با حفظ ترتیب FIFO روی اتصال پراکسی فرستاده می‌شوند؛ ورودی تودرتو پس از بایت‌های قدیمی‌تر قرار می‌گیرد.

در TCP، توقف ناشی از صف دادهٔ برنامه یا تخلیهٔ آن با آخرین Pause/Resume سمت بعدی ترکیب می‌شود.
Resume فقط پس از رفع هر دو علت به منبع می‌رسد؛ Resume مسیر انتقال صف منتظر مذاکره را آزاد نمی‌کند
و تخلیهٔ صف نیز Pause مسیر انتقال را پاک نمی‌کند. وقتی توقف محلی وجود ندارد، اعلان‌های تکراری فشار مسیر انتقال عبور می‌کنند.
پیام آغازین و خروجی آمادهٔ برنامه یا پاسخ منتظر Resume نمی‌مانند. Pause دریافت، حتی هنگام مذاکره
به آداپتور بعدی می‌رسد؛ فرستندهٔ آن باید خودش Resume یا بستن اتصال را ترتیب دهد.

پس از موفقیت مذاکرهٔ TCP، تخلیهٔ تمام ورودی و خروجی نگه‌داری‌شده و رفع توقف محلی و فشار مسیر انتقال،
کلاینت وضعیت line خود را نابود می‌کند و برای آن line به‌طور دائمی bypass می‌شود.
callbackهای بعدی مستقیماً بین همسایه‌ها عبور می‌کنند. callback در حال اجرا پیش از استفاده از
وضعیتی که ممکن است در تبادل بازگشتی نابود شده باشد، فعال بودن گره را بررسی می‌کند.

اگر پیش از موفق شدن درخواست SOCKS، دادهٔ upstream برسد، در صفی با محدودیت
۲ MiB دادهٔ منطقی و ۸ MiB هزینهٔ حافظهٔ صف نگه داشته می‌شود. حافظهٔ صف فقط هنگام اولین استفاده تخصیص
می‌یابد. محدودیت ۴٬۰۹۶ بایت فقط برای فرادادهٔ ناقص پاسخ است؛ یک پاسخ کامل
می‌تواند همراه با بدنهٔ بزرگ‌تر برنامه دریافت شود. پردازش بازگشتی پاسخ‌ها
ترتیبی است و دادهٔ پاسخِ نگه‌داری‌شده بودجهٔ مشترک ۲ MiB دادهٔ منطقی و ۸ MiB هزینهٔ حافظهٔ صف در جهت
پایین‌دست دارد. این صف پس از ورودی قدیمی‌تر پاسخ تخلیه می‌شود، حتی در حضور Pause؛
ارسال مستقیم TCP همچنان همگام است. ورودی خالی TCP از پراکسی نادیده گرفته می‌شود و
باقی‌ماندهٔ TCP روی line کنترل مربوط به UDP پس از برقراری ارتباط دور ریخته می‌شود.
line‌های برنامه و رلهٔ UDP برای جریان بایتی مربوط به مذاکرهٔ آغازین حافظه تخصیص نمی‌دهند.

اگر پراکسی همه روش‌ها را رد کند، احراز هویت شکست بخورد، پاسخ فرمان
نامعتبر باشد یا فرمان با خطا تمام شود، تونل آن line را می‌بندد.

<a id="رفتار-udp"></a>

### رفتار UDP {#udp-behavior}

در حالت UDP، line اصلی همان مسیر برنامه است و `Socks5Client` دو line داخلی می‌سازد:

| line داخلی | کاربرد |
| --- | --- |
| line کنترل UDP | یک line TCP که به پراکسی SOCKS وصل می‌شود و `UDP ASSOCIATE` را با مقصد `0.0.0.0:0` می‌فرستد. |
| line رلهٔ UDP | یک line UDP که به آدرس رلهٔ برگشتی از پراکسی وصل می‌شود. |

line رله از `BND.ADDR` و `BND.PORT` پاسخ موفق `UDP ASSOCIATE` استفاده می‌کند.
این line، پورت کنترل TCP را دوباره به‌کار نمی‌برد و نقطهٔ اتصال مذاکره‌شده را با
آدرس و پورت ثابت پراکسی SOCKS در گره اتصال بعدی جایگزین نمی‌کند. بنابراین سرور
می‌تواند یک پورت رلهٔ موقت و اختصاصی برگرداند؛ سیاست مربوط به دیوارهٔ آتش و NAT
باید نقطهٔ اتصال برگشتی را اجازه دهد، نه فقط پورت کنترل TCP را.

مرجع مقصدِ حاصل از این مذاکره حتی پس از پاک‌شدن فرادادهٔ پروتکل برنامهٔ مشاهده‌شده
توسط `Router` یا گره تشخیص پروتکل حفظ می‌شود. آداپتور خروجی UDP آن را دقیقاً یک‌بار مصرف
می‌کند و سپس نشانگر داخلی را پاک می‌کند تا روی مسیریابی نامرتبط بعدی اثر نگذارد.

پیام آغازین پس از بازگشت `Init` گره بعدی برای line کنترل و در صورت زنده‌بودن ارتباط آمادهٔ ارسال می‌شود.
فشار نوشتن روی line کنترل می‌تواند ارسال آن را به تأخیر بیندازد. اعلان `Est` مسیر انتقال کنترل یک بار
به line برنامه منتقل می‌شود. تحویل دیتاگرام تا موفقیت ارتباط کنترلی و آماده‌شدن مسیر رلهٔ UDP منتظر می‌ماند و صف انتظار آن به
۲ MiB بایت منطقی و ۸ MiB هزینهٔ حافظهٔ صف محدود است.

وقتی دادهٔ برنامه در جهت upstream فرستاده می‌شود، `Socks5Client` یک سرآیند درخواست
SOCKS5 UDP شامل مقصد نهایی تنظیم‌شده به ابتدای دیتاگرام اضافه می‌کند و آن را از
line رلهٔ UDP می‌فرستد. وقتی دیتاگرام پاسخ در جهت downstream برمی‌گردد، سرآیند
SOCKS5 UDP اعتبارسنجی و حذف می‌شود و فقط دادهٔ آن به گره قبلی می‌رسد.

قطعه‌های SOCKS5 UDP دوباره سرهم نمی‌شوند؛ دیتاگرام‌هایی که `FRAG != 0`
دارند برای احتیاط نادیده گرفته می‌شوند.

## جزئیات پیاده‌سازی {#implementation-details}

<a id="جهت-مقداردهی-اولیه"></a>

### جهت مقداردهی اولیه {#initialization-direction}

line‌های برنامه از طریق `Init` در جهت upstream وارد `Socks5Client` می‌شوند.
`Init` در جهت downstream برای همه نقش‌های line، شامل برنامه، کنترل و رله
در حالت UDP، غیرفعال است؛ دریافت آن یک پیام غیرقابل‌ادامه ثبت می‌کند و با
`abortProgramNow(1)` فرایند را خاتمه می‌دهد. callback‌های downstream برای `Est`
و داده همچنان برای پاسخ‌های پراکسی و داده‌های رله پشتیبانی می‌شوند.

<a id="پشتیبانی-از-splice"></a>

### پشتیبانی از splice {#splice-support}

`Socks5Client` از داده‌های TCP مبتنی بر splice پشتیبانی می‌کند. هنگام مذاکرهٔ
روش SOCKS5، احراز هویت و فرمان، کل هر ورودی پاسخ پراکسی با `sbufEnsureOrdinary()`
پیش از ورود به تجزیه‌گر یا صف ورودی بازگشتی به حافظهٔ عادی تبدیل می‌شود. پس از
مذاکره، داده‌های TCP و ورودی‌های لازم در صف FIFO می‌توانند بافر اصلی را حفظ
کنند. محدودیت مذاکرهٔ آغازین ناقص از محدودیت داده‌های درانتظار برنامه جدا می‌ماند.

line‌های برنامهٔ UDP، کنترل TCP و رلهٔ UDP در هر دو جهت خواندن عادی را برای
تمام عمر خود درخواست می‌کنند. آماده‌سازی مقصد UDP این ترجیح را پیش از نگه‌داری
ورودی توسط DNS محلی تنظیم می‌کند. این ترجیح تضمین نوع بافر نیست و به line‌های
مرتبط منتقل نمی‌شود؛ هر دیتاگرام همچنان پیش از نگه‌داری، خواندن سرآیند یا
قالب‌بندی کاملاً عادی می‌شود. ورودی عادی بدون تغییر عبور می‌کند. line‌های TCP
CONNECT ترجیح خواندن عادی را درخواست نمی‌کنند.

`DomainResolver` داخلی قابلیت splice را حفظ می‌کند. فعال‌شدن واقعی به زنجیره
نهاییِ واجد شرایط و `misc.splice` وابسته است؛ وجود TLS یا گره مسدودکنندهٔ دیگر
splice را برای کل زنجیرهٔ داده غیرفعال می‌کند.

<a id="متادیتای-نود"></a>

### فرادادهٔ گره {#node-metadata}

این مقدار padding اجازه می‌دهد سرآیند SOCKS5 UDP بدون نقض قرارداد
فضای پیشوند بافر به ابتدای دیتاگرام افزوده شود. اگر بافر ورودی باز هم فضای کافی در سمت
چپ نداشته باشد، تونل یک بافر جایگزین می‌گیرد و پیش از افزودن سرآیند، داده
را در آن کپی می‌کند.

فرادادهٔ برگرفته از کد منبع:

| ویژگی | مقدار |
| --- | --- |
| پرچم‌های گره | `kNodeFlagSupportsSplice` |
| `can_have_prev` | `true` |
| `can_have_next` | `true` |
| `layer_group` | `kNodeLayer4` |
| `layer_group_prev_node` | `kNodeLayer4` |
| `layer_group_next_node` | `kNodeLayer4` |
| `required_padding_left` | `262` بایت |

`Est` اتصال مسیر انتقال را اعلام می‌کند، نه موفقیت مذاکرهٔ SOCKS. برای UDP نیز `Est` کنترل TCP یک بار به line برنامه نگاشت می‌شود.
داده پس از Init پذیرفته می‌شود، اما تا آماده شدن پروتکل در صف محدود به ۲ MiB دادهٔ منطقی و ۸ MiB هزینهٔ حافظهٔ صف می‌ماند.
در TCP، پیام آغازین و خروجی آمادهٔ برنامه یا پاسخ بدون انتظار برای Resume و با حفظ ترتیب FIFO فرستاده می‌شوند.
اولین دادهٔ نگه‌داری‌شده، منبع خود را Pause می‌کند. Resume پس از تخلیهٔ صف قدیمی‌تر و رفع فشار مسیر انتقال فرستاده می‌شود.
هیچ‌یک از این دو علت توقف نمی‌تواند دیگری را آزاد کند.
Pause دریافت در TCP حتی هنگام مذاکره به آداپتور بعدی می‌رسد؛ فرستندهٔ آن باید Resume یا بستن اتصال را ترتیب دهد.
در UDP، فشار مسیرهای کنترل و رله تجمیع می‌شود و Resume یکی، Pause دیگری را پاک نمی‌کند.
تخلیهٔ داده‌های درانتظار برنامه و پیام آغازین خط کنترلِ تحت مالکیت گره همچنان این فشار را رعایت می‌کنند؛
فشار دریافت برنامه پس از Init خط رله به همان خط منتقل می‌شود.
line‌های برنامه، کنترل و رلهٔ UDP برای قالب‌بندی، مالکیت ارتباط و نگاشت فشار فعال می‌مانند.
