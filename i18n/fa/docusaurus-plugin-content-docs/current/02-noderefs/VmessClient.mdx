# VmessClient

## نمای کلی {#overview}

<bdi dir="ltr">`VmessClient`</bdi> درخواست‌های جدید VMess AEAD را با یک UUID یا شناسهٔ رشته‌ای کوتاهِ پیکربندی‌شده ارسال می‌کند.
این گره جریان‌های TCP یا دیتاگرام‌های UDP با مقصد ثابت را روی یک بستر انتقالِ جریان بایتی حمل می‌کند.
امنیت پیش‌فرض بدنه <bdi dir="ltr">`aes-128-gcm`</bdi> است. مقصدهای IPv4، IPv6 و دامنه پشتیبانی می‌شوند.

آدرس و پورت این گره، **مقصد نهایی پراکسی‌شده** را انتخاب می‌کنند. <bdi dir="ltr">`TcpConnector`</bdi> بعدی،
**نقطهٔ اتصال سرور VMess** را تعیین می‌کند. TLS و WebSocket به گره‌های انتقالِ موجود خود تعلق دارند؛
VmessClient آن‌ها را شناسایی یا پیکربندی نمی‌کند.

## جایگاه معمول در زنجیره {#typical-placement}

<a id="جایگاه-و-نمونهها"></a>

### جایگاه و نمونه‌ها {#placement-and-examples}

```text
TcpListener    -> VmessClient -> TcpConnector
UdpListener    -> VmessClient -> TcpConnector
TcpUdpListener -> VmessClient -> TlsClient -> TcpConnector
TcpListener    -> VmessClient -> HttpClient (WebSocket) -> TcpConnector
TcpListener    -> VmessClient -> HttpClient (WebSocket) -> TlsClient -> TcpConnector
```

برای WebSocket مبتنی بر HTTP/1.1 روی TLS، در TlsClient گزینهٔ ALPN متناظر با HTTP/1.1 را تنظیم کنید.
اعتبارسنجی گواهی و SNI همچنان از تنظیمات TlsClient هستند.

محافظت از بدنهٔ VMess انتخابی مستقل از TLS است. <bdi dir="ltr">`none`</bdi> و <bdi dir="ltr">`zero`</bdi> بدنهٔ برنامه را بدون رمزنگاری
و بدون احراز اصالت باقی می‌گذارند. مقدار پیش‌فرض <bdi dir="ltr">`encrypted-counter-policy: "wrap"`</bdi> سرانجام
nonceهای AEAD را با همان کلید نشست تکرار می‌کند؛ این کار تعویض کلید نیست. <bdi dir="ltr">`strict`</bdi> پیش از
استفادهٔ مجدد از nonce اتصال را می‌بندد. پیش از انتخاب سیاست، تنظیمات امنیت و شمارنده را بخوانید.

## نمونهٔ کاربردی ساده {#minimal-practical-example}

این یک **قطعهٔ پیکربندی گره** است. زنجیرهٔ پیرامون آن را کامل کنید و UUID نمونه را با
اطلاعات احراز هویت متناظرِ همتا جایگزین کنید.

```json
{
  "name": "vmess-client",
  "type": "VmessClient",
  "next": "tls-client",
  "settings": {
    "uuid": "5783a3e7-e373-51cd-8642-c83782b807c5",
    "address": "example.com",
    "port": 443,
    "protocol": "tcp",
    "security": "aes-128-gcm",
    "dns-behaviour": {"resolve": false},
    "first-payload-timeout-ms": 400,
    "verbose": false
  }
}
```

در اینجا <bdi dir="ltr">`example.com:443`</bdi> مقصدی است که از سرور VMess درخواست می‌شود، حتی اگر گره اتصال‌دهندهٔ
بعدی به میزبان و پورت دیگری متصل شود.

<bdi dir="ltr">`tls-client`</bdi> نام لایهٔ انتقال TLS پیکربندی‌شدهٔ شماست؛ گره اتصال‌دهندهٔ پس از آن به سرور
VMess وصل می‌شود. مقصد گره، یعنی <bdi dir="ltr">`example.com:443`</bdi>، سرویسی است که از آن سرور درخواست می‌شود.

<a id="تنظیمات"></a>

### تنظیمات {#settings}

| تنظیم | پیش‌فرض | مقادیر پذیرفته‌شده |
| --- | --- | --- |

| <bdi dir="ltr">`target-address`</bdi> / <bdi dir="ltr">`address`</bdi> / <bdi dir="ltr">`target`</bdi> | الزامی | میزبان/IP صریح، <bdi dir="ltr" style={{display: "inline-block", maxWidth: "100%"}}>`dest_context->address`</bdi> یا <bdi dir="ltr" style={{display: "inline-block", maxWidth: "100%"}}>`line->dest_ctx->address`</bdi>. دامنه‌ها شامل <bdi dir="ltr">1..255</bdi> بایت غیر NUL هستند. |

| <bdi dir="ltr">`protocol`</bdi> / <bdi dir="ltr">`proto`</bdi> | <bdi dir="ltr">`tcp`</bdi> | <bdi dir="ltr">`tcp`</bdi>/<bdi dir="ltr">`connect`</bdi>، <bdi dir="ltr">`udp`</bdi>/<bdi dir="ltr">`udp-associate`</bdi>، <bdi dir="ltr" style={{display: "inline-block", maxWidth: "100%"}}>`dest_context->protocol`</bdi> یا <bdi dir="ltr" style={{display: "inline-block", maxWidth: "100%"}}>`line->dest_ctx->protocol`</bdi>. |
| <bdi dir="ltr">`dns-behaviour`</bdi> | تفکیک نام محلی غیرفعال است | جست‌وجوی محلی، انتخاب آدرس و بستر انتقال DNS؛ بخش رفتار DNS را در ادامه ببینید. |
| <bdi dir="ltr">`first-payload-timeout-ms`</bdi> | <bdi dir="ltr">`400`</bdi> | عدد صحیح <bdi dir="ltr">0..4294967295</bdi>؛ صفر، درخواستِ بدون داده را پس از Est بستر انتقال، بدون انتظار عمدی ارسال می‌کند. |
| <bdi dir="ltr">`security`</bdi> | <bdi dir="ltr">`aes-128-gcm`</bdi> | <bdi dir="ltr">`aes-128-gcm`</bdi>، <bdi dir="ltr">`chacha20-poly1305`</bdi>، <bdi dir="ltr">`auto`</bdi>، <bdi dir="ltr">`none`</bdi> یا <bdi dir="ltr">`zero`</bdi>. |
| <bdi dir="ltr">`chunk-masking`</bdi> | وابسته به حالت | بولی؛ به‌جز در <bdi dir="ltr">`zero`</bdi> برابر true است. |
| <bdi dir="ltr">`global-padding`</bdi> | وابسته به حالت | بولی؛ برای حالت‌های رمزنگاری‌شده true و برای <bdi dir="ltr">`none`</bdi> و <bdi dir="ltr">`zero`</bdi> برابر false است. |
| <bdi dir="ltr">`authenticated-length`</bdi> | <bdi dir="ltr">`false`</bdi> | بولی؛ فقط برای حالت‌های رمزنگاری‌شده. |
| <bdi dir="ltr">`encrypted-counter-policy`</bdi> | <bdi dir="ltr">`wrap`</bdi> | <bdi dir="ltr">`wrap`</bdi> یا <bdi dir="ltr">`strict`</bdi>؛ سیاست محلی برای هر جهت رمزنگاری‌شده. |
| <bdi dir="ltr">`send-termination`</bdi> | <bdi dir="ltr">`true`</bdi> | بولی؛ هنگام بسته‌شدن محلی، رکورد قاب‌بندی‌شدهٔ خالی و اختیاریِ پایانی را ارسال می‌کند. |
| <bdi dir="ltr">`packet-encoding`</bdi> | <bdi dir="ltr">`none`</bdi> | <bdi dir="ltr">`none`</bdi> یا <bdi dir="ltr">`packetaddr`</bdi>؛ packetaddr فقط برای UDP اعمال می‌شود. |
| <bdi dir="ltr">`verbose`</bdi> | <bdi dir="ltr">`false`</bdi> | پیام‌های عیب‌یابی دارای کد علت، با نمونه‌برداری حداکثر یک‌بار در ثانیه برای هر گره، بدون اطلاعات احراز هویت، کلیدها یا متن آشکار. |

از هر گروه نام‌های جایگزینِ اطلاعات احراز هویت/آدرس دقیقاً یک نام، و حداکثر یک انتخابگر پروتکل
استفاده کنید. کلیدهای تکراری JSON، نام‌های جایگزین متعارض، تنظیمات پشتیبانی‌نشده، نوع‌های نادرست JSON
و ترکیب‌های نامعتبر قاب‌بندی باعث شکست ساخت گره می‌شوند. نام تنظیمات و مقادیر رشته‌ای باید UTF-8
معتبر و فاقد NUL داخلی باشند. فهرست کاربران و تنظیمات fallback مختص سرور، AlterID و تنظیمات
احراز هویت قدیمی پذیرفته نمی‌شوند.

انتخاب پویای پروتکل فقط TCP یا UDP دقیق را می‌پذیرد. نبودن پروتکل یا مبهم یا پشتیبانی‌نشده بودن آن،
هشداری ثبت می‌کند و به TCP برمی‌گردد. نبودن آدرس پویا، پورت نامعتبر یا صفر، یا ترکیب UDP/<bdi dir="ltr">`zero`</bdi>
که به‌صورت پویا انتخاب شده باشد، پیش از Init بستر انتقال آن association را می‌بندد.
پیکربندی ثابت UDP/<bdi dir="ltr">`zero`</bdi> باعث شکست ساخت گره می‌شود.

شناسه‌های کوتاه دقیقاً از بایت‌های UTF-8 استفاده می‌کنند؛ بدون حذف فاصله‌های ابتدا و انتها،
یکسان‌سازی حروف بزرگ و کوچک یا نرمال‌سازی Unicode. برای نمونه، <bdi dir="ltr">`waterwall`</bdi> به
<bdi dir="ltr">`106b9dde-356b-5769-b2f6-7ea4193ec5f7`</bdi> نگاشت می‌شود. رشته‌های بدشکلِ هم‌اندازهٔ UUID و
شناسه‌های غیر UUID با طول بیش از 30 بایت رد می‌شوند. VmessServer مدیریت‌شده به UUID نگاشت‌شده
با قالب معیار در پایگاه دادهٔ گذرواژهٔ AuthenticationClient نیاز دارد؛ نرمال‌سازی نام کوتاه
فقط برای این کلاینت و اطلاعات احراز هویت محلی سرور اعمال می‌شود.

UUID می‌تواند توسط همان سامانهٔ مدیریتی صادر شود که VmessServer مدیریت‌شده از آن استفاده می‌کند.
VmessClient به AuthenticationClient یا UserController وابسته نیست، آن اطلاعات احراز هویتِ خروجی
را به‌عنوان هویت احرازشدهٔ همتای محلی منتشر نمی‌کند و حسابداری ترافیک را روی حامل UDP خود تکرار
نمی‌کند. پذیرش، سهمیه‌ها، تعویض حساب و شکل‌دهی ترافیک کاربران همچنان بر عهدهٔ سمت سرور/برنامه است.

<a id="رفتار-dns"></a>

### رفتار DNS {#dns-behaviour}

تفکیک نام میزبان به معنای جست‌وجوی آدرس IP آن است. <bdi dir="ltr">`VmessClient`</bdi> می‌تواند نام میزبانِ مقصد نهایی
را در درخواست VMess بفرستد، یا آن را به‌صورت محلی تفکیک کند و IP انتخاب‌شده را به‌جایش بفرستد.
تفکیک محلی فقط در صورت فعال بودن و برای نام میزبانی انجام می‌شود که هنوز تفکیک نشده است.
IPهای صریح و مقصدهایی که قبلاً تفکیک شده‌اند به جست‌وجو نیاز ندارند.

این تنظیم به مقصد نهایی مربوط است که از طریق پراکسی به آن دسترسی پیدا می‌کنید. گره اتصال‌دهندهٔ
بعدی آدرس سرور پراکسی را انتخاب می‌کند و تنظیمات DNS خودش را دارد. بدون <bdi dir="ltr">`dns-behaviour`</bdi>،
تفکیک نام محلی غیرفعال است.

Packetaddr به مقصد IP نیاز دارد. نام میزبانِ تفکیک‌نشده باید ابتدا به‌صورت محلی تفکیک شود؛
غیرفعال‌کردن جست‌وجو باعث نمی‌شود packetaddr نام میزبان را بپذیرد.

این جست‌وجو را با <bdi dir="ltr">`settings.dns-behaviour`</bdi> پیکربندی کنید:

```json
{
  "dns-behaviour": {
    "resolve": true,
    "mode": "direct",
    "strategy": "prefer-ipv4",
    "servers": ["203.0.113.53:53"]
  }
}
```

این آدرس صرفاً نمونه‌ای برای مستندات است؛ آن را با آدرس resolver خود جایگزین کنید.

| فیلد | معنا |
| --- | --- |
| <bdi dir="ltr">`resolve`</bdi> | مقدار بولی الزامی: <bdi dir="ltr">`true`</bdi> اجازهٔ جست‌وجوی نام‌های میزبان تفکیک‌نشده را می‌دهد؛ <bdi dir="ltr">`false`</bdi> جست‌وجوی محلی را غیرفعال می‌کند. |
| <bdi dir="ltr">`mode`</bdi> | <bdi dir="ltr">`native`</bdi> (پیش‌فرض هنگام فعال بودن)، <bdi dir="ltr">`direct`</bdi> یا <bdi dir="ltr">`chain`</bdi>. |
| <bdi dir="ltr">`strategy`</bdi> | <bdi dir="ltr">`core-settings`</bdi>، <bdi dir="ltr">`accept-dns-returned-order`</bdi>، <bdi dir="ltr">`prefer-ipv4`</bdi>، <bdi dir="ltr">`prefer-ipv6`</bdi>، <bdi dir="ltr">`only-ipv4`</bdi> یا <bdi dir="ltr">`only-ipv6`</bdi>؛ با حذف آن، اولویت پیش‌فرض آدرسِ همین مصرف‌کننده استفاده می‌شود. |
| <bdi dir="ltr">`servers`</bdi> | <bdi dir="ltr">1–32</bdi> نقطهٔ اتصال به‌شکل IP عددی، <bdi dir="ltr">IP:port</bdi> یا <bdi dir="ltr">[IPv6]:port</bdi>؛ برای direct/chain الزامی و برای native غیرمجاز است. |
| <bdi dir="ltr">`dns-next`</bdi> | نام غیرخالیِ ورودی DNS، فقط برای chain. |

<bdi dir="ltr">`native`</bdi> از تنظیمات DNS هسته و resolver مشترک worker استفاده می‌کند. وقتی تفکیک نام محلی
فعال باشد، این حالت بستر پیش‌فرض انتقال DNS است.

<bdi dir="ltr">`direct`</bdi> پرس‌وجوهای DNS را از طریق یک گره اتصال‌دهندهٔ TCP/UDP خصوصیِ WaterWall به سرورهایی
که مشخص می‌کنید می‌فرستد.

<bdi dir="ltr">`chain`</bdi> پرس‌وجوهای DNS را از طریق زنجیره‌ای انتخاب‌شده می‌فرستد. برای محافظت از این پرس‌وجوها،
از مسیری رمزنگاری‌شده مانند VPN خود استفاده کنید؛ این حالت به‌تنهایی آن‌ها را رمز نمی‌کند.
مسیر DNS باید هم پرس‌وجوهای UDP و هم مسیر جایگزین TCP را حمل کند. شکست مسیریابی یا جست‌وجو
باعث تغییر به DNS بومی یا حالت دیگری نمی‌شود.

در حالت <bdi dir="ltr">`chain`</bdi>، حذف <bdi dir="ltr">`dns-next`</bdi> باعث می‌شود درخواست‌های DNS از همین کلاینت پراکسی و بستر
انتقال پس از آن عبور کنند. برای استفاده از مسیر دیگر، <bdi dir="ltr">`dns-next`</bdi> را روی شاخهٔ DNS جداگانه‌ای
تنظیم کنید که از قبل به گره دیگری تعلق نداشته باشد. برای استفاده از همین گره، فیلد را حذف کنید؛
آن را برابر نام خود گره قرار ندهید.

شکل غیرفعال دقیقاً <bdi dir="ltr">`"dns-behaviour": {"resolve": false}`</bdi> است. این شکل، <bdi dir="ltr">`mode`</bdi>، <bdi dir="ltr">`strategy`</bdi>، <bdi dir="ltr">`servers`</bdi> و <bdi dir="ltr">`dns-next`</bdi> را رد می‌کند. سیاست‌های خالی، null یا غیرشیء، فیلدهای ناشناخته و راهبردهای عددی رد می‌شوند. نام راهبردها باید همان رشته‌های معیارِ بالا با حروف کوچک باشد. <bdi dir="ltr">`core-settings`</bdi> فقط اولویت آدرس را انتخاب می‌کند و هرگز بستر انتقال DNS را تغییر نمی‌دهد.

<bdi dir="ltr">`resolve: false`</bdi> نام میزبان را در درخواست‌هایی که از آن پشتیبانی می‌کنند حفظ می‌کند. گره اتصال‌دهندهٔ بعدی همچنان نقطهٔ اتصال مستقل پراکسی/VPN را انتخاب می‌کند و سیاست DNS خودش را دارد. از نقطهٔ اتصال بیرونیِ عددی یا یک مسیر مستقل برای راه‌اندازی اولیه استفاده کنید.

Packetaddr پس از آماده‌سازی/تفکیک نام همچنان به مقصد IP نیاز دارد. ورودی مشترک DNS باید با قاب‌بندی VMess پیکربندی‌شده، هم TCP و هم UDP را پشتیبانی کند.

برای نمونه‌های پیکربندی native، direct و زنجیرهٔ محافظت‌شده و محدودیت گزینه‌های هسته، [DomainResolver](./DomainResolver.mdx) را ببینید. این سیاست جست‌وجوهای متعلق به همین گره را کنترل می‌کند؛ fake DNS در PTC، DNS سیستم در TunDevice یا همهٔ منابع DNS برنامه را پیکربندی نمی‌کند.

## کاربرد و رفع اشکال {#usage-and-troubleshooting}

### نمونهٔ استفاده از زمینهٔ مقصد {#destination-context-example}

برای حفظ مقصد ورودی از پراکسی/مسیریاب:

```json
{
  "name": "vmess-client",
  "type": "VmessClient",
  "next": "tcp-to-vmess-server",
  "settings": {
    "id": "5783a3e7-e373-51cd-8642-c83782b807c5",
    "address": "dest_context->address",
    "port": "dest_context->port",
    "protocol": "dest_context->protocol",
    "security": "chacha20-poly1305"
  }
}
```

<a id="آمار-فقطخواندنی"></a>

### آمار فقط‌خواندنی {#read-only-stats}

عملیات ثبت‌شدهٔ <bdi dir="ltr">`stats`</bdi> در API گره، یک شیء JSON خالی یعنی <bdi dir="ltr">`{}`</bdi> را با حداکثر 64 بایت،
با احتساب فاصله‌ها، می‌پذیرد. این عملیات امکان بازنشانی یا تغییر ندارد. دسترسی به آن نیازمند
مجوز معمول گره/عملیات در APIServer است؛ [پروتکل مشترک API](../05-devguides/api/protocol.mdx)
را در مرجع گره ببینید.

پاسخ JSON با ساختار ثابت شامل تنظیمات مؤثر امنیت/گزینه‌ها/پروتکل، شمارنده، خاتمه و کدگذاری بسته،
تعداد تقریبی برنامه‌ها/حامل‌های فعال، رکوردهای موفق بدنهٔ TX/RX، بایت‌های برنامه، بایت‌های روی سیم،
تعداد گردش‌های شمارنده، علت‌های ثابت بستن/حذف و پیام‌های verbose سرکوب‌شده است. هر شمارندهٔ uint64
یک رشتهٔ ده‌دهی JSON است تا دقت کامل حفظ شود. بایت‌های برنامه پوشش‌های packetaddr را شامل نمی‌شوند
و داده‌های TX با کدگذاری موفق و داده‌های RX تحویل‌شده را می‌شمارند؛ بایت‌های روی سیم، بایت‌های
TX سپرده‌شده برای ارسال و RX دریافت‌شده، شامل handshake و قاب‌بندی را می‌شمارند. EOF قاب‌بندی‌شده
یک رکورد محسوب می‌شود، اما بایتی به شمار بایت‌های برنامه اضافه نمی‌کند. نماهای لحظه‌ای، شمارنده‌های
اتمی را مستقل از هم می‌خوانند و هنگام جریان ترافیک تقریبی هستند؛ هرگز lineهای زنده را پیمایش
نمی‌کنند. کلاینت مالک backend مقصد، حافظهٔ نهان احراز هویت یا جدول replay نیست. بدنه‌های نامعتبر
یا غیرخالی، مهلت‌های منقضی و بودجهٔ ناکافیِ نتیجه/حافظهٔ کاری، خطای API برمی‌گردانند. حافظهٔ کاری
شامل 4,608 بایت فضای موقت ثابت برای تولید خروجی/فراداده، به‌اضافهٔ هزینهٔ واقعی تخصیص از مخزن
نتیجه است.

<a id="build-و-محدودیتها"></a>

### ساخت و محدودیت‌ها {#build-and-limitations}

<bdi dir="ltr">`INCLUDE_VMESS_CLIENT`</bdi> این گره را در ساخت‌های استاندارد فعال می‌کند. VmessClient و VmessServer
کدک داخلی VmessCommon و الزام استفادهٔ مستقیم از فراهم‌کنندهٔ OpenSSL آن را به اشتراک می‌گذارند
(نسخهٔ 3.3 یا جدیدتر برای SHAKE جریانی)، مستقل از backend عمومی رمزنگاری. ساختِ فقط کلاینت،
نه به VmessServer و نه به AuthenticationClient/UserController نیاز دارد.

زنجیرهٔ کاملِ گسترش‌یافته از بافرهای معمولی استفاده می‌کند؛ خروجی جدید، تمام فضای padding مخزن
ادامهٔ مسیر را حفظ می‌کند.

قابلیت‌های پشتیبانی‌نشده عبارت‌اند از سرآیندهای قدیمی، AlterID، AES-CFB، AES-CTR، Mux.Cool، XUDP،
فرمان‌های معکوس، تعویض خودکار حساب/امنیت، اتصال مجدد/بازپخش و پیاده‌سازی بسترهای انتقال جدید.

قاب‌بندی Mux در WaterWall اختصاصی است و سازگاری با VMess Mux.Cool خارجی را فراهم نمی‌کند.

## رفتار پیشرفته {#advanced-behavior}

### پراکسی محلی SOCKS5 روی WebSocket و TLS {#socks5-websocket-tls-client}

این سناریوی دوطرفه به برنامه‌های محلی SOCKS5 اجازه می‌دهد مقصد خود را انتخاب کنند و سپس هر
درخواست TCP را از طریق WebSocket و TLS به یک سرور VMess راه دور می‌فرستد:

```text
Client: TcpListener -> Socks5Server -> VmessClient -> HttpClient -> TlsClient -> TcpConnector
Server: TcpListener -> TlsServer -> HttpServer -> VmessServer -> TcpConnector
```

پیکربندی زیر را به‌عنوان فایل پیکربندی گره‌های کلاینت استفاده کنید و از <bdi dir="ltr">`core.json`</bdi> آن به این
فایل ارجاع دهید. [پیکربندی کامل و متناظر سرور](./VmessServer.mdx#socks5-websocket-tls-server)
در صفحهٔ VmessServer آمده است. دو پیکربندی را در پردازه‌های جداگانهٔ WaterWall اجرا کنید.
UUID نمونه را در هر دو سمت، <bdi dir="ltr">`203.0.113.10`</bdi> را با آدرس سرورتان، و <bdi dir="ltr">`tunnel.example.com`</bdi> را
با نام مندرج در گواهی TLS مورد اعتمادِ سرور جایگزین کنید.

```json
{
  "name": "vmess-websocket-client",
  "nodes": [
    {
      "name": "local-socks", "type": "TcpListener",
      "next": "socks",
      "settings": {"address": "127.0.0.1", "port": 1080}
    },
    {
      "name": "socks", "type": "Socks5Server",
      "next": "vmess",
      "settings": {"no-auth": true, "connect": true, "udp": false}
    },
    {
      "name": "vmess", "type": "VmessClient",
      "next": "websocket",
      "settings": {
        "uuid": "5783a3e7-e373-51cd-8642-c83782b807c5",
        "address": "dest_context->address",
        "port": "dest_context->port",
        "protocol": "tcp",
        "security": "aes-128-gcm",
        "dns-behaviour": {"resolve": false}
      }
    },
    {
      "name": "websocket", "type": "HttpClient",
      "next": "tls",
      "settings": {"http-version": 1, "websocket": true, "host": "tunnel.example.com", "path": "/vmess"}
    },
    {
      "name": "tls", "type": "TlsClient",
      "next": "server",
      "settings": {"sni": "tunnel.example.com", "verify": true, "alpns": ["http/1.1"]}
    },
    {
      "name": "server", "type": "TcpConnector",
      "settings": {"address": "203.0.113.10", "port": 443}
    }
  ]
}
```

شنوندهٔ محلی SOCKS به loopback متصل است و فقط TCP CONNECT را می‌پذیرد. برنامهٔ خود را برای
SOCKS5 در <bdi dir="ltr">`127.0.0.1:1080`</bdi> تنظیم کنید؛ اگر نام میزبان مقصد باید بدون تغییر به سرور برسد،
گزینهٔ DNS راه دورِ برنامه را فعال کنید. برای نمونه،
<bdi dir="ltr">`curl --socks5-hostname 127.0.0.1:1080 https://example.com/`</bdi>.

مقصد اصلیِ درخواستی از <bdi dir="ltr">`Socks5Server`</bdi> می‌آید و VmessClient آن را ثبت می‌کند. گره اتصال‌دهندهٔ
نهایی همیشه به **سرور VMess** متصل می‌شود، نه به آن مقصد اصلی. Host/مسیر WebSocket و SNI در TLS
سرویس تونل را توصیف می‌کنند؛ جایگزین مقصد اصلیِ درخواستی نمی‌شوند. هر دو گره HTTP از
<bdi dir="ltr">`http-version: 1`</bdi>، <bdi dir="ltr">`websocket: true`</bdi> و مسیر یکسان استفاده می‌کنند و هر دو گره TLS،
<bdi dir="ltr">`http/1.1`</bdi> را انتخاب می‌کنند. به CDN نیازی نیست. TLS و WebSocket در هر اتصال یک‌بار VMess
را در بر می‌گیرند؛ در اینجا گره Mux لازم نیست.

<a id="امنیت-و-framing"></a>

### امنیت و قاب‌بندی {#security-and-framing}

تمام حالت‌ها از سرآیندهای درخواست و پاسخ AEAD با احراز اصالت استفاده می‌کنند. <bdi dir="ltr">`none`</bdi> و <bdi dir="ltr">`zero`</bdi>
بدنهٔ برنامه را بدون رمزنگاری و احراز اصالت باقی می‌گذارند. TLS همچنان جداگانه تنظیم می‌شود.
اگر قرار است TLS محافظت از بدنه را بر عهده داشته باشد، برای TCP روی TLS حالت <bdi dir="ltr">`zero`</bdi> و برای
UDP حالت قاب‌بندی‌شدهٔ <bdi dir="ltr">`none`</bdi> را به‌صورت دستی انتخاب کنید. کلاینت هرگز وجود TLS را استنباط
نمی‌کند و امنیت بدنه را بر اساس گره‌های همسایه کاهش نمی‌دهد.

<bdi dir="ltr">`auto`</bdi> یک‌بار هنگام ساخت گره تعیین می‌شود. اگر قابلیت‌های CPU/OS در زمان اجرا وجود شتاب‌دهی
AES و ضرب بدون نقلی را اثبات کنند و فراهم‌کنندهٔ OpenSSL مربوط به VMess از AES پشتیبانی کند،
AES-GCM انتخاب می‌شود؛ در غیر این صورت، ChaCha20-Poly1305 موجود ترجیح داده می‌شود.
اگر الگوریتمی که صریحاً انتخاب شده در دسترس نباشد، ساخت شکست می‌خورد. Auto هرگز <bdi dir="ltr">`none`</bdi>/<bdi dir="ltr">`zero`</bdi>
را انتخاب نمی‌کند.

| امنیت و فرمان | ماسک‌گذاری | padding سراسری | طول‌های احرازشده |
| --- | --- | --- | --- |
| AES-GCM یا ChaCha، TCP/UDP | اختیاری | اختیاری؛ نیازمند ماسک‌گذاری | اختیاری |
| <bdi dir="ltr">`none`</bdi>، TCP | اختیاری | غیرفعال | غیرفعال |
| <bdi dir="ltr">`none`</bdi>، UDP | اختیاری | اختیاری؛ نیازمند ماسک‌گذاری | غیرفعال |
| <bdi dir="ltr">`zero`</bdi>، TCP | غیرفعال | غیرفعال | غیرفعال |

<bdi dir="ltr">`none`</bdi> از قاب‌بندی قطعه‌ای استفاده می‌کند؛ <bdi dir="ltr">`zero`</bdi> نشان‌دهندهٔ NONE بدون قاب‌بندی است و فقط
TCP را پشتیبانی می‌کند. طول‌های احرازشده جایگزین طول‌های معمولی/ماسک‌شده می‌شوند و به ماسک‌گذاری
نیاز ندارند. در صورت استفاده از طول‌های احرازشده و padding سراسری، SHAKE برای padding پیش
می‌رود، نه برای ماسک طول. padding سرآیند درخواست مستقل و تصادفی، با اندازهٔ <bdi dir="ltr">0..15</bdi> بایت است.

برای بیت‌های داخلی <bdi dir="ltr">CHUNK=1</bdi>، <bdi dir="ltr">MASK=4</bdi>، <bdi dir="ltr">PADDING=8</bdi> و <bdi dir="ltr">AUTH_LENGTH=16</bdi>، ترکیب‌های پشتیبانی‌شده
<bdi dir="ltr">`1,5,13,17,21,29`</bdi> برای حالت‌های رمزنگاری‌شده، <bdi dir="ltr">`1,5`</bdi> برای TCP NONE، <bdi dir="ltr">`1,5,13`</bdi> برای UDP NONE
و <bdi dir="ltr">`0`</bdi> برای zero هستند. این اعداد یک تنظیم bitmask در JSON نیستند.

## جزئیات پیاده‌سازی {#implementation-details}

<a id="زمان-ارسال-و-پاسخ"></a>

### زمان‌بندی درخواست و پردازش پاسخ {#request-timing-and-response-handling}

Init مقصد را آماده و بستر انتقال را آغاز می‌کند، بدون اینکه درخواست VMess بفرستد. اولین payload
واجد شرایط فوراً ارسال می‌شود، حتی پیش از Est، درون callback مربوط به Est یا پس از Pause
مشورتی. هنگام قطعی‌شدن اولین درخواست، مُهر زمانی، کلید/IV درخواست، نشانگر پاسخ، دادهٔ تصادفی AuthID،
nonce و padding تازه تولید می‌شوند. درخواست و اولین رکورد کدگذاری‌شدهٔ بدنه در یک بافر معمولی
قرار می‌گیرند. ورودی TCP بزرگ‌تر به‌ترتیب به رکوردهایی با حداکثر اندازهٔ 16 KiB تقسیم می‌شود.

هر Est مستقیم TCP، از جمله موارد تکراری، بی‌درنگ عبور داده می‌شود. Est حامل UDP یک‌بار به
برنامه نگاشت می‌شود. اگر هنوز درخواستی ارسال نشده باشد، اولین Est مهلت اصلی بی‌کاری را آغاز
می‌کند؛ تکرارها هرگز آن را بازنشانی نمی‌کنند. با انقضای مهلت، TCP حتی هنگام Pause مشورتی یک
درخواستِ فقط سرآیند می‌فرستد. حامل UDP بی‌کار، تا زمانی که همان حامل دقیقاً در وضعیت Pause
باشد، این ارسال را به تعویق می‌اندازد و هنگام Resume می‌فرستد. payload واجد شرایط همچنان
فوراً ارسال می‌شود. ورودی خالی TCP درخواستی آغاز نمی‌کند. یک خروجی معمولی تضمین‌کنندهٔ یک
فراخوانی سیستمی، یک بستهٔ TCP یا یک رکورد TLS نیست.

دادهٔ ورودیِ مسیر ارسال هرگز منتظر پاسخ VMess نمی‌ماند. مهلت جداگانه‌ای برای انتظار پاسخ وجود ندارد:
VmessServer می‌تواند به‌درستی تا رسیدن دادهٔ پاسخ backend، ارسال سرآیند پاسخ را به تعویق
بیندازد. چرخهٔ عمر و مهلت‌های موجود بستر انتقال همچنان برقرارند. کلاینت اصالت پاسخ با طول
متغیر و محدود را تأیید می‌کند، نشانگر مورد انتظار و طول دقیق فرمان بیرونی را بررسی می‌کند
و گزینه‌ها/فرمان‌های اختیاری را بدون اعمال SwitchAccount یا تغییر نقطهٔ اتصال یا اطلاعات
احراز هویت مصرف می‌کند. بایت‌های بدنه که با هم رسیده‌اند ترتیب خود را حفظ می‌کنند. برچسب‌های
خراب، طول‌های بدشکل و نشانگرهای احرازشدهٔ نادرست، اتصال مربوط را می‌بندند.

<a id="udp-محدودیتها-و-پایان-عمر"></a>

### UDP، محدودیت‌ها و چرخهٔ عمر {#udp-bounds-and-lifecycle}

line مربوط به UDP برنامه قرض‌گرفته‌شده است. VmessClient برای هر association یک حامل TCP
روی همان worker می‌سازد و مالک آن است و یک مقصد نهایی ثابت را حفظ می‌کند. هر دیتاگرام پذیرفته‌شده
به یک رکورد تبدیل می‌شود؛ هر رکورد دریافتی کامل و غیرخالی به یک دیتاگرام تبدیل می‌شود. UDP بومی
دیتاگرام‌های محلی خالی را حذف می‌کند؛ همهٔ حالت‌ها دیتاگرام‌های بزرگ‌تر از سقف خود را بدون تقسیم
یا آغاز درخواست حذف می‌کنند. زمان‌سنج بی‌کاری همچنان می‌تواند سرآیند بفرستد. رکورد قاب‌بندی‌شدهٔ
خالی به معنای خاتمه است؛ در حالت‌های مربوط، پس از تأیید برچسب اصالت.

| حالت بدنه | حداکثر payload محلی UDP |
| --- | --- |
| AES/ChaCha، طول معمولی/ماسک‌شده | 65,519 بایت |
| AES/ChaCha، طول معمولی/ماسک‌شده و padding | 65,456 بایت |
| AES/ChaCha، طول احرازشده | 65,535 بایت |
| AES/ChaCha، طول احرازشده و padding | 65,472 بایت |
| NONE، طول معمولی/ماسک‌شده | 65,535 بایت |
| NONE، طول ماسک‌شده و padding | 65,472 بایت |

با <bdi dir="ltr">`packet-encoding=packetaddr`</bdi>، فرمان 2 مقصد ویژهٔ دقیق <bdi dir="ltr">`sp.packet-addr.v2fly.arpa:0`</bdi>
را هدف می‌گیرد؛ این نشانگر هرگز به DNS یا گره اتصال‌دهنده داده نمی‌شود. هر رکورد شامل پوشش
خانوادهٔ آدرس/IP/پورت و سپس یک دیتاگرام برنامه است. کلاینت یک مقصد ثابت و یک حامل را نگه
می‌دارد. IP/پورت مبدأ پاسخ باید با آن مقصد یکسان باشد؛ مبدأهای غیرمنتظره حذف و شمرده می‌شوند.
پوشش‌های بدشکل association را می‌بندند. پوشش‌های فقط سرآیند، دیتاگرام‌های خالی برنامه را حفظ
می‌کنند، درحالی‌که رکورد بیرونی خالی VMess همچنان EOF است. برای محاسبهٔ حداکثر payload برنامه
در packetaddr، برای IPv4 مقدار 7 بایت و برای IPv6 مقدار 19 بایت از جدول بالا کم کنید.

Packetaddr به مقصد IP نیاز دارد. DNS محلیِ صریح می‌تواند ابتدا دامنه را تفکیک کند؛ اگر با
تفکیک محلی غیرفعال، مقصد همچنان نام میزبان باشد، association پیش از Init بستر انتقال رد
می‌شود. TCP ثابت همراه با packetaddr باعث شکست ساخت می‌شود؛ TCP پویا کدگذاری معمولی را حفظ
می‌کند. این پوشش مستقل از Mux.Cool و XUDP است و اشتراک‌گذاری مخزن حامل‌ها را اضافه نمی‌کند.

در هر جهت، ورودی نگه‌داری‌شده به 2 MiB بایت منطقی و 8 MiB حجم تخصیصِ محاسبه‌شده محدود است؛
رسیدن به خود این سقف‌ها نیز مجاز است. بافرهای فعالِ برداشته‌شده از صف و قطعات ناقص نیز در این
محاسبه منظور می‌شوند. این سقف‌ها پذیرش و ذخیره‌سازی ورودی را محدود می‌کنند؛ محدودکنندهٔ نرخ
یا سقف RSS کل پردازه نیستند. TX و RX محافظ‌های مستقلِ ورود مجدد
دارند. رکوردهای کاملِ پذیرفته‌شده به‌تدریج و به‌ترتیب FIFO تخلیه می‌شوند، حتی اگر تحویل موجب
Pause مشورتی شود؛ صف خروجیِ رمزگشایی‌شده صرفاً برای کنترل فشار وجود ندارد.

VmessServer سقف ورودی احرازنشدهٔ 64 KiB خود را حفظ می‌کند. یک موج اولیهٔ به‌اندازهٔ کافی بزرگ
از متن آشکار می‌تواند پس از قاب‌بندی، در زمانی که شناسایی هنوز در انتظار است، از آن سقف روی
سیم عبور کند. کلاینت پاسخ را تأییدیهٔ احراز هویت تلقی نمی‌کند، به‌طور ضمنی آهنگ ارسال را تنظیم
نمی‌کند، ظرفیت مجاز سرور را افزایش نمی‌دهد و موج ردشده را با اتصال مجدد/بازپخش تکرار نمی‌کند.

مقدار پیش‌فرض <bdi dir="ltr">`encrypted-counter-policy=wrap`</bdi> تمام شماره‌های ترتیبی داده از <bdi dir="ltr">0..65,535</bdi> را
استفاده می‌کند و با همان کلیدهای نشست از 65,535 به 0 ادامه می‌دهد. برای سازگاری با پیاده‌سازی‌های
رایج، این رفتار عمداً توالی nonce شانزده‌بیتی AEAD را تکرار می‌کند: تعویض کلید نیست و یکتایی
nonceهای AEAD را حفظ نمی‌کند. طول‌های احرازشده از همان شمارهٔ ترتیبی استفاده می‌کنند؛ SHAKE
مربوط به ماسک‌گذاری/padding بدون بازنشانی ادامه می‌یابد.

<bdi dir="ltr">`strict`</bdi> دادهٔ خروجی را به <bdi dir="ltr">0..65,534</bdi> محدود می‌کند و 65,535 را برای EOF رزرو می‌کند. دادهٔ
ورودی معتبر در 65,535 تحویل داده می‌شود و سپس association پیش از استفادهٔ مجدد از nonce
بسته می‌شود. NONE/zero این تنظیم را می‌پذیرند، اما اثری بر شمارندهٔ رمزنگاری ندارند. سیاست
شمارنده محلی است و مذاکره‌ای اضافه نمی‌کند؛ یک سمت strict می‌تواند همتای wrap را در سقف خود ببندد.

Finish از معنای بستن کامل در WaterWall پیروی می‌کند: سمت فرستنده فوراً بسته می‌شود، زمان‌سنج
اولین payload لغو می‌شود، associationها جدا می‌شوند، بافرهای نگه‌داری‌شده تسویه و کلیدهای
نشست پاک می‌شوند. فقط وقتی <bdi dir="ltr">`send-termination=true`</bdi> باشد و درخواست آغاز شده باشد، یک رکورد
خاتمهٔ محدود می‌تواند به سمت بازِ مسیر روی سیم فرستاده شود؛ false آن رکورد را حذف می‌کند و
همان چرخهٔ عمرِ بستن کامل، از جمله هنگام اتمام شمارنده در strict، برقرار می‌ماند. EOF ورودی
معتبر همیشه پذیرفته می‌شود. zero خام EOF صریحِ قاب‌بندی‌شده ندارد. این‌ها انتخاب‌های محلی‌اند
و مذاکره‌ای در handshake ندارند. Finish هرگز درخواست تازه‌ای ایجاد نمی‌کند. Finish حاملِ
تحت مالکیت با مرگ منطقی همان حامل برمی‌گردد. تخلیه توسط مالک مبدأ، lineهای قرض‌گرفته‌شده و
حامل‌های وابستهٔ آن‌ها را پیش از برچیدن زنجیره/مخزن می‌بندد؛ مرحلهٔ quiescence از خروجی جدید
زمان‌سنج یا associationهای جدید جلوگیری می‌کند. گره در تمام طول اتصال، از جمله در
<bdi dir="ltr">`none`</bdi>/<bdi dir="ltr">`zero`</bdi>، فعال باقی می‌ماند.
