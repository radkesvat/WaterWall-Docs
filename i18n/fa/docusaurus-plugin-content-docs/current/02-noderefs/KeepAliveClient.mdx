# KeepAliveClient



## نمای کلی {#overview}

`KeepAliveClient` بخش کلاینت `KeepAliveServer` است. payload‌های upstream را در قالب فریم کوچک keepalive قرار می‌دهد و روی هر line زنده‌ای که این تونل دنبال می‌کند، به‌صورت دوره‌ای فریم ping داخلی می‌فرستد.

این گره زمانی کاربرد دارد که مسیر WaterWall باید مرتب ترافیک تولید کند تا middleboxها، دستگاه‌های NAT یا فایروال‌های دارای timeout، احتمال کمتری داشته باشد که اتصال را بیکار تشخیص دهند. سمت مقابل باید `KeepAliveServer` باشد؛ وگرنه به‌جای payload اصلی، بایت‌های فریم‌شده را دریافت می‌کند.

`KeepAliveClient` یک تونل عادی و قابل ترکیب است. socket یا object‌ای از نوع `line_t` نمی‌سازد، line را آزاد نمی‌کند و پس از پایان تمیز اتصال هیچ state پروتکلی را باقی نمی‌گذارد.

<a id="جایگاه-رایج"></a>

## جایگاه معمول در زنجیره {#typical-placement}

جفت مستقیم داخل یک process:

```text
TesterClient -> KeepAliveClient -> KeepAliveServer -> TesterServer
```

چیدمان TCP روی دو سرور:

```text
client side: TcpListener -> KeepAliveClient -> TcpConnector
server side: TcpListener -> KeepAliveServer -> TcpConnector
```

هر تونل میان کلاینت و سرور باید بایت‌های فریم keepalive را بدون تغییر عبور دهد.

## نمونهٔ کاربردی ساده {#minimal-practical-example}

این‌ها قطعه‌های پیکربندی گره هستند؛ گره‌های مجاورِ ارجاع‌شده را در پیکربندی پیرامون آن‌ها تعریف کنید.

<a id="نمونه-تنظیم"></a>

### نمونهٔ پیکربندی {#configuration-example}

```json
{
  "name": "ka-client",
  "type": "KeepAliveClient",
  "settings": {
    "ping-interval": 30000,
    "sensitive-mode": false,
    "tolerance-ms": 90000
  },
  "next": "transport"
}
```

سمت server متناظر:

```json
{
  "name": "ka-server",
  "type": "KeepAliveServer",
  "settings": {},
  "next": "service"
}
```

## پیکربندی {#configuration}



<a id="فیلدهای-اجباری"></a>

### فیلدهای اجباری {#required-fields}

فیلدهای سطح اصلی:

| فیلد | نوع | توضیح |
| --- | --- | --- |
| `name` | string | نام یکتای گره در config. |
| `type` | string | باید دقیقاً `"KeepAliveClient"` باشد. |
| `settings` | object | اختیاری. در صورت حذف، interval‌های پیش‌فرض استفاده می‌شوند و watchdog پاسخ غیرفعال است. |
| `next` | string | در استفاده عادی اجباری است. گره بعدی داده فریم‌شده upstream را می‌گیرد. |

`KeepAliveClient` باید گره قبلی داشته باشد و در مسیر منطقی به `KeepAliveServer` متناظر برسد.

<a id="تنظیمات"></a>

### تنظیمات {#settings}

| گزینه | نوع | پیش‌فرض | توضیح |
| --- | --- | --- | --- |
| `ping-interval` | integer | `30000` | فاصله ping دوره‌ای به میلی‌ثانیه. باید حداقل `1` باشد؛ در صورت کمتر بودن startup شکست می‌خورد. |
| `sensitive-mode` | boolean | `false` | تنها یک ping منتظر پاسخ روی هر line نگه می‌دارد و در صورت نرسیدن pong یا دیر رسیدن آن اتصال را می‌بندد. |
| `tolerance-ms` | integer | `90000` | مهلت پاسخ به میلی‌ثانیه، با احتساب Pause محلی. باید در بازهٔ `1..2147483647` باشد و در sensitive mode استفاده می‌شود. |

از فاصله‌های بسیار کوتاه استفاده نکنید، مگر اینکه عمداً ترافیک keepalive زیادی می‌خواهید. در هر دو حالت، نخستین ping یک `ping-interval` پس از `Est` انتقال در downstream موعد دارد. تایمر worker آن را در نخستین بررسیِ مجاز در زمان موعد یا پس از آن، حتی در طول Pause توصیه‌ای، می‌فرستد. ترافیک برنامه می‌تواند در این انتظار اولیه جریان داشته باشد. در حالت حساس، مهلت پاسخ درست پیش از تحویل ping به گره بعدی آغاز می‌شود و زمان احتمالی انتظار در صف آن گره را هم در بر می‌گیرد.

وقتی حالت حساس غیرفعال است، آیتم ping در زمان موعد یک ping خالی می‌فرستد و سپس فاصلهٔ بعدی را زمان‌بندی می‌کند. اگر callback رمزگذاری فعال باشد، ping همچنان موعدرسیده می‌ماند تا در بررسی بعدی ارسال شود. pingهای عقب‌افتاده به‌صورت یک‌جا ارسال نمی‌شوند.

<a id="watchdog-پاسخ"></a>

### ناظر مهلت پاسخ {#reply-watchdog}

در حالت حساس، تنها یک ping روی هر line می‌تواند منتظر پاسخ باشد. pong خالی روی همان
line انتظار را پایان می‌دهد. فریم داده، ping سمت مقابل، نوع ناشناخته و pong دارای
payload پاسخ معتبر نیستند؛ pong بدون انتظار جاری نادیده گرفته می‌شود.

نرسیدن pong یا دیر رسیدن آن، اتصال از نوع borrowed را از مسیر Finish و از طریق owner
می‌بندد. KeepAliveClient اتصال را دوباره نمی‌سازد. deadline از ساعت monotonic event loop
worker مالک استفاده می‌کند. item جداگانهٔ deadline با pong به‌موقع حذف می‌شود و
item مربوط به ping هرگز این مهلت را تمدید نمی‌کند. timeout در اولین بررسی idle table
در یا پس از deadline، یا هنگام decode شدن pong دیررس اعمال می‌شود. deadline جدید
و کوتاه ممکن است حدود یک ثانیه دیرتر بررسی شود؛ دقت بیدارسازی زیر یک ثانیه تضمین نمی‌شود.

Pause و Resume در هر دو جهت، حتی در صورت تکرار، به‌صورت شفاف منتقل می‌شوند.
Ping موعدرسیده و Pong آماده منتظر Resume نمی‌مانند. parser ورودی Ping بازگشتی را
با همان محدودیت‌های ذخیره‌سازی، پشت پاسخ فعال نگه می‌دارد؛ صف مستقلی برای Pong وجود ندارد.
مهلت پاسخ جاری ادامه دارد و Pong خالیِ به‌موقع هنگام Pause نیز آن را پایان می‌دهد.
Finish پردازش را متوقف می‌کند، ورودی نگه‌داشته‌شده را آزاد و هر دو idle item را حذف می‌کند.

مهلت را متناسب با توان انتقال و تأخیر مسیر انتخاب کنید. pong و فریم‌های عادی در
همان جریان مرتب قرار دارند؛ زمان Pause، صف، انتقال و بدنهٔ 1 MiB می‌توانند
پاسخ را عقب بیندازند. KeepAliveServer همین pingها را پاسخ می‌دهد.

## کاربرد و رفع اشکال {#usage-and-troubleshooting}



<a id="یادداشتهای-buffer-و-padding"></a>

### نکته‌های buffer و padding {#buffer-and-padding-notes}

`KeepAliveClient` هنگام encode کردن، prefix پنج‌بایتی frame را prepend می‌کند، بنابراین metadata این گره چنین است:

```text
required_padding_left = 5
layer_group = kNodeLayer4
layer_group_next_node = kNodeLayer4
layer_group_prev_node = kNodeLayer4
```

caller باید padding کافی در سمت چپ برای prefix فراهم کند؛ Debug این پیش‌شرط را assert می‌کند. محاسبه padding در زنجیره این فضای اعلام‌شده را رزرو می‌کند.

<a id="نکتههای-عملی"></a>

### نکته‌های عملی {#practical-notes}

- این گره را با `KeepAliveServer` جفت کنید؛ به‌تنهایی مفید نیست.
- فریم‌های ping و pong داخلی جفت KeepAlive هستند و به‌عنوان payload به گره‌های اطراف داده نمی‌شوند.
- این گره یک مسیر را فعال نگه می‌دارد؛ health-check protocol خارجی نیست.
- این گره بایت‌های payload را رمزنگاری، احراز هویت، فشرده یا بازنویسی نمی‌کند.
- برای استفادهٔ مطمئن، transport باید datagram یا جریان و بایت‌های فریم‌شده را بین کلاینت و سرور بدون تغییر نگه دارد.

## رفتار پیشرفته {#advanced-behavior}



<a id="فرمت-frame"></a>

### قالب فریم {#frame-format}

هر frame با یک prefix پنج‌بایتی شروع می‌شود:

| بایت‌ها | فیلد | توضیح |
| --- | --- | --- |
| `0..3` | طول بدنه | عدد صحیح unsigned و 32-bit با ترتیب big-endian. این طول شامل بایت type فریم به‌علاوه بایت‌های payload است. |
| `4` | نوع فریم | `1` payload عادی، `2` ping، یا `3` pong. |

نوع‌های frame:

| نوع | معنی | payload بدنه |
| ---: | --- | --- |
| `1` | payload عادی | بایت‌های payload اصلی WaterWall. |
| `2` | ping | در ترافیک keepalive عادی خالی است. |
| `3` | pong | پاسخ خالی به یک ping frame. |

طول body شامل بایت kind هم می‌شود. هر فریم عادی حداکثر `1 MiB` (`1,048,576 bytes`) payload دارد و حداکثر طول بدنه `1,048,577` است. payload‌های upstream بزرگ‌تر به چند فریم تقسیم می‌شوند. هر دو peer از همین prefix پنج‌بایتی استفاده می‌کنند.

## جزئیات پیاده‌سازی {#implementation-details}



<a id="این-نود-چه-میکند"></a>

### کارکرد گره {#what-it-does}

- با دریافت `Init` در upstream، state محلی line را مقداردهی اولیه می‌کند.
- lineهای قرض‌گرفته‌شدهٔ مقداردهی‌اولیه‌شده را در وضعیت worker مربوط به آن‌ها حساب می‌کند.
- در اولین `Est` مربوط به transport روی هر worker، یک idle table محلی می‌سازد.
- برای ping دوره‌ای و مهلت پاسخ جاری از دو idle item جدا استفاده می‌کند.
- ping خالی را با فاصلهٔ `ping-interval` زمان‌بندی می‌کند؛ sensitive mode پس از `Est` مربوط به transport آغاز می‌شود و منتظر پاسخ هر ping می‌ماند.
- payload‌های upstream را در فریم عادی keepalive encode می‌کند و به `next` می‌فرستد.
- payload‌های upstream بزرگ‌تر از `1 MiB` را به چند frame عادی تقسیم می‌کند.
- header فریم‌های downstream را اعتبارسنجی می‌کند و بایت‌های آمادهٔ payload عادی را تدریجی می‌فرستد.
- فریم‌های عادی downstream را decode و payload آن‌ها را به گره قبلی می‌فرستد.
- به فریم ping در downstream، با فرستادن فریم pong در upstream پاسخ می‌دهد.
- در `sensitive-mode`، pong خالی downstream انتظار ping جاری را پایان می‌دهد؛ در غیر این صورت نادیده گرفته می‌شود.
- فریم‌های عادی خالی و type‌های ناشناخته را دور می‌اندازد.
- line را از فهرست پیگیری خارج می‌کند، state محلی آن را از بین می‌برد و `Finish` را در همان جهت منتشر می‌کند.

watchdog اختیاریِ پاسخ، در صورت نرسیدن pong یا دیر رسیدن آن اتصال را می‌بندد. این قابلیت به‌صورت پیش‌فرض غیرفعال است.

<a id="رفتار-جهتها"></a>

### رفتار جهت‌ها {#direction-behavior}

| callback ورودی | رفتار |
| --- | --- |
| upstream `Init` | buffer خواندن و فیلدهای پیگیری را مقداردهی اولیه می‌کند، line را در worker مالک ثبت می‌کند و سپس `Init` را به `next` می‌فرستد. |
| upstream `Payload` | payload را در یک یا چند فریم عادی encode و به `next` ارسال می‌کند. buffer payload‌های خالی برای استفاده مجدد برمی‌گردد. |
| upstream `Est` | به `next` فرستاده می‌شود. |
| upstream `Pause` / `Resume` | هر اعلان، حتی تکراری، به `next` فرستاده می‌شود؛ مهلت پاسخ جاری ادامه دارد. |
| upstream `Finish` | line را از فهرست پیگیری خارج می‌کند و state محلی را از بین می‌برد، سپس `Finish` را به `next` می‌فرستد. |
| downstream `Payload` | بایت‌ها را ورودی فریم‌شده `KeepAliveServer` در نظر می‌گیرد و payload‌های عادی decodeشده را به گره قبلی می‌فرستد. |
| downstream `Est` | آمادگی انتقال برای watchdog ثبت می‌شود، سپس فوری به گره قبلی فرستاده می‌شود. |
| downstream `Pause` / `Resume` | هر اعلان، حتی تکراری، به گره قبلی فرستاده می‌شود؛ خروجی آمادهٔ Ping/Pong و مهلت پاسخ ادامه دارند. |
| downstream `Finish` | line را از فهرست پیگیری خارج می‌کند و state محلی را از بین می‌برد، سپس `Finish` را به گره قبلی می‌فرستد. |
| downstream `Init` | غیرفعال؛ رسیدن به این callback به‌عنوان زنجیره flow نامعتبر fatal در نظر گرفته می‌شود. |

<a id="پردازش-ورودی-framed"></a>

### پردازش ورودی قاب‌بندی‌شده {#framed-input-handling}

بایت‌های downstream در یک `splice_stream_t` جمع می‌شوند؛ بنابراین ممکن است یک فریم در چند callbackِ payload تکه‌تکه برسد یا چند فریم در یک callback دریافت شوند.

رفتار decoder:

- فقط برای prefix ناقص یا بخش نرسیدهٔ body منتظر ورودی بعدی می‌ماند و کنترل را به worker برمی‌گرداند.
- اگر طول body فریم خارج از بازهٔ `1..1,048,577` باشد، line از طریق owner بسته می‌شود
- فریم‌های عادی خالی دور ریخته می‌شوند.
- type‌های ناشناخته فریم دور ریخته می‌شوند.
- بایت‌های آمادهٔ body ابتدا تخلیه می‌شوند؛ اگر پس از compaction هزینهٔ تخصیص همچنان بیش از سقف باشد، line بسته می‌شود

<a id="پشتیبانی-از-splice"></a>

### پشتیبانی از splice {#splice-support}

`KeepAliveClient` پرچم `kNodeFlagSupportsSplice` را دارد. framing در تمام طول اتصال ادامه
دارد. decoder از cache پنج‌بایتی `splice_stream_t` استفاده می‌کند و encoder فقط
header پنج‌بایتی را در padding واقعی سمت چپ می‌نویسد. بدنهٔ payload می‌تواند در pipe
باقی بماند. payload بزرگ‌تر از 1 MiB با عملیات range متناسب با نوع buffer تقسیم می‌شود. شکست تخصیص pipe یا فشار ظرفیت می‌تواند fallback کامل به buffer عادی
ایجاد کند. فریم‌های ping و pong از buffer عادی استفاده می‌کنند.

پس از اعتبارسنجی header، بایت‌های عادی برنامه به‌محض رسیدن فرستاده می‌شوند و
گیرنده منتظر کامل‌شدن body نمی‌ماند. یک فریم ممکن است چند callback از نوع
Payload تولید کند. اگر اتصال وسط فریم بسته شود، پیشوندی که قبلاً تحویل شده
پس گرفته نمی‌شود. body فریم کنترلی تدریجی دور ریخته می‌شود، اما اثر Ping/Pong
فقط پس از مصرف همهٔ body اعلام‌شده اعمال می‌شود.

ورودی re-entrant encoder پشت suffix فعال می‌ماند و مجموع آن‌ها به 8 MiB بایت منطقی
و 16 MiB هزینهٔ صف، با احتساب suffix فعال، محدود است. decoder ورودی nested را به ترتیب پردازش می‌کند؛ بایت‌های
nested سقف 8 MiB و هزینهٔ تخصیص باقی‌مانده سقف 16 MiB دارند. پیش از رد هزینهٔ اضافی،
ابتدا compaction به buffer عادی، در صورت کاهش هزینه، امتحان می‌شود. بایت‌های آمادهٔ body پیش از بررسی
هزینهٔ نگهداری تخلیه می‌شوند. اعتبارسنجی طول فریم تضمین می‌کند که remainder ناقص، با احتساب header،
کوچک‌تر از 1 MiB + 5 بایت باشد. Pause فوری منتقل می‌شود و
پردازش batch همگامِ پذیرفته‌شده را قطع نمی‌کند. اعلان‌های تکراری Pause/Resume بدون تغییر عبور می‌کنند؛ pingهای موعدرسیده و پاسخ‌های آماده منتظر Resume نمی‌مانند. وظایف framing و watchdog در تمام طول اتصال ادامه دارند، پس این گره فعال می‌ماند و نمی‌تواند برای همیشه از مسیر کنار برود. Pause و Resume هرگز مهلت پاسخ جاری را عقب نمی‌اندازند.

طول بدنهٔ صفر یا بیش از 1 MiB + 1، شکست admission یا سرریز ذخیره‌سازی، line از نوع borrowed را
از طریق owner می‌بندد. Finish، فریم ناقص، suffix فعال encoder و صف ورودی re-entrant
را آزاد می‌کند؛ این گره خودش `line_t` را destroy نمی‌کند.
