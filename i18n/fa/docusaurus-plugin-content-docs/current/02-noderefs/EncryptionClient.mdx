# EncryptionClient {#encryptionclient}

## نمای کلی {#overview}

پیش‌فرض حالت جریان بایتی است. برای بسته‌های کامل IPv4 TCP/UDP گزینهٔ `packet-mode: true`
را فعال کنید؛ در آن حالت فقط payload لایهٔ انتقال رمز می‌شود و سرآیند شبیه TLS وجود ندارد.

`EncryptionClient` بخش کلاینت `EncryptionServer` است. payload‌های upstream را با AEAD رمز می‌کند و در رکورد‌هایی شبیه TLS application data می‌فرستد. در جهت downstream نیز رکورد‌های رمز‌شده را باز می‌کند و payload خام را به گره قبلی برمی‌گرداند.

برای محافظت AEAD درون زنجیرهٔ جریان بایتی WaterWall، بدون اجرای handshake کامل TLS، از این گره استفاده کنید.

:::warning
این گره `TlsClient` نیست: TLS handshake انجام نمی‌دهد، certificate را تأیید نمی‌کند و SNI/ALPN ندارد. در حالت جریان بایتی، قالب رکورد شبیه TLS فقط برای فریم‌بندی payload رمز‌شده به کار می‌رود.
:::

## جایگاه معمول در زنجیره {#typical-placement}

<a id="جایگاه-رایج"></a>

اتصال مستقیم دو گره در یک process:

```text
TesterClient -> EncryptionClient -> EncryptionServer -> TesterServer
```

تونل TCP دو سروری:

```text
client side: TcpListener -> EncryptionClient -> TcpConnector
server side: TcpListener -> EncryptionServer -> TcpConnector
```

تنظیمات دو طرف باید با هم سازگار باشند و تونل‌های میانی باید بایت‌های رکورد رمز‌شده را بدون تغییر عبور دهند.

## نمونهٔ کاربردی ساده {#minimal-practical-example}

این‌ها قطعه‌های پیکربندی گره هستند؛ گره‌های همسایهٔ ارجاع‌شده را در پیکربندی پیرامون آن‌ها تعریف کنید.

### نمونهٔ پیکربندی {#configuration-example}

<a id="نمونه-تنظیم"></a>

```json
{
  "name": "enc-client",
  "type": "EncryptionClient",
  "settings": {
    "algorithm": "chacha20-poly1305",
    "password": "replace-with-a-strong-secret",
    "salt": "chain-a",
    "kdf-iterations": 20000,
    "max-frame-size": 16356
  },
  "next": "transport"
}
```

تنظیمات متناظر سمت سرور:

```json
{
  "name": "enc-server",
  "type": "EncryptionServer",
  "settings": {
    "algorithm": "chacha20-poly1305",
    "password": "replace-with-a-strong-secret",
    "salt": "chain-a",
    "kdf-iterations": 20000,
    "max-frame-size": 16356
  },
  "next": "service"
}
```

## پیکربندی {#configuration}

### فیلدهای الزامی {#required-fields}

<a id="فیلدهای-لازم"></a>

فیلدهای سطح اصلی:

| فیلد | نوع | توضیح |
| --- | --- | --- |
| `name` | string | نام گره در پیکربندی که باید یکتا باشد. |
| `type` | string | باید دقیقاً `"EncryptionClient"` باشد. |
| `next` | string | اجباری. گره بعدی که رکورد‌های رمز‌شده را می‌گیرد. |
| `settings` | object | اجباری است و باید حداقل `password` داشته باشد. |

فیلدهای لازم داخل `settings`:

| فیلد | نوع | توضیح |
| --- | --- | --- |
| `password` | non-empty string | secret مشترک برای ساخت کلید AEAD که باید در سمت سرور نیز یکسان باشد. |

این گره هم به گره قبلی و هم به `next` نیاز دارد؛ ابتدا یا انتهای زنجیره نیست.

### تنظیمات اختیاری {#optional-settings}

<a id="تنظیمات-اختیاری"></a>

| گزینه | نوع | پیش‌فرض | توضیح |
| --- | --- | --- | --- |
| `packet-mode` | boolean | `false` | فعال‌کردن رمزنگاری payload بسته‌های کامل IPv4 TCP/UDP. |
| `algorithm` | string یا numeric enum | `chacha20-poly1305` در جریان بایتی؛ `xchacha20-poly1305` در حالت بسته‌ای | الگوریتم AEAD. اگر `algorithm` وجود نداشته باشد، `method` نیز به‌عنوان نام مستعار پذیرفته می‌شود. |
| `salt` | string | `waterwall-encryption` | ورودی salt برای ساخت کلید که باید در سمت سرور یکسان باشد. |
| `kdf-iterations` | integer | `12000` | تعداد دورهای KDF. بازه معتبر `1` تا `1000000` است. |
| `max-frame-size` | integer | `16356` | حداکثر متن آشکار هر رکورد. بازه معتبر `1` تا `16356` است. |

مقدارهای قابل قبول برای `algorithm` در حالت جریان بایتی:

| الگوریتم | مقدارها |
| --- | --- |
| ChaCha20-Poly1305 | `chacha20-poly1305`, `chacha20poly1305`, `chacha20`, `chacha` |
| AES-256-GCM | `aes-gcm`, `aes256gcm`, `aes-256-gcm`, `aes256-gcm` |

تجزیه‌گر برای سازگاری با enum مقدار پویای WaterWall، مقادیر عددی الگوریتم را نیز می‌پذیرد؛ بااین‌حال مقادیر رشته‌ای روشن‌ترند و توصیه می‌شوند.

اگر AES-GCM را انتخاب کنید ولی backend فعال رمزنگاری از آن پشتیبانی نکند، راه‌اندازی شکست می‌خورد.

## کاربرد و رفع اشکال {#usage-and-troubleshooting}

### محدودیت‌ها و فضای خالی در حالت جریان بایتی {#stream-limits-and-padding}

<a id="محدودیتها-و-padding-در-حالت-stream"></a>

| مقدار | اندازه |
| --- | --- |
| TLS-like سرآیند | `5 bytes` |
| nonce | `12 bytes` |
| AEAD tag | `16 bytes` |
| حداکثر بدنه هر رکورد | `16384 bytes` |
| حداکثر متن آشکار هر رکورد | `16356 bytes` |
| `required_padding_left` | `17 bytes` |

مقدار `required_padding_left` برابر `17` است؛ فضای کافی برای سرآیند پنج‌بایتی و nonce دوازده‌بایتی که پیش از رمزنگاری prepend می‌شوند.

اگر payloadِ upstream از `max-frame-size` بزرگ‌تر باشد، کلاینت آن را میان چند رکورد تقسیم می‌کند. بافر payload صفرطول برای استفاده مجدد برگردانده می‌شود و داده عبور نمی‌کند.

### نکته‌ها و ملاحظات {#notes-and-caveats}

<a id="نکتهها"></a>

- باید با `EncryptionServer` استفاده شود.
- این گره از بایت‌های payload محافظت می‌کند، اما استفاده از قالب رکورد شبیه TLS در WaterWall را پنهان نمی‌کند.
- `password` باید طولانی و تصادفی باشد و در پیکربندی‌های عمومی قرار نگیرد.
- بهتر است `max-frame-size` در دو طرف یکسان باشد. گیرنده رکورد‌های بزرگ‌تر از سقف خودش را رد می‌کند.
- اگر به رفتار واقعی TLS نیاز دارید، از `TlsClient` و `TlsServer` استفاده کنید.

## رفتار پیشرفته {#advanced-behavior}

### حالت بسته‌ای {#packet-mode}

<a id="حالت-بستهای"></a>

گزینهٔ `"packet-mode": true` را صریحاً برای پردازش بسته‌های کامل IPv4 فعال کنید.
این حالت فرادادهٔ لایهٔ 3 و تبدیل بستهٔ بدون حالت را به‌جای خوانندهٔ رکورد جریان بایتی انتخاب می‌کند؛
وجود یک بسته adapter در بخش دیگری از زنجیره به‌تنهایی این حالت را فعال نمی‌کند.
پیش‌فرض `false` است و رفتار جریان بایتی را نگه می‌دارد.

```json
{
  "packet-mode": true,
  "algorithm": "xchacha20-poly1305",
  "password": "replace-with-a-long-random-shared-secret"
}
```

در حالت بسته‌ای فقط `xchacha20-poly1305` پذیرفته می‌شود و اگر `algorithm` حذف شود،
همین الگوریتم انتخاب می‌شود. حالت جریان بایتی همچنان ChaCha20-Poly1305 یا AES-GCM را
می‌پذیرد و XChaCha20-Poly1305 را رد می‌کند. `max-frame-size` مخصوص جریان بایتی است و در حالت بسته‌ای
رد می‌شود؛ دادهٔ بسته هرگز به رکوردها تقسیم نمی‌شود. `password`، `salt` و `kdf-iterations` کلید پایه را تعیین می‌کنند و باید
در دو طرف یکسان باشند. در حالت بسته‌ای SHA-256 رمز به‌عنوان کلید دورهای تکرار
BLAKE2s استفاده می‌شود تا رمز بلند از محدودیت طول کلید BLAKE2s عبور نکند؛ سپس
کلیدهای جداگانه برای ترافیک کلاینت به سرور و سرور به کلاینت ساخته می‌شود.

برای هر بستهٔ کامل و قطعه‌قطعه‌نشدهٔ IPv4 TCP یا UDP:

```text
before: [IPv4 header][TCP/UDP header][transport payload]
after:  [IPv4 header][TCP/UDP header][24-byte nonce][encrypted payload][16-byte tag]
```

برای هر بستهٔ پذیرفته‌شده دقیقاً یک بسته تولید می‌شود؛ حتی payload خالی TCP/UDP
معتبر است، ولی یک `sbuf_t` خالی بستهٔ کامل نیست و حذف می‌شود. سرآیند اضافی IP یا TLS-like
اضافه نمی‌شود. IHL واقعی IPv4 و data offset واقعی TCP محل payload را مشخص می‌کنند؛
گزینه‌های IP و TCP نیز حفظ می‌شوند. هر رمزگذاری از یک nonce تازهٔ مولد تصادفی رمزنگاری استفاده می‌کند؛
گم‌شدن یا جابه‌جایی بسته‌ها مانع رمزگشایی بسته‌های بعدی نمی‌شود و دادهٔ ناقص نگه
داشته نمی‌شود.

طول IP، طول UDP و checksumهای قابل مشاهده به‌روز می‌شوند؛ آدرس‌ها، portها، flags،
sequence و acknowledgment تغییر نمی‌کنند. checksumهای IPv4 و TCP/UDP در حالت عادی
باید معتبر باشند؛ checksum صفر UDP پذیرفته و حفظ می‌شود. flag درخواست ترمیم checksum
در ارسال اجازهٔ ترمیم می‌دهد و در دریافت فقط اعتبارسنجی checksumهای آشکار را کنار
می‌گذارد، نه احراز اصالت را. ترمیم صریح برای UDP صفر نیز checksum فعال تولید می‌کند.
شمارهٔ پروتکل آشکار احراز اصالت می‌شود؛ فیلدهای متغیر IP/transport احراز اصالت
نمی‌شوند تا بازنویسی آدرس/port و تغییر معمول TTL ممکن باشد. محافظت مربوط به payload
است، نه فیلدهای آشکار یا زمان‌بندی. جلوگیری از replay وجود ندارد.

در هر دو جهت، IPv6، fragmentها با MF یا offset غیرصفر، پروتکل آشکار غیر از TCP/UDP، طول نامعتبر،
بایت اضافه پس از IPv4، data offset نامعتبر TCP و طول UDP متفاوت با payload IPv4
رد می‌شوند. DF به‌تنهایی مجاز است؛ fragmentها باید پیش از این گره بازسازی شوند.
رمز اشتباه یا tag نامعتبر فقط همان بسته را حذف می‌کند؛ line بسته‌ای زنده می‌ماند
و هیچ `Finish` یا تخریب line بسته‌ای رخ نمی‌دهد.

سربار دقیقاً **۴۰ بایت** است. طول نهایی IPv4 باید حداکثر `65535` باشد، بنابراین
بستهٔ ورودی متن آشکار حداکثر `65495` بایت است؛ MTU مسیر یا carrier معمولاً محدودیت
کوچک‌تری دارد. این گره fragmentation، کشف PMTU، تنظیم MSS یا جبران sequence TCP
برای سربار را انجام نمی‌دهد. در این حالت 24 بایت فضای خالی در سمت چپ برای nonce اعلام می‌شود؛ فضای tag را رمزگذار بسته مدیریت می‌کند. دو سر بومی TCP همچنان مالک فضای شمارهٔ توالی خود هستند؛ بنابراین این قالب تضمین رفتار شفاف TCP در عبور از هر middlebox نیست.

برای FakeTcpHeader بهتر است `password` همان گره را تنظیم کنید. آن گره به‌صورت
خصوصی Encryption مناسب را می‌سازد و پس از ساخت fake TCP رمزنگاری می‌کند؛ در نتیجه
بایت پروتکل و سرآیند اصلی TCP/UDP همراه payload رمز می‌شوند. FakeTcpHeader آن ۴۰
بایت را در sequence و سقف carrier برابر ۱۵۰۰ حساب می‌کند. اضافه‌کردن دستی Encryption
به زنجیره باعث نمی‌شود FakeTcpHeader خودکار از سربار آن آگاه شود. برای ترتیب زنجیره، مرجع گره‌های FakeTcpHeader را ببینید.

بخش‌های بعدی دربارهٔ فریم‌بندی رکورد، محدودیت فریم، بافرکردن و چرخهٔ عمر جریان بایتی، حالت `packet-mode: false` را توضیح می‌دهند.
حالت بسته‌ای از line بسته‌ای متعلق به زنجیره و callbackهای معمول تونل بسته‌ای استفاده
می‌کند و reader یا وضعیت مخصوص هر line ندارد.

### مشتق‌سازی کلید {#key-derivation}

<a id="ساخت-کلید"></a>

این بخش ساخت کلید پایه را توضیح می‌دهد؛ حالت بسته‌ای دو کلید مستقل جهت‌ها را از
همین کلید پایه مشتق می‌کند.

هر دو peer با استفاده از موارد زیر همان کلید ۳۲ بایتی را می‌سازند:

- `password`
- `salt`
- `kdf-iterations`

پیاده‌سازی از حلقه‌ای اختصاصی در WaterWall و مبتنی بر BLAKE2s برای ساخت کلید استفاده می‌کند، نه از PBKDF2 یا Argon2. کلید ساخته‌شده در وضعیت تونل نگه داشته می‌شود و هنگام آزاد شدن نمونه تونل با صفر بازنویسی می‌شود.

برای کار کردن مسیر رمزشده، هر دو سمت باید `password`، `salt`، `kdf-iterations` یکسان و `algorithm` سازگار داشته باشند.

### قالب روی مسیر در حالت جریان بایتی {#stream-wire-format}

<a id="فرمت-record-در-حالت-stream"></a>

هر بخش رمز‌شده با این ساختار ارسال می‌شود:

```text
5-byte TLS-like header | 12-byte nonce | AEAD ciphertext | 16-byte tag
```

| بخش | مقدار |
| --- | --- |
| نوع رکورد | `0x17`، دادهٔ برنامهٔ TLS |
| version | `0x0303` |
| بدنه length | طول `nonce + ciphertext + tag` به‌صورت big-endian ۱۶ بیتی |

سرآیند پنج‌بایتی به‌عنوان associated data در AEAD احراز اصالت می‌شود. نام الگوریتم داخل رکورد نوشته نمی‌شود و باید در پیکربندی دو طرف یکسان باشد.

## جزئیات پیاده‌سازی {#implementation-details}

### عملکرد گره {#what-it-does}

<a id="این-نود-چه-میکند"></a>

رفتار پیش‌فرض جریان بایتی است؛ فهرست زیر این حالت را توضیح می‌دهد. گزینهٔ `packet-mode: true` نمایهٔ بسته‌ای جداگانهٔ توضیح‌داده‌شده را انتخاب می‌کند.

- از `password`، `salt` و `kdf-iterations` یک کلید ۳۲ بایتی AEAD می‌سازد.
- payload‌های upstream را رمز می‌کند.
- متن آشکار upstream بزرگ‌تر از `max-frame-size` را به چند رکورد تقسیم می‌کند.
- هر chunk رمز‌شده را در یک رکورد شبیه TLS application data قرار می‌دهد.
- بایت‌های رمز‌شده downstream را تا کامل شدن رکورد‌ها بافر می‌کند.
- پیش از رمزگشایی، سرآیند و طول بدنه هر رکورد را اعتبارسنجی می‌کند.
- رکورد‌های downstream را باز می‌کند و متن آشکار بازیابی‌شده را به گره قبلی می‌فرستد.
- در صورت نامعتبر بودن رکورد یا شکست احراز اصالت AEAD، هر دو جهت را می‌بندد.

در حالت جریان بایتی، `EncryptionClient` یک تونل میانی جریان بایتی است و socket یا line بسته‌ای نمی‌سازد.

### رفتار جهت‌ها در حالت جریان بایتی {#stream-direction-behavior}

<a id="رفتار-جهتها-در-حالت-stream"></a>

| جهت | رفتار |
| --- | --- |
| upstream payload | رمز و فریم‌بندی می‌شود و به `next` می‌رود. |
| downstream payload | بافر، parse و رمزگشایی می‌شود و متن آشکار به `prev` می‌رود. |

ممکن است یک فریم کامل downstream در چند callbackِ payload تکه‌تکه برسد یا چند فریم با یک callback دریافت شوند. جریان بایتی خواندن، بایت‌های بافر‌شده را تا زمان parse شدن رکورد‌های کامل نگه می‌دارد.

رکورد‌های کامل به‌محض آماده شدن پردازش می‌شوند و فقط رکورد ناقص فعلی بین callbackها در بافر باقی می‌ماند. پس از کامل شدن سرآیند، طول رکورد با توجه به `max-frame-size` اعتبارسنجی می‌شود و سپس برای دریافت ادامه بدنه منتظر می‌ماند.

### رفتار چرخهٔ عمر در حالت جریان بایتی {#stream-lifecycle-behavior}

<a id="رفتار-lifecycle-در-حالت-stream"></a>

با دریافت `Init` در upstream، کلاینت جریان بایتی خواندن مخصوص line را مقداردهی اولیه می‌کند و `Init` را در همان جهت به `next` می‌فرستد.

با دریافت `Finish` از هر جهت، وضعیت محلی line را از بین می‌برد و `Finish` را در همان جهت منتشر می‌کند: در upstream به `next` و در downstream به `prev`.

Pause و resume در همان جهت دریافت‌شده عبور داده می‌شوند:

| callback | مقصد ارسال |
| --- | --- |
| upstream pause/resume | next tunnel upstream |
| downstream pause/resume | previous tunnel downstream |

upstream `Est` و downstream `Init` برای این گره غیرفعال هستند.

### فرادادهٔ گره {#node-metadata}

<a id="متادیتای-نود"></a>

فراداده برگرفته از کد منبع:

این گره با `kNodeFlagBlocksSplice` استفاده از splice را برای کل زنجیره صریحاً غیرفعال می‌کند. این flag حتی در صورت وجود هم‌زمان `kNodeFlagSupportsSplice` اولویت دارد.

| ویژگی | مقدار |
| --- | --- |
| پرچم‌های گره | `kNodeFlagBlocksSplice` |
