# ConnectionFisherServer

`ConnectionFisherServer` سمت server برای `ConnectionFisherClient` است. این نود منتظر probe ثابت client می‌ماند، با marker ثابت server پاسخ می‌دهد و تنها بعد از آن اجازه می‌دهد line به stream forwarding عادی تبدیل شود.

فقط در مسیرهایی استفاده شود که انتظار می‌رود ترافیک از `ConnectionFisherClient` دریافت کنند.

## جایگاه رایج

طرح‌بندی ساده TCP:

```text
TcpListener -> ConnectionFisherServer -> TcpConnector
```

جفت با client:

```text
TcpListener -> ConnectionFisherClient -> TcpConnector
TcpListener -> ConnectionFisherServer -> TcpConnector
```

با tunnel‌های stream دیگر در میان:

```text
ConnectionFisherClient -> EncryptionClient -> TcpConnector
TcpListener -> EncryptionServer -> ConnectionFisherServer -> TcpConnector
```

سرور باید همان byteهای `FISH?` را ببیند که client بعد از decode شدن توسط هر جفت tunnel client/server میانی می‌فرستد.

## این نود چه می‌کند؟

- در upstream `Init`، فقط state محلی line را initialize می‌کند.
- upstream `Init` به `next` را به تأخیر می‌اندازد.
- byteهای upstream را تا زمانی که حداقل ۵ بایت در دسترس باشد buffer می‌کند.
- نیاز دارد ۵ بایت اول دقیقاً `FISH?` باشند.
- پاسخ ثابت `FISH!` را downstream به client می‌فرستد.
- `next` را فقط وقتی payload بعد از probe موجود باشد initialize می‌کند.
- بعد از کامل شدن فاز probe، payload را به صورت عادی forward می‌کند.
- در صورت داده probe نامعتبر یا buffer شدن handshake بیش از حد، line را می‌بندد.

`ConnectionFisherServer` یک middle stream tunnel است. socket مستقیم نمی‌سازد و packet line نمی‌سازد.

## نمونه تنظیم

```json
{
  "name": "fisher-server",
  "type": "ConnectionFisherServer",
  "next": "service"
}
```

در نسخه فعلی `settings` استفاده نمی‌شود.

## فیلدهای اجباری

فیلدهای top-level:

| فیلد | نوع | توضیح |
| --- | --- | --- |
| `name` | string | نام یکتای نود داخل config. |
| `type` | string | باید دقیقاً `"ConnectionFisherServer"` باشد. |
| `next` | string | اجباری. نود stream بعدی که payload بعد از فاز probe را دریافت می‌کند. |

`ConnectionFisherServer` باید نود قبلی هم داشته باشد. chain head یا chain end نیست.

## تنظیمات

در حال حاضر هیچ فیلد `settings` parse نمی‌شود.

## تبادل Probe

| جهت | Bytes | معنی |
| --- | --- | --- |
| client به server | `FISH?` | ۵ بایت اول upstream اجباری. |
| server به client | `FISH!` | بعد از probe معتبر ارسال می‌شود. |

marker‌ها byteهای ASCII ثابت هستند. مکانیزم امنیتی نیستند.

## فازهای Server

پیاده‌سازی از سه فاز استفاده می‌کند:

| فاز | رفتار |
| --- | --- |
| wait ping | byteهای upstream buffer می‌شوند تا حداقل ۵ بایت در دسترس باشد. |
| wait payload | probe معتبر بود و `FISH!` فرستاده شد، اما `next` هنوز initialize نشده مگر اینکه payload اضافه از قبل buffer شده باشد. |
| established | `next` initialize شده و callback‌های payload/lifecycle به صورت عادی forward می‌شوند. |

## جریان Handshake

در upstream `Init`، سرور فقط state محلی line خود را initialize می‌کند. هنوز `tunnelNextUpStreamInit()` را فراخوانی نمی‌کند.

در upstream payload قبل از establishment:

1. سرور byteهای ورودی را buffer می‌کند.
2. اگر handshake buffer از `4096` بایت بگذرد، line بسته می‌شود.
3. وقتی حداقل ۵ بایت در دسترس باشد، ۵ بایت اول خوانده می‌شوند.
4. اگر دقیقاً `FISH?` نباشند، line بسته می‌شود.
5. اگر match کردند، `FISH!` به سمت previous downstream فرستاده می‌شود.
6. اگر payload بعد از ۵ بایت اول باقی مانده باشد، سرور `next` را initialize می‌کند و payload باقی‌مانده را upstream forward می‌کند.
7. اگر payload اضافه‌ای نباشد، سرور منتظر می‌ماند تا upstream payload بعدی برسد، سپس `next` را initialize و آن payload را forward می‌کند.

بعد از initialize شدن `next`، line توسط این tunnel established در نظر گرفته می‌شود و payload‌های بعدی به صورت عادی forward می‌شوند.

## رفتار Lifecycle

قبل از establishment:

- upstream `Init` فقط local است
- upstream payload به عنوان probe یا اولین payload بعد از probe در نظر گرفته می‌شود
- upstream `Pause` و `Resume` forward نمی‌شوند
- downstream `Est`، `Pause` و `Resume` forward نمی‌شوند
- payload downstream غیرمنتظره است، recycle می‌شود و باعث بسته شدن line می‌شود

بعد از establishment:

- payload upstream به `next` forward می‌شود
- payload downstream به نود قبلی forward می‌شود
- upstream pause/resume به `next` forward می‌شوند
- downstream est/pause/resume به نود قبلی forward می‌شوند

در upstream `Finish`، سرور state محلی را destroy می‌کند و فقط در صورتی upstream `Finish` را forward می‌کند که `next` قبلاً initialize شده باشد. در صورت خطای پروتکل قبل از وجود `next`، فقط سمت previous بسته می‌شود چون هنوز next-side line‌ای وجود ندارد.

## محدودیت‌ها

| محدودیت | مقدار | رفتار |
| --- | --- | --- |
| طول probe | `5` bytes | ۵ بایت اول باید `FISH?` باشند. |
| Handshake buffer | `4096 bytes` | اگر byte‌های بیشتری قبل از کامل شدن probe جمع شوند، line بسته می‌شود. |
| `required_padding_left` | `0` | سرور به buffer‌های موجود اضافه نمی‌کند. |

پاسخ `FISH!` به عنوان یک buffer کوچک جداگانه اختصاص می‌یابد.

## نکته‌ها

- با `ConnectionFisherClient` متناظر استفاده کنید.
- بعد از هر tunnel server-side که transport بین client و server را decode می‌کند قرار دهید.
- برای chainهای stream طراحی شده است، نه packet-line.
- probe ثابت و عمومی است؛ برای امنیت واقعی از نودهای دیگر WaterWall استفاده کنید.
- upstream `Est` و downstream `Init` برای این نود غیرفعال هستند.
