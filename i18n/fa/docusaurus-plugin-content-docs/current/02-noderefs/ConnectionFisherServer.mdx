# ConnectionFisherServer {#connectionfisherserver}

## نمای کلی {#overview}

`ConnectionFisherServer` بخش سرور `ConnectionFisherClient` است. منتظر probe ثابت کلاینت می‌ماند، با نشانگر ثابت سرور پاسخ می‌دهد و تنها پس از آن اجازه می‌دهد line وارد حالت عادی عبور جریان بایتی شود.

این گره را فقط در مسیری قرار دهید که انتظار دارید ترافیک `ConnectionFisherClient` را دریافت کند.

## جایگاه معمول در زنجیره {#typical-placement}

<a id="جایگاه-رایج"></a>

پیش از انتقال اتصال یک سرویس TCP محلی، چند اتصال به gateway را هم‌زمان امتحان کنید:

```text
client: TcpListener(127.0.0.1:15432) -> ConnectionFisherClient -> TcpConnector(gateway:7443)
server: TcpListener(0.0.0.0:7443) -> ConnectionFisherServer -> TcpConnector(127.0.0.1:5432)
```

با `simultaneous-tries-perline: 3`، client برای هر اتصال برنامه سه اتصال کاندید
باز می‌کند و نخستین موردی را که پاسخ معتبر probe برگرداند نگه می‌دارد. connector
آخر سرویس PostgreSQL را انتخاب می‌کند؛ connector سمت client مقصد gateway
WaterWall را دارد. یک connector با مقصد ثابت، اتصال‌های همان endpoint را
امتحان می‌کند، نه سه server متفاوت در پیکربندی.

برای محافظت مسیر peer با TLS، TLS را دور تبادل Fisher قرار دهید:

```text
client: TcpListener -> ConnectionFisherClient -> TlsClient -> TcpConnector
server: TcpListener -> TlsServer -> ConnectionFisherServer -> TcpConnector
```

اعتبارسنجی certificate مربوط به gateway را در `TlsClient` و certificate و key
را در `TlsServer` تنظیم کنید. هر اتصال کاندید handshake جداگانه‌ی TLS دارد.
server باید پس از رمزگشایی TLS همان probe اصلی `FISH?` را دریافت کند؛ گره
Fisher سمت server را پیش از connector سرویس قرار دهید.

## نمونهٔ کاربردی ساده {#minimal-practical-example}

این‌ها قطعه‌های پیکربندی گره هستند؛ گره‌های همسایهٔ ارجاع‌شده را در پیکربندی پیرامون آن‌ها تعریف کنید.

### نمونهٔ پیکربندی {#configuration-example}

<a id="نمونه-تنظیم"></a>

```json
{
  "name": "fisher-server",
  "type": "ConnectionFisherServer",
  "next": "service"
}
```

در نسخه فعلی `settings` استفاده نمی‌شود.

فیلدهای سطح اصلی:

| فیلد | نوع | توضیح |
| --- | --- | --- |
| `name` | string | نام یکتای گره در پیکربندی. |

## کاربرد و رفع اشکال {#usage-and-troubleshooting}

### محدودیت‌ها {#limits}

<a id="محدودیتها"></a>

| محدودیت | مقدار | رفتار |
| --- | --- | --- |
| طول probe | `5` بایت | پنج بایت نخست باید `FISH?` باشند. |
| probe ناقص | `4 bytes` | probe کامل پنج‌بایتی بی‌درنگ اعتبارسنجی می‌شود. |
| داده pending برنامه | 2 MiB بایت منطقی / 8 MiB هزینهٔ صف | بدنه در انتظار Init نیز شمرده می‌شود؛ نشانگر از سقف کم نمی‌کند. |
| `required_padding_left` | `0` | سرور چیزی به بافر‌های موجود اضافه نمی‌کند. |

برای پاسخ `FISH!` یک بافر کوچک جداگانه گرفته می‌شود.

### نکته‌ها و ملاحظات {#notes-and-caveats}

<a id="نکتهها"></a>

- با `ConnectionFisherClient` متناظر استفاده کنید.
- آن را پس از هر تونل سمت سرور قرار دهید که transport میان کلاینت و سرور را decode می‌کند.
- برای زنجیره‌های جریان بایتی طراحی شده است، نه line بسته‌ای.
- probe ثابت و عمومی است؛ برای امنیت واقعی از گره‌های دیگر WaterWall استفاده کنید.
- upstream `Est` و downstream `Init` برای این گره غیرفعال هستند.

## رفتار پیشرفته {#advanced-behavior}

### تبادل probe {#probe-exchange}

<a id="تبادل-probe"></a>

| جهت | Bytes | معنی |
| --- | --- | --- |
| کلاینت به سرور | `FISH?` | پنج بایت الزامی ابتدای upstream. |
| سرور به کلاینت | `FISH!` | پس از دریافت probe معتبر ارسال می‌شود. |

نشانگرها بایت‌های ثابت ASCII هستند و سازوکار امنیتی محسوب نمی‌شوند.

### مرحله‌های سرور {#server-phases}

<a id="مرحلههای-سرور"></a>

پیاده‌سازی از سه فاز استفاده می‌کند:

| فاز | رفتار |
| --- | --- |
| wait ping | بایت‌های upstream تا رسیدن دست‌کم ۵ بایت بافر می‌شوند. |
| wait payload | probe معتبر بوده و `FISH!` فرستاده شده است؛ با این حال `next` هنوز مقداردهی نشده، مگر اینکه payload اضافه از قبل در بافر باشد. |
| established | Init سمت `next` شروع شده است؛ ورودی نگه‌داشته‌شده پیش از بازنشستگی سرور تخلیه می‌شود. |

### روند handshake {#handshake-flow}

<a id="جریان-handshake"></a>

با دریافت `Init` در upstream، سرور فقط وضعیت محلی line را مقداردهی اولیه می‌کند و هنوز `tunnelNextUpStreamInit()` را فراخوانی نمی‌کند.

پردازش payloadِ upstream پیش از برقراری کامل:

1. سرور بایت‌های ورودی را بافر می‌کند.
2. probe ناقص حداکثر چهار بایت دارد؛ بدنه پس از probe کامل سقف جداگانه 2 MiB دارد.
3. وقتی حداقل ۵ بایت در دسترس باشد، ۵ بایت اول خوانده می‌شوند.
4. اگر دقیقاً `FISH?` نباشند، line بسته می‌شود.
5. اگر منطبق باشند، `FISH!` در جهت downstream به سمت previous فرستاده می‌شود.
6. اگر پس از پنج بایت اول payload‌ی مانده باشد، سرور `next` را مقداردهی اولیه می‌کند و payload باقی‌مانده را در upstream می‌فرستد.
7. اگر payload اضافه‌ای نباشد، سرور منتظر payload بعدی upstream می‌ماند؛ سپس `next` را مقداردهی اولیه و آن payload را ارسال می‌کند.

مسیر ادامه پیش از فراخوانی Init بعدی منتشر می‌شود. همه اعلان‌های Est مربوط به transport، حتی اعلان تکراری از داخل Init، فوری منتقل می‌شوند. payload برای Est منتظر نمی‌ماند.

بدنه همراه FISH? و نخستین payload پس از probe، هنگام پاسخ FISH!، Init بعدی و Est
re-entrant جای FIFO خود را حفظ می‌کنند. ترتیب موقت ورودی، شامل بدنه در انتظار بازگشت
Init، سقف 2 MiB بایت منطقی و 8 MiB هزینهٔ صف دارد و در همان dispatch پذیرفته‌شده تکمیل می‌شود. Pause یا Est به‌تنهایی
صف داده آماده ایجاد نمی‌کنند. probe ناقص حداکثر چهار بایت دارد و بدنه پس از probe کامل
سقف جداگانه 2 MiB دارد. بسته‌شدن در Init یا Est دادهٔ محلی قدیمی را پیش از بازگشت آزاد می‌کند.

## جزئیات پیاده‌سازی {#implementation-details}

### عملکرد گره {#what-it-does}

<a id="این-نود-چه-میکند"></a>

- با دریافت `Init` در upstream، فقط وضعیت محلی line را مقداردهی اولیه می‌کند.
- upstream `Init` به `next` را به تأخیر می‌اندازد.
- بایت‌های upstream را تا رسیدن دست‌کم ۵ بایت بافر می‌کند.
- نیاز دارد ۵ بایت اول دقیقاً `FISH?` باشند.
- پاسخ ثابت `FISH!` را downstream به client می‌فرستد.
- `next` را تنها پس از رسیدن payload بعد از probe مقداردهی اولیه می‌کند.
- پس از کامل شدن مرحله probe، payload را به‌صورت عادی عبور می‌دهد.
- اگر probe نامعتبر باشد یا فضای نگه‌داری راه‌اندازی تمام شود، line را می‌بندد.

`ConnectionFisherServer` یک تونل میانی جریان بایتی است. مستقیماً socket یا line بسته‌ای نمی‌سازد.

### رفتار چرخهٔ عمر {#lifecycle-behavior}

<a id="رفتار-lifecycle"></a>

قبل از establishment:

- `Init` در upstream فقط محلی است.
- upstream payload به‌عنوان probe یا اولین payload بعد از probe در نظر گرفته می‌شود
- آخرین `Pause` در upstream برای ارسال پس از Init سمت next نگه داشته می‌شود؛ `Resume` آن را لغو می‌کند، حتی هنگام ورود مجدد در Init.
- `Est`، `Pause` و `Resume` در downstream عبور داده نمی‌شوند.
- payloadِ downstream در این مرحله غیرمنتظره است؛ بافر آن برای استفاده مجدد برمی‌گردد و line بسته می‌شود.

بعد از establishment:

- payloadِ upstream به `next` فرستاده می‌شود.
- payloadِ downstream به گره قبلی می‌رود.
- Pause و Resume در upstream، از جمله اعلان‌های تکراری، به `next` فرستاده می‌شوند.
- Est، Pause و Resume در downstream، از جمله اعلان‌های تکراری، به گره قبلی می‌روند.

پس از اتمام Init سمت next، ارسال Pause باقی‌مانده و تخلیه همه ورودی پذیرفته‌شده،
سرور وضعیت خط را آزاد و کاملاً صفر می‌کند و روی همان line برای همیشه bypass می‌شود.
این کار برای Est یا Resume منتظر نمی‌ماند. Pause یا Resume تازه هنگام Init، ارسال
درخواست قدیمی را لغو می‌کند. callback‌های بعدی مستقیماً میان همسایه‌ها عبور می‌کنند.

پیش از bypass، با دریافت `Finish` در upstream، سرور وضعیت محلی را از بین می‌برد. تنها در صورتی `Finish` را در upstream منتشر می‌کند که `next` قبلاً مقداردهی اولیه شده باشد. اگر پیش از ایجاد سمت `next` خطای پروتکل رخ دهد، فقط سمت previous بسته می‌شود، زیرا هنوز line‌ای در سمت next وجود ندارد.

### پشتیبانی از splice و آزادسازی وضعیت راه‌اندازی {#splice-support-and-setup-retirement}

<a id="پشتیبانی-از-splice-و-بازنشستگی-state-راهاندازی"></a>

هر دو گره، بافر عادی و payload موجود در pipe خصوصی را می‌پذیرند. هر delivery که وارد parsing
handshake یا ترتیب‌دهی هنگام انتخاب child شود، با `sbufEnsureOrdinary()` کامل به بافر عادی تبدیل
می‌شود. FIFO برنامه بافر را بدون خواندن محتوا نگه می‌دارد. نشانگر کامل پنج‌بایتی می‌تواند تا 2 MiB
داده برنامه همراه داشته باشد؛ نشانگر از سقف داده برنامه کم نمی‌کند و نشانگر ناقص حداکثر چهار بایت دارد.

پس از راه‌اندازی و تخلیه FIFO، client فضای handshake و صف خالی را آزاد می‌کند، اما نگاشت main به child
منتخب و کنترل جریان endpoint برای payload، فشار و Finish باقی می‌ماند. server پس از اتمام Init سمت backend
و replay، همه وضعیت خط را آزاد و صفر می‌کند و روی همان line برای همیشه bypass می‌شود. payload آماده بدون
inspection، materialization یا سقف backlog راه‌اندازی عبور می‌کند. server همچنان backend را با نخستین
payload برنامه مقداردهی می‌کند؛ childهای بازنده اتصال backend نمی‌سازند. برای TCP آماده، ترجیح خواندن عادی ثبت نمی‌شود.
