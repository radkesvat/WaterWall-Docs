# ConnectionStripeServer

`ConnectionStripeServer` اتصال‌های ساخته‌شده توسط `ConnectionStripeClient` را
به یک جریان مرتب و دوطرفه تبدیل می‌کند. برای گروه هشت‌عضوی، هشت transport را
می‌پذیرد و دقیقاً یک line از مسیر `next` می‌سازد. هر عضو می‌تواند هم upload و
هم download را حمل کند.

```text
TcpListener -> TlsServer -> ConnectionStripeServer -> TcpConnector
```

تمام اعضای یک گروه باید به همین نمونهٔ node در یک فرایند WaterWall برسند.
هر transport باید stream قابل‌اعتماد و مرتب فراهم کند؛ رکوردهایی که از
اعضای متفاوت با ترتیب متفاوت می‌رسند، در این node بازچینی می‌شوند.

برای TLS، `TlsServer` را قبل از این node قرار دهید تا frameهای رمزگشایی‌شدهٔ
Stripe را دریافت کند. برای KCP از
`UdpListener -> KcpServer -> ConnectionStripeServer` استفاده کنید تا KCP
stream قابل‌اعتماد را فراهم کند. framing در Stripe از UDP مستقیم یا حفظ مرز
پیام‌های برنامه پشتیبانی نمی‌کند. مسیرهای transport متناظر در صفحهٔ
[ConnectionStripeClient](ConnectionStripeClient.mdx) آمده‌اند.

گروه‌ها محلی و متعلق به همین نمونهٔ node هستند. فرایندها یا replicaهای مجزای
سرور جدول session مشترک ندارند؛ load balancer خارجی باید تمام اعضای هر گروه
را به همان نمونه برساند. این node تنظیم `pair` ندارد.

## اشتراک گروه Stripe با Mux

برای اتصال چند برنامه به یک سرویس ثابت، این دو زنجیره را جفت کنید:

```text
Server 1: TcpListener -> MuxClient -> ConnectionStripeClient -> TcpConnector
Server 2: TcpListener -> ConnectionStripeServer -> MuxServer -> TcpConnector(service)
```

سرور Stripe از هر گروه یک جریان parent از نوع Mux بازسازی می‌کند. MuxServer
برای هر child رمزگشایی‌شده یک اتصال سرویس جدا باز می‌کند؛ بنابراین یک گروه
می‌تواند به چند برنامه خدمت دهد. `max-connections` سقف اعضای هر گروه است، نه
تعداد childها یا اتصال‌های سرویس. Mux محدودیت‌های مستقل child و buffering دارد.
برای TLS، TlsClient بعد از StripeClient و TlsServer قبل از StripeServer قرار
می‌گیرد.

این ترکیب وقتی مفید است که سقف upload یا download برای هر اتصال TCP بین دو
سرور مستقل باشد و ظرفیت مجموع مسیر آزاد باشد. سقف مشترک لینک، مجموع هر IP یا
ظرفیت سرویس افزایش نمی‌یابد. تأخیر بازچینی میان childهای گروه مشترک است و قطع
هر عضو، گروه و childهایش را پایان می‌دهد؛ بسته‌شدن عادی یک child، siblingها را
نمی‌بندد.

Mux اتصال سرویس را بعد از اولین payload هر child باز می‌کند. برای سرویس‌هایی
که ابتدا پیام خوشامد می‌فرستند، نمونهٔ بدون Mux را انتخاب کنید. شمارش اتصال‌ها
در [مرجع کلاینت](ConnectionStripeClient.mdx) و هر دو پیکربندی در
[نمونهٔ کامل TLS به انگلیسی](https://radkesvat.github.io/WaterWall-Docs/docs/examples/tunnels/connection-stripe-tls)
توضیح داده شده‌اند.

## تنظیمات

```json
{
  "name": "stripe-server",
  "type": "ConnectionStripeServer",
  "next": "destination",
  "settings": {
    "max-connections": 32
  }
}
```

### فیلدهای اصلی

| فیلد | الزام |
| --- | --- |
| `name` | نام الزامی node که باید در پیکربندی یکتا باشد. |
| `type` | دقیقاً `"ConnectionStripeServer"`. |
| `next` | نام الزامی و غیرخالی node ورودی مسیر سمت برنامه. |
| `settings` | شیء اختیاری؛ تنظیمات حذف‌شده از مقادیر پیش‌فرض زیر استفاده می‌کنند. |

### تنظیمات node

همهٔ تنظیمات اختیاری‌اند، اما مقدار ارائه‌شده باید عدد صحیح باشد؛ رشته، مقدار
اعشاری، boolean و null پذیرفته نمی‌شوند. اگر `settings` ارائه شود، باید شیء باشد.

| تنظیم | پیش‌فرض | کاربرد |
| --- | --- | --- |
| `max-connections` | `32` | سقف اعضای هر گروه، از `1` تا `32`؛ این مقدار سقف تعداد کل sessionها نیست. |
| `receive-window-bytes` | `1048576` | سقف بایت مصرف‌نشدهٔ مجاز برای ارسال همتا؛ از `16384` تا `16777216`. |
| `max-buffered-bytes` | `4194304` | سقف مستقل بایت و هزینهٔ حافظه برای صف برنامه و parser هر عضو؛ از `65536` تا `67108864`. |
| `setup-timeout-ms` | `10000` | مهلت تکمیل گروه ورودی، از `1` تا `600000` میلی‌ثانیه. |
| `drain-timeout-ms` | `10000` | مهلت پایان مرتب پروتکل، از `1` تا `600000` میلی‌ثانیه. |
| `max-sessions` | `1024` | حداکثر session هم‌زمان نگه‌داری‌شده روی هر worker، از `1` تا `65536`. |
| `max-pending-connections` | `1024` | حداکثر line منتظر JOIN کامل روی هر worker، از `1` تا `65536`. |

نام تنظیم ناشناخته یا تکراری باعث رد تنظیمات می‌شود. بررسی انقضا روی worker
با فاصلهٔ یک ثانیه انجام می‌شود؛ مقدار کوچک میلی‌ثانیه دقت زیرثانیه‌ای را تضمین
نمی‌کند. مهلت drain با اولین Finish محلی یا CLOSE همتا آغاز می‌شود و پیشرفت
بعدی آن را تمدید نمی‌کند.

کلاینت تعداد هر گروه را با `connections` انتخاب می‌کند؛ سرور مقدار بیشتر از
`max-connections` را رد می‌کند. پنجرهٔ دریافت دو طرف می‌تواند متفاوت باشد.

## معنای محدودیت‌ها

`max-connections: 32` گروه هشت‌عضوی کلاینت را می‌پذیرد؛ منتظر ۳۲ عضو نمی‌ماند
و ۳۲ اتصال مقصد نمی‌سازد. هر گروه کامل یک line برنامه از مسیر `next` می‌سازد.
با `TcpConnector` مستقیم در آن مسیر، ۱۰۰ گروه هشت‌عضوی شامل ۸۰۰ اتصال transport
ورودی و ۱۰۰ اتصال مقصد هستند.

`receive-window-bytes` سرور اعتبار **upload** کل گروه را کنترل می‌کند. همین
تنظیم در کلاینت، اعتبار **download** را کنترل می‌کند. هیچ‌کدام در تعداد اعضا
ضرب نمی‌شوند. سقف ثابت ۲۵۶ رکورد هم اعمال می‌شود؛ با رکوردهای ۱۶ KiB، حتی با
پنجرهٔ بایتی بزرگ‌تر، بیش از ۴ MiB دادهٔ DATA نمی‌تواند تأییدنشده بماند.

صف برنامهٔ معلق در سرور شامل دادهٔ download است که منتظر ظرفیت transport یا
اعتبار کلاینت می‌ماند. `max-buffered-bytes` آن صف و parser هر transport را
مستقل از هم محدود می‌کند. حافظهٔ بازچینی ورودی، bufferهای transport و گروه‌های
دیگر جدا هستند؛ این تنظیم بودجهٔ کل حافظه نیست.

`max-pending-connections` lineهای ورودی را **پیش از کامل‌شدن JOIN** می‌شمارد.
وقتی JOIN معتبر یک line را به گروه متصل کند، آن line از شمارش pending خارج
می‌شود. `max-sessions` تعداد گروه‌ها را، از جمله گروه‌های ناقص و در حال drain،
می‌شمارد. هر دو محدودیت پذیرش برای هر worker جداگانه اعمال می‌شوند؛ ممکن است
یک worker به سقف خود برسد در حالی که دیگری هنوز ظرفیت دارد.

## گروه‌بندی و workerها

JOIN هر عضو شامل شناسهٔ تصادفی ۱۲۸ بیتی گروه، اندیس یکتا، تعداد اعضا و پنجرهٔ
دریافت کلاینت است. اندیس تکراری و مشخصات ناسازگار رد می‌شوند. گروه ناقص پس از
مهلت setup بسته می‌شود. گروه فعال در جدول باقی می‌ماند تا معرفی دیرهنگام باعث
ساخته‌شدن line برنامهٔ دوم برای همان گروه نشود.

hash کلیددار شناسهٔ کامل گروه، worker پردازش را مشخص می‌کند. PipeTunnel در صورت
نیاز اعضا را به آن worker منتقل می‌کند و مسیر برگشت هر transport حفظ می‌شود.
سرور مالک line برنامهٔ بازسازی‌شده است؛ lineهای transport ورودی قرضی هستند.

پیش از Init شدن node بعدی، context آدرس مبدأ عضو صفر، شامل IP و port، به line
برنامه منتقل می‌شود. انتقال بین workerها این اطلاعات را حفظ می‌کند تا مسیریابی
و محدودسازی بر اساس IP مبدأ در nodeهای بعدی همان مقادیر را ببینند.

پس از حضور همهٔ اعضا، سرور دقیقاً یک line از `next` راه‌اندازی و READY ارسال
می‌کند. این کار به payload برنامه وابسته نیست؛ در مسیر مستقیم بدون Mux، مقصد
می‌تواند ابتدا داده بفرستد. با Mux، اتصال سرویس هر child همچنان منتظر اولین
payload می‌ماند. node تا پایان session برای نگاشت lineها، framing، فشار و پایان
در مسیر callbackها فعال می‌ماند.

## ترتیب و حافظه

دو جهت offset بایت و اندیس رکورد مستقل دارند. هر DATA حداکثر `16384` بایت
دارد. گیرنده فقط دادهٔ پیوسته را تحویل می‌دهد و اعتبار کل گروه را اعلام می‌کند.
فرستنده هم‌زمان حداکثر به اندازهٔ پنجرهٔ اعلام‌شده بایت مصرف‌نشده و `256`
رکورد DATA تأییدنشده نگه می‌دارد.

حافظهٔ بازچینی ورودی محدود و از صف دادهٔ ارسال‌نشدهٔ برنامه مستقل است. صف
برنامه هر دو سقف بایت منطقی و هزینهٔ حافظهٔ `max-buffered-bytes` را رعایت می‌کند.
پنجرهٔ دریافت سقف کل حافظهٔ فرایند نیست؛ transportها و برنامه bufferهای خود را دارند.

ارسال میان اعضای قابل‌نوشتن پخش می‌شود و اعضای Pauseشده انتخاب نمی‌شوند.
عضو کندی که بایت بعدی را حمل می‌کند همچنان می‌تواند تحویل را عقب بیندازد.
فشار برنامه، تحویل داده و اعتبار جدید را متوقف می‌کند؛ پیام‌های کنترلی برای
پیشرفت پروتکل همچنان قابل‌پردازش هستند.

## پایان و محدودیت‌ها

Finish کل line برنامه را می‌بندد و API جداگانهٔ TCP half-close وجود ندارد.
CLOSE تعداد نهایی بایت‌ها و رکوردها را مشخص می‌کند. حتی اگر زودتر از داده‌های
پیشین برسد، تأیید آن پس از تحویل همهٔ آن داده‌ها ارسال می‌شود. line جداشدهٔ
برنامه دوباره استفاده نمی‌شود و تخلیهٔ پروتکل مهلت محدود دارد. قطع غیرمنتظرهٔ
هر عضو تمام session را متوقف می‌کند؛ ارسال مجدد بین اعضا وجود ندارد.
پس از Finish محلی، دادهٔ برگشتی برای line پایان‌یافته مصرف و کنار گذاشته می‌شود.

شناسهٔ گروه احراز هویت و رمزنگاری فراهم نمی‌کند. چند اتصال می‌تواند استفاده
از ظرفیت آزاد را بهتر کند، اما ظرفیت گلوگاه مشترک را افزایش نمی‌دهد. با
TcpConnector مستقیم، هر گروه یک اتصال مقصد دارد؛ با MuxServer، هر child اتصال
مقصد جداگانه دارد.

## عیب‌یابی

| نشانه | موارد قابل‌بررسی |
| --- | --- |
| اتصال‌های ورودی دیده می‌شوند، ولی اتصال مقصد ساخته نمی‌شود | سرور منتظر همهٔ اعضای متمایز می‌ماند. بررسی کنید که همه به همین نمونه برسند، تعداد کلاینت از `max-connections` بیشتر نباشد و transport قبلی stream موردانتظار را بازسازی کند. |
| اتصال یا گروه ناقص پس از setup ناپدید می‌شود | مهلت setup و سقف‌های پذیرش را بررسی کنید. JOIN ناقص یک جایگاه pending می‌گیرد؛ JOIN کاملِ منتظر سایر اعضا از ظرفیت session استفاده می‌کند. |
| فقط upload یا download متوقف می‌شود | فشار برنامهٔ گیرنده و پنجرهٔ Stripe گیرنده برای همان جهت را بررسی کنید. نرسیدن یک رکورد قبلی می‌تواند تحویل رکوردهای بعدی از اعضای سالم را هم عقب بیندازد. |
| افزایش تعداد workerها یک stream را سریع‌تر نمی‌کند | هر گروه روی یک worker بازسازی می‌شود. workerهای بیشتر می‌توانند گروه‌های دیگر را پردازش کنند، ولی بازچینی یک گروه را تقسیم نمی‌کنند. |

## متادیتای node

مقادیر زیر از `instance/node.c` و ثابت‌های مشترک framing گرفته شده‌اند:

| ویژگی | مقدار |
| --- | --- |
| node flags | `kNodeFlagBlocksSplice` |
| `can_have_prev` | `true` |
| `can_have_next` | `true` |
| `layer_group` | `kNodeLayer4` |
| `layer_group_prev_node` | `kNodeLayer4` |
| `layer_group_next_node` | `kNodeLayer4` |
| `required_padding_left` | `24` بایت (`kStripeHeaderSize`) |

`can_have_next` قابلیت توپولوژی را توصیف می‌کند؛ سازندهٔ این node وجود `next`
را الزامی می‌داند. splice در زنجیره‌های دارای این node غیرفعال است.
PipeTunnel داخلی انتقال پردازش بین workerها را انجام می‌دهد و الزامات لایه
یا مسیر `next` سمت برنامهٔ node پیکربندی‌شده را تغییر نمی‌دهد.

[نمونهٔ کامل TLS به انگلیسی](https://radkesvat.github.io/WaterWall-Docs/docs/examples/tunnels/connection-stripe-tls)
و فایل‌های آمادهٔ [با Mux](https://github.com/radkesvat/WaterWall/tree/main/tunnels/ConnectionStripeClient/examples/tls-mux)
و [بدون Mux](https://github.com/radkesvat/WaterWall/tree/main/tunnels/ConnectionStripeClient/examples/tls)
در دسترس هستند.
