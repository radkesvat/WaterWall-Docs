# گره TunDevice {#tundevice-node}

## نمای کلی {#overview}

`TunDevice` رابط TUN را به WaterWall متصل می‌کند. بسته‌های IP را از دستگاه شبکهٔ مجازی می‌خواند و وارد زنجیره می‌کند؛ بسته‌های IP را نیز از زنجیره در همان دستگاه TUN می‌نویسد.

این گره یک آداپتور لایهٔ ۳ است، نه تونلی اتصال‌محور.

`device-mtu` یک بار هنگام ساخت تعیین و اعتبارسنجی می‌شود. هر نمونه MTU مستقل
خود را نگه می‌دارد؛ تنظیم node‌های دیگر آن را تغییر نمی‌دهد. مقدار نامعتبر ارث‌رسیده
از `misc.mtu` هسته به override صریح و معتبر همان node نیاز دارد.

برای تونل‌های Ping یا Ping6، [نیازمندی‌های راه‌اندازی متناسب با مسیر](#using-tundevice-with-ping-and-ping6) را ببینید.

### کارهایی که انجام می‌دهد {#what-it-does}

- رابط TUN را ایجاد و پیکربندی می‌کند.
- آدرس IP و ماسک زیرشبکه را به دستگاه اختصاص می‌دهد.
- دستگاه را فعال می‌کند.
- بسته‌ها را از دستگاه می‌خواند و به سمت مجاور در زنجیره می‌فرستد.
- بسته‌های دریافتی از زنجیره را در دستگاه می‌نویسد.
- در صورت درخواست بافر بسته، checksum را پیش از نوشتن دوباره محاسبه می‌کند.

<a id="جایگاه-رایج"></a>

## جایگاه معمول در زنجیره {#typical-placement}

`TunDevice` می‌تواند در هر یک از دو انتهای زنجیره قرار بگیرد:

- اگر آخرین گره باشد، بسته‌های خوانده‌شده از دستگاه TUN به گره قبلی فرستاده می‌شوند.
- در غیر این صورت، بسته‌های خوانده‌شده از دستگاه TUN به گره بعدی فرستاده می‌شوند.

محتوای رسیده به `TunDevice` از هر دو سمت، در رابط TUN نوشته می‌شود.

<a id="انتخاب-مسیر-packet"></a>
<a id="معنی-آدرس-tun"></a>

### انتخاب مسیر بسته {#choosing-the-packet-path}

برای gateway از نوع IPv4 TCP/UDP با socketهای خروجی معمول:

```text
TunDevice -> PacketsToConnection -> TcpUdpConnector
```

از [تنظیم connector با حفظ مقصد](./PacketsToConnection.mdx#typical-placement)
استفاده کنید و اگر ورودی ممکن است fragmented باشد،
`fragment-policy: "reassemble"` را نگه دارید. این مسیر جریان TCP/UDP را حمل
می‌کند؛ ICMP ping آزمون مناسبی برای این bridge نیست.

برای حفظ packetهای کامل IPv4 میان دو میزبان:

```text
client: TunDevice -> PacketsToStream -> TlsClient -> TcpConnector
server: TcpListener -> TlsServer -> StreamToPackets -> TunDevice
```

[راه‌اندازی packet روی TLS](./PacketsToStream.mdx#packet-over-tls) مسئولیت‌های
transport و routing را توضیح می‌دهد. [نمونهٔ تونل بسته با WireGuard](../03-examples/tunnels/wireguard.mdx)
پیکربندی هر دو میزبان را نشان می‌دهد. در سمت سرور، TUN در انتهای زنجیرهٔ
`UdpListener -> WireGuardServer(mode=packet) -> TunDevice` قرار می‌گیرد.

این نمودارها نوع node را نشان می‌دهند، نه نام آن در JSON. آدرس interface و
route ترافیک موردنظر به TUN را تنظیم کنید؛ `device-ip` به‌تنهایی همهٔ مقصدهای
برنامه را انتخاب نمی‌کند. peer بیرونی TCP/UDP باید خارج از تونل قابل دسترسی
بماند. برای LAN مسیریابی‌شده، forwarding میزبان و مسیر برگشت نیز لازم است.

## نمونهٔ کاربردی ساده {#minimal-practical-example}

این نمونه قطعه‌ای از پیکربندی گره است؛ همسایه‌ها و همتاهای ارجاع‌شده را در همان استقرار تعریف کنید.

این قطعه یک TUN با IPv4 دارد و GSO را صریحاً غیرفعال می‌کند؛ بنابراین رابط‌های از پیش ساخته‌شدهٔ Linux را نیز پوشش می‌دهد. نام و آدرس دستگاه را جایگزین کنید و `next-node-name` را به‌عنوان مسیر بسته تعریف کنید. این نمونه هیچ مسیر سیستمی نصب نمی‌کند. MTU را برای تمام مسیر کپسوله‌شده انتخاب کنید؛ مسیرهای Ping و Ping6 به بازسازی fragmentها نیاز دارند و باید در [محدودهٔ MTU حالت مربوطه](#using-tundevice-with-ping-and-ping6) باشند. راه‌اندازی پلتفرم و حالت‌های مسیریابی در ادامه آمده‌اند. در Linux، رابط جدید دریافت چندصفی را امتحان می‌کند و در صورت نبود امکان، به یک صف برمی‌گردد؛ دریافت در پلتفرم‌های دیگر متفاوت است. نمونه، آدرس IPv4 دستگاه را تنظیم می‌کند.

```json
{
  "name": "tun0-adapter",
  "type": "TunDevice",
  "settings": {
    "device-name": "tun0",
    "device-ip": "10.10.0.1/24",
    "device-mtu": 1500,
    "gso": false,
    "route-table": "off"
  },
  "next": "next-node-name"
}
```

برای پیش‌فرض‌ها و الزام‌های مشروط، [پیکربندی](#configuration) و برای نمونه‌های کامل و محدودیت‌های عملیاتی، [کاربرد و رفع اشکال](#usage-and-troubleshooting) را ببینید.

## پیکربندی {#configuration}

<a id="تنظیمات-ضروری"></a>

### فیلدهای ضروری JSON {#required-json-fields}

#### فیلدهای سطح بالا {#top-level-fields}

- `name` `(string)`
  نامی که کاربر برای این گره انتخاب می‌کند.

- `type` `(string)`
  باید دقیقاً برابر با `"TunDevice"` باشد.

#### `settings` {#settings}

- `device-name` `(string)`
  نام رابط TUN که باید ساخته یا باز شود.

- `device-ip` `(string)`
  آدرس IPv4 رابط و زیرشبکه در قالب CIDR. IPv6 رد می‌شود، زیرا مسیر دادهٔ بسته فقط IPv4 را پشتیبانی می‌کند.
  نمونه: `"10.10.0.1/24"`

  پیاده‌سازی فعلی آن را به این دو بخش تقسیم می‌کند:
  - آدرس IP دستگاه
  - طول ماسک زیرشبکه

### فیلدهای اختیاری `settings` {#optional-settings-fields}

- `opaque-flow-mode` `(string)`
  سیاست دریافت IPv4 با محتوای نامشخص: `prefix` (پیش‌فرض)، `peer`، `spread` یا `auto`.
  جزئیات انتخاب و محدودیت‌ها در بخش `opaque-flow-mode` در ادامه آمده است.

- `device-mtu` `(integer)`
  MTU رابط TUN در بازهٔ بستهٔ `68..65535`. اندازهٔ بسته‌هایی را کنترل می‌کند که سیستم‌عامل از رابط به WaterWall می‌فرستد؛ سقف اندازهٔ بسته‌هایی نیست که WaterWall به سیستم‌عامل بازمی‌گرداند. عدد کسری، رشته، مقدار بولی و `null` رد می‌شوند.

  پیش‌فرض: MTU سراسری WaterWall.

- `multi-queue` `(boolean)`
  به Linux اجازه می‌دهد برای هر worker رویداد یک صف TUN بسازد. پیش‌فرض: `true`.
  نبود پشتیبانی چندصفی یا هدایت ثابت، یا رد شدن راه‌اندازی صف اضافی، به‌طور خودکار یک صف با مالکیت worker صفر را انتخاب می‌کند.

  مقدار `false` راه‌اندازی چندصفی را غیرفعال می‌کند و از یک صف متعلق به worker صفر استفاده می‌کند. workerهای دیگر همچنان بسته‌های تخصیص‌یافته به خود را پردازش می‌کنند؛ تعداد workerهای تنظیم‌شده تغییر نمی‌کند. خواندن و نوشتن از مجموعهٔ صف حاصل استفاده می‌کنند. این گزینه مستقل از `gso` است. نوع نامعتبر، از جمله `null`، در همهٔ پلتفرم‌ها رد می‌شود. پلتفرم‌های غیر Linux مقدار بولی را می‌پذیرند و نادیده می‌گیرند.

- `kernel-queue-tune` `(boolean)`
  تنظیم صف دریافت کرنل Linux هنگام راه‌اندازی. پیش‌فرض در Linux برابر `true` و در سایر پلتفرم‌ها `false` است. مقدار `false` طول صف موجود را تغییر نمی‌دهد؛ راه‌اندازی همچنان آن را گزارش می‌کند. مقدار معتبر در پلتفرم‌های دیگر اثری ندارد.

- `kernel-queue-length` `(integer)`
  طول درخواستی صف TUN در Linux بر حسب تعداد بسته **به‌ازای هر صف دریافت**. حذف گزینه، پیش‌فرض پروفایل RAM توضیح‌داده‌شده در ادامه را انتخاب می‌کند. مقدار باید عدد صحیح در بازهٔ `1..2147483647` (`INT_MAX`) باشد؛ `0` به معنی انتخاب خودکار نیست. صف موجود بزرگ‌تر حفظ می‌شود. مقدار صریح فقط هنگام فعال بودن `kernel-queue-tune` اعمال می‌شود.

  نوع هر دو گزینهٔ صف در همهٔ پلتفرم‌ها، حتی هنگام غیرفعال بودن تنظیم صف، بررسی می‌شود. برای `kernel-queue-length` عدد کسری، رشته، مقدار بولی و `null` نامعتبرند؛ `kernel-queue-tune` مقدار بولی می‌خواهد.

- `gso` `(boolean)`
  درخواست واگذاری segmentation برای TCPv4 در Linux. پیش‌فرض همچنان `true` است؛ `false` تقسیم‌بندی را غیرفعال می‌کند، اما هر دستگاه تازهٔ Linux همچنان checksum offload را امتحان می‌کند. نوع نامعتبر، از جمله `null`، رد می‌شود. پشتیبانی checksum offload به‌طور خودکار مذاکره می‌شود. حالت نهایی فعال در گزارش راه‌اندازی ثبت می‌شود:

  | حالت فعال | قالب‌بندی | قابلیت‌ها |
  | --- | --- | --- |
  | بازگشت به حالت خام | بایت‌های IP | بدون offload |
  | فقط checksum | هدر 10 بایتی little-endian از نوع virtio + IP | `TUN_F_CSUM` |
  | checksum و TCPv4 GSO | همان قالب virtio | `TUN_F_CSUM \| TUN_F_TSO4` |

  Linux ابتدا پشتیبانی checksum را مذاکره می‌کند و سپس در صورت درخواست به GSO ارتقا می‌دهد. رد شدن ارتقای GSO حالت checksum-only را حفظ می‌کند. نبود پشتیبانی checksum/قالب‌بندی یا منابع مشترک دریافت، حالت خام را انتخاب می‌کند. پلتفرم‌های غیر Linux قالب معمول فعلی را حفظ می‌کنند. MTU تنظیم‌شده همچنان اندازهٔ هر بستهٔ خروجی segmentation را محدود می‌کند. اصلاح‌کنندهٔ ECN مربوط به TCPv4 GSO در Linux، اگر در رکورد دستگاه با GSO فعال وجود داشته باشد، پشتیبانی می‌شود.

  > **رابط‌های از پیش ساخته‌شده در Linux:** درخواست GSO به نام رابط جدید نیاز دارد. برای اتصال به TUN از پیش ساخته‌شده باید `"gso": false` را صریحاً تنظیم کنید تا رفتار اتصال معمول حفظ شود؛ حتی اگر قبلاً این گزینه حذف شده بود. بازگشت خودکار هنگام نبود امکانات offload، تداخل نام رابط را بی‌صدا نمی‌پذیرد. آزمون checksum انحصاری است؛ رابط خام از پیش ساخته‌شده با قالب خام و بدون مذاکرهٔ offload روی آن رابط متصل می‌شود.

- `route-table` `(string)`
  نصب مسیرهای بومی سیستم را کنترل می‌کند.

  پیش‌فرض: `"off"`

  مقدارهای پشتیبانی‌شده:
  - `"off"`: هیچ مسیری نصب نمی‌شود.
  - `"main"` یا `"auto"`: مسیرها در جدول معمول مسیریابی پلتفرم نصب می‌شوند.
  - فقط Linux: شماره یا نام جدول مسیریابی قابل‌قبول برای `ip route`.

- `system-route` `(boolean)`
  میان‌بری برای مسیریابی کامل دستگاه. اگر `true` باشد و `route-table` تنظیم نشده باشد، مانند `"route-table": "main"` رفتار می‌کند.

  پیش‌فرض: `false`

- `windows-kill-switch-owner` (بولی، پیش‌فرض `false`)
  اگر چند `TunDevice` در فایل‌های بارگذاری‌شده مالک رابط خود باشند و مسیرهایشان تمام
  فضای IPv4 را پوشش دهند، در اجرای محافظت‌شدهٔ ویندوز این گزینه را فقط روی یکی از
  آن‌ها `true` کنید. اگر فقط یک گره واجد شرایط باشد، خودکار انتخاب می‌شود. حذف گزینه
  یا مقدار `false` مانع انتخاب خودکار نیست. قفل با گزینهٔ `"windows-kill-switch": true`
  در فایل هسته فعال می‌شود. برای خروج فیزیکی، launcher از میان رابط‌های فیزیکیِ متصل،
  مسیر پیش‌فرض IPv4 با کمترین مجموع متریک مسیر و رابط را انتخاب می‌کند.
  انتخاب مالک، مجوز فایروال را تعیین می‌کند. اولویت مسیرهای
  رابط‌ها همچنان تابع پیشوند و متریک آن‌ها در ویندوز است.

- `route-cidrs` `(array of strings)`
  CIDRهای IPv4 که هنگام فعال بودن مسیریابی باید به رابط TUN هدایت شوند.

  وجود هر CIDR مربوط به IPv6 در فهرست فعال capture، ساخت گره را پیش از اعمال استثناها یا نصب مسیر رد می‌کند. فهرست مختلط IPv4/IPv6 نیز رد می‌شود، حتی اگر استثناها ورودی IPv6 را حذف می‌کردند. `"route-table": "off"` هیچ مسیری نصب نمی‌کند و CIDRهای capture را استفاده نمی‌کند.

  پیش‌فرض: مسیر کامل IPv4، یعنی `"0.0.0.0/0"`.
  مسیر پیش‌فرض به‌صورت دو مسیر `/1` نصب می‌شود تا نیازی به جایگزینی مسیر پیش‌فرض موجود نباشد.

- `route-exclude-cidrs` `(array of strings)`
  CIDRهایی که باید از مسیرهای نصب‌شده با `route-cidrs` کنار گذاشته شوند. استثناهای خانوادهٔ دیگر بر مسیرهای capture مربوط به IPv4 اثری ندارند.

  وقتی `route-cidrs` سراسری است و بعضی محدوده‌های محلی، مدیریت یا endpoint بالادست باید از مسیر فعلی سیستم استفاده کنند، این گزینه مفید است.

- `dns` `(array of IPv4 strings)`
  سرورهای DNS مرتبط با رابط TUN.

  آرایه باید یک یا دو آدرس IPv4 معتبر داشته باشد. نام میزبان، آدرس IPv6، رشتهٔ خالی و بیش از دو ورودی هنگام ساخت گره رد می‌شوند.

  `null` مانند حذف گزینه است.

  Linux از تنظیم DNS روی رابط از پیش ساخته‌شده با `gso: false` پشتیبانی می‌کند. برای چنین اتصالی، `busctl` پیش از هر تغییر DNS، سرورهای DNS و دامنه‌های جست‌وجو/مسیریابی موجود systemd-resolved را می‌خواند. پاک‌سازی این فیلدها را با ترتیب اصلی بازمی‌گرداند و تنظیمات نامرتبط resolver را بازنشانی نمی‌کند. اگر وضعیت اولیه خوانده نشود، تنظیم DNS بدون تغییر آن شکست می‌خورد. تغییرهای خارجی شناسایی‌شده دست‌نخورده می‌مانند و پاک‌سازی ناقص گزارش می‌شود. تغییر DNS هر رابط را با دیگر مدیرهای شبکه هماهنگ کنید؛ عملیات خواندن/مقایسه/نوشتن systemd میان فرایندها تراکنش اتمی نیست. فرمان‌های داخلی مهلت هفت‌ثانیه‌ای خود را حفظ می‌کنند.

  در Linux این قابلیت به `systemd-resolved` / `resolvectl` نیاز دارد؛ سرورهای DNS و دامنهٔ مسیریابی `~.` را تنظیم می‌کند تا هنگام فعال بودن دستگاه، این سرورها مسیر پیش‌فرض resolver باشند. در Windows، با `netsh` سرورهای IPv4 DNS ثابت روی آداپتور Wintun تنظیم می‌شوند؛ تقدم DNS همچنان تابع metric رابط‌های Windows است. تنظیم DNS برای TUN در macOS هنگام ساخت گره رد می‌شود؛ برای تنظیم resolver مختص پلتفرم از `post-up-script` / `pre-down-script` استفاده کنید.

- `loop-protection` `(boolean)`
  هنگامی که TUN مسیر سیستمی/کامل است، از هدایت دوبارهٔ ترافیک خروجی خود WaterWall به TUN و ایجاد حلقهٔ مسیریابی جلوگیری می‌کند.

  پیش‌فرض: با فعال شدن مسیریابی سیستمی فعال می‌شود، یعنی از `system-route` / `route-table` پیروی می‌کند؛ در غیر این صورت غیرفعال است. برای غیرفعال کردن صریح، `false` بگذارید.

  در حالت فعال، `TunDevice` پیش از نصب مسیرهای TUN، رابط فیزیکی پیش‌فرض فعلی را ثبت می‌کند و آن را به‌عنوان egress pin سراسری فرایند منتشر می‌کند. سوکت‌های آداپتور خروجی مانند `TcpConnector`، `UdpConnector` و `UdpStatelessSocket` این pin را اعمال می‌کنند، مگر اینکه گزینهٔ `interface` خودشان صریحاً تنظیم شده باشد.

- `post-up-script` `(string)`
  فرمان اختیاری پوسته که پس از فعال شدن رابط و نصب مسیرهای بومی اجرا می‌شود.

- `pre-down-script` `(string)`
  فرمان اختیاری پوسته که پیش از حذف مسیرهای بومی و پایین آوردن رابط اجرا می‌شود.

### سیاست‌های دریافت بسته {#packet-receive-policies}

<a id="گزینهٔ-opaque-flow-mode"></a>

#### `opaque-flow-mode` (اختیاری، پیش‌فرض: `prefix`) {#opaque-flow-mode-optional-default-prefix}

پیش‌فرض `prefix` است، حتی کنار decoder مربوط به Ping. فقط stringهای دقیق
`prefix`، `peer`، `spread` و `auto` پذیرفته می‌شوند؛ string خالی یا ناشناخته،
`null` و نوع‌های دیگر در همهٔ پلتفرم‌ها رد می‌شوند. RawSocket در حالت write-only
نیز مقدار را اعتبارسنجی می‌کند، هرچند دریافت ندارد. این گزینه از `multi-queue`،
`gso` و `fragment-policy` مستقل است؛ با یک صف دریافت نیز همهٔ workerهای پردازش
طبق همین سیاست استفاده می‌شوند.

برای IPv4 کامل و بدون fragment با protocol غیر از TCP برابر ۶ و UDP برابر ۱۷:

| مقدار | انتخاب worker دریافت |
| --- | --- |
| `prefix` | hash متقارن آدرس‌ها، protocol و چهار بایت اول payload به شکل دو عدد ۱۶ بیتی big-endian، همراه endpoint متناظر. |
| `peer` | فقط جفت آدرس و protocol؛ تمام payload نادیده گرفته می‌شود. |
| `spread` | پخش packet با سازوکار قبلی backend. |
| `auto` | یک بار هنگام startup طبق همسایهٔ مستقیم decoder به `peer` یا در غیر آن به `prefix` تبدیل می‌شود. |

prefix از انتهای header واقعی IPv4، شامل options، شروع می‌شود و باید داخل طول
اعلام‌شدهٔ IP باشد. payload کوتاه‌تر از چهار بایت از fallback آدرس/protocol
استفاده می‌کند. TCP/UDP در هر حالت از hash مشترک ۳۲ بیتی آدرس/port/protocol، یا
در صورت کوتاه‌بودن header از fallback آدرس/protocol استفاده می‌کند؛ flags، طول
transport و checksum شرط تشخیص flow نیستند. محدودهٔ IPv6 و سیاست fragment تغییر
نمی‌کند.

`prefix` تنها وقتی affinity می‌دهد که چهار بایت اول flow ثابت بماند؛ XOR ثابت
می‌تواند آن را حفظ کند، ولی encryption دلخواه یا mask متغیر چنین تضمینی ندارد.
`peer` همهٔ flowهای پنهان با جفت آدرس و protocol یکسان را روی یک worker جمع
می‌کند و ممکن است موازی‌سازی را کم کند. `spread` می‌تواند پیش از consumer ترتیب
packetها را تغییر دهد. consumer دارای state پس از decode یا بازنویسی tuple، مالک
خود را جداگانه تعیین می‌کند.

فقط `auto` توپولوژی نهایی را پیش از ساخت TUN یا فعال‌کردن capture بررسی می‌کند:
انتشار upstream به `next` تنها کنار همسایهٔ فیزیکی مستقیم با type دقیق
`PingServer` یا `Ping6Server` به `peer` می‌رسد؛ انتشار downstream به `prev` تنها کنار type دقیق
`PingClient` یا `Ping6Client` به `peer` می‌رسد. جهت encoding، node واسط، wrapper و هر حالت دیگر
`prefix` است. نام instance ملاک نیست؛ مقدار صریح همیشه اولویت دارد و RawSocket
مقابل هرگز `spread` را فعال نمی‌کند. اگر هر دو device مقدار `auto` داشته باشند:

```text
TunDevice -> PingClient -> RawSocket
  prefix                     peer

RawSocket -> PingServer -> TunDevice
   peer                     prefix
```

mode مؤثر در generation ثابت است و با fallback تک‌صف یا restart دوباره به رفتار
وابسته به صف تبدیل نمی‌شود. reader برای هر packet ترافیک یا chain را بررسی
نمی‌کند. گیرندهٔ Ping برای IPv4 بسته‌هایی را که در بررسی‌های حامل رد می‌شوند حذف می‌کند.
Ping6 بسته‌های معتبر و قطعه‌نشدهٔ IPv4 را که پروتکلشان با پروتکل حامل پیکربندی‌شده
فرق دارد، عبور می‌دهد. با Ping6، انتخاب خودکار `peer` این ترافیک opaque نامرتبط را
بر اساس جفت آدرس و پروتکل گروه‌بندی می‌کند. اگر برای ترافیک ترکیبی به توزیع دیگری
نیاز دارید، mode را صریح انتخاب کنید.
startup مقدار درخواستی، mode مؤثر، دلیل انتخاب و تعداد نهایی صف‌ها را log می‌کند.

<a id="fragment-policy-اختیاری-پیشفرض-reassemble"></a>

#### `fragment-policy` (اختیاری، پیش‌فرض: `reassemble`) {#fragment-policy-optional-default-reassemble}

حذف این تنظیم مقدار `reassemble` را انتخاب می‌کند: fragment‌های IPv4 پیش از
تحویل به chain بازسازی می‌شوند. `preserve-fragments` بایت‌ها و مرز fragment‌ها را
حفظ می‌کند. برای این policy فهرست مجاز نام node یا topology وجود ندارد؛ validation
عادی لایه‌ها و chain همچنان برقرار است. مقدار نامعتبر، از جمله `null`، startup را رد می‌کند.

ورودی packet در جهت upstream برای `PacketsToConnection` و در جهت downstream
برای `ConnectionToPackets` به datagram کامل IPv4 نیاز دارد. هر یک از این ورودی‌ها
fragmentهای پشتیبانی‌نشده را پیش از تحویل به پشته دور می‌ریزد، نخستین مورد را
به صورت warning گزارش می‌کند و موارد بعدی را بدون خاتمهٔ فرایند می‌شمارد. پیش از
این consumerها، مستقل از policy دستگاه یا nodeهای میانی، reassembly لازم است.
بیت DF به‌تنهایی fragment نیست؛ MF یا offset غیرصفر نشانهٔ fragmentation است.

بازسازی تا ۶۵٬۵۳۵ بایت را تحویل می‌دهد، ولی سقف خروجی nodeهای دیگر یا MTU
interface را بالا نمی‌برد و fragmentation دوبارهٔ خروجی را خودکار انجام نمی‌دهد.
نوشتن در TUN می‌تواند این datagramها را حتی با اندازهٔ بزرگ‌تر از `device-mtu`
به سیستم‌عامل تحویل دهد. محدودیت‌های نگهداری و مالکیت packet در بخش چهارم
راهنمای توسعه‌دهنده آمده است.

<a id="اندازهٔ-صف-دریافت-کرنل-در-linux"></a>

### اندازهٔ صف دریافت کرنل در Linux {#linux-kernel-receive-queue-sizing}

پس از ساخت صف‌ها و هر fallback به حالت تک‌صف، `kernel-queue-tune` هدف اولیهٔ
`txqueuelen` را با تعداد نهایی صف‌های دریافت تعیین می‌کند:

| RAM profile تنظیم‌شده | تعداد خودکار packet در هر صف |
| --- | ---: |
| S1 / S2 | 1,024 |
| M1 (`client`) | 2,048 |
| M2 (`client-larger`) | 4,096 |
| L1 / L2 (`server`) | 8,192 |

هدف خودکار به `131072 / active_queue_count` با تقسیم صحیح محدود می‌شود.
`kernel-queue-length` جای هدف خودکار را می‌گیرد و مشمول این سقف نیست. هیچ‌کدام
`txqueuelen` موجودِ بزرگ‌تر را کاهش نمی‌دهد. profile بیانگر سیاست حافظهٔ تنظیم‌شده
است و با تشخیص RAM میزبان انتخاب نمی‌شود. هر TUN بودجهٔ مستقل دارد.

این تنظیم best effort است: رد شدن تغییر یا در دسترس نبودن query یک هشدار ایجاد
می‌کند و صف‌های قابل‌استفاده همچنان کار می‌کنند. startup تعداد صف‌های فعال، منبع
هدف (`auto`، `override` یا `disabled`) و طول قبلی، درخواستی و خوانده‌شده از کرنل
را ثبت می‌کند؛ مقدارهای غیرقابل‌خواندن مشخص می‌شوند. این گزارش با غیرفعال بودن
تنظیم نیز ثبت می‌شود.

این گزینه مربوط به packetهای منتظر خواندن WaterWall در کرنل است. FIFO مشترک
userspace، اندازهٔ batchهای خواندن و نوشتن و سقف backlog خروجی جدا هستند. تعداد
صف یا packet نشان‌دهندهٔ RSS تخصیص‌یافته یا تعداد بایت payload نیست. صف بزرگ‌تر
می‌تواند burst را جذب کند، ولی مصرف حافظه و تأخیر را هم افزایش دهد و تضمینی برای
throughput نیست. این تنظیم sysctl سراسری جدیدی نمی‌نویسد و از
`misc.tcp-tune` در core مستقل است.

### نکته‌ها و ملاحظات {#notes-and-caveats}

- مسیر دریافت فعلی فقط بسته‌های IPv4 را عبور می‌دهد.
- `device-ip` باید رشتهٔ CIDR معتبر باشد.
- در Windows، بارگذاری و مدیریت درایور تونل به دسترسی مدیر نیاز دارد.
- در macOS، نام درخواستی باید به شکل `utunN` باشد؛ اگر واحد مشخص `utun` درخواست نشود، macOS نام واقعی رابط را اختصاص می‌دهد.
- نصب مسیرهای بومی سیستم به‌طور پیش‌فرض غیرفعال است. در صورت فعال بودن، هنگام destroy مسیرها به ترتیب معکوس نصب حذف می‌شوند.
- در Linux، راه‌اندازی همیشه `0` را در `/proc/sys/net/ipv4/conf/all/rp_filter` و `rp_filter` خود رابط TUN می‌نویسد تا فیلتر مسیر معکوس بسته‌های هدایت‌شده از TUN را حذف نکند. این رفتار برای هر TUN در Linux اجرا می‌شود، نه فقط هنگام فعال بودن مسیرهای بومی؛ زیرا کرنل از `max(all, <interface>)` استفاده می‌کند و برای معاف شدن TUN هر دو باید `0` باشند. فایل‌های `rp_filter` دیگر رابط‌ها تغییر نمی‌کنند؛ هر رابط با مقدار غیرصفر اختصاصی خود همچنان فیلتر می‌شود، اما رابطی که مقدار خودش `0` بوده و فقط `all` غیرصفر داشته، به‌عنوان اثر جانبی بدون فیلتر می‌شود. این تغییرهای sysctl هنگام stop یا destroy بازگردانده نمی‌شوند. فایل فقط‌خواندنی باعث ثبت هشدار و ادامهٔ راه‌اندازی می‌شود.
- مقدار اختصاصی رابط تا پایدار شدن دوباره اعمال می‌شود. در توزیع‌های systemd، udev در پاسخ به رویداد `add` رابط جدید، `systemd-sysctl --prefix=/net/ipv4/conf/<interface>` را اجرا می‌کند که الگوهایی مانند خط `net.ipv4.conf.*.rp_filter` در `/usr/lib/sysctl.d/50-default.conf` را دوباره اعمال می‌کند و در غیر این صورت چند میلی‌ثانیه پس از نوشتن، مقدار را بازنویسی می‌کرد. بنابراین راه‌اندازی مقدار را پایین نگه می‌دارد تا 300 ms روی `0` بماند؛ تقریباً همین زمان به فعال‌سازی TUN اضافه می‌شود و پس از 2 s با ثبت خطا از ادامهٔ تلاش صرف‌نظر می‌کند.
- تنظیم DNS اختیاری است. در صورت تنظیم، IPv4 نامعتبر هنگام ساخت گره رد می‌شود و شکست اعمال DNS پلتفرم، راه‌اندازی را متوقف می‌کند.
- در Windows و macOS، مقدارهای `route-table` غیر از `"main"` یا `"auto"` رد می‌شوند.
- پشتیبانی پلتفرم به build و پشتیبانی سیستم‌عامل از دستگاه TUN بستگی دارد.

<a id="مسیر-packet"></a>

### راه‌اندازی دستگاه {#device-setup}

هنگام ساخت تونل، `TunDevice`:

- تنظیمات route/DNS را تجزیه می‌کند.
- اگر حفاظت در برابر حلقه فعال باشد، رابط فیزیکی پیش‌فرض فعلی را ثبت و برای سوکت‌های آداپتور خروجی منتشر می‌کند.

در `onStart`، گره `TunDevice`:

- همسایهٔ دریافت‌کنندهٔ بسته‌های خوانده‌شده از دستگاه را تعیین می‌کند.
- دستگاه TUN را می‌سازد.
- در صورت درخواست، TCPv4 GSO را در Linux امتحان و فعال بودن آن یا استفاده از قالب معمول TUN را ثبت می‌کند.
- IP/زیرشبکهٔ تنظیم‌شده را اختصاص می‌دهد.
- دستگاه را فعال می‌کند.
- در Linux همیشه فیلتر مسیر معکوس IPv4 را برای `all` و رابط TUN غیرفعال می‌کند و مقدار رابط را تا پایدار شدن پایین نگه می‌دارد.
- در صورت تنظیم، مسیرهای بومی سیستم را نصب می‌کند.
- در صورت تنظیم، `post-up-script` را اجرا می‌کند.

ساخت واقعی دستگاه تا زمان شروع به تعویق می‌افتد؛ تونل برای تعیین سمت دریافت‌کنندهٔ بسته‌ها به زمینهٔ زنجیره نیاز دارد.

<a id="loop-protection"></a>
<a id="shutdown"></a>

### حفاظت در برابر حلقهٔ ترافیک خود برنامه {#self-traffic-loop-protection}

وقتی TUN خود را به‌عنوان مسیر پیش‌فرض سیستم نصب می‌کند، تمام بسته‌های خروجی ماشین، از جمله سوکت‌های upstream خود WaterWall، به TUN هدایت می‌شوند. بدون حفاظت، این بسته‌ها دوباره از TUN خوانده و ارسال می‌شوند و حلقهٔ مسیریابی تشکیل می‌دهند.

با فعال بودن `loop-protection` (پیش‌فرض حالت system-route)، گره `TunDevice`:

- رابط پیش‌فرض اصلی هر خانواده را *پیش از* نصب مسیرهای TUN ثبت می‌کند.
- رابط را به‌عنوان egress pin سراسری فرایند منتشر می‌کند.
- اجازه می‌دهد سوکت‌های آداپتور خروجی پیش از آنکه ترافیک `connect()`، `bind()` یا `sendto()` بتواند مسیر پیش‌فرض جدید TUN را دنبال کند، pin را اعمال کنند.
- هنگام stop یا destroy گره مالک `TunDevice`، pin را آزاد می‌کند.

در Linux، pin با `SO_BINDTODEVICE` و در Windows با `IP_UNICAST_IF` / `IPV6_UNICAST_IF` اعمال می‌شود. macOS فعلاً pin خروجی خودکار ندارد؛ در آن از `interface` صریح connector یا `route-exclude-cidrs` استفاده کنید.

تنظیم صریح `interface` آداپتور بر pin خودکار اولویت دارد. `source-ip` به‌تنهایی آن را کنار نمی‌زند؛ اگر IP مبدأ متعلق به کارت شبکه‌ای غیر از رابط پیش‌فرض تشخیص‌داده‌شده است، به‌ویژه در تنظیمات strong-host ویندوز، `interface` را صریحاً تعیین کنید.

سوکت‌های resolver مربوط به c-ares با این قابلیت pin نمی‌شوند. رابط پیش‌فرض فقط یک بار هنگام راه‌اندازی تشخیص داده می‌شود؛ اگر مسیر فیزیکی پیش‌فرض تغییر کرد، WaterWall را دوباره راه‌اندازی یا رابط‌ها/مسیرها را صریحاً تنظیم کنید.

در Windows، پیشگیری خودکار از حلقه فقط رابط سوکت‌های مشارکت‌کننده را انتخاب می‌کند؛ مسیر میزبان روی رابط فیزیکی اضافه نمی‌کند. تنظیمات داخلی IP، route و DNS مربوط به TUN، آداپتور تحت مالکیت را هدف می‌گیرند. پایان فرایند، جمع‌کردن نشست بسته، حذف آداپتور و فایل‌ها/ویژگی‌های باقی‌ماندهٔ دستگاه، مرزهای تکمیل جداگانه دارند. [قرارداد بازیابی Windows](https://github.com/radkesvat/WaterWall/blob/main/core/tools/windows_launcher/LIFECYCLE.md#what-remains-after-forced-termination) توضیح می‌دهد چه چیزهایی خودکار آزاد می‌شوند و چه چیزهایی ممکن است پس از خروج اجباری باقی بمانند.

راه‌اندازی Windows پیش از انتخاب رابط خروجی، `device-name` را بدون حساسیت به بزرگی حروف رزرو می‌کند. runtime و ابزارهای داخلی DNS مالکیت کرنل را نگه می‌دارند؛ Windows با بسته‌شدن آخرین handle، حتی پس از crash، آن را آزاد می‌کند. سپس راه‌اندازی می‌تواند دستگاه Wintun قدیمی خود با برچسب دقیق را حذف و تونل جدید را آماده کند. نام‌های متفاوت مستقل می‌مانند. سابقهٔ قدیمی بازیابی که تأیید نشده، جلوی اجرای دیگر را نمی‌گیرد؛ اما مالک فعلی، نام رابط اشغال‌شده، رد دسترسی یا شکست عملیات Windows همچنان می‌تواند آماده‌سازی را متوقف کند. آداپتورهای بدون برچسب یا متعلق به دیگران پس گرفته نمی‌شوند. نامی مختص این برنامه انتخاب کنید. [روند راه‌اندازی مجدد](https://github.com/radkesvat/WaterWall/blob/main/core/tools/windows_launcher/LIFECYCLE.md#restart-after-a-crash) را ببینید.

### استفاده از TunDevice با Ping و Ping6 {#using-tundevice-with-ping-and-ping6}

Ping از همان سربرگ IPv4 استفاده می‌کند و ۱۰ بایت اضافه می‌کند. در سقف حامل ۱۵۰۰ بایتی، حداکثر اندازهٔ بستهٔ بومی ۱۴۹۰ بایت است. اگر آدرس‌های بومی و حامل متفاوت‌اند، از IpOverrider استفاده کنید. آدرس مبدأ همتای موردنظر را روی شبکه با `capture-protocols: [1]` برای capture انتخاب کنید. پیام نامرتبط ICMP هم ممکن است با قالب Ping منطبق باشد.

Ping6 مستقیم ۹ بایت اضافه می‌کند و تا ۱۴۹۱ بایت بومی می‌پذیرد. در حالت `ipv6-in-ipv4`، این اندازه‌ها ۴۹ و ۱۴۵۱ بایت هستند. برای Ping6 آدرس مبدأ همتا را به‌ترتیب با پروتکل ۵۸ یا ۴۱ بگیرید.

اگر IpOverrider بین RawSocket و decoder قرار دارد، برای انتخاب worker بر اساس همتا مقدار `"opaque-flow-mode": "peer"` را صریح تنظیم کنید. حالت `auto` همسایهٔ مستقیم decoder را تشخیص می‌دهد. روی آداپتورهای بسته `"fragment-policy": "reassemble"` را تنظیم کنید و MTU دستگاه یا پل را با مسیر واقعی هماهنگ کنید.

## جزئیات پیاده‌سازی {#implementation-details}

### صف‌های دریافت و توزیع worker {#receive-queues-and-worker-distribution}

این گره آداپتور بسته است و برای هر اتصال line جدا نمی‌سازد؛ از packet lineهای worker که زنجیره فراهم می‌کند استفاده می‌کند.

Linux صف‌های دریافت متعلق به worker دارد. با پیش‌فرض `multi-queue: true`، رابط جدید ایجاد یک صف برای هر worker رویداد با هدایت ثابت کرنل را امتحان می‌کند. نبود چندصفی یا هدایت مناسب، یک صف متعلق به worker صفر را انتخاب می‌کند؛ رابط‌های تک‌صف موجود همچنان پشتیبانی می‌شوند. IPv4 TCP/UDP اصلی از hash متقارن مشترک 32 بیتی worker استفاده می‌کند که برای tuple بدون تغییر با وابستگی مصرف‌کننده هماهنگ است. IPv4 با محتوای نامشخص از `opaque-flow-mode` پیروی می‌کند که پیش‌فرضش hash پیشوند ثابت است. در حالت چندصفی تمام بسته‌های کامل روی worker دریافت‌کننده ادامه می‌یابند. reader تکی همان سیاست مؤثر را پیش از ورود به FIFOهای worker اعمال می‌کند؛ حتی هنگام تأخیر workerها، جریان اصلی TCP/UDP روی worker ثابت می‌ماند.

فقط `spread` برای TUN با محتوای نامشخص از هدایت تقریباً نوبتی استفاده می‌کند. map مربوط به eBPF هر رابط، شمارندهٔ محدود 32 بیتی به‌ازای هر CPU کرنل، افزایش معمولی و offset شناسهٔ CPU دارد. به‌روزرسانی‌های هم‌زمان ممکن است یک گام را از دست بدهند؛ بنابراین ترتیب سراسری دقیق یا تعداد برابر صف‌ها تضمین نمی‌شود. حالت‌های قطعی به map پخش نیاز ندارند.

تمام fragmentهای IPv4، از جمله fragment صفر، از fallback آدرس/protocol کرنل استفاده می‌کنند. جدول مشترک fragment، نگهداری موقت، بایت‌های حفظ‌شده و طبقه‌بندی فعلی فیلدهای fragment صفر از جمله SCTP را نگه می‌دارد؛ جای‌گذاری worker از hash مشترک 32 بیتی، مستقل از اثرانگشت سازگاری 64 بیتی بدون تغییر، استفاده می‌کند. بسته‌های fragmentشده و معمولی یک جریان ممکن است worker متفاوتی انتخاب کنند. بستهٔ بازسازی‌شده در حالت چندصفی روی worker خواننده می‌ماند و با یک reader از سیاست مؤثر بستهٔ کامل پیروی می‌کند. بستهٔ ناقص و نسخهٔ IP پشتیبانی‌نشده در کرنل، همچنان صف صفر و اعتبارسنجی بعدی را دارند. تعداد صف و حالت در زمان فعال‌سازی ثابت و مستقل از `gso` هستند.

Windows با اعلان رویداد Wintun روی worker صفر دریافت می‌کند. Linux و Windows رشتهٔ اختصاصی برنامه برای خواندن TUN ندارند. Windows و Darwin/BSD همان سیاست تک‌خواننده، از جمله حالت انتخابی opaque، را اعمال می‌کنند. IPv6 TCP/UDP ساده ضمن استفاده از hash مشترک worker، ترکیب نرم‌افزاری فعلی آدرس و حدود تجزیهٔ خود را حفظ می‌کند؛ هدایت IPv6 در کرنل و طبقه‌بندی opaque-prefix اضافه نمی‌شود. مصرف‌کنندهٔ دارای state پس از تبدیل‌ها مالک خود را انتخاب می‌کند. Darwin/BSD از رشته‌های reader خارجی با pool بافر مستقل استفاده می‌کنند.

در Windows، macOS و BSD، صف دریافت هر دستگاه به 8 MiB تخصیص بافر نگهداری‌شده و 1,024 بسته محدود است. پذیرش هرگز منتظر worker نمی‌ماند؛ با رسیدن به هر سقف، باقی‌ماندهٔ پذیرفته‌نشدهٔ batch جاری حذف می‌شود. خواندن بعدی می‌تواند از ظرفیت آزادشده بر اثر تحویل یا پاک‌سازی استفاده کند. batch جاری در Windows/macOS حداکثر 128 بسته دارد. در BSD اندازه به پروفایل RAM بستگی دارد و با پروفایل `server` به 256 بسته می‌رسد. این batch، ذخیره‌سازی محدود fragment و metadata صف از بودجهٔ تخصیص جدا هستند. ترتیب بسته‌های پذیرفته‌شدهٔ هر worker حفظ می‌شود. macOS همچنین یک بایت بیشتر از `device-mtu` می‌خواند تا فریم بزرگ‌تر با گزارش محدودشده از نظر نرخ حذف شود و با ورودی دقیقاً برابر MTU اشتباه نشود.

رکورد معمولی offload در Linux، شامل `DATA_VALID` و `NEEDS_CSUM` مطابق با تضمین
ورودی، فقط بایت‌های IP را در تخصیص best-fit کپی می‌کند. هزینهٔ همان تخصیص و metadata
کار، یک slot و بدون سهم خروجی segmentation رزرو می‌شود؛ scratch نزد reader برای
استفادهٔ دوباره می‌ماند. GSO سهم aggregate و خروجی و دو slot را حفظ می‌کند. جفت
مستقیم trusted از TUN/PTC می‌تواند aggregate تضمین‌شدهٔ TCPv4 GSO را بدون segmentation
تحویل دهد؛ سایر مسیرها segmentهای اندازهٔ MTU می‌گیرند. startup فقط هندسه و هزینهٔ
scratch را نگه می‌دارد، نه یک buffer بلااستفاده.

### رفتار تفصیلی {#detailed-behavior}

#### مسیر ورود بسته {#packet-input-path}

وقتی دستگاه TUN بسته‌ای تولید می‌کند:

- بسته روی یک worker دریافت می‌شود.
- خارج از جفت مستقیم trusted در ادامه، در هر دو حالت offload در Linux، رکورد معمولی TCP/UDP بدون fragment با metadata مطابق checksum معوق، پیش از انتشار checksum خود را روی worker مقصد کامل می‌کند؛ IPv6 TCP/UDP ساده بدون extension header نیز شامل می‌شود. metadata دیگر و پردازش fragment در مسیر reader می‌ماند؛ رکوردهای `GSO_NONE` از جمله IPv6 سیاست پذیرش فعلی را بدون بررسی مقدماتی محدود به IPv4 حفظ می‌کنند.
- برای TCPv4 GSO، reader کل مجموعه را اعتبارسنجی و بافرش را به worker انتخابی دریافت منتقل می‌کند؛ این worker بسته‌های مستقل در اندازهٔ MTU تخصیص می‌دهد، هدر و payload را کپی می‌کند و در حالت معمول، checksumهای IPv4 و TCP را پیش از تحویل عادی TunDevice، ثبت گزارش یا انتشار بسته کامل می‌کند.
- batchهای معمولی و مجموعه‌های GSO یک FIFO محدود برای هر worker دارند؛ segmentation ناتمام جلوتر از بسته‌های بعدی می‌ماند و در callbackهای محدود ادامه می‌یابد تا ترتیب FIFO پذیرفته‌شده بدون منتظر گذاشتن worker برای ظرفیت صف حفظ شود.
- در قالب معمول TUN، بستهٔ بدون fragment تولیدشدهٔ کرنل در این مرز آداپتور trusted می‌ماند؛ مصرف‌کنندهٔ بعدی سیاست اعتبارسنجی خود را حفظ می‌کند، مگر جفت مستقیم receive-trust در ادامه. fragmentهای IPv4 از parser مشترک fragment می‌گذرند که پیش از مرتبط‌سازی، ساختار و checksum هدر را بررسی می‌کند؛ جفت مستقیم بررسی checksum هدر را حذف می‌کند.
- callback بستهٔ TunDevice همچنان فقط بستهٔ دقیق IPv4 را عبور می‌دهد؛ رکورد معمولی IPv6 به همان callback می‌رسد و طبق رفتار فعلی رد می‌شود.
- بسته با packet line همان worker به همسایهٔ انتخاب‌شده فرستاده می‌شود.

اگر دستگاه پایین باشد، بسته حذف می‌شود.

سیاست fragment خواننده نحوهٔ انتشار را تعیین می‌کند: `reassemble` بایت‌ها را تا امکان تحویل datagram کامل نگه می‌دارد، اما `preserve-fragments` مرز fragmentها و وابستگی worker را حفظ می‌کند. بافر منتشرشده در کپی، تأخیر و تحویل میان workerها از مالکیت معمول پیروی می‌کند و ادعای تسویهٔ fragment همراه ندارد. ورودی بستهٔ پشتهٔ محلی شرط datagram کامل را هنگام تحویل اعمال می‌کند. بخش fragment-policy را ببینید.

<a id="نکتههای-mtu"></a>

#### مسیر خروج بسته {#packet-output-path}

وقتی payload از upstream یا downstream به `TunDevice` می‌رسد:

- payload یک بستهٔ IP در نظر گرفته می‌شود.
- کل بسته، حتی بدون درخواست محاسبهٔ مجدد checksum، از نظر ساختار به‌عنوان IPv4 دقیق اعتبارسنجی می‌شود؛ بایت اضافی انتهایی، بستهٔ بدساخت یا ناقص حذف می‌شود.
- اگر بافر بسته درخواست کند، checksum دوباره محاسبه می‌شود.
- بسته فقط در صورت موفقیت محاسبهٔ مجدد درخواستی checksum در دستگاه TUN نوشته می‌شود؛ بستهٔ بدساخت یا ناقصی که قابل محاسبه نیست، با هشدار محدودشده از نظر نرخ حذف می‌شود.

هر دو handler مربوط به upstream و downstream در همان دستگاه TUN می‌نویسند. نوشتن در TUN بستهٔ ورودی را به سیستم‌عامل تحویل می‌دهد. بستهٔ معتبر IPv4 تا 65,535 بایت، حتی بزرگ‌تر از `device-mtu`، می‌تواند از این مسیر عبور کند؛ بررسی ساختار، checksum و صف خروجی همچنان برقرار است. backend بومی ممکن است بسته را رد کند. در Unix، خطای `EMSGSIZE` بسته یا رکورد GSO ردشده را حذف می‌کند و بدون خراب علامت‌گذاری کردن دستگاه، اجازهٔ ادامه به بسته‌های بعدی می‌دهد.

callbackهای payload اعتبارسنجی می‌کنند و بسته را بدون انتظار برای ظرفیت یا اجرای I/O بومی، به FIFO خروجی worker رویداد فعلی اضافه می‌کنند. یک flush معوق برای هر worker نوشتن بومی و بازیافت بافر در pool موجود همان worker را انجام می‌دهد. TUN رشته یا pool اختصاصی writer ندارد. workerها می‌توانند هم‌زمان بنویسند؛ ترتیب FIFO هر worker حفظ می‌شود. جریان مستقیم PTC روی worker مالک بسته می‌ماند؛ خروجی workerهای متفاوت ترتیب FIFO مشترک ندارد. پذیرش در سطح دستگاه، خروجی صف‌شده و فعال را محدود می‌کند. تضمین enqueue-only به PTC بلافاصله مجاور اجازه می‌دهد sbuf نهایی را روی worker بسته مستقیم تحویل دهد.

در دستگاه با GSO فعال و جفت مستقیم trusted در Linux، هر worker بسته‌های مجاور و سازگار دادهٔ TCP را در رکورد GSO محدود scatter/gather ترکیب می‌کند. فقط بسته‌های موجود را برمی‌دارد، هرگز برای پر شدن batch صبر نمی‌کند و ترتیب را حفظ می‌کند. هر flush حداکثر 64 بسته و 256 KiB هزینهٔ تخصیص پردازش می‌کند؛ تخصیص منفرد بزرگ‌تر به‌تنهایی پیش می‌رود. باقی‌مانده flush معوق دیگری زمان‌بندی می‌کند. هر رکورد GSO حداکثر 65,535 بایت IPv4 دارد. بسته‌های منتخب برای ترکیب GSO باید در `device-mtu` جا شوند؛ بستهٔ معتبر بزرگ‌تر جداگانه نوشته می‌شود. UDP، fragmentها، بسته‌های کنترلی، TCP ناسازگار، گره‌های میانی و `gso:false` نوشتن جداگانه را حفظ می‌کنند. خروجی checksum-only همچنان هدر virtio دارد: بستهٔ معمولی غیر trusted از metadata صفر و بایت‌های کامل استفاده می‌کند؛ TCP/UDP trusted ممکن است seed ناقص و `NEEDS_CSUM` همراه `GSO_NONE` داشته باشد. ورودی checksum-only تمام رکوردهای غیر `GSO_NONE` را رد می‌کند. بایت‌های payload در بافر تجمیعی کپی نمی‌شوند.

<a id="checksum-در-جفت-مستقیم-tundevice-و-packetstoconnection"></a>

#### checksum در اتصال مستقیم PacketsToConnection {#direct-packetstoconnection-checksums}

اتصال مستقیم و دوطرفهٔ `TunDevice -> PacketsToConnection` در Linux، checksum
ورودی header مربوط به IPv4 و TCP/UDP را خودکار معتبر فرض می‌کند؛ این رفتار در
حالت raw، checksum-only و GSO و مستقل از `gso` فعال است و تنظیم اضافی ندارد.
سیستم‌عامل دیگر و node واسط اعتبارسنجی عادی را حفظ می‌کنند. فرض اعتماد به ورودی
kernel در بخش چهارم راهنمای توسعه‌دهنده توضیح داده شده است.

در TUN، PTC و fake DNS، بررسی checksum ورودی IPv4 و TCP/UDP، از جمله ورودی بدون
تضمین metadata و پذیرش fragment، حذف می‌شود. بررسی ساختار، سازگاری metadata،
شرایط fragment، درخواست repair، بودجهٔ FIFO و مالکیت هنگام shutdown تغییر نمی‌کند.
header تولیدشده و بازسازی‌شده همچنان checksum معتبر دارد. بررسی IPv6 و UDP-Lite
فعال می‌ماند.

metadata معتبر `NEEDS_CSUM` با مختصات مطابق یا `DATA_VALID` قابل اعمال، تضمین
مثبت را فقط در کار خصوصی TUN و FIFO نگه می‌دارد؛ اعتماد ورودی به packet بدون
تضمین چنین نشانه‌ای اضافه نمی‌کند. metadata متناقض و fragment با checksum ناقص
رد می‌شود. قواعد تبدیل GSO تغییر نمی‌کند.

اعتماد ورودی checksum خروجی را partial نمی‌کند. خروجی raw همچنان checksum کامل
نرم‌افزاری و checksum-on-copy دارد. فقط پس از مذاکرهٔ واقعی checksum offload و
آماده شدن منابع آن، PTC برای packet کامل و مناسب MTU از محاسبهٔ transport checksum
صرف‌نظر می‌کند و TUN آن را با seed صحیح pseudoheader و metadata `NEEDS_CSUM` به
kernel می‌دهد. datagram بزرگ پیش از fragmentation checksum کامل می‌گیرد و
fragment‌ها metadata عادی دارند. حالت‌های انتخاب‌شده تا destroy ثابت می‌مانند.

<a id="checksum"></a>

#### رفتار checksum {#checksum-behavior}

پیش از نوشتن بسته، `TunDevice` درخواست بافر همان بسته را بررسی می‌کند:

- اگر `sbufGetRecalculateChecksum(buf)` برابر true باشد، checksum بسته دوباره محاسبه می‌شود.
- محاسبهٔ مجدد checksum کل بسته امتحان می‌شود.
- برای fragmentهای IPv4، محاسبهٔ transport checksum خودکار کنار گذاشته می‌شود و فقط checksum هدر IP دوباره محاسبه می‌شود.
- اگر محاسبهٔ درخواستی نتواند ساختار موجود بسته را اعتبارسنجی کند، پرچم درخواست پاک و بافر بدون فراخوانی writer سیستم‌عامل برای TUN بازیافت می‌شود.

<a id="packet-line"></a>

#### رفتار callbackها {#callback-behavior}

مسیر اصلی callback، payload است. callbackهای عادی چرخهٔ عمر اتصال (`Init`، `Est`، `Pause` و `Resume`) در این آداپتور بسته جذب و متوقف می‌شوند. `Finish` غیرمنتظره در هر جهت، نقض مهلک چرخهٔ عمر packet line است و برنامه را abort می‌کند؛ بی‌اثر نیست.

زنجیره مالک یک packet line پایدار برای هر worker است. `TunDevice` هرگز این lineها را نابود نمی‌کند و صفر بایت state مربوط به line دارد.

### متادیتای گره {#node-metadata}

متادیتای برگرفته از کد منبع:

| ویژگی | مقدار |
| --- | --- |
| node flags | `kNodeFlagChainHead` &#124; `kNodeFlagChainEnd` &#124; `kNodeFlagSupportsTrustedPacketChecksums` &#124; `kNodeFlagPacketPayloadEnqueueOnly` |
| `can_have_prev` | `true` |
| `can_have_next` | `true` |
| `layer_group` | `kNodeLayer3` |
| `layer_group_prev_node` | `kNodeLayer3` |
| `layer_group_next_node` | `kNodeLayer3` |
| `required_padding_left` | ۱۰ بایت در Linux؛ ۰ بایت در سایر پلتفرم‌های پشتیبانی‌شده |

پرچم‌های checksum و enqueue-only قابلیت‌های یک جفت مستقیم
`TunDevice`–`PacketsToConnection` را اعلام می‌کنند. جفت واجد شرایط در Linux، اعتماد
ورودی را هنگام setup حتی در حالت raw خودکار فعال می‌کند. checksum offload خروجی
علاوه بر این به پشتیبانی مذاکره‌شده و منابع آماده نیاز دارد؛ پرچم‌های ثابت
به‌تنهایی به معنی فعال بودن هیچ‌یک از این حالت‌ها نیستند.

این مقدار نیاز منطقی اعلام‌شدهٔ node به فضای خالی سمت چپ است. در Linux حتی با
`"gso": false` نیز همین مقدار اعلام می‌شود. هم‌ترازی تخصیص حافظه موضوع جداگانه‌ای
است؛ بنابراین هر تخصیص لزوماً دقیقاً ده بایت بزرگ‌تر نمی‌شود.
