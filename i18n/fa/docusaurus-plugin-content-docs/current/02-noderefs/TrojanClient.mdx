# TrojanClient

## نمای کلی {#overview}

`TrojanClient` پیاده‌سازی سمت کلاینت پروتکل Trojan در WaterWall است. هش مربوط به گذرواژه، فرمان درخواست و سرآیند مقصد
را با قالب استاندارد Trojan می‌نویسد و سپس ترافیک برنامه را از گره بعدیِ دارای رابط جریان بایتی عبور می‌دهد.

هر دو حالت TCP `CONNECT` و UDP `ASSOCIATE` در Trojan پشتیبانی می‌شوند. خود گره TLS ایجاد نمی‌کند و اتصال به سرور راه دور
را هم باز نمی‌کند.


<a id="جایگاه-رایج"></a>

## جایگاه معمول در زنجیره {#typical-placement}

کلاینت Trojan برای TCP:

```text
TcpListener -> TrojanClient -> TlsClient -> TcpConnector
```

کلاینت Trojan برای UDP:

```text
UdpListener -> TrojanClient -> TlsClient -> TcpConnector
```

مقصد پویا از پراکسی یا مسیریاب:

```text
Socks5Server -> TrojanClient -> TlsClient -> TcpConnector
SniffRouter -> TrojanClient -> TlsClient -> TcpConnector
```

`TcpConnector` معمولاً به آدرس و پورت سرور Trojan وصل می‌شود. مقصد واقعی سرویس در درخواست Trojan یا در هر بستهٔ UDP مربوط به Trojan قرار می‌گیرد.

این گره پروتکل، رمزنگاری بستر انتقال فراهم نمی‌کند. پیش از در دسترس قرار دادن سرویس، گره‌های TLS بالا و اطلاعات احراز هویت متناظر همتا را تنظیم کنید.

## نمونهٔ کاربردی ساده {#minimal-practical-example}

این یک **قطعه از آرایهٔ گره‌ها** است، نه یک فایل پیکربندی کامل. شنوندهٔ ورودی و گره‌های همسایهٔ نشان‌داده‌شده در بالا را اضافه کنید و اطلاعات احراز هویت و آدرس‌های نمونهٔ سرور را جایگزین کنید.

<a id="نمونه-tcp"></a>

### نمونهٔ TCP {#tcp-example}

```json
[
  {
    "name": "trojan-client",
    "type": "TrojanClient",
    "settings": {
      "password": "secret-password",
      "address": "example.com",
      "port": 443,
      "protocol": "tcp",
      "dns-behaviour": {"resolve": false},
      "verbose": false
    },
    "next": "tls-client"
  },
  {
    "name": "tls-client",
    "type": "TlsClient",
    "settings": {
      "sni": "trojan.example.net",
      "verify": true
    },
    "next": "server-out"
  },
  {
    "name": "server-out",
    "type": "TcpConnector",
    "settings": {
      "address": "trojan.example.net",
      "port": 443,
      "nodelay": true
    }
  }
]
```

این درخواست به این شکل ارسال می‌شود:

```text
hex(SHA224("secret-password")) CRLF
command 01
destination example.com:443
CRLF
```

## پیکربندی {#configuration}

<a id="فیلدهای-اجباری"></a>

### فیلدهای لازم {#required-fields}

فیلدهای سطح بالا:

| فیلد | نوع | توضیح |
| --- | --- | --- |
| `name` | رشته | نام دلخواه گره؛ باید داخل پیکربندی یکتا باشد. |
| `type` | رشته | باید دقیقاً `"TrojanClient"` باشد. |
| `settings` | شیء | تنظیمات کلاینت Trojan؛ نباید خالی باشد. |
| `next` | رشته | گره دارای رابط جریان بایتی که بایت‌های پروتکل Trojan را حمل می‌کند؛ در استفادهٔ معمول لازم است. |

فیلدهای اجباری داخل `settings`:

| فیلد | نام‌های قابل قبول | توضیح |
| --- | --- | --- |
| اطلاعات گذرواژه | `password`, `pass`, `sha224`, `password-sha224`, `password_sha224` | یا گذرواژهٔ خام بدهید یا چکیدهٔ هگزِ ازپیش‌محاسبه‌شدهٔ SHA224؛ استفاده هم‌زمان از هر دو مجاز نیست. |
| آدرس مقصد | `target-address`, `address`, `target` | مقصد نهایی میزبان/IP، یا `"dest_context->address"` / `"line->dest_ctx->address"`. |
| پورت مقصد | `port` | پورت مقصد نهایی، یا `"dest_context->port"` / `"line->dest_ctx->port"`. پورت ثابت باید در بازه `1..65535` باشد. |

`password` و `pass` مقدار خام گذرواژه در Trojan هستند. `TrojanClient` مقدار `SHA224(password)` را محاسبه و به‌شکل هگز
با حروف کوچک ارسال می‌کند. مقدار ارائه‌شده با هرکدام از نام‌های جایگزین `sha224` باید دقیقاً ۵۶ کاراکتر هگزادسیمال باشد؛ حروف بزرگ به‌طور خودکار به
حروف کوچک تبدیل می‌شوند.

<a id="تنظیمات-اختیاری"></a>

### تنظیمات اختیاری {#optional-settings}

| فیلد | پیش‌فرض | توضیح |
| --- | --- | --- |
| `protocol` | `"tcp"` | فرمان Trojan را انتخاب می‌کند. نام جایگزین آن `proto` است. |
| `first-payload-timeout-ms` | `400` | مهلت بر حسب عدد صحیح میلی‌ثانیه در بازه 0 تا 4,294,967,295؛ صفر انتظار عمدی را غیرفعال می‌کند. |
| `verbose` | `false` | ثبت جزئیات بیشترِ تونل را فعال می‌کند. |
| `dns-behaviour` | تفکیک محلی غیرفعال | کنترل جست‌وجوی محلی، انتخاب آدرس و انتقال DNS؛ بخش رفتار DNS را ببینید. |

مقادیر قابل قبول `protocol`:

| مقدار | رفتار |
| --- | --- |
| `"tcp"` یا `"connect"` | فرمان `0x01` پروتکل Trojan برای TCP `CONNECT` ارسال می‌شود. |
| `"udp"` یا `"udp-associate"` | فرمان `0x03` پروتکل Trojan برای UDP `ASSOCIATE` ارسال می‌شود و دیتاگرام‌های UDP روی line حامل داخلی TCP حمل می‌شوند. |
| `"dest_context->protocol"` یا `"line->dest_ctx->protocol"` | پروتکل از زمینهٔ مقصد ورودی خوانده می‌شود. TCP دقیق `0x01` و UDP دقیق `0x03` را انتخاب می‌کند. |

اگر با انتخاب `dest_context->protocol`، پروتکل ورودی وجود نداشته باشد، مبهم باشد یا TCP/UDP نباشد، کلاینت یک هشدار ثبت می‌کند و TCP را انتخاب می‌کند.

<a id="رفتار-dns"></a>

### رفتار DNS {#dns-behaviour}

تفکیک نام میزبان یعنی پیدا کردن آدرس IP آن. `TrojanClient` می‌تواند نام میزبانِ
مقصد نهایی را در درخواست Trojan بفرستد، یا آن را محلی تفکیک کند و IP انتخاب‌شده
را بفرستد. تفکیک محلی فقط برای نام میزبانِ تفکیک‌نشده و در صورت فعال بودن انجام
می‌شود. IP عددی یا مقصدی که از قبل تفکیک شده باشد به جست‌وجو نیاز ندارد.

این تنظیم مربوط به مقصد نهایی است که از طریق پراکسی به آن می‌رسید. گره اتصال‌دهندهٔ بعدی
آدرس سرور پراکسی را انتخاب می‌کند و تنظیمات DNS مستقل خودش را دارد. با حذف
`dns-behaviour`، تفکیک محلی غیرفعال است.

این جست‌وجو را با `settings.dns-behaviour` تنظیم کنید:

```json
{
  "dns-behaviour": {
    "resolve": true,
    "mode": "direct",
    "strategy": "prefer-ipv4",
    "servers": ["203.0.113.53:53"]
  }
}
```

این آدرس نمونه‌ای برای مستندات است؛ آن را با آدرس resolver خود جایگزین کنید.

| فیلد | معنی |
| --- | --- |
| `resolve` | بولی اجباری: `true` اجازهٔ جست‌وجوی نام میزبانِ تفکیک‌نشده را می‌دهد و `false`، جست‌وجوی محلی را غیرفعال می‌کند. |
| `mode` | `native` (پیش‌فرض هنگام فعال بودن)، `direct` یا `chain`. |
| `strategy` | یکی از `core-settings`، `accept-dns-returned-order`، `prefer-ipv4`، `prefer-ipv6`، `only-ipv4` یا `only-ipv6`؛ حذف آن اولویت پیش‌فرض آدرس مصرف‌کننده را به کار می‌برد. |
| `servers` | 1–32 نقطهٔ اتصال به‌شکل IP عددی، `IP:port` یا `[IPv6]:port`؛ در `direct`/`chain` الزامی و در `native` غیرمجاز. |
| `dns-next` | نام غیرخالی ورودی DNS، فقط در `chain`. |

`native` از تنظیمات DNS در هسته و resolver مشترک worker استفاده می‌کند. هنگام
فعال بودن تفکیک محلی، این حالت پیش‌فرض انتقال DNS است.

`direct` درخواست‌های DNS را از طریق یک گره اتصال‌دهندهٔ خصوصی TCP/UDP در WaterWall به
سرورهایی که مشخص کرده‌اید می‌فرستد.

`chain` درخواست‌های DNS را از زنجیرهٔ انتخابی می‌فرستد. برای محافظت از آن‌ها، مسیری
رمزنگاری‌شده مانند VPN خود را انتخاب کنید؛ این حالت به‌تنهایی درخواست‌ها را
رمزنگاری نمی‌کند. مسیر DNS باید هم درخواست‌های UDP و هم fallback روی TCP را حمل
کند. خطای مسیریابی یا جست‌وجو باعث تغییر به DNS بومی یا حالت دیگر نمی‌شود.

در حالت `chain`، با حذف `dns-next` درخواست‌های DNS از همین کلاینت پراکسی و بستر انتقال
بعد از آن عبور می‌کنند. برای مسیر دیگر، نام یک شاخهٔ DNS جدا را در `dns-next`
بگذارید که از قبل به گره دیگری تعلق نداشته باشد. برای استفاده از همین گره، فیلد
را ننویسید؛ نام خود گره را در آن قرار ندهید.

شکل غیرفعال دقیقاً `"dns-behaviour": {"resolve": false}` است و فیلدهای `mode`، `strategy`، `servers` و `dns-next` را رد می‌کند. شیء تهی، null، نوع غیرشیء، فیلد ناشناخته و راهبرد عددی رد می‌شوند. نام راهبرد باید یکی از رشته‌های معیار بالا با حروف کوچک باشد. `core-settings` فقط اولویت آدرس را انتخاب می‌کند و انتقال DNS را تغییر نمی‌دهد.

با `resolve: false`، درخواست پراکسی در صورت پشتیبانی پروتکل نام میزبان را نگه می‌دارد. گره اتصال‌دهندهٔ بعدی مقصد مستقل پراکسی یا VPN و سیاست DNS خودش را دارد؛ برای راه‌اندازی اولیه از IP عددی یا مسیر مستقل استفاده کنید.

مثال‌های native، direct و زنجیرهٔ محافظت‌شده و محدودیت گزینه‌های هسته را در [DomainResolver](./DomainResolver.mdx) ببینید. این سیاست فقط جست‌وجوهای متعلق به همین گره را کنترل می‌کند؛ fake DNS در PTC، DNS سیستم در TunDevice و همهٔ منابع DNS برنامه را تغییر نمی‌دهد.

## کاربرد و رفع اشکال {#usage-and-troubleshooting}

<a id="نمونه-dynamic-destination"></a>

### نمونهٔ مقصد پویا {#dynamic-destination-example}

```json
{
  "name": "trojan-client",
  "type": "TrojanClient",
  "settings": {
    "sha224": "7e240de74fb1ed08fa08d38063f6a6a91462a815c15d3f6abf1d7e0b",
    "address": "dest_context->address",
    "port": "dest_context->port",
    "protocol": "dest_context->protocol"
  },
  "next": "tls-client"
}
```

اگر نمی‌خواهید گذرواژهٔ خام در پیکربندی نوشته شود، از `sha224` استفاده کنید. مقدار آن باید چکیدهٔ هش شانزدهی ۵۶ کاراکتری
SHA224 باشد.

<a id="نمونه-udp"></a>

### نمونهٔ UDP {#udp-example}

```json
{
  "name": "trojan-client-udp",
  "type": "TrojanClient",
  "settings": {
    "password": "secret-password",
    "address": "dest_context->address",
    "port": "dest_context->port",
    "protocol": "udp"
  },
  "next": "tls-client"
}
```

در حالت UDP، گره قبلی همچنان با UDP کار می‌کند. `TrojanClient` یک line حامل TCP داخلی می‌سازد، درخواست Trojan
`UDP ASSOCIATE` را روی آن می‌فرستد و هر payload مربوط به UDP محلی را با قاب‌بندی مخصوص Trojan UDP حمل می‌کند.

<a id="اشتباههای-رایج"></a>

### اشتباه‌های رایج {#common-mistakes}

- انتظار نداشته باشید `TrojanClient` خودش به سرور Trojan وصل شود؛ بعد از آن `TlsClient` و گره اتصال‌دهنده بگذارید.
- در استقرار عمومی Trojan، `TlsClient` را حذف نکنید مگر اینکه عمداً Trojan را به‌صورت آشکار روی سیم بخواهید.
- آدرس سرور Trojan را با آدرس مقصد نهایی اشتباه نگیرید.
- حالت UDP را با گره بعدی که رابط جریان بایتی ندارد به کار نبرید.

## رفتار پیشرفته {#advanced-behavior}

<a id="فرمت-request"></a>

### قالب درخواست {#request-format}

درخواست اولیه Trojan:

```text
password:     56 ASCII hex bytes, hex(SHA224(password))
separator:    CRLF
command:      01 CONNECT or 03 UDP ASSOCIATE
destination:  ATYP + address + port
separator:    CRLF
```

قالب مقصد:

```text
ATYP 01: IPv4 address, 4 bytes, then 2-byte big-endian port
ATYP 03: domain length, domain bytes, then 2-byte big-endian port
ATYP 04: IPv6 address, 16 bytes, then 2-byte big-endian port
```

در حالت UDP، درخواست اولیه `UDP ASSOCIATE` از `0.0.0.0:0` به‌عنوان آدرس association استفاده می‌کند. مقصد واقعی راه دور
داخل هر بستهٔ UDP بعدیِ Trojan حمل می‌شود.

قالب بستهٔ UDP در Trojan:

```text
destination:  ATYP + address + port
length:       2 bytes big-endian
separator:    CRLF
payload:      length bytes
```

<a id="قابلیتهای-پشتیبانینشده"></a>

### قابلیت‌های پشتیبانی‌نشده {#unsupported-features}

این پیاده‌سازی موارد زیر را ایجاد یا مدیریت نمی‌کند:

- TLS
- WebSocket، HTTP، gRPC یا پوشش‌های دیگرِ بستر انتقال
- fallback سمت سرور
- افزونه‌های غیراستاندارد Trojan

وقتی به این لایه‌ها نیاز دارید، از گره‌های جداگانه WaterWall مثل `TlsClient`، `HttpClient`، `MuxClient` یا
`TcpConnector` استفاده کنید.

## جزئیات پیاده‌سازی {#implementation-details}

<a id="اولین-داده-و-برقراری-transport"></a>

### اولین payload و برقراری بستر انتقال {#first-payload-and-transport-establishment}

`Init` مقصد را آماده و گره بعدی را مقداردهی اولیه می‌کند.
اولین payload واجد شرایطِ برنامه ممکن است پیش از `Est` بستر انتقال، داخل callback آن یا پس از Pause برسد.
این payload فوراً همراه با درخواست کامل در یک بافر معمولی ارسال می‌شود؛ در حالت UDP
سرآیند قاب یک دیتاگرام نیز در همان بافر قرار می‌گیرد. ورودی عادی با فضای پیشوند کافی برای تمام سرآیندها در همان بافر
استفاده می‌شود؛ در غیر این صورت بافر عادی با اندازهٔ متناسب ساخته می‌شود و پیشوند مقیم و بدنه pipe خصوصی به ترتیب کپی می‌شوند. TCP خالی درخواست را فعال نمی‌کند.
دیتاگرام خالی Trojan معتبر است.

در TCP مستقیم، تمام رویدادهای `Est` بستر انتقال، حتی تکراری‌ها، مستقل از دادهٔ پروتکل و Pause بی‌درنگ به برنامهٔ زنده می‌رسند.
در UDP، Est مربوط به حامل فقط یک بار به برنامه نگاشت می‌شود.
پس از بازگشت `Init` گره بعدی، اگر line هنوز زنده و درخواست هنوز ارسال‌نشده باشد،
مهلت آغاز می‌شود. در حالت UDP، این `Init` به حامل TCP مربوط است.
`settings.first-payload-timeout-ms` به‌طور پیش‌فرض **400** است و عدد صحیح از **0**
تا **4,294,967,295** را می‌پذیرد؛ نوع‌ها و مقدارهای دیگر نامعتبرند. صفر انتظار عمدی
را غیرفعال می‌کند. زمان Pause نیز محاسبه می‌شود. در TCP مستقیم، انقضای مهلت حتی پس از Pause یک درخواستِ فقط سرآیند ارسال می‌کند. تمام اعلان‌های Pause/Resume، حتی تکراری‌ها، شفاف عبور
می‌کنند و وضعیت Pause گیرنده نگهداری نمی‌شود. در حامل متعلق به کلاینت برای UDP، این گره
سر همان line است و کنترل تولید خروجی را حفظ می‌کند: اگر موعد درخواست بدون payload هنگام
Pause آن حامل برسد، ارسال تا Resume منتظر می‌ماند. رسیدن payload واجد شرایط پیش از ارسال درخواست،
زمان‌سنج را لغو کرده و خروجی ترکیبی را ارسال می‌کند. Est یا Resume تکراری درخواست را دوباره ارسال
نمی‌کنند و مهلت را از نو آغاز نمی‌کنند. Finish نیز زمان‌سنج را لغو می‌کند.
یک بافر معمولی تضمین یک فراخوانی سیستمی، بسته TCP یا رکورد TLS نیست.

ارسال upstream در مسیر مستقیم TCP و برای هر دیتاگرام منتظر Est یا Resume نمی‌ماند و صف خروجی برنامه ندارد.
Trojan پاسخ موفقیت ندارد و TCP برگشتی از Init بدون بررسی بدنه عبور می‌کند.
به‌محض آماده شدن درخواست کامل اولیه TCP، کلاینت وضعیت راه‌اندازی را نابود و زمان‌سنج را لغو می‌کند
و پیش از تحویل بافر، برای آن line به‌طور دائمی خود را از مسیر پردازش کنار می‌گذارد. callback‌های بعدی مستقیماً
بین همسایه‌ها روی همان line عبور می‌کنند. پس از بازگشت از `Init` بازورودی، کلاینت پیش از شروع زمان‌سنج فعال بودن وضعیت راه‌اندازی خودش را بررسی می‌کند. lineهای برنامه و حامل در UDP برای
قاب‌بندی، نگاشت سیگنال و پاک‌سازی حامل متعلق به کلاینت فعال می‌مانند.

line برنامه همچنان قرض‌گرفته‌شده و دارای رابط UDP است. کلاینت روی worker برنامه یک
line حامل TCP وابسته می‌سازد و مالک آن است. Est و Pause/Resume و Finish به association درست نگاشت می‌شوند.
درخواست از `0.0.0.0:0` استفاده می‌کند و هر فریم مقصد، طول و CRLF دارد.
کدگشای UDP تمام دیتاگرام‌های کاملِ ورودی پذیرفته‌شده را تکمیل می‌کند، حتی اگر تحویل دیتاگرام قبلی موجب Pause شود.
ورودی callback تو در تو پشت ورودی قدیمی در FIFO محافظت‌شدهٔ تجزیه‌گر قرار می‌گیرد؛ تنها قطعه
ناقص یا وضعیت لازم برای ترتیب باقی می‌ماند. Finish، ورودی خراب یا رد گیرنده،
تحویل را متوقف و association را می‌بندد. این گره فقط حامل متعلق به خودش را
نابود می‌کند؛ مالک برنامه هنگام خاموش‌سازی همین حامل وابسته را نیز تخلیه می‌کند.

<a id="splice-و-محدودیت-نگهداری"></a>

### Splice و نگهداری {#splice-and-retention}

اولین درخواست همراه با payload در یک بافر معمولی قرار می‌گیرد؛ خود درخواست حداکثر 320 بایت است.
دادهٔ TCP بعدی بدون تفسیر عبور می‌کند و نمایش اصلیِ معمولی یا splice خود را حفظ می‌کند. هنگام ارسال UDP،
حداکثر 263 بایت سرآیند در محدودهٔ بودجهٔ padding اعلام‌شدهٔ 331 بایتی به ابتدای داده اضافه می‌شود.
تجزیهٔ سرآیند و جابه‌جایی دقیق بدنه، مرزها را حفظ می‌کنند و در صورت نیاز ناشی از کمبود padding یا ظرفیت pipe،
کاملاً به بافر معمولی برمی‌گردند. استخراج دادهٔ دریافتی، padding کامل مسیر بعدی را حفظ می‌کند.

| ورودی نگهداری‌شده تجزیه‌گر | سقف منطقی شامل برابری |
| --- | --- |
| ورودی UDP با سر فعال صف و سرآیند ذخیره‌شده در حافظهٔ نهان | 2,162,950 بایت، برابر 2 MiB به‌علاوه یک فریم حداکثری 65,798 بایتی |
| بدنه UDP | حداکثر 65,535 بایت؛ بدنه خالی معتبر است |

برابری مجاز است؛ سرریز یا رد صف تجزیه‌گر همان association را می‌بندد. صف خروجی
کدگشایی‌شده و محدودیت 1,024 رکورد برای دستهٔ همگام وجود ندارد. تعداد قطعه‌های
ورودی سهمیه خروجی را مصرف نمی‌کند. این‌ها محدودیت‌های منطقی پروتکل‌اند و از اندازهٔ مخزن بافر، پروفایل RAM و ظرفیت
pipe مستقل‌اند. دیتاگرام محلی بیش‌ازحد بزرگ حذف می‌شود و فریم دریافتی خراب association
را می‌بندد. آدرس‌های مبدأ دریافتی بدون تغییر مقصد برنامه اعتبارسنجی می‌شوند.

فیلد طول دو‌بایتی در هر دو جهت payload از صفر تا 65,535 بایت را می‌پذیرد؛ آدرس،
طول و CRLF حداکثر 263 بایت دیگر به فریم اضافه می‌کنند. این سقف قاب‌بندی در Trojan
است، نه تضمین پذیرش همهٔ اندازه‌ها توسط سوکت UDP یا همتا. برای نمونه، UDP روی
IPv4 معمولی و بدون گزینه‌های IP حداکثر 65,507 بایت payload دارد؛ مسیر یا همتا ممکن است
سقف پایین‌تری داشته باشد. هر payload پذیرفته‌شده یک دیتاگرام می‌ماند. TCP می‌تواند
فریم را در چند خواندن تحویل دهد، ولی Trojan بدنه را کوتاه یا به چند دیتاگرام برنامه
تقسیم نمی‌کند.

اگر مجموع هزینهٔ ظرفیت سر فعال صف و ورودی صف‌شدهٔ UDP از 8 MiB بیشتر شود، داده‌های خوانده‌نشده در بافرهای کمتری تجمیع می‌شوند.
فریم‌های کامل پذیرفته‌شده ابتدا تحویل داده می‌شوند؛ ورودی ناقص و ورودی callback
تو در تو پیش از بازگشت بررسی و در صورت نیاز تجمیع می‌شوند. ترتیب بایت‌ها و سرآیندهای ذخیره‌شده در حافظهٔ نهان حفظ می‌شود. این آستانه‌ها تعداد قطعه‌های مجاز یک دیتاگرام معتبر را محدود
نمی‌کنند. اگر داده حتی پس از تجمیع در سقف هزینهٔ ظرفیت جا نگیرد، association بسته
و ورودی نگهداری‌شدهٔ آن آزاد می‌شود.

splice نیازمند `misc.splice`، ساخت مناسب و پشتیبانی تمام گره‌های زنجیرهٔ نهایی، از جمله کمک‌کننده‌های داخلی، است.
`DomainResolver` پشتیبانی می‌کند؛ `TlsClient` همچنان splice را برای کل زنجیره
غیرفعال می‌کند. در استقرار معمول TLS را نگه دارید؛ این قابلیت تضمین zero-copy
یا افزایش سرعت اندازه‌گیری‌شده نیست.

<a id="رفتار-finish"></a>

### رفتار Finish {#finish-behavior}

`TrojanClient` پیش از انتشار callbackهای واقعی `Finish`، وضعیت line خود را از بین می‌برد. برای line‌های معمولی بیرونی هم
`lineDestroy()` را فراخوانی نمی‌کند.

در حالت UDP، مالک line حامل TCP داخلی‌ای است که خودش ساخته است. بسته شدن line برنامه یا line حامل باعث بسته شدن سمت
مقابل و از بین رفتن امن line حامل می‌شود.

### فضای padding {#padding}

`TrojanClient` برای درخواست association UDP با اندازه ۶۸ بایت و بزرگ‌ترین سرآیند دیتاگرام با اندازه ۲۶۳ بایت
که همراه اولین payload ارسال می‌شوند، padding رزرو می‌کند:

```text
required_padding_left = 331
```

سرآیند دیتاگرام شامل `ATYP + domain length + 255-byte domain + port + payload length + CRLF` است.
همین بودجه بزرگ‌ترین درخواست TCP با اندازه ۳۲۰ بایت را نیز پوشش می‌دهد.
