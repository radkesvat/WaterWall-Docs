# SynReply

`SynReply` یک گره داخلی در میانهٔ زنجیرهٔ لایهٔ ۳ است. برای هر SYN واجد شرایط که از مسیر upstream می‌رسد، ابتدا بستهٔ اصلی را به `next` تحویل می‌دهد و سپس، اگر مسیر همان worker هنوز باز باشد، یک SYN-ACK جداگانه به `prev` می‌فرستد. هر دو گره مجاور باید از packet line همان worker که متعلق به زنجیره است استفاده کنند. اگر فرستنده SYN را دوباره بفرستد، پاسخ دیگری می‌گیرد. ادامهٔ دست‌دهی بر عهدهٔ دو سر اتصال TCP است.

## جریان بسته‌ها {#packet-flow}

در زنجیرهٔ `RawSocket → SynReply → TunDevice`، بسته‌های SYN دریافت‌شده به سمت `TunDevice` می‌روند و پاسخ‌های تولیدشده به سمت `RawSocket` برمی‌گردند.

| بستهٔ ورودی به SynReply | سرنوشت بستهٔ اصلی | پاسخ تولیدشده |
| --- | --- | --- |
| SYN آغازین TCP در مسیر upstream روی IPv4، بدون قطعه‌بندی و بدون داده، با سرآیندها و checksumهای معتبر | بدون تغییر به `next` می‌رود | یک SYN-ACK به فرستنده برمی‌گردد. پورت‌های مبدأ و مقصد TCP جابه‌جا می‌شوند. |
| سایر بسته‌های upstream، از جمله بسته‌های IPv6، قطعه‌های IP، SYNهای حامل داده و ACKهای بعدی | بدون تغییر به `next` می‌روند | ندارد |
| همهٔ بسته‌های downstream، از جمله SYN-ACK یک شنوندهٔ واقعی TCP | بدون تغییر به `prev` می‌روند | ندارد |

SYN آغازین می‌تواند گزینه‌های TCP یا پرچم‌های ECN داشته باشد. SynReply اعتبار checksumهای IPv4 و TCP را بر اساس بایت‌های دریافتی بررسی می‌کند و هر درخواست در انتظارِ اصلاح checksum را روی بستهٔ اصلی حفظ می‌کند. اگر مبدأ یا مقصد بسته آدرس نامعین (`0.0.0.0`)، آدرس پخش محدود (`255.255.255.255`) یا آدرس چندپخشی (`224.0.0.0/4`) باشد، بسته بدون پاسخ عبور می‌کند.

## تنظیمات

مقدار `type` را برابر `"SynReply"` و مقدار `next` را برابر نام گره بعدی لایهٔ ۳ قرار دهید. هر سه فیلد زیر اختیاری‌اند. اگر `settings` را حذف کنید یا آن را برابر `{}` بگذارید، همهٔ مقادیر پیش‌فرض اعمال می‌شوند.

| تنظیم | نوع و مقادیر مجاز در JSON | پیش‌فرض | اثر بر SYN-ACK تولیدشده |
| --- | --- | --- | --- |
| `reply-source-ip` | رشته‌ای حاوی یک آدرس تک‌پخشی IPv4، مانند `"192.0.2.20"` | آدرس IPv4 مقصد هر SYN دریافتی | آدرس مبدأ پاسخ را تعیین می‌کند. آدرس تنظیم‌شده **باید متعلق به سروری باشد که SynReply را اجرا می‌کند**. مقصد پاسخ همیشه فرستندهٔ بستهٔ اصلی است. |
| `ttl` | عدد صحیح از `1` تا `255` | `64` | مقدار TTL را در سرآیند IPv4 پاسخ تعیین می‌کند. |
| `fake-checksum` | مقدار بولی `true` یا `false` | `false` | با `true`، مقدار checksum مربوط به TCP غیرصفر و نامعتبر است. با `false`، این checksum معتبر است. در هر دو حالت checksum سرآیند IPv4 معتبر است. |

کلید ناشناخته یا تکراری، مقدار `null` و مقداری با نوع JSON نادرست باعث رد پیکربندی هنگام راه‌اندازی می‌شوند. برای آدرس، نام میزبان و پیشوند CIDR پذیرفته نمی‌شوند.

## نمونه‌ها

### مشاهدهٔ SYN-ACK روی یک رابط آزمایشی محلی {#observe-a-syn-ack-on-a-local-test-interface}

این پیکربندی لینوکس از یک رابط TUN در فضای نام شبکهٔ جداگانه‌ای برای آزمایش استفاده می‌کند. گره `BlackHole` در حالت `passive` بستهٔ SYN اصلی را مصرف می‌کند. بنابراین تنها SYN-ACK ثبت‌شده را `SynReply` می‌فرستد. در این فضای نام، زیرشبکه‌ای را انتخاب کنید که استفاده نمی‌شود و پیکربندی را با مجوز ایجاد رابط TUN بارگذاری کنید. [TunDevice](./TunDevice.mdx) · [BlackHole](./BlackHole.mdx)

```json
{
  "name": "synreply-local",
  "nodes": [
    {
      "name": "tun-in",
      "type": "TunDevice",
      "next": "syn-reply",
      "settings": {
        "device-name": "wwsyn0",
        "device-ip": "192.0.2.1/30",
        "gso": false,
        "route-table": "off"
      }
    },
    {
      "name": "syn-reply",
      "type": "SynReply",
      "next": "sink",
      "settings": { "ttl": 48 }
    },
    {
      "name": "sink",
      "type": "BlackHole",
      "settings": { "mode": "passive" }
    }
  ]
}
```

در فضای نام آزمایش، بررسی کنید که مسیر رسیدن به همتا از رابط `wwsyn0` می‌گذرد. سپس ضبط دو بسته را آغاز کنید.

```sh
ip route get 192.0.2.2
tcpdump -nnv -i wwsyn0 -c 2 'tcp port 443'
```

در پوستهٔ دوم، در همان فضای نام، یک بار برای برقراری اتصال تلاش کنید. برای مقصد از آدرس همتا، یعنی `.2`، استفاده کنید، چون `.1` به خود میزبان آزمایش اختصاص دارد.

```sh
python3 -c "import socket; socket.create_connection(('192.0.2.2', 443), timeout=2).close()"
```

اگر کلاینت از پورت `54321` استفاده کند، انتظار می‌رود بسته‌های زیر را ببینید.

| بستهٔ مشاهده‌شده روی `wwsyn0` | مبدأ | مقصد | پرچم‌های TCP | TTL در IPv4 |
| --- | --- | --- | --- | --- |
| SYN اصلی کلاینت | `192.0.2.1:54321` | `192.0.2.2:443` | SYN | کلاینت تعیین می‌کند |
| پاسخ تولیدشده توسط SynReply | `192.0.2.2:443` | `192.0.2.1:54321` | SYN, ACK | `48` |

معیار موفقیت آزمایش، مشاهدهٔ پاسخ در بسته‌های ضبط‌شده است. گره `BlackHole`، ACK بعدی کلاینت و هر دادهٔ برنامه را هم مصرف می‌کند. اگر در زنجیره، بعد از `SynReply` یک شنوندهٔ واقعی TCP وجود داشته باشد، آن شنونده نیز می‌تواند به SYN عبوری پاسخ دهد.

## مشخصات گره {#node-metadata}

| ویژگی | مقدار |
| --- | --- |
| `type` | `SynReply` |
| `flags` | `0` (هیچ پرچمی فعال نیست) |
| `can_have_prev` / `can_have_next` | `true` / `true` |
| `layer_group` | `kNodeLayer3` |
| `layer_group_prev_node` / `layer_group_next_node` | `kNodeLayer3` / `kNodeLayer3` |
| `required_padding_left` | `0` بایت |
| فضای نگهداری وضعیت برای هر line | `0` بایت |
| گزینهٔ ساخت | `INCLUDE_SYN_REPLY`، به‌طور پیش‌فرض فعال است |
