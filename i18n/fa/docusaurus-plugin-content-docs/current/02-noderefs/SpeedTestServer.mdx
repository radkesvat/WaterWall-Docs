# SpeedTestServer

`SpeedTestServer` peer سمت chain-end برای `SpeedTestClient` است. این نود frameهای speed-test را از upstream می‌گیرد،
upload data را validate می‌کند، در صورت درخواست download data را downstream می‌فرستد، و گزارش نهایی sender/receiver را
به client برمی‌گرداند.

این نود connection-oriented است. خودش line نمی‌سازد، مالک destroy کردن line ساخته‌شده توسط listener نیست، و packet-line
tunnel هم نیست.

## جایگاه رایج

`SpeedTestServer` باید آخرین نود chain باشد.

```text
TcpListener -> SpeedTestServer
UdpListener -> SpeedTestServer
TcpListener -> TlsServer -> SpeedTestServer
TcpListener -> EncryptionServer -> SpeedTestServer
```

سمت client معمولا با `SpeedTestClient` شروع می‌شود:

```text
SpeedTestClient -> TcpConnector
SpeedTestClient -> UdpConnector
SpeedTestClient -> TlsClient -> TcpConnector
SpeedTestClient -> EncryptionClient -> TcpConnector
```

## نمونه TCP

```json
[
  {
    "name": "speedtest-listener",
    "type": "TcpListener",
    "settings": {
      "address": "0.0.0.0",
      "port": 9000,
      "nodelay": true
    },
    "next": "speedtest-server"
  },
  {
    "name": "speedtest-server",
    "type": "SpeedTestServer",
    "settings": {
      "report-interval-ms": 1000,
      "json-summary": true,
      "quiet": false
    }
  }
]
```

سمت client matching:

```json
[
  {
    "name": "speedtest-client",
    "type": "SpeedTestClient",
    "settings": {
      "mode": "tcp",

    }
  }
```

## فیلدهای لازم

`SpeedTestServer` یک chain end است و نباید `next` داشته باشد.

`settings` اختیاری است. اگر نباشد، defaultها استفاده می‌شوند.

## تنظیمات اختیاری

| فیلد | پیش‌فرض | توضیح |
| --- | --- | --- |
| `report-interval-ms` | `1000` | cadence گزارش interval قبل از دریافت `HELLO`. بعد از `HELLO`، مقدار درخواستی client برای همان line استفاده می‌شود. باید positive باشد. |
| `json-summary` | `false` | default برای summary JSON-style per-stream. client هم می‌تواند از طریق `HELLO` برای line درخواست کند. |
| `quiet` | `false` | logهای runtime مثل accepted-stream، interval، final summary و failureهای per-stream را خاموش می‌کند. diagnostics fatal همچنان ممکن است log شوند. |

## Init و establishment

در upstream `Init`، server:

1. line state را initialize می‌کند
2. برای TCP-mode یک receive stream buffer می‌سازد
3. بلافاصله `Est` را downstream به سمت نود قبلی می‌فرستد

این `Est` به `SpeedTestClient` اجازه می‌دهد `HELLO` را شروع کند.

## HELLO و ACK

اولین frame باید `HELLO` باشد. این frame رفتار per-line server را تنظیم می‌کند:

- mode `tcp` یا `udp`
- direction شامل upload، download یا bidirectional
- duration و warmup
- report interval
- payload size
- target bandwidth
- total stream count
- stream id

بعد از قبول `HELLO`، server فریم `ACK` را downstream می‌فرستد. در UDP، `HELLO`های duplicate دوباره ACK می‌شوند تا گم شدن
ACK باعث گیر کردن client نشود.

server مقادیر `duration-ms`، `report-interval-ms`، `payload-size` و total stream count را validate می‌کند. payload UDP
باید داخل حداکثر `64952` byte جا شود.

## مسیر upload

وقتی upload فعال باشد، فریم‌های upstream `DATA` با همان pattern deterministic تولیدشده توسط `SpeedTestClient` validate
می‌شوند.

server این آمارها را track می‌کند: bytes، packets، valid packets، lost packets، duplicate packets، out-of-order packets،
validation errors و jitter estimate.

وقتی client فریم upload `END` را بفرستد، server آمار receiver را final می‌کند و یک `REPORT` receiver downstream می‌فرستد.
در UDP، بعد از finish شدن receiver، `END`های duplicate نادیده گرفته می‌شوند.

## مسیر download

وقتی download فعال باشد، server بعد از قبول `HELLO` فریم‌های downstream `DATA` را schedule می‌کند. payload size، warmup،
duration و target bandwidth همان مقادیری هستند که client درخواست کرده است.

در پایان download، server فریم‌های زیر را می‌فرستد:

- `END` برای download
- `REPORT` مربوط به sender

در UDP، فریم‌های final `END` و `REPORT` سه بار تکرار می‌شوند.

## Framing

در TCP، bytes ورودی داخل `buffer_stream_t` جمع می‌شوند و به frameهای speed-test decode می‌شوند.

در UDP، هر Waterwall payload buffer باید دقیقا یک frame کامل speed-test باشد. اولین packet که `HELLO` با flag UDP داشته
باشد، line را وارد UDP-frame handling می‌کند.

هدر malformed، frame type غیرمنتظره، payload length نامعتبر یا ترتیب protocol اشتباه باعث fail شدن line می‌شود. اگر
ممکن باشد server قبل از close یک frame `ERROR` می‌فرستد.

## رفتار Finish

اگر upstream قبل از کامل شدن test بسته شود، server فقط line state خودش را destroy می‌کند و `lineDestroy()` صدا نمی‌زند،
چون line توسط listener یا adapter upstream ساخته شده است.

وقتی server خودش test را کامل یا fail کند، protocol bytes لازم را می‌فرستد، state خودش را destroy می‌کند، و سپس
downstream `Finish` را forward می‌کند.

## اشتباه‌های رایج

- بعد از `SpeedTestServer` نود دیگری نگذارید؛ chain end است.
- بدون `SpeedTestClient` matching استفاده نکنید.
- انتظار پردازش application traffic از آن نداشته باشید.
- آن را packet-line node فرض نکنید؛ با lineهای عادی ساخته‌شده توسط listener یا adapter upstream کار می‌کند.
