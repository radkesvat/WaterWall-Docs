# SpeedTestServer

## نمای کلی {#overview}

`SpeedTestServer` همتای انتهای زنجیره برای `SpeedTestClient` است. قاب‌های speed-test
را از `upstream` می‌گیرد، داده آپلود را اعتبارسنجی می‌کند، در صورت درخواست داده
دانلود را در جهت `downstream` می‌فرستد و گزارش نهایی فرستنده/گیرنده را به کلاینت
برمی‌گرداند.

این یک تونل معمول اتصال‌گرا است. خودش `line` نمی‌سازد، مالک از بین
بردن `line` ساخته‌شده توسط شنونده نیست و تونل مبتنی بر `line` بسته هم محسوب نمی‌شود.

## جایگاه معمول در زنجیره {#typical-placement}

<a id="جایگاه-رایج"></a>

`SpeedTestServer` باید آخرین گره زنجیره باشد.

```text
TcpListener -> SpeedTestServer
UdpListener -> SpeedTestServer
TcpListener -> TlsServer -> SpeedTestServer
TcpListener -> EncryptionServer -> SpeedTestServer
```

سمت کلاینت معمولاً با `SpeedTestClient` متناظر آغاز می‌شود:

```text
SpeedTestClient -> TcpConnector
SpeedTestClient -> UdpConnector
SpeedTestClient -> TlsClient -> TcpConnector
SpeedTestClient -> EncryptionClient -> TcpConnector
```

### اندازه‌گیری مسیر جریان روی QUIC یا Mux {#measure-a-quic-or-multiplexed-stream-path}

<a id="اندازهگیری-مسیر-stream-روی-quic-یا-mux"></a>

```text
QUIC client: SpeedTestClient -> QuicClient -> UdpConnector
QUIC peer:   UdpListener -> QuicServer -> SpeedTestServer
Mux client:  SpeedTestClient -> MuxClient -> TcpConnector
Mux peer:    TcpListener -> MuxServer -> SpeedTestServer
```
در هر دو سناریو، روی `SpeedTestClient` مقدار `mode: "tcp"` را تنظیم کنید؛
`SpeedTestServer` حالت را از `HELLO` کلاینت می‌گیرد. رابط برنامه‌ی آزمون کارایی یک
جریان بایتی است، حتی وقتی حامل بیرونی QUIC از UDP استفاده می‌کند. برای QUIC، ALPN برابر و بررسی گواهی را تنظیم کنید.
[نمونه‌ی جفت QUIC](./QuicClient.mdx) را ببینید. در Mux، `connection-count` تعداد
اتصال منطقی آزمون کارایی را مشخص می‌کند که ممکن است حامل مشترک داشته باشند؛ این
عدد تعداد درخواستی سوکت‌های فیزیکی TCP نیست.

آرایه‌های گره در نمونه‌های TCP و UDP پایین، مسیرهای پایه هستند. هر آرایه را در
فیلد `nodes` یک پیکربندی گره بگذارید و فایل را از `core.json.configs` بارگذاری کنید.
برای مقایسه مسیرها، مدت، جهت، اندازه بار مفید و تعداد اتصال منطقی را
یکسان نگه دارید.

## نمونهٔ کاربردی ساده {#minimal-practical-example}

این‌ها قطعه‌های پیکربندی گره هستند؛ گره‌های همسایهٔ ارجاع‌شده را در پیکربندی پیرامونی تعریف کنید.

### نمونهٔ TCP {#tcp-example}

<a id="نمونه-tcp"></a>

سمت سرور:

```json
[
  {
    "name": "speedtest-listener",
    "type": "TcpListener",
    "settings": {
      "address": "0.0.0.0",
      "port": 9000,
      "nodelay": true
    },
    "next": "speedtest-server"
  },
  {
    "name": "speedtest-server",
    "type": "SpeedTestServer",
    "settings": {
      "report-interval-ms": 1000,
      "json-summary": true,
      "quiet": false
    }
  }
]
```

سمت کلاینت متناظر:

```json
[
  {
    "name": "speedtest-client",
    "type": "SpeedTestClient",
    "settings": {
      "mode": "tcp",
      "direction": "bidirectional",
      "duration-ms": 10000,
      "warmup-ms": 1000,
      "connection-count": 4,
      "payload-size": 131072
    },
    "next": "speedtest-out"
  },
  {
    "name": "speedtest-out",
    "type": "TcpConnector",
    "settings": {
      "address": "198.51.100.10",
      "port": 9000,
      "nodelay": true
    }
  }
]
```

## پیکربندی {#configuration}

### فیلدهای لازم {#required-fields}

<a id="فیلدهای-لازم"></a>

`SpeedTestServer` گره انتهایی زنجیره است و نباید `next` داشته باشد.

`settings` اختیاری است و در صورت حذف یا خالی بودن، مقدارهای پیش‌فرض به کار می‌روند.

### تنظیمات اختیاری {#optional-settings}

<a id="تنظیمات-اختیاری"></a>

| فیلد | پیش‌فرض | توضیح |
| --- | --- | --- |
| `report-interval-ms` | `1000` | فاصله پیش‌فرض گزارش‌ها پیش از دریافت `HELLO`. پس از آن، فاصلهٔ درخواستی کلاینت برای همان `line` استفاده می‌شود. باید مثبت باشد. |
| `json-summary` | `false` | مقدار پیش‌فرض برای خلاصه شبیه JSON هر جریان. کلاینت نیز می‌تواند از طریق `HELLO` آن را برای هر `line` درخواست کند. |
| `quiet` | `false` | گزارش‌های زمان اجرا مانند پذیرفته شدن جریان، گزارش دوره‌ای، خلاصه نهایی و خطاهای هر جریان را خاموش می‌کند. خطاهای مهلک مربوط به راه‌اندازی همچنان ممکن است ثبت شوند. |

### اشتباه‌های رایج {#common-mistakes}

<a id="اشتباههای-رایج"></a>

- بعد از `SpeedTestServer` گره دیگری نگذارید؛ انتهای زنجیره است.
- بدون `SpeedTestClient` متناظر از آن استفاده نکنید.
- انتظار پردازش ترافیک برنامه از آن نداشته باشید.
- آن را گره مبتنی بر `line` بسته فرض نکنید؛ با `line`های عادی ساخته‌شده توسط شنونده یا آداپتور `upstream` کار می‌کند.

## رفتار پیشرفته {#advanced-behavior}

### اعتبارسنجی بار مفید و splice {#payload-verification-and-splice}

<a id="اعتبارسنجی-payload-و-splice"></a>

تنظیم `verify-payload` در `SpeedTestClient` به‌صورت پیش‌فرض `false` است و سیاست هر دو سمت را از طریق پرچم‌های `HELLO` تعیین می‌کند. برای تولید و بررسی الگوی قطعی بار مفید، آن را روی `true` بگذارید. وقتی اعتبارسنجی غیرفعال است، فرستنده‌ها بدنه‌هایی مقداردهی‌شده و پر از صفر تولید می‌کنند و گیرنده‌ها طول آن‌ها را بدون بررسی بایت‌های بار مفید می‌شمارند. سرآیند قاب‌ها، طول‌ها، شناسه‌های جریان، حسابداری شمارهٔ توالی و گزارش‌های نهایی همچنان پردازش می‌شوند. در این حالت `valid_packets` و `validation_errors` مربوط به بار مفید صفر می‌مانند؛ خلاصه‌های JSON شامل `verification_enabled` هستند.

هر دو گره در زنجیره‌های TCP واجد شرایط و با `misc.splice=true` از splice پشتیبانی می‌کنند. گیرنده سرآیند 48 بایتی را در حافظهٔ موقت نگه می‌دارد، برای قاب‌های ناقص فوراً بازمی‌گردد و در Linux بدنه‌های `DATA` بدون اعتبارسنجی را از لوله‌های خصوصی آن‌ها به `/dev/null` تخلیه می‌کند، بدون آنکه بدنه را به فضای کاربر کپی کند. اگر مقصد تخلیه یا پشتیبانی splice در دسترس نباشد، از خواندن معمولی با حدود مشخص استفاده می‌شود. بدنه‌های کنترلی و بدنه‌های `DATA` نیازمند اعتبارسنجی در صورت نیاز به حافظهٔ عادی منتقل می‌شوند. UDP همچنان هر دیتاگرام را جداگانه پردازش می‌کند. خروجی تولیدشده در حافظهٔ عادی است؛ فعال‌کردن splice تولید بار مفید را بدون کپی نمی‌کند.

هر `line` فضای نگهداری قاب‌های ناقص را به `2 * (16 MiB + 48)` بایتِ محاسبه‌شده محدود می‌کند و پیش از رد فضای اضافی، فشرده‌سازی را انجام می‌دهد. این حد برای حسابداری صف است، نه کل حافظهٔ فرایند یا هسته. وظیفه‌های ارسال به `Pause` پایبندند و پس از حداکثر 32 قاب نوبت اجرا را واگذار می‌کنند؛ تنظیم آهنگ ارسال با وظیفه‌های زمان‌بندی‌شده انجام می‌شود، نه با خواب مسدودکننده.

## جزئیات پیاده‌سازی {#implementation-details}

### مقداردهی اولیه و برقراری اتصال {#init-and-establishment}

<a id="init-و-establishment"></a>

در `upstream` `Init`، سرور:

1. وضعیت هر `line` را مقداردهی اولیه می‌کند
2. برای قاب‌بندی در حالت TCP یک بافر جریان دریافت می‌سازد
3. بلافاصله `Est` را `downstream` به سمت گره قبلی می‌فرستد

`Est` آمادگی سمت سرور را اعلام می‌کند. آزمون با دریافت `HELLO` کلاینت در سرور آغاز می‌شود.

### پیام‌های HELLO و ACK {#hello-and-ack}

<a id="hello-و-ack"></a>

نخستین قاب دریافتی از کلاینت باید `HELLO` باشد. این قاب رفتار سرور را برای همان `line` تعیین می‌کند:

- حالت `tcp` یا `udp`
- جهت شامل آپلود، دانلود یا دوطرفه
- مدت و گرم‌کردن
- فاصلهٔ گزارش‌دهی
- اندازهٔ بار مفید
- پهنای باند هدف
- تعداد کل جریان‌ها
- سیاست اعتبارسنجی بار مفید
- شناسهٔ جریان

پس از پذیرفتن `HELLO`، سرور یک `ACK` در جهت `downstream` می‌فرستد. در حالت UDP،
برای `HELLO`های تکراری نیز دوباره `ACK` ارسال می‌شود تا گم شدن پاسخ، کلاینت را
برای همیشه منتظر نگذارد.

سرور قابل‌استفاده بودن `duration-ms`، `report-interval-ms`، `payload-size` و تعداد کل
جریان‌ها را اعتبارسنجی می‌کند. بار مفید در حالت UDP حداکثر می‌تواند `64952` بایت
باشد.

### مسیر دریافت آپلود {#upload-receive-path}

<a id="مسیر-upload"></a>

وقتی آپلود فعال باشد، قاب‌های `upstream` نوع `DATA` شمارش می‌شوند. با فعال بودن
`verify-payload`، بدنه آن‌ها نیز با الگوی قطعی کلاینت بررسی می‌شود.

سرور این آمار را نگه می‌دارد:

- تعداد بایت‌ها
- بسته‌ها
- بسته‌های معتبر
- بسته‌های ازدست‌رفته
- بسته‌های تکراری
- بسته‌های خارج از ترتیب
- خطاهای اعتبارسنجی
- برآورد jitter

با رسیدن قاب نوع `END` برای آپلود، سرور آمار گیرنده را نهایی می‌کند و یک
`REPORT` گیرنده در جهت `downstream` می‌فرستد. در حالت UDP، پس از پایان گیرنده،
`END`های تکراری نادیده گرفته می‌شوند.

### مسیر ارسال دانلود {#download-send-path}

<a id="مسیر-download"></a>

وقتی دانلود فعال باشد، سرور پس از پذیرفتن `HELLO` ارسال قاب‌های `downstream` نوع `DATA` را زمان‌بندی می‌کند. اندازهٔ بار مفید، گرم‌کردن،
مدت و پهنای باند هدف اختیاری همان مقادیری هستند که کلاینت درخواست کرده است.

در پایان دانلود، سرور قاب‌های زیر را می‌فرستد:

- `END` برای دانلود
- `REPORT` مربوط به فرستنده

در UDP، قاب‌های نهایی `END` و `REPORT` سه بار تکرار می‌شوند.

### قاب‌بندی جریان و دیتاگرام {#stream-and-datagram-framing}

<a id="framing"></a>

در حالت TCP، بایت‌های ورودی در `splice_stream_t` جمع و به قاب‌های speed-test رمزگشایی می‌شوند.

در UDP، هر بافر بار مفید Waterwall باید دقیقاً یک قاب کامل speed-test باشد. اولین بسته که `HELLO` با پرچم UDP داشته
باشد، `line` را وارد پردازش قاب‌های UDP می‌کند.

سرآیند نامعتبر، نوع قاب غیرمنتظره، طول ناممکن بار مفید یا ترتیب نادرست پروتکل
باعث شکست `line` می‌شود. سرور در صورت امکان پیش از بستن آن، یک قاب نوع `ERROR`
می‌فرستد.

### رفتار Finish {#finish-behavior}

<a id="رفتار-finish"></a>

اگر `upstream` پیش از پایان کامل تست بسته شود، سرور فقط وضعیت هر `line` خودش را
از بین می‌برد و `lineDestroy()` را فراخوانی نمی‌کند؛ زیرا `line` را شنونده یا
آداپتور `upstream` ساخته است.

وقتی سرور خودش تست را کامل کند یا با خطا پایان دهد، ابتدا بایت‌های نهایی لازم
برای پروتکل را می‌فرستد، سپس وضعیت خودش را از بین می‌برد و `downstream`
`Finish` را می‌فرستد.
