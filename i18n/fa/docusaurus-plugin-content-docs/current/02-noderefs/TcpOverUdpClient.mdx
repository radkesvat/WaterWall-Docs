# TcpOverUdpClient

`TcpOverUdpClient` یک byte stream شبیه TCP را روی یک مسیر UDP packet-preserving حمل می‌کند. این نود با اجرای KCP به صورت داخلی کار می‌کند؛ payload stream را از نود قبلی می‌گیرد، آن byte stream را به segmentهای KCP تبدیل می‌کند، و datagramهای حاصل را به نود بعدی forward می‌کند.

این نود معمولاً با `TcpOverUdpServer` در سمت مقابل استفاده می‌شود.

## جایگاه رایج

سمت client:

```text
TcpListener -> TcpOverUdpClient -> UdpConnector
TcpListener -> MuxClient -> TcpOverUdpClient -> UdpConnector
```

سمت server:

```text
UdpListener -> TcpOverUdpServer -> TcpConnector
UdpListener -> TcpOverUdpServer -> MuxServer -> TcpConnector
```

نود بعد از `TcpOverUdpClient` باید datagram boundary را حفظ کند. مسیر UDP-style transport مقصود اصلی است.

## نمونه پایه

```json
{
  "name": "tcp-over-udp-client",
  "type": "TcpOverUdpClient",
  "settings": {
    "fec": false,
    "kcp-send-window": 8192,
    "kcp-recv-window": 8192,
    "ping-interval-ms": 10000,
    "no-recv-timeout-ms": 30000
  },
  "next": "udp-out"
}
```

connector متناظر:

```json
{
  "name": "udp-out",
  "type": "UdpConnector",
  "settings": {
    "address": "198.51.100.10",
    "port": 9000
  }
}
```

## نمونه با FEC

```json
{
  "name": "tcp-over-udp-client",
  "type": "TcpOverUdpClient",
  "settings": {
    "fec": true,
    "fec-data-shards": 10,
    "fec-parity-shards": 3
  },
  "next": "udp-out"
}
```

FEC باید در هر دو سمت `TcpOverUdpClient` و `TcpOverUdpServer` با shard settingهای یکسان فعال باشد. اگر یک سمت FEC داشته باشد و سمت دیگر نداشته باشد، یا تعداد shardها با هم تفاوت داشته باشد، peer نمی‌تواند packet stream را به درستی decode کند.

## فیلدهای ضروری

`settings` اختیاری است. اگر وجود نداشته باشد یا object نباشد، از مقادیر پیش‌فرض استفاده می‌شود.

در استفاده معمول، `next` لازم است و باید به یک transport یا stack که datagram boundary را حفظ می‌کند اشاره کند.

## تنظیمات اختیاری

| فیلد | پیش‌فرض | اعتبارسنجی | توضیح |
| --- | --- | --- | --- |
| `fec` | `false` | boolean | فعال‌سازی Reed-Solomon forward error correction روی datagramهای KCP. |
| `fec-data-shards` | `10` | مثبت، با مجموع shardها حداکثر `255` | تعداد data shard در هر FEC block. فقط وقتی `fec` فعال است استفاده می‌شود. |
| `fec-parity-shards` | `3` | مثبت، با مجموع shardها حداکثر `255` | تعداد parity shard در هر FEC block. فقط وقتی `fec` فعال است استفاده می‌شود. |
| `kcp-nodelay` | `true` | boolean | فعال‌سازی KCP nodelay mode. |
| `kcp-interval-ms` | `10` | `10..5000` | فاصله update شدن KCP. |
| `kcp-resend` | `2` | `>= 0` | آستانه fast-resend در KCP. |
| `kcp-no-congestion-control` | `true` | boolean | غیرفعال کردن congestion control در KCP. |
| `kcp-send-window` | `8192` | `>= 1` | send window بر حسب segment. |
| `kcp-recv-window` | `8192` | `>= 1` | receive window بر حسب segment. |
| `kcp-initial-cwnd` | نصف `kcp-send-window` | `1..kcp-send-window` | congestion window اولیه KCP. |
| `kcp-rx-minrto-ms` | `30` | `>= 1` | حداقل retransmission timeout در KCP. |
| `kcp-send-buffer-limit` | `0` | `>= 0` | آستانه backpressure. مقدار `0` حد را از local send window + remote window + `10` محاسبه می‌کند. |
| `ping-interval-ms` | `10000` | `>= 1` | مدت idle receive قبل از ارسال ping frame داخلی. |
| `no-recv-timeout-ms` | `30000` | بزرگ‌تر از `ping-interval-ms` | مدت idle receive قبل از بستن line. |

## مدل KCP transport

در upstream `Init`، client per-line state را initialize می‌کند، یک session KCP می‌سازد، timer loop KCP را شروع می‌کند، در صورت فعال بودن FEC state آن را می‌سازد، یک ping frame داخلی اولیه queue می‌کند، و سپس upstream `Init` را به نود بعدی forward می‌کند.

وقتی payload stream از نود قبلی می‌رسد:

1. payload به chunkهایی با حداکثر اندازه KCP write MTU موثر تقسیم می‌شود.
2. هر chunk یک flag یک‌بایتی داخلی prefix می‌گیرد.
3. chunk فریم‌شده از طریق KCP ارسال می‌شود.
4. datagramهای خروجی KCP upstream به نود بعدی forward می‌شوند.

وقتی datagramها از نود بعدی برمی‌گردند:

1. در صورت فعال بودن، FEC decoding اعمال می‌شود.
2. KCP datagram را می‌گیرد.
3. payloadهای کامل‌شده KCP drain می‌شوند.
4. flag یک‌بایتی داخلی حذف می‌شود.
5. data frameها به صورت payload stream بازسازی‌شده downstream به نود قبلی forward می‌شوند.

## flagهای داخلی

داخل payload KCP، `TcpOverUdpClient` از یک flag یک‌بایتی استفاده می‌کند:

| Flag | معنی |
| --- | --- |
| `0x00` | data frame. byteهای بعد از flag همان payload stream واقعی هستند. |
| `0xF0` | ping frame. به عنوان نشانگر keepalive داخلی استفاده می‌شود. |
| `0xFF` | close frame. درخواست shutdown برای line paired. |

data frame خالی drop می‌شود.

## MTU و padding

KCP MTU از `GLOBAL_MTU_SIZE` می‌آید. وقتی FEC غیرفعال است، KCP از `GLOBAL_MTU_SIZE` به عنوان KCP MTU بیرونی استفاده می‌کند. وقتی FEC فعال است، 8 بایت header بیرونی FEC کم می‌شود.

بودجه موثر payload برای write stream:

```text
GLOBAL_MTU_SIZE - 20 - 8 - 24 - 1 - fec_overhead
```

عدد `1` همان flag frame داخلی TcpOverUdp است. نود `required_padding_left = 1` را advertise می‌کند تا بتواند این flag را قبل از دادن داده به KCP prepend کند.

## رفتار FEC

با `fec: true`، datagramهای خروجی KCP داخل packetهای Reed-Solomon FEC wrap می‌شوند. data shardها فوراً ارسال می‌شوند. بعد از هر block data shard کامل، parity shardها ارسال می‌شوند.

در receive، decoder:

- datagramهای KCP wrap‌شده با FEC را می‌پذیرد
- data shardهای معتبر را به KCP می‌دهد
- تلاش می‌کند datagramهای KCP گم‌شده را از parity shardها بازسازی کند
- packetهای FEC نامعتبر را محافظه‌کارانه drop می‌کند

FEC باعث overhead پهنای باند می‌شود. با پیش‌فرض `10` data shard و `3` parity shard، یک block کامل حدود 30 درصد parity اضافه به همراه headerهای FEC دارد.

## Backpressure

اگر داده queue ارسال KCP از `kcp-send-buffer-limit` بیشتر شود، client یک downstream `Pause` به سمت stream قبلی schedule می‌کند. وقتی خروجی KCP به زیر آستانه drain شود، callback خروجی KCP یک downstream `Resume` schedule می‌کند.

این از رشد بی‌نهایت حافظه جلوگیری می‌کند وقتی مسیر UDP congested است یا peer نمی‌تواند به سرعت کافی دریافت کند.

## رفتار Close و timeout

اگر سمت stream قبلی finish شود، `TcpOverUdpClient`:

1. downstream را به عنوان closed علامت می‌زند تا callbackهای re-entrant به سمت finished برنگردند
2. یک close frame داخلی از طریق KCP می‌فرستد
3. خروجی KCP را flush می‌کند
4. per-line state محلی را destroy می‌کند
5. upstream `Finish` را به سمت packet forward می‌کند

اگر close frame از peer برسد، client state محلی را destroy می‌کند، سمت packet را finish می‌کند، و سپس اگر line هنوز زنده باشد سمت stream را finish می‌کند.

اگر برای مدت `ping-interval-ms` هیچ receive activity نباشد، یک ping frame ارسال می‌شود. اگر inactivity receive از `no-recv-timeout-ms` بیشتر شود، line بسته می‌شود.

## اشتباه‌های رایج

- بعد از `TcpOverUdpClient` نود stream-only نگذارید؛ سمت بعدی باید packet boundary را حفظ کند.
- FEC را فقط در یک سمت فعال نکنید.
- تعداد FEC shard را در دو سمت mismatch نکنید.
- فرض نکنید KCP همه loss را از بین می‌برد؛ KCP retransmit می‌کند و FEC اختیاری می‌تواند با loss متوسط کمک کند، اما loss شدید یا bursty همچنان آسیب می‌زند.
- `no-recv-timeout-ms` را کمتر یا مساوی `ping-interval-ms` نگذارید.
