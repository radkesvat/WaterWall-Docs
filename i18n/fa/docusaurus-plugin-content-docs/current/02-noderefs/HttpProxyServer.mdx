# HttpProxyServer

این نود میانی لایهٔ ۴، درخواست‌های پراکسی HTTP/1.0 و HTTP/1.1 و تونل CONNECT را از مسیر خروجی انتخاب‌شده عبور می‌دهد:

```text
TcpListener -> HttpProxyServer -> configured outbound chain
```

آدرس و پورت شنود در TcpListener تنظیم می‌شوند. درخواست عادی باید مقصد مطلق با طرح `http://` داشته باشد. مقصد URI برای مسیریابی و تولید Host استفاده می‌شود؛ Host ورودی حتی در صورت متفاوت بودن، مقصد را عوض نمی‌کند. HTTPS از CONNECT با پورت صریح ۱ تا ۶۵۵۳۵ استفاده می‌کند. پاسخ موفق CONNECT فقط بعد از برقراری واقعی خروجی و پیش از دادهٔ مقصد ارسال می‌شود. پس از آن داده‌ها بدون تفسیر HTTP عبور می‌کنند.

HttpClient و HttpServer برای انتقال دادهٔ WaterWall در قالب HTTP هستند. این نود از پورت مشترک SOCKS/HTTP، پراکسی خروجی HTTP، رهگیری TLS، Upgrade/WebSocket یا رابط پراکسی HTTP/2 و HTTP/3 پشتیبانی نمی‌کند. متدهای توسعه مانند PROPFIND عبور می‌کنند؛ TRACE با 405 رد می‌شود. OPTIONS با مقصد ستاره یا Max-Forwards صفر، پس از احراز هویت پاسخ محلی خالی می‌گیرد و اتصال بسته می‌شود. در OPTIONS خروجی، Max-Forwards یک واحد کم می‌شود.

## تنظیمات

| کلید | پیش‌فرض و محدوده |
| --- | --- |
| `no-auth` | false؛ برای دسترسی بدون احراز هویت true باشد و دو انتخاب دیگر حذف شوند |
| `users` | آرایهٔ غیرخالی از اشیای username و password؛ دسترسی نامحدود و بدون حسابداری، مطابق هشدار زیر |
| `auth-client-node-name` | نام AuthenticationClient برای حساب‌های قابل پیگیری؛ با users و no-auth=true ناسازگار است |
| `sweep-interval-ms` | 1000؛ فاصلهٔ بررسی سیاست توسط UserController داخلی |
| `max-header-bytes` | 32768؛ بین 1024 و 65536 برای هر بلوک سرآیند |
| `max-pending-bytes` | 262144؛ بین 65536 و 1048576 و حداقل برابر محدودیت سرآیند |
| `header-timeout-ms` | 15000؛ مهلت سرآیند ناقص از اولین بایت، بدون تمدید با ورودی قطره‌ای |
| `connect-timeout-ms` | 30000؛ از Init فرزند تا Est واقعی، شامل DNS و مسیریابی |
| `idle-timeout-ms` | 300000؛ مهلت نبود پیشرفت در درخواست، پاسخ، بدنه، اتصال بیکار و تونل |
| `verbose` | false؛ رمزها و سرآیند کامل ورودی ثبت نمی‌شوند |

> **هشدار کاربران محلی:** `users` فقط دسترسی با نام کاربری و رمز می‌دهد. مصرف این اعتبارنامه‌ها در سامانهٔ حساب کاربری WaterWall پیگیری نمی‌شود و سهمیهٔ ترافیک، محدودیت اتصال/IP، پهنای باند یا انقضای حساب برای هر کاربر اعمال نمی‌شود. مجوزهای هر کاربر نامحدود است و امکان سوءاستفاده از دسترسی یا تمام‌کردن منابع سرور وجود دارد. برای حساب‌های قابل پیگیری و محدودیت‌های پشتیبانی‌شده از `auth-client-node-name` استفاده کنید. محدودیت بافر پراکسی، مهلت‌ها، سیاست مسیریابی و کنترل‌های جداگانه همچنان اعمال می‌شوند.

مهلت‌ها و فاصلهٔ sweep عدد صحیح بین ۱ و 2147483647 میلی‌ثانیه هستند. تنظیمات ناشناخته، تکراری، ناسازگار یا با نوع اشتباه، و نبود مسیر بعدی موجب خطای راه‌اندازی می‌شوند. توپولوژی به همسایهٔ لایهٔ ۴ در هر دو سمت نیاز دارد.

حدود ثابت: خط آغاز 8192 بایت، 128 فیلد سرآیند، خط اندازه و افزونهٔ chunk برابر 1024 بایت، بخش trailer برابر 16384 بایت و 64 فیلد، و حداکثر 32 پاسخ اطلاعاتی برای هر تبادل. محتوای معلق در هر دو جهت و سرآیندهای خروجی جمع می‌شود. بودجهٔ کاری چهار بافر تجمیع‌شده را پوشش می‌دهد و هزینهٔ تخصیص آن‌ها از چهار برابر max-pending-bytes بیشتر نمی‌شود. حافظهٔ موقت تحلیل سرآیند و اعتبارنامه جداگانه محدود است. بدنه به‌صورت جریانی پردازش می‌شود؛ محدودیت بافر، محدودیت اندازهٔ بدنه نیست. Pause تولید را متوقف می‌کند و Resume پس از کاهش صف اعمال می‌شود.

## احراز هویت و حسابداری

در بدنهٔ chunked حداکثر دو بلوک سرآیند با حد مستقل max-header-bytes برای بررسی trailer نگه‌داری می‌شود تا فیلدهای hop-by-hop نام‌برده در Connection نیز رد شوند. این بلوک‌ها با تکمیل بدنه یا بستن نشست آزاد می‌شوند.

دقیقاً یک حالت انتخاب کنید: `no-auth: true`، فهرست محلی `users` یا `auth-client-node-name`. در دو حالت دارای احراز هویت، no-auth می‌تواند غایب یا false باشد. انتخاب‌های متعارض حتی با مقدار null یا نامعتبر رد می‌شوند؛ آرایهٔ خالی دسترسی بدون احراز هویت ایجاد نمی‌کند.

هر عضو users دقیقاً دو فیلد رشته‌ای اجباری username و password دارد، هر کدام ۱ تا ۲۵۵ بایت در رشتهٔ تجزیه‌شده و بدون بایت کنترلی یا DEL. نام کاربری نمی‌تواند دونقطه داشته باشد؛ رمز می‌تواند. تطبیق دقیق و حساس به بزرگی حروف است؛ فاصله حذف نمی‌شود و Unicode یا encoding تبدیل نمی‌شود. بایت‌های UTF-8 تنظیم‌شده و ارسالی باید یکسان باشند. NUL داخلی پشتیبانی نمی‌شود و در دادهٔ شبکه رد می‌شود؛ نمایش رشتهٔ موجود cJSON استفاده می‌شود. زوج کاملاً تکراری، فیلد تکراری و فیلد ناشناخته مانند limit، enabled یا expire-at-ms خطای راه‌اندازی است. یک نام با رمزهای متفاوت یا نام‌های متفاوت با رمز مشترک مجاز است؛ هر دو جزء باید با یک عضو فهرست منطبق باشند.

فهرست محلی هنگام راه‌اندازی کپی و تا پایان اجرا ثابت نگه‌داری می‌شود. تغییر آن نیاز به اجرای مجدد WaterWall با تنظیمات جدید دارد؛ ویرایش زنده، ابطال فعال و hot reload ارائه نمی‌شود. رمزها در تنظیمات ذخیره می‌شوند و HTTP Basic به‌خودی‌خود آن‌ها را رمزنگاری نمی‌کند.

Proxy-Authorization از نوع Basic در هر درخواست، حتی هنگام استفادهٔ مجدد از اتصال، بررسی می‌شود. اعتبارنامهٔ غایب، نامعتبر یا ردشده پاسخ 407 با `Proxy-Authenticate: Basic realm="WaterWall"`، بدنهٔ خالی و Connection close می‌گیرد. فقط در حالت حساب قابل پیگیری، آماده‌نبودن سرویس احراز هویت پاسخ 503 می‌دهد؛ حالت محلی به این سرویس مراجعه نمی‌کند. OPTIONS محلی هم احراز هویت می‌شود و CONNECT پیش از ایجاد فرزند احراز هویت می‌شود. فیلد تکراری اعتبارنامه خطای قالب درخواست است.

Base64 باید معتبر و canonical باشد. نام کاربری و رمز هر کدام ۱ تا ۲۵۵ بایت‌اند و نباید NUL یا نویسهٔ کنترلی داشته باشند. اولین دونقطه جداکننده است. بایت‌های اعتبارنامهٔ ذخیره‌شده و ارسالی باید دقیقاً برابر باشند، از جمله UTF-8؛ تبدیل charset یا نرمال‌سازی Unicode انجام نمی‌شود. فیلد password کاربر در AuthenticationServer مقدار کامل `username:password` را نگه می‌دارد؛ name فقط فراداده است. Proxy-Authorization در حالت no-auth نیز حذف می‌شود؛ Authorization مقصد تغییر نمی‌کند.

فقط در حالت حساب قابل پیگیری، UserController داخلی افزوده می‌شود؛ برای همین لایه کنترلر دیگری دستی اضافه نکنید. فرزند خروجی، نشانگرهای کاربر موروثی، هندل معتبر و اعتبارنامه، آدرس مبدأ و پورت‌های شنود و همتا را دریافت می‌کند. محدودیت‌های پشتیبانی‌شدهٔ اتصال، ترافیک و ابطال فعال با کنترلر موجود اعمال می‌شوند. CONNECT یک بار احراز هویت می‌شود ولی کنترل سیاست حساب در طول تونل ادامه دارد. حالت محلی مستقیماً وارد زنجیرهٔ خروجی می‌شود و فقط یک نشانگر اعتبارنامهٔ بدون هندل حساب به هر فرزند جدید اضافه می‌کند؛ رکورد حساب، گزارش مصرف، رزرو اتصال/IP یا تایمر سیاست کاربر ایجاد نمی‌کند. هویت موروثی و کنترل‌های مستقل حفظ می‌شوند. نشانگرها روی کلاینت قرض‌گرفته‌شده یا فرزند استفاده‌شدهٔ مجدد انباشته نمی‌شوند.

## جریان داده، استفادهٔ مجدد و مسیریابی

بدنه‌های fixed-length و chunked در هر دو جهت، پاسخ با مرز EOF، HEAD و پاسخ بی‌بدنه، پاسخ‌های اطلاعاتی، Expect: 100-continue و پاسخ نهایی زودهنگام پشتیبانی می‌شوند. پاسخ نهایی زودهنگام آپلود را متوقف می‌کند و اتصال پس از تحویل پاسخ بسته می‌شود. فیلدهای hop-by-hop پالایش و Via افزوده می‌شود. وضعیت واقعی مقصد، کوکی، تغییرمسیر، چالش احراز هویت و محتوا حفظ می‌شوند؛ تغییرمسیر خودکار دنبال نمی‌شود.

Content-Length تکراری یا فهرستی، CL همراه Transfer-Encoding، کدگذاری انتقال پشتیبانی‌نشده، folded header، مقصد نامعتبر و chunk/trailer خراب رد می‌شوند. سرآیند کامل، مقصد و احراز هویت پیش از ایجاد خروجی بررسی می‌شوند. خطای بعدی بدنه باعث بستن تبادل می‌شود؛ دادهٔ قبلاً ارسال‌شده قابل بازگرداندن نیست. پس از ارسال پاسخ نهایی، خطا پاسخ دوم تولید نمی‌کند.

برای هر کلاینت حداکثر یک فرزند خروجی زنده وجود دارد. درخواست‌ها حتی با ورودی pipelined به‌ترتیب اجرا می‌شوند. استفادهٔ مجدد به تکمیل هر دو بدنه، سلامت اتصال، مقصد و حالت احراز هویت یکسان وابسته است. حالت محلی زوج کامل اعتبارنامهٔ یکسان می‌خواهد؛ حالت حساب قابل پیگیری علاوه بر اعتبارنامه، user ID/generation یکسان می‌خواهد. نام دامنه بدون حساسیت به بزرگی حروف و IP با بایت آدرس مقایسه می‌شود. دامنه‌های متفاوت یا نقطهٔ پایانی DNS ادغام نمی‌شوند. تغییر مقصد یا هویت فرزند تازه ایجاد می‌کند. درخواست شکست‌خورده خودکار بازپخش نمی‌شود.

دامنه به زنجیرهٔ تنظیم‌شده سپرده می‌شود؛ DNS، انتخاب IPv4/IPv6 و اتصال سوکت خصوصی در این نود وجود ندارد. IPv4 باید dotted-decimal دقیق و IPv6 داخل کروشه باشد. دامنه ASCII/A-label پذیرفته می‌شود. userinfo، fragment، authority کدشده، zone identifier، آدرس عددی مبهم و پورت نامعتبر رد می‌شوند. بایت‌های escaped مسیر و query حفظ می‌شوند.

کنترلر می‌تواند خروجی را با زنجیرهٔ سازگار مانند Router یا تونل راه‌دور جایگزین کند. authority درخواست‌شده، IP محلی resolveشده و همتای انتقال نهایی ممکن است متفاوت باشند. اتصال استفاده‌شدهٔ مجدد مسیر قبلی را حفظ می‌کند؛ فرزند تازه دوباره مسیریابی می‌شود.

کلاینت HTTP/1.0 یک تبادل دارد و بسته می‌شود. یک فیلد Expect: 100-continue در درخواست عادی HTTP/1.0 نادیده گرفته و پیش از ارسال به مقصد حذف می‌شود؛ بدنه بدون انتظار برای پاسخ Continue ارسال می‌شود. پاسخ chunked برای آن به بدنهٔ close-delimited تبدیل و trailer حذف می‌شود. پاسخ Connection close قبل از بستن کامل تحویل داده می‌شود. رفتار فعلی آداپتورهای TCP در POSIX و Windows IOCP، EOF خواندن را به بستن کامل تبدیل می‌کند؛ half-close کامل و دریافت ترافیک برگشتی تازه پس از EOF تضمین نمی‌شود.

خط ورودی از مالک مبدأ قرض گرفته می‌شود. HttpProxyServer فقط فرزند خروجی خود را می‌سازد، فهرست می‌کند و از بین می‌برد. در quiescence تایمرها جدا و کار تازه متوقف می‌شود؛ drain فرزند مستقل از ترتیب توقف مبدأ است.

## نمونه‌های کامل

در مخزن، core.json و config.json کامل موجود است:

- `tunnels/HttpProxyServer/examples/noauth/`: SOCKS روی loopback:1080 و HTTP روی loopback:8080 با کانکتورهای جدا.
- `tunnels/HttpProxyServer/examples/local-users/`: HTTP روی loopback:8080 با دو زوج محلی نمونه و بدون سرویس یا پایگاه دادهٔ حساب.
- `tunnels/HttpProxyServer/examples/authenticated/`: HTTP روی loopback:8080، سرویس احراز هویت و users.json با نمونهٔ `user:pass`.

از پوشهٔ نمونه اجرا کنید تا مسیرهای نسبی درست باشند:

```text
/path/to/Waterwall --restricted-config --config:core.json
```

در ویندوز مسیر مطلق Waterwall.exe و همان آرگومان‌ها را استفاده کنید. هویت اجرا باید شرایط elevation لانچر ویندوز را داشته باشد. صلاحیت فایل اجرایی، ترکیب CPU/OS، IOCP، کنسول و recovery جداگانه بررسی می‌شود.

نمونهٔ `tests/cases/http_proxy/` مسیر Router را با مقصد sentinel آزمایش می‌کند؛ مقصد انتقال درخواست‌شده در آن آزمون در دسترس نیست، بنابراین موفقیت وابسته به مسیر تنظیم‌شده است.

### نمونهٔ مستقل کاربران محلی

> **هشدار دسترسی نامحدود و بدون پیگیری:** users فقط نام کاربری و رمز را بررسی می‌کند. مصرف در سامانهٔ حساب WaterWall ثبت نمی‌شود؛ سهمیهٔ ترافیک، محدودیت اتصال/IP یا پهنای باند و انقضای حساب برای این کاربران وجود ندارد. امکان سوءاستفاده یا تمام‌کردن منابع سرور وجود دارد. برای حساب قابل پیگیری و محدودیت‌های پشتیبانی‌شده auth-client-node-name را انتخاب کنید. بافر، مهلت، مسیریابی و کنترل‌های مستقل همچنان اعمال می‌شوند.

نمونهٔ کامل local-users زنجیرهٔ `TcpListener -> HttpProxyServer -> TcpConnector` و تنظیمات زیر را دارد:

```json
{
  "users": [
    { "username": "alice", "password": "replace-alice-password" },
    { "username": "bob", "password": "replace-bob-password" }
  ]
}
```

از پوشهٔ `tunnels/HttpProxyServer/examples/local-users/` در ویندوز اجرا کنید: `../../../../build/msvc/Release/Waterwall.exe --restricted-config`. این نمونه به AuthenticationClient، AuthenticationServer یا users.json نیاز ندارد. رمزهای نمونه را پیش از استفاده عوض کنید؛ Basic رمزنگاری فراهم نمی‌کند. برای مقصد HTTP محلی روی پورت 8000:

```sh
curl --noproxy "" --proxy http://127.0.0.1:8080 --proxy-basic --proxy-user alice:replace-alice-password http://127.0.0.1:8000/
```

بودجهٔ کاری `P = max-pending-bytes` از فضای ورودیِ قبلاً تحویل‌شده جداست. هر جهت یک باقیمانده با حداکثر `D = 2 MiB` بایت دارد و مجموع بایت‌های نگه‌داری‌شده از `P + 2 * D` بیشتر نمی‌شود. این حاشیه برای هر جهت ثابت و مستقل از اندازهٔ pool، پروفایل حافظه و تنظیمات splice است. ظرفیت payload هر باقیمانده حداکثر `max(small capacity, 2 * D)` به‌اضافهٔ گردکردن cache-line است؛ padding، header بافر و سربار alignment جداگانه حساب می‌شوند. باقیمانده‌ها در Pause و تخلیهٔ FIFO و تمام مسیرهای خطا، timeout و Finish لحاظ می‌شوند؛ هزینهٔ چهار بافر کاری همچنان حداکثر `4 * P` است.

حد هر ورودی یک‌باره `P + D` است؛ پیشوندی که فوراً قابل تخلیه باشد پیش از نگه‌داری باقیمانده پردازش می‌شود.
