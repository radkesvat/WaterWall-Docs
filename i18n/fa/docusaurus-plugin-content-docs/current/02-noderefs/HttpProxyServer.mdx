# HttpProxyServer

## نمای کلی {#overview}

<bdi dir="ltr">`HttpProxyServer`</bdi> درخواست‌های پراکسی فوروارد HTTP/1.0 و HTTP/1.1 و تونل‌های CONNECT را می‌پذیرد. این گره میانی لایهٔ 4 مستقل از پلتفرم است.

آدرس و پورت شنونده متعلق به <bdi dir="ltr">`TcpListener`</bdi> است. درخواست‌های عادی به URI مطلق <bdi dir="ltr">`http://`</bdi> نیاز دارند؛ پراکسی HTTP/1.1 را با قالب origin-form عبور می‌دهد و Host را از همان URI دوباره می‌سازد. یک Host ورودی معتبر ولی متفاوت، هرگز مقصد را تغییر نمی‌دهد. HTTPS از CONNECT با پورت صریح 1 تا 65535 استفاده می‌کند. پاسخ موفق CONNECT پس از آماده‌سازی فرزند خروجی زنده و پیش از عبور دادهٔ تونل در هر دو جهت ارسال می‌شود. برقراری اتصال خروجی ممکن است هنوز ادامه داشته باشد.

<bdi dir="ltr">`HttpClient`</bdi> و <bdi dir="ltr">`HttpServer`</bdi> ترافیک WaterWall را در قاب‌بندی HTTP حمل می‌کنند. آن‌ها این رابط پراکسی فوروارد را ارائه نمی‌دهند. پورت مشترک SOCKS/HTTP، مذاکره با پراکسی HTTP خروجی، رهگیری TLS، Upgrade/WebSocket و رابط پراکسی HTTP/2 یا HTTP/3 پشتیبانی نمی‌شوند. متدهای افزودهٔ معتبر مانند PROPFIND عبور می‌کنند؛ TRACE پاسخ 405 می‌گیرد. درخواست احرازهویت‌شدهٔ <bdi dir="ltr">`OPTIONS *`</bdi> و OPTIONS با Max-Forwards صفر، پاسخ محلی خالی می‌گیرند و بسته می‌شوند؛ در OPTIONS عبوری، Max-Forwards یک واحد کاهش می‌یابد.

برای مذاکره با پراکسی HTTP خروجی، [<bdi dir="ltr">`HttpProxyClient`</bdi>](./HttpProxyClient.mdx) را در زنجیرهٔ خروجی پیکربندی‌شده قرار دهید. برای حفظ مقصد درخواست ورودی، حالت پیش‌فرض <bdi dir="ltr">`connect`</bdi> آن را با <bdi dir="ltr">`target-address: "dest_context->address"`</bdi> و <bdi dir="ltr">`port: "dest_context->port"`</bdi> به کار ببرید. connector بعدی را با آدرس و پورت پراکسی بالادستی تنظیم کنید.

## جایگاه معمول در زنجیره {#typical-placement}

```text
TcpListener -> HttpProxyServer -> configured outbound chain
```

شنونده سوکت TCP ورودی را فراهم می‌کند. این گره پروتکل، احراز هویت را انجام می‌دهد و مقصد درخواستی را انتخاب می‌کند؛ زنجیرهٔ خروجی اتصال را باز می‌کند.

## نمونهٔ کاربردی ساده {#minimal-practical-example}

از پوشهٔ آمادهٔ <bdi dir="ltr">`tunnels/HttpProxyServer/examples/local-users/`</bdi> استفاده کنید. JSON زیر یک **قطعهٔ تنظیمات** است؛ آن پوشه شامل <bdi dir="ltr">`core.json`</bdi> و پیکربندی کامل گره‌هاست. HTTP Basic اطلاعات ورود را رمزنگاری نمی‌کند؛ این نمونه روی loopback باقی می‌ماند.

<Link id="نمونهٔ-مستقل-کاربران-محلی" />

### نمونهٔ مستقل کاربران محلی {#standalone-local-users-example}

> **دسترسی نامحدود و بدون ثبت مصرف:** <bdi dir="ltr">`users`</bdi> محلی فقط دسترسی با نام کاربری/گذرواژه را فراهم می‌کند. مصرف آن‌ها در سامانهٔ حساب کاربری WaterWall ثبت نمی‌شود و هیچ سهمیهٔ ترافیک، محدودیت اتصال/IP، محدودیت پهنای باند یا انقضای حساب به‌ازای کاربر برای این اطلاعات ورود اعمال نمی‌شود. سهم مجاز هر کاربر نامحدود است و کاربران می‌توانند از این دسترسی سوءاستفاده کنند یا منابع سرور را به پایان برسانند. برای حساب‌های دارای ثبت مصرف و محدودیت‌های پشتیبانی‌شدهٔ آن‌ها از <bdi dir="ltr">`auth-client-node-name`</bdi> استفاده کنید. محدودیت بافر پراکسی، مهلت‌ها، سیاست مسیریابی و هر کنترل جداگانهٔ پیکربندی‌شده همچنان اعمال می‌شوند.

فایل آمادهٔ <bdi dir="ltr">`local-users/config.json`</bdi> از <bdi dir="ltr">`TcpListener -> HttpProxyServer -> TcpConnector`</bdi> با این تنظیمات پراکسی استفاده می‌کند:

```json
{
  "users": [
    { "username": "alice", "password": "replace-alice-password" },
    { "username": "bob", "password": "replace-bob-password" }
  ]
}
```

از پوشهٔ <bdi dir="ltr">`tunnels/HttpProxyServer/examples/local-users/`</bdi>، فایل اجرایی ساخته‌شده را با <bdi dir="ltr">`--restricted-config`</bdi> اجرا کنید؛ برای مثال در ویندوز <bdi dir="ltr">`../../../../build/msvc/Release/Waterwall.exe --restricted-config`</bdi>. به AuthenticationClient، AuthenticationServer یا پایگاه دادهٔ کاربران نیاز نیست. پیش از استفاده، گذرواژه‌های نمونه را جایگزین کنید. اگر مقصد HTTP روی پورت 8000 در loopback گوش می‌دهد:

```sh
curl --noproxy "" --proxy http://127.0.0.1:8080 --proxy-basic --proxy-user alice:replace-alice-password http://127.0.0.1:8000/
```

### تنظیمات {#settings}

| تنظیم | پیش‌فرض / مقادیر پذیرفته‌شده |
| --- | --- |
| <bdi dir="ltr">`no-auth`</bdi> | false؛ برای دسترسی بدون احراز هویت true بگذارید و هر دو انتخاب‌گر دیگر را حذف کنید |
| <bdi dir="ltr">`users`</bdi> | آرایهٔ غیرخالی از <bdi dir="ltr">`{ "username": "...", "password": "..." }`</bdi>؛ دسترسی نامحدود و بدون ثبت مصرف (هشدار پایین) |
| <bdi dir="ltr">`auth-client-node-name`</bdi> | AuthenticationClient موجود برای حساب‌های دارای ثبت مصرف؛ با users و no-auth برابر true ناسازگار است |
| <bdi dir="ltr">`fallback-node-name`</bdi> | نام غیرخالی اختیاری یک سرویس مستقل لایهٔ 4؛ فقط برای شکست احراز هویت اولین درخواست؛ بایت‌های اصلی اطلاعات ورود را دریافت می‌کند |
| <bdi dir="ltr">`sweep-interval-ms`</bdi> | 1000؛ فاصلهٔ اعمال سیاست UserController در حالت ثبت مصرف |
| <bdi dir="ltr">`max-header-bytes`</bdi> | 32768؛ بازهٔ <bdi dir="ltr">1024–65536</bdi> برای هر بلوک سرآیند درخواست/پاسخ |
| <bdi dir="ltr">`max-pending-bytes`</bdi> | 262144؛ بازهٔ <bdi dir="ltr">65536–1048576</bdi>، دست‌کم برابر حد سرآیند |
| <bdi dir="ltr">`header-timeout-ms`</bdi> | 15000؛ مهلت از اولین بایت سرآیند ناقص فعال |
| <bdi dir="ltr">`connect-timeout-ms`</bdi> | 30000؛ از Init فرزند تا Est واقعی، شامل مسیریابی/resolve |
| <bdi dir="ltr">`idle-timeout-ms`</bdi> | 300000؛ مهلت نبود پیشرفت برای کلاینت‌های بیکار، پاسخ‌ها، بدنه‌ها و relay |
| <bdi dir="ltr">`verbose`</bdi> | false؛ اطلاعات ورود و سرآیندهای کامل نامطمئن هرگز ثبت نمی‌شوند |

> **هشدار کاربران محلی:** <bdi dir="ltr">`users`</bdi> محلی فقط دسترسی با نام کاربری/گذرواژه را فراهم می‌کند. مصرف آن‌ها در سامانهٔ حساب کاربری WaterWall ثبت نمی‌شود و هیچ سهمیهٔ ترافیک، محدودیت اتصال/IP، محدودیت پهنای باند یا انقضای حساب به‌ازای کاربر برای این اطلاعات ورود اعمال نمی‌شود. سهم مجاز هر کاربر نامحدود است و کاربران می‌توانند از این دسترسی سوءاستفاده کنند یا منابع سرور را به پایان برسانند. برای حساب‌های دارای ثبت مصرف و محدودیت‌های پشتیبانی‌شدهٔ آن‌ها از <bdi dir="ltr">`auth-client-node-name`</bdi> استفاده کنید. محدودیت بافر پراکسی، مهلت‌ها، سیاست مسیریابی و هر کنترل جداگانهٔ پیکربندی‌شده همچنان اعمال می‌شوند.

مهلت‌ها و فاصلهٔ sweep عدد صحیح از 1 تا 2147483647 میلی‌ثانیه‌اند. تنظیمات ناشناخته، تکراری، متعارض، مفقود یا دارای نوع نادرست باعث شکست راه‌اندازی می‌شوند. اعتبارسنجی توپولوژی وجود گره لایهٔ 4 را هم در سمت قبلی و هم در سمت بعدی الزامی می‌کند.

حدود ثابت عبارت‌اند از: خط آغاز 8192 بایتی، 128 فیلد سرآیند، خط اندازه/افزونهٔ قطعهٔ 1024 بایتی، بخش trailer با 16384 بایت/64 فیلد و 32 پاسخ اطلاعاتی در هر تبادل. محتوای درانتظار در مجموع هر دو جهت شمرده می‌شود و سرآیندهای بازنویسی‌شدهٔ صف‌شده را نیز شامل می‌شود. بودجهٔ کاری <bdi dir="ltr">`P = max-pending-bytes`</bdi> چهار بافر تجمیع‌شدهٔ جریان/خروجی را با هزینهٔ تخصیص حداکثر <bdi dir="ltr">`4 * P`</bdi> پوشش می‌دهد. هر جهت همچنین یک باقیماندهٔ ازقبل‌تحویل‌شده با حداکثر <bdi dir="ltr">`D = 2 MiB`</bdi> بایت را مجاز می‌داند. این فضای اضافی ثابت هر جهت مستقل از اندازهٔ poolها، نمایهٔ RAM و تنظیمات splice است. مجموع بایت‌های منطقی نگه‌داری‌شده حداکثر <bdi dir="ltr">`P + 2 * D`</bdi> است. هر تحویل به <bdi dir="ltr">`P + D`</bdi> محدود است؛ پیشوندی که فوراً قابل تخلیه باشد ممکن است پیش از نگه‌داری باقیمانده فضای کاری مصرف کند. هر باقیمانده از فضای ذخیره‌سازی معمولی با اندازهٔ متناسب استفاده می‌کند که ظرفیت payload آن حداکثر <bdi dir="ltr">`max(small capacity, 2 * D)`</bdi> به‌اضافهٔ گردکردن به cache-line، تمام padding مربوط به pool، سرآیند sbuf و سربار تخصیص هم‌تراز است. ورودی به‌تعویق‌افتاده در محاسبهٔ فشار شرکت می‌کند و پیش از بایت‌های جدیدتر به ترتیب FIFO تخلیه می‌شود؛ فضای موقت تجزیه/بازنویسی سرآیند و اطلاعات ورود، ذخیره‌سازی محدود جداگانه دارند. ورودی در برش‌های جریانی پردازش می‌شود، بنابراین حد دادهٔ درانتظار محدودیت اندازهٔ بدنه نیست. فشار تولید را متوقف می‌کند و پس از کاهش به زیر آستانهٔ پایین آن را از سر می‌گیرد؛ سرریز تبادل را می‌بندد.

### احراز هویت و ثبت مصرف {#authentication-and-accounting}

در طول بدنه‌های chunked، حداکثر دو بلوک سرآیند با حدود جداگانه در دسترس می‌مانند تا اعتبارسنجی trailer نیز فیلدهای hop-by-hop نام‌برده در Connection را در نظر بگیرد. هر بلوک به max-header-bytes محدود است و هنگام تکمیل قاب‌بندی یا بسته‌شدن نشست آزاد می‌شود.

دقیقاً یک حالت را انتخاب کنید: <bdi dir="ltr">`no-auth: true`</bdi>، فهرست محلی <bdi dir="ltr">`users`</bdi> یا <bdi dir="ltr">`auth-client-node-name`</bdi>. در هر دو حالت احرازهویت‌شده، <bdi dir="ltr">`no-auth`</bdi> می‌تواند غایب یا false باشد. انتخاب‌گرهای متعارض، حتی اگر null یا نامعتبر باشند، راه‌اندازی را ناموفق می‌کنند؛ آرایهٔ محلی خالی هرگز دسترسی بدون احراز هویت را فعال نمی‌کند.

ورودی‌های محلی دقیقاً دو فیلد رشته‌ای اجباری <bdi dir="ltr">`username`</bdi> و <bdi dir="ltr">`password`</bdi> دارند. هر کدام در نمایش رشته‌ای تجزیه‌شده <bdi dir="ltr">1-255</bdi> بایت دارد و فاقد بایت کنترلی یا DEL است. نام کاربری نمی‌تواند دونقطه داشته باشد؛ گذرواژه می‌تواند. تطبیق دقیق و حساس به بزرگی و کوچکی حروف است و حذف فاصله یا نرمال‌سازی Unicode انجام نمی‌شود. بایت‌های پیکربندی‌شده و ارائه‌شده، از جمله بایت‌های UTF-8، باید برابر باشند. NUL تعبیه‌شده پشتیبانی نمی‌شود؛ رمزگشای دادهٔ شبکه آن را رد می‌کند. نمایش رشته‌ای موجود در cJSON به کار می‌رود. زوج‌های کاملاً تکراری و فیلدهای تکراری یا ناشناختهٔ شیء (از جمله فیلدهای سیاست مانند <bdi dir="ltr">`limit`</bdi>، <bdi dir="ltr">`enabled`</bdi> یا <bdi dir="ltr">`expire-at-ms`</bdi>) باعث شکست راه‌اندازی می‌شوند. نام کاربری یکسان با گذرواژه‌های متفاوت یا نام‌های کاربری متفاوت با یک گذرواژه مجاز است؛ هر دو جزء باید با یک ورودی یکسان مطابقت داشته باشند.

فهرست محلی هنگام راه‌اندازی کپی می‌شود و تا خاموش‌شدن تغییرناپذیر می‌ماند. برای تغییر آن، WaterWall را با پیکربندی جدید دوباره راه‌اندازی کنید. ویرایش زنده، لغو فعال دسترسی و بارگذاری مجدد در حال اجرا فراهم نشده‌اند. گذرواژه‌ها در پیکربندی ذخیره می‌شوند و HTTP Basic به‌خودی‌خود اطلاعات ورود را رمزنگاری نمی‌کند.

<bdi dir="ltr">`Proxy-Authorization`</bdi> از نوع Basic در هر درخواست HTTP، از جمله روی اتصال‌های استفاده‌شدهٔ مجدد، بررسی می‌شود. اطلاعات ورود مفقود، پشتیبانی‌نشده یا ردشده پاسخ 407 با <bdi dir="ltr">`Proxy-Authenticate: Basic realm="WaterWall"`</bdi>، بدنهٔ خالی قاب‌بندی‌شده و Connection close می‌گیرند. در حالت ثبت مصرف، در دسترس نبودن AuthenticationClient به پاسخ 503 می‌انجامد. حالت محلی به سرویس حساب مراجعه نمی‌کند. OPTIONS محلی نیز احراز هویت می‌شود؛ CONNECT پیش از ایجاد فرزند خود احراز هویت می‌کند و سپس بایت‌ها را بدون تفسیر محتوا عبور می‌دهد. فیلدهای تکراری اطلاعات ورود نامعتبرند. اطلاعات ورود حتی در حالت no-auth حذف می‌شوند؛ Authorization مقصد اصلی همچنان دادهٔ مقصد اصلی است.

Base64 باید استاندارد و معتبر باشد. نام کاربری و گذرواژه هر کدام باید <bdi dir="ltr">1–255</bdi> بایت داشته باشند و فاقد NUL یا بایت‌های کنترلی باشند؛ اولین دونقطه آن‌ها را جدا می‌کند. بایت‌های ثبت‌شده و ارائه‌شده، از جمله بایت‌های UTF-8 در صورت استفاده، باید دقیقاً یکسان باشند. نرمال‌سازی Unicode یا تبدیل مجموعه‌نویسه انجام نمی‌شود. فیلد <bdi dir="ltr">`password`</bdi> کاربر در AuthenticationServer مقدار کامل <bdi dir="ltr">`username:password`</bdi> را نگه می‌دارد؛ <bdi dir="ltr">`name`</bdi> فرادادهٔ حساب است.

فقط حالت ثبت مصرف یک UserController داخلی اضافه می‌کند. برای این لایهٔ احراز هویت، کنترلر دیگری را دستی اضافه نکنید. هر فرزند خروجی جدید، نشانگرهای کاربر به‌ارث‌رسیده، handle مقدار اعتبارسنجی‌شده و اطلاعات ورود، و فرادادهٔ اصلی مبدأ/شنونده را حمل می‌کند. پذیرش با ثبت مصرف، حسابداری مصرف، محدودیت‌های پشتیبانی‌شده و لغو فعال دسترسی از کنترلر موجود استفاده می‌کنند. CONNECT یک بار پیش از relay احراز هویت می‌شود؛ اعمال سیاست کنترلر ثبت مصرف در طول relay ادامه دارد. حالت محلی مستقیماً زنجیرهٔ پیکربندی‌شده را دنبال می‌کند و دقیقاً یک نشانگر صرفاً اطلاعات ورود به هر فرزند جدید اضافه می‌کند، بدون ایجاد handle کاربر، رکورد حساب، گزارش مصرف، رزرو یا تایمر اعمال سیاست به‌ازای کاربر. هویت‌های به‌ارث‌رسیده و سیاست‌های مستقل پیکربندی‌شده همچنان اعمال می‌شوند. هیچ‌یک از دو حالت، نشانگرهای تکراری را به line قرض‌گرفته‌شدهٔ کلاینت یا فرزند استفاده‌شدهٔ مجدد اضافه نمی‌کند.

هر درخواست HTTP روی اتصال استفاده‌شدهٔ مجدد، یک پذیرش تازه بر پایهٔ cache است. هنگام رد اطلاعات ورود خود کلاینت، تبادل مجازِ درحال‌اجرا یا جریان CONNECT ادامه می‌یابد؛ درخواست بعدی با مسدودبودن پذیرش مواجه می‌شود.

مخزن ورودی‌های کامل <bdi dir="ltr">`core.json`</bdi> و <bdi dir="ltr">`config.json`</bdi> را ارائه می‌کند:

- <bdi dir="ltr">`tunnels/HttpProxyServer/examples/noauth/`</bdi>: پورت‌های جداگانهٔ SOCKS روی 1080 و HTTP روی 8080 در loopback، با connectorهای مستقل.
- <bdi dir="ltr">`tunnels/HttpProxyServer/examples/local-users/`</bdi>: HTTP مستقل روی پورت 8080 در loopback با دو زوج محلی نمونه و بدون سرویس حساب یا پایگاه دادهٔ کاربران.
- <bdi dir="ltr">`tunnels/HttpProxyServer/examples/authenticated/`</bdi>: HTTP روی پورت 8080 در loopback، AuthenticationClient/AuthenticationServer و <bdi dir="ltr">`users.json`</bdi> نمونه با <bdi dir="ltr">`user:pass`</bdi>.

از پوشهٔ نمونهٔ انتخاب‌شده اجرا کنید تا مسیرهای نسبی پیکربندی/پایگاه داده درست تفسیر شوند:

```text
/path/to/Waterwall --restricted-config --config:core.json
```

در ویندوز، مسیر مطلق <bdi dir="ltr">`Waterwall.exe`</bdi> را با همان آرگومان‌ها از همان پوشه اجرا کنید. هویت اجرای عمومی باید الزامات ارتقای دسترسی راه‌انداز ویندوز را برآورده کند. ارزیابی فایل ساخته‌شدهٔ بومی ویندوز، CPU/OS، IOCP، کنسول و بازیابی، از قرارداد مستقل از پلتفرم این گره جداست.

نمونهٔ آزمون <bdi dir="ltr">`tests/cases/http_proxy/`</bdi> همچنین شاخهٔ خروجی انتخاب‌شده توسط Router را نشان می‌دهد که با وجود در دسترس نبودن نقطهٔ انتقال درخواستی، به مقصد آزمون sentinel می‌رسد. این نمونه هر دو شنوندهٔ پراکسی و احراز هویت واقعی را بدون گره یا اسکریپت خارجی در زنجیرهٔ زمان اجرا می‌آزماید.

## رفتار پیشرفته {#advanced-behavior}

<Link id="مسیر-جایگزین-احراز-هویت" />

### مسیر جایگزین احراز هویت {#authentication-fallback}

<bdi dir="ltr">`fallback-node-name`</bdi> به‌صورت اختیاری نام یک شاخهٔ سرویس مستقل لایهٔ 4 در همان پیکربندی را مشخص می‌کند. این شاخه فقط هنگام شکست احراز هویت **اولین درخواست** انتخاب می‌شود: نبود اطلاعات ورود، روش پشتیبانی‌نشده یا کدگذاری Basic ردشده، عدم تطابق زوج محلی، در دسترس نبودن AuthenticationClient/جدول کاربران، یا رد جست‌وجوی حساب (ناشناخته، نامنطبق، غیرفعال، منقضی، فراتر از حد یا فاقد شناسهٔ حساب الزامی). بدون fallback پیکربندی‌شده، رفتار موجود 407/503 باقی می‌ماند. در حالت <bdi dir="ltr">`no-auth`</bdi> این تنظیم اثری ندارد.

HTTP نامعتبر، فیلدهای تکراری احراز هویت، authority/قاب‌بندی نامعتبر، قابلیت‌های پشتیبانی‌نشده، حدود/مهلت‌های سرآیند، خطاهای داخلی احراز هویت و خطاهای ذخیره‌سازی محلی، fallback را انتخاب نمی‌کنند. احراز هویت موفق، اتصال را برای همیشه به مسیر محافظت‌شده متعهد می‌کند؛ از جمله برای OPTIONS محلی و CONNECT. شکست‌های بعدی احراز هویت همان رفتار خطا/بستن موجود را حفظ می‌کنند. شکست پذیرش UserController، مسیریابی، DNS و مقصد اصلی پس از احراز هویت هرگز fallback را فعال نمی‌کند.

تحویل به fallback یک فرزند تحت مالکیت پراکسی از طریق شاخهٔ fallback پیکربندی‌شده ایجاد می‌کند و UserController خصوصی این پراکسی را دور می‌زند. سرآیند اصلی، بدنه و دنبالهٔ pipeline را بایت‌به‌بایت می‌فرستد، از جمله مقصد اصلی درخواست، فاصله‌های سفید، فیلدهای hop-by-hop و **بایت‌های اطلاعات ورود ردشدهٔ Proxy-Authorization**. سرویسی را تنظیم کنید که برای دریافت این بایت‌ها قابل اعتماد باشد؛ پراکسی هرگز آن‌ها را ثبت نمی‌کند. سپس اتصال یک جریان بایتی دوطرفه و بدون تفسیر محتوا باقی می‌ماند، حتی اگر بایت‌های بعدی اطلاعات ورود معتبر داشته باشند. هیچ خطای احراز هویت محلی، پاسخ موفق CONNECT، Continue یا OPTIONS تولید نمی‌شود. سرویس fallback پاسخ خودش را تعیین می‌کند.

شاخهٔ fallback مقصد خودش را انتخاب می‌کند؛ authority درخواست شکست‌خورده به‌عنوان نقطهٔ اتصال آن ثبت نمی‌شود. وجود <bdi dir="ltr">`next`</bdi> محافظت‌شده همچنان الزامی است. مقصدهایی که از یال قبلی متعلق به مالک دیگر، شاخهٔ محافظت‌شده، خود پراکسی یا کنترلر خصوصی آن استفادهٔ مجدد کنند رد می‌شوند. این تحویل به سرویس پیکربندی‌شده است، نه ترجمهٔ پروتکل یا تلاش مجدد برای مقصد اصلی درخواستی. برای مثال، این گره‌ها می‌توانند پس از TcpListener قرار بگیرند:

```json
[
  {
    "name": "proxy", "type": "HttpProxyServer", "next": "protected",
    "settings": {
      "users": [{ "username": "alice", "password": "replace-me" }],
      "fallback-node-name": "fallback-service"
    }
  },
  {
    "name": "protected", "type": "TcpConnector",
    "settings": { "address": "dest_context->address", "port": "dest_context->port" }
  },
  {
    "name": "fallback-service", "type": "TcpConnector",
    "settings": { "address": "127.0.0.1", "port": 8081 }
  }
]
```

هیچ تأخیر عمدی وجود ندارد. مهلت اتصال همچنان از Init فرزند تا Est محاسبه می‌شود و مهلت بیکاری بر relay خام اعمال می‌شود؛ مهلت‌های سرآیند HTTP هنگام تحویل پایان می‌یابند. پاسخ‌های زودهنگام Est مصنوعی ایجاد نمی‌کنند. شکست پس از انتخاب، اتصال را بدون خطای HTTP یا تلاش برای شاخهٔ دیگر می‌بندد. پاسخ‌های پذیرفته‌شده، با رعایت Pause گیرنده، پیش از آن تخلیه می‌شوند که EOF فرزند کلاینت را ببندد. Finish کلاینت فوراً داده‌های محلی نگه‌داری‌شده را دور می‌ریزد. خاموش‌شدن worker، فرزندان fallback را از طریق همان فهرست فرزندان محافظت‌شده تخلیه می‌کند.

حدود منطقی و تخصیص موجود <bdi dir="ltr">`P`</bdi>/<bdi dir="ltr">`D`</bdi> تغییر نمی‌کنند. تصویر موقت و تغییرناپذیر اولین سرآیند به <bdi dir="ltr">`max-header-bytes + 1`</bdi> محدود است؛ هنگام قطعی‌شدن انتخاب یا ردشدن پاک می‌شود. پس از انتخاب، بایت‌های بازپخش آن پیش از Init شاخه وارد بودجهٔ کاری/خروجی موجود می‌شوند. بدنه‌ها و دنباله‌ها در نسخهٔ جداگانه‌ای کپی نمی‌شوند. relay آمادهٔ fallback می‌تواند بافرهای splice را تحت همان شرایط CONNECT که در ادامه آمده حفظ کند.

### تحویل جریان CONNECT {#connect-stream-handoff}

پراکسی پس از اعتبارسنجی درخواست و پذیرش آن طبق سیاست احراز هویت پیکربندی‌شده، فرزند خروجی را برای authority درخواستی آماده می‌کند. اگر پس از بازگشت <bdi dir="ltr">`Init`</bdi> فرزند، ارتباط زنده باشد، پراکسی یک پاسخ <bdi dir="ltr">`200 Connection Established`</bdi> در صف می‌گذارد. پراکسی پیش از تحویل پاسخ، وضعیت فشار پس از راه‌اندازی را هماهنگ می‌کند. تحویل پاسخ پیش از عبور بایت‌های خام تونل در هر دو جهت انجام می‌شود و بایت‌های دریافتی در حین <bdi dir="ltr">`Init`</bdi> را هم شامل می‌شود.

پیش از تحویل پاسخ، اگر فرزند بسته شود پراکسی <bdi dir="ltr">`502`</bdi> می‌فرستد و اگر مهلت اتصال یا بیکاری تمام شود <bdi dir="ltr">`504`</bdi> می‌فرستد. پس از تحویل پاسخ، این رویدادها جریان خام را می‌بندند. نخستین <bdi dir="ltr">`Est`</bdi> واقعی فرزند همچنان مهلت اتصال را لغو می‌کند. پراکسی این اعلان را مستقل از پاسخ HTTP به line کلاینت می‌فرستد.

```text
TcpListener -> HttpProxyServer -> TrojanServer -> TcpConnector
```

در این زنجیره، کلاینت پس از دریافت <bdi dir="ltr">`200`</bdi> می‌تواند سرآیند پروتکل Trojan را از طریق جریان CONNECT بفرستد. <bdi dir="ltr">`TrojanServer`</bdi> می‌تواند مقصد خروجی خود را از این سرآیند انتخاب کند.

<Link id="جریان-داده-استفادهٔ-مجدد-و-مسیریابی" />

### جریان داده، استفادهٔ مجدد و مسیریابی {#streaming-reuse-and-routing}

آپلودها و دانلودهای با طول ثابت و chunked به‌تدریج جریان می‌یابند. پاسخ‌های close-delimited، پاسخ‌های HEAD/بدون بدنه، پاسخ‌های اطلاعاتی، Expect: 100-continue و پاسخ‌های نهایی زودهنگام پشتیبانی می‌شوند. پاسخ نهایی زودهنگام آپلود را متوقف می‌کند و پس از تحویل پاسخ، کلاینت را می‌بندد. فیلدهای hop-by-hop فیلتر می‌شوند و Via اضافه می‌شود. وضعیت، تغییرمسیرها، کوکی‌ها، چالش‌ها و محتوای مقصد اصلی حفظ می‌شوند؛ پراکسی تغییرمسیرها را دنبال نمی‌کند.

Content-Length تکراری/فهرستی، CL همراه با Transfer-Encoding، زنجیره‌های کدگذاری انتقال پشتیبانی‌نشده، فیلدهای تاشده، authority نامعتبر، قاب‌بندی نامعتبر قطعه‌ها و trailerهای ممنوع رد می‌شوند. تمام سرآیندهای درخواست، authority و احراز هویت پیش از ایجاد مقصد اعتبارسنجی می‌شوند. خطای بعدی بدنه تبادل را می‌بندد؛ پیشوندی که قبلاً عبور داده شده قابل بازگرداندن نیست. پس از قطعی‌شدن پاسخ نهایی، خطاها اتصال را بدون افزودن پاسخ دیگری می‌بندند.

هر کلاینت حداکثر یک فرزند خروجی زنده دارد. درخواست‌ها، از جمله ورودی pipeline، به‌ترتیب اجرا می‌شوند. تبادل تکمیل‌شدهٔ واجد شرایط فقط برای همان میزبان/پورت درخواستی و همان حالت احراز هویت می‌تواند از فرزندش دوباره استفاده کند. حالت محلی همچنین به همان زوج کامل اطلاعات ورود نیاز دارد؛ حالت ثبت مصرف به بایت‌های اطلاعات ورود به‌علاوهٔ شناسه/نسل کاربر نیاز دارد. نام میزبان بدون حساسیت به بزرگی و کوچکی حروف و IP صریح بر اساس آدرس مقایسه می‌شود؛ نام‌های میزبان متفاوت و تفاوت نقطهٔ پایانی DNS یکسان فرض نمی‌شوند. تغییر مقصد یا هویت، فرزند را جایگزین می‌کند. درخواست‌های محافظت‌شده دوباره امتحان نمی‌شوند.

دامنه‌ها به زنجیرهٔ پیکربندی‌شده داده می‌شوند؛ پراکسی مسیر DNS یا سوکت خصوصی ندارد. IPv4 صریح باید دقیقاً ده‌دهیِ نقطه‌دار، IPv6 صریح داخل کروشه، و نام دامنه ASCII/A-label باشد. userinfo، fragmentها، authorityهای کدگذاری‌شده، شناسه‌های zone، آدرس‌های عددی مبهم و پورت‌های نامعتبر رد می‌شوند. بایت‌های escape‌شدهٔ مسیر/query معنای خود را حفظ می‌کنند.

یک کنترلر می‌تواند بخش خروجی را با هر زنجیرهٔ سازگار، از جمله Router یا تونل راه‌دور، جایگزین کند. authority درخواستی، آدرس resolve‌شدهٔ محلی و همتای نهایی انتقال می‌توانند به‌درستی متفاوت باشند. فرزندان استفاده‌شدهٔ مجدد مسیر برقرارشدهٔ خود را نگه می‌دارند؛ فرزندان جدید دوباره مسیریابی عادی را اجرا می‌کنند.

کلاینت‌های HTTP/1.0 یک تبادل انجام می‌دهند و بسته می‌شوند. یک Expect: 100-continue در درخواست عادی HTTP/1.0 نادیده گرفته و پیش از عبور حذف می‌شود؛ بدنهٔ آن بدون handshake مربوط به Continue پیش می‌رود. پاسخ‌های chunked بالادستی برای این کلاینت‌ها به خروجی close-delimited تبدیل می‌شوند و trailerها دور ریخته می‌شوند. پاسخ‌های close-delimited و پاسخ‌های Connection close پیش از بستن کلاینت کامل می‌شوند. آداپتورهای TCP موجود، EOF خواندن را هم در POSIX و هم در Windows IOCP به بستن کامل تبدیل می‌کنند؛ معنای کامل half-close و ترافیک برگشتی جدید پس از EOF همتا تضمین نمی‌شود.

line ورودی از مالک مبدأ قرض گرفته شده است. HttpProxyServer فرزند خروجی جداگانهٔ خود را می‌سازد، در فهرست نگه می‌دارد و از بین می‌برد. این گره انتهای line ورودی و ابتدای فرزند است؛ از جمله هنگام relay مربوط به CONNECT و fallback. بنابراین برای نگاشت payload، فشار و بسته‌شدن میان این lineها فعال می‌ماند و با پردازش تکرارپذیر و بدون اثر اضافی Pause/Resume، کنترل تولیدکننده را حفظ می‌کند. bypass دائمی تونل به‌ازای line برای این ارتباط اعمال نمی‌شود. در مرحلهٔ quiescence، worker تایمرها را جدا و کار جدید را غیرفعال می‌کند؛ مرحلهٔ drain آن، مستقل از ترتیب تخلیهٔ مبدأ، تمام فرزندان تحت مالکیت را می‌بندد.

## جزئیات پیاده‌سازی {#implementation-details}

<Link id="پذیرش-از-cache-محلی" />

### پذیرش حساب از cache {#cached-account-admission}

با AuthenticationClient، پذیرش هنگام قطعی عادی شبکه و احراز هویت مجدد از آخرین جدول معتبر RAM و مبنای ساعت آن استفاده می‌کند. وضعیت فعال‌بودن، انقضا، سهمیهٔ ترافیک و رزروهای محلی اتصال/IP ذخیره‌شده در cache همچنان اعمال می‌شوند. نبود cache اولیه، توقف، شکست نهایی در تداوم حسابداری مصرف یا رد صریح اطلاعات ورود خود کلاینت، پذیرش جدید را مسدود می‌کند. فقط مجوز اعتبارسنجی‌شده آن رد را برطرف می‌کند؛ ترافیک مجاز موجود، اعمال سیاست و ثبت مصرف مبتنی بر cache را حفظ می‌کند. تغییرات مدیریتی در زمان قطع ارتباط پس از تازه‌سازی اعمال می‌شوند. سهم‌های مجاز محلی در چند کلاینت قطع‌شده می‌توانند از محدودیت تجمیعی فراتر بروند؛ آن‌ها رزرو سراسری نیستند.

<Link id="بافرهای-splice" />

### بافرهای splice {#splice-buffers}

در زنجیره‌های واجد شرایط لینوکس، HttpProxyServer ورودی splice را در هر دو جهت می‌پذیرد. درخواست‌ها و پاسخ‌های HTTP، شامل بدنه‌ها و trailerها، برای تجزیه به‌طور کامل به بافر معمولی تبدیل می‌شوند. دادهٔ گذار CONNECT، بازپخش fallback، ورودی متوقف‌شده و ورودی بازورود نیز پیش از ورود به فضای ذخیره‌سازی نشست به بافر معمولی تبدیل می‌شوند. پس از تحویل موفقیت CONNECT، یا تکمیل Init مربوط به fallback و بازپخش قدیمی‌تر هر جهت، یک بافر کامل و جدید splice می‌تواند دست‌نخورده به گیرنده‌ای که Pause نیست عبور کند. HTTP عادی هرگز صرفاً به‌دلیل انتخاب مقصد به جریان بدون تفسیر محتوا تبدیل نمی‌شود.

پس از احراز هویت و انتخاب HTTP عادی، پراکسی برای خواندن upstream روی line ورودی و خواندن downstream روی هر فرزند HTTP پیش از Init آن، ورودی معمولی درخواست می‌کند. CONNECT و fallback این ترجیح‌ها را درخواست نمی‌کنند. اگر پس از یک تبادل HTTP قبلی، CONNECT روی همان اتصال انجام شود، ترجیح ورودی باقی می‌ماند. بافرهای splice همچنان ورودی معتبرند؛ از جمله دادهٔ ازقبل‌تحویل‌شده و ورودی رسیده از ارتباط‌های Mux.

تبدیل، موقتاً یک ورودی معمولی با حداکثر <bdi dir="ltr">`P + D`</bdi> بایت منطقی تخصیص می‌دهد؛ حد تخصیص باقیمانده همان <bdi dir="ltr">`max(small capacity, 2 * D)`</bdi> به‌اضافهٔ هم‌ترازی، padding مسیر بعدی و سربار سرآیند بافر است. پذیرش موجود همچنان بایت‌های نگه‌داری‌شده را محدود می‌کند؛ این نه حد RSS است و نه تضمین نبود کپی. همهٔ بافرهای نگه‌داری‌شدهٔ نشست معمولی باقی می‌مانند.

تنظیم <bdi dir="ltr">`misc.splice`</bdi> هسته، پشتیبانی پلتفرم و هر گره در زنجیرهٔ گسترش‌یافته، از جمله UserController، DomainResolver و شاخه‌های fallback، شرایط استفاده را تعیین می‌کنند. زنجیره‌های غیرفعال یا فاقد پشتیبانی رفتار معمولی را حفظ می‌کنند. به تنظیم جدید پراکسی نیاز نیست؛ HttpClient و HttpServer همچنان فقط بافر معمولی دارند.
