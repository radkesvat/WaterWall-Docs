# AuthenticationClient {#authenticationclient}

## نمای کلی {#overview}

`AuthenticationClient` بخش frontend پروتکل دیتابیس احراز هویت WaterWall است. این گرهٔ کنترلی در ابتدای زنجیره قرار دارد و هنگام شروع تونل روی worker شماره `0` یک line کنترلی داخلی می‌سازد و آن را در جهت upstream به گره `next` می‌فرستد. سپس در `AuthenticationServer` احراز هویت می‌شود، جدول مرجع کاربران را می‌گیرد و با ارسال دوره‌ای پیام‌ها، session را زنده نگه می‌دارد و شمارنده‌های ترافیک محلی را به سرور می‌فرستد.

`AuthenticationClient` تونلی برای عبور داده نیست. گره‌هایی که ترافیک کاربران را سرویس می‌دهند، از API داخلی آن در `include/AuthenticationClient/interface.h` برای خواندن اطلاعات کاربران و ثبت مصرف محلی در جدول دریافت‌شده استفاده می‌کنند.

<span id="جایگاه-رایج" />

## جایگاه معمول در زنجیره {#typical-placement}

### زنجیرهٔ مورد انتظار {#expected-chain}

<span id="استفادهی-یک-proxy-edge-از-پایگاه-کاربران-مشترک" />

#### اشتراک یک پایگاه کاربران با لبهٔ پراکسی {#share-one-user-database-with-a-proxy-edge}

```text
edge data:    TcpListener -> TlsServer -> VmessServer -> TcpUdpConnector
edge control: AuthenticationClient -> TlsClient -> TcpConnector
central:      TcpListener -> TlsServer -> AuthenticationServer
```
دو زنجیره سمت edge در یک config قرار دارند. `VmessServer` با
`auth-client-node-name: "auth-client"` کلاینت محلی را انتخاب می‌کند؛ payload کاربر از
زنجیره کنترل عبور نمی‌کند. connector داده مقصد درخواست را از context می‌گیرد، اما
connector کنترل به TLS listener مرکزی وصل می‌شود. نام و secret کلاینت در دو گره
authentication باید برابر باشد و هویت TLS سرور مرکزی بررسی شود.

در استقرار یک‌پردازه‌ای، `AuthenticationClient -> AuthenticationServer` بدون socket
هم معتبر است. [نمونه کامل authentication و مدیریت](../03-examples/api/client.mdx)
ساخت database، اعتبارنامه‌ها و دسترسی API را نشان می‌دهد. قطعه تنظیمات پایین گره‌های
کنترل را توضیح می‌دهند و در آرایه‌ی `nodes` config انتخاب‌شده قرار می‌گیرند.

## نمونهٔ کاربردی ساده {#minimal-practical-example}

این یک قطعهٔ پیکربندی گره است؛ همسایه‌ها و همتاهای ارجاع‌داده‌شده را در همان استقرار تعریف کنید.

`auth-db` را به‌عنوان مسیر کنترل به AuthenticationServer تعریف کنید و در آن اعتبارنامهٔ منطبق `edge-1` قرار دهید. `long-random-secret` را در دو سمت جایگزین کنید. این اتصال کنترل پایگاه داده از ترافیک payload کاربران جداست.

پروتکل کنترل، اعتبارنامه‌ها و رمزهای کاربران را حمل می‌کند. لینک راه‌دور نامطمئن به انتقال رمزگذاری‌شده و احرازشده با بررسی هویت سرور نیاز دارد؛ نمونه‌های مستقیم درون‌پردازه‌ای یا loopback چنین حفاظتی فراهم نمی‌کنند.

```json
{
  "name": "auth-client",
  "type": "AuthenticationClient",
  "settings": {
    "name": "edge-1",
    "secret": "long-random-secret"
  },
  "next": "auth-db"
}
```

برای پیش‌فرض‌ها و الزامات مشروط، [پیکربندی](#configuration) و برای مثال‌های کامل و محدودیت‌های عملیاتی، [کاربرد و رفع اشکال](#usage-and-troubleshooting) را ببینید.

## پیکربندی {#configuration}

<span id="فیلدهای-اجباری" />

### فیلدهای الزامی JSON {#required-json-fields}

#### فیلدهای سطح اصلی {#top-level-fields}

- `name` `(string)`
  نام انتخابی این گره. گره‌های دیگر، مانند `Socks5Server`، با این مقدار به کلاینت احراز هویت ارجاع می‌دهند.

- `type` `(string)`
  باید دقیقاً `"AuthenticationClient"` باشد.

- `next` `(string)`
  الزامی است. گرهٔ بعدی باید مستقیم یا از مسیر تونل‌های انتقال/کلاینت مانند `TcpConnector`، `TlsClient` یا دیگر اجزای زنجیره به یک `AuthenticationServer` برسد.

#### `settings` {#settings}

- `name` `(string)`
  نام کلاینت احراز هویت که به `AuthenticationServer` فرستاده می‌شود. این نامِ اعتبارنامهٔ بخش کنترل باید با یکی از ورودی‌های آرایهٔ `settings.auth-clients` سرور یکسان باشد.

- `secret` `(string)`
  راز کلاینت احراز هویت که همراه `settings.name` ارسال می‌شود. این مقدار رمز یک کاربر ترافیک نیست.

<span id="تنظیمات-اختیاری" />

### مرجع تنظیمات {#settings-reference}

تنظیمات الزامی:

```json
{
  "name": "edge-a",
  "secret": "shared-secret"
}
```

تنظیمات اختیاری:

```json
{
  "ping-interval-ms": 60000,
  "pull-interval-ms": 300000,
  "push-interval-ms": 300000,
  "reconnect-interval-ms": 5000,
  "request-timeout-ms": 120000,
  "max-pending-requests": 64,
  "sync-max-users": 100000,
  "sync-max-bytes": 268435456,
  "traffic-multiplier": 1,
  "verbose": false
}
```

هر پنج تنظیم بازهٔ زمانی، عدد صحیح سادهٔ JSON از `0` تا `2147483647` (`INT_MAX`) می‌پذیرند. `max-pending-requests` عدد صحیح از `1` تا `2147483647` می‌پذیرد. پیش‌فرض فقط در نبود تنظیم اعمال می‌شود. مقدار کسری، نگارش دارای ممیز یا توان، رشته، `null` و مقدار خارج از بازه هنگام راه‌اندازی رد می‌شوند؛ هرگز گرد نمی‌شوند یا سرریز نمی‌کنند. معنای مقدار صریح `0` برای هر بازه حفظ می‌شود. تنظیم شناخته‌شدهٔ تکراری رد می‌شود و `verbose` فقط Boolean در JSON می‌پذیرد.

وقتی line کنترل مقداردهی اولیه شده و نوشتن مجاز است، `ping-interval-ms` پس از احراز
هویت `Ping` می‌فرستد. پیش از احراز هویت، اگر درخواست `Authenticate` بی‌پاسخی در
جریان نباشد، آن را دوباره می‌فرستد.

`pull-interval-ms` پیمایش‌های دوره‌ای کامل `GetUsersPage` را فعال می‌کند. مقدار `0` دریافت مبتنی بر زمان‌سنج را غیرفعال می‌کند، اما احراز هویت و هر ACK مصرف منطبق همچنان تازه‌سازی را درخواست می‌کنند. تازه‌سازی ناموفق مستقل تکرار می‌شود و گزارش مصرف از آخرین مبنای نصب‌شده ادامه می‌یابد.

`push-interval-ms` ارسال دوره‌ای `PushUserStats` را فعال می‌کند. مقدار `0` آن را غیرفعال می‌کند؛ تونل‌های دیگر همچنان می‌توانند با API داخلی درخواست ارسال بدهند.

وقتی pull یا push فعال است، یک `sync_timer` با کوتاه‌ترین بازهٔ فعال اجرا می‌شود. هر تیک، کارهای سررسیده را بررسی می‌کند و ابتدا `PushUserStats` را امتحان می‌کند. با تفاوت revision تنظیمات یا فرارسیدن موعد pull، `GetUsersPage` پیمایش را آغاز می‌کند. اختلاف revision آمار تابع برنامهٔ تنظیم‌شده است؛ revisionهای پاکت پاسخ ممکن است از snapshot نگه‌داشته‌شده جدیدتر باشند. تیک‌های دوره‌ای به پیمایش فعال می‌پیوندند. درخواست صریح `authenticationclientRequestPull()` در طول پیمایش، یک پیمایش بعدی را نگه می‌دارد؛ نصب جدول این تقاضای صریح را پاک نمی‌کند.

`reconnect-interval-ms` تأخیر اتصال مجدد پس از بسته‌شدن انتقال کنترل است. مقدار `0` تلاش را برای نوبت بعدی حلقه صف می‌کند. درخواست‌های تکراری، نخستین مهلت مثبت را حفظ می‌کنند. رد اعتبارنامه حداقل یک ثانیه تأخیر دارد و حتی با بازهٔ اتصال مجدد صفر، از عقب‌نشینی نمایی پیروی می‌کند.

`request-timeout-ms` با زمان‌سنج مستقل روی worker 0، اگر درخواستی بیش از زمان
تنظیم‌شده بی‌پاسخ بماند، line کنترل را می‌بندد و دوباره متصل می‌کند. این مهلت
حتی با غیرفعال بودن ping/pull/push اعمال می‌شود و از لحظهٔ تحویل درخواست به
تونل بعدی شروع می‌شود. برای `Authenticate`، زمان انتظار در صف تونل بعدی برای
برقراری اتصال یا handshake نیز در مهلت حساب می‌شود. مقدار `0` مهلت را غیرفعال می‌کند.

`max-pending-requests` سقف پذیرش درخواست است. جدول پر، pull و push و کار جبرانی مطلوب را تا آزادشدن ظرفیت با پاسخ منطبق حفظ می‌کند؛ batch را پی‌درپی نمی‌سازد، هشدار نمی‌دهد و زمان‌سنج کوتاه تکرار فعال نمی‌کند. پاسخ از نظر معنایی اعتبارسنجی می‌شود و پردازش ثبت اولیه/ACK/خطا پیش از ادامهٔ کار صف‌شده تمام می‌شود. بازگردانی محلی ارسال، ادامه‌ای با تأخیر زمان‌بندی می‌کند؛ correlation قدیمی ظرفیتی آزاد نمی‌کند. با غیرفعال‌بودن مهلت درخواست و کارهای اختیاری، درخواست بی‌پاسخ می‌تواند بدون تکرار پرمصرف، نامحدود منتظر بماند.

`verbose` گزارش‌های متمرکز debug برای چرخهٔ line کنترل، تصمیم اتصال مجدد، تیک زمان‌سنج و تطبیق درخواست/پاسخ را فعال می‌کند. رازها، توکن‌های نشست، رمزها یا JSON خام کاربران ثبت نمی‌شوند.

<span id="پهنای-باند-محلی-هر-user" />

### پهنای باند محلی هر کاربر {#local-per-user-bandwidth}

UserController مقدار `limit.bandwidth.u` و `.d` را بر حسب بایت منطقی واقعی در ثانیه اعمال می‌کند؛ صفر نامحدود است.
همهٔ lineها، controllerها و workerهای همین AuthenticationClient سهم هر user و جهت را مشترک مصرف می‌کنند؛ userها
و clientهای دیگر مستقل‌اند و هماهنگی بین ماشین‌ها وجود ندارد. ورود مثبت first-use را پیش از queue شروع می‌کند،
ولی مصرف سهمیه فقط هنگام handoff ثبت می‌شود. bucket و ticket با ID پایدار در refresh منتقل و از JSON، snapshot و
persistence حذف می‌شوند. multiplier فقط سهمیه را تغییر می‌دهد.

در هر AuthenticationClient، صف‌های هر کاربر حداکثر 4 MiB بایت منطقی، 8 MiB هزینهٔ تخصیص و 1024 نوبت جهت دارند. سقف کل همان AuthenticationClient برابر 64 MiB، 128 MiB و 16384 نوبت است؛ دفترهای بایت/هزینه و نوبت مستقل حساب می‌شوند. این بودجه‌ها میان کلاینت‌ها مشترک نیستند.

<span id="ضریب-مصرف-ترافیک" />

### ضریب مصرف ترافیک {#traffic-multiplier}

گزینهٔ اختیاری `traffic-multiplier` داخل `settings` یک عدد JSON است و پیش‌فرض آن `1` است. مقدارهای
`0.001` تا `1000` با حداکثر سه رقم اعشار مؤثر پذیرفته می‌شوند؛ مثلاً `2` برای یک گیگابایت ترافیک واقعی،
دو گیگابایت از سهمیه کم می‌کند، `1.5` یک‌ونیم گیگابایت و `0.5` نیم گیگابایت. صفر، مقدار منفی، رشته و دقت
پشتیبانی‌نشده هنگام راه‌اندازی رد می‌شوند. ضریب تا پایان عمر همین instance ثابت است.

ضریب برای upload و download همهٔ کاربرها و پروتکل‌هایی که این instance را استفاده می‌کنند یکسان است.
`UserController` و دیگر callerها بایت واقعی اندازه‌گیری‌شده را بدون ضرب اولیه به AuthenticationClient می‌دهند.
کلاینت هر اندازه‌گیری تازه را دقیقاً یک بار، پیش از افزایش شمارنده و بررسی سهمیه، به مصرف قابل‌کسر تبدیل می‌کند؛
در حالت آفلاین نیز همین قاعده برقرار است. مجموع دریافتی از سرور، batch معلق، retry، ACK و بدهی catch-up قبلاً
با واحد قابل‌کسر هستند و هرگز دوباره ضرب نمی‌شوند. AuthenticationServer مقدار گزارش‌شده را بدون ضریب دیگری جمع می‌کند.

محاسبه با عدد صحیح انجام می‌شود و هر کاربر برای هر جهت باقی‌ماندهٔ کسری مستقل دارد. فقط بایت کامل قابل‌کسر
به شمارنده اضافه می‌شود؛ خردکردن ترافیک به payload کوچک هزینه را عوض نمی‌کند. با `0.5`، دو upload یک‌بایتی
مجموعاً یک بایت مصرف حساب می‌شوند؛ download یک‌بایتی باقی‌ماندهٔ نیم‌بایت مستقل دارد. باقی‌مانده‌ها در refresh
با ID پایدار، حتی با تغییر credential همان حساب، منتقل و هنگام reconnect حفظ می‌شوند. این state فقط در RAM است،
در JSON دیتابیس یا پروتکل ذخیره نمی‌شود و با حذف کاربر یا نابودی کلاینت از بین می‌رود؛ crash recovery وجود ندارد.
سرریز شمارنده به مقدار کوچک‌تر برنمی‌گردد و با اشباع کنترل می‌شود.

اولین ترافیک واقعی مثبت، شمارش زمان انقضا را شروع می‌کند، حتی اگر ضریب تخفیفی هنوز یک بایت کامل هزینه نسازد.
login و فراخوانی صفر بایت شروع استفاده نیستند. قواعد فعلی انقضا و رزرو تغییری نمی‌کنند. مجموع ترافیک حساب، محدودیت ترافیک و بایت تأییدنشدهٔ status همگی
**بایت قابل‌کسر از سهمیه** هستند، نه الزاماً بایت فیزیکی شبکه. مجموع کلاینت‌های با ضریب متفاوت، ترافیک واقعی را
قابل بازیابی نمی‌کند. bandwidth، سرعت، تعداد اتصال/IP و timestamp ضرب نمی‌شوند. برای نرخ‌های مختلف از instanceهای
AuthenticationClient جدا با هویت producer مستقل استفاده کنید.

### نمونهٔ پیکربندی {#configuration-example}

نمونه حداقلی برای احراز هویت درون همان process:

```json
{
  "name": "auth-client",
  "type": "AuthenticationClient",
  "settings": {
    "name": "edge-1",
    "secret": "long-random-secret"
  },
  "next": "auth-db"
}
```

نمونه transport محلی loopback:

```json
{
  "name": "auth-client",
  "type": "AuthenticationClient",
  "settings": {
    "name": "edge-1",
    "secret": "long-random-secret",
    "ping-interval-ms": 60000,
    "pull-interval-ms": 300000,
    "push-interval-ms": 300000,
    "reconnect-interval-ms": 5000,
    "request-timeout-ms": 120000,
    "max-pending-requests": 64,
  "sync-max-users": 100000,
  "sync-max-bytes": 268435456,
    "traffic-multiplier": 1,
    "verbose": false
  },
  "next": "auth-server-connector"
}
```

```json
{
  "name": "auth-server-connector",
  "type": "TcpConnector",
  "settings": {
    "address": "127.0.0.1",
    "port": 9000,
    "nodelay": true
  }
}
```

پروتکل احراز هویت، اعتبارنامهٔ کلاینت و جدول کامل کاربران، شامل رمزهای آن‌ها، را حمل می‌کند. لینک راه‌دور نامطمئن به انتقال رمزگذاری‌شده و احرازشده با بررسی هویت سرور نیاز دارد. برای نمونه، `next` گرهٔ احراز هویت را به `auth-tls` تغییر دهید و این پوشش TLS پشتیبانی‌شده را پیش از connector قرار دهید:

```json
{
  "name": "auth-tls",
  "type": "TlsClient",
  "settings": {"sni": "auth.example.com", "verify": true, "alpns": []},
  "next": "auth-server-connector"
}
```

connector را به listener مربوط به TLS همان سرور متصل کنید. ترکیب سرور `TcpListener -> TlsServer -> AuthenticationServer` است؛ `TlsServer` از `cert-file` و `key-file` برای گواهی معتبر `auth.example.com` استفاده می‌کند. `verify:true` زنجیرهٔ گواهی و نام میزبان را بررسی می‌کند. نمونهٔ سادهٔ `127.0.0.1` بالا محلی است.

اعتبارنامه‌های تنظیم‌شده پس از escape در JSON و با احتساب epoch بازگشت 64 بایتی باید در payload دادهٔ Authenticate به اندازهٔ 16,375 بایت جا شوند. مقدار بزرگ‌تر بدون کوتاه‌سازی در راه‌اندازی رد می‌شود.

مقادیر `settings.name` و `settings.secret` باید با یکی از ورودی‌های `settings.auth-clients` در `AuthenticationServer` یکسان باشند:

```json
{
  "name": "edge-1",
  "secret": "long-random-secret",
  "allow-user-pull": true,
  "allow-stats-push": true,
  "allow-user-write": false
}
```

معمولاً گره‌های دیگر با نام گره به `AuthenticationClient` ارجاع می‌دهند. برای نمونه، `Socks5Server` می‌تواند به شکل زیر از یک `AuthenticationClient` موجود استفاده کند:

```json
{
  "name": "socks-server",
  "type": "Socks5Server",
  "settings": {
    "auth-client-node-name": "auth-client",
    "connect": true,
    "udp": false
  },
  "next": "outbound-tcp"
}
```

`AuthenticationClient` در مسیر داده `Socks5Server` قرار نمی‌گیرد. این گره اتصال کنترلی جداگانه‌ای دارد و جدول کاربران دریافت‌شده را از طریق API داخلی در اختیار گره‌های دیگر می‌گذارد.

<span id="api-وضعیت-خارجی" />

### API وضعیت خارجی {#external-status-api}

گره `APIServer` عملیات فقط‌خواندنی `status` را روی worker 0 در دسترس قرار می‌دهد. نوع محتوای درخواست و پاسخ
`application/json` و کدگذاری آن UTF-8 است. بدنهٔ `{}` وضعیت پایه را می‌دهد؛ برای حسابداری تجمیعی از
`{"include_accounting":true}` استفاده کنید. فیلد ناشناخته یا تکراری، مقدار غیربولی و JSON نامعتبر یا دادهٔ اضافی انتهایی، خطای محدود operation می‌دهند.

`traffic_multiplier` همیشه ضریب مؤثر را به صورت عدد دقیق ده‌دهی JSON نشان می‌دهد، حتی بدون نمونه‌گیری حسابداری.
`can_authenticate` و `blocking_reason` مستقل از `connected`، `authenticated` و `sync_phase` هستند.
`connected` دریافت `Est` در جهت downstream را نشان می‌دهد. اعتبارسنجی پاسخ
`Session` می‌تواند `authenticated` را هنگامی که `connected` هنوز false است، فعال کند.
تا وقتی درخواست `Authenticate` در جریان است، `sync_phase` می‌تواند پیش از دریافت
`Est` مقدار `authenticating` داشته باشد.
ترتیب دلیل مسدودشدن: توقف، شروع‌نشدن، خطای پیوستگی، رد اعتبارنامه، کش/ساعت نامعتبر، سپس `none`.
وضعیت صف و درخواست جاری، اندازه و شمار ورودی‌های batch حل‌نشده، مهلت‌های باقی‌مانده، revisionهای اعمال‌شده و
مشاهده‌شده، سن آخرین موفقیت احراز هویت/نصب جدول و ساعت/ACK مصرف، و آخرین خطای محدودشده گزارش می‌شوند.
کش معتبر می‌تواند هنگام قطعی ترافیک تازه را بپذیرد؛ رد صریح اعتبارنامه ممکن است پذیرش را مسدود کند، درحالی‌که `users_loaded` همچنان true است. sequence و تعداد/اندازهٔ batch حل‌نشده و محدودیت‌های باقی‌ماندهٔ درخواست و retry نیز گزارش می‌شوند. `retained_catchup_slots` تعهدهای نگه‌داشته‌شده را می‌شمارد؛ `orphan_debt_count` تعهدهای IDهایی را می‌شمارد که مرجع، نبودن آن‌ها را تأیید کرده است. کلاینت بیکار با فقط این تعهدها `sync_phase: "orphan_debt"` دارد و پی‌درپی batch غیرقابل‌ارسال زمان‌بندی نمی‌کند.
وقتی مصرف ثبت‌شده یا مشاهدهٔ اولین مصرف منتظر batch بعدی است، `sync_phase` برابر `catchup_pending` است.
مرحلهٔ capture، refresh اجباری و عملیات در حال اجرا وضعیت مشخص‌تر خود را حفظ می‌کنند. کلاینت با وضعیت `idle`
ممکن است هنوز ترافیک محلی داشته باشد که منتظر push دوره‌ای بعدی است.
زمان موفقیت نامعلوم `null` است؛ صفر ساعت monotonic معتبر است. تاریخچه با اتصال مجدد باقی می‌ماند.
آخرین خطای محدودشده فقط کد و نام عملیات ثابت دارد و متن خطای سرور را نشان نمی‌دهد؛ خطای تاریخی الزاماً به معنی مسدودبودن پذیرش فعلی نیست.
سن ACK پذیرش در حافظهٔ سرور را نشان می‌دهد و به معنای ذخیرهٔ پایدار روی دیسک نیست.

`accounting_state` یکی از `not_requested`، `available` یا `unavailable` است. تنها در نمونهٔ درخواستی و موفق،
`locally_unacknowledged_upload_bytes`، `locally_unacknowledged_download_bytes`، `usage_user_count`،
`first_use_observation_count`، `accounting_lower_bound`، `sampling_started_ms` و `sampling_finished_ms` وجود دارند.
شمارنده‌های upload/download بر حسب بایت قابل‌کسر از سهمیه هستند. ACK گم‌شده ممکن است متعلق به مصرفی باشد که سرور قبلاً اعمال کرده است. همهٔ اعداد بدون علامت ۶۴ بیتی به صورت
رشتهٔ ده‌دهی JSON ارسال می‌شوند. هیچ token، epoch، batch خام، شناسه یا اطلاعات کاربر و فهرست IP برگردانده نمی‌شود.

بدهی فعال، catch-up و batch تغییرناپذیر بر اساس شناسه ادغام می‌شوند و همپوشانی دوباره شمرده نمی‌شود؛ ترافیک بعدی
و بدهی حفظ‌شدهٔ کاربران غیرفعال نیز منظور می‌شوند. شمار مشاهدهٔ اولین مصرف از وضعیت صریح تأییدنشده محاسبه می‌شود،
نه صرفاً وجود timestamp در batch. اشباع شمارنده یا سرریز مجموع، حتی با مقدار نمایشی صفر،
`accounting_lower_bound` را فعال می‌کند. نمونه‌گیری پیش از کپی حسابداری زیر قفل جدول، mutex پذیرش/کنترل را آزاد می‌کند. کپی هر کاربر در بازهٔ monotonic گزارش‌شده سازگار است و ترافیک میان نمونه‌ها ادامه دارد. جدول‌ها با reference حفظ می‌شوند، حافظهٔ موقت با رزرو handler از پیش بررسی می‌شود و کار محدود اسکن خطی/ادغام radix با بررسی deadline انجام می‌شود.
حافظه و مهلت پیش از کار و میان مراحل محدود بررسی می‌شوند؛ در صورت ناکافی‌بودن، وضعیت پایه حفظ می‌شود و حسابداری
`unavailable` است. پرس‌وجو شمارنده‌ها، baseline، مشاهده‌ها، batch، retry یا زمان‌بندی همگام‌سازی را تغییر نمی‌دهد.

## رفتار پیشرفته {#advanced-behavior}

<span id="مدل-ارتباطی" />

### مدل ارتباطی {#communication-model}

`AuthenticationClient` یک line کنترل بلندمدت دارد؛ برای هر درخواست یا کار line جدا نمی‌سازد.

هنگام راه‌اندازی، worker 0 یک `line_t` داخلی می‌سازد و `Init` را به تونل بعدی می‌فرستد. در زنجیره‌ای مانند `AuthenticationClient -> TcpConnector`، همان line واتروال به یک اتصال انتقال خروجی به زنجیرهٔ سرور تبدیل می‌شود. درخواست‌های احراز هویت، ping، pull و push همگی به‌شکل پیام‌های پروتکل روی همان line فریم‌بندی می‌شوند.

عملیات جدا، اتصال جدا باز نمی‌کنند. همگام‌سازی زمان‌بندی‌شده، `authenticationclientRequestPull()` و `authenticationclientRequestPush()` صریح و جریان احراز هویت اولیه همگی پیام را روی همان line صف می‌کنند. پاسخ‌ها با `correlation_id` تطبیق داده می‌شوند؛ بنابراین حتی با چند درخواست معلق روی یک انتقال، پاسخ‌ها قابل‌شناسایی‌اند.

کلاینت تا زنده‌بودن انتقال سمت downstream، line را باز نگه می‌دارد. با بسته‌شدن آن، `Finish` در downstream، line تحت مالکیت را می‌بندد و از بین می‌برد، توکن نشست فعال و وضعیت درخواست‌های معلق را پاک می‌کند و اتصال مجدد را زمان‌بندی می‌کند. اتصال بعدی با `Authenticate` تازه آغاز می‌شود؛ کلاینت توکن قبلی را استفاده نمی‌کند، گرچه سرور ممکن است رکورد نشست قبلی را تا پایان مهلت بی‌کاری نگه دارد.

جدول محلی طبق سیاست پذیرش به‌صورت کش در اختیار فراخوانندگان می‌ماند. همگام‌سازی
سرور روی line کنترل تازه پس از اعتبارسنجی پاسخ `Session` شروع می‌شود.

<span id="پروتکل-wire" />

### پروتکل روی سیم {#wire-protocol}

پروتکل با `AuthenticationServer` تطابق دارد.

پیام request:

```text
u32 body_len
u8[64] session_token
request_frame...
```

فریم request:

```text
u8 request_type
u32 correlation_id
u32 request_data_len
u8[request_data_len] request_data
```

پیام response:

```text
u32 body_len
u64 config_revision
u64 stats_revision
response_frame...
```

فریم response:

```text
u8 response_type
u32 correlation_id
u32 response_data_len
u8[response_data_len] response_data
```

همه فیلدهای integer با ترتیب big-endian نوشته می‌شوند. کلاینت در هر پیام یک فریم درخواست می‌فرستد. parser می‌تواند هر تعداد فریم پاسخ را در یک پیام پاسخ بخواند و هر فریم را با correlation ID به درخواستش مرتبط کند.

revision‌های پاسخ به‌عنوان آخرین revision‌های سرور ذخیره می‌شوند و پیش از دریافت‌های زمان‌بندی‌شده، با revision جدول کاربران محلی مقایسه می‌شوند.

<span id="این-نود-چه-میکند" />

### جریان راه‌اندازی {#startup-flow}

در `onStart`، تونل کار راه‌اندازی را برای worker 0 صف می‌کند.

سپس worker 0:

1. زمان‌سنج‌های دوره‌ای ping و sync را فعال می‌کند.
2. line کنترل تحت مالکیت را می‌سازد.
3. وضعیت محلی این تونل برای line را پیش از فراخوانی تونل بعدی آماده می‌کند.
4. `tunnelNextUpStreamInit()` را می‌فرستد.

وقتی `Init` تونل بعدی بازگردد و line کنترل تحت مالکیت همچنان زنده باشد، کلاینت
می‌تواند `Authenticate` را با توکن نشست صفر بفرستد. اگر تونل بعدی نوشتن را متوقف
کرده باشد، ارسال تا دریافت `Resume` به تعویق می‌افتد.

`Authenticate` فیلدهای `name`، `secret` و برای بازگشت، `epoch` اختیاری را می‌پذیرد. پاسخ Session شامل 128 بایت است: توکن 64 بایتی و سپس epoch حسابداری 64 بایتی؛ هر دو نمایش شانزده‌شانزدهی مقادیر تصادفی امن سیستم‌عامل‌اند. کلاینت توکن را ذخیره می‌کند، ابتدا batch باقی‌مانده را تعیین‌تکلیف می‌کند و سپس با `GetUsersPage` جدول را می‌گیرد. پاسخ کهنه نمی‌تواند epoch ثبت‌شده را جایگزین کند.

<span id="همگامسازی-صفحهای-و-retry" />

### همگام‌سازی صفحه‌ای {#paged-synchronization}

`GetUsersPage` شماره ۹ و پاسخ `Users` شماره ۳ جدول کامل را صفحه‌ای منتقل می‌کنند. هدف هر صفحه با framing برابر
۲۵۶ KiB و حداکثر ۱۲۸ کاربر است. یک رکورد نخست بزرگ‌تر می‌تواند به‌تنهایی تا سقف سخت پیام با کسر metadata و header
جا بگیرد؛ رکورد غیرقابل‌جاگیری خطای مرتبط `user-too-large` می‌دهد و هیچ فیلدی truncate نمی‌شود. جدول بیش از ۱۶ MiB
قابل همگام‌سازی است. `sync-max-users` پیش‌فرض `100000` و `sync-max-bytes` پیش‌فرض `268435456` دارند؛ هر دو عدد
صحیح دقیق مثبت و قابل‌نمایش روی میزبان‌اند. بایت‌ها مجموع span دقیق object هر user، با whitespace داخلی و بدون
metadata/کاما/bracket هستند و پیش از ساخت کاربران تازه بررسی می‌شوند. کل total از پیش reserve نمی‌شود. عبور از سقف
`sync_limit` می‌دهد، staging را حذف و cache و بدهی را حفظ می‌کند. این سقف RAM دقیق نیست: جدول‌های active/baseline/
staging، indexها، JSON و صف‌ها حافظهٔ بیشتری می‌خواهند. تغییر تنظیم restart عادی می‌خواهد و crash recovery نمی‌آورد.

درخواست نخست `epoch`، `sequence` به شکل رشتهٔ ده‌دهی دقیق و `digest` با ۶۴ رقم hex کوچک برای آخرین ACK مطابق دارد؛
در enrollment، sequence برابر `"0"` و digest شامل ۶۴ صفر است. ادامه `cursor` و `total` ده‌دهی دارد. cursor شامل
۳۲ رقم instance، ۱۶ رقم config revision و ۱۶ رقم موقعیت بعدی است و مجوز محسوب نمی‌شود. هر درخواست token، مجوز pull
و checkpoint زندهٔ producer را دوباره می‌سنجد. پاسخ فیلدهای `instance`، `config-revision`، `stats-revision`، `total`،
`position`، `count`، `cursor`، `complete`، `validated`، `epoch`، `sequence`، `digest`، `server-time-ms`،
`accounting-time-ms` و آرایهٔ credential-bearing `users` دارد؛ تمام اعداد ۶۴ بیتی رشتهٔ ده‌دهی دقیق‌اند.

صفحه‌ها پیوسته پیش می‌روند. جدول خالی یک صفحهٔ دادهٔ complete خالی دارد. پس از آخرین داده با `complete:true` و
`validated:false`، کلاینت cursor/total نهایی و `validate:true` می‌فرستد؛ سرور تنظیمات و checkpoint را زیر قفل وضعیت دوباره بررسی می‌کند و پاسخ تأیید `validated:true`، count صفر و
users خالی دارد. سرور برای traversal یک snapshot تغییرناپذیر با سقف حافظه نگه می‌دارد؛ ویرایش config در میانهٔ
دریافت آن را باطل نمی‌کند. اتمام بودجه یا انقضای idle ممکن است retry لازم کند. revision تنظیمات و آمار snapshot ثابت
است و می‌تواند از revision زندهٔ envelope قدیمی‌تر باشد. هر صفحه نمونهٔ ساعت تازهٔ مخصوص همان پاسخ را دارد.

شکست traversal فقط staging را حذف می‌کند و روی همان اتصال احرازشده با backoff تکرار می‌شود. تناقض پروتکل یا checkpoint همچنان پیوستگی را متوقف می‌کند. با cache معتبر، مصرف تازه از baseline فعلی میان تلاش‌های دریافت گزارش
می‌شود؛ هیچ batch تازه‌ای از traversal فعال عبور نمی‌کند. retry موعددار تنظیمات حتی زیر گزارش پیوسته نوبت می‌گیرد.
بدهی ID حذف‌شده مانع نصب جدول نیست: بایت و مشاهدهٔ اولین مصرف در ledger محدود orphan می‌مانند و تا بازگشت همان
ID ارسال نمی‌شوند. بدهی هرگز حذف نمی‌شود؛ بازگشت ID آن را به سهمیهٔ محلی برمی‌گرداند و فقط یک بار گزارش می‌کند.
مبدأ محلی اولین مصرف و سن سپری‌شده پیش از projection ساعت تازه برمی‌گردند؛ غیبت حساب expiry را از ابتدا شروع نمی‌کند.
سقف `sync-max-bytes` اوج حافظهٔ آماده‌سازی ledger شامل آرایهٔ قبلی، جایگزین، کپی موقت و فضای realloc را هم محدود
می‌کند. اتمام این بودجه `sync_limit` می‌دهد و جدول قبلی و تمام بدهی را حفظ می‌کند. رد بودجهٔ capture کار معلق را نگه می‌دارد و حداکثر هر یک ثانیه
دوباره تلاش می‌کند؛ حلقهٔ timer کوتاه ایجاد نمی‌شود.

تا validation نهایی generation و جدول عمومی عوض نمی‌شوند. ابتدا تمام کارهای fallible تمام، سپس delta زنده،
مشاهدهٔ اولین مصرف، carry ضریب، reservation، صف و ticket با ID منتقل و active/baseline با هم publish می‌شوند.
ساعت هر user پس از migration با نمونهٔ wall/accounting و receipt همان صفحه نصب می‌شود؛ تأخیر صفحه‌های بعدی سن را
reset نمی‌کند. batch حل‌نشده پیش از صفحهٔ نخست replay می‌شود. تمام traversal و validation مانع batch تازه‌اند و
first-use/push به‌صورت latch می‌مانند. تناقض checkpoint صفحه خطای continuity است و بدهی را پاک نمی‌کند.

مهلت مطلق `request-timeout-ms` برای هر صفحه و validation، شامل درخواست‌های متوقف‌شده با Pause، جداست؛ کل traversal پیش‌رونده می‌تواند طولانی‌تر باشد. قطع، timeout،
صفحهٔ malformed یا بدون پیشرفت، conflict و limit تنها staging را حذف می‌کنند. quiescence پیش از آزادکردن وضعیت تحت مالکیت، callbackها و زمان‌سنج‌ها را تعیین‌تکلیف می‌کند. retry دریافت حداقل یک ثانیه فاصله دارد؛ retry عادی transport نخست interval اتصال مجدد را حفظ می‌کند، حتی صفر force-queued. شکست‌های بعدی از
`max(reconnect-interval-ms,1000)` دوبرابر تا `max(base,60000)` می‌شوند و jitter افزوده تا یک‌چهارم دارند. کف refusal
آمار ۳۰ ثانیه یا interval بزرگ‌تر نیز رعایت می‌شود. درخواست مستقیم، Resume، first-use و timer آن را دور نمی‌زنند.
Session/Pong/صفحهٔ میانی streak را پاک نمی‌کند؛ نصب کامل پاک می‌کند. status شامل `sync_retry_streak`،
`sync_retry_remaining_ms`، `sync_retry_failure`، `orphan_debt_count`، `traversal_active`، `sync_staged_users`، `sync_staged_bytes` و
`sync_total_users` است. wakeup مستقل با intervalهای اختیاری صفر هم کار می‌کند.

<span id="جدول-کاربران-محلی" />

### جدول کاربران محلی {#local-users-table}

کلاینت یک جدول محلی فعال از کاربران نگه می‌دارد که یک `wrwlock_t` در سطح تونل از آن محافظت می‌کند.

از دید تونل‌های دیگر، جایگزینی جدول در جریان `GetUsersPage` به‌صورت atomic انجام می‌شود:

1. هر صفحه در یک `users_t` خصوصی موقت وارد می‌شود؛ تأیید نهایی باید پیش از نصب موفق شود.
2. جدول تازه اعتبارسنجی می‌شود؛ هر کاربر باید ID پایدار غیرصفر داشته باشد و range‌های هم‌پوشان در `wireguard-allowed-ips` پذیرفته نمی‌شوند.
3. deltaهای مصرف قابل‌کسرِ sync‌نشده، باقی‌ماندهٔ کسری هر جهت و شمارنده‌های runtime مخصوص همان process، با durable user id منتقل می‌شوند؛ هیچ fallback از credential برای هویت کاربر وجود ندارد.
4. deadline محلی انقضای هر کاربر از فیلدهای زمانی متعلق به سرور و هر دو metadata ساعت، با حفظ سن اولین استفاده و جزء تاریخ مطلق محاسبه می‌شود.
5. pointer جدول فعال زیر write lock مربوط به rwlock جابه‌جا می‌شود.
6. شمارنده generation افزایش می‌یابد.
7. جدول قدیمی پس از جابه‌جایی آزاد می‌شود.

reader‌ها هنگام کپی JSON یا آمار و نیز هنگام به‌روزرسانی ترافیک با ID پایدار، read lock همان rwlock را نگه می‌دارند. به این ترتیب هیچ pointer‌ای داخل `users_t` فعلی در میانه عملیات نامعتبر نمی‌شود.

جدول محلی هم نقش cache را دارد و هم شمارنده‌های محلی را تجمیع می‌کند. مرجع اصلی config کامل هر کاربر، از جمله `wireguard-allowed-ips` اختیاری و `first-usage-at-ms`، سرور است.

سرور `first-usage-at-ms` مرجع را نگه می‌دارد؛ کلاینت‌ها مشاهدهٔ تغییرناپذیر نخستین ترافیک محلی را با batchهای دارای حذف تکرار گزارش می‌کنند. انقضای محلی منتظر این گزارش نمی‌ماند.

### پذیرش از کش و انقضای محلی {#cached-admission-and-local-expiry}

پس از نخستین همگام‌سازی معتبر جدول و مبنای ساعت، `authenticationclientCanAuthenticate()` در قطع شبکه و
احراز هویت دوباره از آخرین cache حافظه استفاده می‌کند؛ cache مهلت کهنگی ندارد. enabled، انقضا، سهمیه ترافیک و
reservation محلی اتصال/IP همچنان اعمال می‌شوند. نبود cache، توقف، خطای نهایی continuity یا رد صریح اعتبارنامه
خود کلاینت، پذیرش جدید را می‌بندد. فقط پاسخ موفق و معتبر Session رد صریح را پاک می‌کند؛ timeout، قطع اتصال،
پاسخ خراب و `authentication-required` چنین اثری ندارند. اتصال‌های قبلاً مجاز به ثبت مصرف و اجرای محدودیت‌های
محلی ادامه می‌دهند. هر درخواست HTTP روی اتصال reused پذیرش تازه است؛ exchange جاری و CONNECT ادامه می‌یابند.
ویرایش مدیر پس از refresh معتبر می‌رسد. دو کلاینت قطع‌شده با مصرف شناخته‌شده ۸۰ از سهمیه ۱۰۰ گیگابایت می‌توانند
هر کدام ۲۰ مصرف کنند و مجموع نهایی ۱۲۰ شود؛ سهمیه و reservation محلی، تضمین سراسری نیستند.

`authenticationclientCanAuthenticate()` پذیرش حساب را از آمادگی نشست کنترل جدا می‌کند. رد صریح، پاسخ مرتبط `authentication-failed` به Authenticate است. `session-unavailable` پس از تطبیق اعتبارنامه، شکست موقت ظرفیت سرور یا تولید token/epoch را نشان می‌دهد؛ مسیر عمومی خطای راه‌دور با اتصال مجدد، کش معتبر و حسابداری معلق را حفظ می‌کند. `GetState()` و `IsReady()` همچنان وضعیت نشست کنترل‌اند. جست‌وجوی password، SHA224، SHA256، UUID، کلید WireGuard صادرشده و پذیرش اتصال، دسترس‌پذیری را با ترتیب قفل mutex کنترل و سپس قفل کاربران دوباره بررسی می‌کنند. تازه‌سازی خراب کش قبلی را حفظ می‌کند. مصرف قبلاً حساب‌شده حتی پس از غیرفعال‌سازی کاربر یا کاهش محدودیت در سرور قابل‌پذیرش است.

پاسخ هر صفحه باید هر دو فیلد canonical و دقیق `server-time-ms` و `accounting-time-ms` (با مقدار مثبت برای دومی) را داشته باشد؛
metadata نامعتبر refresh را بدون جایگزینی cache معتبر رد می‌کند و fallback به ساعت دیواری کلاینت وجود ندارد.
سرور یک بار `C0 = max(wall-ms, 1)` و monotonic `M0` را ثبت می‌کند و با جمع saturating زمان سپری‌شده monotonic
ساعت حسابداری را پیش می‌برد. اصلاح بعدی ساعت دیواری آن را reset نمی‌کند و anchor در فایل ذخیره نمی‌شود.

اولین upload یا download واقعی غیرصفر، حتی با هزینهٔ گرد‌شدهٔ صفر، درون قفل write کاربر، نمونه تازه monotonic، origin محلی معتبر حتی در صفر و
برآورد مثبت و تغییرناپذیر اولین استفاده برای گزارش را ثبت می‌کند. login، reservation، فراخوانی صفر بایت و rebase
شروع مصرف نیستند. ثبت مشاهده، شمارنده و تصمیم انقضا در transaction با ترتیب user سپس stats انجام می‌شود؛ نبود
خروجی notification مانع مشاهده نیست. سن سپری‌شده حتی با مدت صفر حفظ می‌شود؛ ACK، reconnect، pull تکراری یا نبود
فیلد canonical آن را پاک یا جوان نمی‌کنند. مشاهده زودتر کلاینت دیگر می‌تواند سن را بیشتر کند. origin واردشده
در آینده تا رسیدن زمانش آینده می‌ماند؛ مصرف محلی واقعی می‌تواند origin زودتری بسازد.

انقضای تاریخ مطلق با ساعت دیواری سرور و مدت پس از اولین استفاده با سن monotonic جدا محاسبه می‌شوند. تاریخ
بدون تغییر deadline زودتر را حفظ می‌کند؛ ویرایش/پاک‌کردن هر سیاست فقط جزء خودش را دوباره محاسبه می‌کند. deadline
زودتر حاکم است؛ انقضای گذشته در monotonic صفر هرگز به unlimited تبدیل نمی‌شود. state زمان/مشاهده/ACK و reservation
با ID پایدار، حتی هنگام تغییر credential همان ID، منتقل می‌شوند؛ policy و timestamp مرجع جدید حفظ می‌شوند.
کپی عمومی و JSON این state محلی را ندارند. تبدیل بین ماشین‌ها برآوردی با خطای تأخیر شبکه/serialization و drift
است. رفتار suspend ساعت runtime عوض نمی‌شود؛ CLOCK_MONOTONIC لینوکس زمان تعلیق میزبان را حساب نمی‌کند.

همهٔ این وضعیت‌ها فقط در RAM هستند؛ بازیابی پس از خرابی، journal، outbox یا تحویل نهایی تضمین‌شده وجود ندارد.

### ارسال آمار {#stats-push}

دلتاهای بایت و مشاهده اولین مصرف محلی با ID پایدار همگام می‌شوند:

```json
{"epoch":"<64 hexadecimal bytes>","sequence":1,"users":[{"id":42,"up":10,"down":0,"first-usage-at-ms":1792252800000}]}
```

ریشه فقط `epoch`، `sequence`، `users` و هر ورودی دقیقاً `id`، `up`، `down`، `first-usage-at-ms` دارد؛ تمام فیلدها اجباری‌اند.
کلید ناشناخته/تکراری یا غیرترافیکی، NUL خام/escaped، UTF-8 نامعتبر، داده اضافی، عمق بیش از سه container یا بیش از ۳۶۸۷۱ مقدار واژگانی (شامل کلیدها) رد
می‌شود و بودجه پیام authentication برقرار است.
کلاینت یک batch immutable و snapshot متعلق به خود از IDها، مجموع شمارنده‌ها و مشاهده‌های نخستین استفاده را در طول عمر تونل تا ACK دارای epoch، sequence و SHA-256 digest مطابق یا اثبات معتبر عدم commit نگه می‌دارد.
refusal، timeout، پاسخ malformed و قطع اتصال آن را حذف نمی‌کنند. retry همان بایت‌ها را با correlation تازه و token
فعلی می‌فرستد. batch خالی ارسال نمی‌شود، هر batch حداکثر ۴۰۹۶ ورودی دارد و sequence از ۱ بدون wrap جلو می‌رود.
فقط کاربران/directionهای subset تأییدشده baseline را جلو می‌برند. اعداد صحیح ساده تا INT64_MAX و رشته decimal
تا UINT64_MAX دقیق هستند؛ tokenهای decimal/exponent یا مقادیر کسری، منفی، nonfinite و overflow رد می‌شوند.

اگر A مجموع محلی، B baseline تأییدشده و S snapshot باشد، ACK معتبر B را برای همان subset به S می‌رساند. pull
بعدی مجموع `G + (A - B)` را با baseline برابر G نصب می‌کند. هنگام batch حل‌نشده pull نصب نمی‌شود و push از pull
در حال اجرا جلو نمی‌زند. هر ACK، حتی replay، `needs-pull: true` دارد تا زمان اولین استفاده سرور و مجموع دیگر
کلاینت‌ها دریافت شود. شکست غیرحسابداری refresh مانع گزارش‌های تازه از baseline قبلی نیست؛ retry دریافت مستقل ادامه می‌یابد. کار اولین استفاده و درخواست‌های مسدودشده برای اجرای بعدی باقی می‌مانند.

هنگام pull الزامی یا in-flight، first-use push با latch کلی و flag هر user معلق می‌ماند. اتمام pull بدون packet
دیگر push را ادامه می‌دهد. Pause نوشتن timer پیشرفت تکراری ایجاد نمی‌کند؛ Resume کار ثبت‌شده را ادامه می‌دهد.

هر timestamp گزارش، همان مشاهده تغییرناپذیر تولیدکننده است، حتی در گزارش مثبت پس از ACK. timestamp، ID و
sequence غیرصفرند. برای مشاهده ACKنشده، هر دو delta می‌توانند صفر باشند؛ saturation شمارنده مانع گزارش metadata
نیست. ACK فقط totals و markerهای همان snapshot را تأیید می‌کند و origin/سن را نگه می‌دارد؛ حلقه resend خالی نداریم.

رد `stats-push-not-allowed` پذیرش از cache را با همان enabled/expiry/quota و ظرفیت محلی حفظ می‌کند. batch دقیق،
بدهی و شواهد اولین استفاده باقی می‌مانند. خطاهای push غیرنهایی مانند `invalid-usage-batch`، `usage-digest-failed`
یا خطای ناشناخته نیز بدون فرض درباره commit، همان batch را حفظ می‌کنند. reconnect و reauthenticate پس از cooldown
monotonic حداقل ۳۰ ثانیه یا interval اتصال مجدد در صورت بزرگ‌تر بودن انجام می‌شود؛ حتی با همه intervalهای صفر،
retry سر موعد مستقل زمان‌بندی می‌شود. ترافیک، درخواست صریح یا Resume آن را دور نمی‌زنند. Session موفق این وضعیت
را پاک نمی‌کند؛ فقط ACK مطابق batch حفظ‌شده آن را پاک می‌کند. status دلیل محدود `stats_push_denied` یا
`stats_push_rejected` و deadline/debt واقعی را نشان می‌دهد. diagnostic خطای سرور حداکثر ۱۲۸ بایت ورودی را escape
می‌کند و truncation را مشخص می‌کند.

خطای مرتبط `usage-accounts-missing` یک proof JSON شامل `epoch`، `sequence` و `digest` تلاش،
`checkpoint-sequence`، `checkpoint-digest` و آرایهٔ غیرخالی `missing-ids` دارد؛ عددها رشتهٔ ده‌دهی‌اند.
کلاینت بایت‌های دقیق batch، epoch، checkpoint قبلی و عضویت تمام IDها را بررسی می‌کند. فقط پس از این اثبات عدم
commit، batch آزاد می‌شود؛ sequence، baseline و بدهی مصرف نمی‌شوند. IDهای مفقود فوراً از پذیرش و forwarding
جدید کنار گذاشته می‌شوند؛ ترافیک قبلاً تولیدشده هنوز ثبت و سپس اتصال بسته می‌شود و release اتصال/ticket معتبر است.
کلاینت refresh می‌خواهد و می‌تواند همان sequence را برای حساب‌های باقی‌مانده بازسازی کند. proof نامنطبق یا malformed
batch نامطمئن را دست‌نخورده نگه می‌دارد.

تا حل batch هیچ pull از آن جلو نمی‌زند؛ cache مانند outage قدیمی می‌ماند و ترافیک بعدی جدا جمع می‌شود. بازیابی به
همان epoch زنده سرور وابسته است؛ permission تنظیم startup است و تغییر آن همراه restart تضمین بازیابی checkpoint
حافظه را ندارد. `usage-replay-conflict` و `usage-sequence-invalid` خطای نهایی‌اند و پذیرش تازه را می‌بندند.
`authentication-required` همان مسیر عادی reauthentication را با حفظ batch طی می‌کند.

تازه‌سازی کامل با صفحه‌های محدود انجام می‌شود و مانع حسابداری تا تأیید نهایی حفظ می‌شود؛ بخش همگام‌سازی صفحه‌ای را ببینید.

پس از replay و refresh الزامی reconnect، بدهی نسبی بایت‌ها و مشاهده‌ها تا همان نقطه capture و خودکار در batchهای
محدود تخلیه می‌شود؛ بعد از هر ACK یک pull درخواست می‌شود. با همه intervalهای اختیاری صفر نیز کار انجام می‌شود.
پیشرفت روی worker صفر با timer غیرصفر بین batchها yield و refusal منابع را retry می‌کند. ناتوانی در ایجاد trigger
الزامی، orderly shutdown می‌خواهد؛ quiescence آن را متوقف می‌کند و دوباره فعال نمی‌سازد. بدهی نسبی تا ACK مطابق حفظ می‌شود، حتی اگر rebase saturating آن را در شمارنده مرئی پنهان کند. capture محدود است و زیر
ترافیک پیوسته یا rebase مصرف کلاینت دیگر پایان می‌یابد. مصرف پس از cut از سیاست عادی push و trigger اولین استفاده
پیروی می‌کند. قطع بعدی هم batch تغییرناپذیر و هم بدهی نسبی باقی‌مانده catch-up را نگه می‌دارد. پس از replay/refresh،
capture تازه این بدهی را با deltaهای مرئیِ تأییدنشده ادغام می‌کند، بدون اینکه بخش هم‌پوشان دوبار شمرده شود.
فقط ACK مطابق، بدهی همان گزارش را مصرف می‌کند؛ قطع اتصال یا rebase شمارنده آن را پاک نمی‌کند. نابودی نهایی تونل
این state را از RAM آزاد می‌کند و تحویل نهایی را تضمین نمی‌کند.

checkpoint سرور با هویت احراز‌شده مرتبط است و expiry یا جایگزینی session آن را پاک نمی‌کند. processهای مستقل
نام تنظیم‌شده مستقل لازم دارند. از دست رفتن epoch با batch نامطمئن، وضعیت
`kAuthenticationClientStateContinuityError` ایجاد می‌کند: batch حفظ می‌شود، transport بسته می‌شود و تلاش خودکار
تا رفع وضعیت حسابداری توسط اپراتور متوقف می‌شود؛ API برای reset یا reconciliation وجود ندارد. بدون batch نامطمئن، از دست رفتن continuity در Authenticate اجازهٔ ثبت تازه و pull می‌دهد؛ تناقض checkpoint در صفحه همچنان نهایی است. این تضمین برای قطع اتصال در زمان
اجرای دو process است و بازیابی مصرف پس از crash/restart ارائه نمی‌دهد.
ACK پذیرش در حافظه سرور است، نه ذخیره دیسک. ذخیره دوره‌ای/نهایی دیتابیس checkpoint را ذخیره نمی‌کند. restart
کلاینت ممکن است مصرف گزارش‌نشده را از بین ببرد؛ restart سرور ممکن است مصرف ACKشده پس از آخرین ذخیره موفق و
تمام checkpointها را از دست بدهد. shutdown تضمین تحویل نهایی مصرف نیست.

ترافیک تجمعی و زمان اولین استفاده متعلق به مجموع سرورند. `UpdateUser` با ID پایدار فقط تنظیمات صریح را patch
می‌کند؛ شمارنده، زمان ایجاد/اولین استفاده، credential و runtime حفظ می‌شوند. patch مجوز `allow-user-write` و batch
مجوز مستقل `allow-stats-push` می‌خواهد. عملیات remote reset وجود ندارد.
اتصال فعال و reservation IP وضعیت admission محلی‌اند، نه telemetry global. آمار ذخیره/import شده IP، device،
connection و speed نمای قابل اعتماد از اشغال زنده global یا ورودی admission نیستند. گزارش آینده connection به
snapshot هر producer، ترتیب و expiry، و speed به پنجره اندازه‌گیری و freshness نیاز دارد؛ مقدار مفقود صفر نیست.
IP متمایز نیازمند مجموعه هویت، پنجره و حذف تکرار بین producerها است. device به تعریف هویت و روش جمع‌آوری نیاز
دارد. هیچ‌یک از این گزارش‌ها یا reset در این مرحله پیاده‌سازی نشده است.

### API داخلی {#internal-api}

API داخلی WaterWall از این مسیر در دسترس است:

```c
#include "AuthenticationClient/interface.h"
```

این API عمداً از `api.c`، الگوی API خارجی همهٔ تونل‌ها، جداست.

تونل‌های دیگر نباید اشاره‌گر خام `user_t *` از AuthenticationClient بگیرند یا ذخیره کنند. در عوض از `user_handle_t` در `ww/objects/user_handle.h` استفاده می‌کنند که شامل این فیلدهاست:

```text
users_generation
user_id
```

handle شناسه‌ای مقداری است، نه شیء تحت مالکیت. `user_id` از رکورد همگام‌شده کپی می‌شود و برای اعتبار handle باید غیرصفر باشد. جایگزینی کامل جدول، generation را افزایش می‌دهد؛ helperهای خواندن وابسته به generation ممکن است handle قدیمی را رد کنند. فراخواننده می‌تواند handle تازه بگیرد یا با `authenticationclientUserHandleIsLive()` بررسی کند. `authenticationclientGetUserBySHA224()`، `authenticationclientGetUserBySHA256()`، `authenticationclientGetUserByUUID()` و `authenticationclientGetUserByWireGuardPublicKey()` مسیرهای دیگر جست‌وجو هستند؛ نتیجهٔ موفق همان handle مبتنی بر ID است.

wrapperهای `WithResult` جزئیات شکست جست‌وجو را حفظ می‌کنند؛ `WithProfile` رشته‌های اختیاری هویت را سازگار با handle پیدا‌شده کپی می‌کند. profile را با `authenticationclientUserProfileClear()` آزاد کنید. wrapperهای Boolean و همهٔ خانواده‌های جست‌وجوی اعتبارنامه همچنان موجودند. `UserObservePayload` نخستین استفاده را بدون هزینه ثبت می‌کند؛ `UserCommitDelivery` پس از پذیرش پهنای باند، دقیقاً بایت‌های ارسال‌شده را حساب می‌کند. `UserBandwidthRegister/SetEligible/Cancel/Reserve/Release/Preview` نوبت‌های منصفانهٔ هر جهت و هزینهٔ نگه‌داری را مدیریت می‌کنند. `UserAccountTraffic` برای فراخوانندگان فعلی حسابداری فوری اندازه‌گیری‌شده فراهم می‌کند. `UserAddTraffic` قدیمی به generation حساس است و ممکن است handle را پس از تازه‌سازی رد کند؛ اعمال جاری محدودیت و مسیر مشاهده/تحویل، ID پایدار و کف generation عضویت را حل می‌کنند. getterها، کپی خروجی، handleها و pull/push صریح همچنان موجودند.

`authenticationclientUserToJson()` و `authenticationclientUsersToJson()` خروجی کاملِ مخصوص فراخوانندهٔ مورداعتماد و دارای اعتبارنامه، از جمله رمز متنی، هستند. درخت تازهٔ `cJSON` متعلق به فراخواننده است و باید حذف شود. خروجی کل جدول برای همهٔ حساب‌ها زیر قفل‌های خواندن جدول و مجموعه تخصیص و کپی انجام می‌دهد؛ برای وضعیت عمومی از APIهای وضعیت/نمای پالایش‌شده استفاده کنید. آمار در حافظهٔ فراخواننده کپی می‌شود. ترافیک با ID پایدار handle به‌روز می‌شود؛ فراخواننده هرگز `user_t` را مستقیم تغییر نمی‌دهد. هر دو helper ترافیک، بایت واقعی upload/download می‌گیرند؛ از پیش در ضریب ضرب نکنید. کپی آمار، مصرف قابل‌کسر از سهمیه دارد.

helperهای اعمال زندهٔ محدودیت با ID پایدار کار می‌کنند و صرف افزایش generation در تازه‌سازی `GetUsersPage` handle را رد نمی‌کنند. نبود نتیجه یعنی کاربر از جدول تازه حذف شده است. `now_ms` در دامنهٔ ساعت monotonic محلی کلاینت است، زیرا هنگام نصب جدول، انقضا به همان ساعت نگاشت شده است. handle به یک دورهٔ عضویت پیوسته تعلق دارد. تازه‌سازی عادی اعتبار را حفظ می‌کند، اما حذف و ساخت دوبارهٔ همان ID کف generation تازه می‌سازد. handle قدیمی باطل می‌ماند و نمی‌تواند هزینه یا رزرو اتصال/IP حساب بازساخته‌شده را تغییر دهد؛ ticketهای قدیمی شکل‌دهی همچنان هزینهٔ متعلق به کلاینت را آزاد می‌کنند.

`authenticationclientRequestPull()` و `authenticationclientRequestPush()` از line کنترل جاری استفاده می‌کنند. فراخوانندهٔ خارجی کار را برای worker 0 صف می‌کند. تا زمان آماده‌شدن نشست احرازشده، رفع Pause یا رفع تداخل با همگام‌سازی دیگر، درخواست‌های کار با هم ادغام می‌شوند. pull نمی‌تواند در طول push حل‌نشده مبنا را جایگزین کند و push نمی‌تواند از pull فعال جلو بزند. پس از احراز هویت یا ACK مصرف، تازه‌سازی درخواست می‌شود؛ batch نامطمئن باقی‌مانده پیش از آن بازپخش می‌شود. تازه‌سازی ناموفق غیرحسابداری، میان تلاش‌ها گزارش مصرف تازه از مبنای فعلی را اجازه می‌دهد؛ تازه‌سازی موفق بعدی مجموع تأییدشده را پیش از بازگشت به برنامهٔ معمول تطبیق می‌دهد. retry سررسیدهٔ تازه‌سازی پیش از batch تازه نوبت می‌گیرد؛ در غیر این صورت push منتظر بر pull عادی اولویت دارد.

بررسی اعتبارنامه، فعال‌بودن، انقضا و سهمیهٔ ترافیک را می‌سنجد؛ مقادیر ذخیره‌شدهٔ اتصال، IP، دستگاه و سرعت مانع جست‌وجو نمی‌شوند. ظرفیت زنده جداگانه با helper اتمی پذیرش runtime رزرو می‌شود.

### زمان‌سنج‌ها {#timers}

همهٔ زمان‌سنج‌های پروتکل روی worker 0، همان worker line کنترل تحت مالکیت، هستند:

`ping_timer` درخواست مجاز `Ping` یا `Authenticate` را روی line کنترل مقداردهی‌شده می‌فرستد.

`sync_timer` دریافت جدول و ارسال آمار را با کوتاه‌ترین بازهٔ فعال pull/push پیش می‌برد. هر تیک موعد مستقل آن‌ها را بررسی می‌کند؛ ابتدا `PushUserStats` سررسیده و سپس `GetUsersPage` را در صورت اختلاف revision یا فرارسیدن موعد pull صف می‌کند. تیک دوره‌ای به پیمایش فعال می‌پیوندد؛ pull صریح یک پیمایش بعدی را حفظ می‌کند.

`reconnect_timer` نخستین مهلت مثبت تکرار را حفظ می‌کند و زمان واقعی monotonic را دوباره می‌سنجد. تکرار با تأخیر صفر کار صف‌شده است، نه بازکردن بازگشتی از Finish. latch زیر mutex پیش از ارسال به صف منتشر می‌شود؛ اجرا یا لغو آن را یک بار تسویه می‌کند. لغو به line، pool یا زمان‌سنج متعلق به worker دست نمی‌زند.

`request_timer` مستقل از کارهای اختیاری، نزدیک‌ترین درخواست معلق را دنبال می‌کند و deadline را پیش از Payload منتشر می‌کند تا پاسخ/Finish همگام امن باشد. پاسخ منطبق فقط درخواست خودش را تعیین‌تکلیف می‌کند.

زمان‌سنج‌ها در `onWorkerQuiesce` مربوط به worker 0 و پیش از تخلیهٔ مالک جدا می‌شوند، زیرا حذف زمان‌سنج باید روی همان حلقهٔ رویداد مالک انجام شود.

### چرخهٔ عمر و ایمنی line {#lifecycle-and-line-safety}

state مربوط به line کنترلی، جریان خواندن پاسخ‌های downstream و محافظ ورود دوبارهٔ parser را نگه می‌دارد. این state پیش از `tunnelNextUpStreamInit()` مقداردهی اولیه می‌شود و قبل از انتشار finish در جهت upstream یا آزاد شدن line تحت مالکیت کلاینت، از بین می‌رود.

با دریافت `finish` در جهت downstream، کلاینت:

1. pointer line کنترلی فعال را زیر mutex کنترلی پاک می‌کند.
2. session token، وضعیت احراز هویت، flag‌های in-flight و درخواست‌های pending را پاک می‌کند.
3. state این تونل برای line را از بین می‌برد.
4. line کنترلی تحت مالکیت خود را آزاد می‌کند.
5. batch حل‌نشده و بدهی باقی‌مانده catch-up را حفظ می‌کند و مگر هنگام توقف یا خطای continuity، retry را زمان‌بندی می‌کند.

وقتی کلاینت خودش line کنترلی را می‌بندد، برای مثال هنگام خاموش شدن worker شماره `0` یا پردازش یک پاسخ malformed، ابتدا state محلی line را از بین می‌برد، `tunnelNextUpStreamFinish()` را می‌فرستد و سپس line تحت مالکیت را از بین می‌برد. Finish خروجی به سمت فرستندهٔ خودش callback نمی‌فرستد.

تجزیهٔ payload پاسخ یک reference موقت به line نگه می‌دارد. اگر callback بازگشتی line را ببندد، parser متوقف می‌شود و بدون دست‌زدن به وضعیت ازبین‌رفتهٔ line برمی‌گردد.

### مالکیت جهت‌ها {#direction-ownership}

کلاینت همهٔ درخواست‌ها را به upstream می‌فرستد:

```c
tunnelNextUpStreamInit()
tunnelNextUpStreamPayload()
tunnelNextUpStreamFinish()
```

پاسخ سرور از callbackهای downstream دریافت می‌شود:

```c
AuthenticationClient::DownStreamEst
AuthenticationClient::DownStreamPayload
AuthenticationClient::DownStreamPause
AuthenticationClient::DownStreamResume
AuthenticationClient::DownStreamFinish
```

Pause و Resume به تونل قبلی منعکس نمی‌شوند، زیرا AuthenticationClient در ابتدای زنجیره است و تولیدکنندهٔ دادهٔ قبلی ندارد. آن‌ها فقط مشخص می‌کنند آیا درخواست پروتکل تازه می‌تواند بی‌درنگ ارسال شود.

<span id="نکتهها" />

### معنای packet line {#packet-line-semantics}

`AuthenticationClient` تونل بسته نیست. از packet line استفاده نمی‌کند و `lineDestroy()` را فقط برای line کنترل عادی‌ای فراخوانی می‌کند که خودش ساخته است.

<span id="عملکرد-پایگاه-داده-کاربران" />

### کارایی پایگاه کاربران {#user-database-performance}

- جست‌وجوی password متنی فقط یک بار SHA-256 را محاسبه می‌کند و بدون fallback scan از طریق index هش SHA-256 نتیجه را پیدا می‌کند؛ بنابراین هزینه متوسط hit و miss برابر O(1) است. سپس password متنی candidate به‌صورت دقیق مقایسه می‌شود تا حتی در صورت برخورد فرضی SHA-256، احراز هویت به‌شکل fail-closed انجام شود.
- baseline همگام‌سازی محلی با deep copy بومی `usersCopy()` تکثیر می‌شود، نه با رفت‌وبرگشت از طریق JSON. فقط پاسخ شبکه‌ای دریافت‌شده برای `GetUsersPage` همچنان به یک بار parse کردن JSON در جدول فعال نیاز دارد.

### فرادادهٔ گره {#node-metadata}

metadata برگرفته از کد منبع:

| ویژگی | مقدار |
| --- | --- |
| گره flags | `kNodeFlagChainHead` |
| `can_have_prev` | `false` |
| `can_have_next` | `true` |
| `layer_group` | `kNodeLayer4` |
| `layer_group_prev_node` | `kNodeLayerNone` |
| `layer_group_next_node` | `kNodeLayer4` |
| `required_padding_left` | `0` bytes |

پیام‌های کامل پاسخ پیش از بررسی سقف ورودی ناقص پردازش می‌شوند؛ بنابراین یک تحویل می‌تواند چند پیام داشته باشد.
ورودی ناقص کمتر از `16 MiB + 20 bytes` است و پس از فشرده‌سازی بافرها حداکثر `32 MiB` allocation charge
دارد. ورودی تو‌در‌تو، همراه با ادامهٔ خوانده‌نشدهٔ قبلی، سقف یک پیام کامل به‌اضافهٔ `2 MiB` را دارد؛ قبل از رد کردن
ورودی، بافرهای قطعه‌قطعه ادغام می‌شوند. تحویل خالی آزاد می‌شود. یک پیام استخراج‌شده و مقصد ادغام، scratch محدود
هستند؛ تحویل همگام فعلی، جدول کاربران و cache استخرها خارج از سقف ورودی نگهداری‌شده‌اند.
