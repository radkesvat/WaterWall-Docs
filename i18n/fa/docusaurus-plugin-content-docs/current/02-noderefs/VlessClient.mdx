# VlessClient

## نمای کلی {#overview}

`VlessClient` پیاده‌سازی سمت کلاینت پروتکل VLESS v0 بدون رمزنگاری در WaterWall است.
سرآیند درخواست را با UUID و مقصد تنظیم‌شده می‌نویسد و سپس دادهٔ جریان بایتی TCP یا
دیتاگرام‌های UDP را از گره بعدی که با جریان بایتی کار می‌کند عبور می‌دهد.

این گره فقط پروتکل پایهٔ VLESS را پیاده‌سازی می‌کند. TLS، REALITY، XTLS Vision،
افزونه‌های flow، mux، XUDP، WebSocket، gRPC یا هیچ پوشش انتقال دیگری ایجاد نمی‌کند.


<a id="جایگاه-رایج"></a>

## جایگاه معمول در زنجیره {#typical-placement}

کلاینت VLESS برای TCP:

```text
TcpListener -> VlessClient -> TlsClient -> TcpConnector
```

کلاینت VLESS برای UDP:

```text
UdpListener -> VlessClient -> TlsClient -> TcpConnector
```

مقصد پویا از پراکسی یا مسیریاب:

```text
Socks5Server -> VlessClient -> TlsClient -> TcpConnector
SniffRouter -> VlessClient -> TlsClient -> TcpConnector
```

`VlessClient` خودش TLS ایجاد نمی‌کند. در استقرار معمول VLESS، `TlsClient` را بعد از آن قرار دهید و `TcpConnector` نهایی
را به آدرس و پورت سرور VLESS وصل کنید. مقصد واقعی سرویس در سرآیند درخواست مربوط به VLESS نوشته می‌شود.

این گره پروتکل، رمزنگاری مسیر انتقال فراهم نمی‌کند. پیش از در دسترس قرار دادن سرویس، گره‌های TLS بالا و اطلاعات احراز هویت متناظر همتا را تنظیم کنید.

## نمونهٔ کاربردی ساده {#minimal-practical-example}

این یک **قطعه از آرایهٔ گره‌ها** است، نه یک فایل پیکربندی کامل. شنوندهٔ ورودی و گره‌های همسایهٔ نشان‌داده‌شده در بالا را اضافه کنید و اطلاعات احراز هویت و آدرس‌های نمونهٔ سرور را جایگزین کنید.

<a id="نمونه-tcp"></a>

### نمونهٔ TCP {#tcp-example}

```json
[
  {
    "name": "vless-client",
    "type": "VlessClient",
    "settings": {
      "uuid": "5783a3e7-e373-51cd-8642-c83782b807c5",
      "address": "example.com",
      "port": 443,
      "protocol": "tcp",
      "dns-behaviour": {"resolve": false},
      "verbose": false
    },
    "next": "tls-client"
  },
  {
    "name": "tls-client",
    "type": "TlsClient",
    "settings": {
      "sni": "vless.example.net",
      "verify": true
    },
    "next": "server-out"
  },
  {
    "name": "server-out",
    "type": "TcpConnector",
    "settings": {
      "address": "vless.example.net",
      "port": 443,
      "nodelay": true
    }
  }
]
```

## پیکربندی {#configuration}

<a id="فیلدهای-لازم"></a>

### فیلدهای لازم {#required-fields}

فیلدهای سطح اصلی:

| فیلد | نوع | توضیح |
| --- | --- | --- |
| `name` | رشته | نام گره به انتخاب کاربر. باید در فایل پیکربندی یکتا باشد. |
| `type` | رشته | باید دقیقاً `"VlessClient"` باشد. |
| `settings` | شیء | تنظیمات غیرخالی کلاینت VLESS. |
| `next` | رشته | گره دارای رابط جریان بایتی که بایت‌های مربوط به VLESS را حمل می‌کند؛ در استفاده معمول لازم است. |

فیلدهای لازم داخل `settings`:

| فیلد | نام‌های قابل قبول | توضیح |
| --- | --- | --- |
| UUID | `uuid`, `id`, `user-id` | شناسهٔ کاربر در VLESS؛ می‌تواند قالب RFC4122 دارای خط تیره یا رشتهٔ فشردهٔ ۳۲ نویسه‌ای در مبنای شانزده باشد و به‌شکل ۱۶ بایت خام ارسال می‌شود. |
| آدرس مقصد | `target-address`, `address`, `target` | میزبان یا IP مقصد نهایی در درخواست VLESS، یا `"dest_context->address"`. |
| پورت مقصد | `port` | پورت مقصد نهایی، یا `"dest_context->port"`؛ مقدار عددی باید در بازه `1..65535` باشد. |

UUID با ترتیب بایت متن RFC4122 سریال می‌شود؛ نه به‌شکل ASCII و نه با چیدمان حافظه مربوط به GUID پلتفرم.

<a id="تنظیمات-اختیاری"></a>

### تنظیمات اختیاری {#optional-settings}

| فیلد | پیش‌فرض | توضیح |
| --- | --- | --- |
| `protocol` | `"tcp"` | انتخاب فرمان VLESS. نام `proto` هم پذیرفته می‌شود. |
| `first-payload-timeout-ms` | `400` | مهلت به میلی‌ثانیه صحیح در بازه 0 تا 4,294,967,295؛ صفر انتظار عمدی را غیرفعال می‌کند. |
| `verbose` | `false` | جزئیات بیشتری از تونل را ثبت می‌کند. |
| `dns-behaviour` | resolve محلی غیرفعال | کنترل جست‌وجوی محلی، انتخاب آدرس و انتقال DNS؛ بخش رفتار DNS را ببینید. |

مقدارهای پشتیبانی‌شده برای `protocol`:

| مقدار | رفتار |
| --- | --- |
| `"tcp"` یا `"connect"` | فرمان TCP در VLESS با مقدار `0x01` ارسال می‌شود. |
| `"udp"` یا `"udp-associate"` | فرمان UDP در VLESS با مقدار `0x02` ارسال می‌شود و دیتاگرام‌های UDP روی line حامل TCP داخلی حمل می‌شوند. |
| `"dest_context->protocol"` یا `"line->dest_ctx->protocol"` | پروتکل از زمینهٔ مقصد ورودی گرفته می‌شود. اگر دقیقاً TCP باشد فرمان `0x01` و اگر دقیقاً UDP باشد فرمان `0x02` انتخاب می‌شود. |

اگر با انتخاب `dest_context->protocol`، پروتکل ورودی وجود نداشته باشد، مبهم باشد یا TCP/UDP نباشد، کلاینت یک هشدار ثبت می‌کند و TCP را انتخاب می‌کند.

<a id="رفتار-dns"></a>

### رفتار DNS {#dns-behaviour}

resolve کردن نام دامنه یعنی پیدا کردن آدرس IP آن. `VlessClient` می‌تواند نام دامنهٔ
مقصد نهایی را در درخواست VLESS بفرستد، یا آن را محلی resolve کند و IP انتخاب‌شده
را بفرستد. resolve محلی فقط برای نام دامنهٔ resolve‌نشده و در صورت فعال بودن انجام
می‌شود. IP عددی یا مقصدی که از قبل resolve شده باشد به جست‌وجو نیاز ندارد.

این تنظیم مربوط به مقصد نهایی است که از طریق پراکسی به آن می‌رسید. گره اتصال بعدی
آدرس سرور پراکسی را انتخاب می‌کند و تنظیمات DNS مستقل خودش را دارد. با حذف
`dns-behaviour`، resolve محلی غیرفعال است.

این جست‌وجو را با `settings.dns-behaviour` تنظیم کنید:

```json
{
  "dns-behaviour": {
    "resolve": true,
    "mode": "direct",
    "strategy": "prefer-ipv4",
    "servers": ["203.0.113.53:53"]
  }
}
```

این IP نمونهٔ مستندات است؛ آن را با سرور خود جایگزین کنید.

| فیلد | معنی |
| --- | --- |
| `resolve` | بولی اجباری: `true` اجازهٔ جست‌وجوی نام دامنهٔ resolve‌نشده را می‌دهد و `false`، جست‌وجوی محلی را غیرفعال می‌کند. |
| `mode` | `native` (پیش‌فرض هنگام فعال بودن)، `direct` یا `chain`. |
| `strategy` | یکی از `core-settings`، `accept-dns-returned-order`، `prefer-ipv4`، `prefer-ipv6`، `only-ipv4` یا `only-ipv6`؛ حذف آن اولویت پیش‌فرض آدرس مصرف‌کننده را به کار می‌برد. |
| `servers` | ۱ تا ۳۲ نقطهٔ اتصال عددی IP، `IP:port` یا `[IPv6]:port`؛ در `direct` و `chain` اجباری و در `native` ممنوع. |
| `dns-next` | نام غیرخالی ورودی DNS، فقط در حالت `chain`. |

`native` از تنظیمات DNS در core و resolver مشترک worker استفاده می‌کند. هنگام
فعال بودن resolve محلی، این حالت پیش‌فرض انتقال DNS است.

`direct` درخواست‌های DNS را از طریق یک گره اتصال خصوصی TCP/UDP در WaterWall به
سرورهایی که مشخص کرده‌اید می‌فرستد.

`chain` درخواست‌های DNS را از زنجیرهٔ انتخابی می‌فرستد. برای محافظت از آن‌ها، مسیری
رمزنگاری‌شده مانند VPN خود را انتخاب کنید؛ این حالت به‌تنهایی درخواست‌ها را
رمزنگاری نمی‌کند. مسیر DNS باید هم درخواست‌های UDP و هم fallback روی TCP را حمل
کند. خطای مسیریابی یا جست‌وجو باعث تغییر به DNS بومی یا حالت دیگر نمی‌شود.

در حالت `chain`، با حذف `dns-next` درخواست‌های DNS از همین کلاینت پراکسی و مسیر انتقال
بعد از آن عبور می‌کنند. برای مسیر دیگر، نام یک شاخهٔ DNS جدا را در `dns-next`
بگذارید که از قبل به گره دیگری تعلق نداشته باشد. برای استفاده از همین گره، فیلد
را ننویسید؛ نام خود گره را در آن قرار ندهید.

شکل غیرفعال دقیقاً `"dns-behaviour": {"resolve": false}` است و فیلدهای `mode`، `strategy`، `servers` و `dns-next` را رد می‌کند. شیء تهی، null، نوع غیرشیء، فیلد ناشناخته و strategy عددی رد می‌شوند. نام strategy باید یکی از رشته‌های استاندارد بالا با حروف کوچک باشد. `core-settings` فقط اولویت آدرس را انتخاب می‌کند و انتقال DNS را تغییر نمی‌دهد.

با `resolve: false`، درخواست پراکسی در صورت پشتیبانی پروتکل نام دامنه را نگه می‌دارد. گره اتصال بعدی مقصد مستقل پراکسی یا VPN و سیاست DNS خودش را دارد؛ برای راه‌اندازی اولیه از IP عددی یا مسیر مستقل استفاده کنید.

مثال‌های native، direct و زنجیره محافظت‌شده و محدودیت گزینه‌های core را در [DomainResolver](./DomainResolver.mdx) ببینید. این سیاست فقط جست‌وجوهای متعلق به همین گره را کنترل می‌کند؛ fake DNS در PTC، DNS سیستم در TunDevice و همهٔ منابع DNS برنامه را تغییر نمی‌دهد.

## کاربرد و رفع اشکال {#usage-and-troubleshooting}

<a id="نمونه-dynamic-destination"></a>

### نمونهٔ مقصد پویا {#dynamic-destination-example}

```json
{
  "name": "vless-client",
  "type": "VlessClient",
  "settings": {
    "id": "5783a3e7-e373-51cd-8642-c83782b807c5",
    "address": "dest_context->address",
    "port": "dest_context->port",
    "protocol": "dest_context->protocol"
  },
  "next": "tls-client"
}
```

`id` و `user-id` نام‌های جایگزین قابل قبول برای `uuid` هستند.

<a id="نمونه-udp"></a>

### نمونهٔ UDP {#udp-example}

```json
{
  "name": "vless-client-udp",
  "type": "VlessClient",
  "settings": {
    "uuid": "5783a3e7-e373-51cd-8642-c83782b807c5",
    "address": "dest_context->address",
    "port": "dest_context->port",
    "protocol": "udp"
  },
  "next": "tls-client"
}
```

در حالت UDP، گره قبلی همچنان با UDP کار می‌کند. `VlessClient` برای آن line یک line حامل TCP داخلی می‌سازد، درخواست
VLESS UDP را روی حامل می‌فرستد و هر دادهٔ UDP را پس از یک طول دو بایتی big-endian قرار می‌دهد.

<a id="اشتباههای-رایج"></a>

### اشتباه‌های رایج {#common-mistakes}

- انتظار نداشته باشید `VlessClient` خودش به سرور VLESS وصل شود؛ بعد از آن مسیر انتقال جریان بایتی بگذارید.
- در استقرار عمومی VLESS، `TlsClient` را حذف نکنید مگر اینکه عمداً VLESS بدون رمزنگاری را روی شبکه بخواهید.
- آدرس سرور VLESS را با آدرس مقصد نهایی اشتباه نگیرید. `TcpConnector` به سرور وصل می‌شود؛ سرآیند درخواست VLESS
  مقصد نهایی را حمل می‌کند.
- حالت UDP را با گره بعدی فاقد رابط جریان بایتی به کار نبرید.
- به قابلیت‌های پشتیبانی‌نشده مثل Vision، flow، mux یا XUDP تکیه نکنید.

## رفتار پیشرفته {#advanced-behavior}

<a id="قالب-request-و-response"></a>

### قالب درخواست و پاسخ {#request-and-response-format}

سرآیند درخواست:

```text
version:      00
uuid:         16 raw bytes
addons len:   00
command:      01 TCP or 02 UDP
destination:  port first, then address
```

قالب مقصد:

```text
port:          2 bytes big-endian
address type:  01 IPv4, 02 domain, 03 IPv6
address body:  IPv4 4 bytes, domain length + bytes, or IPv6 16 bytes
```

سرآیند پاسخ:

```text
00 00
```

برای سازگاری با پیاده‌سازی‌های دیگر، کلاینت بخش افزونهٔ غیرخالی پاسخ را می‌پذیرد و
یک هشدار ثبت می‌کند. از بایت‌های افزونه عبور می‌کند و سپس بایت‌های بدنه را تحویل
می‌دهد؛ هیچ عملی بر اساس افزونه‌های پاسخ انجام نمی‌دهد.

<a id="قابلیتهای-پشتیبانینشده"></a>

### قابلیت‌های پشتیبانی‌نشده {#unsupported-features}

این پیاده‌سازی موارد زیر را پشتیبانی نمی‌کند:

- ساخت TLS یا REALITY داخل گره VLESS
- XTLS Vision یا افزونه‌های flow
- VLESS mux
- reverse
- XUDP
- WebSocket، HTTP، gRPC یا پوشش‌های دیگر انتقال

برای این لایه‌ها از گره‌های جدا مثل `TlsClient`، `HttpClient`، `MuxClient` یا `TcpConnector` استفاده کنید.

## جزئیات پیاده‌سازی {#implementation-details}

<a id="اولین-داده-و-برقراری-transport"></a>

### اولین داده و برقراری مسیر انتقال {#first-payload-and-transport-establishment}

`Init` مقصد را آماده و گره بعدی را مقداردهی اولیه می‌کند.
اولین دادهٔ واجد شرایط برنامه می‌تواند پیش از `Est`، داخل callback آن یا پس از Pause برسد.
درخواست کامل و تمام اولین داده بلافاصله در یک بافر معمولی ارسال می‌شوند؛ در حالت UDP
سرآیند یک دیتاگرام نیز در همان بافر قرار می‌گیرد. اگر فضای ابتدای بافر برای همهٔ
سرآیندها کافی باشد، همان بافر ورودی عادی به کار می‌رود. در غیر این صورت بافر عادی
با اندازهٔ متناسب ساخته می‌شود و پیشوند مقیم حافظه و بدنهٔ pipe خصوصی به‌ترتیب
در آن کپی می‌شوند. ورودی خالی TCP درخواست را فعال نمی‌کند.
دیتاگرام خالی UDP با پیشوند طول `00 00` ارسال می‌شود و اگر نخستین داده برنامه باشد، درخواست اولیه را فعال می‌کند.

در TCP مستقیم، تمام رویدادهای مسیر انتقال `Est`، حتی تکراری‌ها، مستقل از داده پروتکل و Pause به برنامه می‌رسند.
در UDP، Est مربوط به حامل فقط یک بار به برنامه نگاشت می‌شود.
پس از بازگشت `Init` گره بعدی، اگر line هنوز زنده و درخواست هنوز ارسال‌نشده باشد،
مهلت آغاز می‌شود. در حالت UDP، این `Init` به حامل TCP مربوط است.
`settings.first-payload-timeout-ms` به‌طور پیش‌فرض **400** است و عدد صحیح از **0**
تا **4,294,967,295** را می‌پذیرد؛ نوع‌ها و مقدارهای دیگر نامعتبرند. صفر انتظار عمدی
را غیرفعال می‌کند. زمان Pause نیز محاسبه می‌شود. در TCP مستقیم، رسیدن موعد حتی پس از Pause
یک درخواست بدون داده ارسال می‌کند. تمام اعلان‌های Pause/Resume، حتی تکراری‌ها، شفاف عبور
می‌کنند و وضعیت Pause گیرنده نگهداری نمی‌شود. در حامل متعلق به کلاینت برای UDP، این گره
سر همان line است و کنترل تولید خروجی را حفظ می‌کند: اگر موعد درخواست بدون داده هنگام
Pause آن حامل برسد، ارسال تا Resume منتظر می‌ماند. رسیدن داده معتبر پیش از ارسال درخواست،
تایمر را لغو کرده و خروجی ترکیبی را ارسال می‌کند. Est یا Resume تکراری درخواست را دوباره ارسال
نمی‌کنند و مهلت را از نو آغاز نمی‌کنند. Finish نیز تایمر را لغو می‌کند.
قرار گرفتن داده در یک بافر معمولی به معنی ارسال آن با یک فراخوانی سیستمی، یک بسته TCP یا یک رکورد TLS نیست.

ارسال upstream در مسیر مستقیم TCP و برای هر دیتاگرام منتظر Est یا Resume نمی‌ماند و صف خروجی برنامه ندارد.
تجزیهٔ پاسخ VLESS نسخهٔ صفر را اعتبارسنجی می‌کند و دقیقاً سرآیند پاسخ و افزونه‌هایش،
در مجموع حداکثر 257 بایت، را مصرف می‌کند. افزونهٔ غیرخالی با ثبت هشدار نادیده
گرفته می‌شود. دادهٔ ارسالی منتظر این پاسخ نمی‌ماند.

پس از ارسال درخواست TCP، مصرف کامل سرآیند پاسخ و تخلیهٔ ورودی نگه‌داشته‌شده و ورودی تودرتو،
گره وضعیت محلی line را نابود می‌کند و برای آن line به‌طور دائمی bypass می‌شود. callback‌های بعدی
مستقیماً بین همسایه‌ها عبور می‌کنند. تکمیل فقط درخواست یا فقط پاسخ کافی نیست.

line برنامه در UDP همچنان قرض‌گرفته‌شده است و با UDP کار می‌کند. کلاینت یک line
حامل TCP وابسته و تحت مالکیت خود روی worker برنامه ایجاد می‌کند. Est و
Pause/Resume و Finish به همین ارتباط نگاشت می‌شوند.
درخواست مقصد ثابت را حمل می‌کند و هر فریم یک طول دوبایتی big-endian دارد.
بازخوان دیتاگرام‌ها تمام دیتاگرام‌های کامل ورودی پذیرفته‌شده را تحویل می‌دهد، حتی اگر تحویل قبلی باعث Pause شده باشد.
ورودی callback تو در تو پشت ورودی قدیمی در FIFO تجزیه‌گر قرار می‌گیرد؛ تنها قطعه
ناقص یا وضعیت لازم برای ترتیب باقی می‌ماند. Finish، ورودی خراب یا رد گیرنده،
تحویل را متوقف و ارتباط را می‌بندد. این گره فقط حامل متعلق به خودش را
نابود می‌کند؛ مالک line برنامه مسئول تخلیهٔ آن هنگام خاموشی است.

<a id="splice-و-محدودیت-نگهداری"></a>

### Splice و نگهداری {#splice-and-retention}

اولین درخواست و داده معمولی هستند؛ خود درخواست حداکثر 278 بایت است.
TCP بعدی هویت بافر معمولی یا splice را حفظ می‌کند. UDP از padding اعلام‌شده
280 بایتی استفاده می‌کند و دو بایت به ابتدای هر دیتاگرام می‌افزاید. تجزیهٔ سرآیند و جابه‌جایی دقیق بدنه،
مرز دیتاگرام و padding کامل مسیر بعدی را حفظ می‌کند. کمبود padding یا ظرفیت pipe
با fallback کامل معمولی مدیریت می‌شود.

| ورودی نگهداری‌شده تجزیه‌گر | سقف منطقی شامل برابری |
| --- | --- |
| بدنه TCP فقط برای ترتیب ورودی تو در تو | 2,097,152 بایت، برابر 2 MiB |
| تکمیل پاسخ TCP با سرِ فعال صف و فرادادهٔ ذخیره‌شده در cache | 2,097,409 بایت، برابر 2 MiB به‌علاوه 257 بایت |
| تکمیل ورودی UDP با سرِ فعال صف و سرآیندهای ذخیره‌شده در cache | 2,162,689 بایت، برابر 2 MiB به‌علاوه 65,537 بایت |
| بدنه UDP | از 0 تا 65,535 بایت |

برابری مجاز است؛ سرریز یا رد صف تجزیه‌گر همان ارتباط را می‌بندد. صف خروجی
بازخوانی‌شده و محدودیت 1,024 رکورد برای دستهٔ همگام وجود ندارد. تعداد قطعه‌های
ورودی سهمیه خروجی را مصرف نمی‌کند. این حدود از اندازه مخزن بافر، نمایهٔ RAM و ظرفیت
pipe مستقل‌اند. دیتاگرام محلی بیش‌ازحد بزرگ حذف می‌شود و فریم دریافتی خراب ارتباط
را می‌بندد. طول دریافتی `0` پیشوند دو بایتی خود را مصرف می‌کند و دقیقاً یک دیتاگرام خالی UDP
تحویل می‌دهد. ارتباط باز می‌ماند و تجزیه‌گر سپس قاب بعدی را به‌ترتیب پردازش می‌کند.
این رفتار با [پیاده‌سازی پایهٔ VLESS در Xray](https://github.com/XTLS/Xray-core/blob/0888beb38a9ba45440557175e71ce21cf8ba3b13/proxy/vless/encoding/addons.go) تفاوت دارد: نویسنده‌ها دیتاگرام خالی را حذف می‌کنند و خواننده از قاب با طول صفر عبور می‌کند.
تحویل دیتاگرام خالی به پشتیبانی همتا نیاز دارد؛ قاب‌بندی داده غیرخالی تغییری نمی‌کند.
دیتاگرام خالی در [لایه UDP معتبر است (RFC 8085 §5)](https://datatracker.ietf.org/doc/html/rfc8085#section-5).

اگر مجموع هزینهٔ ظرفیت سرِ فعال صف و ورودی صف‌شدهٔ UDP از 8 MiB بیشتر شود، داده‌های خوانده‌نشده در بافرهای کمتری تجمیع می‌شوند.
فریم‌های کامل پذیرفته‌شده ابتدا تحویل داده می‌شوند؛ ورودی ناقص و ورودی callback
تو در تو پیش از بازگشت بررسی و در صورت نیاز تجمیع می‌شوند. ترتیب بایت‌ها و سرآیندهای
ذخیره‌شده در cache حفظ می‌شود. این آستانه‌ها تعداد قطعه‌های مجاز یک دیتاگرام معتبر را محدود
نمی‌کنند. اگر داده حتی پس از تجمیع در سقف هزینهٔ ظرفیت جا نگیرد، ارتباط بسته
و ورودی نگهداری‌شدهٔ آن آزاد می‌شود.

splice نیازمند `misc.splice`، ساخت مناسب و پشتیبانی تمام گره‌های زنجیرهٔ نهایی، از جمله کمک‌کننده‌های داخلی، است.
`DomainResolver` پشتیبانی می‌کند؛ `TlsClient` همچنان splice را برای کل زنجیره
غیرفعال می‌کند. در استقرار معمول TLS را نگه دارید؛ این قابلیت تضمین انتقال بدون کپی
یا افزایش سرعت اندازه‌گیری‌شده نیست.

<a id="رفتار-finish"></a>

### رفتار Finish {#finish-behavior}

`VlessClient` پیش از فرستادن `Finish` واقعی، وضعیت line خود را از بین می‌برد. برای line‌های معمولی بیرونی نیز
`lineDestroy()` را فراخوانی نمی‌کند.

در حالت UDP، مالک line حامل داخلی‌ای است که خودش ساخته است. بسته شدن line برنامه یا line حامل باعث بسته شدن سمت مقابل
و از بین رفتن امن line حامل می‌شود.

### فضای پیشوند (padding) {#padding}

`VlessClient` برای بزرگ‌ترین درخواست با اندازه ۲۷۸ بایت و پیشوند دو بایتی طول اولین دیتاگرام UDP
مقدار زیر را اعلام می‌کند:

```text
required_padding_left = 280
```
