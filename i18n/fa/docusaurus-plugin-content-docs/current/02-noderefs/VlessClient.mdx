# VlessClient

`VlessClient` تونل سمت client برای VLESS v0 plain در WaterWall است. این نود یک VLESS request header با UUID و مقصد نهایی
می‌نویسد، سپس داده TCP stream یا UDP datagramها را از طریق نود stream-facing بعدی حمل می‌کند.

این نود فقط base VLESS را پیاده‌سازی می‌کند. TLS، REALITY، XTLS Vision، flow addon، mux، XUDP، WebSocket، gRPC یا
transport wrapperهای دیگر را خودش ایجاد نمی‌کند.

## جایگاه رایج

VLESS client برای TCP:

```text
TcpListener -> VlessClient -> TlsClient -> TcpConnector
```

VLESS client برای UDP:

```text
UdpListener -> VlessClient -> TlsClient -> TcpConnector
```

destination داینامیک از proxy/router:

```text
Socks5Server -> VlessClient -> TlsClient -> TcpConnector
SniffRouter -> VlessClient -> TlsClient -> TcpConnector
```

`VlessClient` خودش TLS نمی‌سازد. برای deployment عادی VLESS، بعد از آن `TlsClient` بگذارید و `TcpConnector` نهایی را به
address و port سرور VLESS وصل کنید. مقصد واقعی service داخل VLESS request header encode می‌شود.

## نمونه TCP

```json
[
  {
    "name": "vless-client",
    "type": "VlessClient",
    "settings": {
      "uuid": "5783a3e7-e373-51cd-8642-c83782b807c5",
      "address": "example.com",
      "port": 443,
      "protocol": "tcp",
      "domain-strategy": "do-not-resolve-domains",
      "verbose": false
    },
    "next": "tls-client"
  },
  {
    "name": "tls-client",
    "type": "TlsClient",
    "settings": {
      "sni": "vless.example.net",
      "verify": true
    },
    "next": "server-out"
  },
  {
    "name": "server-out",
    "type": "TcpConnector",
    "settings": {
      "address": "vless.example.net",
      "port": 443,
      "nodelay": true
    }
  }
]
```

## نمونه Dynamic Destination

```json
{
  "name": "vless-client",
  "type": "VlessClient",
  "settings": {
    "id": "5783a3e7-e373-51cd-8642-c83782b807c5",
    "address": "dest_context->address",
    "port": "dest_context->port",
    "protocol": "dest_context->protocol"
  },
  "next": "tls-client"
}
```

`id` و `user-id` aliasهای قابل قبول برای `uuid` هستند.

## نمونه UDP

```json
{
  "name": "vless-client-udp",
  "type": "VlessClient",
  "settings": {
    "uuid": "5783a3e7-e373-51cd-8642-c83782b807c5",
    "address": "dest_context->address",
    "port": "dest_context->port",
    "protocol": "udp"
  },
  "next": "tls-client"
}
```

در UDP mode، سمت previous همچنان UDP-facing می‌ماند. `VlessClient` برای آن line یک TCP carrier line داخلی می‌سازد، روی
carrier یک VLESS UDP request می‌فرستد، و هر UDP payload را به شکل length دو بایتی big-endian به‌علاوه payload wrap می‌کند.

## فیلدهای لازم

| فیلد | نوع | توضیح |
| --- | --- | --- |
| `name` | string | نام یکتای نود داخل config. |
| `type` | string | باید دقیقا `"VlessClient"` باشد. |
| `settings` | object | تنظیمات غیرخالی VLESS client. |
| `next` | string | نود stream-facing که bytes مربوط به VLESS را حمل می‌کند. در استفاده عادی لازم است. |

فیلدهای لازم داخل `settings`:

| فیلد | نام‌های قابل قبول | توضیح |
| --- | --- | --- |
| UUID | `uuid`, `id`, `user-id` | user ID مربوط به VLESS. مقدار می‌تواند RFC4122 dashed یا compact hex با 32 کاراکتر باشد. به صورت 16 raw byte ارسال می‌شود. |
| target address | `target-address`, `address`, `target` | host یا IP مقصد نهایی داخل VLESS request، یا `"dest_context->address"`. |
| target port | `port` | port مقصد نهایی، یا `"dest_context->port"`. port عددی باید در بازه `1..65535` باشد. |

UUID با byte order متن RFC4122 serialize می‌شود؛ ASCII نیست و memory layout مربوط به GUID پلتفرم هم نیست.

## تنظیمات اختیاری

| فیلد | پیش‌فرض | توضیح |
| --- | --- | --- |
| `protocol` | `"tcp"` | انتخاب VLESS command. نام `proto` هم پذیرفته می‌شود. |
| `verbose` | `false` | log اضافی tunnel را فعال می‌کند. |
| `domain-strategy` | `"do-not-resolve-domains"` | کنترل می‌کند domain target قبل از نوشتن request محلی resolve شود یا نه. |

مقدارهای پشتیبانی‌شده برای `protocol`:

| مقدار | رفتار |
| --- | --- |
| `"tcp"` یا `"connect"` | VLESS TCP command `0x01` ارسال می‌شود. |
| `"udp"` یا `"udp-associate"` | VLESS UDP command `0x02` ارسال می‌شود و UDP datagramها روی TCP carrier داخلی حمل می‌شوند. |
| `"dest_context->protocol"` یا `"line->dest_ctx->protocol"` | protocol از destination context ورودی گرفته می‌شود. TCP دقیق command `0x01` و UDP دقیق command `0x02` را انتخاب می‌کند. |

اگر `dest_context->protocol` انتخاب شود ولی protocol ورودی missing، ambiguous یا غیر TCP/UDP باشد، client warning log
می‌کند و به TCP fallback می‌کند.

## Domain Strategy

`domain-strategy` تعیین می‌کند target address نهایی داخل VLESS request چطور encode شود.

| مقدار | رفتار |
| --- | --- |
| `"do-not-resolve-domains"` | domain target به همان شکل داخل request می‌ماند و سمت VLESS server آن را resolve می‌کند. |
| `"resolve-domains-and-accept-dns-returned-order"` | resolve محلی و استفاده از اولین نتیجه usable. |
| `"resolve-domains-and-prefer-ipv4"` | resolve محلی، ترجیح IPv4، و fallback به IPv6. |
| `"resolve-domains-and-prefer-ipv6"` | resolve محلی، ترجیح IPv6، و fallback به IPv4. |
| `"resolve-domains-and-use-only-ipv4"` | فقط IPv4 قبول می‌شود. اگر DNS پاسخ IPv4 ندهد line بسته می‌شود. |
| `"resolve-domains-and-use-only-ipv6"` | فقط IPv6 قبول می‌شود. اگر DNS پاسخ IPv6 ندهد line بسته می‌شود. |
| `"resolve-domains-with-core-settings"` | resolve با تنظیمات `dns` داخل `core.json`. |

وقتی resolve محلی فعال باشد، `VlessClient` یک `DomainResolver` داخلی می‌سازد که prepare hook آن قبل از DNS resolution
target تنظیم‌شده را اعمال می‌کند. resolve وقتی انجام می‌شود که آدرس نهایی VLESS یک domain باشد؛ هم برای target ثابت
JSON و هم برای `"dest_context->address"`. IPهای literal بدون تغییر می‌مانند.

## قالب Request و Response

request header:

```text
version:      00
uuid:         16 raw bytes
addons len:   00
command:      01 TCP or 02 UDP
destination:  port first, then address
```

destination format:

```text
port:          2 bytes big-endian
address type:  01 IPv4, 02 domain, 03 IPv6
address body:  IPv4 4 bytes, domain length + bytes, or IPv6 16 bytes
```

response header:

```text
00 00
```

client برای interoperability response addons غیرخالی را می‌پذیرد، warning log می‌کند، آن addon bytes را skip می‌کند و
بعد body را تحویل می‌دهد. روی addon هیچ عملی انجام نمی‌دهد.

## رفتار Runtime در TCP

در upstream `Init`، آماده‌سازی target قبل از شروع protocol core انجام می‌شود؛ یا از طریق prepare hook داخلی resolver
یا مستقیما در init خود client وقتی local DNS resolution غیرفعال است. سپس `VlessClient` state line را initialize
می‌کند و `Init` را به نود بعدی forward می‌کند.

وقتی transport downstream برقرار شود، `VlessClient`:

1. downstream `Est` را به نود قبلی forward می‌کند
2. VLESS request header را upstream می‌فرستد
3. upstream application payloadهای queue شده را بلافاصله بعد از header flush می‌کند

برای ارسال application bytes منتظر VLESS response header نمی‌ماند. ولی downstream body تا وقتی response header parse و
validate نشود نگه داشته می‌شود.

## رفتار Runtime در UDP

در UDP mode، application line و carrier line جدا هستند:

| Line | هدف |
| --- | --- |
| UDP app line | line قابل مشاهده برای نود UDP-facing قبلی. |
| TCP carrier line | line داخلی ساخته‌شده توسط `VlessClient` و ارسال‌شده به نود stream-facing بعدی. |

carrier line یک VLESS UDP request برای یک destination ثابت می‌فرستد. بعد از آن:

- هر UDP payload upstream به شکل `uint16_be length + payload` encode می‌شود
- هر VLESS UDP frame downstream length-decode می‌شود و به app line به شکل raw UDP payload برمی‌گردد
- UDP payload با length `0` یا بزرگ‌تر از `65535` به صورت local drop می‌شود

client تا 1 MiB داده upstream pending را هنگام انتظار برای carrier/request queue می‌کند. response bytes downstream هم
هنگام انتظار برای response header معتبر یا frameهای UDP کامل، تا 1 MiB محدود هستند.

## رفتار Finish

`VlessClient` قبل از propagation واقعی `Finish`، line state خودش را destroy می‌کند. روی lineهای خارجی عادی
`lineDestroy()` صدا نمی‌زند.

در UDP mode، carrier line داخلی‌ای که خودش ساخته را مالک است. وقتی app line یا carrier line بسته شود، سمت paired را هم
می‌بندد و carrier line owned را safely destroy می‌کند.

## Padding

`VlessClient` ممکن است VLESS UDP length prefix دو بایتی را prepend کند، پس مقدار زیر را advertise می‌کند:

```text
required_padding_left = 2
```

## متادیتای نود

| ویژگی | مقدار |
| --- | --- |
| Node flag | `kNodeFlagNone` |
| previous node | مجاز، و در استفاده عادی لازم |
| next node | مجاز، و در استفاده عادی لازم |
| layer group | `kNodeLayerAnything` |
| `required_padding_left` | `2` |
| line state | target context، phase، read stream، pending queue، لینک‌های UDP app/carrier |

## قابلیت‌های پشتیبانی‌نشده

این implementation موارد زیر را پشتیبانی نمی‌کند:

- ساخت TLS یا REALITY داخل node VLESS
- XTLS Vision یا flow addons
- VLESS mux
- reverse
- XUDP
- WebSocket، HTTP، gRPC یا transport wrapperهای دیگر

برای این لایه‌ها از نودهای جدا مثل `TlsClient`، `HttpClient`، `MuxClient` یا `TcpConnector` استفاده کنید.

## اشتباه‌های رایج

- انتظار نداشته باشید `VlessClient` خودش به VLESS server وصل شود؛ بعد از آن stream transport بگذارید.
- برای deployment عمومی VLESS، `TlsClient` را حذف نکنید مگر اینکه عمدا plain VLESS روی wire می‌خواهید.
- address سرور VLESS را با target address نهایی اشتباه نگیرید. `TcpConnector` به server وصل می‌شود؛ VLESS request header
  مقصد نهایی را حمل می‌کند.
- UDP mode را با next node غیر stream-facing استفاده نکنید.
- به featureهای پشتیبانی‌نشده مثل Vision، flow، mux یا XUDP تکیه نکنید.
