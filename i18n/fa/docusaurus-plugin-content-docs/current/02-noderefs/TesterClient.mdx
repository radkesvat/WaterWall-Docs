# TesterClient

## نمای کلی {#overview}

`TesterClient` یک گرهٔ مصنوعی برای اعتبارسنجی در ابتدای زنجیره است. ترافیک قطعی و قابل تکرار تولید می‌کند، آن را به گره بعدی می‌فرستد و ترتیب پاسخ‌های برگشتی را با الگوی مورد انتظار می‌سنجد. اگر پاسخ‌ها تطابق نداشته باشند یا مهلت زمانی به پایان برسد، اجرای فرایند متوقف می‌شود.

از این گره برای آزمایش ترکیب تونل‌ها، قاب‌بندی، مدیریت بسته، ترتیب داده‌ها و سالم ماندن بار مفید استفاده کنید. `TesterClient` برای ترافیک واقعی و محیط عملیاتی ساخته نشده است.

## جایگاه معمول در زنجیره {#typical-placement}

### بررسی رلهٔ رمز‌شده پیش از اتصال برنامه {#verify-an-encrypted-relay-before-attaching-an-application}

<a id="بررسی-relay-رمزشده-پیش-از-اتصال-برنامه"></a>

```text
client: TesterClient -> EncryptionClient -> TcpConnector
server: TcpListener -> EncryptionServer -> TesterServer
```
اتصال‌دهنده را به شنونده سمت سرور متصل کنید و الگوریتم و گذرواژه جفت رمزنگاری
را یکسان قرار دهید. هر دو گرهٔ آزمایش باید در حالت جریان و با `chunk-count` یکسان باشند.
این مسیر بدون سرور برنامه، درستی بایت‌ها را در هر دو جهت انتقال و کدک‌ها
بررسی می‌کند.

برای بررسی کدک بدون سوکت، جفت را داخل یک فرایند بگذارید:

```text
TesterClient -> EncryptionClient -> EncryptionServer -> TesterServer
```
برای بررسی بازیابی KCP هنگام شبیه‌سازی از دست رفتن بسته‌ها،
[سناریوی Disturber](./Disturber.mdx#typical-placement) را ببینید. این‌ها شکل زنجیره
آزمایش هستند؛ قطعه‌های پایین فقط همان گرهٔ آزمایش را تنظیم می‌کنند. هر پیکربندی فقط یک
`TesterClient` می‌تواند داشته باشد.

## نمونهٔ کاربردی ساده {#minimal-practical-example}

این‌ها قطعه‌های پیکربندی گره هستند؛ گره‌های همسایهٔ ارجاع‌شده را در پیکربندی پیرامونی تعریف کنید.

### نمونه‌های پایه {#basic-examples}

<a id="نمونه-تنظیم"></a>

حالت جریان:

```json
{
  "name": "tester-client",
  "type": "TesterClient",
  "next": "next-node"
}
```

## پیکربندی {#configuration}

### فیلدهای لازم {#required-fields}

<a id="فیلدهای-ضروری"></a>

| فیلد | نوع | توضیح |
|---|---|---|
| `name` | string | نام دلخواه گره. |
| `type` | string | باید `TesterClient` باشد. |
| `next` | string | گره‌ای که `line` جریان مصنوعی یا `line` بسته را دریافت می‌کند. |

`settings` اختیاری است؛ اگر آن را ننویسید، گره با تنظیمات پیش‌فرض حالت جریان کار می‌کند.

### تنظیمات {#settings}

<a id="تنظیمات"></a>

| فیلد | پیش‌فرض | توضیح |
|---|---|---|
| `packet-mode` | `false` | به‌جای `line`های معمولی جریان از `line` بستهٔ هر worker استفاده می‌کند. |
| `packet-start-immediately` | `false` | فقط در حالت بسته؛ ارسال را بدون انتظار برای `downstream` `Est` آغاز می‌کند. |
| `packet-start-delay-ms` | `0` | فقط در حالت بسته؛ تأخیر مسیر شروع فوری. نباید منفی باشد. |
| `allow-early-response` | `false` | فقط در حالت جریان؛ اجازه می‌دهد پیش از ارسال کامل دنبالهٔ درخواست، بایت‌های پاسخ در جهت `downstream` دریافت شوند. |
| `packet-stateless` | `false` | فقط در حالت بسته؛ اجازه می‌دهد بسته‌های پاسخ خارج از ترتیب برسند و قطعه‌ها بر اساس اندازهٔ بسته شناسایی شوند. |
| `chunk-count` | `11` | تعداد قطعه‌های فعال از ابتدای جدول. بازه معتبر `1` تا `11`. |
| `max-payload-size` | `0` | حداکثر اندازه بافرهای جریان یا بسته‌ها. مقدار `0` یعنی استفاده از اندازه معمول جدول یا بافر. |
| `split-payload-delay-ms` | `1` | فقط در حالت جریان؛ فاصله ارسال بارهای مفید تکه‌شده، زمانی که `max-payload-size` فعال است. |
| `split-payload-burst` | `1` | فقط در حالت جریان؛ تعداد بافرهای که پیش از اعمال `split-payload-delay-ms` فرستاده می‌شوند. باید مثبت باشد. |
| `dest-context` | ندارد | زمینهٔ مسیریابی مقصد اولیه که پیش از `upstream` `Init` روی هر `line` آزمایشی کپی می‌شود. |
| `packet-ipv4` | ندارد | فقط در حالت بسته؛ هر بسته آزمایشی را در یک بسته مصنوعی IPv4 قرار می‌دهد. |

`packet-stateless` نیازمند `packet-mode=true` است. `max-payload-size` با `packet-stateless=true` پشتیبانی نمی‌شود.

### جدول‌های قطعه‌ها {#chunk-tables}

<a id="جدول-chunkها"></a>

این گره قطعه‌های درخواست با محتوای قطعی می‌فرستد و انتظار دریافت قطعه‌های پاسخ با محتوای قطعی را دارد. `chunk-count` مشخص می‌کند چند عضو نخست جدول فعال باشند.

حالت جریان:

```text
1, 2, 4, 32, 512, 1024, 4096, 32768, 32769, 1048576, 2097152
```

حالت بسته:

```text
1, 2, 4, 32, 64, 128, 256, 512, 1024, 1499, 1500
```

حالت بسته با IPv4 خام:

```text
21, 22, 24, 52, 84, 148, 276, 532, 1044, 1499, 1500
```

حالت بسته با IPv4 و سرآیند انتقال مثل `tcp`، `udp` یا `icmp`:

```text
41, 42, 44, 52, 84, 148, 276, 532, 1044, 1499, 1500
```

الگوی بایت‌ها قطعی است و به شاخص هر قطعه، موقعیت بایت، شناسهٔ جریان و جهت بستگی دارد. نخستین بایت درخواست حاوی شناسهٔ جریان است تا حتی اگر یک گام انتقال واقعی ادامهٔ کار را به worker دیگری سپرد، بررسی پاسخ به‌هم نخورد.

### زمینهٔ مقصد {#destination-context}

`dest-context` پیش از `upstream` `Init` مقدار اولیه `lineGetDestinationAddressContext(line)` را روی `line` آزمایشی قرار می‌دهد. این قابلیت برای تست مسیریاب‌ها، اتصال‌دهنده‌ها و آداپتور‌های بسته/UDP که فراداده مقصد را از `line` می‌خوانند کاربرد دارد.

```json
{
  "dest-context": {
    "address": "example.com",
    "port": 443,
    "protocol": "tcp"
  }
}
```

فیلدهای پشتیبانی‌شده:

| فیلد | توضیح |
|---|---|
| `address` | آدرس IP یا دامنه؛ نام دامنه باید در محدودیت طول زمینهٔ آدرس جا شود. |
| `port` | پورت مقصد، `1` تا `65535`. |
| `protocol` | `tcp` یا `udp`. |

### حالت بستهٔ IPv4 {#packet-ipv4-mode}

<a id="حالت-packet-ipv4"></a>

`packet-ipv4` فقط با `packet-mode=true` معتبر است و بار مفید هر بسته را، بدون تفسیر ساختار داخلی آن، به یک بستهٔ کامل و مصنوعی IPv4 تبدیل می‌کند.

فیلدهای ضروری:

| فیلد | توضیح |
|---|---|
| `source-ip` | آدرس IPv4 مبدأ برای بسته‌های درخواست. |
| `dest-ip` | آدرس IPv4 مقصد برای بسته‌های درخواست. |

فیلدهای اختیاری:

| فیلد | پیش‌فرض | توضیح |
|---|---|---|
| `transport` | `none` | سرآیند اختیاری انتقال؛ یکی از `tcp`، `udp`، `icmp`، `raw` یا `none`. |
| `protocol` | `253` | شماره پروتکل در IPv4. برای `tcp`، `udp` یا `icmp` باید با انتقال انتخاب‌شده هماهنگ باشد. |
| `ttl` | `64` | مقدار TTL در IPv4. |
| `worker-affine-flow` | `false` | برای هر worker یک پورت مبدأ درخواست انتخاب می‌کند که جریان درونی آن به همان worker نگاشت شود. بسته‌های دریافتی نیز پیش از بررسی به همان worker فرستاده می‌شوند تا وقتی حامل داده را روی worker دیگری تحویل می‌دهد، وضعیت بررسی هماهنگ بماند. فقط با انتقال از نوع `tcp` یا `udp` معتبر است. |

در بسته‌های پاسخ آدرس مبدأ و مقصد به‌طور خودکار جابه‌جا می‌شوند. برای `tcp`، `udp` و `icmp`، سرآیندهای انتقال با الگوی قطعی ساخته و بررسی می‌شوند. درخواست‌های TCP و UDP از پورت مبدأ برابر `40123` و پورت مقصد برابر `40234` استفاده می‌کنند؛ این دو در پاسخ جابه‌جا می‌شوند. با فعال بودن `worker-affine-flow`، پورت مبدأ درخواست به‌جای آن نخستین پورت برابر یا بزرگ‌تر از `40123` است که جریان درونی آن worker فعلی را انتخاب کند؛ بنابراین هر دو گره باید `source-ip`، `dest-ip`، `transport` و خود این تنظیم را یکسان تنظیم کنند.

وقتی `packet-ipv4` فعال است، مقدار `max-payload-size` باید فضای کافی برای سرآیندهای IPv4 و انتقال انتخاب‌شده باقی بگذارد.

## کاربرد و رفع اشکال {#usage-and-troubleshooting}

### نمونه‌های دیگر {#alternative-examples}

حالت بسته:

```json
{
  "name": "tester-client",
  "type": "TesterClient",
  "settings": {
    "packet-mode": true
  },
  "next": "packet-node"
}
```

حالت بسته همراه با IPv4 مصنوعی:

```json
{
  "name": "tester-client",
  "type": "TesterClient",
  "settings": {
    "packet-mode": true,
    "packet-ipv4": {
      "source-ip": "198.51.100.10",
      "dest-ip": "203.0.113.20",
      "transport": "udp",
      "ttl": 64
    }
  },
  "next": "packet-node"
}
```

### بررسی پاسخ {#verification}

<a id="بررسی-پاسخ"></a>

در حالت جریان:

- بایت‌های پاسخ تا کامل‌شدن هر قطعهٔ پاسخ مورد انتظار در بافر نگه داشته می‌شوند
- قطعه‌ها به‌ترتیب بررسی می‌شوند
- بایت‌های اضافی پس از دنبالهٔ مورد انتظار آزمون را ناموفق می‌کنند
- دریافت `Finish` در جهت `downstream` پیش از بررسی کامل، آزمون را ناموفق می‌کند

در حالت بسته:

- هر بستهٔ پاسخ باید دقیقاً با یکی از قطعه‌های پاسخ مورد انتظار مطابقت داشته باشد
- `line`های بسته باید در زمان اجرا زنده بمانند
- دریافت `Finish` روی `line` بسته شکست آزمون محسوب می‌شود
- با `packet-stateless=true` قطعه‌های پاسخ می‌توانند خارج از ترتیب برسند، اما هر قطعهٔ مورد انتظار باید دقیقاً یک بار دریافت شود

وقتی همهٔ workerها بررسی را کامل کنند، `TesterClient` موفقیت را گزارش می‌کند و برنامه را با کد خروج `0` پایان می‌دهد. عدم تطابق، پایان مهلت زمانی، رویداد نامعتبر چرخهٔ عمر یا مرگ `line` بسته، برنامه را با وضعیت شکست خاتمه می‌دهد.

### خطاهای رایج {#common-mistakes}

<a id="خطاهای-رایج"></a>

- استفاده در محیط عملیاتی؛ این گره عمداً برای اعتبارسنجی ساخته شده و ممکن است فرایند را متوقف کند.
- فراموش کردن `next`؛ `TesterClient` در ابتدای زنجیره قرار دارد و باید داده را به گره دیگری بفرستد.
- فعال کردن حالت بسته بدون گره لایهٔ بسته در زنجیره.
- انتظار بسته شدن `line` بسته در حالت بسته؛ `line`های بسته ابزارهای ماندگار هر worker هستند.
- ترکیب `packet-stateless=true` با `max-payload-size`.
- استفاده از `packet-ipv4` بدون `packet-mode=true`.

## جزئیات پیاده‌سازی {#implementation-details}

### جریان اجرا {#runtime-flow}

<a id="جریان-اجرا"></a>

هنگام راه‌اندازی، `TesterClient` با تأخیر `100 ms` برای هر worker زنجیره یک وظیفه زمان‌بندی می‌کند. هر وظیفه:

1. در حالت بسته از `line` بسته همان worker استفاده می‌کند و در غیر این صورت یک `line` معمولی جریان می‌سازد
2. وضعیت `line` این تونل را مقداردهی اولیه می‌کند
3. در صورت وجود، `dest-context` را روی `line` کپی می‌کند
4. `upstream` `Init` را به گره بعدی می‌فرستد
5. یک پایشگر مهلت زمانی به مدت `30000 ms` فعال می‌کند

در حالت جریان، ارسال درخواست‌ها پس از دریافت `downstream` `Est` آغاز می‌شود. در حالت بسته می‌توانید با `packet-start-immediately=true` این انتظار را حذف کنید.

در شروع فوری حالت بسته، تأخیر `packet-start-delay-ms` حتی اگر گره بعدی هنگام `Init` رویداد `Est` یا `Resume` بفرستد اعمال می‌شود؛ این رویدادها نه تأخیر را حذف می‌کنند و نه ارسال درخواست را دوباره زمان‌بندی می‌کنند.

`downstream` `Pause` و `Resume` نیز ارسال درخواست‌ها را متوقف یا دوباره برقرار می‌کنند.

### فرادادهٔ گره {#node-metadata}

<a id="متادیتای-نود"></a>

`TesterClient` حداکثر از `254` worker پشتیبانی می‌کند و برای هر worker یک پایشگر مهلت زمانی با مدت `30000 ms` دارد.

فرادادهٔ برگرفته از کد منبع:

| ویژگی | مقدار |
| --- | --- |
| پرچم‌های گره | `kNodeFlagChainHead` &#124; `kNodeFlagSingleton` |
| `can_have_prev` | `false` |
| `can_have_next` | `true` |
| `layer_group` | `kNodeLayerAnything` |
| `layer_group_prev_node` | `kNodeLayerNone` |
| `layer_group_next_node` | `kNodeLayerAnything` |
| `required_padding_left` | `0` بایت |
