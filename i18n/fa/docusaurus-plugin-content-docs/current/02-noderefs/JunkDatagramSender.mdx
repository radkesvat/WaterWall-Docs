# JunkDatagramSender



## نمای کلی {#overview}

`JunkDatagramSender` تونلی میانی و قابل ترکیب است که پیش از payloadهای ابتدایی upstream روی هر line، چند payload ساختگی شبیه datagramهای UDP تزریق می‌کند.

این گره برای آزمایش استتار و نویز پروتکل در مسیرهای شبیه UDP طراحی شده است و payload واقعی را تغییر نمی‌دهد. با رسیدن payloadِ upstream، ممکن است ابتدا مجموعه‌ای تصادفی از payload‌های junk را به `next` بفرستد و سپس داده واقعی را بدون تغییر عبور دهد.

`JunkDatagramSender` یک تونل عادی با state مخصوص هر line است. Adapter مبتنی بر socket یا تونل بسته‌ای خام IPv4 نیست و object‌ای از نوع `line_t` نمی‌سازد و آزاد نمی‌کند.

اگر تولید دیتاگرام فعال باشد، خط عادی پیش از ادامهٔ `Init` پروتکل UDP را
از گزینه‌های مقصد انتخاب می‌کند. خطی که UDP عرضه نکند بسته می‌شود.
اگر تعداد دفعات ارسال (`resend-again-times`) صفر باشد، هیچ پروتکلی انتخاب نشده باشد یا حداکثر تعداد بسته‌ها پس از اعمال تنظیمات صفر باشد، گره گزینه‌های مقصد را حفظ می‌کند.

## جایگاه معمول در زنجیره {#typical-placement}



<a id="مشاهده-datagramهای-تولیدشده-در-آزمایش-udp-کنترلشده"></a>

### مشاهدهٔ دیتاگرام‌های تولیدشده در آزمایش کنترل‌شدهٔ UDP {#observe-generated-datagrams-in-a-controlled-udp-test}

```text
sender:   UdpListener -> JunkDatagramSender -> UdpConnector
receiver: UdpListener -> LoggerTunnel -> BlackHole(passive)
```
یک payload شناخته‌شده‌ی UDP به listener فرستنده بفرستید. connector آن را به listener
گیرنده متصل کنید، LoggerTunnel را روی `mode: "log"` و BlackHole را روی
`mode: "passive"` بگذارید. گیرنده packetهای تولیدشده و سپس payload واقعی را ثبت
و بدون پاسخ برنامه مصرف می‌کند. تنظیمات پایین generatorهای نویز و تعداد trigger
را مشخص می‌کنند.

گره متناظری برای حذف junk وجود ندارد؛ برنامه‌ی راه‌دور عادی این datagramهای اضافه
را هم دریافت می‌کند. قرار دادن JunkDatagramSender پیش از رمزنگاری packet-mode، junk
را هم به‌عنوان دادهٔ برنامه احراز اصالت می‌کند؛ رمزنگاری آن را حذف نمی‌کند. گیرنده‌ی
واقعی باید صریحاً نویز انتخاب‌شده را تحمل کند. مسیر باید مرز datagramها را نگه دارد؛
در جریان بایتی، بایت تزریق‌شده بخشی از جریان برنامه می‌شود.

## نمونهٔ کاربردی ساده {#minimal-practical-example}

این‌ها قطعه‌های پیکربندی گره هستند؛ گره‌های مجاورِ ارجاع‌شده را در پیکربندی پیرامون آن‌ها تعریف کنید.

<a id="نمونه-تنظیم"></a>

### نمونهٔ پیکربندی {#configuration-example}

```json
{
  "name": "junk",
  "type": "JunkDatagramSender",
  "settings": {
    "packet-count-perline-min": 2,
    "packet-count-perline-max": 5,
    "resend-again-times": 2,
    "selected-protocols": [
      "dns",
      "ntp",
      "quic-http3",
      "rtp-rtcp-srtp"
    ],
    "keep-sending-max-ms": 1500
  },
  "next": "udp-out"
}
```

با تنظیمات پیش‌فرض، رسیدن نخستین upstream payload روی هر line باعث تولید یک junk payload می‌شود؛ سپس payload واقعی به مسیر خود ادامه می‌دهد.

<a id="فیلدهای-لازم"></a>

فیلدهای سطح اصلی:

| فیلد | نوع | توضیح |
| --- | --- | --- |

| `type` | string | باید دقیقاً `"JunkDatagramSender"` باشد. |
| `settings` | object | object تنظیمات اختیاری؛ تنظیمات خالی از مقادیر پیش‌فرض استفاده می‌کند. |
| `next` | string | در metadata گره اختیاری است، اما معمولاً نام تونل بعدی را می‌گیرد که payloadِ upstream را دریافت می‌کند. |

<a id="تنظیمات"></a>

### تنظیمات {#settings}

| گزینه | نوع | پیش‌فرض | توضیح |
| --- | --- | --- | --- |
| `packet-count-perline-min` | integer | `1` | کمترین تعداد payloadِ junk برای هر trigger. مقادیر منفی به `0` محدود می‌شوند. |
| `packet-count-perline-max` | integer | `1` | حداکثر تعداد junk payload تولیدشده برای هر trigger. مقادیر منفی به `0` و بالاتر از `256` به `256` clamp می‌شوند. اگر کمتر از min باشد، به min clamp می‌شود. |
| `resend-again-times` | integer | `1` | تعداد callback‌های payloadِ upstream که روی هر line ارسال junk را فعال می‌کنند. مقدار `0` این ارسال را غیرفعال می‌کند. مقادیر منفی به `0` و مقادیر بالاتر از `256` به `256` محدود می‌شوند. |
| `selected-protocols` | array از string | همه protocol‌های پیاده‌سازی‌شده | مولدهای پروتکلی که می‌توانند به‌طور تصادفی انتخاب شوند. اگر این گزینه حذف شود، از همهٔ مولدهای پیاده‌سازی‌شده استفاده می‌شود. آرایهٔ خالی پذیرفته می‌شود، اما گره ترافیک را بدون junk عبور می‌دهد. |
| `keep-sending-max-ms` | integer | `0` | مقدار `0` ارسال کپی‌های تأخیری را غیرفعال می‌کند. اگر بزرگ‌تر از `0` باشد، از هر payload تولیدشدهٔ junk یک کپی ساخته و ارسال آن با تأخیر تصادفی از `1` تا این مقدار به میلی‌ثانیه زمان‌بندی می‌شود. مقادیر منفی ارسال تأخیری را غیرفعال می‌کنند. |

<a id="رفتار-trigger"></a>

### رفتار فعال‌سازی ارسال {#trigger-behavior}

`resend-again-times` تعداد callback‌های payloadِ upstream را می‌شمارد، نه تعداد بایت‌ها یا تلاش‌های اتصال را.

مثلاً:

```json
{
  "packet-count-perline-min": 2,
  "packet-count-perline-max": 4,
  "resend-again-times": 3
}
```

روی هر line، هریک از سه callback نخست payloadِ upstream مجموعه‌ای تصادفی شامل `2` تا `4` payloadِ junk تولید می‌کنند. payload چهارم و بعدی بدون junk اضافه عبور داده می‌شوند.

هیچ junk‌ای در طول `Init` به‌تنهایی فرستاده نمی‌شود. گره منتظر می‌ماند تا یک upstream payload واقعی برسد.

## کاربرد و رفع اشکال {#usage-and-troubleshooting}



<a id="یادداشتهای-buffer-و-padding"></a>

### نکته‌های buffer و padding {#buffer-and-padding-notes}

`JunkDatagramSender` بایتی به ابتدای payload واقعی اضافه نمی‌کند و buffer آن را تغییر نمی‌دهد. برای payload‌های junk، buffer‌های بزرگ و جداگانه می‌گیرد.

metadata گره تنظیم می‌کند:

```text
required_padding_left = 0
layer_group = kNodeLayerAnything
```

با اینکه metadata محدودیتی برای لایه نمی‌گذارد، داده تولیدی payload‌ی شبیه برنامه UDP است. این گره را ابزاری برای دست‌کاری بسته‌های IPv4 در نظر نگیرید؛ برای تغییر بسته خام از گره‌هایی مانند `IpManipulator` یا `IpOverrider` استفاده کنید.

<a id="یادداشتهای-عملی"></a>

### یادداشت‌های عملی {#practical-notes}

- `resend-again-times: 0` گره را به pass-through تبدیل می‌کند.
- `packet-count-perline-max: 0` گره را به pass-through تبدیل می‌کند.
- `selected-protocols: []` گره را به pass-through تبدیل می‌کند و یک warning log می‌کند.
- `keep-sending-max-ms` برای هر payloadِ junk یک کپی با تأخیر زمان‌بندی می‌کند و ارسال را برای همیشه ادامه نمی‌دهد.
- scheduler مربوط به line ترتیب کپی‌های با تأخیر را تضمین نمی‌کند.
- این گره آدرس، port، checksum یا headerِ بسته را بازنویسی نمی‌کند.
- payload‌های تولیدشده تنها نویز استتاری هستند و رمزنگاری یا احراز هویت فراهم نمی‌کنند.

## رفتار پیشرفته {#advanced-behavior}



<a id="انواع-payload-تولیدشده"></a>

### انواع payload تولیدشده {#generated-payload-types}

ماژول‌های پیاده‌سازی‌شده payloadهایی با ظاهر معتبر برای برنامه‌های UDP می‌سازند، نه headerِ UDP/IP:

| پروتکل | شکل تولیدشده |
| --- | --- |
| `dns` | payload پرس‌وجوی DNS، گاهی با داده‌هایی به سبک EDNS(0). |
| `dhcp` | payload پیام کلاینت DHCPv4. |
| `ntp` | payload درخواست کلاینت NTP. |
| `quic-http3` | payload شبیه QUIC Initial با دادهٔ ALPN مربوط به HTTP/3. |
| `rtp-rtcp-srtp` | payload رسانهٔ RTP، کنترل RTCP و داده‌هایی به شکل SRTP. |
| `stun-turn-ice` | payload مربوط به برقراری ارتباط یا کنترل رله در STUN، TURN و ICE. |
| `mdns` | payload پرس‌وجو و اعلان DNS چندپخشی. |
| `snmp` | payload درخواست مدیر SNMP v1/v2c. |
| `syslog` | پیام‌های syslog به سبک RFC3164/RFC5424. |
| `ipsec-nat-t` | payload به شکل keepalive در NAT-T، IKEv2 و ESP-in-UDP. |
| `sip` | payload درخواست و پاسخ SIP. |

گره آرگومان‌های generator را با بازه هدف پیش‌فرض `12` تا `1200` بایت می‌فرستد. generator‌های مختلف ممکن است با توجه به قالب پروتکل، اندازه‌های ثابتی انتخاب کنند.

## جزئیات پیاده‌سازی {#implementation-details}



<a id="این-نود-چه-میکند"></a>

### کارکرد گره {#what-it-does}

- شمارنده triggerهای باقی‌مانده هر line را از `resend-again-times` مقداردهی اولیه می‌کند.
- junk را فقط وقتی upstream payload callback برسد می‌فرستد.
- junk را قبل از upstream payload واقعی می‌فرستد.
- تعدادی تصادفی payloadِ junk میان `packet-count-perline-min` و `packet-count-perline-max` می‌فرستد.
- generator پروتکل هر payloadِ junk را به‌طور تصادفی از `selected-protocols` انتخاب می‌کند.
- می‌تواند ارسال یک کپی با تأخیر از هر payloadِ junk را زمان‌بندی کند.
- پس از مجموعه junk، payload واقعی upstream را بدون تغییر عبور می‌دهد.
- payload‌های downstream را بدون تغییر عبور می‌دهد.
- callback‌های `Est`، `Pause` و `Resume` را بدون تغییر در همان جهت عبور می‌دهد.
- پیش از انتشار `Finish` در هر جهت، state محلی line را از بین می‌برد.

اگر هنگام ساخت یا ارسال junk، line پیش از فرستادن payload واقعی بسته شود، گره buffer داده واقعی را برای استفاده مجدد برمی‌گرداند و از callback خارج می‌شود.

<a id="رفتار-جهتها"></a>

### رفتار جهت‌ها {#direction-behavior}

| callback ورودی | رفتار |
| --- | --- |
| upstream `Init` | state مربوط به line را مقداردهی اولیه می‌کند و سپس `Init` را به `next` می‌فرستد. |
| upstream `Payload` | اگر trigger باقی مانده باشد مجموعه junk را می‌فرستد و سپس payload واقعی را به `next` عبور می‌دهد. |
| upstream `Est` / `Pause` / `Resume` | به `next` فرستاده می‌شوند. |
| upstream `Finish` | state محلی line را از بین می‌برد و سپس `Finish` را به `next` می‌فرستد. |
| downstream `Init` | state مربوط به line را مقداردهی اولیه می‌کند و سپس `Init` را به گره قبلی می‌فرستد. |
| downstream `Payload` | بدون تغییر به گره قبلی می‌رود. |
| downstream `Est` / `Pause` / `Resume` | به گره قبلی فرستاده می‌شوند. |
| downstream `Finish` | state محلی line را از بین می‌برد و سپس `Finish` را به گره قبلی می‌فرستد. |

کد منبع یک helper برای junk در downstream دارد، اما مسیر فعال payload تنها در callbackِ payloadِ upstream ارسال junk را آغاز می‌کند.

<a id="ایمنی-line"></a>

### ایمنی line {#line-safety}

`JunkDatagramSender` یک شمارنده و مجوزهای جهت‌دار انتشار را برای هر line نگه می‌دارد:

```text
remaining_resend_again_times
upstream_publication_open / downstream_publication_open
```

هنگام پردازش payloadِ upstream، گره برای فرستادن مجموعه junk با `lineRef()` یک reference موقت از line نگه می‌دارد، پس از هر ارسال بازگشتی ابتدا `lineIsAlive()` و سپس مجوز انتشار محلی را بررسی می‌کند و reference را با `lineUnref()` آزاد می‌کند. این reference حافظهٔ تخصیص‌یافته را حفظ می‌کند، نه محتوای line یا دسترسی worker را. اگر حین ارسال، `Finish` پردازش شود ولی line عادی همچنان زنده بماند، مجموعه متوقف می‌شود و buffer برنامه که هنوز در مالکیت گره است recycle می‌شود.

`Init` مجوز انتشار هر دو جهت را باز می‌کند؛ state صفرشده به معنای بسته بودن انتشار است. `Finish` در هر جهت، پیش از انتشار callback، هر دو مجوز را می‌بندد: برای line عادی state را صفر می‌کند و برای line بسته‌ای پایدار مجوزها را می‌بندد. کپی‌های تأخیردار best-effort هستند و در همهٔ نتیجه‌های submission مالکیت buffer را به `lineScheduleDelayedTaskWithBuf()` منتقل می‌کنند. scheduler زنده بودن line را بررسی می‌کند و خود task نیز مجوز انتشار این گره را بررسی می‌کند. `Finish` خروجی معلق را نامعتبر می‌کند ولی task‌های متعلق به scheduler را فوراً حذف نمی‌کند. کپی تا اجرا یا لغو در مالکیت scheduler باقی می‌ماند؛ اگر روی line زنده‌ای اجرا شود که مجوز انتشار محلی آن بسته است، task آن را به‌جای انتشار recycle می‌کند.

این گره `lineDestroy()` را فراخوانی نمی‌کند. state یک line عادی پیش از انتشار `Finish` نابود می‌شود؛ state مربوط به line بسته‌ای با هر دو مجوز بسته باقی می‌ماند.

<a id="پشتیبانی-splice"></a>

### پشتیبانی splice {#splice-support}

دادهٔ junk تولیدشده و نسخه‌های تأخیری آن همچنان buffer عادی هستند. payload برنامه بدون بررسی بدنه عبور می‌کند و بدنهٔ pipe خصوصی و ترتیب فعلی نسبت به junk فوری حفظ می‌شود. انتشار بسته‌شده ورودی را دور می‌ریزد؛ اگر ارسال junk، line را ببندد یا state این گره را از بین ببرد، buffer برنامه که هنوز تحت مالکیت گره است بازیافت می‌شود.

buffer‌های عادیِ fallback همچنان پذیرفته می‌شوند. splice به build پشتیبانی‌شدهٔ Linux، فعال‌بودن `misc.splice`، نبود گره بسته و پشتیبانی همهٔ گره‌های زنجیرهِ نهایی پس از گسترش و ادغام نیاز دارد. flag قابلیت این بررسی‌ها را دور نمی‌زند. بدون اندازه‌گیری، بهبود کارایی تضمین نمی‌شود.

config بسته این گره دولایه همچنان splice را فعال نمی‌کند.
