# TlsServer

## نمای کلی {#overview}

`TlsServer` لایه TLS سمت server در WaterWall است و از OpenSSL استفاده می‌کند. TLS record‌های رمزنگاری‌شده را از گره قبلی
می‌گیرد، یک handshake واقعی در سمت server انجام می‌دهد و application data رمزگشایی‌شده را به گره بعدی می‌فرستد. داده
cleartext برگشتی نیز دوباره رمزنگاری می‌شود و به‌شکل TLS record به گره قبلی برمی‌گردد.

رفتار این گره شبیه یک TLS terminator عمومی مانند nginx `stream` است، نه nginx `http`. خود node HTTP، HTTP/2، Trojan،
VLESS یا هر application protocol دیگری را که بعد از TLS قرار دارد تجزیه نمی‌کند.

<span id="جایگاه-رایج"></span>

## جایگاه معمول در زنجیره {#typical-placement}

chain سمت server برای HTTP:

```text
TcpListener -> TlsServer -> HttpServer (WebSocket) -> VmessServer -> TcpUdpConnector
```

chain همراه با proxy protocol:

```text
TcpListener -> TlsServer -> TrojanServer -> TcpUdpConnector
TcpListener -> TlsServer -> VlessServer -> TcpUdpConnector
```

TLS termination عمومی قبل از routing:

```text
TcpListener -> TlsServer -> Router
```

گره بعدی application data را به‌شکل cleartext دریافت می‌کند، نه TLS record.

## نمونهٔ کاربردی ساده {#minimal-practical-example}

این قطعه بخشی از پیکربندی یک گره است؛ همسایه‌ها و همتاهای ارجاع‌شده را در همان استقرار تعریف کنید.

مسیرهای PEM را با مسیر زنجیرهٔ گواهی سرور و کلید خصوصی جایگزین کنید و `http-server` را برای جریان رمزگشایی‌شدهٔ HTTP/1.1 تعریف کنید. یک listener باید بایت‌های TLS را به این گره برساند. کلاینت باید به گواهی اعتماد کند و از نام آن استفاده کند.

```json
{
  "name": "tls-server",
  "type": "TlsServer",
  "settings": {
    "cert-file": "/etc/waterwall/fullchain.pem",
    "key-file": "/etc/waterwall/privkey.pem",
    "select-alpns": [
      "http/1.1"
    ]
  },
  "next": "http-server"
}
```

برای پیش‌فرض‌ها و الزام‌های مشروط، [پیکربندی](#configuration) و برای نمونه‌های کامل و محدودیت‌های عملیاتی، [کاربرد و رفع اشکال](#usage-and-troubleshooting) را ببینید.

## پیکربندی {#configuration}



<span id="فیلدهای-اجباری"></span>

### فیلدهای اجباری {#required-fields}

فیلدهای سطح بالای پیکربندی:

| فیلد | نوع | توضیح |
| --- | --- | --- |
| `name` | رشته | نام دلخواه گره؛ باید داخل config یکتا باشد. |
| `type` | رشته | باید دقیقاً `"TlsServer"` باشد. |
| `settings` | شیء | تنظیمات TLS server؛ نباید خالی باشد. |
| `next` | رشته | node‌ای که پس از موفقیت TLS داده cleartext را دریافت می‌کند؛ در استفاده معمول لازم است. |

فیلدهای اجباری داخل `settings`:

| فیلد | نوع | توضیح |
| --- | --- | --- |
| `cert-file` | رشته | مسیر فایل PEM certificate سرور. |
| `key-file` | رشته | مسیر فایل PEM private key سرور. |

هر دو فایل باید برای OpenSSL context معتبر باشند.

<span id="تنظیمات-اختیاری"></span>

### تنظیمات اختیاری {#optional-settings}

| فیلد | پیش‌فرض | توضیح |
| --- | --- | --- |
| `sni` | تنظیم نشده | تطبیق دقیق SNI بدون حساسیت به بزرگی حروف. SNI نامنطبق یا غایب در صورت تنظیم fallback به آن هدایت می‌شود؛ در غیر این صورت handshake رد می‌شود. |
| `select-alpns` | `["http/1.1"]` | فهرست انتخاب ALPN به‌ترتیب ترجیح server. |
| `alpns` | تنظیم نشده | نام قدیمی تنظیم ALPN؛ بهتر است از `select-alpns` استفاده کنید. |
| `min-version` | `"TLSv1.2"` | حداقل TLS version. |
| `max-version` | `"TLSv1.3"` | حداکثر TLS version. |
| `ciphers` | `"HIGH:!aNULL:!MD5"` | OpenSSL cipher string برای TLS 1.2 و قدیمی‌تر. |
| `prefer-server-ciphers` | `false` | server cipher preference را فعال می‌کند. |
| `session-timeout` | `300` | عمر TLS session به ثانیه. |
| `handshake-timeout-ms` | `60000` | مهلت قطعی برای کامل شدن TLS handshake؛ مقدار `0` آن را غیرفعال می‌کند. |
| `session-cache` | `"none"` | حالت session cache. |
| `session-cache-size` | `20480` | اندازه cache داخلی OpenSSL. |
| `session-tickets` | `true` | TLS session ticket‌ها را فعال می‌کند. |
| `fallback-node-name` | تنظیم نشده | شاخهٔ جایگزین برای ورودی آشکارا غیر TLS یا SNI نامنطبق/غایب در صورت تنظیم `sni`، پیش از قطعی شدن مسیر TLS. نام‌های `fallback-node` و `fallback` هم پذیرفته می‌شوند. |
| `fallback-intentional-delay-ms` | `7` | تأخیر عمدی برای payload‌های upstream در fallback؛ در delay غیرصفر jitter اعمال می‌شود. در `0`، fallback مقداردهی‌شده که FIFO قدیمی یا drain زمان‌بندی‌شده ندارد حتی هنگام Pause، payload را inline می‌گیرد؛ بایت‌های نگه‌داشته‌شده بدون انتظار برای Resume و به‌ترتیب FIFO تخلیه می‌شوند. |
| `fallback-intentional-delay-jitter-ms` | `1` | jitter تصادفی برای زمان‌بندی payload‌های fallback؛ اگر delay صفر باشد نادیده گرفته می‌شود. |
| `tls13-record-shaping` | تنظیم نشده | تنظیم آزمایشی padding و delay سمت فرستنده برای TLS 1.3. |
| `verbose` | `false` | جزئیات بیشتری از lifecycle مربوط به TLS را log می‌کند. |

می‌توانید `sni` را همراه fallback تنظیم کنید تا SNI نامنطبق یا غایب، پیش از تولید خروجی TLS محلی، به یک listener واقعی TLS هدایت شود.

<span id="شکلدهی-آزمایشی-tls-13-record"></span>

### شکل‌دهی آزمایشی رکوردهای TLS 1.3 {#experimental-tls-13-record-shaping}

تنظیم `tls13-record-shaping` به‌صورت اختیاری نخستین application record‌های TLS 1.3 را که همین node می‌فرستد pad می‌کند و
به تأخیر می‌اندازد. اگر این تنظیم وجود نداشته باشد، قابلیت غیرفعال است. این قابلیت هرگز ciphertext دریافتی، handshake
record‌ها، alert‌ها، application record‌های خالی، بایت‌های fallback یا record‌های TLS 1.2 را تغییر نمی‌دهد. اگر باید هر دو
جهت ارسال شکل داده شوند، `TlsServer` محلی و `TlsClient` راه دور را جداگانه تنظیم کنید.

فرم سفارشی:

```json
"tls13-record-shaping": {
  "scope": {"first-application-records": 8},
  "outcomes": [
    {
      "probability": 50,
      "padding-bytes": [100, 200],
      "delay": {"probability": 75, "ms": [10, 20]}
    },
    {"probability": 10, "padding-bytes": [400, 600]}
  ]
}
```

`padding-bytes` و `delay.ms` یک integer یا بازه integer شامل دو سر `[minimum, maximum]` می‌پذیرند. تعداد outcome‌ها باید
بین ۱ تا ۱۶ باشد؛ `first-application-records` بین ۱ تا ۱۰۲۴، padding بین ۱ تا ۴۰۹۶ byte و delay بین ۰ تا ۱۰۰۰
millisecond است. probability‌های outcome به‌صورت تجمعی و mutually exclusive تفسیر می‌شوند و مجموع آن‌ها نباید از ۱۰۰
بیشتر باشد. هر بار حداکثر یک outcome انتخاب می‌شود و درصد استفاده‌نشده record را بدون تغییر می‌گذارد. probability مربوط
به delay فقط پس از انتخاب همان outcome بررسی می‌شود. key ناشناخته و مقدار غیرinteger یا خارج از محدوده باعث خطای
startup می‌شود. هر record واجد شرایط یک جایگاه از scope مصرف می‌کند، حتی اگر هیچ outcome‌ای انتخاب نشود.

در حال حاضر فقط فرم سفارشی شامل `scope` و `outcomes` پذیرفته می‌شود. تا زمانی که اندازه‌گیری‌های representative برای
capture، overhead، موفقیت connection و classifier انتشار یک preset versionشده را توجیه نکنند، key به نام `profile`
رد می‌شود.

padding از بایت‌های صفر استاندارد TLS 1.3 در `TLSInnerPlaintext` استفاده می‌کند و به‌اندازه انتخاب‌شده به ciphertext
می‌افزاید، البته تا ظرفیت قانونی باقی‌مانده در TLS record. Delay پس از رمزنگاری اعمال می‌شود و latency انتخاب‌شده را
اضافه می‌کند. ترتیب record‌ها روی wire با رابطه
`release_at = max(now + delay, previous_release_at)` حفظ می‌شود. ciphertext صف‌شده برای هر line حداکثر ۸ MiB است؛ در
۶ MiB فشار محلی بر تولیدکننده فعال و در ۳ MiB رفع می‌شود. تا وقتی فشار محلی یا آخرین Pause دریافتی فعال باشد،
تولیدکننده متوقف می‌ماند. Resume دریافتی فشار محلی را رفع نمی‌کند و رفع فشار محلی نیز Pause دریافتی را از بین نمی‌برد.
اعلان‌های دریافتی تکراری هم، اگر توقف محلی مانع نباشد، منتقل می‌شوند. خروجی ciphertext در زمان مقرر و با ترتیب FIFO بدون انتظار برای Resume تخلیه می‌شود؛
Pause تایمر تخلیه را لغو نمی‌کند. پس از آنکه `close_notify` همتا سمت cleartext را پایان داد، `TlsServer` هیچ payload، Pause یا
Resume‌ای به آن سمت نمی‌فرستد؛ application بایت‌هایی که بعداً دریافت شوند یا پیش‌تر توسط یک callback بیرونی رمزگشایی شده
باشند دور ریخته می‌شوند. در هر دو حالت دریافت `close_notify` از همتا یا پایان سمت cleartext، ciphertext پذیرفته‌شده server و یک `close_notify` بدون padding پیش
از downstream `Finish` تخلیه می‌شوند. پایان سمت wire خروجی صف‌شده را لغو و دور می‌ریزد و فقط به سمت cleartext منتقل می‌شود.
اگر ساخت timer شکست بخورد، record‌ها فوراً و به‌ترتیب تخلیه می‌شوند.

پس از مصرف کامل scope تنظیم‌شده برای application record‌ها، ابتدا صف فعلی shaping به‌طور کامل تخلیه می‌شود تا هیچ TLS
record بعدی از ciphertext تأخیردار سبقت نگیرد. تا زمانی که این مانع ترتیب‌دهی فعال است، درخواست توقف محلی shaping
حتی پایین‌تر از low watermark باقی می‌ماند؛ Resume دریافتی این توقف را رفع نمی‌کند. وقتی صف خالی باشد و write-BIO در یک مرز کامل قرار
داشته باشد، timer و صف shaping مربوط به line آزاد می‌شوند؛ خروجی‌های بعدی TLS بدون parse کردن record یا نگه‌داری metadata
شکل‌دهی، حتی هنگام Pause مستقیم forward می‌شوند. بنابراین محدودیت ۸ MiB و watermark‌های ۶/۳ MiB فقط پنجره محدود و
فعال shaping را مقید می‌کنند. رمزنگاری و رمزگشایی TLS ادامه دارد؛ پایان shaping به معنی bypass دائمی tunnel نیست.

record shaping می‌تواند اندازه و زمان‌بندی record‌های ابتدایی را کمتر قابل پیش‌بینی کند، اما نمی‌تواند یک round trip
داخلی handshake را حذف کند، burst را کوچک‌تر کند یا همه ویژگی‌های جهت و زمان‌بندی را پنهان کند. وقتی multiplexing برای
deployment مناسب است، آن را همراه `MuxClient`/`MuxServer` استفاده کنید.

## کاربرد و رفع اشکال {#usage-and-troubleshooting}



### ورودی TLS برای سرویس محلی HTTP {#tls-http-frontend}

این تنظیم کامل nodeها، سرویس موجود HTTP/1.1 در `127.0.0.1:8080` را از طریق
TLS روی پورت TCP برابر 8443 ارائه می‌کند:

```text
HTTPS client -> TcpListener:8443 -> TlsServer -> TcpConnector -> HTTP service:8080
```

```json
{
  "name": "tls-http-frontend",
  "nodes": [
    {
      "name": "public-tls",
      "type": "TcpListener",
      "settings": {
        "address": "0.0.0.0",
        "port": 8443
      },
      "next": "tls"
    },
    {
      "name": "tls",
      "type": "TlsServer",
      "settings": {
        "cert-file": "/etc/waterwall/fullchain.pem",
        "key-file": "/etc/waterwall/privkey.pem",
        "select-alpns": [
          "http/1.1"
        ]
      },
      "next": "http-service"
    },
    {
      "name": "http-service",
      "type": "TcpConnector",
      "settings": {
        "address": "127.0.0.1",
        "port": 8080
      }
    }
  ]
}
```

این فایل nodeها را از `core.json` ارجاع دهید، گواهی معتبر `service.example.com`
و کلید خصوصی آن را در مسیرهای نشان‌داده‌شده قرار دهید و TCP ورودی 8443 را باز
کنید. کلاینت عادی HTTPS می‌تواند مستقیماً به
`https://service.example.com:8443/` وصل شود؛ این نام باید به سرور برسد.

backend درخواست کامل HTTP، از جمله headerها را دریافت می‌کند. اینجا HttpServer
لازم نیست؛ آن node فریم‌بندی انتقال را مصرف می‌کند و فقط body را تحویل می‌دهد.
برای VMess داخل WebSocket روی TLS، [تنظیم سرور VMess](./VmessServer.mdx#socks5-websocket-tls-server)
را ببینید. [forward متناظر TlsClient](./TlsClient.mdx#tls-http-client) هم به
برنامهٔ HTTP محلیِ بدون TLS اجازه می‌دهد از این endpoint استفاده کند.

<span id="نمونه-fallback"></span>

### نمونه fallback {#fallback-example}

```json
{
  "name": "tls-server",
  "type": "TlsServer",
  "settings": {
    "cert-file": "/etc/waterwall/fullchain.pem",
    "key-file": "/etc/waterwall/privkey.pem",
    "fallback-node-name": "nginx-fallback",
    "fallback-intentional-delay-ms": 7,
    "fallback-intentional-delay-jitter-ms": 1,
    "select-alpns": ["http/1.1"]
  },
  "next": "protected-protocol"
}
```

fallback فقط تا پیش از قطعی شدن مسیر TLS قابل انتخاب است. کاربردش رسیدگی به probe‌های plaintext یا malformed روی یک پورت
عمومی TLS است، نه مسیریابی application پس از authentication.

<span id="نکتههای-nginx-matching"></span>

### نکته‌های تطبیق با Nginx {#nginx-matching-notes}

مقادیر پیش‌فرض برای شباهت به رفتار عادی TLS server در nginx `stream` انتخاب شده‌اند. تغییر گزینه‌های زیر ممکن است همچنان
TLS معتبری بسازد، اما خروجی دیگر شبیه آن baseline نخواهد بود:

- `ciphers`
- `min-version` یا `max-version`
- `prefer-server-ciphers`
- `session-cache`
- `session-tickets`
- ALPN selection
- `sni`
- fallback target و fallback timing

اگر هدفتان شباهت در سطح wire به nginx پیش‌فرض است، این مقدارها را تغییر ندهید مگر اینکه اندازه‌گیری مشخصی دلیل آن را نشان
داده باشد.

<span id="اشتباههای-رایج"></span>

### اشتباه‌های رایج {#common-mistakes}

- انتظار نداشته باشید `TlsServer` خودش HTTP را تجزیه کند؛ برای این کار `HttpServer` را بعد از آن قرار دهید.
- هنگام ترکیب `sni` با fallback، مقصد fallback را listener مبتنی بر TLS قرار دهید که بتواند ClientHello اصلی را پردازش کند.
- از ALPN برای authentication یا رد کردن اتصال استفاده نکنید؛ نبودن ALPN مشترک، handshake را بدون ALPN توافق‌شده ادامه می‌دهد.
- `h2` را اعلام نکنید مگر اینکه هر دو مسیر محافظت‌شده و fallback بتوانند پاسخی قابل‌قبول برای HTTP/2 بدهند.
- از `shared` برای session cache استفاده نکنید؛ پیاده‌سازی نشده است.

## رفتار پیشرفته {#advanced-behavior}



<span id="tls-versionها"></span>

### نسخه‌های TLS {#tls-versions}

مقادیر قابل قبول:

```text
TLSv1
TLSv1.1
TLSv1.2
TLSv1.3
TLS1.0
TLS1.1
TLS1.2
TLS1.3
1.0
1.1
1.2
1.3
```

`min-version` نباید از `max-version` بزرگ‌تر باشد.

### انتخاب ALPN {#alpn-selection}

`TlsServer` از ALPN فقط برای انتخاب protocol استفاده می‌کند، نه برای کنترل دسترسی.

ترتیب اعضای array همان ترتیب ترجیح server است:

```json
"select-alpns": ["h2", "http/1.1"]
```

اگر client هر دو مقدار را ارائه کند، `h2` انتخاب می‌شود. اگر ALPN ارسال‌شده با هیچ گزینه‌ای مشترک نباشد، handshake بدون
ALPN توافق‌شده ادامه پیدا می‌کند. وقتی client اصلاً ALPN نفرستد، callback انتخاب در OpenSSL اجرا نمی‌شود و handshake باز
هم بدون ALPN ادامه می‌یابد.

mode‌های `select-alpns`:

| پیکربندی | رفتار |
| --- | --- |
| نوشته نشده | مقدار پیش‌فرض `["http/1.1"]` به کار می‌رود. |
| `[]` | انتخاب ALPN کاملاً غیرفعال می‌شود. |
| array غیرخالی | نخستین مقدار تنظیم‌شده‌ای انتخاب می‌شود که client نیز آن را ارائه کرده باشد. |

`alpns` قدیمی است، اما همچنان خوانده می‌شود. هر عضو می‌تواند یک string یا objectی با فیلد `value` باشد. `alpns` و
`select-alpns` را هم‌زمان با مقدار غیرخالی تنظیم نکنید.

ALPN، protocol انتخاب‌شده را به tunnel‌های بعدی اعلام نمی‌کند. اگر `h2` را ارائه می‌کنید، chain بعد از `TlsServer` باید
واقعاً بتواند رفتاری قابل‌قبول برای HTTP/2 نشان دهد؛ در غیر این صورت deployment راحت‌تر fingerprint می‌شود.

### حافظهٔ نهان نشست {#session-cache}

مقادیر پشتیبانی‌شده برای `session-cache`:

| مقدار | رفتار |
| --- | --- |
| `"none"` | حالت server cache در OpenSSL، با lookup و store داخلی غیرفعال؛ مقدار پیش‌فرض. |
| `"off"` | session cache را غیرفعال می‌کند. |
| `"builtin"` | cache داخلی server در OpenSSL را با `session-cache-size` فعال می‌کند. |
| `"builtin:SIZE"` | cache داخلی را فعال می‌کند و اندازه را همان‌جا می‌گیرد؛ برای مثال `"builtin:4096"`. |

حالت `shared` در پیاده‌سازی فعلی پشتیبانی نمی‌شود.

<span id="رفتار-fallback"></span>

### رفتار fallback {#fallback-behavior}

بازپخش خام fallback روی همان خط ورودیِ قرض‌گرفته‌شده انجام می‌شود. هویت مبدأ
و انتخاب قبلی مقصد حفظ می‌شوند. اگر انتقال مقصد تعیین نشده و مقصد ثابت
نباشد، پیش از `Init` شاخهٔ fallback، TCP ثبت می‌شود.

fallback فقط تا پیش از قطعی شدن مسیر TLS قابل انتخاب است.

classifier، بایت‌های ابتدایی upstream را بررسی می‌کند:

- بایت‌هایی که آشکارا TLS نیستند به fallback می‌روند
- بایت‌هایی که شبیه رکورد handshake مربوط به TLS شروع می‌شوند، مانند `16 03`، توسط OpenSSL تجزیه می‌شوند؛ اگر `sni` و fallback تنظیم شده باشند، callback اولیهٔ ClientHello، SNI نامنطبق یا غایب را به fallback هدایت می‌کند
- با تولید ServerHello توسط OpenSSL، مسیر line روی branch محافظت‌شده TLS قطعی می‌شود

با شروع fallback، `TlsServer` منابع TLS مربوط به line را آزاد و branch جایگزین را مقداردهی اولیه می‌کند. در عملیات عادی
و delay غیرصفر، بایت‌های ذخیره‌شده و batch‌های upstream بعدی با delay و jitter تنظیم‌شده فرستاده می‌شوند. در delay صفر،
fallback مقداردهی‌شده که FIFO قدیمی یا drain زمان‌بندی‌شده ندارد حتی هنگام Pause، payload را inline می‌گیرد.
بایت‌های نگه‌داشته‌شده بدون انتظار برای Resume و با ترتیب FIFO تخلیه می‌شوند؛ ورودی جدید از آن‌ها سبقت نمی‌گیرد. از آن به بعد
payload‌ها بدون رمزنگاری یا رمزگشایی TLS از fallback عبور می‌کنند. FIFO تأخیردار upstream در fallback برای هر line
به 1 MiB بایت منطقی و 8 MiB هزینهٔ تخصیص بافر محدود است. هنگام فشار ناشی از هزینهٔ حافظه، batch تأخیردار ابتدا در صورت
جاگرفتن در محدودیت‌ها در فضای با اندازهٔ متناسب ادغام می‌شود؛ ترتیب بایت‌ها و تأخیر زمان‌بندی‌شده حفظ می‌شوند.

ورودی معیوب ClientHello/SNI که پیش از مسیریابی رد شود در مسیر خطای TLS باقی می‌ماند. ورودی ناقص یا کند تا مهلت handshake
منتظر می‌ماند؛ پس از انتخاب fallback بر اساس SNI، سرور fallback مذاکره و خطاهای TLS را مدیریت می‌کند.

با فعال بودن مسیریابی SNI، ورودی اصلی تا قطعی شدن TLS یا انتخاب fallback در بافرهای فشرده و قابل ادغام نگه داشته می‌شود؛
سقف ورودی برای هر line برابر 1 MiB است. تقسیم داده در socket و تقسیم ClientHello میان رکوردهای TLS پشتیبانی می‌شود و
بایت‌های بعدیِ ادغام‌شده نیز به‌ترتیب بازپخش می‌شوند. مهلت موجود `handshake-timeout-ms` ورودی ناقص را پوشش می‌دهد؛
`0` این مهلت را غیرفعال می‌کند. عبور از سقف بافر اتصال را بدون انتخاب شاخه می‌بندد. ServerHello، از جمله HelloRetryRequest،
مسیر TLS را قطعی می‌کند؛ خطاهای بعدی هرگز آن را به fallback تغییر نمی‌دهند.

تأخیر fallback فقط روی payload‌های upstream در عملیات عادی اعمال می‌شود. پاسخ‌های
downstream عمداً به تأخیر نمی‌افتند. اگر upstream `Finish` برسد، بایت‌های صف‌شده حتی هنگام Pause به‌صورت همگام و به‌ترتیب
FIFO پیش از `Finish` fallback تخلیه می‌شوند. اگر Init هنوز روی stack باشد، batch دور ریخته می‌شود. delay باقی‌مانده پس از
`Finish` زنده نگه داشته نمی‌شود. این گره برای انتخاب branch خارج از مسیر عادی `next` فعال می‌ماند و bypass نمی‌شود.

پیش از Init branch منتخب، آخرین Pause دریافتی فقط برای بازپخش پس از Init نگه داشته می‌شود و Resume آن را لغو می‌کند.
پس از Init، شاخهٔ fallback همهٔ Pause و Resumeها را دریافت می‌کند. شاخهٔ محافظت‌شده فشار دریافتی را با فشار محلی
شکل‌دهی رکورد ترکیب می‌کند؛ این اعلان‌ها مانع خروجی آماده نمی‌شوند.

برای camouflage روی یک پورت عمومی، بهتر است fallback یک سرویس واقعی TLS، معمولاً nginx، با certificate، SNI، ALPN،
cipher، ticket و نسخه protocol مشابه `TlsServer` باشد. قرار دادن HTTP ساده پشت یک پورت عمومی TLS معمولاً خیلی راحت‌تر
fingerprint می‌شود.

<span id="مسیریابی-بر-اساس-sni-با-fallback-واقعی-tls"></span>

### مسیریابی بر اساس SNI با fallback واقعی TLS {#sni-routing-with-a-real-tls-fallback}

وب‌سرور Nginx دو ورودی غیرمنتظره عمومی روی HTTPS listener را از یکدیگر متمایز می‌کند:

1. **درخواست Plaintext HTTP روی پورت HTTPS**: Nginx یک درخواست عادی روی پورت HTTPS را در داخل با وضعیت 497 دسته‌بندی می‌کند. اگر `error_page` سفارشی نشده باشد، پاسخ پیش‌فرض معمولاً همان صفحه HTML قابل‌شناسایی با وضعیت بیرونی 400 است. گزینه `fallback-node-name` در `TlsServer` این حالت را با هدایت بایت‌های غیر TLS پیش از تعهد به TLS به سمت node fallback مدیریت می‌کند. بخش [پردازش خطاهای SSL در مستندات Nginx](https://nginx.org/en/docs/http/ngx_http_ssl_module.html#errors) را ببینید.
2. **پیام TLS ClientHello با SNI ناشناخته یا متفاوت**: اتصال ابتدا در context سرور پیش‌فرض Nginx ساخته می‌شود و اگر SNI منطبق پیدا نشود، handshake معمولاً با certificate و تنظیمات همان context کامل می‌شود. سرور پیش‌فرض می‌تواند با تنظیم صریح [`ssl_reject_handshake on`](https://nginx.org/en/docs/http/ngx_http_ssl_module.html#ssl_reject_handshake) این handshake‌ها را رد کند. بخش [انتخاب virtual server در Nginx](https://nginx.org/en/docs/http/server_names.html#virtual_server_selection) را ببینید.

با تنظیم هم‌زمان `sni` و `fallback-node-name`، گره `TlsServer` پیش از تولید خروجی TLS، SNI آشکار نامنطبق یا غایب را
مستقیماً به fallback هدایت می‌کند. SNI منطبق مسیر محافظت‌شدهٔ `next` را ادامه می‌دهد. برای این مسیر تک‌نامی نیازی به
`SniffRouter` نیست. بدون fallback، تنظیم `sni` همچنان فیلتر سخت‌گیرانهٔ رد handshake است.

```text
TcpListener :443 -> TlsServer (sni: protected.example.com)
                      |-- next -> protected backend
                      `-- fallback-node-name -> TcpConnector -> real nginx HTTPS listener
```

گره TLS را این‌گونه تنظیم کنید:

```json
{
  "name": "tls-server",
  "type": "TlsServer",
  "settings": {
    "cert-file": "server.crt",
    "key-file": "server.key",
    "sni": "protected.example.com",
    "fallback-node-name": "nginx-fallback-connector"
  },
  "next": "protected-backend"
}
```

connector باید به یک listener واقعی TLS اشاره کند: fallback بایت‌های اصلی TLS روی شبکه را دریافت می‌کند، نه HTTP
رمزگشایی‌شده. در ECH از SNI آشکار بیرونی استفاده می‌شود؛ SNI رمزنگاری‌شدهٔ درونی در دسترس نیست. SNI متادیتای مسیریابی
است و احراز هویت محسوب نمی‌شود.

`SniffRouter` همچنان گزینه‌ای برای مسیرهای چنددامنه‌ای یا مسیریابی ترکیبی پروتکل‌ها است:

```text
TcpListener :443 -> SniffRouter
                      |-- route (expected SNI) -> TlsServer -> protected backend
                      `-- default (unmatched)  -> TcpConnector -> real nginx HTTPS listener
```

الگوی config مینیمال:

```json
{
  "name": "sniff-router",
  "type": "SniffRouter",
  "settings": {
    "routes": [
      {
        "domain": "vpn.example.com",
        "detection": "tls",
        "next": "protected-tls-server"
      }
    ]
  },
  "next": "nginx-fallback-connector"
}
```

در این معماری:
- node `SniffRouter` پیش از پایان TLS، مقدار SNI در ClientHello آشکار را بررسی و دسته‌بندی می‌کند.
- پیام‌های ClientHello منطبق به `TlsServer` هدایت می‌شوند (که نباید `fallback-node-name` داشته باشد). استفاده از فیلتر `sni` در `TlsServer` اختیاری و به عنوان بررسی redundant fail-closed است، نه مکانیزم اصلی مسیریابی.
- پیام‌های ClientHello با SNI آشکار نامنطبق، پیام‌های فاقد SNI آشکار و ترافیک plaintext به شاخه پیش‌فرض `next` در `SniffRouter` و به Nginx واقعی بدون رمزگشایی هدایت می‌شوند.
- ECH مقدار SNI درونی را پنهان می‌کند، اما ClientHello بیرونی آن ممکن است همچنان نام سرور آشکاری داشته باشد. `SniffRouter` بر اساس همان مقدار بیرونی مسیریابی می‌کند: نام بیرونی منطبق به شاخه محافظت‌شده می‌رود و نام بیرونی نامنطبق یا غایب به شاخه پیش‌فرض می‌رود. این گره نمی‌تواند بر اساس نام درونی رمزنگاری‌شده مسیریابی کند.
- پیام‌های کامل ClientHello پیش از اعمال حد آستانه buffer ارزیابی می‌شوند. ورودی‌های ناقصی که کمتر از سقف ۸۱۹۲ بایت هستند در حالت انتظار می‌مانند و تخصیص‌نیافته می‌مانند؛ `SniffRouter` تایمر طبقه‌بندی ندارد، بنابراین timeoutهای بیکاری listener (مانند `TcpListener`) زمان انتظار این ورودی‌ها را تعیین می‌کنند.
- برای مشاهده config کامل، فایل `tests/examples/vless_tls_sni_camouflage_server.json` را بررسی کنید.

**محدودیت‌ها و مرزهای شناسایی**:
- **مقدار SNI تنها متادیتای مسیریابی است، نه احراز هویت**: هر کلاینتی که SNI مورد انتظار را بداند به `TlsServer` محافظت‌شده می‌رسد. احراز هویت باید در لایه‌های درونی پروتکل (مانند VLESS یا Trojan) انجام گیرد.
- **رفتار پروتکل درونی همچنان قابل مشاهده است**: بایت‌های پاسخ رد یا fallback، شیوه بسته‌شدن اتصال و timing پس از رسیدن probe به SNI محافظت‌شده همچنان می‌توانند پروتکل درونی یا deployment را آشکار کنند.
- **سلامت و پاسخ‌دهی fallback**: در صورت در دسترس نبودن سرور Nginx پشتیبان، برگرداندن صفحه‌های خطای غیرمنتظره یا تفاوت در رفتارهای certificate/ALPN/cipher/session، سرویس قابل شناسایی خواهد بود.
- **تایمینگ و timeout‌ها**: buffering در `SniffRouter` و اتصال مجدد تأخیر اندکی ایجاد می‌کنند. زمان‌های timeout در `TcpListener` را با سرور پوششی هماهنگ کنید. WaterWall ادعای یکسان‌بودن کامل تایمینگ یا تطابق بایت‌به‌بایت اثر انگشت TLS را ندارد.

### مهلت handshake {#handshake-timeout}

`handshake-timeout-ms` مهلتی قطعی است که با مقداردهی line آغاز می‌شود و دریافت بایت‌های جدید آن را تمدید نمی‌کند. این زمان
از timeout‌های listener، مانند `initial-idle-timeout-ms` و `active-idle-timeout-ms` در `TcpListener`، مستقل است.

فقط زمانی `handshake-timeout-ms` را `0` بگذارید که عمداً هیچ deadline قطعی برای TLS handshake نمی‌خواهید.

## جزئیات پیاده‌سازی {#implementation-details}



<span id="رفتار-در-زمان-اجرا"></span>

### رفتار هنگام اجرا {#runtime-behavior}

`TlsServer` مقداردهی اولیه line را فقط از طریق upstream `Init` می‌پذیرد.
فراخوانی downstream `Init` در هر حالتی، از جمله هنگام تخلیه نهایی fallback،
استفاده نادرست و fatal از callback است؛ node خطا را ثبت و فرایند را خاتمه می‌دهد.
payload پاسخ در جهت downstream همچنان روی line‌هایی که از upstream مقداردهی اولیه شده‌اند پشتیبانی می‌شود.

در upstream `Init`، `TlsServer`:

1. state مربوط به OpenSSL را برای line می‌سازد
2. memory BIO‌ها را می‌سازد
3. SSL object را در server mode قرار می‌دهد
4. مگر با `handshake-timeout-ms: 0`، deadline مربوط به handshake را فعال می‌کند
5. اگر fallback تنظیم نشده باشد، branch محافظت‌شده `next` را بلافاصله راه می‌اندازد
6. در صورت وجود fallback، منتظر بایت‌های اولیه می‌ماند تا مسیر TLS یا fallback را انتخاب کند

بایت‌های رمزنگاری‌شده upstream از گره قبلی وارد OpenSSL می‌شوند. پس از پایان TLS handshake، application data رمزگشایی‌شده
به `next` می‌رود.

داده cleartext برگشتی از `next` تا کامل شدن TLS handshake در صف می‌ماند. سپس با `SSL_write()` رمزنگاری می‌شود و به‌شکل
TLS record در جهت downstream فرستاده می‌شود.

<span id="مفهوم-establishment"></span>

### معنای برقراری اتصال {#establishment-semantics}

در WaterWall، `Est` یعنی transport زیرین برقرار شده است؛ نه اینکه TLS handshake هم پایان یافته باشد.

`TlsServer` downstream `Est` را فقط یک بار می‌فرستد و ممکن است این اتفاق پیش از پایان TLS handshake رخ دهد. آماده بودن TLS
در state داخلی و پس از پایان handshake در OpenSSL مشخص می‌شود.

<span id="رفتار-finish"></span>

### رفتار Finish {#finish-behavior}

برای بستن تمیز جهت downstream، اگر handshake کامل شده باشد، `TlsServer` هشدار TLS `close_notify` می‌فرستد.
ciphertext پذیرفته‌شده پیش از هشدار تخلیه می‌شود و تأخیر تنظیم‌شدهٔ رکورد حتی هنگام Pause مشورتی حفظ می‌شود.
سپس گره وضعیت محلی TLS را از بین می‌برد و `Finish` مربوط به WaterWall را در جهت downstream ادامه می‌دهد.

دریافت `close_notify` از همتا همین خاتمهٔ آرام محلی را آغاز می‌کند: ابتدا `TlsServer` یک بار upstream `Finish` را
به شاخهٔ cleartext مقداردهی‌شده می‌فرستد؛ سپس `close_notify` خودش را ارسال می‌کند و پس از تخلیهٔ خروجی صف‌شده،
downstream `Finish` را کامل می‌کند. پس از پایان شاخهٔ cleartext، منتظر بسته‌شدن TCP از طرف کلاینت یا timeout بیکاری
نمی‌ماند. callback دیگری به آن شاخه فرستاده نمی‌شود و دادهٔ جدید برنامه هنگام بسته‌شدن دور ریخته می‌شود.

در مقابل، upstream `Finish` خام، خروجی معلق را لغو و وضعیت TLS را بدون فرستادن هشدار یا بازگرداندن callback به سمت
پایان‌یافتهٔ شبکه از بین می‌برد. fallback خام همچنان بایت‌ها و بسته‌شدن سرویس منتخب را منتقل می‌کند.

خطاهای fatal در OpenSSL وضعیت محلی را از بین می‌برند و جهت‌های مربوط را می‌بندند. در حالت fallback، شاخهٔ fallback
مقداردهی‌شده نیز پیش از پایان سمت قبلی بسته می‌شود.

### فضای رزروشده در ابتدای بافر {#padding}

`TlsServer` مستقیماً چیزی به ابتدای payload‌های WaterWall اضافه نمی‌کند، بنابراین مقدار زیر را اعلام می‌کند:

```text
required_padding_left = 0
```

ساخت TLS record‌ها از طریق memory BIO‌های OpenSSL انجام می‌شود.
