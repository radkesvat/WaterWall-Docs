# ConnectionStripeClient

`ConnectionStripeClient` داده‌های یک اتصال برنامه را روی چند اتصال مستقل و
دوطرفه تقسیم می‌کند. در سمت مقابل، `ConnectionStripeServer` داده‌ها را با ترتیب
اصلی به یک جریان تبدیل می‌کند. هر اتصال می‌تواند هم upload و هم download را
حمل کند و تقسیم داده در دو جهت مستقل است.

```text
Client: TcpListener -> ConnectionStripeClient -> TlsClient -> TcpConnector
                                             == 8 TLS/TCP connections ==>
Server: TcpListener -> TlsServer -> ConnectionStripeServer -> TcpConnector
```

برای هر جریان ورودی، گروه جداگانه‌ای از اتصال‌های transport از مسیر مشترک
`next` ساخته می‌شود. اگر `TlsClient` بعد از این node باشد، هر عضو TLS مستقل
خواهد داشت. همهٔ اعضا باید به یک نمونهٔ `ConnectionStripeServer` در یک فرایند
WaterWall برسند. مسیر transport باید stream قابل‌اعتماد با ترتیب بایت‌ها را
برای هر عضو فراهم کند. جریان ورودی می‌تواند یک اتصال برنامه یا parent مشترک
Mux باشد؛ توضیح آن در بخش بعد آمده است.

## جایگاه transport در زنجیره

هر عضو یک line جداگانه از همان مسیر `next` کلاینت باز می‌کند.
transport متناظر در سرور باید این مسیر را پیش از تحویل بایت‌ها به
`ConnectionStripeServer` رمزگشایی یا بازسازی کند:

| transport | بعد از `ConnectionStripeClient` | قبل از `ConnectionStripeServer` |
| --- | --- | --- |
| TCP | `TcpConnector` | `TcpListener` |
| TLS روی TCP | `TlsClient -> TcpConnector` | `TcpListener -> TlsServer` |
| KCP روی UDP | `KcpClient -> UdpConnector` | `UdpListener -> KcpServer` |

UDP مستقیم stream قابل‌اعتماد موردنیاز را فراهم نمی‌کند. Stripe مرز پیام‌ها
یا datagramهای برنامه را هم حفظ نمی‌کند؛ در صورت نیاز، framing مناسب اضافه
کنید. تنظیمات `upload`، `download` یا مسیر جداگانه برای هر عضو وجود ندارند.
تنظیمات طرف مقابل در صفحهٔ
[ConnectionStripeServer](ConnectionStripeServer.mdx) آمده است.

## محدودیت پهنای باند هر اتصال و Mux

اگر هر اتصال TCP بین دو سرور محدودیت مستقل upload یا download داشته باشد و
ظرفیت مجموع مسیر هنوز پر نشده باشد، ConnectionStripe می‌تواند سرعت انتقال را
بیشتر کند. مثلاً هشت اتصال با سقف مستقل ۱۰ Mbit/s، پیش از سربار، ظرفیت نظری
مجموع ۸۰ Mbit/s در همان جهت دارند. این فقط مثال محاسباتی است، نه نتیجهٔ آزمون
یا تضمین سرعت. سقف مشترک لینک، محدودیت مجموع هر IP و ظرفیت سرویس همچنان اعمال
می‌شوند؛ تأخیر، پنجرهٔ دریافت و CPU هم روی نتیجه اثر دارند.

برای اشتراک اتصال‌های transport میان چند برنامه، Mux را این‌گونه قرار دهید:

```text
Server 1: TcpListener -> MuxClient -> ConnectionStripeClient -> TcpConnector
Server 2: TcpListener -> ConnectionStripeServer -> MuxServer -> TcpConnector(service)
```

Mux اتصال‌های برنامه را در جریان‌های parent مشترک جمع می‌کند و Stripe برای
**هر parent یک گروه جدا** می‌سازد. MuxServer پس از بازسازی، برای هر child یک
اتصال مستقل به سرویس باز می‌کند. با `K` parent فعال و `connections: N`، تعداد
اتصال‌های بین دو سرور `K × N` است. حالت Mux، تعداد workerها و تعویض parentها
روی `K` اثر دارند؛ `connections: 8` سقف کل فرایند نیست. childها پنجرهٔ دریافت
گروه خود را نیز به اشتراک می‌گذارند.

برای نمونهٔ کوچک، MuxClient را در حالت `fixed-connections-count` با
`per-worker-connections-count: 1` و یک worker در کلاینت اجرا کنید. برنامه‌ها
از یک parent سالم و قابل‌انتخاب و گروه هشت‌عضوی آن استفاده می‌کنند. بسته‌شدن
عادی یک child، siblingها را نمی‌بندد. کندی یک عضو Stripe می‌تواند همهٔ childهای
همان parent را معطل کند و قطع هر عضو، گروه و childهایش را پایان می‌دهد؛ گروه‌های
دیگر مستقل‌اند.

**Mux اتصال سرویس هر child را پس از اولین payload آن باز می‌کند.** این ترکیب
برای پروتکل‌هایی مانند HTTP مناسب است که کلاینت ابتدا داده می‌فرستد. برای
سرویسی که پیش از ارسال کلاینت پیام خوشامد می‌فرستد، از زنجیرهٔ بدون Mux استفاده
کنید. Mux آدرس مقصد جداگانه برای هر child حمل نمی‌کند؛ این مثال یک سرویس ثابت
دارد. محدودیت‌های مستقل آن در [MuxClient](MuxClient.mdx) آمده‌اند.

برای TLS، در کلاینت `TlsClient` را بعد از StripeClient و در سرور `TlsServer`
را قبل از StripeServer قرار دهید.
[نمونهٔ کامل TLS به انگلیسی](https://radkesvat.github.io/WaterWall-Docs/docs/examples/tunnels/connection-stripe-tls)
تنظیمات کامل با Mux و بدون Mux را نشان می‌دهد.

## تنظیمات

```json
{
  "name": "stripe-client",
  "type": "ConnectionStripeClient",
  "next": "tls-client",
  "settings": {
    "connections": 8
  }
}
```

### فیلدهای اصلی

| فیلد | الزام |
| --- | --- |
| `name` | نام الزامی node که باید در پیکربندی یکتا باشد. |
| `type` | دقیقاً `"ConnectionStripeClient"`. |
| `next` | نام الزامی و غیرخالی node ورودی مسیر transport مشترک. |
| `settings` | شیء الزامی شامل `connections`؛ سایر تنظیمات اختیاری‌اند. |

### تنظیمات node

مقادیر تنظیمات باید عدد صحیح باشند؛ رشته، مقدار اعشاری، boolean و null
پذیرفته نمی‌شوند.

| تنظیم | پیش‌فرض | کاربرد |
| --- | --- | --- |
| `connections` | الزامی | تعداد اعضای گروه هر جریان ورودی (اتصال برنامه یا parent مشترک Mux)، از `1` تا `32`. |
| `receive-window-bytes` | `1048576` | حداکثر بایت مصرف‌نشده‌ای که به همتا اجازهٔ ارسال داده می‌شود؛ از `16384` تا `16777216`. |
| `max-buffered-bytes` | `4194304` | سقف مستقل بایت و هزینهٔ حافظه برای صف برنامه و parser هر عضو؛ از `65536` تا `67108864`. |
| `setup-timeout-ms` | `10000` | مهلت تکمیل گروه، از `1` تا `600000` میلی‌ثانیه. |
| `drain-timeout-ms` | `10000` | مهلت پایان مرتب پروتکل، از `1` تا `600000` میلی‌ثانیه. |
| `max-sessions` | `1024` | حداکثر session هم‌زمان نگه‌داری‌شده روی هر worker، از `1` تا `65536`. |

نام تنظیم ناشناخته یا تکراری باعث رد تنظیمات می‌شود. بررسی انقضا روی worker
با فاصلهٔ یک ثانیه انجام می‌شود؛ مقدار کوچک میلی‌ثانیه دقت زیرثانیه‌ای را تضمین
نمی‌کند. مهلت drain با اولین Finish محلی یا CLOSE همتا آغاز می‌شود و پیشرفت
بعدی آن را تمدید نمی‌کند.

پنجرهٔ دریافت دو طرف می‌تواند متفاوت باشد. هر فرستنده هم پنجرهٔ طرف مقابل و
هم سقف `256` رکورد DATA تأییدنشده را رعایت می‌کند.

## انتخاب تعداد اتصال‌ها و محدودیت‌ها

`connections` برای **هر جریان ورودی** اعمال می‌شود. بدون Mux، مثلاً ۱۰۰ اتصال
فعال برنامه با `connections: 8` به ۸۰۰ اتصال transport نیاز دارند و با
TcpConnector مستقیم در سرور، ۱۰۰ اتصال مقصد ساخته می‌شود. Stripe خودش گروه‌ها
را مشترک نمی‌کند؛ با Mux قبل از Stripe، برنامه‌ها گروه parent خود را به اشتراک
می‌گذارند.
`connections: 1` هم پروتکل Stripe را به کار می‌برد و به `ConnectionStripeServer`
نیاز دارد؛ framing را دور نمی‌زند.

تعداد یک را مبنای مقایسه قرار دهید و سپس تعدادهای بیشتر را با همان بار کاری
مقایسه کنید. افزایش تعداد، handshake و buffering بیشتری دارد؛ پنجرهٔ دریافت
گروه را تغییر نمی‌دهد و افزایش سرعت را تضمین نمی‌کند.

| جهت | تنظیم محدودکنندهٔ اعتبار بایتی اعلام‌شدهٔ گیرنده |
| --- | --- |
| upload: از کلاینت به سرور | `receive-window-bytes` در `ConnectionStripeServer`. |
| download: از سرور به کلاینت | `receive-window-bytes` در `ConnectionStripeClient`. |

پنجرهٔ بایتی برای کل گروه در آن جهت مشترک است و در `connections` ضرب نمی‌شود.
سقف مستقل ۲۵۶ رکورد همچنان برقرار است؛ با رکوردهای کامل ۱۶ KiB، حداکثر ۴ MiB
دادهٔ DATA می‌تواند تأییدنشده بماند، حتی اگر پنجرهٔ بایتی بزرگ‌تر باشد.
`max-buffered-bytes` به‌طور جداگانه دادهٔ محلی ارسال‌نشدهٔ برنامه و parser هر
عضو را محدود می‌کند؛ این تنظیم سقف کل حافظهٔ فرایند نیست.

`max-sessions` گروه‌های هر worker را، از جمله گروه‌های در حال setup یا drain،
می‌شمارد. هر گروه در هر طرف روی یک worker پردازش می‌شود؛ افزودن اعضا، بازچینی
آن گروه را بین workerهای CPU پخش نمی‌کند.

## آغاز، ترتیب و کنترل جریان

آغاز گروه هنگام Init انجام می‌شود و به اولین payload برنامه وابسته نیست.
هر عضو یک JOIN شامل شناسهٔ تصادفی مشترک ۱۲۸ بیتی، اندیس عضو، تعداد اعضا و
پنجرهٔ دریافت می‌فرستد. سرور پس از ورود همهٔ اعضا دقیقاً یک line برنامه می‌سازد.
بدون Mux در مسیر برنامه، پروتکل‌هایی که ابتدا سرور داده می‌فرستد نیز قابل
استفاده‌اند؛ Mux همچنان منتظر اولین payload هر child می‌ماند.
اگر دادهٔ سرور از یک عضو زودتر از READY برسد، در محدودهٔ حافظهٔ دریافت نگه‌داری
می‌شود و تحویل آن به برنامه تا رسیدن READY عقب می‌افتد.

Est transport از آماده‌شدن پروتکل جداست. دادهٔ برنامه در زمان setup در صف
محدود نگه‌داری می‌شود. پس از آماده‌شدن گروه، داده به رکوردهای حداکثر `16384`
بایتی تقسیم و میان اعضای قابل‌نوشتن پخش می‌شود؛ عضو Pauseشده انتخاب نمی‌شود.
گیرنده با offsetها ترتیب اصلی را بازسازی می‌کند. کندی یک عضو می‌تواند تحویل
بایت‌های بعدی را که از اعضای دیگر رسیده‌اند به تأخیر بیندازد.

اعتبار دریافت برای کل گروه محاسبه می‌شود تا وجود یک شکاف باعث رشد نامحدود
حافظه نشود. محدودیت صف دادهٔ برنامه از حافظهٔ دریافت و بازچینی مستقل است.
عبور از سقف سخت حافظه باعث بسته‌شدن session می‌شود، نه حذف بخشی از stream.

## پایان و محدودیت‌ها

Finish کل line برنامه را می‌بندد؛ API جداگانهٔ TCP half-close وجود ندارد.
CLOSE تعداد نهایی بایت‌ها و رکوردها را اعلام می‌کند و همتا پس از تحویل تمام
داده‌های پیشین آن را تأیید می‌کند. گروه transport تا پایان این تخلیهٔ محدود
می‌تواند زنده بماند، ولی دیگر callback به line جداشدهٔ برنامه نمی‌فرستد.
پس از Finish محلی، دادهٔ برگشتی برای line پایان‌یافته مصرف و کنار گذاشته می‌شود.
قطع غیرمنتظرهٔ هر عضو کل session را متوقف می‌کند. بازیابی اتصال یا ارسال مجدد
دادهٔ عضو ازدست‌رفته روی اعضای دیگر انجام نمی‌شود.

چند اتصال می‌تواند به استفادهٔ بهتر از ظرفیت آزاد کمک کند، ولی ظرفیت گلوگاه
مشترک را چندبرابر نمی‌کند. با TcpConnector مستقیم، هر گروه یک اتصال مقصد دارد؛
با MuxServer، هر child اتصال مقصد جداگانه دارد. تقسیم فقط بین دو Stripe node
انجام می‌شود. تعداد بیشتر اعضا socket، TLS و حافظهٔ بیشتری مصرف می‌کند.

شناسهٔ گروه احراز هویت یا رمزنگاری نیست؛ در صورت نیاز، nodeهای امنیتی را در
مسیر transport قرار دهید.

## عیب‌یابی

| نشانه | موارد قابل‌بررسی |
| --- | --- |
| transport متصل می‌شود، ولی برنامه داده‌ای دریافت نمی‌کند | همهٔ اعضا باید پیش از آماده‌شدن گروه به همان سرور Stripe بپیوندند. زنجیرهٔ transport طرف مقابل، `max-connections` سرور، مهلت setup و اتصال مقصد را بررسی کنید. Est در transport به‌تنهایی به معنی آماده‌شدن گروه نیست. |
| افزایش `connections` سرعت را بیشتر نمی‌کند | گلوگاه مشترک، اتصال مقصد، کندترین عضو و مصرف CPU را بررسی کنید. هر گروه یک worker برای بازچینی دارد و از buffer عادی استفاده می‌کند. |
| با قطع یک عضو، برنامه هم بسته می‌شود | سیاست خطا بستن کل گروه است. خطاها و timeoutهای transport همان عضو را بررسی کنید؛ اعضای باقی‌مانده جای آن را نمی‌گیرند. |
| sessionها زیر بار بسته می‌شوند | سقف پذیرش session روی هر worker، محدودیت صف و parser محلی و محدودیت‌های transport مجاور را بررسی کنید. پنجرهٔ دریافت بزرگ‌تر این سقف‌های مستقل را افزایش نمی‌دهد. |

## متادیتای node

مقادیر زیر از `instance/node.c` و ثابت‌های مشترک framing گرفته شده‌اند:

| ویژگی | مقدار |
| --- | --- |
| node flags | `kNodeFlagBlocksSplice` |
| `can_have_prev` | `true` |
| `can_have_next` | `true` |
| `layer_group` | `kNodeLayer4` |
| `layer_group_prev_node` | `kNodeLayer4` |
| `layer_group_next_node` | `kNodeLayer4` |
| `required_padding_left` | `24` بایت (`kStripeHeaderSize`) |

`can_have_next` قابلیت توپولوژی را توصیف می‌کند؛ سازندهٔ این node وجود `next`
را الزامی می‌داند. splice در زنجیره‌های دارای این node غیرفعال است و framing
از buffer عادی استفاده می‌کند.

[نمونهٔ کامل TLS به انگلیسی](https://radkesvat.github.io/WaterWall-Docs/docs/examples/tunnels/connection-stripe-tls)
و فایل‌های آمادهٔ [با Mux](https://github.com/radkesvat/WaterWall/tree/main/tunnels/ConnectionStripeClient/examples/tls-mux)
و [بدون Mux](https://github.com/radkesvat/WaterWall/tree/main/tunnels/ConnectionStripeClient/examples/tls)
در دسترس هستند.
