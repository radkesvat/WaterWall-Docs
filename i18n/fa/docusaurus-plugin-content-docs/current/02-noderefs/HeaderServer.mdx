# HeaderServer



## نمای کلی {#overview}

`HeaderServer` در سمت سرور، header‌های کوچکِ metadata اتصال را می‌خواند. این
گره چهار کار مختلف انجام می‌دهد:

- header دوبایتی port مخصوص WaterWall را از `HeaderClient` می‌خواند و در `dest_context->port` می‌نویسد.
- header تک‌بایتی TCP/UDP مخصوص WaterWall را می‌خواند و پروتکل مقصد را روی TCP یا UDP اعلام‌شده تنظیم می‌کند.
- HAProxy PROXY protocol v1 یا v2 را می‌خواند و IPv4 و port اعلام‌شدهٔ کلاینت را در `src_context` می‌نویسد.
- هنگام `Init` در upstream یک destination port ثابت تنظیم می‌کند.

حالت‌های خواندن header از جریان بایت می‌خوانند. هدر پروتکل، انتقال مقصد خروجی را انتخاب می‌کند. حالت پورت ثابت، جریان بایت و دیتاگرام کامل
را در هر دو جهت حفظ می‌کند.

<a id="جایگاه-رایج"></a>

## جایگاه معمول در زنجیره {#typical-placement}

metadata مربوط به destination port در WaterWall:

```text
client side: TcpListener -> HeaderClient -> TcpConnector
server side: TcpListener -> HeaderServer -> TcpConnector
```

metadata مبدأ از طریق PROXY protocol، با فرستندهٔ قابل اعتماد:

```text
trusted PROXY sender -> TcpListener -> HeaderServer -> TcpConnector
```

destination port ثابت:

```text
TcpListener -> HeaderServer -> TcpConnector
```

حالت PROXY را تنها پس از یک فرستنده قابل اعتماد قرار دهید. اگر کلاینت اینترنتی مستقیم به این گره برسد، می‌تواند header پروتکل PROXY را جعل کند؛ مگر
اینکه proxy یا transport خصوصی جلوی آن را گرفته باشد.

## نمونهٔ کاربردی ساده {#minimal-practical-example}

نمونهٔ نخست شامل آرایه‌های گره‌های کلاینت و سرور است. هر آرایه را به پیکربندی جداگانهٔ خود اضافه کنید و پیش از استفاده، آدرس‌های استقرار را جایگزین کنید.

<a id="مثالهای-کاربردی"></a>

### نمونه‌های کاربردی {#practical-examples}



<a id="برگرداندن-port-اصلی-listener-از-headerclient"></a>

#### بازیابی پورت اصلی listener از HeaderClient {#restore-the-original-listener-port-from-headerclient}

این حالت جفت کلاسیک WaterWall است. instance اول روی چند port عمومی گوش می‌دهد،
اما همه ترافیک را به یک port میانی می‌فرستد. سمت relay، port اصلی اتصال را قبل از انتخاب backend توسط `TcpConnector` برمی‌گرداند.

```json
{
  "name": "header-server",
  "type": "HeaderServer",
  "settings": {
    "override": "dest_context->port"
  },
  "next": "connector"
}
```

`HeaderClient` سمت کلاینتِ متناظر باید از تنظیم زیر استفاده کند:

```json
{
  "name": "header-client",
  "type": "HeaderClient",
  "settings": {
    "data": "src_context->port"
  },
  "next": "relay-connector"
}
```

## پیکربندی {#configuration}



<a id="فیلدهای-لازم"></a>

### فیلدهای لازم {#required-fields}

فیلدهای سطح اصلی:

| فیلد | نوع | توضیح |
| --- | --- | --- |
| `name` | string | نام دلخواه گره که باید در فایل پیکربندی یکتا باشد. |
| `type` | string | باید دقیقاً `"HeaderServer"` باشد. |
| `settings` | object | اجباری است و باید `override` داشته باشد. |
| `next` | string | اجباری است. گره بعدی در لایهٔ ۴ باید نوع payload خروجی این حالت را بپذیرد. |

فیلد لازم داخل `settings`:

| فیلد | نوع | توضیح |
| --- | --- | --- |
| `override` | number یا string | مشخص می‌کند کدام فیلد جایگزین شود و، در صورت وجود، کدام header خوانده شود. |

این گره باید هم گره قبلی داشته باشد و هم `next`. برای ابتدا یا انتهای زنجیره نیست.

### `settings.override` {#settingsoverride}

مقدارهای قابل قبول:

| مقدار | معنی |
| --- | --- |
| `"dest_context->port"` | header دو بایتی upstream مخصوص WaterWall خوانده می‌شود و `dest_ctx.port` تنظیم می‌شود. |
| `"line->dest_ctx->port"` | نام مستعار سازگار با `"dest_context->port"`. |
| `"dest_context->protocol"` | header تک‌بایتی TCP/UDP مخصوص WaterWall خوانده می‌شود و پروتکل مقصد روی TCP یا UDP اعلام‌شده تنظیم می‌شود. |
| `"line->dest_ctx->protocol"` | نام مستعار `"dest_context->protocol"`. |
| `"line-mark"` | ۱۶ بایت خام را می‌خواند و پیش از `Init` بعدی، نشان خط را ثبت می‌کند. |
| `"proxy-protocol->source-fields"` | PROXY protocol v1 یا v2 خوانده می‌شود و `src_ctx.ip` و `src_ctx.port` تنظیم می‌شوند. |
| `1` تا `65535` | این destination port ثابت در upstream `Init` تنظیم می‌شود. |

اگر `override` وجود نداشته باشد، رشته‌ای ناشناخته باشد یا عددی بیرون بازه `1`
تا `65535` داشته باشد، راه‌اندازی شکست می‌خورد.

## کاربرد و رفع اشکال {#usage-and-troubleshooting}



### نمونه‌های بیشتر {#more-examples}



<a id="بازیابی-تنها-هویت-tcpudp"></a>

### بازیابی تنها هویت TCP/UDP {#restore-only-tcpudp-identity}

اگر فرستنده فقط پروتکل را می‌فرستد و آدرس و port مقصد از قبل مشخص هستند، از این حالت استفاده کنید:

```json
{
  "name": "protocol-reader",
  "type": "HeaderServer",
  "settings": {
    "override": "dest_context->protocol"
  },
  "next": "router-or-connector"
}
```

برای transport مقصد مورد نظر فرستنده، آن را با `HeaderClient.data = "dest_context->protocol"` جفت کنید؛ برای transport مبدأ پذیرفته‌شده، از `"src_context->protocol"` استفاده کنید. سرور پیش از مقداردهی اولیهٔ `next` نشانگر را اعمال می‌کند، بدون اینکه آدرس، port یا metadata مبدأ را تغییر دهد.

برای مثال، اگر گره بعدی `TcpUdpConnector` باشد، بایت `17` باعث می‌شود سوکت UDP را انتخاب کند. این بایت مشخص نمی‌کند هر دیتاگرام کجا تمام می‌شود.

اگر فقط می‌خواهید `Router` یک شاخه را انتخاب کند، `line-mark` انتخاب مطمئن‌تری است. قانون Router می‌تواند نشان را تطبیق دهد و جریان TCP را به `UdpOverTcpServer` بفرستد تا دیتاگرام‌ها را بازسازی کند. اگر فقط برای انتخاب همین شاخه، پروتکل مقصد را UDP کنید، این گره اتصال را می‌بندد، چون ورودی TCP می‌خواهد.

<a id="خواندن-source-ip-و-port-از-proxy-protocol"></a>

### خواندن IP و پورت مبدأ از PROXY protocol {#read-source-ip-and-port-from-proxy-protocol}

اگر peer واقعی قبلی HAProxy PROXY protocol می‌فرستد و گره‌های بعدی WaterWall
باید کلاینت اصلی را در `lineGetSourceAddressContext(line)` ببینند، از این حالت
استفاده کنید.

```json
{
  "name": "proxy-source-reader",
  "type": "HeaderServer",
  "settings": {
    "override": "proxy-protocol->source-fields"
  },
  "next": "router-or-connector"
}
```

فرستنده می‌تواند HAProxy، nginx، Envoy یا `HeaderClient` با یکی از مقادیر
`"proxy-protocol"`، `"proxy-protocol-v1"` یا `"proxy-protocol-v2"` باشد.

نمونه فرستنده در WaterWall:

```json
{
  "name": "proxy-header",
  "type": "HeaderClient",
  "settings": {
    "data": "proxy-protocol",
    "frontend-ipv4": "203.0.113.10"
  },
  "next": "relay-connector"
}
```

در این حالت، `HeaderServer` تنها header‌های IPv4 TCP مربوط به PROXY را می‌پذیرد.
header را می‌خواند، source IP و source port را در `src_ctx` می‌نویسد، سپس گره
بعدی upstream را مقداردهی اولیه می‌کند و payload باقی‌مانده پس از header را
می‌فرستد.

<a id="اجبار-به-یک-backend-port"></a>

### تعیین یک پورت ثابت برای backend {#force-one-backend-port}

وقتی همه line‌ها باید یک destination port ثابت داشته باشند و نباید هیچ header‌ای
مصرف شود، از override عددی استفاده کنید.

```json
{
  "name": "force-https",
  "type": "HeaderServer",
  "settings": {
    "override": 443
  },
  "next": "connector"
}
```

در حالت عددی، پیش از این گره یک `HeaderClient` با قابلیت افزودن header قرار ندهید؛ مگر اینکه عمداً بخواهید
آن header به‌عنوان application payload باقی بماند.

<a id="محدودیتها-و-padding"></a>

### محدودیت‌ها و padding {#limits-and-padding}

| مقدار | اندازه |
| --- | --- |
| WaterWall port header | `2 bytes` |
| WaterWall protocol header | `1 byte` |
| حداقل port قابل قبول از WaterWall header | `10` |
| PROXY protocol v1 header | حداکثر `108 bytes` |
| PROXY protocol v2 base header | `16 bytes` |
| address block لازم برای PROXY protocol v2 TCP4 | `12 bytes` |
| `required_padding_left` | `0 bytes` |

سرور فقط header را می‌خواند. بایت جدیدی prepend نمی‌کند و به padding چپ نیاز
ندارد.

<a id="نکتهها"></a>

### نکته‌ها {#notes-and-caveats}

- حالت port-header در WaterWall را همراه با `HeaderClient.data = "src_context->port"` استفاده کنید.
- حالت protocol-header را با `HeaderClient.data = "src_context->protocol"` یا `"dest_context->protocol"` جفت کنید؛ حمل UDP روی TCP به framing جداگانه نیاز دارد.
- حالت PROXY source-fields را تنها با یک فرستنده قابل اعتماد PROXY به کار ببرید.
- حالت PROXY source-fields فعلاً فقط IPv4 را پشتیبانی می‌کند.
- حالت PROXY source-fields فقط `src_ctx` را به‌روز می‌کند و `dest_ctx` را تغییر نمی‌دهد.
- تا پیش از دریافت header، `HeaderServer` گره بعدی را مقداردهی اولیه نکرده است.
- نباید به‌عنوان state مشترک packet-line استفاده شود.

## رفتار پیشرفته {#advanced-behavior}



<a id="حالت-waterwall-port-header"></a>

### حالت سربرگ پورت WaterWall {#waterwall-port-header-mode}

وقتی `override` برابر `"dest_context->port"` یا `"line->dest_ctx->port"` باشد،
`HeaderServer` منتظر دو بایت نخست upstream می‌ماند. این دو بایت به‌عنوان port
با ترتیب big-endian decode می‌شوند و در فیلد زیر نوشته می‌شوند:

```text
lineGetDestinationAddressContext(line)->port
```

`Init` در upstream عمداً تا زمان decode شدن header به تأخیر می‌افتد. بایت‌های
payload در `buffer_stream_t` نگه داشته می‌شوند، بنابراین header دوبایتی می‌تواند
در چند callbackِ payload تکه‌تکه دریافت شود.

port‌های decodeشده کمتر از `10` رد می‌شوند تا رفتار محافظه‌کارانه قدیمی این تونل
حفظ شود.

<a id="حالت-waterwall-protocol-header"></a>

### حالت سربرگ پروتکل WaterWall {#waterwall-protocol-header-mode}

با تنظیم `"override": "dest_context->protocol"` یا نام معادل `"line->dest_ctx->protocol"`، سرور بایت `6` را TCP و بایت `17` را UDP می‌خواند و همان انتقال دقیق را پیش از `Init` بعدی در مقصد ثبت می‌کند. اطلاعات مبدأ، نشانی و پورت مقصد و سایر فراداده‌ها حفظ می‌شوند. هدر پروتکل طول دیتاگرام را حمل نمی‌کند. بایت نامعتبر خط را پیش از `Init` بعدی می‌بندد.

### هدر نشان خط

برای دریافت نشان، `"settings": {"override": "line-mark"}` را با `HeaderClient` دارای `"data": "line-mark"` جفت کنید. سرور ورود همهٔ ۱۶ بایت خام، از جمله بایت صفر، را حتی طی چند تحویل منتظر می‌ماند. سپس پیش از `Init` بعدی نشان خط را تنظیم می‌کند و بایت‌های بعد از هدر را به ترتیب تحویل می‌دهد. حامل TCP می‌ماند. Router می‌تواند با نشان خط جریان قاب‌بندی‌شده را به رمزگشای آن بفرستد.

<a id="حالت-proxy-protocol-source-fields"></a>

### حالت فیلدهای مبدأ PROXY protocol {#proxy-protocol-source-fields-mode}

اگر `override` برابر `"proxy-protocol->source-fields"` باشد، نخستین بایت‌های
upstream باید یک header معتبر HAProxy PROXY protocol v1 یا v2 باشند. اگر header
وجود نداشته باشد، malformed باشد، از نوع IPv4 نباشد یا فیلدهای source را نداشته
باشد، `HeaderServer` خطایی در لاگ ثبت می‌کند و اتصال را می‌بندد.

header‌های قابل قبول:

| header | فرم قابل قبول |
| --- | --- |
| PROXY v1 | `PROXY TCP4 <source-ip> <dest-ip> <source-port> <dest-port>\r\n` |
| PROXY v2 | version 2، command برابر `PROXY`، family/transport برابر `TCP4` |

موارد رد شده:

- PROXY v1 `UNKNOWN`
- PROXY v1 `TCP6`
- PROXY v2 `LOCAL`
- PROXY v2 `UNSPEC`، `TCP6`، `UDP4`، `UDP6` یا هر family پشتیبانی‌نشده
- header‌های malformed یا بیش از حد بزرگ

فقط این فیلدها اعمال می‌شوند:

```text
lineGetSourceAddressContext(line)->ip_address = PROXY source IPv4
lineGetSourceAddressContext(line)->port       = PROXY source port
lineGetSourceAddressContext(line)->proto_tcp  = true
```

فیلدهای destination، TLVها و دیگر فیلدهای PROXY خوانده می‌شوند، اما نادیده گرفته
می‌شوند. IPv6 در این mode پشتیبانی نمی‌شود. `peer_source_port` بازنویسی نمی‌شود.

حداکثر طول PROXY v1 برابر `108` بایت است. PROXY v2 تمام record، از جمله TLVها، را می‌خواند ولی وجود address block ثابت TCP4 را لازم دارد.

<a id="حالت-constant-override"></a>

### حالت جایگزینی ثابت {#constant-override-mode}

اگر `override` عدد باشد، `HeaderServer` هیچ header‌ای از payload نمی‌خواند و چیزی
را حذف نمی‌کند.

در upstream `Init` این مقدار تنظیم می‌شود:

```text
lineGetDestinationAddressContext(line)->port = configured port
```

سپس `Init` بی‌درنگ در upstream به `next` فرستاده می‌شود و تمام payload‌های upstream
بدون تغییر عبور می‌کنند.

## جزئیات پیاده‌سازی {#implementation-details}



### ترتیب راه‌اندازی و کنار رفتن از مسیر {#startup-ordering-and-bypass}

`HeaderServer` وضعیت مسیر ادامه را پیش از فراخوانی Init گره بعدی ثبت می‌کند؛ بنابراین Est همگام transport بلافاصله، حتی در صورت تکرار،
منتقل می‌شود. ورودی re-entrant از Init، Est یا replay اولیه پشت بایت‌های قدیمی‌تر می‌ماند. صف موقت ترتیب
به 2 MiB بایت منطقی و 8 MiB هزینهٔ صف محدود است و در همان dispatch همگام تخلیه می‌شود؛ مسیر عادی مستقیم صفی نگه نمی‌دارد.
سرریز، line از نوع borrowed را از طریق owner می‌بندد.

پس از بازگشت Init بعدی و پایان replay صف اولیه، گره همهٔ state محلی را آزاد و صفر می‌کند و برای همیشه روی آن line از مسیر callbackها کنار می‌رود. در حالت port ثابت، این bypass بلافاصله پس از تنظیم port و پیش از ارسال Init انجام می‌شود. پس از مقداردهی اولیهٔ سمت بعدی، Pause/Resume شفاف و تکرارپذیر هستند و replay اولیه را متوقف نمی‌کنند.

<a id="رفتار-جهتها"></a>

### رفتار جهت‌ها {#direction-behavior}

| جهت | رفتار در حالت‌های header تأخیری |
| --- | --- |
| upstream `Init` | state محلی مقداردهی اولیه می‌شود، اما ارسال init به `next` تا decode شدن header تنظیم‌شده عقب می‌افتد. |
| upstream payload قبل از header | تا کامل شدن header تنظیم‌شده buffer می‌شود. |
| upstream payload بعد از header | به `next` فرستاده می‌شود. |
| upstream pause/resume قبل از header | نادیده گرفته می‌شود؛ سمت `next` هنوز مقداردهی اولیه نشده است. |
| upstream pause/resume بعد از header | به `next` فرستاده می‌شود. |
| downstream `Est` / pause / resume قبل از header | نادیده گرفته می‌شود. |
| downstream payload قبل از header | buffer‌ش برای استفاده مجدد برگردانده و سمت قبلی بسته می‌شود. |
| downstream callbacks بعد از header | به گره قبلی فرستاده می‌شود. |

در حالت مقدار ثابت، line با `Init` در upstream برقرار می‌شود؛ بنابراین callback‌های
upstream و downstream به شکل معمول و در جهت خود عبور داده می‌شوند.

callback‌های `UpStreamEst` و `DownStreamInit` برای این گره غیرفعال هستند.

<a id="finish"></a>

### رفتار Finish {#finish-behavior}

پس از bypass، Finish مستقیماً به گره فعال بعدی در همان جهت می‌رسد. پاک‌سازی زیر تا پیش از پایان مسیریابی header و replay اولیه اعمال می‌شود.

با دریافت `Finish` در upstream، `HeaderServer` state محلی را از بین می‌برد. Finish
تنها زمانی به `next` فرستاده می‌شود که خواندن header مسیریابی کامل شده و سمت `next`
قبلاً مقداردهی اولیه شده باشد.

با دریافت `Finish` در downstream، state محلی از بین می‌رود و finish به گره قبلی
فرستاده می‌شود.

در صورت خطای پروتکل، state محلی از بین می‌رود. اگر `next` قبلاً مقداردهی اولیه شده
باشد آن سمت بسته می‌شود و سپس سمت قبلی نیز بسته خواهد شد.

چون این تونل سازنده line نیست، `lineDestroy()` را فراخوانی نمی‌کند.

<a id="پشتیبانی-از-splice"></a>

### پشتیبانی از splice {#splice-support}

`HeaderServer` پرچم `kNodeFlagSupportsSplice` را دارد. هنگام انتظار برای header
پورت، پروتکل TCP/UDP یا PROXY protocol، کل payload دریافتی را با `sbufEnsureOrdinary()` به حافظهٔ
عادی تبدیل می‌کند و سپس به BufferStream می‌دهد. بایت‌های application همراه header
حفظ می‌شوند. پس از تکمیل header، هر دو جهت و صف محدود reentry، buffer‌های splice
را بدون تبدیل عبور می‌دهند. حالت پورت ثابت به خواندن payload نیاز ندارد.

برای parsing موقت، ترجیح خواندن عادی تنظیم نمی‌شود؛ این ترجیح تا پایان line باقی
می‌ماند و خواندن splice بعدی را هم غیرفعال می‌کند.
