# HeaderServer

`HeaderServer` reader سمت server برای headerهای کوچک metadata اتصال است. این
نود سه کار مختلف انجام می‌دهد:

- header دو بایتی port مخصوص WaterWall را از `HeaderClient` مصرف می‌کند و داخل `dest_context->port` می‌نویسد
- HAProxy PROXY protocol v1 یا v2 را مصرف می‌کند و IPv4 و port واقعی client را داخل `src_context` می‌نویسد
- در upstream `Init` یک destination port ثابت تنظیم می‌کند

این نود یک tunnel عادی layer-4 stream است. socket باز نمی‌کند، packet line
نمی‌سازد و `line_t` ایجاد نمی‌کند.

## جایگاه رایج

metadata مربوط به destination port در WaterWall:

```text
client side: TcpListener -> HeaderClient -> TcpConnector
server side: TcpListener -> HeaderServer -> TcpConnector
```

metadata مربوط به source از طریق PROXY protocol و از سمت sender قابل اعتماد:

```text
trusted PROXY sender -> TcpListener -> HeaderServer -> TcpConnector
```

destination port ثابت:

```text
TcpListener -> HeaderServer -> TcpConnector
```

mode مربوط به PROXY را فقط پشت sender قابل اعتماد استفاده کنید. اگر client خام
اینترنتی مستقیم به این نود برسد، می‌تواند header پروتکل PROXY را جعل کند؛ مگر
اینکه proxy یا transport خصوصی جلوی آن را گرفته باشد.

## مثال‌های کاربردی

### برگرداندن port اصلی listener از HeaderClient

این حالت pair کلاسیک WaterWall است. instance اول روی چند public port گوش می‌دهد
ولی همه ترافیک را به یک relay port می‌فرستد. سمت relay، port اصلی پذیرفته‌شده
را قبل از انتخاب backend توسط `TcpConnector` برمی‌گرداند.

```json
{
  "name": "header-server",
  "type": "HeaderServer",
  "settings": {
    "override": "dest_context->port"
  },
  "next": "connector"
}
```

`HeaderClient` سمت مقابل معمولا این تنظیم را دارد:

```json
{
  "name": "header-client",
  "type": "HeaderClient",
  "settings": {
    "data": "src_context->port"
  },
  "next": "relay-connector"
}
```

### خواندن source IP و port از PROXY protocol

وقتی peer واقعی قبلی HAProxy PROXY protocol می‌فرستد و nodeهای بعدی WaterWall
باید client اصلی را در `line->routing_context.src_ctx` ببینند، از این mode
استفاده کنید.

```json
{
  "name": "proxy-source-reader",
  "type": "HeaderServer",
  "settings": {
    "override": "proxy-protocol->source-fields"
  },
  "next": "router-or-connector"
}
```

sender می‌تواند HAProxy، nginx، Envoy یا `HeaderClient` با یکی از مقدارهای
`"proxy-protocol"`، `"proxy-protocol-v1"` یا `"proxy-protocol-v2"` باشد.

نمونه sender در WaterWall:

```json
{
  "name": "proxy-header",
  "type": "HeaderClient",
  "settings": {
    "data": "proxy-protocol",
    "frontend-ipv4": "203.0.113.10"
  },
  "next": "relay-connector"
}
```

در این mode، `HeaderServer` فقط headerهای IPv4 TCP مربوط به PROXY را قبول
می‌کند. header را مصرف می‌کند، source IP و source port را داخل `src_ctx` می‌نویسد،
بعد نود upstream بعدی را initialize می‌کند و payload باقی‌مانده بعد از header را
forward می‌کند.

### اجبار به یک backend port

وقتی همه lineها باید یک destination port ثابت داشته باشند و نباید هیچ headerی
مصرف شود، از override عددی استفاده کنید.

```json
{
  "name": "force-https",
  "type": "HeaderServer",
  "settings": {
    "override": 443
  },
  "next": "connector"
}
```

قبل از mode عددی، `HeaderClient` headerنویس قرار ندهید؛ مگر اینکه عمدا بخواهید
آن header به عنوان application payload باقی بماند.

## فیلدهای لازم

فیلدهای top-level:

| فیلد | نوع | توضیح |
| --- | --- | --- |
| `name` | string | نام دلخواه و یکتا برای node. |
| `type` | string | باید دقیقا `"HeaderServer"` باشد. |
| `settings` | object | اجباری است و باید `override` داشته باشد. |
| `next` | string | نود layer-4 stream بعدی که line route شده را دریافت می‌کند. |

فیلد لازم داخل `settings`:

| فیلد | نوع | توضیح |
| --- | --- | --- |
| `override` | number یا string | مشخص می‌کند چه فیلدی override شود و چه headerی، اگر وجود دارد، مصرف شود. |

این نود باید هم نود قبلی داشته باشد و هم `next`. برای ابتدا یا انتهای chain نیست.

## `settings.override`

مقدارهای قابل قبول:

| مقدار | معنی |
| --- | --- |
| `"dest_context->port"` | header دو بایتی upstream مخصوص WaterWall خوانده می‌شود و `dest_ctx.port` تنظیم می‌شود. |
| `"line->dest_ctx->port"` | alias سازگار با `"dest_context->port"`. |
| `"proxy-protocol->source-fields"` | PROXY protocol v1 یا v2 خوانده می‌شود و `src_ctx.ip` و `src_ctx.port` تنظیم می‌شوند. |
| `1` تا `65535` | این destination port ثابت در upstream `Init` تنظیم می‌شود. |

اگر `override` وجود نداشته باشد، string ناشناخته باشد، یا عدد خارج از بازه `1`
تا `65535` باشد، startup شکست می‌خورد.

## حالت WaterWall Port Header

وقتی `override` برابر `"dest_context->port"` یا `"line->dest_ctx->port"` باشد،
`HeaderServer` منتظر دو byte اول upstream می‌ماند. این دو byte به عنوان port
big-endian decode می‌شوند و داخل این فیلد نوشته می‌شوند:

```text
line->routing_context.dest_ctx.port
```

upstream `Init` عمدا تا زمان decode شدن header به تاخیر می‌افتد. byteهای payload
داخل `buffer_stream_t` نگه داشته می‌شوند، بنابراین header دو بایتی می‌تواند بین
چند payload callback split شده باشد.

portهای decode شده کمتر از `10` رد می‌شوند تا رفتار conservative قدیمی این tunnel
حفظ شود.

## حالت PROXY Protocol Source-Fields

وقتی `override` برابر `"proxy-protocol->source-fields"` باشد، اولین byteهای
upstream باید یک header معتبر HAProxy PROXY protocol v1 یا v2 باشند. اگر header
وجود نداشته باشد، malformed باشد، IPv4 نباشد، یا source fields نداشته باشد،
`HeaderServer` با log سطح error اتصال را می‌بندد.

headerهای قابل قبول:

| Header | فرم قابل قبول |
| --- | --- |
| PROXY v1 | `PROXY TCP4 <source-ip> <dest-ip> <source-port> <dest-port>\r\n` |
| PROXY v2 | version 2، command برابر `PROXY`، family/transport برابر `TCP4` |

موارد رد شده:

- PROXY v1 `UNKNOWN`
- PROXY v1 `TCP6`
- PROXY v2 `LOCAL`
- PROXY v2 `UNSPEC`، `TCP6`، `UDP4`، `UDP6` یا هر family پشتیبانی‌نشده
- headerهای malformed یا بیش از حد بزرگ

فقط این فیلدها اعمال می‌شوند:

```text
line->routing_context.src_ctx.ip_address = PROXY source IPv4
line->routing_context.src_ctx.port       = PROXY source port
line->routing_context.src_ctx.protocol   = TCP
```

destination fields، TLVها و بقیه فیلدهای PROXY مصرف می‌شوند ولی نادیده گرفته
می‌شوند. IPv6 در این mode پشتیبانی نمی‌شود. `peer_source_port` بازنویسی نمی‌شود.

PROXY v1 حداکثر `108` byte است. PROXY v2 تمام طول record را، از جمله TLVها، مصرف
می‌کند ولی وجود address block ثابت TCP4 را لازم دارد.

## حالت Constant Override

وقتی `override` عدد باشد، `HeaderServer` هیچ headerی از payload نمی‌خواند یا حذف
نمی‌کند.

در upstream `Init` این مقدار تنظیم می‌شود:

```text
line->routing_context.dest_ctx.port = configured port
```

سپس upstream `Init` بلافاصله به `next` forward می‌شود و تمام upstream payloadها
بدون تغییر عبور می‌کنند.

## رفتار جهت‌ها

| جهت | رفتار در modeهای header تاخیری |
| --- | --- |
| upstream `Init` | state محلی initialize می‌شود، اما init به `next` تا زمان decode شدن header تنظیم‌شده delay می‌شود. |
| upstream payload قبل از header | تا کامل شدن header تنظیم‌شده buffer می‌شود. |
| upstream payload بعد از header | به `next` forward می‌شود. |
| upstream pause/resume قبل از header | ignore می‌شود؛ هنوز سمت `next` initialize نشده است. |
| upstream pause/resume بعد از header | به `next` forward می‌شود. |
| downstream `Est` / pause / resume قبل از header | ignore می‌شود. |
| downstream payload قبل از header | recycle می‌شود و سمت قبلی بسته می‌شود. |
| downstream callbacks بعد از header | به نود قبلی forward می‌شود. |

در constant mode، line در upstream `Init` established می‌شود؛ بنابراین callbackهای
upstream و downstream به شکل معمول و جهت‌دار forward می‌شوند.

callbackهای `UpStreamEst` و `DownStreamInit` برای این نود غیرفعال هستند.

## Finish

در upstream `Finish`، `HeaderServer` state محلی را destroy می‌کند. finish فقط وقتی
به `next` forward می‌شود که header routing کامل شده و سمت `next` قبلا initialize
شده باشد.

در downstream `Finish`، state محلی destroy می‌شود و finish به نود قبلی forward
می‌شود.

در protocol error، state محلی destroy می‌شود، اگر `next` قبلا initialize شده باشد
آن سمت بسته می‌شود، و سمت قبلی هم بسته می‌شود.

این tunnel چون line را خودش نمی‌سازد، `lineDestroy()` صدا نمی‌زند.

## محدودیت‌ها و Padding

| مقدار | اندازه |
| --- | --- |
| WaterWall port header | `2 bytes` |
| حداقل port قابل قبول از WaterWall header | `10` |
| PROXY protocol v1 header | حداکثر `108 bytes` |
| PROXY protocol v2 base header | `16 bytes` |
| address block لازم برای PROXY protocol v2 TCP4 | `12 bytes` |
| `required_padding_left` | `0 bytes` |

server فقط header مصرف می‌کند. byte جدید prepend نمی‌کند و به padding چپ نیاز
ندارد.

## نکته‌ها

- WaterWall port-header mode را با `HeaderClient.data = "src_context->port"` استفاده کنید.
- PROXY source-fields mode را با یک sender قابل اعتماد PROXY استفاده کنید.
- PROXY source-fields mode فعلا فقط IPv4 است.
- PROXY source-fields mode فقط `src_ctx` را update می‌کند؛ `dest_ctx` را بازنویسی نمی‌کند.
- تا قبل از دریافت header، `HeaderServer` نود بعدی را initialize نکرده است.
- نباید به عنوان state مشترک packet-line استفاده شود.
