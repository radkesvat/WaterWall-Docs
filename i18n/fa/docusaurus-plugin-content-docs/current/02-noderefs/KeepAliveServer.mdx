# KeepAliveServer



## نمای کلی {#overview}

`KeepAliveServer` بخش سرور `KeepAliveClient` است. فریم‌های keepalive را که از کلاینت و در جهت upstream می‌رسند decode می‌کند، payload‌های عادی را به `next` می‌فرستد، به فریم ping با pong پاسخ می‌دهد و payload‌های downstream را در همان قالب فریم قرار می‌دهد.

این گره را فقط به‌عنوان peer متناظر `KeepAliveClient` به کار ببرید. ورودی upstream آن باید فریم‌شده باشد و به‌تنهایی بایت‌های معمولی و بدون فریم payload را تشخیص نمی‌دهد.

`KeepAliveServer` یک تونل عادی و قابل ترکیب است. socket یا object‌ای از نوع `line_t` نمی‌سازد، line را آزاد نمی‌کند و timer دوره‌ای ندارد.

<a id="جایگاه-رایج"></a>

## جایگاه معمول در زنجیره {#typical-placement}

جفت مستقیم داخل یک process:

```text
TesterClient -> KeepAliveClient -> KeepAliveServer -> TesterServer
```

چیدمان TCP روی دو سرور:

```text
client side: TcpListener -> KeepAliveClient -> TcpConnector
server side: TcpListener -> KeepAliveServer -> TcpConnector
```

هر تونل میان کلاینت و سرور باید بایت‌های فریم keepalive را بدون تغییر عبور دهد.

## نمونهٔ کاربردی ساده {#minimal-practical-example}

این‌ها قطعه‌های پیکربندی گره هستند؛ گره‌های مجاورِ ارجاع‌شده را در پیکربندی پیرامون آن‌ها تعریف کنید.

<a id="نمونه-تنظیم"></a>

### نمونهٔ پیکربندی {#configuration-example}

```json
{
  "name": "ka-server",
  "type": "KeepAliveServer",
  "settings": {},
  "next": "service"
}
```

سمت کلاینت متناظر:

```json
{
  "name": "ka-client",
  "type": "KeepAliveClient",
  "settings": {
    "ping-interval": 60000
  },
  "next": "transport"
}
```

## پیکربندی {#configuration}



<a id="فیلدهای-اجباری"></a>

### فیلدهای اجباری {#required-fields}

فیلدهای سطح اصلی:

| فیلد | نوع | توضیح |
| --- | --- | --- |
| `name` | string | نام یکتای گره در config. |
| `type` | string | باید دقیقاً `"KeepAliveServer"` باشد. |
| `settings` | object | اختیاری. پیاده‌سازی فعلی تنظیم اختصاصی برای سرور ندارد. |
| `next` | string | در استفاده عادی اجباری است. گره بعدی payload‌های decodeشده upstream را می‌گیرد. |

`KeepAliveServer` باید گره قبلی داشته باشد و توسط `KeepAliveClient` متناظر قابل دسترس باشد.

<a id="تنظیمات"></a>

### تنظیمات {#settings}

`KeepAliveServer` در حال حاضر تنظیم معنی‌داری ندارد. زمان‌بندی keepalive در `KeepAliveClient` با `settings.ping-interval` تنظیم می‌شود.

## کاربرد و رفع اشکال {#usage-and-troubleshooting}



<a id="یادداشتهای-buffer-و-padding"></a>

### نکته‌های buffer و padding {#buffer-and-padding-notes}

`KeepAliveServer` هنگام encode کردن payload‌های downstream، prefix پنج‌بایتی frame را prepend می‌کند، بنابراین metadata این گره چنین است:

```text
required_padding_left = 5
layer_group = kNodeLayer4
layer_group_next_node = kNodeLayer4
layer_group_prev_node = kNodeLayer4
```

caller باید padding کافی در سمت چپ برای prefix فراهم کند؛ Debug این پیش‌شرط را assert می‌کند. محاسبه padding در زنجیره این فضای اعلام‌شده را رزرو می‌کند.

<a id="نکتههای-عملی"></a>

### نکته‌های عملی {#practical-notes}

- این گره را با `KeepAliveClient` جفت کنید؛ به‌تنهایی مفید نیست.
- فریم‌های ping و pong داخلی جفت KeepAlive هستند و به‌عنوان payload به گره‌های اطراف داده نمی‌شوند.
- سرور به ping‌ها پاسخ می‌دهد، اما health سمت client را اندازه نمی‌گیرد یا pong timeout اعمال نمی‌کند.
- این گره بایت‌های payload را رمزنگاری، احراز هویت، فشرده یا بازنویسی نمی‌کند.
- برای استفادهٔ مطمئن، transport باید بایت‌های فریم‌شده را بین کلاینت و سرور بدون تغییر نگه دارد.

## رفتار پیشرفته {#advanced-behavior}



<a id="فرمت-frame"></a>

### قالب فریم {#frame-format}

سرور از همان prefix پنج‌بایتی client استفاده می‌کند:

| بایت‌ها | فیلد | توضیح |
| --- | --- | --- |
| `0..3` | طول بدنه | عدد صحیح unsigned و 32-bit با ترتیب big-endian. این طول شامل بایت type فریم به‌علاوه بایت‌های payload است. |
| `4` | نوع فریم | `1` payload عادی، `2` ping، یا `3` pong. |

نوع‌های frame:

| نوع | معنی | payload بدنه |
| ---: | --- | --- |
| `1` | payload عادی | بایت‌های payload اصلی WaterWall. |
| `2` | ping | در ترافیک keepalive عادی خالی است. |
| `3` | pong | پاسخ خالی به یک ping frame. |

طول body شامل بایت kind هم می‌شود. هر فریم عادی حداکثر `1 MiB` (`1,048,576 bytes`) payload دارد و حداکثر طول بدنه `1,048,577` است. payload‌های downstream بزرگ‌تر به چند فریم تقسیم می‌شوند. هر دو peer از همین prefix پنج‌بایتی استفاده می‌کنند.

## جزئیات پیاده‌سازی {#implementation-details}



<a id="این-نود-چه-میکند"></a>

### کارکرد گره {#what-it-does}

- با دریافت `Init` در upstream، state محلی line را مقداردهی اولیه می‌کند.
- header فریم‌های upstream را اعتبارسنجی می‌کند و بایت‌های آمادهٔ payload عادی را تدریجی می‌فرستد.
- فریم‌های عادی upstream را decode و payload آن‌ها را به `next` می‌فرستد.
- به فریم ping در upstream، با فرستادن فریم pong در downstream پاسخ می‌دهد.
- pong frame‌های upstream را نادیده می‌گیرد.
- فریم‌های عادی خالی و type‌های ناشناخته را دور می‌اندازد.
- payload‌های downstream را به‌عنوان keepalive frame عادی encode می‌کند و به گره قبلی می‌فرستد.
- payload‌های downstream بزرگ‌تر از `1 MiB` را به چند frame عادی تقسیم می‌کند.
- state محلی line را از بین می‌برد و `Finish` را در همان جهت منتشر می‌کند.

سرور timer جداگانه‌ای برای keepalive ندارد؛ `KeepAliveClient` مسئول ساخت ping‌های دوره‌ای است.

<a id="رفتار-جهتها"></a>

### رفتار جهت‌ها {#direction-behavior}

| callback ورودی | رفتار |
| --- | --- |
| upstream `Init` | buffer خواندن را مقداردهی اولیه می‌کند و سپس `Init` را به `next` می‌فرستد. |
| upstream `Payload` | بایت‌ها را ورودی فریم‌شده `KeepAliveClient` در نظر می‌گیرد و payload‌های عادی decodeشده را به `next` می‌فرستد. |
| upstream `Est` / `Pause` / `Resume` | به `next` فرستاده می‌شوند. |
| upstream `Finish` | state محلی را از بین می‌برد و سپس `Finish` را به `next` می‌فرستد. |
| downstream `Payload` | payload را در یک یا چند فریم عادی encode و به گره قبلی ارسال می‌کند. buffer payload‌های خالی برای استفاده مجدد برمی‌گردد. |
| downstream `Est` / `Pause` / `Resume` | به گره قبلی فرستاده می‌شوند. |
| downstream `Finish` | state محلی را از بین می‌برد و سپس `Finish` را به گره قبلی می‌فرستد. |
| downstream `Init` | غیرفعال؛ رسیدن به این callback به‌عنوان زنجیره flow نامعتبر fatal در نظر گرفته می‌شود. |

<a id="پردازش-ورودی-framed"></a>

### پردازش ورودی قاب‌بندی‌شده {#framed-input-handling}

بایت‌های upstream در یک `splice_stream_t` جمع می‌شوند؛ بنابراین ممکن است یک فریم در چند callbackِ payload تکه‌تکه برسد یا چند فریم در یک callback دریافت شوند.

رفتار decoder:

- فقط برای prefix ناقص یا بخش نرسیدهٔ body منتظر ورودی بعدی می‌ماند و کنترل را به worker برمی‌گرداند.
- اگر طول body فریم خارج از بازهٔ `1..1,048,577` باشد، line از طریق owner بسته می‌شود
- فریم‌های عادی خالی دور ریخته می‌شوند.
- type‌های ناشناخته فریم دور ریخته می‌شوند.
- بایت‌های آمادهٔ body ابتدا تخلیه می‌شوند؛ اگر پس از compaction هزینهٔ تخصیص همچنان بیش از سقف باشد، line بسته می‌شود

<a id="پشتیبانی-از-splice"></a>

### پشتیبانی از splice {#splice-support}

`KeepAliveServer` پرچم `kNodeFlagSupportsSplice` را دارد. framing در تمام طول اتصال ادامه
دارد. decoder در upstream از cache پنج‌بایتی سربرگ `splice_stream_t` استفاده می‌کند و encoder در downstream فقط
header پنج‌بایتی را در padding واقعی سمت چپ می‌نویسد. بدنهٔ payload می‌تواند در pipe
باقی بماند. payload بزرگ‌تر از 1 MiB با عملیات range متناسب با نوع buffer تقسیم می‌شود. شکست تخصیص pipe یا فشار ظرفیت می‌تواند fallback کامل به buffer عادی
ایجاد کند. فریم‌های کنترلی Pong از buffer عادی استفاده می‌کنند.

پس از اعتبارسنجی header، بایت‌های عادی برنامه به‌محض رسیدن فرستاده می‌شوند و
گیرنده منتظر کامل‌شدن body نمی‌ماند. یک فریم ممکن است چند callback از نوع
Payload تولید کند. اگر اتصال وسط فریم بسته شود، پیشوندی که قبلاً تحویل شده
پس گرفته نمی‌شود. body فریم کنترلی تدریجی دور ریخته می‌شود، اما اثر Ping/Pong
فقط پس از مصرف همهٔ body اعلام‌شده اعمال می‌شود.

ورودی re-entrant encoder پشت suffix فعال می‌ماند و مجموع آن‌ها به 8 MiB بایت منطقی
و 16 MiB هزینهٔ صف، با احتساب suffix فعال، محدود است. decoder ورودی nested را به ترتیب پردازش می‌کند؛ بایت‌های
nested سقف 8 MiB و هزینهٔ تخصیص باقی‌مانده سقف 16 MiB دارند. پیش از رد هزینهٔ اضافی،
ابتدا compaction به buffer عادی، در صورت کاهش هزینه، امتحان می‌شود. بایت‌های آمادهٔ body پیش از بررسی
هزینهٔ نگهداری تخلیه می‌شوند. اعتبارسنجی طول فریم تضمین می‌کند که remainder ناقص، با احتساب header،
کوچک‌تر از 1 MiB + 5 بایت باشد. Pause فوری منتقل می‌شود و
پردازش batch همگامِ پذیرفته‌شده را قطع نمی‌کند. Pause و Resume تکراری نیز شفاف منتقل
می‌شوند و Pong آماده منتظر Resume نمی‌ماند. parser ورودی Ping بازگشتی را پشت پاسخ
فعال و با همان محدودیت‌های ذخیره‌سازی نگه می‌دارد؛ صف مستقلی برای Pong وجود ندارد.
framing تا پایان اتصال لازم است؛ بنابراین این گره فعال می‌ماند و bypass دائمی نمی‌شود.

طول بدنهٔ صفر یا بیش از 1 MiB + 1، شکست admission یا سرریز ذخیره‌سازی، line از نوع borrowed را
از طریق owner می‌بندد. Finish، فریم ناقص، suffix فعال encoder و صف ورودی re-entrant
را آزاد می‌کند؛ این گره خودش `line_t` را destroy نمی‌کند.
