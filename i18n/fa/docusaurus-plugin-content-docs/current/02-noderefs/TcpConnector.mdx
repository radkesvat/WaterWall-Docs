# TcpConnector

`TcpConnector` نود خروجی TCP است. این نود در upstream `Init` مقصد را از تنظیمات خودش یا از routing context خط انتخاب می‌کند، socket TCP می‌سازد، به مقصد connect می‌کند و payload را بین نود قبلی و remote server جابه‌جا می‌کند.

این نود معمولا انتهای زنجیر است و `next` لازم ندارد.

## نمونه تنظیم ساده

```json
{
  "name": "outbound-tcp",
  "type": "TcpConnector",
  "settings": {
    "address": "example.com",
    "port": 443,
    "nodelay": true,
    "fastopen": false,
    "reuseaddr": false,
    "fwmark": 10,
    "interface": "eth0",
    "source-ip": "192.0.2.10",
    "domain-strategy": "prefer-ipv4"
  }
}
```

## نمونه چند مقصد weighted

```json
{
  "name": "outbound-tcp",
  "type": "TcpConnector",
  "settings": {
    "addresses": [
      {
        "address": "192.0.2.10",
        "port": 443,
        "weight": 5
      },
      {
        "address": "198.51.100.20",
        "port": "dest_context->port",
        "weight": 1
      }
    ],
    "nodelay": true
  }
}
```

## تنظیم مقصد

باید دقیقا یکی از این دو سبک را انتخاب کنید:

- `address` + `port`
- `addresses`

این دو سبک را با هم ترکیب نکنید.

| گزینه | توضیح |
|---|---|
| `address` | مقصد ثابت یا context-based |
| `port` | پورت ثابت یا context-based |
| `addresses` | آرایه مقصدهای weighted |

مقدارهای معتبر برای `address`:

- IPv4 ثابت، مثل `93.184.216.34`
- IPv6 ثابت
- domain ثابت، مثل `example.com`
- `src_context->address`
- `dest_context->address`

مقدارهای معتبر برای `port`:

- عدد ثابت، مثل `443`
- `src_context->port`
- `dest_context->port`

:::warning
در نسخه فعلی `TcpConnector`، فرم `random(x,y)` برای `port` پشتیبانی نمی‌شود.
:::

## addresses

`addresses` آرایه‌ای از مقصدهاست. هر entry باید این فیلدها را داشته باشد:

| فیلد | توضیح |
|---|---|
| `address` | همان فرم‌های معتبر `address` |
| `port` | همان فرم‌های معتبر `port` |
| `weight` | عدد مثبت؛ احتمال انتخاب مقصد متناسب با وزن |

هر entry می‌تواند گزینه‌های socket مثل `nodelay`، `fastopen`، `reuseaddr`، `large-send-buffer`، `large-recv-buffer`، `fwmark`، `interface`، `source-ip` و `domain-strategy` را override کند. اگر گزینه‌ای در entry نیاید، مقدار top-level از `settings` استفاده می‌شود. برای `interface` و `source-ip` مقدار `null` مقدار inherited را غیرفعال می‌کند.

alias قدیمی `adresses` هم توسط parser پذیرفته می‌شود، اما spelling درست و پیشنهادی `addresses` است.

## تنظیمات socket

| گزینه | پیش‌فرض | توضیح |
|---|---:|---|
| `nodelay` | `true` | فعال‌سازی `TCP_NODELAY` |
| `fastopen` | `false` | درخواست `TCP_FASTOPEN` اگر platform پشتیبانی کند |
| `reuseaddr` | `false` | فعال‌سازی `SO_REUSEADDR` |
| `large-send-buffer` | `false` یا در صورت وجود mux مقدار large پیش‌فرض | تنظیم `SO_SNDBUF` |
| `large-recv-buffer` | `false` یا در صورت وجود mux مقدار large پیش‌فرض | تنظیم `SO_RCVBUF` |
| `fwmark` | - | socket mark در Linux با `SO_MARK` |
| `interface` | - | bind به interface؛ در Linux با `SO_BINDTODEVICE` |
| `source-ip` | - | bind کردن socket به source IP مشخص با source port موقت |
| `domain-strategy` | مقدار `dns.domain-strategy` در core | انتخاب IPv4/IPv6 برای نتیجه DNS |

## domain-strategy

`domain-strategy` در `TcpConnector` واقعا در مسیر DNS استفاده می‌شود. اگر مقصد domain باشد، مقدار انتخاب‌شده روی destination context خط ست می‌شود و `DomainResolver` داخلی بر اساس آن آدرس را resolve می‌کند.

مقدارهای string معتبر:

| مقدار | رفتار |
|---|---|
| `prefer-ipv4` | اولویت با IPv4، سپس IPv6 |
| `prefer-ipv6` | اولویت با IPv6، سپس IPv4 |
| `only-ipv4` | فقط IPv4 |
| `only-ipv6` | فقط IPv6 |
| `accept-dns-returned-order` | پذیرش ترتیب برگشتی DNS |

## CIDR روی IP ثابت

اگر `address` یک IP ثابت همراه CIDR باشد، `TcpConnector` host part را random می‌کند:

```json
"address": "198.51.100.0/24"
```

این فقط برای IP ثابت است، نه domain و نه context lookup. IPv4 prefix باید در محدوده `/0` تا `/32` باشد. IPv6 prefix باید در محدوده `/64` تا `/128` باشد.

## رفتار lifecycle

- upstream `Init` مقصد، پورت، optionها و domain strategy را انتخاب می‌کند.
- اگر مقصد domain باشد، DNS resolution به صورت async توسط `DomainResolver` داخلی انجام می‌شود.
- بعد از resolve، connect به صورت async شروع می‌شود.
- اگر connect موفق شود، downstream `Est` به نود قبلی ارسال می‌شود.
- payload upstream روی TCP socket نوشته می‌شود.
- داده دریافتی از remote به صورت downstream payload به نود قبلی برمی‌گردد.
- اگر DNS resolution یا connect شکست بخورد، line finish می‌شود.

## صف و flow control

اگر DNS، connect، یا write هنوز آماده نباشد، payloadهای upstream ممکن است queue شوند.

| وضعیت | رفتار |
|---|---|
| بیشتر از `1 KB` queue | نود قبلی pause می‌شود |
| خالی شدن writeهای pending | نود قبلی resume می‌شود |
| بیشتر از `16 MB` queue | connection بسته و line finish می‌شود |

## نکته‌ها

- DNS resolution در این مسیر asynchronous است.
- `domain-strategy` در مسیر DNS استفاده می‌شود.
- `fwmark` و bind به interface platform-dependent هستند.
- این نود chain end است و خودش `next` لازم ندارد.
