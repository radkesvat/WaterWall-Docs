# TcpConnector

## نمای کلی {#overview}

`TcpConnector` یک adapter خروجی TCP است. یک line از گره قبلی می‌گیرد، مقصد را از تنظیمات خود یا routing context آن line انتخاب می‌کند، اتصال TCP را باز می‌کند و payload را میان زنجیره و سرور راه دور جابه‌جا می‌کند. این گره معمولاً در انتهای زنجیرهٔ جریان بایتی قرار می‌گیرد.

`TcpConnector` پیش از آماده‌سازی resolver، پروتکل TCP را از گزینه‌های مقصد
خط انتخاب می‌کند. خطی که فقط TCP یا هر دو پروتکل را عرضه کند، پذیرفته
می‌شود. اگر گزینه‌های مقصد معتبر و سازگار نباشند، خط پیش از باز شدن سوکت بسته می‌شود.

## جایگاه معمول در زنجیره {#typical-placement}

```text
TcpListener -> ... -> TcpConnector -> remote TCP service
```
<a id="انتخاب-مقصد-connector-بر-اساس-نقش-آن"></a>

### انتخاب مقصد connector بر اساس نقش آن {#choose-the-connectors-destination-by-its-role}

```text
direct proxy: TcpListener -> Socks5Server -> TcpConnector
HTTP carrier: TcpListener -> Socks5Server -> HttpProxyClient -> TcpConnector
```
در زنجیره مستقیم SOCKS، روی TcpConnector مقدارهای
`address: "dest_context->address"` و `port: "dest_context->port"` را تنظیم کنید.
در زنجیره HTTP proxy، این مقدارهای پویا متعلق به HttpProxyClient هستند؛ TcpConnector
به endpoint ثابت proxy بالادستی وصل می‌شود.
[نمونه کامل listener](./TcpListener.mdx#configuration-example) حالت دوم را نشان می‌دهد.
برای انتخاب مستقیم/proxy بر اساس rule، [config مربوط به Router](./Router.mdx#complete-example)
را ببینید.

## نمونهٔ کاربردی ساده {#minimal-practical-example}

این یک **قطعهٔ پیکربندی گره** است، نه پیکربندی کامل. آن را در آرایهٔ `nodes` پیکربندی بگذارید و گره‌های مجاور بالا را به هم متصل کنید.

<a id="مقصد-راه-دور-ثابت"></a>

### مقصد راه دور ثابت {#fixed-remote-destination}

```json
{
  "name": "out",
  "type": "TcpConnector",
  "settings": {
    "address": "example.com",
    "port": 443,
    "dns-behaviour": {"resolve": true, "strategy": "prefer-ipv4"}
  }
}
```


## پیکربندی {#configuration}

<a id="فیلدهای-ضروری"></a>

### فیلدهای ضروری {#required-fields}

فیلدهای سطح بالا:

| فیلد | نوع | توضیح |
| --- | --- | --- |
| `name` | string | نام دلخواه گره. باید داخل فایل config یکتا باشد. |
| `type` | string | باید دقیقاً `"TcpConnector"` باشد. |
| `settings` | object | تنظیمات مقصد و socket. |

`settings` باید دقیقاً از یک سبک مقصد استفاده کند:

| سبک | فیلدهای لازم | توضیح |
| --- | --- | --- |
| مقصد تکی | `address` و `port` | هر line از همان قانون مقصد استفاده می‌کند. |
| مقصدهای وزن‌دار | `addresses` | برای هر line یک مقصد بر اساس وزن انتخاب می‌شود. |

`addresses` را با `address` یا `port` top-level ترکیب نکنید.

<a id="انتخاب-مقصد"></a>

### انتخاب مقصد {#destination-selection}

<a id="مقصد-تکی"></a>

#### مقصد تکی {#single-destination}

از `address` و `port` مستقیماً زیر `settings` استفاده کنید.

```json
{
  "settings": {
    "address": "93.184.216.34",
    "port": 443
  }
}
```

مقادیر معتبر برای `address`:

| مقدار | رفتار |
| --- | --- |
| string IPv4 | اتصال به آن آدرس IPv4. |
| string IPv6 | اتصال به آن آدرس IPv6. |
| string domain | resolve کردن domain پیش از اتصال. |
| `"src_context->address"` | استفاده از آدرس source در routing context مربوط به line. |
| `"dest_context->address"` | استفاده از آدرس destination در routing context مربوط به line. |

نام domain ثابت باید بین ۱ تا ۲۵۵ بایت باشد.

مقادیر معتبر برای `port`:

| مقدار | رفتار |
| --- | --- |
| عدد | اتصال به آن پورت ثابت. باید `1` تا `65535` باشد. |
| `"src_context->port"` | استفاده از پورت source در routing context مربوط به line. |
| `"dest_context->port"` | استفاده از پورت destination در routing context مربوط به line. |

`random(x,y)` در parser فعلی برای `TcpConnector` پشتیبانی نمی‌شود.

<a id="مقصدهای-weighted"></a>

#### مقصدهای وزن‌دار {#weighted-destinations}

برای انتخاب یک مقصد وزن‌دار به‌ازای هر line از `addresses` استفاده کنید.

```json
{
  "settings": {
    "addresses": [
      {
        "address": "192.0.2.10",
        "port": 443,
        "weight": 3
      },
      {
        "address": "198.51.100.20",
        "port": 443,
        "weight": 1
      }
    ]
  }
}
```

هر object باید شامل باشد:

| فیلد | نوع | توضیح |
| --- | --- | --- |
| `address` | string | همان فرم‌های معتبر `address` در مقصد تکی. |
| `port` | عدد یا string خاص | همان فرم‌های معتبر `port` در مقصد تکی. |
| `weight` | عدد صحیح مثبت | وزن نسبی این مقصد هنگام انتخاب. |

هر object می‌تواند گزینه‌های زیر را هم برای همان مقصد تغییر دهد:

| گزینه |
| --- |
| `nodelay` |
| `fastopen` |
| `large-send-buffer` |
| `large-recv-buffer` |
| `fwmark` |
| `interface` |
| `source-ip` |
| `dns-behaviour` (فقط `strategy`) |

parser برای سازگاری کلید قدیمی و غلط‌نویسی‌شده `adresses` را هم می‌پذیرد، اما در config جدید از `addresses` استفاده کنید و هر دو نام را هم‌زمان ننویسید.

<a id="تنظیمات-اختیاری"></a>

### تنظیمات اختیاری {#optional-settings}

| گزینه | نوع | پیش‌فرض | توضیح |
| --- | --- | --- | --- |
| `nodelay` | boolean | `true` | فعال‌سازی `TCP_NODELAY` روی socket‌های خروجی. |
| `linger-on-normal-close` | boolean | `true` | linger محدود را برای سوکت‌های عادی TCP خروجی در لینوکس فعال می‌کند. |
| `fastopen` | boolean | `false` | در صورت پشتیبانی platform، `TCP_FASTOPEN` را درخواست می‌کند. |
| `large-send-buffer` | boolean یا عدد صحیح مثبت | در صورت حذف، وابسته به زنجیره؛ توضیح در ادامه | تنظیم `SO_SNDBUF`. |
| `large-recv-buffer` | boolean یا عدد صحیح مثبت | در صورت حذف، وابسته به زنجیره؛ توضیح در ادامه | تنظیم `SO_RCVBUF`. |
| `fwmark` | integer | تنظیم نشده | اعمال socket mark به سبک Linux از طریق `SO_MARK` در صورت پشتیبانی. |
| `interface` | string | تنظیم نشده | محدود کردن socket‌های خروجی به یک network device محلی در صورت پشتیبانی. |
| `source-ip` | string | تنظیم نشده | socket خروجی را با یک source port موقت به source IP محلی مشخص bind می‌کند. |
| `dns-behaviour` | object | native با اولویت آدرس core | کنترل lookup محلی، انتخاب آدرس و انتقال DNS. |

هنگام استفاده از `addresses` می‌توانید گزینه‌های مخصوص هر مقصد را که در بالا آمده‌اند در سطح بالای `settings`
به‌عنوان پیش‌فرض بنویسید؛ هر object مقصد می‌تواند مقدار خودش را جایگزین کند.
`dns-behaviour` هر مقصد فقط `strategy` می‌پذیرد؛ فعال‌بودن lookup و انتقال DNS
همچنان در سطح گره تنظیم می‌شوند.

#### linger هنگام بستن TCP {#tcp-close-linger}

گزینهٔ `linger-on-normal-close` در سطح گره تنظیم می‌شود و برای همهٔ مقصدها یکسان
است. با دریافت `Finish`، ‏`TcpConnector` نوشته‌های پذیرفته‌شده را به WIO می‌سپارد
و state خود را در line قرضی آزاد می‌کند. در لینوکس، سوکت برقرار و واجد شرایط
این نوشته‌ها را تخلیه می‌کند، FIN می‌فرستد و برای مدتی کوتاه ورودی دیرهنگام همتا
را دور می‌ریزد تا خطر reset و ناقص ماندن خروجی کاهش یابد. تلاش برای اتصال که
هنوز در جریان است از مسیر بستن خودش استفاده می‌کند.

با مقدار `false`، اتصال‌های عادی از مسیر بستن معمول WIO عبور می‌کنند. در این
حالت سوکت برای linger نگه داشته نمی‌شود و احتمال اینکه ورودی خوانده‌نشده باعث
reset و ناقص ماندن خروجی شود بیشتر است. وقتی بسته‌شدن فقط سمت نوشتن همتای fallback
تأیید شود، linger همچنان درخواست می‌شود تا همتای گیرنده بتواند خواندن را تمام کند.
بسته‌شدن کامل fallback یا بسته‌شدن تأییدنشده از مسیر بستن معمول عبور می‌کند.
پلتفرم‌های فاقد پشتیبانی از linger این گزینه را می‌پذیرند و از بستن معمول استفاده
می‌کنند. [مرجع بستن سوکت TCP](../05-devguides/reference/line-protocols.mdx#tcp-socket-close-lingering)

<a id="گزینههای-socket-buffer"></a>

#### گزینه‌های socket buffer {#socket-buffer-options}

`large-send-buffer` و `large-recv-buffer` مقادیر زیر را می‌پذیرند:

| مقدار | معنا |
| --- | --- |
| `true` | استفاده از buffer بزرگ پیش‌فرض WaterWall برای socket؛ در حال حاضر `16777216` بایت. |
| `false` | تنظیم نکردن صریح اندازه buffer و استفاده از مقدار پیش‌فرض kernel. |
| عدد صحیح مثبت | درخواست مستقیم آن تعداد بایت. |

اگر زنجیره نهایی شامل `MuxClient` یا `MuxServer` باشد، گزینه‌های حذف‌شده‌ی buffer
اندازه‌ی پیش‌فرض 16 MiB را صریحاً درخواست می‌کنند، مستقل از core `misc.tcp-tune`
و موفقیت اجرای sysctl. در نبود Mux در زنجیره، گزینه‌های حذف‌شده به kernel واگذار
می‌شوند. مقادیر صریح، از جمله `false`، در هر دو حالت اولویت دارند.
مقصدهای TcpConnector برای گزینه‌های حذف‌شده مقدار مؤثر سطح اصلی را به ارث می‌برند.

<a id="انتخاب-آدرس"></a>

#### انتخاب آدرس {#address-selection}

`dns-behaviour.strategy` مشخص می‌کند وقتی DNS هم IPv4 و هم IPv6 برمی‌گرداند، کدام آدرس برای مقصد domain انتخاب شود.

اگر این گزینه را ننویسید، مقدار `dns.domain-strategy` در core به کار می‌رود. در نبود آن هم WaterWall از `"prefer-ipv4"` استفاده می‌کند.

فقط رشته‌های canonical زیر با حروف کوچک پذیرفته می‌شوند:

| مقدار | رفتار |
| --- | --- |
| `"core-settings"` | استفاده از اولویت `dns.domain-strategy` در core. |
| `"prefer-ipv4"` | نخستین نتیجه IPv4 را انتخاب می‌کند و اگر وجود نداشت به IPv6 برمی‌گردد. |
| `"prefer-ipv6"` | نخستین نتیجه IPv6 را انتخاب می‌کند و اگر وجود نداشت به IPv4 برمی‌گردد. |
| `"only-ipv4"` | فقط نتیجه IPv4 را می‌پذیرد؛ نبودن IPv4 یعنی resolution برای آن line قابل استفاده نیست. |
| `"only-ipv6"` | فقط نتیجه IPv6 را می‌پذیرد؛ نبودن IPv6 یعنی resolution برای آن line قابل استفاده نیست. |
| `"accept-dns-returned-order"` | نخستین آدرس قابل استفاده در ترتیب بازگشتی resolver را انتخاب می‌کند. |

در `addresses` وزن‌دار، هر object می‌تواند `dns-behaviour.strategy` مخصوص line‌هایی را تعریف کند که همان مقصد را انتخاب کرده‌اند.

<a id="interface-source-ip-و-egress-pinning"></a>

#### interface، source IP و egress pinning {#interface-source-ip-and-egress-pinning}

`interface` socket خروجی را به یک device محلی محدود می‌کند.

در Linux، WaterWall در صورت امکان از `SO_BINDTODEVICE` استفاده می‌کند. روی platform‌های بدون device binding، socket به آدرس IPv4 مربوط به interface bind می‌شود. اگر آدرسی پیدا نشود، راه‌اندازی اتصال شکست می‌خورد.

`source-ip` socket خروجی را قبل از connect به یک source IP محلی مشخص bind می‌کند. خانواده آدرس باید با خانواده مقصد مطابقت داشته باشد.

اگر loop protection در `TunDevice` یک egress pin خودکار ایجاد کرده باشد و `interface` را ننوشته باشید، `TcpConnector` از همان pin استفاده می‌کند. `source-ip` به‌تنهایی آن interface را تغییر نمی‌دهد؛ اطمینان یابید IP مبدأ متعلق به interface پین‌شده یا پیش‌فرض است، یا `interface` را صریحاً بنویسید.

<a id="رفتار-dns"></a>

### رفتار DNS {#dns-behaviour}

resolve کردن نام دامنه یعنی پیدا کردن آدرس IP آن. `TcpConnector` ابتدا مقصد را
از تنظیمات آدرس و پورت، از جمله انتخاب وزن‌دار، مشخص می‌کند. سپس فقط وقتی آدرس
انتخاب‌شده یک نام دامنهٔ resolve‌نشده باشد و resolve محلی فعال باشد، lookup انجام
می‌دهد. IP عددی یا مقصدی که از قبل resolve شده باشد به lookup نیاز ندارد.

این lookup مربوط به سروری است که connector به آن وصل می‌شود: پس از یک proxy client،
سرور proxy است و در اتصال مستقیم، مقصد برنامه. با حذف `dns-behaviour`، resolve محلی
در حالت `native` فعال می‌ماند و اولویت آدرس از `dns.domain-strategy` در core گرفته می‌شود.

این lookup را با `settings.dns-behaviour` تنظیم کنید:

```json
{
  "dns-behaviour": {
    "resolve": true,
    "mode": "direct",
    "strategy": "prefer-ipv4",
    "servers": ["203.0.113.53:53"]
  }
}
```

این آدرس نمونهٔ مستندات است؛ آن را با آدرس resolver خود جایگزین کنید.

| فیلد | معنی |
| --- | --- |
| `resolve` | boolean اجباری: `true` اجازهٔ lookup نام دامنهٔ resolve‌نشده را می‌دهد و `false`، lookup محلی را غیرفعال می‌کند. |
| `mode` | `native` (پیش‌فرض هنگام فعال بودن)، `direct` یا `chain`. |
| `strategy` | یکی از `core-settings`، `accept-dns-returned-order`، `prefer-ipv4`، `prefer-ipv6`، `only-ipv4` یا `only-ipv6`؛ حذف آن اولویت پیش‌فرض آدرس مصرف‌کننده را به کار می‌برد. |
| `servers` | ۱ تا ۳۲ endpoint عددی IP، IP:port یا [IPv6]:port؛ در حالت‌های `direct` و `chain` اجباری و در `native` ممنوع. |
| `dns-next` | نام غیرخالی ورودی DNS، فقط در حالت `chain`. |

`native` از تنظیمات DNS در core و resolver مشترک worker استفاده می‌کند. هنگام
فعال بودن resolve محلی، این حالت پیش‌فرض انتقال DNS است.

`direct` درخواست‌های DNS را از طریق یک connector خصوصی TCP/UDP در WaterWall به
سرورهایی که مشخص کرده‌اید می‌فرستد.

`chain` درخواست‌های DNS را از زنجیره انتخابی می‌فرستد. برای محافظت از آن‌ها، مسیری
رمزنگاری‌شده مانند VPN خود را انتخاب کنید؛ این حالت به‌تنهایی درخواست‌ها را
رمزنگاری نمی‌کند. مسیر DNS باید هم درخواست‌های UDP و هم fallback روی TCP را حمل
کند. خطای route یا lookup باعث تغییر به DNS بومی یا حالت دیگر نمی‌شود.

در حالت `chain`، مقدار `dns-next` را نام یک شاخهٔ DNS جدا بگذارید که هم UDP و هم
TCP را پشتیبانی کند. این شاخه نباید از قبل به گره دیگری تعلق داشته باشد. این گره
شاخهٔ DNS پیش‌فرض ندارد و نام‌بردن از خود آن مجاز نیست.

شکل غیرفعال دقیقاً `"dns-behaviour": {"resolve": false}` است و فیلدهای `mode`، `strategy`، `servers` و `dns-next` را رد می‌کند. object تهی، null، نوع غیرobject، فیلد ناشناخته و strategy عددی رد می‌شوند. نام strategy باید یکی از رشته‌های canonical بالا با حروف کوچک باشد. `core-settings` فقط اولویت آدرس را انتخاب می‌کند و انتقال DNS را تغییر نمی‌دهد.

با `resolve: false`، آماده‌سازی مقصد همچنان اجرا می‌شود. IP عددی یا مقصد از قبل resolve‌شده کار می‌کند؛ نام resolve‌نشده از مسیر عادی خطای line یا datagram رد می‌شود و به DNS بومی برنمی‌گردد.

هر عضو وزن‌دار `destinations[]` می‌تواند فقط override مربوط به strategy، مانند `"dns-behaviour": {"strategy": "only-ipv4"}` داشته باشد؛ نام `addresses` هم پذیرفته می‌شود. انتقال، سرورها و شاخه از گره ارث می‌رسند. فیلدهای دیگر یا override هنگام غیرفعال بودن resolve رد می‌شوند. مقصد فقط یک بار انتخاب و گزینه‌های socket و strategy پس از انجام DNS نیز حفظ می‌شوند.

مثال‌های `native`، `direct` و `chain` محافظت‌شده و محدودیت گزینه‌های core را در [DomainResolver](./DomainResolver.mdx) ببینید. این سیاست فقط lookupهای متعلق به همین گره را کنترل می‌کند؛ fake DNS در PTC، DNS سیستم در TunDevice و همهٔ منابع DNS برنامه را تغییر نمی‌دهد.


## کاربرد و رفع اشکال {#usage-and-troubleshooting}

<a id="نمونه-تنظیم"></a>

### نمونهٔ پیکربندی {#configuration-example}

این نمونه یک قطعهٔ connector است که گزینه‌های اختیاری سوکت را نشان می‌دهد. مقادیری مانند `interface`، `source-ip` و `fwmark` به پیکربندی متناسب میزبان نیاز دارند؛ اگر این bind را نمی‌خواهید، آن‌ها را حذف کنید.

```json
{
  "name": "outbound-tcp",
  "type": "TcpConnector",
  "settings": {
    "address": "example.com",
    "port": 443,
    "nodelay": true,
    "fastopen": false,
    "large-send-buffer": true,
    "large-recv-buffer": 4194304,
    "fwmark": 10,
    "interface": "eth0",
    "source-ip": "192.0.2.10",
    "dns-behaviour": {"resolve": true, "strategy": "prefer-ipv4"}
  }
}
```

<a id="نمونه-چند-مقصد-وزندار"></a>

### نمونهٔ چند مقصد وزن‌دار {#weighted-multi-destination-example}

```json
{
  "name": "outbound-tcp",
  "type": "TcpConnector",
  "settings": {
    "addresses": [
      {
        "address": "192.0.2.10",
        "port": 443,
        "weight": 5,
        "nodelay": true,
        "interface": "eth0",
        "dns-behaviour": {"strategy": "prefer-ipv4"}
      },
      {
        "address": "example.org",
        "port": "dest_context->port",
        "weight": 1,
        "source-ip": "198.51.100.10",
        "dns-behaviour": {"strategy": "only-ipv4"}
      },
      {
        "address": "2001:db8:1::/64",
        "port": 443,
        "weight": 1,
        "interface": null,
        "source-ip": null,
        "dns-behaviour": {"strategy": "only-ipv6"}
      }
    ],
    "nodelay": true,
    "fastopen": false,
    "large-send-buffer": true,
    "large-recv-buffer": true,
    "interface": "eth0",
    "dns-behaviour": {"resolve": true, "strategy": "prefer-ipv4"}
  }
}
```

برای هر line جدید، یکی از object‌های `addresses` با احتمالی متناسب با `weight` آن انتخاب می‌شود. گزینه‌هایی که در object مقصد نوشته نشده‌اند از سطح بالای `settings` به ارث می‌رسند. برای `interface` و `source-ip` می‌توانید با مقدار `null`، مقدار به‌ارث‌رسیده را فقط برای همان مقصد غیرفعال کنید.

<a id="مهلت-برقراری-اتصال"></a>

### مهلت برقراری اتصال {#connection-establishment-timeout}

هر تلاش برای برقراری اتصال خروجی TCP یک مهلت `60 ثانیه‌ای` دارد که با پیش‌فرض
`proxy_connect_timeout` در NGINX هماهنگ است. این مهلت پس از Resolve شدن آدرس و
با آغاز تلاش اتصال TCP شروع می‌شود و پس از برقراری اتصال لغو می‌شود. خطاهای فوری
اتصال همچنان می‌توانند line را زودتر ببندند. این مهلت از idle timeout اولیه‌ی
listener و محدودیت پاک‌سازی اتصال‌های بی‌فعالیت connector جداست؛ `TcpConnector`
مرحله‌ی idle جداگانه‌ای برای انتظار اولین payload ندارد.

### idle timeout {#idle-timeout}

هر اتصال خروجی در جدول idle همان worker دنبال می‌شود. timeout فعلی نزدیک به `600 ثانیه` است و هر read یا write آن را تمدید می‌کند.

اگر اتصال منقضی شود، socket بسته می‌شود و `finish` در جهت downstream به گره قبلی فرستاده می‌شود.

این محدودیت ده‌دقیقه‌ای برای پاک‌سازی اتصال‌های بی‌فعالیت با timeout فعال پیش‌فرض
`TcpListener` هماهنگ است. اگر مقصد زودتر اتصال را ببندد، `finish` بدون انتظار
تا پایان مهلت idle به سمت downstream فرستاده می‌شود. این مقدار سقف تعیین‌شده از سوی NGINX نیست؛
اگر مقصد fallback بی‌فعالیتی طولانی‌تری را مجاز بداند، محدودیت idle هر دو adapter
باید آن را پوشش دهد.

<a id="نکات-و-هشدارها"></a>

### نکات و هشدارها {#notes-and-caveats}

- `TcpConnector` یک گره خروجی در انتهای زنجیره است و به `next` نیاز ندارد.
- حل نام DNS ناهمگام است و از `dns-behaviour.strategy` انتخاب‌شده استفاده می‌کند.
- `fwmark`، `TCP_FASTOPEN` و device binding به platform وابسته هستند.
- `fwmark` روی Windows در دسترس نیست.
- `source-ip` باید یک آدرس IP معتبر باشد و باید با خانواده آدرس مقصد مطابقت داشته باشد.
- کلید قدیمی `adresses` برای سازگاری پذیرفته می‌شود، اما `addresses` نام‌گذاری مستند‌شده است.


## رفتار پیشرفته {#advanced-behavior}

### حل نام دامنه {#domain-resolution}

حل نام دامنه در صورت نیاز و فعال بودن، به‌شکل ناهمگام انجام می‌شود. `TcpConnector` از یک زنجیرهٔ داخلی `DomainResolver` استفاده می‌کند و پیش از حل نام، `dns-behaviour.strategy` انتخاب‌شده را در context مقصد line ذخیره می‌کند.

payload‌های رسیده در زمان انتظار برای DNS نزد resolver می‌مانند. payload‌هایی که پس از موفقیت DNS و پیش از برقراری TCP می‌رسند نیز تا آماده شدن socket در `TcpConnector` صف می‌شوند.

<a id="cidr-randomization-روی-ipهای-ثابت"></a>

### تصادفی‌سازی CIDR روی IPهای ثابت {#cidr-randomization-on-constant-ips}

یک `address` ثابت IP می‌تواند پسوند CIDR داشته باشد. در این حالت `TcpConnector` پیش از اتصال، host part را به‌صورت تصادفی انتخاب می‌کند.

```json
{
  "settings": {
    "address": "198.51.100.0/24",
    "port": 443
  }
}
```

```json
{
  "settings": {
    "address": "2001:db8:1::/64",
    "port": 443
  }
}
```

پسوندهای CIDR فقط روی آدرس‌های IP ثابت معتبر هستند. روی domain‌ها، `"src_context->address"` یا `"dest_context->address"` معتبر نیستند.

قوانین پیاده‌سازی:

| خانواده آدرس | طول prefix معتبر | توضیح |
| --- | --- | --- |
| IPv4 | `0` تا `32` | `/0` هر ۳۲ بیت آدرس را تصادفی می‌کند؛ `/32` آدرس را ثابت نگه می‌دارد. |
| IPv6 | `64` تا `128` | `/64` هر ۶۴ بیت بخش host را با حفظ prefix شبکه تصادفی می‌کند؛ `/128` آدرس را ثابت نگه می‌دارد. |

پسوند باید فقط شامل رقم‌های ده‌دهی باشد. prefix خالی، نامعتبر یا خارج از بازه رد می‌شود.
prefix طولانی‌تر فقط بیت‌های باقی‌ماندهٔ بخش host را تصادفی می‌کند.


## جزئیات پیاده‌سازی {#implementation-details}

<a id="قابلیتها"></a>

### چه کاری انجام می‌دهد {#what-it-does}

- انتخاب آدرس و پورت مقصد برای هر line.
- resolve کردن نام دامنهٔ resolve‌نشده در صورت فعال بودن DNS محلی.
- باز کردن یک socket TCP خروجی.
- نوشتن payload‌های upstream از گره قبلی روی socket راه دور.
- فرستادن داده‌های خوانده‌شده از socket راه دور به‌عنوان payload downstream به گره قبلی.
- فرستادن downstream `est` پس از برقراری موفق اتصال TCP خروجی.
- اعمال گزینه‌های socket مانند `TCP_NODELAY`، `TCP_FASTOPEN`، اندازه buffer‌ها، `SO_MARK`، device binding و source-IP binding در صورت پشتیبانی platform.

`TcpConnector` در انتهای زنجیره قرار می‌گیرد، با upstream `init` راه می‌افتد و به گره `next` نیاز ندارد.

<a id="رفتار-chain"></a>

### رفتار زنجیره {#chain-behavior}

هنگام upstream `init`، `TcpConnector` state مربوط به line را مقداردهی می‌کند، قانون مقصد را برمی‌گزیند، address و port را در destination context می‌گذارد و domain strategy را تنظیم می‌کند.

جریان داخلی:

1. تنظیمات مقصد شامل `address`، `port`، گزینه‌های socket و اطلاعات اختیاری CIDR randomization انتخاب می‌شوند.
2. اگر resolve محلی فعال باشد، `DomainResolver` داخلی نام دامنهٔ resolve‌نشده را lookup می‌کند. IP یا مقصد از قبل resolve‌شده از این مرحله می‌گذرد.
3. پس از تبدیل مقصد به IP و port، `TcpConnector` socket خروجی را می‌سازد و اتصال async را آغاز می‌کند.
4. با موفقیت اتصال، downstream `est` به گره قبلی فرستاده می‌شود.
5. payload‌های upstream روی socket نوشته می‌شوند و داده‌های خوانده‌شده از socket به payload downstream تبدیل می‌شوند.

اگر آماده‌سازی مقصد، DNS resolution، ساخت socket یا اتصال ناموفق باشد، line در جهت downstream و به سمت گره قبلی finish می‌شود.

<a id="کنترل-جریان-و-buffering"></a>

### کنترل جریان و بافرگذاری {#flow-control-and-buffering}

در حالی که DNS، connect یا socket write‌ها در انتظار هستند، `TcpConnector` ممکن است payload‌های upstream را صف کند.

آستانه‌های فعلی:

| وضعیت صف | رفتار |
| --- | --- |
| رسیدن حجم یا هزینهٔ ظرفیت صف به `1 KiB` | گره قبلی pause می‌شود. |
| تکمیل write‌های pending | گره قبلی resume می‌شود. |
| عبور حجم یا هزینهٔ ظرفیت صف از `16 MiB` | اتصال بسته و line finish می‌شود. |

هنگام پذیرش در صف، پیش از اطلاع‌دادن به تولیدکننده، buffer، حسابداری صف و وضعیت ثبت‌شدهٔ Pause منتشر می‌شوند تا ترتیب FIFO در صورت ورود مجدد از طریق callback حفظ شود.
حجم منطقی و هزینهٔ ظرفیت buffer (شامل sbuf، padding و alignment) هرکدام سقف مستقل `16 MiB` دارند؛ مقدار برابر سقف پذیرفته می‌شود.
با رسیدن هرکدام به `1 KiB`، Pause ارسال می‌شود. buffer خالی نیز هزینهٔ ظرفیت دارد.
بودجهٔ TCP صف adapter و buffer فعال WIO را با هم حساب می‌کند. در نوشتن جزئی، هزینهٔ تخصیص فعال تا تکمیل نوشتن همچنان محاسبه می‌شود.
عبور از سقف، همان اتصال را از طریق مالک line می‌بندد.

این آستانه‌ها نمی‌گذارند هنگام کند بودن server راه دور یا آماده نبودن اتصال، مصرف حافظه بی‌حد رشد کند.

اگر خواندن پیش از `Finish` متوقف شده باشد، [سیاست بستن TCP](#tcp-close-linger)
همچنان اعمال می‌شود. پس از EOF سمت backend، آداپتور سمت کلاینت که هنوز زنده است
برای سوکت خودش تصمیم می‌گیرد. هنگام EOF بدون خطا در fallback، connector می‌تواند
با ابزار تشخیص لینوکس بسته‌شدن فقط سمت نوشتن همتا را در همان فضای نام شبکه تأیید
کند و پیش از انتشار `Finish` روی line علامت بگذارد.
