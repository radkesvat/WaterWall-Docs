# TesterClient

`TesterClient` یک نود validation مصنوعی در ابتدای chain است. این نود traffic قطعی و قابل پیش‌بینی تولید می‌کند، آن را به نود بعدی می‌فرستد، response برگشتی را verify می‌کند و در صورت mismatch یا timeout، process را abort می‌کند.

این نود برای تست ترکیب tunnelها، framing، packet handling، ordering و payload integrity است؛ adapter تولیدی برای traffic واقعی نیست.

## جایگاه رایج

Stream mode:

```text
TesterClient -> SomeTunnel -> SomeTunnel -> TesterServer
```

Packet mode:

```text
TesterClient(packet-mode=true) -> PingClient -> Bridge
TesterServer(packet-mode=true) -> PingServer -> Bridge
```

`TesterClient` باید chain head باشد و نوع آن singleton است؛ یعنی در یک config فقط یک instance از آن داشته باشید.

## نمونه تنظیم

Stream mode:

```json
{
  "name": "tester-client",
  "type": "TesterClient",
  "next": "next-node"
}
```

Packet mode:

```json
{
  "name": "tester-client",
  "type": "TesterClient",
  "settings": {
    "packet-mode": true
  },
  "next": "packet-node"
}
```

Packet mode همراه با IPv4 مصنوعی:

```json
{
  "name": "tester-client",
  "type": "TesterClient",
  "settings": {
    "packet-mode": true,
    "packet-ipv4": {
      "source-ip": "198.51.100.10",
      "dest-ip": "203.0.113.20",
      "transport": "udp",
      "ttl": 64
    }
  },
  "next": "packet-node"
}
```

## فیلدهای ضروری

| فیلد | نوع | توضیح |
|---|---|---|
| `name` | string | نام node. |
| `type` | string | باید `TesterClient` باشد. |
| `next` | string | نودی که line یا packet line تست را دریافت می‌کند. |

`settings` اختیاری است. اگر نباشد، stream-mode پیش‌فرض استفاده می‌شود.

## تنظیمات

| فیلد | پیش‌فرض | توضیح |
|---|---|---|
| `packet-mode` | `false` | به جای line معمولی از worker packet line استفاده می‌کند. |
| `packet-start-immediately` | `false` | فقط packet mode؛ بدون انتظار برای downstream `Est` شروع می‌کند. |
| `packet-start-delay-ms` | `0` | فقط packet mode؛ تاخیر مسیر immediate-start. باید non-negative باشد. |
| `allow-early-response` | `false` | فقط stream mode؛ اجازه response قبل از تمام شدن request sequence. |
| `packet-stateless` | `false` | فقط packet mode؛ response packetها می‌توانند out of order برسند و با size تشخیص داده می‌شوند. |
| `chunk-count` | `11` | تعداد chunkهای فعال از ابتدای جدول. بازه معتبر `1` تا `11`. |
| `max-payload-size` | `0` | محدود کردن اندازه bufferهای stream یا packet size. مقدار `0` یعنی حالت عادی. |
| `split-payload-delay-ms` | `1` | فقط stream mode؛ تاخیر بین payloadهای split شده. |
| `split-payload-burst` | `1` | فقط stream mode؛ تعداد buffer قبل از اعمال delay. |
| `dest-context` | ندارد | destination routing context اولیه برای هر line مصنوعی. |
| `packet-ipv4` | ندارد | فقط packet mode؛ ساخت IPv4 packet مصنوعی برای هر test packet. |

`packet-stateless` نیازمند `packet-mode=true` است. `max-payload-size` با `packet-stateless=true` پشتیبانی نمی‌شود.

## جدول Chunkها

Stream mode:

```text
1, 2, 4, 32, 512, 1024, 4096, 32768, 32769, 1048576, 2097152
```

Packet mode:

```text
1, 2, 4, 32, 64, 128, 256, 512, 1024, 1499, 1500
```

Packet mode با IPv4 خام:

```text
21, 22, 24, 52, 84, 148, 276, 532, 1044, 1499, 1500
```

Packet mode با IPv4 و transport header مثل `tcp`، `udp` یا `icmp`:

```text
41, 42, 44, 52, 84, 148, 276, 532, 1044, 1499, 1500
```

الگوی byteها deterministic است و بر اساس chunk index، offset، flow id و direction ساخته می‌شود. اولین byte request، flow id را حمل می‌کند تا اگر transport واقعی worker را عوض کرد، verification خراب نشود.

## Dest Context

با `dest-context` می‌توانید قبل از upstream `Init` مقدار `line->routing_context.dest_ctx` را روی line تست قرار دهید.

```json
{
  "dest-context": {
    "address": "example.com",
    "port": 443,
    "protocol": "tcp"
  }
}
```

فیلدها:

| فیلد | توضیح |
|---|---|
| `address` | IP یا domain. |
| `port` | پورت مقصد، `1` تا `65535`. |
| `protocol` | `tcp` یا `udp`. |

## Packet IPv4

`packet-ipv4` فقط با `packet-mode=true` معتبر است.

| فیلد | پیش‌فرض | توضیح |
|---|---|---|
| `source-ip` | اجباری | IPv4 source برای request packetها. |
| `dest-ip` | اجباری | IPv4 destination برای request packetها. |
| `transport` | `none` | مقدار `tcp`، `udp`، `icmp`، `raw` یا `none`. |
| `protocol` | `253` | IPv4 protocol number. اگر transport مشخص باشد باید با آن match کند. |
| `ttl` | `64` | مقدار TTL. |

برای response packetها، source و destination خودکار برعکس می‌شوند. برای `tcp` و `udp`، request از portهای `40123` به `40234` استفاده می‌کند و response آن‌ها را reverse می‌کند.

## Runtime

در startup، `TesterClient` برای هر worker بعد از `100 ms` یک task اجرا می‌کند. این task:

1. در packet mode، worker packet line را استفاده می‌کند و در غیر این صورت line معمولی می‌سازد
2. line state خودش را initialize می‌کند
3. در صورت وجود، `dest-context` را روی line کپی می‌کند
4. upstream `Init` را به نود بعدی می‌فرستد
5. watchdog برابر `30000 ms` فعال می‌کند

در stream mode، ارسال request بعد از دریافت downstream `Est` شروع می‌شود. در packet mode، `packet-start-immediately=true` می‌تواند این انتظار را حذف کند.

## Verification

در stream mode، responseها buffer می‌شوند، chunkها به ترتیب verify می‌شوند، trailing byte اضافه خطاست و `Finish` زودهنگام fail محسوب می‌شود.

در packet mode، هر response packet باید دقیقا با chunk مورد انتظار match شود. packet line نباید در runtime بسته شود و `Finish` روی packet line خطاست. با `packet-stateless=true` ترتیب packetها آزادتر است، ولی هر chunk باید دقیقا یک بار برسد.

وقتی همه workerها کامل شوند، `TesterClient` با exit code `0` برنامه را تمام می‌کند. mismatch، timeout یا lifecycle اشتباه باعث failure می‌شود.

## مشخصات Node

| ویژگی | مقدار |
|---|---|
| Position | Chain head |
| Singleton | بله |
| Maximum workers | `254` |
| Watchdog | `30000 ms` |
| Required left padding | `0` |

## خطاهای رایج

- استفاده در production. این نود عمدا برای validation است.
- فراموش کردن `next`.
- فعال کردن packet mode بدون packet-layer node در chain.
- انتظار close شدن packet line در packet mode.
- ترکیب `packet-stateless=true` با `max-payload-size`.
- استفاده از `packet-ipv4` بدون `packet-mode=true`.
