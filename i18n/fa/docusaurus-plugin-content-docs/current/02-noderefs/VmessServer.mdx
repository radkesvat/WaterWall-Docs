# VmessServer

`VmessServer` درخواست‌های VMess AEAD را دریافت می‌کند، حساب کاربر را با UUID احراز هویت می‌کند
و ترافیک TCP یا UDP با مقصد ثابت را پس از رمزگشایی به `next` می‌فرستد. این node مستقل از
transport است. برای TLS یا WebSocket، nodeهای `TlsServer` یا `HttpServer` را پیش از آن قرار دهید.

## احراز هویت

یکی از دو روش را انتخاب کنید:

- کاربران محلی: از `uuid`/`id`، آرایه `uuids` یا `users`/`clients` استفاده کنید. هر شیء کاربر
  یک `uuid` یا `id`/`user-id` و در صورت نیاز `username` دارد. این روش به پایگاه AuthenticationClient نیاز ندارد.
- کاربران مدیریت‌شده: `auth-client-node-name` را تنظیم و تمام اعتبارنامه‌های محلی را حذف کنید.
  UUID کاربر در فیلد `password` حساب AuthenticationServer قرار می‌گیرد. این node از جدول
  همگام‌شده حافظه AuthenticationClient استفاده می‌کند و یک `UserController` داخلی پیش از
  outbound می‌گذارد؛ روی همین مسیر یک UserController دیگر به‌صورت دستی اضافه نکنید.

روش مدیریت‌شده از پذیرش حساب، ثبت مصرف، محدودیت اتصال و IP، سهمیه و shaping تنظیم‌شده
کاربر استفاده می‌کند. پس از اولین همگام‌سازی معتبر، قطع معمول شبکه کنترل باعث استفاده از آخرین
جدول پذیرفته‌شده می‌شود. نبود جدول اولیه یا رد صریح اعتبارنامه AuthenticationClient پذیرش
جدید را می‌بندد. تغییرات مدیر پس از refresh معتبر اعمال می‌شوند. محدودیت cache محلی تضمین
reservation سراسری بین چند AuthenticationClient قطع‌شده نیست.

VMess به‌جای UUID آشکار، AuthID رمز‌شده می‌فرستد. شناسایی AuthID تازه در بدترین حالت
به جستجوی `O(N)` بین `N` کلید نامزدِ دارای UUID نیاز دارد. کلید فرمان و کلید AuthID
از پیش محاسبه می‌شوند و جدول آن‌ها بین workerهای همین node مشترک است. حساب‌های دارای
UUID پیش از بررسی شرایط پذیرش در فهرست نامزدها قرار می‌گیرند؛ تطبیق کلید به‌تنهایی
مجوز پذیرش حساب غیرفعال نیست. پس از تطبیق رمزنگاری، در روش مدیریت‌شده هویت فعلی حساب
و شرایط پذیرش آن با lookup نمایه‌دار AuthenticationClient دوباره بررسی می‌شود.

کار احراز هویت در نوبت‌های محدود event loop انجام می‌شود و کارهای منتظر و cache
اعتبارنامه بودجه محدود دارند. کلید cache‌شده مجوز حساب حذف‌شده یا جایگزین‌شده نیست.
این محدودیت‌ها برای کار و حافظه‌اند و نرخ انتقال داده برنامه را محدود نمی‌کنند.

## پشتیبانی پروتکل

| security بدنه در کلاینت | TCP | UDP |
| --- | --- | --- |
| `aes-128-gcm` | پشتیبانی می‌شود | پشتیبانی می‌شود |
| `chacha20-poly1305` | پشتیبانی می‌شود | پشتیبانی می‌شود |
| `none` با chunk framing | پشتیبانی می‌شود | پشتیبانی می‌شود |
| `zero` یا `none` بدون framing | پشتیبانی می‌شود | رد می‌شود |

در همه حالت‌ها، header درخواست و پاسخ AEAD است و `alterId` باید صفر باشد. حالت‌های
`none` و `zero` بدنه برنامه را رمز یا احراز اصالت نمی‌کنند؛ اگر محرمانگی بدنه لازم است،
transport محافظ مناسب را جداگانه انتخاب کنید. `zero` تنظیم کلاینت است و روی wire به
`none` بدون chunk تبدیل می‌شود؛ stream بدون framing مرز datagramهای UDP را نگه نمی‌دارد.

مقصد IPv4، IPv6 و نام دامنه غیرخالی پشتیبانی می‌شود. UDP یک backend برای مقصد ثابت
درخواست دارد. رکورد بدنه خالی علامت پایان پروتکل است، نه datagram خالی.

هر جهت رمز‌شده شمارنده‌ای ۱۶ بیتی دارد که از صفر شروع می‌شود. داده سرور به کلاینت از
شمارنده‌های `0..65,534` استفاده می‌کند و مقدار `65,535` برای رکورد پایانِ احراز اصالت‌شده
رزرو است. داده کلاینت به سرور می‌تواند از شمارنده `65,535` استفاده کند؛ سرور آن رکورد را
تحویل می‌دهد و سپس اتصال را می‌بندد. رکوردهای طول احراز‌شده نیز همین مقدارهای شمارنده
و محدودیت پایان را دارند. شمارنده‌ها هرگز wrap نمی‌شوند؛ این سقف بر تعداد رکوردها اعمال
می‌شود، نه تعداد بایت‌ها، و انتقال رمز‌شده طولانی به اتصال تازه نیاز دارد.

header قدیمی VMess و alter ID، AES-CFB، Mux.Cool، XUDP و فرمان reverse پشتیبانی نمی‌شوند.
TLS، WebSocket و HTTP مسئولیت nodeهای خودشان هستند؛ VmessServer تنظیمات یا تشخیص داخلی
این transportها ندارد. این node splice را برای chain غیرفعال می‌کند، چون parser و رمزنگاری
به buffer عادی حافظه نیاز دارند.

## چیدمان و مثال

```text
TcpListener -> VmessServer -> TcpUdpConnector
TcpListener -> TlsServer -> VmessServer -> TcpUdpConnector
TcpListener -> HttpServer (WebSocket) -> VmessServer -> TcpUdpConnector
TcpListener -> TlsServer -> HttpServer (WebSocket) -> VmessServer -> TcpUdpConnector
```

کاربر محلی:

```json
{
  "name": "vmess",
  "type": "VmessServer",
  "settings": {
    "users": [
      {"username": "alice", "uuid": "5783a3e7-e373-51cd-8642-c83782b807c5"}
    ],
    "connect": true,
    "udp": true
  },
  "next": "outbound"
}
```

کاربر مدیریت‌شده:

```json
{
  "name": "vmess",
  "type": "VmessServer",
  "settings": {"auth-client-node-name": "auth-client"},
  "next": "outbound"
}
```

connector خروجی معمولاً `"address": "dest_context->address"` و
`"port": "dest_context->port"` دارد. برای TCP از `TcpConnector`، برای UDP از
`UdpConnector` و برای هر دو از `TcpUdpConnector` استفاده کنید.

## تنظیمات

| تنظیم | پیش‌فرض | کاربرد |
| --- | --- | --- |
| `uuid` / `id` | ندارد | یک UUID محلی؛ فقط یکی از دو نام را بنویسید. |
| `uuids` | ندارد | آرایه رشته UUID یا شیء کاربر. |
| `users` / `clients` | ندارد | آرایه رشته UUID یا شیء کاربر؛ یکی از دو نام را انتخاب کنید. |
| `auth-client-node-name` | ندارد | نام AuthenticationClient؛ با تنظیمات کاربر محلی همزمان مجاز نیست. |
| `connect` | `true` | اجازه درخواست TCP. |
| `udp` | `true` | اجازه UDP دارای framing؛ حداقل یکی از TCP و UDP باید فعال باشد. |
| `handshake-timeout-ms` | `10000` | مهلت قطعی handshake درخواست؛ دریافت داده آن را تمدید نمی‌کند. |
| `auth-max-pending` | `4096` | بیشترین تعداد کار احراز هویت منتظر در node. |
| `auth-pending-max-bytes` | `67108864` | بودجه مشترک بایت منطقی ورودی کارهای احراز هویت منتظر. |
| `auth-cache-max-bytes` | `67108864` | بودجه حافظه cache اعتبارنامه و احراز هویت، برحسب بایت. |
| `replay-max-entries` | `262144` | بیشترین ورودی زنده در هر یک از جدول‌های replay مربوط به AuthID و session. |
| `fallback-node-name` | ندارد | شاخه اختیاری برای ترافیک واجد شرایط پیش از احراز هویت. |
| `fallback-intentional-delay-ms` | `7` | تأخیر عمدی fallback؛ صفر آن را غیرفعال می‌کند. |
| `fallback-intentional-delay-jitter-ms` | `1` | jitter افزوده؛ با تأخیر صفر نادیده گرفته می‌شود. |
| `verbose` | `false` | گزارش‌های بیشتر پروتکل. |

محدودیت‌های احراز هویت و timeout باید عدد صحیح در بازه `1..2147483647` باشند؛ اندازه جدول
replay نیز باید در ظرفیت قابل نمایش میزبان جا شود. تنظیم نامعتبر startup را رد می‌کند.
پر شدن ظرفیت درخواست تازه مربوط را رد می‌کند؛ برای باز کردن جا هیچ علامت replay منقضی‌نشده‌ای حذف نمی‌شود.

پیش از پایان احراز هویت، هر اتصال حداکثر ۶۵۵۳۶ بایت منطقی ورودی در ۲۵۶ buffer نگه می‌دارد.
صف ورودی و صف پاسخ، هر کدام سقف ۲ MiB بایت منطقی، ۸ MiB هزینه تخصیص buffer و ۱۰۲۴ ورودی
دارند؛ buffer فعالِ خارج‌شده از صف تا آزاد شدن همچنان حساب می‌شود. این سقف‌های ثابت مکمل
بودجه مشترک احراز هویت‌اند و تضمین سقف RSS یا کل حافظه فرایند نیستند.

## Fallback و جلوگیری از replay

با `fallback-node-name` یک شاخه stream موجود را برای اعتبارنامه ناشناخته یا احراز هویت
در دسترس‌نبودنی انتخاب کنید. prefix بررسی‌شده و بقیه بایت‌ها دقیق و به همان ترتیب بازپخش
می‌شوند. هویت ردشده به شاخه fallback منتشر نمی‌شود و UserController داخلی در این مسیر نیست.

پس از شناسایی احراز هویت VMess، fallback دیگر مجاز نیست. AuthID تکراری یا منقضی، session
تکراری، tag نامعتبر، header احراز‌شده خراب، فرمان پشتیبانی‌نشده پس از احراز هویت، رد منابع یا
پایان مهلت handshake اتصال مربوط را می‌بندند و به fallback تبدیل نمی‌شوند.

جدول replay بین همه workerهای این node مشترک است. بازه پذیرش زمان AuthID برابر ۱۲۰ ثانیه
در هر جهت با احتساب مرزهاست؛ علامت آن تا پایان تمام بازه اعتبار، حتی برای timestamp آینده،
باقی می‌ماند. عقب رفتن ساعت نمی‌تواند درخواست منقضی‌شده را دوباره معتبر کند. هویت session
شامل UUID، کلید بدنه درخواست و IV است و بازه replay آن سه دقیقه است. هر نمونه جداگانه
VmessServer دامنه replay مستقل دارد.
