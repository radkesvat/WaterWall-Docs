# HeaderClient

`HeaderClient` روی اولین payload مسیر upstream هر line عادی layer-4، یک header
یک‌باره prepend می‌کند.

این نود معمولا برای یکی از دو کار زیر استفاده می‌شود:

- عبور دادن metadata مسیریابی WaterWall به یک `HeaderServer` جفت‌شده
- اضافه کردن header پروتکل HAProxy PROXY قبل از رسیدن ترافیک به گیرنده‌ای که PROXY protocol را می‌فهمد

`HeaderClient` socket باز نمی‌کند و line نمی‌سازد. فقط اولین upstream payload را تغییر می‌دهد و بعد از آن برای بقیه عمر line شفاف عبور می‌کند.

## عملکرد

- `settings.data` را لازم دارد تا format header یک‌باره را انتخاب کند.
- در upstream `Init`، state محلی line را مقداردهی می‌کند.
- upstream `Init` را بلافاصله به `next` forward می‌کند.
- فقط روی اولین upstream payload، header تنظیم‌شده را prepend می‌کند.
- از header قدیمی دو بایتی port مخصوص WaterWall پشتیبانی می‌کند.
- از headerهای IPv4-only مربوط به HAProxy PROXY protocol v1 و v2 با یک frontend IPv4 تنظیم‌شده پشتیبانی می‌کند.
- همه payloadهای upstream بعدی را بدون تغییر عبور می‌دهد.
- downstream payload، `Est`، `Pause` و `Resume` را بدون تغییر عبور می‌دهد.
- قبل از forward کردن `Finish` در هر جهت، state محلی خودش را destroy می‌کند.

## جایگاه رایج

header داخلی WaterWall برای port:

```text
TcpListener -> HeaderClient -> ... -> HeaderServer -> TcpConnector
```

header پروتکل PROXY برای receiver ریموت سازگار با PROXY:

```text
sender side:   TcpListener -> HeaderClient -> TcpConnector
receiver side: HeaderServer/HAProxy/nginx/backend
```

در mode پروتکل PROXY، peer واقعی بعدی باید انتظار HAProxy PROXY protocol داشته
باشد. این peer می‌تواند `HeaderServer` با `settings.override =
"proxy-protocol->source-fields"` یا یک backend دیگر سازگار با PROXY باشد. این
mode همچنین `settings.frontend-ipv4` را لازم دارد؛ این مقدار باید frontend IPv4ای
باشد که clientها به آن وصل می‌شوند، نه address backend.

## مثال‌های کاربردی

### حفظ port listener پذیرفته‌شده در یک relay

این استفاده کلاسیک `HeaderClient` همراه با `HeaderServer` است. یک instance سمت client روی چند public port گوش می‌دهد، اما همه ترافیک را به یک relay port روی instance دیگر WaterWall می‌فرستد. سمت relay، port اصلی پذیرفته‌شده را داخل `dest_context->port` برمی‌گرداند و بعد به service محلی وصل می‌شود.

سمت client:

```json
[
  {
    "name": "public-listener",
    "type": "TcpListener",
    "settings": {
      "address": "0.0.0.0",
      "port": [80, 443, 8443]
    },
    "next": "header-client"
  },
  {
    "name": "header-client",
    "type": "HeaderClient",
    "settings": {
      "data": "src_context->port"
    },
    "next": "relay-connector"
  },
  {
    "name": "relay-connector",
    "type": "TcpConnector",
    "settings": {
      "address": "198.51.100.20",
      "port": 9000
    }
  }
]
```

سمت relay:

```json
[
  {
    "name": "relay-listener",
    "type": "TcpListener",
    "settings": {
      "address": "0.0.0.0",
      "port": 9000
    },
    "next": "header-server"
  },
  {
    "name": "header-server",
    "type": "HeaderServer",
    "settings": {
      "override": "dest_context->port"
    },
    "next": "local-service"
  },
  {
    "name": "local-service",
    "type": "TcpConnector",
    "settings": {
      "address": "127.0.0.1",
      "port": "dest_context->port"
    }
  }
]
```

با این چیدمان، اگر سمت client اتصال را روی public port `443` بپذیرد، آن اتصال به `198.51.100.20:9000` relay می‌شود و بعد سمت relay به `127.0.0.1:443` وصل می‌شود.

### اجبار همه ترافیک relay شده به یک backend port

وقتی سمت relay انتظار header دو بایتی WaterWall را دارد، اما مقدار باید ثابت باشد و از line context کپی نشود، از مقدار عددی برای `settings.data` استفاده کنید.

```json
{
  "name": "header-client",
  "type": "HeaderClient",
  "settings": {
    "data": 8443
  },
  "next": "relay-connector"
}
```

در سمت جفت‌شده، `HeaderServer` را طوری تنظیم کنید که این header را بخواند و داخل `dest_context->port` بنویسد؛ سپس `TcpConnector` از `"dest_context->port"` استفاده کند. هر line از این client، backend port برابر `8443` را انتخاب می‌کند.

### ارسال PROXY protocol v2 به backend محلی

وقتی peer واقعی بعدی HAProxy، nginx، Envoy یا service دیگری است که قبل از payload اصلی client انتظار PROXY protocol دارد، از `"proxy-protocol"` استفاده کنید.

```json
[
  {
    "name": "public-listener",
    "type": "TcpListener",
    "settings": {
      "address": "0.0.0.0",
      "port": 443
    },
    "next": "proxy-header"
  },
  {
    "name": "proxy-header",
    "type": "HeaderClient",
    "settings": {
      "data": "proxy-protocol",
      "frontend-ipv4": "203.0.113.10"
    },
    "next": "backend"
  },
  {
    "name": "backend",
    "type": "TcpConnector",
    "settings": {
      "address": "192.0.2.50",
      "port": 443
    }
  }
]
```

`"proxy-protocol"` alias برای `"proxy-protocol-v2"` است. PROXY protocol v2 فشرده، binary، و default ترجیحی است وقتی backend از آن پشتیبانی می‌کند. مقدار `frontend-ipv4` را برابر IPv4ای بگذارید که client برای رسیدن به این frontend واتروال استفاده می‌کند. آن را `0.0.0.0` یا address backend نگذارید.

### ارسال PROXY protocol v1 برای receiverهای قدیمی

بعضی receiverهای قدیمی فقط format متنی PROXY protocol را قبول می‌کنند. برای این حالت از `"proxy-protocol-v1"` استفاده کنید:

```json
{
  "name": "proxy-header",
  "type": "HeaderClient",
  "settings": {
    "data": "proxy-protocol-v1",
    "frontend-ipv4": "203.0.113.10"
  },
  "next": "backend"
}
```

receiver باید طوری تنظیم شده باشد که انتظار PROXY protocol v1 داشته باشد. برای
receiverهای WaterWall از `HeaderServer` با `settings.override =
"proxy-protocol->source-fields"` استفاده کنید.

## فیلدهای لازم

فیلدهای top-level:

| فیلد | نوع | توضیح |
| --- | --- | --- |
| `name` | string | نام دلخواه کاربر. باید داخل config یکتا باشد. |
| `type` | string | باید دقیقا `"HeaderClient"` باشد. |
| `settings` | object | اجباری است و باید `data` داشته باشد. |
| `next` | string | نود layer-4 stream بعدی که stream دارای header را دریافت می‌کند. |

فیلدهای لازم داخل `settings`:

| فیلد | نوع | توضیح |
| --- | --- | --- |
| `data` | number یا string | format header و dataای که داخل اولین upstream payload encode می‌شود. |

فیلدهای شرطی داخل `settings`:

| فیلد | نوع | توضیح |
| --- | --- | --- |
| `frontend-ipv4` | string | وقتی `data` برابر `"proxy-protocol"`، `"proxy-protocol-v1"` یا `"proxy-protocol-v2"` باشد اجباری است. این مقدار باید frontend IPv4ای باشد که clientها به آن وصل می‌شوند. |

`HeaderClient` باید نود قبلی هم داشته باشد. این نود برای ابتدا یا انتهای chain نیست.

## `settings.data`

مقدارهای قابل قبول:

| مقدار | معنی |
| --- | --- |
| `1` تا `65535` | همین port ثابت را به عنوان header دو بایتی WaterWall encode می‌کند. |
| `"src_context->port"` | مقدار `line->routing_context.src_ctx.port` را به عنوان header دو بایتی WaterWall encode می‌کند. |
| `"line->src_ctx->port"` | alias سازگار با `"src_context->port"`. |
| `"proxy-protocol"` | یک header PROXY protocol v2 emit می‌کند. |
| `"proxy-protocol-v1"` | یک header PROXY protocol v1 emit می‌کند. |
| `"proxy-protocol-v2"` | یک header PROXY protocol v2 emit می‌کند. |

اگر `data` وجود نداشته باشد، string ناشناخته باشد، یا عدد خارج از بازه `1` تا `65535` باشد، startup شکست می‌خورد.

## رفتار روی Wire

برای modeهای عددی و source-port، اولین upstream payload از این حالت:

```text
payload
```

به این حالت تبدیل می‌شود:

```text
2-byte port header | payload
```

port header یک مقدار شانزده‌بیتی big-endian است و فقط یک بار برای هر line ارسال می‌شود. payloadهای upstream بعدی دقیقا بدون تغییر forward می‌شوند.

برای modeهای PROXY protocol، `HeaderClient` یک header TCP PROXY نوع IPv4 emit می‌کند. source IP از `line->routing_context.src_ctx` می‌آید. destination IP از `settings.frontend-ipv4` می‌آید؛ برای destination داخل PROXY از `dest_ctx` استفاده نمی‌شود، چون `TcpConnector` ممکن است قبل از ارسال اولین payload، `dest_ctx` را به backendی که قرار است به آن dial کند تغییر دهد.

portهای انتخاب‌شده:

- source port: اگر `routing_context.peer_source_port` وجود داشته باشد همان، وگرنه `src_ctx.port`
- destination port: اگر `routing_context.local_listener_port` وجود داشته باشد همان، وگرنه `src_ctx.port`

اگر هنگام رسیدن اولین upstream payload، source address از نوع IPv4 نباشد، v1 مقدار `PROXY UNKNOWN` و v2 یک header LOCAL/UNSPEC emit می‌کند. headerهای IPv6 PROXY و TLVهای PROXY protocol emit نمی‌شوند.

اگر اولین upstream payload خالی باشد، همین callback اولین payload باز هم header تنظیم‌شده را ارسال می‌کند.

## نکته‌های Routing Context

`HeaderClient` فقط اطلاعاتی را serialize می‌کند که از قبل روی line موجود است. domain resolve نمی‌کند و فیلد address گمشده نمی‌سازد.

برای mode قدیمی header دو بایتی WaterWall، معمولا جریان این است:

- `TcpListener`، port listener محلی پذیرفته‌شده را داخل `src_ctx.port` می‌گذارد
- `HeaderClient` می‌تواند آن مقدار را داخل header دو بایتی کپی کند
- `HeaderServer` می‌تواند آن را در سمت دیگر داخل `dest_ctx.port` بازسازی کند

برای mode پروتکل PROXY، source address context باید قابل تبدیل به socket address نوع IPv4 باشد. destination address داخل header PROXY همان `frontend-ipv4` تنظیم‌شده است، نه `dest_ctx`. این عمدی است: در chainهای رایج مثل `TcpListener -> HeaderClient -> TcpConnector`، معمولا `dest_ctx` backend انتخاب‌شده توسط `TcpConnector` را توصیف می‌کند، نه frontend addressای که client به آن رسیده است.

## استفاده با HeaderServer

`HeaderClient` را با `HeaderServer` در یکی از modeهای سازگار استفاده کنید.

برای header دو بایتی WaterWall:

```json
{
  "name": "header-server",
  "type": "HeaderServer",
  "settings": {
    "override": "dest_context->port"
  },
  "next": "connector"
}
```

برای برگرداندن source fields از PROXY protocol:

```json
{
  "name": "header-server",
  "type": "HeaderServer",
  "settings": {
    "override": "proxy-protocol->source-fields"
  },
  "next": "connector"
}
```

این حالت را با `HeaderClient.data` برابر `"proxy-protocol"`،
`"proxy-protocol-v1"` یا `"proxy-protocol-v2"` جفت کنید. reader سمت server برای
PROXY فعلا فقط IPv4 است و فقط `src_ctx.ip` و `src_ctx.port` را اعمال می‌کند.

اگر `HeaderServer.settings.override` عدد باشد، server در upstream `Init` یک destination port ثابت تنظیم می‌کند و هیچ headerی مصرف نمی‌کند. در آن حالت اگر قبلش `HeaderClient` بگذارید، header دو بایتی به عنوان application payload باقی می‌ماند.

## رفتار جهت‌ها

| جهت | رفتار |
| --- | --- |
| upstream `Init` | state محلی را initialize می‌کند و به `next` forward می‌کند. |
| اولین upstream payload | header تنظیم‌شده را prepend می‌کند و به `next` می‌فرستد. |
| payloadهای upstream بعدی | بدون تغییر به `next` می‌روند. |
| upstream pause/resume | به `next` forward می‌شود. |
| downstream payload | بدون تغییر به نود قبلی برمی‌گردد. |
| downstream `Est` / pause / resume | به نود قبلی forward می‌شود. |

callbackهای `UpStreamEst` و `DownStreamInit` برای این نود غیرفعال هستند.

## Finish

در upstream `Finish`، `HeaderClient` state محلی خودش را destroy می‌کند و finish را به `next` forward می‌کند.

در downstream `Finish`، state محلی destroy می‌شود و finish به نود قبلی forward می‌شود.

این tunnel چون line را خودش نمی‌سازد، `lineDestroy()` صدا نمی‌زند.

## محدودیت‌ها و Padding

| مقدار | اندازه |
| --- | --- |
| header دو بایتی WaterWall برای port | `2 bytes` |
| header پروتکل PROXY v1 | حداکثر `108 bytes` |
| header پروتکل PROXY v2 | `16` یا `28 bytes` |
| `required_padding_left` | `108 bytes` |

این نود چون بزرگ‌ترین header پشتیبانی‌شده را با `sbufShiftLeft()` prepend می‌کند، مقدار `required_padding_left = 108` اعلام می‌کند.

## نکته‌ها و محدودیت‌ها

- فقط در chainهای layer-4 stream استفاده شود.
- نباید به عنوان state مشترک packet-line استفاده شود.
- header دو بایتی port فقط metadata داخلی WaterWall است، نه یک protocol عمومی.
- modeهای PROXY protocol فعلا IPv4-only هستند.
- destination IP در PROXY protocol از `settings.frontend-ipv4` می‌آید، نه `dest_ctx`.
- اگر یک listener روی چند frontend IPv4 ترافیک قبول کند، یک مقدار ثابت `frontend-ipv4` ممکن است همه اتصال‌های پذیرفته‌شده را درست توصیف نکند.
- مقدار encode شده هنگام رسیدن اولین upstream payload خوانده می‌شود.
- فقط اولین upstream payload تغییر می‌کند و مسیر response شفاف است.
