# TcpOverUdpServer

`TcpOverUdpServer` peer سمت server برای `TcpOverUdpClient` است. این نود datagramهای KCP packet-preserving را از نود قبلی می‌گیرد، byte stream اصلی را بازسازی می‌کند، و آن stream را به نود بعدی forward می‌کند. پاسخ‌های نود بعدی دوباره به datagramهای KCP رمزگذاری می‌شوند و به سمت packet side قبلی downstream ارسال می‌شوند.

این نود معمولاً با `TcpOverUdpClient` در سمت مقابل استفاده می‌شود.

## جایگاه رایج

سمت server:

```text
UdpListener -> TcpOverUdpServer -> TcpConnector
UdpListener -> TcpOverUdpServer -> MuxServer -> TcpConnector
```

سمت client متناظر:

```text
TcpListener -> TcpOverUdpClient -> UdpConnector
TcpListener -> MuxClient -> TcpOverUdpClient -> UdpConnector
```

سمت قبلی `TcpOverUdpServer` باید datagram boundary را حفظ کند. سمت بعدی stream-facing است.

## نمونه پایه

```json
{
  "name": "tcp-over-udp-server",
  "type": "TcpOverUdpServer",
  "settings": {
    "fec": false,
    "kcp-send-window": 8192,
    "kcp-recv-window": 8192,
    "ping-interval-ms": 10000,
    "no-recv-timeout-ms": 30000
  },
  "next": "service-out"
}
```

connector سرویس متناظر:

```json
{
  "name": "service-out",
  "type": "TcpConnector",
  "settings": {
    "address": "127.0.0.1",
    "port": 8080
  }
}
```

## نمونه با FEC

```json
{
  "name": "tcp-over-udp-server",
  "type": "TcpOverUdpServer",
  "settings": {
    "fec": true,
    "fec-data-shards": 10,
    "fec-parity-shards": 3
  },
  "next": "service-out"
}
```

تنظیمات FEC باید دقیقاً با سمت `TcpOverUdpClient` یکسان باشد.

## فیلدهای ضروری

`settings` اختیاری است. اگر وجود نداشته باشد یا object نباشد، از مقادیر پیش‌فرض استفاده می‌شود.

در استفاده معمول، `next` لازم است و باید به مسیر stream-side service که payload بازسازی‌شده را دریافت می‌کند اشاره کند.

## تنظیمات اختیاری

`TcpOverUdpServer` از همان نام‌های setting و مقادیر پیش‌فرض `TcpOverUdpClient` استفاده می‌کند.

| فیلد | پیش‌فرض | اعتبارسنجی | توضیح |
| --- | --- | --- | --- |
| `fec` | `false` | boolean | فعال‌سازی Reed-Solomon forward error correction روی datagramهای KCP. |
| `fec-data-shards` | `10` | مثبت، با مجموع shardها حداکثر `255` | تعداد data shard در هر FEC block. فقط وقتی `fec` فعال است استفاده می‌شود. |
| `fec-parity-shards` | `3` | مثبت، با مجموع shardها حداکثر `255` | تعداد parity shard در هر FEC block. فقط وقتی `fec` فعال است استفاده می‌شود. |
| `kcp-nodelay` | `true` | boolean | فعال‌سازی KCP nodelay mode. |
| `kcp-interval-ms` | `10` | `10..5000` | فاصله update شدن KCP. |
| `kcp-resend` | `2` | `>= 0` | آستانه fast-resend در KCP. |
| `kcp-no-congestion-control` | `true` | boolean | غیرفعال کردن congestion control در KCP. |
| `kcp-send-window` | `8192` | `>= 1` | send window بر حسب segment. |
| `kcp-recv-window` | `8192` | `>= 1` | receive window بر حسب segment. |
| `kcp-initial-cwnd` | نصف `kcp-send-window` | `1..kcp-send-window` | congestion window اولیه KCP. |
| `kcp-rx-minrto-ms` | `30` | `>= 1` | حداقل retransmission timeout. |
| `kcp-send-buffer-limit` | `0` | `>= 0` | آستانه backpressure. مقدار `0` حد را از local send window + remote window + `10` محاسبه می‌کند. |
| `ping-interval-ms` | `10000` | `>= 1` | مدت idle receive قبل از ارسال ping frame داخلی. |
| `no-recv-timeout-ms` | `30000` | بزرگ‌تر از `ping-interval-ms` | مدت idle receive قبل از بستن line. |

## مدل KCP transport

در upstream `Init`، server per-line state را initialize می‌کند، یک session KCP می‌سازد، timer loop KCP را شروع می‌کند، در صورت فعال بودن FEC state آن را می‌سازد، یک ping frame داخلی اولیه queue می‌کند، و سپس upstream `Init` را به نود stream-side بعدی forward می‌کند.

وقتی payload packet از نود قبلی می‌رسد:

1. در صورت فعال بودن، FEC decoding اعمال می‌شود.
2. KCP datagram را می‌گیرد.
3. payloadهای کامل‌شده KCP drain می‌شوند.
4. flag یک‌بایتی داخلی حذف می‌شود.
5. data frameها upstream به نود بعدی به عنوان payload stream بازسازی‌شده forward می‌شوند.

وقتی payload stream از نود بعدی برمی‌گردد:

1. payload به chunkهایی با حداکثر اندازه KCP write MTU موثر تقسیم می‌شود.
2. هر chunk data flag یک‌بایتی prefix می‌گیرد.
3. chunk فریم‌شده از طریق KCP ارسال می‌شود.
4. datagramهای خروجی KCP downstream به packet side قبلی forward می‌شوند.

## flagهای داخلی

داخل payload KCP، `TcpOverUdpServer` از همان flagهای frame یک‌بایتی سمت client استفاده می‌کند:

| Flag | معنی |
| --- | --- |
| `0x00` | data frame. byteهای بعد از flag همان payload stream واقعی هستند. |
| `0xF0` | ping frame. به عنوان نشانگر keepalive داخلی استفاده می‌شود. |
| `0xFF` | close frame. درخواست shutdown برای line paired. |

data frame خالی drop می‌شود.

## MTU و padding

KCP MTU از `GLOBAL_MTU_SIZE` می‌آید. با فعال بودن FEC، 8 بایت header بیرونی FEC از KCP MTU و بودجه write stream کم می‌شود.

بودجه موثر payload برای write stream:

```text
GLOBAL_MTU_SIZE - 20 - 8 - 24 - 1 - fec_overhead
```

نود `required_padding_left = 1` را advertise می‌کند تا بتواند flag frame داخلی را قبل از دادن داده به KCP prepend کند.

## رفتار FEC

با `fec: true`، datagramهای خروجی KCP داخل packetهای Reed-Solomon FEC wrap می‌شوند. data shardها فوراً ارسال می‌شوند و parity shardها بعد از هر block data shard کامل ارسال می‌شوند.

در receive، decoder:

- datagramهای KCP wrap‌شده با FEC را می‌پذیرد
- data shardهای معتبر را به KCP می‌دهد
- تلاش می‌کند datagramهای KCP گم‌شده را از parity shardها بازسازی کند
- packetهای FEC نامعتبر را drop می‌کند

FEC در این pair symmetric است. آن را با shard count یکسان در هر دو peer فعال و تنظیم کنید.

## Backpressure

اگر داده queue ارسال KCP از `kcp-send-buffer-limit` بیشتر شود، server یک upstream `Pause` به سمت stream بعدی schedule می‌کند. وقتی خروجی KCP drain شود، callback خروجی KCP upstream `Resume` را schedule می‌کند.

این از رشد بی‌نهایت queue جلوگیری می‌کند وقتی packet side نمی‌تواند به سرعت کافی drain کند.

## رفتار Close و timeout

اگر سمت stream بعدی finish شود، `TcpOverUdpServer`:

1. upstream را به عنوان closed علامت می‌زند تا callbackهای re-entrant به سمت finished برنگردند
2. یک close frame داخلی از طریق KCP می‌فرستد
3. خروجی KCP را flush می‌کند
4. per-line state محلی را destroy می‌کند
5. downstream `Finish` را به packet side forward می‌کند

اگر close frame از peer برسد، server state محلی را destroy می‌کند، سمت stream را finish می‌کند، و سپس اگر line هنوز زنده باشد سمت packet را finish می‌کند.

اگر برای مدت `ping-interval-ms` هیچ receive activity نباشد، یک ping frame ارسال می‌شود. اگر inactivity receive از `no-recv-timeout-ms` بیشتر شود، line بسته می‌شود.

## اشتباه‌های رایج

- `TcpOverUdpServer` را از نود stream-only قبلی تغذیه نکنید. سمت قبلی باید packet boundary را حفظ کند.
- بدون `TcpOverUdpClient` متناظر استفاده نکنید.
- FEC را فقط در یک سمت فعال نکنید.
- تعداد FEC shard را در دو سمت mismatch نکنید.
- `TcpOverUdpServer` را chain end فرض نکنید؛ این نود payload stream بازسازی‌شده را به `next` forward می‌کند.
