# Disturber {#disturber}

## نمای کلی {#overview}

`Disturber` تونلی آزمایشی برای شبیه‌سازی شرایط نامطلوب شبکه در یک زنجیره از WaterWall است. بدون نیاز به ابزار خارجی می‌تواند قطع اتصال، از دست رفتن payload، خرابی داده، تکرار، جابه‌جایی ترتیب، تأخیر و dead-hang ایجاد کند.

از این گره برای stress test تونل‌هایی استفاده کنید که باید روی مسیرهای ناپایدار تاب بیاورند؛ مانند mux، TCP-over-UDP، HTTP، TLS، بسته transport، منطق اتصال مجدد و تونل‌های سفارشی.

:::warning
`Disturber` عمداً ترافیک را مختل می‌کند. برای تست، debug و سنجش پایداری مناسب است، نه عبور عادی ترافیک در محیط production.
:::

## جایگاه معمول در زنجیره {#typical-placement}

### بررسی بازیابی پس از گم‌شدن و جابه‌جایی دیتاگرام‌ها {#check-recovery-from-datagram-loss-and-reordering}

<a id="بررسی-بازیابی-پس-از-گمشدن-و-جابهجایی-datagram"></a>

Disturber را سمت دیتاگرام کدشده‌ی جفت KCP بگذارید. سطر اول دو codec را در یک process
آزمایش می‌کند؛ دو سطر بعد همان آزمایش را روی مسیر socket UDP نشان می‌دهند:

```text
local:  TesterClient -> KcpClient -> Disturber -> KcpServer -> TesterServer
sender: TesterClient -> KcpClient -> Disturber -> UdpConnector
peer:   UdpListener -> KcpServer -> TesterServer
```
هر دو tester در حالت جریان بایتی باقی می‌مانند؛ KCP جریان بایت را به دیتاگرامهای carrier
تبدیل و پیش از verification بازسازی می‌کند. `chunk-count` هر دو tester باید یکسان
باشد و `UdpConnector` به listener سمت مقابل وصل شود. با loss، duplication، reordering
یا delay بازیابی KCP را بررسی کنید. اگر loss را پیش از `KcpClient` قرار دهید،
بایت برنامه قبل از محافظت KCP حذف شده است.

[fixture کامل بازیابی](https://github.com/radkesvat/WaterWall/blob/main/tests/cases/kcp_disturber_roundtrip/config.json)
از ۹ chunk، پانزده درصد loss و delay/reordering محدود استفاده می‌کند و همه گره‌های
حالت درون‌پردازه‌ای را دارد. corruption و forced-close را برای آزمون شکست جدا نگه
دارید؛ موفقیت آزمون بازیابی به معنی بازیابی از هر اختلال دلخواه نیست.

## نمونهٔ کاربردی ساده {#minimal-practical-example}

این‌ها قطعه‌های پیکربندی گره هستند؛ گره‌های همسایهٔ ارجاع‌شده را در پیکربندی پیرامون آن‌ها تعریف کنید.

### نمونهٔ پیکربندی {#configuration-example}

<a id="نمونه-تنظیم"></a>

```json
{
  "name": "disturber",
  "type": "Disturber",
  "settings": {
    "disturb-upstream": true,
    "disturb-downstream": true,
    "chance_instant_close": 5,
    "chance_middle_close": 2,
    "chance_payload_corruption": 3,
    "chance_payload_loss": 10,
    "chance_payload_duplication": 2,
    "chance_payload_out_of_order": 4,
    "chance_payload_delay": 15,
    "chance_connection_deadhang": 1,
    "delay_min_ms": 50,
    "delay_max_ms": 300
  },
  "next": "next-node"
}
```

فقط از دست رفتن بسته:

```json
{
  "name": "loss",
  "type": "Disturber",
  "settings": {
    "disturb-upstream": true,
    "disturb-downstream": false,
    "chance_payload_loss": 100
  },
  "next": "receiver"
}
```

## پیکربندی {#configuration}

### فیلدهای الزامی {#required-fields}

<a id="فیلدهای-لازم"></a>

فیلدهای سطح اصلی:

| فیلد | نوع | توضیح |
| --- | --- | --- |
| `name` | string | نام دلخواه گره که باید در فایل پیکربندی یکتا باشد. |
| `type` | string | باید دقیقاً `"Disturber"` باشد. |
| `next` | string | برای استفاده عملی لازم است. گره بعدی ترافیک upstream را می‌گیرد. |

`settings` اختیاری است. اگر آن را ننویسید، همه chanceها مقدار پیش‌فرض خواهند داشت.

### تنظیمات اختیاری {#optional-settings}

<a id="تنظیمات-اختیاری"></a>

کنترل جهت‌ها:

| گزینه | نوع | پیش‌فرض | توضیح |
| --- | --- | --- | --- |
| `disturb-upstream` | boolean | `true` | اعمال اختلال روی init و payload در جهت upstream. |
| `disturb-downstream` | boolean | `false` | اعمال اختلال روی init و payload در جهت downstream. |

فیلدهای chance:

| گزینه | نوع | پیش‌فرض | توضیح |
| --- | --- | --- | --- |
| `chance_instant_close` | درصد integer | `0` | احتمال بستن مسیر هنگام رسیدن init در جهت فعال. |
| `chance_middle_close` | درصد integer | `0` | احتمال بستن هنگام مدیریت payload جهت فعال. |
| `chance_payload_corruption` | درصد integer | `0` | احتمال تغییر دادن بایت‌های payload پیش از ارسال. |
| `chance_payload_loss` | درصد integer | `0` | احتمال دور انداختن payload فعلی. |
| `chance_payload_duplication` | درصد integer | `0` | احتمال ساخت یک کپی اضافه از payload. |
| `chance_payload_out_of_order` | درصد integer | `0` | احتمال نگه داشتن payload فعلی و آزاد کردن آن در حوالی payload بعدی. |
| `chance_payload_delay` | درصد integer | `0` | احتمال به تأخیر انداختن payload فعلی. |
| `chance_connection_deadhang` | درصد integer | `0` | احتمال قرار دادن جهت در dead-hang mode. |

فیلدهای delay:

| گزینه | نوع | پیش‌فرض | توضیح |
| --- | --- | --- | --- |
| `delay_min_ms` | integer | `0` | کمترین تأخیر هنگام فعال شدن delay برای payload. مقادیر منفی به `0` محدود می‌شوند. |
| `delay_max_ms` | integer | `0` | بیشترین تأخیر هنگام فعال شدن delay برای payload. مقادیر کمتر از `delay_min_ms` به همان مقدار محدود می‌شوند. |

مقادیر `<= 0` هرگز رخ نمی‌دهند و مقادیر `>= 100` همیشه رخ می‌دهند. مقادیر `1`
تا `99` برای هر نوع رخداد، line و direction از gate درصدی شبه‌تصادفی
غیررمزنگاری مستقل استفاده می‌کنند. یک اختلال جریان اختلال دیگر را جلو نمی‌برد
و نتیجه‌ها می‌توانند به‌طور طبیعی پشت سر هم رخ دهند.

## کاربرد و رفع اشکال {#usage-and-troubleshooting}

### نکته‌ها و ملاحظات {#notes-and-caveats}

<a id="نکتهها"></a>

- ترکیب چند chance با مقدار بالا می‌تواند ترافیک بسیار آشفته‌ای بسازد.
- مقدار `chance_payload_duplication = 100` برای تست پروتکل‌های مقاوم در برابر داده تکراری مفید است، اما می‌تواند حجم ترافیک را به‌سرعت چند برابر کند.
- رفتارهای delay و out-of-order از callback‌های زمان‌بندی‌شده استفاده می‌کنند و می‌توانند باگ‌های re-entrancy و lifetime را در تونل‌های اطراف آشکار کنند.
- این گره framing اضافه نمی‌کند و `required_padding_left = 0` دارد.
- در حال حاضر callback مربوط به API فقط پیام API را می‌گیرد و بافر‌ش را برای استفاده مجدد برمی‌گرداند؛ امکان تنظیم در runtime وجود ندارد.

## رفتار پیشرفته {#advanced-behavior}

### مراحل پردازش payload {#payload-pipeline}

<a id="پردازش-payload"></a>

برای هر payload در جهتی که اختلال روی آن فعال است، `Disturber` موارد زیر را به ترتیب بررسی می‌کند:

1. اگر جهت از قبل وارد dead-hang شده باشد، payload دور ریخته می‌شود.
2. `chance_middle_close`
3. `chance_payload_loss`
4. `chance_payload_duplication`
5. `chance_payload_corruption`
6. آزاد کردن payload نگه‌داشته‌شده برای ایجاد ترتیب نادرست
7. `chance_payload_out_of_order`
8. `chance_payload_delay`
9. `chance_connection_deadhang`
10. ارسال عادی

بعضی بررسی‌ها pipeline را همان‌جا متوقف می‌کنند. برای مثال، در payload loss بافر دور ریخته می‌شود و callback برمی‌گردد. Duplication می‌تواند با بررسی‌های بعدی ترکیب شود، زیرا پیش از ادامه pipeline یک بافر اضافه می‌سازد.

### جزئیات اختلال‌ها {#disturbance-details}

<a id="جزئیات-disturbance"></a>

#### بستن فوری {#instant-close}

وقتی init از upstream برسد و `disturb-upstream` فعال باشد، `chance_instant_close` ممکن است به‌جای فرستادن init به `next`، سمت قبلی را ببندد.

وقتی init از downstream برسد و `disturb-downstream` فعال باشد، `chance_instant_close` ممکن است به‌جای فرستادن init به گره قبلی، سمت next را ببندد.

#### بستن حین انتقال {#middle-close}

وقتی `chance_middle_close` روی یک line عادی رخ دهد، payload فعلی دور ریخته می‌شود، وضعیت محلی Disturber برای line از بین می‌رود و هر دو جهت finish می‌شوند.

#### از دست رفتن payload {#payload-loss}

وقتی `chance_payload_loss` رخ دهد، بافر payload فعلی برای استفاده مجدد برگردانده می‌شود و داده عبور نمی‌کند.

#### تکرار {#duplication}

وقتی `chance_payload_duplication` رخ دهد، `Disturber` یک کپی از بافر می‌سازد و ارسال آن را در همان جهت زمان‌بندی می‌کند. بررسی‌های بعدی همچنان می‌توانند payload اصلی را تغییر دهند.

#### خراب‌کردن داده {#corruption}

وقتی `chance_payload_corruption` رخ دهد، چند بایت تصادفی از payload فعلی با XOR تغییر می‌کنند. برای payload‌های غیرخالی، پیاده‌سازی حداکثر حدود 10 درصد داده را خراب می‌کند و دست‌کم یک بایت تغییر می‌یابد.

#### تحویل خارج از ترتیب {#out-of-order-delivery}

`Disturber` برای هر line برای هر جهت حداکثر یک payload نگه می‌دارد.

وقتی out-of-order رخ دهد و payload نگه‌داشته‌شده‌ای وجود نداشته باشد، payload فعلی ذخیره می‌شود و فوراً عبور نمی‌کند. با رسیدن payload بعدی، داده نگه‌داشته‌شده در حوالی آن آزاد می‌شود تا یک جابه‌جایی ساده در ترتیب ایجاد شود.

اگر وضعیت مربوط به line در حالی از بین برود که payload‌ی هنوز نگه داشته شده است، بافر آن برای استفاده مجدد برگردانده می‌شود.

#### تأخیر {#delay}

وقتی `chance_payload_delay` رخ دهد، تأخیری تصادفی میان `delay_min_ms` و `delay_max_ms`، با احتساب هر دو کران، انتخاب می‌شود. سپس ارسال payload روی همان line برای زمان بعد برنامه‌ریزی می‌شود.

خروجی زمان‌بندی‌شده هم به زنده بودن line و هم به مجوز ارسال این گره نیاز دارد.
دریافت `Finish` مجوز ارسال را در هر دو جهت می‌بندد، حتی اگر یک line عادیِ قرض‌گرفته‌شده
هنگام تخلیهٔ خروجی گره دیگری زنده بماند. بافر و reference مربوط به taskهای در انتظار
تا زمان اجرا یا لغو در مالکیت scheduler می‌مانند؛ `Finish` آن‌ها را فوراً حذف نمی‌کند.
اگر task پس از بسته شدن مجوز اجرا شود، بافر را بدون ارسال بازیافت می‌کند.

#### توقف بدون بسته‌شدن (dead-hang) {#dead-hang}

وقتی `chance_connection_deadhang` رخ دهد، جهت مورد نظر dead-hung علامت می‌خورد. payload فعلی دور ریخته می‌شود، ساختار line باقی می‌ماند و payload‌های بعدی در همان جهت بی‌سروصدا حذف می‌شوند.

این حالت یک اتصال را شبیه‌سازی می‌کند که هنوز زنده به نظر می‌رسد اما پیشرفتی نمی‌کند.

## جزئیات پیاده‌سازی {#implementation-details}

### عملکرد گره {#what-it-does}

<a id="این-نود-چه-میکند"></a>

- تا زمانی که اختلالی از نوع بستن اتصال فعال نشود، callback‌های چرخهٔ عمر را در همان جهت عبور می‌دهد.
- می‌تواند line‌های عادی را هنگام init فوراً ببندد.
- می‌تواند line‌های عادی را هنگام payload forwarding ببندد.
- می‌تواند payload را دور بیندازد یا یک نسخه اضافه از آن بسازد.
- می‌تواند بایت‌های payload را خراب کند.
- می‌تواند یک payload را نگه دارد و بعداً آزاد کند تا رسیدن داده خارج از ترتیب شبیه‌سازی شود.
- می‌تواند payload را برای مدتی تصادفی در بازه تعیین‌شده به تأخیر بیندازد.
- می‌تواند یک جهت را وارد حالت dead-hang کند تا payload‌ها در سکوت دور ریخته شوند.
- در line بسته‌ای‌ها، به‌جای آزاد کردن line بسته‌ای مربوط به worker از dead-hang استفاده می‌کند و قواعد lifetime آن را حفظ می‌کند.

مقدار پیش‌فرض همه فیلدهای chance برابر `0` است. بنابراین، به‌جز تنظیم پیش‌فرض جهت، `Disturber` بدون تنظیم خاص مانند گره‌ای شفاف و عبوری رفتار می‌کند.

### رفتار جهت‌ها {#direction-behavior}

<a id="رفتار-جهتها"></a>

به‌طور پیش‌فرض فقط مسیر upstream مختل می‌شود:

```json
{
  "disturb-upstream": true,
  "disturb-downstream": false
}
```

اگر می‌خواهید مسیر پاسخ نیز مختل شود، `disturb-downstream` را `true` کنید. برای ایجاد اختلال فقط در downstream، مقدار `disturb-upstream` را `false` بگذارید.

اگر اختلال در یک جهت غیرفعال باشد، payload همان جهت بی‌واسطه عبور می‌کند:

| جهت | callback forwarding |
| --- | --- |
| upstream payload | `tunnelNextUpStreamPayload` |
| downstream payload | `tunnelPrevDownStreamPayload` |

`Est`، `Pause` و `Resume` در هر دو جهت به‌صورت عادی عبور داده می‌شوند.

### رفتار line بسته‌ای {#packet-line-behavior}

<a id="رفتار-packet-line"></a>

`Disturber` قواعد line بسته‌ای را در نظر می‌گیرد.

برای line‌های اتصال عادی، اختلال‌هایی که اتصال را می‌بندند می‌توانند `Finish` بفرستند و وضعیت مخصوص آن line را در تونل از بین ببرند. اما Disturber در runtime، line بسته‌ای مربوط به worker را آزاد نمی‌کند. در عوض، instant-close و middle-close جهت آسیب‌دیده را dead-hung می‌کنند و بدون فراخوانی `lineDestroy()` ادامه می‌دهند.

به این ترتیب هم قواعد lifetime مربوط به line بسته‌ای در WaterWall حفظ می‌شود و هم می‌توان سناریوهای بسته loss و blackhole را آزمایش کرد.

### فرادادهٔ گره {#node-metadata}

<a id="متادیتای-نود"></a>

فراداده برگرفته از کد منبع:

این گره با `kNodeFlagBlocksSplice` استفاده از splice را برای کل زنجیره صریحاً غیرفعال می‌کند. این flag حتی در صورت وجود هم‌زمان `kNodeFlagSupportsSplice` اولویت دارد.

| ویژگی | مقدار |
| --- | --- |
| پرچم‌های گره | `kNodeFlagBlocksSplice` |
| `can_have_prev` | `true` |
| `can_have_next` | `true` |
| `layer_group` | `kNodeLayerAnything` |
| `layer_group_prev_node` | `kNodeLayerSameAsNext` |
| `layer_group_next_node` | `kNodeLayerSameAsPrev` |
| `required_padding_left` | `0` بایت |
