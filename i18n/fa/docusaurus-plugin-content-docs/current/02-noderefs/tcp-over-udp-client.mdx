# TcpOverUdpClient

`TcpOverUdpClient` یک stream شبیه TCP را روی مسیر UDP packet-preserving حمل می‌کند. این نود payload استریم را از نود
قبلی می‌گیرد، آن را با KCP به segmentهای datagram تبدیل می‌کند، و خروجی را به نود بعدی می‌فرستد.

این نود معمولا با `TcpOverUdpServer` در سمت مقابل استفاده می‌شود.

## جایگاه رایج

سمت client:

```text
TcpListener -> TcpOverUdpClient -> UdpConnector
TcpListener -> MuxClient -> TcpOverUdpClient -> UdpConnector
```

سمت server:

```text
UdpListener -> TcpOverUdpServer -> TcpConnector
UdpListener -> TcpOverUdpServer -> MuxServer -> TcpConnector
```

نود بعد از `TcpOverUdpClient` باید boundary دیتاگرام‌ها را حفظ کند. مسیر UDP-style کاربرد اصلی این نود است.

## نمونه پایه

```json
{
  "name": "tcp-over-udp-client",
  "type": "TcpOverUdpClient",
  "settings": {
    "fec": false,
    "kcp-send-window": 8192,
    "kcp-recv-window": 8192,
    "ping-interval-ms": 10000,
    "no-recv-timeout-ms": 30000
  },
  "next": "udp-out"
}
```

## نمونه با FEC

```json
{
  "name": "tcp-over-udp-client",
  "type": "TcpOverUdpClient",
  "settings": {
    "fec": true,
    "fec-data-shards": 10,
    "fec-parity-shards": 3
  },
  "next": "udp-out"
}
```

اگر FEC را روشن می‌کنید، باید در هر دو سمت `TcpOverUdpClient` و `TcpOverUdpServer` با shard settingهای یکسان روشن باشد.

## فیلدهای لازم

`settings` اختیاری است. اگر object نباشد یا وجود نداشته باشد، defaultها استفاده می‌شوند.

در استفاده معمول، `next` لازم است و باید به یک transport یا stack که datagram boundary را حفظ می‌کند اشاره کند.

## تنظیمات اختیاری

| فیلد | پیش‌فرض | اعتبارسنجی | توضیح |
| --- | --- | --- | --- |
| `fec` | `false` | boolean | فعال‌سازی Reed-Solomon FEC روی datagramهای KCP. |
| `fec-data-shards` | `10` | positive و مجموع shardها حداکثر `255` | تعداد data shard در هر block. فقط وقتی `fec` روشن است استفاده می‌شود. |
| `fec-parity-shards` | `3` | positive و مجموع shardها حداکثر `255` | تعداد parity shard در هر block. فقط وقتی `fec` روشن است استفاده می‌شود. |
| `kcp-nodelay` | `true` | boolean | فعال‌سازی KCP nodelay. |
| `kcp-interval-ms` | `10` | `10..5000` | فاصله update شدن KCP. |
| `kcp-resend` | `2` | `>= 0` | fast-resend threshold در KCP. |
| `kcp-no-congestion-control` | `true` | boolean | غیرفعال کردن congestion control در KCP. |
| `kcp-send-window` | `8192` | `>= 1` | send window بر حسب segment. |
| `kcp-recv-window` | `8192` | `>= 1` | receive window بر حسب segment. |
| `kcp-initial-cwnd` | نصف `kcp-send-window` | `1..kcp-send-window` | congestion window اولیه. |
| `kcp-rx-minrto-ms` | `30` | `>= 1` | حداقل retransmission timeout در KCP. |
| `kcp-send-buffer-limit` | `0` | `>= 0` | آستانه backpressure. مقدار `0` یعنی local send window + remote window + `10`. |
| `ping-interval-ms` | `10000` | `>= 1` | مدت idle receive قبل از ارسال ping داخلی. |
| `no-recv-timeout-ms` | `30000` | بزرگ‌تر از `ping-interval-ms` | مدت idle receive قبل از بستن line. |

## مدل KCP

در upstream `Init`، client line state را initialize می‌کند، session KCP می‌سازد، timer KCP را شروع می‌کند، در صورت فعال
بودن FEC state می‌سازد، یک ping داخلی queue می‌کند، و سپس `Init` را به نود بعدی forward می‌کند.

payloadهای stream از سمت قبلی به chunkهای مناسب MTU تقسیم می‌شوند. هر chunk یک flag یک‌بایتی داخلی می‌گیرد و سپس وارد
KCP می‌شود. خروجی KCP به صورت datagram به نود بعدی می‌رود.

در مسیر برگشت، datagramهای دریافتی وارد FEC decoder و KCP می‌شوند، payloadهای کامل‌شده خوانده می‌شوند، flag داخلی حذف
می‌شود، و data frameها به صورت stream به سمت نود قبلی برمی‌گردند.

## flagهای داخلی

| Flag | معنی |
| --- | --- |
| `0x00` | data؛ byteهای بعد از flag همان payload واقعی stream هستند. |
| `0xF0` | ping داخلی. |
| `0xFF` | close داخلی. |

data frame خالی drop می‌شود.

## MTU و padding

KCP MTU از `GLOBAL_MTU_SIZE` می‌آید. اگر FEC روشن باشد، 8 بایت header بیرونی FEC از بودجه کم می‌شود.

بودجه موثر payload برای write:

```text
GLOBAL_MTU_SIZE - 20 - 8 - 24 - 1 - fec_overhead
```

عدد `1` همان flag داخلی TcpOverUdp است. نود `required_padding_left = 1` دارد تا بتواند این flag را قبل از داده prepend
کند.

## رفتار FEC

با `fec: true`، datagramهای KCP داخل packetهای Reed-Solomon FEC wrap می‌شوند. data shardها سریع ارسال می‌شوند و بعد از
هر block، parity shardها تولید می‌شوند.

در receive، decoder packetهای معتبر را به KCP می‌دهد، تلاش می‌کند datagramهای گم‌شده را از parity بازسازی کند، و packet
نامعتبر را محافظه‌کارانه drop می‌کند.

پیش‌فرض `10` data shard و `3` parity shard حدود 30 درصد parity اضافه در block کامل ایجاد می‌کند، علاوه بر headerهای FEC.

## Backpressure

اگر queue ارسال KCP از `kcp-send-buffer-limit` بیشتر شود، client سمت stream قبلی را pause می‌کند. وقتی خروجی KCP پایین
بیاید، resume ارسال می‌شود. این کار جلوی رشد بی‌نهایت حافظه در مسیر UDP کند یا congested را می‌گیرد.

## Close و timeout

اگر سمت stream قبلی finish شود، client یک close frame داخلی را از طریق KCP می‌فرستد، KCP را flush می‌کند، state خودش را
destroy می‌کند، و سپس سمت packet بعدی را finish می‌کند.

اگر close frame از peer برسد، client state خودش را destroy می‌کند و هر دو جهت را finish می‌کند.

بعد از `ping-interval-ms` بدون receive activity، ping داخلی ارسال می‌شود. اگر این وضعیت تا `no-recv-timeout-ms` ادامه
داشته باشد، line بسته می‌شود.

## متادیتای نود

| ویژگی | مقدار |
| --- | --- |
| flag | `kNodeFlagNone` |
| previous node | مجاز |
| next node | مجاز؛ در استفاده معمول لازم |
| layer group | `kNodeLayerAnything` |
| `required_padding_left` | `1` |

## اشتباه‌های رایج

- بعد از `TcpOverUdpClient` نود stream-only نگذارید؛ سمت بعدی باید packet boundary را حفظ کند.
- FEC را فقط در یک سمت روشن نکنید.
- shardهای FEC را در دو سمت mismatch نکنید.
- انتظار نداشته باشید KCP/FEC loss شدید یا bursty را جادویی حل کند.
- `no-recv-timeout-ms` را کمتر یا مساوی `ping-interval-ms` نگذارید.
