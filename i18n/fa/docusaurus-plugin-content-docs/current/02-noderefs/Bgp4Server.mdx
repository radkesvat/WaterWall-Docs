# Bgp4Server

`Bgp4Server` peer سمت server برای `Bgp4Client` است. BGP-like frameهای upstream از سمت client را باز می‌کند و payloadهای downstream را در جهت معکوس می‌پیچد.

این نود باید با `Bgp4Client` استفاده شود:

```text
TcpListener -> Bgp4Client -> ... -> Bgp4Server -> TcpConnector
```

:::warning
`Bgp4Server` routing واقعی BGP، BGP peering، route exchange یا BGP authentication را پیاده‌سازی نمی‌کند. فقط framing BGP-like تولیدشده توسط `Bgp4Client` را می‌فهمد.
:::

## این نود چه می‌کند؟

- یک per-line read stream و first-frame state در طول upstream `init` initialize می‌کند.
- نیاز دارد که اولین upstream frame یک synthetic OPEN frame از `Bgp4Client` باشد.
- BGP metadata و synthetic OPEN body اولین frame را strip می‌کند.
- marker، length و type را از frameهای upstream بعدی strip می‌کند.
- payloadهای upstream بازیابی‌شده را به tunnel بعدی forward می‌کند.
- payloadهای downstream را به عنوان BGP-like frame می‌پیچد قبل از اینکه به tunnel قبلی بفرستد.
- هر دو جهت را وقتی داده frame نامعتبر دریافت می‌کند می‌بندد.

`Bgp4Server` یک stream tunnel معمولی است. socket شبکه نمی‌سازد و packet line نمی‌سازد یا destroy نمی‌کند.

## نمونه تنظیم

سمت server:

```json
{
  "name": "bgp4-server",
  "type": "Bgp4Server",
  "settings": {
    "password": "compat-value"
  },
  "next": "target"
}
```

سمت client متناظر:

```json
{
  "name": "bgp4-client",
  "type": "Bgp4Client",
  "settings": {
    "password": "compat-value"
  },
  "next": "transport-out"
}
```

فیلد `password` برای سازگاری با شکل قدیمی config پذیرفته می‌شود، اما در منطق پروتکل فعلی برای encryption یا authentication استفاده نمی‌شود.

## فیلدهای اجباری

فیلدهای top-level:

| فیلد | نوع | توضیح |
| --- | --- | --- |
| `name` | string | نام یکتای نود داخل config. |
| `type` | string | باید دقیقاً `"Bgp4Server"` باشد. |
| `next` | string | نود stream بعدی که payloadهای upstream unwrapped را دریافت می‌کند. |

## تنظیمات اختیاری

| گزینه | نوع | پیش‌فرض | توضیح |
| --- | --- | --- | --- |
| `password` | string | `"passwd"` | فیلد compatibility. در طول setup hash می‌شود اما hash آن توسط منطق framing فعلی استفاده نمی‌شود. |

هیچ تنظیم دیگری در حال حاضر parse نمی‌شود.

## فرمت Frame

`Bgp4Server` همان شکل BGP-like frame ای که `Bgp4Client` تولید می‌کند را می‌خواند و می‌نویسد:

```text
16-byte marker | 2-byte body length | 1-byte BGP type | body
```

جزئیات فیلد:

| فیلد | مقدار |
| --- | --- |
| marker | شانزده byte از `0xff`. |
| body length | `uint16_t` big-endian. شامل type byte به اضافه body bytes. |
| BGP type | اولین upstream frame باید `1` باشد؛ frameهای downstream از `2` تا `5` تصادفی استفاده می‌کنند. |
| body | payload tunneled، یا synthetic OPEN body به اضافه payload tunneled برای اولین upstream frame. |

مقادیر نوع پشتیبانی‌شده:

| نوع | نام |
| --- | --- |
| `1` | OPEN |
| `2` | UPDATE |
| `3` | NOTIFICATION |
| `4` | KEEPALIVE |
| `5` | ROUTE-REFRESH |

length field، طول BGP-like tunnel WaterWall است، نه طول استاندارد BGP message: شامل type byte به اضافه body bytes، به استثنای marker و length field است.

## اولین Upstream Frame

اولین upstream frame باید نوع `1` باشد و باید شامل یک synthetic OPEN body به دنبال آن payload bytes tunneled باشد.

برای اولین frame، `Bgp4Server`:

1. تأیید می‌کند که frame حداقل 1-byte type به اضافه 10-byte OPEN header دارد.
2. تأیید می‌کند که type برابر OPEN است.
3. optional parameter length را از OPEN header می‌خواند.
4. طول کامل synthetic OPEN prefix را محاسبه می‌کند.
5. frame را رد می‌کند اگر بعد از OPEN prefix هیچ payload tunneled باقی نمانده باشد.
6. line را به عنوان دریافت‌کننده OPEN علامت می‌زند.
7. type و OPEN prefix را strip می‌کند.
8. payload باقی‌مانده را upstream forward می‌کند.

frameهای upstream بعدی فقط 1-byte type را strip می‌کنند. body بازیابی‌شده نباید خالی باشد.

## Downstream Wrapping

payloadهای downstream قبل از ارسال به سمت tunnel قبلی wrapped می‌شوند.

`Bgp4Server` از یک نوع BGP غیر-OPEN تصادفی برای frameهای payload downstream استفاده می‌کند:

```text
2، 3، 4 یا 5
```

payload توسط این نود encrypt یا authenticate نمی‌شود. فقط frame می‌شود.

## محدودیت‌ها و Padding

| مقدار | مقدار | یادداشت |
| --- | --- | --- |
| حداکثر body length | `65535` bytes | شامل 1-byte type. |
| حداکثر payload body معمولی | `65534` bytes | payload به اضافه type باید در `65535` جا شود. |
| حداکثر bytes خوانده‌شده buffer | حدود `131106` bytes | دو framed message با حداکثر اندازه. |
| `required_padding_left` | `19` bytes | frame marker، length و type. |

اگر یک downstream payload در یک BGP-like frame جا نشود، رد می‌شود و هیچ wrapped frame ای forward نمی‌شود.

## جریان داده

جهت upstream:

```text
نود قبلی -> Bgp4Server باز می‌کند -> نود بعدی
```

جهت downstream:

```text
نود بعدی -> Bgp4Server می‌پیچد -> نود قبلی
```

سمت upstream باید frameهای تولیدشده توسط `Bgp4Client` را دریافت کند. اگر اولین upstream frame، synthetic OPEN frame مورد انتظار نباشد، line بسته می‌شود.

## رفتار Lifecycle

در upstream `init`، `Bgp4Server` line state خود را initialize می‌کند و upstream `init` را به tunnel بعدی forward می‌کند.

در downstream `est`، downstream `est` را به tunnel قبلی forward می‌کند.

در upstream payload، buffer می‌کند، parse می‌کند، validate می‌کند، باز می‌کند و payloadهای بازیابی‌شده را به tunnel بعدی forward می‌کند. در downstream payload، می‌پیچد و به tunnel قبلی forward می‌کند.

در upstream `finish`، line state خود را destroy می‌کند و upstream `finish` را به tunnel بعدی forward می‌کند. در downstream `finish`، line state خود را destroy می‌کند و downstream `finish` را به tunnel قبلی forward می‌کند.

در صورت داده frame نامعتبر، `Bgp4Server` local state را destroy می‌کند و هر دو جهت را به ترتیب middle-tunnel می‌بندد: upstream finish اول، سپس downstream finish.

pause و resume به صورت جهت‌دار forward می‌شوند:

| Callback | forward می‌شود به |
| --- | --- |
| upstream pause/resume | next tunnel upstream |
| downstream pause/resume | previous tunnel downstream |

## نکته‌ها

- `Bgp4Server` نیاز به یک `Bgp4Client` paired برای عملکرد مفید دارد.
- `password` یک feature امنیتی در پیاده‌سازی فعلی نیست.
- اولین upstream frame باید یک OPEN frame با payload tunneled بعد از synthetic OPEN body باشد.
- BGP-like length field، marker و length bytes را exclude می‌کند.
- upstream `est` و downstream `init` غیرفعال هستند.
- این نود یک layer-4 stream tunnel است، نه یک packet tunnel.
