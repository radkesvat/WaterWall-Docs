# Bgp4Server

`Bgp4Server` همتای سمت سرور `Bgp4Client` است. فریم‌های شبیه BGP را که از سمت کلاینت و در جهت upstream می‌رسند باز می‌کند و payload‌های downstream را در جهت عکس داخل همان نوع فریم قرار می‌دهد.

این node باید با `Bgp4Client` استفاده شود:

```text
client: TcpListener(127.0.0.1:18080) -> Bgp4Client -> TcpConnector(gateway:7443)
server: TcpListener(0.0.0.0:7443) -> Bgp4Server -> TcpConnector(127.0.0.1:8080)
```

connector سمت client به listener مربوط به WaterWall در server روی پورت `7443`
وصل می‌شود؛ connector سمت server سرویس HTTP واقعی روی `127.0.0.1:8080` را
انتخاب می‌کند. برنامه‌ی محلی را به `127.0.0.1:18080` متصل کنید. دو node نوع BGP
بایت‌ها را frame و باز می‌کنند؛ HTTP را بازنویسی نمی‌کنند و مقصد را انتخاب نمی‌کنند.

:::warning
`Bgp4Server` مسیریابی واقعی BGP، برقراری BGP peering، تبادل route یا احراز هویت BGP را پیاده‌سازی نمی‌کند. این node فقط فریم‌بندی شبیه BGP ساخته‌شده توسط `Bgp4Client` را می‌شناسد.
:::

## این نود چه می‌کند؟

- هنگام `init` در جهت upstream، برای هر line یک stream خواندن و state مربوط به اولین فریم را مقداردهی اولیه می‌کند.
- نخستین فریم upstream باید فریم ساختگی OPEN از `Bgp4Client` باشد.
- اطلاعات BGP و body ساختگی OPEN را از فریم نخست حذف می‌کند.
- marker، length و type را از فریم‌های بعدی upstream برمی‌دارد.
- payload‌های بازیابی‌شده upstream را به تونل بعدی می‌فرستد.
- پیش از فرستادن payload‌های downstream به تونل قبلی، آن‌ها را در فریم‌های شبیه BGP قرار می‌دهد.
- در صورت دریافت فریم نامعتبر، هر دو جهت را می‌بندد.

`Bgp4Server` یک تونل stream معمولی است. socket شبکه یا packet line نمی‌سازد و packet line‌ای را نیز آزاد نمی‌کند.

## نمونه تنظیم

سمت سرور:

```json
{
  "name": "bgp4-server",
  "type": "Bgp4Server",
  "settings": {},
  "next": "target"
}
```

سمت کلاینت متناظر:

```json
{
  "name": "bgp4-client",
  "type": "Bgp4Client",
  "settings": {},
  "next": "transport-out"
}
```

فیلد `password` برای سازگاری با config‌های قدیمی پذیرفته می‌شود، اما منطق فعلی پروتکل از آن برای رمزنگاری یا احراز هویت استفاده نمی‌کند.

## فیلدهای اجباری

فیلدهای سطح اصلی:

| فیلد | نوع | توضیح |
| --- | --- | --- |
| `name` | string | نام یکتای node در config. |
| `type` | string | باید دقیقاً `"Bgp4Server"` باشد. |
| `next` | string | node stream بعدی که payload‌های بازشده upstream را می‌گیرد. |

## تنظیمات اختیاری

| گزینه | نوع | پیش‌فرض | توضیح |
| --- | --- | --- | --- |
| `password` | string | — | پذیرفته می‌شود اما نادیده گرفته می‌شود؛ برای رمزنگاری یا احراز هویت کاربردی ندارد. |

در حال حاضر تنظیم دیگری خوانده نمی‌شود.

## فرمت فریم

`Bgp4Server` همان قالب فریم شبیه BGP را می‌خواند و می‌نویسد که `Bgp4Client` تولید می‌کند:

```text
16-byte marker | 2-byte body length | 1-byte BGP type | body
```

جزئیات فیلد:

| فیلد | مقدار |
| --- | --- |
| marker | شانزده بایت با مقدار `0xff`. |
| body length | یک `uint16_t` با ترتیب big-endian؛ شامل بایت type به‌علاوه بایت‌های body. |
| BGP type | نخستین فریم upstream باید `1` باشد؛ فریم‌های downstream یکی از مقادیر تصادفی `2` تا `5` را می‌گیرند. |
| body | payload تونل‌شده؛ در نخستین فریم upstream شامل body ساختگی OPEN و سپس payload تونل‌شده است. |

مقادیر نوع پشتیبانی‌شده:

| نوع | نام |
| --- | --- |
| `1` | OPEN |
| `2` | UPDATE |
| `3` | NOTIFICATION |
| `4` | KEEPALIVE |
| `5` | ROUTE-REFRESH |

فیلد length طول قالب شبیه BGP در تونل WaterWall را نشان می‌دهد، نه طول استاندارد پیام BGP. این طول، بایت type و بایت‌های body را در بر می‌گیرد، اما marker و خود فیلد length را حساب نمی‌کند.

## اولین Upstream Frame

نخستین فریم upstream باید type برابر `1` داشته باشد و شامل body ساختگی OPEN و سپس بایت‌های payload تونل‌شده باشد.

`Bgp4Server` برای نخستین فریم:

1. بررسی می‌کند که فریم دست‌کم یک بایت type و ده بایت headerِ OPEN داشته باشد.
2. بررسی می‌کند که type برابر OPEN و نسخه برابر ۴ باشد.
3. optional parameter length را از OPEN header می‌خواند.
4. طول کامل پیشوند ساختگی OPEN را حساب می‌کند.
5. اگر پس از پیشوند OPEN هیچ payload تونل‌شده‌ای باقی نمانده باشد، فریم را رد می‌کند.
6. تمام پیشوند OPEN را پیش از تحویل بایت‌های برنامه مصرف می‌کند.
7. دریافت OPEN را در state مربوط به line ثبت می‌کند.
8. بایت‌های آمادهٔ برنامه را بدون انتظار برای باقی فریم در جهت upstream می‌فرستد.

از فریم‌های بعدی upstream فقط type یک‌بایتی حذف می‌شود. Body بازیابی‌شده نباید خالی باشد.

## Downstream Wrapping

payload‌های downstream پیش از ارسال به تونل قبلی، فریم‌بندی می‌شوند.

`Bgp4Server` از یک نوع BGP غیر-OPEN تصادفی برای frame‌های payload downstream استفاده می‌کند:

```text
2, 3, 4, or 5
```

این node payload را رمزنگاری یا احراز هویت نمی‌کند؛ فقط آن را در فریم قرار می‌دهد.

## محدودیت‌ها و Padding

| مقدار | مقدار | یادداشت |
| --- | --- | --- |
| حداکثر طول body | `65535` بایت | شامل type یک‌بایتی. |
| حداکثر payload در body عادی | `65534` بایت | مجموع payload و type باید در `65535` بایت جا شود. |
| سقف منطقی ورودی بازگشتی | `2162705` | بایت‌های wire قدیمی به‌علاوهٔ ورودی بازگشتی، شامل header کش‌شده. |
| سقف هزینهٔ bufferهای ورودی نگه‌داری‌شده | `4325410` | پس از پذیرش بازگشتی و پایان تخلیهٔ بایت‌های آمادهٔ body؛ فشرده‌سازی مفید پیش از رد انجام می‌شود. |
| سقف بایت‌های خروجی فریم‌بندی‌شده در صف | `2162705` | شامل headerهای تولیدشده؛ پیش از callback بررسی می‌شود. |
| سقف هزینهٔ bufferهای خروجی در صف | `8 MiB` | bufferهای خروجی تا هنگام تحویل محاسبه می‌شوند. |
| `required_padding_left` | `19` بایت | برای marker، length و type فریم. |

دادهٔ بزرگ به چند فریم با حداکثر ۶۵۵۳۴ بایت payload عادی تقسیم می‌شود. فضای واقعی پیشوند OPEN از فریم نخست کم می‌شود و فقط یک OPEN فرستاده می‌شود.

## جریان داده

جهت upstream:

```text
previous node -> Bgp4Server unwraps -> next node
```

جهت downstream:

```text
next node -> Bgp4Server wraps -> previous node
```

سمت upstream باید فریم‌های تولیدشده توسط `Bgp4Client` را دریافت کند. اگر نخستین فریم upstream همان فریم ساختگی OPEN مورد انتظار نباشد، line بسته می‌شود.

## رفتار Lifecycle

با دریافت `init` در جهت upstream، `Bgp4Server` state مربوط به line را مقداردهی اولیه می‌کند و `init` را در همان جهت به تونل بعدی می‌فرستد.

با دریافت `est` در جهت downstream، هر اعلان، حتی تکراری، را به تونل قبلی می‌فرستد.

payload‌های upstream را buffer، parse و اعتبارسنجی می‌کند، فریم را باز می‌کند و داده بازیابی‌شده را به تونل بعدی می‌فرستد. payload‌های downstream را فریم‌بندی و به تونل قبلی ارسال می‌کند.

با دریافت `finish` از هر جهت، state مربوط به line را از بین می‌برد و `finish` را در همان جهت منتشر می‌کند: در upstream به تونل بعدی و در downstream به تونل قبلی.

در صورت دریافت فریم نامعتبر، `Bgp4Server` state محلی را از بین می‌برد و هر دو جهت را با ترتیب لازم برای یک تونل میانی می‌بندد: ابتدا finish در upstream و سپس finish در downstream.

Pause و Resume اعلان‌های راهنمای تکرارپذیر هستند. callbackهای پیش‌فرض هر
اعلان را فوراً در همان جهت منتقل می‌کنند؛ وضعیت توقف مصرف‌کننده ذخیره نمی‌شود
و ارسال payload به Resume وابسته نیست:

| callback | مقصد ارسال |
| --- | --- |
| upstream pause/resume | next tunnel upstream |
| downstream pause/resume | previous tunnel downstream |

## نکته‌ها

- برای استفاده عملی از `Bgp4Server` باید آن را با `Bgp4Client` جفت کنید.
- در پیاده‌سازی فعلی، `password` قابلیت امنیتی محسوب نمی‌شود.
- نخستین فریم upstream باید یک فریم OPEN باشد که پس از body ساختگی OPEN، payload تونل‌شده داشته باشد.
- فیلد طول در قالب شبیه BGP، بایت‌های marker و length را در نظر نمی‌گیرد.
- upstream `est` و downstream `init` غیرفعال هستند.
- این node یک تونل stream لایه ۴ است، نه packet tunnel.

## Splice، فریم‌بندی و کنترل فشار

هر دو جهت buffer عادی، بدنهٔ داخل pipe خصوصی و ترکیب این دو را می‌پذیرند.
فریم تک‌تکه با استفاده از padding موجود در همان buffer ساخته می‌شود؛ بودجهٔ
padding کلاینت ۳۹ و سرور ۱۹ بایت است. ورودی بزرگِ مسیر ارسال پیش از نخستین callback به
یک دستهٔ کامل از فریم‌های مستقل تبدیل می‌شود. شکست ساخت pipe یا پرشدن مقصد
برای همان فریم به buffer عادی با اندازهٔ کافی برمی‌گردد؛ کل ورودی به یک buffer
عادی تجمیع نمی‌شود.

گیرنده header نوزده‌بایتی را cache می‌کند و بایت‌های آمادهٔ body برنامه را
تدریجی تحویل می‌دهد. سرور ابتدا ۱۰ بایت ثابت OPEN را جمع‌آوری و اعتبارسنجی
می‌کند، سپس حداکثر ۲۵۵ بایت اختیاری را پیش از تحویل دادهٔ برنامه مصرف می‌کند؛
بقیهٔ payload می‌تواند داخل pipe بماند. کلاینت ۳ تا ۱۰ بایت
اختیاری تولید می‌کند و اندازهٔ واقعی آن را از ظرفیت فریم نخست کم می‌کند.
ورودی خالی فریمی تولید نمی‌کند و وضعیت نخستین OPEN را مصرف نمی‌کند.
روی هر line کلاینت دقیقاً یک OPEN پذیرفته می‌شود.

گیرنده از `splice_frame_reader_t` مشترک روی `splice_stream_t` استفاده می‌کند.
بایت‌های آمادهٔ body در یک دستهٔ ورودیِ غیر بازگشتی پیش از بررسی باقیماندهٔ ناقص تخلیه
می‌شوند؛ بنابراین اندازهٔ آن دسته می‌تواند از **۲٬۱۶۲٬۷۰۵ بایت**
(`2 MiB + 65553`) بیشتر باشد. هنگام اجرای callback تحویل، ورودی بازگشتی به‌همراه
بایت‌های wire قدیمیِ نگه‌داری‌شده، شامل header کش‌شده، باید در همین سقف منطقی
جا شود. سپس ورودی به انتهای FIFO افزوده می‌شود و پیش از بازگشت از پذیرش
بازگشتی، هزینهٔ محاسبه‌شدهٔ bufferهای نگه‌داری‌شده باید حداکثر **۴٬۳۲۵٬۴۱۰ بایت**
باشد. همین سقف هزینه برای باقیماندهٔ ناقص هنگام پایان تخلیه نیز بررسی می‌شود.
ادغام در فضای موجود یا یک‌بار فشرده‌سازیِ مفید می‌تواند پیش از رد ورودی، فضای
اضافی bufferها را آزاد کند. فشرده‌سازی ممکن است بایت‌های داخل pipe را به حافظهٔ
عادی کپی کند؛ سقف هزینه، حسابداری فضای نگه‌داری‌شده را محدود می‌کند، نه کل حافظهٔ
فرایند یا اوج مصرف موقت را. تعداد قطعه‌های ورودی سقف جداگانه‌ای ندارد. پس از
تخلیهٔ بایت‌های آمادهٔ body، باقیماندهٔ ناقص کمتر از ۶۵٬۵۵۳ بایت منطقی است.

خروجی فریم‌بندی‌شده سقف مستقل **۲٬۱۶۲٬۷۰۵ بایت**، شامل headerهای تولیدشده، و
حداکثر **۸ MiB هزینهٔ bufferهای نگه‌داری‌شده** دارد. این سقف‌ها به پروفایل حافظه، pool، ظرفیت واقعی
pipe، پلتفرم یا `misc.splice` وابسته نیستند. حداکثر فریم کامل ۶۵٬۵۵۳ و payload
فریم غیر-OPEN حداکثر ۶۵٬۵۳۴ بایت است.

یک فریم دریافتی ممکن است چند callback از نوع Payload تولید کند؛ مرز فریم، مرز
تحویل دادهٔ برنامه نیست. اگر اتصال وسط فریم بسته شود، پیشوند برنامه که قبلاً
تحویل شده پس گرفته نمی‌شود. هر دو نود از همان line عادی قرض‌گرفته‌شده
استفاده می‌کنند و تمام payloadها را تبدیل می‌کنند؛ بنابراین bypass دائمی ندارند.
Pause و Resume، حتی اگر تکراری باشند، با callbackهای پیش‌فرض در هر دو جهت
شفاف منتقل می‌شوند. بایت‌های آمادهٔ پذیرفته‌شده بدون انتظار برای Resume تخلیه
می‌شوند. محافظ تخلیه در هر جهت ترتیب FIFO را هنگام callbackهای بازگشتی حفظ
می‌کند؛ frame reader دادهٔ ناقص را نگه می‌دارد و صف محدود خروجی، دسته‌های کامل
فریم‌بندی‌شده را پیش از ورودی بازگشتی ارسال می‌کند. گیرنده هر header کامل در
ابتدای FIFO را بلافاصله پس از پذیرش، حتی برای ورودی بازگشتی، اعتبارسنجی می‌کند؛
فقط حلقهٔ تخلیهٔ بیرونی بایت‌های برنامه را تحویل می‌دهد. دسته‌های فریم‌بندی‌شدهٔ خروجی
پیش از نخستین callback با سقف بایت و هزینهٔ نگه‌داری بررسی می‌شوند.
دادهٔ نامعتبر، عبور از سقف نگه‌داری یا رد شدن به‌دلیل محدودیت ظرفیت صف
فقط همان اتصال را از طریق مالک line می‌بندد. Finish منابع محلی را پیش از
ارسال در جهت دور از فرستنده آزاد می‌کند. این پشتیبانی تضمین zero-copy یا
افزایش throughput بدون اندازه‌گیری نیست.
