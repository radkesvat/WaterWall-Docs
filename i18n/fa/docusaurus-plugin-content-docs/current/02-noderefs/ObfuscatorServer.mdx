# ObfuscatorServer

`ObfuscatorServer` سمت مقابل `ObfuscatorClient` است. این نود همان transform برگشت‌پذیر را با همان method، key و header options اعمال می‌کند.

در نسخه فعلی فقط روش `xor` پشتیبانی می‌شود. این نود یک لایه traffic-shaping و obfuscation است، نه یک لایه رمزنگاری.

`ObfuscatorServer` با packet-tunnel API ساخته می‌شود و per-line tunnel state ندارد. Payload bytes در-جا transform می‌شوند، مگر اینکه حالت TLS-like header نیاز به clone کردن buffer داشته باشد.

## جایگاه رایج

مسیر TCP ساده:

```text
client side: TcpListener -> ObfuscatorClient -> TcpConnector
server side: TcpListener -> ObfuscatorServer -> TcpConnector
```

مسیر UDP:

```text
client side: UdpListener -> ObfuscatorClient -> UdpConnector
server side: UdpListener -> ObfuscatorServer -> UdpConnector
```

مسیر raw packet:

```text
packet transport -> ObfuscatorServer -> RawSocket
```

از همان تنظیمات `skip` و `tls_record_header` در سمت client استفاده کنید.

## این نود چه می‌کند؟

- نیاز دارد `settings.method: "xor"` باشد.
- نیاز دارد `settings.xor_key` باشد.
- XOR را روی upstream payload bytes قبل از forward کردن به `next` اعمال می‌کند.
- به صورت اختیاری بعد از upstream XOR یک header ۵ بایتی شبیه TLS record prepend می‌کند.
- به صورت اختیاری header ۵ بایتی شبیه TLS را قبل از downstream XOR strip می‌کند.
- XOR را روی downstream payload bytes قبل از forward کردن به نود قبلی اعمال می‌کند.
- می‌تواند IPv4 header، یا IPv4 به اضافه TCP/UDP header را بدون obfuscation رها کند.
- payload های packet-line را برای recalculation checksum بعد از تغییر bytes علامت می‌زند.
- payload ها را buffer نمی‌کند و per-line state نگه نمی‌دارد.

پیاده‌سازی server، پیاده‌سازی client را mirror می‌کند. نام client/server نقش deploy را توصیف می‌کند؛ transform خودش symmetric است.

## نمونه تنظیم

```json
{
  "name": "obfuscator-server",
  "type": "ObfuscatorServer",
  "settings": {
    "method": "xor",
    "xor_key": 90,
    "skip": "transport",
    "tls_record_header": true
  },
  "next": "service-node"
}
```

client متناظر:

```json
{
  "name": "obfuscator-client",
  "type": "ObfuscatorClient",
  "settings": {
    "method": "xor",
    "xor_key": 90,
    "skip": "transport",
    "tls_record_header": true
  },
  "next": "transport-node"
}
```

## فیلدهای اجباری

فیلدهای top-level:

| فیلد | نوع | توضیح |
| --- | --- | --- |
| `name` | string | نام یکتای نود داخل config. |
| `type` | string | باید دقیقاً `"ObfuscatorServer"` باشد. |
| `settings` | object | اجباری. باید `method` و `xor_key` داشته باشد. |
| `next` | string | اجباری در استفاده معمولی. نود بعدی upstream payloadهای transform شده را دریافت می‌کند. |

فیلدهای اجباری داخل `settings`:

| فیلد | نوع | توضیح |
| --- | --- | --- |
| `method` | string | باید `"xor"` باشد در پیاده‌سازی فعلی. |
| `xor_key` | integer | کلید XOR مشترک با client. مقدار به یک بایت ذخیره می‌شود. |

## تنظیمات اختیاری

| گزینه | نوع | پیش‌فرض | توضیح |
| --- | --- | --- | --- |
| `skip` | string | `"none"` | header های ابتدایی packet که قبل از XOR clear می‌مانند. مقادیر: `"none"`، `"ipv4"` و `"transport"`. |
| `tls_record_header` | boolean | `false` | یک header ۵ بایتی شبیه TLS application-data روی payload سمت transport اضافه/حذف می‌کند. |
| `tls_header` | boolean | تنظیم نشده | alias deprecated برای `tls_record_header`. پذیرفته می‌شود ولی warning log می‌کند. |

## حالت‌های Skip

`skip` کنترل می‌کند چه مقدار از ابتدای payload XOR نشود:

| مقدار | رفتار |
| --- | --- |
| `"none"` | کل payload XOR می‌شود. |
| `"ipv4"` | اگر payload یک IPv4 packet معتبر باشد، IPv4 header clear می‌ماند و bytes بعد از آن XOR می‌شوند. |
| `"transport"` | اگر payload یک IPv4 TCP/UDP packet معتبر باشد، IPv4 header و TCP/UDP header clear می‌مانند. برای سایر protocolهای IPv4، فقط IPv4 header clear می‌ماند. |

اگر payload خیلی کوتاه باشد یا IPv4 packet معتبر نباشد، skip length به `0` تبدیل می‌شود و کل payload XOR می‌شود.

## Header شبیه TLS

وقتی `tls_record_header` فعال باشد، payload های سمت transport این‌طور ارسال می‌شوند:

```text
17 03 03 + length(2 bytes, big-endian) + obfuscated payload
```

این bytes یک TLS application-data record header را تقلید می‌کنند:

| فیلد | مقدار |
| --- | --- |
| content type | `23` / `0x17` |
| legacy version | `0x0303` |
| length | طول payload obfuscated شده، ۱۶ بیتی big-endian |

در مسیر دریافت، header validate و strip می‌شود و سپس XOR اجرا می‌شود.

:::warning
این TLS نیست. handshake، certificate، SNI، ALPN، رمزنگاری و authentication ندارد. فقط شکل یک TLS application-data record post-handshake را تقلید می‌کند.
:::

محدودیت‌های مهم:

- payloadهای بزرگ‌تر از `65535` بایت هنگام wrap شدن drop می‌شوند
- headerهای truncated هنگام strip شدن drop می‌شوند
- recordهایی که طول اعلام‌شده‌شان دقیقاً با طول payload buffer فعلی مطابقت ندارند drop می‌شوند
- reassembly buffer record وجود ندارد، پس payload callback های سمت receive باید دقیقاً یک TLS-like record کامل داشته باشند

## رفتار جهت‌ها

| callback ورودی | رفتار |
| --- | --- |
| upstream `Payload` | بر اساس `skip` XOR می‌کند، به صورت اختیاری header شبیه TLS را prepend می‌کند، recalculation checksum packet-line را علامت می‌زند و به `next` forward می‌کند. |
| downstream `Payload` | به صورت اختیاری header شبیه TLS را validate و strip می‌کند، بر اساس `skip` XOR می‌کند، recalculation checksum packet-line را علامت می‌زند و به نود قبلی forward می‌کند. |
| downstream `Init` | به نود قبلی forward می‌شود. |
| سایر lifecycle callbackها | از رفتار default packet-tunnel استفاده می‌کند. |

## Buffer و Padding

متادیتای نود:

```text
required_padding_left = 5
layer_group = kNodeLayerAnything
```

۵ بایت برای header اختیاری شبیه TLS است. اگر buffer هنگام فعال بودن `tls_record_header` padding چپ کافی نداشته باشد، نود payload را داخل buffer جدیدی با padding کافی clone می‌کند، buffer اصلی را recycle می‌کند و سپس header را prepend می‌کند.

وقتی line فعلی worker packet line باشد، نود بعد از transform کردن payload bytes مقدار `recalculate_checksum = true` را تنظیم می‌کند.

## نکته‌های Implementation

XOR helper مسیرهای بهینه دارد:

- AVX2 وقتی در دسترس باشد
- aligned 64-bit chunk processing روی buildهای ۶۴ بیتی
- aligned 32-bit یا byte-wise fallback در غیر این صورت

این مسیرها فقط روی performance تأثیر دارند؛ رفتار قابل مشاهده همچنان byte-wise XOR با کلید یک بایتی تنظیم‌شده است.

## نکته‌های عملی

- `ObfuscatorServer` و `ObfuscatorClient` باید `method`، `xor_key`، `skip` و `tls_record_header` یکسان داشته باشند.
- این obfuscation است، نه امنیت cryptographic.
- `skip: "none"` برای byte streamهای معمولی ساده‌ترین حالت است.
- `skip: "transport"` برای packetهای خام IPv4 TCP/UDP که IP و transport headerهایشان باید قابل خواندن بمانند مفید است.
- اگر فقط به رمزنگاری امن نیاز دارید، از `EncryptionClient` و `EncryptionServer` استفاده کنید.
