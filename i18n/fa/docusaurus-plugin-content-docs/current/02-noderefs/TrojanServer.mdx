# TrojanServer

## نمای کلی {#overview}

<bdi dir="ltr">`TrojanServer`</bdi> تونل سمت سرورِ پروتکل Trojan در WaterWall است. این گره جریان بایتی Trojan
را از گره قبلی تجزیه می‌کند، هش استاندارد SHA224 گذرواژه را احراز هویت می‌کند، مقصد درخواستی
TCP یا UDP را استخراج می‌کند و ترافیک پذیرفته‌شده را به گره <bdi dir="ltr">`next`</bdi> پیکربندی‌شده می‌فرستد.

این گره از فهرست‌های مجاز گذرواژهٔ محلی و کاربران مبتنی بر <bdi dir="ltr">`AuthenticationClient`</bdi> پشتیبانی
می‌کند. همچنین برای کاوش‌های نامعتبرِ احرازنشده، fallback اختیاری دارد.

گره فعلی جایگزین چیدمان قدیمیِ دوگرهی شده است که از گره‌های جداگانهٔ <bdi dir="ltr">`TrojanAuthServer`</bdi>
و <bdi dir="ltr">`TrojanSocksServer`</bdi> استفاده می‌کرد.

سمت پروتکل به جریان بایت نیاز دارد. فرمان فعال CONNECT در سمت سرویس خطِ جریان
و فرمان فعال UDP خطِ دیتاگرام ایجاد می‌کند. سرویس با هر دو فرمان به backend دوگانه
یا مسیریابی بر اساس پروتکل نیاز دارد. شاخهٔ fallback جریان بایت را حمل می‌کند.

<a id="جایگاه-رایج"></a>

## جایگاه معمول در زنجیره {#typical-placement}

سرور معمول Trojan:

```text
TcpListener -> TlsServer -> TrojanServer -> TcpUdpConnector
```

خروجی فقط TCP:

```text
TcpListener -> TlsServer -> TrojanServer -> TcpConnector
```

با مسیریابی پس از احراز هویت:

```text
TcpListener -> TlsServer -> TrojanServer -> Router
```

<bdi dir="ltr">`TrojanServer`</bdi> به‌تنهایی TLS را خاتمه نمی‌دهد. برای استقرار عمومی Trojan، <bdi dir="ltr">`TlsServer`</bdi> را
پیش از آن قرار دهید. بدون TLS، هش گذرواژه و فرادادهٔ مقصد روی سیم قابل مشاهده‌اند.

این گره پروتکل، رمزنگاری بستر انتقال را فراهم نمی‌کند. پیش از در دسترس عموم قرار دادن سرویس،
گره‌های TLS نشان‌داده‌شده در بالا و اطلاعات احراز هویت متناظرِ همتا را پیکربندی کنید.

## نمونهٔ کاربردی ساده {#minimal-practical-example}

این یک **قطعه از آرایهٔ گره‌ها** است، نه یک فایل پیکربندی کامل. شنوندهٔ ورودی و گره‌های
همسایهٔ نشان‌داده‌شده در بالا را اضافه کنید و اطلاعات احراز هویت و آدرس‌های نمونهٔ سرور را
جایگزین کنید. مسیرهای گواهی/کلید باید به فایل‌های سرور شما اشاره کنند.

<a id="نمونه-minimal-با-local-password"></a>

### نمونهٔ ساده با گذرواژهٔ محلی {#minimal-local-password-example}

```json
[
  {
    "name": "tls-in",
    "type": "TlsServer",
    "settings": {
      "cert-file": "/etc/waterwall/fullchain.pem",
      "key-file": "/etc/waterwall/privkey.pem"
    },
    "next": "trojan-server"
  },
  {
    "name": "trojan-server",
    "type": "TrojanServer",
    "settings": {
      "password": "secret-password",
      "connect": true,
      "udp": true,
      "verbose": false
    },
    "next": "outbound"
  },
  {
    "name": "outbound",
    "type": "TcpUdpConnector",
    "settings": {
      "address": "dest_context->address",
      "port": "dest_context->port"
    }
  }
]
```

## پیکربندی {#configuration}

<a id="فیلدهای-اجباری"></a>

### فیلدهای الزامی {#required-fields}

فیلدهای سطح بالا:

| فیلد | نوع | توضیح |
| --- | --- | --- |
| <bdi dir="ltr">`name`</bdi> | رشته | نام گره به انتخاب کاربر. باید در فایل پیکربندی یکتا باشد. |
| <bdi dir="ltr">`type`</bdi> | رشته | باید دقیقاً <bdi dir="ltr">`"TrojanServer"`</bdi> باشد. |
| <bdi dir="ltr">`settings`</bdi> | شیء | تنظیمات غیرخالیِ سرور Trojan. |
| <bdi dir="ltr">`next`</bdi> | رشته | الزامی. ترافیک پذیرفته‌شدهٔ Trojan به این گره فرستاده می‌شود. |

دقیقاً یک حالت احراز هویت انتخاب کنید.

<a id="تنظیمات-local-authentication"></a>

### تنظیمات احراز هویت محلی {#local-authentication-settings}

برای احراز هویت محلی، <bdi dir="ltr">`auth-client-node-name`</bdi> را ننویسید و دست‌کم یک گذرواژهٔ خام تنظیم کنید.

| فیلد | نوع | توضیح |
| --- | --- | --- |
| <bdi dir="ltr">`password`</bdi> | رشته | یک گذرواژهٔ خام Trojan. |
| <bdi dir="ltr">`pass`</bdi> | رشته | نام جایگزین <bdi dir="ltr">`password`</bdi>. یکی از <bdi dir="ltr">`password`</bdi> یا <bdi dir="ltr">`pass`</bdi> را استفاده کنید، نه هر دو. |
| <bdi dir="ltr">`passwords`</bdi> | آرایهٔ رشته‌ها | چند گذرواژهٔ خام Trojan. |
| <bdi dir="ltr">`users`</bdi> | آرایه | رشته‌های گذرواژه یا اشیایی با <bdi dir="ltr">`password`</bdi> یا <bdi dir="ltr">`pass`</bdi>. اشیا می‌توانند <bdi dir="ltr">`username`</bdi> داشته باشند. |
| <bdi dir="ltr">`clients`</bdi> | آرایه | نام جایگزین <bdi dir="ltr">`users`</bdi>. یکی از <bdi dir="ltr">`users`</bdi> یا <bdi dir="ltr">`clients`</bdi> را استفاده کنید، نه هر دو. |

رشته‌های گذرواژه باید غیرخالی باشند. گذرواژه‌های محلی تکراری خطای مهلک پیکربندی هستند، حتی
اگر ورودی‌های تکراری نام‌های کاربری متفاوتی داشته باشند.

<a id="تنظیمات-database-authentication"></a>

### تنظیمات احراز هویت پایگاه داده {#database-authentication-settings}

| فیلد | نوع | توضیح |
| --- | --- | --- |
| <bdi dir="ltr">`auth-client-node-name`</bdi> | رشته | نام یک گره <bdi dir="ltr">`AuthenticationClient`</bdi> موجود در همان فایل پیکربندی. |

گره ارجاع‌شده باید وجود داشته باشد، از نوع <bdi dir="ltr">`AuthenticationClient`</bdi> باشد و به خود گره
<bdi dir="ltr">`TrojanServer`</bdi> برنگردد. در حالت پایگاه داده، <bdi dir="ltr">`password`</bdi>، <bdi dir="ltr">`pass`</bdi>، <bdi dir="ltr">`passwords`</bdi>، <bdi dir="ltr">`users`</bdi>
یا <bdi dir="ltr">`clients`</bdi> را پیکربندی نکنید.

<a id="تنظیمات-اختیاری"></a>

### تنظیمات اختیاری {#optional-settings}

| فیلد | پیش‌فرض | توضیح |
| --- | --- | --- |
| <bdi dir="ltr">`connect`</bdi> | <bdi dir="ltr">`true`</bdi> | TCP <bdi dir="ltr">`CONNECT`</bdi> در Trojan، فرمان <bdi dir="ltr">`0x01`</bdi>، را فعال می‌کند. |
| <bdi dir="ltr">`udp`</bdi> | <bdi dir="ltr">`true`</bdi> | UDP <bdi dir="ltr">`ASSOCIATE`</bdi> در Trojan، فرمان <bdi dir="ltr">`0x03`</bdi>، را فعال می‌کند. |
| <bdi dir="ltr">`verbose`</bdi> | <bdi dir="ltr">`false`</bdi> | پیام‌های عیب‌یابیِ متمرکز بر احراز هویت را فعال می‌کند. |
| <bdi dir="ltr">`fallback-node-name`</bdi> | تنظیم نشده | شاخهٔ fallback برای کاوش‌های نامعتبرِ احرازنشده. نام‌های جایگزین: <bdi dir="ltr">`fallback-node`</bdi>، <bdi dir="ltr">`fallback`</bdi>. |
| <bdi dir="ltr">`fallback-intentional-delay-ms`</bdi> | <bdi dir="ltr">`7`</bdi> | تأخیر payloadهای upstream ارسالی به fallback. تأخیر غیرصفر از نوسان تصادفیِ پیکربندی‌شده استفاده می‌کند. در <bdi dir="ltr">`0`</bdi>، ورودی پذیرفته‌شده همگام عبور می‌کند و حتی زیر Pause نیز تکمیل می‌شود؛ Init شاخه و ورود مجدد، FIFO را حفظ می‌کنند. نباید منفی باشد. |
| <bdi dir="ltr">`fallback-intentional-delay-jitter-ms`</bdi> | <bdi dir="ltr">`1`</bdi> | نوسان تصادفی در زمان‌بندی payload تأخیردارِ fallback. وقتی تأخیر <bdi dir="ltr">`0`</bdi> باشد نادیده گرفته می‌شود. نباید منفی باشد. |
| <bdi dir="ltr">`sweep-interval-ms`</bdi> | <bdi dir="ltr">`1000`</bdi> | تنظیم اختیاری که در حالت پایگاه داده به <bdi dir="ltr">`UserController`</bdi> ساخته‌شده در داخل گره فرستاده می‌شود. |

دست‌کم یکی از <bdi dir="ltr">`connect`</bdi> یا <bdi dir="ltr">`udp`</bdi> باید فعال باشد.

## کاربرد و رفع اشکال {#usage-and-troubleshooting}

<a id="نمونه-fallback"></a>

### نمونهٔ fallback {#fallback-example}

```json
{
  "name": "trojan-server",
  "type": "TrojanServer",
  "settings": {
    "password": "secret-password",
    "fallback-node-name": "fallback-service",
    "fallback-intentional-delay-ms": 7,
    "fallback-intentional-delay-jitter-ms": 1,
    "connect": true,
    "udp": true
  },
  "next": "outbound"
}
```

Fallback برای مقاومت در برابر کاوش فعال است. ترافیک نامعتبرِ احرازنشده می‌تواند به‌جای
بسته‌شدن فوری، به گره پیکربندی‌شدهٔ دیگری سپرده شود.

<a id="اشتباههای-رایج"></a>

### اشتباه‌های رایج {#common-mistakes}

- <bdi dir="ltr">`TrojanServer`</bdi> را مستقیماً روی یک شنوندهٔ TCP عمومی و بدون <bdi dir="ltr">`TlsServer`</bdi> در دسترس قرار
  ندهید، مگر اینکه عمداً Trojan آشکار را روی سیم بخواهید.
- گذرواژه‌های محلی را همراه با <bdi dir="ltr">`auth-client-node-name`</bdi> پیکربندی نکنید.
- گره بعدی را روی یک <bdi dir="ltr">`UserController`</bdi> دستی تنظیم نکنید؛ حالت پایگاه داده <bdi dir="ltr">`UserController`</bdi>
  داخلی خودش را درج می‌کند.
- برای پیکربندی‌های جدید از نام‌های قدیمیِ <bdi dir="ltr">`TrojanAuthServer`</bdi> و <bdi dir="ltr">`TrojanSocksServer`</bdi> استفاده نکنید.
- انتظار نداشته باشید آدرس اولیهٔ UDP ASSOCIATE مقصد نهایی UDP را انتخاب کند؛ هر بستهٔ UDP
  در Trojan آدرس مقصد خودش را حمل می‌کند.

## رفتار پیشرفته {#advanced-behavior}

<a id="چند-user-محلی"></a>

### چند کاربر محلی {#multiple-local-users}

```json
{
  "name": "trojan-server",
  "type": "TrojanServer",
  "settings": {
    "users": [
      "secret-password",
      {
        "username": "alice",
        "password": "another-secret"
      }
    ],
    "connect": true,
    "udp": true
  },
  "next": "outbound"
}
```

در حالت فهرست مجاز محلی، <bdi dir="ltr">`TrojanServer`</bdi> گذرواژهٔ خامِ تطبیق‌یافته را روی line ذخیره می‌کند
تا <bdi dir="ltr">`Router`</bdi> بتواند قواعد گذرواژه را تطبیق دهد. اگر شیء منطبق دارای <bdi dir="ltr">`username`</bdi> باشد، آن نام
کاربری نیز روی line ذخیره می‌شود تا در مسیریابی مبتنی بر نام کاربری استفاده شود.

<a id="حالت-authenticationclient"></a>

### حالت AuthenticationClient {#authenticationclient-mode}

```json
{
  "name": "trojan-server",
  "type": "TrojanServer",
  "settings": {
    "auth-client-node-name": "auth-client",
    "connect": true,
    "udp": true,
    "verbose": false
  },
  "next": "outbound"
}
```

در این حالت، <bdi dir="ltr">`AuthenticationClient`</bdi> پیکربندی‌شده مرجع تصمیم‌گیری است. گذرواژهٔ آشکار Trojan
هر کاربر را در فیلد <bdi dir="ltr">`password`</bdi> شیء کاربر ذخیره کنید؛ <bdi dir="ltr">`AuthenticationClient`</bdi> دادهٔ جست‌وجوی
SHA224 را در داخل خود آماده می‌کند. <bdi dir="ltr">`name`</bdi> در شیء کاربر نام حساب است، نه خود گذرواژهٔ Trojan.

وقتی <bdi dir="ltr">`auth-client-node-name`</bdi> تنظیم شده باشد، تنظیمات گذرواژهٔ محلی رد می‌شوند. <bdi dir="ltr">`TrojanServer`</bdi>
در داخل خود یک <bdi dir="ltr">`UserController`</bdi> پیش از گره خروجیِ پیکربندی‌شده درج می‌کند، بنابراین
<bdi dir="ltr">`UserController`</bdi> دستی را مستقیماً پس از آن قرار ندهید.

<a id="فرمت-request"></a>

### قالب درخواست {#request-format}

درخواست پذیرفته‌شدهٔ Trojan:

```text
password:     56 ASCII hex bytes, hex(SHA224(password))
separator:    CRLF
command:      01 CONNECT or 03 UDP ASSOCIATE
destination:  ATYP + address + port
separator:    CRLF
body:         TCP stream bytes or Trojan UDP packets
```

قالب مقصد:

```text
ATYP 01: IPv4 address, 4 bytes, then 2-byte big-endian port
ATYP 03: domain length, domain bytes, then 2-byte big-endian port
ATYP 04: IPv6 address, 16 bytes, then 2-byte big-endian port
```

قالب بستهٔ UDP در Trojan:

```text
destination:  ATYP + address + port
length:       2 bytes big-endian
separator:    CRLF
payload:      length bytes
```

<a id="جریان-authentication"></a>

### روند احراز هویت {#authentication-flow}

کلاینت‌های Trojan مقدار <bdi dir="ltr">`hex(SHA224(password))`</bdi> را به‌صورت 56 بایت هگز ASCII ارسال می‌کنند.
<bdi dir="ltr">`TrojanServer`</bdi> این مقدار را از نمایش هگز به بایت تبدیل می‌کند و آن را بر اساس حالت انتخاب‌شده احراز هویت می‌کند.

در حالت محلی، سرور SHA224 هر گذرواژهٔ خامِ پیکربندی‌شده را از پیش محاسبه می‌کند. در حالت
پایگاه داده، از API جست‌وجوی SHA224 در <bdi dir="ltr">`AuthenticationClient`</bdi> استفاده می‌کند و پس از تجزیهٔ
درخواست، دستگیرهٔ کاربرِ بازگردانده‌شده را روی line ثبت می‌کند.

هش کامل 56 بایتیِ گذرواژه باید در اولین callback مربوط به payload در جهت upstream موجود
باشد. اگر اولین payload شامل کل هش نباشد، line به‌عنوان کاوش نامعتبرِ احرازنشده در نظر گرفته
می‌شود. اگر fallback پیکربندی شده باشد، آن بایت‌ها به fallback می‌روند؛ در غیر این صورت
line بسته می‌شود. پس از موجود بودن هش کامل گذرواژه، فیلدهای بعدی درخواست، شامل CRLF، فرمان،
مقصد و بایت‌های اولیهٔ بدنه، همچنان می‌توانند در callbackهای بعدی payload برسند.

Trojan حالت بدون احراز هویت ندارد.

<a id="رفتار-runtime-برای-tcp-connect"></a>

### رفتار TCP CONNECT در زمان اجرا {#tcp-connect-runtime-behavior}

برای فرمان <bdi dir="ltr">`0x01`</bdi>، سرور:

1. هش گذرواژه را احراز هویت می‌کند
2. مقصد درخواستی را تجزیه می‌کند
3. آن مقصد را در <bdi dir="ltr" style={{display: "inline-block", maxWidth: "100%"}}>`lineGetDestinationAddressContext(line)`</bdi> می‌نویسد
4. اطلاعات احراز هویت محلی یا پایگاه داده را برای مسیریابی بعدی روی line ثبت می‌کند
5. گره <bdi dir="ltr">`next`</bdi> پیکربندی‌شده را مقداردهی اولیه می‌کند
6. بایت‌های بدنهٔ TCP را که در همان payload سرآیند درخواست رسیده‌اند عبور می‌دهد
7. <bdi dir="ltr">`Est`</bdi> در جهت downstream را فقط پس از برقراری مسیر خروجیِ انتخاب‌شده عبور می‌دهد

گره <bdi dir="ltr">`next`</bdi> پیکربندی‌شده معمولاً <bdi dir="ltr">`TcpConnector`</bdi>، <bdi dir="ltr">`TcpUdpConnector`</bdi>، <bdi dir="ltr">`Router`</bdi> یا گره دیگری
است که زمینهٔ مقصد را می‌شناسد.

<a id="رفتار-runtime-برای-udp-associate"></a>

### رفتار UDP ASSOCIATE در زمان اجرا {#udp-associate-runtime-behavior}

برای فرمان <bdi dir="ltr">`0x03`</bdi>، آدرس درخواست اولیه فقط فرادادهٔ association است. مقصد واقعیِ راه دور
در هر بستهٔ UDP مربوط به Trojan حمل می‌شود.

برای هر مقصد یکتای بستهٔ UDP، <bdi dir="ltr">`TrojanServer`</bdi> یک line داخلیِ backend UDP می‌سازد یا دوباره
از آن استفاده می‌کند. آن line، مقصد بسته را در <bdi dir="ltr" style={{display: "inline-block", maxWidth: "100%"}}>`lineGetDestinationAddressContext(line)`</bdi> دریافت
می‌کند، اطلاعات احراز هویت کاربرِ احرازشده را حمل می‌کند و payload خام UDP را به گره <bdi dir="ltr">`next`</bdi>
پیکربندی‌شده می‌فرستد.

پاسخ‌های lineهای backend UDP دوباره در قالب بستهٔ UDP مربوط به Trojan قرار می‌گیرند و در
جهت downstream به جریان کلاینت اصلیِ Trojan فرستاده می‌شوند. بنابراین یک association UDP
در Trojan می‌تواند با چند نقطهٔ اتصال UDP راه دور ارتباط داشته باشد.

سرآیندهای بدشکل بستهٔ UDP، نام دامنه با طول صفر، نبودن پورت یا جداکننده‌های CRLF خراب، line
مربوط به Trojan را می‌بندند. بدنه‌های UDP از کل بازهٔ <bdi dir="ltr">0–65,535</bdi> بایتیِ فیلد طول دوبایتی
استفاده می‌کنند. پاسخ‌های backend بدون انتظار برای Est یا Resume، همگام قاب‌بندی و فرستاده می‌شوند.

<a id="رفتار-fallback"></a>

### رفتار fallback {#fallback-behavior}

بازپخش خام fallback روی همان خط ورودیِ قرض‌گرفته‌شده انجام می‌شود. هویت مبدأ
و انتخاب قبلی مقصد حفظ می‌شوند. اگر انتقال مقصد تعیین نشده و مقصد ثابت
نباشد، پیش از `Init` شاخهٔ fallback، TCP ثبت می‌شود.

Fallback فقط پیش از احراز هویت موفق گذرواژه استفاده می‌شود. پس از موفقیت احراز هویت، دادهٔ
بدشکل پروتکل Trojan به‌جای بازپخش به fallback، line را می‌بندد.

Fallback ممکن است در این موارد انتخاب شود:

- بایت‌های نامعتبر در پیشوند گذرواژه
- هشی از گذرواژه که تنها بخشی از آن در اولین payload جهت upstream آمده باشد
- CRLF نامعتبرِ گذرواژه پیش از احراز هویت
- هگز نامعتبرِ گذرواژه پیش از احراز هویت
- شکست جست‌وجوی گذرواژه
- در دسترس نبودن پذیرشِ ذخیره‌شده در حافظهٔ نهان AuthenticationClient (بارگذاری‌نشده، در حال توقف، ردشده یا دچار شکست نهاییِ تداوم)

وقتی fallback انتخاب می‌شود:

- شاخهٔ fallback فوراً <bdi dir="ltr">`Init`</bdi> دریافت می‌کند
- بایت‌های اولیهٔ ذخیره‌شده و payloadهای بعدیِ upstream به fallback فرستاده می‌شوند
- payloadهای عادی و زندهٔ upstream در fallback، اگر تأخیر غیرصفر باشد، <bdi dir="ltr">`fallback-intentional-delay-ms`</bdi> به‌اضافهٔ نوسان تصادفی را رعایت می‌کنند
- در تأخیر <bdi dir="ltr">`0`</bdi>، ورودی پذیرفته‌شده حتی زیر Pause همگام عبور می‌کند؛ Init و ورود مجدد FIFO را حفظ می‌کنند
- FIFO تأخیردارِ fallback برای هر line به 2 MiB بایت منطقی و 8 MiB هزینهٔ تخصیص بافر محدود است
- دسته‌های تأخیردارِ معمولی، هنگام فشار بر هزینهٔ تخصیص و پیش از ردشدن، در فضایی با اندازهٔ متناسب ادغام می‌شوند و ترتیب FIFO و تأخیر زمان‌بندی‌شده را حفظ می‌کنند
- fallback انتخاب‌شده تمام Pause/Resumeها، از جمله تکرارها را منتقل می‌کند؛ خروجی تأخیرداری که موعدش رسیده منتظر Resume نمی‌ماند
- هنگام <bdi dir="ltr">`Finish`</bdi> از upstream، شاخه‌ای که مقداردهی اولیه شده است، پیش از <bdi dir="ltr">`Finish`</bdi> مربوط به fallback یک دستهٔ FIFO پذیرفته‌شده را همگام دریافت می‌کند، حتی زیر Pause؛ شاخه‌ای که هنوز داخل Init است، دسته‌ای را که هنوز در مالکیت محلی است دور می‌ریزد و بسته می‌شود
- پاسخ‌های downstream از fallback عمداً به تأخیر انداخته نمی‌شوند

پس از بسته‌شدن upstream، تأخیر عمدیِ باقی‌مانده زنده نگه داشته نمی‌شود.

تأخیر پیش‌فرض fallback عمداً کوچک است. تأخیر و نوسان آن را با رفتار عمومی‌ای تنظیم کنید که
fallback قرار است شبیه آن باشد؛ این‌ها راهکارهای کاهش خطرند، نه اثباتِ غیرقابل‌تشخیص بودن زمان‌بندی.

<a id="قابلیتهای-پشتیبانینشده"></a>

### قابلیت‌های پشتیبانی‌نشده {#unsupported-features}

این پیاده‌سازی موارد زیر را ایجاد یا مدیریت نمی‌کند:

- خاتمهٔ TLS
- لایه‌های انتقال WebSocket، HTTP، gRPC یا سایر پوشش‌های انتقال
- ترکیب قدیمیِ <bdi dir="ltr">`TrojanAuthServer`</bdi> به‌همراه <bdi dir="ltr">`TrojanSocksServer`</bdi>
- افزونه‌های غیراستاندارد Trojan

اگر به این لایه‌ها نیاز دارید، از گره‌های جداگانهٔ WaterWall مانند <bdi dir="ltr">`TlsServer`</bdi>، <bdi dir="ltr">`HttpServer`</bdi>،
<bdi dir="ltr">`MuxServer`</bdi>، <bdi dir="ltr">`TcpUdpConnector`</bdi> یا <bdi dir="ltr">`Router`</bdi> استفاده کنید.

## جزئیات پیاده‌سازی {#implementation-details}

<a id="پذیرش-از-cache-محلی"></a>

### پذیرش حساب از حافظهٔ نهان {#cached-account-admission}

با AuthenticationClient، پذیرش هنگام قطعی معمول شبکه و احراز هویت مجدد از آخرین جدول معتبر
در RAM و مبنای زمانیِ آن استفاده می‌کند. وضعیت فعال بودن، انقضا، سهمیهٔ ترافیک و رزروهای محلی
اتصال/IP که در حافظهٔ نهان هستند همچنان اعمال می‌شوند. نبودن حافظهٔ نهان اولیه، توقف، شکست
نهاییِ تداوم حسابداری یا رد صریح اطلاعات احراز هویت کلاینت، پذیرش جدید را مسدود می‌کند. فقط
مجوزِ اعتبارسنجی‌شده آن رد را برطرف می‌کند؛ ترافیک مجازِ موجود همچنان تابع اعمال محدودیت‌های
ذخیره‌شده و حسابداری است. تغییرات مدیریتی در زمان آفلاین، پس از به‌روزرسانی اعمال می‌شوند.
ظرفیت‌های مجاز محلی می‌توانند در میان چند کلاینت قطع‌شده از شبکه، از محدودیت‌های تجمیعی فراتر
بروند؛ آن‌ها رزروهای سراسری نیستند.

<a id="splice-بافر-و-کنترل-فشار"></a>

### Splice، بافرگذاری و کنترل فشار {#splice-buffering-and-backpressure}

TrojanServer در احراز هویت، CONNECT، ASSOCIATE و fallback، بافرهای معمولی، بافرهای splice
مبتنی بر pipe خصوصی و ورودی ترکیبی را می‌پذیرد. تجزیه‌گر اولیه فقط بایت‌های لازمِ سرآیند را
مصرف می‌کند: 68 بایت برای IPv4، مقدار 80 برای IPv6، یا 65 به‌اضافهٔ طول دامنه، با حداکثر
320 بایت. اولین callback همچنان باید هر 56 بایت هش را داشته باشد. بایت‌های موجودِ CRLF
گذرواژه پیش از احراز هویت بررسی می‌شوند؛ هشی که پیش از رسیدن CRLF بعدی پذیرفته شده باشد،
فقط یک‌بار احراز هویت می‌شود. بایت‌های نامعتبرِ رسیده پس از احراز هویت، جریان محافظت‌شده را
بدون fallback می‌بندند. اطلاعات احراز هویت و دستگیره‌های پایگاه داده پیش از Init شاخهٔ
محافظت‌شده ثبت می‌شوند.

بدنه‌های TCP پس از درخواست بدون تفسیر باقی می‌مانند. تجزیهٔ اولیه، Init شاخه و ورودیِ ورود
مجدد یک FIFO مرجع را حفظ می‌کنند تا بایت‌های پذیرفته‌شدهٔ قدیمی‌تر عقب نیفتند. ورودی معتبر
پس از Init مسیر بعدی، بدون انتظار برای Est بستر انتقال یا Resume، عبور داده می‌شود. پس از
بازگشت Init شاخهٔ عادی TCP، تخلیهٔ ورودی نگه‌داری‌شده و انتقال هر Pause پیش از Init،
TrojanServer وضعیت line خود را از بین می‌برد و صفر می‌کند، سپس برای آن line به‌طور دائمی
خود را از مسیر پردازش کنار می‌گذارد. callbackهای بعدی، از جمله Finish، مستقیماً مسیر عادی
next/prev را دنبال می‌کنند. اطلاعات احراز هویت روی <bdi dir="ltr">`line_t`</bdi> باقی می‌مانند؛ کنار رفتن از
مسیر منتظر Est نمی‌ماند. اعلان‌های Est در TCP و fallback، از جمله تکرارها و callbackهای
داخل Init، بی‌درنگ عبور می‌کنند. Pause/Resume نیز هر اعلان را در مسیرهای TCP و fallback
مقداردهی‌شده عبور می‌دهند. پیش از انتخاب شاخه، فقط آخرین وضعیت Pause در upstream برای Init
شاخهٔ انتخاب‌شده نگه داشته می‌شود؛ Resume آن Pause معوق را لغو می‌کند.

associationهای UDP و fallback، TrojanServer را فعال نگه می‌دارند: آن‌ها همچنان به
قاب‌بندی، پاک‌سازی backendهای تحت مالکیت، انتخاب شاخه یا بازپخش تأخیردار آن نیاز دارند.

Fallback پیشوند مقیمِ بررسی‌شده و دنبالهٔ دست‌نخوردهٔ ورودی را دقیقاً یک‌بار و پیش از ورودی
جدیدتر بازپخش می‌کند. Init همچنان فوری است و تأخیر و نوسان پیکربندی‌شده روی payload اعمال
می‌شود. یک دستهٔ تأخیردار، یک بافر و یک callback از نوع Payload است؛ مونتاژ ترکیبی یا
مبتنی بر pipe از جابه‌جایی دقیق استفاده می‌کند و هنگام فشار بر منابع pipe، کاملاً به بافر
معمولی برمی‌گردد. دسته‌های تأخیرداری که موعدشان رسیده منتظر Resume نمی‌مانند. هنگام Finish
مبدأ، شاخهٔ مقداردهی‌شده حداکثر یک دستهٔ نهایی را همگام دریافت می‌کند، حتی پس از Pause.
شاخه‌ای که هنوز داخل Init است بازپخشِ در انتظار را دور می‌ریزد. هیچ callback نهایی به سمت
پایان‌یافته بازتاب داده نمی‌شود.

Fallback می‌تواند بدون <bdi dir="ltr">`Est`</bdi> خروجی، پاسخ محلی تولید کند؛ از جمله پاسخی که بلافاصله پس از
آن در callback مربوط به Init یا Payload خودش، <bdi dir="ltr">`Finish`</bdi> بیاید. پاسخ‌ها حتی در صورت دریافت
Pause همگام عبور می‌کنند تا پاسخ پذیرفته‌شده پیش از Finish به کلاینت برسد. پاک‌سازیِ
Source-Finish همچنان پاسخ‌های دستهٔ نهایی fallback را جذب می‌کند و آن‌ها را بازتاب نمی‌دهد.

UDP فقط سرآیند 11 بایتیِ IPv4، سرآیند 23 بایتیِ IPv6 یا سرآیند <bdi dir="ltr">`8 + domain_length`</bdi> را
می‌خواند و سپس دقیقاً یک بدنه، از جمله دیتاگرام خالی، استخراج می‌کند. هر backend یک line
عادیِ تحت مالکیت روی worker کلاینت است. اطلاعات احراز هویتِ تأییدشده را حمل می‌کند و فقط پس
از آماده‌شدن عضویت آن در association و مقصدش، مقداردهی اولیه می‌شود. TrojanServer، line
کلاینت را قرض می‌گیرد و فقط backendهای خودش را از بین می‌برد.

فشار ورودی UDP در سطح کل association اعمال می‌شود: هر backend در وضعیت Pause یک‌بار در
توقف کار جدیدِ مبدأ حامل سهم دارد. Resume فقط پس از رفع همهٔ سهم‌ها رخ می‌دهد. ورودی‌ای که
اکنون پذیرفته شده است، همچنان همهٔ دیتاگرام‌های کامل را به‌ترتیب FIFO تکمیل می‌کند، حتی
بیش از 1,024 دیتاگرام کوچک یا خالی. ورودی تودرتو پس از بایت‌های قدیمی‌تر به‌ترتیب پردازش
می‌شود؛ پس از dispatch فقط یک پسوند ناقص باقی می‌ماند. Pause پاسخ کلاینت به همهٔ مبدأهای
backend مقداردهی‌شده، از جمله backendهای تازه‌ساخته‌شده، منتقل می‌شود. بسته‌شدن ناشی از
callback پردازش را متوقف و مالکیت محلی را آزاد می‌کند.

پاسخ‌های backend به‌صورت درجا، پیش یا پس از Est مربوط به backend و زیر Pause، قاب‌بندی و
فرستاده می‌شوند؛ بدون صف خروجیِ رمزگشایی‌شده یا انتظار برای Est. اولین Est بستر انتقالِ
backend یک‌بار به association کلاینت نگاشت می‌شود؛ Estهای بعدیِ backend آن را تکرار
نمی‌کنند. گیرنده‌ها مسئول فضای محدود داده‌های در حال انتقال و سیاست بستن در سقف سخت خود
هستند. اگر backend انتخاب‌شده در طول Init، اعلان اجازه یا تحویل جاری بسته شود، association
حامل بسته می‌شود تا دیتاگرام پذیرفته‌شده بی‌صدا دور ریخته نشود. خطاهای محلیِ backend خارج
از رمزگشایی، دامنهٔ محلی خود را حفظ می‌کنند.

| کار نگه‌داری‌شده | سقف ثابت |
| --- | --- |
| ورودی اولیه/UDP روی سیم، شامل سر فعال و سرآیندهای ذخیره‌شده | 2,162,950 بایت (2 MiB به‌اضافهٔ یک قاب با حداکثر اندازهٔ 65,798 بایت) |
| ترتیب‌دهی موقت TCP در Init/ورود مجدد | 2 MiB بایت منطقی و 8 MiB هزینهٔ صف |
| ورودی انباشتهٔ fallback تأخیردار | 2 MiB بایت منطقی و 8 MiB هزینهٔ بافر |
| ترتیب‌دهی موقت بازپخش با تأخیر صفر | 2 MiB بایت منطقی و 8 MiB هزینهٔ صف |
| حافظهٔ نهان سرآیند اولیه | 320 بایت واقعی |
| بدنهٔ UDP ورودی | 65,535 بایت |
| بدنهٔ پاسخ backend | 65,535 بایت |

مونتاژ اولیه اجازه می‌دهد یک درخواست ناقص با یک تحویل کامل 2 MiB دنبال شود. سرآیندهای
مصرف‌شده پیش از اعمال بودجهٔ بدنهٔ مسیر انتخاب‌شده حذف می‌شوند. قطعه‌قطعه‌شدن ورودی و خروجیِ
مصرف‌شده به‌صورت همگام، سقف 1,024 رکورد ندارند. بدنه‌های ناقص UDP و ورودی تودرتوی UDP
هنگامی فشرده‌سازیِ فضای نگه‌داری می‌شوند که هزینهٔ بافرهای نگه‌داری‌شده، شامل سر فعال، از
8 MiB بیشتر شود. این کار دیتاگرام‌های مجازِ قطعه‌قطعه و ترتیب بایت‌ها را بدون تغییر سقف
بدنه حفظ می‌کند. دیتاگرام‌های کامل از مسیر استخراج موجود ادامه می‌یابند. مقدار برابر سقف
پذیرفته می‌شود؛ عبور وضعیت نگه‌داری‌شده از سقف، association مربوط را می‌بندد. مسیرهای مستقیمِ
بدون تفسیر، صرفاً برای تحمیل سقف بایت صف ایجاد نمی‌کنند. این محدودیت‌های منطقی مستقل از
پروفایل RAM، ابعاد بافر و ظرفیت pipe هستند.

هم دیتاگرام‌های ورودی و هم پاسخ‌های backend از 0 تا 65,535 بایت payload را مطابق فیلد
طول دوبایتی می‌پذیرند. دیتاگرام خالی همچنان معتبر است. قاب حداکثر 263 بایت سرآیند خارج از
بدنه اضافه می‌کند. این بازهٔ قاب‌بندی، محدودیت‌های سوکت UDP بعدی، مسیر شبکه یا همتای راه
دور را تغییر نمی‌دهد؛ برای نمونه، UDP معمولی روی IPv4 بدون گزینه‌های IP حداکثر 65,507
بایت payload می‌پذیرد. هر بدنهٔ پذیرفته‌شده یک دیتاگرام باقی می‌ماند، حتی اگر حامل TCP قاب
آن را در چند خواندن تحویل دهد. Trojan بدنه را کوتاه نمی‌کند و به دیتاگرام‌های UDP جداگانه
تقسیم نمی‌کند.

افزودن سرآیند UDP در محدودهٔ فضای پیشوندِ اعلام‌شدهٔ 263 بایتی باقی می‌ماند و بایت‌های
پیشوند مقیم را به‌عنوان payload حفظ می‌کند. در صورت ناکافی بودن padding و رد منابع pipe
خصوصی، از توابع کمکی مشترکِ جابه‌جایی دقیق و بازگشت کامل به بافر معمولی استفاده می‌شود.
خاموش‌سازی توسط مالک مبدأ، backendهای وابسته، صف‌ها و بدنه‌های خصوصی را پیش از ازبین‌رفتن
زنجیره‌ها و مخزن‌ها آزاد می‌کند؛ کارهای تأخیردار fallback فقط عمر فیزیکی line را حفظ می‌کنند.

بررسی امکان splice پس از نهایی‌شدن زنجیره، UserController داخلی، توابع کمکیِ گره اتصال‌دهنده
و همهٔ شاخه‌های fallback قابل دسترسی را شامل می‌شود. وابستگی جست‌وجو به AuthenticationClient
یک گام در مسیر payload نیست. TlsServer و TlsClient همچنان splice را برای هر زنجیرهٔ حاوی
خود مسدود می‌کنند. TLS را در راهنمای استقرار معمول Trojan حفظ کنید. مجاز بودن splice فقط
پردازش امن بافر را تضمین می‌کند، نه zero-copy همیشگی یا بهبود سرعتِ اندازه‌گیری‌شده.

<a id="رفتار-finish"></a>

### رفتار Finish {#finish-behavior}

<bdi dir="ltr">`TrojanServer`</bdi> پیش از انتشار callbackهای واقعیِ <bdi dir="ltr">`Finish`</bdi>، وضعیت line خودش را از بین می‌برد.

line جریان کلاینت را آداپتور قبلی می‌سازد و <bdi dir="ltr">`TrojanServer`</bdi> آن را از بین نمی‌برد. lineهای
داخلی backend UDP را <bdi dir="ltr">`TrojanServer`</bdi> می‌سازد؛ مالک آن‌هاست و هنگام بسته‌شدن جریان کلاینت یا
بسته‌شدن یک line backend UDP، آن‌ها را به‌طور امن از بین می‌برد.

### فضای padding {#padding}

<bdi dir="ltr">`TrojanServer`</bdi> ممکن است بزرگ‌ترین سرآیند ممکنِ پاسخ UDP در Trojan را به ابتدای داده اضافه کند:

```text
required_padding_left = 263
```

این مقدار، <bdi dir="ltr">`ATYP + domain length + 255-byte domain + port + payload length + CRLF`</bdi> را پوشش می‌دهد.
