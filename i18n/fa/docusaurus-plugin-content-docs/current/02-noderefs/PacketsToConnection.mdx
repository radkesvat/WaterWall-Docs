# PacketsToConnection

## نمای کلی {#overview}

`PacketsToConnection` یک bridge بسته به transport بر پایهٔ lwIP است.

بسته‌های خام IPv4 را از سمت packet می‌پذیرد، به lwIP تزریق می‌کند و flowهای transport حاصل را به صورت connection عادی `line_t` در WaterWall به تونل بعدی ارائه می‌دهد.

پیش از ورود به lwIP، گره با tuple فعلی بسته و پس از هر تبدیل آدرس یا پورت قبلی، affinity مربوط به worker برای TCP/UDP را برقرار می‌کند. محل دریافت، الزام مالکیت flow نیست. dispatcher داخلی از FIFO محدود برای هر مقصد استفاده می‌کند و تونل دیگری میان TunDevice و PTC درج نمی‌کند؛ پس قابلیت checksum و خروجی مستقیم حفظ می‌شود. پاسخ‌ها مالک اتصال موجود را حفظ می‌کنند. affinity کار پذیرفته‌شده را سریالی می‌کند، اما ترتیب از دست رفته پیش از پذیرش را بازسازی نمی‌کند.

<span id="mtu-هر-نمونه"></span>

### MTU هر نمونه {#instance-mtu}

گزینهٔ اختیاری `mtu` یک عدد صحیح می‌گیرد و هنگام ساخت، مقدار پیش‌فرض خود را از `misc.mtu` هسته می‌گیرد (پیش‌فرض
هسته 1500). بازهٔ معتبر **68..65535 بایت** است: MTU خام IPv4 برای تمام رابط‌های مجازی هر worker، حتی رابط‌هایی که بعداً ساخته می‌شوند.
هر نمونه مقدار معتبر خود را ثابت و مستقل نگه می‌دارد؛ ساخت نمونهٔ دیگر یا تغییر
بعدی هسته بر آن اثر ندارد. `null`، نوع نادرست، عدد اعشاری، صفر، منفی و مقدار خارج
از بازه ساخت node را رد می‌کنند. پیش‌فرض ارث‌رسیدهٔ نامعتبر نیز رد می‌شود؛ یک override
معتبر برای node تعیین کنید. این تنظیم اندازه‌گیری یا مذاکرهٔ MTU مسیر نیست.
fragmentation موجود IPv4 در lwIP از MTU همین رابط پیروی می‌کند.

<span id="چیستی-این-نود"></span>

### ماهیت گره {#what-it-is}

این گره برای زنجیره‌ای است که از ترافیک بسته آغاز می‌شود و سپس به بخش connection-oriented معمول WaterWall وارد می‌شود.

به صورت مفهومی:

- سمت packet -> `PacketsToConnection` -> زنجیرهٔ سرویس عادی WaterWall
- پاسخ‌های زنجیرهٔ سرویس -> `PacketsToConnection` -> بسته‌های خام IP به سمت packet

این گره به bridge کوچک پشتهٔ transport درون فرایند نزدیک‌تر است تا آداپتور framing.

### کارهایی که انجام نمی‌دهد {#what-it-is-not}

- مدیر دستگاه TUN نیست.
- مسیر یا policy rule سیستم‌عامل را ایجاد یا پیکربندی نمی‌کند.
- جایگزین `TunDevice` نیست.
- مانند `PacketsToStream` بسته‌ها را روی stream سریال نمی‌کند.

`TunDevice` مالک سمت آداپتور واقعی بسته و `PacketsToConnection` مالک سمت bridge مربوط به lwIP است.

<span id="ترافیک-پشتیبانیشده"></span>

### پشتیبانی فعلی پروتکل {#current-protocol-support}

- IPv4 پشتیبانی می‌شود.
- TCP پشتیبانی می‌شود.
- UDP به صورت lineهای WaterWall برای هر flow پشتیبانی می‌شود.
- IPv6 و ICMP پشتیبانی نمی‌شوند.

بسته‌های پشتیبانی‌نشده محافظه‌کارانه دور ریخته می‌شوند.

## جایگاه معمول در زنجیره {#typical-placement}

این‌ها شکل کامل chain هستند؛ تنظیم nodeها و routeهای میزبان همچنان لازم است.
برای gateway محلی IPv4 TCP/UDP:

```text
TunDevice -> PacketsToConnection -> TcpUdpConnector
```

ترافیک مقصد برنامه را به TUN مسیریابی کنید. اگر ورودی ممکن است fragmented باشد،
روی TunDevice از `fragment-policy: "reassemble"` استفاده کنید؛ این bridge به
packet کامل IPv4 نیاز دارد. socketهای خروجی connector را با
[Loop Protection در TunDevice](./TunDevice.mdx#self-traffic-loop-protection)
بیرون از مسیر گرفته‌شده توسط TUN نگه دارید. آزمون را با TCP یا UDP انجام دهید؛
این bridge از ICMP ping پشتیبانی نمی‌کند.

برای سمت دور یک gateway TCP/UDP روی WireGuard:

```text
UdpListener -> WireGuardServer(mode=packet) -> PacketsToConnection -> TcpUdpConnector
```

socket UDP آدرس و پورت عمومی را فراهم می‌کند؛ WireGuard packet را احراز هویت و
رمزگشایی می‌کند؛ این bridge جریان TCP/UDP آن را به connection خروجی تبدیل می‌کند.
`allowedips` مربوط به peer باید آدرس‌های source داخلی را شامل شود؛ از جمله
`ConnectionToPackets.source-ipv4` وقتی packetهای client را آن node می‌سازد.
برای تنظیم کلیدها و سمت UDP از [جفت WireGuard](./WireGuardServer.mdx)
استفاده کنید و TUN سمت server را با این bridge و connector جایگزین کنید.

برای حفظ مقصد اصلی هر packet، این **قطعهٔ node مربوط به connector** را در انتهای
هر یک از chainها قرار دهید:

```json
{
  "name": "direct-out",
  "type": "TcpUdpConnector",
  "settings": {
    "address": "dest_context->address",
    "port": "dest_context->port"
  }
}
```

مقدار `PacketsToConnection.next` را `direct-out` بگذارید. آدرس یا پورت ثابت روی
connector، جریان‌ها را عمداً به مقصد دیگری می‌فرستد. `TcpUdpConnector` با metadata
این bridge میان TCP و UDP انتخاب می‌کند. خروجی socket-based این دو chain به
forwarding یا NAT سیستم‌عامل نیاز ندارد؛ این موضوع با پایان‌یافتن سمت packet
در یک interface سیستم‌عامل متفاوت است.

## نمونهٔ کاربردی ساده {#minimal-practical-example}

این قطعهٔ گره است؛ همسایه‌ها و همتاهای اشاره‌شده را در همان استقرار تعریف کنید.

این قطعه را از مسیر packet از نوع IPv4 تغذیه و `service-chain-entry` را به عنوان سرویس یا connector سمت connection تعریف کنید. تنظیمات خالی پیش‌فرض‌های معمول بدون fake DNS را انتخاب می‌کنند. بسته‌های برگشتی از سمت packet می‌روند؛ این یک bridge TCP/UDP است.

```json
{
  "name": "ptc",
  "type": "PacketsToConnection",
  "settings": {},
  "next": "service-chain-entry"
}
```

برای پیش‌فرض‌ها و الزام‌های مشروط [پیکربندی](#configuration) و برای نمونه‌های کامل و محدودیت‌های عملیاتی [کاربرد و رفع اشکال](#usage-and-troubleshooting) را ببینید.

### تنظیمات JSON {#json-settings}

`PacketsToConnection` اکنون این گزینه‌ها را پشتیبانی می‌کند:

- `udp-idle-timeout-ms` `(int, default: 300000)` مدت نگه‌داشتن UDP flow line بی‌فعالیت پیش از بستن توسط تونل را کنترل می‌کند؛ حداقل `1` است.
- `max-pending-bytes` `(int, default: 2097152)` بودجهٔ payload TCP نگه‌داشته‌شده هنگام پذیرفته‌نشدن یا تأیید ناقص توسط lwIP است. بازهٔ معتبر `1024..67108864` است. پذیرش یک headroom ثابت 1 MiB برای تحویل نیز دارد؛ عبور از سقف مجموع همان flow را حذف می‌کند.
- `fake-dns` `(bool or object, default: false)` پاسخ‌دهندهٔ fake DNS در تونل برای پرسش IPv4 A را فعال می‌کند. مقصدهای fake IP نگاشت‌شده روی lineهای TCP/UDP تولیدی WaterWall به مقصد domain تبدیل می‌شوند.

بودجهٔ پیش‌فرض معلق TCP برابر 2 MiB و هم‌اندازهٔ ظرفیت ارسال lwIP است. این سقف هر flow است، نه پیش‌تخصیص؛ pool مشترک lwIP ممکن است پیش از رسیدن flow به سقف فشار ایجاد کند.

`Pause` میان تونل‌ها مشورتی است و به‌تنهایی نمی‌تواند حافظهٔ نگه‌داشته‌شده را محدود کند: تونل بعدی ممکن است callback payload صف‌شده داشته باشد، با pause رقابت کند یا آن را نادیده بگیرد. بنابراین سقف پذیرش `P + L` است؛ `P = max-pending-bytes` و `L` حاشیهٔ ثابت 1 MiB مستقل از اندازهٔ pool، پروفایل RAM و تنظیمات splice است. `L` ورودی تحویل‌شده پیش از اثر Pause را پوشش می‌دهد. هر رکورد acknowledgement تا تأیید کامل طول اولیهٔ payload را حساب می‌کند و writeهای صف‌شده و در انتظار تأیید را پوشش می‌دهد. تا وقتی این charge از `P` بیشتر باشد تولید متوقف می‌ماند، حتی پس از خالی‌شدن صف write؛ Resume به پیشرفت کافی acknowledgement نیاز دارد. پذیرش پیش از مالکیت هر صف بررسی می‌شود. payload عبورکننده از سقف drop، اتصال TCP همان flow به جای تخلیه reset و line به سمت تونل بعدی بسته می‌شود. UDP چیزی در downstream نگه نمی‌دارد و مشمول این سقف نیست.

هر flow TCP مستقل از سقف بایت حداکثر 1,024 رکورد ACK/pause نگه می‌دارد. این سقف داخلی ایمنی تخصیص، تنظیم JSON نیست و سربار رکورد برای stream تقسیم‌شده به callbackهای کوچک را محدود می‌کند. رسیدن به entry بعدی فقط همان flow TCP را reset و می‌بندد؛ UDP را تحت تأثیر قرار نمی‌دهد.

فیلدهای object مربوط به `fake-dns`:

- `enabled` `(bool, default: true)`
- `address` `(IPv4 string, default: "198.18.0.2")`
- `port` `(int, default: 53)`
- `network` `(IPv4 string, default: "100.64.0.0")`
- `netmask` `(contiguous IPv4 /1 through /31 prefix mask, default: "255.192.0.0")`
- `cache-size` `(int, default: 10000, maximum: 262144)`
- `ttl` `(int seconds, default: 1)`

کلید قدیمی `mapdns` و کلید `fake_dns` alias برای `fake-dns` هستند. دقیقاً یکی از این نام‌ها می‌تواند وجود داشته باشد؛ alias تکراری حتی با مقدار یکسان رد می‌شود. object غیرفعال همچنان فیلدبه‌فیلد اعتبارسنجی می‌شود، اما جدول fake DNS تخصیص نمی‌دهد.

`address` باید مبدأ unicast مشخص IPv4 و غیرloopback باشد. wildcard، loopback، multicast و limited broadcast رد می‌شوند تا lwIP هویت پاسخ غیرقابل‌استفاده را بازنویسی یا ارسال نکند. listener فقط وقتی می‌تواند prefix شبکهٔ fake را به اشتراک بگذارد که index میزبان آن خارج از `[0, cache-size)` باشد؛ نباید با آدرس تخصیص‌یافته به fake record هم‌پوشانی داشته باشد. نخستین index بلافاصله پس از این بازه معتبر می‌ماند.

همهٔ تنظیمات فوق به جای انتخاب پیش‌فرض هنگام خطا اعتبارسنجی می‌شوند. فقط کلید حذف‌شده پیش‌فرض می‌گیرد؛ نوع JSON نادرست، عدد صحیح کسری یا خارج از بازه ساخت گره را با نام مسیر دقیق JSON رد می‌کند. پرسش DNS ردشده نیز cache را دست نمی‌زند: همهٔ بخش سؤال پیش از نخستین mapping تجزیه و اعتبارسنجی می‌شود. همهٔ نام‌های یکتای A/IN یک پرسش در یک transaction ثبت می‌شوند؛ اگر سیاست lease امکان هم‌زیستی آن‌ها را ندهد، پاسخ SERVFAIL بدون fake answer است و forward map، reverse record و ترتیب LRU قبلی تغییر نمی‌کنند. سؤال‌های تکراری از یک mapping استفاده می‌کنند.

mask باید پیوسته باشد و حداقل یک host bit بگذارد: `/32` فضای آدرس indexشده ندارد و رد می‌شود؛ `/0` به بازهٔ صفر normalize و طبق قاعدهٔ زیر رد می‌شود. cache حداکثر `2^(32 - prefix)` رکورد، شامل هر دو آدرس انتهایی prefix، می‌گیرد؛ پس `/31` دقیقاً دو رکورد دارد. network تنظیم‌شده با prefix ماسک می‌شود، index صفر به آن آدرس ماسک‌شده می‌رسد و index از octetهای IPv4 عبور می‌کند. بازه‌ای که نخستین رکورد آن sentinel خطای رزروشدهٔ `0.0.0.0` باشد رد می‌شود. سقف محصول 262144 رکورد، index تخصیص‌یافتهٔ اولیه و فضای رزروشدهٔ name-map را روی build 64 بیتی به حدود 16 MiB محدود می‌کند. ضرب تخصیص، ظرفیت signed map، رشد load factor و تعداد bucket توان دوی بعدی map پیش از هر دو تخصیص بررسی می‌شوند.

نام‌ها در label فقط حروف ASCII، رقم، خط تیره و underscore دارند. مرز label فقط با طول‌های label DNS نمایش می‌یابد. parser پیش از تغییر cache، NUL داخلی، نقطهٔ literal داخل label، بایت کنترلی و بایت پشتیبانی‌نشده را رد می‌کند. نام پذیرفته‌شده lowercase می‌شود و طول بایتی صریح آن با طول C-string برابر است تا policy matching و resolution هویت مقصد یکسان ببینند.

هر پاسخ موفق mapping را تا زمان صدور monotonic به‌علاوهٔ `ttl` اعلام‌شده محافظت می‌کند؛ هر پاسخ lease را تمدید می‌کند. حذف LRU فقط entry منقضی و unpinned را بازاستفاده می‌کند؛ اگر همهٔ slotها محافظت شوند، mapping جدید با SERVFAIL رد می‌شود و mapping و lease موجود تغییر نمی‌کند. entry منقضی تا نیاز به بازاستفاده باقی می‌ماند. بازهٔ TTL همچنان `0..2147483647` ثانیه است: صفر بازاستفادهٔ فوری را مجاز می‌کند و TTL بلند در cache پر می‌تواند پذیرش نام جدید را مدت طولانی متوقف کند. کلاینت نباید آدرس fake را پس از TTL پاسخ استفاده کند و صف downstream باید محدود بماند.

## کاربرد و رفع اشکال {#usage-and-troubleshooting}


<span id="ظرفیت"></span>

### ظرفیت {#capacity}

همه‌ی نمونه‌های `ConnectionToPackets` و `PacketsToConnection` در یک فرایند از
allocator قابل‌رشد lwIP و سقف‌های مشترک استفاده می‌کنند. این فیلدها را زیر
`misc` در `core.json` تنظیم کنید، نه در `settings` نود:

| تنظیم هسته | پیش‌فرض استاندارد | منبع |
| --- | ---: | --- |
| `lwip-memory-budget` | `536870912` (512 MiB) | حافظه‌ی pool و حافظه‌ی نگه‌داری‌شده‌ی محاسبه‌شده برای stack |
| `lwip-max-tcp-flows` | `65536` | وضعیت اتصال TCP، شامل handshake و اتصال‌های در حال بسته‌شدن |
| `lwip-max-udp-flows` | `65536` | وضعیت اتصال UDP |
| `lwip-max-tcp-listeners` | `1024` | اشیای listener در TCP |
| `lwip-max-tcp-segments` | `1048576` | segmentهای ارسال، ارسال مجدد و دریافت TCP |
| `lwip-max-rx-wrappers` | `262144` | wrapperهای PTC برای نگه‌داری بسته‌ی ورودی |

سقف تعداد، عدد صحیح در بازه‌ی `1..4294967295` را می‌پذیرد. بودجه‌ی بایت از
`1048576` تا مقدار کوچک‌تر از `SIZE_MAX` پلتفرم و `9223372036854775807` است.
مقدار نامعتبر راه‌اندازی را متوقف می‌کند و تغییر تنظیم به restart نیاز دارد.
build سفارشی می‌تواند پیش‌فرض TCP، UDP و listener را تغییر دهد؛ مقدار صریح در
تنظیمات هسته اولویت دارد. افزایش `workers` این سقف‌ها را ضرب نمی‌کند و
`ram-profile` آن‌ها را تغییر نمی‌دهد.

حافظه با تقاضا و در چارچوب سقف بایت و تعداد رشد می‌کند. بودجه، slabهای pool،
header و alignment، اشیای آزاد رزروشده در cache worker، حافظه‌ی handoff بسته‌ی
CTP در هر دو جهت و buffer ورودی PTC تا زمانی که custom pbuf آن را نگه می‌دارد
شامل می‌شود. cache آزاد تا هنگام بازپس‌گیری در بودجه حساب می‌شود. همه‌ی flowهای
مجاز یا کل بودجه‌ی بایت از ابتدا تخصیص داده نمی‌شوند.

در بودجه‌ی بایت `B`، allocator مقدار `R = min(1048576, floor(B / 16))` بایت
را برای ترافیک بازیابی کنار می‌گذارد. داده‌ی عادی و cache آن حداکثر `B - R`
مصرف می‌کنند؛ فقط ACK/RST معتبر و واجد شرایط TCP بدون payload و خروجی
ACK/RST/keepalive در TCP از مسیر مستقل بازیابی استفاده می‌کنند. به این ترتیب وقتی ظرفیت
عادی پر است، acknowledgement هنوز می‌تواند داده‌ی صف ارسال را آزاد کند. این
فضا داخل همان بودجه است، حافظه‌ی ازپیش‌تخصیص‌یافته یا بودجه‌ی اضافه نیست.
ترافیک بازیابی هم محدود است و پس از پرشدن فضای خودش می‌تواند رد شود.

سقف RX wrapper برابر `L` شامل سهم بازیابی هم هست: برای `L > 1`، تعداد
`min(256, max(1, floor(L / 16)))` slot برای بازیابی کنار گذاشته می‌شود و
`L = 1` سهم رزروشده ندارد. پیش‌فرض `262144` یعنی حداکثر `261888` wrapper عادی
و `256` wrapper بازیابی. تعداد و سقف pool در API هر دو دسته را شامل می‌شوند.
CTP نیز داخل سقف ثابت handoff هر instance، یعنی ۱۶ MiB و ۴۰۹۶ تخصیص، سهم
۱ MiB و ۲۵۶ تخصیص برای بازیابی نگه می‌دارد؛ سهم عادی ۱۵ MiB و ۳۸۴۰ تخصیص است.
ورودی بسته و handoff ابتدا پذیرش عادی را امتحان می‌کنند و فقط بسته‌ی واجد
شرایط بازیابی در صورت نیاز به سهم رزروشده می‌رود. SYN، FIN و payload برنامه
همچنان از ظرفیت عادی استفاده می‌کنند.

این بودجه سقف RSS فرایند نیست. صف pending/ACK برنامه، receive staging پس از
پایان مالکیت pbuf، وضعیت line و نود، جدول‌های کنترلی engine و port، bufferهای
مستقل و منابع kernel حافظه‌ی دیگری مصرف می‌کنند. سقف handoff هر CTP برابر
۱۶ MiB و ۴۰۹۶ تخصیص و محدودیت صف هر flow، دریافت خارج از ترتیب و closer در هر
دو bridge مستقل باقی می‌مانند. `tcp-stack-receive-budget` هدف پنجره‌ی دریافت
اعلام‌شده‌ی هر worker است و سقف allocator را افزایش نمی‌دهد. پنجره‌ی ارسال یا
دریافت سقف پروتکل است، نه حافظه‌ی رزروشده برای هر اتصال.

نرسیدن ظرفیت می‌تواند اتصال تازه را نپذیرد، بسته را کنار بگذارد یا write مربوط
به TCP را تا برگشت منابع به تأخیر بیندازد؛ رفتار به مسیر مربوط بستگی دارد.
شکست واقعی تخصیص heap همچنان fatal است. ظرفیت را براساس flow و ترافیک هم‌زمان،
شامل handshake و اتصال‌های در حال بسته‌شدن، تعیین کنید؛ هر کاربر می‌تواند
flowهای زیادی داشته باشد. زنجیره‌ی `TunDevice -> PacketsToConnection` هم از
همین allocator استفاده می‌کند.

هر worker همچنان ۲۵۵ index برای netif دارد که loopback و نودهای متصل در آن
شریک‌اند. تمام‌شدن آن ساخت interface را رد می‌کند. ورودی بسته باید datagram
کامل IPv4 باشد؛ افزایش pool پذیرش fragment یا سیاست reassembly را تغییر نمی‌دهد.

<span id="api-ظرفیت-stack-stats"></span>

### API ظرفیت (`stack-stats`) {#capacity-api-stack-stats}

هر دو bridge عملیات فقط‌خواندنی `stack-stats` را ثبت می‌کنند. به client در
APIServer مجوز دقیق config، node و operation بدهید و از client معمول API با
[قالب‌بندی معمول API](../05-devguides/api/protocol.mdx) برای فرستادن درخواستی مانند نمونه‌ی زیر استفاده کنید:

```json
{
  "id": "capacity-1",
  "auth": {"client": "monitor", "token": "<configured token>"},
  "selector": {"config": "edge", "node": "ptc"},
  "operation": "stack-stats",
  "content_type": "application/json",
  "body_encoding": "utf8",
  "body": "{}"
}
```

selector و اطلاعات دسترسی را با مقادیر پیکربندی‌شده جایگزین کنید. بدنه باید
یک object خالی JSON با حداکثر ۶۴ بایت، شامل whitespace مجاز JSON، باشد.
فیلد اضافی، داده‌ی انتهایی و NUL پذیرفته نمی‌شود. پاسخ JSON با UTF-8 داخل body
نتیجه‌ی معمول API قرار می‌گیرد و وضعیت کل فرایند را نشان می‌دهد، نه فقط نود یا
worker انتخاب‌شده.

| فیلد پاسخ | معنی |
| --- | --- |
| `scope`، `dynamic` | مقدار `"process"` و قابل‌رشد بودن poolها |
| `memory_budget`، `reserved_bytes`، `peak_reserved_bytes` | سقف تنظیم‌شده، حافظه‌ی محاسبه‌شده‌ی فعلی و بیشینه‌ی آن |
| `recovery_headroom`، `recovery_bytes`، `external_recovery_bytes`، `recovery_refusals` | فضای بازیابی داخل سقف، حافظه‌ی محاسبه‌شده‌ی فعلی آن، زیرمجموعه‌ی external آن و تعداد رد درخواست به علت ظرفیت بایت بازیابی |
| `external_bytes`، `external_refusals` | حافظه‌ی handoff در CTP و ورودی نگه‌داری‌شده با pbuf در PTC و رزروهای ردشده‌ی آن |
| `byte_refusals`، `reclaimed_bytes` | رد درخواست به علت بودجه‌ی بایت و حافظه‌ی بازپس‌گرفته‌شده زیر فشار |
| `limits` | سقف مؤثر TCP/UDP، listener، segment و RX wrapper |
| `pools` | نام و اندازه‌ی هر شیء، سقف، تعداد تخصیص‌یافته/نگه‌داشته‌شده، بیشینه‌ی نگه‌داری، بایت رزروشده و رد درخواست تعداد/بایت در هر pool |
| `ports.tcp`، `ports.udp` | رزروهای فعلی و بیشینه، رد درخواست و رزروهای scoped/unscoped |

مجموع بایت‌ها و شمارنده‌های تجمعی برای حفظ دقت به شکل رشته‌ی دهدهی هستند؛
تعداد اشیا و سقف آن‌ها integer JSON است. `reserved_bytes` حافظه‌ی بازیابی را
هم شامل می‌شود و `external_bytes` شامل `external_recovery_bytes` است؛ این
زیرمجموعه‌ها را دوباره جمع نکنید. `held_includes_worker_caches` برابر
true است: `held` و `peak_held` اشیای آزاد رزروشده در cache worker را هم حساب
می‌کنند و تعداد اتصال زنده نیستند. بخش ظرفیت و پورت هرکدام زیر قفل خود snapshot
محدود می‌گیرند؛ کل پاسخ یک سرشماری اتمیک ترافیک نیست.

خروجی handler حداکثر ۳۲ KiB است و سقف پاسخ، بودجه‌ی حافظه‌ی کاری و deadline
درگاه را رعایت می‌کند. بدنه‌ی نامعتبر، در صورت جا شدن پاسخ خطا در این حدود،
`expected_empty_object` برمی‌گرداند؛ رد پاسخ به علت محدودیت می‌تواند بدنه‌ی خالی
داشته باشد. قبل از تغییر سقف، با شمارنده‌ی رد تعداد در هر pool، رد بودجه‌ی بایت
و رد پورت، منبع محدودکننده را مشخص کنید.

<span id="نکات-تخصصی-و-محدودیتها"></span>

### محدودیت‌ها {#limitations}

- IPv6 پیاده‌سازی نشده است.
- ورودی packet در upstream باید datagram کامل IPv4 باشد، از جمله ترافیک خطاب به fake DNS. fragmentهای پشتیبانی‌نشده پیش از پردازش DNS یا stack حذف می‌شوند.
- مسیر دریافت zero-copy هر بستهٔ ورودی را در descriptor استخری قرار می‌دهد. TCP ممکن است آن را برای تحویل خارج از ترتیب نگه دارد. رشد wrapper تابع `lwip-max-rx-wrappers` و بودجهٔ مشترک بایت است؛ حافظهٔ sbuf نگه‌داشته‌شده تا آزادسازی pbuf یا انتقال به staging دریافت برنامه جداگانه charge می‌شود. سقف‌های `TCP_OOSEQ_MAX_PBUFS` و `TCP_OOSEQ_MAX_BYTES` هر PCB همچنان برقرارند. رد ظرفیت بسته را با هشدار محدودشده از نظر نرخ دور می‌ریزد. توقف یک گره حسابداری pool سراسری فرایند را بازنشانی نمی‌کند.
- تبدیل‌های بسته ممکن است cursor بافر را در هر alignment بگذارند و lwIP هدرهای نوع‌دار IP/TCP را مستقیم از آن می‌خواند؛ پس حالت استثنایی در بافر هم‌تراز کپی و از همان wrapper سفارشی pbuf عبور می‌کند. عمداً در lwIP `PBUF_RAM` کپی نمی‌شود: بزرگ‌ترین کلاس تخصیص استخری با احتساب overhead برابر 16 KiB است و در غیر این صورت بستهٔ معتبر ناهماهنگ بزرگ‌تر از حدود آن اندازه بی‌صدا drop می‌شد، در حالی که مسیر هم‌تراز چنین سقفی ندارد.
- ICMP پیاده‌سازی نشده است.
- Pause در UDP با اتلاف است و صف نمی‌شود.
- route/netif context مربوط به IPv4 با تقاضا برای هر packet worker ساخته می‌شود، نه هر IP مقصد، و فعلاً سطح تنظیمی ندارد.
- هر engine مربوط به worker دارای 255 netif index مشترک برای loopback و گره‌های متصل است. index ممکن است میان engineها یکسان باشد؛ engine همراه netif دقیق اتصال را مشخص می‌کند. اتمام ظرفیت ایجاد را فوراً رد می‌کند.
- listenerهای TCP و UDP روی netif محلی worker، PCBهای pretend wildcard هستند، نه listener جدا برای هر پورت مقصد.
- پیکربندی fake-DNS پیش از تخصیص یا فعال‌سازی cache، prefix پیوسته، بازهٔ آدرس قابل استفاده، سقف محصول 262144 رکورد، هندسهٔ رزروشدهٔ name-map و تعداد بایت آرایهٔ رکورد را اعتبارسنجی می‌کند. هر پاسخ چندسؤالی پاسخ‌های موجود را pin و همهٔ نگاشت‌ها و قربانیان جدید را staging و با هم commit می‌کند؛ شکست تخصیص، درج یا هم‌زیستی هیچ fake answer نمی‌دهد و مصرف، ترتیب LRU، forward map و reverse recordهای موجود را تغییر نمی‌دهد.
- این گره فرض می‌کند payload بسته واقعاً ترافیک IP است و فراتر از بررسی‌های پایهٔ محافظه‌کارانه همهٔ حالت‌های malformed را اعتبارسنجی نمی‌کند.
- این گره تونل framing بسته نیست و header برای هر payload اضافه نمی‌کند؛ نیاز اضافی به padding چپ اعلام نمی‌کند.

## رفتار پیشرفته {#advanced-behavior}


<span id="مرز-نهاییسازی-checksum"></span>

### مرز نهایی‌سازی checksum {#checksum-finalization-boundary}

`PacketsToConnection` مصرف‌کنندهٔ نهایی درخواست محاسبهٔ مجدد checksum بافر بسته است. پیش از هر validation یا مسیر drop آن درخواست را می‌گیرد و پاک می‌کند، ورودی جابه‌جاشده را در حافظهٔ قابل تغییر و هم‌تراز قرار می‌دهد و checksumهای پشتیبانی‌شده را پیش از parsing نوع‌دار یا ورود lwIP ترمیم می‌کند. در نتیجه packet معیوب، IPv6، در حال توقف یا ردشده نمی‌تواند درخواستش را به بستهٔ نامرتبط بعدی روی line همان worker منتقل کند.

برای TCP یا UDP کامل IPv4، نهایی‌سازی checksum هدر IPv4 و transport را ترمیم می‌کند.

ورودی packet فقط datagram کامل IPv4 می‌پذیرد. MF یا fragment offset غیرصفر پیش از تحویل به stack drop محدود ایجاد می‌کند؛ DF به‌تنهایی مجاز است. برای تحویل datagram تکه‌شده، در ورودی دستگاه یا پیش از این گره reassembly انجام دهید. نخستین drop fragment پشتیبانی‌نشده هشدار می‌دهد؛ dropهای بعدی شمارندهٔ instance را افزایش می‌دهند و مجموع هنگام تخریب ثبت می‌شود. رد منابع ورودی را آزاد، packet line را حفظ و اتصال‌های دیگر را زنده نگه می‌دارد. ساختار malformed از مسیر validation/drop موجود می‌گذرد.

<span id="تفاوت-با-packetstostream"></span>

### تفاوت با PacketsToStream {#difference-from-packetstostream}

وقتی فقط می‌خواهید مرز packet‌های خام را روی stream transport حفظ کنید، `PacketsToStream` را همراه `StreamToPackets` به کار ببرید.

اگر می‌خواهید lwIP flow‌های TCP/UDP را بازسازی و آن‌ها را به شکل connection line‌های معمول WaterWall ارائه کند، از `PacketsToConnection` استفاده کنید.

<span id="checksum-در-اتصال-مستقیم-به-tundevice"></span>

### سیاست checksum مستقیم TunDevice {#direct-tundevice-checksum-policy}

اتصال مستقیم و دوطرفهٔ `TunDevice -> PacketsToConnection` در Linux، checksum
ورودی header مربوط به IPv4 و TCP/UDP را در حالت raw، checksum-only و GSO خودکار
معتبر فرض می‌کند؛ این رفتار مستقل از `gso` است و تنظیم اضافی ندارد. هر netif
محلی worker حالت منتشرشدهٔ همان instance را می‌خواند. PTC دیگر، ConnectionToPackets،
node واسط و سیستم‌عامل دیگر اعتبارسنجی عادی را حفظ می‌کنند. فرض اعتماد به ورودی
kernel در بخش چهارم راهنمای توسعه‌دهنده توضیح داده شده است.

در TUN، netif فعال PTC و fake DNS، بررسی checksum ورودی IPv4 و TCP/UDP، از جمله
ورودی بدون تضمین metadata، حذف می‌شود. parsing، طول دقیق، اعتبارسنجی metadata،
کپی alignment، guard مربوط به fragment و درخواست repair حفظ می‌شود. بررسی IPv6
و UDP-Lite فعال می‌ماند. تضمین مثبت offload فقط در کار خصوصی TUN باقی می‌ماند؛
اعتماد ورودی packet بدون تضمین را دارای metadata معتبر معرفی نمی‌کند.

اعتماد ورودی و offload خروجی مستقل‌اند. خروجی raw همچنان checksum کامل نرم‌افزاری
و checksum-on-copy مربوط به TCP دارد. فقط پس از مذاکرهٔ واقعی checksum offload
و آماده شدن منابع آن، خروجی transport واجد شرایط و checksum-on-copy مربوط به
TCP از محاسبهٔ payload صرف‌نظر می‌کنند. cache محاسبه‌نشده معتبر علامت نمی‌خورد و
در صورت نیاز checksum از کل pbuf محاسبه می‌شود. checksum خروجی header IPv4 همواره
تولید می‌شود. پاسخ بزرگ، از جمله fake DNS، پیش از fragmentation checksum کامل
می‌گیرد. در حالت offload مذاکره‌شده، TUN packet کامل را با seed pseudoheader و
`NEEDS_CSUM` و fragment را با metadata عادی می‌نویسد. حالت‌ها تا پایان quiescence
و drain مربوط به worker ثابت می‌مانند.

### مدل جریان {#flow-model}


#### ورود بسته {#packet-ingress}

payload در upstream باید یک بستهٔ کامل IPv4 باشد.

`PacketsToConnection` برای هر مقصد IP یک `netif` lwIP نمی‌سازد. در عوض برای هر packet worker فرستنده، route context محلی worker نگه می‌دارد. برای IPv4 آن context مالک یک netif lwIP با `NETIF_FLAG_PRETEND` فعال است.

IP مقصد در بسته و tuple مربوط به PCB حفظ می‌شود، ولی کلید ساخت route context جداگانه نیست. در منبع فعلی، lookup مربوط به route context IPv4 با شناسهٔ packet worker انجام می‌شود. هر route محلی worker فقط پس از موفقیت ساخت pretend netif، TCP wildcard listener و UDP wildcard PCB منتشر می‌شود؛ بسته‌های بعدی همان route کامل را استفاده می‌کنند و ساخت listener برای هر بسته تکرار نمی‌شود.

وصلهٔ pretend در lwIP مربوط به WaterWall به PCBهای wildcard اجازه می‌دهد بستهٔ هر مقصد و پورتی را روی pretend netif بپذیرند و tuple مقصد محلی اصلی را همچنان حفظ کنند.

#### ساخت flow TCP {#tcp-flow-creation}

وقتی lwIP یک اتصال TCP می‌پذیرد:

- `PacketsToConnection` یک line واقعی WaterWall می‌سازد؛
- context آدرس مبدأ/مقصد line را از tuple TCP پر می‌کند؛
- upstream `Init` را زمان‌بندی می‌کند؛
- payloadهای بعدی را با upstream `Payload` می‌فرستد.

payload downstream تونل بعدی با `tcp_write()` به lwIP نوشته می‌شود. TCP listener برای هر پورت مقصد جداگانه نیست؛ به صورت pretend listener روی netif محلی worker bind می‌شود و PCBهای پذیرفته‌شده IP و پورت مقصد اصلی بسته را حمل می‌کنند.

#### ساخت flow UDP {#udp-flow-creation}

UDP به ازای route context محلی worker و 4-tuple شامل آدرس IPv4 مبدأ و مقصد و پورت مبدأ و مقصد دنبال می‌شود.

با رسیدن نخستین datagram یک flow:

- `PacketsToConnection` line واقعی WaterWall برای آن می‌سازد؛
- context آدرس مبدأ و مقصد را پر می‌کند؛
- عملیات Open بررسی‌شده روی worker مالک را در صف می‌گذارد تا upstream `Init` ارسال و یک idle timer فعال شود؛
- datagramها را با upstream `Payload` می‌فرستد.

Open کنترل ضروری است و پیش از عملیات payload عمداً lossy صف می‌شود. اگر پذیرش Open رد شود، گره ابتدا PCB، timer و مدخل flow-map را در engine مالک جدا، line تحت مالکیت را در رجیستری reconciliation نهایی ازپیش‌تخصیص‌یافته ثبت و سپس برای تشدید، خاموشی منظم درخواست می‌کند. بنابراین پاک‌سازی به صف ردشده یا یافتن flow هنوز ثبت‌شده توسط Stop وابسته نیست. رد بعدی payload همچنان drop عادی UDP است، زیرا timer پیش‌تر flow را محدود کرده است.

payload downstream تونل بعدی از UDP PCB متصل برگردانده می‌شود و آدرس و پورت مقصد محلی اصلی به عنوان مبدأ بسته استفاده می‌شوند. UDP line با timeout بی‌فعالیتی بسته می‌شود، نه با معناشناسی half-close بسته.

مانند TCP، UDP listener اولیه به ازای هر پورت مقصد جدا نیست. مسیر pretend UDP یک PCB متصل برای هر flow با tuple اصلی مبدأ/مقصد ایجاد یا استفاده می‌کند و `PacketsToConnection` آن tuple را به line WaterWall نگاشت می‌کند.

### مدل worker و طول عمر {#worker-and-lifetime-model}

این تونل در سمت بسته روی packet line مشترک قرار می‌گیرد و در سمت بعد lineهای عادی WaterWall می‌سازد.

قواعد مهم داخلی:

- packet line در runtime بسته نمی‌شود.
- `Init` packet line رویداد bootstrap راه‌اندازی است، نه باز کردن هر flow.
- lineهای TCP/UDP تولیدشده متعلق به packet worker پذیرندهٔ flow هستند.
- callbackهای lwIP کار را با قرارداد دارای نتیجهٔ نوع‌دار `lineScheduleTask()` و `lineScheduleTaskWithBuf()` به worker مالک line برمی‌گردانند. رد کنترل ضروری تولیدکننده را در engine مالک به وضعیت نهایی می‌برد؛ cancellation اختیاری عمداً null است و پاک‌سازی روی مالک می‌ماند. تحویل با بافر، بافر کپی‌شده را در هر نتیجه منتقل می‌کند.
- بستن UDP بر اثر بی‌فعالیتی از یک timer قابل لغو روی worker مالک استفاده می‌کند. timer هنگام فعال بودن دقیقاً یک reference line دارد، فعالیت همان timer را بازنشانی می‌کند و close پیش از صفر شدن state، timer را لغو و reference را آزاد می‌کند.
- بسته‌های بازگشتی به سمت packet از packet line همان worker استفاده می‌کنند.
- netif محلی هر worker از `mtu` نمونه استفاده می‌کند؛ پاسخ بزرگ‌تر از آن به صورت fragmentهای IPv4 خارج می‌شود، نه یک بستهٔ خام بزرگ که توپولوژی قادر به حمل آن نیست. پاسخ Fake-DNS نیز از همان netif خارج می‌شود، نه مستقیماً به همسایه: نام سؤال بازتاب‌شده و رکورد پاسخ اندازهٔ متغیر دارند و پاسخ می‌تواند از MTU کوچک IPv4 بزرگ‌تر شود. PTC حداقل قانونی MTU هسته یعنی 68 بایت را می‌پذیرد. پاسخ در `PBUF_RAM` متعلق به stack کپی و به صورت datagram UDP از `ip4_output_if()` ارسال می‌شود؛ lwIP هدر IPv4 را می‌سازد، مقدار identification مشترک تخصیص می‌دهد و fragmentation را با offset، پرچم MF، طول هر fragment و checksum متعلق به stack انجام می‌دهد. این انتشار در engine مالک مجاز است، زیرا خروجی netif فقط گیرندهٔ TUN تأییدشدهٔ enqueue-only را inline فراخوانی می‌کند؛ همسایه‌های دلخواه deferred باقی می‌مانند.
- انتشار packet با gate پذیرشی محافظت می‌شود که تا پایان callback همسایهٔ قبلی نگه داشته می‌شود؛ کار `Init`/`Payload`/`Resume`/`Finish` line عادی از gate دیگری استفاده می‌کند که تا پایان callback همسایهٔ بعدی نگه داشته می‌شود. shutdown سراسری هر دو gate را در `onQuiesceRequest()` می‌بندد و پیش از توقف هر مؤلفه، در `onQuiesceWait()` منتظر callbackهای پذیرفته‌شده می‌ماند. callback پذیرفته‌شده پیش از توقف همسایه تمام می‌شود و کار صف‌شدهٔ بعدی لغو می‌شود. کار عادی ردشدهٔ سمت بعد هر آنچه مالک است بازیافت و teardown را به مسیر مالک واگذار می‌کند؛ line مقداردهی‌شده همچنان در drain worker مالک یک `Finish` صریح teardown دریافت می‌کند.
- خروجی netif هر بستهٔ pbuf را مستقیم در یک sbuf دارای padding و best-fit کپی می‌کند. TunDevice متقابل و بلافاصله مجاور که تحویل enqueue-only را تأیید کند همان بافر را inline روی packet worker مالک می‌گیرد؛ سایر همسایه‌ها آن را deferred می‌گیرند. callback دلخواه نمی‌تواند به ورودی stack بازوارد شود. quiesce پذیرش خروجی را می‌بندد؛ پیام لغوشده sbuf جداشدهٔ خود را بدون قرض‌گرفتن pool worker تخریب می‌کند. transactionهای نگاشت Fake-DNS و کپی نام معکوس از یک mutex گره مشترک میان workerها استفاده می‌کنند. هیچ pointer مدخل cache از آن محدوده بیرون نمی‌رود. mutex پیش از خروجی stack، callback همسایه یا post به worker آزاد می‌شود.
- parser سطح بالا پیش از هم‌تراز کردن cursor فقط بایت نسخه را می‌خواند. بافر جابه‌جاشدهٔ بسته پیش از دسترسی نوع‌دار IPv4/UDP در sbuf هم‌تراز کپی می‌شود؛ fake-DNS پیش از پاسخ یا تغییر cache هدر IPv4 و هر checksum غیرصفر UDP را نیز بررسی می‌کند، مگر در جفت مستقیم فعال TUN. بررسی ساختاری در هر دو حالت برقرار است.
- ورودی packet در upstream، fragmentهای IPv4 را پیش از fake DNS، ایجاد route/listener یا ورود lwIP رد می‌کند. بستهٔ بازسازی‌شده مالکیت معمول بافر دارد و به claim تسویهٔ fragment برای هر بافر نیاز ندارد.
- هر line تولیدشدهٔ TCP/UDP تا حذف توسط مسیر close یکتای آن در فهرست مالک همان worker ثبت می‌ماند. `onWorkerStop` lineهای worker را drain و تولیدکنندگان PCB، route-map، callback و UDP-idle را در engine جدا می‌کند؛ تکمیل `Init` سمت بعد را حفظ، state line مربوط به PTC را تخریب، در صورت نیاز دقیقاً یک `Finish` برای teardown سمت بعد ارسال و `lineDestroy()` را فراخوانی می‌کند. Stop پیکربندی منتظر drain همهٔ workerها می‌ماند؛ shutdown نهایی worker همان drain را محلی و بدون اتکا به پذیرش پیام جدید انجام می‌دهد.
- Stop پیش از حذف netif، همهٔ PCBهای UDP هر flow و wildcard و TCP listener متعلق به خود را صریح جدا می‌کند. وصلهٔ lwIP در WaterWall این را پیش‌شرط raw-owner می‌داند و اگر هر یک از مالک‌های خام باقی باشد `netif_remove()` را رد می‌کند؛ اشاره‌گری که تونل ممکن است هنوز نگه دارد بی‌صدا آزاد نمی‌شود. شکست تبدیل PCB کامل TCP به listener نیز پیش از retry مسیر، آن PCB را می‌بندد یا abort می‌کند.

این کار تخریب line و teardown state تونل را در سمت line عادی WaterWall نگه می‌دارد، نه با اتکا به مالکیت موردی پیام بین workerها. lineهای TCP/UDP ساخته‌شده در داخل، connection line عادی و جدا از packet line پایدار worker هستند و می‌توانند در runtime عادی بسته و تخریب شوند.

<span id="معناشناسی-callback-و-lifecycle"></span>

### رفتار Finish / Close {#finish--close-behavior}

وقتی سمت شبکه flow را می‌بندد:

- PCB متصل TCP حتی با صف خالی برنامه به closer متعلق به instance منتقل می‌شود؛
- closer فقط suffix را که `tcp_write()` نپذیرفته کپی می‌کند؛ بایت‌هایی که قبلاً به lwIP کپی شده‌اند تکرار نمی‌شوند؛
- receive credit بازگردانده و دادهٔ همتا مصرف می‌شود؛ `tcp_shutdown()` فقط TX را می‌بندد و پس از تمام بایت‌های پذیرفته‌شده FIN می‌فرستد؛
- این تونل state line خود را تخریب می‌کند؛
- اگر upstream `Init` قبلاً فرستاده شده، upstream `Finish` منتشر می‌شود؛
- سپس `PacketsToConnection`، line ساخته‌شده در داخل را تخریب می‌کند.

وقتی تونل بعدی downstream `Finish` می‌فرستد:

- `PacketsToConnection`، PCB متصل TCP را به همان closer graceful منتقل می‌کند؛
- state line خود را تخریب می‌کند؛
- line ساخته‌شده در داخل را تخریب می‌کند.

این downstream `Finish` را به سمت upstream بازتاب نمی‌دهد.

closer فازهای یکنواخت delivering، FIN-pending و closing دارد. deadline تحویل و بسته‌شدن همتا به 30 و 60 ثانیه محدود است و هر instance حداکثر 4096 closer و 16 MiB suffix کپی‌شده نگه می‌دارد. شکست تخصیص، ظرفیت، write نهایی یا deadline همان flow را reset می‌کند؛ Stop پیش از حذف route/netif همهٔ closerهای فعال را abort می‌کند.

این رفتار با قواعد جهت WaterWall برای line ساخته‌شده در داخل مطابقت دارد. packet line مشترک با این closeها تخریب نمی‌شود و تا تخریب زنجیره زنده می‌ماند.

### Pause / Resume {#pause--resume}


<span id="tcp-backpressure"></span>

#### TCP {#tcp}

backpressure TCP با WaterWall یکپارچه است:

- اگر lwIP تمام بایت‌های downstream را نپذیرد، باقیمانده صف می‌شود؛
- upstream با `tunnelNextUpStreamPause()` متوقف می‌شود؛
- callbackهای sent در lwIP صف را تخلیه می‌کنند و `tcp_poll` وقتی نخستین write هیچ بایتی نپذیرفته پیشرفت محدود فراهم می‌کند؛
- وقتی دوباره writable شود upstream با `tunnelNextUpStreamResume()` از سر گرفته می‌شود؛
- مجموع و محاسبهٔ بایت باقی‌ماندهٔ رکوردهای acknowledgement در 32 بیت حفظ می‌شود؛ پس یک بافر stream می‌تواند از 65535 بایت بزرگ‌تر باشد، هرچند هر callback sent در lwIP شمار 16 بیتی دارد. بافر خالی TCP بدون ورود به صف write یا acknowledgement مصرف می‌شود.

برای backpressure دریافت:

- downstream `Pause`، `tcp_recved()` فوری را متوقف می‌کند؛
- downstream `Resume` اعتبار دریافت معوق را آزاد می‌کند.

<span id="محدودیت-udp-backpressure"></span>

#### UDP {#udp}

UDP مدل backpressure واقعی stream ندارد. رفتار فعلی:

- downstream `Pause`، flow را pause علامت می‌زند؛
- datagram UDP ورودی هنگام Pause دور ریخته می‌شود؛
- downstream `Resume` وضعیت pause را پاک می‌کند؛
- payload برنامه در downstream به بیشینهٔ IPv4 UDP یعنی `65507` بایت محدود است؛ بافر بزرگ‌تر بدون تبدیل محدودکننده به APIهای 16 بیتی lwIP دور ریخته می‌شود، اما payload خالی UDP یک datagram معتبر فقط با header است.

این رفتار عمدی و محدودیت فعلی مسیر UDP است.

<span id="منابع-engine-و-چرخهٔ-عمر"></span>

### منابع engine و چرخهٔ عمر {#engine-resources-and-lifecycle}

runtime به‌صورت lazy برای هر event worker عادی یک engine خام lwIP می‌سازد که همهٔ bridgeهای آن worker به اشتراک می‌گذارند. thread جداگانهٔ stack یا mutex هستهٔ پروتکل وجود ندارد. PTC مالک flow را از tuple فعلی بسته انتخاب می‌کند؛ CTP مالک line برنامه را حفظ و بستهٔ برگشتی را پس از lookup tuple/generation صف می‌کند. callbackهای normal-line و همسایهٔ packet دلخواه، حتی روی همان worker، deferred می‌مانند. فقط گیرندهٔ بلافاصله مجاور PTC با تأیید enqueue-only استثنای تحویل مستقیم دارد.

poolهای قابل‌رشد flow/payload از سقف سراسری بالا استفاده می‌کنند. هر engine فعال جدول‌های کنترل محدود و 17 رکورد timeout دارد؛ worker بدون استفاده engine تخصیص نمی‌دهد. رزرو پورت مبدأ متصل CTP، tuple کامل شبکه را تفکیک و تا بازپس‌گیری PCB، شامل TIME_WAIT، حفظ می‌کند. رزرو unconnected همچنان پورت را محافظه‌کارانه کنار می‌گذارد. ID fragment تولیدی IPv4 و IPv6 توالی مشترک جدا با wrap محدود قبلی دارند. فهرست‌های detached drain محلی worker، سهم تجمیعی 4,096 object و 16 MiB هر گره را حفظ می‌کنند. lockهای pool/quota هرگز پیمایش stack یا خروجی را در بر نمی‌گیرند.

quiescence مربوط به worker، timerهای engine را پیش از بسته‌شدن پذیرش حلقهٔ عادی جدا می‌کند. گره‌ها در drain مالک ریشه‌های stack محلی را حذف می‌کنند؛ سپس runtime پس از تسویهٔ پیام‌های detached و پیش از ناپدید شدن loop و pool، engineها را آزاد می‌کند. poolهای مشترک، حساب‌های اشغال و secret مربوط به ISN فرایند پس از خروج همهٔ workerها نهایی می‌شوند.
