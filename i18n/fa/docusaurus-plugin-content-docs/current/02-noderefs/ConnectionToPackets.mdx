# ConnectionToPackets {#connectiontopackets-node}

<span id="connectiontopackets"></span>

## نمای کلی {#overview}

`ConnectionToPackets` وارون active-open گره `PacketsToConnection` است. یک connection line عادی WaterWall را می‌گیرد، flow متناظر TCP یا UDP را در پشتهٔ lwIP درون فرایند باز می‌کند و بسته‌های خام IPv4 حاصل را روی سمت packet زنجیره صادر می‌کند. بسته‌های برگشتی این سمت به همان flow تزریق می‌شوند و داده به صورت payload عادی downstream روی connection اولیه خارج می‌شود.

```text
ordinary WaterWall connection line
        -> ConnectionToPackets
        -> raw IPv4 TCP/UDP packets on the worker packet line

return IPv4 packets
        -> ConnectionToPackets
        -> downstream data/events on the original connection line
```

`mtu` یک بار هنگام ساخت تعیین و اعتبارسنجی می‌شود. هر نمونه MTU خود را نگه می‌دارد و override گره دیگر آن را تغییر نمی‌دهد. مقدار نامعتبر ارث‌رسیده از `misc.mtu` هسته به override صریح و پشتیبانی‌شدهٔ همان گره نیاز دارد.

### ماهیت گره {#what-it-is}

این یک bridge انتقال در فضای کاربر است، نه جایگزین شفاف رابط TUN سیستم‌عامل. به دستگاه TUN کرنل، raw socket یا دسترسی root نیاز ندارد.

برنامهٔ محلی باید از آداپتور اتصال مانند `TcpListener`، `UdpListener`، `TcpUdpListener` یا `Socks5Server` وارد WaterWall شود. گرفتن ترافیک دلخواه از سوکت‌های نامرتبط کرنل بیرون از محدودهٔ این گره است و همچنان به مسیریابی سیستم‌عامل یا VPN نیاز دارد.

### محدوده {#scope}

پشتیبانی می‌شود:

- TCP روی IPv4؛
- UDP روی IPv4، از جمله datagram بزرگ‌تر از یک MTU؛
- مقصد IP و مقصد domain از طریق `DomainResolver` داخلی؛
- چند event worker.

رد یا drop می‌شود:

- IPv6، به‌صورت دائمی و عامدانه؛
- ICMP و protocol‌های غیر TCP/UDP؛
- UDP payload بالاتر از `65507` بایت؛
- packet برگشتی بدون flow ثبت‌شده.

تحویل ICMP error و حفظ source port اصلی application فعلاً پیاده‌سازی نشده‌اند.

#### فقط IPv4، بر اساس طراحی {#ipv4-only-by-design}

این گره فقط IPv4 صادر می‌کند. این تصمیم محصول است، نه قابلیت ناقص: هدف، اتصال یک connection به توپولوژی بسته‌ای است که سمت مقابلش پشتهٔ IPv4 دارد و بستهٔ IPv6 در آن مقصدی نخواهد داشت.

این قرارداد در دو طرف اعمال می‌شود:

- با resolve محلی فعال، `dns-behaviour.strategy` مؤثر باید `only-ipv4` باشد تا دامنهٔ فقط AAAA در DNS با پیامی شامل نام شکست بخورد، به جای آنکه آدرسی بدهد که گره سپس رد می‌کند؛
- `target-address` صریح IPv6 خطای پیکربندی است؛
- مقصدی که با این حال IPv6 باشد فقط همان line را با خطای صریح می‌بندد.

پشتیبانی فعال IPv6 در lwIP تغییر نمی‌کند. گره‌های یک worker engine آن را به اشتراک می‌گذارند؛ این bridge همچنان فقط IPv4 می‌پذیرد.

## جایگاه معمول در زنجیره {#typical-placement}


<span id="توپولوژیهای-معمول"></span>

### توپولوژی‌ها {#topologies}

برای مقصد ثابت، `target-address` و `port` را در `ConnectionToPackets` تنظیم کنید:

```text
TcpListener -> ConnectionToPackets -> packet transport
```

یک مسیر کامل و مستقیم بدون نیاز به root یا transport مجزا:

```text
TcpListener -> ConnectionToPackets -> PacketsToConnection -> TcpUdpConnector -> destination
```

برای مقصد متفاوت در هر connection، node قبلی می‌تواند destination context را تعیین کند:

```text
TcpListener -> Socks5Server -> ConnectionToPackets
            -> PacketsToConnection -> TcpUdpConnector -> destination
```

یا روی WireGuard:

```text
local application branch: TcpListener -> Socks5Server -> ConnectionToPackets -> Bridge A
local UDP branch:         UdpStatelessSocket -> WireGuardDevice -> Bridge B

remote UdpStatelessSocket
  -> WireGuardDevice
  -> PacketsToConnection
  -> TcpUdpConnector
  -> destination
```

`Bridge A` و `Bridge B` را pair کنید تا شاخهٔ تبدیل connection به packet، به سمت
packet در WireGuard وصل شود. `UdpStatelessSocket` فقط در ابتدای chain مجاز است؛ پس
باید در ابتدای شاخه‌ی خودش بماند و پس از `WireGuardDevice` قرار نگیرد.

آدرس مجازی `source-ipv4` باید در توپولوژی packet مسیر برگشت داشته باشد. در WireGuard،
سمت محلی معمولاً peer را با route مقصد `0.0.0.0/0` انتخاب می‌کند. peer سمت مقابل
هم باید این آدرس مجازی مبدأ را، معمولاً به‌صورت `/32`، مجاز بداند.

این نمودارها توپولوژی را نشان می‌دهند، نه config کامل nodeها. در ورودی SOCKS،
`Socks5Server` را برای TCP CONNECT تنظیم و حالت احراز هویت آن را انتخاب کنید.
برای اجرا بدون root از پورت بالای listener استفاده کنید. دو شاخهٔ محلی باید
[Bridgeهای جفت و متقابل](./Bridge.mdx) داشته باشند؛ برای تنظیم UDP و کلیدها از
[جفت WireGuard](./WireGuardDevice.mdx#example-pair) کمک بگیرید. WireGuard از مقصد
داخلی برای انتخاب peer استفاده می‌کند و peer راه‌دور باید source مجازی client
را مجاز بداند. در سمت مقابل
[TcpUdpConnector باید مقصد را حفظ کند](./PacketsToConnection.mdx#typical-placement)،
مگر آنکه backend ثابت می‌خواهید. این توپولوژی socket-to-socket به TUN، forwarding
IP میزبان یا NAT نیاز ندارد.

## نمونهٔ کاربردی ساده {#minimal-practical-example}

این قطعهٔ گره است؛ همسایه‌ها و همتاهای اشاره‌شده را در همان استقرار تعریف کنید.

آن را پس از گرهی مانند Socks5Server قرار دهید که مقصد و پورت IPv4 را فراهم می‌کند. `packet-side` را به عنوان توپولوژی بسته تعریف کنید و امکان مسیر برگشت به `10.90.0.1` را در آن برقرار کنید. این گره فقط IPv4 TCP/UDP را پشتیبانی می‌کند؛ MTU سازگار با آن توپولوژی انتخاب کنید.

```json
{
  "name": "connection-to-packets",
  "type": "ConnectionToPackets",
  "settings": {
    "source-ipv4": "10.90.0.1",
    "mtu": 1420
  },
  "next": "packet-side"
}
```

برای پیش‌فرض‌ها و الزام‌های مشروط [پیکربندی](#configuration) و برای نمونه‌های کامل و محدودیت‌های عملیاتی [کاربرد و رفع اشکال](#usage-and-troubleshooting) را ببینید.

## پیکربندی {#configuration}


<span id="تنظیمات"></span>

### تنظیمات {#settings}

| تنظیم | اجباری | پیش‌فرض | معنی |
| --- | --- | --- | --- |
| `source-ipv4` | بله | ندارد | source IPv4 مجازی هر netif مربوط به worker و هر PCB بازشده به صورت فعال؛ عمداً پیش‌فرض ندارد، زیرا آدرس انتخاب‌شدهٔ خاموش ممکن است با آدرس واقعی تداخل کند. نباید `0.0.0.0`، loopback، multicast یا broadcast باشد. |
| `target-address` | خیر | `dest_context->address` | آدرس IPv4 یا domain مقصد؛ رشتهٔ دقیق `dest_context->address` آدرس مقصد ورودی را نگه می‌دارد. آدرس تنظیم‌شده فقط بخش آدرس را جایگزین می‌کند. IPv6 صریح پذیرفته نمی‌شود. |
| `port` | خیر | `dest_context->port` | عدد صحیح پورت مقصد در بازهٔ `1..65535`، یا رشتهٔ دقیق `dest_context->port` برای نگه‌داشتن پورت مقصد ورودی. |
| `mtu` | خیر | `misc.mtu` سراسری | بازهٔ `576..9000`؛ MSS از آن مشتق و UDP بالاتر از آن fragment می‌شود. |
| `dns-behaviour` | خیر | lookup بومی با `only-ipv4` | کنترل lookup محلی و انتقال DNS. resolve فعال به `only-ipv4` یا `core-settings` با همین مقدار در core نیاز دارد. |
| `tcp-connect-timeout-ms` | خیر | `30000` | deadline اتصال TCP active-open؛ با انقضا line به سمت گره قبلی بسته می‌شود. |
| `max-pending-bytes` | خیر | `262144` | سقف دادهٔ application پیش از connect یا هنگام پُربودن send window؛ بازهٔ `1024..67108864`. پذیرش یک headroom ثابت 1 MiB برای تحویل هم دارد؛ عبور از سقف مجموع همان flow را حذف می‌کند. |

مقدار پیش‌فرض فقط وقتی استفاده می‌شود که فیلد نوشته نشده باشد. نوع اشتباه، عدد
کسری یا مقدار خارج از بازه باعث رد config با ذکر نام فیلد می‌شود. MTU مربوط به
core پیش از تبدیل به نوع عددی کوچک‌تر، در بازهٔ `68..65535` اعتبارسنجی می‌شود.
اگر مقدار به‌ارث‌رسیده خارج از بازهٔ مجاز خود node باشد، config باز هم رد می‌شود.

```json
{
  "name": "connection-to-packets",
  "type": "ConnectionToPackets",
  "settings": {
    "source-ipv4": "10.90.0.1",
    "mtu": 1420,
    "dns-behaviour": {"resolve": true, "strategy": "only-ipv4"},
    "tcp-connect-timeout-ms": 30000,
    "max-pending-bytes": 262144
  },
  "next": "packet-bridge"
}
```

این قطعهٔ node برای شاخهٔ application روی WireGuard در بالاست.
`packet-bridge` نام node مربوط به `Bridge A` است؛ جفت متقابل و شاخهٔ جداگانهٔ
UDP/WireGuard را مطابق بخش توپولوژی تنظیم کنید.

<span id="رفتار-dns"></span>

### رفتار DNS {#dns-behaviour}

resolve کردن نام دامنه یعنی پیدا کردن آدرس IPv4 لازم برای باز کردن flow مربوط
به TCP یا UDP. این node ابتدا مقصد را از `target-address`، `port` یا مقصد ورودی
انتخاب می‌کند. فقط وقتی آدرس انتخاب‌شده یک نام دامنهٔ resolve‌نشده باشد و resolve
محلی فعال باشد، lookup انجام می‌شود. آدرس عددی IPv4 یا مقصدی که از قبل به IPv4
resolve شده باشد به lookup نیاز ندارد. IPv6 پشتیبانی نمی‌شود.

با حذف `dns-behaviour`، resolve محلی در حالت `native` و با strategy برابر
`only-ipv4` فعال می‌ماند.

این lookup را با `settings.dns-behaviour` تنظیم کنید:

```json
{
  "dns-behaviour": {
    "resolve": true,
    "mode": "direct",
    "strategy": "only-ipv4",
    "servers": ["203.0.113.53:53"]
  }
}
```

این IP نمونهٔ مستندات است؛ آن را با سرور خود جایگزین کنید.

| فیلد | معنی |
| --- | --- |
| `resolve` | boolean اجباری: `true` اجازهٔ lookup نام دامنهٔ resolve‌نشده را می‌دهد و `false`، lookup محلی را غیرفعال می‌کند. |
| `mode` | `native` (پیش‌فرض هنگام فعال بودن)، `direct` یا `chain`. |
| `strategy` | `only-ipv4` (پیش‌فرض)، یا `core-settings` فقط وقتی core هم `only-ipv4` را انتخاب کند. strategyهای دیگر رد می‌شوند. |
| `servers` | ۱ تا ۳۲ endpoint عددی IP، IP:port یا [IPv6]:port؛ در direct/chain اجباری و در native ممنوع. |
| `dns-next` | نام غیرخالی ورودی DNS، فقط در chain. |

`native` از تنظیمات DNS در core و resolver مشترک worker استفاده می‌کند. هنگام
فعال بودن resolve محلی، این حالت پیش‌فرض انتقال DNS است.

`direct` درخواست‌های DNS را از طریق یک connector خصوصی TCP/UDP در WaterWall به
سرورهایی که مشخص کرده‌اید می‌فرستد.

`chain` درخواست‌های DNS را از chain انتخابی می‌فرستد. برای محافظت از آن‌ها، مسیری
رمزنگاری‌شده مانند VPN خود را انتخاب کنید؛ این حالت به‌تنهایی درخواست‌ها را
رمزنگاری نمی‌کند. مسیر DNS باید هم درخواست‌های UDP و هم fallback روی TCP را حمل
کند. خطای route یا lookup باعث تغییر به DNS بومی یا حالت دیگر نمی‌شود.

در حالت `chain`، مقدار `dns-next` را نام یک شاخهٔ DNS جدا بگذارید که هم UDP و هم
TCP را پشتیبانی کند. این شاخه نباید از قبل به node دیگری تعلق داشته باشد. این node
شاخهٔ DNS پیش‌فرض ندارد و نام‌بردن از خود آن مجاز نیست.

شکل غیرفعال دقیقاً `"dns-behaviour": {"resolve": false}` است و فیلدهای `mode`، `strategy`، `servers` و `dns-next` را رد می‌کند. object تهی، null، نوع غیرobject، فیلد ناشناخته و strategy عددی رد می‌شوند. نام strategy باید یکی از رشته‌های canonical بالا با حروف کوچک باشد. `core-settings` فقط اولویت آدرس را انتخاب می‌کند و انتقال DNS را تغییر نمی‌دهد.

با `resolve: false`، آماده‌سازی مقصد همچنان اجرا می‌شود. آدرس عددی IPv4 یا مقصدی که از قبل به IPv4 resolve شده باشد کار می‌کند؛ نام resolve‌نشده از مسیر عادی خطای line یا datagram رد می‌شود و به DNS بومی برنمی‌گردد.

هنگام فعال بودن resolve، strategy مؤثر باید `only-ipv4` باشد؛ `core-settings` فقط وقتی پذیرفته می‌شود که core هم همین مقدار را داشته باشد. حالت chain به `dns-next` صریح نیاز دارد.

مثال‌های native، direct و chain محافظت‌شده و محدودیت گزینه‌های core را در [DomainResolver](./DomainResolver.mdx) ببینید. این سیاست فقط lookupهای متعلق به همین node را کنترل می‌کند؛ fake DNS در PTC، DNS سیستم در TunDevice و همهٔ منابع DNS برنامه را تغییر نمی‌دهد.

## کاربرد و رفع اشکال {#usage-and-troubleshooting}


<span id="ظرفیت"></span>

### ظرفیت {#capacity}

همه‌ی نمونه‌های `ConnectionToPackets` و `PacketsToConnection` در یک فرایند از
allocator قابل‌رشد lwIP و سقف‌های مشترک استفاده می‌کنند. این فیلدها را زیر
`misc` در `core.json` تنظیم کنید، نه در `settings` نود:

| تنظیم هسته | پیش‌فرض استاندارد | منبع |
| --- | ---: | --- |
| `lwip-memory-budget` | `536870912` (512 MiB) | حافظه‌ی pool و حافظه‌ی نگه‌داری‌شده‌ی محاسبه‌شده برای stack |
| `lwip-max-tcp-flows` | `65536` | وضعیت اتصال TCP، شامل handshake و اتصال‌های در حال بسته‌شدن |
| `lwip-max-udp-flows` | `65536` | وضعیت اتصال UDP |
| `lwip-max-tcp-listeners` | `1024` | اشیای listener در TCP |
| `lwip-max-tcp-segments` | `1048576` | segmentهای ارسال، ارسال مجدد و دریافت TCP |
| `lwip-max-rx-wrappers` | `262144` | wrapperهای PTC برای نگه‌داری بسته‌ی ورودی |

سقف تعداد، عدد صحیح در بازه‌ی `1..4294967295` را می‌پذیرد. بودجه‌ی بایت از
`1048576` تا مقدار کوچک‌تر از `SIZE_MAX` پلتفرم و `9223372036854775807` است.
مقدار نامعتبر راه‌اندازی را متوقف می‌کند و تغییر تنظیم به restart نیاز دارد.
build سفارشی می‌تواند پیش‌فرض TCP، UDP و listener را تغییر دهد؛ مقدار صریح در
تنظیمات هسته اولویت دارد. افزایش `workers` این سقف‌ها را ضرب نمی‌کند و
`ram-profile` آن‌ها را تغییر نمی‌دهد.

حافظه با تقاضا و در چارچوب سقف بایت و تعداد رشد می‌کند. بودجه، slabهای pool،
header و alignment، اشیای آزاد رزروشده در cache worker، حافظه‌ی handoff بسته‌ی
CTP در هر دو جهت و buffer ورودی PTC تا زمانی که custom pbuf آن را نگه می‌دارد
شامل می‌شود. cache آزاد تا هنگام بازپس‌گیری در بودجه حساب می‌شود. همه‌ی flowهای
مجاز یا کل بودجه‌ی بایت از ابتدا تخصیص داده نمی‌شوند.

در بودجه‌ی بایت `B`، allocator مقدار `R = min(1048576, floor(B / 16))` بایت
را برای ترافیک بازیابی کنار می‌گذارد. داده‌ی عادی و cache آن حداکثر `B - R`
مصرف می‌کنند؛ فقط ACK/RST معتبر و واجد شرایط TCP بدون payload و خروجی
ACK/RST/keepalive در TCP از مسیر مستقل بازیابی استفاده می‌کنند. به این ترتیب وقتی ظرفیت
عادی پر است، acknowledgement هنوز می‌تواند داده‌ی صف ارسال را آزاد کند. این
فضا داخل همان بودجه است، حافظه‌ی ازپیش‌تخصیص‌یافته یا بودجه‌ی اضافه نیست.
ترافیک بازیابی هم محدود است و پس از پرشدن فضای خودش می‌تواند رد شود.

سقف RX wrapper برابر `L` شامل سهم بازیابی هم هست: برای `L > 1`، تعداد
`min(256, max(1, floor(L / 16)))` slot برای بازیابی کنار گذاشته می‌شود و
`L = 1` سهم رزروشده ندارد. پیش‌فرض `262144` یعنی حداکثر `261888` wrapper عادی
و `256` wrapper بازیابی. تعداد و سقف pool در API هر دو دسته را شامل می‌شوند.
CTP نیز داخل سقف ثابت handoff هر instance، یعنی ۱۶ MiB و ۴۰۹۶ تخصیص، سهم
۱ MiB و ۲۵۶ تخصیص برای بازیابی نگه می‌دارد؛ سهم عادی ۱۵ MiB و ۳۸۴۰ تخصیص است.
ورودی بسته و handoff ابتدا پذیرش عادی را امتحان می‌کنند و فقط بسته‌ی واجد
شرایط بازیابی در صورت نیاز به سهم رزروشده می‌رود. SYN، FIN و payload برنامه
همچنان از ظرفیت عادی استفاده می‌کنند.

این بودجه سقف RSS فرایند نیست. صف pending/ACK برنامه، receive staging پس از
پایان مالکیت pbuf، وضعیت line و نود، جدول‌های کنترلی engine و port، bufferهای
مستقل و منابع kernel حافظه‌ی دیگری مصرف می‌کنند. سقف handoff هر CTP برابر
۱۶ MiB و ۴۰۹۶ تخصیص و محدودیت صف هر flow، دریافت خارج از ترتیب و closer در هر
دو bridge مستقل باقی می‌مانند. `tcp-stack-receive-budget` هدف پنجره‌ی دریافت
اعلام‌شده‌ی هر worker است و سقف allocator را افزایش نمی‌دهد. پنجره‌ی ارسال یا
دریافت سقف پروتکل است، نه حافظه‌ی رزروشده برای هر اتصال.

نرسیدن ظرفیت می‌تواند اتصال تازه را نپذیرد، بسته را کنار بگذارد یا write مربوط
به TCP را تا برگشت منابع به تأخیر بیندازد؛ رفتار به مسیر مربوط بستگی دارد.
شکست واقعی تخصیص heap همچنان fatal است. ظرفیت را براساس flow و ترافیک هم‌زمان،
شامل handshake و اتصال‌های در حال بسته‌شدن، تعیین کنید؛ هر کاربر می‌تواند
flowهای زیادی داشته باشد. زنجیره‌ی `TunDevice -> PacketsToConnection` هم از
همین allocator استفاده می‌کند.

هر worker همچنان ۲۵۵ index برای netif دارد که loopback و نودهای متصل در آن
شریک‌اند. تمام‌شدن آن ساخت interface را رد می‌کند. ورودی بسته باید datagram
کامل IPv4 باشد؛ افزایش pool پذیرش fragment یا سیاست reassembly را تغییر نمی‌دهد.

<span id="ظرفیت-پورت-مبدأ"></span>

#### ظرفیت پورت مبدأ {#source-port-capacity}

CTP پیش از اتصال TCP یا UDP، tuple کامل روی شبکه را رزرو می‌کند: پروتکل، آدرس
و پورت مبدأ، آدرس و پورت مقصد. یک پورت مبدأ می‌تواند برای مقصدهای مختلف یا
آدرس‌های مبدأ متفاوت استفاده شود. tuple یکسان در همه‌ی workerها و netifها تا
آزادشدن PCB، شامل TCP `TIME_WAIT`، انحصاری است؛ تغییر worker این حفاظت را
دور نمی‌زند.

برای یک آدرس IPv4 مبدأ، آدرس IPv4 مقصد و پورت مقصد ثابت، انتخاب خودکار تا
۱۶۳۸۳ پورت TCP در `49152..65534` یا ۱۶۳۸۴ پورت UDP در `49152..65535` دارد؛
رزروهای موجود این تعداد را کم می‌کنند. رزروهای unconnected یا wildcard به‌طور
محافظه‌کارانه همان شماره‌ی پورت را از تخصیص scoped خارج می‌کنند. هر نمونه‌ی
CTP هنوز یک `source-ipv4` دارد و pool خودکار آدرس مبدأ اضافه نشده است. مقصدهای
متنوع می‌توانند شماره‌ی پورت مشترک داشته باشند، ولی افزایش PCB یا بودجه‌ی حافظه
سقف پورت برای tuple ثابت را حذف نمی‌کند.

<span id="api-ظرفیت-stack-stats"></span>

### API ظرفیت (`stack-stats`) {#capacity-api-stack-stats}

هر دو bridge عملیات فقط‌خواندنی `stack-stats` را ثبت می‌کنند. به client در
APIServer مجوز دقیق config، node و operation بدهید و از client معمول API با
[قالب‌بندی معمول API](../05-devguides/api/protocol.mdx) برای فرستادن درخواستی مانند نمونه‌ی زیر استفاده کنید:

```json
{
  "id": "capacity-1",
  "auth": {"client": "monitor", "token": "<configured token>"},
  "selector": {"config": "edge", "node": "connection-to-packets"},
  "operation": "stack-stats",
  "content_type": "application/json",
  "body_encoding": "utf8",
  "body": "{}"
}
```

selector و اطلاعات دسترسی را با مقادیر پیکربندی‌شده جایگزین کنید. بدنه باید
یک object خالی JSON با حداکثر ۶۴ بایت، شامل whitespace مجاز JSON، باشد.
فیلد اضافی، داده‌ی انتهایی و NUL پذیرفته نمی‌شود. پاسخ JSON با UTF-8 داخل body
نتیجه‌ی معمول API قرار می‌گیرد و وضعیت کل فرایند را نشان می‌دهد، نه فقط نود یا
worker انتخاب‌شده.

| فیلد پاسخ | معنی |
| --- | --- |
| `scope`، `dynamic` | مقدار `"process"` و قابل‌رشد بودن poolها |
| `memory_budget`، `reserved_bytes`، `peak_reserved_bytes` | سقف تنظیم‌شده، حافظه‌ی محاسبه‌شده‌ی فعلی و بیشینه‌ی آن |
| `recovery_headroom`، `recovery_bytes`، `external_recovery_bytes`، `recovery_refusals` | فضای بازیابی داخل سقف، حافظه‌ی محاسبه‌شده‌ی فعلی آن، زیرمجموعه‌ی external آن و تعداد رد درخواست به علت ظرفیت بایت بازیابی |
| `external_bytes`، `external_refusals` | حافظه‌ی handoff در CTP و ورودی نگه‌داری‌شده با pbuf در PTC و رزروهای ردشده‌ی آن |
| `byte_refusals`، `reclaimed_bytes` | رد درخواست به علت بودجه‌ی بایت و حافظه‌ی بازپس‌گرفته‌شده زیر فشار |
| `limits` | سقف مؤثر TCP/UDP، listener، segment و RX wrapper |
| `pools` | نام و اندازه‌ی هر شیء، سقف، تعداد تخصیص‌یافته/نگه‌داشته‌شده، بیشینه‌ی نگه‌داری، بایت رزروشده و رد درخواست تعداد/بایت در هر pool |
| `ports.tcp`، `ports.udp` | رزروهای فعلی و بیشینه، رد درخواست و رزروهای scoped/unscoped |

مجموع بایت‌ها و شمارنده‌های تجمعی برای حفظ دقت به شکل رشته‌ی دهدهی هستند؛
تعداد اشیا و سقف آن‌ها integer JSON است. `reserved_bytes` حافظه‌ی بازیابی را
هم شامل می‌شود و `external_bytes` شامل `external_recovery_bytes` است؛ این
زیرمجموعه‌ها را دوباره جمع نکنید. `held_includes_worker_caches` برابر
true است: `held` و `peak_held` اشیای آزاد رزروشده در cache worker را هم حساب
می‌کنند و تعداد اتصال زنده نیستند. بخش ظرفیت و پورت هرکدام زیر قفل خود snapshot
محدود می‌گیرند؛ کل پاسخ یک سرشماری اتمیک ترافیک نیست.

خروجی handler حداکثر ۳۲ KiB است و سقف پاسخ، بودجه‌ی حافظه‌ی کاری و deadline
درگاه را رعایت می‌کند. بدنه‌ی نامعتبر، در صورت جا شدن پاسخ خطا در این حدود،
`expected_empty_object` برمی‌گرداند؛ رد پاسخ به علت محدودیت می‌تواند بدنه‌ی خالی
داشته باشد. قبل از تغییر سقف، با شمارنده‌ی رد تعداد در هر pool، رد بودجه‌ی بایت
و رد پورت، منبع محدودکننده را مشخص کنید.

## رفتار پیشرفته {#advanced-behavior}


<span id="مرز-نهاییسازی-checksum"></span>

### مرز نهایی‌سازی checksum {#checksum-finalization-boundary}

در ورودی بستهٔ سمت بازگشت، `ConnectionToPackets` مصرف‌کنندهٔ نهایی درخواست محاسبهٔ مجدد checksum بافر همان بسته است. پیش از هر اعتبارسنجی یا مسیر drop، درخواست را می‌گیرد و پاک می‌کند، بسته را در حافظهٔ پیام قابل تغییر و هم‌تراز قرار می‌دهد، سپس checksumهای پشتیبانی‌شده را پیش از صف‌گذاری بایت‌ها برای lwIP ترمیم می‌کند. بستهٔ malformed، IPv6، در حال توقف یا ردشده نمی‌تواند درخواست خود را به بستهٔ نامرتبط بعدی روی packet line آن worker منتقل کند.

برای TCP یا UDP کامل IPv4، نهایی‌سازی checksum هدر IPv4 و transport را ترمیم می‌کند.

ورودی packet فقط datagram کامل IPv4 می‌پذیرد. MF یا fragment offset غیرصفر پیش از تحویل به stack موجب drop محدود می‌شود؛ DF به‌تنهایی مجاز است. اگر باید datagram تکه‌شده تحویل شود، در ورودی دستگاه یا پیش از این گره reassembly کنید. نخستین drop fragment پشتیبانی‌نشده هشدار ثبت می‌کند؛ موارد بعدی شمارندهٔ instance را افزایش می‌دهند و مجموع هنگام تخریب ثبت می‌شود. رد، منابع ورودی را آزاد می‌کند و packet line و دیگر اتصال‌ها را زنده نگه می‌دارد. ساختار malformed از مسیر validation/drop موجود می‌گذرد.

### Fragmentation {#fragmentation}

دیتاگرام UDP بزرگ‌تر از MTU تنظیم‌شده به جای حذف، به صورت fragmentهای IPv4 صادر می‌شود. کل datagram به lwIP سپرده می‌شود و `ip4_frag()` آن را تقسیم می‌کند؛ پس identification، offsetها و پرچم `MF` متعلق به stack هستند، نه این گره.

بسته‌های بازگشتی باید پیش از callback بستهٔ downstream این گره بازسازی شده باشند. گره fragment را در stack محلی نمی‌پذیرد. fragmentation خروجی UDP همچنان پشتیبانی می‌شود؛ مصرف‌کنندهٔ packet-to-stack متصل مستقیم باید بستهٔ کامل دریافت کند، پس مسیر این خروجی پیش از مصرف‌کننده به reassembly نیاز دارد. `fragment-policy` دستگاه فقط خواندن همان دستگاه را کنترل می‌کند و بسته‌های تولیدشده در جای دیگر زنجیره را بازسازی نمی‌کند.

همهٔ بسته‌های خروجی یک flow، از جمله fragmentها، به همان packet worker فرستاده می‌شوند. MSS ارسال TCP از MTU تنظیم‌شده مشتق می‌شود. fragmentation خروجی و reassembly ورودی مسئولیت‌های جداگانه‌اند.

کپی handoff بسته در هر دو جهت در هر instance سقف مشترک **16 MiB**، شامل metadata پیام و padding صریح alignment، و **4096 تخصیص** دارد. پذیرش پیش از تخصیص یا کپی، هر دو سهم و `lwip-memory-budget` سراسری فرایند را رزرو می‌کند. رد خروجی `ERR_MEM` به lwIP برمی‌گرداند؛ TCP رفتار retry پشته را حفظ و UDP از سیاست خطای ارسال/drop خود پیروی می‌کند. ورودی بازگشتی بیش از بودجه دور ریخته می‌شود تا TCP بتواند دوباره ارسال کند؛ بایت‌های stream برنامه که قبلاً پذیرفته شده‌اند هرگز با این کار دور ریخته نمی‌شوند. dispatch حتی روی همان worker در صف باقی می‌ماند. لغو، flow قدیمی، shutdown و تحویل هر charge را یک بار آزاد می‌کنند؛ custom pbuf تزریق‌شده تا آزادسازی واقعی charge را حفظ می‌کند و از فضای بودجه‌ای استفاده می‌کند که ممکن است بیش از تونل عمر کند. خروجی در یک بافر دارای padding، به اندازهٔ بسته و با padding زنجیرهٔ مالک engine کپی می‌شود و تمام تخصیص آن charge می‌شود. پیام صف‌شده همان بافر را منتقل می‌کند؛ پس از انتقال مالکیت به همسایه، دریافت‌کننده بودجهٔ نگه‌داری خود را اعمال می‌کند. نخستین رد هر جهت هشدار می‌دهد و هنگام تخریب شمارندهٔ تجمعی رد ورودی بازگشتی و خروجی ثبت می‌شود.

<span id="انتخاب-مقصد-و-protocol"></span>

### انتخاب مقصد و پروتکل {#destination-and-protocol-selection}

قاعده دقیقاً با `TcpUdpConnector` یکسان است: protocol مشخص‌شده در destination context
اولویت دارد؛ در غیر این صورت، protocol مشخص‌شده در source context استفاده می‌شود.
اگر protocol موجود نباشد یا مبهم باشد، همان line رد می‌شود.

`target-address` و `port` مستقل از هم مقصد را انتخاب می‌کنند. حذف هر فیلد یا
استفاده از مقدار دقیق `dest_context->...` مربوط به آن، همان بخش از destination context
ورودی را نگه می‌دارد. `source-ipv4` فقط مبدأ مجازی packet‌های خروجی است و مقصد را
تعیین نمی‌کند.

این تنظیمات مقصد یک بار و پیش از هر lookup اختیاری DNS اعمال می‌شوند. اگر resolve
محلی فعال باشد، نام دامنهٔ resolve‌نشدهٔ انتخاب‌شده lookup می‌شود؛ چه از تنظیمات
آمده باشد و چه از مقصد ورودی. node آدرس IPv4 حاصل را بدون اعمال دوبارهٔ تنظیمات
مقصد استفاده می‌کند. پیش از بازشدن flow، مقصد
باید آدرس و پورت غیرصفر داشته باشد. `TcpListener` عادی protocol مبدأ TCP را تأمین
می‌کند؛ در نتیجه برای forwarding به مقصد ثابت نیازی به SOCKS نیست:

```json
{
  "name": "connection-to-packets",
  "type": "ConnectionToPackets",
  "settings": {
    "source-ipv4": "10.90.0.1",
    "target-address": "example.com",
    "port": 443
  },
  "next": "packets-to-connection"
}
```

این تنظیمات node برای مسیر مستقیم بالا مناسب است. اگر مسیر packet به host دیگری
می‌رود، `next` را به ورودی packet transport خود تغییر دهید.

fake DNS وجود ندارد؛ حفظ domain اصلی در
سمت مقابل به پروتکل جداگانه‌ای برای انتقال metadata نیاز دارد.

<span id="composition"></span>

### نکته‌های ترکیب {#composition-notes}

- node قبلی باید layer 4 و node بعدی layer 3 باشد.
- `next` اجباری و مقصد packetهاست.
- حضور این node chain را packet chain می‌کند و packet line هر worker را می‌سازد.

## جزئیات پیاده‌سازی {#implementation-details}


### کنترل جریان {#flow-control}

TCP در هر دو جهت backpressure واقعی اعمال می‌کند:

- دادهٔ برنامه که lwIP هنوز نمی‌پذیرد با سقف `max-pending-bytes` به‌علاوهٔ headroom تحویل در صف می‌ماند و تا تخلیهٔ send window به گره قبلی `Pause` ارسال می‌شود؛
- دادهٔ دریافتی ابتدا downstream تحویل می‌شود؛ اگر گره قبلی به صورت reentrant توقف دهد، receive credit تا Resume به lwIP برنمی‌گردد و پنجرهٔ TCP بسته می‌شود.

سقف کل بایت معلق `P + L` است که در آن `P = max-pending-bytes` و `L` حاشیهٔ ثابت 1 MiB مستقل از اندازهٔ pool، پروفایل RAM و تنظیمات splice است. این سهم محدود ورودی‌ای را پوشش می‌دهد که پیش از اثر کردن Pause تحویل شده، از جمله تحویل 1 MiB با بودجهٔ پیش‌فرض 256 KiB. سقف entry یا زمان ارسال Pause/Resume تغییر نمی‌کند. پذیرش پیش از افزودن به صف بررسی می‌شود؛ ورودی اضافی فقط همان flow را می‌بندد و وارد تخلیهٔ graceful نمی‌شود.

علاوه بر سقف بایت، هر flow TCP حداکثر 1,024 payload در صف نگه می‌دارد. این سقف داخلی ایمنی تخصیص در JSON قابل تنظیم نیست و سربار هر buffer/deque را حتی برای callbackهای یک‌بایتی محدود می‌کند. عبور از آن فقط flow متخلف TCP را reset و می‌بندد. UDP صف stream ندارد و از حساب entry یا فشار تخصیص صف اثر نمی‌گیرد.

backpressure در UDP عمداً با اتلاف است: هنگام Pause گره قبلی، datagram دریافتی به جای صف نامحدود دور ریخته می‌شود.

<span id="lifecycle"></span>

### نکته‌های چرخهٔ عمر {#lifecycle-notes}

- connection line از نوع **borrowed** است. این گره فقط state خود را مقداردهی و تخریب می‌کند و هرگز `lineDestroy()` فراخوانی نمی‌کند؛ listener یا آداپتور سازندهٔ line آن را تخریب می‌کند.
- packet lineهای هر worker متعلق به زنجیره‌اند. هرگز به عنوان flow مقداردهی اولیه نمی‌شوند و در runtime تخریب نمی‌شوند. `Finish` روی packet line نقض قرارداد است و فرایند را abort می‌کند.
- ساخت مرحله‌ای است: آرایهٔ اشاره‌گرهای netif و رجیستری flow هر یک پیش از تلاش برای مرحلهٔ بعد ثبت می‌شوند و هر شکست از مسیر واحد `onDestroy()` پاک‌سازی می‌شود. آن مسیر بر اساس state منتشرشده توسط هر مرحله تصمیم به آزادسازی می‌گیرد، نه صرفاً میزان پیشرفت ساخت. بنابراین پیمایش رجیستری تا زمان وجود آن no-op است. رجیستری مالک `flows_lock` است و قفل کردن قفلی که هرگز ساخته نشده یا rollback خود رجیستری پیش‌تر آن را تخریب کرده، رفتار تعریف‌نشده است، نه خطای قابل بازیابی.
- چون زنجیره ممکن است با آداپتور لایهٔ ۴ شروع شود، سمت packet در `onStart()` با یک task صف‌شده برای هر worker مقداردهی می‌شود، نه با مقداردهی head لایهٔ ۳ توسط مدیر گره.
- flow TCP که به‌نرمی بسته می‌شود یک tombstone در رجیستری باقی می‌گذارد تا FIN/ACK دیررس به worker و netif درست برسد. این مهلت مسیریابی `2 * TCP_MSL` است، نه مدل عمر PCB. closer متعلق به گره از `tcp_shutdown(pcb, 0, 1)` فقط برای TX استفاده می‌کند و PCB را در `FIN_WAIT_1`، `FIN_WAIT_2`، `CLOSING` یا `LAST_ACK` دنبال می‌کند؛ برای flow متصل `tcp_close()` به کار نمی‌برد. وقتی lwIP، PCB را به `TIME_WAIT` می‌برد، closer callbackهای برنامه را جدا و مدخل زندهٔ رجیستری را فوراً بازنشسته می‌کند؛ فقط lwIP مالک PCB در `TIME_WAIT` می‌ماند. tombstone مستقل ممکن است بیش از PCB عمر کند یا پیش از آن منقضی شود؛ هیچ‌یک flow زنده را از دست نمی‌دهد.
- tombstoneها در حلقهٔ بازنشستگی ثابت با `4096` مدخل نگه‌داری می‌شوند، نه با timer جداگانهٔ worker برای هر یک؛ timer برای هر بستن باعث رشد صف timer و هزینهٔ shutdown با churn اتصال می‌شد. حلقه این سقف را قطعی می‌کند: ممکن است در یک مهلت بیش از تعداد قابل حذف با پیمایش مبتنی بر سن، flow بسته شود؛ پس پس از سقف، قدیمی‌ترین tombstone جای خود را واگذار می‌کند. انقضا هنگام lookup نیز رعایت می‌شود تا گرهی که ساکت شده و چیزی ثبت یا بازنشسته نمی‌کند نتواند برای tuple با مهلت منقضی پاسخ دهد.
- ثبت جدید روی tombstone آن را جایگزین می‌کند. lwIP همان پورت محلی را پیش‌تر انتخاب کرده است؛ رد ثبت، ابهام پذیرفته‌شدهٔ بستهٔ دیررس را به شکست قابل مشاهدهٔ اتصال تبدیل می‌کرد.
- `Finish` محلی یا half-close سالم سمت مقابل ابتدا بایت‌های TCP پذیرفته‌شده را تخلیه می‌کند. سپس PCB به closer متعلق به گره می‌رود؛ flow *متصل* حتی با صف خالی نیز همین مسیر را طی می‌کند، زیرا بایت‌های داخل lwIP ممکن است تأیید نشده باشند، همتا ممکن است همچنان بدون کسی برای بازگرداندن اعتبار دریافت ارسال کند و ACKهایش باید به همین worker مسیریابی شوند. در این انتقال، اعتبار همهٔ بایت‌های قبلاً کپی‌شده از lwIP که هنوز به `tcp_recved()` داده نشده‌اند، پیش از پاک‌شدن اشاره‌گر PCB در line بازگردانده می‌شود. این شامل taskهای مالک که هنوز در صف هستند و زیرمجموعهٔ pauseشده است؛ closer پنجرهٔ دریافت کاملاً باز را تحویل می‌گیرد و اعتبار هر بایت پذیرفته‌شده دقیقاً یک بار بازگردانده می‌شود.
- closer تا دریافت همهٔ بایت‌های پذیرفته‌شده توسط همتا می‌نویسد، سپس shutdown فقط TX را درخواست می‌کند. tuple در وضعیت *draining*، نه فعال و نه tombstone، ثبت می‌ماند تا هنگام مالکیت PCB توسط این گره قابل بیرون‌راندن نباشد. مهلت `30` ثانیه هم تحویل بایت صف‌شده و هم FIN پذیرفته‌شده توسط lwIP که هنوز تخصیص نیافته را پوشش می‌دهد. در حالت دوم، `tcp_shutdown()` با `TF_CLOSEPEND` موفق برمی‌گردد؛ closer callbackها، مالکیت رجیستری و مهلت را حفظ و EOF همتا را بدون بازنشستگی ثبت می‌کند. گذار واقعی به `FIN_WAIT_1`، `FIN_WAIT_2`، `CLOSING` یا `LAST_ACK` با `TF_CLOSEPEND` پاک یعنی FIN صف شده است؛ این وضعیت پیش از اعمال مهلت FIN معلق بررسی می‌شود، پس گذار در همان تیک در برابری مهلت اولویت دارد. `TIME_WAIT` پایان graceful است و closer بدون abort PCB بازنشسته می‌شود. مهلت جداگانهٔ `60` ثانیه برای بسته‌شدن همتا حالت‌های فعال بستن را پوشش می‌دهد. closerها به بودجهٔ مشترک `16 MiB` و شمار `4096` object نیز محدودند؛ عبور از هر سقف PCB را دقیقاً یک بار abort می‌کند، به جای گزارش EOF سالم اما ناقص یا رها کردن PCB بدون پیگیری.
- FIN با shutdown فقط TX فرستاده می‌شود، هرگز با `tcp_close()`. اجرای `tcp_close()` در `ESTABLISHED` یا `CLOSE_WAIT` با اعتبار دریافت باقی‌مانده، PCB را reset و آزاد می‌کند. این گره اعتبار را از task worker مالک برمی‌گرداند و هنگام Pause تونل قبلی آن را کامل نگه می‌دارد؛ پس این وضعیت معمول است. reset همهٔ بایت‌های خروجی تأییدنشده را نیز از بین می‌برد و closer دقیقاً برای جلوگیری از آن است. فقط flow که هرگز متصل نشده همچنان بسته می‌شود، جایی که این قاعده قابل اعمال نیست.
- write ردشده با `ERR_MEM` از callback `tcp_poll` دوباره امتحان می‌شود؛ callback دقیقاً تا زمان blocked بودن write نصب است. `tcp_sent` به‌تنهایی کافی نبود: شکست نخستین write روی PCB بیکار هیچ بایت تأییدنشده‌ای باقی نمی‌گذارد، پس ACKی نمی‌رسد و line پس از رفع فشار همچنان pause می‌ماند. سایر خطاهای write نهایی‌اند و flow را یک بار می‌بندند، نه اینکه برای همیشه تکرار شوند.
- deadline مربوط به active-open یک timer قابل لغو برای هر line است که event worker مالک آن است و دقیقاً یک reference line نگه می‌دارد. اتصال موفق آن را فوراً لغو می‌کند؛ task تأخیری fire-and-forget، پیام و تخصیص line را برای کل مهلت تنظیم‌شده، تا حدود 49.7 روز قابل نمایش با شمار میلی‌ثانیهٔ `uint32_t`، زنده نگه می‌داشت.
- شمارندهٔ generation مانع تزریق packet *صف‌شده*ٔ flow قدیمی به flow جدیدی می‌شود که tuple را میان lookup و تحویل دوباره استفاده کرده است. پیش از تزریق، همان generation روی engine مالک اولیه همراه هویت دقیق netif دوباره اعتبارسنجی می‌شود. این سازوکار packet شبکه‌ای را که پس از بازنشستگی و استفادهٔ دوبارهٔ tuple می‌رسد تشخیص نمی‌دهد، زیرا IP generation حمل نمی‌کند. tombstone این بازه را کاهش می‌دهد ولی حذف نمی‌کند.
- `onQuiesceRequest()` وضعیت stopping را منتشر، پذیرش جدید را از gateهای سمت قبل، سمت بعد و طبقه‌بندی/انتشار packet می‌بندد و بدون انتظار درخواست جداکردن callback می‌دهد. `onQuiesceWait()` بازگشت callbackهای قبلاً پذیرفته‌شده را اثبات می‌کند. `onWorkerStop()` در engine همان worker، callbackهای PCB، ثبت flow، deadline، drain و netif را جدا می‌کند. پاک‌سازی نهایی TCP، PCBها را abort می‌کند تا از رابط حذف‌شده بیشتر عمر نکنند. اشاره‌گرهای stack پیش از آزادسازی پاک می‌شوند. state، بافرهای معلق و referenceهای line قرضی تا Finish منبع واقعی باقی می‌مانند، حتی اگر CTP پیش از منبع drain شود. `onStop()` اصلی barrierهای تکمیل‌شدهٔ مالک را بررسی و رجیستری‌های مشترک را آزاد می‌کند و هرگز PCB خارجی را پیمایش نمی‌کند. انتشار `stopping` به‌تنهایی PCB را جدا نمی‌کند؛ close پاک‌سازی واقعی idempotent سمت مالک را انجام می‌دهد. هر task صف‌شده وارد gate مربوط می‌شود، پس task ردشده داده و رویداد چرخهٔ عمر به هر همسایه را سرکوب می‌کند، در حالی که مسیرهای close زنده می‌مانند تا مالکان بتوانند lineهای قرضی را آزاد کنند.
- ساخت، آرایهٔ netif برای هر worker، ظرفیت اولیهٔ نقشهٔ flow و حلقهٔ ثابت tombstone را پیش از اجرای هر callback flow برقرار می‌کند. شکست تخصیص heap fatal است؛ سایر خطاهای سازنده منابع مقداردهی‌شده را آزاد می‌کنند.
- lwIP دادهٔ دریافت ردشده را از timer حلقهٔ مالک بازپخش می‌کند. تحویل قرارداد موجود pbuf/credit و callback صف‌شده، از جمله بازپخش داده همراه FIN را حفظ می‌کند. رد enqueue کنترل ضروری ابتدا callbackها و route دقیق PCB را در engine مالک جدا می‌کند و line قرضی را در رجیستری نهایی ازپیش‌تخصیص‌یافتهٔ worker مالک منتشر می‌کند. درخواست خاموشی منظم فرایند تشدید بعد از این انتقال مسئولیت است؛ پاک‌سازی به صف ردشده یا یافتن مجدد flow در Stop وابسته نیست.
- lineهای قرضی بعداً توسط مالکان واقعی خود Finish و تخریب می‌شوند.

### منابع engine و چرخهٔ عمر {#engine-resources-and-lifecycle}

runtime برای هر event worker معمولی حداکثر یک engine خام lwIP را هنگام نخستین
استفاده می‌سازد. همهٔ bridge‌های همان worker از آن استفاده می‌کنند؛ thread جداگانهٔ
stack و core mutex وجود ندارد. PTC مالک flow را از tuple فعلی بسته انتخاب می‌کند و CTP مالک
normal line برنامه را حفظ می‌کند. پاسخ CTP پس از lookup کامل tuple/WID/generation
در صف worker مالک قرار می‌گیرد و engine و netif دقیق دوباره بررسی می‌شوند.
callback همسایه همیشه deferred اجرا می‌شود، حتی روی همان worker.

poolهای قابل‌رشد flow/payload از سقف‌های سراسری بالا استفاده می‌کنند. هر engine
فعال حافظه‌ی کنترلی مستقل و ۱۷ رکورد timeout دارد؛ worker استفاده‌نشده engine ندارد.
رزرو پورت اتصال CTP براساس tuple کامل است و تا آزادشدن PCB، شامل TIME_WAIT،
باقی می‌ماند؛ رزرو unconnected همچنان همان شماره‌ی پورت را محافظه‌کارانه کنار می‌گذارد. ID‌های تولیدی fragment در IPv4 و IPv6 هرکدام sequence مشترک جداگانه‌ای دارند
و با همان عرض محدود قبلی wrap می‌شوند. drain list محلی هر worker است، ولی
سقف هر node همچنان ۴۰۹۶ object و ۱۶ MiB است. lock مربوط به pool/quota هنگام پیمایش stack یا تولید خروجی
آن نگه داشته نمی‌شود.

در quiesce، timer مربوط به engine پیش از توقف پذیرش کار عادی جدا می‌شود. node در drain همان
owner ریشه‌های stack خود را آزاد می‌کند. runtime پس از تسویهٔ messageهای detached
و پیش از نابودی loop و pool‌ها engine را آزاد می‌کند. pool‌ها و port accountهای مشترک
و secret مربوط به ISN در سطح process فقط پس از خروج همهٔ worker‌ها نهایی می‌شوند.
