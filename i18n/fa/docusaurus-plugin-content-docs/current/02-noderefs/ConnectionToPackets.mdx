# ConnectionToPackets

`ConnectionToPackets` کار معکوس `PacketsToConnection` را با active-open انجام می‌دهد.
یک connection line عادی WaterWall را می‌گیرد، flow متناظر TCP یا UDP را در stack
lwIP داخل همان process باز می‌کند و packet‌های خام IPv4 را به سمت packet در chain
می‌فرستد. packet‌های برگشتی دوباره به همان flow تزریق می‌شوند و دادهٔ آن‌ها به‌شکل
payload در جهت downstream روی connection line اصلی برمی‌گردد.

```text
normal connection -> ConnectionToPackets -> raw IPv4 TCP/UDP packets
return IPv4 packets -> ConnectionToPackets -> original connection downstream
```

این node یک userspace transport bridge است، نه TUN شفاف سیستم‌عامل. به kernel TUN،
raw socket یا دسترسی root نیاز ندارد. برنامه باید از adapter‌ای مثل
`TcpListener`، ‏`UdpListener`، ‏`TcpUdpListener` یا `Socks5Server` وارد WaterWall
شود؛ capture کردن socket‌های نامرتبط kernel بیرون از scope آن است.

`mtu` یک بار هنگام ساخت تعیین و اعتبارسنجی می‌شود. هر نمونه MTU مستقل
خود را نگه می‌دارد؛ تنظیم node‌های دیگر آن را تغییر نمی‌دهد. اگر مقدار به‌ارث‌رسیده از
`misc.mtu` در core نامعتبر باشد، باید برای همان node یک مقدار معتبر تعیین کنید.

## توپولوژی‌های معمول

برای مقصد ثابت، `target-address` و `port` را در `ConnectionToPackets` تنظیم کنید:

```text
TcpListener -> ConnectionToPackets -> packet transport
```

یک مسیر کامل و مستقیم بدون نیاز به root یا transport مجزا:

```text
TcpListener -> ConnectionToPackets -> PacketsToConnection -> TcpUdpConnector -> destination
```

برای مقصد متفاوت در هر connection، node قبلی می‌تواند destination context را تعیین کند:

```text
TcpListener -> Socks5Server -> ConnectionToPackets
            -> PacketsToConnection -> TcpUdpConnector -> destination
```

یا روی WireGuard:

```text
شاخه‌ی application محلی: TcpListener -> Socks5Server -> ConnectionToPackets -> Bridge A
شاخه‌ی UDP محلی:         UdpStatelessSocket -> WireGuardDevice -> Bridge B
سمت راه‌دور:              UdpStatelessSocket -> WireGuardDevice -> PacketsToConnection
                          -> TcpUdpConnector -> destination
```

`Bridge A` و `Bridge B` را pair کنید تا شاخهٔ تبدیل connection به packet، به سمت
packet در WireGuard وصل شود. `UdpStatelessSocket` فقط در ابتدای chain مجاز است؛ پس
باید در ابتدای شاخه‌ی خودش بماند و پس از `WireGuardDevice` قرار نگیرد.

آدرس مجازی `source-ipv4` باید در توپولوژی packet مسیر برگشت داشته باشد. در WireGuard،
سمت محلی معمولاً peer را با route مقصد `0.0.0.0/0` انتخاب می‌کند. peer سمت مقابل
هم باید این آدرس مجازی مبدأ را، معمولاً به‌صورت `/32`، مجاز بداند.

این نمودارها توپولوژی را نشان می‌دهند، نه config کامل nodeها. در ورودی SOCKS،
`Socks5Server` را برای TCP CONNECT تنظیم و حالت احراز هویت آن را انتخاب کنید.
برای اجرا بدون root از پورت بالای listener استفاده کنید. دو شاخهٔ محلی باید
[Bridgeهای جفت و متقابل](./Bridge.mdx) داشته باشند؛ برای تنظیم UDP و کلیدها از
[جفت WireGuard](./WireGuardDevice.mdx#example-pair) کمک بگیرید. WireGuard از مقصد
داخلی برای انتخاب peer استفاده می‌کند و peer راه‌دور باید source مجازی client
را مجاز بداند. در سمت مقابل
[TcpUdpConnector باید مقصد را حفظ کند](./PacketsToConnection.mdx#typical-placement)،
مگر آنکه backend ثابت می‌خواهید. این توپولوژی socket-to-socket به TUN، forwarding
IP میزبان یا NAT نیاز ندارد.

## Scope

پشتیبانی می‌شود:

- TCP روی IPv4؛
- UDP روی IPv4، از جمله datagram بزرگ‌تر از یک MTU؛
- مقصد IP و مقصد domain از طریق `DomainResolver` داخلی؛
- چند event worker.

رد یا drop می‌شود:

- IPv6، به‌صورت دائمی و عامدانه؛
- ICMP و protocol‌های غیر TCP/UDP؛
- UDP payload بالاتر از `65507` بایت؛
- packet برگشتی بدون flow ثبت‌شده.

تحویل ICMP error و حفظ source port اصلی application فعلاً پیاده‌سازی نشده‌اند.
این node فقط IPv4 تولید می‌کند. `domain-strategy` فقط `only-ipv4` را می‌پذیرد؛ اگر
domain فقط رکورد AAAA داشته باشد، DNS با پیامی شامل نام domain شکست می‌خورد.
آدرس IPv6 صریح در `target-address` باعث رد config می‌شود؛ مقصد IPv6 در context
نیز با بستن همان line رد می‌شود. این
تصمیم، IPv6 سراسری lwIP را برای node‌های دیگر غیرفعال نمی‌کند.

## مرز نهایی‌سازی Checksum

در ورودی مسیر برگشت، این node آخرین مصرف‌کنندهٔ درخواست محاسبهٔ مجدد checksum روی
buffer همان packet است. node پیش از هر
اعتبارسنجی یا drop، درخواست را می‌گیرد و پاک می‌کند. سپس packet را در حافظهٔ قابل
تغییر با alignment مناسب قرار می‌دهد و checksum‌های پشتیبانی‌شده را پیش از تحویل
به lwIP و پیش از صف‌گذاری اصلاح می‌کند؛ پیام بایتی صف دیگر به flag جداگانه نیاز
ندارد. malformed بودن packet، دریافت IPv6، توقف node یا رد ورودی درخواست buffer
دیگری را تغییر نمی‌دهد. برای TCP/UDP بدون fragmentation، header IPv4 و
transport checksum اصلاح می‌شوند؛ برای fragment فقط checksum header IPv4 قابل
محاسبه است و transport checksum ساختگی تولید نمی‌شود.

## Fragmentation

ورودی packet باید datagram کامل IPv4 باشد. packet دارای MF یا fragment offset
غیرصفر پیش از تحویل به lwIP حذف می‌شود؛ DF به‌تنهایی مجاز است. این رد ورودی
buffer و منابع موقت را آزاد می‌کند و packet line و اتصال‌های دیگر زنده می‌مانند.
اولین drop هشدار می‌دهد و تعداد کل dropها هنگام تخریب node گزارش می‌شود.
برای تحویل datagram تکه‌شده، پیش از این node reassembly انجام دهید.
ساختار malformed همچنان از مسیر validation/drop معمول می‌گذرد.

این الزام برای ورودی downstream است. خروجی UDP بزرگ‌تر از MTU همچنان به‌وسیلهٔ
lwIP fragment می‌شود و MSS ارسال TCP از MTU به دست می‌آید. همهٔ fragment‌های
خروجی یک flow به همان worker می‌روند. اگر مصرف‌کنندهٔ خروجی، stack دیگری است،
باید پیش از تحویل به آن reassembly انجام شود. policy دستگاه فقط خواندن از همان
دستگاه را کنترل می‌کند و packet‌های خروجی node دیگر را بازسازی نمی‌کند.

کپی‌های handoff در هر دو جهت، برای هر instance مجموعاً به ۱۶ MiB و ۴۰۹۶ allocation محدودند؛ metadata و padding نیز محاسبه می‌شوند. سهم پیش از allocation رزرو و هنگام آزادسازی واقعی، حتی برای custom pbuf، آزاد می‌شود. اشباع خروجی `ERR_MEM` برمی‌گرداند و ورودی اضافه drop می‌شود. اولین refusal هشدار و مجموع هر جهت هنگام تخریب گزارش می‌شود.

## تنظیمات

| تنظیم | اجباری | پیش‌فرض | معنی |
| --- | --- | --- | --- |
| `source-ipv4` | بله | ندارد | source IPv4 مجازی netif/PCB‌ها؛ نباید wildcard، loopback، multicast یا broadcast باشد. |
| `target-address` | خیر | `dest_context->address` | آدرس IPv4 یا domain مقصد؛ رشتهٔ دقیق `dest_context->address` آدرس مقصد ورودی را نگه می‌دارد. آدرس تنظیم‌شده فقط بخش آدرس را جایگزین می‌کند. IPv6 صریح پذیرفته نمی‌شود. |
| `port` | خیر | `dest_context->port` | عدد صحیح پورت مقصد در بازهٔ `1..65535`، یا رشتهٔ دقیق `dest_context->port` برای نگه‌داشتن پورت مقصد ورودی. |
| `mtu` | خیر | `misc.mtu` سراسری | بازهٔ `576..9000`؛ MSS از آن مشتق و UDP بالاتر از آن fragment می‌شود. |
| `domain-strategy` | خیر | `only-ipv4` | تنها مقدار پذیرفته‌شده `only-ipv4` است. |
| `tcp-connect-timeout-ms` | خیر | `30000` | deadline اتصال TCP active-open. |
| `max-pending-bytes` | خیر | `262144` | سقف دادهٔ application پیش از connect یا هنگام پُربودن send window؛ بازهٔ `1024..67108864`. |

مقدار پیش‌فرض فقط وقتی استفاده می‌شود که فیلد نوشته نشده باشد. نوع اشتباه، عدد
کسری یا مقدار خارج از بازه باعث رد config با ذکر نام فیلد می‌شود. MTU مربوط به
core پیش از تبدیل به نوع عددی کوچک‌تر، در بازهٔ `68..65535` اعتبارسنجی می‌شود.
اگر مقدار به‌ارث‌رسیده خارج از بازهٔ مجاز خود node باشد، config باز هم رد می‌شود.

```json
{
  "name": "connection-to-packets",
  "type": "ConnectionToPackets",
  "settings": {
    "source-ipv4": "10.90.0.1",
    "mtu": 1420,
    "domain-strategy": "only-ipv4",
    "tcp-connect-timeout-ms": 30000,
    "max-pending-bytes": 262144
  },
  "next": "packet-bridge"
}
```

این قطعهٔ node برای شاخهٔ application روی WireGuard در بالاست.
`packet-bridge` نام node مربوط به `Bridge A` است؛ جفت متقابل و شاخهٔ جداگانهٔ
UDP/WireGuard را مطابق بخش توپولوژی تنظیم کنید.

## انتخاب مقصد و Protocol

قاعده دقیقاً با `TcpUdpConnector` یکسان است: protocol مشخص‌شده در destination context
اولویت دارد؛ در غیر این صورت، protocol مشخص‌شده در source context استفاده می‌شود.
اگر protocol موجود نباشد یا مبهم باشد، همان line رد می‌شود.

`target-address` و `port` مستقل از هم مقصد را انتخاب می‌کنند. حذف هر فیلد یا
استفاده از مقدار دقیق `dest_context->...` مربوط به آن، همان بخش از destination context
ورودی را نگه می‌دارد. `source-ipv4` فقط مبدأ مجازی packet‌های خروجی است و مقصد را
تعیین نمی‌کند.

تنظیمات یک بار در prepare hook متعلق به node و پیش از DNS در `DomainResolver` داخلی
اعمال می‌شوند. domain تنظیم‌شده مانند domain ورودی resolve می‌شود و node آدرس
resolve‌شده را بدون اعمال دوبارهٔ تنظیمات مصرف می‌کند. پیش از بازشدن flow، مقصد
باید آدرس و پورت غیرصفر داشته باشد. `TcpListener` عادی protocol مبدأ TCP را تأمین
می‌کند؛ در نتیجه برای forwarding به مقصد ثابت نیازی به SOCKS نیست:

```json
{
  "name": "connection-to-packets",
  "type": "ConnectionToPackets",
  "settings": {
    "source-ipv4": "10.90.0.1",
    "target-address": "example.com",
    "port": 443
  },
  "next": "packets-to-connection"
}
```

این تنظیمات node برای مسیر مستقیم بالا مناسب است. اگر مسیر packet به host دیگری
می‌رود، `next` را به ورودی packet transport خود تغییر دهید.

fake DNS وجود ندارد؛ حفظ domain اصلی در
سمت مقابل به پروتکل جداگانه‌ای برای انتقال metadata نیاز دارد.

## Flow Control

TCP در هر دو جهت backpressure واقعی دارد. داده‌ای که lwIP هنوز نمی‌تواند بپذیرد،
با بودجهٔ `max-pending-bytes` و حاشیهٔ ورودی توضیح‌داده‌شده در ادامه، در صف می‌ماند
و سمت قبلی Pause می‌شود. دادهٔ دریافتی ابتدا downstream تحویل داده می‌شود؛ اگر
در همان callback یک Pause به‌صورت re-entrant برسد، receive credit به lwIP برنمی‌گردد
و receive window بسته می‌شود. هر flow علاوه بر سقف بایت‌ها، حداکثر `1024` ورودی
در صف نگه می‌دارد؛ عبور از این سقف فقط همان flow را reset و بسته می‌کند. UDP صف
stream ندارد و هنگام Pause، datagram‌ها را drop می‌کند.

## Lifecycle

- connection line از نوع **borrowed** است؛ node فقط state خودش را آزاد می‌کند و
  هرگز `lineDestroy()` را فراخوانی نمی‌کند. packet line‌های هر worker متعلق به chain
  هستند و در طول runtime زنده می‌مانند. دریافت `Finish` روی آن‌ها نقض قرارداد است
  و باعث abort شدن process می‌شود.
- پیش از callback نخست، آرایهٔ netif هر worker، ظرفیت اولیهٔ رجیستری flow و
  tombstone ring ساخته می‌شوند. اتمام حافظهٔ heap خطای fatal است؛ سایر خطاهای
  سازنده منابع آماده‌شده را آزاد می‌کنند. رجیستری fragment ورودی وجود ندارد.
- چون chain ممکن است با L4 آغاز شود، packet side در `onStart()` با task جدا برای هر
  worker مقداردهی اولیه می‌شود.
- بسته‌شدن graceful اتصال TCP، یک tombstone برای مسیریابی به مدت `2 * TCP_MSL`
  در ring ثابتی با `4096` ورودی نگه می‌دارد. ثبت مجدد همان tuple، tombstone را
  جایگزین می‌کند.
- flow متصل، حتی با صف خالی، به closer متعلق به node منتقل می‌شود. حساب بایت‌های
  پذیرفته‌شده و receive credit دقیقاً یک بار تسویه می‌شود. closer ابتدا همهٔ بایت‌ها
  را می‌نویسد و سپس با `tcp_shutdown(pcb, 0, 1)` فقط TX را می‌بندد. از `tcp_close()`
  استفاده نمی‌شود، چون با وجود receive credit تسویه‌نشده ممکن است RST بفرستد و
  باعث از دست رفتن داده شود.
- deadline تحویل داده/FIN برابر `30` ثانیه و deadline بسته‌شدن peer برابر `60`
  ثانیه است. closer‌ها در مجموع به `4096` object و `16 MiB` از دنبالهٔ کپی‌شدهٔ
  داده محدودند. عبور از هر سقف، PCB را دقیقاً یک بار abort می‌کند. رسیدن به
  `TIME_WAIT` پایان graceful است و مالکیت PCB با lwIP می‌ماند.
- خطای `ERR_MEM` در write فقط تا وقتی نوشتن blocked است، از طریق `tcp_poll`
  دوباره امتحان می‌شود؛ خطاهای دیگر flow را می‌بندند. deadline اتصال یک timer
  قابل لغو روی worker مالک است که دقیقاً یک reference به line نگه می‌دارد.
- generation مانع تزریق packet صف‌شدهٔ flow قدیمی به flow جدیدی با همان tuple
  می‌شود. با این حال، packet دیررس شبکه generation ندارد؛ tombstone فقط بازه‌ای
  را که ممکن است چنین ابهامی رخ دهد کوتاه‌تر می‌کند.
- `onQuiesceRequest()` وضعیت stopping را منتشر می‌کند و پذیرش جدید را از طریق
  gate‌های prev/next و classification/publication بدون انتظار می‌بندد. سپس
  `onQuiesceWait()` بازگشت همهٔ callback‌های admitted را تضمین می‌کند. در lifecycle-v2،
  message‌های emit، inject و packet-`Init` اولیه پیش از توقف و
  آزادشدن component به پایان می‌رسند؛ بنابراین می‌توانند pointer تونل را مستقیم
  حمل کنند. message لغوشده فقط منابع خودش را آزاد می‌کند. `onWorkerStop()` روی
  worker مالک، همهٔ PCB‌ها، flow‌ها، deadline‌ها، drain‌ها و netif‌های محلی را detach
  می‌کند و PCB‌ها را abort می‌کند. state و buffer و reference مربوط به borrowed line تا Finish
  از source واقعی باقی می‌مانند، حتی اگر CTP زودتر drain شود. `onStop()` فقط پس از
  barrier همهٔ worker‌ها رجیستری مشترک را آزاد می‌کند و PCB خارجی را پیمایش نمی‌کند.
- داده‌ای که قبلاً پذیرفته نشده، از timer روی event loop همان worker مالک دوباره
  تحویل داده می‌شود؛ callback تحویل همچنان در صف قرار می‌گیرد. اگر صف، یک کار
  کنترلی ضروری را نپذیرد، ابتدا callback و route مربوط به PCB جدا می‌شوند و line
  از نوع borrowed در terminal registry ازپیش‌تخصیص‌یافته ثبت می‌شود. درخواست
  shutdown منظم برنامه، اقدام بعدی پس از این تحویل مسئولیت است. مالک واقعی
  line در پایان آن را آزاد می‌کند.

## ظرفیت

همه‌ی نمونه‌های `ConnectionToPackets` و `PacketsToConnection` در یک فرایند از
allocator قابل‌رشد lwIP و سقف‌های مشترک استفاده می‌کنند. این فیلدها را زیر
`misc` در `core.json` تنظیم کنید، نه در `settings` نود:

| تنظیم هسته | پیش‌فرض استاندارد | منبع |
| --- | ---: | --- |
| `lwip-memory-budget` | `536870912` (512 MiB) | حافظه‌ی pool و حافظه‌ی نگه‌داری‌شده‌ی محاسبه‌شده برای stack |
| `lwip-max-tcp-flows` | `65536` | وضعیت اتصال TCP، شامل handshake و اتصال‌های در حال بسته‌شدن |
| `lwip-max-udp-flows` | `65536` | وضعیت اتصال UDP |
| `lwip-max-tcp-listeners` | `1024` | اشیای listener در TCP |
| `lwip-max-tcp-segments` | `1048576` | segmentهای ارسال، ارسال مجدد و دریافت TCP |
| `lwip-max-rx-wrappers` | `262144` | wrapperهای PTC برای نگه‌داری بسته‌ی ورودی |

سقف تعداد، عدد صحیح در بازه‌ی `1..4294967295` را می‌پذیرد. بودجه‌ی بایت از
`1048576` تا مقدار کوچک‌تر از `SIZE_MAX` پلتفرم و `9223372036854775807` است.
مقدار نامعتبر راه‌اندازی را متوقف می‌کند و تغییر تنظیم به restart نیاز دارد.
build سفارشی می‌تواند پیش‌فرض TCP، UDP و listener را تغییر دهد؛ مقدار صریح در
تنظیمات هسته اولویت دارد. افزایش `workers` این سقف‌ها را ضرب نمی‌کند و
`ram-profile` آن‌ها را تغییر نمی‌دهد.

حافظه با تقاضا و در چارچوب سقف بایت و تعداد رشد می‌کند. بودجه، slabهای pool،
header و alignment، اشیای آزاد رزروشده در cache worker، حافظه‌ی handoff بسته‌ی
CTP در هر دو جهت و buffer ورودی PTC تا زمانی که custom pbuf آن را نگه می‌دارد
شامل می‌شود. cache آزاد تا هنگام بازپس‌گیری در بودجه حساب می‌شود. همه‌ی flowهای
مجاز یا کل بودجه‌ی بایت از ابتدا تخصیص داده نمی‌شوند.

در بودجه‌ی بایت `B`، allocator مقدار `R = min(1048576, floor(B / 16))` بایت
را برای ترافیک بازیابی کنار می‌گذارد. داده‌ی عادی و cache آن حداکثر `B - R`
مصرف می‌کنند؛ فقط ACK/RST معتبر و واجد شرایط TCP بدون payload و خروجی
ACK/RST/keepalive در TCP از مسیر مستقل بازیابی استفاده می‌کنند. به این ترتیب وقتی ظرفیت
عادی پر است، acknowledgement هنوز می‌تواند داده‌ی صف ارسال را آزاد کند. این
فضا داخل همان بودجه است، حافظه‌ی ازپیش‌تخصیص‌یافته یا بودجه‌ی اضافه نیست.
ترافیک بازیابی هم محدود است و پس از پرشدن فضای خودش می‌تواند رد شود.

سقف RX wrapper برابر `L` شامل سهم بازیابی هم هست: برای `L > 1`، تعداد
`min(256, max(1, floor(L / 16)))` slot برای بازیابی کنار گذاشته می‌شود و
`L = 1` سهم رزروشده ندارد. پیش‌فرض `262144` یعنی حداکثر `261888` wrapper عادی
و `256` wrapper بازیابی. تعداد و سقف pool در API هر دو دسته را شامل می‌شوند.
CTP نیز داخل سقف ثابت handoff هر instance، یعنی ۱۶ MiB و ۴۰۹۶ تخصیص، سهم
۱ MiB و ۲۵۶ تخصیص برای بازیابی نگه می‌دارد؛ سهم عادی ۱۵ MiB و ۳۸۴۰ تخصیص است.
ورودی بسته و handoff ابتدا پذیرش عادی را امتحان می‌کنند و فقط بسته‌ی واجد
شرایط بازیابی در صورت نیاز به سهم رزروشده می‌رود. SYN، FIN و payload برنامه
همچنان از ظرفیت عادی استفاده می‌کنند.

این بودجه سقف RSS فرایند نیست. صف pending/ACK برنامه، receive staging پس از
پایان مالکیت pbuf، وضعیت line و نود، جدول‌های کنترلی engine و port، bufferهای
مستقل و منابع kernel حافظه‌ی دیگری مصرف می‌کنند. سقف handoff هر CTP برابر
۱۶ MiB و ۴۰۹۶ تخصیص و محدودیت صف هر flow، دریافت خارج از ترتیب و closer در هر
دو bridge مستقل باقی می‌مانند. `tcp-stack-receive-budget` هدف پنجره‌ی دریافت
اعلام‌شده‌ی هر worker است و سقف allocator را افزایش نمی‌دهد. پنجره‌ی ارسال یا
دریافت سقف پروتکل است، نه حافظه‌ی رزروشده برای هر اتصال.

نرسیدن ظرفیت می‌تواند اتصال تازه را نپذیرد، بسته را کنار بگذارد یا write مربوط
به TCP را تا برگشت منابع به تأخیر بیندازد؛ رفتار به مسیر مربوط بستگی دارد.
شکست واقعی تخصیص heap همچنان fatal است. ظرفیت را براساس flow و ترافیک هم‌زمان،
شامل handshake و اتصال‌های در حال بسته‌شدن، تعیین کنید؛ هر کاربر می‌تواند
flowهای زیادی داشته باشد. زنجیره‌ی `TunDevice -> PacketsToConnection` هم از
همین allocator استفاده می‌کند.

هر worker همچنان ۲۵۵ index برای netif دارد که loopback و نودهای متصل در آن
شریک‌اند. تمام‌شدن آن ساخت interface را رد می‌کند. ورودی بسته باید datagram
کامل IPv4 باشد؛ افزایش pool پذیرش fragment یا سیاست reassembly را تغییر نمی‌دهد.

### ظرفیت پورت مبدأ

CTP پیش از اتصال TCP یا UDP، tuple کامل روی شبکه را رزرو می‌کند: پروتکل، آدرس
و پورت مبدأ، آدرس و پورت مقصد. یک پورت مبدأ می‌تواند برای مقصدهای مختلف یا
آدرس‌های مبدأ متفاوت استفاده شود. tuple یکسان در همه‌ی workerها و netifها تا
آزادشدن PCB، شامل TCP `TIME_WAIT`، انحصاری است؛ تغییر worker این حفاظت را
دور نمی‌زند.

برای یک آدرس IPv4 مبدأ، آدرس IPv4 مقصد و پورت مقصد ثابت، انتخاب خودکار تا
۱۶۳۸۳ پورت TCP در `49152..65534` یا ۱۶۳۸۴ پورت UDP در `49152..65535` دارد؛
رزروهای موجود این تعداد را کم می‌کنند. رزروهای unconnected یا wildcard به‌طور
محافظه‌کارانه همان شماره‌ی پورت را از تخصیص scoped خارج می‌کنند. هر نمونه‌ی
CTP هنوز یک `source-ipv4` دارد و pool خودکار آدرس مبدأ اضافه نشده است. مقصدهای
متنوع می‌توانند شماره‌ی پورت مشترک داشته باشند، ولی افزایش PCB یا بودجه‌ی حافظه
سقف پورت برای tuple ثابت را حذف نمی‌کند.

## API ظرفیت (`stack-stats`)

هر دو bridge عملیات فقط‌خواندنی `stack-stats` را ثبت می‌کنند. به client در
APIServer مجوز دقیق config، node و operation بدهید و از client معمول API با
framing استاندارد آن برای فرستادن درخواستی مانند نمونه‌ی زیر استفاده کنید:

```json
{
  "id": "capacity-1",
  "auth": {"client": "monitor", "token": "<configured token>"},
  "selector": {"config": "edge", "node": "connection-to-packets"},
  "operation": "stack-stats",
  "content_type": "application/json",
  "body_encoding": "utf8",
  "body": "{}"
}
```

selector و اطلاعات دسترسی را با مقادیر پیکربندی‌شده جایگزین کنید. بدنه باید
یک object خالی JSON با حداکثر ۶۴ بایت، شامل whitespace مجاز JSON، باشد.
فیلد اضافی، داده‌ی انتهایی و NUL پذیرفته نمی‌شود. پاسخ JSON با UTF-8 داخل body
نتیجه‌ی معمول API قرار می‌گیرد و وضعیت کل فرایند را نشان می‌دهد، نه فقط نود یا
worker انتخاب‌شده.

| فیلد پاسخ | معنی |
| --- | --- |
| `scope`، `dynamic` | مقدار `"process"` و قابل‌رشد بودن poolها |
| `memory_budget`، `reserved_bytes`، `peak_reserved_bytes` | سقف تنظیم‌شده، حافظه‌ی محاسبه‌شده‌ی فعلی و بیشینه‌ی آن |
| `recovery_headroom`، `recovery_bytes`، `external_recovery_bytes`، `recovery_refusals` | فضای بازیابی داخل سقف، حافظه‌ی محاسبه‌شده‌ی فعلی آن، زیرمجموعه‌ی external آن و تعداد رد درخواست به علت ظرفیت بایت بازیابی |
| `external_bytes`، `external_refusals` | حافظه‌ی handoff در CTP و ورودی نگه‌داری‌شده با pbuf در PTC و رزروهای ردشده‌ی آن |
| `byte_refusals`، `reclaimed_bytes` | رد درخواست به علت بودجه‌ی بایت و حافظه‌ی بازپس‌گرفته‌شده زیر فشار |
| `limits` | سقف مؤثر TCP/UDP، listener، segment و RX wrapper |
| `pools` | نام و اندازه‌ی هر شیء، سقف، تعداد تخصیص‌یافته/نگه‌داشته‌شده، بیشینه‌ی نگه‌داری، بایت رزروشده و رد درخواست تعداد/بایت در هر pool |
| `ports.tcp`، `ports.udp` | رزروهای فعلی و بیشینه، رد درخواست و رزروهای scoped/unscoped |

مجموع بایت‌ها و شمارنده‌های تجمعی برای حفظ دقت به شکل رشته‌ی دهدهی هستند؛
تعداد اشیا و سقف آن‌ها integer JSON است. `reserved_bytes` حافظه‌ی بازیابی را
هم شامل می‌شود و `external_bytes` شامل `external_recovery_bytes` است؛ این
زیرمجموعه‌ها را دوباره جمع نکنید. `held_includes_worker_caches` برابر
true است: `held` و `peak_held` اشیای آزاد رزروشده در cache worker را هم حساب
می‌کنند و تعداد اتصال زنده نیستند. بخش ظرفیت و پورت هرکدام زیر قفل خود snapshot
محدود می‌گیرند؛ کل پاسخ یک سرشماری اتمیک ترافیک نیست.

خروجی handler حداکثر ۳۲ KiB است و سقف پاسخ، بودجه‌ی حافظه‌ی کاری و deadline
درگاه را رعایت می‌کند. بدنه‌ی نامعتبر، در صورت جا شدن پاسخ خطا در این حدود،
`expected_empty_object` برمی‌گرداند؛ رد پاسخ به علت محدودیت می‌تواند بدنه‌ی خالی
داشته باشد. قبل از تغییر سقف، با شمارنده‌ی رد تعداد در هر pool، رد بودجه‌ی بایت
و رد پورت، منبع محدودکننده را مشخص کنید.


## Composition

- node قبلی باید layer 4 و node بعدی layer 3 باشد.
- `next` اجباری و مقصد packetهاست.
- حضور این node chain را packet chain می‌کند و packet line هر worker را می‌سازد.

## متادیتای نود

metadata برگرفته از کد منبع:

| ویژگی | مقدار |
| --- | --- |
| node flags | `kNodeFlagNone` |
| `can_have_prev` | `true` |
| `can_have_next` | `true` |
| `layer_group` | `kNodeLayer3` &#124; `kNodeLayer4` |
| `layer_group_prev_node` | `kNodeLayer4` |
| `layer_group_next_node` | `kNodeLayer3` |
| `required_padding_left` | `0` bytes |

بودجهٔ صف TCP برابر `P = max-pending-bytes` است و یک حاشیهٔ محدود به اندازهٔ
`L`، حاشیهٔ ثابت ۱ MiB مستقل از اندازهٔ pool، پروفایل حافظه و تنظیمات splice، برای ورودیِ قبلاً تحویل‌شده دارد. سقف
کل بایت‌های pending برابر `P + L` است تا Pause فرصت اثرگذاری داشته باشد. سقف
۱۰۲۴ entry و زمان ارسال Pause/Resume تغییر نمی‌کند؛ ورودیِ بیش از این سقف پیش
از ورود به صف رد می‌شود و فقط همان flow را می‌بندد.

نوشتن TCP همان سر FIFO را پس از هر write موفق حداکثر ۶۵۵۳۵ بایتی ادامه
می‌دهد تا ظرفیت واقعی تمام شود یا `ERR_MEM` رخ دهد. پیشوند موفق حتی هنگام رد
write بعدی ارسال می‌شود؛ دنباله در ابتدای صف می‌ماند و byteها تکرار نمی‌شوند.

## منابع engine و چرخهٔ عمر

runtime برای هر event worker معمولی حداکثر یک engine خام lwIP را هنگام نخستین
استفاده می‌سازد. همهٔ bridge‌های همان worker از آن استفاده می‌کنند؛ thread جداگانهٔ
stack و core mutex وجود ندارد. PTC مالک flow را از tuple فعلی بسته انتخاب می‌کند و CTP مالک
normal line برنامه را حفظ می‌کند. پاسخ CTP پس از lookup کامل tuple/WID/generation
در صف worker مالک قرار می‌گیرد و engine و netif دقیق دوباره بررسی می‌شوند.
callback همسایه همیشه deferred اجرا می‌شود، حتی روی همان worker.

poolهای قابل‌رشد flow/payload از سقف‌های سراسری بالا استفاده می‌کنند. هر engine
فعال حافظه‌ی کنترلی مستقل و ۱۷ رکورد timeout دارد؛ worker استفاده‌نشده engine ندارد.
رزرو پورت اتصال CTP براساس tuple کامل است و تا آزادشدن PCB، شامل TIME_WAIT،
باقی می‌ماند؛ رزرو unconnected همچنان همان شماره‌ی پورت را محافظه‌کارانه کنار می‌گذارد. ID‌های تولیدی fragment در IPv4 و IPv6 هرکدام sequence مشترک جداگانه‌ای دارند
و با همان عرض محدود قبلی wrap می‌شوند. drain list محلی هر worker است، ولی
سقف هر node همچنان ۴۰۹۶ object و ۱۶ MiB است. lock مربوط به pool/quota هنگام پیمایش stack یا تولید خروجی
آن نگه داشته نمی‌شود. Fake DNS در PTC یک mutex مشترک node برای transaction و کپی
نام reverse دارد؛ هیچ pointer رکوردی بیرون lock باقی نمی‌ماند و output پس از unlock است.

در quiesce، timer مربوط به engine پیش از توقف پذیرش کار عادی جدا می‌شود. node در drain همان
owner ریشه‌های stack خود را آزاد می‌کند. runtime پس از تسویهٔ messageهای detached
و پیش از نابودی loop و pool‌ها engine را آزاد می‌کند. pool‌ها و port accountهای مشترک
و secret مربوط به ISN در سطح process فقط پس از خروج همهٔ worker‌ها نهایی می‌شوند. fragment ورودی هر
دو bridge همچنان رد می‌شود و reassembly دستگاه پیش از انتخاب worker انجام می‌شود؛
MTU و fragmentation خروجی تغییر نکرده‌اند.

طول UDP عادی پیش از checksum و انتشار child بررسی می‌شود: حداقل ۸ بایت و حداکثر
بایت‌های transport محدودشده توسط IP. بایت‌های اضافهٔ پس از طول معتبر UDP از pbuf
حذف می‌شوند؛ فقط payload اعلام‌شده تحویل می‌شود. datagram با header تنها، یک
callback با payload خالی دارد. حالت trusted نیز این بررسی ساختاری را حفظ می‌کند.
