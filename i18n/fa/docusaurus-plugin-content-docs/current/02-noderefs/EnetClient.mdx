# EnetClient

`EnetClient` هر stream برنامه را به‌شکل یک اتصال اصلی ENet از مسیر UDP عبور می‌دهد.
`EnetServer` این اتصال‌ها را می‌پذیرد و برای هر کدام یک stream جدا به سمت مقصد
می‌سازد. قالب روی سیم همان ENet 1.3.18 بدون تغییر است: packetهای reliable و
مرتب روی یک channel.

```text
Client: TcpListener -> EnetClient -> UdpConnector
                                  == one ENet connection per stream, over UDP ==>
Server: UdpListener -> EnetServer -> TcpConnector
```

هر دو node روی خط‌های لایهٔ ۴ کار می‌کنند. `EnetClient` یک byte stream قابل‌اعتماد
را از node قبلی می‌گیرد و دیتاگرام‌های ENet را به node بعدی می‌فرستد. مرز
payloadها حفظ نمی‌شود: در سمت مقابل همان بایت‌ها با همان ترتیب می‌رسند.

## جایگاه در chain

- پیش از `EnetClient`: هر nodeای که byte stream تولید می‌کند، مثل `TcpListener`
  یا یک node پروتکل proxy.
- پس از `EnetClient`: مسیری که مرز دیتاگرام را نگه می‌دارد. در عمل یعنی
  `UdpConnector`، مستقیم یا پشت تونل‌هایی که دیتاگرام را بدون تغییر عبور می‌دهند.
- هر stream ورودی، خط حامل خودش را به سمت `next` و اتصال ENet خودش را می‌گیرد.
  streamها اتصال مشترک ندارند.
- سمت مقابل `EnetServer` است، یا هر برنامهٔ ENet 1.3 که با پیش‌فرض‌های کتابخانه
  کار کند (بدون checksum و بدون فشرده‌سازی) و packetهای reliable را روی channel
  صفر رد و بدل کند.

## پیکربندی

```json
{
  "name": "enet-client",
  "type": "EnetClient",
  "next": "udp-out",
  "settings": {
    "send-mtu": 1400
  }
}
```

### فیلدهای سطح بالا

| فیلد | الزام |
| --- | --- |
| `name` | نام node؛ لازم و یکتا در کل پیکربندی. |
| `type` | دقیقاً `"EnetClient"`. |
| `next` | لازم؛ نام nodeای که دیتاگرام‌ها را حمل می‌کند. |
| `settings` | شیء اختیاری. همهٔ تنظیم‌ها پیش‌فرض دارند. |

### تنظیمات

تنظیم‌ها عدد صحیح‌اند. مقدار از نوع دیگر، عدد کسری، null یا عدد بیرون از محدوده
جلوی راه‌اندازی را می‌گیرد و پیام خطا نام همان تنظیم را می‌آورد.

| تنظیم | پیش‌فرض | رفتار |
| --- | --- | --- |
| `send-mtu` | `misc.mtu` هسته | بودجهٔ packet مبتنی بر IPv4 برای دیتاگرام‌های خروجی، از `604` تا `65535`. بخش [MTU ارسال](#send-mtu) را ببینید. |
| `no-recv-timeout-ms` | `30000` | مهلت زنده‌بودن `T`، از `1` تا `2147483647`. اتصالی که packetهایش تأیید نشوند بین `T` و حدود `2T` پایان می‌یابد. |
| `ping-interval-ms` | `10000` | مدت سکوتی که پس از آن ENet یک ping می‌فرستد، از `1`. باید از `no-recv-timeout-ms` کوچک‌تر باشد. |
| `send-buffer-limit` | `524288` | تعداد بایت‌های پذیرفته‌شده و هنوز تأییدنشده که بالاتر از آن node قبلی Pause می‌شود، از `4096` تا `134217728`. |
| `receive-buffer-limit` | `1048576` | حدِ دادهٔ دریافتی‌ای که پشت یک packet گم‌شده منتظر می‌ماند، از `131072` تا `268435456`. بزرگ‌ترین packet پذیرفتنی ENet نصف این مقدار است. |
| `carrier-queue-limit` | `256` | تعداد دیتاگرام‌هایی که یک فراخوانی ENet می‌تواند به node بعدی بدهد، از `1` تا `65535`. |
| `close-drain-timeout-ms` | `30000` | مدتی که اتصالِ در حال بسته‌شدن برای تأیید بایت‌های باقی‌مانده از سمت مقابل صبر می‌کند، از `1` تا `2147483647`. |
| `incoming-bandwidth` | `0` | پهنای باند ورودی ENet بر حسب بایت بر ثانیه، از `0` تا `4294967295`. مقدار `0` یعنی نامحدود. |
| `outgoing-bandwidth` | `0` | پهنای باند خروجی ENet بر حسب بایت بر ثانیه، از `0` تا `4294967295`. مقدار `0` یعنی نامحدود. |

هر سمت مقدارهای خودش را به کار می‌برد؛ جز اندازهٔ دیتاگرام و پنجرهٔ reliable چیزی
مذاکره نمی‌شود. اگر `no-recv-timeout-ms` برابر `10000` یا کمتر باشد، باید
`ping-interval-ms` هم کوچک‌تر شود.

تنظیم‌های پهنای باند بدون تغییر به ENet داده می‌شوند. ENet با آن‌ها پنجرهٔ reliable
و packet throttle خودش را تنظیم می‌کند؛ این‌ها محدودکنندهٔ دقیق نرخ نیستند. مقدار
غیرصفر کمتر از `1048576` پنجره را کوچک می‌کند: ۴٬۰۹۶ بایت به ازای هر ۶۵٬۵۳۶ بایت
بر ثانیه، و هیچ‌وقت کمتر از ۴٬۰۹۶ بایت.

## MTU ارسال {#send-mtu}

`send-mtu` یک بودجهٔ packet مبتنی بر IPv4 است، با همان معنایی که در `KcpClient`
دارد. حد دیتاگرام ENet این است:

```text
ENet MTU = min(send-mtu - 28, 4096)
```

این ۲۸ بایت headerهای IPv4 و UDP هستند و ۴۰۹۶ بیشینهٔ پروتکل ENet است. با
پیش‌فرض `1500` هسته، این حد ۱۴۷۲ بایت می‌شود. بودجهٔ بالاتر از `4124` معتبر است و
همان ۴۰۹۶ را به کار می‌برد. بودجهٔ کمتر از `604` جلوی راه‌اندازی را می‌گیرد، چه در
خود node نوشته شده باشد و چه از `misc.mtu` هسته به ارث رسیده باشد؛ چون کوچک‌ترین
MTU در ENet برابر ۵۷۶ بایت است.

ENet هنگام اتصال، کوچک‌ترینِ حد دو طرف را مذاکره می‌کند؛ پس بودجهٔ هر سمت هر دو
جهت را محدود می‌کند. دریافت به بودجهٔ محلی وابسته نیست: دیتاگرام تا ۴۰۹۶ بایت
پذیرفته می‌شود.

این کار کشف MTU مسیر نیست. header در IPv6 بیست بایت بیشتر از سهم ثابت IPv4 جا
می‌خواهد و تونل‌های بعد از این node هم بایت‌های خودشان را اضافه می‌کنند. برای
آن‌ها `send-mtu` را کمتر بگذارید.

## توان انتقال و دیگر محدودیت‌های ذاتی

این محدودیت‌ها از خود پروتکل ENet می‌آیند و بدون کنار گذاشتن سازگاری با ENet
اصلی برداشته نمی‌شوند.

- **هر اتصال در هر رفت‌وبرگشت حدود ۶۴ کیلوبایت حمل می‌کند.** ENet روی هر اتصال
  حداکثر ۶۵٬۵۳۶ بایت دادهٔ reliable در راه نگه می‌دارد و هر دو طرف این پنجره را
  محدود می‌کنند. بنابراین یک stream حداکثر `65536 * 8 / RTT` بیت بر ثانیه حمل
  می‌کند: حدود ۲۶ مگابیت بر ثانیه در ۲۰ میلی‌ثانیه، ۱۰٫۵ در ۵۰، ۵٫۲ در ۱۰۰ و ۲٫۶ در
  ۲۰۰ میلی‌ثانیه. روی لینک شبیه‌سازی‌شده، node بدون loss به همین سقف می‌رسد؛ در ۱۰۰
  میلی‌ثانیه با ۱٪ loss به ۹۷٪ آن و با ۵٪ loss به ۷۶٪ آن. بین دو میزبان با
  رفت‌وبرگشت ۳۸ تا ۴۵ میلی‌ثانیه، streamهای تکی ۱۱٫۶ تا ۱۳٫۶ مگابیت بر ثانیه حمل
  کردند. این سقف برای هر اتصال است: چهار stream هم‌زمان چهار برابر حمل کردند، و
  یک stream که `ConnectionStripeClient` آن را روی هشت اتصال ENet پخش کرده بود، در
  همان مسیر ۷۶ تا ۸۳ مگابیت بر ثانیه حمل کرد.
- **قطع‌شدن سمت مقابل از نبودِ تأییدها فهمیده می‌شود.** اتصال بی‌کار پس از
  `ping-interval-ms` یک ping می‌فرستد. سمتی که دیگر پاسخ نمی‌دهد بین `T` و حدود
  `2T` پس از اولین packet بی‌پاسخ تشخیص داده می‌شود؛ `T` همان
  `no-recv-timeout-ms` است. با پیش‌فرض‌ها، سمتِ متوقف‌شده ۳۳ تا ۳۵ ثانیه پس از آن
  packet تشخیص داده شد.
- **اتصال به حامل خودش بسته است.** اگر نشانی مبدأ UDP در client عوض شود، server
  یک حامل تازه می‌بیند و اتصال قبلی timeout می‌شود.
- **بدون رمزنگاری و بدون احراز هویت.** ENet همهٔ بایت‌ها را آشکار می‌فرستد و هر
  طرفی را می‌پذیرد. اگر این ویژگی‌ها لازم است، nodeهای امنیتی را در سمت stream
  بگذارید: پیش از `EnetClient` و پس از `EnetServer`.

## کنترل جریان و حافظه

- تا وقتی بیش از `send-buffer-limit` بایت پذیرفته شده و هنوز از سمت مقابل تأیید
  نشده باشد، node قبلی Pause می‌ماند و وقتی به نصف آن یا کمتر برسد Resume
  می‌شود. Pause از node بعدی هم node قبلی را Pause می‌کند؛ هر کدام از این دو علت
  به‌تنهایی آن را در Pause نگه می‌دارد.
- payloadی که هنگام معوق‌بودنِ بیش از دو برابر `send-buffer-limit` بایت برسد
  پذیرفته نمی‌شود و همان اتصال بسته می‌شود. node قبلی‌ای که Pause را رعایت کند به
  این حالت نمی‌رسد.
- وقتی node قبلی جهت downstream را Pause می‌کند، `EnetClient` نیز node بعدی را
  Pause می‌کند و دریافت دیتاگرام متوقف می‌شود. این کار تأییدها را هم متوقف می‌کند:
  Pause طولانی‌تر از مهلت زنده‌بودن می‌تواند اتصال را تمام کند.
- در `receive-buffer-limit`، دیگر ENet داده‌ای را که جلوتر از یک packet گم‌شده
  رسیده تأیید نمی‌کند و سمت مقابل آن را بعداً دوباره می‌فرستد. خودِ packet گم‌شده
  همچنان پذیرفته می‌شود؛ پس گم‌شدن یک packet نمی‌تواند stream را قفل کند. بایت‌های
  تأییدشده هرگز دور ریخته نمی‌شوند و هر اتصال کمتر از دو و نیم برابر این حد نگه
  می‌دارد. packet دریافتی ENet که از نصف این حد بزرگ‌تر باشد هرگز تأیید نمی‌شود؛
  پس آن اتصال با timeout سمت مقابل پایان می‌یابد.
- دیتاگرام‌های بیش از `carrier-queue-limit` در یک فراخوانی ENet دور ریخته می‌شوند
  و ENet پس از مهلت خودش آن‌ها را دوباره می‌فرستد. اتصال باز می‌ماند.

## رفتار Close و timeout

- وقتی node قبلی stream را Finish می‌کند، `EnetClient` دیگر بایتی نمی‌پذیرد،
  می‌گذارد ENet همهٔ بایت‌های قبلاً پذیرفته‌شده را برساند و سپس به روش خود ENet
  قطع می‌کند. اتصال برای این کار، پس از رفتن خط برنامه، خط حامل خودش را نگه
  می‌دارد. بایت‌هایی که پس از آن Finish از سمت مقابل برسند دور ریخته می‌شوند:
  Finish هر دو جهت stream را می‌بندد.
- به اندازهٔ `close-drain-timeout-ms` پس از آن Finish، دیگر node صبر نمی‌کند، یک
  disconnect می‌فرستد و می‌بندد، و هشداری با تعداد بایت‌های تأییدنشده ثبت می‌کند.
  بسته‌شدنی که زودتر تمام شده باشد هم دلیل قطعیِ رسیدن داده نیست: ENet پایان
  بسته‌شدن را، وقتی سمت مقابل timeout شود، به همان شکل گزارش می‌کند.
- وقتی سمت مقابل قطع می‌کند، بایت‌هایی که پیش از قطع رسیده‌اند اول تحویل می‌شوند و
  سپس node قبلی Finish می‌گیرد. بایت‌هایی که هنوز در این سمت فرستاده نشده بودند
  دور ریخته می‌شوند؛ ENet half-close ندارد.
- وقتی node بعدی حامل را Finish می‌کند، اتصال همان لحظه تمام می‌شود و node قبلی
  Finish می‌گیرد.
- درخواست اتصالی که پاسخی نگیرد با همان مهلت زنده‌بودن پایان می‌یابد.
- هنگام خاموش‌شدن، همهٔ اتصال‌ها بدون انتظار برای تخلیه تمام می‌شوند.

## عیب‌یابی

| نشانه | بررسی |
| --- | --- |
| stream باز می‌شود ولی داده‌ای نمی‌رسد و پس از ۳۰ تا ۶۰ ثانیه بسته می‌شود | آماده‌بودن حامل فقط یعنی سوکت UDP وجود دارد. بررسی کنید دیتاگرام‌ها به یک `EnetServer` برسند و پاسخ‌ها برگردند، و هیچ گامی در مسیر دیتاگرام‌های به اندازهٔ `send-mtu` را دور نریزد. |
| یک انتقال روی مسیر طولانی کند است، با اینکه لینک ظرفیت دارد | این همان پنجرهٔ ۶۴ کیلوبایت در هر رفت‌وبرگشتِ ENet است. streamهای هم‌زمان هر کدام پنجرهٔ خودشان را دارند، و `ConnectionStripeClient` پیش از این node به یک stream چند اتصال می‌دهد. |
| راه‌اندازی شکست می‌خورد و نام `send-mtu` را می‌آورد، با اینکه node آن را تنظیم نکرده | `misc.mtu` هسته کمتر از `604` است. `send-mtu` را در خود node بگذارید. |
| خط لاگ `the send limit refused a payload` | node قبلی پس از Pause به فرستادن ادامه داده است. nodeهای پیش از `EnetClient` را بررسی کنید یا `send-buffer-limit` را بالا ببرید. |
| خط لاگ `close delivery unconfirmed at the fixed deadline` | سمت مقابل بایت‌های آخر را در `close-drain-timeout-ms` تأیید نکرده است. loss مسیر را بررسی کنید یا برای مسیرهای کند این مهلت را بیشتر کنید. |

## متادیتای نود

مقدارهای برگرفته از `instance/node.c`:

| ویژگی | مقدار |
| --- | --- |
| node flags | `kNodeFlagBlocksSplice` |
| `can_have_prev` | `true` |
| `can_have_next` | `true` |
| `layer_group` | `kNodeLayer4` |
| `layer_group_prev_node` | `kNodeLayer4` |
| `layer_group_next_node` | `kNodeLayer4` |
| `required_padding_left` | `0` بایت |

Splice برای chainهایی که این node را دارند خاموش است. هر دیتاگرام در یک buffer
تازه ساخته می‌شود؛ برای همین padding سمت چپ رزرو نمی‌شود.

پیکربندی‌های قابل‌اجرا برای جفت ساده و برای «یک stream روی چند اتصال ENet» در
[نمونه‌های ENet](https://github.com/radkesvat/WaterWall/tree/main/tunnels/EnetClient/examples)
هستند.
