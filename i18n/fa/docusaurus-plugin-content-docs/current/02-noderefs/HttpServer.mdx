# HttpServer

`HttpServer` بخش سرور `HttpClient` است. درخواست ورودی HTTP را تجزیه می‌کند، فریم‌بندی HTTP را برمی‌دارد و فقط body درخواست را به node بعدی می‌دهد. در مسیر برگشت نیز payload دریافتی از node بعدی را به body پاسخ تبدیل می‌کند.

این node از HTTP/1.1، اتصال مستقیم HTTP/2، upgrade از HTTP/1.1 به `h2c`، token سفارشی upgrade، حالت split در HTTP/1.1 و WebSocket پشتیبانی می‌کند.

`HttpServer` خودش TLS را terminate نمی‌کند. اگر ترافیک ورودی HTTPS است، باید `TlsServer` را پیش از `HttpServer` قرار دهید.

برای ارائهٔ پراکسی به مرورگر یا ابزارهایی مانند `curl --proxy`، از
[`HttpProxyServer`](./HttpProxyServer.mdx) استفاده کنید. این node مقصد را از
درخواست پراکسی می‌خواند و تونل CONNECT را هم پشتیبانی می‌کند. `HttpServer`
فریم‌بندی HTTP تنظیم‌شده را باز می‌کند و بایت‌های body را به node تعیین‌شده در
`next` می‌دهد؛ گزینه‌های `host` و `path` آن برای تطبیق درخواست ورودی هستند.
برای اتصال خروجی از chain به یک پراکسی HTTP موجود، از
[`HttpProxyClient`](02-noderefs/HttpProxyClient.mdx) استفاده کنید.

## جایگاه رایج

یک سرویس محلی SOCKS5 می‌تواند مقصد انتخاب‌شدهٔ برنامه را با VMess روی
WebSocket در HTTP/1.1 و TLS حمل کند:

```text
Client: TcpListener -> Socks5Server -> VmessClient -> HttpClient -> TlsClient -> TcpConnector
Server: TcpListener -> TlsServer -> HttpServer -> VmessServer -> TcpConnector
```

تنظیم کامل [کلاینت](./VmessClient.mdx#socks5-websocket-tls-client) و
[سرور](./VmessServer.mdx#socks5-websocket-tls-server) همهٔ nodeها، ‏Host/path
یکسان WebSocket، ‏UUID و ALPN مربوط به HTTP/1.1 را نشان می‌دهد. connector بیرونی
به سرور تونل وصل می‌شود و VMess مقصد برنامه را منتقل می‌کند.

برای یک سرویس ثابت TCP با فریم‌بندی body در HTTP، جفت ساده‌تر چنین است:

```text
Client: TcpListener -> HttpClient -> TcpConnector
Server: TcpListener -> HttpServer -> TcpConnector
```

در هر دو node مربوط به HTTP، ‏`http-version: 1`، ‏`host` و `path` یکسان و
`method: "POST"` قرار دهید. connector کلاینت به listener سرور و connector سرور
به آدرس و پورت ثابت backend وصل می‌شود. برای TLS، ‏TlsClient را پیش از connector
کلاینت و TlsServer را پس از listener سرور بگذارید و ALPN هر دو را HTTP/1.1 انتخاب
کنید. `host` و `port` در HttpClient فقط metadata مربوط به HTTP هستند و socketها
را تنظیم نمی‌کنند.

## نمونه تنظیم

```json
{
  "name": "http-server",
  "type": "HttpServer",
  "settings": {
    "http-version": "both",
    "upgrade": true,
    "host": "example.com",
    "path": "/api/tunnel",
    "method": "POST",
    "status": 200,
    "headers": {
      "server": "waterwall"
    }
  },
  "next": "service"
}
```

## تنظیمات ضروری

این node تنظیم اختصاصی اجباری ندارد، اما object `settings` باید وجود داشته باشد و خالی نباشد.

پیش‌فرض‌های مهم:

| گزینه | پیش‌فرض |
|---|---|
| `http-version` | `both` |
| `upgrade` | در حالت `both` برابر `true` |
| `path` | `/` |
| `method` | `POST` |
| `status` | `200` |
| `websocket` | `false` |
| `http1-mode` | `single` |

## تنظیمات اختیاری

| گزینه | پیش‌فرض | توضیح |
|---|---|---|
| `http-version` | `both` | حالت پروتکل؛ مقدارهای عددی و نام‌های مستعار متنی را می‌پذیرد. |
| `close-drain-timeout-ms` | `30000` | مهلت ثابت تخلیهٔ پاسخ HTTP/2 پس از Finish از backend، بر حسب میلی‌ثانیه. عدد صحیح از `1` تا `86400000`. |
| `upgrade` | فقط در حالت `both` برابر `true` | درخواست‌های upgrade در HTTP/1.1 را می‌پذیرد. |
| `upgrade-protocol` | `h2c` | توکن upgrade. اگر غیر از `h2c` باشد، بعد از `101` مسیر raw می‌شود. |
| `upgrade-request-headers` | ندارد | header‌هایی که باید در درخواست ارتقا وجود داشته باشند. |
| `upgrade-response-headers` | ندارد | header‌های اضافه برای پاسخ `101 Switching Protocols`. |
| `host` | ندارد | host مورد انتظار. اگر تنظیم شود، مقدار ناسازگار رد خواهد شد. |
| `path` | `/` | مسیر مورد انتظار. |
| `method` | `POST` | متد مورد انتظار در حالت غیر WebSocket. |
| `status` | `200` | کد وضعیت پاسخ. بازه معتبر فعلی `100` تا `599` است. |
| `headers` | ندارد | header‌های اضافه پاسخ. مقدارها باید string باشند. |
| `content-type` | ندارد | مقدار Content-type از جدول داخلی واتروال. |
| `websocket` | `false` | handshakeِ WebSocket را می‌پذیرد و سپس payload را در فریم‌های WebSocket منتقل می‌کند. |
| `websocket-origin` | ندارد | مقدار مورد انتظار `Origin`. |
| `websocket-subprotocol` | ندارد | subprotocol مورد انتظار که در پاسخ تکرار می‌شود. |
| `http1-mode` | `single` | شکل HTTP/1.1: مقدار `single` یا `split`. گزینه قدیمی `http1-split` هم پذیرفته می‌شود. |
| `split` | مقادیر پیش‌فرض داخلی | تنظیمات جفت کردن دو درخواست در حالت split. |
| `no-split-upload-buffering-limit` | `false` | گزینه مخصوص تست برای برداشتن سقف buffer سمت upload پیش از متصل شدن download. |
| `verbose` | `false` | لاگ بیشتر برای تشخیص پروتکل، handshake و فریم‌بندی. |

## حالت‌های HTTP

| مقدار `http-version` | معنی |
|---|---|
| `1`, `1.1`, `http1`, `http1.1` | اجبار به HTTP/1.1. |
| `2`, `2.0`, `http2`, `h2` | اجبار به HTTP/2 مستقیم. |
| `both`, `any`, `auto`, `1.1+2` | تشخیص HTTP/2 مستقیم یا HTTP/1.1، همراه با upgrade اختیاری. |

## HTTP/1.1 معمولی

با `http1-mode: "single"` برای هر line در WaterWall یک درخواست و پاسخ HTTP/1.1 استفاده می‌شود:

- header‌های درخواست در `HttpServer` خوانده می‌شوند.
- body درخواست به payloadِ WaterWall تبدیل می‌شود.
- payload برگشتی از node بعدی به body پاسخ تبدیل می‌شود.
- پاسخ با `Transfer-Encoding: chunked` ساخته می‌شود.
- هنگام `Finish` در downstream، chunk پایانی فرستاده و سپس Finishِ WaterWall منتشر می‌شود.

Parser درخواست می‌تواند body از نوع chunked، بدنه دارای `Content-Length` و درخواست بدون body را بخواند. Trailerهای chunked در خود node خوانده می‌شوند.

بدنهٔ chunkهای ورودی به‌محض رسیدن بایت‌ها ارسال می‌شود و node منتظر کامل شدن chunk نمی‌ماند. خط اندازهٔ chunk با احتساب extensionها و CRLF حداکثر ۱ KiB است؛ مجموع trailerها با احتساب پایان‌دهنده‌ها حداکثر ۱۶ KiB است. حد header اولیهٔ HTTP همان ۶۴ KiB باقی می‌ماند. فریم‌بندی نامعتبر یا عبور از حد، اتصال مربوط را می‌بندد. ممکن است پیش از تشخیص پایان‌دهندهٔ نامعتبر chunk، بخشی از بدنه ارسال شده باشد.

`HttpClient` و `HttpServer` در حالت single همیشه full duplex هستند. `Finish` در Waterwall کل line را می‌بندد و half-close وجود ندارد؛ بنابراین پایان body درخواست یا پاسخ به‌تنهایی line تونل را نمی‌بندد. تنها استثنا `http1-mode: "split"` است: نیمه upload یک اتصال جداست و پایان body آن سیگنال توقف ارسال peer محسوب می‌شود.

## حالت HTTP/1.1 split

در حالت split دو درخواست HTTP/1.1 به یک line در WaterWall متصل می‌شوند:

- درخواست upload: body آن به node بعدی داده می‌شود.
- درخواست download: body پاسخ آن، payload برگشتی از node بعدی را حمل می‌کند.
- دو نیمه با id، direction و token اختیاری به هم جفت می‌شوند.

`HttpClient` برای هر line یک شناسه جفت‌سازی ۱۲۸ بیتی تازه با CSPRNG از دو مقدار `fastRand64()` (۱۶ بایت از stream ChaCha20 همان thread) تولید می‌کند و آن را به‌صورت ۳۲ کاراکتر hex با حروف کوچک می‌فرستد. سرور از این مقدار به‌عنوان metadata معمولی برای تطبیق بخش‌های upload و download استفاده می‌کند. اگر استقرار به محافظت از ترافیک نیاز دارد، می‌توان `TlsServer`، `EncryptionServer` یا یک node امنیتی دیگر را به chain اضافه کرد.

پایان body اتصال جداگانه upload، روی line اصلی یک `Finish` در upstream منتشر می‌کند.

این حالت باید با حالت split در `HttpClient` هماهنگ باشد.

```json
{
  "name": "http-server",
  "type": "HttpServer",
  "settings": {
    "http-version": 1,
    "http1-mode": "split",
    "path": "/tunnel",
    "split": {
      "upload-method": "POST",
      "download-method": "GET",
      "id-placement": "query",
      "id-name": "sid",
      "direction-placement": "query",
      "direction-name": "part",
      "token": "shared-token",
      "token-placement": "header",
      "token-name": "X-Tunnel-Token"
    },
    "headers": {
      "Cache-Control": "no-store"
    }
  },
  "next": "service"
}
```

فیلدهای رایج داخل `split`:

| گزینه | پیش‌فرض | توضیح |
|---|---|---|
| `upload-method` | متد سطح اصلی | متد مورد انتظار سمت upload. |
| `download-method` | `GET` | متد مورد انتظار سمت download. |
| `upload-path` | path اصلی | مسیر سمت upload. |
| `download-path` | path اصلی | مسیر سمت download. |
| `id-placement` | `query` | محل خواندن شناسه مشترک. |
| `id-name` | `wwid` | نام فیلد شناسه. |
| `direction-placement` | `query` | محل خواندن marker مربوط به جهت. |
| `direction-name` | `wwdir` | نام marker مربوط به جهت. |
| `upload-value` | `upload` | مقدار جهت برای upload. |
| `download-value` | `download` | مقدار جهت برای download. |
| `token` | ندارد | token مشترک اختیاری. |
| `token-placement` | `header` | محل خواندن token. |
| `token-name` | `X-Waterwall-Token` | نام فیلد token. |

:::warning
Split mode فقط با `http-version = 1` معتبر است و با `websocket` ترکیب نمی‌شود.
:::

`no-split-upload-buffering-limit` سقف ایمنی معمول buffer سمت upload را برمی‌دارد. این گزینه بیشتر برای تست و شرایط کنترل‌شده مناسب است، نه استفاده عادی.

## HTTP/2

در اتصال مستقیم HTTP/2، `HttpServer` یک stream منطقی برای line در WaterWall می‌پذیرد:

- تا وقتی node بعدی باز است، فریم‌های DATA درخواست به payloadِ upstream تبدیل می‌شوند.
- payload برگشتی به فریم DATA پاسخ تبدیل می‌شود.
- `END_STREAM` سمت درخواست فقط در state داخلی ثبت می‌شود و به‌تنهایی line در WaterWall را نمی‌بندد.
- `Finish` در downstream به `END_STREAM` پاسخ تبدیل می‌شود.

جزئیات مهم:

- مقدار `MAX_CONCURRENT_STREAMS` برابر `1` است
- window اولیه stream برابر 1 MiB است.
- بیشترین اندازه فریم 32 KiB است.
- stream‌های اضافه با `REFUSED_STREAM` رد می‌شوند.
- در حالت WebSocket، تنظیم `SETTINGS_ENABLE_CONNECT_PROTOCOL` فعال می‌شود.

بایت‌های ورودی HTTP/2 در قطعه‌های 16 KiB پردازش می‌شوند. پیاده‌سازی فعلی وقتی payload پاسخ در صف از 1 MiB بیشتر شود،
برای node بعدی Pause می‌فرستد و وقتی به کمتر از 256 KiB برسد Resume می‌فرستد. این آستانه‌ها ثابت و فقط درخواست کنترل
فشار هستند، نه سقف قطعی حافظه: تعداد بایت‌هایی را می‌شمارند که هنوز داخل فریم DATA کپی نشده‌اند، نه ظرفیت bufferهای
نگه‌داری‌شده را. صف جداگانهٔ خروجی برنامه که منتظر آماده شدن پروتکل است سقف قطعی 2 MiB برای payload و 8 MiB برای
هزینهٔ ظرفیت buffer دارد.
`TcpListener` نیز برای payload نوشتنِ نگه‌داری‌شده و هزینهٔ ظرفیت آن دو سقف جداگانهٔ 16 MiB دارد؛ عبور از هرکدام اتصال
را می‌بندد. تنظیمات `large-send-buffer` و `large-recv-buffer` مربوط به bufferهای kernel هستند و این سقف‌های صف را تغییر نمی‌دهند.

وقتی node بعدی Finish می‌فرستد، ممکن است بخشی از پاسخ هنوز منتظر اعتبار flow control از کلاینت باشد.
`HttpServer` در این فاصله state مربوط به HTTP/2 و line قرض‌گرفته‌شدهٔ transport را نگه می‌دارد و فریم‌های کنترلی مثل
WINDOW_UPDATE را پردازش می‌کند، اما دادهٔ بیشتر بدنهٔ درخواست را دور می‌ریزد؛ حتی رویدادهای بدنه که قبلاً decode و در
صف ذخیره شده‌اند. هیچ callback دیگری به سمت node تمام‌شده ارسال نمی‌شود. پس از تحویل DATA و `END_STREAM` پاسخ به
node قبلی، state مربوط به HTTP آزاد و Finish به همان سمت ارسال می‌شود. این تحویل به معنی تأیید دریافت توسط کلاینت نیست.

اگر transport در زمان انتظار قطع شود، پاسخ باقی‌مانده لغو و state و bufferهای HTTP آزاد می‌شوند.
لغو stream توسط طرف مقابل نیز پاسخ باقی‌مانده را لغو می‌کند؛ node منتظر تمام کردن stream لغوشده نمی‌ماند.
اگر قطع شدن درون
callback ارسال بایت‌های نهایی رخ دهد، همان عملیات بستنِ فعال یک‌بار پاک‌سازی را انجام می‌دهد؛ اگر بعداً رخ دهد، پاک‌سازی
فوری است.

گزینهٔ `close-drain-timeout-ms` این انتظار را محدود می‌کند؛ پیش‌فرض آن 30000 میلی‌ثانیه است و عدد صحیح از 1 تا
86400000 را می‌پذیرد. مهلت از نخستین Finishِ backend شروع می‌شود. ترافیک ورودی، WINDOW_UPDATE و پیشرفت جزئی ارسال
پاسخ آن را تمدید نمی‌کنند. اگر تا پایان مهلت DATA و END_STREAM پاسخ به node قبلی تحویل نشده باشند، باقی پاسخ دور
ریخته می‌شود، state مربوط به HTTP آزاد می‌شود و Finish فقط به سمت transportِ هنوز فعال فرستاده می‌شود؛ هیچ callback
دیگری به backendِ تمام‌شده فرستاده نمی‌شود. تحویل کامل پاسخ، قطع transport و لغو stream تایمر را لغو می‌کنند؛ خاموش
شدن برنامه نیز این انتظار را فوراً متوقف می‌کند.

این گزینه برای HTTP/2 مستقیم، HTTP/2 پس از ارتقای h2c و WebSocket روی HTTP/2 اعمال می‌شود. رفتار بستن HTTP/1.1،
حالت split و ارتقای سفارشی raw تغییر نمی‌کند. این مهلت سقف قطعی حافظه برای صف پاسخ ایجاد نمی‌کند. محدودیت idle معمول
transport مستقل است و می‌تواند اتصال را زودتر ببندد.
این مهلت انتظار و state مربوط به پاسخ HTTP را محدود می‌کند، نه عمر socketِ TCP را: بایت‌هایی که قبلاً به transport
تحویل شده‌اند تابع مسیر معمول بستن و تخلیهٔ نوشتن آن هستند. پایان مهلت، درخواست linger مخصوص پاسخ کامل را فعال نمی‌کند.

در Linux، تحویل کامل پاسخ از `TcpListener` درخواست linger در سطح socket می‌کند. line در WaterWall فوراً از بین می‌رود.
socket مستقل حداکثر 60 ثانیه برای تخلیهٔ داده‌های پذیرفته‌شده فرصت دارد؛ سپس جهت نوشتن را می‌بندد و ورودی باقی‌ماندهٔ
طرف مقابل را می‌خواند و دور می‌ریزد، تا 5 ثانیه بی‌کاری یا حداکثر 30 ثانیه در مجموع. این مهلت‌های ثابت مربوط به دو مرحلهٔ
پیاپی هستند. خواندن ورودی باقی‌مانده از TCP reset ناشی از بستن socket با دادهٔ خوانده‌نشده جلوگیری می‌کند. خطا، قطع طرف
مقابل یا خاموش شدن برنامه ممکن است این مراحل را زودتر تمام کند. سیستم‌عامل‌های دیگر از مسیر معمول بستن adapter استفاده
می‌کنند. تنظیمات قابل‌تغییر و جداگانهٔ `TcpListener` یعنی `initial-idle-timeout-ms` با پیش‌فرض 60000 و
`active-idle-timeout-ms` با پیش‌فرض 600000 مهلت idle را مشخص می‌کنند، نه مهلت linger را.

## Upgrade

با `http-version: "both"` و `upgrade: true`، node می‌تواند درخواست‌های upgrade را بپذیرد.

برای `h2c`، درخواست باید metadata لازم را داشته باشد:

- `Connection` شامل `Upgrade` و `HTTP2-Settings`
- `Upgrade: h2c`
- `HTTP2-Settings`

پس از پذیرش upgrade، پاسخ `101 Switching Protocols` فرستاده می‌شود و node وارد HTTP/2 می‌شود. درخواست اصلی پس از upgrade stream شماره 1 است و طراحی فعلی برای payload منتظر یک stream تونل پس از upgrade می‌ماند.

اگر `upgrade-protocol` توکنی سفارشی و غیر از `h2c` باشد، پس از handshake موفق مسیر به عبور دوطرفه بایت‌های خام تبدیل می‌شود.

پس از ارسال کامل پاسخ `101` و داده‌های خام پذیرفته‌شده، HttpServer وضعیت HTTP
خود را آزاد می‌کند و برای آن line به‌صورت دائمی bypass می‌شود. داده‌های خامی که
هنگام این گذار به‌صورت بازگشتی وارد می‌شوند، ترتیب FIFO را حفظ می‌کنند؛ حد هر
صف جهت‌دار ۲ MiB هزینهٔ تخصیص و ۱٬۰۲۴ بافر است و عبور از حد، اتصال را می‌بندد.
حالت‌های بدنهٔ HTTP، HTTP/2، WebSocket و split برای framing یا نگاشت line فعال
می‌مانند. اعلان‌های Pause/Resume روی همان line شفاف و تکرارپذیر هستند، حتی در
زمان upgrade، و ارسال خروجی آماده را به تعویق نمی‌اندازند.

## WebSocket

دادهٔ فریم‌های WebSocket ورودی در HTTP/1.1 و HTTP/2 به‌تدریج از فریم استخراج و ارسال می‌شود. بدنهٔ Ping، ‏Pong و Close به‌صورت رویداد کنترلی کامل و با حداکثر ۱۲۵ بایت پردازش می‌شود. اندازهٔ پشتیبانی‌نشدهٔ فریم از روی header و پیش از انتظار برای بایت‌های بدنه رد می‌شود.

با `websocket: true`، ابتدا handshakeِ WebSocket بررسی می‌شود و سپس payload در فریم‌های WebSocket جابه‌جا می‌شود.

در HTTP/1.1:

- متد باید `GET` باشد
- header‌های upgrade WebSocket باید وجود داشته باشند
- `Sec-WebSocket-Key` باید معتبر باشد
- `Sec-WebSocket-Version` باید `13` باشد
- request body پذیرفته نمی‌شود
- اگر `host`، `path`، `websocket-origin` یا `websocket-subprotocol` تنظیم شده باشند، باید با درخواست منطبق باشند.

در HTTP/2:

- request باید extended `CONNECT` باشد
- مقدار `:protocol` باید `websocket` باشد
- `:path` و authority/host در صورت تنظیم باید منطبق باشند.
- `Sec-WebSocket-Version` باید `13` باشد

بعد از handshake:

- فریم‌های سمت کلاینت باید mask شده باشند.
- فریم‌های سمت سرور بدون mask فرستاده می‌شوند.
- payload برگشتی WaterWall به فریم binary تبدیل می‌شود.
- فریم‌های text، binary و continuation از peer به payload خام تبدیل می‌شوند.
- ping و pong داخل node مدیریت می‌شوند
- پیش از Finish یک فریم close فرستاده می‌شود.

## رفتار Finish و Lifecycle

`HttpServer` پیش از انتشار بعضی رویدادهای Finish در WaterWall، بایت‌های پایانی پروتکل را می‌فرستد:

- HTTP/1.1 آخرین chunk پاسخ را می‌فرستد.
- HTTP/2 یک `END_STREAM` برای پاسخ می‌فرستد.
- WebSocket یک فریم close می‌فرستد.

پیاده‌سازی ابتدا جهت مربوط را finished علامت می‌زند، سپس state محلی HTTP را از بین می‌برد و در پایان `Finish` واقعی WaterWall را منتشر می‌کند. این ترتیب مانع از آن می‌شود که backpressure ناشی از بایت‌های پایانی پروتکل، callback‌های pause/resume را به سمتی برگرداند که قبلاً finish شده است.

در حالت split، `HttpServer` همان line منطقی WaterWall را می‌سازد و مدیریت می‌کند که دو نیمه upload و download در HTTP را به هم وصل می‌کند. نیمه‌های transport بسته می‌شوند، بی‌آنکه مانند اتصال‌های مستقل سرویس با آن‌ها رفتار شود.

## Buffer Padding

`HttpServer` برای مسیرهای فریم‌بندی، `16` بایت left padding اعلام می‌کند. هنگام ترکیب آن با node‌هایی که بایت پروتکل اضافه می‌کنند، این فضا را در نظر بگیرید.

## اشتباه‌های رایج

- قرار دادن `HttpServer` مستقیم بعد از `TcpListener` وقتی ترافیک ورودی TLS رمزنگاری شده است. ابتدا `TlsServer` بگذارید.
- انتظار عبور header به node بعدی؛ node بعدی فقط payloadِ body را می‌گیرد.
- ترکیب حالت split با WebSocket یا HTTP/2.
- انتظار تبدیل چند stream مستقل HTTP/2 به چند line در WaterWall.
- استفاده از extension سفارشی WebSocket؛ مسیر WebSocket فقط فریم‌های بدون extension را منتقل می‌کند.

## متادیتای نود

metadata برگرفته از کد منبع:

| ویژگی | مقدار |
| --- | --- |
| node flags | `kNodeFlagBlocksSplice` |
| `can_have_prev` | `true` |
| `can_have_next` | `true` |
| `layer_group` | `kNodeLayer4` |
| `layer_group_prev_node` | `kNodeLayer4` |
| `layer_group_next_node` | `kNodeLayer4` |
| `required_padding_left` | `16` bytes |

حد انتظار upload در split برابر `131070 * max(1, ceil(L / 32768))` بایت است و فقط عبور از آن موجب بستن می‌شود. `L` مبنای مستقل بودجهٔ انتظار در pool مربوط به line است: ۶۴ KiB در S1/S2 و ۱ MiB در پروفایل‌های بالاتر. این مبنا از اندازهٔ buffer‌های عادی و سقف splice مستقل است. header و جفت‌شدن ابتدا پردازش می‌شوند؛ body همراه header جزو حد header نیست. گزینهٔ `no-split-upload-buffering-limit` همچنان این حد را غیرفعال می‌کند.
