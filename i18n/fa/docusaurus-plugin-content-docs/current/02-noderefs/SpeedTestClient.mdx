# SpeedTestClient

## نمای کلی {#overview}

`SpeedTestClient` یک تونل مصنوعی برای آزمون کارایی است که در ابتدای زنجیره قرار
می‌گیرد. این گره `line`های معمول WaterWall را می‌سازد، ترافیک قاب‌بندی‌شده speed-test را
به تونل بعدی می‌فرستد، قاب‌های برگشتی از `SpeedTestServer` را اعتبارسنجی می‌کند
و گزارش‌های دوره‌ای و نهایی نرخ گذردهی را چاپ می‌کند.

این گره برای اندازه‌گیری کارایی یک زنجیره یا مسیر انتقال در WaterWall است. خودش
سوکت باز نمی‌کند، پراکسی برنامه نیست و تونل مبتنی بر `line` بسته هم محسوب نمی‌شود.

## جایگاه معمول در زنجیره {#typical-placement}

<a id="جایگاه-رایج"></a>

`SpeedTestClient` باید نخستین گره زنجیره باشد؛ `line`های آزمایش را خودش تولید می‌کند و آن‌ها را در جهت `upstream` به پشتهٔ انتقال تنظیم‌شده می‌فرستد.

```text
SpeedTestClient -> TcpConnector
SpeedTestClient -> UdpConnector
SpeedTestClient -> TlsClient -> TcpConnector
SpeedTestClient -> EncryptionClient -> TcpConnector
```

سمت راه‌دور باید به `SpeedTestServer` متناظر ختم شود:

```text
TcpListener -> SpeedTestServer
UdpListener -> SpeedTestServer
TcpListener -> TlsServer -> SpeedTestServer
TcpListener -> EncryptionServer -> SpeedTestServer
```

### اندازه‌گیری مسیر جریان روی QUIC یا Mux {#measure-a-quic-or-multiplexed-stream-path}

<a id="اندازهگیری-مسیر-stream-روی-quic-یا-mux"></a>

```text
QUIC client: SpeedTestClient -> QuicClient -> UdpConnector
QUIC peer:   UdpListener -> QuicServer -> SpeedTestServer
Mux client:  SpeedTestClient -> MuxClient -> TcpConnector
Mux peer:    TcpListener -> MuxServer -> SpeedTestServer
```
در هر دو سناریو، روی `SpeedTestClient` مقدار `mode: "tcp"` را تنظیم کنید؛
`SpeedTestServer` حالت را از `HELLO` کلاینت می‌گیرد. رابط برنامه‌ی آزمون کارایی یک
جریان بایتی است، حتی وقتی حامل بیرونی QUIC از UDP استفاده می‌کند. برای QUIC، ALPN برابر، بررسی گواهی و `carrier-mode: "datagram"` لازم
است؛ [نمونه‌ی جفت QUIC](./QuicClient.mdx) را ببینید. در Mux، `connection-count` تعداد
اتصال منطقی آزمون کارایی را مشخص می‌کند که ممکن است حامل مشترک داشته باشند؛ این
عدد تعداد درخواستی سوکت‌های فیزیکی TCP نیست.

آرایه‌های گره در نمونه‌های TCP و UDP پایین، مسیرهای پایه هستند. هر آرایه را در
فیلد `nodes` یک پیکربندی گره بگذارید و فایل را از `core.json.configs` بارگذاری کنید.
برای مقایسه مسیرها، مدت، جهت، اندازه بار مفید و تعداد اتصال منطقی را
یکسان نگه دارید.

## نمونهٔ کاربردی ساده {#minimal-practical-example}

این‌ها قطعه‌های پیکربندی گره هستند؛ گره‌های همسایهٔ ارجاع‌شده را در پیکربندی پیرامونی تعریف کنید.

### نمونهٔ TCP {#tcp-example}

<a id="نمونه-tcp"></a>

سمت کلاینت:

```json
[
  {
    "name": "speedtest-client",
    "type": "SpeedTestClient",
    "settings": {
      "mode": "tcp",
      "direction": "bidirectional",
      "duration-ms": 10000,
      "warmup-ms": 1000,
      "report-interval-ms": 1000,
      "connection-count": 4,
      "payload-size": 131072,
      "terminate-on-complete": true
    },
    "next": "speedtest-out"
  },
  {
    "name": "speedtest-out",
    "type": "TcpConnector",
    "settings": {
      "address": "198.51.100.10",
      "port": 9000,
      "nodelay": true
    }
  }
]
```

سمت سرور:

```json
[
  {
    "name": "speedtest-listener",
    "type": "TcpListener",
    "settings": {
      "address": "0.0.0.0",
      "port": 9000,
      "nodelay": true
    },
    "next": "speedtest-server"
  },
  {
    "name": "speedtest-server",
    "type": "SpeedTestServer",
    "settings": {
      "report-interval-ms": 1000,
      "json-summary": true
    }
  }
]
```

## پیکربندی {#configuration}

### فیلدهای لازم {#required-fields}

<a id="فیلدهای-لازم"></a>

وجود `next` برای `SpeedTestClient` الزامی است. گره بعدی همان مسیری است که ترافیک آزمایشی تولیدشده را دریافت می‌کند.

`settings` در عمل اختیاری است و در صورت حذف یا خالی بودن، مقدارهای پیش‌فرض به کار می‌روند.
برای انتخاب حالت، مدت، جهت، اندازه بار مفید، تعداد جریان، نرخ ارسال زمان‌بندی‌شده یا قالب
خروجی مشخص، آن را اضافه کنید.

### تنظیمات اختیاری {#optional-settings}

<a id="تنظیمات-اختیاری"></a>

| فیلد | پیش‌فرض | توضیح |
| --- | --- | --- |
| `mode` | `tcp` | حالت قاب‌بندی. مقدارهای مجاز: `tcp`, `TCP`, `udp`, `UDP`. |
| `direction` | `upload` | جهت تست. مقدارهای مجاز: `upload`, `UPLOAD`, `send`, `download`, `DOWNLOAD`, `receive`, `bidirectional`, `both`, `BOTH`. |
| `duration-ms` | `10000` | مدت اندازه‌گیری پس از گرم‌کردن؛ باید مثبت باشد. |
| `warmup-ms` | `0` | مدت گرم‌کردن؛ باید منفی نباشد. قاب‌های گرم‌کردن ارسال و در صورت فعال بودن گزینه اعتبارسنجی می‌شوند، اما در مجموع بایت‌های اندازه‌گیری‌شده حساب نمی‌شوند. |
| `report-interval-ms` | `1000` | فاصله میان گزارش‌های دوره‌ای؛ باید مثبت باشد. |
| `start-delay-ms` | `50` | تأخیر آغاز هر جریان تولیدشده پس از راه‌اندازی تونل؛ باید منفی نباشد. |
| `timeout-ms` | `warmup-ms + duration-ms + 30000` | پایشگر مهلت زمانی هر جریان. باید در بازهٔ `1..INT_MAX` میلی‌ثانیه و بزرگ‌تر از `warmup-ms + duration-ms` باشد. اگر مقدار پیش‌فرض از این بازه بیشتر باشد، مهلت زمانی معتبری تعیین کنید یا مدت تست را کاهش دهید. |
| `connection-count` | `1` | تعداد `line`های معمول WaterWall که به‌صورت موازی ساخته می‌شوند؛ باید مثبت باشد. |
| `payload-size` | TCP: `131072`, UDP: `3800` | تعداد بایت داخل بار مفید قاب `DATA`، بدون سرآیند 48 بایتی speed-test. |
| `target-bits-per-sec` | TCP: `0` | تنظیم آهنگ ارسال اختیاری بر حسب بیت بر ثانیه. مقدار `0` یعنی تا جایی که backpressure اجازه دهد ارسال شود. |
| `udp-target-bits-per-sec` | UDP: `10000000` | تنظیم آهنگ ارسال مخصوص UDP بر حسب بیت بر ثانیه. |
| `target-megabits-per-sec` | تنظیم نشده | فرم جایگزین تنظیم آهنگ ارسال بر حسب مگابیت بر ثانیه. |
| `verify-payload` | `false` | تولید و بررسی بایت‌های قطعی بار مفید در هر دو سمت؛ برای تست صحت فعال شود. |
| `json-summary` | `false` | علاوه بر گزارش‌های معمول، یک خلاصه فشرده شبیه JSON چاپ می‌کند. |
| `terminate-on-complete` | `true` | پس از پایان همه جریان‌ها WaterWall را متوقف می‌کند؛ کد خروج در حالت موفق `0` و اگر هر یک از جریان‌ها شکست بخورد `1` است. |

تنها یکی از `target-bits-per-sec`، `udp-target-bits-per-sec` و `target-megabits-per-sec` را می‌توان هم‌زمان تنظیم کرد. نرخ پس از تبدیل به بیت بر ثانیه باید متناهی، غیرمنفی و کمتر از `2^64` باشد.

`payload-size` باید بین `1` و `16777216` باشد. در UDP حداکثر `64952` است، چون هر بار مفید UDP یک قاب کامل speed-test با
سرآیند 48 بایتی دارد.

### آمار {#statistics}

<a id="آمار"></a>

سمت گیرنده این آمار را نگه می‌دارد:

- تعداد بایت‌ها
- بسته‌ها
- بسته‌های معتبر
- بسته‌های ازدست‌رفته
- بسته‌های تکراری
- بسته‌های خارج از ترتیب
- خطاهای اعتبارسنجی
- برآورد jitter

با `verify-payload=true` بدنه‌ها از الگویی قطعی بر اساس شناسهٔ جریان، شمارهٔ توالی
و جهت استفاده می‌کنند. شمارش ترتیب بسته‌ها در حالت غیرفعال هم برقرار است.

در پایان، کلاینت گزارش‌های راه‌دور هر جریان را از سرور چاپ می‌کند و یک خلاصه نهایی تجمیعی می‌سازد. اگر
`json-summary: true` باشد، یک خط تجمیعی فشرده به سبک JSON هم چاپ می‌شود.

### اشتباه‌های رایج {#common-mistakes}

<a id="اشتباههای-رایج"></a>

- این گره را وسط زنجیره ترافیک واقعی قرار ندهید؛ سر زنجیره است و خودش `line` می‌سازد.
- بدون `SpeedTestServer` متناظر از آن استفاده نکنید.
- انتظار باز کردن سوکت مستقیم از آن نداشته باشید؛ پس از آن `TcpConnector`، `UdpConnector` یا پشتهٔ انتقال دیگری قرار دهید.
- بار مفید UDP خیلی بزرگ انتخاب نکنید مگر اینکه کل مسیر آن را بدون تکه‌تکه شدن یا از دست رفتن تحمل کند.

## رفتار پیشرفته {#advanced-behavior}

### جریان پروتکل {#protocol-flow}

<a id="جریان-protocol"></a>

هر جریان تولیدشده از این نوع قاب‌ها استفاده می‌کند:

| قاب | جهت | کاربرد |
| --- | --- | --- |
| `HELLO` | کلاینت به سرور | حالت، جهت، مدت، گرم‌کردن، فاصلهٔ گزارش‌دهی، اندازهٔ بار مفید، تنظیم آهنگ ارسال، سیاست اعتبارسنجی، تعداد جریان و شناسهٔ جریان را اعلام می‌کند. |
| `ACK` | سرور به کلاینت | تایید `HELLO`. در UDP کلاینت قبل از ارسال داده منتظر آن می‌ماند. |
| `DATA` | فرستنده به گیرنده | بدنه صفرشده یا الگوی اعتبارسنجی برای آپلود یا دانلود. |
| `END` | فرستنده به گیرنده | پایان یک جهت فرستنده. |
| `REPORT` | سرور به کلاینت | آمار نهایی فرستنده/گیرنده. |
| `ERROR` | سرور به کلاینت | خطای پروتکل. |

سرآیند هر قاب برابر 48 بایت است. `payload-size` فقط اندازه بار مفید در قاب نوع `DATA` را مشخص می‌کند و سرآیند را شامل نمی‌شود.

### رفتار TCP {#tcp-behavior}

<a id="رفتار-tcp"></a>

در حالت TCP، بایت‌های دریافتی در بافر جریان جمع و به قاب‌های speed-test
رمزگشایی می‌شوند. TCP به‌طور پیش‌فرض تنظیم آهنگ ارسال ندارد و تا جایی که زنجیره و رفتار معمول سوکت و فشار برگشتی (backpressure)
اجازه دهند ارسال می‌کند، مگر آن‌که پهنای باند هدف تنظیم شده باشد.

کلاینت پس از دریافت `downstream` `Est` از تونل بعدی شروع به ارسال می‌کند. با
رسیدن `callback`های `downstream` `Pause` و `Resume` نیز وظیفه ارسال خودش را متوقف یا
از سر می‌گیرد.

### رفتار UDP {#udp-behavior}

<a id="رفتار-udp"></a>

در حالت UDP، هر بافر بار مفید در WaterWall دقیقاً یک قاب کامل speed-test است.
کلاینت تا دریافت `ACK`، قاب نوع `HELLO` را دوباره می‌فرستد. فاصله تلاش مجدد برابر
مقدار کوچک‌تر میان `report-interval-ms` و 250 ms است. قاب نهایی `END` برای
آپلود نیز سه بار ارسال می‌شود تا احتمال جلوگیری از تکمیل آزمون بر اثر از دست رفتن یک دیتاگرام کمتر شود.

نرخ پیش‌فرض UDP برابر `udp-target-bits-per-sec: 10000000` است. این حالت از دست رفتن،
بسته‌های تکراری و خارج از ترتیب، خطاهای اعتبارسنجی و jitter را گزارش می‌کند.

### اعتبارسنجی بار مفید و splice {#payload-verification-and-splice}

<a id="اعتبارسنجی-payload-و-splice"></a>

تنظیم `verify-payload` در `SpeedTestClient` به‌صورت پیش‌فرض `false` است و سیاست هر دو سمت را از طریق پرچم‌های `HELLO` تعیین می‌کند. برای تولید و بررسی الگوی قطعی بار مفید، آن را روی `true` بگذارید. وقتی اعتبارسنجی غیرفعال است، فرستنده‌ها بدنه‌هایی مقداردهی‌شده و پر از صفر تولید می‌کنند و گیرنده‌ها طول آن‌ها را بدون بررسی بایت‌های بار مفید می‌شمارند. سرآیند قاب‌ها، طول‌ها، شناسه‌های جریان، حسابداری شمارهٔ توالی و گزارش‌های نهایی همچنان پردازش می‌شوند. در این حالت `valid_packets` و `validation_errors` مربوط به بار مفید صفر می‌مانند؛ خلاصه‌های JSON شامل `verification_enabled` هستند.

هر دو گره در زنجیره‌های TCP واجد شرایط و با `misc.splice=true` از splice پشتیبانی می‌کنند. گیرنده سرآیند 48 بایتی را در حافظهٔ موقت نگه می‌دارد، برای قاب‌های ناقص فوراً بازمی‌گردد و در Linux بدنه‌های `DATA` بدون اعتبارسنجی را از لوله‌های خصوصی آن‌ها به `/dev/null` تخلیه می‌کند، بدون آنکه بدنه را به فضای کاربر کپی کند. اگر مقصد تخلیه یا پشتیبانی splice در دسترس نباشد، از خواندن معمولی با حدود مشخص استفاده می‌شود. بدنه‌های کنترلی و بدنه‌های `DATA` نیازمند اعتبارسنجی در صورت نیاز به حافظهٔ عادی منتقل می‌شوند. UDP همچنان هر دیتاگرام را جداگانه پردازش می‌کند. خروجی تولیدشده در حافظهٔ عادی است؛ فعال‌کردن splice تولید بار مفید را بدون کپی نمی‌کند.

هر `line` فضای نگهداری قاب‌های ناقص را به `2 * (16 MiB + 48)` بایتِ محاسبه‌شده محدود می‌کند و پیش از رد فضای اضافی، فشرده‌سازی را انجام می‌دهد. این حد برای حسابداری صف است، نه کل حافظهٔ فرایند یا هسته. وظیفه‌های ارسال به `Pause` پایبندند و پس از حداکثر 32 قاب نوبت اجرا را واگذار می‌کنند؛ تنظیم آهنگ ارسال با وظیفه‌های زمان‌بندی‌شده انجام می‌شود، نه با خواب مسدودکننده.

## جزئیات پیاده‌سازی {#implementation-details}

### راه‌اندازی و مالکیت `line` {#startup-and-line-ownership}

<a id="startup-و-مالکیت-line"></a>

هنگام شروع تونل، کلاینت به تعداد `connection-count` یک وظیفهٔ راه‌اندازی برای هر جریان زمان‌بندی می‌کند. برای هر جریان:

1. worker را با `stream_id % workers_count` انتخاب می‌کند
2. یک `line_t` عادی می‌سازد
3. وضعیت `line` مربوط به `SpeedTestClient` را مقداردهی اولیه می‌کند
4. `Init` را در جهت `upstream` به تونل بعدی می‌فرستد
5. پایشگر مهلت زمانی مربوط به `timeout-ms` را فعال می‌کند

چون کلاینت این `line`ها را می‌سازد، از بین بردن آن‌ها نیز بر عهده خودش است. با کامل شدن یا شکست هر جریان، در صورت لزوم `upstream` `Finish` را می‌فرستد و سپس `line` خودش را از بین می‌برد.

### فرادادهٔ گره {#node-metadata}

<a id="متادیتای-نود"></a>

فرادادهٔ برگرفته از کد منبع:

| ویژگی | مقدار |
| --- | --- |
| پرچم‌های گره | `kNodeFlagChainHead` + `kNodeFlagSupportsSplice` |
| `can_have_prev` | `false` |
| `can_have_next` | `true` |
| `layer_group` | `kNodeLayer4` |
| `layer_group_prev_node` | `kNodeLayerNone` |
| `layer_group_next_node` | `kNodeLayer4` |
| `required_padding_left` | `0` بایت |
