# GnsClient

`GnsClient` هر stream برنامه را به‌شکل یک اتصال اصلی GameNetworkingSockets از
مسیر UDP عبور می‌دهد. `GnsServer` این اتصال‌ها را می‌پذیرد و برای هر کدام یک
stream جدا به سمت مقصد می‌سازد. قالب روی سیم همان پروتکل UDP کتابخانهٔ متن‌باز
GameNetworkingSockets از Valve است، بدون تغییر: پیام‌های reliable روی یک اتصال.

```text
Client: TcpListener -> GnsClient -> UdpConnector
                                 == one GNS connection per stream, over UDP ==>
Server: UdpListener -> GnsServer -> TcpConnector
```

هر دو node روی خط‌های لایهٔ ۴ کار می‌کنند. `GnsClient` یک byte stream قابل‌اعتماد
را از node قبلی می‌گیرد و دیتاگرام‌های GNS را به node بعدی می‌فرستد. مرز
payloadها حفظ نمی‌شود: در سمت مقابل همان بایت‌ها با همان ترتیب می‌رسند.

GameNetworkingSockets با نرخ تنظیم‌شده می‌فرستد و کنترل ازدحام ندارد. `send-rate`
را برای مسیر خودتان تنظیم کنید؛ پیش‌فرض حدود ۲ مگابیت بر ثانیه است.

## جایگاه در chain

- پیش از `GnsClient`: هر nodeای که byte stream تولید می‌کند، مثل `TcpListener`
  یا یک node پروتکل proxy.
- پس از `GnsClient`: مسیری که مرز دیتاگرام را نگه می‌دارد. در عمل یعنی
  `UdpConnector`، مستقیم یا پشت تونل‌هایی که دیتاگرام را بدون تغییر عبور می‌دهند.
- هر stream ورودی، خط حامل خودش را به سمت `next` و اتصال GNS خودش را می‌گیرد.
  streamها اتصال مشترک ندارند.
- سمت مقابل `GnsServer` است، یا هر برنامهٔ GameNetworkingSockets که با
  `CreateListenSocketIP` گوش کند، با پیش‌فرض‌های کتابخانه کار کند و پیام‌های
  reliable رد و بدل کند.

## پیکربندی

```json
{
  "name": "gns-client",
  "type": "GnsClient",
  "next": "udp-out",
  "settings": {
    "send-mtu": 1400,
    "send-rate": 4194304
  }
}
```

### فیلدهای سطح بالا

| فیلد | الزام |
| --- | --- |
| `name` | نام node؛ لازم و یکتا در کل پیکربندی. |
| `type` | دقیقاً `"GnsClient"`. |
| `next` | لازم؛ نام nodeای که دیتاگرام‌ها را حمل می‌کند. |
| `settings` | شیء اختیاری. همهٔ تنظیم‌ها پیش‌فرض دارند. |

### تنظیمات

تنظیم‌ها عدد صحیح‌اند. مقدار از نوع دیگر، عدد کسری، null یا عدد بیرون از محدوده
جلوی راه‌اندازی را می‌گیرد و پیام خطا نام همان تنظیم را می‌آورد.

| تنظیم | پیش‌فرض | رفتار |
| --- | --- | --- |
| `send-mtu` | `misc.mtu` هسته | بودجهٔ packet مبتنی بر IPv4 برای دیتاگرام‌های خروجی، از `228` تا `65535`. بخش [MTU ارسال](#send-mtu) را ببینید. |
| `send-rate` | `262144` | تعداد بایتی که یک اتصال در هر ثانیه می‌فرستد، از `1024` تا `104857600`. بخش [نرخ ارسال](#send-rate) را ببینید. |
| `no-recv-timeout-ms` | `30000` | مهلت زنده‌بودن `T`، از `1` تا `2147483647`. اتصال وقتی پایان می‌یابد که به مدت `T` چیزی از سمت مقابل نرسد، یا سمت مقابل به مدت `T` هیچ‌چیز از دادهٔ منتظر را تأیید نکند. |
| `timeout-initial-ms` | `10000` | مدتی که تلاش برای اتصال می‌تواند طول بکشد، از `1` تا `2147483647`. |
| `send-buffer-limit` | `524288` | تعداد بایت‌های پذیرفته‌شده و هنوز تأییدنشده که بالاتر از آن node قبلی Pause می‌شود، از `4096` تا `134217728`. مقدار بالاتر از نصف پنجرهٔ packet در GNS، که با `send-mtu` برابر `1328` یا بیشتر ۹٬۶۰۰٬۰۰۰ بایت است، با یک هشدار به همان مقدار کم می‌شود. |
| `receive-buffer-limit` | `1048576` | حدِ دادهٔ دریافتی‌ای که پشت یک packet گم‌شده منتظر می‌ماند، از `131072` تا `268435456`. بزرگ‌ترین پیام پذیرفتنی GNS نصف این مقدار است. |
| `carrier-queue-limit` | `256` | تعداد دیتاگرام‌هایی که می‌توانند منتظر node بعدی بمانند، از `1` تا `65535`. |
| `close-drain-timeout-ms` | `30000` | مدتی که اتصالِ در حال بسته‌شدن برای تأیید بایت‌های باقی‌مانده از سمت مقابل صبر می‌کند، از `1` تا `2147483647`. |

هر سمت مقدارهای خودش را به کار می‌برد؛ چیزی مذاکره نمی‌شود. `send-rate` نرخ
فرستادنِ همین سمت است؛ پس دو جهتِ یک اتصال می‌توانند نرخ‌های متفاوت داشته باشند.

## MTU ارسال {#send-mtu}

`send-mtu` یک بودجهٔ packet مبتنی بر IPv4 است، با همان معنایی که در `KcpClient`
دارد. حد دیتاگرام GNS این است:

```text
GNS packet size = min(send-mtu - 28, 1300)
```

این ۲۸ بایت headerهای IPv4 و UDP هستند و ۱۳۰۰ بیشینهٔ پروتکل GNS است. با
پیش‌فرض `1500` هسته، این حد ۱۳۰۰ بایت می‌شود. بودجهٔ بالاتر از `1328` معتبر است و
همان ۱۳۰۰ را به کار می‌برد. بودجهٔ کمتر از `228` جلوی راه‌اندازی را می‌گیرد، چه در
خود node نوشته شده باشد و چه از `misc.mtu` هسته به ارث رسیده باشد؛ چون کوچک‌ترین
اندازهٔ packet در GNS برابر ۲۰۰ بایت است.

هر سمت فقط آنچه را خودش می‌فرستد محدود می‌کند. دریافت به بودجهٔ محلی وابسته
نیست: دیتاگرام تا ۱۳۰۰ بایت پذیرفته می‌شود. اولین packet هر تلاش برای اتصال، با
هر بودجه‌ای، ۵۱۲ بایت است.

این کار کشف MTU مسیر نیست. header در IPv6 بیست بایت بیشتر از سهم ثابت IPv4 جا
می‌خواهد و تونل‌های بعد از این node هم بایت‌های خودشان را اضافه می‌کنند. برای
آن‌ها `send-mtu` را کمتر بگذارید.

## نرخ ارسال {#send-rate}

GNS هر وقت داده داشته باشد با `send-rate` می‌فرستد و با گم‌شدن packetها کندتر
نمی‌شود. این نرخ برای هر اتصال و هر جهت جداست.

- **زیر ظرفیت مسیر، اتصال همان نرخ را حمل می‌کند.** بین دو میزبان با رفت‌وبرگشت
  ۴۴ میلی‌ثانیه، یک اتصال با نرخ پیش‌فرض ۲٫۰ مگابیت بر ثانیه، با `1048576` برابر
  ۸٫۰، با `4194304` برابر ۳۰٫۸ و با بافرهای بزرگ‌تر، با `16777216` برابر ۱۲۹٫۵
  مگابیت بر ثانیه حمل کرد. این ۹۲ تا ۹۷٪ نرخ تنظیم‌شده است؛ باقی را headerهای
  packet می‌گیرند. با `33554432` همان اتصال ۲۰۹ تا ۲۲۸ مگابیت بر ثانیه حمل کرد،
  یعنی حدود ۸۰٪ نرخ.
- **حدهای بافر را همراه نرخ بالا ببرید.** node قبلی در `send-buffer-limit` Pause
  می‌شود؛ پس این حد باید برای داده‌ای که در یک رفت‌وبرگشت در راه است جا داشته
  باشد. در همان مسیر، `8388608` با حدهای پیش‌فرض ۴۱، با `send-buffer-limit` برابر
  ۱ مبی‌بایت ۶۲ و با ۲ مبی‌بایت ۶۵ مگابیت بر ثانیه حمل کرد؛ `16777216` با پیش‌فرض،
  ۲ مبی‌بایت و ۴ مبی‌بایت به‌ترتیب ۴۷، ۱۲۳ و ۱۳۰ مگابیت بر ثانیه. آنجا به اندازهٔ
  یک‌چهارم ثانیه از `send-rate` کافی بود. `receive-buffer-limit` را در سمت مقابل
  دو برابر آن بگذارید.
- **GNS برای مسیرِ پُر کند نمی‌شود.** هرچه جا نشود در راه دور ریخته می‌شود و با
  همان نرخ دوباره فرستاده می‌شود. از یک گلوگاه ۲۰ مگابیت بر ثانیه‌ای، اتصالی با
  نرخ ۱۶٫۸ مگابیت بر ثانیه ۱۶٫۲ حمل کرد، و اتصال‌هایی با نرخ ۳۳٫۶ و ۶۷٫۱ مگابیت بر
  ثانیه ۱۴٫۸ و ۱۷٫۳ حمل کردند، در حالی که گلوگاه مازاد را دور می‌ریخت. نرخِ بالاتر
  از ظرفیت چیزی اضافه نمی‌کند و مسیر را از ترافیک دیگر می‌گیرد. نرخ را برابر یا
  کمتر از ظرفیت مسیر بگذارید.
- **loss اینجا گران‌تر از پروتکلی است که خودش را تطبیق می‌دهد.** پس از یک packet
  گم‌شده، GNS فقط `receive-buffer-limit` بایت را جلوتر از جای خالی نگه می‌دارد و
  فرستنده آنچه جا نشده را تکرار می‌کند. روی لینک شبیه‌سازی‌شده با رفت‌وبرگشت ۱۰۰
  میلی‌ثانیه و ۱٪ loss، نرخ ۱۰ مگابایت بر ثانیه با `receive-buffer-limit` پیش‌فرض
  ۳٫۷ تا ۴٫۷ و با ۱۶ مبی‌بایت ۸٫۸ مگابایت بر ثانیه حمل کرد.
- **نرخ برای هر اتصال است.** چهار stream هم‌زمان با `4194304` روی هم ۱۲۳ مگابیت
  بر ثانیه حمل کردند، و یک stream که `ConnectionStripeClient` آن را روی هشت اتصال
  با `2097152` پخش کرده بود ۱۲۹ مگابیت بر ثانیه حمل کرد.

برای مقایسه، در همان مسیر یک اتصال `EnetClient` برابر ۱۳ و یک اتصال `KcpClient`
برابر ۵۱ تا ۶۷ مگابیت بر ثانیه حمل کرد.

## دیگر محدودیت‌های ذاتی

این محدودیت‌ها از خود کتابخانهٔ GameNetworkingSockets می‌آیند و بدون کنار گذاشتن
سازگاری با GNS اصلی برداشته نمی‌شوند.

- **اولین packet بیشترش صفر است.** تلاش برای اتصال با یک دیتاگرام ۵۱۲ بایتی شروع
  می‌شود که حدود بیست بایت محتوا دارد و بقیه‌اش صفر است. بعضی شبکه‌ها چنین
  دیتاگرام‌هایی را دور می‌ریزند؛ در مسیرِ اندازه‌گیری‌های بالا این packet هرگز
  نرسید و هیچ اتصالی باز نشد. nodeای که بایت‌های روی سیم را عوض کند از چنین مسیری
  رد می‌شود: با `ObfuscatorClient` پس از `GnsClient` و `ObfuscatorServer` پیش از
  `GnsServer`، همان مسیر همهٔ عددهای این صفحه را حمل کرد.
  [نمونهٔ obfuscated](https://github.com/radkesvat/WaterWall/tree/main/tunnels/GnsClient/examples/obfuscated)
  را ببینید.
- **داده رمز می‌شود، ولی طرف‌ها احراز هویت نمی‌شوند.** GNS هر packet داده را با
  AES-256-GCM رمز می‌کند و کلیدها را از یک تبادل Curve25519 می‌گیرد. کتابخانهٔ
  متن‌باز مرجع صدور گواهی ندارد؛ پس این کار محتوا را از ناظر پنهان می‌کند ولی
  ثابت نمی‌کند سمت مقابل کیست. اگر این لازم است، nodeهای امنیتی را در سمت stream
  بگذارید: پیش از `GnsClient` و پس از `GnsServer`.
- **یک قفل برای کل پردازه.** GNS همهٔ دیتاگرام‌های همهٔ اتصال‌ها را زیر یک قفل
  پردازش می‌کند و یک thread سرویس دارد. همهٔ اتصال‌های GNS یک پردازه، با هر تعداد
  worker، همین ظرفیت را شریک‌اند. یک اتصال که ۲۶۵ مگابیت بر ثانیه دریافت می‌کرد
  کمی بیش از یک هسته مصرف کرد.
- **یک پردازه حدود ۶۵٬۰۰۰ اتصال GNS نگه می‌دارد،** با شمردن اتصال‌هایی که در پنج
  ثانیهٔ اخیر بسته شده‌اند.
- **حداکثر ۱۶٬۰۰۰ packet می‌تواند منتظر تأیید بماند.** GNS packetها را با ۱۶ بیت
  شماره می‌زند. برای همین node هرگز نمی‌گذارد روی یک اتصال بیش از بایت‌های ۱۶٬۰۰۰
  packet و بیش از ۸٬۱۹۲ پیام منتظر بماند، `send-buffer-limit` هرچه باشد؛ و اتصالی
  را که رفت‌وبرگشتش با نرخ فعلی بیش از این تعداد packet را در خود جا می‌دهد تمام
  می‌کند.
- **اعلام بسته‌شدن فقط یک بار فرستاده می‌شود.** سمتی که آن را از دست بدهد و خودش
  هم چیزی نفرستد، پایان اتصال را فقط با مهلت زنده‌بودن خودش می‌فهمد.
- **قطع‌شدن سمت مقابل از نبودِ پاسخ‌ها فهمیده می‌شود.** اتصال به اندازهٔ
  `no-recv-timeout-ms` پس از اولین packet بی‌پاسخ پایان می‌یابد، و اتصال بی‌کار هر
  ده ثانیه چنین packetی می‌فرستد. با پیش‌فرض‌ها، سمتِ متوقف‌شدهٔ یک اتصال بی‌کار
  ۳۹ ثانیه پس از توقف تشخیص داده شد.
- **اتصال به حامل خودش بسته است.** اگر نشانی مبدأ UDP در client عوض شود، server
  یک حامل تازه می‌بیند و اتصال قبلی timeout می‌شود.

## کنترل جریان و حافظه

- تا وقتی بیش از `send-buffer-limit` بایت پذیرفته شده و هنوز از سمت مقابل تأیید
  نشده باشد، node قبلی Pause می‌ماند و وقتی به نصف آن یا کمتر برسد Resume
  می‌شود. Pause از node بعدی هم node قبلی را Pause می‌کند؛ هر کدام از این دو علت
  به‌تنهایی آن را در Pause نگه می‌دارد. GNS با هر پیام یک تا سه بایت قاب‌بندی هم
  می‌شمارد؛ پس Pause کمی پیش از این حد می‌آید.
- payloadی که هنگام معوق‌بودنِ بیش از دو برابر `send-buffer-limit` بایت برسد
  پذیرفته نمی‌شود و همان اتصال بسته می‌شود. node قبلی‌ای که Pause را رعایت کند به
  این حالت نمی‌رسد.
- وقتی node قبلی جهت downstream را Pause می‌کند، `GnsClient` نیز node بعدی را
  Pause می‌کند و دریافت دیتاگرام متوقف می‌شود. این کار تأییدها را هم متوقف می‌کند:
  Pause طولانی‌تر از مهلت زنده‌بودن می‌تواند اتصال را تمام کند.
- در `receive-buffer-limit`، GNS داده‌ای را که جلوتر از یک packet گم‌شده رسیده
  نمی‌پذیرد و سمت مقابل آن را دوباره می‌فرستد. بایت‌های تأییدشده هرگز دور ریخته
  نمی‌شوند و هر اتصال کمتر از دو برابر این حد نگه می‌دارد. پیام دریافتی GNS که از
  نصف این حد بزرگ‌تر باشد اتصال را تمام می‌کند.
- اگر بیش از `carrier-queue-limit` دیتاگرام منتظر node بعدی باشد، دیتاگرام تازه
  پذیرفته نمی‌شود. GNS دادهٔ آن را نگه می‌دارد و لحظه‌ای بعد دوباره عرضه می‌کند.
  اتصال باز می‌ماند.

## رفتار Close و timeout

- وقتی node قبلی stream را Finish می‌کند، `GnsClient` دیگر بایتی نمی‌پذیرد،
  می‌گذارد GNS همهٔ بایت‌های قبلاً پذیرفته‌شده را برساند و سپس اتصال را به روش خود
  GNS می‌بندد. اتصال برای این کار، پس از رفتن خط برنامه، خط حامل خودش را نگه
  می‌دارد، و یک ثانیه پس از بستن هم؛ تا اعلام بسته‌شدن و پاسخ به packetهای
  دیررسیده رد شوند. بایت‌هایی که پس از آن Finish از سمت مقابل برسند دور ریخته
  می‌شوند: Finish هر دو جهت stream را می‌بندد.
- به اندازهٔ `close-drain-timeout-ms` پس از آن Finish، دیگر node صبر نمی‌کند،
  اعلام بسته‌شدن را می‌فرستد و می‌بندد، و هشداری با تعداد بایت‌های تأییدنشده ثبت
  می‌کند.
- وقتی سمت مقابل می‌بندد، بایت‌هایی که پیش از بستن رسیده‌اند اول تحویل می‌شوند و
  سپس node قبلی Finish می‌گیرد. بایت‌هایی که هنوز در این سمت فرستاده نشده بودند
  دور ریخته می‌شوند؛ GNS half-close ندارد.
- وقتی node بعدی حامل را Finish می‌کند، اتصال همان لحظه تمام می‌شود و node قبلی
  Finish می‌گیرد.
- تلاش برای اتصالی که پاسخی نگیرد پس از `timeout-initial-ms` پایان می‌یابد. تا آن
  موقع GNS اولین packet خود را هر نیم ثانیه تکرار می‌کند.
- هنگام خاموش‌شدن، همهٔ اتصال‌ها بدون انتظار برای تخلیه تمام می‌شوند.

| stream باز می‌شود ولی داده‌ای نمی‌رسد و پس از ۱۰ ثانیه بسته می‌شود | آماده‌بودن حامل فقط یعنی سوکت UDP وجود دارد. تلاش برای اتصال در `timeout-initial-ms` پاسخی نگرفته است. بررسی کنید دیتاگرام‌ها به یک `GnsServer` برسند و پاسخ‌ها برگردند. اگر دیتاگرام‌های کوچک می‌رسند ولی اولین packet خودِ GNS نمی‌رسد، مسیر دیتاگرام‌هایی را که بیشترشان صفر است دور می‌ریزد: `ObfuscatorClient` و `ObfuscatorServer` را دو طرف مسیر UDP بگذارید. |
| انتقال‌ها کندند، با اینکه لینک ظرفیت دارد | محدودیت همان `send-rate` است. پیش‌فرض ۲۶۲۱۴۴ بایت بر ثانیه است. آن را در سمتی که می‌فرستد بالا ببرید و همراهش `send-buffer-limit` را در همان سمت و `receive-buffer-limit` را در سمت مقابل. |
| بالا بردن `send-rate` انتقال را سریع‌تر نمی‌کند | یا `send-buffer-limit` جلوی فرستنده را می‌گیرد، یا نرخ از ظرفیت مسیر بیشتر است و GNS packetهای دورریخته را تکرار می‌کند. حدها را همراه نرخ بالا ببرید و نرخ را برابر یا کمتر از ظرفیت مسیر نگه دارید. |
| راه‌اندازی شکست می‌خورد و نام `send-mtu` را می‌آورد، با اینکه node آن را تنظیم نکرده | `misc.mtu` هسته کمتر از `228` است. `send-mtu` را در خود node بگذارید. |
| خط لاگ `the send limit refused a payload` | node قبلی پس از Pause به فرستادن ادامه داده است. nodeهای پیش از `GnsClient` را بررسی کنید یا `send-buffer-limit` را بالا ببرید. |
| خط لاگ `close delivery unconfirmed at the fixed deadline` | سمت مقابل بایت‌های آخر را در `close-drain-timeout-ms` تأیید نکرده است. loss مسیر را بررسی کنید یا برای مسیرهای کند این مهلت را بیشتر کنید. |
| خط لاگ سطح debug با متن `the peer acknowledged nothing for no-recv-timeout-ms` | packetهای سمت مقابل می‌رسند، ولی او هیچ‌کدام از packetهای این سمت را تأیید نمی‌کند. جهتِ این node به سمت مقابل را بررسی کنید. |

## متادیتای نود

مقدارهای برگرفته از `instance/node.c`:

| ویژگی | مقدار |
| --- | --- |
| node flags | `kNodeFlagBlocksSplice` |
| `can_have_prev` | `true` |
| `can_have_next` | `true` |
| `layer_group` | `kNodeLayer4` |
| `layer_group_prev_node` | `kNodeLayer4` |
| `layer_group_next_node` | `kNodeLayer4` |
| `required_padding_left` | `0` بایت |

Splice برای chainهایی که این node را دارند خاموش است. هر دیتاگرام در یک buffer
تازه ساخته می‌شود؛ برای همین padding سمت چپ رزرو نمی‌شود.

پیکربندی‌های قابل‌اجرا برای جفت ساده، برای مسیری که اولین packet خودِ GNS را دور
می‌ریزد و برای «یک stream روی چند اتصال GNS» در
[نمونه‌های GNS](https://github.com/radkesvat/WaterWall/tree/main/tunnels/GnsClient/examples)
هستند.
