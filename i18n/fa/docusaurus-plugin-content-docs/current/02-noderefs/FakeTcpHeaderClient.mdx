# گره FakeTcpHeaderClient {#faketcpheaderclient-node}

## نمای کلی {#overview}

`FakeTcpHeaderClient` یک هدر اضافی شبیه TCP به بستهٔ IPv4 موجود اضافه می‌کند. همتای آن، [FakeTcpHeaderServer](./FakeTcpHeaderServer.mdx)، این هدر و بایت پروتکل را برمی‌دارد تا ترافیک اصلی IPv4 بازیابی شود. پاسخ مسیر معکوس را طی می‌کند: سرور هر دو را اضافه می‌کند و کلاینت آن‌ها را برمی‌دارد. هدر IPv4 موجود دوباره استفاده می‌شود؛ بنابراین دقیقاً یک هدر IPv4 وجود دارد.

در این صفحه **بومی** به بستهٔ اصلی یا payload اصلی IP گفته می‌شود. **حامل** بسته‌ای است که هدر TCP جعلی و بایت پروتکل به آن اضافه شده‌اند. کدگذاری این قالب را اضافه و رمزگشایی آن را حذف می‌کند.

لایهٔ TCP جعلی اتصال TCP برقرار نمی‌کند، نشست TCP را دنبال نمی‌کند و بسته‌های ازدست‌رفته را دوباره نمی‌فرستد. به‌طور پیش‌فرض هر پورت کلاینت از یک شمارهٔ توالی تصادفی مستقل شروع می‌کند و سپس با شمارندهٔ خود به اندازهٔ payload جعلی TCP پیش می‌رود. acknowledgment آن به‌طور پیش‌فرض صفر ثابت است؛ حالت‌های اختیاری مقدار تصادفی به ازای گره، پورت یا بسته انتخاب می‌کنند. ترافیک اصلی TCP همچنان رفتار واقعی TCP خود را دارد؛ UDP اصلی از این طریق تحویل قابل‌اعتماد TCP به دست نمی‌آورد.

گره فقط بسته‌ها را تبدیل می‌کند. آدرس‌های IP را انتخاب یا آدرس‌های اصلی را ذخیره نمی‌کند. پیکربندی زنجیره، از جمله `IpOverrider`، آدرس‌های عمومی را تعیین و آدرس‌های مورد انتظار پشتهٔ دریافت‌کننده را بازیابی می‌کند.

| رویداد | عمل |
| --- | --- |
| بستهٔ IPv4 بومی در upstream | TCP جعلی از `first client port + i` به `server-port` و بایت پروتکل را درج و به upstream ارسال می‌کند. |
| حامل در downstream | TCP جعلی و بایت پروتکل را اعتبارسنجی و حذف و بستهٔ بومی را به downstream ارسال می‌کند. |
| بستهٔ ردشده | آن را روی worker مربوط بازیافت و پیام تشخیصی با محدودیت نرخ ثبت می‌کند. |

## جایگاه معمول در زنجیره {#typical-placement}

### ترتیب زنجیره {#chain-order}

```text
client: UdpListener -> ConnectionToPackets -> FakeTcpHeaderClient -> IpOverrider -> RawSocket
        TunDevice   -> FakeTcpHeaderClient -> IpOverrider -> RawSocket

server: RawSocket -> IpOverrider -> FakeTcpHeaderServer -> PacketsToConnection -> UdpConnector
        RawSocket -> IpOverrider -> FakeTcpHeaderServer -> TunDevice
```

درخواست‌ها در هر دو زنجیره upstream و پاسخ‌ها downstream حرکت می‌کنند. هر دو همسایه باید گره‌های بستهٔ لایهٔ 3 باشند. از `ConnectionToPackets` برای تبدیل اتصال‌های عادی به بسته‌های بومی استفاده کنید؛ این گره را مستقیماً به listener یا connector مربوط به UDP وصل نکنید.

زنجیره‌های listener/connector نشان‌داده‌شده به‌دلیل نقاط انتهایی خود UDP حمل می‌کنند. برای TCP بومی از listener/connectorهای TCP با همان پل‌های بسته استفاده کنید. `ConnectionToPackets` (CTP) و `PacketsToConnection` (PTC) فقط TCP/UDP را پشتیبانی می‌کنند؛ برای ICMP یا پروتکل‌های opaque در هر دو سر از مسیرهای بستهٔ مناسب مانند TUN استفاده کنید. upstream به‌سمت گره بعد و downstream به‌سمت گره قبلی است؛ نام کلاینت/سرور این جهت‌ها را معکوس نمی‌کند.

## نمونهٔ کاربردی ساده {#minimal-practical-example}

این یک قطعهٔ گره است؛ همسایگان و همتاهای ارجاع‌شده را در همان استقرار تعریف کنید.

تنظیمات پورت همسان را روی FakeTcpHeaderServer استفاده کنید و `carrier-addresses` را برای آدرس‌دهی و خروجی حامل تعریف کنید. این کار فقط قالبی شبیه TCP اضافه می‌کند و تحویل قابل‌اعتماد TCP فراهم نمی‌کند. بازیابی آدرس، انتخاب capture و بودجه‌بندی MTU همچنان لازم‌اند؛ ترتیب زنجیره و MTU و اعتبارسنجی را در ادامه ببینید.

```json
{
  "name": "fake-tcp-header",
  "type": "FakeTcpHeaderClient",
  "settings": {
    "server-port": 40000,
    "client-port-range": [
      40001,
      40016
    ]
  },
  "next": "carrier-addresses"
}
```

برای پیش‌فرض‌ها و شرایط لازم، [پیکربندی](#configuration) و برای نمونه‌های کامل و محدودیت‌های عملیاتی، [کاربرد و رفع اشکال](#usage-and-troubleshooting) را ببینید.

## پیکربندی {#configuration}

### تنظیمات هدر {#header-settings}

هر دو گره کلیدهای یکسانی را می‌پذیرند. حذف `settings` یا استفاده از `{}` همهٔ مقادیر پیش‌فرض را انتخاب می‌کند؛ نیازی به تنظیم پروتکل بومی نیست.

| تنظیم | پیش‌فرض | معنا |
| --- | --- | --- |
| `password` | تنظیم‌نشده | رمز مشترک اختیاری و غیرخالی؛ یک گره کمکی داخلی Encryption در حالت بسته ایجاد می‌کند. [رمزگذاری اختیاری payload](#optional-payload-encryption) را ببینید. |
| `server-port` | `40000` | پورت سرور TCP جعلی. عدد صحیح در بازهٔ `1..65535`. |
| `client-port` | تنظیم‌نشده | دقیقاً از یک پورت کلاینت TCP جعلی استفاده می‌کند. عدد صحیح در بازهٔ `1..65535`؛ استفادهٔ هم‌زمان با `client-port-range` مجاز نیست. |
| `client-port-range` | اگر هیچ‌یک از دو تنظیم کلاینت ارائه نشده باشد، `[40001, 40016]` | بازهٔ شامل دو سر `[first, last]` از پورت‌های صحیح `1..65535`، به ترتیب صعودی و شامل `1..1024` پورت. |
| `increment-sequence` | `true` | شمارهٔ توالی پورت انتخاب‌شده را به اندازهٔ طول payload جعلی TCP، به‌علاوهٔ یک واحد برای هر بیت SYN یا FIN انتخاب‌شده، افزایش می‌دهد. فقط مقدار بولی می‌پذیرد. برای استفاده از شمارهٔ توالی ثابت، `false` تنظیم کنید. |
| `sequence` | `"random_port"` | مقدار شروع: یک عدد صحیح در بازهٔ `0..4294967295`، مقدار `"random_node"` برای یک شروع تصادفی مشترک میان همهٔ پورت‌های کلاینت، یا `"random_port"` برای شروع تصادفی مستقل هر پورت. [پیشروی شمارهٔ توالی](#sequence-progression) را ببینید. |
| `acknowledgment` | `0` | یک عدد صحیح در بازهٔ `0..4294967295`، یا `"random_node"`، `"random_port"` یا `"random_packet"`. هرگز از بسته‌های دریافتی مشتق نمی‌شود. [حالت‌های acknowledgment](#acknowledgment-modes) را ببینید. |
| `increment-acknowledgment` | `false` | ACK پورت انتخاب‌شدهٔ کلاینت را برای هر بسته‌ای که با موفقیت کدگذاری می‌شود یک واحد افزایش می‌دهد. فقط مقدار بولی می‌پذیرد؛ با `"acknowledgment": "random_packet"` ناسازگار است. |
| `flags` | `[{"ack": true, "psh": true}]` | دنبالهٔ مرتب‌شده‌ای از `1..32` شیء پرچم که برای هر پورت کلاینت جداگانه دنبال می‌شود؛ آخرین مدخل را تکرار می‌کند. [دنبالهٔ پرچم‌های خروجی](#outgoing-flag-script) را ببینید. |
| `window` | `65535` | پنجرهٔ TCP جعلی. عدد صحیح در بازهٔ `0..65535`. |
| `urgent-pointer` | `0` | اشاره‌گر فوری TCP جعلی. عدد صحیح در بازهٔ `0..65535`. |
| `options` | `""` | گزینه‌های هگزادسیمال TCP جعلی، از `0..40` بایت و در مضرب‌های 4 بایت، که عیناً صادر می‌شوند. هر padding مربوط به NOP/EOL را نیز وارد کنید. |

`"client-port": 40001` فقط از پورت 40001 استفاده می‌کند. `"client-port-range": [40001, 40016]` از هر 16 پورت 40001 تا 40016، شامل هر دو سر بازه، استفاده می‌کند. بازه‌ای مانند `[40001, 40001]` نیز دقیقاً یک پورت را انتخاب می‌کند. `client-port` یک عدد صحیح می‌پذیرد، نه آرایه؛ `client-port-range` دقیقاً دو عدد صحیح می‌پذیرد، نه فهرستی از پورت‌های جداگانه. ارائهٔ هر دو کلید نامعتبر است. اگر هیچ‌یک ارائه نشود، بازهٔ کلاینت `40001..40016` است. `server-port` باید خارج از پورت‌های انتخاب‌شدهٔ کلاینت باشد، از جمله زمانی که بازهٔ پیش‌فرض استفاده می‌شود.

کلیدهای ناشناخته، از جمله `payload-protocol` و `client-port-count`، نوع‌های نادرست، مقادیر کسری و مقادیر قالب خارج از بازه باعث شکست ایجاد می‌شوند و پیام تشخیصی نام کلید را ذکر می‌کند؛ برای مثال `FakeTcpHeaderClient->settings->server-port`. مقدار `settings` که شیء نباشد نامعتبر است. گزینه‌های هگزادسیمال نامعتبر، طول فرد رشتهٔ hex، طول‌هایی که مضرب چهار بایت نیستند و طول‌های بیش از 40 بایت رد می‌شوند. در اینجا هیچ تنظیمی برای آدرس، MTU یا پروتکل جایگزین حامل وجود ندارد.

هر دو همتا باید دربارهٔ `server-port` و پورت یا بازهٔ انتخاب‌شدهٔ کلاینت توافق داشته باشند. تنظیمات sequence و ACK، دنبالهٔ پرچم‌ها، window، urgent pointer و گزینه‌های آن‌ها می‌توانند متفاوت باشند. سمت دریافت data offset و بایت پروتکل ورودی را می‌خواند؛ این فیلدها یا پرچم‌ها را با مقادیر خروجی خود مقایسه نمی‌کند.

همهٔ تنظیمات پورت و قالب TCP در این جدول **هدر جعلی** را توصیف می‌کنند. برای مثال، ترافیک بومی UDP برای پورت 5300 می‌تواند در شبکه از پورت مقصد TCP جعلی 40000 استفاده کند. پورت اصلی UDP در هدر اصلی UDP باقی می‌ماند؛ تنظیم `server-port` پورت مقصد برنامه را تغییر نمی‌دهد.

### رمزگذاری اختیاری payload {#optional-payload-encryption}

برای رمزگذاری بایت پروتکل و payload کامل IP اصلی، مقدار `password` یکسان و غیرخالی را روی هر دو همتای FakeTcpHeader تنظیم کنید. از یک رمز مشترک طولانی و تصادفی استفاده کنید. حذف `password` قالب حامل بدون رمزگذاری را که در بخش‌های دیگر این صفحه نشان داده شده حفظ می‌کند. رشتهٔ خالی، `null` و هر مقدار غیررشته‌ای نامعتبر است.

```json
{
  "password": "replace-with-a-long-random-shared-secret",
  "client-port-range": [40001, 40016],
  "server-port": 40000
}
```

لازم نیست گره دیگری به زنجیرهٔ JSON اضافه کنید. هنگام ساخت، کلاینت یک `EncryptionClient` خصوصی بلافاصله پس از خود و سرور یک `EncryptionServer` خصوصی بلافاصله پیش از خود اضافه می‌کند. هر دو از `packet-mode: true` و `algorithm: "xchacha20-poly1305"` با salt و تعداد تکرار KDF پیش‌فرض گره‌های Encryption استفاده می‌کنند. زنجیره‌های گسترش‌یافته:

```text
client: ... -> FakeTcpHeaderClient -> internal EncryptionClient -> IpOverrider -> RawSocket
server: RawSocket -> IpOverrider -> internal EncryptionServer -> FakeTcpHeaderServer -> ...
```

هر بستهٔ خروجی به این شکل درمی‌آید:

```text
[IPv4][fake TCP + options][24-byte nonce][encrypted protocol byte + native IP payload][16-byte tag]
```

هیچ هدر رکوردی مشابه TLS وجود ندارد. هدر IPv4 و هدر TCP جعلی قابل‌مشاهده برای مسیریابی و بازنویسی آدرس در دسترس می‌مانند؛ هدر اصلی UDP/TCP داخل متن رمزگذاری‌شده است. دریافت‌کننده ابتدا اصالت بسته را بررسی و آن را رمزگشایی می‌کند، سپس FakeTcpHeader پروتکل اصلی و نمایش checksum را بازمی‌گرداند. درخواست‌ها و پاسخ‌ها از کلیدهای مشتق‌شدهٔ جداگانه استفاده می‌کنند. هر بسته یک nonce تصادفی مستقل دارد، بنابراین از دست رفتن بسته‌ها و تغییر ترتیب آن‌ها مانع رمزگشایی بسته‌های بعدی نمی‌شود. رمز نادرست و متن رمزگذاری‌شدهٔ دست‌کاری‌شده باعث حذف بسته می‌شوند، نه بسته‌شدن line بسته. این قابلیت محافظت در برابر بازپخش یا تحویل قابل‌اعتماد اضافه نمی‌کند.

گره کمکی **40 بایت** اضافه می‌کند. FakeTcpHeader این بایت‌ها را در رزرو شماره‌های توالی خروجی و محدودیت 1500 بایتی حامل نهایی لحاظ می‌کند. برای مثال، یک payload صدبایتی TCP جعلی به 140 بایت تبدیل می‌شود؛ بنابراین یک شمارهٔ توالی افزایشی که از 5000 شروع شود تا 5139 رزرو می‌کند و شمارهٔ بعدی از 5140 شروع می‌شود. SYN/FIN همچنان جایگاه‌های معمول خود را در توالی اضافه می‌کنند. غیرفعال‌کردن افزایش شمارهٔ توالی همچنان شمارهٔ انتخاب‌شده را ثابت نگه می‌دارد؛ رفتار ACK تغییر نمی‌کند. رمزگذاری هیچ‌یک از این دو فیلد را تغییر نمی‌دهد.

بدون گزینه‌های TCP جعلی، حداکثر اندازهٔ بستهٔ بومی IPv4 برابر **1439 بایت** است (1411 بایت برای برنامه، با فرض هدر 20 بایتی IPv4 به‌علاوهٔ UDP). با چهار بایت گزینه این مقدار 1435 و با چهل بایت گزینه 1399 است. MTU مربوط به TUN یا پل بسته را متناسب با بیشترین سربار هر دو همتا تنظیم کنید. فقط سربار این گره کمکی که به‌طور خودکار ایجاد می‌شود لحاظ شده است؛ تبدیل‌های اضافی که دستی پیکربندی می‌شوند به برنامه‌ریزی جداگانه برای اندازه و توالی نیاز دارند.

همچنین یک گره Encryption را بلافاصله بیرون از این گره کمکی پیکربندی نکنید: ترکیب‌های `FakeTcpHeaderClient -> Encryption...` یا `Encryption... -> FakeTcpHeaderServer` همراه با `password` برای جلوگیری از رمزگذاری تکراری ناخواسته رد می‌شوند.

وقتی `password` تنظیم می‌شود، ماژول Encryption مربوطه باید در دسترس باشد؛ در غیر این صورت ساخت با خطایی روشن شکست می‌خورد. بدون رمز، FakeTcpHeader در زمان اجرا به هیچ‌یک از گره‌های Encryption نیاز ندارد. هیچ مسیر جایگزین متن ساده‌ای استفاده نمی‌شود. گره کمکی خصوصی در padding، اعتبارسنجی و پاک‌سازی عادی زنجیره مشارکت می‌کند و در محدودیت تعداد گره‌های زنجیره به حساب می‌آید.

رمزگذاری از محتوای حمل‌شده محافظت می‌کند، اما از فیلدهای قابل‌مشاهده و قابل‌تغییر IP/TCP، طول بسته‌ها یا زمان‌بندی آن‌ها محافظت نمی‌کند. دریافت بر اساس IP/پروتکل و بررسی پورت جعلی همچنان برای مسیریابی ضروری‌اند؛ این موارد به‌تنهایی احراز هویت نیستند. ProtoSwap باید هنگام ارسال پس از رمزگذاری اجرا شود و هنگام دریافت، پیش از رمزگشایی، پروتکل 6 را بازگرداند.

### الگوی پرچم خروجی {#outgoing-flag-script}

گزینهٔ `flags` یک الگوی مرتب برای هدر TCP جعلی انتخاب می‌کند. مقدار پیش‌فرض آن چنین است:

```json
{
  "flags": [{"ack": true, "psh": true}]
}
```

این الگوی تک‌مرحله‌ای در هر بستهٔ حامل خروجی از ACK|PSH (`0x18`) استفاده می‌کند. برای استفاده از الگویی دیگر، `1..32` شیء وارد کنید. هر شیء نام پرچم‌های `fin`، `syn`، `rst`، `psh`، `ack`، `urg`، `ece` و `cwr` را با مقادیر بولی JSON می‌پذیرد. پرچم حذف‌شده `false` است؛ `{}` معتبر است و هیچ پرچمی را تنظیم نمی‌کند. نام پرچم ناشناخته یا تکراری، نویسهٔ NUL درون مقدار، مقادیر غیربولی، ورودی‌های غیرشیء، آرایهٔ خالی و بیش از 32 ورودی رد می‌شوند. برای مثال، `"syn": 1` و `"ack": "true"` نامعتبرند. گزینهٔ `options` همچنان یک رشتهٔ هگزادسیمال جداگانه است و بخشی از این الگو نیست.

برای مثال:

```json
{
  "flags": [
    {"syn": true},
    {"fin": true},
    {"ack": true, "fin": true, "cwr": true}
  ]
}
```

هر پورت کلاینت انتخاب‌شده هنگام ایجاد گره از ورودی اول شروع می‌کند. هر بسته‌ای که با موفقیت کدگذاری شود از ورودی فعلی استفاده می‌کند و سپس به ورودی بعدی می‌رود. **آخرین ورودی برای همیشه تکرار می‌شود**؛ الگو به ابتدا بازنمی‌گردد. برای بسته‌هایی که پورت کلاینت یکسانی را انتخاب می‌کنند، مثال بالا چنین نتیجه‌ای دارد:

| کدگذاری موفق | پرچم‌های TCP جعلی | بایت پرچم |
| --- | --- | --- |
| اول | SYN | `0x02` |
| دوم | FIN | `0x01` |
| سوم | ACK، FIN، CWR | `0x91` |
| چهارم و پس از آن | ACK، FIN، CWR | `0x91` |

هر پورت کلاینت دیگر الگوی خود را از ورودی اول شروع می‌کند. workerها، جریان‌های بومی و همتایانی که به یک پورت کلاینت نگاشت می‌شوند، جایگاه آن را به‌صورت ایمن به اشتراک می‌گذارند. اتصال‌های بومی جدید الگو را از ابتدا شروع نمی‌کنند؛ ایجاد دوبارهٔ گره آن را بازنشانی می‌کند. مسیر upstream کلاینت و مسیر downstream سرور الگوهای مستقلی دارند و دو همتا می‌توانند الگوهای متفاوتی پیکربندی کنند.

هر ورودی همچنان بستهٔ بومی‌ای را حمل می‌کند که باعث کدگذاری شده است. ورودی SYN بستهٔ handshake اضافی ایجاد نمی‌کند و منتظر پاسخ نمی‌ماند؛ FIN و RST نیز گره، line بستهٔ آن یا اتصال بومی را نمی‌بندند. این یک الگوی صریح هدر است، نه نشست TCP یا سازوکار تضمین تحویل. زمان‌بندی workerها و تغییر ترتیب در شبکه می‌توانند ترتیب ارسال یا دریافت را تغییر دهند. کدگذاری ردشده الگو را جلو نمی‌برد، ACK مستقل برای بسته تولید نمی‌کند و هیچ‌یک از دو شمارنده را افزایش نمی‌دهد؛ دور انداختن بسته پس از کدگذاری موفق این تغییرات را برنمی‌گرداند.

وقتی افزایش شمارهٔ توالی فعال باشد، هر یک از بیت‌های انتخاب‌شدهٔ SYN و FIN جعلی یک واحد به افزایش شمارهٔ توالی آن بسته اضافه می‌کند. تنظیم هر دو به معنی دو جایگاه توالی اضافی است؛ پرچم‌های دیگر چیزی اضافه نمی‌کنند. [پیشروی شمارهٔ توالی](#sequence-progression) را ببینید. تولید ACK و افزایش اختیاری ACK مستقل از این موارد انجام می‌شوند، حتی اگر الگو مقدار `ack` را `false` تنظیم کند. فیلد ACK همچنان مقدار عددی، تصادفی یا شمارندهٔ پیکربندی‌شده را در خود دارد. checksum حامل پرچم‌ها، شمارهٔ توالی و ACK واقعی نوشته‌شده را پوشش می‌دهد. رمزگشایی معنای پرچم‌ها را تفسیر نمی‌کند، آن‌ها را با الگوی خود مقایسه نمی‌کند، وضعیت الگوی محلی را تغییر نمی‌دهد و ترتیب مورد انتظاری را الزامی نمی‌داند؛ بررسی‌های معمول ساختار بسته و checksum همچنان برقرارند.

### پیشروی شمارهٔ توالی {#sequence-progression}

پروفایل پیشنهادی، مقدار پیش‌فرض نیز هست:

```json
{
  "sequence": "random_port",
  "increment-sequence": true,
  "acknowledgment": 0,
  "increment-acknowledgment": false,
  "flags": [{"ack": true, "psh": true}]
}
```

`sequence` مقدار شروع را انتخاب می‌کند؛ `increment-sequence` مشخص می‌کند در بسته‌های بعدی چه اتفاقی بیفتد. گزینه‌های پذیرفته‌شده برای مقدار شروع عبارت‌اند از:

| مقدار `sequence` | هنگام ایجاد گره | با `increment-sequence: false` |
| --- | --- | --- |
| یک عدد صحیح در بازهٔ `0..4294967295` | هر پورت انتخاب‌شدهٔ کلاینت از آن عدد شروع می‌کند. | هر بستهٔ خروجی از همان عدد استفاده می‌کند. |
| `"random_node"` | یک عدد تصادفی 32 بیتی انتخاب می‌شود و به‌عنوان مقدار شروع همهٔ پورت‌ها به کار می‌رود. | هر بستهٔ خروجی از همان عدد انتخاب‌شده استفاده می‌کند. |
| `"random_port"` (پیش‌فرض) | برای هر پورت انتخاب‌شدهٔ کلاینت یک مقدار شروع تصادفی 32 بیتی مستقل انتخاب می‌شود. | هر پورت به‌طور مکرر از عدد انتخاب‌شدهٔ خود استفاده می‌کند. |

مقدارهای شروع تصادفی هنگام ایجاد گره و پیش از ارسال هر بسته انتخاب می‌شوند، حتی زمانی که افزایش غیرفعال است. این مقدارها برای هر بسته یا هر اتصال بومی جدید دوباره انتخاب نمی‌شوند. همهٔ مقدارهای 32 بیتی، از جمله صفر، معتبرند و انتخاب‌های تصادفی مستقل ممکن است به‌طور اتفاقی یکسان باشند؛ یکتایی تضمین نمی‌شود. ایجاد دوبارهٔ گره در هر دو حالت تصادفی مقدارهای تازه‌ای انتخاب می‌کند. تنظیم عددی دوباره از عدد پیکربندی‌شده شروع می‌شود.

با `"increment-sequence": true`، هر پورت انتخاب‌شدهٔ کلاینت شمارندهٔ خروجی مخصوص خود را دارد. `"random_node"` به شمارنده‌ها مقدار اولیهٔ یکسان می‌دهد، اما با استفادهٔ ترافیک از پورت‌های مختلف ممکن است شمارنده‌ها از هم فاصله بگیرند. با `"random_port"`، هر شمارنده از مقدار مستقلاً انتخاب‌شدهٔ خود شروع می‌کند. هر کدگذاری پذیرفته‌شده مقدار فعلی شمارندهٔ انتخاب‌شده را در هدر TCP جعلی قرار می‌دهد، سپس آن را به این اندازه افزایش می‌دهد:

```text
1 protocol byte + original IPv4 payload length
+ 40 if password encryption is enabled
+ 1 if the chosen fake SYN bit is set
+ 1 if the chosen fake FIN bit is set
```

payload اصلی IPv4 شامل هدر بومی TCP/UDP و دادهٔ آن، یا بدنهٔ کامل ICMP/opaque است. نه هدر IPv4 و نه هدر TCP جعلی و گزینه‌های آن در این افزایش حساب نمی‌شوند. SYN و FIN هرکدام بدون افزودن بایت به بسته، یک جایگاه اضافی از توالی مصرف می‌کنند. برای مثال، با پرچم‌های پیش‌فرض ACK|PSH و بدون رمز، روی یک پورت انتخاب‌شدهٔ کلاینت با `"sequence": 1000`:

| بسته | دادهٔ اصلی UDP | طول payload جعلی TCP | شمارهٔ توالی استفاده‌شده | مقدار بعدی شمارنده |
| --- | --- | --- | --- | --- |
| اول | 100 بایت | `1 + 8 + 100 = 109` | `1000` | `1109` |
| دوم | 50 بایت | `1 + 8 + 50 = 59` | `1109` | `1168` |

بسته‌هایی که پورت دیگری از کلاینت را انتخاب می‌کنند، شمارندهٔ مستقل همان پورت را افزایش می‌دهند. همهٔ workerهای یک نمونهٔ گره به‌شکل ایمن در این شمارنده‌ها سهیم هستند. جریان‌های بومی و همتایانی که یک پورت را انتخاب می‌کنند، در شمارندهٔ آن پورت سهیم‌اند؛ وضعیت شمارهٔ توالی جداگانه‌ای برای هر اتصال وجود ندارد. یک جریان بومی جدید آن را بازنشانی نمی‌کند. محاسبات به پیمانهٔ `2^32` دور می‌زنند.

بسته‌هایی که این کدگذار رد می‌کند شمارنده را افزایش نمی‌دهند. پس از موفقیت کدگذاری، حذف‌های بعدی افزایش را لغو نمی‌کنند. زمان‌بندی workerها و تغییر ترتیب در شبکه می‌توانند ترتیب رسیدن را تغییر دهند؛ بنابراین این شمارنده‌ها توالی پیوستهٔ TCP را از دید دریافت‌کننده تضمین نمی‌کنند. checksum جعلی TCP با استفاده از شمارهٔ توالی‌ای محاسبه می‌شود که واقعاً در هر بسته نوشته شده است.

با `"increment-sequence": false`، مقدارهای شروع انتخاب‌شده مطابق جدول ثابت می‌مانند. برای این تنظیم فقط مقادیر بولی JSON پذیرفته می‌شوند؛ رشته‌ها، اعداد و `null` نامعتبرند. برای `sequence` فقط یک عدد صحیح در بازهٔ ذکرشده یا رشته‌های دقیق `"random_node"` و `"random_port"` پذیرفته می‌شود. حالتی برای انتخاب یک شمارهٔ توالی تصادفی تازه برای هر بسته وجود ندارد.

انتخاب acknowledgment مستقل از پیشروی شمارهٔ توالی است، همان‌طور که در ادامه توضیح داده می‌شود. دریافت بسته نه شمارندهٔ خروجی را افزایش می‌دهد و نه مقدار ACK را به‌روزرسانی می‌کند؛ ACKها هرگز از ترافیک همتا مشتق نمی‌شوند.

کلاینت هنگام کدگذاری upstream از این منطق استفاده می‌کند؛ سرور هنگام کدگذاری downstream از آن استفاده می‌کند. آن‌ها شمارنده‌های مستقلی دارند و می‌توانند از حالت‌ها یا مقادیر اولیهٔ متفاوتی استفاده کنند. رمزگشایی بر اساس مقدارهای sequence یا acknowledgment بسته‌ها را محدود، مرتب یا حذف نمی‌کند. این پیشروی تقریبی بر اساس بایت هیچ handshake، ارسال مجدد، کنترل جریان یا تضمین تحویل اضافه نمی‌کند و پذیرفته‌شدن توسط شبکه‌های آگاه از TCP را نیز وعده نمی‌دهد.

### حالت‌های تأیید دریافت {#acknowledgment-modes}

گزینهٔ `acknowledgment` مقدار ACK هدر جعلی را مستقل از `sequence` و `increment-sequence` کنترل می‌کند. این مقدار هرگز از بسته‌های دریافت‌شده از همتا محاسبه نمی‌شود. مقدار پیش‌فرض `increment-acknowledgment` برابر `false` است؛ برای استفاده از شمارنده‌ای جداگانه برای هر پورت کلاینت انتخاب‌شده، آن را فعال کنید.

| مقدار `acknowledgment` | با `increment-acknowledgment: false` (پیش‌فرض) | با `increment-acknowledgment: true` |
| --- | --- | --- |
| یک عدد صحیح در بازهٔ `0..4294967295` (پیش‌فرض `0`) | همان عدد ثابت در هر هدر جعلی خروجی نوشته می‌شود. | شمارندهٔ هر پورت کلاینت از آن عدد شروع می‌شود. |
| `"random_node"` | یک مقدار تصادفی 32 بیتی هنگام ایجاد گره انتخاب و برای تمام بسته‌های خروجی در همهٔ پورت‌های کلاینت انتخاب‌شده استفاده می‌شود. | شمارندهٔ همهٔ پورت‌ها از همان مقدار تصادفی انتخاب‌شده شروع می‌شود؛ سپس مستقل از هم پیش می‌روند. |
| `"random_port"` | هنگام ایجاد، یک مقدار تصادفی 32 بیتی مستقل برای هر پورت انتخاب‌شده تعیین می‌شود؛ مقدار هر پورت ثابت می‌ماند. | شمارندهٔ هر پورت از مقدار تصادفی مستقل انتخاب‌شده برای همان پورت شروع می‌شود. |
| `"random_packet"` | برای هر بسته‌ای که با موفقیت کدگذاری شود، یک مقدار تصادفی 32 بیتی جدید انتخاب می‌شود. | ترکیب نامعتبر است و ایجاد گره شکست می‌خورد. |

انتخاب‌های تصادفی ACK از انتخاب‌های شمارهٔ توالی جدا هستند. تمام مقادیر 32 بیتی، از جمله صفر، ممکن‌اند؛ انتخاب‌های جداگانه می‌توانند یکسان باشند، حتی در بسته‌های متوالی در حالت `random_packet`. تصادفی بودن به معنی یکتا بودن نیست. مقادیر ACK انتخاب‌شده هنگام ایجاد و شمارنده‌ها میان همهٔ workerها و جریان‌های بومی‌ای که آن پورت را انتخاب می‌کنند مشترک‌اند. اتصال‌های بومی جدید آن‌ها را دوباره انتخاب یا بازنشانی نمی‌کنند. ایجاد دوبارهٔ گره برای حالت‌های تصادفیِ زمان ایجاد مقادیر جدیدی انتخاب می‌کند یا مقدار شروع عددی پیکربندی‌شده را بازمی‌گرداند.

با `"increment-acknowledgment": true`، هر کدگذاری موفق ACK فعلی پورت انتخاب‌شده را می‌نویسد و سپس شمارندهٔ آن را، صرف‌نظر از اندازهٔ payload، **یک واحد** افزایش می‌دهد. برای مثال:

```json
{
  "acknowledgment": 5000,
  "increment-acknowledgment": true
}
```

سه بسته که یک پورت کلاینت را انتخاب می‌کنند از ACKهای `5000`، `5001` و `5002` استفاده می‌کنند. پورت دیگر شمارندهٔ خود را از `5000` شروع می‌کند. اگر `acknowledgment` حذف شود، شمارنده‌ها از `0` شروع می‌شوند. محاسبات به پیمانهٔ `2^32` دور می‌زنند، بنابراین پس از `4294967295` مقدار `0` می‌آید. زمان‌بندی workerها و تغییر ترتیب در شبکه می‌توانند ترتیب دریافت را تغییر دهند؛ مقادیر متوالی در مسیر شبکه تضمین نمی‌شوند. این یک شمارندهٔ مصنوعی بسته است، نه تأیید دریافت واقعی TCP یا شمار بایت‌های دریافت‌شده.

برای حفظ پیشروی پیش‌فرض شمارهٔ توالی و در عین حال تغییر تصادفی تاریخچهٔ ظاهری ACK در هر بسته، صریحاً این گزینه‌ها را انتخاب کنید:

```json
{
  "sequence": "random_port",
  "increment-sequence": true,
  "acknowledgment": "random_packet",
  "increment-acknowledgment": false
}
```

گزینهٔ `random_packet` افزایش شمارهٔ توالی را غیرفعال نمی‌کند و به غیرفعال بودن آن نیز نیاز ندارد. این گزینه با `"increment-sequence": false` هم کار می‌کند. به همین ترتیب، افزایش ACK را می‌توان با هر یک از تنظیمات شمارهٔ توالی فعال کرد. ترکیب `"acknowledgment": "random_packet"` با `"increment-acknowledgment": true` رد می‌شود و هیچ‌یک از دو تنظیم بی‌سروصدا تغییر نمی‌کند.

پیش‌فرض‌ها همچنان ACK ثابت `0` و افزایش ندادن ACK هستند؛ هر رفتار دیگر ACK باید صریحاً انتخاب شود. گزینهٔ `acknowledgment` فقط اعداد صحیح در بازهٔ گفته‌شده و رشته‌های دقیق جدول را می‌پذیرد. رشته‌های عددی، رشته‌های دیگر، مقادیر بولی، اعداد کسری و `null` نامعتبرند. گزینهٔ `increment-acknowledgment` فقط `true` یا `false` در JSON را می‌پذیرد؛ رشته‌ها، اعداد و `null` نامعتبرند.

کدگذاری ردشده هیچ ACK مستقل برای بسته انتخاب نمی‌کند و وضعیت شمارهٔ توالی یا ACK را پیش نمی‌برد. پس از کدگذاری موفق، دور انداختن بعدی بسته انتخاب تصادفی یا افزایش شمارنده را برنمی‌گرداند. checksum مربوط به TCP جعلی شمارهٔ توالی و تأیید دریافتی را پوشش می‌دهد که واقعاً در آن بسته نوشته شده‌اند. رمزگشایی نه ACK انتخاب می‌کند و نه هیچ‌یک از شمارنده‌ها را پیش می‌برد و این فیلدها را با تنظیمات خروجی محلی مقایسه نمی‌کند؛ بررسی معمول checksum بستهٔ حامل همچنان برقرار است.

تصادفی کردن یا افزایش ACKها می‌تواند عمداً تاریخچهٔ ظاهری تأیید دریافت را تغییر دهد. هیچ‌یک از این دو، بایت‌های دریافت‌شده را دنبال یا تحویل را تأیید نمی‌کند. یک ناظر ممکن است مقادیر ناسازگار را نادیده بگیرد یا الگو را تشخیص دهد؛ هیچ بهبودی در پنهان‌سازی یا پذیرش توسط شبکه تضمین نمی‌شود.

### محدودیت‌ها و قابلیت شناسایی {#limits-and-detectability}

- framing مربوط به TCP جعلی، نبود handshake و payload بومی دارای tag به‌راحتی قابل fingerprint شدن هستند. فایروال‌های stateful، NAT و middleboxها ممکن است آن را دور بیندازند.
- بازنویسی پورت‌های TCP جعلی توسط NAT، نگاشت پیکربندی‌شده را از کار می‌اندازد.
- بدون `password`، احراز اصالت یا رمزگذاری وجود ندارد: ترافیک قابل‌مشاهده می‌ماند و tupleهای captureشدهٔ منطبق می‌توانند بسته تزریق کنند. با آن، محتوا احراز اصالت و رمزگذاری می‌شود، اما بسته‌های معتبر همچنان قابل replay هستند.
- لایهٔ TCP جعلی ترتیب‌دهی، بازیابی از دست رفتن بسته یا قابلیت اطمینان اضافه نمی‌کند. UDP رفتار بومی خود در از دست رفتن بسته و تغییر ترتیب را حفظ می‌کند؛ TCP بومی نیز رفتار TCP خود را حفظ می‌کند.

### مثال‌ها {#examples}

- [examples/client](https://github.com/radkesvat/WaterWall/blob/main/tunnels/FakeTcpHeaderClient/examples/client/config.json): ترافیک UDP روی `127.0.0.1:5000`، از طریق CTP از `10.90.0.1` به `10.90.0.2:5300`.
- [examples/client-tun](https://github.com/radkesvat/WaterWall/blob/main/tunnels/FakeTcpHeaderClient/examples/client-tun/config.json): دستگاه TUN در `10.90.0.1/24`؛ ترافیک UDP را به `10.90.0.2:5300` که تخصیص نیافته است بفرستید تا به TUN مسیریابی شود.
- [نمونهٔ سرور](https://github.com/radkesvat/WaterWall/blob/main/tunnels/FakeTcpHeaderServer/examples/server/config.json): همتای هر دو مثال که ترافیک را به UDP در `127.0.0.1:5300` هدایت می‌کند.

همهٔ مثال‌ها آدرس‌های خصوصی را صراحتاً بازمی‌گردانند و بدون گزینه‌های TCP جعلی از MTU بومی 1479 استفاده می‌کنند. آن‌ها UDP را حمل می‌کنند، چون سرور به PTC و `UdpConnector` ختم می‌شود، نه به دلیل انتخاب پروتکل توسط FakeTcpHeader. آدرس‌های عمومی نمونه `192.0.2.10` و `198.51.100.10` را در RawSocket و IpOverrider جایگزین کنید. هر مثال را از دایرکتوری خودش با `core.json` همان مثال اجرا کنید. تنظیم `route-table: "off"` در مثال TUN انتخاب مسیر را به شما واگذار می‌کند: سرور عمومی را از طریق رابط معمولی در دسترس نگه دارید تا حامل‌ها نتوانند به TUN حلقه بزنند. TCP بومی به نقاط انتهایی TCP مناسب نیاز دارد. پروتکل‌های گسترده‌تر به نقاط انتهایی بستهٔ مناسب در هر دو سمت نیاز دارند، مانند یک جفت مستقیم TUN.

## رفتار پیشرفته {#advanced-behavior}

### بایت پروتکل برای هر بسته {#per-packet-protocol-byte}

کدگذار بایت Protocol اصلی IPv4 را بلافاصله پس از TCP جعلی و گزینه‌های آن کپی می‌کند. دریافت‌کننده این بایت را می‌خواند و پروتکل اصلی IPv4 را بازمی‌گرداند. بنابراین یک جفت پیکربندی‌شده می‌تواند TCP، UDP، ICMP و دیگر پروتکل‌های IPv4 را بسته به بسته و بدون تنظیم پروتکل یا به‌خاطر سپردن انتخاب قبلی حمل کند.

این بایت نخستین بایت **payload** جعلی TCP است و بخشی از هدر آن نیست. پروتکل قابل‌مشاهدهٔ IPv4 هنگام کدگذاری همیشه TCP (6) است. یک گره ProtoSwap جداگانه می‌تواند بعداً این پروتکل حامل را تغییر دهد؛ [ترکیب](#composition) را ببینید. مقادیر زیر شمارهٔ پروتکل IP هستند، نه شمارهٔ پورت یا پروتکل‌های کاربردی مانند HTTP یا DNS.

#### مثال UDP {#udp-example}

```text
Before encoding:
[IPv4 says UDP][original UDP header][data]

Between the FakeTcpHeader peers:
[IPv4 says TCP][fake TCP + options][17: one byte][original UDP header][data]

After decoding:
[IPv4 says UDP][original UDP header][data]
```

دریافت‌کننده TCP جعلی و بایت حاوی 17 را حذف می‌کند و سپس UDP را بازمی‌گرداند. هدر اصلی UDP و دادهٔ برنامه باقی می‌مانند؛ UDP هیچ تضمینی برای تحویل یا ترتیب به دست نمی‌آورد.

#### مثال TCP {#tcp-example}

```text
Before encoding:
[IPv4 says TCP][original TCP header][data]

Between the FakeTcpHeader peers:
[IPv4 says TCP][fake TCP + options][6: one byte][original TCP header][data]

After decoding:
[IPv4 says TCP][original TCP header][data]
```

**هنگام کدگذاری دو هدر TCP وجود دارد**، اما فقط یک هدر IPv4 وجود دارد. دریافت‌کننده هدر TCP جعلی و بایت پروتکل را حذف می‌کند. هدر اصلی TCP، از جمله گزینه‌ها، شماره‌های توالی، acknowledgmentها و پرچم‌های آن، حفظ می‌شود. checksum آن مطابق توضیح [نمایش checksum بومی](#native-checksum-representation) تنظیم می‌شود.

نقاط انتهایی اصلی TCP همچنان handshake و ارسال‌های مجدد واقعی خود را انجام می‌دهند. برای مثال، با پرچم‌های پیش‌فرض، یک بستهٔ SYN اصلی پشت یک هدر جعلی ACK|PSH حمل می‌شود؛ پس از رمزگشایی، SYN اصلی به پشتهٔ TCP دریافت‌کننده می‌رسد. تنظیمات `sequence`، `acknowledgment`، `flags`، `window` و `options` گره فقط هدر جعلی را کنترل می‌کنند. آن‌ها جایگزین فیلدهای اتصال واقعی TCP نمی‌شوند.

#### مثال ICMP {#icmp-example}

```text
Before encoding:
[IPv4 says ICMP][original ICMP header][ICMP message body]

Between the FakeTcpHeader peers:
[IPv4 says TCP][fake TCP + options][1: one byte][original ICMP header][ICMP message body]

After decoding:
[IPv4 says ICMP][original ICMP header][ICMP message body]
```

ICMP به‌صورت یک پیام کامل حفظ می‌شود. checksum آن آدرس‌های IPv4 پیرامونی را در بر نمی‌گیرد، بنابراین به نرمال‌سازی آدرس نیاز ندارد. هدرهای IP نقل‌شده در خطاهای ICMP به‌صورت بایت‌های حمل‌شده باقی می‌مانند؛ آدرس آن هدرهای نقل‌شده ترجمه نمی‌شود.

#### دیگر پروتکل‌های IPv4 {#other-ipv4-protocols}

همهٔ مقادیر بایت پروتکل در بازهٔ `0..255` قابل نمایش هستند. به‌جز بررسی‌های ساختاری TCP، UDP و ICMP، payload بومی IP مبهم تلقی می‌شود و بایت‌های آن، از جمله payload خالی، حفظ می‌شوند. مقادیر رزروشده یا ناشناخته حمل می‌شوند، بدون اینکه ادعا شود سیستم‌عامل یا گره downstream آن‌ها را پیاده‌سازی می‌کند.

حمل opaque تضمینی برای یکپارچگی مستقل از آدرس یا اصلاح عمومی checksum نمی‌دهد. UDP-Lite، AH و دیگر پروتکل‌ها ممکن است از آدرس‌ها یا فیلدهای دیگر هدر محافظت کنند. فیلدهای موردنیاز آن‌ها را حفظ یا بازگردانی کنید، یا در جای دیگری رسیدگی آگاه از پروتکل فراهم کنید. مسیر TUN می‌تواند طیف گسترده‌تری از پروتکل‌ها را حمل کند؛ `ConnectionToPackets` و `PacketsToConnection` همچنان فقط از TCP/UDP پشتیبانی می‌کنند.

### قواعد روی شبکه {#wire-rules}

بدون password اختیاری، برای بایت پروتکل اصلی `P`:

```text
native:  [existing IPv4, protocol P][original IP payload]
carrier: [same IPv4, protocol 6][fake TCP + options][P: one byte][original IP payload]
decoded: [same IPv4, protocol P][original IP payload]
```

فرض کنید `H` طول واقعی هدر IPv4 و `F` طول هدر دریافت‌شدهٔ TCP جعلی باشد. بایت پروتکل در `H + F` قرار دارد؛ بایت‌های بومی از `H + F + 1` آغاز می‌شوند. data offset مربوط به TCP جعلی برابر `F / 4` است و بایت پروتکل را شامل نمی‌شود. checksum آن و طول کل IPv4 این بایت را شامل می‌شوند؛ checksumهای بومی آن را شامل نمی‌شوند. رمزگشایی مستقل از گزینه‌های خروجی محلی، از data offset دریافت‌شده استفاده می‌کند.

برای TCP بومی، پروتکل IP در هر دو بستهٔ بومی و کدگذاری‌شده برابر 6 است. جهت callback تعیین می‌کند که کدگذاری انجام شود یا رمزگشایی؛ پروتکل قابل‌مشاهده به‌تنهایی هرگز این انتخاب را تعیین نمی‌کند.

IHL مربوط به IPv4 طول هدر موجود IPv4، شامل همهٔ گزینه‌های IPv4، است. این طول واقعی محل TCP جعلی را تعیین می‌کند. تبدیل، مبدأ/مقصد، IHL/options، شناسه، DF، TTL و DSCP/ECN را حفظ می‌کند. این تبدیل پروتکل و طول کل را تغییر می‌دهد و checksum مربوط به IPv4 را روی IHL واقعی دوباره محاسبه می‌کند. تغییرات TTL یا ECN در مسیر پس از رمزگشایی همچنان قابل‌مشاهده‌اند. هیچ هدر داخلی محافظت‌شدهٔ IPv4 و هیچ آدرس ذخیره‌شده‌ای برای بازیابی وجود ندارد.

TCP جعلی از پورت‌ها و الگوی پیکربندی‌شده، مدخل الگوی انتخاب‌شده (به‌طور پیش‌فرض ACK|PSH، یعنی `0x18`) و یک checksum معتبر استفاده می‌کند. این checksum روی هدر/options آن، بایت پروتکل و بدنهٔ کامل بومی، به‌علاوهٔ یک pseudo-header با پروتکل 6 و آدرس‌های جاری بسته محاسبه می‌شود. دریافت، checksumهای IPv4 و TCP جعلی را بررسی می‌کند، مگر اینکه یک درخواست داخلی ترمیم checksum معلق باشد. آدرس‌ها با الگوی محلی مقایسه نمی‌شوند؛ فیلتر capture مربوط به RawSocket را پیکربندی کنید.

### نمایش checksum بومی {#native-checksum-representation}

محاسبهٔ checksumهای TCP و UDP شامل آدرس‌های IP است. اگر `IpOverrider` این آدرس‌ها را زمانی تغییر دهد که هدر انتقال اصلی پشت TCP جعلی قرار دارد، checksum اصلی به تعدیل متناظر نیاز دارد. codec این کار را با حذف موقت سهم آدرس‌ها از checksum بومی و افزودن سهم آدرس‌های جاری هنگام رمزگشایی انجام می‌دهد. **این کار فیلدهای آدرس IP بسته را صفر نمی‌کند.** آدرس‌های صفر در توضیحات زیر فقط به محاسبهٔ checksum مربوط‌اند.

پیش از درج، کدگذاری سهم آدرس‌ها را در checksum بومی TCP/UDP به‌صورت افزایشی از آدرس‌های جاری به صفر/صفر تغییر می‌دهد. سهم پروتکل بومی و طول انتقال باقی می‌ماند. رمزگشایی سهم آدرس‌های موجود در هدر باقی‌ماندهٔ IPv4 را بازمی‌گرداند. به این ترتیب `IpOverrider` می‌تواند بستهٔ کدگذاری‌شده را فقط با استفاده از هدر قابل‌مشاهدهٔ TCP جعلی بازنویسی کند و checksumهای بومی هنگام رمزگشایی با آدرس‌های نهایی سازگار می‌شوند. بازنویسی‌های معمول پیش از کدگذاری یا پس از رمزگشایی روی TCP/UDP بومی عمل می‌کنند.

بدون درخواست ترمیم بومی، این تعدیل باقی‌مانده‌های نامعتبر checksum بومی را حفظ می‌کند. checksum صفرِ غیرفعال UDP صفر باقی می‌ماند؛ صفر حسابی برای UDP فعال به‌صورت `0xffff` نمایش داده می‌شود و صفر در TCP یک مقدار عادی checksum است. UDP از طول اعلام‌شدهٔ دیتاگرام خود استفاده می‌کند، از جمله هنگامی که padding مجاز در payload مربوط به IP پس از آن قرار دارد. checksumهای عمداً نامعتبر هدر IPv4 حفظ نمی‌شوند.

ICMP یک pseudo-header شامل آدرس‌های IPv4 پیرامونی ندارد. پیام کامل آن، از جمله بایت‌های checksum، بدون تغییر باقی می‌ماند، مگر آنکه ترمیم بومی درخواست شده باشد. برای پروتکل‌های opaque هیچ تجزیهٔ checksum انتقال یا تعدیل آدرسی انجام نمی‌شود؛ بایت‌های بدنهٔ آن‌ها بدون ادعایی دربارهٔ تأیید یکپارچگی حفظ می‌شوند.

درخواست معلق checksum بومی پیش از درج و پیش از نرمال‌سازی TCP/UDP تکمیل می‌شود. این درخواست با استفاده از ابزار کمکی مشترک کل بسته، TCP، UDP و ICMP را ترمیم می‌کند. برای پروتکل‌های opaque فقط هدر IPv4 را ترمیم می‌کند و بدنهٔ opaque را دست‌نخورده باقی می‌گذارد. بدون این درخواست، اعتبارسنجی پروتکل‌های شناخته‌شده ساختار را بررسی می‌کند، نه اعتبار checksum بومی را.

در زمان رمزگشایی، وجود درخواست باعث می‌شود checksumهای قابل‌مشاهدهٔ IPv4 و TCP جعلی مبنای اعتبار قرار نگیرند، اما بررسی‌های framing، پورت‌ها، وجود بایت پروتکل، ساختار بومی، fragmentها یا اندازه را معاف نمی‌کند. این درخواست هرگز ترمیم بایت‌های پنهان TCP، UDP، ICMP یا opaque را مجاز نمی‌کند. رمزگشایی سهم آدرس‌ها را در TCP/UDP بازمی‌گرداند و فقط checksum هدر باقی‌ماندهٔ IPv4 را دوباره محاسبه می‌کند. کدگذاری یا رمزگشایی موفق درخواست مصرف‌شده را پاک می‌کند. ویرایش دلخواه داده‌های انتقال یا payload پنهان در حالت کدگذاری‌شده، به تبدیلی نیاز دارد که این نمایش را درک کند.

### پورت‌های حامل برای هر جریان {#per-flow-carrier-ports}

هر بستهٔ بومی پیش از درج، یک پورت حامل کلاینت انتخاب می‌کند. نخستین پورت کلاینت و تعداد پورت‌های کلاینت از مقدار تکی یا بازهٔ شامل دو سر انتخاب‌شده به دست می‌آیند. برای `[40001, 40016]` این مقادیر به‌ترتیب 40001 و 16 هستند؛ مقدار تکی یک پورت را انتخاب می‌کند. تعداد پورت‌های موجود محدودیت اتصال نیست: جریان‌های بومی متفاوت می‌توانند یک پورت را انتخاب کنند و هیچ listener یا اتصال واقعی TCP باز نمی‌شود.

انتخاب از این رابطه استفاده می‌کند:

```text
i = deviceFlowWorkerHash(native packet) % number of client ports

client -> server: source first client port + i, destination server-port
server -> client: source server-port,           destination first client port + i
```

وقتی هش‌کردن در دسترس نباشد، اندیس جایگزین صفر است. ابزار کمکی موجود، پورت‌های TCP/UDP/SCTP بومی را در صورت وجود تشخیص می‌دهد و در غیر این صورت از روش جایگزین موجود خود استفاده می‌کند؛ این ابزار توزیع ICMP یا داده‌های opaque را برای هر نشست تضمین نمی‌کند. هش نسبت به دو نقطهٔ انتهایی متقارن است: وقتی tupleهای درخواست و پاسخ در دو کدگذار معکوس یکدیگر باشند، هر دو یک اندیس انتخاب می‌کنند. بازنویسی دلخواه آدرس‌ها می‌تواند این رابطه را تغییر دهد. با این حال، tuple بومی پایدار در هر جهت همچنان توزیع دریافت پایداری ایجاد می‌کند.

RawSocket آدرس‌های قابل مشاهده و پورت‌های TCP جعلی را هش می‌کند. `multi-queue` از توزیع دریافت kernel استفاده می‌کند؛ یک صف از انتخاب نرم‌افزاری worker استفاده می‌کند. رمزگشایی پورت سرور و بازهٔ پیکربندی‌شدهٔ کلاینت را بررسی می‌کند، نه اینکه اندیس مورد انتظار جریان بومی را دوباره محاسبه کند.

### فیلتر دریافت {#receive-filtering}

در کلاینت، TCP روی IPv4 را از آدرس مبدأ عمومی سرور دریافت کنید:

```json
{
  "name": "raw",
  "type": "RawSocket",
  "settings": {
    "capture-filter-mode": "source-ip",
    "capture-ips": ["198.51.100.10"],
    "capture-protocols": [6]
  }
}
```

سرور آدرس مبدأ عمومی کلاینت را انتخاب می‌کند و آن نیز از `"capture-protocols": [6]` استفاده می‌کند. RawSocket، **تمام TCP از آدرس‌های مبدأ انتخاب‌شده** را، صرف‌نظر از پورت، دریافت می‌کند. بنابراین SSH یا HTTPS معمول میان این نقاط انتهایی نیز ممکن است رهگیری شود. رمزگشایی همچنان به `server-port` و یک پورت کلاینت در بازهٔ پیکربندی‌شده نیاز دارد، اما رد کردن یک بستهٔ دریافت‌شده نمی‌تواند آن را به پشتهٔ میزبان بازگرداند. انتخاب IP/پروتکل و بررسی پورت توسط codec به‌تنهایی احراز هویت فراهم نمی‌کنند؛ محافظت اختیاری با گذرواژه توسط ابزار داخلی Encryption پیش از آن اعمال می‌شود که codec بستهٔ حامل رمزگشایی‌شده را ببیند.

### ترکیب {#composition}

از آنجا که فقط یک هدر IPv4 وجود دارد، بازنویسی آدرس همان فیلدهای آدرسی را تغییر می‌دهد که پس از رمزگشایی باقی می‌مانند. گره نمی‌تواند آدرس‌های خصوصی را که با آدرس‌های عمومی جایگزین شده‌اند بازیابی کند. هر جا TUN یا پشتهٔ اتصال دریافت‌کننده انتظار آدرس‌های اصلی را دارد، بازیابی آن‌ها را پیکربندی کنید.

این `IpOverrider` در سمت کلاینت، میان codec و RawSocket، هنگام ارسال آدرس‌های عمومی را تنظیم می‌کند و هنگام دریافت، **پیش از رمزگشایی** tuple بومی را بازمی‌گرداند:

```json
{
  "name": "carrier-addresses",
  "type": "IpOverrider",
  "settings": {
    "up": {
      "source-ip": { "ipv4": "192.0.2.10" },
      "dest-ip": { "ipv4": "198.51.100.10" }
    },
    "down": {
      "source-ip": { "ipv4": "10.90.0.2" },
      "dest-ip": { "ipv4": "10.90.0.1" }
    }
  },
  "next": "raw"
}
```

نمونهٔ متناظر سرور در مسیر upstream، `10.90.0.1 -> 10.90.0.2` را بازمی‌گرداند و در مسیر downstream، `198.51.100.10 -> 192.0.2.10` را تنظیم می‌کند. بازیابی یک انتخاب در زنجیره است و هر جا TUN یا پشتهٔ اتصال انتظار آن آدرس‌های خصوصی را داشته باشد ضروری است. codec هرگز آن‌ها را به خاطر نمی‌سپارد. محل‌های دیگر بازنویسی نیز تا زمانی معتبرند که checksumها و مسیریابی را حفظ کنند.

برای انتخاب پرچم‌های TCP جعلی خروجی، از الگوی `flags` این گره استفاده کنید. یک `IpManipulator` میان codec و RawSocket می‌تواند با `up-tcp-bit-*` در کلاینت و `dw-tcp-bit-*` در سرور آن‌ها را بیشتر بازنویسی کند، اما این بازنویسی‌های بعدی افزایش شمارهٔ توالی‌ای را که این گره قبلاً رزرو کرده است تغییر نمی‌دهند. برای حمل TCP جعلی تحت یک پروتکل IP دیگر، یک `IpManipulator` با `protoswap-tcp` کنار هر codec قرار دهید و آن پروتکل را دریافت کنید؛ برای مثال `"capture-protocols": [253]`. ProtoSwap باید پیش از رمزگشایی TCP جعلی پروتکل 6 را بازگرداند. مقدار پیش‌فرض `opaque-flow-mode: "prefix"` در RawSocket این پروتکل opaque را با استفاده از چهار بایت اول payload، یعنی پورت‌های TCP جعلی، هدایت می‌کند.

### MTU و اعتبارسنجی {#mtu-and-validation}

با فرض `H` به‌عنوان IHL موجود IPv4 (`20..60`)، مقدار `F = 20 + options length` (`20..60`) و یک بایت پروتکل:

```text
native length    = H + original IP payload length
encryption overhead E = 40 with password, otherwise 0
inserted overhead O = F + 1 + E                 (21..61 bytes without encryption)
encoded length   = native length + O
maximum native IPv4 packet length = 1500 - outgoing O
```

جدول زیر برای حالتی است که `password` مشخص نشده باشد؛ وقتی رمزگذاری فعال است، از هر دو حد payload مقدار 40 بایت کم کنید.

| گزینه‌های TCP جعلی | سربار | حداکثر بستهٔ IP بومی | بایت‌های دادهٔ برنامهٔ UDP با IPv4 بیست‌بایتی |
| --- | --- | --- | --- |
| 0 بایت | 21 بایت | 1479 بایت | 1451 بایت |
| 4 بایت | 25 بایت | 1475 بایت | 1447 بایت |
| 40 بایت | 61 بایت | 1439 بایت | 1411 بایت |

این MTUهای بومی **کل بستهٔ اصلی IPv4**، شامل هدر IP و payload اصلی آن، را در بر می‌گیرند. بدون گزینه‌های TCP جعلی، یک بستهٔ بومی 1479 بایتی به یک حامل با اندازهٔ 1500 بایت تبدیل می‌شود. با یک هدر 20 بایتی IPv4 و یک هدر 8 بایتی UDP، مقدار 1451 بایت برای دادهٔ UDP برنامه باقی می‌ماند. گزینه‌های IPv4 درون بستهٔ بومی فضا مصرف می‌کنند، در حالی که گزینه‌های TCP جعلی سربار اضافه‌شده را افزایش می‌دهند.

`TunDevice.device-mtu`، `ConnectionToPackets.mtu` و `PacketsToConnection.mtu` را، که در غیر این صورت از `misc.mtu` هسته به ارث می‌رسند، متناسب با بزرگ‌ترین هدر جعلی خروجی به‌علاوهٔ بایت پروتکل که هر یک از دو همتا استفاده می‌کند تنظیم کنید. MTU پایین‌تر مسیر به مقادیر کوچک‌تر نیاز دارد. codec بسته‌ها را fragment یا segment نمی‌کند، PMTU را کشف نمی‌کند و MSS بومی TCP را تنظیم نمی‌کند. این codec مقدار 61 بایت padding چپ اعلام می‌کند؛ خود تبدیل FakeTcpHeader به `F + 1` بایت نیاز دارد و فقط هدر موجود IPv4 را جابه‌جا می‌کند. گره کمکی اختیاری padding و عملیات رمزگذاری خود را اضافه می‌کند. بدون رمزگذاری، بایت‌های بدنهٔ بومی در جای خود باقی می‌مانند و به فضای اضافی در انتها نیاز ندارند.

هر دو نقطهٔ ورود، برای هر پروتکل اصلی، دقیقاً به یک دیتاگرام کامل و بدون fragment از نوع IPv4 نیاز دارند. کدگذاری مقدار MF یا offset غیرصفر fragment را **پیش از** تجزیهٔ انتقال بومی، ترمیم checksum یا هرگونه تغییر بافر رد می‌کند. بنابراین fragmentهای اول، میانی و آخر حتی در صورت وجود درخواست ترمیم دور انداخته می‌شوند. رمزگشایی نیز MF یا offset غیرصفر را رد می‌کند. DF به‌تنهایی پذیرفته و حفظ می‌شود. برای ورودی fragmentشده، از بازترکیب دستگاه upstream (`fragment-policy: "reassemble"`، مقدار پیش‌فرض) استفاده کنید. حاملی که در مسیر fragment شده است نیز باید پیش از رمزگشایی بازترکیب شود. `preserve-fragments` نمی‌تواند fragmentها را برای این codec قابل‌قبول کند. fragmentهای UDP تولیدشده توسط CTP نیز پیش از کدگذاری به بازترکیب نیاز دارند، بنابراین دیتاگرام‌های برنامه را در محدودهٔ MTU بومی نگه دارید.

کدگذاری پروتکل اصلی IPv4 را می‌خواند. رمزگشایی به پروتکل 6، ساختار و پورت‌های معتبر TCP جعلی، و دست‌کم یک بایت payload مربوط به TCP جعلی برای tag نیاز دارد. tag بررسی‌های ساختاری بومی را تعیین می‌کند: TCP به یک هدر کامل و data offset در محدودهٔ بومی نیاز دارد؛ UDP به دست‌کم هشت بایت و طول اعلام‌شده‌ای نیاز دارد که در آن محدوده جا شود؛ ICMP نیز به دست‌کم هدر پایهٔ هشت‌بایتی خود نیاز دارد. padding مربوط به UDP که از پیش در payload مربوط به IP مجاز است همچنان پذیرفته می‌شود. مقادیر دیگر بدنه‌های opaque را حمل می‌کنند، از جمله بدنهٔ خالی. حامل دارای فقط tag برای opaque معتبر است؛ اما حامل دارای فقط tag برای TCP، UDP یا ICMP رد می‌شود. tag با مقدار صفر وجود دارد و معتبر است؛ نبود بایت tag رد می‌شود.

طول کل IPv4 باید با طول بافر برابر باشد. هدرهای معیوب، IPv6، بایت‌های اضافی انتهای بافر، حامل‌های بیش از حد بزرگ و headroom ناکافی دور انداخته می‌شوند. رمزگشایی معمولاً checksumهای قابل‌مشاهدهٔ IPv4 و TCP جعلی، از جمله tag، را بررسی می‌کند.

هر مورد رد، بایت‌های بافر، headroom، cursor، طول و درخواست checksum را تا پیش از بازیافت بافر توسط گره حفظ می‌کند. پیام‌های تشخیصی مربوط به دور انداختن، دلیل را مشخص می‌کنند و با سطح `ERROR` در network logger ثبت می‌شوند. پیام‌های تشخیصی خروجی شامل اندازهٔ بسته، حداکثر اندازهٔ بومی، سربار و headroom هستند؛ پیام‌های ورودی شامل اندازهٔ بسته و حداکثر اندازهٔ حامل هستند. حداکثر یک پیام تشخیصی در هر پنج ثانیه برای هر گره صادر می‌شود؛ این محدودیت میان هر دو جهت، همهٔ دلایل و همهٔ workerها مشترک است.

## جزئیات پیاده‌سازی {#implementation-details}

### فرادادهٔ گره {#node-metadata}

| ویژگی | مقدار |
| --- | --- |
| `version` | `1` |
| پرچم‌های گره | `kNodeFlagNone` |
| `can_have_prev`, `can_have_next` | `true` |
| لایهٔ گره و همسایه‌ها | `kNodeLayer3` |
| `required_padding_left` | `61` بایت |
| وضعیت line | ندارد |

گزینهٔ ساخت: `INCLUDE_FAKE_TCP_HEADER_CLIENT` (پیش‌فرض `TRUE`). هر دو گره از `FakeTcpHeaderCommon` و `ww` استفاده می‌کنند؛ هیچ‌یک برای ساخت به گره همتا یا ماژول IpManipulator نیاز ندارند. تنظیم password علاوه بر این به گره Encryption متناظر در زمان اجرا نیاز دارد، بدون وابستگی مستقیم هنگام ساخت.

پیاده‌سازی یک تونل بستهٔ خالص است که با `packettunnelCreate()` ساخته می‌شود. وضعیت اتصال برای هر line نگه نمی‌دارد. شمارنده‌های sequence، شمارنده‌های اختیاری ACK، موقعیت‌های الگوی پرچم و هر مقدار تصادفی ثابت ACK متعلق به نمونهٔ گره و میان workerهای آن مشترک‌اند.
