# KcpClient

## نمای کلی {#overview}

`KcpClient` با اجرای داخلی KCP، یک جریان بایتی شبیه TCP را از مسیر UDP با حفظ مرز بسته‌ها عبور می‌دهد. دادهٔ جریان را از گره قبلی می‌گیرد، آن را در قطعه‌های KCP قرار می‌دهد و دیتاگرام‌های حاصل را به گره بعدی می‌فرستد.

این node معمولاً با `KcpServer` در سمت مقابل استفاده می‌شود.

## جایگاه معمول در زنجیره {#typical-placement}

<a id="جایگاه-رایج"></a>

سمت client:

```text
TcpListener -> KcpClient -> UdpConnector
TcpListener -> MuxClient -> KcpClient -> UdpConnector
```

سمت server:

```text
UdpListener -> KcpServer -> TcpConnector
UdpListener -> KcpServer -> MuxServer -> TcpConnector
```

node‌ای که بعد از `KcpClient` قرار می‌گیرد باید مرز datagram‌ها را حفظ کند. این node در اصل برای مسیرهای انتقال UDP-style ساخته شده است.

## نمونهٔ کاربردی ساده {#minimal-practical-example}

نمونهٔ پایه یک پیکربندی کامل گره‌هاست. آن را با پیکربندی سرور که در ادامه پیوند داده شده و تنظیمات راه‌اندازی متناسب با استقرار خود جفت کنید.

### نمونهٔ پایه {#basic-example}

<a id="نمونه-پایه"></a>

این config را روی ماشین برنامه ذخیره کنید. اتصال به TCP محلی `18080` از طریق
UDP به gateway مربوط به WaterWall در `198.51.100.10:9000` منتقل می‌شود. آن را
با [config سمت server](KcpServer.mdx) جفت کنید؛ connector آخر آن، سرویس
HTTP واقعی روی TCP `127.0.0.1:8080` را انتخاب می‌کند. آدرس gateway را عوض کنید.

```json
{
  "name": "kcp-client",
  "nodes": [
    {
      "name": "app-in",
      "type": "TcpListener",
      "settings": {
        "address": "127.0.0.1",
        "port": 18080
      },
      "next": "kcp-client"
    },
    {
      "name": "kcp-client",
      "type": "KcpClient",
      "settings": {
        "fec": false
      },
      "next": "udp-out"
    },
    {
      "name": "udp-out",
      "type": "UdpConnector",
      "settings": {
        "address": "198.51.100.10",
        "port": 9000
      }
    }
  ]
}
```

## پیکربندی {#configuration}

### فیلدهای لازم {#required-fields}

<a id="فیلدهای-ضروری"></a>

`settings` اختیاری است. اگر آن را ننویسید یا مقدارش object نباشد، مقادیر پیش‌فرض به کار می‌روند.

در حالت معمول `next` لازم است و باید به transport یا stackی اشاره کند که مرز datagram‌ها را حفظ می‌کند.

### تنظیمات اختیاری {#optional-settings}

<a id="تنظیمات-اختیاری"></a>

| فیلد | پیش‌فرض | اعتبارسنجی | توضیح |
| --- | --- | --- | --- |
| `send-mtu` | `misc.mtu` هسته (پیش‌فرض 1500) | عدد صحیح `118..65535` بدون FEC؛ `126..65535` با FEC | بودجهٔ بستهٔ خروجی با فرض IPv4؛ دریافت محدودیت مستقل پروتکل دارد. |
| `fec` | `false` | boolean | فعال‌سازی Reed-Solomon forward error correction روی datagram‌های KCP. |
| `fec-data-shards` | `10` | مثبت، با مجموع shard‌ها حداکثر `255` | تعداد data shard در هر FEC block. فقط وقتی `fec` فعال است استفاده می‌شود. |
| `fec-parity-shards` | `3` | مثبت، با مجموع shard‌ها حداکثر `255` | تعداد parity shard در هر FEC block. فقط وقتی `fec` فعال است استفاده می‌شود. |
| `kcp-nodelay` | `true` | boolean | فعال‌سازی KCP nodelay mode. |
| `kcp-interval-ms` | `10` | `10..5000` | فاصله زمانی بین update‌های KCP. |
| `kcp-resend` | `2` | `>= 0` | آستانه fast-resend در KCP. |
| `kcp-no-congestion-control` | `true` | boolean | غیرفعال کردن congestion control در KCP. |
| `kcp-send-window` | `8192` | `>= 1` | send window بر حسب segment. |
| `kcp-recv-window` | `8192` | `>= 1` | receive window بر حسب segment. |
| `kcp-initial-cwnd` | نصف `kcp-send-window` | `1..kcp-send-window` | congestion window اولیه KCP. |
| `kcp-rx-minrto-ms` | `30` | `>= 1` | حداقل retransmission timeout در KCP. |
| `kcp-send-buffer-limit` | `0` | `>= 0` | آستانه backpressure. با مقدار `0`، حد از مجموع local send window، remote window و `10` محاسبه و به `2147483647` محدود می‌شود. |
| `ping-interval-ms` | `10000` | `>= 1` | اگر تا این مدت داده‌ای دریافت نشود، یک ping frame داخلی فرستاده می‌شود. |
| `close-drain-timeout-ms` | `30000` | عدد صحیح `1..2147483647` | بازهٔ محدود ارسال و نگهداری هنگام بستن؛ مقدار موثر کمینهٔ تنظیم دو سمت است. |
| `no-recv-timeout-ms` | `30000` | بزرگ‌تر از `ping-interval-ms` | اگر تا این مدت داده‌ای دریافت نشود، line بسته می‌شود. |

## کاربرد و رفع اشکال {#usage-and-troubleshooting}

### نمونه با FEC {#fec-example}

<a id="نمونه-با-fec"></a>

```json
{
  "name": "kcp-client",
  "type": "KcpClient",
  "settings": {
    "fec": true,
    "fec-data-shards": 10,
    "fec-parity-shards": 3
  },
  "next": "udp-out"
}
```

FEC را باید در هر دو سمت `KcpClient` و `KcpServer` با تعداد shard یکسان فعال کنید. اگر FEC فقط در یک سمت فعال باشد یا تعداد shard‌ها با هم فرق کند، peer نمی‌تواند packet stream را درست decode کند.

### MTU ارسال و padding {#sending-mtu-and-padding}

<a id="mtu-ارسال-و-padding"></a>

گزینهٔ اختیاری `send-mtu` از نوع عدد صحیح هنگام ساخت از `misc.mtu` هسته مقدار می‌گیرد؛ پیش‌فرض
هسته 1500 است. بازهٔ معتبر **118..65535 بدون FEC** و **126..65535 با FEC** است.
این مقدار بودجهٔ بستهٔ خروجی برحسب بایت با فرض IPv4 است. مقدار صریح یا ارث‌رسیدهٔ نامعتبر
ساخت گره را ناموفق می‌کند؛ با override معتبر می‌توان پیش‌فرض نامناسب هسته را جایگزین
کرد. `null`، نوع نادرست، عدد اعشاری، صفر، عدد منفی و مقدار خارج از بازه خطا هستند.
هر نمونه مقدار معتبر خود را مستقل و ثابت نگه می‌دارد.

با `F = 0` بدون FEC و `F = 8` با FEC:

```text
KCP MTU = min(send-mtu - 20 - 8 - 40 - F, 64000)
application chunk = KCP MTU - 24 - 1
```

سهم ثابت IPv4 برابر 20 بایت و UDP برابر 8 بایت است. هر بسته همچنین یک پوشش 40 بایتی session در بیرون KCP/FEC دارد. سقف ده‌دهی 64000 شامل کل
بستهٔ KCP و هدر 24 بایتی آن است. پرچم یک‌بایتی داخل payload قرار دارد و node
`required_padding_left = 1` اعلام می‌کند. همین MTU خروجی داده و ACK/control
تجمیع‌شده را محدود می‌کند؛ FEC حداکثر 8 بایت، شامل بسته‌های parity، اضافه می‌کند.

دریافت محدودیت مستقل پروتکل دارد: حداکثر 64000 بایت برای بستهٔ KCP یا 64008
بایت برای shard مربوط به FEC، بدون احتساب envelope چهل‌بایتی session. دو peer
می‌توانند مقدارهای متفاوت `send-mtu` داشته باشند. بستهٔ ورودی فقط به دلیل
بزرگ‌تر بودن از بودجهٔ ارسال گیرنده رد نمی‌شود؛ اعتبارسنجی frame، هویت session
و FEC همچنان انجام می‌شود. مذاکرهٔ MTU انجام نمی‌شود.

برای `send-mtu: 1500`، MTU مؤثر KCP و chunk برنامه بدون FEC برابر **1432/1407** و
با FEC برابر **1424/1399** هستند. بودجهٔ 64068 بدون FEC یا 64076 با FEC به سقف
می‌رسد. مقادیر معتبر بزرگ‌تر، از جمله 65535، پذیرفته می‌شوند و MTU مؤثر 64000
و chunk برابر 63975 دارند؛ خود تنظیم به 64000 کاهش نمی‌یابد.

این تنظیم کشف یا مذاکرهٔ MTU مسیر نیست. هدر پایهٔ IPv6 بیست بایت بیشتر نیاز دارد؛
بودجهٔ 1500 می‌تواند بستهٔ IPv6 با طول 1520 بسازد. گزینه‌های IPv4، هدرهای توسعهٔ
IPv6 و پوشش‌های بعدی به حاشیهٔ اضافی نیاز دارند. هیچ تعدیلی بر اساس خانوادهٔ IP انجام نمی‌شود.

### اشتباه‌های رایج {#common-mistakes}

<a id="اشتباههای-رایج"></a>

- بعد از `KcpClient` node stream-only نگذارید؛ سمت بعدی باید packet boundary را حفظ کند.
- FEC را فقط در یک سمت فعال نکنید.
- تعداد FEC shard‌ها باید در هر دو سمت یکسان باشد.
- تصور نکنید KCP جلوی هر نوع packet loss را می‌گیرد؛ KCP داده را دوباره می‌فرستد و FEC اختیاری در برابر loss متوسط کمک می‌کند، اما loss شدید یا bursty همچنان مشکل‌ساز است.
- `no-recv-timeout-ms` را کمتر یا مساوی `ping-interval-ms` نگذارید.

## رفتار پیشرفته {#advanced-behavior}

### مدل انتقال KCP {#kcp-transport-model}

<a id="مدل-kcp-transport"></a>

هنگام `Init` برنامه، کلاینت line برنامه را قرض می‌گیرد و یک line مستقل برای انتقال UDP در همان worker می‌سازد که مالک آن است. پیش از `Init` انتقال، contextهای مسیریابی، پورت‌های شنونده و مبدأ، اطلاعات احراز هویت و سیاست خواندن را کپی می‌کند. پروتکل مبدأ و مقصد line برنامه حفظ می‌شوند؛ پروتکل مبدأ و مقصد line انتقال جدید هر دو UDP هستند. `Est` واقعی انتقال بی‌درنگ و مستقل از آماده‌بودن handshake به برنامهٔ متصل منتقل می‌شود.

دو همتا با تبادل HELLO، CHALLENGE، CONFIRM و READY یک session تازه برقرار می‌کنند. nonceهای مستقل 128 بیتی کلاینت و سرور، پیش از رمزگشایی، هویت هر دیتاگرام KCP/FEC را مشخص می‌کنند. پیام‌های handshake بازهٔ بستن و تنظیمات دقیق FEC را حمل می‌کنند. کلاینت درخواست جاری را هر 250 میلی‌ثانیه تا مهلت اصلی `no-recv-timeout-ms` تکرار می‌کند. سرور تنها پس از تأیید تازه، line سرویس مستقلی را مقداردهی می‌کند. ترافیک با تأخیر نمی‌تواند session برقرارشده را بازنشانی یا سرویس قدیمی را دوباره ایجاد کند. این شناسه‌ها احراز هویت یا رمزنگاری فراهم نمی‌کنند.

دادهٔ پذیرفته‌شدهٔ برنامه پیش از آماده‌شدن session وارد صف مرتب ارسال KCP می‌شود؛ ارسال عادی روی شبکه تا دریافت READY متناظر منتظر می‌ماند. callbackهای تو در تو به‌ترتیب اجرا می‌شوند و فضای نگهداری بافرهای معلق محدود است.

وقتی payload stream از node قبلی می‌رسد:

1. payload به chunk‌هایی با حداکثر اندازه KCP write MTU موثر تقسیم می‌شود.
2. هر chunk یک flag یک‌بایتی داخلی prefix می‌گیرد.
3. chunk فریم‌شده از طریق KCP ارسال می‌شود.
4. datagram‌های خروجی KCP در جهت upstream به node بعدی فرستاده می‌شوند.

وقتی datagram‌ها از node بعدی برمی‌گردند:

1. envelope کامل session، جفت nonce دقیق و نوع wire مورد انتظار پیش از رمزگشایی FEC بررسی می‌شوند.
2. KCP datagram را می‌گیرد.
3. payload‌های کامل‌شده از KCP خوانده می‌شوند.
4. flag یک‌بایتی داخلی حذف می‌شود.
5. data frame‌ها به شکل payload stream بازسازی می‌شوند و در جهت downstream به node قبلی می‌روند.

### پرچم‌های داخلی frame {#internal-frame-flags}

<a id="flagهای-داخلی"></a>

داخل payload KCP، `KcpClient` از یک flag یک‌بایتی استفاده می‌کند:

| Flag | معنی |
| --- | --- |
| `0x00` | data frame. بایت‌های بعد از flag همان payload stream واقعی هستند. |
| `0xF0` | ping frame؛ نشانگر داخلی keepalive. |
| `0xFF` | close frame؛ درخواست بستن line در peer. |

یک data frame که فقط بایت flag دارد دور ریخته می‌شود. پیام خالی KCP فاقد flag
است و اتصال مربوط به آن بسته می‌شود؛ flag ناشناخته یا پیام کامل KCP که از بافر
دریافت محلی بزرگ‌تر باشد نیز اتصال را می‌بندد. پیام ناقص KCP منتظر دریافت
قطعه‌های باقی‌مانده می‌ماند.

### رفتار FEC {#fec-behavior}

<a id="رفتار-fec"></a>

با `fec: true`، datagram‌های خروجی KCP در packet‌های Reed-Solomon FEC قرار می‌گیرند. data shard‌ها بلافاصله فرستاده می‌شوند و پس از کامل شدن هر block، parity shard‌های آن ارسال می‌شوند.

در receive، decoder:

- datagram‌های KCP wrap‌شده با FEC را می‌پذیرد
- data shard‌های معتبر را به KCP می‌دهد
- تلاش می‌کند datagram‌های KCP گم‌شده را از parity shard‌ها بازسازی کند
- packet‌های FEC نامعتبر را دور می‌ریزد

FEC مصرف پهنای باند را بالا می‌برد. با تنظیم پیش‌فرض `10` data shard و `3` parity shard، هر block کامل نزدیک به ۳۰ درصد داده parity اضافه دارد؛ header‌های FEC نیز جداگانه به آن افزوده می‌شوند.

## جزئیات پیاده‌سازی {#implementation-details}

### Backpressure {#backpressure}

client پیش از فرستادن سیگنال به stream قبلی برنامه، فشار صف محلی KCP و فشار carrier را با هم در نظر می‌گیرد. تا زمانی که هر یک از این دو علت فعال باشد، برنامه در حالت Pause می‌ماند. سیگنال‌های Pause/Resume دریافتی از carrier، حتی در حالت تکراری، فقط وقتی به برنامه منتقل می‌شوند که توقف محلی KCP فعال نباشد. تغییر فشار محلی نیز فقط وقتی به برنامه اطلاع داده می‌شود که carrier در حالت Pause نباشد؛ Resume مربوط به یک علت نمی‌تواند توقف ناشی از علت دیگر را آزاد کند. سیگنال‌های Pause/Resume سمت برنامه همچنان به carrier منتقل می‌شوند.

پس از پذیرش کامل ورودی و تحویل packet‌های خروجی تولیدشده، client تعداد segmentهای صف‌شده و تأییدنشدهٔ KCP را با `kcp-send-buffer-limit` مقایسه می‌کند. بالاتر از آستانه، توقف محلی فعال و پایین‌تر از آن غیرفعال می‌شود؛ در مقدار برابر، وضعیت فعلی حفظ می‌شود. وقتی مقدار تنظیم `0` است، آستانه از windowهای فعلی KCP محاسبه می‌شود. حتی ورودی فقط شامل ACK نیز می‌تواند توقف محلی را آزاد کند و نیازی به تولید packet خروجی دیگری نیست. وضعیت پیش از callback هم‌زمان ثبت می‌شود و پس از Finish، سیگنالی به برنامهٔ بسته‌شده فرستاده نمی‌شود.

این تنظیم همچنان آستانهٔ نرم تعداد segmentهاست، نه سقف سخت حافظه یا پذیرش داده. دادهٔ آمادهٔ KCP، ACK، ارسال مجدد و pingهای موعدرسیده در حالت Pause برنامه نیز ادامه دارند. windowها، timerهای KCP و مهلت دریافت همچنان اعمال می‌شوند. هر payload به پردازش KCP/FEC نیاز دارد؛ بنابراین node نمی‌تواند خودش را bypass کند.

### رفتار بستن و timeout {#close-and-timeout-behavior}

<a id="رفتار-close-و-timeout"></a>

با `Finish` برنامه، ارتباط آن با انتقال و state قرضی برنامه بلافاصله پاک می‌شود. مالک می‌تواند به‌محض بازگشت `Finish` آن line را نابود کند. line انتقال تحت مالکیت کلاینت و session پایدار، ارسال خروجی قبلاً پذیرفته‌شدهٔ KCP را طی بازهٔ مذاکره‌شدهٔ `D = min(client setting, server setting)` ادامه می‌دهند.

مهلت ثابت ارسال از نخستین `Finish` محلی یا CLOSE همتا آغاز می‌شود. پس از تأیید داده‌های قبلی، فرستنده CLOSE را دقیقاً یک بار در صف قرار می‌دهد و منتظر ACK خود KCP برای آن می‌ماند. صرف flush شدن به معنی تأیید تحویل نیست. با رسیدن مهلت، ارسال تأییدنشده متوقف می‌شود و نتیجه به‌صورت تأییدنشده گزارش می‌شود. ترافیک دریافتی و پیشرفت handshake این مهلت را تمدید نمی‌کنند. اگر `Finish` پیش از مذاکره رخ دهد، ابتدا بازهٔ محلی استفاده می‌شود و مذاکره فقط می‌تواند آن را کوتاه کند.

با دریافت CLOSE همتا، دادهٔ ورودی قبلی پیش از `Finish` برنامه تحویل داده می‌شود؛ برنامه فقط یک بار خاتمه می‌یابد و خروجی پذیرفته‌شده همان فرصت محدود تخلیه را حفظ می‌کند. driver پیش از انتشار ACK مربوط به CLOSE در KCP وارد حالت بستن می‌شود. state دریافت KCP باقی می‌ماند تا بسته‌های تکراری CLOSE بدون بازکردن دوبارهٔ برنامه یا تمدید نگهداری، ACK دیگری دریافت کنند.

پاسخ‌دهنده‌ای که فقط CLOSE همتا را دریافت کرده است تا نخستین دریافت CLOSE به‌اضافهٔ D باقی می‌ماند. اگر CLOSE محلی در زمان A تأیید شود، پاسخ‌دهندهٔ قادر به ارسال ACK تا A + D نگه داشته می‌شود؛ این قاعده در بستن هم‌زمان نیز برقرار است. انقضای ارسال محلی، تعهد قبلی برای ACK همتا را حذف نمی‌کند. کل نگهداری از نخستین رویداد بستن حداکثر 2D است: با پیش‌فرض، حداکثر 30 ثانیه برای ارسال و 60 ثانیه در مجموع. در مرحلهٔ نگهداری فقط برای ACK، یک تایمر مهلت را کنترل می‌کند و ورودی باعث flush شدن ACK می‌شود؛ خروجی PUSH منقضی پیش از FEC فیلتر می‌شود.

`no-recv-timeout-ms` در کارکرد عادی سکوت را مستقل تشخیص می‌دهد؛ در حالت بستن، مهلت‌های ثابت بستن حاکم‌اند. `Finish` انتقال، خطای مهلک پروتکل و خاموشی فرایند فوراً عملیات را قطع می‌کنند. quiescence مربوط به worker، ریشه‌های تایمر را جدا می‌کند و `Stop` آن worker همهٔ lineهای انتقال تحت مالکیت را بدون انتظار برای بستن آرام تخلیه می‌کند. ACK در KCP فقط دریافت توسط لایهٔ انتقال همتا را ثابت می‌کند، نه مصرف یا ذخیرهٔ داده در برنامهٔ دوردست. این پروتکل TCP half-close فراهم نمی‌کند.
