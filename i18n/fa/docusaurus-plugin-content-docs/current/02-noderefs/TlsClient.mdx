# TlsClient

`TlsClient` wrapper سمت client برای TLS در WaterWall است. این نود روی BoringSSL موجود داخل همین repository ساخته شده
است. داده cleartext را از نود قبلی می‌گیرد، آن را به TLS record برای نود بعدی encrypt می‌کند، و TLS recordهای downstream
را دوباره به cleartext تبدیل می‌کند.

این نود یک TLS client handshake واقعی انجام می‌دهد. شکل handshake طوری تنظیم شده که به رفتار Chrome نزدیک باشد؛ از جمله
ALPN ثابت Chrome-like، ALPS، GREASE، permutation extensionها، certificate compression و گروه hybrid اختیاری
`X25519MLKEM768`.

## جایگاه رایج

زنجیره شبیه HTTPS client:

```text
HttpClient -> TlsClient -> TcpConnector
```

زنجیره proxy protocol:

```text
TrojanClient -> TlsClient -> TcpConnector
VlessClient -> TlsClient -> TcpConnector
```

`TlsClient` خودش socket باز نمی‌کند. بعد از آن معمولا نودی مثل `TcpConnector` قرار می‌گیرد تا bytes رمزنگاری‌شده TLS را
به server remote حمل کند.

## نمونه

```json
[
  {
    "name": "tls-client",
    "type": "TlsClient",
    "settings": {
      "sni": "example.com",
      "verify": true,
      "ech-sni-trick": "example.net",
      "x25519mlkem768": true,
      "verbose": false
    },
    "next": "server-out"
  },
  {
    "name": "server-out",
    "type": "TcpConnector",
    "settings": {
      "address": "example.com",
      "port": 443,
      "nodelay": true
    }
  }
]
```

## فیلدهای اجباری

فیلدهای top-level:

| Field | Type | توضیح |
| --- | --- | --- |
| `name` | string | نام دلخواه node. باید داخل config یکتا باشد. |
| `type` | string | باید دقیقا `"TlsClient"` باشد. |
| `settings` | object | تنظیمات TLS client. |
| `next` | string | نود stream-facing که TLS recordهای encrypt شده را حمل می‌کند. در استفاده عادی required است. |

فیلد اجباری داخل `settings`:

| Field | Type | توضیح |
| --- | --- | --- |
| `sni` | string | Server Name Indication برای TLS. مقدار missing یا empty reject می‌شود. |

وقتی `verify` فعال باشد، همین `sni` برای certificate verification هم استفاده می‌شود.

## تنظیمات اختیاری

| Field | Default | توضیح |
| --- | --- | --- |
| `verify` | `true` | peer certificate verification در BoringSSL را فعال می‌کند. |
| `ech-sni-trick` | تنظیم نشده | یک fake inner ClientHello با این hostname می‌سازد و آن را به عنوان GREASE ECH payload قرار می‌دهد. |
| `x25519mlkem768` | `true` | گروه hybrid `X25519MLKEM768` را برای رفتار نزدیک‌تر به Chrome advertise می‌کند. |
| `verbose` | `false` | لاگ اضافی TLS state را فعال می‌کند. |

وقتی `verify` برابر `true` باشد، `TlsClient` CA bundle داخلی `utils/cacert.h` را داخل BoringSSL context بارگذاری می‌کند.
وقتی `verify` برابر `false` باشد، handshake واقعی است ولی certificate-chain verification برای این tunnel instance غیرفعال
می‌شود.

`ech-sni-trick` اگر تنظیم شود باید string غیرخالی باشد. این گزینه outer cleartext SNI را تغییر نمی‌دهد؛ outer SNI همان
`settings.sni` باقی می‌ماند.

## ALPN و پیش‌فرض‌های Chrome-like

مسیر create فعلی از تنظیم JSON برای ALPN استفاده نمی‌کند.

`TlsClient` همیشه این ALPN list را advertise می‌کند:

```text
h2
http/1.1
```

در سورس هنوز helper قدیمی برای یک رشته `alpn` دیده می‌شود، اما در ساخت معمولی node فعال نیست. برای تغییر ALPN روی
`TlsClient` به تنظیم JSON تکیه نکنید.

TLS context با این رفتار ساخته می‌شود:

| رفتار | مقدار فعلی |
| --- | --- |
| حداقل TLS version | TLS 1.2 |
| حداکثر TLS version | TLS 1.3 |
| Session cache | client session cache فعال |
| Session timeout | 7200 seconds |
| GREASE | فعال |
| Extension permutation | فعال |
| Certificate compression | Brotli decompression support |
| Signed certificate timestamps | فعال |
| OCSP stapling request | فعال per line |

گروه‌های پشتیبانی‌شده:

```text
X25519MLKEM768:X25519:P-256:P-384:P-521
```

اگر `x25519mlkem768` برابر `false` باشد، گروه اول حذف می‌شود:

```text
X25519:P-256:P-384:P-521
```

signature algorithmها هم با ترتیب Chrome-like pin شده‌اند و BoringSSL vendored شده داخل پروژه patchهای local برای
شکل‌دهی ClientHello و cipher ordering دارد.

## ALPS

`TlsClient` برای هر دو protocol advertise شده ALPS application settings اضافه می‌کند:

| Protocol | ALPS payload |
| --- | --- |
| `h2` | Chrome payload ثابت `02 68 32` |
| `http/1.1` | payload خالی |

مقدار `h2` یک payload خام Chrome است، نه HTTP/2 `SETTINGS` frame سریال‌شده.

## ECH SNI Trick

وقتی `ech-sni-trick` تنظیم شود، `TlsClient` یک ClientHello دوم و fake با آن hostname می‌سازد. این ClientHello fake به
عنوان GREASE `encrypted_client_hello` payload داخل ClientHello اصلی قرار می‌گیرد.

جزئیات مهم:

- outer SNI همان `settings.sni` است
- fake ClientHello همان ALPN list ثابت را دارد
- fake ClientHello برای کوچک‌تر ماندن payload، `x25519mlkem768` را غیرفعال می‌کند
- این قابلیت برای هماهنگی با ترفندهای packet-side مثل `IpManipulator` طراحی شده است

هدف این است که bytes مورد استفاده در hash داخلی BoringSSL با bytes روی wire هماهنگ بمانند.

## رفتار Runtime

در upstream `Init`، `TlsClient`:

1. state مربوط به BoringSSL را برای line initialize می‌کند
2. memory BIOها را می‌سازد
3. SSL object را در client mode قرار می‌دهد
4. SNI تنظیم‌شده را اعمال می‌کند
5. upstream `Init` را به نود بعدی forward می‌کند
6. `SSL_connect()` را اجرا می‌کند تا اولین ClientHello flight تولید شود
7. bytes handshake تولیدشده را upstream forward می‌کند

به همین دلیل این نود قبل از `TcpConnector` خوب کار می‌کند؛ connector می‌تواند ClientHello را تا زمان connect واقعی socket
buffer کند.

## مفهوم Establishment

در WaterWall، `Est` یعنی transport زیرین established شده، نه اینکه TLS handshake تمام شده باشد.

در حالت عادی، downstream `Est` از نود بعدی بلافاصله به نود قبلی forward می‌شود. اگر tunnel قبلی قبل از کامل شدن handshake
TLS payload بفرستد، `TlsClient` آن را queue می‌کند و بعد از پایان handshake از مسیر `SSL_write()` flush می‌کند.

در handshake-takeover mode، `TlsClient` تا کامل شدن TLS handshake، `Est` معمولی downstream را suppress می‌کند.

## جریان Payload

cleartext upstream:

- قبل از کامل شدن handshake queue می‌شود
- بعد از handshake به `SSL_write()` داده می‌شود
- TLS recordهای تولیدشده از write BIO خوانده و به نود بعدی ارسال می‌شوند

TLS recordهای downstream:

- bytes رمزنگاری‌شده داخل read BIO نوشته می‌شوند
- `SSL_connect()` handshake را جلو می‌برد
- protocol byteهای تولیدشده upstream flush می‌شوند
- application byteهای decrypt شده با `SSL_read()` به نود قبلی forward می‌شوند

خطاهای certificate verification با verify result و reason مربوط به BoringSSL لاگ می‌شوند.

## API

`TlsClient` یک API کوچک برای ساخت raw ClientHello دارد:

```text
generateTlsHello:<sni>
```

ClientHello تولیدشده از تنظیمات همین tunnel instance استفاده می‌کند، از جمله `x25519mlkem768` و `ech-sni-trick`.

## رفتار Finish

`TlsClient` قبل از propagate کردن `Finish`، TLS line state خودش را destroy می‌کند.

برای finishهای عادی directional، finish همان جهت را propagate می‌کند. برای خطاهای fatal در BoringSSL read/write، local
state destroy می‌شود و هر دو direction بسته می‌شوند. این نود مالک lineهای external معمولی نیست و برای آن‌ها
`lineDestroy()` صدا نمی‌زند.

## Padding

`TlsClient` خودش bytes را مستقیم به payloadهای WaterWall prepend نمی‌کند، بنابراین مقدار زیر را advertise می‌کند:

```text
required_padding_left = 0
```

ساخت TLS recordها از طریق memory BIOهای BoringSSL انجام می‌شود.

## Metadata نود

| Property | Value |
| --- | --- |
| Node flag | `kNodeFlagChainHead` |
| Previous node | مجاز، در استفاده عادی required |
| Next node | مجاز، در استفاده عادی required |
| Layer group | `kNodeLayerAnything` |
| `required_padding_left` | `0` |
| Line state | SSL object مربوط به BoringSSL، memory BIOها، handshake flagها، payloadهای upstream queue شده |

## اشتباه‌های رایج

- انتظار نداشته باشید `TlsClient` خودش به remote server وصل شود؛ بعد از آن connector بگذارید.
- فرض نکنید WaterWall `Est` یعنی TLS handshake کامل شده است.
- `alpn` را تنظیم نکنید با این انتظار که ALPN list فعال را عوض کند.
- برای اتصال عمومی، `verify` را فقط وقتی غیرفعال کنید که عمدا certificate validation را نمی‌خواهید.
- اگر هدف شما handshake نزدیک به Chrome فعلی است، `x25519mlkem768` را غیرفعال نکنید.
