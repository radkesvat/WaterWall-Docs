# RawSocket {#rawsocket-node}

<span id="rawsocket"></span>

## نمای کلی {#overview}

`RawSocket`، WaterWall را به capture و تزریق بستهٔ خام IPv4 متصل می‌کند. اگر محدوده‌های capture تنظیم شوند، بسته‌های IP منطبق را از پشتهٔ شبکهٔ میزبان می‌گیرد و وارد زنجیره می‌کند. مستقل از آن، می‌تواند بسته‌های خام IP زنجیره را دوباره به سیستم تزریق کند.

این گره یک آداپتور لایهٔ 3 است، نه تونل اتصال‌محور.

برای مسیرهای Ping/Ping6 با بازنویسی آدرس، IpOverrider را میان RawSocket و decoder قرار دهید و `"opaque-flow-mode": "peer"` را صریح انتخاب کنید؛ `auto` فقط همسایهٔ مستقیم decoder را می‌شناسد. همهٔ حالت‌های Ping از هدر IPv4 دوباره استفاده می‌کنند. Ping معمول و Ping6 مستقیم 9 بایت اضافه و حداکثر 1491 بایت بومی کامل می‌پذیرند؛ Ping6 با `ipv6-in-ipv4`، 49 بایت اضافه و حداکثر 1451 بایت می‌پذیرد. هر دو ورودی fragment را رد می‌کنند. روی آداپتورها `"fragment-policy": "reassemble"` تنظیم و MTU دستگاه/bridge را برای مسیر واقعی تعیین کنید. آدرس شبکهٔ همتا را با پروتکل 1 برای Ping، 58 برای Ping6 مستقیم و 41 برای IPv6-in-IPv4 Ping6 capture کنید. Echo معمول ممکن است با قالب مطابقت داشته باشد؛ انتخاب capture اختصاصی احراز هویت فراهم نمی‌کند.

### کارکرد {#what-it-does}

- در صورت تنظیم، دستگاه capture برای بسته‌های IPv4 منطبق می‌سازد.
- دستگاه خروجی raw برای ارسال بسته‌های خام IPv4 می‌سازد.
- هنگام فعال بودن capture، بسته‌های منطبق با فیلتر IP و protocol را می‌گیرد و از stack کرنل میزبان حذف می‌کند تا فقط WaterWall آن‌ها را دریافت و پردازش کند.
- بستهٔ captureشده را به سمت مجاور زنجیره ارسال می‌کند.
- بستهٔ خام IP زنجیره را از دستگاه raw می‌نویسد.
- در صورت درخواست بافر بسته، پیش از نوشتن checksum را دوباره محاسبه می‌کند.
- در Linux برای ورودی capture فعال و خروجی raw، conntrack را دور می‌زند؛ خروجی از socket mark صریح یا خودکار اختصاصی استفاده می‌کند.

<span id="جایگاه-رایج"></span>

## جایگاه معمول در زنجیره {#typical-placement}

`RawSocket` می‌تواند در هر لبهٔ زنجیره باشد:

- اگر آخرین گره باشد، بستهٔ captureشده را به گره قبلی می‌فرستد؛
- در غیر آن، بسته را به گره بعدی می‌فرستد.

payload رسیده از upstream یا downstream یک بستهٔ IP است و از دستگاه raw تزریق می‌شود.

با استتار بستهٔ PingClient/PingServer، ترتیب لبه‌ها چنین است:

```text
TunDevice -> PingClient -> IpOverrider -> RawSocket
RawSocket -> IpOverrider -> PingServer -> TunDevice
```

وقتی RawSocket نخستین گره است، بستهٔ حامل captureشده را upstream به PingServer می‌فرستد. PingServer بستهٔ داخلی را به سمت TunDevice بازمی‌گرداند؛ فقط با `send-replies: true` ابتدا Echo Reply دقیق نوع 0 را به سمت RawSocket می‌فرستد. ارسال Reply در هر دو گره Ping پیش‌فرض false است و مستقل فعال می‌شود. بستهٔ سادهٔ TunDevice در downstream به صورت Echo Request تازهٔ نوع 8 برای تزریق raw می‌رود و در Echo Reply نامرتبط وارد نمی‌شود.

برای سرویس TCP روی همان حامل بدون TUN:

```text
client: TcpListener -> ConnectionToPackets -> PingClient -> IpOverrider -> RawSocket
server: RawSocket -> IpOverrider -> PingServer -> PacketsToConnection -> TcpConnector
```

[راهنمای استقرار Ping](./PingClient.mdx#deployment-scenarios) آدرس‌های داخلی و بیرونی، MTU، فیلتر capture و مقصد backend را مشخص می‌کند. برای حامل fake TCP از [نمونه‌های کامل FakeTcpHeader](./FakeTcpHeaderClient.mdx#examples) استفاده کنید. در هر دو حالت **آدرس مبدأ بیرونی** همتا و پروتکل حامل را capture کنید: `capture-protocols: [1]` برای Ping، `[58]` برای Ping6 یا `[6]` برای fake TCP. پروتکل برنامهٔ داخلی می‌تواند متفاوت باشد. RawSocket فقط‌نوشتنی حامل برگشتی را دریافت نمی‌کند؛ هر دو طرف تونل دوطرفه به تنظیم capture نیاز دارند.

بلوک‌های JSON زیر قطعه‌های مستقل گره‌اند. نخستین را در لبهٔ capture با `next` متصل به decoder و دومی را در پایان زنجیرهٔ یک‌طرفهٔ تولید بسته مانند `PacketGenerator -> RawSocket` استفاده کنید.

## نمونهٔ کاربردی ساده {#minimal-practical-example}

این قطعهٔ گره است؛ همسایه‌ها و همتاهای اشاره‌شده را در همان استقرار تعریف کنید.

آدرس‌های capture را با آدرس همتای مورد نظر جایگزین و `next-node-name` را مسیر بسته تعریف کنید. این قطعه fragmentها را حفظ می‌کند؛ برای مصرف‌کنندهٔ نیازمند بستهٔ کامل، از جمله Ping/Ping6، reassembly به کار ببرید. capture و تزریق raw به پشتیبانی پلتفرم و مجوزهای شرح‌داده‌شده در ادامه نیاز دارند.

```json
{
  "name": "raw-ip",
  "type": "RawSocket",
  "settings": {
    "fragment-policy": "preserve-fragments",
    "capture-device-name": "capture-in",
    "raw-device-name": "raw-out",
    "capture-filter-mode": "source-ip",
    "capture-ips": [
      "192.0.2.10",
      "198.51.100.0/24"
    ]
  },
  "next": "next-node-name"
}
```

برای پیش‌فرض‌ها و الزام‌های مشروط [پیکربندی](#configuration) و برای نمونه‌های کامل و محدودیت‌های عملیاتی [کاربرد و رفع اشکال](#usage-and-troubleshooting) را ببینید.

### فیلدهای الزامی JSON {#required-json-fields}


#### فیلدهای سطح بالا {#top-level-fields}

- `name` `(string)` نام دلخواه گره است.
- `type` `(string)` باید دقیقاً `"RawSocket"` باشد.

<span id="تنظیمات-اختیاری"></span>

### فیلدهای اختیاری `settings` {#optional-settings-fields}

- `opaque-flow-mode` `(string)` سیاست دریافت IPv4 مبهم است: `prefix` پیش‌فرض، `peer`، `spread` یا `auto`. انتخاب و محدودیت‌ها در بخش تفصیلی زیر آمده است.

- `capture-ips` یا `capture-ip` `(string or array of strings)` نام‌های معادل برای آدرس‌ها یا محدوده‌های CIDR از نوع IPv4 در فیلتر دستگاه capture هستند. هر دو یک رشته یا آرایه می‌پذیرند و هر عضو آرایه یک محدوده است. `listen-ips` نیز با همین شکل‌های ورودی alias سازگاری است. هر مقدار می‌تواند IPv4 تکی مانند `"192.0.2.10"` یا CIDR مانند `"198.51.100.0/24"` باشد؛ IPv6 رد می‌شود. نبود کلید capture یا آرایهٔ خالی در کلید انتخاب‌شده capture را غیرفعال می‌کند و `RawSocket` فقط دستگاه خروجی raw را شروع می‌کند.

- `dont-capture-protocols` `(array of integers)` شناسه‌های IPv4 Protocol مستثنا از capture، مانند `1` برای ICMP، `6` برای TCP یا `17` برای UDP است. عدد صحیح `0..255` پذیرفته می‌شود و تکراری‌ها نادیده گرفته می‌شوند. صفر بایت پروتکل صفر است، نه همهٔ پروتکل‌ها. پیش‌فرض `[]` است. بستهٔ ورودی مستثنا از ruleهای capture این گره عبور می‌کند و conntrack و firewall معمول میزبان را ادامه می‌دهد. خروجی raw محدود نمی‌شود: بسته‌های raw socket در Linux همچنان conntrack را دور می‌زنند. نمونهٔ سپردن ICMP و TCP ورودی به میزبان:

  ```json
  { "dont-capture-protocols": [1, 6] }
  ```

- `capture-protocols` `(array of integers)` فقط بایت‌های literal پروتکل IPv4 فهرست‌شده را capture می‌کند، مثلاً `[6]` برای حامل fake TCP هر دو همتا. عدد صحیح `0..255` پذیرفته و تکراری نادیده گرفته می‌شود. حذف گزینه پیش‌فرض همهٔ پروتکل‌ها را حفظ می‌کند؛ آرایهٔ خالی صریح هیچ‌کدام را نمی‌گیرد. این گزینه با `dont-capture-protocols` حتی برای فهرست خالی ناسازگار است.

  allowlist یک بار به predicate موجود پروتکل تبدیل می‌شود: Linux در هر rule NFQUEUE از cBPF با اندازهٔ ثابت و Windows از WinDivert استفاده می‌کند. پروتکل انتخاب‌نشده در stack میزبان و پردازش معمول conntrack/firewall می‌ماند؛ خروجی raw تغییر نمی‌کند. استثناهای غیرخالی، از جمله حاصل از allowlist، به matcher `bpf` مربوط به iptables لینوکس نیاز دارند. محدوده‌های source IP همچنان اعمال می‌شوند. نمونهٔ client fake TCP برای گرفتن TCP از سرور:

  ```json
  {
    "capture-filter-mode": "source-ip",
    "capture-ips": ["198.51.100.10"],
    "capture-protocols": [6]
  }
  ```

  در سرور، آدرس مبدأ client را به کار ببرید. این **همهٔ TCP از آدرس‌های مبدأ انتخاب‌شده**، شامل SSH یا HTTPS معمول میان همان endpointها، را مستقل از پورت می‌گیرد. FakeTcpHeader پورت حامل را پس از capture بررسی می‌کند؛ رد بسته نمی‌تواند آن را به stack میزبان بازگرداند. فیلتر IP/protocol احراز هویت نیست. برای پورت و قالب حامل [FakeTcpHeaderClient](./FakeTcpHeaderClient.mdx) و [FakeTcpHeaderServer](./FakeTcpHeaderServer.mdx) را ببینید.

- `capture-filter-mode` `(string)` حالت فیلتر ترافیک capture است. وقتی حداقل یک محدوده تنظیم شود الزامی و در write-only نادیده گرفته می‌شود. parser مقدارهای `"source-ip"` و `"dest-ip"` را می‌شناسد، اما پیاده‌سازی فعلی فقط `"source-ip"` را قبول می‌کند. انتخاب `"dest-ip"` ساخت تونل را با پیام استفاده از `TunDevice` برای capture خروجی متوقف می‌کند.

- `skip-sysctl` `(boolean)` در Linux تنظیم best-effort کارایی Capture با `sysctl` را حذف می‌کند. تنظیم سوکت NFQUEUE و ruleهای لازم iptables همچنان انجام می‌شوند. پیش‌فرض `false` است.

- `multi-queue` `(boolean)` در Linux یک صف دریافت برای هر event worker امتحان می‌کند. اگر صف اضافی یا steering در دسترس نباشد، یک صف متعلق به worker صفر استفاده می‌شود. `false` مستقیماً مسیر تک‌صف را انتخاب می‌کند. پردازش بسته همچنان از همهٔ workerهای تنظیم‌شده استفاده می‌کند. دریافت Linux در هر دو حالت روی event worker انجام می‌شود و thread اختصاصی reader ندارد. Windows این تنظیم را می‌پذیرد و آرایش دریافت موجود را حفظ می‌کند. حالت write-only صف دریافت ندارد. پیش‌فرض `true` است.

- `kernel-queue-tune` `(boolean)` صف‌های دریافت کرنل Linux را هنگام راه‌اندازی تنظیم می‌کند. پیش‌فرض در Linux برابر `true` و در جاهای دیگر `false` است. `false` تنظیم پایهٔ NFQUEUE و receive buffer را حفظ می‌کند و همچنان تنظیم کرنل را گزارش می‌کند. مقدار معتبر در سایر پلتفرم‌ها یا حالت write-only اثری ندارد. از `skip-sysctl` و `misc.tcp-tune` هسته مستقل است.

- `kernel-queue-packets` `(integer)` سهم درخواستی packet در NFQUEUE **برای کل دستگاه capture** است که میان صف‌های دریافت فعال نهایی تقسیم می‌شود. برای اندازه‌گذاری خودکار حذف شود.

- `kernel-receive-buffer` `(integer)` بافر دریافتی Netlink بر حسب بایت **برای کل دستگاه capture** است که میان سوکت‌های فعال نهایی تقسیم می‌شود. برای اندازه‌گذاری خودکار حذف شود. مقیاس درخواست `SO_RCVBUF` پیش از حسابداری دوبرابری Linux است.

  هر دو عدد صحیح در بازهٔ `1..2147483647` (`INT_MAX`) می‌خواهند. صفر، منفی، کسری، رشته، بولی و `null` رد می‌شوند؛ فقط حذف فیلد حالت خودکار است. override جای هدف خودکار را می‌گیرد اما مقدار پایه یا مقدار فعلی بزرگ‌تر را کم نمی‌کند و فقط با `kernel-queue-tune` فعال اعمال می‌شود. هر سه تنظیم حتی با tuning یا capture غیرفعال و در پلتفرم غیر Linux اعتبارسنجی می‌شوند.

- `capture-device-name` `(string)` نام قابل مشاهده یا داخلی دستگاه capture است؛ پیش‌فرض `"unnamed-capture-device"`.
- `raw-device-name` `(string)` نام قابل مشاهده یا داخلی دستگاه خروجی raw است؛ پیش‌فرض `"unnamed-raw-device"`.
- `mark` `(integer)` mark اختیاری سوکت خروجی Linux از `1` تا `4294967295` است. باید مختص WaterWall باشد؛ معافیت خروجی NOTRACK دقیقاً همین mark را تطبیق می‌دهد، پس ترافیک نامرتبط با همان mark نیز conntrack را دور می‌زند. صفر، منفی، کسری و غیرعددی رد می‌شوند. مقدار صریح برای routing و NOTRACK از جمله پس از restart دستگاه دقیقاً حفظ می‌شود. در صورت حذف، WaterWall در هر شروع با بررسی‌های برخورد زیر mark خودکار انتخاب می‌کند. WinDivert mark سوکت Linux را اعمال نمی‌کند. برای policy routing صریح:

  ```json
  "settings": {
    "fragment-policy": "preserve-fragments", "mark": 10 }
  ```

### سیاست‌های دریافت بسته {#packet-receive-policies}


<span id="گزینهٔ-opaque-flow-mode"></span>

#### `opaque-flow-mode` (اختیاری، پیش‌فرض: `prefix`) {#opaque-flow-mode-optional-default-prefix}

پیش‌فرض `prefix` است، حتی کنار decoder مربوط به Ping. فقط stringهای دقیق
`prefix`، `peer`، `spread` و `auto` پذیرفته می‌شوند؛ string خالی یا ناشناخته،
`null` و نوع‌های دیگر در همهٔ پلتفرم‌ها رد می‌شوند. RawSocket در حالت write-only
نیز مقدار را اعتبارسنجی می‌کند، هرچند دریافت ندارد. این گزینه از `multi-queue`،
`gso` و `fragment-policy` مستقل است؛ با یک صف دریافت نیز همهٔ workerهای پردازش
طبق همین سیاست استفاده می‌شوند.

برای IPv4 کامل و بدون fragment با protocol غیر از TCP برابر ۶ و UDP برابر ۱۷:

| مقدار | انتخاب worker دریافت |
| --- | --- |
| `prefix` | hash متقارن آدرس‌ها، protocol و چهار بایت اول payload به شکل دو عدد ۱۶ بیتی big-endian، همراه endpoint متناظر. |
| `peer` | فقط جفت آدرس و protocol؛ تمام payload نادیده گرفته می‌شود. |
| `spread` | پخش packet با سازوکار قبلی backend. |
| `auto` | یک بار هنگام startup طبق همسایهٔ مستقیم decoder به `peer` یا در غیر آن به `prefix` تبدیل می‌شود. |

prefix از انتهای header واقعی IPv4، شامل options، شروع می‌شود و باید داخل طول
اعلام‌شدهٔ IP باشد. payload کوتاه‌تر از چهار بایت از fallback آدرس/protocol
استفاده می‌کند. TCP/UDP در هر حالت از hash مشترک ۳۲ بیتی آدرس/port/protocol، یا
در صورت کوتاه‌بودن header از fallback آدرس/protocol استفاده می‌کند؛ flags، طول
transport و checksum شرط تشخیص flow نیستند. محدودهٔ IPv6 و سیاست fragment تغییر
نمی‌کند؛ fragment صفر و fragmentهای بعدی در کرنل همیشه fallback آدرس/protocol دارند.

`prefix` تنها وقتی affinity می‌دهد که چهار بایت اول flow ثابت بماند؛ XOR ثابت
می‌تواند آن را حفظ کند، ولی encryption دلخواه یا mask متغیر چنین تضمینی ندارد.
`peer` همهٔ flowهای پنهان با جفت آدرس و protocol یکسان را روی یک worker جمع
می‌کند و ممکن است موازی‌سازی را کم کند. `spread` می‌تواند پیش از consumer ترتیب
packetها را تغییر دهد. consumer دارای state پس از decode یا بازنویسی tuple، مالک
خود را جداگانه تعیین می‌کند.

فقط `auto` توپولوژی نهایی را پیش از ساخت TUN یا فعال‌کردن capture بررسی می‌کند:
انتشار upstream به `next` تنها کنار همسایهٔ فیزیکی مستقیم با type دقیق
`PingServer` یا `Ping6Server` به `peer` می‌رسد؛ انتشار downstream به `prev` تنها کنار type دقیق
`PingClient` یا `Ping6Client` به `peer` می‌رسد. جهت encoding، node واسط، wrapper و هر حالت دیگر
`prefix` است. نام instance ملاک نیست؛ مقدار صریح همیشه اولویت دارد و RawSocket
مقابل هرگز `spread` را فعال نمی‌کند. اگر هر دو device مقدار `auto` داشته باشند:

```text
TunDevice -> PingClient -> RawSocket
  prefix                     peer

RawSocket -> PingServer -> TunDevice
   peer                     prefix
```

mode مؤثر در generation ثابت است و با fallback تک‌صف یا restart دوباره به رفتار
وابسته به صف تبدیل نمی‌شود. reader برای هر packet ترافیک یا chain را بررسی
نمی‌کند. Ping می‌تواند packetهای دیگر را عبور دهد؛ در نتیجه `peer` خودکار ترافیک
opaque نامرتبط را نیز گروه‌بندی می‌کند و ترافیک ترکیبی ممکن است مقدار صریح بخواهد.
startup مقدار درخواستی، mode مؤثر، دلیل انتخاب و تعداد نهایی صف‌ها را log می‌کند.

<span id="fragment-policy-اختیاری-پیشفرض-reassemble"></span>

#### `fragment-policy` (اختیاری، پیش‌فرض: `reassemble`) {#fragment-policy-optional-default-reassemble}

با حذف این تنظیم، `reassemble` انتخاب می‌شود: fragmentهای IPv4 پیش از انتشار در زنجیره بازسازی می‌شوند. `preserve-fragments` بایت‌ها و مرزهایشان را حفظ می‌کند. این policy فهرست مجاز نام گره یا توپولوژی تحمیل نمی‌کند؛ validation معمول لایه و زنجیره برقرار است. مقدار نامعتبر از جمله `null` شروع را رد می‌کند.

ورودی packet در upstream برای `PacketsToConnection` و در downstream برای `ConnectionToPackets` به datagram کامل IPv4 نیاز دارد. هر یک fragment پشتیبانی‌نشده را پیش از تحویل به stack drop می‌کند، نخستین drop را به صورت warning ثبت و موارد بعدی را بدون خاتمهٔ فرایند می‌شمارد. مستقل از policy دستگاه یا گره واسط، پیش از این مصرف‌کنندگان reassembly انجام دهید. DF به‌تنهایی fragment نیست؛ MF یا offset غیرصفر نشانهٔ آن است.

reassembly، datagram کامل IPv4 تا 65,535 بایت می‌فرستد. سقف خروجی packet یا MTU دستگاه را بالا نمی‌برد و خروجی را خودکار دوباره fragment نمی‌کند. حدود بازسازی و مالکیت packet در بخش چهارم راهنمای توسعه‌دهنده آمده است.

<span id="اندازهٔ-صف-دریافت-کرنل-در-linux"></span>

### اندازهٔ صف دریافت کرنل در Linux {#linux-kernel-receive-queue-sizing}

اندازه‌گذاری از تعداد نهایی صف‌های فعال پس از هر fallback استفاده می‌کند. مقدار
پایه برای کل دستگاه 65,536 packet در NFQUEUE و 64 MiB درخواست receive buffer
در Netlink است. تنظیم خودکار از این بودجه‌ها شروع می‌کند و هدف‌های ترجیحی زیر
را به‌ازای هر صف به کار می‌برد:

| RAM profile تنظیم‌شده | packet ترجیحی در هر صف | درخواست receive buffer ترجیحی برای هر socket |
| --- | ---: | ---: |
| S1 / S2 | 1,024 | 1 MiB |
| M1 / M2 (`client` / `client-larger`) | 2,048 | 2 MiB |
| L1 / L2 (`server`) | 4,096 | 4 MiB |

برای هر منبع، هدف خودکار هر صف برابر بزرگ‌ترِ سهم پایه و هدف ترجیحی است؛ هدف
ترجیحی با سهم آن صف از سقف 131,072 packet یا 128 MiB محدود می‌شود. تقسیم با
تعداد واقعی صف‌ها انجام می‌شود. سقف‌ها فقط هدف خودکار را محدود می‌کنند، نه مقدار
موجودِ بزرگ‌تر یا override صریح. مقدار کل صریح جای هدف خودکار همان منبع را
می‌گیرد و بین صف‌ها تقسیم می‌شود، ولی حداقل سهم پایه حفظ می‌شود. با غیرفعال بودن
tuning، تنظیم پایه همچنان اجرا می‌شود و overrideها اعمال نمی‌شوند.

profile سیاست حافظهٔ تنظیم‌شده است، نه RAM تشخیص‌داده‌شدهٔ میزبان. بودجهٔ هر
capture device مستقل است؛ چند دستگاه بودجه‌های خود را به مصرف کل اضافه می‌کنند.
این عددها RSS واقعی یا سقف بایت payload نیستند. Linux مقدار `SO_RCVBUF` را با
حسابداری دوبرابری گزارش می‌کند و محدودیت‌های socket میزبان می‌توانند درخواست را
کاهش دهند. اگر افزایش مؤثر قابل‌تأیید نباشد، tuning مقدار buffer موجود را حفظ
می‌کند. صف بزرگ‌تر می‌تواند burst را جذب کند،
ولی حافظه و تأخیر بیشتری مصرف می‌کند و تضمین throughput نیست.

startup تعداد صف‌های فعال، منبع هدف (`auto`، `override` یا `disabled`)، سقف هر
NFQUEUE که کرنل با ACK تأیید کرده و `SO_RCVBUF` درخواستی و خوانده‌شده را گزارش
می‌دهد. سقف تأییدنشده به‌صورت unknown گزارش می‌شود. گزارش‌ها با tuning غیرفعال
نیز ثبت می‌شوند. رد شدن tuning یا نبود readback هشدار ایجاد می‌کند و صف‌های
capture قابل‌استفاده را متوقف نمی‌کند.

این تنظیم FIFO مشترک userspace، اندازهٔ batch callbackها یا backlog خروجی raw
را تغییر نمی‌دهد. sysctl سراسری جدیدی نمی‌نویسد و مستقل از `skip-sysctl` و
`misc.tcp-tune` در core است.

<span id="محدودیتهای-capture-filter"></span>

### رفتار فیلتر capture {#capture-filter-behavior}

دستگاه capture از محدوده‌های `capture-ips` یا `capture-ip` پیکربندی می‌شود. بستهٔ منطبق با فیلتر مبدأ IP و پروتکل از stack شبکهٔ کرنل میزبان حذف می‌شود: تا زمان فعال بودن capture، تحویل محلی transport متوقف است و WaterWall کپی captureشده را پردازش می‌کند.

رفتار فعلی:

- در Windows فیلتر capture تطبیق برابر یا بازهٔ شامل دو سر `ip.SrcAddr` را با استثناهای `ip.Protocol` ترکیب می‌کند؛
- در Linux حالت چندصفی برای هر صف و محدوده flow rule می‌سازد؛ فقط `spread` rule تصادفی opaque اضافه می‌کند. حالت تک‌صف برای هر محدوده یک queue rule می‌سازد؛
- `capture-filter-mode` تجزیه می‌شود، اما فعلاً فقط مسیر `source-ip` پیاده‌سازی شده است.

در Linux استثنای غیرخالی پروتکل، چه صریح و چه حاصل از `capture-protocols`، به matcher ‏`bpf` مربوط به iptables (`xt_bpf`) نیاز دارد. predicate مربوط به classic BPF با اندازهٔ ثابت بایت پروتکل IPv4 را در هر rule NFQUEUE بررسی و fragment و پروتکل صفر را بدون تفسیر هدر transport مدیریت می‌کند. درج، rollback و حذف از predicate یکسان استفاده می‌کنند. نبود matcher راه‌اندازی را ناموفق و ruleهای نصب‌شده را rollback می‌کند. انتخاب نامحدود پروتکل matcher اضافه نمی‌کند. Windows همان انتخاب را در فیلتر WinDivert اعمال می‌کند.

به‌صورت پیش‌فرض backend لینوکس پیش از ساخت resource‌های NFQUEUE یک batch از
تنظیمات best-effort مربوط به backlog و سایر پارامترهای TCP را با `sysctl` اعمال می‌کند.
گزینه‌ی `misc.tcp-tune` در هسته، در صورت فعال‌بودن `misc.splice`، تنظیم جداگانه‌ی
`net.ipv4.tcp_mem` را کنترل می‌کند.
گزینه `"skip-sysctl": true` فقط
همین batch را حذف می‌کند؛ operation‌های netlink و command‌های iptables لازم برای
ساخت و هدایت NFQUEUE همچنان اجرا می‌شوند.

در لینوکس، ruleهای `NFQUEUE` همیشه در `raw PREROUTING` نصب می‌شوند؛ شرط‌های
مبدأ و پروتکل همراه `--dst-type LOCAL` محدودهٔ capture را مشخص می‌کنند.
هنگام فعالیت، `NF_DROP` بستهٔ اصلی را پیش از conntrack، DNAT و مسیریابی متوقف
می‌کند و کپی آن به WaterWall تحویل داده می‌شود. بسته‌های نامنطبق، عبوری،
broadcast و multicast مسیر عادی میزبان را ادامه می‌دهند. ورودی انتخاب‌شده از
hookهای بعدی firewall میزبان عبور نمی‌کند. rule ورودی `NOTRACK` نصب نمی‌شود؛
خروجی همیشه rule مستقل `NOTRACK` با تطبیق دقیق mark دارد.

اولویت معمول raw ترتیب فعلی defragmentation را حفظ می‌کند و سقف ۱۵۰۰ بایت تغییری
ندارد. این ruleها MTU را تغییر نمی‌دهند و جایگزین PMTU discovery نیستند؛ پیام‌های
ICMP لازم باید به stack مسئول برسند. گزینهٔ `skip-sysctl` نصب ruleهای queue را
غیرفعال نمی‌کند.

راه‌اندازی ابتدا readerها را آماده می‌کند؛ coordinator تا نصب تمام ruleهای queue،
verdict را `NF_ACCEPT` نگه می‌دارد. اگر نصب چند queue شکست بخورد، ابتدا ruleهای
جزئی پاک می‌شوند و سپس حالت تک‌queue امتحان می‌شود. شکست نصب تک‌queue یا
rollback ناقص باعث شکست startup می‌شود. پاک‌سازی، نتیجه‌های نامشخص عملیات را با
بررسی `raw PREROUTING` تعیین تکلیف و مالکیت ruleهای باقی‌مانده را برای
تلاش مجدد حفظ می‌کند. شکست reader باعث درخواست shutdown منظم می‌شود؛ مالک
lifecycle مسئول پاک‌سازی است.

در Linux، ‏rule‌های NFQUEUE از `--queue-bypass` استفاده می‌کنند. اگر WaterWall
روی queue گوش نکند، packet‌های matching به‌جای drop شدن به‌علت نبود queue، از
پردازش میزبان را در جدول‌های بعدی ادامه می‌دهند؛ ruleهای باقی‌ماندهٔ همان جدولِ
دارای queue اجرا نمی‌شوند. با capture زودهنگام، بستهٔ پذیرفته‌شده می‌تواند وارد
conntrack شود. این یک سیاست availability از نوع fail-open است:
تا وقتی listener وجود ندارد، packet‌ها capture یا transform نمی‌شوند. این گزینه
در زمانی که WaterWall هنوز به queue متصل است، overflow شدن queue را fail-open
نمی‌کند. WaterWall از شماره queueهایی که از قبل در ruleهای
`filter INPUT` یا `raw PREROUTING` استفاده شده‌اند دوری می‌کند. شکست startup، queueها را می‌بندد؛ rollback کامل اجازهٔ
restart بعدی را می‌دهد. cleanup ناموفق ruleها یا خطای I/O در queue غیرفعال،
capture-device object را غیرقابل restart می‌کند. بسته‌شدن queueها باعث فعال‌شدن
`--queue-bypass` برای ruleهای NFQUEUE باقی‌مانده می‌شود.
پیش از فعال‌شدن capture و پس از جداشدن watcherهای workerها، coordinator در زمان
نصب rule، rollback و cleanup هنگام bring-down، خواندن‌های محدود و nonblocking
با verdict برابر `NF_ACCEPT` انجام می‌دهد. raw output device پیش از فعال‌شدن
capture آماده است. فعال‌سازی دریافت پس از packet Init در صف هر worker قرار
می‌گیرد. هنگام فرمان‌های بعدی startup، capture از `NF_DROP` استفاده می‌کند و
packetها را با همان بودجهٔ مشترک برای تحویل روی worker در صف می‌گذارد؛ پرشدن FIFO
نشست، خواندن native را متوقف می‌کند. تا زمان اجرای event loop ممکن است packetها
در queueهای محدود kernel و FIFO نشست باقی بمانند. worker فعال از drop-and-dispatch
استفاده می‌کند. هنگام shutdown،
capture غیرفعال و پذیرش دریافت بسته می‌شود؛ هر watcher روی worker مالک جدا
می‌شود و سپس ruleها پاک و descriptorها آزاد می‌شوند. خطای نهایی دریافت، پذیرش
را می‌بندد و cleanup منظم را درخواست می‌کند؛ بسته‌شدن socket صف باعث می‌شود
ruleهای باقی‌مانده fail-open شوند. در Linux هیچ thread اختصاصی برای capture
reader یا cleanup ساخته نمی‌شود.

### نکته‌ها و ملاحظات {#notes-and-caveats}

- مسیر دریافت فعلی فقط IPv4 را می‌فرستد.
- `capture-filter-mode` هنگام capture عملاً به `"source-ip"` محدود است.
- حذف محدوده‌های capture عمداً تزریق raw فقط‌نوشتنی را انتخاب می‌کند.
- پشتیبانی پلتفرم به backend خام/capture موجود در سیستم‌عامل بستگی دارد.

### چرا گاهی `TunDevice` مناسب‌تر است {#why-tundevice-may-be-a-better-fit-for-some-cases}

پیاده‌سازی فعلی `RawSocket` روی capture ترافیک ورودی IPv4 منطبق با فیلتر source IP و تزریق بستهٔ خام IPv4 متمرکز است.

برای مدل رابط مجازی یا پردازش بسته نزدیک‌تر به ترافیک رابط مسیریابی‌شده، معمولاً `TunDevice` مناسب‌تر است.

## جزئیات پیاده‌سازی {#implementation-details}


### رفتار تفصیلی {#detailed-behavior}


<span id="مسیر-capture"></span>

#### مسیر capture {#capture-path}

در `onStart`، `RawSocket`:

- وقتی حداقل یک محدودهٔ capture تنظیم شده باشد، تونل مجاور دریافت‌کنندهٔ بسته‌ها را تعیین و دستگاه capture را می‌سازد؛
- دستگاه خروجی raw را می‌سازد؛
- پیش از فعال‌سازی ruleهای capture، دستگاه خروجی raw را بالا می‌آورد.

بدون محدودهٔ capture، دستگاه capture، سوکت NFQUEUE، reader یا rule مربوط به capture ساخته نمی‌شود و فقط دستگاه خروجی raw شروع می‌شود.

در Linux هر صف دریافت دقیقاً به یک worker اختصاص می‌یابد و خواندن محدود و nonblocking روی event loop همان worker انجام می‌شود. تعداد صف، steering و حالت مبهم تعیین‌شده تا زمان فعال بودن capture ثابت می‌مانند. IPv4 TCP/UDP بومی از هش متقارن مشترک 32 بیتی آدرس/پورت/پروتکل همانند TUN و affinity مصرف‌کننده استفاده می‌کند. IPv4 مبهم از `opaque-flow-mode` با پیش‌فرض `prefix` پیروی می‌کند. با چند صف بستهٔ کامل روی worker دریافت‌کننده ادامه می‌یابد؛ با یک صف نرم‌افزار حالت مؤثر را پیش از پذیرش FIFO worker اعمال می‌کند. capture در Windows نیز همان سیاست نرم‌افزاری را دارد. مصرف‌کننده پس از decode یا بازنویسی tuple همچنان مالکیت را تعیین می‌کند.

فقط `spread` rule تصادفی opaque برای NFQUEUE (`statistic --mode random`) نصب می‌کند. احتمال‌های آبشاری سهم تقریبی برابر به صف‌ها می‌دهند؛ تعداد دقیق و ترتیب بسته تضمین نمی‌شود. مسیر نرم‌افزاری تک‌reader، cursor محلی نشست را حفظ می‌کند. حالت قطعی بستهٔ opaque را از flow predicate عبور می‌دهد و rule تصادفی نصب نمی‌کند.

همهٔ fragmentهای IPv4، از جمله fragment صفر، steering کرنل آدرس/پروتکل را حفظ می‌کنند. جدول fragment مشترک staging و دسته‌بندی fragment صفر موجود را حفظ و هش worker مشترک را جدا از fingerprint سازگاری full64 نگه‌داشته‌شده استفاده می‌کند. reassembly با چند صف روی worker خواننده می‌ماند و با یک reader از سیاست مؤثر بستهٔ کامل استفاده می‌کند. بستهٔ fragmentشده و عادی یک flow ممکن است worker متفاوتی داشته باشد. استثنای پروتکل یکسان بر همهٔ خانواده‌های rule اعمال می‌شود. predicate صف به matcher `bpf` در iptables نیاز دارد؛ فقط ruleهای opaque حالت spread به `statistic` نیاز دارند. شکست چندصفی پس از پاک‌سازی کامل ruleهای تحت مالکیت به یک صف بازمی‌گردد.

وقتی بسته‌ای capture می‌شود:

- نسخهٔ IP بررسی می‌شود.
- capture در Linux به IPv4 کامل، طول هدر محدود و طول کل برابر بایت‌های captureشده نیاز دارد. checksum نامعتبر و بایت‌های transport مبهم، از جمله هدر XORشده، پرچم غیرمعمول TCP، offset دادهٔ TCP نامعتبر و طول ناسازگار UDP را حفظ می‌کند. بررسی ایمنی پیام Netlink، تشخیص کوتاه‌شدن واقعی و سقف capture برابر 1,500 بایت حفظ می‌شوند.
- Linux فقط وقتی روی بستهٔ بدون fragment، `NFQA_SKB_INFO` صریحاً `NFQA_SKB_CSUMNOTREADY` را تنظیم کند تلاش به تکمیل checksum می‌کند. اگر هدر را نتوان ایمن تفسیر کرد بایت‌ها تغییر نمی‌کنند و capture همچنان بسته را می‌پذیرد. checksum نامعتبر بدون metadata مربوط به offload معوق هرگز موجب ترمیم یا رد نمی‌شود.
- Windows رسیدگی به منشأ checksum و جهت WinDivert را حفظ می‌کند: offload صریحاً معوق در صورت امکان تکمیل، اما checksum خراب و غیرtrusted و offload transport مربوط به fragment رد می‌شود.
- سقف capture ویندوز نیز 1,500 بایت است. بستهٔ بزرگ‌تر گزارش‌شده با `ERROR_INSUFFICIENT_BUFFER` از WinDivert با هشدار محدودشده از نظر نرخ دور ریخته می‌شود؛ خواندن ادامه دارد و دستگاه فعال می‌ماند. بایت ناقص هرگز ارسال نمی‌شود. سایر خطاهای نهایی دریافت همچنان دستگاه را ناموفق می‌کنند.
- برای fragment هرگز checksum transport از یک fragment محاسبه نمی‌شود. Linux بایت‌ها را بدون تغییر به اعتبارسنجی fragment-affinity موجود می‌سپارد که ممکن است آن‌ها را رد کند.
- این مسیر فعلاً فقط IPv4 را ارسال می‌کند.
- بستهٔ منطبق رهگیری و با verdictهای drop-and-dispatch یا packet diversion از stack کرنل میزبان حذف می‌شود؛ هنگام پردازش کپی توسط WaterWall تحویل عادی transport محلی متوقف است.
- بسته با packet line همان worker به سمت مجاور انتخاب‌شده ارسال می‌شود.

سیاست fragment خواننده انتشار را تعیین می‌کند: `reassemble` بایت‌ها را تا تحویل datagram کامل نگه می‌دارد و `preserve-fragments` مرزها و affinity worker را حفظ می‌کند. بافر منتشرشده در کپی، تأخیر و handoff میان workerها از مالکیت معمول پیروی می‌کند و claim تسویهٔ fragment همراه ندارد. ورودی packet پشتهٔ محلی هنگام تحویل شرط datagram کامل را اعمال می‌کند. بخش fragment-policy را ببینید.

<span id="مسیر-output"></span>

#### مسیر خروجی {#output-path}

وقتی upstream یا downstream payload به `RawSocket` می‌رسد:

1. buffer مربوط به payload یک packet خام IP در نظر گرفته می‌شود.
2. payload بررسی می‌شود تا **دقیقاً یک** packet کامل IPv4 باشد؛ header ناقص، طول ناسازگار و بایت‌های اضافی در انتها drop می‌شوند.
3. اگر buffer همان packet درخواست checksum داشته باشد، WaterWall پیش از نوشتن checksum‌های قابل محاسبه را اصلاح می‌کند. شکست validation/checksum buffer را recycle می‌کند و raw writer فراخوانی نمی‌شود.
4. packet از طریق raw output device نوشته می‌شود.
5. اگر raw device در دسترس نباشد یا نوشتن شکست بخورد، buffer به pool برگردانده می‌شود.

هر دو callback upstream و downstream payload از همین write path استفاده می‌کنند.

خروجی در FIFO مربوط به همان event worker ارسال‌کننده صف می‌شود و بعداً روی همان
worker نوشته می‌شود. bufferهای تمام‌شده به pool همان worker برمی‌گردند؛ raw
writer دیگر thread یا pool اختصاصی ندارد و mutex سراسری نوشتن workerها را سری
نمی‌کند. محدودیت کل device همچنان ۱۳۱٬۰۷۲ packet در Linux و ۲۵۶ packet در
Windows است و خروجی صف‌شده و در حال ارسال را شامل می‌شود. ترتیب هر worker حفظ می‌شود؛ بین workerهای مستقل ترتیب سراسری وجود ندارد.

در Linux، هر flush حداکثر ۵۱۲ packet اصلی را با یک `sendmmsg()` غیرمسدودکننده
ارسال می‌کند. در ارسال ناقص فقط prefix ارسال‌شده آزاد می‌شود و suffix باقی‌مانده
پیش از packetهای جدید می‌ماند. `EINTR` تلاش بعدی را به callback بعدی می‌سپارد.
پس از `EAGAIN`، retry روی worker با تأخیر ۱ ms و `poll()` با timeout صفر،
آمادگی socket را بررسی می‌کند؛ event worker منتظر نمی‌ماند. خطاهای کمبود منابع
kernel و خطاهای packet یا مقصد همچنان تنها packet اول ارسال‌نشده را drop می‌کنند؛
خطای دائمی descriptor درخواست shutdown می‌دهد. برای پر شدن batch هیچ timerی صبر نمی‌کند.

در Windows، خروجی WinDivert به‌صورت overlapped انجام می‌شود. packet اصلی تا پایان
عملیات معلق حفظ می‌شود؛ اعلان native completion فقط کار را روی worker مالک صف
می‌کند و به pool آن دست نمی‌زند. Stop پذیرش را می‌بندد، اعلان‌ها را quiesce می‌کند
و پیش از آزاد کردن packetها دسترسی native معلق را تکمیل یا لغو می‌کند.

در Linux، خروجی raw همیشه conntrack را دور می‌زند و به `iptables` و مجوز
مدیریت firewall (`CAP_NET_ADMIN`) نیاز دارد. پیش از فعال شدن writer، WaterWall
مقدار `SO_MARK` را تنظیم و rule خروجی `CT --notrack` را با تطبیق دقیق همان mark
در `raw OUTPUT` نصب می‌کند. مقدار صریح `mark` بدون تغییر برای هر دو استفاده
می‌شود و باید مختص WaterWall باشد؛ ترافیک نامرتبط با همان mark نیز مشمول
`NOTRACK` می‌شود. در صورت حذف گزینه، در هر راه‌اندازی وضعیت firewall و routing
خوانده و mark تصادفی انتخاب می‌شود؛ این انتخاب خودکار به `iptables-save` و `ip`
از iproute2 نیز نیاز دارد. شکست در خواندن policy لازم، انتخاب یا تنظیم mark،
یا نصب rule باعث شکست startup و تلاش برای rollback می‌شود.

انتخاب خودکار mark بازهٔ `0x80000000..0xffffffff` را ترجیح می‌دهد و در صورت نیاز به
مقادیر پایین‌تر مراجعه می‌کند؛ مقادیر کمتر از `0x00010000` انتخاب نمی‌شوند.
مقایسه‌ها و انتساب‌های ثابت mark در `iptables-save` و selector‌های fwmark در
`ip -4 rule show`، از جمله mask‌ها و نتیجهٔ تطبیق packet بدون mark، بررسی
می‌شوند. مقدار انتخاب‌شده در log ثبت می‌شود. این کار فقط احتمال تداخل را کم
می‌کند و رزرو سراسری نیست: policy بومی nftables، tc/eBPF، mark دیگر socket‌ها،
تغییرات هم‌زمان و برنامه‌هایی که بعداً اجرا می‌شوند ممکن است دیده نشوند.

این معافیت فقط conntrack را کنار می‌گذارد؛ routing و firewall همچنان اعمال
می‌شوند و خروجی معاف نباید به NAT یا stateful filtering مبتنی بر conntrack
میزبان متکی باشد. اولویت معمول raw، پردازش fragment و محدودیت MTU تغییر نمی‌کند.
rule‌های سایر مدیران مستقل می‌مانند. پیش از حذف rule با comment
`WWRAW_NOTRACK_...`، پذیرش خروجی بسته و نوشتن‌های native پذیرفته‌شده تمام می‌شوند.
Stop خروجی صف‌شده را آزاد می‌کند و callback قدیمی نمی‌تواند در device دوباره
راه‌اندازی‌شده بنویسد. rollback و destroy حذف rule‌های معلق یا
دارای نتیجهٔ نامشخص را دوباره امتحان می‌کنند. مرگ ناگهانی process یا شکست
مداوم cleanup ممکن است rule را در `raw OUTPUT` باقی بگذارد؛ در این حالت rule
با comment ثبت‌شده در log را دستی حذف کنید.

<span id="رفتار-checksum"></span>

#### رفتار checksum {#checksum-behavior}

پیش از نوشتن بسته، `RawSocket` درخواست بافر بسته را بررسی می‌کند:

- اگر `sbufGetRecalculateChecksum(buf)` درست باشد checksumها دوباره محاسبه می‌شوند؛
- تلاش برای محاسبهٔ مجدد checksum کل بسته انجام می‌شود؛
- برای fragmentهای IPv4، محاسبهٔ checksum transport خودکار حذف می‌شود و فقط checksum هدر IPv4 دوباره محاسبه می‌شود.

<span id="رفتار-direction-و-lifecycle"></span>

#### چرخهٔ عمر callback و line {#callback-and-line-lifecycle}

Payload مسیر معنادار callback است. callbackهای چرخهٔ عمر اتصال معمول (`Init`، `Est`، `Pause` و `Resume`) در این آداپتور بسته جذب‌کنندهٔ نهایی هستند. `Finish` غیرمنتظره در هر جهت نقض fatal چرخهٔ عمر packet line است و برنامه را abort می‌کند؛ no-op نیست.

زنجیره برای هر worker یک packet line پایدار دارد. `RawSocket` هرگز این lineها را تخریب نمی‌کند و line state آن صفر بایت است.
