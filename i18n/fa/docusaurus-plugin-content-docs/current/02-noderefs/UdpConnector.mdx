# UdpConnector

## نمای کلی {#overview}

`UdpConnector` یک adapter خروجی UDP است. socketهای UDP محلی worker را مدیریت می‌کند، آدرس و پورت مقصد را انتخاب می‌کند و datagramها را میان گره قبلی و peer راه دور انتخاب‌شده جابه‌جا می‌کند. این گره معمولاً انتهای زنجیرهٔ UDP با مدل جریان است.

`UdpConnector` accepts normal layer-4 lines, including a carrier created by
WireGuardClient. In `TunDevice -> WireGuardClient -> UdpConnector`, use
`dest_context->address` and `dest_context->port` to connect to the WireGuard
endpoint, or configure another destination such as a UDP relay. Compatible
datagram transforms may appear between the client and connector.

## جایگاه معمول در زنجیره {#typical-placement}

```text
UdpListener -> ... -> UdpConnector -> remote UDP service
```
<a id="حمل-stream-از-طریق-quic-یا-relay-کردن-datagram-برنامه"></a>

### حمل جریان بایتی با QUIC یا عبور دادن datagramهای برنامه {#carry-a-quic-stream-or-relay-application-datagrams}

```text
QUIC client: TcpListener -> QuicClient -> UdpConnector
QUIC peer:   UdpListener -> QuicServer -> TcpConnector
UDP relay:   UdpListener -> UdpConnector
```
در جفت QUIC، UdpConnector به listener راه‌دور QUIC وصل می‌شود؛ TcpConnector سمت peer
به سرویس واقعی TCP متصل است. روی هر دو گره QUIC، `carrier-mode: "datagram"` را تنظیم
کنید و certificate و ALPN را مطابق [نمونه جفت QUIC](./QuicClient.mdx) قرار دهید.
سطر UDP relay خود datagram برنامه را به سرویس ثابت می‌فرستد؛
[نمونه کامل DNS relay](./UdpListener.mdx#configuration-example) را ببینید.

## نمونهٔ کاربردی ساده {#minimal-practical-example}

این یک **قطعهٔ پیکربندی گره** است، نه پیکربندی کامل. آن را در آرایهٔ `nodes` پیکربندی بگذارید و گره‌های مجاور بالا را به هم متصل کنید.

<a id="مقصد-dns-ثابت"></a>

### مقصد DNS ثابت {#fixed-dns-destination}

```json
{
  "name": "dns-out",
  "type": "UdpConnector",
  "settings": {
    "address": "1.1.1.1",
    "port": 53
  }
}
```


## پیکربندی {#configuration}

<a id="فیلدهای-ضروری"></a>

### فیلدهای ضروری {#required-fields}

فیلدهای سطح بالا:

| فیلد | نوع | توضیح |
| --- | --- | --- |
| `name` | string | نام دلخواه گره. باید داخل فایل config یکتا باشد. |
| `type` | string | باید دقیقاً `"UdpConnector"` باشد. |
| `settings` | object | تنظیمات مقصد و socket. |

`settings` باید دقیقاً از یک سبک مقصد استفاده کند:

| سبک | فیلدهای لازم | توضیح |
| --- | --- | --- |
| مقصد تکی | `address` و `port` | هر line از همان قانون مقصد استفاده می‌کند. |
| مقصدهای وزن‌دار | `addresses` | بسته به `balance-mode` برای هر line یا بسته یک مقصد بر اساس وزن انتخاب می‌شود. |

`addresses` را با `address` یا `port` top-level ترکیب نکنید.

<a id="انتخاب-مقصد"></a>

### انتخاب مقصد {#destination-selection}

<a id="مقصد-تکی"></a>

#### مقصد تکی {#single-destination}

از `address` و `port` مستقیماً زیر `settings` استفاده کنید.

```json
{
  "settings": {
    "address": "example.com",
    "port": 53
  }
}
```

مقادیر معتبر برای `address`:

| مقدار | رفتار |
| --- | --- |
| string IPv4 | ارسال به آن آدرس IPv4. |
| string IPv6 | ارسال به آن آدرس IPv6. |
| string domain | resolve کردن domain پیش از ساخت socket. |
| `"src_context->address"` | استفاده از آدرس source در routing context مربوط به line. |
| `"dest_context->address"` | استفاده از آدرس destination در routing context مربوط به line. |

نام domain ثابت باید بین ۱ تا ۲۵۵ بایت باشد.

مقادیر معتبر برای `port`:

| مقدار | رفتار |
| --- | --- |
| عدد | استفاده از آن پورت ثابت. باید `1` تا `65535` باشد. |
| string عددی | استفاده از آن پورت ثابت، مثلاً `"53"`. |
| `"src_context->port"` | استفاده از پورت source در routing context مربوط به line. |
| `"dest_context->port"` | استفاده از پورت destination در routing context مربوط به line. |
| `"random(x,y)"` | انتخاب یک پورت تصادفی در بازهٔ `[x, y]` با احتساب هر دو کران. |

در `random(x,y)` هر دو کران باید در بازهٔ `1..65535` باشند و `x <= y` برقرار باشد.
مقدار کامل کران‌ها استفاده می‌شود؛ برای مثال `random(1000,2000)` از بازهٔ `1000..2000`
انتخاب می‌کند. متن اضافی پس از `)` رد می‌شود.

<a id="مقصدهای-weighted"></a>

#### مقصدهای وزن‌دار {#weighted-destinations}

برای انتخاب مقصد وزن‌دار از `addresses` استفاده کنید.

```json
{
  "settings": {
    "addresses": [
      {
        "address": "1.1.1.1",
        "port": 53,
        "weight": 3
      },
      {
        "address": "8.8.8.8",
        "port": 53,
        "weight": 1
      }
    ]
  }
}
```

هر object باید شامل باشد:

| فیلد | نوع | توضیح |
| --- | --- | --- |
| `address` | string | همان فرم‌های معتبر `address` در مقصد تکی. |
| `port` | عدد یا string | همان فرم‌های معتبر `port` در مقصد تکی، شامل `random(x,y)`. |
| `weight` | عدد صحیح مثبت | وزن نسبی این مقصد هنگام انتخاب. |

برخلاف `TcpConnector`، object‌های مقصد در `UdpConnector` نمی‌توانند گزینه‌های socket را جداگانه تغییر دهند. گزینه‌هایی مانند `large-send-buffer`، `interface`، `source-ip` و `dns-behaviour` باید در سطح بالای `settings` قرار بگیرند.

parser برای سازگاری کلید قدیمی و غلط‌نویسی‌شده `adresses` را هم می‌پذیرد، اما در config جدید از `addresses` استفاده کنید و هر دو نام را هم‌زمان ننویسید.

### حالت balance {#balance-mode}

`balance-mode` زمان انتخاب مقصد وزن‌دار را مشخص می‌کند.

| مقدار | رفتار |
| --- | --- |
| `"connection"` | حالت پیش‌فرض؛ هنگام `init` در جهت upstream یک مقصد بر اساس وزن انتخاب می‌شود و تمام payloadهای آن line در WaterWall از همان مقصد استفاده می‌کنند. |
| `"packet"` | پیش از ارسال هر بستهٔ payload در جهت upstream، یک مقصد بر اساس وزن انتخاب می‌شود. |

`balance-mode` اختیاری است و پیش‌فرض `"connection"` است.

lineهای عادی در mode برابر `"packet"` می‌توانند از مقصدهای IPv4 و IPv6 استفاده
کنند. انتخاب socket و source port محلی به‌صورت داخلی مدیریت می‌شود.

<a id="تنظیمات-اختیاری"></a>

### تنظیمات اختیاری {#optional-settings}

| گزینه | نوع | پیش‌فرض | توضیح |
| --- | --- | --- | --- |
| `balance-mode` | string | `"connection"` | حالت انتخاب مقصد weighted: `"connection"` یا `"packet"`. |
| `large-send-buffer` | boolean یا عدد صحیح مثبت | `true` | تنظیم `SO_SNDBUF` روی socket‌های UDP ساخته‌شده. |
| `large-recv-buffer` | boolean یا عدد صحیح مثبت | `true` | تنظیم `SO_RCVBUF` روی socket‌های UDP ساخته‌شده. |
| `fwmark` | integer | تنظیم نشده | اعمال socket mark به سبک Linux از طریق `SO_MARK` در صورت پشتیبانی. |
| `interface` | string | تنظیم نشده | محدود کردن socket‌های خروجی به یک network device محلی در صورت پشتیبانی. |
| `source-ip` | string | تنظیم نشده | socket خروجی را با یک source port موقت به source IP محلی مشخص bind می‌کند. |
| `dns-behaviour` | object | native با اولویت آدرس core | کنترل lookup محلی، انتخاب آدرس و انتقال DNS. |

<a id="گزینههای-socket-buffer"></a>

#### گزینه‌های socket buffer {#socket-buffer-options}

`large-send-buffer` و `large-recv-buffer` مقادیر زیر را می‌پذیرند:

| مقدار | معنا |
| --- | --- |
| `true` | استفاده از buffer بزرگ پیش‌فرض WaterWall برای socket؛ در حال حاضر `16777216` بایت. |
| `false` | تنظیم نکردن صریح اندازه buffer و استفاده از مقدار پیش‌فرض kernel. |
| عدد صحیح مثبت | درخواست مستقیم آن تعداد بایت. |

هر دو گزینه به‌طور پیش‌فرض buffer بزرگ WaterWall را روی socket‌های UDP connector فعال می‌کنند.

<a id="انتخاب-آدرس"></a>

#### انتخاب آدرس {#address-selection}

`dns-behaviour.strategy` مشخص می‌کند وقتی DNS هم IPv4 و هم IPv6 برمی‌گرداند، کدام آدرس برای مقصد domain انتخاب شود.

اگر این گزینه را ننویسید، مقدار `dns.domain-strategy` در core به کار می‌رود. در نبود آن هم WaterWall از `"prefer-ipv4"` استفاده می‌کند.

فقط رشته‌های canonical زیر با حروف کوچک پذیرفته می‌شوند:

| مقدار | رفتار |
| --- | --- |
| `"core-settings"` | استفاده از اولویت `dns.domain-strategy` در core. |
| `"prefer-ipv4"` | نخستین نتیجه IPv4 را انتخاب می‌کند و اگر وجود نداشت به IPv6 برمی‌گردد. |
| `"prefer-ipv6"` | نخستین نتیجه IPv6 را انتخاب می‌کند و اگر وجود نداشت به IPv4 برمی‌گردد. |
| `"only-ipv4"` | فقط نتیجه IPv4 را می‌پذیرد؛ نبودن IPv4 یعنی resolution برای آن line قابل استفاده نیست. |
| `"only-ipv6"` | فقط نتیجه IPv6 را می‌پذیرد؛ نبودن IPv6 یعنی resolution برای آن line قابل استفاده نیست. |
| `"accept-dns-returned-order"` | نخستین آدرس قابل استفاده در ترتیب بازگشتی resolver را انتخاب می‌کند. |


<a id="interface-source-ip-و-egress-pinning"></a>

#### interface، source IP و egress pinning {#interface-source-ip-and-egress-pinning}

`interface` socket UDP را به یک device محلی محدود می‌کند.

در Linux، WaterWall در صورت امکان از `SO_BINDTODEVICE` استفاده می‌کند. روی platform‌های بدون device binding، socket به آدرس IPv4 مربوط به interface bind می‌شود. اگر آدرسی پیدا نشود، ساخت socket شکست می‌خورد.

`source-ip` socket UDP را به یک source IP محلی مشخص با source port `0` bind می‌کند؛ این از OS یک port موقت می‌خواهد. خانواده آدرس باید با خانواده مقصد انتخاب‌شده مطابقت داشته باشد.

اگر loop protection در `TunDevice` یک egress pin خودکار ایجاد کرده باشد و `interface` را ننوشته باشید، `UdpConnector` از همان pin استفاده می‌کند. `source-ip` به‌تنهایی آن interface را تغییر نمی‌دهد؛ اطمینان یابید IP مبدأ متعلق به interface پین‌شده یا پیش‌فرض است، یا `interface` را صریحاً بنویسید.

<a id="رفتار-dns"></a>

### رفتار DNS {#dns-behaviour}

resolve کردن نام دامنه یعنی پیدا کردن آدرس IP آن پیش از ارسال datagram.
`UdpConnector` ابتدا مقصد را از تنظیمات آدرس و پورت انتخاب می‌کند. فقط وقتی مقصد
یک نام دامنهٔ resolve‌نشده باشد و resolve محلی فعال باشد، lookup انجام می‌دهد.
IP عددی یا مقصدی که از قبل resolve شده باشد به lookup نیاز ندارد.

این سیاست هم هنگام راه‌اندازی اتصال و هم وقتی توزیع بسته‌ای بعداً مقصد دیگری را
انتخاب کند اعمال می‌شود. با حذف `dns-behaviour`، resolve محلی در حالت `native` فعال
می‌ماند و اولویت آدرس از `dns.domain-strategy` در core گرفته می‌شود.

این lookup را با `settings.dns-behaviour` تنظیم کنید:

```json
{
  "dns-behaviour": {
    "resolve": true,
    "mode": "direct",
    "strategy": "prefer-ipv4",
    "servers": ["203.0.113.53:53"]
  }
}
```

این آدرس نمونهٔ مستندات است؛ آن را با آدرس resolver خود جایگزین کنید.

| فیلد | معنی |
| --- | --- |
| `resolve` | boolean اجباری: `true` اجازهٔ lookup نام دامنهٔ resolve‌نشده را می‌دهد و `false`، lookup محلی را غیرفعال می‌کند. |
| `mode` | `native` (پیش‌فرض هنگام فعال بودن)، `direct` یا `chain`. |
| `strategy` | یکی از `core-settings`، `accept-dns-returned-order`، `prefer-ipv4`، `prefer-ipv6`، `only-ipv4` یا `only-ipv6`؛ حذف آن اولویت پیش‌فرض آدرس مصرف‌کننده را به کار می‌برد. |
| `servers` | ۱ تا ۳۲ endpoint عددی IP، IP:port یا [IPv6]:port؛ در حالت‌های `direct` و `chain` اجباری و در `native` ممنوع. |
| `dns-next` | نام غیرخالی ورودی DNS، فقط در حالت `chain`. |

`native` از تنظیمات DNS در core و resolver مشترک worker استفاده می‌کند. هنگام
فعال بودن resolve محلی، این حالت پیش‌فرض انتقال DNS است.

`direct` درخواست‌های DNS را از طریق یک connector خصوصی TCP/UDP در WaterWall به
سرورهایی که مشخص کرده‌اید می‌فرستد.

`chain` درخواست‌های DNS را از زنجیره انتخابی می‌فرستد. برای محافظت از آن‌ها، مسیری
رمزنگاری‌شده مانند VPN خود را انتخاب کنید؛ این حالت به‌تنهایی درخواست‌ها را
رمزنگاری نمی‌کند. مسیر DNS باید هم درخواست‌های UDP و هم fallback روی TCP را حمل
کند. خطای route یا lookup باعث تغییر به DNS بومی یا حالت دیگر نمی‌شود.

در حالت `chain`، مقدار `dns-next` را نام یک شاخهٔ DNS جدا بگذارید که هم UDP و هم
TCP را پشتیبانی کند. این شاخه نباید از قبل به گره دیگری تعلق داشته باشد. این گره
شاخهٔ DNS پیش‌فرض ندارد و نام‌بردن از خود آن مجاز نیست.

شکل غیرفعال دقیقاً `"dns-behaviour": {"resolve": false}` است و فیلدهای `mode`، `strategy`، `servers` و `dns-next` را رد می‌کند. object تهی، null، نوع غیرobject، فیلد ناشناخته و strategy عددی رد می‌شوند. نام strategy باید یکی از رشته‌های canonical بالا با حروف کوچک باشد. `core-settings` فقط اولویت آدرس را انتخاب می‌کند و انتقال DNS را تغییر نمی‌دهد.

با `resolve: false`، آماده‌سازی مقصد همچنان اجرا می‌شود. IP عددی یا مقصد از قبل resolve‌شده کار می‌کند؛ نام resolve‌نشده از مسیر عادی خطای line یا datagram رد می‌شود و به DNS بومی برنمی‌گردد.

این سیاست هم lookup در Init و هم مقصدهای بعدی در توزیع بسته‌ای را پوشش می‌دهد. هر درخواست پیش از تغییر context، دامنه، پورت و strategy مؤثر خود را ثبت می‌کند.

مثال‌های `native`، `direct` و `chain` محافظت‌شده و محدودیت گزینه‌های core را در [DomainResolver](./DomainResolver.mdx) ببینید. این سیاست فقط lookupهای متعلق به همین گره را کنترل می‌کند؛ fake DNS در PTC، DNS سیستم در TunDevice و همهٔ منابع DNS برنامه را تغییر نمی‌دهد.


## کاربرد و رفع اشکال {#usage-and-troubleshooting}

<a id="نمونه-تنظیم"></a>

### نمونهٔ پیکربندی {#configuration-example}

این قطعه گزینه‌های اختیاری سوکت و پورت تصادفی را نشان می‌دهد. برای peer ثابت، پورت واقعی همان peer را به‌صورت عدد صحیح بنویسید و مقادیر وابسته به میزبان مانند `interface`، `source-ip` یا `fwmark` را، مگر آنکه روی میزبان تنظیم شده باشند، حذف کنید.

```json
{
  "name": "udp-out",
  "type": "UdpConnector",
    "settings": {
    "address": "example.com",
    "port": "random(40000,40100)",
    "large-send-buffer": true,
    "large-recv-buffer": true,
    "fwmark": 10,
    "interface": "eth0",
    "source-ip": "192.0.2.10",
    "dns-behaviour": {"resolve": true, "strategy": "prefer-ipv4"}
  }
}
```

<a id="نمونه-چند-مقصد-وزندار"></a>

### نمونهٔ چند مقصد وزن‌دار {#weighted-multi-destination-example}

```json
{
  "name": "udp-out",
  "type": "UdpConnector",
  "settings": {
    "balance-mode": "packet",
    "addresses": [
      {
        "address": "1.1.1.1",
        "port": 53,
        "weight": 3
      },
      {
        "address": "8.8.8.8",
        "port": "random(40000,40100)",
        "weight": 1
      }
    ],
    "large-send-buffer": true,
    "large-recv-buffer": true,
    "dns-behaviour": {"resolve": true, "strategy": "prefer-ipv4"}
  }
}
```

`balance-mode` مستقیماً داخل `settings` قرار می‌گیرد، نه داخل هر object در `addresses`.

<a id="نمونههای-رایج"></a>

### نمونه‌های رایج {#common-examples}

<a id="مقصد-مبتنی-بر-context"></a>

#### مقصد مبتنی بر context {#context-based-destination}

```json
{
  "name": "context-udp-out",
  "type": "UdpConnector",
  "settings": {
    "address": "dest_context->address",
    "port": "dest_context->port"
  }
}
```

این حالت پس از گره‌هایی کاربرد دارد که routing context را به‌صورت پویا پر یا بازنویسی می‌کنند.

یک تونل پروتکلی داخلی می‌تواند مقصد مذاکره‌شده را برای یک adapter خروجی، مقصد
قطعی علامت‌گذاری کند. در این حالت `UdpConnector` آدرس و پورت داده‌شده را حفظ
می‌کند و انتخاب مقصد یا توزیع بسته‌ایِ پیکربندی‌شده را اعمال نمی‌کند. این
فرادادهٔ داخلی زنجیره است، نه یک تنظیم در JSON؛ به این ترتیب relay UDP در SOCKS5
می‌تواند از `BND.ADDR` و `BND.PORT` مذاکره‌شده با پروکسی استفاده کند.

`Router` یا sniffer قبلی ممکن است فرادادهٔ پروتکل‌های مشاهده‌شده را پاک کند،
اما قطعی‌بودن مقصد برای کنترل مسیر پس از آن پاک‌سازی محدود حفظ می‌شود. `UdpConnector`
این نشان را هنگام راه‌اندازی خروجی دقیقاً یک بار مصرف می‌کند و پیش از تصمیم‌های
عادی بعدیِ مسیریابی آن را پاک می‌کند.

<a id="پورت-مقصد-تصادفی"></a>

#### پورت مقصد تصادفی {#random-destination-port}

```json
{
  "name": "random-port-out",
  "type": "UdpConnector",
  "settings": {
    "address": "203.0.113.10",
    "port": "random(40000,40100)"
  }
}
```

در mode برابر `"connection"`، پورت تصادفی هنگام مقداردهی line یک بار انتخاب می‌شود و تا پایان عمر همان line ثابت می‌ماند.

<a id="استخر-dns-packet-balanced"></a>

#### استخر DNS با توزیع بسته‌ای {#packet-balanced-dns-pool}

```json
{
  "name": "packet-balanced-dns",
  "type": "UdpConnector",
  "settings": {
    "balance-mode": "packet",
    "addresses": [
      {
        "address": "1.1.1.1",
        "port": 53,
        "weight": 3
      },
      {
        "address": "8.8.8.8",
        "port": 53,
        "weight": 1
      }
    ]
  }
}
```

### idle timeout {#idle-timeout}

UDP line‌های idle به‌صورت خودکار منقضی می‌شوند و ادامه ترافیک deadline را تمدید
می‌کند. هنگام expiry، state مربوط به connector آزاد و downstream `finish` به گره
قبلی فرستاده می‌شود.

<a id="نکات-و-هشدارها"></a>

### نکات و هشدارها {#notes-and-caveats}

- `UdpConnector` یک گره خروجی در انتهای زنجیره است و به `next` نیاز ندارد.
- حل نام DNS ناهمگام است و از `dns-behaviour.strategy` انتخاب‌شده استفاده می‌کند.
- object‌های مقصد زیر `addresses` فقط `address`، `port` و `weight` دارند؛ socket option‌ها تنظیمات top-level هستند.
- `fwmark` و device binding به platform وابسته هستند.
- `fwmark` روی Windows در دسترس نیست.
- وقتی read در حالت pause است، datagram ورودی به‌جای قرار گرفتن در buffer دور ریخته می‌شود.
- source port محلی توسط connector مدیریت می‌شود و نباید به‌عنوان شناسه line
  استفاده شود.
- `PacketsToStream` در حال حاضر فقط بسته‌های IPv4 با ساختار داخلی سازگار را عبور می‌دهد و
  routing context متغیر هر بسته را روی line عادی خروجی کپی نمی‌کند. برای تبدیل
  IPv4 TCP/UDP به ازای flow از `PacketsToConnection` و برای semantics مستقیم
  مسیریابی line بسته‌ای از adapter UDP سازگار با بسته استفاده کنید.
- برای رفتار UDP stateless در سطح بسته، `UdpStatelessSocket` ممکن است مناسب‌تر از `UdpConnector` باشد.


## رفتار پیشرفته {#advanced-behavior}

### حل نام دامنه {#domain-resolution}

DNS resolution هنگام راه‌اندازی اتصال، در صورت نیاز و فعال بودن، به‌شکل async انجام می‌شود. payload‌هایی که پیش از پایان DNS می‌رسند در صف محدود resolver می‌مانند. شکست resolution باعث finish شدن فوری line است.

با فعال بودن resolve محلی، balance mode `"packet"` مقصدهای resolve‌نشدهٔ دیگر را هنگامی lookup می‌کند که یک بسته آن‌ها را انتخاب کند:

- نخستین بسته‌ای که یک domain حل‌نشده را انتخاب کند، یک DNS request از نوع async برای همان object آغاز می‌کند
- بسته‌های مربوط به آن مقصد در یک صف محدود منتظر می‌مانند
- پس از موفقیت resolution، پیش از تخلیه صف resource مقصد آماده می‌شود؛ شکست آن
  فقط صف همان مقصد را حذف می‌کند
- context مقصد ثابت برای بسته‌های بعدی همان line cache می‌شود؛ مقصدی که از
  line context متغیر می‌آید پیش از استفاده دوباره ساخته می‌شود
- اگر line context متغیر هنگام pending بودن DNS request قبلی برای همان slot مقصد
  تغییر کند، بسته جدید به‌جای پیوستن به request منسوخ drop می‌شود
- cache زمان‌دار DNS یا DNS request جدا برای هر بسته وجود ندارد


## جزئیات پیاده‌سازی {#implementation-details}

<a id="قابلیتها"></a>

### چه کاری انجام می‌دهد {#what-it-does}

- مدیریت socket‌های UDP خروجی در state محلی هر worker.
- انتخاب address و port مقصد از تنظیمات ثابت، مقصدهای وزن‌دار یا routing context.
- resolve کردن نام domain از طریق یک `DomainResolver` داخلی و async.
- ارسال payload‌های upstream از گره قبلی به remote UDP peer.
- ارسال datagram‌های UDP دریافت‌شده به‌صورت downstream به گره قبلی.
- هدایت datagram‌های دریافتی به line مبدأ و رد کردن peer‌های ثبت‌نشده.
- ردیابی UDP line‌ها با idle timeout.
- اعمال socket option‌های اختیاری مثل socket buffer‌ها، `SO_MARK`، device binding و source-IP binding در صورت پشتیبانی.

`UdpConnector` در انتهای زنجیره قرار می‌گیرد، با upstream `init` راه می‌افتد و به گره `next` نیاز ندارد.

<a id="راهاندازی-socket-و-lifecycle"></a>

### راه‌اندازی و چرخهٔ عمر socket {#socket-setup-and-lifecycle}

در طول upstream `init`، `UdpConnector`:

1. آدرس و پورت مقصد را برای line انتخاب می‌کند.
2. `dns-behaviour.strategy` را روی destination context line تنظیم می‌کند.
3. اگر DNS محلی فعال باشد، نام دامنهٔ resolve‌نشده را resolve می‌کند؛ مقصد IP به lookup نیاز ندارد.
4. resource‌های UDP محلی worker را برای مقصد resolveشده آماده می‌کند.
5. buffer‌های send/receive و تنظیمات `interface`، `fwmark`، source IP و egress pin
   را روی هر socket تازه‌ای که لازم باشد اعمال می‌کند.
6. پردازش دریافت را در صورت نیاز پیش از ارسال `est` در جهت downstream به گره قبلی آغاز می‌کند.

UDP در اینجا handshake اتصال ندارد. `est` آماده بودن binding محلی line را نشان
می‌دهد، نه پاسخ دادن peer راه دور.

<a id="مدیریت-socket-محلی-worker"></a>

### مدیریت socket محلی worker {#worker-local-socket-management}

state مربوط به socket محلی worker و وابسته به خانواده آدرس است. پاسخ فقط از
endpoint‌های مورد انتظار پذیرفته می‌شود و source ناشناس دور ریخته می‌شود. رفتار
socket و source port محلی توسط connector مدیریت می‌شود و نباید به‌عنوان شناسه
line استفاده شود. pause و idle deadline به ازای line مستقل‌اند.

<a id="جریان-داده"></a>

### جریان داده {#data-flow}

از گره قبلی به remote peer:

```text
upstream payload -> UdpConnector -> UDP send
```

از remote peer به گره قبلی:

```text
UDP receive -> UdpConnector -> downstream payload
```

در هر دو balance mode، datagram دریافتی فقط از peer ثبت‌شده پذیرفته و به line مبدأ
هدایت می‌شود.

<a id="کنترل-جریان-و-buffering"></a>

### کنترل جریان و بافرگذاری {#flow-control-and-buffering}

در حالی که DNS یا resolution مقصد بسته در انتظار است، `UdpConnector` ممکن است payload‌های upstream را صف کند.

آستانه‌های صف فعلی:

| وضعیت صف | رفتار |
| --- | --- |
| رسیدن حجم یا هزینهٔ ظرفیت صف به `1 KiB` | گره قبلی pause می‌شود. |
| تکمیل write‌های pending | گره قبلی resume می‌شود. |
| عبور حجم یا هزینهٔ ظرفیت صف از `16 MiB` | UDP line بسته می‌شود. |

هنگام پذیرش در صف، پیش از اطلاع‌دادن به تولیدکننده، buffer، حسابداری صف و وضعیت ثبت‌شدهٔ Pause منتشر می‌شوند تا ترتیب FIFO در صورت ورود مجدد از طریق callback حفظ شود.
حجم منطقی و هزینهٔ ظرفیت buffer (شامل sbuf، padding و alignment) هرکدام سقف مستقل `16 MiB` دارند؛ مقدار برابر سقف پذیرفته می‌شود.
با رسیدن هرکدام به `1 KiB`، Pause ارسال می‌شود. buffer خالی نیز هزینهٔ ظرفیت دارد.
صف مقداردهی اولیه و صف‌های DNS مقصدها، یک بودجهٔ مشترک با حسابداری تدریجی برای هر line دارند.
عبور از سقف فقط همان association را می‌بندد و association‌های دیگر روی socket مشترک قابل استفاده می‌مانند.
ارسال datagram سیاست فعلی ارسال یا حذف را حفظ می‌کند و صف retry ندارد.

وقتی read در حالت pause است، `UdpConnector` datagram ورودی را در صف نمی‌گذارد و آن را دور می‌ریزد.

<a id="ارسال-udp-با-splice"></a>

### ارسال UDP با splice {#udp-splice-sending}

دریافت UDP همچنان از buffer عادی استفاده می‌کند. در زنجیره واجد شرایط روی Linux، ارسال UDP دادهٔ عادی یا prefix واقعی همراه با بدنهٔ pipe خصوصی را به‌صورت یک datagram به مقصد مشخص می‌پذیرد؛ datagram خالی نیز معتبر است. چیدمان‌های پشتیبانی‌شده از splice بین pipe و socket استفاده می‌کنند. برای pipe با fragment‌های زیاد، یا وقتی پیش از ارسال نتوان حد امن fragment‌ها را اثبات کرد، کل datagram پیش از شروع تجمیع روی socket به buffer عادی تبدیل می‌شود. دادهٔ بیش‌ازحد بزرگ بدون تقسیم رد می‌شود.

فشار پیش از شروع تجمیع همان سیاست drop فعلی را حفظ می‌کند و صف retry برای UDP ایجاد نمی‌شود. splice ناقص یا شکست commit پس از priming فقط socket مربوط را بازنشسته می‌کند و line‌های عادی وابسته از مسیر مالکشان بسته می‌شوند. بنابراین peer‌های یک socket مشترک ممکن است با هم بسته شوند. باقی‌ماندهٔ ناقص دوباره ارسال نمی‌شود و socket‌های دیگر فعال می‌مانند. سیاست خطای ارسال عادی تغییر نمی‌کند.

این پرچم بررسی پشتیبانی پلتفرم، `misc.splice`، کنارگذاشتن حالت بسته‌ای و پشتیبانی همهٔ گره‌های زنجیرهٔ نهایی پس از گسترش و ادغام را دور نمی‌زند. zero-copy سرتاسری یا بهبود کاراییِ اندازه‌گیری‌شده تضمین نمی‌شود.

این رفتار balancing بر اساس connection یا بسته روی line عادی، صف‌های pause و DNS و ارسال زمان بستن را پوشش می‌دهد. بازنشستگی socket پیش از callback‌ها binding‌های peer را حذف می‌کند و اگر مالک مبدأ line را ببندد، drain متوقف می‌شود. هنگام ارسال زمان بستن، Finish دریافت‌شده به فرستنده منعکس نمی‌شود.
