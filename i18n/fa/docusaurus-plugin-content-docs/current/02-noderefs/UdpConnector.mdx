# UdpConnector

`UdpConnector` آداپتور خروجی UDP است. یک socket UDP محلی می‌سازد، یک آدرس و پورت مقصد انتخاب می‌کند و datagramها را بین نود قبلی و remote UDP peer انتخاب‌شده جابه‌جا می‌کند.

جایگاه رایج:

```text
UdpListener -> ... -> UdpConnector -> سرویس UDP راه دور
```

این نود معمولاً انتهای یک UDP stream-style chain است.

## قابلیت‌ها

- ساختن یک socket UDP bound به یک port موقت محلی.
- انتخاب آدرس و پورت مقصد از تنظیمات ثابت، مقصدهای weighted، یا routing context line.
- Resolve کردن domain name از طریق یک `DomainResolver` داخلی async.
- ارسال payloadهای upstream از نود قبلی به remote UDP peer.
- ارسال datagramهای UDP دریافت‌شده به صورت downstream به نود قبلی.
- Drop کردن datagramهای peer غیرمنتظره در balance mode `"connection"`.
- ردیابی UDP lineها با idle timeout.
- اعمال socket option‌های اختیاری مثل `SO_REUSEADDR`، socket bufferها، `SO_MARK`، device binding و source-IP binding در صورت پشتیبانی.

`UdpConnector` مثل یک chain end رفتار می‌کند. توسط upstream `init` شروع می‌شود و به نود `next` نیاز ندارد.

## نمونه تنظیم

```json
{
  "name": "udp-out",
  "type": "UdpConnector",
  "settings": {
    "address": "example.com",
    "port": "random(40000,40100)",
    "reuseaddr": true,
    "large-send-buffer": true,
    "large-recv-buffer": true,
    "fwmark": 10,
    "interface": "eth0",
    "source-ip": "192.0.2.10",
    "domain-strategy": "prefer-ipv4"
  }
}
```

## نمونه چند مقصد weighted

```json
{
  "name": "udp-out",
  "type": "UdpConnector",
  "settings": {
    "balance-mode": "packet",
    "addresses": [
      {
        "address": "1.1.1.1",
        "port": 53,
        "weight": 3
      },
      {
        "address": "8.8.8.8",
        "port": "random(40000,40100)",
        "weight": 1
      }
    ],
    "reuseaddr": true,
    "large-send-buffer": true,
    "large-recv-buffer": true,
    "domain-strategy": "prefer-ipv4"
  }
}
```

`balance-mode` مستقیماً داخل `settings` قرار می‌گیرد، نه داخل هر object در `addresses`.

## فیلدهای ضروری

فیلدهای سطح بالا:

| فیلد | نوع | توضیح |
| --- | --- | --- |
| `name` | string | نام دلخواه نود. باید داخل فایل config یکتا باشد. |
| `type` | string | باید دقیقاً `"UdpConnector"` باشد. |
| `settings` | object | تنظیمات مقصد و socket. |

`settings` باید دقیقاً از یک سبک مقصد استفاده کند:

| سبک | فیلدهای لازم | توضیح |
| --- | --- | --- |
| مقصد تکی | `address` و `port` | هر line از همان قانون مقصد استفاده می‌کند. |
| مقصدهای weighted | `addresses` | هر line یا packet بسته به `balance-mode` یک مقصد weighted انتخاب می‌کند. |

`addresses` را با `address` یا `port` top-level ترکیب نکنید.

## انتخاب مقصد

### مقصد تکی

از `address` و `port` مستقیماً زیر `settings` استفاده کنید.

```json
{
  "settings": {
    "address": "example.com",
    "port": 53
  }
}
```

مقادیر معتبر برای `address`:

| مقدار | رفتار |
| --- | --- |
| string IPv4 | ارسال به آن آدرس IPv4. |
| string IPv6 | ارسال به آن آدرس IPv6. |
| string domain | Resolve کردن domain قبل از راه‌اندازی socket. |
| `"src_context->address"` | کپی آدرس source از routing context line. |
| `"dest_context->address"` | کپی آدرس destination از routing context line. |

مقادیر معتبر برای `port`:

| مقدار | رفتار |
| --- | --- |
| عدد | استفاده از آن پورت ثابت. باید `1` تا `65535` باشد. |
| string عددی | استفاده از آن پورت ثابت، مثلاً `"53"`. |
| `"src_context->port"` | کپی پورت source از routing context line. |
| `"dest_context->port"` | کپی پورت destination از routing context line. |
| `"random(x,y)"` | انتخاب یک پورت تصادفی در بازه inclusive `[x, y]`. |

`random(x,y)` به پورت‌های معتبر نیاز دارد و `x` نباید از `y` بزرگ‌تر باشد.

### مقصدهای weighted

از `addresses` برای انتخاب مقصد weighted استفاده کنید.

```json
{
  "settings": {
    "addresses": [
      {
        "address": "1.1.1.1",
        "port": 53,
        "weight": 3
      },
      {
        "address": "8.8.8.8",
        "port": 53,
        "weight": 1
      }
    ]
  }
}
```

هر object باید شامل باشد:

| فیلد | نوع | توضیح |
| --- | --- | --- |
| `address` | string | همان فرم‌های معتبر `address` در مقصد تکی. |
| `port` | عدد یا string | همان فرم‌های معتبر `port` در مقصد تکی، شامل `random(x,y)`. |
| `weight` | عدد صحیح مثبت | احتمال نسبی برای انتخاب این مقصد. |

برخلاف `TcpConnector`، objectهای مقصد `UdpConnector` در پیاده‌سازی فعلی override socket option per-entry ندارند. گزینه‌هایی مثل `reuseaddr`، `large-send-buffer`، `interface`، `source-ip` و `domain-strategy` در سطح top-level داخل `settings` تنظیم می‌شوند.

Parser کلید قدیمی غلط‌نویسی‌شده `adresses` را هم می‌پذیرد، اما config‌های جدید باید از `addresses` استفاده کنند. هر دو نام را همزمان تعریف نکنید.

## balance mode

`balance-mode` کنترل می‌کند انتخاب مقصد weighted چه زمانی انجام شود.

| مقدار | رفتار |
| --- | --- |
| `"connection"` | پیش‌فرض. یک مقصد weighted را در طول upstream `init` انتخاب کن؛ تمام payloadهای روی آن WaterWall line از همان مقصد استفاده می‌کنند. |
| `"packet"` | یک مقصد weighted را برای هر upstream payload packet قبل از ارسال انتخاب کن. |

`balance-mode` اختیاری است و پیش‌فرض `"connection"` است.

در mode `"packet"`، `UdpConnector` همچنان از یک socket UDP به ازای هر WaterWall line استفاده می‌کند. تمام مقصدهای انتخاب‌شده باید با خانواده آدرس آن socket سازگار باشند. برای مثال، از ترکیب مقصدهای فقط-IPv4 و فقط-IPv6 در یک لیست packet-balanced خودداری کنید مگر اینکه خانواده socket انتخاب‌شده بتواند به همه آن‌ها ارسال کند.

## تنظیمات اختیاری

| گزینه | نوع | پیش‌فرض | توضیح |
| --- | --- | --- | --- |
| `balance-mode` | string | `"connection"` | حالت انتخاب مقصد weighted: `"connection"` یا `"packet"`. |
| `reuseaddr` | boolean | `false` | فعال‌سازی `SO_REUSEADDR` روی socketهای UDP ساخته‌شده. |
| `large-send-buffer` | boolean یا عدد مثبت | `true` | تنظیم `SO_SNDBUF` روی socketهای UDP ساخته‌شده. |
| `large-recv-buffer` | boolean یا عدد مثبت | `true` | تنظیم `SO_RCVBUF` روی socketهای UDP ساخته‌شده. |
| `fwmark` | integer | تنظیم نشده | اعمال socket mark به سبک Linux از طریق `SO_MARK` در صورت پشتیبانی. |
| `interface` | string | تنظیم نشده | محدود کردن socketهای خروجی به یک network device محلی در صورت پشتیبانی. |
| `source-ip` | string | تنظیم نشده | Bind کردن socketهای خروجی به یک source IP محلی مشخص با source port موقت. |
| `domain-strategy` | string یا integer | `dns.domain-strategy` در core | نحوه انتخاب نتایج DNS برای مقصدهای domain. |

### گزینه‌های socket buffer

`large-send-buffer` و `large-recv-buffer` مقادیر زیر را می‌پذیرند:

| مقدار | معنا |
| --- | --- |
| `true` | استفاده از buffer socket بزرگ پیش‌فرض WaterWall که فعلاً `4194304` بایت است. |
| `false` | عدم تنظیم صریح این socket buffer؛ استفاده از پیش‌فرض kernel. |
| عدد مثبت | درخواست مستقیم آن تعداد بایت. |

هر دو گزینه پیش‌فرض buffer socket بزرگ WaterWall را برای socketهای UDP connector به‌کار می‌برند.

### domain strategy

`domain-strategy` نحوه تبدیل یک مقصد domain به آدرس IP را کنترل می‌کند وقتی DNS هر دو نتیجه IPv4 و IPv6 برمی‌گرداند.

اگر حذف شود، نود از مقدار `dns.domain-strategy` در core استفاده می‌کند. اگر مقدار core هم حذف شده باشد، WaterWall پیش‌فرض `"prefer-ipv4"` را به‌کار می‌برد.

مقادیر معتبر string:

| مقدار | رفتار |
| --- | --- |
| `"prefer-ipv4"` | اگر موجود باشد اولین نتیجه IPv4 را انتخاب کن؛ در غیر این صورت به IPv6 برگرد. |
| `"prefer-ipv6"` | اگر موجود باشد اولین نتیجه IPv6 را انتخاب کن؛ در غیر این صورت به IPv4 برگرد. |
| `"only-ipv4"` | فقط از نتایج DNS IPv4 استفاده کن. اگر هیچ‌کدام برنگشت، resolution برای آن line قابل استفاده نیست. |
| `"only-ipv6"` | فقط از نتایج DNS IPv6 استفاده کن. اگر هیچ‌کدام برنگشت، resolution برای آن line قابل استفاده نیست. |
| `"accept-dns-returned-order"` | از اولین آدرس قابل استفاده در ترتیب برگشتی resolver استفاده کن. |

مقادیر integer قدیمی هم پذیرفته می‌شوند:

| مقدار | استراتژی |
| --- | --- |
| `0` | `accept-dns-returned-order` |
| `1` | `prefer-ipv4` |
| `2` | `prefer-ipv6` |
| `3` | `only-ipv4` |
| `4` | `only-ipv6` |

### interface، source IP و egress pinning

`interface` socket UDP را به یک device محلی محدود می‌کند.

در Linux، WaterWall در صورت وجود از `SO_BINDTODEVICE` استفاده می‌کند. روی platformهایی که device binding ندارند، به bind کردن socket به آدرس IPv4 interface برمی‌گردد. اگر این fallback نتواند یک IP interface پیدا کند، راه‌اندازی socket شکست می‌خورد.

`source-ip` socket UDP را به یک source IP محلی مشخص با source port `0` bind می‌کند؛ این از OS یک port موقت می‌خواهد. خانواده آدرس باید با خانواده مقصد انتخاب‌شده مطابقت داشته باشد.

اگر `TunDevice` loop protection یک egress pin خودکار منتشر کرده باشد و `interface` حذف شده باشد، `UdpConnector` آن pin را اعمال می‌کند. در این حالت، `source-ip` به تنهایی interface pinned را override نمی‌کند؛ مطمئن شوید source IP به interface pinned/پیش‌فرض تعلق دارد یا `interface` را صریحاً تنظیم کنید.

## راه‌اندازی socket و lifecycle

در طول upstream `init`، `UdpConnector`:

1. آدرس و پورت مقصد را برای line انتخاب می‌کند.
2. `domain-strategy` را روی destination context line تنظیم می‌کند.
3. در صورت نیاز از طریق `DomainResolver` داخلی domain را resolve می‌کند.
4. بعد از اینکه مقصد یک آدرس IP شد یک socket UDP می‌سازد.
5. send و receive socket bufferها را اعمال می‌کند.
6. تنظیمات اختیاری `interface`، `fwmark`، `reuseaddr` و egress pin را اعمال می‌کند.
7. به `source-ip:0` وقتی `source-ip` تنظیم شده bind می‌کند، در غیر این صورت به آدرس wildcard برای خانواده آدرس انتخاب‌شده.
8. مقصد انتخاب‌شده را به عنوان peer address socket ذخیره می‌کند.
9. شروع به خواندن از socket می‌کند و downstream `est` را به نود قبلی می‌فرستد.

UDP اینجا handshake اتصال ندارد. `est` یعنی socket UDP محلی آماده است، نه اینکه remote peer پاسخ داده است.

## domain resolution

DNS resolution مبتنی بر connection-init async است. payloadهایی که قبل از تکمیل DNS می‌رسند در صف pending محدود resolver نگه داشته می‌شوند. اگر resolution شکست بخورد، line فوراً finish می‌شود.

در balance mode `"packet"`، domain nameهای داخل objectهای مقصد weighted به صورت lazy per destination object روی هر WaterWall line resolve می‌شوند:

- اولین packet که یک domain resolve‌نشده را انتخاب می‌کند یک DNS request async برای آن destination object شروع می‌کند
- packetهایی برای آن مقصد resolve‌نشده در یک صف محدود منتظر می‌مانند
- بعد از موفقیت resolution، آدرس resolve‌شده برای packetهای بعدی روی همان line استفاده می‌شود
- هیچ DNS cache زمانی و هیچ DNS request per-packet وجود ندارد

## جریان داده

از نود قبلی به remote peer:

```text
payload upstream -> UdpConnector -> ارسال UDP
```

از remote peer به نود قبلی:

```text
دریافت UDP -> UdpConnector -> payload downstream
```

در mode `"connection"`، datagramهای ورودی فقط از remote peer تکی انتخاب‌شده پذیرفته می‌شوند. datagramهای peer غیرمنتظره نادیده گرفته می‌شوند.

در mode `"packet"`، datagramهای دریافت‌شده روی socket connector پذیرفته می‌شوند تا پاسخ‌ها از هر مقصد packet-balanced بتوانند برگردند حتی اگر خارج از ترتیب برسند.

## کنترل جریان و buffering

در حالی که DNS یا resolution مقصد packet در انتظار است، `UdpConnector` ممکن است payloadهای upstream را صف کند.

آستانه‌های صف فعلی:

| وضعیت صف | رفتار |
| --- | --- |
| بیشتر از `1 KB` در صف | نود قبلی pause می‌شود. |
| تکمیل write‌های pending | نود قبلی resume می‌شود. |
| بیشتر از `16 MB` در صف | UDP line بسته می‌شود. |

وقتی read‌ها paused هستند، `UdpConnector` datagramهای دریافت‌شده را صف نمی‌کند. یک datagram که در حالی که read‌ها paused هستند برسد drop می‌شود.

## idle timeout

هر UDP line در یک جدول idle ردیابی می‌شود.

timeout‌های فعلی:

| وضعیت | timeout |
| --- | --- |
| بعد از مقداردهی اولیه | حدود `30 ثانیه` |
| بعد از ادامه ترافیک | حدود `300 ثانیه` |

اگر UDP line منقضی شود، socket بسته می‌شود و downstream `finish` به نود قبلی فرستاده می‌شود.

## نکات و هشدارها

- `UdpConnector` یک chain end خروجی است و به `next` نیاز ندارد.
- DNS resolution async است و از `domain-strategy` انتخاب‌شده استفاده می‌کند.
- objectهای مقصد زیر `addresses` فقط `address`، `port` و `weight` دارند؛ socket option‌ها تنظیمات top-level هستند.
- `fwmark` و device binding به platform وابسته هستند.
- `fwmark` روی Windows در دسترس نیست.
- read‌های paused datagramهای ورودی را به جای buffer کردن drop می‌کنند.
- برای رفتار UDP stateless در سطح packet، `UdpStatelessSocket` ممکن است مناسب‌تر از `UdpConnector` باشد.
