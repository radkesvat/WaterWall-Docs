# TcpUdpListener

## نمای کلی {#overview}


`TcpUdpListener` یک wrapper در ابتدای زنجیره است که `TcpListener` و `UdpListener` را در یک گره ترکیب می‌کند. با تنظیمات یکسان، یک listener داخلی برای TCP و یکی برای UDP می‌سازد تا یک ورودی WaterWall بتواند هر دو نوع ترافیک را روی آدرس و مجموعه پورت‌های یکسان بپذیرد.

این گره TCP را به UDP یا UDP را به TCP تبدیل نمی‌کند؛ فقط ترافیک ورودی هر دو adapter را به یک گره بعدی مشترک می‌فرستد.

<a id="جایگاه-رایج"></a>

## جایگاه معمول در زنجیره {#typical-placement}

وقتی یک ورودی باید هم TCP و هم UDP را بپذیرد، از `TcpUdpListener` استفاده کنید:

```text
DNS relay: TcpUdpListener -> TcpUdpConnector
SOCKS5:    TcpUdpListener -> Socks5Server -> TcpUdpConnector
```

گره بعدی باید توان کار با ترافیک ورودی را داشته باشد. اگر در محیط production هر دو نوع TCP و UDP وارد می‌شوند، گره بعدی باید هم line‌های معمولی TCP و هم line‌های peer در UDP را پشتیبانی کند، یا آن‌ها را بر اساس protocol مسیریابی کند.

`TcpUdpListener` ورودی استاندارد داخلی برای
[`Socks5Server`](./Socks5Server.mdx) با `udp: true` است: child نوع TCP، ‏control
connection مربوط به SOCKS5 را می‌پذیرد و child نوع UDP، ‏provider مربوط به endpoint
پویا را فراهم می‌کند. یک `TcpListener` ساده فقط SOCKS5 TCP/`CONNECT` را پشتیبانی
می‌کند و نمی‌تواند نیاز `UDP ASSOCIATE` را برآورده کند.


## نمونهٔ کاربردی ساده {#minimal-practical-example}

### نمونهٔ ساده {#basic-example}

<a id="یک-ورودی-dns-محلی-برای-tcp-و-udp"></a>

#### یک ورودی DNS محلی برای TCP و UDP {#one-local-dns-entry-for-tcp-and-udp}

```json
{
  "name": "local-dns-relay",
  "nodes": [
    {
      "name": "dns-in",
      "type": "TcpUdpListener",
      "settings": {
        "address": "127.0.0.1",
        "port": 1053
      },
      "next": "dns-out"
    },
    {
      "name": "dns-out",
      "type": "TcpUdpConnector",
      "settings": {
        "address": "192.0.2.53",
        "port": 53
      }
    }
  ]
}
```
این پیکربندی کامل گره‌ها را در فایلی از `core.json.configs` ذخیره کنید. DNS client را
برای `127.0.0.1:1053` تنظیم کنید و `192.0.2.53` را با resolverی جایگزین کنید که روی
پورت 53 هر دو TCP و UDP را می‌پذیرد. درخواست TCP همچنان TCP و درخواست UDP همچنان
UDP می‌ماند. WaterWall DNS cache نمی‌سازد و پروتکل‌ها را به هم تبدیل نمی‌کند؛ هر دو
از آدرس و پورت backend یکسان استفاده می‌کنند.


## پیکربندی {#configuration}

<a id="فیلدهای-ضروری"></a>

### فیلدهای ضروری {#required-fields}

فیلدهای سطح بالا:

| فیلد | نوع | توضیح |
| --- | --- | --- |
| `name` | string | نام دلخواه گره. باید داخل فایل config یکتا باشد. |
| `type` | string | باید دقیقاً `"TcpUdpListener"` باشد. |
| `settings` | object | تنظیمات مشترک هر دو listener داخلی؛ باید objectی غیرخالی باشد. |
| `next` | string | گره‌ای که هم TCP line‌ها و هم UDP peer line‌ها را دریافت می‌کند. |

فیلدهای ضروری داخل `settings`:

| فیلد | نوع | توضیح |
| --- | --- | --- |
| `address` | string | آدرس bind محلی برای هر دو child listener. |
| `port` یا `port-range` | عدد، آرایه، یا آرایه بازه | port‌هایی که هر دو listener TCP و UDP استفاده می‌کنند. باید دقیقاً یکی از این دو فیلد را بنویسید. |

<a id="تنظیم-پورت"></a>

### تنظیم پورت {#port-configuration}

syntax تعریف پورت در `TcpUdpListener` همان syntax مورد استفاده `TcpListener` و `UdpListener` است.

<a id="یک-پورت"></a>

#### یک پورت {#single-port}

```json
{
  "settings": {
    "address": "0.0.0.0",
    "port": 443
  }
}
```

<a id="لیست-پورت-مشخص"></a>

#### فهرست صریح پورت‌ها {#explicit-port-list}

```json
{
  "settings": {
    "address": "0.0.0.0",
    "port": [
      443,
      8443,
      2083
    ]
  }
}
```

این حالت فقط روی پورت‌های لیست‌شده برای هر دو TCP و UDP گوش می‌دهد.

<a id="بازه-پیوسته"></a>

#### بازهٔ پیوستهٔ پورت {#contiguous-port-range}

```json
{
  "settings": {
    "address": "0.0.0.0",
    "port-range": [
      40000,
      40100
    ]
  }
}
```

`port-range` باید یک آرایه دو عضوی باشد: `[min, max]`.

<a id="تنظیمات-اختیاری"></a>

### تنظیمات اختیاری {#optional-settings}

چون object یکسان `settings` به هر دو listener داخلی داده می‌شود، بیشتر گزینه‌ها همان‌هایی هستند که در صفحه‌های `TcpListener` و `UdpListener` توضیح داده شده‌اند.

| گزینه | گره داخلی متأثر | توضیح |
| --- | --- | --- |
| `nodelay` | گره داخلی TCP | فعال‌سازی `TCP_NODELAY` روی socket‌های TCP پذیرفته‌شده. |
| `large-send-buffer` | گره‌های داخلی TCP و UDP | تنظیم `SO_SNDBUF` در صورت پشتیبانی. |
| `large-recv-buffer` | گره‌های داخلی TCP و UDP | تنظیم `SO_RCVBUF` در صورت پشتیبانی. |
| `interface` | گره‌های داخلی TCP و UDP | محدود کردن socket‌ها به یک interface محلی در صورت پشتیبانی. |
| `fwmark` | گره‌های داخلی TCP و UDP | اعمال socket mark به سبک Linux در صورت پشتیبانی. |
| `balance-group` | گره‌های داخلی TCP و UDP | listener‌های سازگار و هم‌پورت را برای توزیع sticky در یک گروه قرار می‌دهد. |
| `balance-interval` | گره‌های داخلی TCP و UDP | مدت حفظ شدن client یا peer تکراری روی یک عضو از balance group. |
| `initial-idle-timeout-ms` | گره داخلی TCP | timeout اولیه idle قبل از فعالیت payload TCP سمت listener. |
| `active-idle-timeout-ms` | گره داخلی TCP | timeout idle بعد از شروع فعالیت TCP. |
| `multiport-backend` | گره‌های داخلی TCP و UDP | backend برای `port-range` پیوسته: `"iptables"` یا `"socket"`. |
| `whitelist` | گره‌های داخلی TCP و UDP | IP‌ها و محدوده‌های CIDR مجاز برای client یا peer. |
| `blacklist` | گره‌های داخلی TCP و UDP | IP‌ها و محدوده‌های CIDR مسدود برای client یا peer. |

برای جزئیات گزینه‌های socket، پیش‌فرض timeout‌ها و تنظیمات multiport، به صفحه‌های `TcpListener` و `UdpListener` مراجعه کنید.


## کاربرد و رفع اشکال {#usage-and-troubleshooting}

<a id="نمونه-multiport"></a>

### نمونهٔ چندپورتی {#multiport-example}

```json
{
  "name": "mixed-public-entry",
  "type": "TcpUdpListener",
  "settings": {
    "address": "0.0.0.0",
    "port": [
      443,
      8443
    ],
    "nodelay": true,
    "large-send-buffer": true,
    "large-recv-buffer": true,
    "interface": "eth0",
    "fwmark": 10,
    "balance-group": "public-mixed",
    "balance-interval": 30000,
    "multiport-backend": "socket",
    "whitelist": [
      "192.0.2.0/24",
      "2001:db8::/64"
    ],
    "blacklist": [
      "192.0.2.99/32"
    ]
  },
  "next": "next-node"
}
```

همین فهرست پورت برای TCP و UDP به کار می‌رود. پورت TCP شمارهٔ `443` و پورت UDP شمارهٔ `443` از پروتکل‌های متفاوت سوکت استفاده می‌کنند و می‌توانند هم‌زمان bind شوند.

<a id="اشتباههای-رایج"></a>

### اشتباه‌های رایج {#common-mistakes}

- از `TcpUdpListener` به‌عنوان protocol converter استفاده نکنید؛ هر دو protocol را می‌پذیرد، اما یکی را به دیگری تبدیل نمی‌کند.
- آن را به گره بعدی که فقط TCP را می‌فهمد وصل نکنید اگر ترافیک UDP هم ممکن است بیاید.
- در توپولوژی `Socks5Server` که UDP را فعال می‌کند آن را با `TcpListener` جایگزین
  نکنید؛ `TcpListener` provider پویای UDP ندارد.
- نمی‌توان برای TCP و UDP دو مجموعه port متفاوت روی این wrapper تعریف کرد؛ هر دو listener همان `settings` را دریافت می‌کنند.
- metadata مربوط به source protocol را پیش از بازگشت callback‌های downstream به این گره حذف یا خراب نکنید.


## رفتار پیشرفته {#advanced-behavior}

<a id="واگذاری-endpoint-پویای-udp"></a>

### واگذاری endpoint پویای UDP {#dynamic-udp-endpoint-delegation}

برای یک tunnel پروتکلی سازگار در ادامهٔ همان زنجیره، از جمله `Socks5Server`،
‏`TcpUdpListener` قابلیت endpoint پویای UDP با رابط نوع‌دار را به گره داخلی
[`UdpListener`](./UdpListener.mdx) واگذار می‌کند. `Socks5Server` این provider را
به‌صورت خودکار از مسیر قبلی نهایی‌شدهٔ خود پیدا می‌کند؛ هیچ نام گره provider یا
setting مربوط به JSON API لازم نیست. مالک socket پویا، registry محلی worker و هر
line عادی ساخته‌شده توسط provider همچنان خود child است؛ wrapper فقط زنجیره عادی
callback را حفظ می‌کند.

```text
dynamic UDP child endpoint -> UdpListener child -> TcpUdpListener -> next chain
```

در مسیر بازگشت، wrapper با protocol منبع line، ‏child UDP را انتخاب می‌کند تا پاسخ
downstream به endpoint اختصاصی برسد. Wrapper نباید lifecycle endpoint child را
جداگانه close، drain یا دوباره اجرا کند. تخصیص پویا از یک port موقت UDP در child
استفاده می‌کند، نه port ثابت TCP/UDP تنظیم‌شده روی wrapper.

Child پیش از ساخت line، ‏IP نرمال‌شدهٔ مورد انتظار endpoint را بررسی می‌کند؛
source port غیرصفر باید دقیقاً برابر باشد و source port صفر نخستین بسته معتبر را
pin می‌کند. موارد نامطابق بی‌صدا drop می‌شوند و TCP control line مرتبط را
نمی‌بندند یا به آن پیام نمی‌دهند. تنظیم `large-*-buffer: false` نیز برای socket
پویای child مقدار پیش‌فرض Kernel را دست‌نخورده می‌گذارد.


## جزئیات پیاده‌سازی {#implementation-details}

<a id="جریان-runtime"></a>

### جریان اجرا {#runtime-flow}

هنگام راه‌اندازی، `TcpUdpListener` دو tunnel داخلی می‌سازد:

- `TcpListener` با نامی شبیه `<node-name>.tcp-listener`
- `UdpListener` با نامی شبیه `<node-name>.udp-listener`

هر دو گره داخلی در زنجیره قرار می‌گیرند و مالک socket‌های واقعی و lifecycle مربوط به line‌های خود هستند:

- `TcpListener` داخلی socket‌های TCP را می‌پذیرد و line‌های TCP را می‌سازد
- `UdpListener` داخلی برای peer‌های UDP line می‌سازد
- callback‌های upstream هر دو گره داخلی وارد `TcpUdpListener` می‌شوند
- `TcpUdpListener` callback‌های upstream شامل `Init`، `Payload`، `Pause`، `Resume`، `Est` و `Finish` را به `next` می‌فرستد

در مسیر downstream، callback گره بعدی به `TcpUdpListener` می‌رسد. wrapper سپس source protocol ثبت‌شده روی line را بررسی می‌کند:

| فرادادهٔ پروتکل مبدأ | گره داخلی در مسیر downstream |
| --- | --- |
| TCP | گره داخلی `TcpListener` |
| UDP | گره داخلی `UdpListener` |
| پرچم‌های TCP/UDP ناموجود یا مبهم | خطای مهلک در پیکربندی یا مسیریابی |

به همین دلیل، گره‌های بعد از `TcpUdpListener` باید metadata مربوط به source protocol را روی line حفظ کنند.

<a id="مالکیت-line"></a>

### مالکیت line {#line-ownership}

`TcpUdpListener` خودش per-line state ندارد، line نمی‌سازد و `lineDestroy()` را هم فراخوانی نمی‌کند.

مالکیت هر line در اختیار همان adapter داخلی می‌ماند که آن را ساخته است:

- TCP line‌ها متعلق به child داخلی `TcpListener` هستند
- UDP peer line‌ها متعلق به child داخلی `UdpListener` هستند

<a id="متادیتای-نود"></a>

### فرادادهٔ گره {#node-metadata}

متادیتای برگرفته از کد منبع:

| ویژگی | مقدار |
| --- | --- |
| پرچم‌های گره | `kNodeFlagChainHead` &#124; `kNodeFlagSupportsSplice` |
| `can_have_prev` | `false` |
| `can_have_next` | `true` |
| `layer_group` | `kNodeLayer4` |
| `layer_group_prev_node` | `kNodeLayerNone` |
| `layer_group_next_node` | `kNodeLayer4` |
| `required_padding_left` | `0` بایت |

<a id="ارسال-udp-با-splice"></a>

### ارسال UDP با splice {#udp-splice-sending}

دریافت UDP همچنان از buffer عادی استفاده می‌کند. در زنجیره واجد شرایط روی Linux، ارسال UDP دادهٔ عادی یا prefix واقعی همراه با بدنهٔ pipe خصوصی را به‌صورت یک datagram به مقصد مشخص می‌پذیرد؛ datagram خالی نیز معتبر است. چیدمان‌های پشتیبانی‌شده از splice بین pipe و socket استفاده می‌کنند. برای pipe با fragment‌های زیاد، یا وقتی پیش از ارسال نتوان حد امن fragment‌ها را اثبات کرد، کل datagram پیش از شروع تجمیع روی socket به buffer عادی تبدیل می‌شود. دادهٔ بیش‌ازحد بزرگ بدون تقسیم رد می‌شود.

فشار پیش از شروع تجمیع همان سیاست drop فعلی را حفظ می‌کند و صف retry برای UDP ایجاد نمی‌شود. splice ناقص یا شکست commit پس از priming فقط socket مربوط را بازنشسته می‌کند و line‌های عادی وابسته از مسیر مالکشان بسته می‌شوند. بنابراین peer‌های یک socket مشترک ممکن است با هم بسته شوند. باقی‌ماندهٔ ناقص دوباره ارسال نمی‌شود و socket‌های دیگر فعال می‌مانند. سیاست خطای ارسال عادی تغییر نمی‌کند.

این پرچم بررسی پشتیبانی پلتفرم، `misc.splice`، کنارگذاشتن حالت بسته‌ای و پشتیبانی همهٔ گره‌های زنجیرهٔ نهایی پس از گسترش و ادغام را دور نمی‌زند. zero-copy سرتاسری یا بهبود کاراییِ اندازه‌گیری‌شده تضمین نمی‌شود.

هر دو listener داخلی پرچم قابلیت خود را حفظ می‌کنند. مسیر TCP فقط وقتی کل زنجیره گسترش‌یافته واجد شرایط باشد از مسیر فعلی splice برای دریافت و ارسال استفاده می‌کند؛ دریافت UDP عادی می‌ماند. انتخاب پروتکل تغییر نمی‌کند.
