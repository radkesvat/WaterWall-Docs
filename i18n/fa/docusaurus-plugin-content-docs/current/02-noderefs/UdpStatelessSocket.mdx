# UdpStatelessSocket


## نمای کلی {#overview}


`UdpStatelessSocket` یک adapter در ابتدای زنجیره و در لبه UDP است. یک UDP socket را bind می‌کند، datagram‌ها را از peer‌های مختلف می‌گیرد و برای flow ورودی هر peer یک line معمولی WaterWall می‌سازد.

کاربرد اصلی این گره پشتیبانی از اجزایی مانند `WireGuardServer` است؛ جایی که یک سوکت UDP باید هم برای peerهای پیکربندی‌شده داده بفرستد و هم بسته‌های peerهایی را بپذیرد که خودشان نخست با سوکت تماس می‌گیرند.


<a id="جایگاه-رایج"></a>

## جایگاه معمول در زنجیره {#typical-placement}

چیدمان پشتیبانی‌شده با `UdpStatelessSocket` آغاز می‌شود:

```text
UdpListener -> WireGuardServer(mode=packet) -> packet side node
```

قرارگیری فقط در ابتدای زنجیره، تصمیم فعلی طراحی است، نه محدودیتی موقت. وجود گره قبلی یا نبود گره بعدی هنگام راه‌اندازی رد می‌شود. قرارگیری در انتهای زنجیره و مقداردهی اولیهٔ peer در جهت downstream غیرفعال است.

`UdpStatelessSocket` برای لبهٔ UDP زنجیره در نظر گرفته شده است: جایی که یک جزء برای ارسال و دریافت UDP به یک سوکت نیاز دارد، اما peerهای دریافتی باید همچنان lineها و چرخهٔ عمر جداگانه‌ای در WaterWall داشته باشند.

برای زنجیره کامل، مقصد بسته رمزگشایی‌شده را انتخاب کنید:

```text
OS packet interface: UdpListener -> WireGuardServer(mode=packet) -> TunDevice
TCP/UDP gateway:      UdpListener -> WireGuardServer(mode=packet) -> PacketsToConnection -> TcpUdpConnector
```

[جفت WireGuard](./WireGuardServer.mdx) config کامل گره‌های client و
server را دارد. `endpoint` هر peer، آدرس UDP سمت مقابل را انتخاب می‌کند؛
`listen-address` و `listen-port` این گره، socket محلی را تعیین می‌کنند. برای
حالت gateway از [connector با حفظ مقصد](./PacketsToConnection.mdx#typical-placement)
استفاده کنید.



## نمونهٔ کاربردی ساده {#minimal-practical-example}

این یک **قطعهٔ پیکربندی گره** است، نه پیکربندی کامل. آن را در آرایهٔ `nodes` قرار دهید و گره‌های مجاور بالا را متصل کنید.

```json
{
  "name": "wg-udp-socket",
  "type": "UdpStatelessSocket",
  "settings": {
    "listen-address": "0.0.0.0",
    "listen-port": 51820
  },
  "next": "wg"
}
```

گره `wg` را به‌عنوان گره WireGuard خود، همراه با کلیدها، peerها و سمت بستهٔ آن پیکربندی کنید. این قطعه فقط endpoint محلی bind مربوط به UDP را انتخاب می‌کند.


## پیکربندی {#configuration}


<a id="تنظیمات-ضروری"></a>

### فیلدهای الزامی JSON {#required-json-fields}



#### فیلدهای سطح بالا {#top-level-fields}

- `name` `(string)`: نام انتخابی کاربر برای این گره.
- `type` `(string)`: باید دقیقاً `"UdpStatelessSocket"` باشد.


#### `settings` {#settings}

- `listen-address` `(string)`: آدرس IP محلی bind؛ باید یک رشتهٔ IP معتبر باشد.
- `listen-port` `(integer)`: پورت UDP محلی bind؛ بازهٔ معتبر `0` تا `65535` است.

<a id="تنظیمات-اختیاری"></a>

<a id="رفتار-interface-و-source-ip"></a>

### فیلدهای اختیاری `settings` {#optional-settings-fields}

- `interface` `(string)`: در صورت پشتیبانی، سوکت UDP را به یک دستگاه شبکهٔ محلی محدود می‌کند. در Linux از `SO_BINDTODEVICE` استفاده می‌شود؛ در پلتفرم بدون bind به device، اگر `source-ip` تنظیم نشده باشد، WaterWall سوکت را به آدرس IPv4 همان interface bind می‌کند.
- `fwmark` `(integer)`: نشان سوکت به سبک Linux که در پلتفرم دارای `SO_MARK` پیش از bind روی سوکت اعمال می‌شود. پیش‌فرض: تنظیم نشده.
- `source-ip` `(string)`: IP مبدأ محلی مشخص برای سوکت UDP. چون یک سوکت برای ارسال و دریافت استفاده می‌شود، این مقدار جای `listen-address` را می‌گیرد. اگر loop protection در `TunDevice` یک egress pin خودکار منتشر کرده باشد، `source-ip` به‌تنهایی آن را تغییر نمی‌دهد. اطمینان یابید IP مبدأ متعلق به interface انتخاب‌شده یا پیش‌فرض است، یا `interface` را صریح تنظیم کنید.
- `large-send-buffer` `(boolean یا integer مثبت)`: مقدار `SO_SNDBUF` را تنظیم می‌کند. `true` اندازهٔ بزرگ پیش‌فرض WaterWall، در حال حاضر `16777216` بایت، را درخواست می‌کند؛ `false` پیش‌فرض kernel را تغییر نمی‌دهد؛ integer مثبت تعداد بایت درخواستی است. پیش‌فرض: `true`.
- `large-recv-buffer` `(boolean یا integer مثبت)`: مقدار `SO_RCVBUF` را تنظیم می‌کند. `true` اندازهٔ بزرگ پیش‌فرض WaterWall، در حال حاضر `16777216` بایت، را درخواست می‌کند؛ `false` پیش‌فرض kernel را تغییر نمی‌دهد؛ integer مثبت تعداد بایت درخواستی است. پیش‌فرض: `true`.
- `verbose` `(boolean)`: گزارش debug هر بسته را برای datagramهای دریافتی و ارسالی peerها فعال می‌کند. پیش‌فرض: `false`.

<a id="رفتار-dns"></a>

### رفتار DNS {#dns-behaviour}


resolve کردن نام دامنه یعنی پیدا کردن آدرس IP مقصد datagram. پاسخ‌های روی line
یک peer ورودی از IP و پورت ذخیره‌شدهٔ همان peer استفاده می‌کنند و به lookup نیاز
ندارند. datagramهای خروجی دیگر از مقصد line استفاده می‌کنند. فقط نام دامنهٔ
resolve‌نشده به resolve نیاز دارد؛ IP عددی یا مقصدی که از قبل resolve شده باشد
بدون lookup ارسال می‌شود. پاسخ موجود در cache هم می‌تواند نیاز به lookup تازه را
برطرف کند.

با حذف `dns-behaviour`، resolve محلی در حالت `native` فعال است و از اولویت آدرس
در destination context استفاده می‌کند؛ اگر اولویتی مشخص نشده باشد، ترتیب پاسخ DNS
به کار می‌رود. با غیرفعال بودن resolve، datagram خروجی با نام دامنهٔ resolve‌نشده
دور ریخته می‌شود.

این lookup را با `settings.dns-behaviour` تنظیم کنید:

```json
{
  "dns-behaviour": {
    "resolve": true,
    "mode": "direct",
    "strategy": "prefer-ipv4",
    "servers": ["203.0.113.53:53"]
  }
}
```

این آدرس نمونهٔ مستندات است؛ آن را با آدرس resolver خود جایگزین کنید.

| فیلد | معنی |
| --- | --- |
| `resolve` | boolean اجباری: `true` اجازهٔ lookup نام دامنهٔ resolve‌نشده را می‌دهد و `false`، lookup محلی را غیرفعال می‌کند. |
| `mode` | `native` (پیش‌فرض هنگام فعال بودن)، `direct` یا `chain`. |
| `strategy` | یکی از `core-settings`، `accept-dns-returned-order`، `prefer-ipv4`، `prefer-ipv6`، `only-ipv4` یا `only-ipv6`؛ حذف آن اولویت پیش‌فرض آدرس مصرف‌کننده را به کار می‌برد. |
| `servers` | ۱ تا ۳۲ endpoint عددی IP، IP:port یا [IPv6]:port؛ در حالت‌های `direct` و `chain` اجباری و در `native` ممنوع. |
| `dns-next` | نام غیرخالی ورودی DNS، فقط در حالت `chain`. |

`native` از تنظیمات DNS در core و resolver مشترک worker استفاده می‌کند. هنگام
فعال بودن resolve محلی، این حالت پیش‌فرض انتقال DNS است.

`direct` درخواست‌های DNS را از طریق یک connector خصوصی TCP/UDP در WaterWall به
سرورهایی که مشخص کرده‌اید می‌فرستد.

`chain` درخواست‌های DNS را از زنجیره انتخابی می‌فرستد. برای محافظت از آن‌ها، مسیری
رمزنگاری‌شده مانند VPN خود را انتخاب کنید؛ این حالت به‌تنهایی درخواست‌ها را
رمزنگاری نمی‌کند. مسیر DNS باید هم درخواست‌های UDP و هم fallback روی TCP را حمل
کند. خطای route یا lookup باعث تغییر به DNS بومی یا حالت دیگر نمی‌شود.

در حالت `chain`، مقدار `dns-next` را نام یک شاخهٔ DNS جدا بگذارید که هم UDP و هم
TCP را پشتیبانی کند. این شاخه نباید از قبل به گره دیگری تعلق داشته باشد. این گره
شاخهٔ DNS پیش‌فرض ندارد و نام‌بردن از خود آن مجاز نیست.

شکل غیرفعال دقیقاً `"dns-behaviour": {"resolve": false}` است و فیلدهای `mode`، `strategy`، `servers` و `dns-next` را رد می‌کند. object تهی، null، نوع غیرobject، فیلد ناشناخته و strategy عددی رد می‌شوند. نام strategy باید یکی از رشته‌های canonical بالا با حروف کوچک باشد. `core-settings` فقط اولویت آدرس را انتخاب می‌کند و انتقال DNS را تغییر نمی‌دهد.

با `resolve: false`، آماده‌سازی مقصد همچنان اجرا می‌شود. IP عددی یا مقصد از قبل resolve‌شده کار می‌کند؛ نام resolve‌نشده از مسیر عادی خطای line یا datagram رد می‌شود و به DNS بومی برنمی‌گردد.

این سیاست lookup ناهمگام datagramهای خروجی همین socket را پوشش می‌دهد. `next` عادی نقش peer و line دارد و ورودی ضمنی DNS نیست. نام endpoint همتای WireGuard هنوز از resolve همگام و مستقل هنگام startup استفاده می‌کند.

مثال‌های `native`، `direct` و `chain` محافظت‌شده و محدودیت گزینه‌های core را در [DomainResolver](./DomainResolver.mdx) ببینید. این سیاست فقط lookupهای متعلق به همین گره را کنترل می‌کند؛ fake DNS در PTC، DNS سیستم در TunDevice و همهٔ منابع DNS برنامه را تغییر نمی‌دهد.



## کاربرد و رفع اشکال {#usage-and-troubleshooting}


<a id="نمونه-تنظیم"></a>

### نمونهٔ پیکربندی {#configuration-example}

نمونهٔ زیر یک قطعهٔ گره است. `interface`، `source-ip` و `fwmark` گزینه‌های اختیاری وابسته به میزبان هستند؛ اگر interface، آدرس و policy routing میزبان برای آن‌ها تنظیم نشده است، حذفشان کنید.


```json
{
  "name": "wg-udp-socket",
  "type": "UdpStatelessSocket",
  "settings": {
    "listen-address": "0.0.0.0",
    "listen-port": 51820,
    "interface": "eth0",
    "fwmark": 10,
    "large-send-buffer": true,
    "large-recv-buffer": true,
    "source-ip": "192.0.2.10",
    "verbose": false
  },
  "next": "wg"
}
```


<a id="خطاهای-رایج"></a>

### نکات و محدودیت‌ها {#notes-and-caveats}

- `UdpStatelessSocket` برای ترافیک لبهٔ UDP، به‌ویژه کنار `WireGuardServer` در نظر گرفته شده است.
- برای lineهایی که مالکشان نیست، ارسال خروجی به routing context معتبر وابسته است؛ به‌خصوص `dest_ctx` باید پیش از ارسال payload مقداردهی شود.
- برای lineهای بسته‌ای، ارسال دامنهٔ حل‌نشده پیش از resolve یک نسخه از دامنه و پورت همان datagram می‌گیرد، چون routing context مربوط به line بسته‌ای فرادادهٔ موقت است.
- peerهای UDP دریافتی lineهای معمولی جداگانه دارند؛ lineهای بسته‌ای هنگام اجرا نابود نمی‌شوند.
- `fwmark` و bind به device وابسته به پلتفرم هستند. `fwmark` در Windows در دسترس نیست.
- parser مربوط به JSON به `listen-address` و `listen-port` نیاز دارد؛ `source-ip` می‌تواند آدرس مؤثر bind محلی را جایگزین کند.


## جزئیات پیاده‌سازی {#implementation-details}



### چه کاری انجام می‌دهد {#what-it-does}

- یک سوکت UDP را روی آدرس و پورت محلی پیکربندی‌شده bind می‌کند.
- datagramهای UDP را از هر peer راه دور دریافت می‌کند.
- جریان ورودی peer را با endpointهای peer و محلی و هویت تونل کلیدگذاری می‌کند.
- برای هر جریان ورودی peer یک line معمولی می‌سازد و datagramهای دریافتی را روی آن می‌فرستد.
- datagram خروجی روی lineهای peer که خود گره مالکشان است را به endpoint ذخیره‌شدهٔ همان peer برمی‌گرداند.
- datagram خروجی روی lineهای دیگر را به مقصد ذخیره‌شده در routing context همان line می‌فرستد.
- ترافیک دریافتی peer را upstream به `next` می‌فرستد و datagramهای خروجی را downstream از `next` می‌پذیرد.

lineهای peer ورودی مانند `UdpListener` عمر idle دارند: init timeout کوتاه و پس از شروع ترافیک keepalive timeout طولانی‌تر.


### رفتار جزئی {#detailed-behavior}


<a id="مسیر-دریافت"></a>

#### مسیر دریافت peer {#peer-receive-path}


وقتی یک datagram UDP به سوکت bindشده برسد:

- `UdpStatelessSocket` از endpoint همتای UDP، endpoint محلی سوکت و هویت این نمونهٔ تونل، کلید جریان می‌سازد.
- اگر جریان متناظری وجود نداشته باشد، یک line عادی می‌سازد، وضعیت این تونل برای آن line را مقداردهی اولیه می‌کند و `Init` را در جهت upstream به `next` می‌فرستد.
- endpoint همتا را در context مسیریابی مبدأ line می‌نویسد و پورت محلی listener را ثبت می‌کند.
- بدنهٔ datagram را روی line همان peer می‌فرستد.

datagramهای دریافتی همواره از ابتدای زنجیره وارد می‌شوند و در جهت upstream به `next` می‌روند.


<a id="مسیر-ارسال"></a>

#### مسیر ارسال {#send-path}


وقتی payload از طریق `UdpStatelessSocket` ارسال می‌شود:

- اگر line برای یک peer ورودی ساخته شده باشد، datagram به endpoint ذخیره‌شدهٔ همان peer ارسال می‌شود.
- در غیر این صورت، تونل آدرس مقصد را از `l->routing_context.dest_ctx` می‌خواند.
- اگر resolve محلی فعال باشد و پاسخ ذخیره‌شده‌ای وجود نداشته باشد، نام دامنهٔ resolve‌نشده به‌صورت ناهمگام lookup می‌شود؛ با غیرفعال بودن resolve، همان datagram دور ریخته می‌شود.
- نتایج ناهمگام بر اساس دامنه، پورت و strategy به مدت 30 دقیقه در یک cache ثابت FIFO با 256 ورودی ذخیره می‌شوند. کلیدهای موجود در همان محل به‌روز می‌شوند، ورودی‌های منقضی پیش از درج ورودی تازه آزاد می‌شوند و با پرشدن ظرفیت، قدیمی‌ترین ورودی حذف می‌شود.
- IP و پورت مقصد به آدرس سوکت تبدیل می‌شوند و datagram از همان سوکت bindشده ارسال می‌شود.

ارسال‌های منتظر DNS برای هر نمونهٔ socket و worker ارسال‌کننده محدودیت جداگانه دارند:
حداکثر ۲۵۶ درخواست، ۲ MiB از payload دیتاگرام‌ها و ۴ MiB از حافظهٔ تخصیص‌یافتهٔ
bufferها. عبور از هر محدودیت باعث دور ریختن همان دیتاگرام به‌طور کامل می‌شود. تکمیل،
خطا و shutdown سهم درخواست را آزاد می‌کنند؛ cache پاسخ‌های تکمیل‌شده از این سهم استفاده نمی‌کند.

رد پذیرش به‌دلیل محدودیت انتظار DNS، یک پیام `WARN` در logger DNS ثبت می‌کند که
نام گره، worker ارسال‌کننده، مقصد، محدودیت مشخص، مصرف فعلی و ورودی، مقدار مجاز و
دور ریختن کامل دیتاگرام را نشان می‌دهد. اولین رخداد فوراً ثبت می‌شود؛ تکرارها برای
هر گره، worker و دلیل جداگانه، حداکثر هر پنج ثانیه یک گزارش دارند. اولین رخداد
بعد از این فاصله گزارش را همراه تعداد پیام‌های حذف‌شده ایجاد می‌کند؛ گزارش دوره‌ای
با timer وجود ندارد. line باز می‌ماند. این هشدارها به فعال‌بودن سطح WARN در logger
DNS نیاز دارند، نه `verbose`. عملیات عادی cache این پیام‌ها را تولید نمی‌کند.

این رفتار سازگاری با تولیدکنندگان line بسته‌ای مانند `WireGuardServer` را حفظ می‌کند و در عین حال به peerهای ورودی امکان می‌دهد مسیر بازگشت جداگانه داشته باشند.


<a id="چرا-udplistener-یا-udpconnector-نه"></a>

#### نقش listener و connector {#listener-and-connector-role}


اگرچه پیاده‌سازی همیشه یک سوکت UDP محلی را bind می‌کند، تونل می‌تواند نقش هر دو طرف تبادل با peer را داشته باشد:

- مانند listener، بسته‌ها را از peerهای دلخواه دریافت کند.
- مانند connector، بسته‌ها را به peer انتخاب‌شده بفرستد.

به همین دلیل برای `WireGuardServer` مفید است؛ این دستگاه ممکن است لازم باشد با همان سوکت UDP بدون‌حالت، تماس با peer را آغاز کند یا نخستین بسته را از peer دریافت کند.



#### ادغام در زنجیره {#chain-integration}

`UdpStatelessSocket` همواره مالک lineهای peer تازه در ابتدای زنجیره است. `Init`، payload و `Finish` محلی یا ناشی از انقضای idle را در جهت upstream به `next` می‌فرستد. `Finish` در جهت downstream از `next`، line متعلق به آن peer را بدون بازتاب callback می‌بندد. ارسال downstream روی lineهای transport قرضی یا line بسته‌ای همچنان پشتیبانی می‌شود. فراخوانی adapter از گره قبلی یا upstream غیرفعال است.

<a id="worker-ownership"></a>

#### رفتار worker {#worker-behavior}


سوکت UDP روی حلقهٔ رویداد یک worker ساخته می‌شود. اگر payload برای ارسال از worker دیگری برسد، ارسال روی worker مالک سوکت زمان‌بندی می‌شود و نوشتن واقعی UDP همان‌جا انجام می‌گیرد.

این کار مالکیت صحیح سوکت را حفظ می‌کند و در عین حال اجازه می‌دهد payload از line هر worker بیاید.

<a id="packet-line-semantics"></a>

#### معنای اتصال {#connection-semantics}

`UdpStatelessSocket` فقط مالک lineهای peer ساخته‌شده از datagramهای ورودی UDP است. این lineها با `Finish` از سمت مجاور زنجیره یا انقضای idle timer بسته می‌شوند. lineهای بسته‌ای همچنان برای ارسال خروجی بر اساس routing context پشتیبانی می‌شوند، اما datagram دریافتی روی line بسته‌ای worker فرستاده نمی‌شود.

<a id="ارسال-udp-با-splice"></a>

### ارسال UDP با splice {#udp-splice-sending}


دریافت UDP همچنان از buffer عادی استفاده می‌کند. در زنجیره واجد شرایط روی Linux، ارسال UDP دادهٔ عادی یا prefix واقعی همراه با بدنهٔ pipe خصوصی را به‌صورت یک datagram به مقصد مشخص می‌پذیرد؛ datagram خالی نیز معتبر است. چیدمان‌های پشتیبانی‌شده از splice بین pipe و socket استفاده می‌کنند. برای pipe با fragment‌های زیاد، یا وقتی پیش از ارسال نتوان حد امن fragment‌ها را اثبات کرد، کل datagram پیش از شروع تجمیع روی socket به buffer عادی تبدیل می‌شود. دادهٔ بیش‌ازحد بزرگ بدون تقسیم رد می‌شود.

فشار پیش از شروع تجمیع همان سیاست drop فعلی را حفظ می‌کند و صف retry برای UDP ایجاد نمی‌شود. splice ناقص یا شکست commit پس از priming فقط socket مربوط را بازنشسته می‌کند و line‌های عادی وابسته از مسیر مالکشان بسته می‌شوند. بنابراین peer‌های یک socket مشترک ممکن است با هم بسته شوند. باقی‌ماندهٔ ناقص دوباره ارسال نمی‌شود و socket‌های دیگر فعال می‌مانند. سیاست خطای ارسال عادی تغییر نمی‌کند.

این پرچم بررسی پشتیبانی پلتفرم، `misc.splice`، کنارگذاشتن حالت بسته‌ای و پشتیبانی همهٔ گره‌های زنجیرهٔ نهایی پس از گسترش و ادغام را دور نمی‌زند. zero-copy سرتاسری یا بهبود کاراییِ اندازه‌گیری‌شده تضمین نمی‌شود.

socket همچنان فقط نقش سر زنجیره دارد. worker مالک I/O ارسال محلی و ارسال‌شده از worker دیگر را سریالی اجرا می‌کند. buffer محلی به pool محلی برمی‌گردد؛ buffer جداشده از worker دیگر و buffer لغوشده مستقیماً آزاد می‌شوند. retry فعلی EINTR برای ارسال عادی حفظ می‌شود، اما تجمیع ناقص splice هرگز retry نمی‌شود.
