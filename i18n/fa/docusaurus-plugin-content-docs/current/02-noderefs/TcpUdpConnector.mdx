# TcpUdpConnector

`TcpUdpConnector` یک wrapper از نوع chain-end روی `TcpConnector` و `UdpConnector` است. این نود یک connector داخلی TCP و یک connector داخلی UDP با همان تنظیمات می‌سازد، سپس بر اساس routing metadata WaterWall برای هر line child connector درست را انتخاب می‌کند.

این نود TCP را داخل UDP encapsulate نمی‌کند و UDP را داخل TCP نمی‌برد. یک wrapper connector دو-protocol است.

## جایگاه رایج

از `TcpUdpConnector` وقتی استفاده کنید که یک نود خروجی باید هم TCP و هم UDP را پشتیبانی کند:

```text
Socks5Server -> TcpUdpConnector
TcpUdpListener -> TcpUdpConnector
TcpUdpListener -> SniffRouter -> TcpUdpConnector
PacketsToConnection -> TcpUdpConnector
```

نود قبلی باید protocol metadata را داخل destination context یا source context ارائه دهد. `TcpUdpConnector` از این metadata استفاده می‌کند تا تصمیم بگیرد line باید از child داخلی `TcpConnector` یا child داخلی `UdpConnector` خارج شود.

## نمونه ساده

```json
{
  "name": "mixed-out",
  "type": "TcpUdpConnector",
  "settings": {
    "address": "198.51.100.10",
    "port": 443,
    "domain-strategy": "prefer-ipv4",
    "reuseaddr": true,
    "nodelay": true,
    "fastopen": false,
    "large-send-buffer": true,
    "large-recv-buffer": true,
    "interface": "eth0",
    "fwmark": 10,
    "balance-mode": "connection"
  }
}
```

هم TCP lineها و هم UDP peer lineها از همان destination تنظیم‌شده استفاده می‌کنند. TCP lineها توسط child داخلی `TcpConnector` و UDP lineها توسط child داخلی `UdpConnector` مدیریت می‌شوند.

## نمونه dynamic destination

```json
{
  "name": "mixed-out",
  "type": "TcpUdpConnector",
  "settings": {
    "address": "dest_context->address",
    "port": "dest_context->port",
    "domain-strategy": "prefer-ipv4",
    "reuseaddr": true,
    "large-send-buffer": true,
    "large-recv-buffer": true
  }
}
```

این حالت بعد از نودهایی مثل `Socks5Server`، `SniffRouter` یا نودهای دیگر routing-aware که destination address، destination port و destination protocol را populate می‌کنند مفید است.

## نمونه weighted destination

```json
{
  "name": "mixed-out",
  "type": "TcpUdpConnector",
  "settings": {
    "addresses": [
      {
        "address": "198.51.100.10",
        "port": 443,
        "weight": 3
      },
      {
        "address": "198.51.100.20",
        "port": 443,
        "weight": 1
      }
    ],
    "domain-strategy": "prefer-ipv4",
    "reuseaddr": true,
    "large-send-buffer": true,
    "large-recv-buffer": true,
    "balance-mode": "connection"
  }
}
```

همین آرایه `addresses` به هر دو child connector داده می‌شود. اگر هر دو protocol ممکن است انتخاب شوند از destination syntaxهایی استفاده کنید که برای هر دو `TcpConnector` و `UdpConnector` معتبر هستند.

## فیلدهای ضروری

فیلدهای سطح بالا:

| فیلد | نوع | توضیح |
| --- | --- | --- |
| `name` | string | نام دلخواه نود. باید داخل فایل config یکتا باشد. |
| `type` | string | باید دقیقاً `"TcpUdpConnector"` باشد. |
| `settings` | object | تنظیمات مشترک که به هر دو connector داخلی داده می‌شوند. باید object غیرخالی باشد. |

`TcpUdpConnector` یک chain end است. نباید `next` داشته باشد.

تنظیمات destination لازم:

| سبک | فیلدهای لازم | توضیح |
| --- | --- | --- |
| مقصد تکی | `address` و `port` | هر child connector انتخاب‌شده از همان قانون destination استفاده می‌کند. |
| مقصدهای weighted | `addresses` | هر line از یک لیست destination weighted انتخاب می‌کند. spelling قدیمی `adresses` توسط child connectorها پذیرفته می‌شود، اما config‌های جدید باید از `addresses` استفاده کنند. |

`addresses` را با `address` یا `port` top-level ترکیب نکنید.

## تنظیمات مشترک connector

object settings باید هنگام startup برای هر دو child connector قابل قبول باشد. این حتی اگر انتظار دارید فقط یک protocol در runtime استفاده شود هم اهمیت دارد، چون wrapper هنگام بارگذاری config هر دو child داخلی را می‌سازد.

| گزینه | روی کدام child اثر دارد | توضیح |
| --- | --- | --- |
| `address` | TCP و UDP | آدرس ثابت، domain، `"src_context->address"` یا `"dest_context->address"`. |
| `port` | TCP و UDP | پورت ثابت، `"src_context->port"` یا `"dest_context->port"`. |
| `addresses` | TCP و UDP | لیست weighted destination. |
| `domain-strategy` | TCP و UDP | استراتژی انتخاب نتیجه DNS برای مقصدهای domain. |
| `reuseaddr` | TCP و UDP | فعال‌سازی `SO_REUSEADDR` در صورت پشتیبانی. |
| `large-send-buffer` | TCP و UDP | تنظیم `SO_SNDBUF` در صورت پشتیبانی. |
| `large-recv-buffer` | TCP و UDP | تنظیم `SO_RCVBUF` در صورت پشتیبانی. |
| `fwmark` | TCP و UDP | اعمال socket mark به سبک Linux در صورت پشتیبانی. |
| `interface` | TCP و UDP | محدود کردن socketهای خروجی به یک network device در صورت پشتیبانی. |
| `source-ip` | TCP و UDP | Bind کردن socketهای خروجی به یک source IP محلی مشخص. |
| `nodelay` | TCP child | فعال‌سازی `TCP_NODELAY` روی TCP socketهای خروجی. |
| `fastopen` | TCP child | درخواست `TCP_FASTOPEN` در صورت پشتیبانی. |
| `balance-mode` | UDP child | انتخاب weighted destination در UDP: `"connection"` یا `"packet"`. |

برای جزئیات کامل انتخاب destination، DNS، socket option‌ها و UDP balance mode، صفحه‌های `TcpConnector` و `UdpConnector` را ببینید.

:::warning
`UdpConnector` از syntax مخصوص UDP مثل `"random(x,y)"` برای port پشتیبانی می‌کند، اما `TcpConnector` نه. چون `TcpUdpConnector` هر دو child connector را می‌سازد، از syntax مخصوص UDP اینجا خودداری کنید مگر اینکه در کد فعلی برای `TcpConnector` هم معتبر شده باشد.
:::

## انتخاب protocol

در طول upstream `Init`، `TcpUdpConnector` یک child connector را انتخاب می‌کند و آن انتخاب را در per-line state خودش ذخیره می‌کند. callbackهای upstream بعدی از همان child ذخیره‌شده استفاده می‌کنند، پس connector انتخاب‌شده حتی اگر نود دیگری بعداً routing context را آپدیت کند ثابت می‌ماند.

ترتیب انتخاب:

| مرحله | رفتار |
| --- | --- |
| 1 | `line->routing_context.dest_ctx` بررسی می‌شود. |
| 2 | اگر destination context flag TCP دقیق داشته باشد، child داخلی `TcpConnector` انتخاب می‌شود. |
| 3 | اگر destination context flag UDP دقیق داشته باشد، child داخلی `UdpConnector` انتخاب می‌شود. |
| 4 | اگر destination context هیچ protocol flag نداشته باشد، به `line->routing_context.src_ctx` برمی‌گردد. |
| 5 | اگر source context flag TCP یا UDP دقیق داشته باشد، child connector matching انتخاب می‌شود. |
| 6 | اگر هیچ protocol دقیق انتخاب نشود، به عنوان خطای fatal در config یا routing در نظر گرفته می‌شود. |

Destination protocol از source protocol اولویت بالاتری دارد. این اجازه می‌دهد نودهای routing-aware یک transport روی inbound دریافت کنند و outbound transport را از destination درخواست‌شده انتخاب کنند.

## جریان runtime

در startup، `TcpUdpConnector` دو tunnel داخلی می‌سازد:

- `TcpConnector` با نامی شبیه `<node-name>.tcp-connector`
- `UdpConnector` با نامی شبیه `<node-name>.udp-connector`

هر دو child زیر wrapper داخل chain درج می‌شوند. callbackهای runtime به این صورت کار می‌کنند:

1. نود قبلی upstream `Init` را به `TcpUdpConnector` می‌فرستد
2. wrapper یک child connector را انتخاب و مقداردهی اولیه می‌کند
3. upstream payload، pause، resume، establishment و finish callbackها به همان child forward می‌شوند
4. downstream callbackهای child connector وارد `TcpUdpConnector` می‌شوند
5. wrapper downstream callbackها را به نود قبلی forward می‌کند

## مالکیت line

`TcpUdpConnector` connection lineها نمی‌سازد یا از بین نمی‌برد. adapter یا bridge قبلی مالک ساختن line است.

این wrapper فقط child connector انتخاب‌شده را در یک per-line state کوچک ذخیره می‌کند. قبل از forward کردن یک upstream یا downstream finish واقعی آن state را پاک می‌کند. هیچ‌وقت `lineDestroy()` را صدا نمی‌زند.

## متادیتای نود

| ویژگی | مقدار |
| --- | --- |
| Node flag | `kNodeFlagChainEnd` |
| نود قبلی | لازم است |
| نود بعدی | مجاز نیست |
| layer group | `kNodeLayerAnything` |
| `required_padding_left` | `0` |
| line state | child connector انتخاب‌شده |

## اشتباه‌های رایج

- از `TcpUdpConnector` به عنوان protocol converter استفاده نکنید. فقط بین child connectorهای TCP و UDP انتخاب می‌کند.
- برای آن `next` قرار ندهید؛ chain end است.
- انتظار destination جداگانه برای TCP و UDP نداشته باشید؛ settings مشترک است.
- در config‌هایی که internal `TcpConnector` هم باید ساخته شود از syntax مخصوص UDP مثل `"random(x,y)"` استفاده نکنید.
- آن را بعد از نودی قرار ندهید که metadata protocol دقیق TCP یا UDP تولید نمی‌کند.
