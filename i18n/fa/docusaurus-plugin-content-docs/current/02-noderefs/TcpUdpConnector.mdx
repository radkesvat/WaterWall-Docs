# TcpUdpConnector

`TcpUdpConnector` یک wrapper از نوع chain-end روی `TcpConnector` و `UdpConnector` است. این نود یک connector داخلی TCP و
یک connector داخلی UDP با همان settings می‌سازد، سپس برای هر line بر اساس routing metadata تصمیم می‌گیرد از کدام child
استفاده کند.

این نود TCP را داخل UDP encapsulate نمی‌کند و UDP را هم داخل TCP نمی‌برد. فقط یک connector دو protocol است.

## جایگاه رایج

```text
Socks5Server -> TcpUdpConnector
TcpUdpListener -> TcpUdpConnector
TcpUdpListener -> SniffRouter -> TcpUdpConnector
PacketsToConnection -> TcpUdpConnector
```

نود قبلی باید protocol metadata را داخل destination context یا source context قرار داده باشد. `TcpUdpConnector` با همین
metadata انتخاب می‌کند line از child داخلی `TcpConnector` خارج شود یا از child داخلی `UdpConnector`.

## نمونه ساده

```json
{
  "name": "mixed-out",
  "type": "TcpUdpConnector",
  "settings": {
    "address": "198.51.100.10",
    "port": 443,
    "domain-strategy": "prefer-ipv4",
    "reuseaddr": true,
    "nodelay": true,
    "fastopen": false,
    "large-send-buffer": true,
    "large-recv-buffer": true,
    "interface": "eth0",
    "fwmark": 10,
    "balance-mode": "connection"
  }
}
```

TCP lineها و UDP peer lineها از همان destination تنظیم‌شده استفاده می‌کنند. TCP توسط child داخلی `TcpConnector` و UDP
توسط child داخلی `UdpConnector` مدیریت می‌شود.

## نمونه Dynamic Destination

```json
{
  "name": "mixed-out",
  "type": "TcpUdpConnector",
  "settings": {
    "address": "dest_context->address",
    "port": "dest_context->port",
    "domain-strategy": "prefer-ipv4",
    "reuseaddr": true,
    "large-send-buffer": true,
    "large-recv-buffer": true
  }
}
```

این حالت بعد از نودهایی مثل `Socks5Server`، `SniffRouter` یا نودهای routing-aware مناسب است؛ یعنی جایی که destination
address، destination port و destination protocol تنظیم شده‌اند.

## نمونه Weighted Destination

```json
{
  "name": "mixed-out",
  "type": "TcpUdpConnector",
  "settings": {
    "addresses": [
      {
        "address": "198.51.100.10",
        "port": 443,
        "weight": 3
      },
      {
        "address": "198.51.100.20",
        "port": 443,
        "weight": 1
      }
    ],
    "domain-strategy": "prefer-ipv4",
    "reuseaddr": true,
    "large-send-buffer": true,
    "large-recv-buffer": true,
    "balance-mode": "connection"
  }
}
```

همین `addresses` array به هر دو child connector داده می‌شود. اگر هر دو protocol ممکن است انتخاب شوند، از destination
syntaxهایی استفاده کنید که برای هر دو `TcpConnector` و `UdpConnector` معتبر هستند.

## فیلدهای لازم

| فیلد | نوع | توضیح |
| --- | --- | --- |
| `name` | string | نام یکتای نود داخل config. |
| `type` | string | باید دقیقا `"TcpUdpConnector"` باشد. |
| `settings` | object | settings مشترک برای هر دو connector داخلی. باید object غیرخالی باشد. |

`TcpUdpConnector` chain end است و نباید `next` داشته باشد.

تنظیم destination باید یکی از این دو شکل باشد:

| شکل | فیلد لازم | توضیح |
| --- | --- | --- |
| Single destination | `address` و `port` | هر child connector همان destination rule را استفاده می‌کند. |
| Weighted destinations | `addresses` | انتخاب destination از یک لیست weighted انجام می‌شود. spelling قدیمی `adresses` توسط childها پذیرفته می‌شود، ولی در config جدید از `addresses` استفاده کنید. |

`addresses` را با top-level `address` یا `port` ترکیب نکنید.

## تنظیمات مشترک Connector

settings باید هنگام startup برای هر دو child connector قابل قبول باشد. حتی اگر انتظار دارید فقط یک protocol در runtime
استفاده شود، wrapper هنگام load config هر دو child را می‌سازد.

| setting | روی کدام child اثر دارد | توضیح |
| --- | --- | --- |
| `address` | TCP و UDP | آدرس ثابت، domain، `"src_context->address"` یا `"dest_context->address"`. |
| `port` | TCP و UDP | port ثابت، `"src_context->port"` یا `"dest_context->port"`. |
| `addresses` | TCP و UDP | لیست weighted destination. |
| `domain-strategy` | TCP و UDP | انتخاب نتیجه DNS برای domain destinationها. |
| `reuseaddr` | TCP و UDP | فعال‌سازی `SO_REUSEADDR` در صورت پشتیبانی. |
| `large-send-buffer` | TCP و UDP | تنظیم `SO_SNDBUF` در صورت پشتیبانی. |
| `large-recv-buffer` | TCP و UDP | تنظیم `SO_RCVBUF` در صورت پشتیبانی. |
| `fwmark` | TCP و UDP | اعمال mark لینوکسی در صورت پشتیبانی. |
| `interface` | TCP و UDP | محدود کردن socket خروجی به interface مشخص در صورت پشتیبانی. |
| `source-ip` | TCP و UDP | bind کردن socket خروجی به source IP مشخص. |
| `nodelay` | TCP child | فعال‌سازی `TCP_NODELAY` روی TCP خروجی. |
| `fastopen` | TCP child | درخواست `TCP_FASTOPEN` در صورت پشتیبانی. |
| `balance-mode` | UDP child | حالت انتخاب weighted destination در UDP: `"connection"` یا `"packet"`. |

برای جزئیات کامل destination selection، DNS، socket optionها و UDP balance mode، صفحه‌های `TcpConnector` و `UdpConnector`
را ببینید.

:::warning
`UdpConnector` syntax مخصوص UDP مثل `"random(x,y)"` را برای port پشتیبانی می‌کند، ولی `TcpConnector` نه. چون
`TcpUdpConnector` هر دو child connector را می‌سازد، از syntax مخصوص UDP در این node استفاده نکنید مگر اینکه در کد فعلی
برای `TcpConnector` هم معتبر شده باشد.
:::

## انتخاب Protocol

در upstream `Init`، این نود یک child connector را انتخاب می‌کند و آن انتخاب را در line state خودش نگه می‌دارد. callbackهای
بعدی همان child ذخیره‌شده را استفاده می‌کنند؛ پس انتخاب connector حتی اگر routing context بعدا تغییر کند ثابت می‌ماند.

ترتیب انتخاب:

| مرحله | رفتار |
| --- | --- |
| 1 | اول `line->routing_context.dest_ctx` بررسی می‌شود. |
| 2 | اگر destination context دقیقا TCP باشد، child داخلی `TcpConnector` انتخاب می‌شود. |
| 3 | اگر destination context دقیقا UDP باشد، child داخلی `UdpConnector` انتخاب می‌شود. |
| 4 | اگر destination context protocol نداشته باشد، source context بررسی می‌شود. |
| 5 | اگر source context دقیقا TCP یا UDP باشد، child matching انتخاب می‌شود. |
| 6 | اگر protocol دقیق پیدا نشود، خطای fatal در config یا routing رخ می‌دهد. |

destination protocol از source protocol اولویت بیشتری دارد. به همین دلیل یک نود routing-aware می‌تواند transport ورودی را
یک چیز بگیرد ولی outbound protocol را بر اساس destination درخواستی تعیین کند.

## جریان Runtime

در startup، این نود دو tunnel داخلی می‌سازد:

- `TcpConnector` با نامی شبیه `<node-name>.tcp-connector`
- `UdpConnector` با نامی شبیه `<node-name>.udp-connector`

هر دو child زیر wrapper داخل chain قرار می‌گیرند:

1. نود قبلی upstream `Init` را به `TcpUdpConnector` می‌فرستد
2. wrapper یک child connector را انتخاب و initialize می‌کند
3. upstream payload، pause، resume، est و finish به همان child forward می‌شوند
4. callbackهای downstream از child connector وارد `TcpUdpConnector` می‌شوند
5. wrapper callbackهای downstream را به نود قبلی forward می‌کند

## مالکیت Line

`TcpUdpConnector` line نمی‌سازد و line را destroy نمی‌کند. line توسط adapter یا bridge قبلی ساخته شده است.

این wrapper فقط selected child connector را در یک line state کوچک ذخیره می‌کند. قبل از forward کردن finish واقعی، state
خودش را پاک می‌کند. `lineDestroy()` در این نود صدا زده نمی‌شود.

## متادیتای نود

| ویژگی | مقدار |
| --- | --- |
| Node flag | `kNodeFlagChainEnd` |
| previous node | لازم است |
| next node | مجاز نیست |
| layer group | `kNodeLayerAnything` |
| `required_padding_left` | `0` |
| line state | selected child connector |

## اشتباه‌های رایج

- این نود protocol converter نیست؛ فقط بین childهای TCP و UDP انتخاب می‌کند.
- برای آن `next` نگذارید؛ chain end است.
- انتظار destination جدا برای TCP و UDP نداشته باشید؛ settings مشترک است.
- در configهایی که internal `TcpConnector` هم باید ساخته شود، از syntax مخصوص UDP مثل `"random(x,y)"` استفاده نکنید.
- آن را بعد از نودی نگذارید که protocol metadata دقیق TCP یا UDP تولید نمی‌کند.
