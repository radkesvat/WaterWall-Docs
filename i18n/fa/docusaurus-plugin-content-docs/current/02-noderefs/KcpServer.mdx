# KcpServer

## نمای کلی {#overview}

`KcpServer` peer سمت server برای `KcpClient` است. datagram‌های KCP را بدون از بین بردن مرز packet‌ها از node قبلی می‌گیرد، جریان بایتی اصلی را بازسازی می‌کند و آن را به node بعدی می‌فرستد. پاسخ node بعدی نیز دوباره به datagram‌های KCP تبدیل می‌شود و در جهت downstream به سمت packet قبلی برمی‌گردد.

این node معمولاً با `KcpClient` در سمت مقابل استفاده می‌شود.

## جایگاه معمول در زنجیره {#typical-placement}

<a id="جایگاه-رایج"></a>

یک برنامهٔ TCP محلی را از طریق مسیر UDP همتا به سرویس HTTP هدایت کنید:

```text
client: TcpListener(127.0.0.1:18080) -> KcpClient -> UdpConnector(gateway:9000)
server: UdpListener(0.0.0.0:9000) -> KcpServer -> TcpConnector(127.0.0.1:8080)
```

برای اشتراک انتقال والد میان چند اتصال برنامه، `MuxClient` را پیش از `KcpClient` و `MuxServer` را پس از `KcpServer` قرار دهید. مسیر UDP بیرونی باید datagramهای کامل KCP را حفظ کند.

## نمونهٔ کاربردی ساده {#minimal-practical-example}

این نمونه‌ها بخش‌هایی از پیکربندی گره هستند؛ گره‌های مجاور ارجاع‌داده‌شده را در پیکربندی پیرامون آن تعریف کنید.

### نمونهٔ پیکربندی {#configuration-example}

<a id="نمونه-پایه"></a>

این config کامل با [config پایه‌ی client](KcpClient.mdx) متناظر است.
gateway ترافیک KCP را روی UDP `9000` می‌گیرد و stream بازسازی‌شده‌ی TCP را به
سرویس HTTP محلی روی `8080` می‌فرستد. هر دو مثال FEC را خاموش می‌کنند؛ اگر آن
حالت را انتخاب کردید، در هر دو peer با تعداد shard یکسان فعالش کنید.

```json
{
  "name": "kcp-server",
  "nodes": [
    {
      "name": "udp-in",
      "type": "UdpListener",
      "settings": {
        "address": "0.0.0.0",
        "port": 9000
      },
      "next": "kcp-server"
    },
    {
      "name": "kcp-server",
      "type": "KcpServer",
      "settings": {
        "fec": false
      },
      "next": "service-out"
    },
    {
      "name": "service-out",
      "type": "TcpConnector",
      "settings": {
        "address": "127.0.0.1",
        "port": 8080
      }
    }
  ]
}
```

## پیکربندی {#configuration}

### فیلدهای JSON لازم {#required-json-fields}

<a id="فیلدهای-ضروری"></a>

#### فیلدهای سطح بالا {#top-level-fields}

- `name` `(string)`
  نامی که کاربر برای این گره انتخاب می‌کند.

- `type` `(string)`
  باید دقیقاً `"KcpServer"` باشد.

- `next` `(string)`
  گره بعدی که جریان بازسازی‌شده را دریافت می‌کند.

#### `settings` {#settings}

تنظیم اجباری مخصوص تونل وجود ندارد.

### فیلدهای اختیاری `settings` {#optional-settings-fields}

<a id="تنظیمات-اختیاری"></a>

- `send-mtu` `(integer)`
  بودجهٔ بستهٔ خروجی برحسب بایت با فرض IPv4: بازهٔ `118..65535` بدون FEC و `126..65535` با FEC. دریافت محدودیت‌های مستقل پروتکل را دارد.
  پیش‌فرض: `misc.mtu` هسته (معمولاً `1500`)

- `fec` `(boolean)`
  تصحیح خطای پیشرو Reed-Solomon را پیرامون دیتاگرام‌های KCP فعال می‌کند.
  اگر حذف شود یا `false` باشد، دیتاگرام‌های KCP از پوشش session بدون FEC استفاده می‌کنند.

- `fec-data-shards` `(number)`
  تعداد shardهای داده در هر بلوک FEC، هنگامی که `fec` فعال است.
  پیش‌فرض: `10`

- `fec-parity-shards` `(number)`
  تعداد shardهای parity در هر بلوک FEC، هنگامی که `fec` فعال است.
  پیش‌فرض: `3`

- `kcp-nodelay` `(boolean)`
  حالت nodelay در KCP را فعال می‌کند.
  پیش‌فرض: `true`

- `kcp-interval-ms` `(number)`
  فاصلهٔ به‌روزرسانی KCP برحسب میلی‌ثانیه.
  پیش‌فرض: `10`

- `kcp-resend` `(number)`
  آستانهٔ ارسال مجدد سریع در KCP.
  پیش‌فرض: `2`

- `kcp-ack-batch` `(integer)`
  هر همتا آستانهٔ خود را در بازهٔ `0..kcp-recv-window` جداگانه تعیین می‌کند. با مقدار `1`، KCP پس از دریافت هر دیتاگرام معتبر، صف ارسال را تخلیه می‌کند. با مقدار بزرگ‌تر، به‌محض اینکه تعداد ACKهای منتظر به آستانه برسد، ارسال می‌شوند. با مقدار `0`، ACKهای دادهٔ عادی تا به‌روزرسانی بعدی `kcp-interval-ms` در صف می‌مانند.
  ارسال گروهی ACKها تعداد دیتاگرام‌ها را کم می‌کند و در انتقال‌های حجیم می‌تواند مصرف CPU را کاهش دهد. هر ACK ممکن است به‌اندازهٔ یک بازهٔ به‌روزرسانی در صف بماند و در نتیجه RTT اندازه‌گیری‌شده افزایش یابد. ارسال مجدد سریع هم ممکن است دیرتر انجام شود، چون KCP در هر دیتاگرام دریافتی فقط یک بار ACK تکراری را می‌شمارد. وقتی ارسال گروهی فعال است، اگر دیتاگرام ورودی فقط ACK داشته باشد، داده‌ای که تازه امکان ارسال پیدا کرده ممکن است تا به‌روزرسانی بعدی در صف بماند.
  گیرنده بلافاصله به PING نگه‌دارندهٔ اتصال پاسخ ACK می‌دهد، حتی اگر PING دوباره ارسال شده باشد. با دریافت نخستین CLOSE از همتا، خط برنامه را می‌بندد و بلافاصله ACK را می‌فرستد. هنگام تخلیهٔ داده‌های خروجی نیز به هر CLOSE تکراری بلافاصله ACK می‌دهد. در دوره‌ای که نشست فقط برای پاسخ ACK نگه داشته می‌شود، هر ورودی معتبر باعث ارسال خروجی آماده می‌شود.
  پیش‌فرض: `1`

- `kcp-no-congestion-control` `(boolean)`
  کنترل ازدحام KCP را برای مسیرهای UDP با توان عملیاتی بالاتر غیرفعال می‌کند.
  پیش‌فرض: `true`

- `kcp-send-window` `(number)`
  پنجرهٔ ارسال KCP برحسب تعداد قطعه‌ها.
  پیش‌فرض: `8192`

- `kcp-recv-window` `(number)`
  پنجرهٔ دریافت محلی KCP برحسب تعداد قطعه‌ها. ظرفیت خالی اعلام‌شده به همتا حداکثر 65535 قطعه است.
  پیش‌فرض: `8192`

- `kcp-initial-cwnd` `(number)`
  پنجرهٔ اولیهٔ ازدحام KCP برحسب تعداد قطعه‌ها. در صورت حذف، نصف `kcp-send-window` در نظر گرفته می‌شود.
  پیش‌فرض با پنجرهٔ ارسال داخلی: `4096`

- `kcp-rx-minrto-ms` `(number)`
  حداقل مهلت ارسال مجدد KCP برحسب میلی‌ثانیه.
  پیش‌فرض: `30`

- `kcp-send-buffer-limit` `(number)`
  آستانهٔ فشار برگشتی برای بسته‌های KCP صف‌شده. مقدار `0` حد را از مجموع پنجرهٔ ارسال محلی، پنجرهٔ همتا و `10` محاسبه می‌کند و آن را به `2147483647` محدود می‌کند.
  پیش‌فرض: `0`

- `ping-interval-ms` `(number)`
  زمان از دریافت آخرین بستهٔ معتبر session تا ارسال ping داخلی.
  پیش‌فرض: `10000`

- `no-recv-timeout-ms` `(number)`
  زمان از دریافت آخرین بستهٔ معتبر session تا بستن آن. باید از `ping-interval-ms` بیشتر باشد.
  پیش‌فرض: `30000`

- `close-drain-timeout-ms` `(integer)`
  حداکثر بازهٔ ارسال/تخلیه و بازهٔ نگهداری ACK، که با مذاکره برابر کمینهٔ تنظیم دو همتا می‌شود. بازهٔ مجاز: `1..2147483647`. افزایش بازهٔ مؤثر نیازمند اجازهٔ هر دو همتاست.
  پیش‌فرض: `30000`

## کاربرد و رفع اشکال {#usage-and-troubleshooting}

### نکته‌ها و محدودیت‌ها {#notes-and-caveats}

<a id="اشتباههای-رایج"></a>

- `KcpServer` برای استفاده همراه `KcpClient` در نظر گرفته شده است.
- FEC باید در هر دو peer با تنظیمات shard یکسان فعال باشد.
- گره قبلی باید مرز بسته‌ها را حفظ کند.
- `DownStreamInit` غیرفعال است؛ lineهای سرویس از طریق handshake در upstream ساخته می‌شوند.
- خاموش‌شدن worker تایمرها را لغو و همهٔ سرویس‌ها و sessionهای تحت مالکیت را فوراً تخلیه می‌کند.

## جزئیات پیاده‌سازی {#implementation-details}

### کارکرد گره {#what-it-does}

- payload بسته را از گره قبلی می‌گیرد و به KCP می‌دهد.
- از session مربوط به KCP یک جریان بایتی شبیه TCP بازسازی و به گره بعدی ارسال می‌کند.
- پاسخ‌های جریان downstream را دریافت، دوباره با KCP کدگذاری و به‌صورت بسته بازمی‌گرداند.
- از frameهای داخلی ping و close برای نگه‌داری session استفاده می‌کند.

سمت قبلی زنجیره باید انتقالی با حفظ مرز بسته‌ها فراهم کند.

### رفتار تفصیلی {#detailed-behavior}

#### مدل انتقال KCP {#kcp-transport-model}

<a id="مدل-kcp-transport"></a>

`Init` ورودی فقط حامل UDP قرضی را مقداردهی می‌کند. تبادل HELLO، CHALLENGE، CONFIRM و READY با nonceهای مستقل 128 بیتی، هر session را برقرار می‌کند. شاخهٔ سرویس پس از CONFIRM متناظر، دقیقاً یک بار `Init` دریافت می‌کند. هر session مالک یک line سرویس مستقل است و state مربوط به KCP/FEC جدا از آن line زنده می‌ماند.

<a id="envelope-و-هویت-session"></a>

هر دیتاگرام یک پوشش session به طول 40 بایت دارد که صریحاً سریال‌سازی می‌شود: نشانگر `WWKC`، نوع پیام، یک بایت رزروشدهٔ صفر، طول بدنهٔ دوبایتی با ترتیب بایت شبکه، nonce شانزده‌بایتی کلاینت و nonce شانزده‌بایتی سرور. نوع‌ها عبارت‌اند از HELLO `1`، CHALLENGE `2`، CONFIRM `3`، READY `4`، KCP `5` و FEC `6`. بدنهٔ پیام‌های handshake شامل بازهٔ بستن چهاربایتی با ترتیب بایت شبکه، تعداد shardهای داده و parity و دو بایت رزروشدهٔ صفر است. هر دو nonce پیش از ورود به KCP یا FEC اعتبارسنجی می‌شوند؛ session ناشناس نمی‌تواند سرویس باز کند. این nonceها هویت session را مشخص می‌کنند و رمزنگاری یا احراز هویت اضافه نمی‌کنند.

کلاینت درخواست جاری handshake را هر 250 میلی‌ثانیه تا مهلت اصلی `no-recv-timeout-ms` تکرار می‌کند. هر حامل یک challenge معلق با زمان انقضای ثابت و حداکثر 64 session برقرارشده می‌پذیرد؛ sessionهای در حال تخلیه یا نگهداری ACK نیز در این شمارش قرار دارند. با پرشدن ظرفیت، پذیرش جدید بدون کوتاه‌کردن نگهداری موجود رد می‌شود؛ تکرارهای کلاینت همچنان به مهلت اصلی محدودند. استفادهٔ دوباره از یک endpoint UDP، هویت‌های تازهٔ session و سرویس می‌سازد، در حالی که sessionهای قدیمی می‌توانند همچنان به ارسال‌های مجدد ACK بدهند. این سقف هر حامل، بودجهٔ سراسری حافظهٔ heap مربوط به KCP/FEC در فرایند نیست.

رکوردهای KCP ورودی یک پرچم داخلی یک‌بایتی دارند. پاسخ‌ها قطعه‌بندی و قاب‌بندی می‌شوند و از طریق KCP به سمت قبلی فرستاده می‌شوند. `Est` حامل ثبت می‌شود و یک بار به هر سرویس زنده‌ای که Init آن آغاز شده است می‌رسد. هر سرویس نیز نخستین `Est` خود را به حامل منتقل می‌کند. این callbackها آمادگی انتقال را مستقل از پیشرفت handshake مربوط به KCP گزارش می‌کنند. callbackهای KCP/FEC خروجی را پیش از اجرای تونل‌های مجاور آماده می‌کنند و ورودی تو در تو با محدودیت پذیرش از نظر بایت و هزینهٔ تخصیص حافظه، به‌ترتیب پردازش می‌شود.

#### پرچم‌های داخلی frame {#internal-frame-flags}

<a id="flagهای-داخلی"></a>

این تونل در payload مربوط به KCP از این پرچم‌ها استفاده می‌کند:

- `0x00`: داده
- `0xF0`: ping
- `0xFF`: بستن

فریم‌های داده پس از بایت پرچم، بایت‌های جریان را حمل می‌کنند.

یک data frame که فقط بایت flag دارد دور ریخته می‌شود. پیام خالی KCP فاقد flag
است و اتصال مربوط به آن بسته می‌شود؛ flag ناشناخته یا پیام کامل KCP که از بافر
دریافت محلی بزرگ‌تر باشد نیز اتصال را می‌بندد. پیام ناقص KCP منتظر دریافت
قطعه‌های باقی‌مانده می‌ماند.

#### تنظیمات پیش‌فرض KCP {#default-kcp-settings}

پیاده‌سازی، تنظیم KCP را از طریق JSON در دسترس قرار می‌دهد. پیش‌فرض‌های مناسب توان عملیاتی بالاتر عبارت‌اند از:

- `kcp-nodelay = true`
- `kcp-interval-ms = 10`
- `kcp-resend = 2`
- `kcp-ack-batch = 1`
- `kcp-no-congestion-control = true`
- `kcp-send-window = 8192`
- `kcp-recv-window = 8192`
- `kcp-initial-cwnd = 4096`
- `kcp-rx-minrto-ms = 30`
- `kcp-send-buffer-limit = 0` (برگرفته از پنجره‌های KCP)
- `ping-interval-ms = 10000`
- `no-recv-timeout-ms = 30000`

#### MTU ارسال {#sending-mtu}

<a id="mtu-ارسال-و-padding"></a>

گزینهٔ اختیاری `send-mtu` از نوع عدد صحیح هنگام ساخت از `misc.mtu` هسته مقدار می‌گیرد؛ پیش‌فرض
هسته 1500 است. بازهٔ معتبر **118..65535 بدون FEC** و **126..65535 با FEC** است.
این مقدار بودجهٔ بستهٔ خروجی برحسب بایت با فرض IPv4 است. مقدار صریح یا ارث‌رسیدهٔ نامعتبر
ساخت گره را ناموفق می‌کند؛ با override معتبر می‌توان پیش‌فرض نامناسب هسته را جایگزین
کرد. `null`، نوع نادرست، عدد اعشاری، صفر، عدد منفی و مقدار خارج از بازه خطا هستند.
هر نمونه مقدار معتبر خود را مستقل و ثابت نگه می‌دارد.

با `F = 0` بدون FEC و `F = 8` با FEC:

```text
KCP MTU = min(send-mtu - 20 - 8 - 40 - F, 64000)
application chunk = KCP MTU - 24 - 1
```

سهم ثابت IPv4 برابر 20 بایت، UDP برابر 8 بایت و envelope برابر 40 بایت است. سقف ده‌دهی 64000 شامل کل
بستهٔ KCP و هدر 24 بایتی آن است. پرچم یک‌بایتی داخل payload قرار دارد و node
`required_padding_left = 1` اعلام می‌کند. همین MTU خروجی داده و ACK/control
تجمیع‌شده را محدود می‌کند؛ FEC حداکثر 8 بایت، شامل بسته‌های parity، اضافه می‌کند.

دریافت محدودیت مستقل پروتکل دارد: حداکثر 64000 بایت برای بستهٔ KCP یا 64008
بایت برای shard مربوط به FEC، بدون احتساب envelope چهل‌بایتی session. دو peer
می‌توانند مقدارهای متفاوت `send-mtu` داشته باشند. بستهٔ ورودی فقط به دلیل
بزرگ‌تر بودن از بودجهٔ ارسال گیرنده رد نمی‌شود؛ اعتبارسنجی frame، هویت session
و FEC همچنان انجام می‌شود. مذاکرهٔ MTU انجام نمی‌شود.

برای `send-mtu: 1500`، MTU مؤثر KCP و chunk برنامه بدون FEC برابر **1432/1407** و
با FEC برابر **1424/1399** هستند. بودجهٔ 64068 بدون FEC یا 64076 با FEC به سقف
می‌رسد. مقادیر معتبر بزرگ‌تر، از جمله 65535، پذیرفته می‌شوند و MTU مؤثر 64000
و chunk برابر 63975 دارند؛ خود تنظیم به 64000 کاهش نمی‌یابد.

این تنظیم کشف یا مذاکرهٔ MTU مسیر نیست. هدر پایهٔ IPv6 بیست بایت بیشتر نیاز دارد؛
بودجهٔ 1500 می‌تواند بستهٔ IPv6 با طول 1520 بسازد. گزینه‌های IPv4، هدرهای توسعهٔ
IPv6 و پوشش‌های بعدی به حاشیهٔ اضافی نیاز دارند. هیچ تعدیلی بر اساس خانوادهٔ IP انجام نمی‌شود.

#### لایهٔ اختیاری FEC {#optional-fec-layer}

<a id="رفتار-fec"></a>

وقتی `fec` فعال است، سرور انتظار دارد سمت قبلی بسته‌های KCP پیچیده‌شده در FEC را با تعداد shard مطابق تنظیمات حمل کند.

هنگام دریافت:

- shardهای مستقیم داده را فوراً به KCP می‌دهد
- تلاش می‌کند دیتاگرام‌های KCP گم‌شده را از shardهای parity بازسازی کند
- بسته‌های نامعتبر FEC را با رویکرد محافظه‌کارانه نادیده می‌گیرد

هنگام ارسال، دیتاگرام‌های خروجی KCP را در همان قالب FEC قرار می‌دهد و پس از هر بلوک دادهٔ تنظیم‌شده، shardهای parity را می‌فرستد.

وقتی `fec` غیرفعال باشد، هر پوشش session مستقیماً یک بستهٔ KCP حمل می‌کند.

<a id="نمونه-با-fec"></a>

#### جهت جریان داده {#data-flow-direction}

- سمت بسته به سمت جریان: گره قبلی -> `KcpServer` -> گره بعدی
- پاسخ جریان به سمت بسته: گره بعدی -> `KcpServer` -> گره قبلی

frameهای دادهٔ KCP ورودی رمزگشایی و به‌صورت payload جریان به گره بعدی فرستاده می‌شوند. payload جریان خروجی به قطعه‌های مناسب KCP تقسیم، به‌عنوان frame داده علامت‌گذاری و از سمت قبلی بازگردانده می‌شود.

#### رفتار بستن و timeout {#close-and-timeout-behavior}

<a id="رفتار-close-و-timeout"></a>

با `Finish` سرویس، line سرویس تحت مالکیت سرور بلافاصله جدا و نابود می‌شود، در حالی که session مستقل آن خروجی پذیرفته‌شده را نگه می‌دارد. از همان نخستین رویداد بستن، session یک بازهٔ ثابت و مذاکره‌شدهٔ D دارد تا تأیید داده‌های قبلی را دریافت کند، سپس CLOSE را یک بار در صف قرار دهد و منتظر ACK خود KCP برای CLOSE بماند. صرف flush شدن به معنی تأیید بستن نیست. انقضای مهلت، ارسال را با نتیجهٔ تأییدنشده پایان می‌دهد.

CLOSE همتا پس از تحویل بایت‌های ورودی قبلی، سرویس را یک بار خاتمه می‌دهد و بودجهٔ تخلیهٔ خروجی محلی صف‌شده را پیش از انتشار ACK مربوط به KCP ثابت می‌کند. state دریافت پس از EOF برنامه برای تأیید CLOSEهای تکراری در دسترس می‌ماند. پاسخ‌دهنده‌ای که فقط CLOSE همتا را دریافت کرده است، تا D پس از نخستین دریافت CLOSE باقی می‌ماند. وقتی CLOSE ما در زمان A تأیید شود، state دریافت تا A + D حفظ می‌شود؛ CLOSE دیرترِ همتا آن را تمدید نمی‌کند. فرستندهٔ محلی منقضی‌شده، تعهد قبلی برای ACK همتا را حفظ می‌کند و از خروجی PUSH بیشتر برای دادهٔ برنامه یا CLOSE جلوگیری می‌کند.

با مقدار پیش‌فرض، ارسال حداکثر 30 ثانیه فرصت دارد و state قادر به ارسال ACK ممکن است حداکثر 60 ثانیه از نخستین رویداد بستن باقی بماند. این محدودیت دربارهٔ دریافت در لایهٔ انتقال است، نه مصرف یا ذخیرهٔ داده در برنامهٔ دوردست. معنای TCP half-close اضافه نمی‌شود. `Finish` انتقال، خطای مهلک پروتکل و خاموشی فوراً عملیات را قطع می‌کنند؛ خاموشی هرگز منتظر مهلت بستن آرام نمی‌ماند.

در sessionهای عادی، زمان ارسال ping و انقضای دریافت از آخرین دریافت معتبر و مستقل از فاصلهٔ به‌روزرسانی KCP محاسبه می‌شود. اگر هر دو موعد فرا رسیده باشند، انقضا اولویت دارد. sessionهای در حال بستن از مهلت‌های ثابت بستن استفاده می‌کنند. بسته‌های نامعتبر یا نامرتبط هیچ مهلت session را تازه نمی‌کنند. وقتی هیچ session یا challenge معلقی به حامل نیاز نداشته باشد، state محلی پاک می‌شود و مالک UDP یک `Finish` دریافت می‌کند. بستن یک session، حامل مورد نیاز session دیگر را حفظ می‌کند.

#### رفتار Backpressure {#backpressure-behavior}

<a id="backpressure"></a>

server پیش از فرستادن سیگنال به stream سرویس سمت بعدی هر session، فشار صف محلی KCP آن session و فشار carrier مشترک را با هم در نظر می‌گیرد. تا زمانی که هر یک از این دو علت فعال باشد، سرویس در حالت Pause می‌ماند. در کارکرد عادی، سیگنال‌های Pause/Resume دریافتی از carrier، حتی در حالت تکراری، فقط به سرویسی منتقل می‌شوند که توقف محلی KCP آن فعال نباشد. تغییر فشار محلی نیز فقط وقتی به آن سرویس اطلاع داده می‌شود که carrier در حالت Pause نباشد؛ Resume مربوط به یک علت نمی‌تواند توقف ناشی از علت دیگر را آزاد کند. پس از Init سرویس جدید، Pause در انتظار carrier حتی اگر Init فشار محلی KCP ایجاد کرده باشد به سرویس تحویل داده می‌شود تا توقف اولیهٔ آن برقرار شود.

در جهت دیگر، آخرین Pause یا Resume هر سرویس، درخواست همان سرویس برای توقف خواندن از حامل را تعیین می‌کند. Pause تکراری همچنان یک توقف برای آن سرویس به شمار می‌رود و حامل تنها زمانی Resume دریافت می‌کند که توقف همهٔ سرویس‌ها برداشته شده باشد. با Finish سرویس یا دریافت CLOSE همتا، session وارد وضعیت بستن می‌شود، سرویس را جدا می‌کند و توقف مربوط به آن را برمی‌دارد تا حامل زنده بتواند ACKهای لازم برای تخلیه را دریافت کند. اگر session به‌طور مستقل پایان یابد و حامل زنده بماند، توقف آن session نیز برداشته می‌شود.

پس از پذیرش کامل ورودی stream و تحویل packet‌های خروجی تولیدشده، تعداد segmentهای صف‌شده و تأییدنشدهٔ KCP بالاتر از `kcp-send-buffer-limit`، توقف محلی همان session را فعال می‌کند. پایین‌تر از آستانه این توقف غیرفعال می‌شود و در مقدار برابر، وضعیت فعلی حفظ می‌شود. حتی ورودی فقط شامل ACK نیز می‌تواند توقف محلی را آزاد کند و نیازی به تولید packet خروجی دیگری نیست. وقتی مقدار تنظیم `0` است، آستانه از windowهای فعلی KCP محاسبه می‌شود. وضعیت پیش از callback ثبت می‌شود و پس از Finish، سیگنالی به سرویس بسته‌شده فرستاده نمی‌شود.

این تنظیم همچنان آستانهٔ نرم تعداد segmentهاست، نه سقف سخت حافظه یا پذیرش داده. دادهٔ آمادهٔ KCP، ACK، ارسال مجدد و pingهای موعدرسیده در حالت Pause سرویس نیز ادامه دارند. windowها، timerهای KCP و مهلت دریافت همچنان اعمال می‌شوند. هر payload به پردازش KCP و در صورت فعال بودن، FEC نیاز دارد؛ بنابراین node پس از راه‌اندازی نیز نمی‌تواند خودش را bypass کند.
