# KcpServer

`KcpServer` peer سمت server برای `KcpClient` است. datagram‌های KCP را بدون از بین بردن مرز packet‌ها از node قبلی می‌گیرد، byte stream اصلی را بازسازی می‌کند و آن را به node بعدی می‌فرستد. پاسخ node بعدی نیز دوباره به datagram‌های KCP تبدیل می‌شود و در جهت downstream به سمت packet قبلی برمی‌گردد.

این node معمولاً با `KcpClient` در سمت مقابل استفاده می‌شود.

## جایگاه رایج

سمت server:

```text
UdpListener -> KcpServer -> TcpConnector
UdpListener -> KcpServer -> MuxServer -> TcpConnector
```

سمت client متناظر:

```text
TcpListener -> KcpClient -> UdpConnector
TcpListener -> MuxClient -> KcpClient -> UdpConnector
```

node قبلی `KcpServer` باید مرز datagram‌ها را حفظ کند؛ node بعدی با stream سروکار دارد.

## نمونه پایه

این config کامل با [config پایه‌ی client](KcpClient.mdx) متناظر است.
gateway ترافیک KCP را روی UDP `9000` می‌گیرد و stream بازسازی‌شده‌ی TCP را به
سرویس HTTP محلی روی `8080` می‌فرستد. هر دو مثال FEC را خاموش می‌کنند؛ اگر آن
حالت را انتخاب کردید، در هر دو peer با تعداد shard یکسان فعالش کنید.

```json
{
  "name": "kcp-server",
  "nodes": [
    {
      "name": "udp-in",
      "type": "UdpListener",
      "settings": {
        "address": "0.0.0.0",
        "port": 9000
      },
      "next": "kcp-server"
    },
    {
      "name": "kcp-server",
      "type": "KcpServer",
      "settings": {
        "fec": false
      },
      "next": "service-out"
    },
    {
      "name": "service-out",
      "type": "TcpConnector",
      "settings": {
        "address": "127.0.0.1",
        "port": 8080
      }
    }
  ]
}
```


## نمونه با FEC

```json
{
  "name": "kcp-server",
  "type": "KcpServer",
  "settings": {
    "fec": true,
    "fec-data-shards": 10,
    "fec-parity-shards": 3
  },
  "next": "service-out"
}
```

تنظیمات FEC باید دقیقاً با سمت `KcpClient` یکسان باشد.

## فیلدهای ضروری

`settings` اختیاری است. اگر آن را ننویسید یا مقدارش object نباشد، مقادیر پیش‌فرض به کار می‌روند.

در حالت معمول `next` لازم است و باید به مسیر stream-side سرویس اشاره کند؛ همان مسیری که payload بازسازی‌شده را دریافت خواهد کرد.

## تنظیمات اختیاری

نام setting‌ها و مقدارهای پیش‌فرض `KcpServer` با `KcpClient` یکسان است.

| فیلد | پیش‌فرض | اعتبارسنجی | توضیح |
| --- | --- | --- | --- |
| `send-mtu` | `misc.mtu` هسته (پیش‌فرض 1500) | عدد صحیح `118..65535` بدون FEC؛ `126..65535` با FEC | بودجهٔ بستهٔ خروجی با فرض IPv4؛ دریافت محدودیت مستقل پروتکل دارد. |
| `fec` | `false` | boolean | فعال‌سازی Reed-Solomon forward error correction روی datagram‌های KCP. |
| `fec-data-shards` | `10` | مثبت، با مجموع shard‌ها حداکثر `255` | تعداد data shard در هر FEC block. فقط وقتی `fec` فعال است استفاده می‌شود. |
| `fec-parity-shards` | `3` | مثبت، با مجموع shard‌ها حداکثر `255` | تعداد parity shard در هر FEC block. فقط وقتی `fec` فعال است استفاده می‌شود. |
| `kcp-nodelay` | `true` | boolean | فعال‌سازی KCP nodelay mode. |
| `kcp-interval-ms` | `10` | `10..5000` | فاصله زمانی بین update‌های KCP. |
| `kcp-resend` | `2` | `>= 0` | آستانه fast-resend در KCP. |
| `kcp-no-congestion-control` | `true` | boolean | غیرفعال کردن congestion control در KCP. |
| `kcp-send-window` | `8192` | `>= 1` | send window بر حسب segment. |
| `kcp-recv-window` | `8192` | `>= 1` | receive window بر حسب segment. |
| `kcp-initial-cwnd` | نصف `kcp-send-window` | `1..kcp-send-window` | congestion window اولیه KCP. |
| `kcp-rx-minrto-ms` | `30` | `>= 1` | حداقل retransmission timeout. |
| `kcp-send-buffer-limit` | `0` | `>= 0` | آستانه backpressure. با مقدار `0`، حد از مجموع local send window، remote window و `10` محاسبه و به `2147483647` محدود می‌شود. |
| `ping-interval-ms` | `10000` | `>= 1` | اگر تا این مدت داده‌ای دریافت نشود، یک ping frame داخلی فرستاده می‌شود. |
| `no-recv-timeout-ms` | `30000` | بزرگ‌تر از `ping-interval-ms` | مهلت مستقل سکوت session عادی و برقراری handshake. |
| `close-drain-timeout-ms` | `30000` | عدد صحیح `1..2147483647` | مهلت ارسال پس از بستن برنامه و نگهداری ACK؛ مقدار مؤثر کمینهٔ تنظیم دو peer است. |

## مدل KCP transport

هنگام upstream `Init` فقط state مربوط به carrier قرضی ساخته می‌شود؛ هنوز
هیچ سرویس بعدی Init نمی‌شود. handshake با HELLO، CHALLENGE، CONFIRM و READY
از nonce مستقل ۱۲۸ بیتی هر سمت استفاده می‌کند. سرویس تنها پس از CONFIRM دقیق
همان جفت nonce یک بار Init می‌شود و line عادی مستقل و تحت مالکیت server دارد.
KCP/FEC و timer در session پایدار بیرون line سرویس نگهداری می‌شوند.

client هر ۲۵۰ میلی‌ثانیه درخواست فعلی handshake را تا مهلت اصلی
`no-recv-timeout-ms` تکرار می‌کند. برای هر carrier حداکثر یک challenge معلق و
۶۴ session فعال، در حال تخلیه یا نگهداری ACK مجاز است. ظرفیت پر، پذیرش تازه
را بدون قطع نگهداری sessionهای قبلی رد می‌کند. packet ناشناس یا قدیمی سرویس
را ایجاد نمی‌کند؛ HELLO قدیمی فقط challenge تازه می‌گیرد و CONFIRM قدیمی
نمی‌تواند آن را پاسخ دهد. `Est` واقعی transport فوری و مستقل از آمادگی
handshake عبور می‌کند. خروجی READY و Init می‌تواند re-entrant باشد؛ تحویل
KCP تا امن شدن Init سرویس به تعویق می‌افتد.

وقتی payload packet از node قبلی می‌رسد:

1. ابتدا طول، نوع و جفت nonce در envelope بررسی می‌شود؛ سپس FEC decoding در صورت فعال بودن اعمال می‌شود.
2. KCP datagram را می‌گیرد.
3. payload‌های کامل‌شده از KCP خوانده می‌شوند.
4. flag یک‌بایتی داخلی حذف می‌شود.
5. data frame‌ها به شکل payload stream بازسازی می‌شوند و در جهت upstream به node بعدی می‌روند.

وقتی payload stream از node بعدی برمی‌گردد:

1. payload به chunk‌هایی با حداکثر اندازه KCP write MTU موثر تقسیم می‌شود.
2. هر chunk data flag یک‌بایتی prefix می‌گیرد.
3. chunk فریم‌شده از طریق KCP ارسال می‌شود.
4. datagram‌های خروجی KCP در جهت downstream به سمت packet قبلی فرستاده می‌شوند.

## flag‌های داخلی {#flagهای-داخلی}

داخل payload KCP، `KcpServer` از همان flag‌های frame یک‌بایتی سمت client استفاده می‌کند:

| Flag | معنی |
| --- | --- |
| `0x00` | data frame. بایت‌های بعد از flag همان payload stream واقعی هستند. |
| `0xF0` | ping frame؛ نشانگر داخلی keepalive. |
| `0xFF` | close frame؛ درخواست بستن line در peer. |

یک data frame که فقط بایت flag دارد دور ریخته می‌شود. پیام خالی KCP فاقد flag
است و اتصال مربوط به آن بسته می‌شود؛ flag ناشناخته یا پیام کامل KCP که از بافر
دریافت محلی بزرگ‌تر باشد نیز اتصال را می‌بندد. پیام ناقص KCP منتظر دریافت
قطعه‌های باقی‌مانده می‌ماند.

## MTU ارسال و padding

گزینهٔ اختیاری و صحیح `send-mtu` هنگام ساخت از `misc.mtu` هسته مقدار می‌گیرد؛ پیش‌فرض
هسته 1500 است. بازهٔ معتبر **118..65535 بدون FEC** و **126..65535 با FEC** است.
این مقدار بودجهٔ بستهٔ خروجی برحسب بایت با فرض IPv4 است. مقدار صریح یا ارث‌رسیدهٔ نامعتبر
ساخت node را رد می‌کند؛ با override معتبر می‌توان پیش‌فرض نامناسب هسته را جایگزین
کرد. `null`، نوع نادرست، عدد اعشاری، صفر، عدد منفی و مقدار خارج از بازه خطا هستند.
هر نمونه مقدار معتبر خود را مستقل و ثابت نگه می‌دارد.

با `F = 0` بدون FEC و `F = 8` با FEC:

```text
KCP MTU = min(send-mtu - 20 - 8 - 40 - F, 64000)
application chunk = KCP MTU - 24 - 1
```

سهم ثابت IPv4 برابر 20 بایت، UDP برابر 8 بایت و envelope برابر 40 بایت است. سقف ده‌دهی 64000 شامل کل
بستهٔ KCP و هدر 24 بایتی آن است. پرچم یک‌بایتی داخل payload قرار دارد و node
`required_padding_left = 1` اعلام می‌کند. همین MTU خروجی داده و ACK/control
تجمیع‌شده را محدود می‌کند؛ FEC حداکثر 8 بایت، شامل بسته‌های parity، اضافه می‌کند.

دریافت محدودیت مستقل پروتکل دارد: حداکثر 64000 بایت برای بستهٔ KCP یا 64008
بایت برای shard مربوط به FEC، بدون احتساب envelope چهل‌بایتی session. دو peer
می‌توانند مقدارهای متفاوت `send-mtu` داشته باشند. بستهٔ ورودی فقط به دلیل
بزرگ‌تر بودن از بودجهٔ ارسال گیرنده رد نمی‌شود؛ اعتبارسنجی frame، هویت session
و FEC همچنان انجام می‌شود. مذاکرهٔ MTU انجام نمی‌شود.

برای `send-mtu: 1500`، MTU مؤثر KCP و chunk برنامه بدون FEC برابر **1432/1407** و
با FEC برابر **1424/1399** هستند. بودجهٔ 64068 بدون FEC یا 64076 با FEC به سقف
می‌رسد. مقادیر معتبر بزرگ‌تر، از جمله 65535، پذیرفته می‌شوند و MTU مؤثر 64000
و chunk برابر 63975 دارند؛ خود تنظیم به 64000 کاهش نمی‌یابد.

این تنظیم کشف یا مذاکرهٔ MTU مسیر نیست. هدر پایهٔ IPv6 بیست بایت بیشتر نیاز دارد؛
بودجهٔ 1500 می‌تواند بستهٔ IPv6 با طول 1520 بسازد. گزینه‌های IPv4، هدرهای توسعهٔ
IPv6 و پوشش‌های بعدی به حاشیهٔ اضافی نیاز دارند. تشخیص خودکار خانواده انجام نمی‌شود.

## رفتار FEC

با `fec: true`، datagram‌های خروجی KCP در packet‌های Reed-Solomon FEC قرار می‌گیرند. data shard‌ها بلافاصله و parity shard‌ها پس از کامل شدن هر block فرستاده می‌شوند.

در receive، decoder:

- datagram‌های KCP wrap‌شده با FEC را می‌پذیرد
- data shard‌های معتبر را به KCP می‌دهد
- تلاش می‌کند datagram‌های KCP گم‌شده را از parity shard‌ها بازسازی کند
- packet‌های FEC نامعتبر را دور می‌ریزد

FEC در دو سمت این pair رفتاری متقارن دارد. آن را در هر دو peer فعال کنید و تعداد shard‌ها را یکسان بگذارید.

## Backpressure

server پیش از فرستادن سیگنال به stream سرویس سمت بعدی هر session، فشار صف محلی KCP آن session و فشار carrier مشترک را با هم در نظر می‌گیرد. تا زمانی که هر یک از این دو علت فعال باشد، سرویس در حالت Pause می‌ماند. در کارکرد عادی، سیگنال‌های Pause/Resume دریافتی از carrier، حتی در حالت تکراری، فقط به سرویسی منتقل می‌شوند که توقف محلی KCP آن فعال نباشد. تغییر فشار محلی نیز فقط وقتی به آن سرویس اطلاع داده می‌شود که carrier در حالت Pause نباشد؛ Resume مربوط به یک علت نمی‌تواند توقف ناشی از علت دیگر را آزاد کند. پس از Init سرویس جدید، Pause در انتظار carrier حتی اگر Init فشار محلی KCP ایجاد کرده باشد به سرویس تحویل داده می‌شود تا توقف اولیهٔ آن برقرار شود. سیگنال‌های Pause/Resume سمت سرویس همچنان به carrier منتقل می‌شوند.

پس از پذیرش کامل ورودی stream و تحویل packet‌های خروجی تولیدشده، تعداد segmentهای صف‌شده و تأییدنشدهٔ KCP بالاتر از `kcp-send-buffer-limit`، توقف محلی همان session را فعال می‌کند. پایین‌تر از آستانه این توقف غیرفعال می‌شود و در مقدار برابر، وضعیت فعلی حفظ می‌شود. حتی ورودی فقط شامل ACK نیز می‌تواند توقف محلی را آزاد کند و نیازی به تولید packet خروجی دیگری نیست. وقتی مقدار تنظیم `0` است، آستانه از windowهای فعلی KCP محاسبه می‌شود. وضعیت پیش از callback ثبت می‌شود و پس از Finish، سیگنالی به سرویس بسته‌شده فرستاده نمی‌شود.

این تنظیم همچنان آستانهٔ نرم تعداد segmentهاست، نه سقف سخت حافظه یا پذیرش داده. دادهٔ آمادهٔ KCP، ACK، ارسال مجدد و pingهای موعدرسیده در حالت Pause سرویس نیز ادامه دارند. windowها، timerهای KCP و مهلت دریافت همچنان اعمال می‌شوند. هر payload به پردازش KCP و در صورت فعال بودن، FEC نیاز دارد؛ بنابراین node پس از راه‌اندازی نیز نمی‌تواند خودش را bypass کند.

## رفتار Close و timeout

مقدار `D = min(client, server)` از `close-drain-timeout-ms` دو peer مذاکره
می‌شود؛ افزایش مهلت مؤثر نیازمند اجازهٔ هر دو سمت است. با پیش‌فرض، ارسال
حداکثر ۳۰ ثانیه و نگهداری state قابل ACK حداکثر ۶۰ ثانیه از نخستین رویداد
بستن ادامه دارد. این زمان تأخیر اجباری EOF برنامه نیست.

با Finish سرویس، ارتباط دوطرفهٔ line سرویس از session جدا و state آن صفر
می‌شود و server همان line تحت مالکیت خود را پیش از بازگشت نابود می‌کند.
session روی carrier قرضی زنده می‌ماند. دادهٔ پذیرفته‌شده ابتدا تخلیه می‌شود؛
پس از ACK شدن آن، تنها یک CLOSE در KCP قرار می‌گیرد. ارسال تنها پس از ACK
شدن خود CLOSE تأییدشده است؛ flush یا خالی بودن صف پیش از CLOSE اثبات نیست.
مهلت از نخستین بستن محلی یا دریافتی ثابت می‌شود؛ handshake، پیشرفت ACK،
packet تکراری یا ping آن را تمدید نمی‌کند. برابری زمان با deadline انقضا است.

نخستین CLOSE دریافتی، برنامه را یک بار پس از داده‌های قبلی Finish می‌کند و
مهلت تخلیهٔ خروجی قبلاً پذیرفته‌شده را پیش از انتشار ACK ثابت می‌کند. CLOSE
تکراری با ACK عادی KCP پاسخ می‌گیرد و برنامه را دوباره ایجاد یا Finish
نمی‌کند. responder فقط برای CLOSE peer تا دریافت آن به‌اضافهٔ D نگه می‌ماند؛
فرستندهٔ CLOSE تأییدشده تا زمان تأیید به‌اضافهٔ D قابلیت پاسخ ACK را حفظ
می‌کند. هیچ‌یک از این deadlineها تمدید نمی‌شود.

پس از انقضای ارسال، PUSH تازه یا ارسال مجدد داده/CLOSE متوقف می‌شود؛ ACK
لازم برای CLOSE تکراری حتی در datagram ترکیبی با PUSH حفظ می‌شود. انقضا،
خرابی transport یا shutdown نتیجهٔ تأییدنشده/abort است. shutdown فوری منابع
تحت مالکیت و timerها را تخلیه می‌کند و منتظر close عادی نمی‌ماند. server
هرگز carrier قرضی را `lineDestroy` نمی‌کند؛ تا وجود session یا challenge
معلق carrier حفظ می‌شود. callback دیگری به line سرویس بازنشسته نمی‌رسد.

این قرارداد TCP half-close نیست و ACK KCP فقط دریافت transport peer را ثابت
می‌کند؛ مصرف یا ذخیرهٔ داده در برنامهٔ دوردست را تضمین نمی‌کند. timeout سکوت
عادی مستقل است و نگهداری ACK وعده‌داده‌شده را کوتاه نمی‌کند.

## envelope و هویت session

هدر ۴۰ بایتی به‌صورت صریح serialize می‌شود: magic شبکه‌ای `0x57574b43`
(`WWKC`)، بایت kind، بایت reserved صفر، طول body شبکه‌ای ۱۶ بیتی، nonce
شانزده‌بایتی client و nonce شانزده‌بایتی server. HELLO=1، CHALLENGE=2،
CONFIRM=3، READY=4، KCP=5 و FEC=6 هستند. در HELLO، nonce سرور صفر است.
body تنظیمات handshake هشت بایت دارد: مهلت close شبکه‌ای ۳۲ بیتی، دو بایت
شمار data/parity shard و دو reserved صفر. صفر/صفر یعنی FEC خاموش.
طول دقیق، reserved، nonce و تنظیم FEC پیش از دسترسی به decoder بررسی
می‌شوند. این هویت تصادفی احراز هویت یا رمزنگاری اضافه نمی‌کند.

## اشتباه‌های رایج

- `KcpServer` را از node stream-only قبلی تغذیه نکنید. سمت قبلی باید packet boundary را حفظ کند.
- بدون `KcpClient` متناظر استفاده نکنید.
- FEC را فقط در یک سمت فعال نکنید.
- تعداد FEC shard‌ها باید در هر دو سمت یکسان باشد.
- `KcpServer` را chain end در نظر نگیرید؛ payload stream بازسازی‌شده را به `next` می‌فرستد.

## متادیتای node {#متادیتای-نود}

متادیتای برگرفته از کد منبع:

این node با `kNodeFlagBlocksSplice` استفاده از splice را برای کل chain صریحاً غیرفعال می‌کند. این پرچم حتی در صورت وجود هم‌زمان `kNodeFlagSupportsSplice` اولویت دارد.

| ویژگی | مقدار |
| --- | --- |
| node flags | `kNodeFlagBlocksSplice` |
| `can_have_prev` | `true` |
| `can_have_next` | `true` |
| `layer_group` | `kNodeLayer4` |
| `layer_group_prev_node` | `kNodeLayer4` |
| `layer_group_next_node` | `kNodeLayer4` |
| `required_padding_left` | `1` byte |
