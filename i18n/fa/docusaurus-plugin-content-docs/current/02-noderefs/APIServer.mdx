# APIServer

`APIServer` یک node انتهایی برای دسترسی بیرونی به operationهایی است که صریحاً ثبت شده‌اند. خودش socket باز نمی‌کند. operationهای فقط‌خواندنی ثبت‌شده شامل `AuthenticationClient.status` و `AuthenticationServer.status`، `get-user` و `list-users` هستند؛ `AuthenticationServer.update-user` نوشتن مشروط با مجوز صریح است. اعتبارنامه‌های ثابت مدیر و مجوزهای دقیق آن از رمز کاربران ترافیک و secret سرور احراز هویت مستقل‌اند؛ قطع یا رد AuthenticationClient دسترسی تشخیصی را وابسته به آن نمی‌کند.

## جایگاه

```text
TcpListener -> APIServer
TcpListener -> HttpServer -> APIServer
UdpListener -> TcpOverUdpServer -> APIServer
```

اتصال مستقیم `UdpListener -> APIServer` پشتیبانی نمی‌شود؛ frameهای API به stream مرتب و قابل اعتماد نیاز دارند. برای برنامهٔ TCP در مسیر UDP قابل اعتماد، از nodeهای موجود استفاده کنید:

```text
TCP caller -> TcpListener -> TcpOverUdpClient -> UdpConnector
                                      loopback/protected UDP
                            UdpListener -> TcpOverUdpServer -> APIServer
```

احراز هویت API رمزنگاری transport نیست. مثال‌ها را روی loopback قرار دهید و برای دسترسی راه دور از stream حفاظت‌شده استفاده کنید.

## تنظیمات

این node به config با `name` منطقی `edge-europe` تعلق دارد؛ همان config باید AuthenticationClient عمومی با نام `auth-client` داشته باشد و config بارشدهٔ `central` یک AuthenticationServer به نام `auth-db` داشته باشد:

```json
{
  "name": "management-api",
  "type": "APIServer",
  "settings": {
    "clients": [
      {
        "name": "monitor",
        "token": "<64 hexadecimal characters representing 32 random bytes>",
        "allow": [
          {"config": "edge-europe", "node": "auth-client", "operations": ["status"]},
          {"config": "central", "node": "auth-db", "operations": ["status", "get-user", "list-users"]}
        ]
      },
      {
        "name": "editor",
        "token": "<different 64 hexadecimal characters representing 32 random bytes>",
        "allow": [
          {"config": "central", "node": "auth-db", "operations": ["get-user", "update-user"]}
        ]
      }
    ]
  }
}
```

placeholder را با token تصادفی تازه جایگزین کنید؛ برای نمونه `python3 -c 'import secrets; print(secrets.token_hex(32))'`. `clients` و فهرست مجوزها نباید خالی باشند. نام clientها و tokenهای decodeشدهٔ ۳۲ بایتی باید یکتا باشند. هر مجوز یک config منطقی، node عمومی و فهرست غیرخالی operationهای دقیق را مشخص می‌کند؛ wildcard و مجوز ضمنی مدیر وجود ندارد. reference نامعتبر یا operation ثبت‌نشده، آماده‌سازی را متوقف می‌کند. وجود `TunnelApi` به‌تنهایی آن را بیرونی نمی‌کند.

با حضور هر APIServer، تمام configهای بارشده باید نام منطقی غیرخالی و یکتا داشته باشند. selector مسیر فایل نیست و فایل تازه‌ای بار نمی‌کند. نام config/node به حروف حساس و حداکثر ۲۵۶ بایت UTF-8 است. childهای داخلی و تولیدشده هدف عمومی نیستند.

## محدودیت‌های اختیاری

همهٔ مقدارها عدد صحیح مثبت و محدودند؛ صفر حفاظت را غیرفعال نمی‌کند. هندسهٔ ناسازگار که یک request/response محدود را جا ندهد در startup رد می‌شود. envelope بدون prefix حساب می‌شود؛ بودجهٔ حافظه، charge تخصیص و copyهای موقت مربوط را نیز در بر می‌گیرد.

| تنظیم | پیش‌فرض | کاربرد |
| --- | --- | --- |
| `max_request_envelope` | 1048576 | بایت envelope درخواست. |
| `max_response_envelope` | 1048576 | بایت envelope پاسخ encodeشده. |
| `max_input_bytes` | 2097152 | payload ورودی نگه‌داشته‌شده در هر line. |
| `max_line_memory` | 8388608 | charge حافظهٔ نگه‌داشته‌شده در هر line. |
| `max_input_fragments` | 256 | سقف fragment/ورودی FIFO هر line. |
| `max_queued_requests` | 8 | درخواست منتظر، علاوه بر یک درخواست فعال. |
| `max_sessions` | 256 | session زندهٔ هر instance. |
| `max_jobs` | 64 | job پذیرفته‌شده و تمام‌نشدهٔ هر instance. |
| `handler_working_memory` | 8388608 | allowance موقت رزروشدهٔ هر handler. |
| `max_memory` | 67108864 | مجموع حافظهٔ نگه‌داشته‌شده و reservationها. |
| `frame_timeout_ms` | 15000 | مهلت مطلق تکمیل frame از نخستین بایت. |
| `request_timeout_ms` | 10000 | پذیرش request کامل تا انتشار پاسخ، شامل انتظار FIFO/worker. |
| `output_timeout_ms` | 15000 | انتشار پاسخ تا تحویل به transport، شامل Pause. |
| `idle_timeout_ms` | 60000 | زمان بی‌کاری بدون frame/request/output جاری. |

ورودی قطره‌ای مهلت frame را reset نمی‌کند. پس از انتشار پاسخ کامل، deadline درخواست پایان می‌یابد و deadline مستقل خروجی آغاز می‌شود. timeout یا قطع، job را abandoned می‌کند؛ reservation آن تا لغو واقعی یا پایان handler محدودِ در حال اجرا آزاد نمی‌شود.

حافظهٔ کاری باید تخصیص واقعی استخر worker برای نتیجهٔ ۴۰۹۶ بایتی و ۸۱۹۲ بایت فرادادهٔ تجزیه را پوشش دهد. محدودیت کوچک‌تر پاکت پاسخ، برای نتیجهٔ معتبرِ بزرگ یک خطای محدود `response_too_large` برمی‌گرداند.

## پروتکل

هر request و response با طول unsigned چهار بایتی big-endian شروع می‌شود و سپس دقیقاً همان تعداد بایت JSON با UTF-8 دارد. طول شامل prefix نیست. newline یا NUL انتهایی وجود ندارد. مرز callback، chunk HTTP یا packet UDP مرز پیام API نیست؛ prefix/body می‌توانند تکه‌تکه یا چند frame در یک read باشند.

```json
{
  "id": "request-42",
  "auth": {"client": "monitor", "token": "<configured token>"},
  "selector": {"config": "edge-europe", "node": "auth-client"},
  "operation": "status",
  "content_type": "application/json",
  "body_encoding": "utf8",
  "body": "{\"include_accounting\":true}"
}
```

همهٔ فیلدهای نمایش‌داده‌شده به‌جز `selector.config` اجباری‌اند. حذف config فقط وقتی مجاز است که نام دقیق node میان **تمام nodeهای top-level تمام configهای بارشده** یکتا باشد. ابهام پیش از بررسی ثبت API یا مجوز محاسبه می‌شود؛ allowlist آن را یکتا نمی‌کند. احراز هویت پیش از lookup هدف انجام می‌شود و مجوز به هدف و operation حل‌شده اعمال می‌شود.

`id` رشتهٔ غیرخالی UTF-8 با حداکثر ۶۴ بایت برای correlation است؛ deduplication یا checkpoint اجرا نیست. نام operation حداکثر ۶۴ و content type حداکثر ۱۲۸ بایت دارد. content type باید با descriptor operation برابر باشد. کلید ناشناخته/تکراری، type نادرست، دادهٔ اضافه، UTF-8 خراب و NUL decodeشده در metadata یا body نوع UTF-8 رد می‌شوند.

`body` همیشه رشتهٔ JSON است. نوع `utf8` بایت‌های decodeشده را بدون تغییر تحویل می‌دهد؛ نوع `base64` باید strict و canonical باشد و بایت دلخواه از جمله NUL را حمل می‌کند. gateway محتوای node را parse یا normalize نمی‌کند. schema آن با handler است؛ `AuthenticationClient.status` بدنهٔ `{}` یا `{"include_accounting":true}` را می‌پذیرد.

پاسخ dispatchشده، حتی خطای سطح node، شکل زیر را دارد:

```json
{
  "id": "request-42",
  "error": null,
  "result": {
    "code": 0,
    "content_type": "application/json",
    "body_encoding": "utf8",
    "body": "{\"can_authenticate\":true}"
  }
}
```

body بالا نمونهٔ خلاصه است؛ snapshot کامل در [AuthenticationClient](AuthenticationClient.mdx) آمده است. مقدارهای unsigned 64-bit در status رشتهٔ ده‌دهی‌اند. `result.code` معنای موفقیت/خطای handler را حفظ می‌کند. نتیجهٔ null handler به body خالی با type/encoding اعلام‌شده تبدیل می‌شود.

نماهای سرور در [AuthenticationServer](AuthenticationServer.mdx) مستند شده‌اند.
`AuthenticationServer.status` دقیقاً `{}`، `get-user` بدنهٔ `{"id":"42"}` و
`list-users` بدنهٔ `{}` یا `{"limit":50,"cursor":"<returned opaque cursor>"}`
را می‌پذیرند. تمام کمیت‌های عددی سرور رشتهٔ ده‌دهی unsigned هستند. تغییر
تنظیمات، cursor را باطل می‌کند؛ تغییر صرف آمار ادامهٔ پیمایش با مصرف تازه‌تر
را مجاز می‌گذارد. مجوز status مجوز get/list نیست و هر ادامه دوباره مجوزسنجی
می‌شود.

خطای gateway، `result: null` دارد:

```json
{
  "id": "request-42",
  "error": {"code": "ambiguous_target", "message": "Specify the configuration name."},
  "result": null
}
```

اگر ID محدود و قابل اعتماد قابل بازیابی نباشد، null است. codeها عبارت‌اند از `invalid_request`، `invalid_encoding`، `unauthorized`، `forbidden`، `target_not_found`، `ambiguous_target`، `unsupported_api`، `unsupported_operation`، `unsupported_content_type`، `busy`، `timeout`، `shutting_down` و `response_too_large`. پیام‌ها ثابت و محدودند. client ناشناس و token نادرست هر دو `unauthorized` می‌دهند.

frame/schema خراب و احراز هویت نامعتبر پس از حداکثر یک پاسخ خطای محدود، اتصال را می‌بندند. خطاهای هدف/operation/body در request معتبر و مجاز می‌توانند به ترتیب FIFO ادامه یابند. اگر خطا هم در بودجه جا نشود، بستن مستقیم مجاز است. پس از شروع پاسخ، خرابی transport یا timeout اتصال را می‌بندد و frame تازه در میانهٔ پاسخ درج نمی‌کند. انقضای request صف‌شده پشت پاسخ قبلی نیز بدون خطای خارج از ترتیب اتصال را می‌بندد.

## تونل body در HTTP

برای ترکیب مستندشده از HTTP/1.1 معمولی در حالت single استفاده کنید:

```json
{
  "name": "http-body",
  "type": "HttpServer",
  "settings": {
    "http-version": "1.1",
    "http1-mode": "single",
    "upgrade": false,
    "path": "/management",
    "method": "POST"
  },
  "next": "management-api"
}
```

بایت‌های frame API را در body با Content-Length یا chunked معتبر بفرستید. پاسخ HTTP را ابتدا dechunk کنید و سپس طول API را بخوانید. برای شناخت پاسخ کامل منتظر EOF یا chunk پایانی نمانید. method/path تنظیم‌شده فقط تونل body را انتخاب می‌کند؛ APIServer تنها بایت body را می‌بیند. اعتبارنامه در envelope هر request است. این رابط request object از نوع REST، احراز هویت header یا HTTP status جدا برای هر operation ندارد.

## برنامهٔ نمونه

`examples/api_client.py` فقط از کتابخانهٔ استاندارد Python استفاده می‌کند. token از محیط یا فایل خوانده می‌شود و آرگومان خط فرمان نیست:

```bash
export WATERWALL_API_TOKEN="$(cat /private/path/operator-token)"
python3 examples/api_client.py --host 127.0.0.1 --port 9080 \
  --client monitor --token-env WATERWALL_API_TOKEN \
  --config edge-europe --node auth-client
```

به‌جای محیط می‌توانید `--token-file /private/path/operator-token` بدهید. body پیش‌فرض status برابر `{}` است؛ `--body-file` بایت فایل را حفظ می‌کند و `--body-encoding base64` برای operation دودویی است. client طول و ID پاسخ را کنترل می‌کند، frame را کامل می‌خواند و body decodeشده را به stdout می‌نویسد. retry خودکار ندارد. برای TcpOverUdp به TcpListener محلی نمودار وصل شوید؛ پیاده‌سازی KCP در Python لازم نیست.

برای خواندن دیتابیس مرجع، در کلاینت نمونه `--config central --node auth-db`
را مشخص کنید. پیش‌فرض `--operation status` بدنهٔ `{}` دارد. برای جزئیات،
`{"id":"9007199254740993"}` را در فایل UTF-8 قرار دهید و
`--operation get-user --body-file /private/path/query.json` بدهید. برای فهرست
از `--operation list-users` و بدنهٔ `{"limit":50}` استفاده کنید؛ در ادامه cursor
دریافتی را به همان بدنه اضافه کنید. `stale_cursor` نیاز به پیمایش تازه بدون
cursor دارد و `busy` به معنی امتناع محدود نمونه‌برداری است. retryها به تصمیم
فراخواننده‌اند و کلاینت نمونه به‌صورت خودکار تکرار نمی‌کند.

برای ویرایش مشروط، token جداگانهٔ editor با مجوز دقیق `get-user` و
`update-user` تنظیم کنید؛ token مانیتور فقط‌خواندنی می‌ماند. در فایل
`lookup.json` بدنهٔ `{"id":"42"}` قرار دهید و ابتدا حساب را بخوانید:

```bash
python3 examples/api_client.py --host 127.0.0.1 --port 9080 \
  --client editor --token-file /private/path/editor-token \
  --config central --node auth-db --operation get-user \
  --body-file lookup.json > account.json
```

پس از بازبینی حساب، فقط برگ‌های مورد نظر را همراه token همان snapshot در
فایل ویرایش قرار دهید؛ کل user را به patch تبدیل نکنید:

```python
import json
from pathlib import Path

account = json.loads(Path("account.json").read_text(encoding="utf-8"))
request = {"id": account["user"]["id"], "if_match": account["edit_token"],
           "patch": {"enabled": False}}
Path("update.json").write_text(json.dumps(request), encoding="utf-8")
```

یک بار ارسال کنید:

```bash
python3 examples/api_client.py --host 127.0.0.1 --port 9080 \
  --client editor --token-file /private/path/editor-token \
  --config central --node auth-db --operation update-user \
  --body-file update.json
```

تمام خواندن‌های سرور `edit_token` دارند؛ `update-user` آن را به‌عنوان
`if_match` می‌خواهد. تغییر تنظیمات، حتی حساب دیگر، هم token ویرایش قبلی و هم
cursor قبلی را باطل می‌کند؛ تغییر صرف آمار آن‌ها را باطل نمی‌کند. پاسخ موفق
فقط `id`، `config_revision` و `edit_token` همان commit در حافظه را دارد؛ ذخیره
و refresh کلاینت جدا هستند. `conflict` سطح node یعنی commit نشده: دوباره
بخوانید و قصد تغییر را بازبینی کنید. گم‌شدن پاسخ، قطع یا timeout gateway
می‌تواند پس از commit رخ دهد؛ نتیجه نامعلوم است و پیش از تصمیم تازه باید
حساب دوباره خوانده شود. token تازه را خودکار نگیرید و patch قدیمی را replay
نکنید. کلاینت نمونه راهنمای conflict/نتیجهٔ نامعلوم را چاپ می‌کند و retry
خودکار نوشتن ندارد؛ ID درخواست باعث deduplication نمی‌شود.

## lifecycle و metadata

تمام lineهای پذیرفته‌شده برای APIServer از نوع borrowed normal هستند و هرگز `lineDestroy()` نمی‌شوند. state پیش از Est سمت قبلی آماده و پاسخ‌ها downstream ارسال می‌شوند. در هر اتصال فقط یک operation dispatch می‌شود و بقیه FIFO هستند. Pause/Resume تولیدکنندهٔ پاسخ را کنترل می‌کند؛ deadline و سقف‌ها فعال می‌مانند. job جداشده فقط token session/request دارد؛ تنها worker اتصال می‌تواند session زنده را resolve کند و line را لمس کند. shutdown پیش از quiescence هدف‌ها admission عمومی API را می‌بندد؛ مالک واقعی lineها پیش از نابودی registry آن‌ها را drain می‌کند.

| ویژگی | مقدار |
| --- | --- |
| node flags | `kNodeFlagChainEnd`, `kNodeFlagBlocksSplice` |
| `can_have_prev` | `true` |
| `can_have_next` | `false` |
| `layer_group` | `kNodeLayer4` |
| `layer_group_prev_node` | `kNodeLayer4` |
| `layer_group_next_node` | `kNodeLayerNone` |
| `required_padding_left` | `0` bytes |
