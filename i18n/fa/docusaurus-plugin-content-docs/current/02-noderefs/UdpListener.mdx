# UdpListener

## نمای کلی {#overview}

`UdpListener` یک adapter سرور UDP است که روی آدرس و پورتی محلی به datagramهای ورودی گوش می‌دهد. listener ثابت آن‌ها را بر اساس دو سر ارتباط، یعنی endpoint راه دور و endpoint محلی، گروه‌بندی می‌کند و payload هر line را در جهت upstream به گره بعدی می‌فرستد. این گره معمولاً در ابتدای زنجیرهٔ UDP با مدل جریان قرار می‌گیرد.

پیش از `Init` رو به upstream، مبدأ و مقصد هر خط عادی جدید با پروتکل دقیق UDP
ثبت می‌شوند.

## جایگاه معمول در زنجیره {#typical-placement}

```text
client -> UdpListener -> ... -> UdpConnector -> remote UDP service
```

## نمونهٔ کاربردی ساده {#minimal-practical-example}

<a id="نمونهی-پیکربندی"></a>

### نمونهٔ پیکربندی {#configuration-example}

<a id="عبور-درخواستهای-dns-روی-udp-از-resolver-انتخابشده"></a>

#### ارسال درخواست‌های DNS روی UDP به resolver انتخاب‌شده {#relay-udp-dns-requests-to-a-chosen-resolver}

```json
{
  "name": "local-udp-dns-relay",
  "nodes": [
    {
      "name": "dns-in",
      "type": "UdpListener",
      "settings": {
        "address": "127.0.0.1",
        "port": 1053
      },
      "next": "dns-out"
    },
    {
      "name": "dns-out",
      "type": "UdpConnector",
      "settings": {
        "address": "192.0.2.53",
        "port": 53
      }
    }
  ]
}
```
این پیکربندی کامل گره‌ها، UDP دریافتی روی `127.0.0.1:1053` را به یک DNS resolver می‌فرستد.
`192.0.2.53:53` را با resolver قابل‌دسترسی خود جایگزین کنید و فایل را در
`core.json.configs` بگذارید. پاسخ به همان peer محلی برمی‌گردد؛ WaterWall پیام DNS را
parse یا cache نمی‌کند. این زنجیره فقط UDP دارد. اگر frontend یکسان باید DNS روی
هر دو TCP و UDP را بپذیرد، [نمونه DNS با TcpUdpListener](./TcpUdpListener.mdx#basic-example)
را ببینید.


## پیکربندی {#configuration}

<a id="فیلدهای-الزامی"></a>

### فیلدهای الزامی {#required-fields}

فیلدهای سطح اول:

| فیلد | نوع | توضیح |
| --- | --- | --- |
| `name` | string | نامی که کاربر برای گره انتخاب می‌کند و باید در فایل config یکتا باشد. |
| `type` | string | باید دقیقاً `"UdpListener"` باشد. |
| `next` | string | نام گره‌ای که line‌ها و payload‌های peer‌های UDP را دریافت می‌کند. |

فیلدهای الزامی در `settings`:

| فیلد | نوع | توضیح |
| --- | --- | --- |
| `address` | string | آدرس محلی برای bind، مانند `"0.0.0.0"`، ‏`"::"` یا یک IP محلی مشخص. |
| `port` یا `port-range` | number، ‏array یا range array | تعریف پورت listen؛ وجود دقیقاً یکی از این دو فیلد الزامی است. |

`settings` باید یک object غیرخالی باشد.

<a id="تنظیم-پورت"></a>

### تنظیم پورت {#port-configuration}

`UdpListener` سه حالت برای پورت دارد.

<a id="یک-پورت"></a>

#### یک پورت {#single-port}

```json
{
  "settings": {
    "address": "0.0.0.0",
    "port": 5353
  }
}
```

<a id="فهرست-صریح-پورتها"></a>

#### فهرست صریح پورت‌ها {#explicit-port-list}

```json
{
  "settings": {
    "address": "0.0.0.0",
    "port": [
      5353,
      853,
      123
    ]
  }
}
```

در این حالت فقط روی پورت‌های نوشته‌شده گوش داده می‌شود؛ این array به‌معنای بازه‌ی
`123` تا `5353` نیست.

<a id="بازهی-پیوستهی-پورتها"></a>

#### بازهٔ پیوستهٔ پورت‌ها {#contiguous-port-range}

```json
{
  "settings": {
    "address": "0.0.0.0",
    "port-range": [
      20000,
      20100
    ]
  }
}
```

`port-range` باید array‌ای شامل دقیقاً دو پورت integer مثبت به‌شکل `[min, max]`
باشد. مقدار کمینه باید کوچک‌تر یا مساوی مقدار بیشینه باشد.

قواعد:

| قاعده | رفتار |
| --- | --- |
| استفاده‌ی هم‌زمان از `port` و `port-range` | راه‌اندازی متوقف می‌شود. |
| مقدار number برای `port` | روی یک پورت UDP گوش می‌دهد. |
| مقدار array برای `port` | روی پورت‌های صریح موجود در array گوش می‌دهد. |
| مقدار array برای `port-range` | روی همه‌ی پورت‌های UDP از مقدار کمینه تا بیشینه گوش می‌دهد. |
| پورت نامعتبر، صفر، منفی یا بیشتر از `65535` | راه‌اندازی متوقف می‌شود. |

:::warning
از بازه‌های قدیمی با قالب string، مانند `"20000-20100"`، استفاده نکنید. parser
فعلی برای `port-range` یک array دومقداری انتظار دارد.
:::

<a id="تنظیمات-اختیاری"></a>

### تنظیمات اختیاری {#optional-settings}

| تنظیم | نوع | مقدار پیش‌فرض | توضیح |
| --- | --- | --- | --- |
| `large-send-buffer` | boolean یا integer مثبت | `true` | مقدار `SO_SNDBUF` را روی socket‌های listener نوع UDP تنظیم می‌کند. |
| `large-recv-buffer` | boolean یا integer مثبت | `true` | مقدار `SO_RCVBUF` را روی socket‌های listener نوع UDP تنظیم می‌کند. |
| `interface` | string | تنظیم نشده | listener را به یک interface محلی شبکه محدود می‌کند. |
| `fwmark` | integer | تنظیم نشده | در صورت پشتیبانی، یک socket mark به سبک Linux اعمال می‌کند. |
| `balance-group` | string | تنظیم نشده | listener‌های سازگار و هم‌پورت را برای توزیع پایدار peer‌ها در یک گروه قرار می‌دهد. |
| `balance-interval` | integer، بر حسب میلی‌ثانیه | مقدار پیش‌فرض socket manager | مدت حفظ انتخاب قبلی برای peer‌های تکراری در balance group. |
| `multiport-backend` | string | مقدار پیش‌فرض runtime برای `port-range` | backend مربوط به بازه‌ی پیوسته‌ی پورت‌ها: `"iptables"` یا `"socket"`. |
| `whitelist` | array‌ای از string‌ها | تنظیم نشده | IP‌ها یا بازه‌های CIDR مجاز برای peer. |
| `blacklist` | array‌ای از string‌ها | تنظیم نشده | IP‌ها یا بازه‌های CIDR مسدود برای peer. |

<a id="گزینههای-socket-buffer"></a>

#### گزینه‌های socket buffer {#socket-buffer-options}

`large-send-buffer` و `large-recv-buffer` مقادیر زیر را می‌پذیرند:

| مقدار | مفهوم |
| --- | --- |
| `true` | از اندازه‌ی پیش‌فرض WaterWall برای socket buffer بزرگ استفاده می‌کند که در حال حاضر `16777216` byte است. |
| `false` | این socket buffer را صریحاً تنظیم نمی‌کند و مقدار پیش‌فرض Kernel به کار می‌رود. |
| integer مثبت | همان تعداد byte را مستقیماً درخواست می‌کند. |

هر دو گزینه برای listener‌های UDP به‌صورت پیش‌فرض از socket buffer بزرگ WaterWall
استفاده می‌کنند. همین parser برای socket‌های association پویا هم اعمال می‌شود:
`false` مقدار پیش‌فرض Kernel را برای آن‌ها نیز دست‌نخورده می‌گذارد و buffer بزرگ
WaterWall درخواست نمی‌کند.

<a id="interface-و-fwmark"></a>

#### interface و `fwmark` {#interface-and-fwmark}

`interface`، ‏listener را به یک دستگاه محلی شبکه محدود می‌کند.

در Linux، ‏WaterWall از `SO_BINDTODEVICE` استفاده می‌کند. در platform‌هایی که bind
به device را پشتیبانی نمی‌کنند، WaterWall در صورت امکان روی آدرس IPv4 همان
interface bind می‌شود.

روی socket متصل به device، انتخاب فقط میان listenerهای همان interface و
listenerهای بدون محدودیت interface انجام می‌شود. listener مربوط به interface
دیگر، حتی با اولویت بالاتر ACL یا انتخاب ذخیره‌شده‌ی balance، واجد شرایط نیست.
listenerهای بدون محدودیت همچنان بر اساس اولویت معمول آدرس و ACL و ترتیب ثبت
رقابت می‌کنند؛ محدودیت interface اولویت تازه‌ای ایجاد نمی‌کند. socket بدون
محدودیت، interface ورودی مشخصی ندارد و نمی‌تواند listener محدود به یک interface
را انتخاب کند. در platformهای دیگر، انتخاب بر اساس آدرس مؤثر bind همان interface
انجام می‌شود. انتخاب پایدار balance علاوه بر IP کلاینت، آدرس محلی و پورت مقصد
منطقی، بر اساس protocol و محدوده‌ی مؤثر interface نیز جدا می‌شود.

`fwmark` در platform‌های پشتیبانی‌شده از `SO_MARK` استفاده می‌کند. این قابلیت به
platform وابسته است و در Windows در دسترس نیست.


## کاربرد و رفع اشکال {#usage-and-troubleshooting}

<a id="filter-و-توزیع"></a>

### فیلتر و توزیع {#filtering-and-balancing}

پیش از آنکه datagram به `UdpListener` برسد، socket manager مشترک عملیات filter
و توزیع را انجام می‌دهد.

| تنظیم | رفتار |
| --- | --- |
| `whitelist` | در صورت تنظیم، فقط peer‌هایی پذیرفته می‌شوند که IP آن‌ها با فهرست منطبق باشد. |
| `blacklist` | peer‌هایی را که IP آن‌ها با فهرست منطبق است رد می‌کند. |
| `balance-group` | توزیع پایدار peer‌ها را میان listener‌های سازگار روی یک پورت فعال می‌کند. |
| `balance-interval` | مشخص می‌کند peer چه مدت به listener انتخاب‌شده اختصاص داده شود. |
| `multiport-backend` | روش پیاده‌سازی listener دارای `port-range` پیوسته را تعیین می‌کند. |

اگر هر دو ACL تنظیم شده باشند، peer باید، در صورت وجود Whitelist، با آن منطبق
باشد و نباید با Blacklist تطابق داشته باشد.

نمونه:

```json
{
  "settings": {
    "address": "0.0.0.0",
    "port": 5353,
    "whitelist": [
      "10.0.0.0/8",
      "203.0.113.10/32",
      "2001:db8::/64"
    ],
    "blacklist": [
      "10.0.0.99/32"
    ]
  }
}
```

### idle timeout {#idle-timeout}

هر line مربوط به peer در یک جدول idle ردیابی می‌شود.

timeout‌های فعلی:

| وضعیت | timeout |
| --- | --- |
| line تازه‌ساخته‌شده برای peer | حدود `30 seconds` |
| peer فعال پس از ادامه‌ی ترافیک | حدود `300 seconds` |

اگر line مربوط به peer منقضی شود، `UdpListener` یک `finish` در upstream می‌فرستد
و line‌ای را که خودش ساخته است نابود می‌کند.

<a id="نکات-و-محدودیتها"></a>

### نکات و محدودیت‌ها {#notes-and-caveats}

- `UdpListener` یک گره آغاز زنجیره برای UDP است و به `next` نیاز دارد.
- array‌های `port` فهرست صریح‌اند، نه بازه.
- برای بازه‌های پیوسته از `port-range` استفاده کنید.
- `whitelist` و `blacklist`، ‏string‌های CIDR مربوط به IPv4 و IPv6 را می‌پذیرند.
- `fwmark` و bindشدن به device به platform وابسته‌اند.
- line‌های peer در حالت Pause، ‏datagram‌های ورودی را به‌جای bufferکردن دور می‌ریزند.
- endpointهای پویا زیرساخت داخلی این قابلیت‌اند، نه پورت‌های عمومی اضافه‌ای که با
  `port` یا `port-range` تنظیم شوند.
- برای سرویس داخلی SOCKS5 UDP، توپولوژی
  `TcpUdpListener -> ... -> Socks5Server` را config کنید، نه یک ورودی مستقل
  `UdpListener` یا `TcpListener`.
- برای رفتار stateless و در سطح بسته در UDP، شاید `UdpStatelessSocket` انتخاب
  مناسب‌تری از `UdpListener` باشد.


## رفتار پیشرفته {#advanced-behavior}

<a id="ارائهدهندهٔ-endpoint-پویا"></a>

### ارائه‌دهندهٔ endpoint پویا {#dynamic-endpoint-provider}

`UdpListener` یک ارائه‌دهندهٔ درون‌پردازه‌ای با رابط نوع‌دار برای ساخت endpoint پویا نیز
در اختیار تونل پروتکلی سازگار در همان زنجیره می‌گذارد.
[`Socks5Server`](./Socks5Server.mdx) یکی از مصرف‌کنندگان این قابلیت است. برای یک
سرویس عادی SOCKS5 از [`TcpUdpListener`](./TcpUdpListener.mdx) استفاده کنید: child
داخلی `TcpListener`، ‏control connection الزامی TCP را می‌پذیرد و child داخلی
`UdpListener` این provider را واگذار می‌کند. یک `UdpListener` مستقل به‌تنهایی
ورودی کامل SOCKS5 نیست، زیرا نمی‌تواند آن control connection نوع TCP را بپذیرد.

این یک قابلیت از `interface.h` است، نه یک تنظیم در JSON و نه API پیام خارجی
`instance/api.c`. گره `Socks5Server` آن را به‌صورت خودکار از مسیر قبلی نهایی‌شدهٔ
خود پیدا می‌کند؛ اپراتور نام گره provider را config نمی‌کند.

provider روی Event worker درخواست‌کننده یک socket UDP اختصاصی را با bind انحصاری
روی `port: 0` می‌سازد و یک handle مقداری و opaque (شامل WID مالک و generation)،
آدرس محلی تخصیص‌داده‌شده توسط kernel، و port واقعی را برمی‌گرداند. Handle فقط روی
worker مالک معتبر است؛ close تکراری یا handle قدیمی بی‌خطر است و endpoint جدیدتر را
نمی‌بندد.

ورود داده از endpoint پویا مسیر عادی زنجیره را طی می‌کند:

```text
dynamic UDP socket -> UdpListener -> TcpUdpListener (if present) -> next chain
```

پاسخ‌های downstream از همان endpoint به peer پین‌شده بازمی‌گردند. socket پویا از
address، ‏interface، ‏`fwmark`، ‏buffer‌های send/receive، ‏whitelist و blacklist
listener استفاده می‌کند، اما از `port` ثابت، بازهٔ port، ‏balance group و
multiport backend استفاده نمی‌کند.

پیش از آن‌که یک datagram پویا بتواند line متعلق به provider را بسازد یا استفاده
کند، IP نرمال‌شدهٔ peer باید دقیقاً با IP مورد انتظار endpoint برابر باشد. source
port غیرصفرِ تنظیم‌شده نیز باید دقیقاً برابر باشد؛ source port صفر نخستین sender
معتبر را pin می‌کند و همهٔ port‌های بعدی باید با همان pin برابر باشند. datagram‌های
نامطابق بی‌صدا drop می‌شوند و TCP control association را نمی‌بندند یا به آن پیام
نمی‌دهند.

در Quiesce، بازکردن یا فعال‌سازی endpoint تازه رد می‌شود. روی worker مالک، ابتدا
callback‌های WIO جدا می‌شوند، سپس endpoint از registry محلی worker حذف می‌شود و یک
مسیر بستن واحد و تکرارپذیر بدون اثر اضافی (idempotent) برای line عادی متعلق به provider اجرا می‌شود.
این فهرست endpointها از جدول عادی peerها در socket manager جدا است.


## جزئیات پیاده‌سازی {#implementation-details}

<a id="چه-کاری-انجام-میدهد"></a>

### چه کاری انجام می‌دهد {#what-it-does}

- روی یک پورت UDP، چند پورت مشخص یا یک بازه‌ی پیوسته از پورت‌ها گوش می‌دهد.
- datagram‌های UDP ورودی را از طریق socket manager در WaterWall دریافت می‌کند.
- filter‌های اختیاری listener، مانند `whitelist`، ‏`blacklist` و balance group‌ها
  را اعمال می‌کند.
- در تونل انتخاب‌شده، lineهای ثابت را بر اساس جفت endpoint راه دور و محلی ردیابی می‌کند.
- datagram‌های ورودی را به‌صورت payload در upstream به گره بعدی می‌فرستد.
- payload‌های downstream را به آدرس peer ذخیره‌شده بازمی‌گرداند.
- line‌های peer را با idle timeout مربوط به UDP ردیابی می‌کند.

<a id="مدل-یک-line-بهازای-هر-peer"></a>

### lineهای listener ثابت {#per-peer-line-model}

نخستین datagram پذیرفته‌شده در تونل انتخاب‌شده یک line می‌سازد. این line آدرس IP و
پورت مبدأ peer، آدرس IP مقصد محلی و پورت منطقی listener را ثبت می‌کند. بسته‌هایی که
دو سر ارتباط و مبدأ پاسخشان یکسان است، تا زمان انقضا از همان line استفاده می‌کنند.
اگر کلاینت از یک socket به دو آدرس unicast روی یک listener
از نوع wildcard بفرستد، دو line ساخته می‌شود. پاسخ هر line از همان آدرسی می‌آید که
کلاینت بسته را به آن فرستاده است.

برای broadcast و multicast، انتخاب listener و مسیریابی بر اساس آدرس مقصد بسته انجام
می‌شود و پاسخ از یک آدرس unicast محلی فرستاده می‌شود. اگر برای بسته‌های بین همان دو
endpoint آدرس‌های مبدأ متفاوتی برای پاسخ ترجیح داده شوند، listener برای هر آدرس یک
line جدا نگه می‌دارد تا مبدأ پاسخ‌هایی که با تأخیر ارسال می‌شوند نیز حفظ شود. وقتی
بستهٔ IPv4 از طریق listener دوپشتهٔ `::` دریافت می‌شود، آدرس مقصد در `dest_ctx` از نوع
IPv4 است و قواعد IPv4 در Router می‌توانند با آن مطابقت داشته باشند.

هنگام استفاده از backend نوع `iptables` برای بازهٔ پورت، ممکن است IP مقصد پیش از
رسیدن بسته به socket بازنویسی شود. WaterWall از IP تحویل‌شده به socket استفاده
می‌کند و می‌کوشد پورت مقصد اصلی را به‌عنوان پورت منطقی listener بازیابی کند. اگر
بازیابی ممکن نباشد، پورت محلی socket را به کار می‌برد.

<a id="جریان-داده"></a>

### جریان داده {#data-flow}

از peer به زنجیره:

```text
UDP datagram -> UdpListener -> upstream payload -> next node
```

از زنجیره به peer:

```text
previous downstream payload -> UdpListener -> UDP send to remembered peer
```

در یک line ثابت، source context مربوط به UDP شامل IP سمت peer و پورت منطقی
listener است. پورت مبدأ واقعی peer در `routing_context.peer_source_port` قرار دارد.
destination context مربوط به UDP شامل IP مقصد محلی و پورت منطقی listener است.

<a id="معنای-establishment"></a>

### معنای Establishment {#establishment-semantics}

line جدید peer با نخستین datagram پذیرفته‌شده ساخته می‌شود، اما فقط زمانی
Established خواهد شد که callback مربوط به `est` در downstream از گره بعدی به
`UdpListener` برسد.

<a id="رفتار-pause"></a>

### رفتار Pause {#pause-behavior}

وقتی line مربوط به peer در حالت Pause است، `UdpListener`، ‏datagram‌های ورودی را در
صف نگه نمی‌دارد.

اگر datagramی برای یک line در حالت Pause برسد:

- datagram دور ریخته می‌شود؛
- line زنده می‌ماند؛
- پس از Resume، ‏datagram‌های تازه‌ی همان peer دوباره قابل Forward هستند.

این رفتار با Backpressure شبیه TCP متفاوت است. در این گره، ‏Pause یعنی دورریختن
داده، نه نگه‌داشتن آن در buffer.

<a id="ارسال-udp-با-splice"></a>

### ارسال UDP با splice {#udp-splice-sending}

دریافت UDP همچنان از buffer عادی استفاده می‌کند. در زنجیره واجد شرایط روی Linux، ارسال UDP دادهٔ عادی یا prefix واقعی همراه با بدنهٔ pipe خصوصی را به‌صورت یک datagram به مقصد مشخص می‌پذیرد؛ datagram خالی نیز معتبر است. چیدمان‌های پشتیبانی‌شده از splice بین pipe و socket استفاده می‌کنند. برای pipe با fragment‌های زیاد، یا وقتی پیش از ارسال نتوان حد امن fragment‌ها را اثبات کرد، کل datagram پیش از شروع تجمیع روی socket به buffer عادی تبدیل می‌شود. دادهٔ بیش‌ازحد بزرگ بدون تقسیم رد می‌شود.

فشار پیش از شروع تجمیع همان سیاست drop فعلی را حفظ می‌کند و صف retry برای UDP ایجاد نمی‌شود. splice ناقص یا شکست commit پس از priming فقط socket مربوط را بازنشسته می‌کند و line‌های عادی وابسته از مسیر مالکشان بسته می‌شوند. بنابراین peer‌های یک socket مشترک ممکن است با هم بسته شوند. باقی‌ماندهٔ ناقص دوباره ارسال نمی‌شود و socket‌های دیگر فعال می‌مانند. سیاست خطای ارسال عادی تغییر نمی‌کند.

این پرچم بررسی پشتیبانی پلتفرم، `misc.splice`، کنارگذاشتن حالت بسته‌ای و پشتیبانی همهٔ گره‌های زنجیرهٔ نهایی پس از گسترش و ادغام را دور نمی‌زند. zero-copy سرتاسری یا بهبود کاراییِ اندازه‌گیری‌شده تضمین نمی‌شود.

بازنشستگی listener ثابت ابتدا پذیرش را می‌بندد و سپس worker‌های مالک peer را مطلع می‌کند. اگر اعلان لغو شود، مهلت محدود idle موجود و drain زمان shutdown مسئول بستن باقی می‌مانند؛ ترافیک socket بازنشسته نمی‌تواند peer بسازد یا مهلت آن را تمدید کند. endpoint پویا، handle و WIO و line خود را با هم جدا می‌کند.
