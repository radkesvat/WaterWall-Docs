# TcpListener

`TcpListener` آداپتور سرور TCP است. روی یک آدرس و پورت TCP محلی گوش می‌دهد، اتصال‌های TCP ورودی را می‌پذیرد، برای هر socket پذیرفته‌شده یک line در WaterWall می‌سازد و آن line را به نود بعدی در chain تحویل می‌دهد.

جایگاه رایج:

```text
client -> TcpListener -> ... -> TcpConnector -> سرویس راه دور
```

این نود معمولاً در ابتدای یک stream chain قرار می‌گیرد.

## قابلیت‌ها

- گوش دادن روی یک پورت TCP، چند پورت مشخص، یا یک بازه پیوسته.
- پذیرش clientهای TCP ورودی.
- ساختن یک line برای هر socket پذیرفته‌شده.
- ارسال payload client به صورت upstream به نود بعدی.
- ارسال payload downstream از chain به socket client.
- اعمال فیلترهای اختیاری در زمان accept مثل `whitelist`، `blacklist` و گروه‌های balance.

`TcpListener` یک نود chain-head است. اتصال‌ها توسط clientهای خارجی TCP ساخته می‌شوند، نه توسط تونل WaterWall قبلی.

## نمونه تنظیم

```json
{
  "name": "inbound-listener",
  "type": "TcpListener",
  "settings": {
    "address": "0.0.0.0",
    "port": [
      443,
      80,
      2083
    ],
    "nodelay": true,
    "large-send-buffer": true,
    "large-recv-buffer": true,
    "interface": "eth0",
    "fwmark": 10,
    "balance-group": "public-443",
    "balance-interval": 30000,
    "initial-idle-timeout-ms": 5000,
    "active-idle-timeout-ms": 300000,
    "multiport-backend": "socket",
    "whitelist": [
      "192.168.1.0/24",
      "2001:db8::/64"
    ],
    "blacklist": [
      "192.168.1.50/32"
    ]
  },
  "next": "next-node-name"
}
```

## فیلدهای ضروری

فیلدهای سطح بالا:

| فیلد | نوع | توضیح |
| --- | --- | --- |
| `name` | string | نام دلخواه نود. باید داخل فایل config یکتا باشد. |
| `type` | string | باید دقیقاً `"TcpListener"` باشد. |
| `next` | string | نودی که lineهای TCP پذیرفته‌شده را دریافت می‌کند. |

فیلدهای ضروری داخل `settings`:

| فیلد | نوع | توضیح |
| --- | --- | --- |
| `address` | string | آدرس bind محلی، مثل `"0.0.0.0"`، `"::"` یا یک IP محلی مشخص. |
| `port` یا `port-range` | عدد، آرایه، یا آرایه بازه | تعریف پورت گوش دادن. دقیقاً یکی از این دو فیلد لازم است. |

`settings` باید یک object غیرخالی باشد.

## تنظیم پورت

`TcpListener` سه حالت پورت دارد.

### یک پورت

```json
{
  "settings": {
    "address": "0.0.0.0",
    "port": 443
  }
}
```

### لیست پورت مشخص

```json
{
  "settings": {
    "address": "0.0.0.0",
    "port": [
      443,
      80,
      2083
    ]
  }
}
```

این حالت فقط روی پورت‌های لیست‌شده گوش می‌دهد. بازه‌ای از `80` تا `2083` نیست.

### بازه پیوسته

```json
{
  "settings": {
    "address": "0.0.0.0",
    "port-range": [
      40000,
      40100
    ]
  }
}
```

`port-range` باید آرایه‌ای با دقیقاً دو پورت عدد صحیح مثبت باشد: `[min, max]`. مقدار کمینه باید کوچک‌تر یا برابر بیشینه باشد.

:::warning
از فرم‌های قدیمی string مثل `"40000-40100"` استفاده نکنید. parser فعلی انتظار دارد `port-range` یک آرایه دو عضوی باشد.
:::

قوانین:

| قانون | رفتار |
| --- | --- |
| استفاده همزمان از `port` و `port-range` | شروع با خطا. |
| `port` عددی | روی یک پورت گوش می‌دهد. |
| `port` آرایه | روی پورت‌های مشخص داخل آرایه گوش می‌دهد. |
| `port-range` آرایه | روی هر پورت از کمینه تا بیشینه گوش می‌دهد. |
| پورت نامعتبر، صفر، منفی یا بزرگ‌تر از `65535` | شروع با خطا. |

## تنظیمات اختیاری

| گزینه | نوع | پیش‌فرض | توضیح |
| --- | --- | --- | --- |
| `nodelay` | boolean | `false` | فعال‌سازی `TCP_NODELAY` روی socketهای پذیرفته‌شده. |
| `large-send-buffer` | boolean یا عدد مثبت | `false`، یا `true` اگر mux وجود داشته باشد و مقدار حذف شده باشد | تنظیم `SO_SNDBUF` روی socketهای پذیرفته‌شده. |
| `large-recv-buffer` | boolean یا عدد مثبت | `false`، یا `true` اگر mux وجود داشته باشد و مقدار حذف شده باشد | تنظیم `SO_RCVBUF` روی socketهای پذیرفته‌شده. |
| `interface` | string | تنظیم نشده | محدود کردن listener به یک interface محلی. |
| `fwmark` | integer | تنظیم نشده | اعمال socket mark به سبک Linux در صورت پشتیبانی. |
| `balance-group` | string | تنظیم نشده | قرار دادن این listener در یک گروه با listenerهای هم‌پورت دیگر برای توزیع client. |
| `balance-interval` | integer، میلی‌ثانیه | پیش‌فرض socket manager | مدت sticky بودن clientهای تکراری در یک balance group. |
| `initial-idle-timeout-ms` | عدد مثبت، میلی‌ثانیه | `5000` | timeout قبل از مشاهده فعالیت payload سمت listener. |
| `active-idle-timeout-ms` | عدد مثبت، میلی‌ثانیه | `300000` | timeout بعد از مشاهده فعالیت سمت listener. |
| `multiport-backend` | string | پیش‌فرض runtime برای `port-range` | backend برای بازه‌های پیوسته: `"iptables"` یا `"socket"`. |
| `whitelist` | آرایه string | تنظیم نشده | IPها یا محدوده‌های CIDR مجاز برای client. |
| `blacklist` | آرایه string | تنظیم نشده | IPها یا محدوده‌های CIDR مسدود برای client. |

### گزینه‌های socket buffer

`large-send-buffer` و `large-recv-buffer` مقادیر زیر را می‌پذیرند:

| مقدار | معنا |
| --- | --- |
| `true` | استفاده از buffer socket بزرگ پیش‌فرض WaterWall که فعلاً `4194304` بایت است. |
| `false` | عدم تنظیم صریح این socket buffer؛ استفاده از پیش‌فرض kernel. |
| عدد مثبت | درخواست مستقیم آن تعداد بایت. |

اگر این گزینه حذف شود و chain نهایی شامل `MuxClient` یا `MuxServer` باشد، `TcpListener` به‌طور خودکار از buffer socket بزرگ پیش‌فرض برای گزینه حذف‌شده استفاده می‌کند.

### Interface و `fwmark`

`interface` listener را به یک network device محلی محدود می‌کند.

در Linux، WaterWall از `SO_BINDTODEVICE` استفاده می‌کند. روی platformهایی که device binding ندارند، WaterWall در صورت امکان از bind کردن به آدرس IPv4 interface استفاده می‌کند.

`fwmark` از `SO_MARK` روی platformهایی که آن را ارائه می‌دهند استفاده می‌کند. به platform وابسته است و روی Windows در دسترس نیست.

## نمونه‌های رایج

### listener آزمایشی محلی

```json
{
  "name": "local-entry",
  "type": "TcpListener",
  "settings": {
    "address": "127.0.0.1",
    "port": 8080
  },
  "next": "outbound"
}
```

این فقط clientهایی را که روی همان دستگاه هستند می‌پذیرد.

### listener عمومی VPS

```json
{
  "name": "public-entry",
  "type": "TcpListener",
  "settings": {
    "address": "0.0.0.0",
    "port": 443,
    "nodelay": true,
    "initial-idle-timeout-ms": 5000,
    "active-idle-timeout-ms": 300000
  },
  "next": "tls-server"
}
```

این clientهای IPv4 را روی تمام interfaceهای محلی می‌پذیرد. فایروال VPS و provider باید پورت انتخاب‌شده را هم مجاز کنند.

### listener چندپورتی

```json
{
  "name": "multiport-entry",
  "type": "TcpListener",
  "settings": {
    "address": "0.0.0.0",
    "port": [
      443,
      8443,
      2083
    ],
    "nodelay": true
  },
  "next": "router"
}
```

آرایه‌های `port` مشخص از socket-per-port برای گوش دادن استفاده می‌کنند.

### listener بازه پورت

```json
{
  "name": "range-entry",
  "type": "TcpListener",
  "settings": {
    "address": "0.0.0.0",
    "port-range": [
      40000,
      40100
    ],
    "multiport-backend": "socket"
  },
  "next": "router"
}
```

برای `port-range`، runtime می‌تواند با backend `socket` یک socket گوش‌دهنده به ازای هر پورت بسازد، یا با backend `iptables` از یک socket اصلی به همراه قوانین redirect استفاده کند. وقتی به یک backend مشخص نیاز دارید، `multiport-backend` را صریحاً تنظیم کنید.

## مسیر accept

وقتی یک TCP client وصل می‌شود، `TcpListener`:

1. socket پذیرفته‌شده را به یک worker loop متصل می‌کند
2. یک line جدید در WaterWall می‌سازد
3. وضعیت line listener را برای آن اتصال ذخیره می‌کند
4. اطلاعات routing را از اتصال پذیرفته‌شده پر می‌کند
5. upstream `init` را به نود بعدی می‌فرستد
6. خواندن از socket client را شروع می‌کند

routing context سورس از اتصال پذیرفته‌شده پر می‌شود. IP peer داخل `src_ctx` ثبت می‌شود، پورت محلی که اتصال را پذیرفته داخل `src_ctx.port` و `local_listener_port` ذخیره می‌شود، و source port واقعی TCP client جداگانه داخل `peer_source_port` نگه داشته می‌شود.

## جریان داده

```text
socket client -> TcpListener -> نود بعدی
socket client <- TcpListener <- نود بعدی
```

جهت‌ها:

| جهت | رفتار |
| --- | --- |
| از client به chain | خواندن socket به payload upstream برای `next` تبدیل می‌شود. |
| از chain به client | payload downstream روی socket پذیرفته‌شده نوشته می‌شود. |

نود بعدی باید انتظار ترافیک از clientهای پذیرفته‌شده را داشته باشد و پاسخ‌ها را به صورت downstream برگرداند.

## backpressure و صف نوشتن

`TcpListener` از فرآیند در برابر socketهای client که کند هستند یا موقتاً قابل نوشتن نیستند محافظت می‌کند.

رفتار:

- اگر write نتواند فوری تکمیل شود، bufferهای خروجی در صف قرار می‌گیرند.
- وقتی داده در صف از `1 KB` بیشتر شود، نود بعدی pause می‌شود.
- وقتی socket دوباره قابل نوشتن شود، bufferهای صف فلاش می‌شوند و نود بعدی resume می‌شود.
- اگر داده در صف از `16 MB` بیشتر شود، اتصال بسته می‌شود.

این از رشد بی‌محدود حافظه به‌خاطر یک client کند جلوگیری می‌کند.

## رفتار idle timeout

هر اتصال پذیرفته‌شده در یک جدول idle مخصوص worker ردیابی می‌شود.

| فاز | timeout پیش‌فرض |
| --- | --- |
| اتصال تازه پذیرفته‌شده قبل از فعالیت payload سمت listener | `5000 ms` |
| اتصال فعال بعد از مشاهده فعالیت سمت listener | `300000 ms` |

اگر اتصالی منقضی شود، socket و line بسته می‌شوند.

مقادیر اولیه و فعال با این تنظیمات پیکربندی می‌شوند:

```json
{
  "settings": {
    "initial-idle-timeout-ms": 5000,
    "active-idle-timeout-ms": 300000
  }
}
```

برای chain‌هایی مثل `TcpListener -> TlsServer`، فعالیت سمت listener با تکمیل TLS handshake یکی نیست. یک client که یک TLS record ناقص ارسال می‌کند می‌تواند وارد active timeout شود در حالی که `TlsServer` هنوز منتظر بایت‌های بیشتر handshake است. هنگام تنظیم رفتار TLS probe-resistant، این timeoutها را با زمان‌بندی سرویس عمومی که می‌خواهید شبیه‌سازی کنید هماهنگ نگه دارید.

## balance group

`balance-group` این listener را در یک گروه با listenerهای سازگار دیگر روی همان پورت قرار می‌دهد.

وقتی چند listener یک `balance-group` و پورت مشترک دارند، socket manager با استفاده از hash آدرس IP client یک listener برای client جدید انتخاب می‌کند و آن انتخاب را به خاطر می‌سپارد. در طول `balance-interval`، اتصال‌های بعدی از همان IP client به همان listener sticky می‌مانند.

نمونه:

```json
{
  "settings": {
    "address": "0.0.0.0",
    "port": 443,
    "balance-group": "public-443",
    "balance-interval": 30000
  }
}
```

## whitelist و blacklist

`whitelist` و `blacklist` آرایه‌هایی از string IP یا CIDR می‌پذیرند. هر دو IPv4 و IPv6 پشتیبانی می‌شوند.

نمونه:

```json
{
  "settings": {
    "whitelist": [
      "10.0.0.0/8",
      "192.168.1.20/32",
      "2001:db8::/64"
    ],
    "blacklist": [
      "10.0.0.13/32"
    ]
  }
}
```

رفتار:

| تنظیم | نتیجه |
| --- | --- |
| بدون لیست | بدون فیلتر IP client توسط این listener. |
| `whitelist` تنظیم شده | فقط IPهای client که match می‌شوند توسط این listener پذیرفته می‌شوند. |
| `blacklist` تنظیم شده | IPهای client که match می‌شوند توسط این listener رد می‌شوند. |
| هر دو تنظیم شده | client باید با whitelist مطابقت داشته باشد و با blacklist مطابقت نداشته باشد. |

اگر چند listener روی یک پورت ثبت شده باشند، ممکن است listener دیگری همان اتصال را دریافت کند اگر فیلترش match شود و فیلتر این listener match نشود.

## نکات multiport backend

برای آرایه‌های `port` مشخص، WaterWall هر عضو آرایه را به عنوان یک پورت مشخص می‌شناسد و از socket-per-port استفاده می‌کند.

برای `port-range`، WaterWall می‌تواند از این backendها استفاده کند:

| backend | توضیح |
| --- | --- |
| `"socket"` | برای هر پورت یک socket گوش‌دهنده می‌سازد. ساده و قابل فهم. |
| `"iptables"` | از قوانین redirect استفاده می‌کند. برای بازه‌های بزرگ مفید است، اما به محیط و قوانین فایروال سیستم وابسته است. |

برای بازه‌های کوچک، `socket` معمولاً راحت‌تر برای debug است. برای بازه‌های بزرگ، اگر deploy شما قوانین سیستم را کنترل می‌کند، `iptables` می‌تواند تعداد socketها را کاهش دهد.

## اولویت فیلترها و مسیر پیش‌فرض

وقتی چند `TcpListener` روی یک پورت مشترک دارند، socket manager همه را با اولویت برابر ارزیابی نمی‌کند. فیلترهای مشخص‌تر اول ارزیابی می‌شوند. یک listener با `whitelist` یا `blacklist` نسبت به یک listener معادل بدون فیلتر IP اولویت بالاتری دارد.

این به شما اجازه می‌دهد یک الگوی مسیر پیش‌فرض بسازید:

```text
پورت عمومی مشترک
  ├─ listener فیلتردار مطابقت‌یافته   -> مسیر ویژه
  └─ listener بدون فیلتر              -> مسیر پیش‌فرض
```

نمونه:

```json
{
  "nodes": [
    {
      "name": "trusted-entry",
      "type": "TcpListener",
      "settings": {
        "address": "0.0.0.0",
        "port": 443,
        "whitelist": [
          "203.0.113.10/32",
          "2001:db8:100::/48"
        ]
      },
      "next": "trusted-path"
    },
    {
      "name": "default-entry",
      "type": "TcpListener",
      "settings": {
        "address": "0.0.0.0",
        "port": 443
      },
      "next": "default-path"
    }
  ]
}
```

در این ساختار، clientهایی که با `trusted-entry.whitelist` مطابقت دارند توسط `trusted-entry` مدیریت می‌شوند. بقیه clientها به `default-entry` می‌رسند، چون listener بدون فیلتر مثل مسیر پیش‌فرض آن پورت رفتار می‌کند.

از همین ایده می‌توانید با `blacklist` استفاده کنید تا یک بازه از یک مسیر حذف شود و listener دیگری اتصال را دریافت کند.

فیلترهای `TcpListener` فقط IP/CIDR هستند. GeoIP، دسته‌بندی دامنه، SNI، HTTP Host یا protocol sniffing را پشتیبانی نمی‌کنند. برای routing مبتنی بر کشور مثل `geoip:ir`، بعد از پذیرش اتصال از نود `Router` استفاده کنید.

اگر از `balance-group` استفاده می‌شود، listenerهای متعادل از طریق منطق balance-group انتخاب می‌شوند نه به عنوان یک branch ساده first-match. وقتی می‌خواهید routing IP-specific قطعی داشته باشید از الگوی اولویت/مسیر-پیش‌فرض با listenerهای معمولی فیلتردار استفاده کنید.

## نکات و هشدارها

- `TcpListener` به عنوان یک نقطه ورودی ورودی طراحی شده است.
- parser انتظار دارد `port` یک عدد یا آرایه‌ای از پورت‌های مشخص باشد.
- parser انتظار دارد `port-range` یک آرایه بازه دو عضوی باشد.
- `multiport-backend` فقط برای listenerهای `port-range` پیوسته اهمیت دارد.
- `fwmark` و device binding به platform وابسته هستند.
- listener بسته شده به `127.0.0.1` فقط clientهای محلی را می‌پذیرد.
- listener بسته شده به `0.0.0.0` روی تمام interfaceهای IPv4 می‌پذیرد، با توجه به فایروال سیستم‌عامل و provider.
