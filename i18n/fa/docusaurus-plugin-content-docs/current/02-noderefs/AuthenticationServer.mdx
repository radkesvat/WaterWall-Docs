# AuthenticationServer

`AuthenticationServer` node‌ای منطقی در انتهای chain برای مدیریت دیتابیس کاربران WaterWall است. این node socket باز نمی‌کند و مستقیماً I/O شبکه انجام نمی‌دهد؛ در عوض، یک دیتابیس در حافظه از نوع `users_t` نگه می‌دارد، آن را در قالب JSON بارگذاری و ذخیره می‌کند و به درخواست‌های فریم‌بندی‌شده `AuthenticationClient` پاسخ می‌دهد.

## ساعت و اولین استفاده محلی

پاسخ GetAllUsers باید هر دو فیلد canonical و دقیق `server-time-ms` و `accounting-time-ms` مثبت را داشته باشد؛
metadata نامعتبر refresh را بدون جایگزینی cache معتبر رد می‌کند و fallback به ساعت دیواری کلاینت وجود ندارد.
سرور یک بار `C0 = max(wall-ms, 1)` و monotonic `M0` را ثبت می‌کند و با جمع saturating زمان سپری‌شده monotonic
ساعت حسابداری را پیش می‌برد. اصلاح بعدی ساعت دیواری آن را reset نمی‌کند و anchor در فایل ذخیره نمی‌شود.

اولین upload یا download غیرصفر درون قفل write کاربر، نمونه تازه monotonic، origin محلی معتبر حتی در صفر و
برآورد مثبت و تغییرناپذیر اولین استفاده برای گزارش را ثبت می‌کند. login، reservation، فراخوانی صفر بایت و rebase
شروع مصرف نیستند. ثبت مشاهده، شمارنده و تصمیم انقضا در transaction با ترتیب user سپس stats انجام می‌شود؛ نبود
خروجی notification مانع مشاهده نیست. سن سپری‌شده حتی با مدت صفر حفظ می‌شود؛ ACK، reconnect، pull تکراری یا نبود
فیلد canonical آن را پاک یا جوان نمی‌کنند. مشاهده زودتر کلاینت دیگر می‌تواند سن را بیشتر کند. origin واردشده
در آینده تا رسیدن زمانش آینده می‌ماند؛ مصرف محلی واقعی می‌تواند origin زودتری بسازد.

انقضای تاریخ مطلق با ساعت دیواری سرور و مدت پس از اولین استفاده با سن monotonic جدا محاسبه می‌شوند. تاریخ
بدون تغییر deadline زودتر را حفظ می‌کند؛ ویرایش/پاک‌کردن هر سیاست فقط جزء خودش را دوباره محاسبه می‌کند. deadline
زودتر حاکم است؛ انقضای گذشته در monotonic صفر هرگز به unlimited تبدیل نمی‌شود. state زمان/مشاهده/ACK و reservation
با ID پایدار، حتی هنگام تغییر credential همان ID، منتقل می‌شوند؛ policy و timestamp مرجع جدید حفظ می‌شوند.
کپی عمومی و JSON این state محلی را ندارند. تبدیل بین ماشین‌ها برآوردی با خطای تأخیر شبکه/serialization و drift
است. رفتار suspend ساعت runtime عوض نمی‌شود؛ CLOCK_MONOTONIC لینوکس زمان تعلیق میزبان را حساب نمی‌کند.

## جایگاه رایج

```text
AuthenticationClient -> AuthenticationServer
```

این node در انتهای chain قرار می‌گیرد و نباید `next` داشته باشد.

## این نود چه می‌کند؟

- کاربران را از `db-path` در یک جدول در حافظه `users_t` بارگذاری می‌کند.
- اگر فایل اصلی دیتابیس JSON بارگذاری نشود، سراغ `db-path.backup` می‌رود.
- پس از بازیابی موفق از backup، فایل اصلی دیتابیس را دوباره می‌نویسد.
- دیتابیس فعلی در حافظه را به‌صورت دوره‌ای ذخیره می‌کند.
- `db-path.backup` را قبل از نوشتن `db-path` در ذخیره‌سازی‌های عادی می‌نویسد.
- می‌تواند snapshot‌های تاریخی backup را به‌صورت ساعتی، روزانه یا هفتگی بنویسد.
- پیام‌های درخواست فریم‌بندی‌شده را از `AuthenticationClient` می‌پذیرد.
- از چند فریم درخواست در یک پیام بیرونی پشتیبانی می‌کند.
- هر فریم درخواست را به ماژول داخلی مناسب برای احراز هویت یا مدیریت کاربر می‌فرستد.
- برای هر پیام پردازش‌شده، یک پیام پاسخ ترکیبی شامل همه فریم‌های پاسخ را در جهت downstream می‌فرستد.

`AuthenticationServer` مرجع اصلی اطلاعات کاربران است. node‌هایی که ترافیک کاربران را سرویس می‌دهند باید از طریق `AuthenticationClient` با آن ارتباط بگیرند و نباید فریم‌های پروتکل سرور را مستقیم بفرستند.

## نمونه تنظیم

```json
{
  "name": "auth-db",
  "type": "AuthenticationServer",
  "settings": {
    "db-path": "users.json",
    "file-save-rate-ms": 10000,
    "normal-backups": "daily",
    "normal-backups-path": "backups/",
    "normal-backups-count-limit": 10,
    "session-idle-timeout-ms": 600000,
    "verbose": false,
    "auth-clients": [
      {
        "name": "edge-1",
        "secret": "long-random-secret",
        "allow-stats-push": true,
        "allow-user-pull": true,
        "allow-user-write": false,
        "session-idle-timeout-ms": 600000
      }
    ]
  }
}
```

## فیلدهای اجباری

فیلدهای سطح اصلی:

| فیلد | نوع | توضیح |
| --- | --- | --- |
| `name` | string | نام انتخابی node که باید در config یکتا باشد. |
| `type` | string | باید دقیقاً `"AuthenticationServer"` باشد. |
| `settings` | object | تنظیمات دیتابیس، ذخیره‌سازی، backup، session و auth client. |

فیلدهای اجباری داخل `settings`:

| فیلد | نوع | توضیح |
| --- | --- | --- |
| `db-path` | string | مسیر فایل دیتابیس JSON کاربران. |
| `file-save-rate-ms` | عدد مثبت | بازه ذخیره دوره‌ای به میلی‌ثانیه. |
| `auth-clients` | آرایه غیرخالی | کلاینت‌های control-plane که اجازه دارند در این سرور احراز هویت شوند. |

`AuthenticationServer` config‌هایی را که در آن‌ها `next` تعریف شده باشد نمی‌پذیرد.

## تنظیمات اختیاری

| گزینه | نوع | پیش‌فرض | توضیح |
| --- | --- | --- | --- |
| `session-idle-timeout-ms` | عدد مثبت | `600000` | timeout پیش‌فرض بی‌کار ماندن session، بر حسب میلی‌ثانیه. |
| `verbose` | boolean | `false` | لاگ‌های debug مربوط به روند احراز هویت، parse درخواست‌ها، دسترسی‌ها و روند پاسخ را فعال می‌کند. |
| `normal-backups` | string | غیرفعال | حالت backup تاریخی: `"hourly"`، `"daily"` یا `"weekly"`. |
| `normal-backups-path` | string | تنظیم نشده | دایرکتوری snapshot‌های تاریخی backup. اگر `normal-backups` تنظیم شود، این گزینه اجباری است. |
| `normal-backups-count-limit` | عدد مثبت | `10` | حداکثر فایل‌های backup تاریخی که برای این دیتابیس و حالت backup نگه داشته می‌شوند. |

`normal-backups` و `normal-backups-path` باید با هم تنظیم شوند. اگر بدون فعال کردن backupهای عادی، `normal-backups-count-limit` را تنظیم کنید، راه‌اندازی با خطا متوقف می‌شود.

`normal-backups-path` می‌تواند مسیر نسبی یا مطلق باشد. اگر دایرکتوری وجود نداشته باشد سرور آن را می‌سازد؛ اما اگر مسیر وجود داشته باشد و دایرکتوری نباشد، راه‌اندازی شکست می‌خورد.

## Auth Clients

`auth-clients` مشخصات ورود control-plane را برای instance‌های `AuthenticationClient` تعریف می‌کند. این موارد با کاربران عادی ترافیک در دیتابیس کاربران فرق دارند.

هر ورودی باید این فیلدها را داشته باشد:

| فیلد | نوع | توضیح |
| --- | --- | --- |
| `name` | non-empty string | نام کلاینت احراز هویت. |
| `secret` | non-empty string | secret مشترک با همان کلاینت احراز هویت. |

فیلدهای اختیاری هر کلاینت:

| فیلد | نوع | پیش‌فرض | توضیح |
| --- | --- | --- | --- |
| `allow-stats-push` | boolean | `false` | به ماژول‌های همگام‌سازی مصرف ترافیک اجازه اجرا می‌دهد. |
| `allow-user-pull` | boolean | `false` | به ماژول‌های جست‌وجوی کاربر و دریافت کامل جدول اجازه اجرا می‌دهد. |
| `allow-user-write` | boolean | `false` | ماژول‌های ایجاد/به‌روزرسانی کاربر را مجاز می‌کند. |
| `session-idle-timeout-ms` | عدد مثبت | timeout سطح اصلی | timeout پیش‌فرض session‌های ساخته‌شده برای این کلاینت را جایگزین می‌کند. |

این دسترسی‌ها به session مربوط‌اند، نه به کاربران:

| Permission | مجاز می‌کند |
| --- | --- |
| `allow-user-pull` | `GetAllUsers`، user lookup با password، SHA-224 یا SHA-256. |
| `allow-stats-push` | `PushUserStats`. |
| `allow-user-write` | `AddNewUser` و `UpdateUser`. |

`Authenticate` برای همه قابل استفاده است. تمام ماژول‌های دیگر به یک session token معتبر نیاز دارند.

## فرمت دیتابیس

فرمت پیشنهادی روی دیسک، یک object دارای آرایه `users` است:

```json
{
  "users": [
    {
      "id": 1001,
      "name": "alice",
      "password": "alice:alice-secret",
      "email": "alice@example.com",
      "wireguard-allowed-ips": "10.44.0.23/32",
      "enabled": true,
      "limit": {
        "traffic": {
          "up": 1073741824,
          "down": 1073741824,
          "total": 2147483648
        },
        "bandwidth": {
          "up": 1048576,
          "down": 1048576
        },
        "ips": 4,
        "devices": 2,
        "connections-in": 16,
        "connections-out": 16
      },
      "time": {
        "created-at-ms": 1735689600000,
        "expire-at-ms": 1767225600000
      },
      "stats": {
        "traffic": {
          "up": 0,
          "down": 0
        },
        "connections-in": 0,
        "connections-out": 0
      }
    }
  ]
}
```

Loader چند شکل مختلف از ورودی را می‌پذیرد:

| Layout | توضیح |
| --- | --- |
| `null`، آرایه خالی، یا object خالی | به‌عنوان جدول کاربران خالی پذیرفته می‌شود. |
| `[user, ...]` | آرایه‌ای از object‌های کاربر. |
| `{"users": [user, ...]}` | ساختار پیشنهادی. |
| `{"alice": user, "bob": user}` | یک object map. اگر کاربر `name` غیرخالی نداشته باشد، کلید فقط به‌عنوان راهنمای نام کاربری استفاده می‌شود. |
| یک object مستقل کاربر | در صورتی پذیرفته می‌شود که `id` یا `user-id` و همچنین `password` یا `pass` داشته باشد. |

Saver همیشه دیتابیس را با ساختار `{"users": [...]}` بازنویسی می‌کند.

## Object کاربر

هر object کاربر باید این فیلدها را داشته باشد:

| فیلد | نوع | توضیح |
| --- | --- | --- |
| `id` یا `user-id` | unsigned integer غیرصفر | شناسه منطقی و ماندگار کاربر که باید یکتا و ثابت باشد. |
| `password` یا `pass` | string | کلید جست‌وجوی password که index‌های مشتق‌شده بر اساس آن ساخته می‌شوند. |

فیلدهای اختیاری:

| فیلد | توضیح |
| --- | --- |
| `name` | نام خوانای کاربر. نام‌های غیرخالی باید یکتا باشند. |
| `email` | اطلاعات ایمیل کاربر. |
| `notes` | یادداشت آزاد مدیر سیستم. |
| `gid` یا `group-id` | شناسه گروه. |
| `enabled` یا `enable` | پیش‌فرض `true`؛ برای غیرفعال کردن کاربر `false` بگذارید. |
| `record-stat-interval-ms` | فاصله ثبت آمار. |
| `wireguard-allowed-ips` | یک CIDR داخلی و اختیاری WireGuard برای این کاربر، مانند `10.44.0.23/32` یا `fd00::23/128`. مقدار خالی، `null` یا نبودن این فیلد یعنی تنظیم نشده است. IPv4 و IPv6 پذیرفته می‌شوند؛ مقدار به شکل استاندارد network ذخیره می‌شود و محدوده آن نباید با کاربر دیگری هم‌پوشانی داشته باشد. |
| `limit` | محدودیت‌های کاربر. مقادیر مفقود یا صفر به معنی نامحدود است. |
| `time` | اطلاعات زمانی کاربر. |
| `stats` | آمار runtime که معمولاً WaterWall آن را نگه می‌دارد. |

برای `Socks5Server`، کلید نهایی جست‌وجو را در `password` و با قالب `username:password` ذخیره کنید؛ برای مثال `"alice:alice-secret"`.

Passwordها به‌صورت plaintext در دیتابیس JSON ذخیره می‌شوند، زیرا اطلاعات exportشده کاربران فیلد `password` را هم در بر دارد. با permissionهای مناسب فایل‌سیستم از `db-path`، فایل `db-path.backup` و دایرکتوری backupهای عادی که حاوی اطلاعات محرمانه‌اند محافظت کنید.

کلیدهای جست‌وجوی مشتق‌شده از password مستقیماً در JSON ذخیره نمی‌شوند. هنگام بارگذاری کاربران، SHA-224، SHA-256، مشخصات UUID و public keyهای سازگار با WireGuard دوباره از `password` ساخته می‌شوند. هیچ دو کاربری نباید password/SHA-224، SHA-256، UUID یا public key مشتق‌شده WireGuard یکسان داشته باشند.

`wireguard-allowed-ips` بخشی ماندگار از config کاربر است و از password مشتق نمی‌شود. این فیلد در JSON ذخیره و با `GetAllUsers` همگام می‌شود؛ همچنین اعتبارسنجی می‌شود تا محدوده‌های کاربران با یکدیگر هم‌پوشانی نداشته باشند.

## محدودیت‌ها، زمان و آمار

`limit` می‌تواند داشته باشد:

| فیلد | توضیح |
| --- | --- |
| `traffic` | محدودیت تعداد بایت برای `up`، `down` و `total`. نام‌های مستعار `u` و `d` نیز پذیرفته می‌شوند. |
| `bandwidth` | محدودیت بایت بر ثانیه برای `up` و `down`. نام‌های مستعار `u` و `d` نیز پذیرفته می‌شوند. |
| `ips` یا `ip` | حداکثر تعداد IP. |
| `devices` | حداکثر تعداد دستگاه. |
| `connections-in` یا `cons-in` | حداکثر تعداد اتصال ورودی. |
| `connections-out` یا `cons-out` | حداکثر تعداد اتصال خروجی. |

`time` می‌تواند داشته باشد:

| فیلد |
| --- |
| `created-at-ms` یا `created_at_ms` |
| `first-usage-at-ms` یا `first_usage_at_ms` |
| `expire-at-ms` یا `expires-at-ms` |
| `expire-after-first-usage-ms` یا `expire-after-first-use-ms` |

همین فیلدهای زمانی در سطح اصلی object کاربر نیز پذیرفته می‌شوند. همه زمان‌ها تعداد میلی‌ثانیه از Unix epoch هستند؛ به‌جز `expire-after-first-usage-ms` که یک مدت‌زمان است.

`stats` می‌تواند داشته باشد:

| فیلد | توضیح |
| --- | --- |
| `traffic` | شمارنده‌های بایت برای `up` و `down`. نام‌های مستعار `u` و `d` نیز پذیرفته می‌شوند. |
| `speed` | شمارنده‌های سرعت برای `up` و `down`. نام‌های مستعار `u` و `d` نیز پذیرفته می‌شوند. |
| `ips` یا `ip` | تعداد IP runtime. |
| `devices` | تعداد دستگاه‌ها در runtime. |
| `connections-in` یا `cons-in` | تعداد اتصال‌های ورودی در runtime. |
| `connections-out` یا `cons-out` | تعداد اتصال‌های خروجی در runtime. |

مقادیر عددی بزرگ را می‌توان به‌صورت رشته ده‌دهی خواند و نوشت.

## ذخیره‌سازی و بازیابی

ذخیره زیر write lock سرور انجام می‌شود: ابتدا دیتابیس پیشنهادی در فایل موقت خصوصی کنار primary نوشته و sync
می‌شود؛ سپس **primary قبلاً commit‌شده** به‌عنوان `db-path.backup` آماده و اتمی منتشر می‌شود؛ در پایان primary
با فایل پیشنهادی اتمی جایگزین می‌شود. این جایگزینی نقطه commit است. شکست پیش از آن، افزودن کاربر را رد می‌کند
و حافظه rollback می‌شود؛ backup شامل افزودن ردشده نخواهد بود. شکست نگهداری تاریخچه، pruning یا directory sync
پس از جایگزینی، commit را به شکست API تبدیل نمی‌کند و فقط گزارش می‌شود.

تمام فایل‌های primary، recovery، تاریخچه و موقت پیش از نخستین بایت محرمانه خصوصی هستند: روی POSIX با ایجاد
انحصاری `0600` و روی Windows با DACL محافظت‌شده برای کاربر process و SYSTEM. مجوز primary و recovery موجود
هنگام بارگذاری محدود می‌شود؛ شکست محدودسازی باعث رد startup می‌شود. write، flush، file sync و close بررسی
می‌شوند. فایل موقت نام یکتا دارد، نامزد recovery نیست و cleanup فقط فایل موقت همان عملیات را پاک می‌کند.

primary معتبر اولویت دارد. اگر بارگذاری آن شکست بخورد، backup معتبر با همین writer خصوصی و اتمی بازیابی
می‌شود و تا پایان و پس از بازیابی باقی می‌ماند. تاریخچه برای بازیابی خودکار استفاده نمی‌شود. backup از پیش موجود
اطلاعاتی برای اثبات زمان commit محتوایش ندارد. تضمین کلی در برابر خرابی filesystem یا قطع برق داده نمی‌شود.

## Sessions و Revisionها

نام‌های `auth-clients` باید یکتا باشند و processهای مستقل نام‌های مستقل داشته باشند. session شامل token، مجوزها،
زمان بی‌کاری و اشاره به هویت تنظیم‌شده است. هر هویت یک checkpoint با epoch، آخرین sequence و SHA-256 آخرین
payload دارد؛ expiry یا جایگزینی session این checkpoint را پاک نمی‌کند. session و checkpoint روی دیسک ذخیره
نمی‌شوند. timeout پیش‌فرض `600000 ms` است و worker صفر هر `60000 ms` sessionهای بی‌کار را پاک می‌کند.
درخواست با token معتبر زمان فعالیت را تازه می‌کند؛ قفل state مانع حذف session در حین dispatch می‌شود.

`config_revision` و `stats_revision` از ۱ شروع می‌شوند و به‌ترتیب با تغییر تنظیمات و مصرف جدید افزایش می‌یابند.
point readها read lock مشترک می‌گیرند؛ احراز هویت، pull، ذخیره و mutation زیر write lock اجرا می‌شوند.

## مدل همگام‌سازی

Authenticate اولیه `name` و `secret` می‌گیرد. پاسخ Session شامل ۱۲۸ بایت است: token شصت‌وچهاربایتی و سپس epoch
شصت‌وچهاربایتی؛ هر کدام نمایش hexadecimal سی‌ودو بایت random امن سیستم‌عامل هستند. اتصال مجدد همان process،
`epoch` را نیز در Authenticate می‌فرستد. epoch گم‌شده یا جایگزین‌شده خطای `accounting-continuity-lost` می‌دهد.
ثبت تازه بدون epoch، checkpoint جدید ایجاد می‌کند و session قبلی آن هویت را نامعتبر می‌کند.

کلاینت یک batch دلتا را با بایت‌های ثابت نگه می‌دارد. ترتیب reconnect عبارت است از authenticate/resume، تکرار
batch حل‌نشده، اعتبارسنجی ACK و سپس pull کامل. ID پایدار کاربر کلید مصرف است و تغییر password آن را عوض نمی‌کند.
با ACK معتبر، baseline فقط برای کاربران همان subset تا snapshot جلو می‌رود. pull شمارنده‌های محلی را با
فرمول `G + (A - B)` نصب می‌کند؛ ترافیک پس از snapshot از بین نمی‌رود. هنگام batch حل‌نشده، جایگزینی جدول ممنوع
است و درخواست‌های pull/push مسدودشده برای اجرای بعدی ادغام می‌شوند.

تضمین حسابداری فقط قطع اتصال در زمان زنده‌بودن دو process را پوشش می‌دهد. اگر نتیجه batch نامطمئن باشد و epoch
از دست برود، کلاینت batch را حفظ می‌کند، وارد `kAuthenticationClientStateContinuityError` می‌شود و همگام‌سازی
خودکار را برای رسیدگی اپراتور متوقف می‌کند. اگر batch نامطمئن ندارد، ثبت تازه و pull مجاز است. بازیابی مصرف پس از
crash/restart ارائه نمی‌شود.

ACK فقط پذیرش در حافظه سرور است، نه تأیید ذخیره روی دیسک. ذخیره دوره‌ای/نهایی دیتابیس checkpoint را ذخیره نمی‌کند.
راه‌اندازی دوباره کلاینت ممکن است مصرف گزارش‌نشده را از بین ببرد؛ راه‌اندازی دوباره سرور ممکن است مصرف ACKشده
پس از آخرین ذخیره موفق را از دست بدهد و checkpointها را پاک می‌کند. shutdown تضمین تحویل نهایی مصرف نیست.
بازیابی مصرف پس از crash و عملیات remote reset وجود ندارد.

## فریم‌بندی درخواست و پاسخ

بایت‌های upstream به شکل stream buffer می‌شوند. envelope بیرونی درخواست چنین ساختاری دارد:

| Bytes | فیلد |
| --- | --- |
| `4` | Unsigned big-endian body size. |
| `64` | session token. |
| بقیه body | یک یا چند request frame. |

اندازه body شامل token شصت‌وچهاربایتی به‌علاوه payload فریم درخواست است. در درخواست احرازنشده `Authenticate`، همه بایت‌های token می‌توانند صفر باشند. درخواست‌های دیگر به token معتبر نیاز دارند.

هر request frame:

| Bytes | فیلد |
| --- | --- |
| `1` | Request type. |
| `4` | Correlation ID. |
| `4` | Unsigned big-endian request data length. |
| variable | Request data bytes. |

ساختار envelope پاسخ:

| Bytes | فیلد |
| --- | --- |
| `4` | Unsigned big-endian body size. |
| `8` | Unsigned big-endian `config_revision`. |
| `8` | Unsigned big-endian `stats_revision`. |
| بقیه body | یک یا چند response frame. |

هر response frame:

| Bytes | فیلد |
| --- | --- |
| `1` | Response type. |
| `4` | Correlation ID کپی‌شده از request. |
| `4` | Unsigned big-endian response data length. |
| variable | Response data bytes. |

پیامی که session token معتبر دارد نباید شامل `Authenticate` باشد. envelope خراب، فریم ناقص، payload بزرگ‌تر از حد مجاز یا بایت‌های اضافه‌ای که حتی یک header کامل درخواست را تشکیل نمی‌دهند، باعث بسته شدن امن اتصال منطقی می‌شوند.

## یادداشت‌های ماژول

### Authenticate

داده درخواست `{"name":"edge-1","secret":"long-random-secret"}` است؛ برای resume فیلد `epoch` نیز ارسال
می‌شود. envelope باید token صفر داشته باشد. پاسخ موفق نوع `4` و شامل token و epoch با طول مجموع ۱۲۸ بایت است.
احراز هویت در envelope دارای token معتبر با `already-authenticated` رد می‌شود. شکست resume خطای
`accounting-continuity-lost` می‌دهد.

### GetAllUsers

`GetAllUsers` به payload خالی نیاز دارد. در صورت موفقیت، JSON استانداردشده کاربران را همراه با دو فیلد پاسخ `server-time-ms` و `accounting-time-ms` برمی‌گرداند:

```json
{"users":[],"server-time-ms":1767225600000,"accounting-time-ms":1767225600000}
```

`server-time-ms` در دیتابیس نوشته نمی‌شود. این مقدار به `AuthenticationClient` کمک می‌کند زمان‌های انقضای متعلق به سرور را به ساعت محلی کلاینت تبدیل کند.

این pull شمارنده‌های مرجع و revision فعلی را برمی‌گرداند و checkpoint حسابداری را تغییر نمی‌دهد.

### AddNewUser

`AddNewUser` یک object کاربر در قالب JSON می‌خواهد. کاربر فرستاده‌شده باید `id` یا `user-id` یکتا و غیرصفر داشته باشد.

ماژول نام یا id تکراری و نیز کلید جست‌وجوی تکراری مشتق‌شده از password را نمی‌پذیرد. پس از موفقیت، دیتابیس را بی‌درنگ ذخیره می‌کند. اگر ذخیره شکست بخورد، تلاش می‌کند افزودن در حافظه را rollback کند و `database-save-failed` برمی‌گرداند.

پاسخ `storage-unavailable` یعنی ظرفیت درخواستی برای ذخیره‌سازی یا ایندکس کاربر پذیرفته نشده یا مقداردهی اولیه قفل‌های بومی برای نسخه کپی‌شده کاربر شکست خورده است. تمام شدن حافظه heap به خاتمه فرایند منجر می‌شود و پاسخ خطا تولید نمی‌کند.

### UpdateUser

درخواست فقط patch تنظیمات است و `id` دقیق، غیرصفر و unsigned 64-bit برای انتخاب حساب لازم دارد:

```json
{"id":42,"name":"Alice"}
```

اگر مدیر در ۱۰۰ بایت حساب را خوانده و سپس ۱۰ بایت مصرف ثبت شده باشد، این تغییر نام، مجموع ۱۱۰ بایت را حفظ
می‌کند. password یا object کامل صادرشده کاربر ارسال نمی‌شود. حذف هر فیلد از درخواست یعنی حفظ مقدار فعلی آن،
حتی برای siblingهای object تو در تو:

```json
{"id":42,"limit":{"traffic":{"total":1073741824}},"time":{"expire-after-first-usage-ms":86400000}}
```

در این مثال فقط quota کل و مدت انقضا پس از اولین استفاده تغییر می‌کنند؛ limitهای دیگر، انقضای مطلق، زمان ایجاد،
اولین استفاده و تمام شمارنده‌ها حفظ می‌شوند.

| leaf مجاز | نوع |
| --- | --- |
| `name`، `email`، `notes`، `wireguard-allowed-ips` | string؛ رشته خالی برای پاک‌کردن طبق قواعد index/CIDR |
| `gid` | unsigned 64-bit دقیق |
| `enabled` | boolean واقعی JSON |
| `record-stat-interval-ms` | عدد صحیح نامنفی تا INT_MAX؛ scheduler تازه‌ای اضافه نمی‌کند |
| `limit.traffic.up`، `.down`، `.total` | unsigned 64-bit دقیق |
| `limit.bandwidth.up`، `.down` | unsigned 64-bit دقیق |
| `limit.ips`، `.devices`، `.connections-in`، `.connections-out` | unsigned 64-bit دقیق |
| `time.expire-at-ms`، `.expire-after-first-usage-ms` | unsigned 64-bit دقیق |

نقطه‌ها مسیر object تو در تو هستند. صفر limit/expiry مربوط را پاک می‌کند. token صحیح ساده تا INT64_MAX و رشته
decimal تا UINT64_MAX پذیرفته می‌شود؛ منفی، کسر، decimal/exponent عددی و overflow رد می‌شوند.
حداقل یک leaf لازم است؛ patch صرفاً دارای id، container خالی، null، کلید ناشناخته/alias/با case متفاوت و کلید
decodeشده تکراری در هر سطح رد می‌شود. کل بازه بایت‌ها بررسی می‌شود: UTF-8 نامعتبر، NUL خام یا escaped، داده اضافی
و بیش از هشت container تو در تو مجاز نیست. بودجه پیام authentication برقرار است، نه محدودیت اندازه فایل config.
`stats`، password/hash/credential، ID جایگزین، runtime/client-view و زمان ایجاد/اولین استفاده، از جمله aliasهای
سطح بالا، مجاز نیستند. وجود یک فیلد معتبر کنار فیلد ممنوع باعث اعمال جزئی نمی‌شود.

حساب ناشناخته، نام تکراری، CIDR نامعتبر/هم‌پوشان یا رد ظرفیت، هیچ فیلد، index منطقی، revision یا checkpoint را
تغییر نمی‌دهد. موفقیت نوع `0` و `user-updated` است و زیر write lock فقط config_revision را یک بار افزایش می‌دهد؛
حتی اگر مقدار برابر مقدار فعلی باشد. این ویرایش در حافظه است و ذخیره فوری ندارد. patchهای مستقل فیلدهای حذف‌شده
از درخواست را حفظ می‌کنند؛ برای یک فیلد، آخرین ویرایش پذیرفته‌شده برنده است. expected-revision لازم نیست.
`allow-user-write` و `allow-stats-push` مستقل‌اند؛ یکی مجوز دیگری نیست. opcode شماره `8` پشتیبانی نمی‌شود و
`unknown-request-type` می‌دهد.

### مالکیت آمار

| مقدار | مالک و قاعده فعلی |
| --- | --- |
| بایت upload/download تجمعی | مجموع سرور؛ گزارش remote فقط با batch deduplicated؛ patch تنظیمات آن را حفظ می‌کند |
| کمترین مشاهده غیرصفر اولین استفاده | کمترین مشاهده غیرصفر تولیدکننده مجاز، پس از clamp به زمان حسابداری پذیرش؛ patch آن را حفظ می‌کند |
| زمان ایجاد | metadata ایجاد/import؛ ویرایش عادی آن را حفظ می‌کند |
| limit، enabled و سیاست expiry | تنظیم حساب، قابل تغییر فقط با leaf صریح patch |
| اتصال خروجی فعال و reservation IP | وضعیت admission محلی، قابل نگهداری/آزادسازی در runtime؛ تعداد global نیست |
| آمار ذخیره/import شده IP، device، connection و speed | نمای قابل اعتماد از اشغال زنده global یا ورودی admission نیست؛ گزارش تازه‌ای اضافه نشده است |

گزارش آینده connection باید snapshot هر producer با ترتیب نمونه و expiry داشته باشد؛ نمونه بعدی جای قبلی را
می‌گیرد و مثل ترافیک جمع نمی‌شود. speed به بازه/زمان اندازه‌گیری و freshness نیاز دارد؛ نمونه مفقود/قدیمی صفر
اندازه‌گیری‌شده نیست و تجمیع producerها به بازه‌های سازگار نیاز دارد. IP متمایز به مجموعه هویت، پنجره مشاهده و
حذف تکرار بین producerها نیاز دارد؛ جمع تعدادهای کلاینت، تعداد IP متمایز global نمی‌سازد. device به تعریف هویت و
روش جمع‌آوری نیاز دارد. reset نیازمند تصمیم جدا درباره مصرف با تأخیر و cutoff توزیع‌شده است و اینجا عملیاتی ندارد.

### PushUserStats

تنها مسیر remote گزارش مصرف، `PushUserStats` و صرفاً برای بایت ترافیک است. شکل دقیق payload:

```json
{"epoch":"<64 hexadecimal bytes>","sequence":1,"users":[{"id":42,"up":10,"down":0,"first-usage-at-ms":1792252800000}]}
```

ریشه فقط `epoch`، `sequence` و `users` و هر ورودی دقیقاً `id`، `up`، `down` و `first-usage-at-ms` دارد؛ همه اجباری‌اند.
فیلد ناشناخته/تکراری، آمار غیرترافیکی، timestamp دیگر یا مجموع مطلق، کل درخواست را رد می‌کند. قواعد strict JSON/UTF-8،
NUL، عمق هشت container و مصرف کامل ورودی مانند patch برقرار است. digest از بایت‌های اصلی payload محاسبه می‌شود.
هر batch بین ۱ تا ۴۰۹۶ ID یکتا و غیرصفر دارد. هر ورودی هر دو delta و timestamp غیرصفر دارد؛ هر دو delta برای گزارش فقط metadata می‌توانند صفر باشند. tokenهای integer ساده تا INT64_MAX و رشته decimal تا UINT64_MAX دقیق‌اند؛ decimal/exponent عددی،
مقادیر کسری، منفی، nonfinite و overflow برای استخراج عدد صحیح رد می‌شوند.

checkpoint با هویت احراز‌شده انتخاب می‌شود. زیر یک write lock، replay آخرین sequence با digest یکسان پیش از
بررسی دوباره حساب‌ها ACK می‌شود. برای sequence دقیقاً بعدی، همه ورودی‌ها پیش از mutation بررسی می‌شوند؛ سپس
ساعت حسابداری یک بار نمونه‌گیری می‌شود؛ مشاهده به حداکثر همان زمان clamp و کمترین مقدار غیرصفر با canonical
merge می‌شود. مصرف saturating، اولین استفاده و checkpoint با یک افزایش stats_revision منتشر می‌شوند؛
config_revision تغییر نمی‌کند. گزارش بعدی همان timestamp محلی را حفظ می‌کند؛ receipt-time fallback وجود ندارد. ID ناشناخته، تکرار ID، epoch قدیمی، gap،
sequence قدیمی یا محتوای متفاوت همان sequence، بدون mutation رد می‌شود. sequence wrap مجاز نیست.

ACK موفق نوع `0` و JSON دارای `epoch`، `sequence`، `digest` شصت‌وچهارکاراکتری SHA-256 و `needs-pull: true`
است. replay دقیق حتی پس از تغییر یا حذف حساب ACK می‌شود و همچنان pull زمان اولین استفاده و مجموع مرجع را لازم
می‌داند. تاریخچه checkpoint ثابت و محدود به آخرین batch هر هویت است؛ snapshot جدول در session نگهداری نمی‌شود.
کلاینت پس از reconnect ابتدا batch باقی‌مانده را replay و ACK آن را اعتبارسنجی می‌کند، سپس جدول کامل را می‌گیرد.
دریافت الزامی جدول پس از احراز هویت یا هر ACK باید پیش از ساخت batch جدید تمام شود. پس از آن، push منتظر بر
pullهای عادی دوره‌ای یا صریح اولویت دارد تا pullهای مکرر باعث توقف نامحدود گزارش مصرف نشوند.

## رفتار Lifecycle

با دریافت `init` در جهت upstream، `AuthenticationServer` وضعیت buffer مخصوص همان line را مقداردهی اولیه می‌کند و `est` را در جهت downstream به تونل قبلی می‌فرستد.

در payloadِ upstream، بایت‌ها را buffer می‌کند، پیام‌های بیرونی کامل را بیرون می‌کشد، هر فریم درخواست را پردازش می‌کند و با `tunnelPrevDownStreamPayload()` یک پیام پاسخ ترکیبی در جهت downstream می‌فرستد.

با دریافت `finish` در جهت upstream، فقط state مخصوص همان line را از بین می‌برد. چون سازنده line نبوده، `lineDestroy()` را فراخوانی نمی‌کند.

اگر سرور به دلیل داده malformed یا بزرگ‌تر از حد مجاز اتصال منطقی را ببندد، ابتدا state خودش برای line را از بین می‌برد و سپس `finish` را در جهت downstream به تونل قبلی می‌فرستد.

## نکته‌ها

- سقف payload پیام بیرونی `16 MiB` است.
- سقف داده درخواست `16 MiB` است.
- سقف payload پاسخ `16 MiB` است.
- پاسخ‌های صف‌شده و فعال مشترکاً ۱۰۲۴ entry، `16 MiB + 20 bytes` داده منطقی و `32 MiB` allocation charge دارند.
  refusal فقط همان line را می‌بندد. خروجی با chunkهای حداکثر `16 KiB`، padding کافی و FIFO در برابر reentry ارسال
  می‌شود؛ backing فعال تا آزاد شدن charge دارد. این سقف RSS کل نیست.
- scratch ساخت شامل یک frame، یک پیام در حال رشد، یک متن JSON محدود و یک chunk خروجی است؛ هر پیام/frame حداکثر
  `16 MiB` به‌اضافه envelope است و printer پنج بایت اضافه دارد. هنگام تعویض allocation، قدیم و جدید موقتاً هم‌زمان‌اند.
- پیام‌های کامل درخواست قبل از بررسی سقف ورودی ناقص پردازش می‌شوند؛ چند پیام در یک تحویل، یک پیام بیش‌ازحد بزرگ نیست.
  ورودی ناقص کمتر از `16 MiB + 68 bytes` است و پس از ادغام بافرها حداکثر ۱۰۲۴ entry و `32 MiB` charge دارد.
  ورودی تو‌در‌تو همراه با ادامهٔ خوانده‌نشدهٔ قبلی، سقف یک پیام کامل به‌اضافهٔ `2 MiB` را دارد؛ بافرهای قطعه‌قطعه
  پیش از رد ورودی ادغام می‌شوند. تحویل خالی آزاد می‌شود. یک درخواست استخراج‌شده و مقصد ادغام، scratch محدود هستند؛
  تحویل همگام فعلی خارج از سقف ورودی نگهداری‌شده است.
- این node به left padding نیاز ندارد و چیزی را درجا prepend نمی‌کند.
- این node packet tunnel نیست و از قواعد packet line استفاده نمی‌کند.

## عملکرد پایگاه داده کاربران

- SHA-256 کلید اصلی جست‌وجوی password متنی است. هر جست‌وجوی password فقط یک بار SHA-256 را محاسبه می‌کند و بدون fallback scan روی جدول کاربران، از index هش SHA-256 نتیجه را پیدا می‌کند؛ بنابراین هزینه متوسط hit و miss برابر O(1) است. مقایسه دقیق password متنی پس از hit شدن index، بررسی نهایی و مقاوم در برابر برخورد hash است.
- تمام جست‌وجوهای کلیددار، شامل SHA-224، SHA-256، UUID، کلید عمومی WireGuard، id ماندگار و name غیرخالی، هزینه متوسط O(1) دارند. جست‌وجوی آدرس Allowed-IP مربوط به WireGuard و تشخیص هم‌پوشانی range‌ها با یک index بازه‌ای مرتب‌شده و هزینه O(log M) انجام می‌شود.
- پیام‌های صرفاً point read، شامل `Ping`، `GetUserBySHA-224/256` و `GetUserByPassword`، read lock مربوط به state سرور را به‌اشتراک می‌گذارند و می‌توانند هم‌زمان اجرا شوند. هر پیام شامل احراز هویت، `GetAllUsers`، تغییر کاربر، تغییر آمار یا درخواست ناشناخته یا ترکیبیِ غیر point read، در تمام مدت dispatch از state write lock استفاده می‌کند.
