# IpOverrider

## نمای کلی {#overview}

`IpOverrider` آدرس‌های IP مبدأ و مقصد را در payload بسته‌های خام بازنویسی می‌کند.

این گره یک تونل بسته در لایهٔ 3 است. سوکت نمی‌سازد، line اتصال عادی ایجاد
نمی‌کند و بسته را بافر نمی‌کند. فقط بسته‌هایی را بررسی می‌کند که از قبل در یک زنجیرهٔ بسته‌محورِ WaterWall جریان دارند و فیلدهای تعیین‌شده در سرآیندِ IPv4 را درجا تغییر می‌دهد.

## جایگاه معمول در زنجیره {#typical-placement}

<a id="جایگاه-رایج"></a>

برای بازنویسی آدرس حامل در یک جفت FakeTcpHeader:

```text
client: UdpListener -> ConnectionToPackets -> FakeTcpHeaderClient -> IpOverrider -> RawSocket
server: RawSocket -> IpOverrider -> FakeTcpHeaderServer -> PacketsToConnection -> UdpConnector
```

کلاینت پیش از خروجی خام، آدرس‌های خصوصی داخلی را به آدرس‌های بیرونی قابل دسترسی
تبدیل می‌کند و در پاسخ‌ها آدرس‌های خصوصی را برمی‌گرداند. سرور نگاشت معکوس را
انجام می‌دهد. هر دو جهت باید صریحاً تنظیم شوند؛ `IpOverrider` جدول اتصال
برای NAT نگه نمی‌دارد و قاعده معکوس را حدس نمی‌زند.
[نمونه‌های کامل حامل UDP](./FakeTcpHeaderClient.mdx#examples)
قواعد متناظر، فیلترهای دریافت بسته، MTU و مقصد backend را نشان می‌دهند.

برای بازنویسی بسته‌های داخلی IPv4 در زنجیرهٔ مربوط به WireGuard، گره را در سمت
بسته بگذارید:

```text
UdpListener -> WireGuardServer(mode=packet) -> IpOverrider -> TunDevice
```

در این چیدمان، `up` روی بستهٔ رمزگشایی‌شده پیش از تحویل به TUN و `down` روی
بستهٔ خوانده‌شده از TUN پیش از رمزنگاری WireGuard عمل می‌کند. `allowedips` هر
همتا باید با آدرس‌های مبدأ/مقصدی که WireGuard در سمت مربوط به بازنویسی می‌بیند
مطابقت داشته باشد. سمت بستر انتقال شامل بدنهٔ پیام WireGuard است، نه بسته خام
IPv4؛ بنابراین `IpOverrider` نباید میان WireGuard و سوکت UDP آن قرار بگیرد.

## نمونهٔ کاربردی ساده {#minimal-practical-example}

JSON زیر **قطعهٔ پیکربندی گره** است و پیکربندی کامل نیست. آدرس‌های بسته و نام `next` را برای نگاشت صریح خود جایگزین کنید. دو جهت مستقل هستند و این گره قواعد معکوس NAT را حدس نمی‌زند.

### نمونهٔ پیکربندی {#configuration-example}

<a id="نمونه-تنظیم"></a>

قالب جدید چندقاعده‌ای:

```json
{
  "name": "ip-rewrite",
  "type": "IpOverrider",
  "settings": {
    "up": {
      "source-ip": {
        "ipv4": "10.0.0.10"
      },
      "dest-ip": {
        "ipv4": "198.51.100.10"
      }
    },
    "down": {
      "source-ip": {
        "ipv4": "203.0.113.10"
      },
      "dest-ip": {
        "ipv4": "10.0.0.20"
      }
    }
  },
  "next": "next-packet-node"
}
```

## پیکربندی {#configuration}

### فیلدهای الزامی {#required-fields}

<a id="فیلدهای-لازم"></a>

فیلدهای سطح بالا:

| فیلد | نوع | توضیح |
| --- | --- | --- |
| `name` | رشته | نام گره به انتخاب کاربر؛ باید در فایل پیکربندی یکتا باشد. |
| `type` | رشته | باید دقیقاً `"IpOverrider"` باشد. |
| `settings` | شیء | اجباری است و باید دست‌کم یک قاعده بازنویسی داشته باشد. |
| `next` | رشته | برای عبور عادی داده در upstream لازم است. |

در چیدمان مفید، این گره باید یک گره بستهٔ قبلی هم داشته باشد.

### قالب جدید چندقاعده‌ای {#new-multi-rule-format}

<a id="قالب-جدید-چند-rule"></a>

قالب پیشنهادی فعلی از اشیای `up` و/یا `down` استفاده می‌کند:

| مسیر قاعده | معنی |
| --- | --- |
| `settings.up.source-ip` | بازنویسی آدرس IPv4 مبدأ در بسته‌های upstream. |
| `settings.up.dest-ip` | بازنویسی آدرس IPv4 مقصد در بسته‌های upstream. |
| `settings.down.source-ip` | بازنویسی آدرس IPv4 مبدأ در بسته‌های downstream. |
| `settings.down.dest-ip` | بازنویسی آدرس IPv4 مقصد در بسته‌های downstream. |

دست‌کم یکی از این اشیای قاعده باید وجود داشته باشد. اگر کلید `up` یا `down`
وجود داشته باشد، تجزیه‌گر قالب جدید را انتخاب می‌کند و دیگر شیء را به‌عنوان
تنظیمات قدیمی نمی‌خواند.

هر شیء قاعدهٔ موجود باید `ipv4` یا `ipv6` داشته باشد.

### گزینه‌های گره {#node-options}

<a id="گزینههای-نود"></a>

`chance` و `only120` باید مستقیماً در شیء اصلی `settings` و کنار `up` و
`down` قرار بگیرند:

| فیلد | نوع | پیش‌فرض | توضیح |
| --- | --- | --- | --- |
| `chance` | درصدِ صحیح از `0` تا `100` | `100` | احتمال اجرای کل عمل بازنویسی گره روی یک بسته واجد شرایط. |
| `only120` | بولی | `false` | کل عمل گره را به بسته‌های IPv4 با طول کل IP حداکثر `120` بایت محدود می‌کند. |

هیچ‌کدام از این گزینه‌ها را داخل `source-ip` یا `dest-ip` قرار ندهید. در قالب
جدید، `chance` و `only120` داخل قاعده پذیرفته نمی‌شوند و باید به
`settings.chance` و `settings.only120` منتقل شوند.

### فیلدهای آدرس قاعده {#rule-address-fields}

<a id="فیلدهای-آدرس-هر-rule"></a>

| فیلد | نوع | توضیح |
| --- | --- | --- |
| `ipv4` | رشته یا آرایهٔ رشته‌ها | آدرس IPv4 جایگزین یا فهرستی غیرخالی از آدرس‌های IPv4. مقادیر باید آدرس صریح IPv4 باشند، نه CIDR یا نام میزبان. |
| `ipv6` | رشته | آدرس صریح IPv6؛ تجزیه و ذخیره می‌شود، اما بازنویسی IPv6 در مسیر فعلیِ زمان اجرا غیرفعال است. رشته خالی، آدرس IPv4، نام میزبان و قالب CIDR پذیرفته نمی‌شوند. |

اگر `ipv4` آرایه باشد، هر بسته‌ای که قاعده روی آن اعمال می‌شود آدرس بعدی آرایه
را به‌صورت چرخشی می‌گیرد. نشانگر هر قاعده جداست.

اگر یک قاعده هم `ipv4` و هم `ipv6` داشته باشد، `ipv4` به کار می‌رود، زیرا تجزیه‌گر
ابتدا آن را بررسی می‌کند.

### قالب قدیمی {#legacy-format}

<a id="قالب-قدیمی-1"></a>

در قالب قدیمی یک قاعده مستقیم داخل `settings` تعریف می‌شود:

| فیلد | نوع | توضیح |
| --- | --- | --- |
| `direction` | رشته | باید `"up"` یا `"down"` باشد. |
| `mode` | رشته | باید `"source-ip"` یا `"dest-ip"` باشد. |
| `ipv4` / `ipv6` | رشته، یا آرایهٔ آدرس‌های IPv4 برای `ipv4` | آدرس جایگزین برای قاعده انتخاب‌شده. |
| `chance` | درصدِ صحیح | احتمال اعمال بازنویسی بر بسته در سطح گره، با همان بازه `0` تا `100` و پیش‌فرض قالب جدید. |
| `only120` | بولی | شرط طول بستهٔ IPv4 در سطح گره با پیش‌فرض `false` و مرز `120` بایت، مانند قالب جدید. |

برای پیکربندی‌های تازه بهتر است از قالب جدید استفاده کنید، زیرا تا چهار قاعده را
در یک گره پوشش می‌دهد. در قالب قدیمی، `chance` و `only120` از قبل در ریشه
`settings` قرار دارند؛ چون این قالب فقط یک قاعده دارد، رفتار شرط مشترک جدید از
نظر نتیجه تفاوت دیگری ایجاد نمی‌کند.

### `chance` {#chance}

گزینه `chance` مشخص می‌کند کل عمل گره با چه احتمالی اجرا شود. این مقدار برای هر
بسته واجد شرایط فقط یک بار ارزیابی می‌شود، نه جداگانه برای قاعده‌های مبدأ و
مقصد:

- مقدار `100` یعنی عمل گره همیشه اجرا شود.
- مقدار `0` یعنی بسته همیشه بدون تغییر عبور کند.
- مقادیر `1` تا `99` درصد احتمال اجرای عمل کامل گره را مشخص می‌کنند.

برای هر worker و جهت، یک شرط درصدی شبه‌تصادفیِ مستقل و غیررمزنگاری وجود دارد. نتیجه‌ها
می‌توانند پشت سر هم رخ دهند و در طول زمان به درصد تنظیم‌شده نزدیک می‌شوند، نه
اینکه از یک الگوی ثابت «هر N بسته» پیروی کنند.

در مثال زیر، هر دو بازنویسی مبدأ و مقصد تقریباً روی 25 درصد بسته‌های واجد شرایطِ upstream با هم اجرا می‌شوند. در سایر بسته‌ها هیچ‌کدام اجرا نمی‌شوند:

```json
{
  "name": "probabilistic-ip-rewrite",
  "type": "IpOverrider",
  "settings": {
    "chance": 25,
    "up": {
      "source-ip": {
        "ipv4": "10.0.0.10"
      },
      "dest-ip": {
        "ipv4": "198.51.100.10"
      }
    }
  },
  "next": "next-packet-node"
}
```

### `only120` {#only120}

گزینه `only120` یک شرط اندازه برای کل عمل گره است. وقتی `true` باشد، همهٔ
بازنویسی‌های تنظیم‌شده برای بسته‌های IPv4 با طول کل IP حداکثر `120`
بایت با هم اجرا می‌شوند. بسته‌های بزرگ‌تر بدون تغییر عبور می‌کنند.

```json
{
  "name": "small-packet-ip-rewrite",
  "type": "IpOverrider",
  "settings": {
    "only120": true,
    "up": {
      "source-ip": {
        "ipv4": "10.0.0.10"
      },
      "dest-ip": {
        "ipv4": "198.51.100.10"
      }
    }
  },
  "next": "next-packet-node"
}
```

### ترکیب `only120` و `chance` {#combining-only120-and-chance}

<a id="ترکیب-only120-و-chance"></a>

گره برای هر بسته، شرط‌های سطح ریشهٔ تنظیمات را پیش از اجرای هر قاعده ارزیابی می‌کند:

- وقتی `only120` فعال است، برای بستهٔ IPv4 با طول کل IP بیشتر از `120` بایت، از کل عمل گره صرف‌نظر می‌شود.
- در غیر این صورت، `settings.chance` دقیقاً یک بار ارزیابی می‌شود. اگر شرط احتمال برقرار نشود، کل عمل گره رد می‌شود.
- وقتی هر دو شرط برقرار باشند، همهٔ قواعد مبدأ و مقصد تنظیم‌شده برای
  جهت بسته ارزیابی می‌شوند.

وقتی هرکدام از شرط‌ها عمل گره را رد کند، بسته بدون تغییر عبور می‌کند، نشانگر
آرایه‌های IPv4 جلو نمی‌رود و این گره درخواست محاسبه دوباره checksum نمی‌دهد.

### نکته‌ها و محدودیت‌ها {#notes-and-caveats}

<a id="نکتهها"></a>

- مسیر فعلی بازنویسی در زمان اجرا فقط سرآیند بسته‌های IPv4 را تغییر می‌دهد.
- IPv6 از پیکربندی خوانده و ذخیره می‌شود، اما بخش مربوط به بازنویسی آن در کد
  فعلاً غیرفعال است.
- مقادیر `ipv4` باید آدرس صریح IPv4 باشند. CIDR و نام میزبان پذیرفته نمی‌شوند.
- جعل آدرس IP مبدأ فقط زمانی کار می‌کند که شبکه و دیتاسنتر شما بسته‌هایی با آن آدرس مبدأ بازنویسی‌شده را مجاز بدانند؛ بسیاری از ارائه‌دهندگان چنین ترافیکی را حذف می‌کنند.
- `IpOverrider` تنها آدرس IP را تغییر می‌دهد و پورت مربوط به TCP/UDP را بازنویسی نمی‌کند.

## جزئیات پیاده‌سازی {#implementation-details}

### عملکرد {#what-it-does}

<a id="عملکرد"></a>

- در upstream، آدرس IPv4 مبدأ را در صورت وجود قاعده تغییر می‌دهد.
- در upstream، آدرس IPv4 مقصد را در صورت وجود قاعده تغییر می‌دهد.
- در downstream، آدرس IPv4 مبدأ را در صورت وجود قاعده تغییر می‌دهد.
- در downstream، آدرس IPv4 مقصد را در صورت وجود قاعده تغییر می‌دهد.
- یک شرط `only120` در سطح گره برای کل عمل بازنویسی گره دارد.
- یک شرط `chance` در سطح گره برای کل عمل بازنویسی گره دارد.
- هر قاعده می‌تواند یک آدرس IPv4 یا آرایه‌ای غیرخالی از آدرس‌های IPv4 داشته باشد.
- پس از بازنویسی IPv4، checksum‌های سرآیندِ IPv4 و شبه‌سرآیند مربوط به TCP/UDP
  را به‌صورت افزایشی به‌روز می‌کند.
- بسته‌های upstream را به `next` و بسته‌های downstream را به گره قبلی می‌فرستد.

نسخه فعلی می‌تواند در یک نمونه برای هر دو جهت و هر دو فیلد قاعده مستقل داشته
باشد؛ بنابراین در بسیاری از سناریوهایی که قبلاً چند `IpOverrider` پشت سر هم لازم
بود، حالا یک گره کافی است.

### رفتار جهت‌ها {#direction-behavior}

<a id="رفتار-جهتها"></a>

payload در جهت upstream:

1. شرط‌های `only120` و `chance` در سطح گره ارزیابی می‌شوند
2. اگر هر دو برقرار باشند، `up.source-ip` و `up.dest-ip` بررسی می‌شوند
3. بسته با `tunnelNextUpStreamPayload()` به `next` می‌رود

payload در جهت downstream:

1. شرط‌های `only120` و `chance` در سطح گره ارزیابی می‌شوند
2. اگر هر دو برقرار باشند، `down.source-ip` و `down.dest-ip` بررسی می‌شوند
3. بسته با `tunnelPrevDownStreamPayload()` به گره قبلی برمی‌گردد

اگر برای یک جهت قاعده وجود نداشته باشد، بسته بدون تغییر عبور می‌کند.
`IpOverrider` زنجیره را خاتمه نمی‌دهد و بسته را نگه نمی‌دارد.

### رفتار checksum {#checksum-behavior}

<a id="checksum"></a>

پس از بازنویسی آدرس IPv4، `IpOverrider` checksumِ سرآیندِ IPv4 را به‌صورت
افزایشی و درجا به‌روز می‌کند. برای بسته‌های TCP و بسته‌های UDP با checksum
فعال نیز تغییر مربوط به شبه‌سرآیندِ IPv4 را اعمال می‌کند. checksum صفر
(غیرفعال) UDP صفر باقی می‌ماند. این گره برای بازنویسی خودش درخواست محاسبهٔ دوبارهٔ checksum کل بسته را نمی‌دهد و هر درخواست محاسبه دوباره‌ای را که از قبل وجود داشته حفظ
می‌کند.

### معنای line بسته {#packet-line-semantics}

<a id="packet-line"></a>

`IpOverrider` یک تونل بسته خالص است:

- چرخهٔ عمر مجزایی برای هر اتصال ندارد.
- line نمی‌سازد و آزاد نمی‌کند.
- callbackهای payload بسته، مسیر مورد نظر برای اجرا هستند.
- callback‌های به‌سبک جریان بایتی مثل `Finish`، `Pause`، `Resume` و `Est` برای استفاده
  عادی معتبر نیستند.

پیاده‌سازی برای lineهای بسته، وضعیت مخصوص هر line تخصیص نمی‌دهد.

### محدودیت‌ها و padding {#limits-and-padding}

<a id="محدودیتها-و-padding"></a>

| مقدار | اندازه |
| --- | --- |
| `required_padding_left` | `0 bytes` |
| بازه `chance` | `0` تا `100` |
| شرط `only120` | طول کل IPv4 برابر یا کمتر از `120` بایت |

این گره فقط فیلدهای موجود در سرآیند را درجا بازنویسی می‌کند و به فضای padding سمت چپ
نیاز ندارد.

### فرادادهٔ گره {#node-metadata}

<a id="متادیتای-نود"></a>

فراداده برگرفته از کد منبع:

| ویژگی | مقدار |
| --- | --- |
