# بخش ۷: خاتمه‌ی Application

WaterWall یک مرجع واحد برای خاتمه‌ی منظم پردازه دارد. کنترل‌کننده‌ی Shutdown
درخواست‌ها و Exit Status را ثبت می‌کند؛ Main Thread پس از خروج Worker 0 از Dispatch
عادی Event Loop، توالی Shutdown مبتنی بر مالکیت را اجرا می‌کند. Workerها، Loopها،
Tunnelها، Deviceها، Queueها و کد پروتکل به عملیات صریح و محلی Lifecycle از سوی
Owner خود پاسخ می‌دهند. آن‌ها Process Controller را Poll نمی‌کنند.

خاتمه‌ی Fatal مسیر جداگانه‌ای دارد. `abortProgramNow()` عمداً Cleanup منظم را رد
می‌کند و فقط برای Corruption، شکست Invariant یا شکست Handoff منظم در وضعیتی است که
ادامه‌ی امن ممکن نیست.

## ۱. کنترل‌کننده‌ی Shutdown پردازه

Controller فقط رو به جلو در مراحل زیر حرکت می‌کند:

```text
Running
  -> Requested
  -> ClosingAdmissions
  -> QuiescingWorkers
  -> QuiescingExternalProducers
  -> DrainingWorkers
  -> StoppingComponents
  -> DestroyingWorkers
  -> Finalizing
```

`requestProgramShutdown(code)` نمای عمومی درخواست منظم است. درخواست اول سه واقعیت
مستقل را ثبت می‌کند: Origin تشخیصی، Scope مربوط به Cleanup و Exit Status. ‏Scope
از نقطه‌ی Commitشدن Runtime می‌آید، نه از Origin: هر درخواست پذیرفته‌شده پیش از
Commit، ‏`StartupRollback` را انتخاب می‌کند و هر درخواست پذیرفته‌شده پس از آن،
`ProcessShutdown` را. بنابراین Signal هنگام Startup همچنان Origin نوع Signal دارد،
اما Cleanup از نوع Rollback دریافت می‌کند.

درخواست اول یک Transaction واحد از Controller به Worker است. Controller در حالی
که Mutex خود را نگه داشته، Scope را انتخاب می‌کند و درخواست Quiesce سطح‌حساس
Worker 0 را، شامل بستن Admission عادی و Message، نصب می‌کند. تنها پس از آن
`Requested` را Publish می‌کند. اگر Worker 0 نتواند درخواست محلی را بپذیرد، Controller
در `Running` می‌ماند. پس از پذیرش، Wake ناقص درخواست را Rollback نمی‌کند. ترتیب
Lock ابتدا Mutex کنترل‌کننده و سپس Mutex کنترل Worker است؛ مسیرهای Failure مربوط به
Worker پیش از گزارش سراسری، Lock همان Worker را آزاد می‌کنند.

پس از موفقیت همه‌ی مراحل Startup و Admission همه‌ی Taskهای الزامی، اما پیش از
Publishشدن `workers_run_flag`، Owner اصلی Startup عملیات Commit Runtime را اجرا
می‌کند. Commit و پذیرش درخواست با Mutex کنترل‌کننده Serialize می‌شوند؛ در نتیجه یا
درخواست برنده می‌شود و Rollback رخ می‌دهد یا Runtime از قبل Commit شده است. درخواست‌های
تکراری Coalesce می‌شوند. نخستین Status غیرصفر بعدی می‌تواند Status موفق را تا زمانی
بالا ببرد که Origin، ‏Scope و Status هنگام ورود به `Finalizing` با هم Freeze شوند.

`Requested` فقط تضمین می‌کند رکورد درخواست وجود دارد و Controller اصلی اجرا باید
وارد Shutdown شود. این State به معنی بسته‌شدن Admission، بازگشت Callback، مرده‌شدن
Line یا امن‌بودن Reclaim یک Object نیست.

فقط Handoff سیستم‌عامل در SignalManager و Coordinator اصلی، Phase سراسری پردازه را
می‌خوانند. هیچ `application_stopping_flag`، بررسی Leaf از
`isApplicationTerminating()` یا State ثانویه‌ی Shutdown قابل‌مشاهده برای Componentها
وجود ندارد.

## ۲. Handoff درخواست و Worker 0

در POSIX، ‏Handler ‏Async مربوط به Signal، نخستین Signal را در Mailbox نوع
`volatile sig_atomic_t` ذخیره می‌کند و به‌صورت best-effort یک Byte در Self-pipe
غیرمسدودکننده می‌نویسد. Pipe پر از قبل نشان‌دهنده‌ی Wake در انتظار است. Handler هیچ
Lock مربوط به Application نمی‌گیرد و Cleanup انجام نمی‌دهد. Worker 0 ‏Mailbox را
مصرف و درخواست Typeدار Controller را Publish می‌کند. عملیات Take-and-clear مربوط
به Mailbox دقیقاً مجموعه‌ی Signalهای Graceful را Block می‌کند، Signal گرفته‌شده را
پیش از Unblockشدن Publish می‌کند و Mask قبلی Caller را دقیقاً برمی‌گرداند. مرز شکست
Startup در حالی که همان مجموعه Block است، Mailbox را Take می‌کند، Signal را Publish
می‌کند و `StartupFailure` را نیز Publish می‌کند. Signalای که هنگام گرفتن Mask از
قبل Capture شده باشد Origin تغییرناپذیر را می‌برد؛ Signalای که فقط پس از گرفتن
Mask تحویل شود پس از مرز ترتیب می‌گیرد و نمی‌تواند Startup Failure پذیرفته‌شده را
جایگزین کند. مسیر اصلی Startup نیز در Checkpointهای هر Stage ‏Mailbox را مصرف می‌کند.

در Windows، یک Gate اتمیک با طول عمر پردازه Admission مربوط به Handler و تعداد
Entrantهای فعال را ترکیب می‌کند. Handler پیش از خواندن Storage مربوط به Manager یا
Controller این Gate را می‌گیرد. Destruction، ‏Gate را می‌بندد، Handler سیستم‌عامل
را Unregister می‌کند، Waiterها را آزاد می‌کند و فقط منتظر Entrantهای پذیرفته‌شده
می‌ماند. Entrant دیررس از Fallback مربوط به Fatal Status که به Manager نیاز ندارد
استفاده می‌کند. Handleکردن Close/Logoff/Shutdown کنسول، هر جا قرارداد سیستم‌عامل
لازم بداند، می‌تواند مدت محدودی منتظر بماند.

Callback، ‏Event Loop، ‏Workerها، Nodeها یا Global State خود را نابود نمی‌کند.
`wloopRun()` درخواست محلی را میان Rootهای Callback مشاهده می‌کند و نتیجه‌ای Typeدار
برمی‌گرداند. سپس `runMainThread()` بیرون از Stack مربوط به Event Dispatch،
Coordinator را فراخوانی می‌کند.

Signal دوم Operator می‌تواند از Escape Hatch مربوط به خروج فوری در SignalManager
استفاده کند. `abortProgramNow()` فقط Arbitration بدون Lock مربوط به Status و
`_Exit`/`ExitProcess` فوری را انجام می‌دهد؛ هیچ Diagnosticای که ممکن است روی Stream
پر Block شود تولید نمی‌کند. در مسیر C11، ‏Compile-time الزام می‌کند Integer مربوط
به Fatal Status همیشه Lock-free باشد. Fallback ویندوز از Primitive متناظر و
Lock-free نوع Interlocked استفاده می‌کند. Operationهای آن Relaxed باقی می‌مانند،
زیرا این Integer هیچ State دیگری را Publish نمی‌کند.

در POSIX، ‏Signalهای Fatal Crash، ‏Disposition پیش‌فرض خود را Restore می‌کنند،
Unblock و دوباره Raise می‌شوند و فقط در صورت شکست از `_Exit(128 + signum)` استفاده
می‌شود. Handlerهای Fatal در Windows با Status داوری‌شده خاتمه می‌دهند، زیرا معنای
Signal/Core در POSIX آنجا کاربرد ندارد.

## ۳. چرخه‌ی عمر Worker

هر Event Worker معمولی مراحل زیر را طی می‌کند:

```text
Initialized
  -> Running
  -> QuiesceRequested
  -> Quiesced
  -> DrainRequested
  -> Drained
  -> TeardownRequested
  -> Exited
  -> Joined
```

Coordinator اصلی درخواست‌ها را Publish می‌کند. Worker مالک فقط پس از کامل‌شدن کار
نمایندگی‌شده Acknowledgement را Publish می‌کند. Mutex و Condition Variable مربوط
به Worker، Releaseهای Drain و Teardown را پس از پایان Dispatch عادی Event Loop
منتقل می‌کنند؛ فرمان‌های Lifecycle به‌طور پنهانی از Queue عادی Event عبور داده
نمی‌شوند.

Worker 0 همان معنا را رعایت می‌کند، اما مراحل Quiesce، ‏Drain و Teardown خود را
مستقیماً روی Main Thread اجرا می‌کند. Slot مربوط به lwIP یک Pseudo-worker است:
Pool دارد، اما Event Loop مربوط به WaterWall یا Worker Thread ساخته‌شده ندارد.
منابع آن فقط پس از Joinشدن Thread مربوط به lwIP نابود می‌شوند.

یک Worker در State ‏Quiesced:

- هیچ کار Asynchronous عادی تازه‌ای را نمی‌پذیرد؛
- هیچ Root مربوط به Callback عادی در حال اجرا ندارد و Root بعدی را آغاز نمی‌کند؛
- Messageهای Queueشده و Timed پذیرفته‌شده را تسویه کرده است؛
- Timerها و Watcherهای Component مربوط به WID خود را Detach کرده است؛
- از Dispatch عادی Loop برگشته است؛
- همچنان مالک Loop، ‏Queue، ‏Tunnel، ‏Line و Poolهای لازم برای Drain و Teardown است.

## ۴. مرزهای Callback عادی

Root یک Callback عادی، یک ورود از Scheduler یا Producer خارجی به رفتار معمول
Application است: Callback مربوط به I/O، ‏Timer، ‏Idle، ‏Custom Event، پیام Queueشده‌ی
Worker، تحویل Device یا تحویل lwIP. ‏Callbackهای Synchronous و Nested تونل متعلق
به Root پذیرفته‌شده برای دقیقاً همان `wloop_t` هستند؛ Callback روی Loop ‏A هیچ
Authority ارث‌رسیده‌ای روی Loop ‏B ندارد. Direct Writeها روی NIO و IOCP نیز همین
قاعده را دارند: Caller مستقل باید Admission مربوط به Loop مقصد را در تمام مدت
System Send، ثبت Interest، درج Queue و Publish عملیات Asynchronous نگه دارد.
Callback هم‌زمان Write یک Root مربوط به Callback مقصد است: فقط با Authority عادی
Loop مقصد اجرا می‌شود و هنگام بازگشت هر Authority مربوط به Loop مبدأ بیرونی را
Restore می‌کند. Admission پیش از فراخوانی User Code آزاد می‌شود؛ بنابراین Admission
بسته Root بعدی را Suppress می‌کند و Backend، ‏Buffer منتقل‌شده یا عملیات Queueشده
را دقیقاً یک بار تسویه می‌کند.

WIO Write مستقل ممکن است از Thread دیگری آغاز شود، اما Callerها باید Writeهای یک
`wio_t` را Serialize کنند؛ قرارداد Mutex بازگشتی برای هر WIO وجود ندارد. Writeهای
TCP با طول صفر و Branchهای موجود Stream Queue از همان Gate مربوط به Loop مقصد
عبور می‌کنند. Rejection هیچ Byteای نمی‌فرستد، به‌عنوان Side Effect ‏WIO را نمی‌بندد
و Buffer منتقل‌شده را یک بار مصرف می‌کند. Datagramهای UDP با طول صفر همچنان
Datagram معتبرند.

Event Loop درخواست Quiesce محلی خود را در نقاط زیر بررسی می‌کند:

1. پیش از Poll؛
2. بلافاصله پس از Poll؛
3. پیش از Root هر Callback مربوط به Timer، ‏Idle، ‏I/O آماده، ‏Custom Event،
   ‏Completion و Message مربوط به Worker؛
4. میان Entryهای Batch گرفته‌شده و Drainهای Queue.

اگر درخواست هنگام اجرای Callback برسد، همان Callback عادی برمی‌گردد. Loop هیچ
Root عادی دیگری را شروع نمی‌کند. یک درخواست Level-triggered همراه Wake مربوط به
Poller حتی وقتی هیچ Event عادی قابل‌پذیرش نیست Progress را تضمین می‌کند.

Postکردن Custom از نوع خام `wevent_t` خصوصیِ Plumbing مربوط به Event Loop و Worker
است و نباید Payload متعلق به Application حمل کند. Post عادی پس از بسته‌شدن Admission
رد می‌شود. Posting یک Copy محلی ذخیره می‌کند که Metadata مربوط به Loop آن همیشه
برای مقصد Normalize شده است؛ Storage متعلق به Caller نمی‌تواند Authority مربوط به
Callback را جعل کند. Queue کنترل محدودتری، Cleanup الزامی WIO را تا زمان Drainشدن
Quiescence Worker می‌پذیرد و سپس پیش از Publishشدن `Quiesced`، ‏Admission خودش را
می‌بندد. Callbackهای کنترل بدون Authority عادی ارث‌رسیده اجرا می‌شوند؛ بنابراین کار
عادی‌ای که عمداً شروع می‌کنند باید Admission تازه بگیرد. Task دلخواه Application
که مالکیت حمل می‌کند باید از API با قرارداد صریح Run-or-cancel استفاده کند.

## ۵. مالکیت Run-or-cancel

یک پیام Worker پذیرفته‌شده دقیقاً یکی از مسیرهای Callback یا Cleanup خود را اجرا
می‌کند. Admission و Closure مربوط به Queue زیر Lock طول عمر Worker و Lock Queue
Linearize می‌شوند. پیام‌های Queueشده و Timed در انتظار، پیش از Acknowledgeشدن
Quiescence روی Worker مالک Cancel می‌شوند؛ نابودی Queue هرگز آن‌ها را بی‌صدا Drop
نمی‌کند.

APIهای Posting دو سبک مالکیت مورد استفاده در Runtime را از هم جدا می‌کنند:

- APIهای cleanup-on-refusal درخواست را رد و Cleanup ثبت‌شده را بلافاصله اجرا
  می‌کنند؛
- APIهای retain-on-refusal وقتی Message پذیرفته نشده، مالکیت را به Caller
  برمی‌گردانند؛
- پس از پذیرش، Task System تا زمانی که Callback یا Cleanup آرگومان‌ها را تسویه کند
  مالک آن‌ها است.

Submission با Delay نیز همین تفاوت را هنگام Setup ‏Timer رعایت می‌کند. Call از نوع
retain-on-refusal که نتواند Timer همان Worker را نصب کند، Payload را بدون اجرای
Cleanup به Caller برمی‌گرداند. اگر Wrapper مربوط به Setup در Queue پذیرفته شده باشد
و سپس تخصیص Timer روی Worker مقصد شکست بخورد، مالکیت قبلاً منتقل شده است؛ در نتیجه
Cleanup یک بار با `ResourceFailure` اجرا می‌شود.

Submissionهای بررسی‌شده مقدار `worker_message_submit_result_e` برمی‌گردانند:
پذیرفته‌شده، ردشده با حفظ مالکیت Caller، یا ردشده پس از اجرای Cleanup. ‏Cleanup یک
`worker_message_cancel_reason_e` دریافت می‌کند که مقصد unavailable، ‏Admission
بسته، شکست Enqueue/منبع، ‏Quiescence و Teardown را از هم جدا می‌کند. Cancelشدن
عمدی در Quiescence و Teardown تسویه‌ی عادی مالکیت است، نه شکست تازه‌ی پردازه.

اجرای Inline روی همان Worker پس از بسته‌شدن هم‌زمان Admission فقط وقتی معتبر است
که عملیات Synchronous و Nested داخل یک Root عادی از قبل پذیرفته‌شده باشد. Cleanup
مربوط به Shutdown صرفاً به‌دلیل برابر بودن WID در TLS با مقصد نمی‌تواند Admission
عادی را دوباره به‌دست آورد.

Cleanup مالکیت را آزاد می‌کند. نباید کار Application را Restart کند، Graph نامحدود
همسایه‌ها را فراخوانی کند یا صرفاً به‌دلیل Cancelشدن Task در Quiescence عمدی یک
Shutdown دیگر درخواست کند.

## ۶. ‏Lifecycle ABI v2

هر Tunnel یک جدول کامل Callback چرخه‌ی عمر با Context دارد. Shutdown پردازه مراحل
دقیق زیر را از Source تا Tail اجرا می‌کند:

| مرحله | Context | قرارداد |
| --- | --- | --- |
| `onQuiesceRequest` | Main Thread | Admission مربوط به Source محلی، ‏Producer، ‏Rearm و Component را ببندد و Wakeهای توقف را صادر کند. باید محدود و Nonblocking باشد. |
| `onWorkerQuiesce` | Worker مالک | Timerها، ‏Watcherها، ‏Handleهای Async و Handleهای Queueشده‌ی این WID را در حالی Detach کند که Loop و Tunnel State هنوز زنده‌اند. |
| `onQuiesceWait` | Main Thread | پس از Quiesceشدن همه‌ی Workerها، Rootهای Callback خارجی را Join یا Detach کند و خالی‌بودن Gateهای محلی را اثبات کند. منابع لازم برای Drain ‏Line را حفظ کند. |
| `onWorkerStop` | Worker مالک | Inventory معتبر Source و Lineهای عادی داخلیِ Owned را Drain کند. برای Lineهای Borrowed هرگز Inventory تازه اختراع نکند. |
| `onStop` | Main Thread | پس از Drainشدن همه‌ی Workerها، ‏Writerها، ‏Socketها، ‏PCBها، ‏Netifها و State مشترک نهایی را ببندد. هیچ Timer یا Watcher وابسته به Worker را لمس نکند. |
| `onDestroy` | Main Thread | پس از حذف همه‌ی ارجاع‌های Callback، ‏Message، ‏Line، ‏Thread خارجی و Worker، ‏Instance را Reclaim کند. |

همه‌ی Callbackها یک `ww_lifecycle_context_t` فقط‌خواندنی دریافت می‌کنند. Scopeهای
پشتیبانی‌شده عبارت‌اند از Shutdown پردازه، ‏Rollback مربوط به Startup، توقف private
child به‌دست Owner و Restart محلی Device. ‏Context همچنین Policy نوع Close را،
Graceful یا Abortive، مشخص می‌کند. Componentها رفتار را از این Context انتخاب
می‌کنند، نه از State محیطی پردازه.

حذف زنده‌ی یک Configuration در حال اجرا در این Lifecycle پشتیبانی نمی‌شود. چنین
قابلیتی به Lease اجرای مختص همان Configuration و قرارداد Publication/Removal خود
نیاز دارد.

Private Child Tunnelها با Helperهای Lifecycle مربوط به Owned Child هدایت می‌شوند.
Childای که در Chain عادی NodeManager درج شده است دوباره به‌دست Parent هدایت نمی‌شود؛
Traversal مرکزی از قبل مالک آن است.

### Nodeهای خارجی

Lifecycle v2 عمداً Layout خارجی `tunnel_t` و Signatureهای Callback را تغییر می‌دهد.
Library یک Node دینامیک باید تابع زیر را Export کند:

```c
uint32_t waterwallNodeLifecycleAbiVersion(void)
{
    return WW_EXTERNAL_NODE_LIFECYCLE_ABI_VERSION;
}
```

Loader پیش از Resolve یا فراخوانی Node Getter این Symbol را بررسی می‌کند. Library
با Descriptor گمشده یا ناسازگار رد می‌شود. WaterWall هیچ Callback قدیمی تک‌آرگومانی
را از طریق Function Pointer دارای Context صدا نمی‌زند و Layout قدیمی را Normalize
نمی‌کند.

## ۷. توالی مرتب Shutdown

Coordinator اصلی مراحل زیر را انجام می‌دهد:

1. همه‌ی `onQuiesceRequest`ها را فراخوانی و Admission عادی همه‌ی Workerها را ببندد؛
2. برای همه‌ی Workerهای معمولی Quiescence درخواست کند، Worker 0 را Quiesce کند و
   سپس منتظر Acknowledgement ‏`Quiesced` همه‌ی آن‌ها بماند؛
3. همه‌ی `onQuiesceWait`ها را برای Join یا Detachکردن Producerهای خارجی فراخوانی
   کند؛
4. همه‌ی Workerها را وارد Drain کند؛ SocketManager پیش از آنکه NodeManager
   `onWorkerStop` را از Source تا Tail اجرا کند جدول Owner مربوط به Sourceهای UDP
   خود را Drain کند؛
5. منتظر Acknowledgement ‏`Drained` همه بماند و سپس همه‌ی `onStop`ها را فراخوانی
   کند؛
6. Workerهای معمولی را وارد Teardown مربوط به Loop/Message/Pool کند، منتظر `Exited`
   بماند و Workerهای غیر Main را Join کند؛
7. ‏lwIP را Stop و Join و سپس Poolهای Pseudo-worker را نابود کند؛
8. Observerهای دیرهنگام و بدون مالکیت Exit و Finalizer صریح Application را اجرا
   کند؛
9. ‏Exit Status را Freeze و Nodeها، ‏SocketManager، ‏Poolها، ‏Shortcutها،
   Synchronization مربوط به Worker، زیرساخت Signal و Global Storage را نابود کند؛
10. با Status ثابت‌شده خارج شود.

Logging تا Diagnosticهای دیرهنگام Cleanup در دسترس می‌ماند. Registry مربوط به Exit
Observer در SignalManager یک Stack عمومی مالکیت نیست: Observerها می‌توانند
Diagnostic نهایی تولید یا Status هنوز Freezeنشده را تنظیم کنند، اما مالک Worker،
Node، ‏Device یا Queue نیستند.

## ۸. ‏Lineها هنگام Drain

قواعد Line در [بخش ۲](./part2-lines-and-callbacks.mdx) تغییر نمی‌کنند. Admission
مربوط به Source پیش از Drainشدن Inventoryها بسته می‌شود. جدول Owner مربوط به UDP
در SocketManager پیش از Hookهای Worker مربوط به Tunnel Drain می‌شود و هر Chain از
Source تا Tail پیمایش می‌شود تا Tunnelهای Middle، مجموعه‌ی Childهای Borrowed را فقط
پس از بسته‌شدن Owner واقعی آن‌ها ببینند.

Event Loop، ‏Chain، ‏Tunnel State، منابع Tail لازم برای `Finish` و Poolهای Line و
Buffer در سراسر Drain مربوط به Worker زنده می‌مانند. فقط Creator یک Line عادی
`lineDestroy()` را صدا می‌زند و Drain هر Owner همه‌ی Lineهای عادی آن را از نظر منطقی
مرده باقی می‌گذارد. Shutdown در Runtime هیچ‌گاه Packet Line را نابود نمی‌کند.

ReverseClient هر Pair ساخته‌شده را از زمان Publication تا Close در Registry مالک
به‌ازای هر Worker نگه می‌دارد؛ این شامل Pairهای Connecting، ‏Unused و Active است.
Idle Table مشترک آن فقط Index مربوط به Starvation Timeout است؛ Activation یک Item
را بدون حذف مالکیت از این Index بیرون می‌آورد. Expiry، ‏Finish همسایه، شکست
Re-entrant در Init و Drain مربوط به Worker همگی از یک مسیر Close برای Pair استفاده
می‌کنند که پیش از Callback همسایه Unregister می‌کند و هر دو Line ساخته‌شده را مرده
می‌سازد. Drain مربوط به Worker ابتدا Idle Itemها را تسویه و سپس هر Pair باقی‌مانده
در Owner Registry را می‌بندد.

پیام Expiration در IdleTable موقتاً مالک Delivery است، نه Index مربوط به Owner. اگر
Delivery در حالی Cancel شود که Item هنوز Attached است، Cleanup نشانگر Pending را
پاک و Item را با Deadline اصلی خود به Heap مربوط به Expiration برمی‌گرداند. Cleanup
هرگز جای Callback وابسته به Worker برای Expiration را نمی‌گیرد. Removal صریح،
Detachment مربوط به Worker یا نابودی Table، ‏Item را در مالکیت Message باقی می‌گذارد
تا Cancellation آن را به‌جای Restoreکردن دقیقاً یک بار Free کند. Staging مربوط به
Expiration نیز Transactional است: شکست Reservation هر دو Index را دست‌نخورده باقی
می‌گذارد و شکست بعدی در رشد Staging دقیقاً همان Item بیرون‌آمده را پیش از توقف Scan
برمی‌گرداند. ساخت Item تنها پس از مالک‌شدن Map و Expiration Heap یک Handle را
Expose می‌کند؛ شکست Publication در Heap، درج Map را Rollback می‌کند.

درخواست Shutdown منظم معادل نابودی Line نیست. Handler مربوط به `Finish` برای یک
Line عادی Owned، حتی وقتی Shutdown پردازه را نیز درخواست می‌کند، باید پیش از بازگشت
Producerها را Detach، ‏Line State را نابود و Line را از نظر منطقی مرده کند.

## ۹. ‏Timerها، ‏Watcherها و Reclamation معوق Timer

Timerها و Watcherهای Component وابسته به Worker هستند. `onQuiesceRequest`، ‏State
مربوط به Rearm/Admission آن‌ها را می‌بندد؛ `onWorkerQuiesce`، ‏Pointer منتشرشده‌ی
Timer یا Watcher همان Component را روی Worker مالک حذف می‌کند.

Quiescence عمومی Loop هر Timer باقی‌مانده را Deactivate و Callback و Userdata آن
را پاک می‌کند. Allocation روی List معوق متعلق به Loop نگه داشته می‌شود، زیرا Line
State ممکن است هنوز Pointer همان Timer را داشته باشد و در Drain بعدی Line به‌دست
Owner آن را حذف کند. `wtimerDelete()` این State را تشخیص می‌دهد و Free نهایی را
دقیقاً یک بار انجام می‌دهد. نابودی Loop فقط Timerهای معوق باقی‌مانده پس از Drain را
Free می‌کند.

One-shot سررسیدشده پیش از اجرای Callback برای Reclamation علامت می‌خورد. اجرای موفق
`wtimerReset()` آن را دوباره زنده می‌کند. اگر Self-rearm رد شود، Callback همه‌ی Slotهای
معتبر Owner را پاک و کار نمایندگی‌شده را تسویه می‌کند و بدون Delete یا Retainکردن
Timer در حال اجرا برمی‌گردد؛ Release مربوط به Pending Event، ‏Reclamation یکتا را
انجام می‌دهد. این با Callback Suppressشده در Quiescence فرق دارد؛ Allocation آن
برای Cleanup روی Worker مالک در دسترس می‌ماند.

در IOCP، ‏Cancellation به معنی Completion نیست. Quiescence ‏Callbackهای User را
Suppress می‌کند، اما رکوردهای عملیات Kernel تا زمانی که Completionهای Cancelشده
Retire شوند زنده می‌مانند. حافظه‌ی WIO فقط پس از Drainشدن آن Referenceها Reclaim
می‌شود.

## ۱۰. ‏Deviceهای خارجی و lwIP

Deviceهای TUN، ‏Raw و Capture، ‏Stop را به عملیات Request و Wait تقسیم می‌کنند.
Phase مربوط به Request، ‏Admission محلی Delivery/Rearm را می‌بندد و بدون Joinکردن
به Threadهای Reader یا Writer Signal می‌دهد. Phase مربوط به Wait، در حالی که Device
و Tunnel State هنوز معتبرند، Rootهای Callback خارجی را Join می‌کند. Stop نهایی پس
از Drainشدن Lineهای Worker، منابع باقی‌مانده‌ی Interface، ‏Writer، ‏Route، ‏DNS و
Platform را آزاد می‌کند.

هر Backend مربوط به TUN در Phase درخواست `deviceReaderSessionEndRequest()` را
فراخوانی می‌کند و `deviceReaderSessionEndWait()` را تا BringDown به تأخیر می‌اندازد.
Stop Pipeها در Linux و Darwin ‏Nonblocking و Close-on-exec هستند؛ `EINTR` دوباره
تلاش می‌شود، Pipe پر یعنی Wake از قبل Arm شده است و Poll محدود Reader مانع می‌شود
شکست سخت Wake، ‏Join را به Wait نامحدود تبدیل کند. هر Generation بازشده‌ی Reader
در Rollback، ‏Restart و Shutdown همان ترتیب Close، ‏Signal، ‏`EndWait`، ‏Join،
Resetکردن Owner مربوط به Pool و Retireکردن Generation را طی می‌کند. Generation
مربوط به Writer پس از Reader ‏Retire می‌شود و `Down` تنها وقتی Publish می‌شود که
همه‌ی مالکیت لازم از بین رفته باشد. `UdpStatelessSocket` نیز Gate مربوط به Async
Session را روی Main Thread می‌بندد، اما WIO خود را فقط از `onWorkerQuiesce` روی
`io_wid` ثبت‌شده می‌بندد.

Delivery مربوط به Device از Gateهای محلی Generation/Session استفاده می‌کند.
Producerای که پیش از Closure ‏Gate وارد شده می‌تواند کامل شود؛ Entrant بعدی رد
می‌شود و مالکیت Retainشده‌ی خود را آزاد می‌کند. Generation قدیمی Reader پیش از
بازشدن Generation تازه در Restart ‏Join می‌شود. Publication مربوط به Writer پیش
از بسته‌شدن Channel آن با Null ‏Exchange می‌شود؛ Generationهای Retireشده تا زمانی
که هیچ Producer نتواند Publication تغییرناپذیر آن‌ها را Retain کند Allocated
می‌مانند.

هر Join ناموفق، Handle بومی و منابعی را که Thread می‌تواند به آن‌ها دسترسی داشته
باشد حفظ می‌کند. نابودکردن آن‌ها زیر Thread احتمالاً زنده هرگز Fallback منظم نیست.

Admission مربوط به Callbackهای lwIP پیش از درخواست Stop از Thread آن Detach می‌شود.
Thread آن پس از Workerهای معمولی و Stop مربوط به Component ‏Join می‌شود و تنها پس
از آن می‌توان Poolهای Pseudo-worker را نابود کرد.

## ۱۱. انتخاب API خاتمه

State را دسته‌بندی کنید، نه سطح Log را:

| وضعیت | اقدام |
| --- | --- |
| پایان موردانتظار Runtime | نتیجه را Commit کنید، مالکیت محلی را آزاد کنید، `requestProgramShutdown(0)` را فراخوانی و Return کنید. |
| شکست منظم Runtime با State ساختاری معتبر | شکست Component را Publish کنید، مالکیت محلی Callback را آزاد کنید، `requestProgramShutdown(code)` را فراخوانی و عادی Unwind کنید. |
| شکست مختص Line | همان Line را با قرارداد Owner آن ببندید؛ بدون نیاز Product آن را سراسری نکنید. |
| نقض Invariant یا State ناامن/خراب | Log کنید و `abortProgramNow(code)` را فراخوانی کنید. |
| شکست Startup | Status مربوط به Startup را از پایین به بالا Return/Record کنید، منابع محلی و Lockها را آزاد کنید و اجازه دهید Owner بالایی Startup یک بار `StartupRollback` را انتخاب کند. |
| شکست Command/Configuration پیش از Controller | State متعلق به Parser را آزاد و Exit Code را مستقیماً Return کنید. |

`requestProgramShutdown()` را هنگام نگه‌داشتن Lock یا Buffer موقتی که Callback فعلی
باید آزاد کند فراخوانی نکنید. Publishشدن درخواست، Callback را Preempt نمی‌کند. پس
از پذیرش درخواست، از Control Flow عادی Return کنید و کار تازه‌ای Arm نکنید.

API مبهم `terminateProgram()` وجود ندارد. Siteهای Runtime از درخواست منظم Typeدار
یا مسیر Fatal مستقل و Lock-free استفاده می‌کنند؛ Siteهای Startup ‏Status را به
Owner خود منتقل می‌کنند.

Stageهای اصلی Startup یک `ww_startup_result_t` برمی‌گردانند. یک Stage هم‌زمان در
سطح بالای Startup می‌تواند `ww_startup_context_t` مربوط به Thread Local را به‌عنوان
Collector پویای Error با Bound مشخص نصب کند و Scopeهای Nested را دور Callbackهای
Tunnel با ABI ثابت تاریخی قرار دهد. Context پیش از اجرای Event Loopهای Worker به
صورت قطعی Restore می‌شود و Callbackهای Asynchronous نباید از آن استفاده کنند.
APIهایی که Result Type مفید دارند همچنان باید Error را صریح Return کنند.

پس از Loadشدن Tunnelهای Importشده، Parse و نصب Configuration و Startup مربوط به
SocketManager، ‏Main Thread صرف‌نظر از اینکه Result همان Stage از قبل Failure بوده
Mailbox مربوط به Signal را مصرف می‌کند. مرز مشترک Startup Failure از عملیات Arbitration
محافظت‌شده با Mask در SignalManager که بالاتر توضیح داده شد استفاده می‌کند. بنابراین
Signal موجود در Mailbox، ‏`Signal` را به‌عنوان Origin تغییرناپذیر حفظ می‌کند و هر دو
علت همچنان `StartupRollback` را انتخاب می‌کنند؛ Signal به‌تعویق‌افتاده پس از گرفتن
Mask بعداً Handle می‌شود و نمی‌تواند `StartupFailure` را با اثر بازگشتی جایگزین کند.
Stageهای بعدی وارد نمی‌شوند.

## ۱۲. اعتبارسنجی

اعتبارسنجی متمرکز باید رفتار تغییرکرده را پوشش دهد:

```bash
ctest --preset linux-unit-release --output-on-failure \
  -R 'shutdown|signal|worker.*quies|wloop_(stop|wakeup)|lifecycle_node_abi|device_lifetime|reader_session|lwip'

# Focused race coverage on supported Linux toolchains
ctest --preset linux-tsan-unit --output-on-failure
```

Fixtureهای مهم موارد زیر را اثبات می‌کنند:

- پذیرش پایدار با Wake ناقص، Handleکردن Wake اشباع‌شده در POSIX، ‏Coalesceشدن
  Requestها، انتخاب Reason اول و Arbitration نهایی Status؛
- بازگشت Callback مربوط به Worker 0 پیش از Coordination؛
- ترتیب Quiesce، ‏Drain، ‏Teardown و Join برای دو Worker؛
- Suppressشدن Batch ‏Callback پس از نخستین درخواست Quiesce؛
- تسویه‌ی دقیق Callback یا Cleanup برای Messageهای Queueشده و Timed؛
- کامل‌شدن Passهای Request مربوط به Component پیش از آغاز هر Pass مربوط به Wait؛
- Drainشدن Source Owner در SocketManager پیش از Hookهای Worker مربوط به Tunnel؛
- Composition واقعی `shutdown_production_sequence` یک Smoke Test چندWorkerه برای
  مالکیت Source در UDP، مالکیت Carrier/Child در Mux، کار Queueشده و خروج پردازه از
  Coordinator است؛ این Test اثبات کامل Wait برای Producer خارجی یا Ledger همه‌ی
  Phaseها نیست؛
- Unitهای متمرکز ReverseClient، ‏Pairهای Connecting و Active را Drain می‌کنند،
  Close از Re-entrant Init و Finish همسایه پیش از Drain را می‌پوشانند و پیش از
  نابودی Timeout Index یک Owner Registry خالی می‌خواهند؛ Reverse TCP Bridge همچنان
  Smoke Test است؛
- Race میان Enter و Close برای Device/Session و میان Join و Reclamation؛
- پذیرش lifecycle ABI v2 و ردشدن Descriptor گمشده یا ناسازگار پیش از Node Getter؛
- هیچ Leaf در کد تولید Phase سراسری Shutdown پردازه را نمی‌خواند.

Preset ‏`linux-tsan-unit`، ‏Unitهای متمرکز هم‌زمانی را همراه Fixtureهای واقعی
Production Sequence و Reverse Teardown می‌سازد. اجرای Native مربوط به Lifetime
کنسول و Testهای Admission در IOCP بر عهده‌ی CI ویندوز است. تکمیل محلی همچنان باید
کوچک‌ترین مجموعه‌ی متمرکزی را اجرا کند که مرز مالکیت تغییرکرده را پوشش می‌دهد.
مسیرهای کامل Production و Unit یک Checkpoint مربوط به Release باقی می‌مانند.
