# بخش ۶: ساخت، آزمون و بازبینی

تغییر یک تونل صرفاً با کامپایل‌شدن تمام نمی‌شود؛ زمانی تمام است که با یک
پیش‌تنظیم (`preset`) سالم و شناخته‌شده ساخته شود، آزمون‌های یکپارچه‌سازی مرتبط را
پشت سر بگذارد و از فهرست بازبینی عبور کند. این بخش روش اعتبارسنجی کار و ارائه‌ی
نتیجه را توضیح می‌دهد.

## ساخت

پیش‌تنظیم `linux` در CMake را ترجیح دهید. یک بار پیکربندی و سپس ساخت را انجام دهید:

```bash
cmake --preset linux
cmake --build --preset linux -j8
```

برای ساخت متمرکز فقط روی هدف (`target`) تونلی که تغییر کرده است ــ که هنگام
تکرار کار بسیار سریع‌تر است ــ از این دستور استفاده کنید:

```bash
cmake --build --preset linux --target TlsClient -j8
```

نام هدف تونل‌ها با نام دایرکتوری آن‌ها یکسان است؛ مانند `TcpConnector`،
`UdpConnector`، ‏`TcpListener`، ‏`TlsClient` و `MuxClient`.

درخت ساخت پیکربندی‌شده در `build/linux/` قرار دارد و فایل اجرایی برای هر پیکربندی
جداگانه تولید می‌شود؛ برای مثال `build/linux/Release/Waterwall` و همچنین مسیرهای
`Debug/` و `RelWithDebInfo/`. در `build/` درخت‌های پیش‌تنظیم دیگری مانند
`linux-gcc-x64`، ‏`linux-clang-x64` و `linux-tsan-unit` نیز وجود دارند. در یک روند
اعتبارسنجی آن‌ها را با هم ترکیب نکنید.

### قواعد ساخت

- دستور `cmake --build build ...` را روی یک درخت دلخواه `build/` اجرا نکنید، مگر
  آنکه مطمئن شده باشید درخت سالمی است که با پیش‌تنظیم ساخته شده و قصد استفاده از
  همان را دارید.
- در یک روند اعتبارسنجی، درخت‌های ساخت `build/`، ‏`build/linux` و
  `build/linux-gcc-x64` را با هم ترکیب نکنید؛ ممکن است در نهایت فایل اجرایی قدیمی
  را آزمایش کنید.
- ساخت هدف با پیش‌تنظیم را به ساخت از درخت ریشه ترجیح دهید.

## قالب‌بندی فایل‌های C و Headerها

روی هر فایل C یا Header که تغییر می‌دهید، فرمان قابل‌حمل `clang-format` را با
فایل `.clang-format` مخزن اجرا کنید:

```bash
clang-format -i --style=file path/to/changed_file.c
clang-format --dry-run -Werror --style=file path/to/changed_file.c
```

هر محیط توسعه باید `clang-format` را به نسخه‌ی نصب‌شده و سازگار با پروژه متصل
کند؛ مستندات مخزن نباید نام یک فایل اجرایی مخصوص توزیعی مشخص را ثابت کنند.
فایل‌های جدید باید کاملاً با قالب پروژه سازگار باشند. بعضی فایل‌های قدیمی هنوز
کاملاً سازگار نیستند؛ پس کد دست‌نخورده را یک‌جا دوباره قالب‌بندی نکنید. اگر اجرای
فرمان روی کل فایل، خط‌های نامرتبط را بازنویسی می‌کند، محدوده‌های تغییرکرده را با
`--lines=<start>:<end>` قالب‌بندی و بررسی کنید. اگر فرمان در دسترس نیست، به‌جای
نادیده‌گرفتن بی‌سروصدای بررسی، دقیقاً گزارش کنید کدام قالب‌بندی یا اعتبارسنجی انجام
نشده است.

### حالت‌های مرجعیت ساخت

مدل مرجعیت Ninja در مخزن، پیمایش بدون Symlink در گراف، بستار دقیقِ دستورهای
`include`/`subninja`، زمان ارزیابی متغیرهای Ninja و ورودی‌های تولیدشده‌ی اعلام‌شده
را اعتبارسنجی می‌کند. هویت زنجیره‌ابزار (`toolchain`) نیز بایت‌های مقصد نهایی
Symlink را دربر می‌گیرد.

با این حال، روند کنونی زنجیره‌ابزار میزبان فقط **تشخیصی** (`diagnostic`) است و
مرجع انتشار نیست: Compiler، برنامه‌های فرعی، Headerها، Libraryها، ‏Pluginها،
Objectهای CRT و Sysroot هنوز همگی از یک Snapshot تغییرناپذیر اجرا نمی‌شوند.
بنابراین `tests/tools/cmake_ci_step.py --mode integrity` با خطای مرز زنجیره‌ابزار
تغییرناپذیر و به‌صورت Fail-closed متوقف می‌شود. تا زمانی که Image یا Snapshot
تغییرناپذیر زنجیره‌ابزار بازبینی نشده است، برای CI عادی از `--mode diagnostic`
استفاده کنید و هیچ گزارش تشخیصی را تضمینی برای Hermeticبودن یا مقاومت در برابر
کاربر متخاصمِ هم‌سطح معرفی نکنید.

## آزمایش

آزمون‌ها با نام‌هایی مانند `waterwall.<case>` در CTest ثبت شده‌اند و چارچوب موجود
در `tests/` آن‌ها را اجرا می‌کند. هر مورد یکپارچه‌سازی در `tests/cases/<case>/`
قرار دارد.

در Linux، آزمون‌های یکپارچه‌سازی قطعی بدون نیاز به دسترسی کاربر Root، درون User
Namespace و Network Namespace خصوصی با جداسازی صرفاً Loopback اجرا می‌شوند
(`tests/run_in_network_namespace.sh`) که مانع از تداخل Portها شده و امکان اجرای
هم‌زمان را فراهم می‌کند. آزمون‌ها در مسیرهای (`lane`) مجزا از طریق
`tests/run_test_lane.sh` سازمان‌دهی شده‌اند:

موارد قطعی نباید از DNS عمومی استفاده کنند یا به آزادبودن پورت در شبکه‌ی میزبان
وابسته باشند. موردی که عمداً به اینترنت زنده نیاز دارد باید در مسیر صریح
`external` قرار بگیرد.

مسیر `privileged` از همان جداسازی شبکه استفاده می‌کند؛ اما چون Wrapper آن از قبل
با `sudo -E` اجرا شده است، در User Namespace فراخواننده باقی می‌ماند و فقط یک
Network Namespace خصوصی می‌سازد. این کار دسترسی به مسیرهای فضای کاری متعلق به
اجراکننده را حفظ می‌کند؛ قرار دادن Root درون یک User Namespace نگاشت‌شده، اختیار
دسترسی آن به فایل‌سیستم میزبان را از بین می‌برد.

- `support`: آزمون‌های سیاست تولید و چارچوب آزمون (۱۳ آزمون) که کاملاً ترتیبی اجرا می‌شوند.
- `functional`: آزمون‌های یکپارچه‌سازی قطعی (۱۴۳ آزمون) که به‌صورت موازی (`min(32, max(4, 4 * CPUs))` کار) اجرا می‌شوند.
- `external`: آزمون‌های یکپارچه‌سازی نیازمند اینترنت زنده‌ی میزبان (مانند Reality در برابر Google) که کاملاً ترتیبی اجرا می‌شوند.
- `speed`: معیارهای توان عملیاتی چندجریانه (۱۶ آزمون) که برای جلوگیری از رقابت، کاملاً ترتیبی (`RUN_SERIAL TRUE`) اجرا می‌شوند.
- `privileged`: آزمون‌های Probe نیازمند دسترسی Root/TUN (۶ آزمون) که زیر `sudo -E` اجرا می‌شوند.
- `all`: اجرای توالی مسیرهای `support`، ‏`functional`، ‏`external` و `speed` (در مجموع ۱۷۳ آزمون).

درخت تولید فقط آزمون‌های یکپارچه‌سازی، Smoke و سیاست کد منبع را دارد. آزمون‌های
واحد بومی (`Native Unit`) در درخت جداگانه‌ی بدون LTO اجرا می‌شوند؛ بنابراین
`ctest --preset linux` فقط آزمون‌های تولید را اجرا می‌کند.

اندازه‌گیری‌های مرجع با ساخت گرم روی یک میزبان ۴ پردازنده‌ای حدود ۵۵ ثانیه برای
مسیر `support`، حدود ۲۲ تا ۲۴ ثانیه برای مسیر قطعی و موازی `functional` (۱۶ کار)،
کمتر از یک ثانیه برای مسیر ترتیبی `external`، ‏۴۶ تا ۴۸ ثانیه برای مسیر ترتیبی
`speed` و ۱۴ تا ۱۵ ثانیه برای مسیر `privileged` است. در نتیجه، توالی کامل تولید
بدون نیاز به مجوز ویژه (مسیر `all`: مجموع ۱۷۳ آزمون `support` + `functional` + `external` + `speed`)
حدود ۲ دقیقه (~۱۲۷ ثانیه) طول می‌کشد. اجرای مسیر `functional` روی میزبان محدود به
یک CPU، چهار کار را به‌کار می‌گیرد و حدود ۷۱ ثانیه طول می‌کشد. این اعداد فقط برای
برنامه‌ریزی هستند و تضمین کارایی روی همه‌ی
سامانه‌ها نیستند. مجموع `all` بررسی‌های سیاست و چارچوب آزمون تولید را نیز دربر
می‌گیرد؛ درخت آزمون‌های واحد بومی جدا باقی می‌ماند. اعتبارسنجی کامل تولید به‌همراه
مسیر Release آزمون‌های واحد بومی، با احتساب مسیر `privileged`، حدود ۳٫۵ دقیقه طول
می‌کشد. بخش Release آزمون‌های واحد بومی در سه اجرای گرم `linux-unit-release`
میانه‌ای حدود ۷۴ ثانیه داشت. این اندازه‌گیری مسیر اضافی Debug را دربر نمی‌گیرد؛ CI
ابری Release و Debug را به‌صورت موازی اجرا می‌کند، بنابراین Debug توان پردازشی
بیشتری مصرف می‌کند اما معمولاً کل زمان آن را به مسیر بحرانی اضافه نمی‌کند. این
اعداد به سخت‌افزار و گرم‌بودن ساخت وابسته‌اند.

این زمان کوتاه‌تر، اعتبارسنجی گسترده را عملی می‌کند. برای تغییرهای مشترک شبکه
یا رفتار تونل، مسیر کامل `functional` را به‌آسانی اجرا کنید و برای تغییرهای
گسترده‌ی تونل یا چارچوب آزمون، توالی عادی یکپارچه‌سازی را اجرا کنید. برای قراردادهای
هسته‌ی مشترک، چرخه‌ی عمر/هم‌زمانی، تغییرهای چندزیرسامانه‌ای یا تغییرهایی که دامنه‌ی
اثرشان مشخص نیست، اعتبارسنجی کامل تولید به‌همراه هر دو پیکربندی آزمون‌های واحد
بومی را اجرا کنید. بررسی متمرکز همچنان برای تغییرهای محدود یا بدون تغییر رفتار
انتخاب مناسب‌تری است.

```bash
# توالی عادی Release تولید بدون نیاز به مجوز ویژه در میان مسیرهای آزمون.
cmake --preset linux
cmake --build --preset linux --config Release --target check_waterwall_tests -j8

# اجرای مسیر support تولید (بررسی‌های سیاست و چارچوب آزمون).
bash tests/run_test_lane.sh support build/linux Release

# اجرای مستقیم و موازی مسیر functional.
bash tests/run_test_lane.sh functional build/linux Release

# اجرای همه‌ی مسیرهای تولید بدون نیاز به مجوز ویژه در قالب یک توالی.
bash tests/run_test_lane.sh all build/linux Release

# مجموعه‌ی کامل آزمون‌های واحد بومی: Release بهینه‌شده و Debug همراه با Assert.
cmake --preset linux-unit-tests
cmake --build --preset linux-unit-release -j8
ctest --preset linux-unit-release --output-on-failure
cmake --build --preset linux-unit-debug -j8
ctest --preset linux-unit-debug --output-on-failure
```

### آزمون‌های واحد بومی

آزمون‌های واحد بومی از یک درخت جداگانه‌ی چندپیکربندی استفاده می‌کنند که IPO/LTO
پیش از ساخته‌شدن هر هدف پروژه در آن غیرفعال می‌شود. Release بهینه‌سازی و `NDEBUG`
را حفظ می‌کند و Debug، Assertها و Guardrailهای قراردادی را فعال می‌کند. Release
تولید همچنان IPO/LTO را فعال دارد؛ بنابراین اعتبارسنجی کامل رفتاری از مسیر تولید
و هر دو پیکربندی آزمون واحد بومی استفاده می‌کند:

```bash
# Release تولید: فایل اجرایی منتشرشونده و مجموعه‌ی کامل آزمون‌های تولید.
cmake --preset linux
cmake --build --preset linux --config Release --target check_waterwall_tests -j8

# آزمون واحد بومی: رفتار بهینه‌شده‌ی Release بدون LTO.
cmake --preset linux-unit-tests
cmake --build --preset linux-unit-release -j8
ctest --preset linux-unit-release --output-on-failure

# آزمون واحد بومی: Assertها و Guardrailهای Debug در همان درخت بدون LTO.
cmake --build --preset linux-unit-debug -j8
ctest --preset linux-unit-debug --output-on-failure
```

برای کار رفتاری متمرکز، ابتدا انتخاب مرتبط `linux-unit-debug` را اجرا کنید؛ Assertها
معمولاً نقض قرارداد مالکیت، چرخه‌ی عمر یا State را نزدیک‌تر به علت آن نشان می‌دهند.
پیش از پایان کار همان پوشش را با `linux-unit-release` تکرار کنید، زیرا بهینه‌سازی و
`NDEBUG` می‌توانند رفتار متفاوتی را آشکار کنند. تغییرهای گسترده یا مشترک هر دو
پیش‌تنظیم کامل را اجرا می‌کنند. Debug جای Release، ‏AddressSanitizer،
UndefinedBehaviorSanitizer یا ThreadSanitizer را نمی‌گیرد. آزمون‌های واحد بومی را
هرگز در درخت تولید نسازید، زیرا کتابخانه‌های آن برای `Waterwall` با LTO ساخته
می‌شوند.

اعتبارسنجی Backendهای رمزنگاری نیز از همین قانون دو درخت پیروی می‌کند. هر پیش‌تنظیم
تولید مانند `linux-sodium-crypto` یک پیش‌تنظیم متناظر برای آزمون واحد بومی مانند
`linux-sodium-crypto-unit` دارد. فایل اجرایی منتشرشونده و آزمون‌های یکپارچه‌سازی را
در درخت تولید بسازید و اجرا کنید و آزمون‌های واحد بومی رمزنگاری را فقط در درخت
متناظرِ آزمون‌های واحدِ بدون LTO بسازید و اجرا کنید. پیش‌تنظیم‌های رمزنگاری تولید عمداً
هدف‌های آزمون واحد بومی را تعریف نمی‌کنند.

مسیر متمرکز هم‌زمانی خاموش‌سازی جداگانه پیکربندی می‌شود:

```bash
cmake --preset linux-tsan-unit
cmake --build --preset linux-tsan-unit -j8
ctest --preset linux-tsan-unit --output-on-failure
```

این مسیر Controller، پذیرش مربوط به پیام Worker و حلقه‌ی رویداد، نشست Reader و
Fixtureهای ترتیب واقعی خاموش‌سازی تولید را زیر ThreadSanitizer پوشش
می‌دهد. این یک مسیر متمرکز هم‌زمانی است و جای مسیر آزمون واحد در Release بدون LTO را
نمی‌گیرد.

سیاست ثبت‌شده‌ی no-LTO مستقیماً Cache مربوط به درخت واحد، فرمان‌های قابل‌دسترسی
کامپایل/پیوند و Artifactهای نماینده از WaterWall، ‏lwIP و TlsClient را بررسی
می‌کند. همین برای گرفتن Regression مربوط به Mixed-LTO کافی است و نیازی به ساختن
یک سامانه‌ی Attestation دوم پیرامون کامپایلر، ابزار ساخت یا Verifier نیست.

CI ابری Linux پیش‌تنظیم‌های کامل `linux-unit-release` و `linux-unit-debug` را در
دو Job مستقل و موازی اجرا می‌کند. در macOS و Windows، ‏CI هدف
`waterwall_platform_unit_tests` را می‌سازد، همان سیاست مستقیم no-LTO را اجرا
می‌کند و آزمون‌های واحد Platform را در Release اجرا می‌کند.

برای اجرای یک مورد با نام ثبت‌شده، از عبارت منظم (`Regex`) دارای Anchor استفاده کنید:

```bash
ctest --preset linux --output-on-failure -R '^waterwall\.tls_roundtrip$'
```

برای اجرای مستقیم یک مورد یکپارچه‌سازی هنگام اشکال‌زدایی، فایل اجرایی، دایرکتوری
مورد و Timeout بر حسب ثانیه را بدهید:

```bash
tests/run_waterwall_case.sh \
  build/linux/Release/Waterwall \
  tests/cases/tls_roundtrip \
  60
```

موردهای Roundtrip زیادی برای الگوبرداری آزمون جدید وجود دارند، از جمله
`encryption_roundtrip`، خانواده‌ی `mux_*_roundtrip`، ‏`http1_*` / `http2_*`،
`packets_stream_bridge_roundtrip` و خانواده‌ی `ping_*_roundtrip`. نزدیک‌ترین مورد
به تونل خود را به‌عنوان مرجع ساختاری انتخاب کنید؛ سپس بررسی کنید که Assertهای آن
واقعاً رفتار تغییرکرده و حالت خرابی موردنظر را پوشش می‌دهند.

:::tip آزمونی بنویسید که با برعکس‌شدن جهت شکست بخورد
ارزشمندترین آزمون برای تغییر در جریان یا Packet آن است که با جابه‌جایی Handler مربوط
به upstream/downstream بشکند. در تونل‌های جفت، مانند Client/Server یا
Encode/Decode، همین یک Assert رایج‌ترین Regression این کدبیس را پیدا می‌کند.
قواعد جهت را در [بخش ۲](./part2-lines-and-callbacks.mdx) و
[بخش ۴](./part4-packet-tunnels.mdx) ببینید.
:::

## انتخاب دامنه‌ی اعتبارسنجی و پوشش Regression

اعتبارسنجی باید مستقیماً به پرسش مربوط به محصول پاسخ دهد و متناسب با ریسک باقی
بماند:

- از کوچک‌ترین بررسی‌ای شروع کنید که تغییر را واقعاً می‌آزماید: بازبینی،
  قالب‌بندی، یک هدف متمرکز، یک آزمون متمرکز موجود یا یک مورد یکپارچه‌سازی مستقیم.
- برای رفتار مشترک شبکه یا تونل و تغییرهایی که چند مورد را دربر می‌گیرند، دامنه را
  تا مسیر `functional` گسترش دهید. برای تغییرهای هسته‌ی مشترک، چرخه‌ی
  عمر/هم‌زمانی، چندزیرسامانه‌ای، حساس به امنیت یا دشوار از نظر تعیین دامنه، همه‌ی
  مسیرهای تولید را همراه با آزمون‌های Native Unit اجرا کنید.
- مستندات، توضیحات کد و تغییرهای مکانیکی و آشکارا بدون تغییر رفتار ممکن است فقط
  به بازبینی، بررسی Link و Diff یا یک بررسی Policy مرتبط نیاز داشته باشند. صرفاً
  به‌دلیل تغییر کد یا در دسترس‌بودن یک مسیر، آن مسیر گسترده را اجرا نکنید.
- رفتار قابل‌مشاهده‌ی جدید، حالت‌های مرزی مهم، قراردادهای تغییرکرده و Bugهای
  قابل‌بازتولید و مستعد بازگشت، معمولاً باید پوشش متمرکز داشته باشند. هرگاه عملی
  است، آزمون Regression باید پیش از اصلاح Fail و پس از آن Pass شود.
- وقتی پوشش موجود دقیقاً همان رفتار را نشان می‌دهد، بازتولید عملی نیست یا تغییر
  هیچ رفتار معناداری برای Assertکردن ندارد، آزمون تازه لازم نیست. به‌جای ساختن
  آزمون یا Harness مصنوعی، دلیل آن را بیان کنید.
- یک بررسی مستقیم می‌تواند یک قاعده‌ی محدود و قطعی را ثابت کند. وقتی هم‌زمانی،
  زمان‌بندی، امنیت یا رفتار غیرقطعی باعث می‌شود یک مشاهده کافی نباشد، از تکرار،
  Sanitizerها، آزمون فشار، تزریق خطا یا آزمون‌های گسترده‌تر استفاده کنید.

شکست اعتبارسنجی یا در دسترس نبودن محیط، مدرکی درباره‌ی همان تلاش اعتبارسنجی است؛
نه نتیجه‌ی Pass و نه اثبات خودکار نادرستی محصول. خطای دقیق را حفظ کنید و میان
مدرک **شکست‌خورده** (`failed`) و **غیرقطعی** (`inconclusive`) تفاوت بگذارید.

## بررسی‌های صرفاً نحوی (`Syntax-only`)

دستور کامپایل را دستی سرهم نکنید. اگر به کامپایل تک‌فایل یا صرفاً نحوی نیاز
دارید، Flagهای **دقیق** همان فایل را از `build/linux/compile_commands.json`
تولیدشده بردارید.

:::warning خطر تداخل `structure.h`
هر تونل Header محلی خود را با نام `include/<Tunnel>/structure.h` دارد. اگر در یک
دستور کامپایل دستی، دایرکتوری `include/` چند تونل را هم‌زمان اضافه کنید، ممکن است
`structure.h` اشتباه بی‌سروصدا انتخاب شود. نتیجه می‌تواند خطاهای گیج‌کننده یا،
بدتر از آن، ساختی باشد که Layout نادرست را پیوند داده است. هر تونل را جداگانه
اعتبارسنجی کنید یا ترتیب اصلی Includeها را از `compile_commands.json` حفظ کنید.
این مهم‌ترین دلیل برای پرهیز از کامپایل دستی است.
:::

خطاهای رایج کامپایل دستی عبارت‌اند از نبود Headerهای وابستگی تولیدشده، ریشه‌ی
اشتباه Include در درخت ساخت و تداخل `structure.h` که بالاتر توضیح داده
شد.

## وقتی خود کامپایلر از کار می‌افتد

مشکلی شناخته‌شده در محیط ساخت وجود دارد که طی آن یک درخت ساخت دستی یا ساخته‌شده
بدون پیش‌تنظیم می‌تواند باعث خطای داخلی کامپایلر در GCC شود؛ برای مثال:

```text
internal compiler error: Bus error
```

این اتفاق اغلب هنگام کامپایل‌شدن فایل‌های **هسته** مانند `ww/libc/wlibc.c` رخ
می‌دهد؛ حتی پیش از آنکه کامپایلر به تونل تغییرکرده‌ی شما برسد.

خطای ICE یا Bus Error نتیجه‌ای **غیرقطعی** است. این خطا اغلب از درخت ساخت
قدیمی/دستی یا کمبود منابع میزبان ناشی می‌شود، اما ممکن است یک نقص کامپایلر نیز
باشد که واحد ترجمه‌ی تغییرکرده آن را آشکار کرده است. این خطا نه نادرستی تونل را
اثبات می‌کند و نه درستی آن را. پیش از تصمیم درباره‌ی آنچه باید اشکال‌زدایی شود،
خطا را با یک پیش‌تنظیم پشتیبانی‌شده و پاک بازتولید کنید و هرگز آن مسیر را
موفق گزارش
نکنید.

### راهبرد جایگزین در صورت مسدودشدن کامپایل

این مراحل را به‌ترتیب انجام دهید:

1. `cmake --preset linux`
2. `cmake --build --preset linux --target <ChangedTargets> -j8`
3. `cmake --build --preset linux -j8`
4. اگر خطا باقی ماند، در صورتی که یک پیش‌تنظیم/زنجیره‌ابزار پشتیبانی‌شده‌ی دیگر همان
   پرسش را پاسخ می‌دهد، آن را نیز امتحان کنید؛ برای مثال پیش‌تنظیم متناظر Clang.
5. خطای دقیق کامپایلر را گزارش کنید و اعتبارسنجی مربوط را **غیرقطعی**
   (`inconclusive`) بنامید.
6. قوی‌ترین اعتبارسنجی باقی‌مانده را ادامه دهید:
   - ساخت‌های هدف‌محور با پیش‌تنظیم؛
   - بررسی صرفاً نحوی با `build/linux/compile_commands.json`؛
   - بازبینی متمرکز کد بر اساس قراردادهای این راهنما.

بررسی‌های صرفاً نحوی و بازبینی، ابزارهای تشخیصی سودمندی هستند؛ اما برای یک تغییر
رفتاری، جای شواهد ازدست‌رفته‌ی پیوند و زمان اجرا را نمی‌گیرند. دقیقاً بیان کنید چه
چیزی اعتبارسنجی‌نشده باقی مانده است.

خلاصه‌ی اولویت‌های ساخت:

- پیش‌تنظیم `linux` را ترجیح دهید؛
- ساخت یک هدف با پیش‌تنظیم را بر ریشه‌ی `build/` ترجیح دهید؛
- `build/linux/compile_commands.json` را به Flagهای حدسی ترجیح دهید؛
- تا وقتی یک ساخت پاک و پشتیبانی‌شده خلافش را مشخص نکرده است، GCC ICE یا Bus
  Error را نتیجه‌ای غیرقطعی بدانید.

## بازبینی بهینه‌سازی اختیاری و شواهد

این بخش زمانی کاربرد دارد که یک گزینه‌ی بهینه‌سازی اختیاری، یا معیارسنج
(`benchmark`)، تجزیه‌گر، ‏Manifest یا سازوکار شواهدی که برای تصمیم‌گیری درباره‌ی آن به کار می‌رود، در دامنه‌ی
کار باشد. این قواعد، بازبینی عادی محصول را محدود نمی‌کنند و تسکی را که صریحاً
اصلاح زیرساخت آزمون یا معیارسنج قابل‌استفاده‌ی مجدد را می‌خواهد نیز محدود
نمی‌کنند. درخواست صریح نگه‌دارنده یا کاربر برای چنین زیرساختی، همان مجوز جداگانه‌ی
لازم برای این دامنه است.

اعتبارسنجی یک کار پشتیبان است، نه محصولی دوم. باید یک پس‌رفت واقع‌بینانه را
پیدا کند یا به پرسش مهندسی ازپیش‌اعلام‌شده پاسخ دهد؛ نه اینکه به‌صورت بازگشتی
بکوشد بی‌نقص‌بودن تک‌تک ابزارهای زنجیره‌ی شواهد را اثبات کند.

### یافته‌ها را بدون پنهان‌کردن دسته‌بندی کنید

در کار بهینه‌سازی/شواهد، این دسته‌ها را از هم جدا کنید:

1. **درستی محصول** — نقص مشخصی در قرارداد، مالکیت، طول عمر، هم‌زمانی، امنیت،
   قابلیت حمل یا رفتار قابل‌مشاهده‌ی کاربر در کدی که منتشر می‌شود.
2. **پوشش مستقیم پس‌رفت** — نبود پوشش واقع‌بینانه برای رفتار تغییرکرده‌ی
   محصول که احتمال پس‌رفت آن وجود دارد.
3. **تصمیم کارایی** — مدرکی که نشان دهد یک گزینه‌ی مشخص محصول در برابر بار کاری
   و معیار پذیرش تثبیت‌شده، آستانه را برآورده می‌کند، از آن بازمی‌ماند یا روی میزبان فعلی
   قابل‌اندازه‌گیری نیست.
4. **کیفیت ابزار پشتیبان** — نقص یا فرصت مقاوم‌سازی در اجراکننده، تجزیه‌گر،
   ‏Manifest، محل اتصال آزمایشی، گردآورنده‌ی Artifact یا ابزار شواهد دیگر.

این دسته‌بندی اولویت را مشخص می‌کند و هرگز دلیلی برای پنهان‌کردن یک یافته‌ی معتبر
نیست. نقص ابزار پشتیبان زمانی تصمیم جاری را متوقف می‌کند که بتواند رفتار مرتبط را
جا بیندازد، نتیجه‌ی موفق/ناموفق کاذب بسازد، سنجه را خراب کند یا به‌شکل دیگری تصمیم
را تغییر دهد. در غیر این صورت، آن را به‌عنوان کار تکمیلی غیربازدارنده گزارش کنید؛
دامنه‌ی بازبینی گزینه‌ی جاری را گسترش ندهید. درخواست بازبینی محصول، مجوز بازطراحی
نامرتبط زیرساخت معیارسنج نیست و پاک‌سازی آن نباید فقط برای موفق‌شدن شواهد،
رفتار محصول را تغییر دهد.

### گزینه را به یک تصمیم نهایی برسانید

پیش از جمع‌آوری داده، بار کاری، سنجه‌ها، آستانه‌ها، تعداد نمونه‌ها و ترتیب‌ها،
نیازمندی‌های میزبان و مرز گزینه‌ها را تثبیت کنید. سپس:

- برای هر گزینه‌ی اختیاری و جداشده، دقیقاً یک نتیجه‌ی نهایی تعیین کنید:
  **نگه‌داشتن** (`keep`)، **برگرداندن/به‌تعویق‌انداختن** (`revert/defer`) یا
  **غیرقطعی روی این میزبان** (`inconclusive on this host`). در حالی که سامانه‌ی
  پذیرش را پیرامون گزینه بزرگ‌تر می‌کنید، آن را برای همیشه در حالت معلق رها
  نکنید.
- پس‌رفت یا افت کاراییِ اندازه‌گیری‌شده، یا نرسیدن به بهبود اعلام‌شده، خط مبنای ساده‌تر را
  انتخاب می‌کند. نتیجه‌ی غیرقطعی نیز به‌طور پیش‌فرض خط مبنای ساده‌تر محصول را
  نگه می‌دارد؛ گزینه را می‌توان تا دسترسی به میزبان معیارسنج بهتر به تعویق
  انداخت.
- میزبانی که نتواند بار کاری تثبیت‌شده را با اطمینان اجرا کند، توان تصمیم‌گیری
  ندارد. این واقعیت را ثبت کنید. پس از دیدن نتایج، بار کاری را تنظیم نکنید، تا
  رسیدن به نتیجه‌ی مطلوب پی‌درپی تلاش نکنید، معیار پذیرش را ضعیف نکنید و برای تحمیل یک
  تصمیم، هویت‌های جایگزین برای چارچوب آزمون نسازید.
- به‌طور پیش‌فرض پس از نخستین تلاش سرتاسری، فقط یک نوبت محدودِ تعمیر جانبیِ
  چارچوب آزمون مجاز است. تعمیر بیشتر به یک تسک زیرساختی جدا، با دامنه و درخواست صریح
  نیاز دارد.
- پس از موفق‌شدن بررسی‌های مستقیم درستی و ثبت تصمیم نهایی، اعتبارسنجی گسترده‌ی
  محصول را یک بار روی مجموعه‌ی نهایی و نگه‌داشته‌شده‌ی تولید اجرا کنید. آن را پس
  از هر بازنگری ابزار شواهد دوباره و دوباره اجرا نکنید.

وقتی تنها محدودیت‌های غیربازدارنده‌ی ابزار شواهد باقی مانده‌اند، آن‌ها را همراه با
نتیجه‌ی نهایی محصول گزارش کنید. مگر آنکه نقصی در محصول به‌طور مستقل بازتولید شود
یا زیرساخت قابل‌استفاده‌ی مجدد صریحاً درخواست شده باشد، برنامه‌ی پیاده‌سازی دیگری
برای محصول نسازید.

### برای اثبات، زنجیره‌ای از اثبات‌های تازه نسازید

مگر آنکه یک مدل تهدید جداگانه برای امنیت، زنجیره‌ی تأمین یا ساخت بازتولیدپذیر
به آن‌ها نیاز داشته باشد، موارد زیر را اضافه یا الزامی نکنید:

- اجرای دوباره‌ی Verifier، خوداعتبارسنجی Validator، چارچوب Mutation برای
  آزمون‌کردن خود آزمون یا Attestation تراکنش پذیرش؛
- Hash فایل اجرایی/ابزار/کد منبع، کپی کد منبع مربوط به Verifier در هر دایرکتوری
  نتیجه، اثبات ancestry پردازه‌ی فرزند، منشأ فایل‌سیستم یا هویت CI Runner؛
- Parser عمومی برای فرمان‌های Shell/CMake که تنها هدفش اثبات تطابق فرمان‌های
  ثبت‌شده با Flagهای ثبت‌شده است؛
- Schemaهای جامع و Fail-closed برای فیلدهای تشخیصی که نمی‌توانند درستیِ در محدوده‌ی کار
  یا تصمیم `keep`/`revert` را تغییر دهند؛ یا
- تنظیم محصول، فیلد پروتکل، شاخه‌ی زمان اجرا، شمارنده، API یا Hook چرخه‌ی عمر که
  فقط برای آسان‌ترکردن احراز اصالت شواهد اختیاری افزوده شده است.

یک بررسی مستقیم و قطعی اغلب برای گزینه‌ی محدود ساخت، مسیر، توازن مالکیت، Timeout
یا سنجه‌ی خروجی کافی است. زمان‌بندی، هم‌زمانی، امنیت و رفتار غیرقطعی ممکن است به
شواهد تکرارشده یا مستقل نیاز داشته باشند؛ این قاعده اعتبارسنجیِ بازگشتیِ خودِ
فرایند اعتبارسنجی را منع می‌کند،
نه آزمون متناسب با ریسک را.

### کد پشتیبان و Artifactها را تابع محصول نگه دارید

- آزمون‌های موجود و Fixtureهای کوچک را ترجیح دهید. اگر کد جدید شواهد به‌طور
  محسوسی از تغییر محصول بزرگ‌تر می‌شود یا یک چارچوب تازه می‌سازد، متوقف شوید؛
  مگر آنکه دامنه‌ی زیرساخت صریحاً مجاز شده باشد.
- محل‌های اتصال آزمایشی و شمارنده‌هایی که فقط برای شواهد اضافه شده‌اند باید در
  ساخت عادی محصول کامپایل نشوند. API تولیدی که فقط برای معیارسنج افزوده می‌شود،
  به توجیه و تأیید جداگانه‌ی محصول نیاز دارد.
- خروجی خام معیارسنج، ‏Manifestهای کپی‌شده، درخت‌های موقت State و Snapshotهای
  تکراری اجراکننده، ‏Artifact تولیدشده‌اند. یک خلاصه‌ی کوتاه از نتایج را در کد منبع
  نگه دارید و بسته‌های حجیم بازتولیدپذیری را بیرون از تاریخچه‌ی عادی قرار دهید، مگر
  آنکه صریحاً درخواست شده باشند.
- اگر اعتماد به سازوکار اثبات اختیاری از اعتماد به بررسی مستقیم دشوارتر شد،
  ساده‌سازی، جایگزینی یا حذف آن را به افزودن Validator دیگر ترجیح دهید. حذف نیز
  تغییر کد است و باید از مرز مجوز تسک پیروی کند.

## قواعد بازبینی کد و فهرست بررسی تونل

این فهرست حداقل موارد است، نه مرز بازبینی. رفتار تغییرکرده و Callerها، ‏Calleeها،
همسایه‌ها و مسیرهای خطای متأثر را از نظر رفتار تعریف‌نشده، خطای کران و اعداد صحیح،
Race، نشت حافظه/منبع، اتمام منابع یا محروم‌سازی از سرویس، مشکلات امنیتی، مدیریت پیکربندی
نامعتبر، سازگاری، قابلیت حمل و نقص‌های ساخت/آزمون بررسی کنید. الگوهای موجود،
آزمون‌های موفق، بررسی‌های سیاست و توضیحات کد مدرک هستند، نه اثبات.

برای هر یافته، Trigger و اثر مشخص گزارش کنید؛ نقص تأییدشده را از پرسش یا بهبود
اختیاری جدا کنید و نقص مهم خارج از دامنه را بدون ویرایش پنهانی گزارش دهید. اگر
یافته‌ی قابل‌اقدامی وجود ندارد، همین را بگویید و به‌جای ساختن ایرادهای سلیقه‌ای،
ریسک باقی‌مانده یا شکاف مهم اعتبارسنجی را نام ببرید.

برای تغییر یک تونل، همه‌ی موارد مرتبط زیر را تأیید کنید:

**چرخه‌ی عمر و جهت**

- `Init` پیش از استفاده‌ی هر Callback، ‏Line State همین تونل را مقداردهی می‌کند.
- Callbackهای upstream فقط با `tunnelNextUpStream*` Forward می‌شوند.
- Callbackهای downstream فقط با `tunnelPrevDownStream*` Forward می‌شوند.
- هیچ Flagی به نام `initialized` اضافه نشده است، مگر آنکه یک قرارداد صریح و
  مستند برای نقش Line یا Callback، وجود State پیش از `Init` عادی را لازم بداند.

**ایمنی Line**

- هر Callback از نوع Re-entrant یا بلافاصله برمی‌گردد، یا با
  `lineCallWithRef()` / `lineRef()` دستی و `lineIsAlive()` از Line محافظت می‌کند.
- وقتی `lineCallWithRef()` مقدار `false` برمی‌گرداند، کد به `line`، ‏Line State یا
  `LinestateDestroy()` دست نمی‌زند.
- فقط **مالک** Line تابع `lineDestroy()` را فراخوانی می‌کند.
- هر مالک Line عادی پس از دریافت `Finish`، تولیدکننده‌ها و Inventoryها را جدا
  می‌کند، State خود را نابود می‌کند و در همه‌ی شاخه‌های خطا، Timeout و تصمیم پایانی
  با `! lineIsAlive(line)` برمی‌گردد.
- مسیر مربوط به Line قرض‌گرفته‌شده فقط State خودش را نابود می‌کند و هرگز
  `lineDestroy()` را فراخوانی نمی‌کند.
- هرگز `requestProgramShutdown()` را جایگزین بستن یک Line تحت مالکیت نکنید.

**Finish**

- `Finish` پیش از Propagateکردن Close واقعی، State محلی را نابود می‌کند.
- Teardown از تونل میانی ابتدا upstream و سپس downstream را Finish می‌کند و بعد
  برمی‌گردد.
- هیچ‌یک از `Payload`، ‏`Est`، ‏`Pause`، ‏`Resume` یا `Finish` به‌سمتی که `Finish`
  را فرستاده است بازتاب داده نمی‌شود.
- اگر هنگام `Finish` ‏Byteهای پایانی پروتکل فرستاده می‌شوند، پیش از ارسال سمت
  فرستنده Finish‌شده علامت می‌خورد؛ ارسال Re-entrant در حالی که Reference خط نگه
  داشته شده است انجام می‌شود و Handler پس از آزادسازی Reference (unref)، بدون
  دست‌زدن به State نابودشده برمی‌گردد.

**Backpressure**

- پس از دریافت `Pause`، تولیدکننده تا هنگام `Resume` هیچ Payload تازه‌ای به‌سمت
  آن مصرف‌کننده آغاز نمی‌کند.
- هر تحمل عمدی برای داده‌ی پیش از `Pause` باید محدود، حافظ ترتیب FIFO، ثبت‌شده و
  قابل‌ردیابی و دارای مسیر روشن Resume یا Overflow/Close باشد. تونل‌های میانی شفاف
  صرفاً به این دلیل که Adapterها صف محدود دارند، Buffering تازه‌ای ابداع نمی‌کنند.

**بافرها و Padding**

- هر Prepend در محدوده‌ی `required_padding_left` اعلام‌شده‌ی تونل قرار دارد.
- فقط با ظرفیت کافی سمت چپ از `sbufShiftLeft()` استفاده می‌شود.
- بافرها دقیقاً در مسیرهایی Recycle می‌شوند که هنوز مالکشان هستند و هیچ بافری
  Leak نمی‌شود.

**معنای Packet، در صورت ارتباط**

- Packet Lineها در Runtime عادی زنده نگه داشته می‌شوند.
- State مربوط به Packet Line، ‏State محلی و مشترک Worker در نظر گرفته می‌شود.
- منبع Init مربوط به Packet Line، یعنی Node Manager یا `onStart` دستی، بررسی شده
  است.
- هر Handler مربوط به `Finish` در Packet Line برای همان نقش و جهت دقیق
  دسته‌بندی شده است: Anchor مرگبار، Forward شفاف در همان جهت یا جذب پایانی و
  مستندشده. هیچ‌کدام از این دسته‌ها Packet Line را نابود نمی‌کند.

**اعتبارسنجی**

- Testها جهت موردنظر Callback را واقعاً پوشش می‌دهند.
- اعتبارسنجی از Metadata مربوط به Build با Preset استفاده کرده است، نه Flagهای
  حدسی Compiler.
- همه‌ی فایل‌های C/Header تغییرکرده با `clang-format` قالب‌بندی شده‌اند؛ یا در
  صورت نبودن ابزار، این کمبود صریحاً گزارش شده است.
- هرجا پوشش Regression از رفتار به‌شکل معناداری محافظت می‌کند، افزوده شده است؛
  وگرنه دلیل کافی‌بودن پوشش موجود یا اعتبارسنجی بدون آزمون بیان شده است.
- دامنه‌ی اعتبارسنجی متناسب است: برای تغییر محدود متمرکز و برای کار مشترک،
  هم‌زمان، حساس به امنیت یا دشوار از نظر تعیین دامنه، گسترده/کامل.

## فهرست جامع خطاهای رایج

این راهنما برای پیشگیری از خطاهای زیر نوشته شده است:

- دسترسی به Line State تونل پس از `LinestateDestroy()` یا خواندن فیلدهای Zero‌شده.
- افزودن Flagهای `initialized` برای جبران Control Flow ناامن.
- دست‌زدن به Pointer نوع `line_t*` پس از Callback میان‌تونلی، بدون محافظت.
- فراخوانی `tunnelNext*` یا `tunnelPrev*` در جهت اشتباه.
- Reflection مربوط به `Pause`/`Resume`/`Finish` به‌سمتی که Finish شده است.
- تولید `Est`، ‏`Pause`، ‏`Resume` یا `Finish` در زمان نادرست.
- زنده نگه‌داشتن Line در طول `Finish` بدون `lineRef()`.
- فراموش‌کردن اینکه `lineDestroy()` انتظار دارد State تونل‌ها Zero شده باشد، مگر
  آنکه Reference Count همچنان مثبت باشد.
- Leakشدن بافر وقتی Callback، ‏Line را از بین می‌برد.
- استفاده‌ی نادرست از `sbufShiftLeft()` یا نادیده‌گرفتن `required_padding_left`.
- رفتاری که فقط در یک چیدمان زنجیره کار می‌کند و قابلیت ترکیب عمومی را می‌شکند.
- درنظرگرفتن Packet Line State به‌عنوان State مختص اتصال، یا نابودکردن Packet Line
  هنگام Runtime.
- مقداردهی Callbackها یا دسترسی به State تونل پیش از بررسی نتیجه‌ی Nullable از
  `tunnelCreate()`، ‏`adapterCreate()` یا `packettunnelCreate()`.
- Indexکردن Arrayهای تحت مالکیت Worker با `getWID()` خام، به‌جای استفاده از زمینه‌ی
  Line، ‏Worker، ‏Loop یا Event Worker بررسی‌شده.
- درنظرگرفتن یک پیاده‌سازی موجود به‌عنوان اثبات درستی، به‌جای بررسی قرارداد و
  Callerهای آن.
- ساختن دستی دستور Compile در حالی که Metadata مربوط به Build با Preset وجود
  دارد.
- گزارش Crash مربوط به Compiler یا محیط دردسترس‌نبوده به‌عنوان اعتبارسنجی موفق.

## خروجی مورد انتظار از Coding Agent

پاسخ را با درخواست هماهنگ کنید و نتیجه را در ابتدا بیاورید. با این حال، در یک
تغییر یا بازبینی کامل باید بتوان این واقعیت‌ها را به‌آسانی بررسی کرد:

1. **نتیجه** — چه چیزی تغییر کرده است، یا یافته‌های تأییدشده به‌ترتیب شدت.
2. **شواهد درستی** — رفتار مشخص، Callerها و قراردادهای مرتبط چرخه‌ی عمر، ‏Line،
   جهت، بافر، Packet، ‏Worker یا Shutdown.
3. **اعتبارسنجی** — فرمان‌هایی که واقعاً اجرا شده‌اند، نتیجه‌ی آن‌ها و هر بررسی
   شکست‌خورده یا غیرقطعی. القا نکنید مسیری که اجرا نشده Pass شده است.
4. **ریسک باقی‌مانده** — شکاف‌ها، فرض‌ها یا کار تکمیلی مهم.

تحلیل نامرتبط تونل را به نتیجه‌ی یک تسک مستندات یا ابزار تحمیل نکنید. در مقابل،
تغییر تونلی که نتواند جهت Callback و نقش دقیق Line خود را مشخص کند آماده نیست.
وقتی موضوع مهمی روشن نیست، کد منبع، آزمون‌ها، Callerها و مستندات را بررسی کنید و
اگر مخزن پاسخ را مشخص نمی‌کند، پرسشی متمرکز از Maintainer بپرسید؛ الگوی موجود را
اثبات ندانید و برای یک راهکار موردی، مفهوم تازه‌ای برای چرخه‌ی عمر ابداع نکنید.
