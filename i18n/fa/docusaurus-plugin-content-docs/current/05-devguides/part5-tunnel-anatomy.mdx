# بخش ۵: ساختار یک تونل و روند کار

این بخش قراردادهای بخش‌های ۱ تا ۴ را به فایل‌هایی مرتبط می‌کند که در عمل ویرایش
می‌کنید. وقتی بدانید هر فایل چه مسئولیتی دارد، افزودن یا اصلاح یک تونل به کاری
قاعده‌مند تبدیل می‌شود: کوچک‌ترین اصلاح کاملِ علت ریشه‌ای را در جای درست انجام
دهید و یکپارچگی چرخه‌ی عمر را حفظ کنید.

## چیدمان دایرکتوری

بیشتر تونل‌ها از ساختار زیر پیروی می‌کنند. این چیدمان واقعی `TcpListener`،
`TlsClient`، ‏`MuxClient` و `template` است:

```text
tunnels/MyTunnel/
  CMakeLists.txt
  description.md
  include/MyTunnel/
    interface.h          # API عمومی WW_EXPORT و اعلان همهٔ Callbackها
    structure.h          # Structهای tstate/lstate، Enumهای اندازه و توابع کمکی
  instance/
    create.c             # tunnelCreate()، تعیین Callbackها، Parse و اعتبارسنجی تنظیمات
    node.c               # فرادادهٔ Node: نوع، Flagها، گروه لایه، Padding و createHandle
    chain.c              # قلاب onChain (معمولاً کار را به پیش‌فرض می‌سپارد)
    index.c              # قلاب onIndex (معمولاً کار را به پیش‌فرض می‌سپارد)
    prepair.c            # قلاب onPrepare
    start.c              # قلاب onStart
    stop.c               # قلاب‌های Quiesce، Drain و Stop در lifecycle-v2
    destroy.c            # قلاب onDestroy: آزادسازی State و سپس tunnelDestroy()
    api.c                # ورودی API زمان اجرا (tunnelApi)
  common/
    helpers.c            # توابع کمکی مشترک پروتکل/ماشین حالت
    line_state.c         # مقداردهی و نابودی State مختص Line
  upstream/
    init.c  est.c  payload.c  pause.c  resume.c  fin.c
  downstream/
    init.c  est.c  payload.c  pause.c  resume.c  fin.c
```

:::note چیدمان واقعی در مقایسه با خلاصه‌ی قدیمی
دو نکته در عمل مهم است: همه‌ی تونل‌ها فایل `instance/api.c` را دارند و نام فایل
قلاب آماده‌سازی به‌شکل **`prepair.c`** نوشته می‌شود؛ نام تابع نیز
`...OnPrepair` است. فایل‌های پایان در upstream/downstream نیز `fin.c` هستند، نه
`finish.c`.
:::

قرارگرفتن هر ترکیب `{direction}/{event}` در فایلی جدا باعث می‌شود هر Callback
کوچک بماند. منطق مشترک پروتکل و ماشین حالت در `common/helpers.c` قرار می‌گیرد تا
فایل‌های Callback خوانا بمانند. این قاعده را رعایت کنید؛ بازبین‌ها انتظار همین
ساختار را دارند.

## مسئولیت هر فایل

| فایل | مسئولیت |
| --- | --- |
| `instance/node.c` | `node_t` توصیف‌کننده‌ی نوع تونل را برمی‌گرداند: `type`، ‏`version`، ‏`createHandle`، ‏`flags`، ‏`required_padding_left`، ‏`layer_group` و محدودیت لایه‌ی همسایه‌ها. |
| `instance/create.c` | `tunnelCreate(node, sizeof(tstate), sizeof(lstate))` را فراخوانی می‌کند، دوازده Callback جریان و قلاب‌های چرخه‌ی عمر را تنظیم می‌کند، تنظیمات JSON را تجزیه و اعتبارسنجی می‌کند، منابع هر Worker را تخصیص می‌دهد و در هر مسیر شکست پاک‌سازی می‌کند. |
| `instance/chain.c` / `index.c` | قلاب‌های `onChain` / `onIndex`. بیشتر تونل‌ها پیش‌فرض‌های چارچوب را نگه می‌دارند. توپولوژی داخلی ایستایی که پیش از حل معلوم است در `onChain` تعریف می‌شود. تونلی که توپولوژی خصوصی‌اش به لایه‌های حل‌شده‌ی مجاور بستگی دارد، می‌تواند `onSolvedTopology` اختیاری را نیز در `create.c` تنظیم کند. این قلاب تصویر لحظه‌ایِ حل‌شده‌ی فعلی را دریافت می‌کند که لزوماً نهایی نیست. ممکن است چند بار فراخوانی شود و فقط و فقط هنگامی `true` برمی‌گرداند که توپولوژی را تغییر داده باشد؛ در این صورت تصویر لحظه‌ای دیگر معتبر نیست و مدیر پیش از فراخوانی قلابی دیگر دوباره مسئله را حل می‌کند. وقتی یک گذر کامل هیچ تغییری گزارش نکند، `onIndex` یک بار روی توپولوژی تغییرناپذیر اجرا می‌شود و می‌تواند لایه‌های نهاییِ حل‌شده را مصرف کند. |
| `instance/prepair.c` / `start.c` / `stop.c` | قلاب‌های `onPrepare` / `onStart` و قلاب‌های خاموش‌سازی lifecycle-v2. راه‌اندازی اولیه را در `onStart` انجام دهید؛ پذیرش را در `onQuiesceRequest` ببندید؛ کارهای وابسته به Worker را در `onWorkerQuiesce` جدا کنید؛ در `onQuiesceWait` منتظر تولیدکننده‌های خارجی بمانید؛ Lineهای تحت مالکیت را در `onWorkerStop` تخلیه کنید؛ و منابع مشترک باقی‌مانده را در `onStop` آزاد کنید. |
| `instance/destroy.c` | قلاب `onDestroy`: تنظیمات، Contextهای SSL، ‏Poolها و آرایه‌های Thread-local را آزاد می‌کند و سپس `tunnelDestroy(t)` را فرا می‌خواند. |
| `instance/api.c` | ورودی زمان اجرای `tunnelApi`. یک پیام `sbuf_t` دریافت می‌کند، باید آن را بازیافت کند و یک `api_result_t` برگرداند. |
| `common/line_state.c` | `LinestateInitialize` که از `Init` فراخوانی می‌شود و `LinestateDestroy` که ناحیه‌ی هم‌تراز وضعیت Line را صفر می‌کند. |
| `common/helpers.c` | منطق مشترک تجزیه و قاب‌بندی پروتکل و توابع کمکی Close/Finish که فایل‌های Callback به کار می‌برند. |
| `upstream/*.c`، `downstream/*.c` | هر فایل یک Callback جریان را در بر دارد. آن‌ها را کوچک نگه دارید و منطق را به `helpers.c` بسپارید. |
| `include/MyTunnel/structure.h` | تعریف `mytunnel_tstate_t`، ‏`mytunnel_lstate_t`، ‏Enumهای اندازه و توابع کمکی Inline کوچک. |
| `include/MyTunnel/interface.h` | Prototypeهای Exportشده‌ی ساخت/نابودی/API با `WW_EXPORT` و Prototype همه‌ی Callbackها. |

### قابلیت‌های تایپ‌شدهٔ داخلی در برابر پیام‌های runtime

برای capability تایپ‌شده‌ای که مستقیماً میان tunnelهای سازگار و حاضر در یک chain
ردوبدل می‌شود، از `include/<Tunnel>/interface.h` استفاده کنید. برای نمونه،
`UdpListener` یک provider مربوط به endpoint پویای UDP را به‌شکل API مبتنی بر
value-handle عرضه می‌کند: فراخواننده endpoint را روی Worker مالکِ اعتبارسنجی‌شده
باز، فعال، query و close می‌کند. Capability باید مالکیت، وابستگی به Worker، رفتار
handle قدیمی و مسیر callback را تعریف کند و نباید یک `line_t *` قابل‌استفاده از
مالک دیگر را در معرض قرار دهد.

چنین capability محلی را به `instance/api.c` تبدیل نکنید. آن فایل ورودی پیام
runtime خارجی است: یک `sbuf_t` می‌گیرد، آن را بازیافت می‌کند و `api_result_t`
برمی‌گرداند؛ بنابراین قرارداد متفاوتی برای admission، serialization و lifecycle
دارد. Capability تایپ‌شدهٔ داخلی همچنان فراخوانی عادی C است و باید زنجیرهٔ معمول
callbackهای tunnel را حفظ کند.

### مالکیت metadata در address context

`address_context_t.optional_flags.detected_protocols` دو دستهٔ منطقی metadata
اختیاری دارد. Bitهای متعلق به Router/sniffer، protocolهای application
مشاهده‌شده را ثبت می‌کنند؛ Bitهای کنترل مسیر یک دستور داخلیِ یک‌بارمصرف، مانند
endpoint مذاکره‌شدهٔ SOCKS UDP، را حمل می‌کنند. Router هنگام آغاز پنجرهٔ sniffing
جدید باید `addresscontextClearDetectedProtocols()` را صدا بزند تا فقط Bitهای
protocol مشاهده‌شده پاک شوند. `addresscontextClearOptionalFlags()` برای reset کامل
زمانی است که caller واقعاً context را جایگزین می‌کند. Adapter خروجیِ تعیین‌شده
metadata کنترل مسیر را دقیقاً یک‌بار مصرف و پس از setup پاک می‌کند؛ ruleها هرگز
نباید این Bitها را protocol مشاهده‌شده بدانند.

تحت lifecycle-v2، پیام‌های Worker، ‏Timerها، ‏Callbackهای WIO و درخواست‌های
ناهمگام DNS متعلق به چارچوب پیش از نابودی Component تسویه می‌شوند؛ بنابراین این
Contextها می‌توانند مستقیماً `tunnel_t *` را حمل کنند، مشروط به اینکه Callback
مربوطه Worker مالکِ صریح خود را نیز اعتبارسنجی کند و همان را به‌کار بگیرد. این یک
قانون عمومی برای طول عمر نیست: ریشه‌ی
Callback خارج از چرخه‌ی عمر Worker، مانند Thread خواننده‌ی Device، باید پیش از
بازپس‌گیری وضعیت تونل یا Device، پذیرش محلی را ببندد و با سازوکاری مختص مالک مانند
`quiescence_gate_t` منتظر پایان عملیات فعال بماند.

## ‏`node.c`: معرفی Node

تونل در `node.c` خود را به زمان اجرا معرفی می‌کند. نمونه‌ی زیر متعلق به
`TcpListener` است و الگوی مناسبی برای یک Adapter به شمار می‌رود:

```c
node_t nodeTcpListenerGet(void)
{
    const char *type_name = "TcpListener";
    node_t node = {
        .type                  = stringDuplicate(type_name),
        .hash_type             = calcHashBytes(type_name, stringLength(type_name)),
        .version               = 0001,
        .createHandle          = tcplistenerTunnelCreate,
        .flags                 = kNodeFlagChainHead,
        .required_padding_left = 0,
        .layer_group           = kNodeLayer4,
        .layer_group_next_node = kNodeLayerAnything,
        .layer_group_prev_node = kNodeLayerAnything,
        .can_have_next         = true,
        .can_have_prev         = true,
    };
    return node;
}
```

فیلدهایی که بیشتر تنظیم می‌کنید، همگی در `ww/objects/node.h` تعریف شده‌اند:

| فیلد | مفهوم |
| --- | --- |
| `type` / `hash_type` | رشته‌ی مورد استفاده در `"type"` فایل JSON و Hash ازپیش‌محاسبه‌شده‌ی آن. |
| `createHandle` | تابع `TunnelCreateHandle` که Instance را می‌سازد. |
| `flags` | یک یا چند `node_flags`: ‏`kNodeFlagChainHead`، ‏`kNodeFlagChainEnd`، ‏`kNodeFlagNoChain`، ‏`kNodeFlagSingleton`. |
| `required_padding_left` | ظرفیت Padding سمت چپ که تونل اجازه دارد داده را در آن Prepend کند؛ [بخش ۳](./part3-buffers-and-padding.mdx) را ببینید. |
| `layer_group` | دسته‌ی لایه‌ای که این Node روی آن کار می‌کند: `kNodeLayer3` (Packet)، ‏`kNodeLayer4` (Stream)، ‏`kNodeLayerAnything` (پشتیبانی از هر دو) یا `kNodeLayerNone`. توجه: `kNodeLayerSameAsNext`، ‏`kNodeLayerSameAsPrev`، ‏`kNodeLayerOppositeNext` و `kNodeLayerOppositePrev` برای `layer_group` ممنوع‌اند و فقط در `layer_group_next_node` / `layer_group_prev_node` مجازند. |
| `layer_group_next_node` / `layer_group_prev_node` | دسته‌ی لایه‌ی لازم برای همسایه‌ی بعدی/قبلی (`kNodeLayer3`، ‏`kNodeLayer4`، ‏`kNodeLayerAnything`، ‏`kNodeLayerSameAsNext`، ‏`kNodeLayerSameAsPrev`، ‏`kNodeLayerOppositeNext`، ‏`kNodeLayerOppositePrev` یا `kNodeLayerNone`). توجه: Flagهای Opposite باید با یک دسته‌ی لایه‌ی پایه ترکیب شوند، مانند `kNodeLayerAnything | kNodeLayerOppositePrev`، و نمی‌توانند به‌تنهایی ظاهر شوند. |
| `can_have_next` / `can_have_prev` | مجاز بودن همسایه در هر سمت (`true`/`false`). |

### گروه‌های لایه و اعتبارسنجی دقیق توپولوژی

در زمان راه‌اندازی زنجیره، `NodeManager` از طریق `validateTunnelChains` و حل‌گرِ
کران‌دار و یکنواخت قیدهای لایه (`nodeLayerSolveChain`)، قابلیت‌های Node و قواعد لایه
را با سخت‌گیری اعمال می‌کند:

- **قیدهای قابلیت:** اگر Node مقدار `.can_have_next = false` (یا
  `.can_have_prev = false`) را مشخص کند، وجود همسایه در آن سمت بی‌درنگ راه‌اندازی
  را شکست می‌دهد. Nodeهای خارج از زنجیره که با `kNodeFlagNoChain` علامت خورده‌اند
  نباید همسایه‌ی مجاور داشته باشند.
- **اعتبارسنجی شکل فراداده:** مقدار `layer_group` باید مشخص و مجاز باشد:
  `kNodeLayerNone`، ‏`kNodeLayer3`، ‏`kNodeLayer4` یا `kNodeLayerAnything`. Flagهای
  نسبی رو‌به‌جلو (`kNodeLayerSameAsNext`، ‏`kNodeLayerOppositeNext`) فقط در
  `layer_group_prev_node` و Flagهای نسبی رو‌به‌عقب (`kNodeLayerSameAsPrev`،
  ‏`kNodeLayerOppositePrev`) فقط در `layer_group_next_node` مجازند. Flagهای
  Opposite باید همیشه یک دسته‌ی لایه‌ی پایه را نیز داشته باشند، برای مثال
  `kNodeLayerAnything | kNodeLayerOppositePrev`.
- **انتشار قید در دامنه‌ی یال‌ها:** زمان اجرا گراف جهت‌داری از یال‌ها می‌سازد که
  اتصال Callback میان تونل‌های مجاور را نمایش می‌دهد. دامنه‌ی هر یال (`{L3}`،
  ‏`{L4}` یا `{L3, L4}`) با توجه به نیازهای لایه‌ی Nodeهای مشارکت‌کننده و همسایه‌ها
  مقدار اولیه می‌گیرد و رابطه‌های `SameAs` و `Opposite` به‌شکل یکنوا تا رسیدن به
  نقطه‌ی ثابت منتشر می‌شوند. اگر دامنه‌ی یالی به `{}` برسد، راه‌اندازی فوراً و با
  پیام روشنی که هر دو Node و سمت‌های آن‌ها را مشخص می‌کند شکست می‌خورد.
- **`SameAs` شرطی در برابر `Opposite` سخت‌گیرانه:** قیدهای نسبی `SameAs`
  (`kNodeLayerSameAsPrev`، ‏`kNodeLayerSameAsNext`) شرطی‌اند: اگر سمت مرجع وجود
  نداشته باشد، رابطه‌ی برابری افزوده نمی‌شود و Flagهای جای‌گذاری Node
  (`kNodeFlagChainHead`، ‏`kNodeFlagChainEnd`، ‏`kNodeFlagNoChain`) تعیین می‌کنند
  که قرارگرفتن در مرز مجاز است یا نه. در مقابل، قیدهای `Opposite`
  (`kNodeLayerOppositePrev`، ‏`kNodeLayerOppositeNext`) سخت‌گیرانه‌اند و همیشه
  حضور هر دو سمت مشارکت‌کننده را لازم دارند.
- **رابطه‌های بین‌تونلیِ نگه‌داری‌شده در State:** برای Nodeهایی که مقصد Callback
  آن‌ها هنگام اجرا به‌صورت پویا تعیین می‌شود، مانند تونل‌های جفت‌شده‌ی `Bridge`،
  تونل‌ها رابطه‌های منطقی لایه را مستقیماً با
  `tunnelchainRegisterLayerRelation()` روی زنجیره ثبت می‌کنند. رابطه‌های ثبت‌شده
  در زمان اجرای حل‌گر دامنه‌ی یال‌های مشارکت‌کننده را به هم وابسته می‌کنند؛ برای
  مثال یال prev در Bridge A را با یال prev در Bridge B و یال next در Bridge A را
  با یال next در Bridge B برابر می‌گیرند. این رابطه‌ها پس از ترکیب زنجیره‌ها با
  `tunnelchainCombine()` نیز باقی می‌مانند.
- **Bridgeهای ثابت و نسبی:** Bridgeهایی که سمت ثابت دارند، به‌جای ادعای
  `kNodeLayerAnything` نیاز لایه‌ی مشخصی را روی یال‌های مجاورشان اعلام می‌کنند.
  `ConnectionToPackets` در سمت `prev` لایه‌ی L4 و در سمت `next` لایه‌ی L3 است؛
  `PacketsToConnection` در `prev` لایه‌ی L3 و در `next` لایه‌ی L4 است؛
  `StreamToPackets` نیز در `prev` لایه‌ی L4 و در `next` لایه‌ی L3 است. Bridgeهای
  پویای دوطرفه مانند `WireGuardDevice` رابطه‌های `Opposite` اعلام می‌کنند تا بدون
  فروریختن زودهنگام زیرزنجیره‌های میانیِ هنوز حل‌نشده، دامنه‌ی یال‌های مخالف را به
  هم وابسته کنند.
- **تشخیص و راه‌اندازی زنجیره‌ی Packet:** زنجیره فقط وقتی برای Workerها Packet
  Line تخصیص می‌دهد و `contains_packet_node = true` را تنظیم می‌کند که دست‌کم یک
  یال به `{L3}` محدود شده باشد، نیاز یک Node یا یال به `L3` ثابت شده باشد، یا رابطه‌ی
  `Opposite` وجود داشته باشد. پیام‌های `Init` برای Packet Lineهای پایدار فقط وقتی
  در زمان اجرا در صف قرار می‌گیرند که یال بعدیِ سر زنجیره به `{L3}` حل شده باشد.
- **معنای شکست:** هر شکست در اعتبارسنجی یا حل، پیام خطای بحرانی (`LOGF`) ثبت
  می‌کند و با `startupFailureRecord(1)` شکست راه‌اندازی را ثبت می‌کند؛ در نتیجه
  WaterWall پیکربندی را رد و بازگردانی تمیز راه‌اندازی را اجرا می‌کند.

### Flagهای Node

| Flag | مفهوم |
| --- | --- |
| `kNodeFlagChainHead` | می‌تواند زنجیره را آغاز کند؛ Ingress Adapter. |
| `kNodeFlagChainEnd` | می‌تواند زنجیره را پایان دهد؛ Egress Adapter. |
| `kNodeFlagNoChain` | بدون حضور در زنجیره کار می‌کند؛ مانند Node مربوط به Database/User-auth. |
| `kNodeFlagSingleton` | در کل فایل پیکربندی فقط یک Instance از آن مجاز است. |

### ABI v3 نودهای خارجی

ساختارهای `tunnel_t`، ‏`node_t` و `line_t` و امضاهای عمومی Line Task بخشی از ABI
Nodeهای خارجی‌اند. چهار `lineSchedule*Task*()` اکنون
`line_task_submit_result_e` برمی‌گردانند و `LineTaskCancelFn` می‌گیرند؛ Library ‏v2
نباید Symbolهای C هم‌نام را با prototype قدیمی فراخوانی کند.

Node پویا باید Symbol تاریخی `waterwallNodeLifecycleAbiVersion()` را Export و
`WW_EXTERNAL_NODE_ABI_VERSION`، فعلاً `3`، را برگرداند. نام قدیمی
`WW_EXTERNAL_NODE_LIFECYCLE_ABI_VERSION` alias سازگاری Source برای همین gate کامل
است. جدول lifecycle همچنان معنای v2 دارد و ABI v3 شکست Line Task را اضافه می‌کند.
Loader پیش از Getter، Library گمشده، v2 یا ناسازگار را رد می‌کند؛ Node خارجی باید
با Headerهای v3 دوباره Build شود.

## ‏`create.c`: ساخت Instance

`create.c` تنها جایی است که تونل در آن تخصیص می‌یابد. الگوی برگرفته از
`TlsClient`:

1. اجرای `tunnel_t *t = tunnelCreate(node, sizeof(tstate), sizeof(lstate));`
2. بلافاصله `t` را بررسی کنید و اگر ساخت شکست خورده بود `NULL` برگردانید.
3. هر دوازده Callback جریان و قلاب‌های چرخه‌ی عمر را تنظیم کنید.
4. تک‌تک تنظیمات را از `node->node_settings_json` بخوانید و اعتبارسنجی کنید.
5. منابع هر Worker را تخصیص دهید، برای مثال یک Context ‏SSL به‌ازای هر Worker.
6. **در صورت هر خطای بعدی، پاک‌سازی و خروج**: State ناقص و تونل را نابود و `NULL`
   برگردانید.

`tunnelCreate()`، ‏`adapterCreate()` و `packettunnelCreate()` طبق قرارداد ممکن است
`NULL` برگردانند. اندازه‌ی نامعتبر یا سرریزکرده‌ی State و شکست تخصیص حافظه از علت‌های
آن هستند. پیش از بررسی نتیجه، هرگز Callbackی تنظیم نکنید و `tunnelGetState()` را
فرا نخوانید.

نظم پاک‌سازی واقعی و ارزشمند است. شکل خلاصه‌شده‌ی آن چنین است:

```c
tunnel_t *tlsclientTunnelCreate(node_t *node)
{
    tunnel_t *t = tunnelCreate(node, sizeof(tlsclient_tstate_t), sizeof(tlsclient_lstate_t));
    if (! t)
    {
        return NULL;
    }

    configureTunnelCallbacks(t);

    tlsclient_tstate_t *ts       = tunnelGetState(t);
    const cJSON        *settings = node->node_settings_json;

    if (! getandvalidateSniSetting(ts, settings))
    {
        goto fail;
    }
    // ... تنظیمات اعتبارسنجی‌شدهٔ بیشتر ...

    if (! createSslContextPool(&ts->threadlocal_ssl_contexts, /* ... */))
    {
        goto fail;
    }

    return t;

fail:
    tlsclientTunnelstateDestroy(ts);
    tunnelDestroy(t);
    return NULL;
}
```

### مراحل خاموش‌سازی در lifecycle-v2

مالکیت چرخه‌ی عمر صریح و دارای Context است. خاموش‌سازی پردازه این مرحله‌ها را برای
هر تونل در همه‌ی زنجیره‌های بارگذاری‌شده اجرا می‌کند. NodeManager درون هر زنجیره
از ترتیب ذخیره‌سازی استفاده می‌کند و تضمینی نیست این ترتیب Source-to-tail باشد:

1. `onQuiesceRequest` روی Main Thread اجرا می‌شود، پذیرش محلی را می‌بندد،
   درخواست توقف Producerها را صادر می‌کند و نباید منتظر بماند.
2. `onWorkerQuiesce` روی هر Worker مالک اجرا می‌شود و Timerها و Watcherهای همان
   Worker و Handleهای مختص مؤلفه را که روی همان Worker صف شده‌اند جدا می‌کند.
3. `onQuiesceWait` پس از Quiesceشدن همه‌ی Workerها روی Main Thread اجرا می‌شود و
   ریشه‌های Callback خارجیِ از قبل پذیرفته‌شده را Join یا Detach می‌کند.
4. `onWorkerStop` هنگام Drain روی هر Worker مالک اجرا می‌شود. هر مالک Source یا
   Line عادی داخلی، هنگام رسیدن نوبتش Inventory مرجع خود را می‌بندد؛ Hook دیگری
   نباید فرض کند مالک همسایه قبلاً اجرا شده یا خالی‌بودن Registry قرضی را الزام
   کند.
5. `onStop` پس از تخلیه‌شدن همه‌ی Workerها روی Main Thread اجرا می‌شود و منابع
   مشترک باقی‌مانده را آزاد می‌کند.
6. `onDestroy` فقط وقتی روی Main Thread اجرا می‌شود که دیگر هیچ Worker، ‏Message،
   ‏Line یا producer خارجی نتواند به Instance ارجاع دهد.

همه‌ی Callbackها یک `ww_lifecycle_context_t` فقط‌خواندنی دریافت می‌کنند. بازگردانی
ساخت، برچیدن فرزند خصوصی به‌دست مالک و راه‌اندازی مجدد محلی Device، ‏Scopeهای مستقل
خود و سیاست بستن Abortive را دارند. Componentها نباید با Pollکردن وضعیت سراسری
خاموش‌سازی، ‏Scope را حدس بزنند. حذف زنده‌ی Configuration یک Scope پشتیبانی‌شده‌ی
چرخه‌ی عمر نیست.

از Helperهای JSON پروژه، مانند `getStringFromJsonObject`،
`getBoolFromJsonObjectOrDefault` و `getIntFromJsonObjectOrDefault` استفاده کنید و
برای پیکربندی نادرست پیام روشنی با `LOGF` بنویسید. پیکربندی اشتباه باید هنگام
راه‌اندازی با خطایی روشن شکست بخورد، نه اینکه در زمان اجرا بی‌صدا باقی بماند.

## ‏`structure.h`: ‏tstate و lstate

دو Struct مربوط به State و اندازه‌هایشان در `structure.h` تعریف می‌شوند. تنظیمات
و فیلدهای Runtime را مانند `TlsClient` به‌وضوح گروه‌بندی کنید:

```c
typedef struct tlsclient_tstate_s
{
    // تنظیمات (یک بار در create.c Parse می‌شوند)
    char *sni;
    char *alpn;
    bool  verify;
    // State زمان اجرا که میان همه‌ی Lineها مشترک است
    SSL_CTX **threadlocal_ssl_contexts;   // یکی به‌ازای هر Worker
} tlsclient_tstate_t;

typedef struct tlsclient_lstate_s
{
    SSL           *ssl;
    BIO           *rbio;
    BIO           *wbio;
    buffer_queue_t bq;
    bool           handshake_completed;
    bool           resources_released;
} tlsclient_lstate_t;
```

آرایه‌های مختص Worker، مانند `threadlocal_ssl_contexts`، در **tstate** قرار می‌گیرند
و فقط با هویت Worker که صریحاً اعتبارسنجی شده Index می‌شوند: `lineGetWID(line)` در
Callback یک Line، ‏`worker->wid` در Callback پیام Worker، یا
`getCurrentEventWorkerWID()` بررسی‌شده هنگامی که قرارداد Callback حضور روی Event
Worker را تضمین می‌کند. هرگز آن‌ها را با `getWID()` خام Index نکنید. State مختص هر
اتصال در **lstate** قرار می‌گیرد.

## ‏`line_state.c`: مقداردهی و نابودی

Line State در `Init` مقداردهی و دقیقاً یک بار نابود می‌شود. تابع Destroy باید کل
ناحیه‌ی **هم‌تراز** را Zero کند تا Assert مربوط به آزادشدن Line در حالت Debug،
یعنی `debugAssertZeroBuf`، برقرار باشد؛ [بخش ۲](./part2-lines-and-callbacks.mdx)
را ببینید:

```c
void templateLinestateInitialize(template_lstate_t *ls)
{
    // State این اتصال را آماده کنید
}

void templateLinestateDestroy(template_lstate_t *ls)
{
    memoryZeroAligned32(ls, tunnelGetCorrectAlignedLineStateSize(sizeof(template_lstate_t)));
}
```

قواعد [بخش ۲](./part2-lines-and-callbacks.mdx)، در همان جایی که کد را می‌نویسید:

- در `Init` مقداردهی کنید؛ Callbackهای بعدی وجود State را فرض می‌کنند.
- فقط یک بار Destroy کنید؛ پس از `LinestateDestroy()`، ‏State را مرده و Zero‌شده
  در نظر بگیرید.
- پس از نابودی State هیچ فیلدی از آن نخوانید.
- یک Boolean به نام `initialized` اضافه نکنید، مگر آنکه قرارداد صریح و مستندِ نقش
  Line یا Callback، وجود State پیش از `Init` عادی را لازم بداند.

## قواعد مختص HTTP

اگر روی `HttpClient` یا `HttpServer` کار می‌کنید، محدودیت‌های زیر که از Source
Code به دست آمده‌اند برقرارند:

- هدف WaterWall پشتیبانی از HTTP/1.x و HTTP/2 **تک‌Stream** است. HTTP/3 اضافه
  نکنید. بیش از یک Stream منطقی HTTP/2 را پشتیبانی نکنید. اگر Peer، ‏Streamهای
  اضافه باز کرد، مطابق طراحی موجود آن‌ها را با رویکردی محافظه‌کارانه رد یا نادیده
  بگیرید.
- در **ارتقای h2c** با `nghttp2_session_upgrade2()`، ‏Stream شماره‌ی `1` همان
  Request اصلی است که Upgrade شده است. Client نباید Request ساختگی دومی را روی
  Stream ‏`1` Submit کند و Server نباید Response ساختگی و جعلی را خودکار روی
  Stream ‏`1` بسازد.
- در **h2c همراه با Request Body**، ارتقای Request اصلی HTTP/1.1 که Body دارد در
  طراحی تک‌Stream به‌شکل امن پشتیبانی نمی‌شود. توصیه می‌شود Client آن را رد کند؛
  Server نیز Upgrade مربوط به Request دارای Body در HTTP/1.1 را نادیده بگیرد یا
  رد کند.
- برای **پایان تمیز (`Clean finish`)**، دریافت یک `Finish` در جهت upstream برای
  سمت Request ممکن است ابتدا
  نیازمند Byteهای پایانی HTTP باشد. آن‌ها را در حالی بفرستید که Reference مربوط
  به Line را نگه داشته‌اید، سپس State محلی را نابود و `Finish` واقعی را Forward
  کنید؛ الگوی عمومی Byteهای پایانی در
  [بخش ۲](./part2-lines-and-callbacks.mdx). پس از چنین Finish تمیزی، ‏Line State
  مربوط به HTTP را زنده نگه ندارید، مگر آنکه عمداً برای این هدف Reference مربوط به Line را نگه داشته
  باشید.

## روند پیاده‌سازی

برای هر قابلیت یا اصلاح جدید، این ترتیب را دنبال کنید. ابتدا مخزن را بررسی
کنید؛ فقط هنگامی پرسشی مشخص بپرسید که یک نیاز اثرگذار، انتخاب سازگاری یا مرز Scope
را نتوان از کد و مستندات تعیین کرد. برای جزئیات کم‌خطر پیاده‌سازی، به‌جای واگذارکردن
   تصمیم به نگه‌دارنده، فرض‌های معقولی در نظر بگیرید و ثبت کنید.

1. **جریان زنجیره را رسم کنید.** Up-end و Down-end را علامت بزنید و مشخص کنید
   کدام جهت Callback مالک Transform است.
2. **مالک Line را مشخص کنید.** کدام تونل Line را می‌سازد و نابود می‌کند؟
3. **تونل موجود** و همسایه‌های مستقیمش را بخوانید.
4. **قراردادها را بخوانید:** `ww/net/line.h`، ‏`ww/net/tunnel.h` و
   `ww/net/chain.c`.
5. **اگر Framing یا Prepend در کار است،** فایل‌های `ww/bufio/shiftbuffer.h` و
   `buffer_pool.h` و همچنین Padding موجود در `node.c` تونل‌های نزدیک را بخوانید.
6. **الگوهای مرتبطِ تونل‌های بالغ را مقایسه کنید،** اما به‌جای کپی کورکورانه،
   آن‌ها را با قرارداد، Callerها و همسایه‌ها بسنجید.
7. **کوچک‌ترین اصلاح کامل علت ریشه‌ای** را پیاده‌سازی کنید که قابلیت ترکیب را حفظ
   کند. برای کوچک‌کردن Diff، عیب شناخته‌شده را نگه ندارید، منطق ناامن را تکرار
   نکنید و فقط نشانه‌ی مشکل را وصله نکنید.
8. **تصمیم بگیرید آیا پوشش Regression متمرکز لازم است.** برای رفتار تازه، باگی
   تکرارپذیر و مستعد بازگشت، حالت مرزی مهم یا تغییر قرارداد معمولاً لازم است؛
   به‌ویژه وقتی Test بتواند با وارونه‌شدن جهت شکست بخورد. اگر پوشش مستقیم موجود
   کافی است از همان استفاده کنید و برای کار مکانیکی یا صرفاً مستندسازی، Test
   رفتاری ساختگی نسازید.
9. با Preset ساخت و Testهای مرتبط **اعتبارسنجی کنید**؛
   [بخش ۶](./part6-build-test-review.mdx) را ببینید.

:::warning از انتزاع‌سازی‌های مبتنی بر حدس دوری کنید
یک لایه‌ی عمومی تازه به‌ندرت راه‌حل اینجا است. قرارداد تثبیت‌شده‌ی چرخه‌ی عمر را
حفظ کنید و یک اصلاح مستقیم و کامل را ترجیح دهید. اگر به نظر می‌رسد تونلی به مفهوم
تازه‌ای در چرخه‌ی عمر نیاز دارد، دست نگه دارید و نیاز را در برابر قرارداد Core و
همه‌ی Callerهای تحت تأثیر بررسی کنید؛ یک تونل مرجع به‌تنهایی درستی ساختار قدیم یا
جدید را ثابت نمی‌کند.
:::
