# راهنمای توسعه‌ی WaterWall

این راهنما با تمرکز بر کد منبع برای افرادی نوشته شده است که تونل‌های موجود در
[`tunnels/`](https://github.com/radkesvat/WaterWall) را پیاده‌سازی، اصلاح یا بازبینی
می‌کنند؛ چه توسعه‌دهنده باشند و چه عامل کدنویسی. راهنما هفت بخش دارد. این صفحه
(بخش ۱) مدل ذهنی لازم را می‌سازد و بخش‌های بعدی قراردادهایی را با جزئیات توضیح
می‌دهند که نباید نقض شوند.

WaterWall سامانه‌ای زنجیره‌محور برای اجرای تونل‌هاست؛ بنابراین یک تونل درست هیچ‌گاه
«فقط» Parser یا Encoder نیست. تونل باید **جهت Callbackها**، **طول عمر Line**،
**State مختص هر Line**، **Padding بافر**، **رفتار Packet Line** و **قابلیت ترکیب**
با هر Node پیش و پس از خود در پیکربندی کاربر را حفظ کند.

:::tip مهم‌ترین قاعده
برای اصلاح موردی یک تونل، در حاشیه‌ی کار مدل تازه‌ای برای چرخه‌ی عمر طراحی نکنید.
کار را از قراردادهای موردنظر در این راهنما و سازوکار فعلی
[`ww/net/`](https://github.com/radkesvat/WaterWall/tree/main/ww/net) آغاز کنید؛ سپس
با تونل‌های بالغی مقایسه کنید که مسئله‌ای مشابه را حل کرده‌اند. پیاده‌سازی
مرجع فقط شاهد است، نه اثبات: آن را با قرارداد، فراخواننده‌ها و همسایه‌هایش تطبیق
دهید، زیرا ممکن است یک الگوی تکرارشده، خطایی تکرارشده هم داشته باشد. بازطراحی
صریحاً درخواست‌شده‌ی چرخه‌ی عمر ممنوع نیست، اما کاری فراگیر است و باید همه‌ی
پیاده‌سازی‌ها، آزمایش‌ها و اسناد قراردادی متأثر را پوشش دهد.
:::

## ابتدا این فایل‌ها را بخوانید

فایل‌ها کوتاه و فشرده‌اند و سازوکار فعلی را تعریف می‌کنند، اما بی‌نقص‌بودن

به‌جای آنکه بی‌سروصدا متن را با کد موجود یکسان کنید، اختلاف را بررسی و گزارش کنید.

## تونل‌های مرجع مناسب

نزدیک‌ترین الگوهای موجود را برای مقایسه به کار ببرید، نه به‌عنوان قالبی که
چشم‌بسته کپی شود. تونل‌های زیر شکل‌های مفیدی از قرارداد را نشان می‌دهند، اما رفتار
آن‌ها نیز باید با نقش دقیق مورد تغییر سنجیده شود:

| مرجع | برای چه چیزی بخوانید؟ |
| --- | --- |
| `TcpListener`، `UdpListener` | Adapterهای ابتدای زنجیره که مالک یک منبع سیستم‌عامل‌اند و Lineهای عادی خود را می‌سازند و نابود می‌کنند. |
| `TcpConnector`، `UdpConnector` | Adapterهای انتهای زنجیره که مالک یک منبع سیستم‌عامل‌اند، اما Line ساخته‌شده در upstream را قرض می‌گیرند. |
| `TlsClient`، `EncryptionClient` | بسته‌بندی Stateful پروتکل، State مختص Line و Finish صحیح همراه با Byteهای پایانی. |
| `MuxClient` | مالکیت داخلی Line، Lineهای Parent/Child و ایمنی در برابر Re-entrancy. |
| `PacketsToStream`، `StreamToPackets`، `PacketsToConnection` | مرزهای Packet-to-Stream و پل‌هایی که به Packet Line متکی‌اند. |
| `PingClient`، `PingServer` | Transformهای جفت و مستقیم ICMP Echo، داده‌ی Decode‌شده در همان جهت، و پاسخ دقیق در جهت مخالف. |
| `template` | اسکلت حداقلی که نقطه‌ی شروع همه‌ی تونل‌هاست. |

## مدل زمان اجرا

WaterWall **Instanceهای تونل** را در یک **زنجیره‌ی** مرتب کنار هم قرار می‌دهد.
یک زنجیره‌ی معمول Stream چنین است:

```text
TcpListener -> ObfuscatorClient -> TlsClient -> TcpConnector
```

Node اول و آخر معمولاً **Adapter** هستند. آن‌ها مالک یک منبع سیستم‌عامل، مانند
Socket نوع TCP یا UDP، دستگاه TUN، ‏Raw Socket و موارد مشابه‌اند. فقط همین Nodeها
از دنیای بیرون داده می‌خوانند یا در آن می‌نویسند.

هر چیزی میان Adapterها یک **تونل میانی** است. تونل‌های میانی باید **قابل ترکیب**
بمانند: Callbackها و Payloadها را بدون هیچ فرضی درباره‌ی Adapter دو طرف تغییر
دهند. تونل میانی‌ای که فقط در کنار یک Adapter خاص کار می‌کند معیوب است، حتی اگر
آزمایش‌های خودش موفق باشند.

```text
 -------------- chain --------------------------------------------------

   ------------          ------------          ------------
   |          | -- up -> |          | -- up -> |          |
   | Tunnel 1 |          | Tunnel 2 |          | Tunnel 3 |
   |          | <- down- |          | <- down- |          |
   ------------          ------------          ------------
   (adapter)              (middle)              (adapter)

 -----------------------------------------------------------------------
```

راهنمای شکل: `chain` یعنی زنجیره، `up` مسیر upstream یا بالادست، `down` مسیر
downstream یا پایین‌دست، `adapter` آداپتور و `middle` تونل میانی است.

هر اتصال یک `line_t` است. Line دو انتها دارد که در `ww/net/line.h` با
`Down-end <----> Up-end` توصیف شده‌اند. Chain Head، یعنی نخستین Adapter، رو به
Down-end قرار می‌گیرد و Chain Tail، یعنی آخرین Adapter، رو به Up-end. سازوکار
Backpressure متقارن است: اگر نوشتن در Down-end متوقف شود، Up-end در حالت Pause
قرار می‌گیرد و برعکس.

## چهار شیء اصلی

| شیء | تعریف |
| --- | --- |

| `tunnel_t` | Instance اجرایی یک Node. دوازده Function Pointer مربوط به Callbackها، لینک‌های `next`/`prev`، ‏Tunnel State، اندازه‌ی Line State و Offsetهای زنجیره را نگه می‌دارد. تعریف در `ww/net/tunnel.h`. |
| `line_t` | یک اتصال: Line عادی اتصال، Line منطقی یا Packet Line مربوط به Worker. شامل Routing Context، نشانه‌های User/Auth، شناسه‌ی Worker مالک، Reference Count، ‏Flag مربوط به `alive` و **State مختص Line برای همه‌ی تونل‌ها** است. تعریف در `ww/net/line.h`. |

### تفاوت Tunnel State و Line State

هر تونل می‌تواند مالک دو نوع State باشد:

- **Tunnel State یا `tstate`** — یک Block به‌ازای هر Instance تونل که میان همه‌ی
  اتصال‌های عبوری مشترک است. اندازه‌ی آن هنگام `tunnelCreate()` ثابت می‌شود.
- **Line State یا `lstate`** — یک Slot به‌ازای هر `line_t` که برای همان اتصال و
  همین تونل خصوصی است.

با Helperهای موجود به آن‌ها دسترسی بگیرید و مستقیماً وارد Structها نشوید:

```c
my_tstate_t *ts = tunnelGetState(t);        // State سراسری این Tunnel
my_lstate_t *ls = lineGetState(line, t);    // State همین Tunnel برای این Line
```

`lineGetState()` چگونه Slot درست را پیدا می‌کند؟ هنگام Index‌شدن زنجیره، سامانه‌ی زمان اجرا
به هر تونل یک `lstate_offset` می‌دهد و به‌اندازه‌ی `lstate_size` در هر Line فضا
رزرو می‌کند؛ به `tunnelDefaultOnIndex` در `ww/net/tunnel.c` نگاه کنید.
`lineGetState()` پس از آن فقط برابر است با
`line->tunnels_line_state + t->lstate_offset`. به همین دلیل **Line State باید در
`Init` مقداردهی اولیه شود** و پس از نابودشدن دیگر معتبر دانسته نشود: این حافظه
بخشی مشترک از فضای داخلی Line است و اندازه‌ی آن فقط یک بار برای کل زنجیره تعیین
می‌شود.

اندازه‌ی Stateها با Cache Line هم‌تراز است. هنگام Zeroکردن Line State، دقیقاً
مانند تونل‌های موجود، تمام ناحیه‌ی *هم‌تراز‌شده* را پاک کنید:

```c
memoryZeroAligned32(ls, tunnelGetCorrectAlignedLineStateSize(sizeof(my_lstate_t)));
```

## جهت Callbackها

مالکیت جهت اولین نکته‌ای است که باید درست فهمیده شود و رایج‌ترین منشأ خطاست.

| جریان | مفهوم | Helper مربوط به Forward |
| --- | --- | --- |
| **Upstream** | مسیر Request، خروجی یا رو به جلو؛ به‌سمت Up-end و `next` | `tunnelNextUpStream*` |
| **Downstream** | مسیر Response، ورودی یا رو به عقب؛ به‌سمت Down-end و `prev` | `tunnelPrevDownStream*` |

هر تونل دوازده Callback مربوط به جریان دارد؛ برای هر ترکیب `{event} x {direction}`
یک Callback:

```c
fnInitU  fnEstU  fnPayloadU  fnPauseU  fnResumeU  fnFinU    // Handlerهای upstream
fnInitD  fnEstD  fnPayloadD  fnPauseD  fnResumeD  fnFinD    // Handlerهای downstream
```

تقریباً هیچ‌گاه این Pointerها را مستقیماً صدا نمی‌زنید. از Helperهای Forwarding
استفاده می‌کنید که Handler متناظر را روی همسایه فراخوانی می‌کنند:

```c
// «Next در upstream»: تابع self->next->fnPayloadU(self->next, line, buf) را صدا می‌زند
tunnelNextUpStreamPayload(t, line, buf);

// «Prev در downstream»: تابع self->prev->fnPayloadD(self->prev, line, buf) را صدا می‌زند
tunnelPrevDownStreamPayload(t, line, buf);
```

Forwardکردن رویدادهای چرخه‌ی عمر نیز از همین نام‌گذاری پیروی می‌کند:

```c
tunnelNextUpStreamInit(t, line);      // ادامهٔ زنجیره را در جهت جلو آغاز می‌کند
tunnelNextUpStreamFinish(t, line);    // جهت رو‌به‌جلو را می‌بندد

tunnelPrevDownStreamEst(t, line);     // برقراری اتصال را به سمت عقب اعلام می‌کند
tunnelPrevDownStreamFinish(t, line);  // جهت رو‌به‌عقب را می‌بندد
```

اگر تونل Callback مشخصی را Override نکند، رفتار پیش‌فرض فریم‌ورک را می‌گیرد که
صرفاً رویداد را در همان جهت به همسایه Pass-through می‌کند؛ به
`tunnelDefaultUpStreamPayload` و `tunnelDefaultDownStreamPayload` در
`ww/net/tunnel.c` نگاه کنید. بنابراین تونلی که فقط در upstream عمل Obfuscation را
انجام می‌دهد، می‌تواند Handler مربوط به Payload در downstream را روی مقدار پیش‌فرض
بگذارد تا Byteها بدون تغییر عبور کنند.

:::warning جهت‌ها را برعکس نکنید
صرفاً چون تونل سمت Server «برعکس به نظر می‌رسد»، Helper مربوط به Forwardکردن
Buffer دریافتی را عوض نکنید. زنجیره‌ی واقعی را رسم کنید، Up-end و Down-end را
علامت بزنید و هر Buffer خروجی را جداگانه دسته‌بندی کنید. در Ping v2، داده‌ی اصلی
پس از Decode در همان جهت Callback درخواست دریافتی ادامه می‌یابد، اما یک Echo Reply
دقیق که جداگانه Clone شده، به‌عنوان تأیید در جهت مخالف حرکت می‌کند. بنابراین
`PingServer` در Handler درخواست upstream خود به downstream پاسخ می‌دهد و
`PingClient` در Handler درخواست downstream خود به upstream پاسخ می‌دهد. داده‌ی
برنامه در جهت معکوس، یک Echo Request جداگانه را آغاز می‌کند. برای جزئیات
[بخش ۴](./part4-packet-tunnels.mdx) را ببینید.
:::

### کدام تابع Forwarding را صدا بزنم؟

| در حال Handleکردن... | و قصد فرستادن رویداد به... | تابع مناسب |
| --- | --- | --- |
| هر چیزی | بخش بالاتر زنجیره، به‌سمت `next` | `tunnelNextUpStream{Init,Payload,Est,Pause,Resume,Finish}` |
| هر چیزی | بخش پایین‌تر زنجیره، به‌سمت `prev` | `tunnelPrevDownStream{Init,Payload,Est,Pause,Resume,Finish}` |

Helperهای قرینه‌ی `tunnelUpStream*` و `tunnelDownStream*` که `Next`/`Prev` ندارند،
Handler را روی تونلی فراخوانی می‌کنند که **Pointer مستقیم آن را در اختیار دارید**.
این حالت زمانی به کار می‌رود که تونل شاخه‌ای را هدایت می‌کند که در پایین خود Bind
کرده است؛ مانند Route Target، ‏Fallback یا شاخه‌ی کمکی. ورودی واقعی چنین شاخه‌ای
را با `tunnelGetBranchEntry()` پیدا کنید و فرض نکنید Node خامی که دریافت کرده‌اید
همان Head قابل‌فراخوانی است.

## چرخه‌ی عمر تونل

Instance تونل از مجموعه‌ای ثابت از Lifecycle Hookها عبور می‌کند. این Hookها با
Callbackهای جریانِ مختص اتصال که در بالا دیدیم متفاوت‌اند: در زمان پیکربندی،
راه‌اندازی و خاموش‌شدن و به‌ازای هر تونل یا Worker یک بار اجرا می‌شوند، نه برای
هر Packet.

سامانه‌ی زمان اجرا تقریباً با ترتیب زیر آن‌ها را اجرا می‌کند؛ توضیح ابتدای `ww/net/tunnel.h`
و پیاده‌سازی‌های پیش‌فرض در `ww/net/tunnel.c` را ببینید:

```text
createHandle(node)         // node.c -> create.c: تخصیص، تعیین Callbackها و Parse تنظیمات
      |
   onChain                 // اتصال به next/prev و درج در زنجیره (پیش‌فرض node->next را می‌پیماید)
      |
   solve + onSolvedTopology // بررسی Snapshot حل‌شده؛ پس از تغییر توپولوژی تکرار می‌شود
      |
   onIndex                 // تعیین chain_index و lstate_offset و رزرو بایت‌های Line State
      |
   onPrepare               // آماده‌سازی پیش از Start (نام پیشین: onChainingComplete)
      |
   onStart                 // زنجیره کامل است؛ آغاز کار واقعی / راه‌اندازی Packet Lineها
      |
    ...                     // زمان اجرا: Callbackهای جریان اینجا اجرا می‌شوند
      |
   onQuiesceRequest        // Thread اصلی: بستن پذیرش؛ درخواست توقف Producer؛ بدون انتظار
      |
   onWorkerQuiesce         // هر Worker مالک: جداسازی Timer/Watcher/Handleهای وابسته به Worker
      |
   onQuiesceWait           // Thread اصلی: Join/Detach ریشه‌های Callback خارجیِ از قبل پذیرفته‌شده
      |
   onWorkerStop            // هر Worker مالک: Drainکردن Lineهای عادی و منابع تحت مالکیت
      |
   onStop                  // Thread اصلی: آزادسازی منابع مشترک باقی‌ماندهٔ مؤلفه
      |
   onDestroy               // Thread اصلی: بازپس‌گیری Instance پس از پایان همهٔ Referenceها
```

کاربرد هر Hook:

| Hook | رفتار پیش‌فرض | مورد معمول Override |
| --- | --- | --- |
| `createHandle` | الزامی است | ساخت تونل با `tunnelCreate(node, sizeof(tstate), sizeof(lstate))`، تنظیم دوازده Callback، ‏Parse و اعتبارسنجی تنظیمات JSON و تخصیص منابع هر Worker. |
| `onChain` | `tunnelDefaultOnChain` با دنبال‌کردن `node->next` زنجیره را می‌سازد | به‌ندرت Override می‌شود. Adapterها نیز مقدار پیش‌فرض را حفظ می‌کنند. |
| `onSolvedTopology` | `NULL` (اختیاری) | Snapshot فعلی توپولوژی حل‌شده را مصرف می‌کند و در صورت نیاز، پیش از Indexing توپولوژی خصوصی وابسته به Layer را می‌سازد. Snapshot لزوماً نهایی نیست و Hook ممکن است چند بار اجرا شود، پس باید تکرار را تحمل کند. فقط و فقط اگر توپولوژی تغییر کرد `true` برگردانید؛ در این حالت Snapshot فوراً نامعتبر می‌شود و NodeManager پیش از اجرای Hook بعدی دوباره مسئله را حل می‌کند. |
| `onIndex` | `tunnelDefaultOnIndex`، ‏Offset مربوط به Line State را تعیین می‌کند | پس از آنکه گسترش توپولوژی و حل Layerها به نقطه‌ی ثابت رسید، یک بار اجرا می‌شود. می‌توان Domainهای نهایی Edgeهای حل‌شده را اینجا مصرف کرد، اما توپولوژی زنجیره نباید تغییر کند. به‌ندرت Override می‌شود. |
| `onPrepare` | بدون عملیات | آماده‌سازی پیش از Start که به وجود زنجیره نیاز دارد. |
| `onStart` | بدون عملیات | آغاز Listen/Connect و Bootstrapکردن Packet Lineها؛ بخش ۴ را ببینید. |
| `onQuiesceRequest` | بدون عملیات | روی Thread اصلی، در زمانی محدود و بدون مسدودکردن، پذیرش را می‌بندد و توقف Producer را درخواست می‌کند. اینجا Join نکنید و منابع لازم برای Drainکردن Lineها را آزاد نکنید. |
| `onWorkerQuiesce` | بدون عملیات | روی هر Worker مالک، پیش از تأیید Quiescence، ‏Timerها، ‏Watcherها و Handleهای وابسته به همان WID را جدا می‌کند. |
| `onQuiesceWait` | بدون عملیات | پس از Quiesceشدن Workerها، روی Thread اصلی ریشه‌های Callback خارجیِ از قبل پذیرفته‌شده را Join یا Detach می‌کند؛ منابع لازم برای Drain Lineها باید همچنان زنده بمانند. |
| `onWorkerStop` | بدون عملیات | هنگام Drain روی هر Worker مالک، فهرست‌های مرجعِ Lineهای Source و Lineهای عادیِ تحت مالکیت داخلی را پیش از اعتبارسنجی تونل‌های میانی و انتهایی می‌بندد. |
| `onStop` | بدون عملیات | پس از Drainشدن همه‌ی Workerها، منابع مشترک باقی‌مانده را روی Thread اصلی آزاد می‌کند؛ نباید به Timer یا Watcher وابسته به Worker دست بزند. |
| `onDestroy` | `tunnelDestroy`، ‏Instance را آزاد می‌کند | آزادکردن تنظیمات، SSL Contextها و Poolها و سپس فراخوانی `tunnelDestroy`. |

بیشتر تونل‌ها فقط مرحله‌های چرخه‌ی عمر مربوط به منابعی را Override می‌کنند که
واقعاً مالکشان هستند؛ به‌علاوه‌ی Callbackهای جریان موردنیاز. رفتار پیش‌فرض Chaining
و Indexing را نگه دارید، مگر آنکه قرارداد توپولوژی تونل چیز دیگری بخواهد. هر
انحراف را با قواعد توپولوژی حل‌شده بسنجید، نه با کپی مکانیکی یک مرجع.

نتایج Layer در دو نقطه‌ی جداگانه مصرف می‌شوند. فقط هنگامی از `onSolvedTopology`
استفاده کنید که تونل باید پیش از Indexing عملی انجام دهد؛ برای نمونه، توپولوژی
خصوصی‌ای درج کند که محل آن به Domainهای حل‌شده‌ی مجاور وابسته است. Callbackی که
توپولوژی را تغییر می‌دهد باید استفاده از Snapshot را متوقف کند و `true` برگرداند.
توپولوژی تنها وقتی نهایی است که یک دور کامل اجرای Callbackها هیچ تغییری گزارش
نکند. اگر تونل فقط باید راه‌حل نهایی را بخواند، از `onIndex` استفاده کنید؛ این
راه‌حل برای `onIndex` و همه‌ی Callbackهای بعدی چرخه‌ی عمر ثابت می‌ماند. توپولوژی
داخلی ثابتی که وجود و محل آن پیش از حل معلوم است، همچنان باید در `onChain` ساخته
شود.

## اسکلت حداقلی تونل

همه‌ی تونل‌ها از یک ساختار یکسان آغاز می‌شوند. نمونه‌ی زیر نسخه‌ی کمی خلاصه‌شده‌ی
`create.c` در تونل `template` است:

```c
tunnel_t *templateTunnelCreate(node_t *node)
{
    tunnel_t *t = tunnelCreate(node, sizeof(template_tstate_t), sizeof(template_lstate_t));
    if (! t)
    {
        return NULL;
    }

    t->fnInitU    = &templateTunnelUpStreamInit;
    t->fnEstU     = &templateTunnelUpStreamEst;
    t->fnFinU     = &templateTunnelUpStreamFinish;
    t->fnPayloadU = &templateTunnelUpStreamPayload;
    t->fnPauseU   = &templateTunnelUpStreamPause;
    t->fnResumeU  = &templateTunnelUpStreamResume;

    t->fnInitD    = &templateTunnelDownStreamInit;
    t->fnEstD     = &templateTunnelDownStreamEst;
    t->fnFinD     = &templateTunnelDownStreamFinish;
    t->fnPayloadD = &templateTunnelDownStreamPayload;
    t->fnPauseD   = &templateTunnelDownStreamPause;
    t->fnResumeD  = &templateTunnelDownStreamResume;

    t->onPrepare = &templateTunnelOnPrepair;
    t->onStart   = &templateTunnelOnStart;
    t->onStop    = &templateTunnelOnStop;
    t->onDestroy = &templateTunnelDestroy;

    return t;
}
```

بخش ۵ ساختار کامل دایرکتوری پشت این اسکلت، از جمله Metadata در `node.c`، فایل
`line_state.c` و محل هر Callback را بررسی می‌کند.

## «درست‌بودن» در اینجا یعنی چه؟

یک تغییر درست در تونل باید **هم‌زمان** همه‌ی موارد **قابل‌اعمال** زیر را حفظ کند:

- قابلیت ترکیب تونل، مستقل از همسایه‌های آن
- قواعد چرخه‌ی عمر Line: مقداردهی در `Init`، یک بار Destroy‌شدن و فقط به‌دست مالک
- مالکیت جهت: هرگز `Next*` و `Prev*` را وارونه نکنید
- فرض‌های مربوط به Padding بافر: رعایت `required_padding_left`
- استفاده‌ی صحیح از Shift Buffer: فراخوانی `sbufShiftLeft` فقط با ظرفیت کافی در چپ
- ایمنی Lock و Reference Count: جلوگیری از Use-after-free برای `line_t` و Line State
- معنای Packet Line: محلی برای Worker و بدون Destroy در زمان اجرا
- رفتار موجود زنجیره: نبود Regression در چیدمان‌های دیگر

اگر یک تغییر پیشنهادی نتواند توضیح دهد که تک‌تک این موارد را چگونه حفظ می‌کند،
هنوز آماده نیست. ادامه‌ی این راهنما در واقع شرح مفصل همین فهرست است.

### هویت Thread مربوط به Worker و WID

هویت Thread مربوط به Worker در WaterWall صریح است و به‌طور پیش‌فرض نامعتبر در
نظر گرفته می‌شود:

- **WID یعنی index یک slot ثبت‌شده‌ی Worker**، نه شناسه‌ی Thread در سیستم‌عامل یا
  برنامه مانند `getTID()`.
- Threadهای ثبت‌نشده، از جمله Threadهای reader/writer مربوط به TUN، ‏Threadهای
  raw device و capture، ‏Threadهای کمکی و آزمایش، مقدار
  `getWID() == kInvalidWID` یعنی `UINT8_MAX` را می‌بینند.
- `getWID()` می‌تواند `kInvalidWID` برگرداند. هر Call Site که به State متعلق به
  Worker دسترسی دارد باید هویت Thread را با Predicateهایی مانند
  `currentThreadIsEventWorker()` یا `workerWIDIsRegistered(wid)` بررسی کند.
- **Threadهای کمکی** باید کارِ دارای مالکیت را از طریق صف پیام Worker ارسال کنند و
  هرگز نباید مستقیماً یک Pool محلی Worker را قرض بگیرند. Custom Event خام Loop فقط
  برای عملیات بدون مالکیت و متعلق به خود Loop رزرو شده است.
- **Pseudo-worker مربوط به lwIP** ثبت‌شده است؛ یعنی `workerWIDIsRegistered()` برای
  آن `true` است، اما Event Worker نیست و `workerWIDIsEventWorker()` برایش `false`
  است، زیرا Event Loop متعلق به WaterWall ندارد.
- Threadهای native/library برای Log و تشخیص خطا از `getTID()` استفاده می‌کنند و تا
  زمانی که صریحاً با `workerBindCurrentThread()` متصل نشوند WID نامعتبر دارند.

### انتخاب Helper مناسب برای Context مربوط به Worker

هرگز `getWID()` را مستقیماً در بررسی Affinity، ‏index یک Array یا lookup منبع
به‌کار نبرید. محدودترین Helper سازگار با Context موجود را انتخاب کنید. Helper
دامنه‌ی معتبر را در قرارداد خود کد می‌کند و اجازه نمی‌دهد یک Thread ثبت‌نشده یا
Pseudo-worker مربوط به lwIP صرفاً به‌دلیل برابری اتفاقی از بررسی عبور کند.

| Context | استفاده |
| --- | --- |
| Callback یک `line_t *` دارد | `lineIsOnCurrentEventWorker(line)`، ‏`lineGetWID(line)`، ‏`lineGetBufferPool(line)`، ‏`lineReuseBuffer(line, buf)` |
| Callback پیام Worker یک `worker_t *worker` دارد | `worker->wid`، ‏`worker->buffer_pool`، ‏`worker->loop`؛ TLS را دوباره نخوانید. |
| Callback مربوط به Event/Timer/I/O یک Loop یا Event دارد | یک بار `getLoopEventWorkerWID(weventGetLoop(ev))` را بگیرید و مقدار محلی را دوباره استفاده کنید. |
| Callback واقعی Event Loop بدون Line یا Worker | `getCurrentEventWorker()`، ‏`getCurrentEventWorkerWID()`، ‏`getCurrentEventWorkerBufferPool()`، ‏`getCurrentEventWorkerLoop()` |
| Callback چرخه‌ی عمر که `wid` صریح دریافت کرده است | `currentThreadIsEventWorkerWID(wid)` |
| کدی که بنا بر طراحی به Worker 0 نیاز دارد | WID صریح `0` همراه `currentThreadIsEventWorkerWID(0)`؛ هرگز آن را از TLS پیش‌فرض استنباط نکنید. |
| API قابل‌دسترسی از بیرون یا در غیر این صورت Fallible | `tryGetCurrentEventWorker()` یا `currentThreadIsEventWorker()`؛ سپس Error یا `NULL` برگردانید یا کار را Queue کنید. |
| کدی که ممکن است روی lwIP اجرا شود | `workerWIDIsRegistered()` یا WID مقصد صریح؛ هرگز Array مربوط به Event Worker. |
| Thread کمکی Device | فقط Pool/Channel متعلق به Device؛ تحویل به یک Event Worker صریح. |
| فقط Logging | استفاده‌ی خام از `getWID()` مجاز است، به شرط عبور از `workerWIDForLog()` و چاپ با `%d` در کنار `getTID()`؛ مقدار `-1` یعنی ثبت‌نشده. |

Accessorهای `getCurrentEventWorker*()` که Pointer برمی‌گردانند فقط برای Callbackهای
داخلی‌اند که قراردادشان از قبل حضور روی Event Worker را تضمین می‌کند. این توابع
به‌جای fallback به Worker 0، ‏Abort می‌کنند. بنابراین هر چیزی که از Thread دستگاه،
Callback یک Library یا API عمومی قابل‌دسترسی است باید از شکل Predicate استفاده کند
و در صورت نبود Context معتبر به‌طور تمیز Fail شود.

```c
// Callback مربوط به Line: هم Affinity و هم مالکیت Pool از خود Line می‌آیند.
if (! lineIsOnCurrentEventWorker(l))
{
    sendWorkerMessageForceQueueWithCleanup(lineGetWID(l), doWork, cleanup, t, l, buf);
    return;
}
lineReuseBuffer(l, buf);

// Callback پیام Worker: پیام دقیقاً به یک Worker تحویل شده است.
static void onWorkerMessage(worker_t *worker, void *arg1, void *arg2, void *arg3)
{
    line_t *packet_line = tunnelchainGetWorkerPacketLine(tunnelGetChain(t), worker->wid);
    ...
}

// Callback مربوط به Timer: مالک را از Loop بگیرید، یک بار بررسی و دوباره استفاده کنید.
const wid_t wid = getLoopEventWorkerWID(weventGetLoop(timer));
ts->worker_timers[wid] = NULL;

// Callback مربوط به lwIP: فقط Worker مقصد Packet می‌تواند Inline عمل کند.
if (currentThreadIsEventWorkerWID(route_ctx->packet_wid)) { emitInline(); }
else                                                     { queueToPacketWorker(); }

// Thread دستگاه: فقط منابع متعلق به دستگاه؛ تحویل با WID صریح.
sbuf_t *buf = bufferpoolGetLargeBuffer(dev->reader_buffer_pool);
sendWorkerMessageForceQueueWithCleanup(target_wid, deliver, cleanup, dev, buf, NULL);
```

پاک‌سازی Buffer میان Threadها با Recycleکردن یکسان نیست. `reuseBuffer(buf)` یعنی
«روی Event Worker فعلی دوباره استفاده کن» و Call Siteای را که Pool محلی Worker
ندارد رد می‌کند. وقتی روی Worker مالک Buffer نیستید، آزادسازی درست
`sbufDestroy(buf)` است؛ این مسیرها را به `reuseBuffer()` تبدیل نکنید.

APIهای معمول تونل، یعنی `<node>TunnelApi()`، روی Event Worker اجرا می‌شوند و
مالکیت پیام خود را می‌گیرند. پیام را با `tunnelapiRecycleMessage()` یا
`tunnelapiUnsupportedMessage()` در `ww/objects/node.h` مصرف کنید. هر دو تابع وقتی
Caller روی Event Worker نیست Buffer را نابود می‌کنند و `kApiResultError`
برمی‌گردانند، نه اینکه Pool مربوط به Worker 0 را قرض بگیرند.

`tests/worker_identity_source_policy_test.py` این قواعد را اعمال می‌کند:
تو‌در‌توکردن تازه‌ی `getWorkerXxx(getWID())`، تصمیم مالکیت با `getWID() == 0` خام،
مقایسه‌ی خام Affinity با WID فعلی و کد تکراری مربوط به Recycle پیام Tunnel API رد
می‌شوند.

## واژه‌نامه

| اصطلاح | مفهوم |
| --- | --- |
| **Adapter** | تونلی در ابتدا یا انتهای زنجیره که مالک یک منبع سیستم‌عامل، مانند Socket، ‏TUN یا Raw Socket است. مالکیت منبع به‌معنای مالکیت `line_t` نیست: Sourceای مانند `TcpListener`، ‏Line عادی را می‌سازد، اما Tailای مانند `TcpConnector` آن را قرض می‌گیرد. |
| **تونل میانی** | تونلی غیر از Adapter که Callbackها یا Payloadها را تغییر می‌دهد و باید قابل ترکیب بماند. |
| **Line** | یک `line_t`؛ یک اتصال یا یک Packet Line مربوط به Worker که State مختص Line همه‌ی تونل‌ها را نگه می‌دارد. |
| **Upstream** | جهت رو به جلو یا خروجی، به‌سمت `next` و Up-end. |
| **Downstream** | جهت رو به عقب یا ورودی، به‌سمت `prev` و Down-end. |
| **tstate** | Tunnel State؛ مختص Instance و مشترک میان همه‌ی Lineها. |
| **lstate** | Line State؛ مختص Line و خصوصی برای یک تونل. |
| **Packet Line** | یک `line_t` پایدار به‌ازای هر Worker در زنجیره‌های Layer 3؛ Line اتصال نیست. |
| **WID** | index یک slot ثبت‌شده‌ی Worker در بازه‌ی `0 .. WORKERS_COUNT - 1`؛ روی Thread ثبت‌نشده `kInvalidWID` است. |
| **kInvalidWID** | مقدار Sentinel برابر `UINT8_MAX` برای Thread ثبت‌نشده یا کمکی. |
| **Re-entrancy** | حالتی که Callback میان‌تونلی پیش از بازگشت کنترل، به‌صورت Synchronous دوباره وارد تونل شما می‌شود و ممکن است Line را ببندد. |
| **Reflection** | Forwardکردن اشتباه Callback به‌سمتی که قبلاً Finish شده است؛ یکی از علت‌های رایج Crash. |
