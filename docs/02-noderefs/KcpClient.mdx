# KcpClient

`KcpClient` carries a TCP-like byte stream over a packet-preserving UDP path by running KCP internally. It accepts
stream payload from the previous node, wraps that byte stream into KCP segments, and forwards the resulting datagrams to
the next node.

It is normally paired with `KcpServer` on the remote side.

## Typical placement

Client side:

```text
TcpListener -> KcpClient -> UdpConnector
TcpListener -> MuxClient -> KcpClient -> UdpConnector
```

Server side:

```text
UdpListener -> KcpServer -> TcpConnector
UdpListener -> KcpServer -> MuxServer -> TcpConnector
```

The node after `KcpClient` must preserve datagram boundaries. A normal UDP-style path is the intended transport.

## Basic example

Save this node config on the application machine. Connections to local TCP
`18080` cross to the WaterWall gateway at `198.51.100.10:9000` over UDP. Pair it
with the [server config](KcpServer.mdx), whose final connector selects
the actual HTTP service on TCP `127.0.0.1:8080`. Replace the gateway address.

```json
{
  "name": "kcp-client",
  "nodes": [
    {
      "name": "app-in",
      "type": "TcpListener",
      "settings": {
        "address": "127.0.0.1",
        "port": 18080
      },
      "next": "kcp-client"
    },
    {
      "name": "kcp-client",
      "type": "KcpClient",
      "settings": {
        "fec": false
      },
      "next": "udp-out"
    },
    {
      "name": "udp-out",
      "type": "UdpConnector",
      "settings": {
        "address": "198.51.100.10",
        "port": 9000
      }
    }
  ]
}
```


## FEC example

```json
{
  "name": "kcp-client",
  "type": "KcpClient",
  "settings": {
    "fec": true,
    "fec-data-shards": 10,
    "fec-parity-shards": 3
  },
  "next": "udp-out"
}
```

FEC must be enabled on both `KcpClient` and `KcpServer` with matching shard settings. If one side uses FEC
and the other side does not, or if the shard counts differ, the peer will not decode the packet stream correctly.

## Required fields

`settings` is optional. If it is absent or not an object, the node uses defaults.

`next` is required in normal use. It should point to a packet-preserving transport or packet-preserving tunnel stack.

## Optional settings

| Field | Default | Validation | Description |
| --- | --- | --- | --- |
| `send-mtu` | core `misc.mtu` (1500 by default) | integer `118..65535` without FEC; `126..65535` with FEC | IPv4-based outgoing packet budget. Receiving uses independent protocol limits. |
| `fec` | `false` | boolean | Enables Reed-Solomon forward error correction around KCP datagrams. |
| `fec-data-shards` | `10` | positive, with total shards less than or equal to `255` | Number of data shards per FEC block. Used only when `fec` is enabled. |
| `fec-parity-shards` | `3` | positive, with total shards less than or equal to `255` | Number of parity shards per FEC block. Used only when `fec` is enabled. |
| `kcp-nodelay` | `true` | boolean | Enables KCP nodelay mode. |
| `kcp-interval-ms` | `10` | `10..5000` | KCP update interval. |
| `kcp-resend` | `2` | `>= 0` | KCP fast-resend threshold. |
| `kcp-no-congestion-control` | `true` | boolean | Disables KCP congestion control. |
| `kcp-send-window` | `8192` | `>= 1` | KCP send window in segments. |
| `kcp-recv-window` | `8192` | `>= 1` | KCP receive window in segments. |
| `kcp-initial-cwnd` | half of `kcp-send-window` | `1..kcp-send-window` | Initial KCP congestion window. |
| `kcp-rx-minrto-ms` | `30` | `>= 1` | Minimum KCP retransmission timeout. |
| `kcp-send-buffer-limit` | `0` | `>= 0` | Backpressure threshold. `0` derives the limit from local send window + remote window + `10`, capped at `2147483647`. |
| `ping-interval-ms` | `10000` | `>= 1` | Idle receive interval before sending an internal ping frame. |
| `close-drain-timeout-ms` | `30000` | integer `1..2147483647` | Close interval; peers negotiate the minimum. |
| `no-recv-timeout-ms` | `30000` | greater than `ping-interval-ms` | Idle receive interval before closing the line. |

## KCP transport model

During application Init, the client borrows that application line and creates a separate owned UDP transport line on the same worker. It copies routing contexts, listener/source ports, credentials and read policy before transport Init. Application context is TCP; transport context is UDP. Actual transport Est is relayed promptly to the attached application, independently of handshake readiness.

The peers establish a fresh session through HELLO, CHALLENGE, CONFIRM and READY. Independent 128-bit client/server nonces identify every KCP/FEC datagram before decoding. Handshake messages carry the close interval and exact FEC settings. The client retries its current request every 250 ms within the original `no-recv-timeout-ms` deadline. The server initializes a distinct service line only after fresh confirmation. Delayed traffic cannot reset an established session or recreate an old service. These identifiers provide no authentication or encryption.

Accepted application data enters KCP's ordered send queue before readiness; ordinary wire output waits for matching READY. Nested callbacks are serialized with bounded retained-buffer storage.

When stream payload arrives from the previous node:

1. The payload is split into chunks no larger than the effective KCP write MTU.
2. Each chunk is prefixed with a one-byte internal frame flag.
3. The framed chunk is sent through KCP.
4. KCP output datagrams are forwarded upstream to the next node.

When datagrams come back from the next node:

1. The complete session envelope, exact nonce pair and expected wire kind are validated before FEC decoding.
2. KCP receives the datagram.
3. Completed KCP payloads are drained.
4. The one-byte internal frame flag is removed.
5. Data frames are forwarded downstream to the previous node as reconstructed stream payload.

## Internal frame flags

Inside the KCP payload, `KcpClient` uses a one-byte flag:

| Flag | Meaning |
| --- | --- |
| `0x00` | Data frame. Bytes after the flag are real stream payload. |
| `0xF0` | Ping frame. Used as an internal keepalive marker. |
| `0xFF` | Close frame. Requests shutdown of the paired line. |

Data frames containing only the flag are discarded. An empty KCP message has no
flag and closes the affected connection, as does an unknown flag or a completed
KCP message larger than the local receive buffer. Incomplete KCP messages wait
for their remaining fragments.

## Sending MTU and padding

Optional integer `send-mtu` inherits core `misc.mtu` at construction (the core fallback
is 1500). The supported range is **118..65535 without FEC**, or **126..65535 with
FEC**. It is an IPv4-based outgoing packet budget in bytes. Invalid explicit or inherited
values reject construction; an explicit supported override can replace an
unsupported core default. Null, wrong types, fractions, zero, negatives and
out-of-range numbers are errors. Each instance keeps its validated sending MTU unchanged.

With `F = 0` without FEC or `F = 8` with FEC:

```text
KCP MTU = min(send-mtu - 20 - 8 - 40 - F, 64000)
application chunk = KCP MTU - 24 - 1
```

The 20-byte IPv4 and 8-byte UDP allowances are fixed. Every packet also carries a 40-byte session envelope outside KCP/FEC. The 64,000-byte decimal cap
covers the complete KCP packet, including its 24-byte header. The one-byte frame
flag occupies KCP payload space; `required_padding_left = 1` provides room for it.
The effective KCP MTU governs data and aggregated acknowledgement/control output.
FEC adds at most 8 bytes to that output, including parity packets.

Receiving uses independent protocol limits: at most 64000 bytes for a KCP packet,
or 64008 bytes for an FEC shard, excluding the 40-byte session envelope. Peers
may use different `send-mtu` values. An incoming packet is not rejected merely
because it exceeds the receiver's own sending budget; framing, session identity,
and FEC validation still apply. There is no MTU negotiation.

At `send-mtu: 1500`, KCP MTU/application chunk are **1432/1407** without FEC and
**1424/1399** with FEC. Budgets of 64068 without FEC or 64076 with FEC reach the
cap; larger valid settings, including 65535, retain KCP MTU 64000 and application
chunk 63975. The configured budget itself is not capped to 64000.

This is not path-MTU discovery or negotiation. An ordinary IPv6 header needs 20
more bytes than the fixed IPv4 allowance, so a 1500 budget can permit a 1520-byte
IPv6 packet. IPv4 options, IPv6 extension headers and later wrappers need extra
operator headroom. No family-dependent adjustment occurs.

## FEC behavior

With `fec: true`, outbound KCP datagrams are wrapped in Reed-Solomon FEC packets. Data shards are emitted immediately.
After each configured data-shard block, parity shards are emitted.

On receive, the decoder:

- accepts FEC-wrapped KCP datagrams
- feeds valid data shards into KCP
- tries to recover missing KCP datagrams from parity shards
- drops invalid FEC packets conservatively

FEC adds bandwidth overhead. With the default `10` data shards and `3` parity shards, a full block carries about 30
percent extra parity traffic, plus FEC headers.

## Backpressure

The client combines its local KCP backlog pressure with carrier pressure before
notifying the previous application stream. The application remains paused while
either reason is active. Carrier Pause/Resume notifications, including repeats,
are relayed only when the local KCP hold is absent. Local pressure transitions
notify the application only while the carrier is not paused; neither reason can
release the other's hold. Application-side Pause/Resume still maps to the carrier.

After admitting the complete input and settling KCP packet output, the node
compares queued and unacknowledged KCP segments with `kcp-send-buffer-limit`.
Crossing above the threshold sets the local hold; falling below it clears that
hold, and equality preserves its state. When the setting is `0`, the threshold
is derived from the current KCP windows. ACK-only input can clear the local hold
without another outgoing packet. State is recorded before synchronous
notification, and no notification targets a finished application.

The setting remains a soft segment-count threshold, not a hard memory or
admission limit. Ready KCP data, acknowledgements, retransmissions and due pings
continue while the application is paused. KCP windows, timers and the receive
timeout remain in force. Every payload still needs KCP/FEC processing, so the
node cannot bypass itself.

## Close and timeout behavior

Application Finish immediately detaches and clears the borrowed application state. Its owner may destroy that line as soon as Finish returns. The owned transport and stable session continue draining previously accepted KCP output for the negotiated interval `D = min(client setting, server setting)`.

The fixed send deadline starts at the first local Finish or peer CLOSE. Once preceding data is acknowledged, the sender queues CLOSE exactly once and waits for its KCP acknowledgment. A flush alone never confirms delivery. At the deadline, unacknowledged sending stops and is reported unconfirmed. Received traffic and handshake progress never extend that deadline. Finish before negotiation uses the local interval initially and can only shorten it after negotiation.

On peer CLOSE, preceding inbound data is delivered before application Finish, the application retires once, and accepted outgoing data retains the same bounded drain. The driver enters closing before publishing the KCP CLOSE ACK. It keeps KCP receive state so duplicate CLOSE packets receive another ACK without reopening an application or extending retention.

A peer-only responder remains until first CLOSE receipt plus D. A locally acknowledged CLOSE at A retains an ACK-capable responder until A + D, including simultaneous close. Expired local sending preserves an earlier peer-ACK obligation. Retention is at most 2D from the first closing event: with defaults, at most 30 seconds to send and 60 seconds total. ACK-only retention uses a deadline timer and input-triggered ACK flushes, with expired PUSH output filtered before FEC.

`no-recv-timeout-ms` independently detects silence during ordinary operation; fixed close deadlines govern closing. Transport Finish, fatal protocol failure and process shutdown abort immediately. Worker quiescence detaches timer roots, and worker Stop drains all owned transports without waiting for graceful close. KCP acknowledgment confirms peer transport receipt, not remote application consumption or persistence. This protocol does not provide TCP half-close.

## Common mistakes

- Do not put a stream-only tunnel after `KcpClient`; the next side must preserve packet boundaries.
- Do not enable FEC on only one side.
- Do not use mismatched FEC shard counts.
- Do not assume KCP removes all loss; it retransmits, and optional FEC can help with moderate loss, but severe or bursty
  loss still hurts.
- Do not set `no-recv-timeout-ms` less than or equal to `ping-interval-ms`.
