# EncryptionClient

The default is stream mode. Set `packet-mode: true` for complete IPv4 TCP/UDP
packets; that profile encrypts only the transport payload and has no TLS-like header.

`EncryptionClient` is the client-side peer for `EncryptionServer`. It encrypts
upstream payloads into TLS-like application-data records and decrypts downstream
records back into plain WaterWall payloads.

Use it when you want AEAD protection inside a WaterWall stream chain without
using a full TLS handshake.

:::warning
`EncryptionClient` is not `TlsClient`. It does not perform a TLS handshake, does
not verify certificates, and does not provide SNI or ALPN. In stream mode it uses a
TLS-like record shape for encrypted payload framing.
:::

## Typical Placement

Direct in-process pair:

```text
TesterClient -> EncryptionClient -> EncryptionServer -> TesterServer
```

Two-server TCP tunnel:

```text
client side: TcpListener -> EncryptionClient -> TcpConnector
server side: TcpListener -> EncryptionServer -> TcpConnector
```

The client and server settings must match. Any stream tunnels between them must
preserve the encrypted record bytes end to end.

## What It Does

The default is stream mode. `packet-mode: true` selects the separate packet
profile below; this list describes the default stream behavior.

- Derives one 32-byte AEAD key from `password`, `salt`, and `kdf-iterations`.
- Encrypts upstream payloads.
- Splits upstream plaintext larger than `max-frame-size` into multiple records.
- Wraps each encrypted chunk in a TLS-like application-data record.
- Buffers downstream encrypted bytes until complete records are available.
- Validates record headers and body lengths before decrypting.
- Decrypts downstream records and forwards recovered plaintext to the previous
  node.
- Closes both directions on malformed records or AEAD authentication failure.

In stream mode, `EncryptionClient` is a middle stream tunnel. It does not create sockets and it
does not create packet lines.

## Configuration Example

```json
{
  "name": "enc-client",
  "type": "EncryptionClient",
  "settings": {
    "algorithm": "chacha20-poly1305",
    "password": "replace-with-a-strong-secret",
    "salt": "chain-a",
    "kdf-iterations": 20000,
    "max-frame-size": 16356
  },
  "next": "transport"
}
```

Matching server-side settings:

```json
{
  "name": "enc-server",
  "type": "EncryptionServer",
  "settings": {
    "algorithm": "chacha20-poly1305",
    "password": "replace-with-a-strong-secret",
    "salt": "chain-a",
    "kdf-iterations": 20000,
    "max-frame-size": 16356
  },
  "next": "service"
}
```

## Required Fields

Top-level fields:

| Field | Type | Description |
| --- | --- | --- |
| `name` | string | User-chosen node name. Must be unique inside the config file. |
| `type` | string | Must be exactly `"EncryptionClient"`. |
| `next` | string | Required. The next stream node receives encrypted records. |
| `settings` | object | Required. Must contain at least `password`. |

Required `settings` fields:

| Field | Type | Description |
| --- | --- | --- |
| `password` | non-empty string | Shared secret used to derive the AEAD key. Must match the server side. |

`EncryptionClient` must also have a previous node in the chain. It is not a
chain head or chain end.

## Optional Settings

| Setting | Type | Default | Description |
| --- | --- | --- | --- |
| `packet-mode` | boolean | `false` | Select complete IPv4 TCP/UDP payload encryption, described below. |
| `algorithm` | string or numeric enum | `chacha20-poly1305` in stream mode; `xchacha20-poly1305` in packet mode | AEAD algorithm. `method` is accepted as a compatibility alias when `algorithm` is absent. |
| `salt` | string | `waterwall-encryption` | Salt input for the WaterWall key derivation process. Must match the server side. |
| `kdf-iterations` | integer | `12000` | Key derivation rounds. Must be in range `1` through `1000000`. |
| `max-frame-size` | integer | `16356` | Maximum plaintext bytes per encrypted record. Must be in range `1` through `16356`. |

Accepted stream algorithm strings:

| Algorithm | Accepted values |
| --- | --- |
| ChaCha20-Poly1305 | `chacha20-poly1305`, `chacha20poly1305`, `chacha20`, `chacha` |
| AES-256-GCM | `aes-gcm`, `aes256gcm`, `aes-256-gcm`, `aes256-gcm` |

Numeric algorithm values are also accepted by the parser for compatibility with
WaterWall's dynamic-value enum, but string values are clearer and recommended.

If AES-GCM is selected and the active crypto backend does not provide AES-GCM,
startup fails.

## Packet Mode

Set `"packet-mode": true` explicitly when the node receives complete IPv4
packets. This selects Layer-3 metadata and a stateless packet transform instead
of the stream record reader. It is not selected merely because a different part
of the chain has a packet adapter. The default remains `false` for stream use.

```json
{
  "packet-mode": true,
  "algorithm": "xchacha20-poly1305",
  "password": "replace-with-a-long-random-shared-secret"
}
```

Packet mode accepts only XChaCha20-Poly1305, which is also its default when
`algorithm` is omitted. Stream mode continues to use ChaCha20-Poly1305 or
AES-GCM and rejects XChaCha20-Poly1305. `max-frame-size` belongs to stream mode
and is rejected in packet mode; packet data is never split into records.
`password`, `salt` and `kdf-iterations` still select the shared base key. Packet
mode hashes the password with SHA-256 for its repeated BLAKE2s KDF key, allowing
long passwords without exceeding BLAKE2s key limits, then derives separate keys
for client-to-server and server-to-client traffic.
Both peers must agree on the password, salt and iteration count.

For each complete, unfragmented IPv4 TCP or UDP packet:

```text
before: [IPv4 header][TCP/UDP header][transport payload]
after:  [IPv4 header][TCP/UDP header][24-byte nonce][encrypted payload][16-byte tag]
```

The actual IPv4 IHL and TCP data offset locate the payload, so IP and TCP options
remain visible and preserved. There is no TLS-like header and no extra IP header.
Exactly one packet is produced per accepted input, including an empty transport
payload. Every encoding uses a fresh nonce from the cryptographic random source;
packets can be lost or reordered without retaining partial data or preventing
later decryption. An empty `sbuf_t` is not a complete packet and is dropped.

IP total length, UDP length and visible checksums are updated; sequence,
acknowledgment, flags, ports and addresses are preserved. IPv4 TCP/UDP checksums
must normally be valid, with disabled UDP checksum zero accepted and preserved.
A pending checksum-repair flag authorizes repair of outgoing checksums and makes
received visible checksums non-authoritative, but never bypasses authentication.
Explicit repair enables a UDP checksum even when its old value was zero.
The packet's exposed protocol is authenticated. Mutable IP/transport fields are
not authenticated, allowing address/port rewriting and normal TTL changes.
Encryption protects the transport payload, not those visible fields or timing.
It does not implement replay rejection.

Both directions reject IPv6, fragments (MF or nonzero offset), malformed lengths,
unsupported visible protocols, trailing buffer bytes, invalid TCP offsets, and
UDP lengths that differ from the IPv4 payload length. DF alone is accepted.
Reassemble fragments before this node. Wrong keys and invalid authentication
tags drop only that packet; the shared packet line stays alive. No failure sends
`Finish` or destroys a packet line.

The format adds **40 bytes**. The final IPv4 packet must fit `65535` bytes, so
its plaintext input can be at most `65495` bytes; the real carrier/device path
can impose a much smaller MTU. The node does not fragment, discover PMTU, adjust
TCP MSS, or recalculate TCP sequence progression for the expanded payload.
It advertises 24 bytes of left padding for the nonce; tag space is managed by
the packet encoder. Native TCP endpoints still own their sequence space, so
this is not a promise of transparent TCP behavior through arbitrary middleboxes.

For FakeTcpHeader, the most convenient setup is its own optional `password`
setting. It inserts and configures the appropriate Encryption node privately,
places encryption after fake-header encoding, and includes the 40 bytes in its
sequence reservations and 1500-byte carrier limit. The protocol byte and original
transport header are then encrypted together behind the visible fake TCP header.
Manually adding a separate Encryption node does not tell FakeTcpHeader to account
for that extra expansion. See the FakeTcpHeader node references for chain order.

The following record framing, frame limits, buffering and stream lifecycle
sections describe `packet-mode: false`. Packet mode uses chain-owned packet
lines, no per-line reader state, and the normal packet-tunnel callback defaults.

## Key Derivation

This describes the base key. Packet mode derives the two direction-specific keys
from that base as described above.

Both peers derive the same 32-byte key from:

- `password`
- `salt`
- `kdf-iterations`

The implementation uses a WaterWall-specific BLAKE2s-based derivation loop, not
PBKDF2 or Argon2. The derived key is stored in tunnel state and zeroed when the
tunnel instance is destroyed.

For the encrypted path to work, both sides must use the same `password`, `salt`,
`kdf-iterations`, and compatible `algorithm`.

## Stream Wire Format

Each encrypted payload chunk is encoded as:

```text
5-byte TLS-like header | 12-byte nonce | AEAD ciphertext | 16-byte tag
```

Header fields:

| Field | Value |
| --- | --- |
| record type | `0x17`, TLS application data |
| version | `0x0303` |
| body length | Big-endian 16-bit length of `nonce + ciphertext + tag` |

The 5-byte header is used as AEAD associated data. The selected algorithm is not
sent in the record header; it must be configured consistently on both peers.

## Stream Limits and Padding

| Value | Size |
| --- | --- |
| TLS-like header | `5` bytes |
| nonce | `12` bytes |
| AEAD tag | `16` bytes |
| maximum TLS-like record body | `16384` bytes |
| maximum plaintext per record | `16356` bytes |
| required left padding | `17` bytes |

`required_padding_left` is `17`, enough for the 5-byte header and 12-byte nonce
that are prepended before encryption.

If an upstream plaintext payload is larger than `max-frame-size`, the client
splits it into multiple encrypted records. Zero-length payload buffers are
recycled and not forwarded.

## Stream Direction Behavior

| Direction | Behavior |
| --- | --- |
| upstream payload | Encrypt, frame, and send to `next`. |
| downstream payload | Buffer, parse, decrypt, and send plaintext to `prev`. |

Complete downstream frames may arrive split across multiple payload callbacks or
several frames may arrive in one callback. The read stream keeps buffered bytes
until complete records can be parsed.

Complete records are drained as they become available; only an incomplete record
remains buffered between callbacks. Once its header is complete, the record length
is checked against `max-frame-size` before waiting for the rest of the body.

## Stream Lifecycle Behavior

On upstream `Init`, the client initializes its per-line read stream and forwards
upstream `Init` to `next`.

On upstream `Finish`, it destroys local line state and forwards upstream
`Finish` to `next`. On downstream `Finish`, it destroys local line state and
forwards downstream `Finish` to `prev`.

Pause and resume are forwarded directionally:

| Callback | Forwarded to |
| --- | --- |
| upstream pause/resume | next tunnel upstream |
| downstream pause/resume | previous tunnel downstream |

Upstream `Est` and downstream `Init` are disabled callbacks for this node.

## Notes and Caveats

- Use it with a matching `EncryptionServer`.
- This node protects payload bytes, but it does not hide that data is flowing
  inside WaterWall's TLS-like record format.
- `password` should be long, random, and kept out of public configs.
- `max-frame-size` should normally match on both sides. A receiver rejects
  records larger than its configured maximum.
- Use `TlsClient`/`TlsServer` when you need real TLS semantics.
