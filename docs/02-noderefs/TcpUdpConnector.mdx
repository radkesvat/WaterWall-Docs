# TcpUdpConnector

`TcpUdpConnector` is a chain-end adapter wrapper around `TcpConnector` and `UdpConnector`. It creates one internal TCP
connector and one internal UDP connector with the same connector settings, then chooses the correct child connector for
each line from WaterWall routing metadata.

This node does not encapsulate TCP inside UDP and does not encapsulate UDP inside TCP. It is a dual-protocol connector
wrapper.

## Typical Placement

Use the complete chain that matches where destination metadata comes from:

```text
DNS relay: TcpUdpListener -> TcpUdpConnector
SOCKS5:    TcpUdpListener -> Socks5Server -> TcpUdpConnector
IP flows:  TunDevice -> PacketsToConnection -> TcpUdpConnector
```
For a DNS relay, configure a fixed backend address/port; TCP and UDP use that
same resolver. For SOCKS5, set `udp: true` on Socks5Server and use destination
context on the connector. TcpUdpListener supplies both the TCP control
connection and the dynamic UDP provider; see the
[complete SOCKS5 configuration](./Socks5Server.mdx#complete-tcpudp-topology-example).

For captured IP traffic, PacketsToConnection converts raw IPv4 TCP/UDP flows into
application lines and supplies their original destinations. Configure the
connector to follow that context and arrange TUN routes for the intended traffic.
The TUN node does not itself make raw IP buffers suitable for a connector.

## Basic Example

```json
{
  "name": "mixed-out",
  "type": "TcpUdpConnector",
  "settings": {
    "address": "198.51.100.10",
    "port": 443,
    "dns-behaviour": {"resolve": true, "strategy": "prefer-ipv4"},
    "nodelay": true,
    "fastopen": false,
    "large-send-buffer": true,
    "large-recv-buffer": true,
    "interface": "eth0",
    "fwmark": 10,
    "balance-mode": "connection"
  }
}
```

Both TCP lines and UDP peer lines use the same configured destination. TCP lines are handled by the internal
`TcpConnector`; UDP lines are handled by the internal `UdpConnector`.

## Dynamic-Destination Example

```json
{
  "name": "mixed-out",
  "type": "TcpUdpConnector",
  "settings": {
    "address": "dest_context->address",
    "port": "dest_context->port",
    "dns-behaviour": {"resolve": true, "strategy": "prefer-ipv4"},
    "large-send-buffer": true,
    "large-recv-buffer": true
  }
}
```

Use this form after `Socks5Server`, `VmessServer`, or `PacketsToConnection`,
which supply a destination and protocol for each flow. A SniffRouter branch
selects where to forward the line; it does not by itself supply a complete
requested destination. If no earlier node provided one, configure a fixed
backend address and port on that branch's connector.

## Weighted Destination Example

```json
{
  "name": "mixed-out",
  "type": "TcpUdpConnector",
  "settings": {
    "addresses": [
      {
        "address": "198.51.100.10",
        "port": 443,
        "weight": 3
      },
      {
        "address": "198.51.100.20",
        "port": 443,
        "weight": 1
      }
    ],
    "dns-behaviour": {"resolve": true, "strategy": "prefer-ipv4"},
    "large-send-buffer": true,
    "large-recv-buffer": true,
    "balance-mode": "connection"
  }
}
```

The same `addresses` array is passed to both child connectors. Use destination forms that are valid for both
`TcpConnector` and `UdpConnector` if both protocols may be selected.

## Required Fields

Top-level fields:

| Field | Type | Description |
| --- | --- | --- |
| `name` | string | User-chosen node name. Must be unique inside the config file. |
| `type` | string | Must be exactly `"TcpUdpConnector"`. |
| `settings` | object | Shared connector settings passed to both internal child connectors. Must be a non-empty object. |

`TcpUdpConnector` is a chain end. It must not have `next`.

Required destination settings:

| Style | Required fields | Description |
| --- | --- | --- |
| Single destination | `address` and `port` | Every selected child connector uses the same destination rule. |
| Weighted destinations | `addresses` | Each line chooses from a weighted destination list. The legacy misspelling `adresses` is accepted by the child connectors, but new configs should use `addresses`. |

Do not mix `addresses` with top-level `address` or `port`.

## Shared Connector Settings

The settings object must be acceptable to both child connectors at startup. This matters even if you expect only one
protocol at runtime, because the wrapper creates both internal connectors while loading the config.

| Setting | Applies to | Description |
| --- | --- | --- |
| `address` | TCP and UDP children | Constant address, domain, `"src_context->address"`, or `"dest_context->address"`. |
| `port` | TCP and UDP children | Constant port, `"src_context->port"`, or `"dest_context->port"`. |
| `addresses` | TCP and UDP children | Weighted destination list. |
| `dns-behaviour` | TCP and UDP children | Shared local lookup, address selection and DNS transport policy. |
| `large-send-buffer` | TCP and UDP children | Sets `SO_SNDBUF` where supported. |
| `large-recv-buffer` | TCP and UDP children | Sets `SO_RCVBUF` where supported. |
| `fwmark` | TCP and UDP children | Applies a Linux-style socket mark where supported. |
| `interface` | TCP and UDP children | Restricts outbound sockets to a network device where supported. |
| `source-ip` | TCP and UDP children | Binds outbound sockets to a specific local source IP. |
| `nodelay` | TCP child | Enables `TCP_NODELAY` on outbound TCP sockets. |
| `fastopen` | TCP child | Requests `TCP_FASTOPEN` where supported. |
| `balance-mode` | UDP child | Controls UDP weighted destination selection: `"connection"` or `"packet"`. |

For full destination selection, DNS, socket-option, and UDP balance-mode details, see the `TcpConnector` and
`UdpConnector` pages.

:::warning
`UdpConnector` supports UDP-only port syntax such as `"random(x,y)"`, but `TcpConnector` does not. Because
`TcpUdpConnector` creates both child connectors, avoid UDP-only destination syntax here unless the current code has also
made it valid for `TcpConnector`.
:::

## DNS behaviour

Resolving a hostname means looking up its IP address before connecting or sending.
The selected TCP or UDP connector first prepares the destination from this node's
settings. It performs a lookup only when that destination is an unresolved
hostname and local resolution is enabled. Literal IPs and already-resolved
destinations need no lookup.

This is the endpoint the connector will reach: the application target in a direct
chain, or the proxy server after a proxy client. Both children use the same DNS
policy. Without `dns-behaviour`, local resolution is enabled in `native` mode,
using the core `dns.domain-strategy` preference.

Configure this lookup with `settings.dns-behaviour`:

```json
{
  "dns-behaviour": {
    "resolve": true,
    "mode": "direct",
    "strategy": "prefer-ipv4",
    "servers": ["203.0.113.53:53"]
  }
}
```

The address is a documentation placeholder; replace it with your resolver.

| Field | Meaning |
| --- | --- |
| `resolve` | Required boolean: `true` allows lookup of unresolved hostnames; `false` disables local lookup. |
| `mode` | `native` (default when enabled), `direct`, or `chain`. |
| `strategy` | `core-settings`, `accept-dns-returned-order`, `prefer-ipv4`, `prefer-ipv6`, `only-ipv4`, or `only-ipv6`; omission uses this consumer's default address preference. |
| `servers` | 1–32 numeric IP, IP:port or [IPv6]:port endpoints; required for direct/chain and rejected for native. |
| `dns-next` | Nonempty DNS-entry name for chain only. |

`native` uses core DNS settings and the worker's shared resolver. It is the default
DNS transport when local resolution is enabled.

`direct` sends DNS queries through a private WaterWall TCP/UDP connector to the
servers you specify.

`chain` sends DNS queries through a selected chain. Use a path with encryption,
such as your VPN, to protect those queries; the mode alone does not encrypt them.
The DNS path must carry both UDP queries and TCP fallback. A route or lookup
failure does not switch to native DNS or another mode.

For `chain`, set `dns-next` to the name of a separate DNS branch that supports
both UDP and TCP. The branch must not already belong to another node. This node
has no default DNS branch; naming this node itself is not allowed.

The disabled form is exactly `"dns-behaviour": {"resolve": false}`. It rejects `mode`, `strategy`, `servers` and `dns-next`. Empty/null/non-object policies, unknown fields and numeric strategies are rejected. Strategy names use the canonical lowercase strings above. `core-settings` chooses address preference only and never changes DNS transport.

With `resolve: false`, destination preparation still runs. Numeric or already-resolved destinations work; unresolved hostnames fail through the normal line/datagram path without an OS/native DNS fallback.

Both private TCP/UDP children use one authoritative provider, channel/cache owner and DNS-branch binding. This node has no default shared DNS entry; supply `dns-next` for chain mode.

See [DomainResolver](./DomainResolver.mdx) for native, direct and protected-chain configuration examples and core option limits. This policy controls lookups owned by this node; it does not configure PTC fake DNS, TunDevice system DNS or every DNS source in the program.

## Protocol Selection

During upstream `Init`, `TcpUdpConnector` chooses one child connector and stores that choice in this node's per-line
state. Later upstream callbacks use the stored child, so the selected connector remains stable even if another node
updates routing context fields later.

Selection order:

| Step | Behavior |
| --- | --- |
| 1 | Check `line->routing_context.dest_ctx`. |
| 2 | If the destination context has an exact TCP protocol flag, select the internal `TcpConnector`. |
| 3 | If the destination context has an exact UDP protocol flag, select the internal `UdpConnector`. |
| 4 | If the destination context has no protocol flags, fall back to `line->routing_context.src_ctx`. |
| 5 | If the source context has an exact TCP or UDP protocol flag, select the matching child connector. |
| 6 | If no exact protocol can be selected, treat it as a fatal configuration or routing error. |

Destination protocol wins over source protocol. That allows routing-aware nodes to receive one transport on the inbound
side and still choose the outbound transport from the requested destination.

## Runtime Flow

At startup, `TcpUdpConnector` creates two internal child tunnels:

- `TcpConnector`, named like `<node-name>.tcp-connector`
- `UdpConnector`, named like `<node-name>.udp-connector`

Both children are inserted into the chain below the wrapper. Runtime callbacks work like this:

1. the previous node sends upstream `Init` to `TcpUdpConnector`
2. the wrapper selects and initializes one child connector
3. upstream payload, pause, resume, establishment, and finish callbacks are forwarded to that same child
4. downstream callbacks from the child connector enter `TcpUdpConnector`
5. the wrapper forwards downstream callbacks to the previous node

## Line Ownership

`TcpUdpConnector` does not create or destroy connection lines. The previous adapter or bridge owns line creation.

The wrapper only stores the selected child connector in a small per-line state. It clears that state before forwarding a
real upstream or downstream finish. It never calls `lineDestroy()`.

## Common Mistakes

- Do not use `TcpUdpConnector` as a protocol converter. It only chooses between TCP and UDP child connectors.
- Do not add `next`; this node is a chain end.
- Do not expect separate TCP and UDP destination settings. Both child connectors receive the same settings object.
- Do not use UDP-only destination syntax such as `"random(x,y)"` in configs that must also create the internal
  `TcpConnector`.
- Do not place it after a node that fails to provide exact TCP or UDP protocol metadata.

## UDP splice sending

UDP receives remain ordinary buffers. On an eligible Linux chain, UDP sends accept ordinary data or a real prefix plus a private-pipe body as one datagram to its explicit destination, including empty datagrams. Supported layouts use pipe-to-socket splice. Highly fragmented pipes, or failure to establish a safe fragment bound before sending, use a complete ordinary fallback before socket assembly. Oversized datagrams are rejected without splitting.

Pressure before assembly retains the existing drop policy, without a UDP retry queue. An incomplete splice or failed commit after priming retires only the affected socket; its associated normal lines close through their owners. Shared-socket peers can therefore close together. No truncated remainder is retried, and unrelated sockets remain active. Ordinary sends retain their existing error policy.

The flag does not bypass platform support, `misc.splice`, packet exclusion, or support from every node in the final expanded/merged chain. No end-to-end zero-copy or measured performance gain is promised.

Both internal connector nodes retain their capability flags. Eligibility includes both branches and inserted helpers, even for a TCP line. Protocol selection and UDP peer routing remain unchanged.
