# HeaderServer

`HeaderServer` either consumes the one-time 2-byte port header produced by
`HeaderClient`, or sets a constant destination port during upstream `Init`.

In dynamic header mode, it reads the header, writes the decoded port into
`line->routing_context.dest_ctx.port`, then initializes the next upstream tunnel.

## Typical Placement

Paired with `HeaderClient`:

```text
client side: TcpListener -> HeaderClient -> TcpConnector
server side: TcpListener -> HeaderServer -> TcpConnector
```

Constant override mode, without `HeaderClient`:

```text
TcpListener -> HeaderServer -> TcpConnector
```

## What It Does

- Requires `settings.override` to choose dynamic-header mode or constant mode.
- In dynamic-header mode, delays upstream `Init` to `next` until the 2-byte
  header has been received.
- Buffers upstream bytes while waiting for the header.
- Allows the 2-byte header to arrive split across payload callbacks.
- Writes the decoded port into the destination routing context.
- Forwards any remaining buffered payload after the header is consumed.
- In constant mode, sets the destination port immediately during upstream
  `Init` and does not consume any payload bytes.
- Forwards lifecycle callbacks only after the line is established toward `next`.

`HeaderServer` is a normal layer-4 stream tunnel. It does not create sockets,
does not create packet lines, and does not create or destroy `line_t` objects.

## Configuration Example

Consume a port header from `HeaderClient`:

```json
{
  "name": "header-server",
  "type": "HeaderServer",
  "settings": {
    "override": "dest_context->port"
  },
  "next": "connector"
}
```

Set a constant destination port:

```json
{
  "name": "header-server",
  "type": "HeaderServer",
  "settings": {
    "override": 443
  },
  "next": "connector"
}
```

## Required Fields

Top-level fields:

| Field | Type | Description |
| --- | --- | --- |
| `name` | string | User-chosen node name. Must be unique inside the config file. |
| `type` | string | Must be exactly `"HeaderServer"`. |
| `settings` | object | Required. Must contain `override`. |
| `next` | string | Required. The next layer-4 stream node receives the routed line. |

Required `settings` fields:

| Field | Type | Description |
| --- | --- | --- |
| `override` | number or string | Selects the destination-port override behavior. |

`HeaderServer` must also have a previous node in the chain. It is not a chain
head or chain end.

## `settings.override`

Accepted values:

| Value | Meaning |
| --- | --- |
| `"dest_context->port"` | Read the 2-byte upstream header and set `dest_ctx.port` from it. |
| `"line->dest_ctx->port"` | Compatibility alias for `"dest_context->port"`. |
| `1` through `65535` | Set this constant destination port during upstream `Init`. |

Startup fails if `override` is missing, is not one of the accepted string
values, or is a numeric value outside `1` through `65535`.

## Dynamic Header Mode

When `override` is `"dest_context->port"` or `"line->dest_ctx->port"`,
`HeaderServer` starts each line in a wait-header phase.

Upstream `Init` initializes local state but is not immediately forwarded to
`next`. The tunnel waits for upstream payload bytes, buffers them in a
`buffer_stream_t`, and reads the first 2 bytes as a big-endian port header.

After the header is decoded:

1. the decoded port is written to `line->routing_context.dest_ctx.port`
2. the line phase becomes established
3. upstream `Init` is forwarded to `next`
4. any payload remaining after the 2-byte header is forwarded upstream

This is why `HeaderServer` can handle a header split across payload callbacks.

Decoded header ports below `10` are treated as invalid. If that happens, the
server recycles buffered data, destroys local line state, and closes the line
toward the previous side. If the next side had already been initialized, it is
closed too.

## Constant Override Mode

When `override` is a number, `HeaderServer` does not read or strip any payload
header.

During upstream `Init`, it sets:

```text
line->routing_context.dest_ctx.port = configured port
```

Then it immediately forwards upstream `Init` to `next`. All upstream payload is
forwarded unchanged.

Do not place `HeaderClient` before this mode unless you intentionally want the
2-byte header to become application payload.

## Direction Behavior

| Direction | Dynamic-header mode |
| --- | --- |
| upstream `Init` | Initialize local state, but delay `next` init until the header is decoded. |
| upstream payload before header | Buffer until at least 2 bytes are available. |
| upstream payload after header | Forward to `next`. |
| upstream pause/resume before header | Ignored; there is no initialized next side yet. |
| upstream pause/resume after header | Forward to `next`. |
| downstream `Est` / pause / resume before header | Ignored. |
| downstream payload before header | Recycled, then the previous side is closed. |
| downstream callbacks after header | Forward to the previous node. |

In constant mode, the line starts established during upstream `Init`, so normal
upstream and downstream callbacks are forwarded directionally.

`UpStreamEst` and `DownStreamInit` are disabled callbacks for this node.

## Finish Behavior

On upstream `Finish`, `HeaderServer` destroys local line state. It forwards the
finish to `next` only if the line had already completed header routing and
initialized the next side.

On downstream `Finish`, it destroys local line state and forwards the finish to
the previous node.

On protocol error, it destroys local state, closes `next` if `next` had already
been initialized, and closes the previous side.

The tunnel does not call `lineDestroy()` because it does not create the line.

## Limits and Padding

| Value | Size |
| --- | --- |
| consumed header | `2 bytes` |
| minimum accepted decoded header port | `10` |
| `required_padding_left` | `0 bytes` |

The server only consumes a header in dynamic-header mode. It does not prepend
bytes and therefore does not require left padding.

## Notes and Caveats

- Use dynamic-header mode with `HeaderClient`.
- Use constant mode by itself when you only want to force a fixed destination
  port.
- The header value is encoded in network byte order.
- While waiting for the header, `HeaderServer` has not initialized the next
  tunnel yet.
- It should not be used as packet-line shared state.
