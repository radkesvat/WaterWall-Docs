# Bgp4Client

`Bgp4Client` is a layer-4 stream tunnel that wraps upstream payloads in
BGP-like frames and unwraps downstream frames produced by `Bgp4Server`.

It is intended to be paired with `Bgp4Server`:

```text
client: TcpListener(127.0.0.1:18080) -> Bgp4Client -> TcpConnector(gateway:7443)
server: TcpListener(0.0.0.0:7443) -> Bgp4Server -> TcpConnector(127.0.0.1:8080)
```

The client connector dials the server-side WaterWall listener on `7443`; the
server connector selects the actual HTTP service on `127.0.0.1:8080`. Point
the local application at `127.0.0.1:18080`. The two BGP nodes frame and unframe
the bytes; they neither rewrite HTTP nor choose a destination.

:::warning
`Bgp4Client` does not implement real BGP routing, BGP peering, route exchange,
or BGP authentication. It only uses a BGP-like frame shape as stream
camouflage/framing.
:::

## What It Does

- Initializes one per-line read stream and first-frame state during upstream
  `init`.
- On the first upstream payload, prepends a synthetic BGP OPEN body before the
  application bytes.
- Wraps upstream payloads as BGP-like frames.
- Chooses a random non-OPEN BGP type for later upstream payload frames.
- Parses downstream BGP-like frames from a stream buffer.
- Strips downstream frame metadata and forwards the recovered payload to the
  previous tunnel.
- Closes both directions when it receives malformed framed data.

`Bgp4Client` is a normal stream tunnel. It does not create network sockets and
does not create or destroy packet lines.

## Configuration Example

Client side:

```json
{
  "name": "bgp4-client",
  "type": "Bgp4Client",
  "settings": {},
  "next": "transport-out"
}
```

Paired server side:

```json
{
  "name": "bgp4-server",
  "type": "Bgp4Server",
  "settings": {},
  "next": "target"
}
```

The `password` field is accepted for compatibility with the old configuration
shape, but it is not used for encryption or authentication in the current
protocol logic.

## Required Fields

Top-level fields:

| Field | Type | Description |
| --- | --- | --- |
| `name` | string | User-chosen node name. Must be unique inside the config file. |
| `type` | string | Must be exactly `"Bgp4Client"`. |
| `next` | string | The next stream node that receives wrapped frames. |

## Optional Settings

| Setting | Type | Default | Description |
| --- | --- | --- | --- |
| `password` | string | — | Accepted but ignored; it provides neither encryption nor authentication. |

No other settings are currently parsed.

## Frame Format

All upstream payloads are wrapped as:

```text
16-byte marker | 2-byte body length | 1-byte BGP type | body
```

Field details:

| Field | Value |
| --- | --- |
| marker | Sixteen bytes of `0xff`. |
| body length | Big-endian `uint16_t`. Covers the type byte plus body bytes. |
| BGP type | `1` for the first OPEN frame; random `2` through `5` for later payload frames. |
| body | Tunneled payload, or synthetic OPEN body plus tunneled payload for the first upstream frame. |

Supported type values used by the implementation:

| Type | Name |
| --- | --- |
| `1` | OPEN |
| `2` | UPDATE |
| `3` | NOTIFICATION |
| `4` | KEEPALIVE |
| `5` | ROUTE-REFRESH |

The frame length is not the standard BGP message length. In this tunnel it is
the older WaterWall contract: type byte plus body bytes, excluding the 16-byte
marker and 2-byte length field.

## First Upstream Payload

`Bgp4Client` does not send a standalone OPEN frame during `init`. Instead, the
first upstream payload is framed as BGP type `1` and the client prepends a
synthetic OPEN body before the application bytes.

Synthetic OPEN fields:

| Field | Behavior |
| --- | --- |
| version | Always `4`. |
| AS number | Random `uint16_t` generated when the tunnel instance is created. |
| hold time | `90` seconds. |
| router id | Random value generated when the tunnel instance is created. |
| optional parameter length | Random length from `3` through `10` bytes. |
| optional parameter bytes | Random bytes in the range `0` through `199`. |

After this first frame, `open_sent` is set for the line. Later upstream payloads
are wrapped without the synthetic OPEN prefix and use a random non-OPEN type.

Because `Bgp4Server` expects tunneled application data after the OPEN prefix,
the first OPEN frame must carry payload bytes after the synthetic OPEN body.

## Downstream Parsing

Downstream bytes are accumulated by the shared `splice_frame_reader_t` over a
`splice_stream_t`.

For each downstream frame, `Bgp4Client`:

1. Gathers the 19-byte header and checks the marker, length and non-OPEN type.
2. Rejects a declared body length that leaves no application payload.
3. Strips the framing metadata and forwards available payload bytes in order,
   without waiting for the rest of the frame.
4. Keeps the current frame's remaining length until its last byte is consumed,
   then starts reading the next header.

An incomplete header or unavailable body suffix returns control to the worker
until more input arrives. Nested-byte or retained-charge refusal closes the line
under the limits below.

## Limits

| Limit | Value | Notes |
| --- | --- | --- |
| Maximum body length | `65535` bytes | Includes the 1-byte type. |
| Maximum ordinary payload body | `65534` bytes | Payload plus type must fit in `65535`. |
| Nested receive logical bytes | `2162705` | Older retained wire bytes plus nested input, including the cached header. |
| Retained receive buffer charge | `4325410` | Settled after nested admission and after available body bytes drain; beneficial compaction precedes refusal. |
| Queued encoded bytes | `2162705` | Includes generated headers; checked before callbacks. |
| Queued encoded charge | `8 MiB` | Counts queued encoded buffers before handoff. |
| Maximum complete wire frame | `65553` bytes | Marker, length, type and body. |
| Required left padding | `39` bytes | Enough for frame prefix plus largest synthetic OPEN prefix. |

Both directions accept ordinary buffers, private-pipe splice buffers, and mixed
fragments. A fitting delivery is framed in place using reserved left padding
(39 bytes for the client, 19 for the server), including any existing resident
prefix. Larger outgoing deliveries are prepared as complete batches of separate
frame buffers before any callback; pipe creation or transfer pressure selects complete
ordinary best-fit fallback for the affected frame. There is no whole-delivery
ordinary aggregate.

The decoder caches the 19-byte marker/length/type header and forwards available
application body bytes incrementally. The server first gathers and validates the
ten fixed OPEN bytes, then consumes at most 255 optional bytes before releasing
application bytes. The remaining application's representation is preserved. The
client generates 3–10 optional bytes and subtracts the actual OPEN overhead from
its first frame's payload room. Empty deliveries emit nothing and do not consume
OPEN state. Exactly one OPEN is admitted per client line.

The shared fixed-header frame reader drains available body bytes from a top-level
receive batch before checking the incomplete remainder. That batch can exceed
**2,162,705 bytes** (`2 MiB + 65,553`). During a delivery callback, nested input
must fit that logical-byte limit together with older retained wire bytes,
including the cached header. It then joins the FIFO, and retained buffer charge
must fit **4,325,410 bytes** before nested admission returns. The same charge
limit applies to the incomplete remainder when the outer drain ends. Coalescing
or one beneficial compaction may release oversized backing storage before
refusal. Compaction may copy pipe-backed bytes into ordinary memory; the charge
limit bounds retained storage accounting, not process memory or transient peaks.
Incoming fragments have no entry-count cap. After available body bytes drain, the
incomplete remainder is smaller than 65,553 logical bytes.

Encoded output keeps its independent **2,162,705-byte limit**, including generated
headers, and **8 MiB retained-buffer charge limit**. These limits are independent of RAM profile,
pools, pipe capacity, platform and `misc.splice`. The maximum complete wire frame
is 65,553 bytes, and a non-OPEN frame carries at most 65,534 application bytes.

A decoded frame can produce several Payload callbacks; frame boundaries are not
application callback boundaries. If the connection ends during a frame, its
already delivered application prefix stays delivered. Both nodes borrow the
normal line and transform every payload, so neither can permanently bypass itself.
Pause and Resume use transparent default forwarding in both directions, including repeated
notifications. Available admitted bytes drain immediately without waiting for
Resume. A pump guard per direction preserves FIFO during reentrant callbacks;
the frame reader retains incomplete input, and the bounded output FIFO keeps
complete encoded batches ahead of reentrant input. The decoder validates any
complete FIFO-head header immediately after admission, including nested input;
only the outer drain delivers application bytes. Encoded batches pass their byte
and charge checks before their first callback.
Malformed data, retention-limit overflow or queue-capacity refusal closes only
the borrowed connection through its owner. Finish releases queued buffers and
pipes before forwarding away from the sender. These behaviors do not guarantee
zero-copy delivery or a throughput improvement.

## Data Flow

Upstream direction:

```text
previous node -> Bgp4Client wraps -> next node
```

Downstream direction:

```text
next node -> Bgp4Client unwraps -> previous node
```

`Bgp4Client` expects `Bgp4Server` on the opposite side. A non-matching peer that
does not produce the expected frame shape will cause protocol errors.

## Lifecycle Behavior

On upstream `init`, `Bgp4Client` initializes its line state and forwards
upstream `init` to the next tunnel after creating its receive stream.

On downstream `est`, it forwards every notification to the previous tunnel,
including repeats.

On upstream payload, it wraps and forwards to the next tunnel. On downstream
payload, it buffers, parses, unwraps, and forwards recovered payloads to the
previous tunnel.

On upstream `finish`, it destroys its own line state and forwards upstream
`finish` to the next tunnel. On downstream `finish`, it destroys its own line
state and forwards downstream `finish` to the previous tunnel.

On malformed framed data, `Bgp4Client` destroys local state and closes both
directions in middle-tunnel order: upstream finish first, then downstream
finish.

Pause and Resume are repeatable advisory notifications. Their default callbacks
forward each notification immediately in the same direction without recording
consumer pause state or gating payload output:

| Callback | Forwarded to |
| --- | --- |
| upstream pause/resume | next tunnel upstream |
| downstream pause/resume | previous tunnel downstream |

## Notes and Caveats

- `Bgp4Client` requires a paired `Bgp4Server` for useful operation.
- `password` is not a security feature in the current implementation.
- The BGP-like length field excludes the marker and length bytes.
- The first OPEN frame is sent only when the first upstream payload arrives.
- Upstream `est` and downstream `init` are disabled callbacks.
- This node is a layer-4 stream tunnel, not a packet tunnel.
