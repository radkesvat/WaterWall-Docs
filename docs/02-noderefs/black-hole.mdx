# BlackHole

`BlackHole` is a sink tunnel. It participates in the normal WaterWall chain
lifecycle, but it never forwards payload bytes. Depending on `settings.mode`,
it can either keep the connection lifecycle moving while silently dropping data,
or immediately finish the line when upstream traffic reaches it.

Use it when you need a deliberate drop point for testing, policy decisions, or
debug chains, without changing the surrounding listener, connector, or protocol
tunnels.

## What It Does

- Drops every upstream payload buffer.
- Drops every downstream payload buffer.
- Recycles dropped payload buffers with `lineReuseBuffer()`.
- Does not prepend, frame, encrypt, decode, or rewrite payload.
- Does not require extra left padding.
- Forwards lifecycle callbacks in passive mode.
- Immediately closes toward the previous side in active mode.

`BlackHole` is a normal chain node. It is not a socket adapter and it does not
create packet lines.

## Typical Placement

Passive drop point between two stream nodes:

```text
TcpListener -> BlackHole -> TcpConnector
```

UDP chain test:

```text
UdpListener -> BlackHole -> UdpConnector
```

Because payload is never forwarded, nodes after `BlackHole` will not receive
application data through it. Passive mode is mostly useful when you want the
chain lifecycle to remain structurally connected while data is consumed.

## Configuration Example

Passive mode:

```json
{
  "name": "dropper",
  "type": "BlackHole",
  "settings": {
    "mode": "passive"
  },
  "next": "next-node"
}
```

Active mode:

```json
{
  "name": "rejector",
  "type": "BlackHole",
  "settings": {
    "mode": "active"
  }
}
```

## Required Fields

Top-level fields:

| Field | Type | Description |
| --- | --- | --- |
| `name` | string | User-chosen node name. Must be unique inside the config file. |
| `type` | string | Must be exactly `"BlackHole"`. |
| `settings` | object | Must contain `mode`. |

Required `settings` fields:

| Field | Type | Description |
| --- | --- | --- |
| `mode` | string | Selects passive payload dropping or active connection finishing. |

`mode` is required. The current implementation does not provide a default.

## Optional Fields

| Field | Type | Description |
| --- | --- | --- |
| `next` | string | Optional at node level. In passive mode, set it when lifecycle callbacks should continue to another node. |

There are no optional `settings` fields.

## Mode Reference

### Passive Mode

Accepted values:

| Value | Meaning |
| --- | --- |
| `passive` | Canonical passive mode name. |
| `drop` | Alias for passive mode. |
| `packet-drop` | Alias for passive mode. The node still behaves as the same payload sink; it does not become a packet tunnel. |
| `silent` | Alias for passive mode. |
| `calm` | Alias for passive mode. |

In passive mode:

- upstream `Init`, `Est`, `Finish`, `Pause`, and `Resume` are forwarded to the
  next node when a next node exists
- downstream `Init`, `Est`, `Finish`, `Pause`, and `Resume` are forwarded to the
  previous node
- upstream payload is dropped
- downstream payload is dropped

Passive mode does not close the line by itself. It only consumes payload.

### Active Mode

Accepted values:

| Value | Meaning |
| --- | --- |
| `active` | Canonical active mode name. |
| `close` | Alias for active mode. |
| `aggressive` | Alias for active mode. |
| `kill` | Alias for active mode. |
| `kill-connection` | Alias for active mode. |

In active mode, upstream `Init` immediately sends downstream `Finish` toward the
previous node and returns. It does not forward that upstream `Init` to the next
node.

Payload callbacks still drop and recycle buffers if any payload reaches the
node, but active mode is intended for quick rejection rather than silent
long-lived dropping.

## Payload Handling

Both payload directions are consumed the same way:

| Callback | Behavior |
| --- | --- |
| upstream payload | Calls `lineReuseBuffer(line, buf)` and returns. |
| downstream payload | Calls `lineReuseBuffer(line, buf)` and returns. |

No payload bytes cross the node. Since no header is prepended and no frame is
allocated, `BlackHole` has `required_padding_left = 0`.

## Lifecycle Behavior

Lifecycle callbacks keep WaterWall direction ownership:

| Callback direction | Passive behavior |
| --- | --- |
| upstream `Init` / `Est` / `Finish` / `Pause` / `Resume` | Forwarded with `tunnelNextUpStream*` when `next` exists. |
| downstream `Init` / `Est` / `Finish` / `Pause` / `Resume` | Forwarded with `tunnelPrevDownStream*`. |

Active mode changes only upstream `Init`: instead of forwarding to `next`, it
finishes the previous side with `tunnelPrevDownStreamFinish()` and returns.

## Notes and Caveats

- `BlackHole` is layer-agnostic in node metadata and can be placed in different
  chain shapes, but it does not transform between stream and packet semantics.
- It is not useful for chains that need an application response, because payload
  never passes through it.
- Passive mode can make the previous side wait forever if the surrounding chain
  expects payload-driven progress.
- Active mode is best used as a deliberate reject or kill point.
- The node has no protocol settings, credentials, remote address, port, or
  framing options.
