# HintConnectionIN

`HintConnectionIN` tells a client that the rest of the chain consumes WaterWall
connections. The edge to `next` is Layer 4 (`kNodeLayer4`). Use
[HintPacketIN](./HintPacketIN.mdx) for a chain that consumes IP packets.

## Profile format

Use the exact `type` value `HintConnectionIN` and choose a unique `name` for the
node. The hint must be the chain head, so no other node may point to it. Its
`next` must name an existing node that accepts the required layer. Its position
in the `nodes` array is immaterial. Omit `settings` or supply an empty object.

This inspection example uses [BlackHole](./BlackHole.mdx), which accepts either
input layer. To run a resolved copy, also set the sink's required
`settings.mode` to `"passive"`.

```json
{
  "name": "Input hint example",
  "nodes": [
    { "name": "sink", "type": "BlackHole" },
    { "name": "entry", "type": "HintConnectionIN", "next": "sink", "settings": {} }
  ]
}
```

## Client handoff

1. Find the hint at the head of the portable chain. Read its `type` and remember
   its `next` target.
2. Copy the profile for execution and replace the hint with concrete input nodes.
   In SRP's system VPN mode, replace `HintConnectionIN` with
   [`TunDevice`](./TunDevice.mdx) followed by
   [`PacketsToConnection`](./PacketsToConnection.mdx), or replace `HintPacketIN`
   with `TunDevice`. Point the last generated node's `next` at the original target.
3. Pass the resolved copy to WaterWall. Keep the hint in the saved profile.

SRP manages its own TUN, SOCKS5 and HTTP choices, raw-socket import policy, and
node editor. An ordinary WaterWall configuration can start with any valid
concrete input node.

## Standalone startup

WaterWall rejects an unresolved hint before constructing any tunnel in that
configuration.

> HintConnectionIN requires a connection input. Replace this hint with a concrete input before starting WaterWall.
