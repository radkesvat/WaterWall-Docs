# HeaderClient

`HeaderClient` prepends a one-time 2-byte port header to the first upstream
payload on each normal layer-4 line.

It is usually paired with `HeaderServer`, which consumes that header and writes
the decoded port into the destination routing context before continuing the
chain.

## Typical Placement

Two-server TCP layout:

```text
client side: TcpListener -> HeaderClient -> TcpConnector
server side: TcpListener -> HeaderServer -> TcpConnector
```

In a larger chain, any stream tunnels between the client and server must
preserve the first two bytes added by `HeaderClient`.

## What It Does

- Requires `settings.data` to choose the port value to encode.
- Initializes local line state on upstream `Init`.
- Immediately forwards upstream `Init` to `next`.
- Prepends a 2-byte port header only on the first upstream payload.
- Encodes the port in network byte order.
- Forwards every later upstream payload unchanged.
- Forwards downstream payload, `Est`, `Pause`, and `Resume` unchanged.
- Destroys local line state before forwarding either directional `Finish`.

`HeaderClient` is a normal layer-4 stream tunnel. It does not create sockets,
does not create packet lines, and does not create or destroy `line_t` objects.

## Configuration Example

Use the accepted connection's source port:

```json
{
  "name": "header-client",
  "type": "HeaderClient",
  "settings": {
    "data": "src_context->port"
  },
  "next": "transport"
}
```

Use a constant port:

```json
{
  "name": "header-client",
  "type": "HeaderClient",
  "settings": {
    "data": 443
  },
  "next": "transport"
}
```

## Required Fields

Top-level fields:

| Field | Type | Description |
| --- | --- | --- |
| `name` | string | User-chosen node name. Must be unique inside the config file. |
| `type` | string | Must be exactly `"HeaderClient"`. |
| `settings` | object | Required. Must contain `data`. |
| `next` | string | Required. The next layer-4 stream node receives the header-prefixed stream. |

Required `settings` fields:

| Field | Type | Description |
| --- | --- | --- |
| `data` | number or string | Port value to encode into the first upstream payload. |

`HeaderClient` must also have a previous node in the chain. It is not a chain
head or chain end.

## `settings.data`

Accepted values:

| Value | Meaning |
| --- | --- |
| `1` through `65535` | Encode this constant port. |
| `"src_context->port"` | Encode `line->routing_context.src_ctx.port`. |
| `"line->src_ctx->port"` | Compatibility alias for `"src_context->port"`. |

Startup fails if `data` is missing, is not one of the accepted string values,
or is a numeric value outside `1` through `65535`.

## Wire Behavior

The first upstream payload is rewritten from:

```text
payload
```

to:

```text
2-byte port header | payload
```

The header is a big-endian 16-bit port value. It is sent only once per line.
Later upstream payloads are forwarded exactly as received.

If the first upstream payload is empty, the tunnel still sends the 2-byte header
on that first payload callback.

## Pairing With HeaderServer

Use `HeaderClient` with `HeaderServer` only when `HeaderServer` is configured to
read the incoming header:

```json
{
  "name": "header-server",
  "type": "HeaderServer",
  "settings": {
    "override": "dest_context->port"
  },
  "next": "connector"
}
```

If `HeaderServer.settings.override` is a number, the server sets a constant
destination port during upstream `Init` and does not consume a header. In that
mode, a `HeaderClient` in front of it would leave the 2-byte header in the
application payload.

## Direction Behavior

| Direction | Behavior |
| --- | --- |
| upstream `Init` | Initialize line state, then forward to `next`. |
| upstream first payload | Prepend the 2-byte port header, then forward to `next`. |
| later upstream payload | Forward unchanged to `next`. |
| upstream pause/resume | Forward to `next`. |
| downstream payload | Forward unchanged to the previous node. |
| downstream `Est` / pause / resume | Forward to the previous node. |

`UpStreamEst` and `DownStreamInit` are disabled callbacks for this node.

## Finish Behavior

On upstream `Finish`, `HeaderClient` destroys its local line state and forwards
the finish to `next`.

On downstream `Finish`, it destroys local line state and forwards the finish to
the previous node.

The tunnel does not call `lineDestroy()` because it does not create the line.

## Limits and Padding

| Value | Size |
| --- | --- |
| port header | `2 bytes` |
| `required_padding_left` | `2 bytes` |

The node declares `required_padding_left = 2` because it prepends the header
with `sbufShiftLeft()`.

## Notes and Caveats

- Use it only in layer-4 stream chains.
- It should not be used as packet-line shared state.
- The port header is internal WaterWall tunnel metadata, not a public protocol.
- The encoded value is taken when the first upstream payload arrives.
- It only mutates the first upstream payload; the response path is transparent.
