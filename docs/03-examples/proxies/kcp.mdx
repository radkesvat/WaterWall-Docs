# Proxy over KCP and TLS

KCP turns a UDP path into a reliable, ordered byte stream. This example puts TLS
over that stream, then uses Mux to share it across VLESS proxy requests. Your
applications connect to a local SOCKS5 port and select their own destinations.

```text
Client: TcpListener → Socks5Server → VlessClient → MuxClient → TlsClient → KcpClient → UdpConnector
Server: UdpListener → KcpServer → TlsServer → MuxServer → VlessServer → TcpConnector → requested destination
```

Use the [common setup](./overview.mdx). Save each side as `config.json`, replace
`198.51.100.20` with the server address, and replace the example UUID on both ends.
Install a trusted certificate for `tunnel.example.com` and its matching private
key on the server. Allow incoming **UDP 4000**.

The local listener binds to `127.0.0.1:1080` and supports SOCKS5 TCP `CONNECT`.
Application UDP is disabled. The UDP packets between the WaterWall processes
carry KCP; they are separate from SOCKS5 `UDP ASSOCIATE` traffic.

## Why this order matters

VLESS encodes the requested destination separately for each Mux child. Mux
combines those streams; TLS encrypts the combined bytes; KCP carries the TLS
records reliably over UDP. The server reverses that sequence before making
one outbound TCP connection for each requested destination.

KCP provides no encryption or server authentication. Keep the TLS nodes and
`verify: true` to protect the proxy credentials and payload. TLS needs KCP's
reconstructed stream: placing `TlsClient` between `KcpClient` and `UdpConnector`
would give TLS raw KCP packets instead. The `http/1.1` ALPN setting agrees on
both peers; it does not turn the enclosed proxy traffic into HTTP.

Mux also needs reliable, ordered bytes. Its two parent connections per worker
share the TLS/KCP setup across child requests. Children on the same parent share
that ordered stream, so loss can delay them together. With the common two-worker
setup there can be up to four active parent transports. For application UDP from
SOCKS5, follow the [Router example](./socks-mux.mdx) instead of sending raw datagrams
into Mux.

## Packet size and optional FEC

`send-mtu: 1400` is KCP's **IPv4-based outgoing packet budget**, including fixed
allowances for IPv4, UDP and WaterWall's session envelope. It is not an
application payload size or path-MTU discovery. This leaves some headroom on a
1500-byte path, but outer tunnels, IPv6 and smaller paths may require a lower
setting. See [KcpClient](../../noderefs/KcpClient) for the exact overhead formula.

Both configurations explicitly enable KCP congestion control with
`kcp-no-congestion-control: false`. Start here on a shared internet connection;
changing windows, retransmission timings or congestion control changes resource
use and traffic behavior, so measure on your actual path.

For a lossy path, you can try forward error correction (FEC). Replace the `kcp`
node's settings object on **both peers** with:

```json title="KcpClient.settings and KcpServer.settings — optional FEC"
{
  "send-mtu": 1400,
  "fec": true,
  "fec-data-shards": 10,
  "fec-parity-shards": 3,
  "kcp-no-congestion-control": false
}
```

These shard counts must match on both ends. A full block adds three parity
shards for ten data shards: about 30% extra parity traffic plus framing. FEC may
reduce the need to wait for retransmission when some packets are lost; it also
uses bandwidth and cannot guarantee recovery from sustained or bursty loss.
Compare it with FEC disabled and with the [QUIC example](./quic.mdx) using your
normal workload. Neither UDP transport is universally faster than TCP.
