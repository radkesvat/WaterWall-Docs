# VMess over WebSocket and TLS

This variant wraps VMess in WebSocket frames before encrypting the connection
with TLS. It is useful when you want an HTTP/1.1 WebSocket carrier for a proxy
connection. WaterWall handles both ends directly.

```text
Client: TcpListener -> Socks5Server -> VmessClient -> HttpClient -> TlsClient -> TcpConnector
Server: TcpListener -> TlsServer -> HttpServer -> VmessServer -> TcpConnector
```

The application still sees a local SOCKS5 proxy. VMess carries the destination
and authenticates the user; the HTTP nodes provide WebSocket framing; the TLS
nodes secure the carrier.

## Before starting

Use the [common setup](./overview.mdx), and save the selected tab as
`config.json` on its host. Replace `198.51.100.20`, the example UUID on both
ends, `tunnel.example.com`, and the certificate paths as in the
[basic protocol examples](./protocol-proxies.mdx). Keep both machines' clocks
synchronized for VMess authentication. Allow incoming **TCP 443** on the server.

The [VMess pre-authentication input limit](./protocol-proxies.mdx) also applies
inside WebSocket: a large initial burst can be rejected before authentication
completes.

These settings must agree:

| Layer | Client | Server |
| --- | --- | --- |
| VMess authentication | Your UUID | The same UUID |
| WebSocket | `http-version: 1`, `websocket: true` | The same values |
| HTTP Host and path | `tunnel.example.com`, `/vmess` | The same host and path |
| TLS application protocol | `alpns: ["http/1.1"]` | `select-alpns: ["http/1.1"]` |
| TLS identity | SNI `tunnel.example.com`, `verify: true` | A trusted certificate covering that name |

Both HTTP nodes explicitly select HTTP/1.1. Offering only `http/1.1` through
TLS keeps the negotiated protocol consistent with the WebSocket Upgrade
handshake.

```json
{
  "name": "vmess-websocket-client",
  "nodes": [
    {
      "name": "local-socks",
      "type": "TcpListener",
      "next": "socks",
      "settings": {
        "address": "127.0.0.1",
        "port": 1080
      }
    },
    {
      "name": "socks",
      "type": "Socks5Server",
      "next": "vmess",
      "settings": {
        "no-auth": true,
        "connect": true,
        "udp": false
      }
    },
    {
      "name": "vmess",
      "type": "VmessClient",
      "next": "websocket",
      "settings": {
        "uuid": "11111111-2222-4333-8444-555555555555",
        "address": "dest_context->address",
        "port": "dest_context->port",
        "protocol": "tcp",
        "security": "aes-128-gcm",
        "domain-strategy": "do-not-resolve-domains"
      }
    },
    {
      "name": "websocket",
      "type": "HttpClient",
      "next": "tls",
      "settings": {
        "http-version": 1,
        "websocket": true,
        "host": "tunnel.example.com",
        "path": "/vmess"
      }
    },
    {
      "name": "tls",
      "type": "TlsClient",
      "next": "server",
      "settings": {
        "sni": "tunnel.example.com",
        "verify": true,
        "alpns": [
          "http/1.1"
        ]
      }
    },
    {
      "name": "server",
      "type": "TcpConnector",
      "settings": {
        "address": "198.51.100.20",
        "port": 443,
        "nodelay": true
      }
    }
  ]
}
```

## Use the proxy

Point your application at SOCKS5 `127.0.0.1:1080`, or try:

```bash
curl --socks5-hostname 127.0.0.1:1080 https://example.com/
```

This example supports TCP CONNECT only. The local SOCKS port is bound to
loopback, and UDP is disabled on both proxy nodes. The requested destination
travels in VMess; the WebSocket Host/path and TLS SNI describe the tunnel
service.

A compatible external VMess client should use AEAD authentication
(`alterId: 0`), your UUID, `aes-128-gcm`, WebSocket transport with host
`tunnel.example.com` and path `/vmess`, and TLS with certificate verification
enabled. Select HTTP/1.1 WebSocket and disable extra multiplexing extensions.

## Where Mux would go

For a WaterWall-only pair carrying many TCP connections, the matching placement
is:

```text
Client: Socks5Server -> VmessClient -> MuxClient -> HttpClient -> TlsClient -> TcpConnector
Server: TcpListener -> TlsServer -> HttpServer -> MuxServer -> VmessServer -> TcpConnector
```

Mux then combines VMess streams into shared WebSocket/TLS carriers. Configure
both ends together; an external VMess client without WaterWall's Mux framing
cannot use that modified endpoint. Start with the complete
[SOCKS routing and Mux example](./socks-mux.mdx) for the Mux settings and the
Router split required when SOCKS also accepts direct UDP.

See [HttpClient](../../noderefs/HttpClient), [HttpServer](../../noderefs/HttpServer),
[TlsClient](../../noderefs/TlsClient), and [TlsServer](../../noderefs/TlsServer)
for transport settings. This example terminates TLS and WebSocket directly in
WaterWall; putting a separate reverse proxy in front requires that proxy to
support and forward the selected WebSocket transport.
