# SOCKS5 proxy over RTMPS

Point an application at `127.0.0.1:1080`. With SOCKS5 `CONNECT`, the remote
WaterWall server opens a TCP connection to the requested destination. With
`UDP ASSOCIATE`, the application receives a local relay address and port.
VLESS frames its datagrams for transport, and the remote server sends them
to the requested destination. Each TCP connection or UDP flow to a given
destination opens its own RTMP session. VLESS authenticates the request with
a UUID, and TLS protects the session between the two WaterWall hosts.

```text
Client: TcpUdpListener → Socks5Server → VlessClient → RtmpClient → TlsClient → TcpConnector
Server: TcpListener → TlsServer → RtmpServer → VlessServer → TcpUdpConnector
```

Both hosts must support WaterWall’s `ww.data` RTMP profile. The SOCKS control
and UDP relay endpoints are on client loopback. For a fixed destination such as
a single HTTP service, see the [direct RTMP tunnel](../tunnels/direct-rtmp.mdx).

## Before starting

Use the [common proxy setup](./overview.mdx#prepare-the-configuration) to
create `core.json` on each host. Save the matching tab below as `config.json`.

- On the client, replace `198.51.100.20` with the WaterWall server’s reachable
  address. Allow incoming TCP on port `443` on the server.
- Replace `tunnel.example.com` throughout with the DNS name on the server
  certificate. Install the certificate chain and private key at the paths in
  `TlsServer`. Keep `verify: true` and use a chain trusted by `TlsClient`.
- Generate a fresh UUID and put the same value in both VLESS nodes. The RTMP
  `app` and `stream` names must also match. Those names select the publication.
  The UUID is the credential.

The client’s `TcpConnector` dials the RTMPS listener. Its `TlsClient` verifies
the server certificate against `sni`. The `tc-url` is the application URL
announced inside the RTMP handshake. Once RTMP accepts the publication,
`VlessServer` can read the request header, authenticate the UUID and pass the
requested protocol, address and port to the final `TcpUdpConnector`.

## Run and check

Start WaterWall on the server, then on the client, using the [common startup
command](./overview.mdx#start-and-test). To check the exit end, start a
temporary HTTP service in a separate terminal on the **server**.

```bash
python3 -m http.server 8080 --bind 127.0.0.1 --directory "$(mktemp -d)"
```

On the **client**, request the server’s loopback service through SOCKS5.

```bash
curl --head --noproxy '' --socks5-hostname 127.0.0.1:1080 http://127.0.0.1:8080/
```

Expect `HTTP/1.0 200 OK` and a `HEAD /` request in the server’s Python log.
The two loopback addresses refer to different machines. Curl connects to the
SOCKS listener on the client, and VLESS asks the exit to dial port `8080` on
the server. Change the URL to reach another destination through the same SOCKS
port. Stop the temporary HTTP service with Ctrl+C.

To check UDP through RTMPS, run the [SOCKS5 UDP echo check](./overview.mdx#check-socks5-udp)
with the echo service on the remote server. VLESS preserves the datagrams
inside the RTMPS connection on TCP 443.

## Sharing an RTMPS connection with Mux

To share one RTMPS connection across several proxy requests, insert `MuxClient`
between `VlessClient` and `RtmpClient`, and `MuxServer` between `RtmpServer`
and `VlessServer`. Each Mux stream then carries one VLESS request with its own
destination. See the [SOCKS and Mux example](./socks-mux.mdx) for Mux settings
and the [RtmpClient](../../noderefs/RtmpClient) and [RtmpServer](../../noderefs/RtmpServer)
references for RTMP settings.
