# SOCKS5 proxy with striped RTMP upload and Reality download

Point a local application at the unauthenticated SOCKS5 proxy on
`127.0.0.1:1080`. The remote WaterWall server opens TCP connections or sends
UDP datagrams to the destinations requested by the application. Client-to-server
payload travels over eight striped RTMP connections per Mux parent.
Server-to-client payload returns over one Reality connection.

```text
Client
  TcpUdpListener → Socks5Server → TrojanClient → MuxClient → HalfDuplexClient
    up   → ConnectionStripeClient → ObfuscatorClient → RtmpClient → TcpConnector (:1935)
    down → RealityClient → TcpConnector (:443)

Server
  TcpListener (:1935) → RtmpServer → ObfuscatorServer → ConnectionStripeServer
    → HalfDuplexServer (up) → MuxServer → TrojanServer → TcpUdpConnector
  TcpListener (:443) → RealityServer → HalfDuplexServer (down, pair: up)
    Reality cover → TcpConnector ($reality_sni$:443)
```

The client dials both paths. Their names describe application payload direction.
Each path also carries its own handshake and control traffic, and the download
path sends a pairing intro from client to server.

The upload path uses plain RTMP and reversible XOR. An observer on that link
can recover the tunneled bytes, including the Trojan credential digest. Use
this configuration on a trusted link. Reality protects the download path.

## Before starting

Install WaterWall with the nodes shown above on both hosts. Use the
[common `core.json`](./overview.mdx#create-corejson) on each host and save
the matching tab below as `config.json`. The node configs use
[WaterWall variables](../../getting-started/tutorial-part3#variables).
Each unquoted `$name$` inserts the whole JSON value from `variables`.

- On the client, set `server_address` to the remote WaterWall server's
  reachable address. Set the host and port in `rtmp_url` to match the RTMP
  endpoint, retaining the `/waterwall` application path.
- Allow inbound TCP `1935` for RTMP and TCP `443` for Reality on the server.
  These TCP carriers also carry the proxied UDP traffic.
- Set the same `reality_sni` on both hosts. The example uses `example.com`.
  The client dials TCP `443` at `server_address`. The server resolves
  `reality_sni` and dials TCP `443` at the separate HTTPS cover site. The
  cover site's certificate must be trusted by the client and valid for that
  hostname.
- Replace `trojan_password` and `reality_password` with two separate secrets.
  Match each secret across the two hosts. Run `openssl rand -hex 24` for
  Trojan and `openssl rand -hex 16` for Reality, which accepts up to 32
  UTF-8 bytes.

## How the paths fit together

With SOCKS5 `CONNECT`, Trojan encodes the requested host and port before the
TCP payload. With `UDP ASSOCIATE`, SOCKS5 returns a local UDP relay and
Trojan frames the datagrams for carriage over a stream. Placing Trojan before
Mux keeps each child's destination independent. On the server, `MuxServer`
separates the children, `TrojanServer` restores their destination context, and
`TcpUdpConnector` uses that context to select TCP or UDP and reach the target.

`MuxClient` shares one healthy parent per active worker across the worker's
proxy streams. `HalfDuplexClient` splits each parent into `up` and `down`.
On `up`, `ConnectionStripeClient` spreads the stream across eight independent
RTMP sessions. `ObfuscatorClient` applies XOR to each carrier's Stripe frames,
including JOIN and other control frames, before RTMP wraps them.
`ObfuscatorServer` uses the same key to restore those frames before
`ConnectionStripeServer` parses them. All eight sessions for a parent must
reach the same Stripe server instance before it can deliver the reassembled
stream.

On `down`, the Reality client verifies the TLS handshake with the cover site
through `RealityServer`. The server forwards the cover handshake to
`cover-connector` on TCP `443` and sends authenticated Reality traffic
through its protected `next`. The two `HalfDuplexServer` nodes share a
pairing group because `down` names `up` in `settings.pair`. Once both halves
arrive, `up` feeds the reconstructed Mux stream to `MuxServer` and replies
return through `down`.

With both workers from the common `core.json` active, expect two healthy Mux
parents to use 16 RTMP connections and two Reality connections in total.

## Run and check

Start WaterWall on the server and then on the client using the
[common startup command](./overview.mdx#start-and-test). To verify the remote
TCP exit, start a temporary HTTP service in a separate terminal on the
**server**.

```bash
python3 -m http.server 8080 --bind 127.0.0.1 --directory "$(mktemp -d)"
```

On the **client**, request that service through SOCKS5.

```bash
curl --head --noproxy '' --socks5-hostname 127.0.0.1:1080 http://127.0.0.1:8080/
```

Expect `HTTP/1.0 200 OK` and a `HEAD /` entry in the server's Python log.
Curl reaches the SOCKS port on client loopback and asks the exit to dial
port `8080` on server loopback. Stop the temporary HTTP service with Ctrl+C.

For UDP, run the [SOCKS5 UDP echo check](./overview.mdx#check-socks5-udp)
with the echo service on the server. The client should print
`SOCKS5 UDP echo received`.

If the SOCKS connection opens but the target stays silent, check both
carrier paths. Verify the RTMP port, the Stripe connection count and matching
XOR key on the upload side. On the download side, verify the Reality
listener, matching Reality secret, and the server's DNS and TLS reachability
to the cover on `443`. Both paths must reach the same server pairing group.
