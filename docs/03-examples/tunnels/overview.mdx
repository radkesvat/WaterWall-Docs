# Tunnel Examples

These examples connect an **Iran server**, where users enter the tunnel, to a
**Kharej server**, where the destination service is reached. Each example includes
the configuration for both servers and explains which values to change.

| Example | Transport between the servers | Options |
| --- | --- | --- |
| [BitSwap + Mux](./bitswap-mux.mdx) | Packet tunnel with BitSwap | CWR / RST / SYN tabs; Mux included |
| [ProtoSwap](./protoswap.mdx) | Packet tunnel with a changed IP protocol number | Without Mux |
| [Ping](./ping.mdx) | IPv4 packets carried in ICMP Echo Requests between Iran and Kharej | Connection bridges or TunDevice; without Mux |
| [Fake TCP header](./fake-tcp-header.mdx) | TCP-looking IPv4 carriers for native TCP, UDP, GRE and other protocols | Connection bridges or TunDevice; optional password |
| [Direct TLS](./direct-tls.mdx) | TLS connection initiated from Iran to Kharej | With Mux recommended; Without Mux available |
| [Direct Reality](./direct-reality.mdx) | Reality connection initiated from Iran to Kharej | With Mux recommended; Without Mux available |
| [Direct QUIC](./direct-quic.mdx) | TCP service carried over encrypted QUIC/UDP from Iran to Kharej | With Mux recommended; Without Mux available |
| [Direct KCP](./direct-kcp.mdx) | TCP service carried over reliable KCP/UDP from Iran to Kharej | With Mux recommended; Without Mux available |
| [HalfDuplex: TLS + KCP](./halfduplex-split-transports.mdx) | Upload over TLS/TCP and download over KCP/UDP for one application connection | Complete client/server example; swap directions or use QUIC for the UDP branch |
| [ConnectionStripe: parallel TLS](./connection-stripe-tls.mdx) | Several TLS/TCP connections to use capacity under independent per-connection limits | With Mux shares groups across client-first applications; Without Mux gives each application its own group |
| [Direct BGP4](./direct-bgp4.mdx) | BGP-like framing over TCP from Iran to Kharej | With Mux recommended; Without Mux available |
| [Reverse TLS](./reverse-tls.mdx) | TLS connection initiated from Kharej to Iran | With Mux recommended; Without Mux available |
| [Reverse Reality](./reverse-reality.mdx) | Reality connection initiated from Kharej to Iran | With Mux recommended; Without Mux available |
| [Reverse QUIC](./reverse-quic.mdx) | QUIC/UDP transport initiated from Kharej to Iran | With Mux recommended; Without Mux available |
| [Reverse KCP](./reverse-kcp.mdx) | KCP/UDP transport initiated from Kharej to Iran | With Mux recommended; Without Mux available |
| [Reverse BGP4](./reverse-bgp4.mdx) | BGP-like framing over TCP initiated from Kharej to Iran | With Mux recommended; Without Mux available |

Choose a direct tunnel when Iran can connect to Kharej's transport listener.
Choose a reverse tunnel when Kharej should initiate the transport connection to
Iran. Users enter through Iran in either case, and the destination service runs
in Kharej.

In the TLS, Reality, QUIC, KCP and BGP4 examples, **With Mux is recommended** and
selected by default. Several user streams share each transport connection,
reducing repeated connection setup. Select the same Mux option for both servers.

The QUIC and KCP examples accept TCP from users and connect to a TCP
service in Kharej, while using UDP only between the servers. QUIC includes
encryption and certificate verification; the basic KCP example provides a
reliable stream without adding encryption or authentication.

The BGP4 examples use `TcpListener` and `TcpConnector` for the inter-server
transport. The paired WaterWall nodes add BGP-like framing without encryption,
authentication or route exchange.

## Prepare the two servers

1. Install WaterWall on both servers using the [installation guide](../../getting-started/installation).
2. Choose one example and follow its prerequisites, including any certificates,
   keys, routes, and firewall rules it needs.
3. Copy its Iran configuration to `config_iran.json` on the Iran server and its
   Kharej configuration to `config_kharej.json` on the Kharej server.
4. Edit the `variables` section in each configuration, then create `core.json`
   using the matching tab below.

The addresses in the examples are placeholders:

| Placeholder | Replace with |
| --- | --- |
| `192.0.2.10` | Your Iran server's public IPv4 address |
| `198.51.100.20` | Your Kharej server's public IPv4 address |

Also replace the example domains, credentials, certificate paths, service ports,
and network interfaces as directed by the chosen example.

The node configurations use WaterWall's [variable syntax](../../getting-started/tutorial-part3).
An unquoted placeholder such as `$iran_ip$` is replaced with its value before
the node configuration is parsed. Leave these placeholders unquoted and edit
their values in `variables`. These templates are not standalone strict JSON
until substitution; `core.json` itself must always be valid JSON.

## Create `core.json`

Save the matching tab as `core.json` beside the server's node configuration.
Use the MTU for your chosen example **on both servers**:

| Example | `misc.mtu` |
| --- | --- |
| BitSwap + Mux, ProtoSwap | `1400` |
| Direct TLS, Direct Reality, Direct QUIC, Direct KCP, Direct BGP4 | `1500` |
| Reverse TLS, Reverse Reality, Reverse QUIC, Reverse KCP, Reverse BGP4 | `1500` |
| Ping | `1500`; the example sets each packet bridge or TUN's inner MTU to `1400` |
| Fake TCP header | `1400`; follow the example's [header and password MTU budget](./fake-tcp-header.mdx#mtu-is-your-responsibility) |

The tabs below start at `1500`; change this to `1400` for BitSwap, ProtoSwap or
Fake TCP header. Follow each example's separate inner MTU requirements.
`workers: 0` uses the CPU core count. Logging starts at `INFO`, with DNS logs
written to a file without console output. See [Core Settings](../../getting-started/tutorial-part1)
for memory profiles, logging, and other runtime settings.

## Start the tunnel

Run from the directory containing `core.json`, the matching node configuration,
and your WaterWall executable:

```bash
./Waterwall --config:core.json
```

This command uses the built executable name `Waterwall`; use your installed
filename if it differs. Relative paths, including the entries in `configs`,
resolve from the directory where you start the process.

Follow the selected example's startup order and connection check. For temporary
startup diagnostics, add `--verbose` to the command above.
