# WireGuard over UDP

Connect two Linux hosts through an encrypted IPv4 packet tunnel. WaterWall
creates a TUN interface on each host, and the server authorizes the client with
a static WireGuard peer. To enforce account limits and open TCP/UDP connections
at the server, use [WireGuard connection mode](./wireguard-connection.mdx).

```text
Client: TunDevice -> WireGuardClient -> UdpConnector
Server: UdpListener -> WireGuardServer (mode=packet) -> TunDevice
```

## Prepare the hosts

Install WaterWall on both hosts. Use hosts that can reach each other over UDP
and have permission to configure a Linux TUN interface. Allow the client to
reach UDP port `51820` on the server. Use an isolated test network for the
checked-in sample keys. Use a different inner subnet if either host already
routes `10.50.0.0/24`.

## Configure each side

Save `core.json` and `config.json` from the corresponding directory beside
`Waterwall` on each host. Run WaterWall from that directory so `core.json` can
find `config.json`.

| Host | Configuration files | Inner TUN address |
| --- | --- | --- |
| Client | [client](https://github.com/radkesvat/WaterWall/tree/main/tunnels/WireGuardClient/examples/client) | `10.50.0.5/24` on `ww-client` |
| Server | [packet-server](https://github.com/radkesvat/WaterWall/tree/main/tunnels/WireGuardClient/examples/packet-server) | `10.50.0.1/24` on `ww-server` |

1. On the client, replace `127.0.0.1:51820` in `WireGuardClient.settings.peers[0].endpoint`
   with the server's reachable IPv4 address and UDP listener port. The
   `UdpConnector` reads the endpoint through `dest_context`.
2. Set the client peer's `allowedips` to `10.50.0.1/32` for this test. The
   server peer's `allowedips` must include the client TUN address `10.50.0.5`.
   The supplied `10.50.0.4/30` does. Keep the addresses consistent across both
   TUN interfaces and peer entries if you choose a different subnet.
3. For deployment, generate a new WireGuard key pair on each host. Set the local
   node's `settings.privatekey` to that host's private key and
   `settings.peers[0].publickey` to the other host's public key. Keep private
   keys on their respective hosts.

The OS route sends the inner packet into the TUN interface. WireGuard uses
`allowedips` to select a peer by inner destination and to check the source of
decrypted packets. The sample uses the connected TUN subnet route and keeps
`route-table` set to `off`. The outer UDP endpoint must remain reachable over
the ordinary network. [TunDevice routing](../../02-noderefs/TunDevice.mdx#typical-placement)

## Run and check

Start the server, then the client. Run this from each host's configuration
directory.

```bash
sudo ./Waterwall --config:core.json
```

Once both TUN interfaces are up, run this on the client.

```bash
ip -4 route get 10.50.0.1
ping -c 3 -I ww-client 10.50.0.1
```

The route should use `ww-client`, and replies should come from `10.50.0.1`.
If the route uses another interface, check for an overlapping subnet. If the
route is correct and the ping times out, check the outer UDP address and
firewall, the two public keys, both peer ranges, and whether the server allows
ICMP to its TUN address.

To reach a network beyond the server, add the corresponding inner route and
peer range on the client. Configure forwarding and a return route or NAT on the
server as required by that network. For optional junk datagrams or a matching
UDP-over-TCP relay, see the [additional configurations](https://github.com/radkesvat/WaterWall/tree/main/tunnels/WireGuardClient/examples).
