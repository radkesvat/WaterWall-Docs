# Part 5: Anatomy of a Tunnel & Workflow

This part maps the contracts from Parts 1-4 onto the actual files you edit. Once
you know which file owns which responsibility, adding or fixing a tunnel becomes
mechanical: make the smallest complete root-cause change in the right place and
keep the lifecycle intact.

## Directory Layout

Tunnel files use the following layout. Callback files and their directories
exist only where the node implements behavior beyond its constructor defaults:

```text
tunnels/MyTunnel/
  CMakeLists.txt
  description.md
  include/MyTunnel/
    interface.h          # public WW_EXPORT API + custom callback prototypes
    structure.h          # tstate / lstate structs, size enums, helpers
  instance/
    create.c             # tunnelCreate(), assign callbacks, parse + validate settings
    node.c               # node metadata: type, flags, layer group, padding, createHandle
    chain.c              # custom onChain hook, when needed
    index.c              # custom onIndex hook, when needed
    prepair.c            # onPrepare hook
    start.c              # onStart hook
    stop.c               # lifecycle-v2 quiesce, drain, and stop hooks
    destroy.c            # onDestroy hook: free state, then tunnelDestroy()
    api.c                # runtime API entry (tunnelApi)
  common/
    helpers.c            # shared protocol helpers
    flow.c               # shared progress coordination, when needed
    input.c              # shared parsing/extraction, when needed
    line_state.c         # initialize + destroy per-line state
  upstream/
    init.c  est.c  payload.c  pause.c  resume.c  fin.c
  downstream/
    init.c  est.c  payload.c  pause.c  resume.c  fin.c
```

:::note Real layout vs. the old summary
Two details matter in practice: every tunnel has an `instance/api.c`, and the
prepare hook file, when present, is spelled **`prepair.c`** (the function is
`...OnPrepair`). The
upstream/downstream finish files are `fin.c`, not `finish.c`.
:::

Keep inherited callbacks at their defaults; do not add forwarding wrappers or
empty lifecycle files for them. Compare against the actual constructor: packet
payload defaults and disabled adapter directions intentionally abort.
`tunnelCreate()` also terminates on upstream `Est` and downstream `Init` by
default; nodes that support these events must explicitly install handlers.
`packettunnelCreate()` preserves lifecycle forwarding in both directions.
Other ordinary flow defaults forward. State changes, event absorption, cleanup,
and error handling require custom callbacks even when their bodies are short.

For an ordinary middle node, a custom Est handler must still promptly relay
adapter establishment. Protocol negotiation, request emission and payload
readiness belong in separate state, not in a delayed or replacement Est. Follow
[Part 2's Est contract](./part2-lines-and-callbacks.mdx#est-is-transport-readiness)
when mapping distinct lines or adding a protocol-completion callback.

Choose flow state by role, not by copying another protocol's pump. Synchronous
transforms use direct Payload and signal forwarding without redundant output
queues. Parsers keep incomplete input; junctions map pressure; timers and deferred
backlogs own bounded, permission-aware drains. Keep any reentry guard attached to
the specific ordering obligation it protects. Completing a bounded admitted input
can continue after Pause; see [Part 2](./part2-lines-and-callbacks.mdx#flow-control-roles-and-admission).

Remove obsolete callback implementations when they have no registrations or
runtime callers, together with their declarations and build-source references.
Check public entrypoints and dynamic loading conventions before declaring a
function unused; retain callbacks and APIs that remain reachable.

Keep one file per custom `{direction}/{event}`. Each callback may contain its
direction-specific dispatch, admission checks and direct forwarding so buffer
ownership and callback direction remain visible. Share parsing, framing, progress
coordination and teardown in cohesive `common/` files, such as `input.c`, `flow.c`,
`fallback.c` or `lifecycle.c`, as their responsibilities warrant. Keep file-local
helpers static and expose only necessary cross-file helpers through the private
header. Callbacks should remain readable without hiding directional decisions
behind a boolean dispatcher; common code need not all live in `helpers.c`.

## What Each File Owns

| File | Responsibility |
| --- | --- |
| `instance/node.c` | Returns the `node_t` describing this tunnel type: `type`, `version`, `createHandle`, `flags`, `required_padding_left`, `layer_group`, and neighbor layer constraints. |
| `instance/create.c` | `tunnelCreate(node, sizeof(tstate), sizeof(lstate))`, assign only the flow callbacks and lifecycle hooks that differ from the constructor defaults, parse and validate JSON settings, allocate per-worker resources, clean up on any failure. |
| `instance/chain.c` / `index.c` | The `onChain` / `onIndex` hooks. Most tunnels keep the framework defaults. Static internal topology known before solving belongs in `onChain`. A tunnel whose private topology depends on solved adjacent layers may also set optional `onSolvedTopology` from `create.c`. It receives the current solved snapshot, which is not necessarily final. The hook may be called repeatedly and returns `true` if and only if it changed topology; the snapshot then becomes stale and the manager solves again before invoking another hook. Once a complete pass reports no changes, `onIndex` runs once over immutable topology and may consume the final solved layers. |
| `instance/prepair.c` / `start.c` / `stop.c` | `onPrepare` / `onStart` and the lifecycle-v2 shutdown hooks. Bootstrap in `onStart`; close admission in `onQuiesceRequest`; detach worker-affine work in `onWorkerQuiesce`; wait for external producers in `onQuiesceWait`; drain owned lines in `onWorkerStop`; release remaining shared resources in `onStop`. |
| `instance/destroy.c` | `onDestroy`: free settings, SSL contexts, pools, thread-local arrays, then call `tunnelDestroy(t)`. |
| `instance/api.c` | The `tunnelApi` runtime entry. It receives an `sbuf_t` message, must recycle it, and returns an `api_result_t`. |
| `common/line_state.c` | `LinestateInitialize` (called from `Init`) and `LinestateDestroy` (zeroes the aligned line-state region). |
| `common/*.c` | Shared algorithms and coordination grouped by responsibility: protocol helpers, parsing, framing, progress, fallback or lifecycle. |
| `upstream/*.c`, `downstream/*.c` | One custom flow callback each. Omit files for inherited callbacks. Keep directional dispatch, admission and direct forwarding here; delegate shared algorithms and coordination to cohesive common files. |
| `include/MyTunnel/structure.h` | `mytunnel_tstate_t`, `mytunnel_lstate_t`, size enums, and small inline helpers. |
| `include/MyTunnel/interface.h` | `WW_EXPORT` create/api and custom destroy prototypes, plus prototypes for implemented callbacks. |

### Caller preconditions and failure handling

Callers establish an internal helper's preconditions. A required tunnel, line,
buffer or output pointer is not an optional input merely because C can represent
NULL. Do not turn a programmer error into an ordinary `false`, `NULL`, success or
silent return, or duplicate argument validation at every layer.

Choose the check according to what can actually cause the condition:

| Condition | Handling |
| --- | --- |
| Caller-owned precondition or programmer-only invariant | Use `assert()` to document and check it in Debug, or remove a redundant check when the surrounding contract already establishes it. |
| Critical internal invariant requiring release-build protection, such as corrupted resource ownership | Keep a runtime check, emit `LOGF`, then call `abortProgramNow()`. Do not disguise corruption as a recoverable protocol failure or request orderly shutdown and continue. |
| Expected failure, external input or supported state | Keep ordinary runtime validation and the documented failure/cleanup path. Examples include allocation/I/O refusal, malformed peer data, exhausted budgets, incomplete frames and optional NULL arguments. |

Trace callers before classifying a condition. A NULL callback context after
detachment, a stale association, a canceled timer, or state released during a
reentrant callback can be expected. Keep those guards and exact-line lifetime
checks. A reference preserves the allocation, not the logical life of the line.
An entry assertion never replaces a required check after calling another tunnel.
Required internal arguments normally belong in the first row; the possibility
that caller misuse could crash does not by itself justify another runtime guard.

Split mixed checks instead of deleting the whole expression. For example, a TLS
output helper can assert that its tunnel, line, state and write BIO are non-null,
while still returning failure if TLS output fails or a callback releases its
state. Document nullable parameters explicitly. Keep operations with side effects
outside `assert()` so Release builds perform them too; assertions disappear under
`NDEBUG`.

### Typed internal capabilities versus runtime messages

Use `include/<Tunnel>/interface.h` for a typed capability exchanged directly
between compatible tunnels already known to share a chain. For example,
`UdpListener` exposes a dynamic UDP endpoint provider as a value-handle API:
the caller opens, activates, queries, and closes an endpoint on its validated
owner worker. The capability must define ownership, worker affinity, stale-handle
behavior, and callback routing; it must not expose a usable foreign `line_t *`.

Do not turn such a local capability into `instance/api.c`. That file is the
external runtime message entry: it accepts an `sbuf_t`, recycles it, and returns
an `api_result_t`. It has different admission, serialization, and lifecycle
requirements. A typed internal capability remains ordinary local C calls and
must still preserve the normal tunnel callback chain.

### Address-context metadata ownership

`address_context_t.optional_flags.detected_protocols` carries two logical
classes of optional metadata. Router/sniffer-owned bits record observed
application protocols; route-control bits carry a one-shot internal instruction
such as an already-negotiated SOCKS UDP relay endpoint. A Router starting a new
sniffing window must call `addresscontextClearDetectedProtocols()`, which clears
only observed protocol bits. `addresscontextClearOptionalFlags()` is the full
reset for a caller that genuinely replaces the context. The designated outbound
adapter consumes route-control metadata exactly once and clears it after setup;
rules must never treat route-control bits as sniffed protocols.

Framework-owned worker messages, timers, WIO callbacks, and async DNS requests
settle before component destruction under lifecycle-v2, so those contexts may
carry `tunnel_t *` directly when they also validate and use their explicit owner
worker. This is not a general lifetime rule: a callback root outside the worker
lifecycle, such as a device reader thread, must close local admission and wait for
active operations through an owner-specific mechanism such as
`quiescence_gate_t` before the tunnel or device state is reclaimed.

## `node.c`: Declaring the Node

`node.c` is where a tunnel announces itself to the runtime. Here is
`TcpListener`'s, which is a good template for an adapter:

```c
node_t nodeTcpListenerGet(void)
{
    const char *type_name = "TcpListener";
    node_t node = {
        .type                  = stringDuplicate(type_name),
        .hash_type             = calcHashBytes(type_name, stringLength(type_name)),
        .version               = 0001,
        .createHandle          = tcplistenerTunnelCreate,
        .flags                 = kNodeFlagChainHead,
        .required_padding_left = 0,
        .layer_group           = kNodeLayer4,
        .layer_group_next_node = kNodeLayerAnything,
        .layer_group_prev_node = kNodeLayerAnything,
        .can_have_next         = true,
        .can_have_prev         = true,
    };
    return node;
}
```

The fields you will set most often (all defined in `ww/objects/node.h`):

| Field | Meaning |
| --- | --- |
| `type` / `hash_type` | The string used in JSON `"type"`, plus its precomputed hash. |
| `createHandle` | The `TunnelCreateHandle` that builds the instance. |
| `flags` | One or more `node_flags`: `kNodeFlagChainHead`, `kNodeFlagChainEnd`, `kNodeFlagNoChain`, `kNodeFlagSingleton`, `kNodeFlagSupportsSplice`, `kNodeFlagBlocksSplice`. |
| `required_padding_left` | Left-padding budget this tunnel may prepend into (see [Part 3](./part3-buffers-and-padding.mdx)). |
| `layer_group` | The layer category this node operates on: `kNodeLayer3` (packet), `kNodeLayer4` (stream), `kNodeLayerAnything` (supports both), or `kNodeLayerNone`. (Note: `kNodeLayerSameAsNext`, `kNodeLayerSameAsPrev`, `kNodeLayerOppositeNext`, and `kNodeLayerOppositePrev` are forbidden for `layer_group` and only allowed in `layer_group_next_node` / `layer_group_prev_node`). |
| `layer_group_next_node` / `layer_group_prev_node` | Required layer group for next/previous neighbor (`kNodeLayer3`, `kNodeLayer4`, `kNodeLayerAnything`, `kNodeLayerSameAsNext`, `kNodeLayerSameAsPrev`, `kNodeLayerOppositeNext`, `kNodeLayerOppositePrev`, or `kNodeLayerNone`). Note: Opposite flags must be combined with a base layer group (e.g. `kNodeLayerAnything | kNodeLayerOppositePrev`) and cannot appear alone. |
| `can_have_next` / `can_have_prev` | Whether a neighbor is permitted on each side (`true`/`false`). |

### Layer Groups & Strict Topology Validation

During chain startup, `NodeManager` strictly enforces node capabilities and layer rules via `validateTunnelChains` and the bounded monotonic layer constraint solver (`nodeLayerSolveChain`):

- **Capability constraints:** If a node specifies `.can_have_next = false` (or `.can_have_prev = false`), having an adjacent neighbor on that side results in immediate startup failure. Unchained nodes marked with `kNodeFlagNoChain` must not have adjacent neighbors.
- **Metadata shape validation:** `layer_group` must be concrete (`kNodeLayerNone`, `kNodeLayer3`, `kNodeLayer4`, `kNodeLayerAnything`). Forward relative flags (`kNodeLayerSameAsNext`, `kNodeLayerOppositeNext`) are allowed only in `layer_group_prev_node`, and backward relative flags (`kNodeLayerSameAsPrev`, `kNodeLayerOppositePrev`) are allowed only in `layer_group_next_node`. Opposite flags must always include a base layer group (e.g. `kNodeLayerAnything | kNodeLayerOppositePrev`).
- **Edge-domain constraint propagation:** The runtime constructs a directed edge graph representing callback connections between adjacent tunnels, seeds each edge domain (`{L3}`, `{L4}`, or `{L3, L4}`) from participating node and neighbor layer requirements, and propagates `SameAs` and `Opposite` relations monotonically to a fixed point. Any edge domain converging to `{}` immediately fails startup with a clear diagnostic identifying both nodes and sides.
- **Conditional SameAs vs Strict Opposite:** `SameAs` relative constraints (`kNodeLayerSameAsPrev`, `kNodeLayerSameAsNext`) are conditional: when the referenced side is absent, no equality relation is added, and the node's placement flags (`kNodeFlagChainHead`, `kNodeFlagChainEnd`, `kNodeFlagNoChain`) determine whether boundary placement is permitted. In contrast, `Opposite` constraints (`kNodeLayerOppositePrev`, `kNodeLayerOppositeNext`) are strict and always require both participating sides to be present.
- **State-held cross-tunnel relations:** For nodes whose callback targets are established dynamically at runtime (such as paired `Bridge` tunnels), tunnels register logical layer relations directly on the chain via `tunnelchainRegisterLayerRelation()`. Registered relations couple the participating edge domains (e.g. equating Bridge A prev edge with Bridge B prev edge, and Bridge A next edge with Bridge B next edge) during solver execution and persist across chain combinations (`tunnelchainCombine()`).
- **Fixed and relative bridges:** Fixed-side bridges explicitly declare concrete
  layer requirements on their adjacent edges rather than claiming
  `kNodeLayerAnything`. `ConnectionToPackets` is L4 on `prev` and L3 on `next`;
  `PacketsToConnection` is L3 on `prev` and L4 on `next`; `StreamToPackets` is L4
  on `prev` and L3 on `next`. Dynamic bidirectional bridges such as
  `WireGuardDevice` declare `Opposite` relations that couple opposite edge domains
  without prematurely collapsing unresolved intermediate subchains.
- **Packet chain classification & bootstrap:** A chain allocates worker packet lines and sets `contains_packet_node = true` only when at least one edge is forced to `{L3}`, a node or edge requirement is fixed to `L3`, or an `Opposite` relation exists. Persistent packet line `Init` messages are queued at runtime only when the chain head's next edge is resolved to `{L3}`.
- **Failure semantics:** Any validation or solver failure logs a fatal diagnostic (`LOGF`) and records a startup failure (`startupFailureRecord(1)`), causing WaterWall to reject the configuration and perform a clean startup rollback.

### Bridge and reverse-node adjacency

The reverse topology requires both direct adjacencies:

- `ReverseServer -> Bridge`: Bridge must be ReverseServer's immediate next node.
- `Bridge -> ReverseClient`: Bridge must be ReverseClient's immediate previous node.

**No node may intervene in either pair**, including a transparent transform,
logger, or limiter. Both `Bridge -> SpeedLimit -> ReverseClient` and
`ReverseServer -> SpeedLimit -> Bridge` are forbidden. ReverseClient creates a
line toward its previous side using downstream `Init`, and Bridge translates
that callback into upstream `Init` on its paired branch. These are chain-design
requirements that users must follow. The code does not automatically enforce
either adjacency rule. The direct connection keeps the exceptional direction
change at the reverse/Bridge boundary; ordinary stream nodes outside it retain
their usual left-owner topology assumptions. See
[Part 2](./part2-lines-and-callbacks.mdx#ownership-and-topology) for the scope of
those assumptions and the corresponding Finish order.

### Node Flags

`UdpStatelessSocket` is a chain-head adapter by design. It requires `next`,
forbids `prev`, and creates normal peer lines using upstream `Init` only.
Outgoing datagrams and callbacks from the chain arrive downstream from `next`.
Tail placement and downstream peer initialization are intentionally disabled;
this is the supported topology contract, not a temporary workaround. WireGuard
layouts using this socket place its transport side toward `prev`.

| Flag | Meaning |
| --- | --- |
| `kNodeFlagChainHead` | May start a chain (an ingress adapter). |
| `kNodeFlagChainEnd` | May end a chain (an egress adapter). |
| `kNodeFlagNoChain` | Works without being in a chain (e.g. a database/user-auth node). |
| `kNodeFlagSingleton` | Only one instance allowed in the whole config. |
| `kNodeFlagSupportsSplice` | Advertises support for splice payloads. |
| `kNodeFlagBlocksSplice` | Explicitly disables splice for the entire chain; takes precedence over `kNodeFlagSupportsSplice`. |

`tunnel_chain_t.supports_splice` is false during assembly. At
`tunnelchainFinalize()`, it becomes true only when `WW_HAVE_SPLICE == 1`,
`misc.splice` is not disabled, the solved chain has no packet nodes
(`contains_packet_node == false`), and the chain is nonempty with **every**
tunnel's node advertising `kNodeFlagSupportsSplice` and none advertising
`kNodeFlagBlocksSplice`. Packet chains and builds without splice support always
leave the chain flag false, regardless of node
flags. The node check includes internal helpers and tunnels brought in by
chain merges. Finalization follows the
complete `onChain` phase and the solve/`onSolvedTopology` expansion loop;
`onChain` alone is too early because topology-dependent helpers can still join.

`kNodeFlagSupportsSplice` is a two-direction safety promise, not a per-callback converter:
every reachable payload, retention, error, and close path must accept splice
input safely, and the node must also accept ordinary fallback input. Advertising
the flag does not promise that every path remains zero-copy.

`kNodeFlagBlocksSplice` records an explicit node-level exclusion. It wins even if
both splice flags are set on a node. A node with neither flag still prevents
splice because support must be explicitly advertised. The blocker applies to the
final expanded/merged topology, including internal helpers, and does not depend
on which runtime mode or branch a particular connection uses.

`TlsClient`, `TlsServer`, `EncryptionClient`, `EncryptionServer`, `RealityClient`,
`RealityServer`, `ObfuscatorClient`, `ObfuscatorServer`, `Disturber`,
`TcpOverUdpClient`, and `TcpOverUdpServer` explicitly block splice. Internal node
copies must preserve these capability flags, including RealityClient's embedded
TlsClient.

The chain flag applies build/startup/topology restrictions. Final eligibility
requires `WW_HAVE_SPLICE == 1`, `misc.splice` not disabled, no packet node, a
nonempty finalized chain, support on every tunnel and no explicit blocker after
helper/topology expansion. Eligibility alone does not activate splice I/O; the adapters still
select it. `WW_HAVE_SPLICE` reports Linux splice API availability independently
of the event watcher.

`TcpListener`, `TcpConnector`, `DomainResolver`, `MuxClient`, `MuxServer`,
`Bgp4Client`, `Bgp4Server`, `VlessClient`, `TrojanClient`, `TrojanServer`, `HeaderClient`, `Bridge`, `UserController`, `BlackHole`, `ReverseClient`, and
`JunkDatagramSender`, `UdpListener`, `UdpConnector`, `UdpStatelessSocket`,
`TcpUdpListener`, and `TcpUdpConnector` advertise the flag. This includes the internal `DomainResolver` inserted by
`TcpConnector`. Mux retains valid queued bodies under local queue-capacity charges. Incoming
assembly shares the parent receive limit with attached child queues; beneficial
pressure compaction and actual pipe-transfer fallback remain available. Its fixed-header stream and atomic large
splice batches preserve both callback directions. This does not promise zero-copy
for every frame. BufferStream and HTTP remain ordinary-only; HTTP nodes do not
advertise splice support.

TrojanClient supports opaque TCP and staged variable-header UDP decoding, including
its dependent owned carrier and destination-context selection. Its internal
DomainResolver remains eligible. TlsClient still blocks a chain containing it;
TrojanServer supports staged request authentication, opaque CONNECT, UDP backends
and exact fallback replay. Eligibility includes its UserController and all reachable
fallback/connector helpers; the AuthenticationClient lookup dependency is not a
payload hop. TlsServer remains a blocker. See the Trojan buffer contracts in Part 3.

VlessClient supports both callback directions for TCP, UDP and destination-context
selection, including retained input and dependent carrier cleanup. Its internal
DomainResolver remains eligible. The response/addon barrier and UDP length parser
use node-local bounded metadata storage; ordinary fallback remains valid. TlsClient
and VlessServer do not become eligible merely by adjoining VlessClient. See Part 3
for exact retention limits and representation handling.

BGP supports both representations through in-place framing, bounded frame FIFOs
and a 19-byte fixed-header receive stream. OPEN inspection reads only its bounded
metadata; private-pipe creation or transfer refusal selects ordinary fallback.
The fixed per-direction retention policy is independent of pool sizing.

HeaderClient prepends its one-time header only in real left padding, preserving
existing prefixes and the private-pipe body. Bridge transfers the original buffer
and line through its paired callback mapping; eligibility includes the merged
chain. UserController forwards opaquely and accounts logical bytes, including
prefixes, preserving reverse-direction accounting. Rejected traffic and BlackHole
input recycle through the line's pool, discarding unread pipe bytes; healthy empty
pipes may remain cached. BlackHole's active Init still closes the line and does
not admit payload afterward.

ReverseClient forwards application buffers between its owned normal lines and
recycles held input if activation closes the pair. Its handshake and
JunkDatagramSender's generated junk/delayed duplicates stay ordinary; forwarded
application bodies can stay in private pipes. Existing callback directions,
ordering, lifecycle, and direct Bridge -> ReverseClient adjacency remain required.
HeaderClient support does not imply HeaderServer support, and ReverseClient
support does not imply ReverseServer support. Ordinary fallback stays valid;
packet configurations of dual-layer nodes still disable splice globally. These
capabilities make no performance promise without measurement.

UDP capability covers sending existing private-pipe bodies; UDP receives stay
ordinary. Combined TCP/UDP wrappers retain both children's flags and include both
branches plus inserted helpers in final eligibility, even for a TCP line. An
eligible TCP branch can therefore use its existing splice I/O without changing
protocol selection. Datagram failure and full fallback follow Part 3; packet
configurations remain excluded globally.

### External-node ABI

External libraries must export `waterwallNodeLifecycleAbiVersion()` returning
`WW_EXTERNAL_NODE_ABI_VERSION`, currently `4`. The loader checks this before
calling a node getter. Rebuild external libraries against the current headers:
removal of the buffer ownership callback API and changes to device constructors
invalidate older compiled inline code and function signatures even though the
32-byte sbuf header size, alignment and payload offset remain unchanged.
`WW_EXTERNAL_NODE_LIFECYCLE_ABI_VERSION` remains an alias for this complete gate;
the lifecycle callback semantics themselves are unchanged.

## `create.c`: Building the Instance

`create.c` is the only place a tunnel is allocated. The pattern, distilled from
`TlsClient`:

1. `tunnel_t *t = tunnelCreate(node, sizeof(tstate), sizeof(lstate));`
2. Check `t` immediately and return `NULL` if creation failed.
3. Assign only callbacks whose behavior differs from the chosen constructor defaults.
4. Read settings from `node->node_settings_json`, validating each one.
5. Allocate per-worker resources (e.g. one SSL context per worker).
6. **On any later failure, clean up and bail out** — destroy partial state and the
   tunnel, return `NULL`.

`tunnelCreate()`, `adapterCreate()`, and `packettunnelCreate()` are nullable by
contract. They return `NULL` on invalid or overflowing state sizes or allocation
failure. Never assign a callback or call `tunnelGetState()` until the result has
been checked.

The cleanup discipline is real and worth following. The distilled shape is:

```c
tunnel_t *tlsclientTunnelCreate(node_t *node)
{
    tunnel_t *t = tunnelCreate(node, sizeof(tlsclient_tstate_t), sizeof(tlsclient_lstate_t));
    if (! t)
    {
        return NULL;
    }

    configureTunnelCallbacks(t);

    tlsclient_tstate_t *ts       = tunnelGetState(t);
    const cJSON        *settings = node->node_settings_json;

    if (! getandvalidateSniSetting(ts, settings))
    {
        goto fail;
    }
    // ... more validated settings ...

    if (! createSslContextPool(&ts->threadlocal_ssl_contexts, /* ... */))
    {
        goto fail;
    }

    return t;

fail:
    tlsclientTunnelstateDestroy(ts);
    tunnelDestroy(t);
    return NULL;
}
```

### The lifecycle-v2 shutdown stages

Lifecycle ownership is explicit and context-bearing. Process shutdown invokes
these stages for every tunnel in every loaded chain. Within a chain, NodeManager
uses storage order; that order is not guaranteed to be source-to-tail:

1. `onQuiesceRequest` runs on the main thread, closes local admission, issues
   producer stop requests, and must not wait.
2. `onWorkerQuiesce` runs on each owner worker and detaches that worker's timers,
   watchers, and component-specific queued handles.
3. `onQuiesceWait` runs on the main thread after every worker is quiesced and
   joins or detaches already-admitted external callback roots.
4. `onWorkerStop` runs on each owner worker during drain. Every source or
   internal normal-line owner closes its authoritative inventory when visited;
   another hook must not assume a neighbouring owner has already run or require
   a borrowed registry to be empty.
5. `onStop` runs on the main thread after every worker is drained and releases
   remaining shared resources.
6. `onDestroy` runs on the main thread only after no worker, message, line, or
   external producer can reference the instance.

Every callback receives a read-only `ww_lifecycle_context_t`. Construction
rollback, owner-driven private-child teardown, and local device restart use
their own scopes and abortive close policy. Components must not infer a scope by
polling process-global shutdown state. Live configuration removal is not a
supported lifecycle scope.

Use the project's JSON helpers (`getStringFromJsonObject`,
`getBoolFromJsonObjectOrDefault`, `getIntFromJsonObjectOrDefault`, etc.) and
`LOGF` a clear message on bad config — misconfiguration should fail loudly at
startup, not silently at runtime.

For per-node MTU settings, seed an `int64_t` from `CORE_DEFAULT_MTU`, strictly
parse any override with `jsonGetObjectIntegerInRange()`, and validate the final
value before narrowing or allocating MTU-dependent resources. Missing settings
must not bypass validation: the JSON helper does not validate an inherited seed.
Store the result in immutable tunnel state and use it for all runtime work,
including delayed callbacks and lazy protocol objects. Invalid inherited values
must name core `misc.mtu` and the supported node override in the diagnostic.
See [Core configuration ownership](./doc1.mdx#core-configuration-ownership).

## `structure.h`: tstate and lstate

`structure.h` defines the two state structs and their sizes. Keep settings and
runtime fields clearly grouped, as `TlsClient` does:

```c
typedef struct tlsclient_tstate_s
{
    // settings (parsed once in create.c)
    char *sni;
    char *alpn;
    bool  verify;
    // runtime, shared across all lines
    SSL_CTX **threadlocal_ssl_contexts;   // one per worker
} tlsclient_tstate_t;

typedef struct tlsclient_lstate_s
{
    SSL           *ssl;
    BIO           *rbio;
    BIO           *wbio;
    buffer_queue_t bq;
    bool           handshake_completed;
    bool           resources_released;
} tlsclient_lstate_t;
```

Per-worker arrays (like `threadlocal_ssl_contexts`) live in **tstate** and are
indexed only by an explicitly validated worker identity: `lineGetWID(line)` in a
line callback, `worker->wid` in a worker-message callback, or a checked
`getCurrentEventWorkerWID()` when the callback contract guarantees an event
worker. Never index them with raw `getWID()`. Per-connection state lives in
**lstate**.

Line-state types must require no more than `kTunnelLineStateAlignment` (32-byte)
alignment. Use `tunnelTryAlignLineStateSize()` when composing embedded line-state
regions, and include each rounded region in the tunnel's reservation before
chaining. `tunnelTryAlignStateSize()` is for cache-aligned tunnel-wide state.
Allocation sizes, embedded offsets, and zeroing lengths must use the same
line-state alignment; clearing a larger region can overwrite the next slot.

## `line_state.c`: Initialize and Destroy

Line state is initialized in `Init` and destroyed exactly once. The destroy
function must zero the **aligned** region so the line-free debug assertion
(`debugAssertZeroBuf`, see [Part 2](./part2-lines-and-callbacks.mdx)) is satisfied:

```c
void templateLinestateInitialize(template_lstate_t *ls)
{
    // set up this connection's state
}

void templateLinestateDestroy(template_lstate_t *ls)
{
    memoryZeroAligned32(ls, tunnelGetCorrectAlignedLineStateSize(sizeof(template_lstate_t)));
}
```

Rules (from [Part 2](./part2-lines-and-callbacks.mdx), restated where you write the
code):

- Initialize in `Init`; later callbacks assume the state exists.
- Initialize the final line-state object before attaching queues to an embedded
  buffer budget. Its address must remain stable; never copy populated state with
  self-references. Destroy attached queues and release active reservations, assert
  zero budget usage, then clear the line-state slot.
- Destroy once; after `LinestateDestroy()` consider the state dead and zeroed.
- Never read a field after destroying the state.
- Do not add an `initialized` boolean unless an explicitly documented
  line-role/callback contract requires state before ordinary `Init`.

## HTTP-Specific Rules

`HttpProxyServer` exposes an HTTP/1.x forward-proxy interface, unlike the body
transport interfaces of `HttpClient` and `HttpServer`. Its incoming normal line
is borrowed; each outbound normal child is created and destroyed by the proxy.
The incoming line stops at the proxy and only the child initializes the actual
next chain entry. Child responses and pressure cross back to the associated
client identity. Authentication selects exactly one of no-auth, an immutable local credential
list, or AuthenticationClient tracked accounts. Each authenticated request
reauthenticates before reuse. Reuse requires the requested authority and mode;
local mode also requires the same complete credential pair, while tracked mode
requires credential bytes and user ID/generation.
Resolved destination context is mutable and must not be used as that authority
key. Only tracked mode creates the internal UserController and adds a real user
handle with credentials to the child. Local mode adds a credentials-only marker
for routing, with no new account tracking or per-user limits. Both preserve
inherited identities and avoid appending repeated markers to the borrowed
client or reused child. Current TCP read EOF closes the full transport,
including on IOCP; proxy persistence does not introduce half-close semantics.

HttpProxyServer treats `max-pending-bytes` (`P`) as its working pending-data
budget. Four working buffers retain at most `4 * P` allocation bytes. Each
direction may additionally hold one already-delivered remainder of at most
`D = 2 MiB` logical bytes. This node-owned headroom is independent of pool sizes,
RAM profile and splice settings. Total retained logical bytes are bounded by
`P + 2 * D`. A single delivery is limited to `P + D`; only its immediately drainable prefix may exceed the
per-direction remainder allowance. Each remainder's
payload capacity is at most `max(small_capacity, 2 * D)` plus cache-line rounding;
its full padding, sbuf header, and aligned-allocation overhead are additional.
Remainder admission copies into ordinary best-fit storage (pooled or dedicated)
when needed to satisfy this bound. Working slice room excludes deferred
bytes so moving bytes into working storage never double-counts them. Remainders
participate in pressure, FIFO pumping, and every error/timeout/close cleanup path.
Blocked pipelined requests leave response progress available.

ReverseServer, HalfDuplexServer, and HttpServer split derive waiting budgets from
`scale = max(1, ceil(basis / 32768))`, where
`basis = bufferpoolGetWaitingBudgetBasis()` is 64 KiB in S1/S2 and 1 MiB in higher
profiles, independently of allocation sizes and the splice limit.
ReverseServer closes above `65535 * scale`;
HalfDuplexServer closes at or above `131070 * scale`, including initial upload
publication; HttpServer split closes above `131070 * scale` unless its explicit
buffering-limit bypass is enabled. Handshake/header validation and available-peer
pairing precede waiting checks. The 32 KiB divisor is a fixed budget reference. Wire and HTTP framing limits remain independent.

If you work on `HttpClient` or `HttpServer`, these source-backed constraints
apply:

- HTTP/1.x header limits count bytes through the first complete `CRLF CRLF`,
  including the terminator. Body bytes received in the same buffer do not count
  against that limit. Without a terminator, the buffered header prefix remains
  subject to the limit. This applies to request, response, and split headers.
- WaterWall targets HTTP/1.x and **single-stream** HTTP/2 only. Do not add HTTP/3.
  Do not support more than one logical HTTP/2 stream. If a peer opens extra
  streams, reject or ignore them conservatively per the existing design.
- **h2c upgrade** (`nghttp2_session_upgrade2()`): stream `1` is the original
  upgraded request. The client must not submit a second synthetic request on
  stream `1`; the server must not auto-generate a fake synthetic response on
  stream `1`.
- **h2c with a request body**: upgrade-with-body on the original HTTP/1.1 request
  is not safely supported in the single-stream design. The client should reject
  it; the server should ignore or reject an upgrade whose HTTP/1.1 request carries
  a body.
- **Clean finish**: an upstream `Finish` for the request side may require final
  HTTP bytes first. Send them while holding a line reference, then destroy local
  state, then forward the real `Finish` — the general final-bytes pattern from
  [Part 2](./part2-lines-and-callbacks.mdx). Do not keep HTTP line state alive
  after a clean finish unless you intentionally held a line reference for that purpose.
- **Pairing IDs (`HttpClient` split mode and `HalfDuplexClient`)**: give every
  logical pair a fresh 128-bit identifier from two sequenced `fastRand64()`
  values, then copy that same identifier to both child transport lines. Never
  derive pairing IDs from counters or non-cryptographic output. The ID is
  internal routing metadata, not authentication or transport protection;
  chains that need those properties use dedicated security nodes.
- **HalfDuplex rendezvous publication**: `HalfDuplexServer` performs the
  opposite-role lookup and, when no peer exists, publication of the current
  role as one lock-linearized transaction across both pending maps. This keeps
  simultaneous upload and download arrivals from both observing a miss. A peer
  owned by another WID is identified while the maps are locked, but the current
  decision copies only that WID, not the borrowed peer line-state pointer, and
  the current line is piped only after releasing the lock. No worker handoff or
  tunnel callback runs inside the pending-map transaction. Final child destroy
  requires both borrowed pending maps to be empty and never reclaims their line
  state or buffered payload on behalf of the real line owners.

## The Implementation Workflow

Use this order for any new feature or fix. Inspect the repository first; ask a
focused question only when a consequential requirement, compatibility choice, or
scope boundary cannot be resolved from code and documentation. Make and record
reasonable assumptions for low-risk implementation details instead of delegating
them back to the maintainer.

1. **Draw the chain flow.** Mark the Up-end and Down-end, and label which callback
   direction owns the transformation.
2. **Identify the line owner.** Which tunnel creates and destroys the line?
3. **Read the existing tunnel** and its immediate neighbors.
4. **Read the contracts:** `ww/net/line.h`, `ww/net/tunnel.h`, and
   `ww/net/chain.c`.
5. **If framing/prepending is involved,** read `ww/bufio/shiftbuffer.h` and
   `buffer_pool.h`, plus nearby tunnels' `node.c` padding.
6. **Compare relevant mature tunnel patterns**, but verify them against the
   contract, callers, and neighbors rather than copying them blindly.
7. **Implement the smallest complete root-cause fix** that preserves composition.
   Do not minimize the diff by retaining a known defect, duplicating unsafe logic,
   or patching only a symptom.
8. **Decide whether focused regression coverage is warranted.** It normally is for
   new behavior, a reproducible regression-prone bug, a meaningful edge case, or a
   contract change—especially when a test can fail on reversed direction. Reuse
   existing direct coverage when sufficient, and do not manufacture behavior tests
   for mechanical or documentation-only work.
9. **Validate** with the preset build and the relevant tests (see
   [Part 6](./part6-build-test-review.mdx)).

:::warning Avoid speculative abstractions
A new generic layer is rarely the fix here. Preserve the established lifecycle
contract and prefer a direct complete fix. If one tunnel appears to require a new
lifecycle concept, stop and verify the need against the core contract and every
affected caller; do not use a reference tunnel as proof that either the old or new
shape is correct.
:::
