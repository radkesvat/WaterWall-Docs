# Part 2: Lines, Callbacks & Lifetime Safety

This part covers the contracts that cause the most crashes when they are broken:
the per-connection callback lifecycle, who owns a line, and how to survive the
re-entrant callbacks that can destroy a line out from under you.

If you read only one part of this guide before touching connection flow, read
this one. Prerequisite: [Part 1](./doc1.mdx) (objects, directions, lifecycle).

## The Six Flow Callbacks

Every connection is driven by six events, each in two directions (upstream toward
`next`, downstream toward `prev`):

| Event | Meaning | Direction notes |
| --- | --- | --- |
| `Init` | A line is starting; initialize this tunnel's per-line state. | Flows upstream from the creating adapter. |
| `Est` | An adapter's transport is established (e.g. the remote socket connected); protocol negotiation is separate. | Normally relayed downstream, back toward the originating adapter. |
| `Payload` | A chunk of data (`sbuf_t`) to transform and forward. | Either direction. |
| `Pause` | Stop new source work and independent drains; bounded admitted synchronous input may finish. | Either direction. |
| `Resume` | Backpressure released: you may send again. | Either direction. |
| `Finish` | This direction is closing. | Directional and destructive. See below. |

A tunnel implements only the handlers whose behavior differs from its constructor
defaults. `tunnelCreate()` terminates on upstream `Est` or downstream `Init` unless
the node explicitly overrides that callback; its other flow defaults forward to
the neighbor. Packet constructors preserve both-direction lifecycle forwarding.
For example, an encryptor overrides `Payload` in both directions but can leave
`Pause`/`Resume` at default.

## How a Line Starts

A normal connection begins with `Init`, originated by an adapter:

1. An adapter (e.g. `TcpListener`) accepts a socket and creates a `line_t`.
2. It calls `tunnelNextUpStreamInit()`.
3. That invokes the next tunnel's `fnInitU`, which initializes its own line state
   and forwards `Init` further upstream.
4. Each middle tunnel initializes its per-line state in turn.
5. The final adapter (e.g. `TcpConnector`) starts the real network operation.

:::danger Init is not isolated
A tunnel's `Init` can synchronously trigger more callbacks **before it returns** —
`Payload`, `Est`, `Pause`, `Resume`, or even `Finish` — because the downstream
tunnel it called into may immediately push data back or close. This is the same
re-entrancy hazard described below; it simply starts at line birth.
:::

Rules for `Init`:

- Initialize **this tunnel's** line state in `Init`. Later callbacks are allowed
  to assume that state already exists.
- Do **not** add an `initialized` boolean to guard later callbacks. In the normal
  WaterWall lifecycle `Init` always runs first for a tunnel; an `initialized`
  flag is almost always a band-aid over unsafe control flow. Add one only when an
  explicitly documented line-role/callback contract truly requires state before
  ordinary `Init`, and cover that exception directly.
- If your `Init` calls a re-entrant forwarding helper and then still needs to
  touch the line afterward, protect it (see [Line References](#protecting-a-line-across-re-entrant-callbacks)).
  If your `Init` just forwards and returns, you do not need to hold a reference.

## Line Lifetime: refcount and `alive`

A `line_t` carries an exactly 32-bit atomic `refc` and a boolean `alive` (see `ww/net/line.h`).
These are two different ideas, and conflating them causes bugs:

- `lineRef(line)` increments `refc`. It guarantees the allocation memory will not
  be freed while you hold the reference. A line reference is **not** a mutex or
  lock: it provides no mutual exclusion and does not transfer worker affinity.
- `lineUnref(line)` releases one reference. A final release physically reclaims
  only a logically dead line; releasing a live line to zero is a fatal contract violation.
- `lineDestroy(line)` sets `alive = false` and drops the creator's reference.
- `lineIsAlive(line)` reports whether the line is still **logically** open.

The crucial distinction:

> Holding a line reference keeps the **allocation memory** valid. It does **not**
> lock line contents, grant cross-thread access, or mean the line is still
> logically alive. After a re-entrant callback, a referenced line may be
> `alive == false`. Always re-check `lineIsAlive()` before continuing.

**Logical death is immediate; physical reclamation is not.** `lineDestroy()`
clears `alive` and drops one reference. If anyone else still holds a reference
via `lineRef()` the allocation remains present until they unref — which is
exactly what makes the owner postcondition below both checkable and cheap:

```c
lineRef(l);                  /* keep the allocation present for the assertion */
owner->fnFinD(owner, l);
assert(! lineIsAlive(l));    /* logical death is immediate */
lineUnref(l);                /* physical free may occur right here */
```

A logically dead line must never receive another flow callback, and by the time
it is reclaimed every tunnel's line state must already be zeroed.

The thread which drops the final reference is not necessarily the line's event
worker. A device thread, lwIP pseudo-worker, or unregistered scheduler can hold
a legitimate reference while the owner destroys the line and closes message
admission. The final `lineUnref()` therefore returns the allocation through a
thread-safe shared-pool path when no registered event worker is current; only a
registered event worker may use the local-pool fast path. Chain teardown treats
checked-out line-pool items as a hard ordering violation, so the shared master
pool remains alive until every outstanding reference is gone.

The reference count is also the publication edge for final reclamation. Every
acquire-release decrement publishes the releasing thread's preceding teardown
writes; the RMW which observes `1 -> 0` acquires that release sequence before reading `alive`, zeroed
tunnel state, routing/domain storage, or credentials. Code that adds another
direct reference-count decrement must preserve this release/acquire protocol.
Do not rely on worker-message locks or an unrelated readiness flag to publish
line state to a foreign final releaser.

Line reference counters use `atomic_u32_t` from
`ww/libc/watomic.h`. Access published counters through its `atomic*U32*`
helpers, including in tests. The generic atomic API uses pointer-sized storage
on the Windows fallback and cannot operate on these 32-bit fields. Incrementing
a zero or maximum reference count is a fatal invariant violation.

### WIO Descriptor Ownership

A `wio_t` stores its owned primary descriptor directly as `int fd`, defined in
`ww/event/wevent.h`. `wioGetFD()` returns that descriptor, or `-1` after it has
been closed or released. Descriptor zero is valid. The descriptor has no separate
allocation, reference count, or pool; only the WIO allocation has deferred
lifetime protection.

WIO close removes watcher interest and settles its queued writes, invokes the
close callback while the descriptor is still available, then invalidates and
closes the descriptor exactly once. Deferred graceful close keeps it open until
draining ends. Reentrant freeing in the close callback preserves the WIO
allocation until that close frame returns. On Windows, the native close kind is
captured at descriptor adoption, so sockets use `closesocket()` and CRT file
descriptors use `_close()` even if the logical I/O type changes later.

The separate `io_slot` field preserves descriptor-table bookkeeping after `fd`
becomes `-1`. It is never used for I/O. Pending and native IOCP operation roots
protect the WIO allocation after close; they do not keep its socket open.

NIO splice reads move socket bytes into a wrapper's private pipe before invoking
the callback. The wrapper contains neither a source pointer nor a source reference;
its length reflects the actual transfer. After delivery the read path does not
inspect the source or buffer, so callbacks may close/free the source immediately.
No socket reservation or post-callback source guard is needed for this read path.

Each splice allocation exclusively owns its private pipe. Buffers can be retained
or partially consumed and deferred immediately, and source WIO reclamation
cannot affect them. Queued writes preserve their private pairs until completion
or discard. Graceful close drains them; cancellation drains or closes each private
pair before recycling. See the
[private-body rules and AAA/BBB example](./part3-buffers-and-padding.mdx#independent-private-bodies).
This source-independent lifetime does not make pipe bytes ordinary pointer data:
parsers and retaining transforms follow the [BufferStream representation contract
in Part 3](./part3-buffers-and-padding.mdx#bufferstream-representation-inspection-and-extraction-contracts).

Freeing a pending NIO detaches its descriptor-table slot immediately but defers
recycling the WIO allocation until the pending dispatcher releases it. Shutdown
also settles these detached pending allocations before destroying the WIO pool.

`pending` also prevents reuse of the allocation for a new descriptor. If the OS
reuses an fd whose closed NIO is still pending, `wioGet()` retires that old object
on its original loop and creates a fresh WIO for the new connection. The old
pending entry never follows an accepted socket to another worker. A closed NIO
whose pending dispatch has finished can still be reused in place.

`wioDetach()` runs on the original owner thread and `wioAttach()` on the
destination owner thread. Both require stopped read/write interest and no
pending dispatch; a pending WIO triggers `LOGF()` and `abortProgramNow(1)`.
Stopping interest alone does not release pending-list ownership. Defer a
handoff until the original loop has finished dispatch. SocketManager hands off
newly accepted, non-pending WIOs, including when an fd number was reused.
The dispatcher retains its `cur->loop == loop` ownership check as well.

`wioReleaseNoClose()` preserves descriptors owned by another subsystem, such
as c-ares. It removes watcher interest, detaches the WIO's array slot, and sets
`fd` to `-1` without closing the external descriptor. The external owner remains
responsible for closing it. Pending/native operations and callback frames still
settle before the WIO allocation can return to its existing pool.

### Scheduled Line Tasks

`lineScheduleTask()`, `lineScheduleTaskWithBuf()`, and the two delayed variants
transfer one task to the immutable event worker recorded by the line. Immediate
work and a delayed call with `delay_ms == 0` are always queued for a later loop
iteration; neither executes inline. Timer creation and task execution remain
owner-worker-affine even when submission originates on another worker, the
lwIP thread, a device thread, or an unregistered thread.

#### Submission precondition

The caller must hold an independently synchronized **live handle** until the
scheduler takes its own line reference. That means both:

- a physical reference keeps the allocation present; and
- a gate, registry lock, or equivalent publication protocol prevents
  `lineDestroy()` from racing the call.

An unprotected raw pointer is invalid. A physical reference alone is also
insufficient because it does not keep `alive` true. The scheduler retains the
line after the call, but it does not retain the supplied `tunnel_t`; the runtime
or component must keep that tunnel valid until task-or-cancellation settlement.

#### What the result proves

Every scheduling result is `line_task_submit_result_e` and must be inspected:

| Result | Synchronous proof |
| --- | --- |
| `kLineTaskSubmitRejectedSettled` | The task will not run. Optional cancellation notification and all scheduler-owned record, line-reference, and buffer settlement have completed before return. |
| `kLineTaskSubmitAcceptedAsync` | Ownership entered an asynchronous queue or setup path. It does **not** prove that a positive-delay timer is armed, that the task remains pending when observed, or that the task will run. |
| `kLineTaskSubmitTimerArmed` | A non-zero-delay call made on the line's owner worker installed its timer before return. Later line death or quiescence can still cancel it. |

The immediate APIs never return `TimerArmed`. Delayed zero returns
`AcceptedAsync`. A positive delay submitted on the owner returns `TimerArmed`
after successful installation. The same positive delay submitted from any
other thread returns `AcceptedAsync` once owner-side setup is queued.

Scheduling records and timers use normal fail-fast allocation. Positive-delay
worker messages install their timer with `wtimerAdd()`. On the loop's owner
worker, timeout records use `genericpoolGetItem()` from a worker-local pool
backed by `GSTATE.masterpool_timers`. Local width is `RAM_PROFILE`; master width
is `2 * RAM_PROFILE`. Pool constructors double those widths for cache capacity,
and local refills request `RAM_PROFILE` records. Allocation either supplies
storage or terminates the process; timer allocation does not report
`ResourceFailure` or invoke cancellation cleanup.

Every pooled checkout resets the record. Expiry, explicit deletion,
quiesced/deferred deletion, loop destruction, and pending-event reclamation
return records only at final release; an executing callback's pending timer
cannot be reused by a nested submission. Worker pools outlive loop cleanup and
the shared master outlives all workers. Foreign startup callers and standalone
loops without a pool use normal event allocation without borrowing an owner's
local pool. Period timers also retain normal event allocation.

Shutdown admission can still refuse timer installation. On the owner worker,
that refusal reports `AdmissionClosed` and returns `RejectedSettled`. A foreign
submission returns `AcceptedAsync` once setup is queued, and may subsequently
be canceled before arming. Cancellation may be delivered before, concurrently
with, or after the submitter observes acceptance. The task never runs inline:
doing so would violate its minimum delay and can make a self-rescheduling task
recurse without bound.
Independent delayed tasks have no equal-deadline FIFO guarantee. Ordered work
belongs in one explicit queue drained by one scheduled task.

#### Exactly one terminal outcome

A non-null `LineTaskCancelFn` makes the public outcome exactly one of task or
cancellation. Cancellation may run synchronously and re-entrantly before the
scheduling call returns, later on the owner worker, on the submitting thread,
or during detached-queue teardown. The scheduler holds its physical line
reference during notification, but the line may already be logically dead and
its tunnel line state may already be destroyed. The callback is notification
only: it owns neither a transferred buffer nor scheduler cleanup.

Set a pending latch **before** submission so synchronous cancellation can settle
it. A cancellation handler may touch only state whose lifetime and concurrency
are independently proved, such as an atomic tunnel-state latch kept alive by the
component lifecycle. It must not restart normal work during quiescence or
teardown. Passing `NULL` deliberately declines notification; internal ownership
still settles exactly once.

Cancellation reasons are precise:

| Reason | Meaning |
| --- | --- |
| `kLineTaskCancelTargetUnavailable` | The target WID has no ordinary event-worker queue. |
| `kLineTaskCancelAdmissionClosed` | The target no longer admits normal work or timer setup. |
| `kLineTaskCancelEnqueueFailure` | Queue growth or wake publication refused submission. |
| `kLineTaskCancelResourceFailure` | Not emitted for timer allocation, which is fail-fast. |
| `kLineTaskCancelQuiesced` | Worker quiescence settled accepted work before execution. |
| `kLineTaskCancelTeardown` | Detached queue teardown settled the task. |
| `kLineTaskCancelLineDead` | Dispatch found the retained allocation logically dead. |

After foreign admission, submitter and owner progress independently:

```text
submitter lane -> setup admission commits result -> return/observe AcceptedAsync
owner lane     -> accepted setup may be canceled -> cancellation(Quiesced)
                 cancellation may precede, race with, or follow submitter observation
```

Memory and resource safety are unconditional; task progress is not. Required
work therefore needs a synchronous `RejectedSettled` fallback and an
authoritative owner/Stop path for cancellation after acceptance. Deliberately
lossy payload and observational-statistics work may pass `NULL` and explicitly
discard the typed result:

```c
const line_task_submit_result_e result =
    lineScheduleDelayedTask(parent, muxclientLogStatsTask, 5000, t, NULL);
discard result; /* statistics are intentionally best effort */
```

A required pending-state design can use an independently safe atomic latch in
tunnel state. Both terminal callbacks clear the same latch; neither assumes that
a timer was armed or reaches into possibly destroyed line state:

```c
static void retryCancelled(tunnel_t *t, line_t *line, line_task_cancel_reason_e reason)
{
    retry_tstate_t *ts = tunnelGetState(t);
    atomicStoreExplicit(&ts->pending[lineGetWID(line)], false, memory_order_release);
    discard reason; /* owner drain is authoritative after cancellation */
}

atomicStoreExplicit(&ts->pending[wid], true, memory_order_release);
const line_task_submit_result_e result =
    lineScheduleDelayedTask(line, retryTask, delay_ms, t, retryCancelled);
if (result == kLineTaskSubmitRejectedSettled)
{
    /* retryCancelled already cleared pending; perform only safe inline policy. */
}
```

Do not let both a cancellation callback and the `RejectedSettled` branch perform
the same fallback. Notification has already run when that result is returned.

The shared `pipe_tunnel` follows the same rule for ordered cross-worker streams.
One explicit pair owner holds the borrowed/owned roles and references; any lost
Init, data, control, or Finish atomically makes the pair terminal. Each side
detaches on its owner worker, only the created companion line is destroyed, and
the owner-worker drain is the no-message fallback. The pair retains
both physical line references until both sides and every queued message have
detached; releasing a target reference at the first-side detach would let a
concurrent sender race storage reuse.

### Who May Destroy a Line

Only the tunnel that **created** a line may call `lineDestroy()` on it —
`lineCreate()` or `lineCreateForWorker()` for that **exact `line_t` instance**.

Ownership belongs to the line, not to the node type. Do not infer it from a name
such as "Client", "Server", "Listener", or "Connector":

- `TcpListener` calls `lineCreate()` for every accepted connection and is that
  line's owner.
- `TcpConnector` owns a **socket**, not a line. It calls neither `lineCreate()`
  nor `lineDestroy()`; it consumes a line created toward the `prev` side. Owning an
  OS resource is not owning a `line_t`.
- A tunnel routinely **mixes roles**: `MuxClient` owns its parent/carrier line
  while borrowing every child line; `HttpClient` owns the upload/download
  transport lines it splits a borrowed main line into; `Socks5Server`,
  `TrojanServer`, and `VlessServer` own UDP remote lines while borrowing the
  client line. Decide per line, in the same handler, before cleaning anything up.

`tests/line_ownership_policy_test.py` records the classification of every
production creation site and fails when a new one appears unclassified.

### Ownership and topology

For ordinary connection streams, the usual layout is:

```text
creator/owner -> middle tunnels -> borrowing socket adapter
     left              upstream toward next ->       right
```

Normal lines are almost always **left-owned** in this layout. The creator sends
upstream `Init`; middle tunnels and the right-side adapter borrow that same line.
The owner may itself be a middle node creating a separate parent, child, or
transport line. "Left-owned" describes the path back to that exact line's
creator, not the first node in the configuration file or its chain-array index.
`TcpListener`, `UdpListener`, and the head-only `UdpStatelessSocket` follow this
pattern for accepted connections or incoming peers. Closing their OS resource
at a borrowing node does not transfer ownership of the line.

An ordinary middle stream tunnel may use the upstream-then-downstream local
Finish sequence below under this topology contract. The downstream Finish
travels back to the owner and may destroy the line; it must be the last use of
that line in the close path. This is distinct from handling a received Finish,
which is forwarded only away from its sender.

Keep these special cases separate:

| Line/path | Ownership and lifetime |
| --- | --- |
| Worker packet line | Shared worker-local packet state, allocated and released by the chain. It stays logically alive throughout runtime; a node must never destroy it on Finish. Worker affinity is not per-connection ownership. |
| Reverse nodes and Bridge | Bridge forwards the same line while reversing callback direction; it does not become the owner. Follow the exact reverse-node ownership contract at the direction-changing boundary. |
| Internal companion transport line | A node that creates one owns that normal line, even inside a packet chain. For example, WireGuardDevice creates normal companion transport lines; when transport faces `prev`, their Init travels downstream. These are not persistent worker packet lines or ordinary left-owned stream ingress. |

The reverse topology has two mandatory direct connections:

```text
Bridge -> ReverseClient
ReverseServer -> Bridge
```

**No node may sit between either pair**, including a transparent transform,
logger, or limiter. Put extra processing outside these gaps. In particular,
ReverseClient's downstream Init must reach Bridge directly; Bridge turns it
into upstream Init on the paired branch. An intervening ordinary stream tunnel
cannot rely on the usual left-owner model at that boundary. These rules define
supported configurations even though startup does not currently enforce the
adjacencies automatically; see [Part 5](./part5-tunnel-anatomy.mdx#bridge-and-reverse-node-adjacency).

Do not infer that every normal line in every topology is left-owned, or that an
explicit downstream Init handler changes ownership. Trace special/internal
creation paths before applying the ordinary stream close sequence. A physical
reference keeps allocation memory available; it does not keep a destroyed line
logically alive.

### Shutdown-complete owners and adapters

Immediate `Finish` ownership is only half of the normal-line contract. Every
autonomous creator must also be able to enumerate all of its live lines during
worker shutdown. Publish each new line into exactly one owner-worker inventory
before any re-entrant `Init` or other callback can expose it, and remove the
entry exactly once on every close path. Clear the slot or idle-table entry
*before* invoking `Finish`: the callback can re-enter, and a repeated stop must
see an empty slot and do nothing.

A connection-admitting/source owner stops admission, enumerates its remaining
lines, destroys its state, sends `Finish` away from any sender as applicable,
and returns with every owned line logically dead. A connection-holding tail
adapter has a different obligation: enumerate every line whose `Init` reached
it, detach and close its OS resource, destroy its adapter state, and send exactly
one downstream `Finish` so the real creator closes the line. A tail owns no
responsibility before its `Init`; the autonomous or internal creator must cover
that interval itself.

Source-owner draining runs on the owning event worker while the event loop,
chain, tunnel states, tail adapters, and line pools are still alive. NodeManager
visits tunnels in chain storage order, which is not guaranteed to be
source-to-tail. A middle or tail worker hook therefore cannot require borrowed
line sets to be empty based on neighbour ordering, and it must not build a
duplicate inventory merely to compensate. Middle tunnels do inventory and drain
normal lines they create internally. Final `onDestroy`, after all worker drains,
may diagnose a residual borrowed registry. Persistent packet lines and
documented terminal absorbers with no per-line resource are explicit exceptions
rather than missing inventories.

Every other tunnel must **propagate `Finish`** and let the owner destroy the
line. Calling `lineDestroy()` on a line you did not create is a serious bug.

There is also a debug invariant to respect: when a line is finally freed,
`lineUnRefInternal()` asserts that every tunnel's line state is already zeroed
(`debugAssertZeroBuf`). That is why each tunnel must destroy its own line state
before the real line-closing `Finish` propagates — unless it is intentionally
holding a positive reference across the close.

## Protecting a Line Across Re-entrant Callbacks

These inter-tunnel calls can indirectly close the line before they return. Treat
every one of them as dangerous:

```c
tunnelNextUpStreamInit       tunnelNextUpStreamPayload
tunnelPrevDownStreamInit     tunnelPrevDownStreamPayload
tunnelNextUpStreamEst        tunnelNextUpStreamPause      tunnelNextUpStreamResume
tunnelPrevDownStreamEst      tunnelPrevDownStreamPause    tunnelPrevDownStreamResume
```

After any of these returns:

- the line may already be dead,
- this tunnel's line state may already be destroyed and zeroed,
- any code that touches `line` or `ls` is unsafe unless you protected the line.

Never reason: *"the call returned, so my line state is still valid."*

### Method A — `lineCallWithRef()` (preferred)

`lineCallWithRef()` and `lineCallWithRefWithBuf()` hold a temporary reference across
the callback and tell you whether the line survived. Their actual implementation
(see `ww/net/line.h`) is:

```c
static inline bool lineCallWithRef(line_t *const line, LineTaskFnNoBuf task, tunnel_t *t)
{
    lineRef(line);
    task(t, line);
    if (! lineIsAlive(line))
    {
        lineUnref(line);
        return false;   // line died during the callback
    }
    lineUnref(line);
    return true;        // line still alive; safe to continue
}
```

Use it whenever you must keep working with the line after a re-entrant call:

```c
if (! lineCallWithRef(line, tunnelNextUpStreamInit, t))
{
    return;   // line died; do not touch line or ls
}

// Still alive here. Re-read state if you need it.
my_lstate_t *ls = lineGetState(line, t);
```

For payload forwarding, use the buffered variant:

```c
if (! lineCallWithRefWithBuf(line, tunnelNextUpStreamPayload, t, buf))
{
    return;
}
```

When a helper returns `false`:

- do **not** touch `line`,
- do **not** touch this tunnel's line state,
- do **not** call your `LinestateDestroy()` "just to clean up" — the close path
  that killed the line already did that,
- if you still own a buffer you did not hand off, recycle it without touching the
  dead line state.

Re-entrancy can also cross exact-line boundaries. A callback on line A may enter
a shared neighbouring tunnel that closes a different tracked line B. If a caller
keeps B in a pointer array or registry snapshot and will examine it after the
callback on A, it must retain B with `lineRef()` before the first callback and
release that reference on every path. Holding a reference only on A, or holding
a registry mutex while copying raw pointers and then releasing it, does not
preserve B's storage.

For example, a SOCKS UDP client can create a backend remote line whose `Init`
closes the control association and provider-owned client line. The caller must
capture the client's buffer pool and retain the **client** before invoking the
remote callback; retaining only the remote makes neither the dead client's
lstate nor `lineReuseBuffer(client, ...)` safe after return. If the client died,
recycle still-local bytes through the captured pool, unref the retained client,
and return without reading either line's destroyed state.

:::tip When you do *not* need the wrapper
If you call a forwarding helper and then immediately `return` with no further work
on the line, wrapping it in `lineCallWithRef()` buys you nothing — the boolean
result would not change your behavior. This is common for plain `Init` and
`Finish` pass-throughs.
:::

### Method B — Manual `lineRef()` / `lineUnref()`

Use manual reference management when you need explicit control across several calls:

```c
lineRef(line);

// one or more potentially re-entrant callbacks ...

if (! lineIsAlive(line))
{
    lineUnref(line);
    return;
}

// still alive: safe to continue
lineUnref(line);
```

Rules: always unref what you ref; never read tunnel state after destroying it;
if a helper both destroys your line state and propagates `Finish`, the caller must
return immediately afterward.

## Finish Semantics

`Finish` is **directional** and **destructive**, and it has one property that
makes it special among all the callbacks:

:::warning Finish forbids reflection on the same line
If Tunnel A sends `Finish` to Tunnel B for a line, Tunnel B must not call **any**
callback (including `Finish`) back in that same direction for that `line_t`.

This guarantee is specific to that line and direction. Handling Finish on line A
may synchronously send a payload on, or close, another still-live line B. This can
happen entirely on one event worker; worker-local ownership does not prevent it.

For example, A and B may share a UDP socket. While its close handler notifies A,
A's owner may cause a send on B before B receives Finish. B being alive, or holding
a line reference, does not make the shared socket usable. Shared-resource teardown
must close operation admission for all affected users before its first outward
callback, and cached send/queue paths must honor that gate. Review callbacks on
siblings as well as callbacks on the line being finished; see
[UDP send retirement in Part 7](./part7-shutdown-and-signals.mdx#udp-send-retirement).
:::

Concretely:

- A tunnel that **receives upstream `Finish`** must not send `tunnelPrevDownStream*`
  (Init/Payload/Est/Pause/Resume/Finish) back toward the sender for that line.
- A tunnel that **receives downstream `Finish`** must not send `tunnelNextUpStream*`
  back toward the sender for that line.

This is called **reflection**, and it is a frequent crash source precisely because
tunnels destroy their line state before propagating `Finish` — reflecting a
callback calls into a tunnel whose state for that line is already gone.

Turn the guarantee around and it becomes a simple, load-bearing rule: **because
`Finish` is non-re-entrant, you are promised you will not be called back on the
finished side — so you must extend the same promise and send nothing back.** The
instant you receive `Finish` from a direction, that direction is closed for that
line. No `Payload`, no `Est`, no `Pause`/`Resume`, no second `Finish`, for **any**
reason, on **any** later event for that `line_t`.

Also remember the destruction direction: a downstream `Finish` that reaches the
adapter which created the line will lead to `lineDestroy()`. So after you
propagate a downstream `Finish`, assume the line can be gone.

### The Simplest Clean Finish

A middle tunnel with nothing to flush just destroys its own line state and
forwards. This is `EncryptionClient`'s upstream finish, verbatim:

```c
void encryptionclientTunnelUpStreamFinish(tunnel_t *t, line_t *l)
{
    encryptionclient_lstate_t *ls = lineGetState(l, t);
    encryptionclientLinestateDestroy(ls);   // destroy local state first
    tunnelNextUpStreamFinish(t, l);          // then propagate
}
```

Order matters: destroy local state **before** propagating the real close. Do not
read any field of `ls` after `LinestateDestroy(ls)` — assume it is zeroed.

### Closing Both Directions From the Middle

When a middle tunnel itself decides to tear down an ordinary borrowed,
left-owned connection (a protocol error, a limit hit), it is responsible for
closing **both** sides. Under the ownership/topology contract above, the ordering is:

1. Destroy this tunnel's own line state.
2. Send the **upstream** `Finish` first. The right side borrows this line and
   must neither destroy it nor reflect callbacks toward the sender.
3. Send the **downstream** `Finish` second. This reaches the left-side owner and
   can destroy the line.
4. Return immediately.

```c
my_lstate_t *ls = lineGetState(l, t);
myLinestateDestroy(ls);          // 1. local state gone

tunnelNextUpStreamFinish(t, l);  // 2. close forward (line still alive)
tunnelPrevDownStreamFinish(t, l); // 3. close backward (line may die now)
return;                          // 4. do not touch l or ls again
```

The line surviving the first Finish follows from its owner being on the other
side, together with the no-reflection rule. Non-re-entrancy alone does not prove
that an arbitrary recipient cannot own and destroy a line. Apply the specific
ownership contract at reverse/Bridge boundaries and for internal companion
lines; do not apply this normal-line teardown recipe to a worker packet line.

Adapters are simpler: sitting at one end of the chain, they only ever send
`Finish` once, toward the opposite direction.

Lines you **own** are different again, and they carry a stronger, checkable
obligation — the next section.

### The Owner Finish Postcondition

> When a tunnel receives `Finish` for a **normal line it created**, that handler
> must not return while the line is still logically alive:
>
> ```c
> /* on return from the owner's Finish handler for a normal line */
> assert(! lineIsAlive(line));
> ```

The postcondition is about **logical** death only. Outstanding `lineRef()`
references may keep the allocation present until suspended or re-entrant frames
unwind; the memory does not have to be freed before the handler returns.

Before returning, an owner must:

1. **Detach every producer** that can still target the line — io callbacks,
   timers, idle-table items, lookup maps, queues, scheduled tasks.
2. Complete whatever cleanup is legal for the direction that sent `Finish`.
3. Destroy its own line state exactly once.
4. Propagate `Finish` only where the topology requires, and only **away from the
   sender** — the no-reflection rule is unchanged by ownership.
5. Call `lineDestroy(line)` unless a nested path already did.
6. Return immediately, touching no destroyed state.

For keyed or timed ownership, detach the map/timer entry and clear the
consumer's handle before invoking a re-entrant Finish or destroying the line.
An indexed idle entry must be removed immediately on explicit close; retaining a
long-deadline tombstone makes memory proportional to historical churn rather
than live ownership.

A creator such as `MuxClient` does exactly that. The excerpt below is
`muxclientTunnelDownStreamFinish()` — the `fnFinD` slot, so **next** is the
sender. The parent's children hang off the prev side, and prev is therefore the
only direction anything may travel:

```c
/* fnFinD on the parent line MuxClient created; next finished us. */
while (child_ls)
{
    /* ... */
    muxclientLinestateDestroy(child_ls);
    tunnelPrevDownStreamFinish(t, child_l);   // away from the sender
    /* ... */
}

muxclientLinestateDestroy(parent_ls);
lineDestroy(parent_l);                        // only the owner may do this
```

The general shape, with the copy-to-stack step that keeps the code safe after
`LinestateDestroy()`. Read the direction off the callback slot the handler is
installed in — this one is `fnFinU`, so **prev** sent it and `next` is the only
side that may be told:

```c
void ownerUpStreamFinish(tunnel_t *t, line_t *l)
{
    owner_lstate_t *ls = lineGetState(l, t);

    ownerDetachResources(t, l, ls);                  /* 1 */

    bool propagate_away = ls->next_init_sent;        /* copy before destroying */
    ownerLinestateDestroy(ls);                       /* 3 */

    if (propagate_away)
    {
        tunnelNextUpStreamFinish(t, l);              /* 4 */
    }
    if (lineIsAlive(l))
    {
        lineDestroy(l);                              /* 5 */
    }
    return;                                          /* 6 */
}
```

The `fnFinD` mirror is the same function with `tunnelPrevDownStreamFinish()` in
step 4. An **endpoint** owner — a chain head such as `TcpListener` or
`UdpStatelessSocket` — has no prev at all, so its `fnFinD` propagates nothing and
step 4 disappears. The postcondition is unchanged either way.

**Why it matters.** Without it, this sequence corrupts memory: a middle tunnel
forwards a re-entrant callback; a nested `Finish` destroys that middle tunnel's
per-line state; the line owner receives the propagated `Finish` but leaves the
line alive; the outer callback then reads `lineIsAlive(line) == true` and resumes
against state that no longer exists. The postcondition makes `lineIsAlive()` an
honest post-callback signal.

**Borrowed lines are the mirror image.** Destroy only your own per-line state,
propagate the same directional `Finish` away from the sender when the topology
requires it, and **never** call `lineDestroy()` — the real owner's destroy must
stay valid. Never reflect `Finish`, payload, `Est`, `Pause`, or `Resume` back
toward the side that finished you.

**A middle tunnel that also owns the line** still follows the both-directions
ordering above for its *local* close, and then the owner postcondition applies on
top: the line must be dead before that close frame returns.

**`requestProgramShutdown()` does not satisfy the postcondition.** It schedules
global teardown on worker 0; the current worker callback returns and unwinds
through every suspended frame first. An owner whose `Finish` reaches a terminal
failure must still detach, destroy its state, and mark the line dead — and *then*
request the shutdown.

**Deferred OS cleanup is not an excuse to stay alive.** If a resource needs
asynchronous teardown, detach it from the line first and give the deferred
cleanup object its own copy of whatever it needs. A live line is not a cleanup
token.

**Packet lines are excluded.** They are never subject to the owned-normal-line
postcondition and must never be destroyed at runtime. A `Finish` on one is not
automatically a contract violation: a packet-lifecycle anchor may reject it, a
transparent middle transform forwards it in the same direction, and an
intentional terminal absorber may absorb it when there is nothing onward to
notify or release. The exact handler role and direction decide which category
applies — see [Part 4](part4-packet-tunnels.mdx).

### Most Tunnels Need No Directional-Finish State

A direct consequence of non-re-entrancy: **do not give a tunnel
`prev_finished` / `next_finished` (or `can_upstream` / `can_downstream`) flags by
default.** A tunnel that simply forwards `Finish` is guaranteed never to be called
back on the finished side, so it has nothing to remember. A speculative
"did this side finish?" boolean is almost always a control-flow problem being
patched instead of fixed — the same anti-pattern as an `initialized` flag.

There is exactly **one** situation that justifies directional-close state: the
tunnel must **send final bytes before it closes**, including a bounded delayed
fallback batch (the next subsections). That send re-enters the adapter or branch,
which can emit `Pause`/`Resume`, and the flag is what lets handlers drop anything
that would reflect toward the already-finished side. The flag is bookkeeping for
that hazard and nothing else.

Real tunnels carry exactly this state and no more. The names differ; the role is
identical:

| Tunnel | Directional-close state | Why it needs it |
| --- | --- | --- |
| `TlsServer` | `upstream_finished`, `downstream_finishing`, `fallback_close_draining` | Sends TLS alert / close and settles delayed fallback before closing |
| `TrojanServer`, `VlessServer` | `fallback_close_draining` | Settles a delayed fallback batch without reflecting toward the finished previous side |
| `TcpOverUdpClient` | `can_downstream` | Must finish its reliable-stream teardown before closing |
| `TcpOverUdpServer` | `can_upstream` | The same, in the opposite direction |
| `HttpClient`, `HttpServer`, `Socks5Server` | `prev_finished`, `next_finished` | Send final protocol bytes before transport close |

If your tunnel does **not** send final bytes during `Finish`, it should not carry
any of these flags. Destroy local state and forward — that is the whole job.

### Final Protocol Bytes Before Closing

Some protocols must emit closing bytes before the transport closes: TLS
`close_notify`, an HTTP final chunk, HTTP/2 `END_STREAM`, a WebSocket close frame,
a KCP close frame. Sending those bytes during `Finish` opens a dangerous
re-entrant window.

The hazard, step by step:

```text
1. Tunnel receives Finish from side A.
2. It sends final protocol bytes toward side B.
3. Side B's adapter blocks while writing and emits Pause (or later Resume).
4. That Pause/Resume travels back through the tunnel...
5. ...and if the tunnel reflects it toward side A — whose state was already
   destroyed by the original Finish — it calls into freed/zeroed state. Crash.
```

The required safe shape:

1. `lineRef(line)` — you are about to send bytes re-entrantly.
2. **Mark the sender side finished first**, using the tunnel's existing
   directional state (`prev_finished`, `next_finished`, `can_downstream = false`,
   `can_upstream = false`, etc.). Your `Pause`/`Resume` handlers must check this
   and refuse to reflect toward a finished side.
3. Send the final protocol bytes toward the other side.
4. Destroy this tunnel's local line state.
5. Propagate the real WaterWall `Finish`.
6. `lineUnref(line)`.
7. Return immediately. Do not touch local line state afterward.

Direction examples:

- Handling **upstream** `Finish`, sending final bytes upstream to `next`: any
  **downstream** `Pause`/`Resume` caused by that send must not be forwarded back
  to `prev`.
- Handling **downstream** `Finish`, sending final bytes downstream to `prev`: any
  **upstream** `Pause`/`Resume` caused by that send must not be forwarded back to
  `next`.

Do not invent a new `initialized` flag for this. Reuse the tunnel's existing
directional finish/close state, or — if the tunnel genuinely lacks one and this is
the final-bytes case — add an explicit directional close flag. As stressed above,
this is the **only** place such a flag belongs.

### TlsServer SNI fallback admission

`TlsServer` borrows the normal line created by its upstream owner. With both `sni`
and fallback configured, its OpenSSL early ClientHello callback compares the visible
SNI before TLS output. A mismatch or absent SNI suspends OpenSSL; the payload driver
must replay the retained original wire bytes to fallback before later payloads.
Matching SNI continues to the protected branch. Without fallback, the SNI gate
still rejects mismatches. Malformed ClientHello/SNI input rejected before routing
stays on the TLS error path.

The original transcript is bounded to 1 MiB, including record headers and coalesced
trailing bytes, and the existing handshake deadline covers incomplete input.
Retained snapshots use compact byte copies and coalescing; never retain a full
receive allocation for each tiny fragment merely because the logical byte count
is below the limit. Copies carry the line pool's left padding for later replay.
ServerHello, including HelloRetryRequest, commits the protected TLS branch: never
switch to fallback afterward. Starting fallback releases TLS state and disarms its
deadline before branch Init. Queue the entire initial input before invoking Init,
including the triggering plaintext buffer when applicable. While Init is on the
stack, later re-entrant input may enqueue behind it, but neither inline payload
nor scheduled drains may run, including through Resume. After Init survives,
release this admission barrier and drain in FIFO order subject to backpressure.
A close during Init discards queued input instead of sending payload into an
unfinished Init callback. Preserve the borrowed line's reference/owner rules.

### Delayed Fallback Batches Before Closing

A scheduled line task holds a physical line reference only. It does **not** keep
the line logically alive, and its runner intentionally skips the callback after
the owner destroys the line. A borrowed middle tunnel therefore must never park an
upstream `Finish` behind a line timer merely because its fallback payload queue is
delayed.

For an initialized fallback branch, use this close order:

1. Mark the previous side finished and publish a fallback-drain gate before any
   final branch `Payload` callback. An empty queue can destroy local state and
   synchronously finish the initialized branch immediately.
2. For a non-empty bounded FIFO, capture the branch and line pool, detach the
   queue from line state, range-check its total, and coalesce it in FIFO order
   into one buffer. One callback prevents a synchronous `Pause` from being
   followed by another newly initiated payload from the same batch.
3. If the branch was already paused, it cannot receive even that one payload.
   Recycle the still-local batch and finish it, or move it to a genuinely detached
   owner; do not bypass backpressure to preserve close-time bytes.
4. While the final callback runs, absorb supported `Init`, `Est`, `Pause`, and
   `Resume` callbacks, and recycle any returned `Payload`. A callback explicitly
   forbidden by the receiving node remains fatal; for example, `TlsServer`
   rejects downstream `Init` even during this drain. A re-entrant downstream `Finish` records that
   the branch already closed and is absorbed, so no reflected or duplicate branch
   `Finish` follows.
5. Re-check `lineIsAlive()` after the final payload while holding the temporary
   reference. If it died, unref and return without touching line state. Otherwise
   destroy local line state before the final branch `Finish`; after that finish,
   only unref and return.

The old timer has no cancellation handle. Emptying/detaching its queue logically
cancels the work; once the real owner destroys the line, the scheduled runner
becomes a harmless reference release. Preserving the exact remaining delay after
`Finish` instead requires a detached session object that owns copied buffers,
timer state, and branch resources without any `line_t` or line-state reference.
That is a different design, not an excuse to keep a borrowed line alive.

With delay zero, the safe referenced inline path is available only when fallback is
unpaused and has no older FIFO batch or scheduled drain. Retained bytes resume
through the scheduled drain, so later payload cannot overtake them.

### Adapters Flush On Their Own

Adapters such as `TcpConnector` and `TcpListener` may flush queued bytes before
they actually close the socket after receiving `Finish`. So a middle tunnel
should: send its final protocol bytes, destroy local state, forward `Finish` —
and then trust the adapter to flush. Do **not** keep protocol state alive just to
"wait for the socket to drain."

## Est, Pause, and Resume

- **`Est`** reports adapter transport establishment. Middle tunnels must relay it
  promptly; their own protocol readiness must not delay or replace that signal.
- **`Pause` / `Resume`** are backpressure signals. Emit them only when
  semantically correct and directionally consistent, and never reflect them back
  toward a finished direction (see above). Do not emit them casually; spurious
  pause/resume can deadlock a stream.

### Est Is Transport Readiness

Adapters originate and consume transport establishment for their connection.
On a continuing normal-line path, an intermediate node must forward a received
`Est` in its supported callback direction without waiting for its request header,
first application payload, authentication, protocol reply, handshake completion,
timer or consumer Resume. In the ordinary upstream-created chain, next-side
`Est` continues toward prev with `tunnelPrevDownStreamEst()`.

Transport establishment and protocol readiness are different facts. A middle
node may record transport state and perform required protocol work, but it must
keep the protocol's readiness and payload barriers separate. `Est` does not prove
authentication, destination acceptance by a remote proxy, or completion of TLS
or another negotiation. Use explicit protocol state and, where two cooperating
nodes need notification, a dedicated protocol-completion hook. Do not send a
second transport `Est` when that protocol work completes.

Publish local establishment/notification state before forwarding: the previous
node can synchronously submit Payload, Pause, Resume or Finish. Keep accepted
payloads ordered and bounded until their protocol can carry them. Preserve the
required wire order, including control messages before application bodies, even
when application data arrives from the Est callback. Pause controls new producer
admission and independent drains, not the establishment signal or the bounded
completion of an already-admitted synchronous input batch. Continuing after any callback still requires the exact
line references and logical-life checks described above. Never forward into a
finished direction or on a logically dead line.

Classify each exact line at topology boundaries. A node that owns a carrier,
multiplexes children, pairs streams or bridges a packet line can terminate one
line lifecycle and map readiness to another; it must use that role's explicit
mapping and notify a live application association once. Do not blindly forward
an owned helper line into a neighbour that was never initialized for it, broadcast
one child's Est to unrelated children, or manufacture establishment before the
relevant transport or local lifecycle endpoint exists. Boundary ownership is not
permission to delay a continuing line's Est behind protocol negotiation.

Payload admission does not require a prior Est. After the adjacent Init has
admitted the exact line, a live node may submit valid protocol bytes while the
transport is connecting; the transport owner handles connection-time writes.
This does not permit Payload before Init, unauthenticated forwarding, application
bytes before required wire headers, or callbacks into a finished direction.

A continuing transform deduplicates with its own notification latch when needed;
a downstream endpoint may mark the shared line before forwarding Est. The shared
marker alone does not prove that the notification reached this transform.

`lineIsEstablished()` / `lineMarkEstablished()` describe line establishment,
not protocol readiness. This rule does not enable otherwise unsupported upstream
Est callbacks on ordinary tunnels, change disabled adapter edges, or replace the
[packet lifecycle rules](./part4-packet-tunnels.mdx).

### Flow-Control Roles and Admission

Flow-control responsibility follows the work a node owns, not its protocol name
or whether its line is borrowed. A node can have different roles in its two
directions or before and after a protocol transition.

| Role | Responsibility |
| --- | --- |
| Source or transport adapter | Control new reads/emissions, accept bounded in-flight output, serialize writes and own the necessary transport queue. |
| Synchronous transform | Forward Pause/Resume promptly and transform already-admitted input inline. Do not add an output queue solely because the next consumer paused. |
| Protocol parser | Retain incomplete headers/bodies and ordering-critical input under explicit bounds. Parsing storage is not an extra transport-output queue. |
| Independent producer or retained-backlog drain | Stop starting new output when its consumer is paused; resume its own ordered work when permission returns. Timers, handshake releases and delayed replay belong here. |
| Association or multiplexing junction | Map exact lines, combine pressure reasons, and own only the queues needed to order or schedule its independent producers. |

Pause tells a source or independent drain to stop admitting new work toward that
consumer. It does not revoke ownership already transferred into an active
synchronous input batch. A regular transform forwards the signal toward the
source, then may finish that batch, checking logical life after every callback.
It must not read more input, start a timer-generated send, or append unrelated
queued work to the active batch merely to evade Pause.

#### Completing an admitted input batch

An input batch consists of one accepted Payload delivery and the bounded parser
prefix/partial frame needed to interpret it. The node must establish its ownership
and FIFO position before invoking another node. Completing this batch can emit
multiple Payload callbacks; these are expected to reach a receiver even after
Pause propagated synchronously through the chain.

Trojan and VLESS UDP decoders complete all complete datagrams in that accepted
input after Pause. They do not leave ready datagrams queued solely for Resume or
stop header parsing solely because Pause arrived during an earlier delivery.
They retain only an incomplete suffix or input held for a genuine protocol or
reentrancy barrier. Reentrant input has its own FIFO position and bound; serialize already-admitted
nested batches after older input within the outer synchronous dispatch. They must
not be relabeled as one ever-growing batch. Work deferred beyond that dispatch,
or released by a later protocol-completion/task callback, is an independent
backlog whose drain respects Pause.

Finish, logical death, protocol rejection and hard-limit refusal are terminal:
stop immediately and release the untransferred remainder. Batch completion never
permits callbacks after Finish or requires a receiver to exceed its hard limit.
A partial frame still needs later input; its existence must not itself suppress
the Resume that allows its producer to complete it.

#### Receiver tolerance and FIFO ownership

A receiver requesting Pause must retain finite admission headroom for output
already in flight. Specify the supported batch envelope, transformation expansion,
queue high/low watermarks, hard limits and overflow policy. Count retained bytes
and entries or allocation charge; tiny and empty datagrams must consume a finite
budget. One coalesced stream input can decode into many datagrams, so a payload-byte
limit alone is not a complete resource bound.

Tolerance is not unlimited acceptance or a guarantee that every protocol-valid
burst fits during congestion. If a burst exhausts the hard limit, close the
smallest supported association or apply the node's documented datagram-drop policy.
Never drop arbitrary TCP bytes, silently lose an accepted suffix, or allocate
without a bound to finish a batch. The sender rechecks exact-line life after each
handoff and stops on closure. Stronger admission reservations may be used where
an entire maximum batch must be guaranteed, but that guarantee must be explicit.

Publish ownership, queue accounting and notification state **before** emitting
Pause, Resume or any callback that can reenter. A callback must not allow newer
data to overtake an older buffer that is still only in a local variable. Ordinary pop releases budget usage before handing a buffer onward. If the same
budget still owns active retention, transfer to a reservation without uncharging;
publish consumption before callbacks and release when that responsibility ends. Use one authoritative FIFO per independent
ordering obligation; a guarded admission/drain can serialize reentry without
adding permanent queues to every middle node.

Resume releases a producer according to the consumer's current policy. It does
not prove that every queue is empty. A junction forwards Resume only after all
pressure reasons for that producer have cleared. Transparent transforms relay
Pause/Resume without inventing their own thresholds or permanent permission queues.
A node that also owns a timer or backlog may record permission for that role
without gating its synchronous forwarding path on the same flag.

BGP and other protocol engines can retain queues for their own negotiation,
control generation and independent drains. Those obligations require explicit
bounds and permission handling; they do not establish a requirement that every
ordinary encoder/decoder own a transport queue.

MuxClient and MuxServer are examples of explicit local buffering: parent transport
Pause immediately forbids all parent-bound Payload, including protocol controls.
They retain encoded output in a bounded per-parent FIFO and pause child producers
at its aggregate queue-capacity threshold, in addition to individual writer holds.
Complete queued frames retain valid private bodies under local queue limits. Incoming assembly and attached child queues share
the existing parent receive limit, with beneficial pressure compaction followed by
largest-child shedding or parent close. There is no worker-wide pipe quota. Pause
still forbids Payload, not retention; see the [Part 3 contract](./part3-buffers-and-padding.mdx#queue-capacity-budgets).
A blocked child writer acquires its own local producer hold immediately after
admission, including empty Data and complete splice batches. A direct write that
leaves the transport paused holds its writer before returning; a transient Pause
then Resume uses the final permission. Controls alone are not attributed writers.
Idle siblings below aggregate high water remain runnable. At high water the
separate pause-all latch holds every attached open child.

The local hold FIFO borrows attached child state and is independent of that
latch. Release requires a live parent state, no Finish/quiescence, writable
transport and charge at/below low water, even when pause-all never activated.
Recheck after every callback and before each release/pop. New output appends
behind existing FIFO entries; renewed transport pressure or charge above low
water stops release. A writer held again joins behind remaining waiters. Snapshot
references protect every member before any callback, followed by logical-life,
attachment and state checks. No persistent references or second cursor are used.

Init/Est defers permission callbacks without confusing a recorded reason with an
emitted Pause. Completion reconciles the current reasons once safe. Peer pressure
and terminal-close state remain independent; local unlink and terminal paths
remove held-list membership without emitting Resume. A writable empty parent
must release ready waiters rather than depend on a future transport event.
TcpListener also preserves a Pause received during accepted-line Init: it enables
initial reads only if Init returns alive and the source is still unpaused.

Mux's fixed header cache owns consumed header bytes until the exact body is
extracted. No callback observes detached stream ownership. Large splice encoding
publishes the complete frame batch and Open state before any callback. A Pause
during its first delivery leaves all later frames in the parent FIFO; nested Data
or child Close follows that remainder. Parent death discards it, while child death
alone does not release its cost. Ordinary large encoding keeps one aggregate.

A local child Pause submits FlowPause immediately, without a queued-byte
threshold. MuxClient defers this control until Open has been admitted. After
submitting the complete first payload, including a large splice batch, it must
re-check both referenced lines and the child's attachment and pause state before
submitting any deferred FlowPause. A resume or close during submission must not
produce a stale control, and an already submitted FlowPause must not be repeated.
FlowResume still requires a writable child and logical queued payload below its
configured resume threshold.

Submitting a Mux control frame can close its child during queue-pressure
callbacks while leaving the parent alive. The receive path distinguishes
those outcomes: it retains the parent across callbacks, stops using the closed
child, and continues processing complete sibling frames on the surviving parent.
Remaining incoming child queues still undergo the normal parent memory-limit check.

UdpConnector rechecks both line life and read-pause state after its fallback
receive-time Est callback. If Est pauses the line, the already-read datagram is
recycled under the same drop policy as other paused receives; it is not delivered
through Pause. Later datagrams may be delivered after Resume.

Transport queue admission must be transactional before threshold callbacks.
Once a queue owns the incoming buffer, callback-driven close releases it through
that queue; the caller must not recycle it again. If admission fails before
ownership transfers, the caller recycles it through the captured line pool and
settles the affected flow. Exact-line references protect callbacks, not logical
life. Preserve this ordering in connecting, paused-write and write-completion paths.

TCP adapters attach their FIFO to a shared byte/charge budget and transfer popped
entries to an active WIO reservation. The original admitted capacity charge remains
until completion or terminal callback detachment. Partial write callbacks, live
write returns and new admissions refresh logical bytes from WIO without reading
the transferred buffer. Cleanup settles reservations before destroying line state;
deferred WIO cleanup retains no budget pointer. UdpConnector initialization and
all per-destination DNS queues attach to one line budget, including recreated DNS
queues; socket datagram writes do not create an active reservation or retry queue.
Empty retained buffers consume charge and entries.

TLS/Reality pending plaintext queues share their existing byte/entry limits with
active backlog reservations. Consumed plaintext releases bytes before wire-output
callbacks, while capacity and the entry remain charged until buffer release.
Direct synchronous inputs retain their existing admitted-input behavior. TrojanServer
attaches its populated FIFO only when selecting CONNECT or fallback output; initial
and UDP parser fragments retain their separate byte and framing policies.

Numeric thresholds and hysteresis are implementation details. Read the target
adapter's `payload.c`, `helpers.c`, and `structure.h`; do not copy one adapter's
current tolerance into another node or into this guide as a universal value.

### Client destination preparation before DNS

TrojanClient, VlessClient and Socks5Client apply their configured address, port
and TCP/UDP selection to the line's destination context before local DNS
resolution. Their internal DomainResolver invokes a client-owned prepare hook;
the resolver itself does not choose the client's protocol. These hooks need no
custom resolver line-state storage.

DNS resolution replaces the destination address while preserving the selected
protocol flags. When Init reaches the client, read those flags from the prepared
destination context. Without local DNS, the client applies the target directly
in Init and then reads the same flags. Target preparation leaves exactly one of
TCP or UDP selected; this is a debug invariant at the client entry, not another
runtime configuration check.

Do not apply the target settings a second time after DNS: a configured domain
could overwrite the resolved destination. Protocol-selection warnings and the
existing TCP fallback for an invalid incoming `dest_context->protocol` belong
to target preparation and occur there once.

### SOCKS transport readiness and protocol ordering

Socks5Client forwards transport Est before negotiation, mapping a UDP control
carrier to its application once. Authentication, command success and relay
readiness retain their distinct application-data gates. Its pending application
FIFO uses the default 2 MiB / 1,024-buffer backlog budget described in
[Part 3](./part3-buffers-and-padding.mdx#protocol-storage-and-admitted-batches).
It releases independently, honors Pause and keeps nested input behind older bytes.
The first retained application input pauses its source; protocol backlog pressure
and transport pressure share one notification latch, and Resume waits until both
clear. Protocol-wait pressure must not stop handshake progress.
Socks5Server forwards Est before generating its success reply; that reply still
precedes backend response bodies, including under Init/Est reentry and Pause.

DomainResolver accepts upstream Init and delays next Init until destination DNS
completes. Its prepare hook runs before resolution and has no direction argument.
Downstream Init and upstream Est retain the normal constructor's rejection policy;
this is a node-specific contract, not a rule for reverse/Bridge or companion lines.
Payload, Pause/Resume and Finish still operate in both ordinary directions.

The resolver keeps one authoritative upstream backlog through next Init. The
Open phase permits downstream Est and replies immediately; an Init guard serializes
new upstream input behind older DNS input. DNS completion releases that FIFO
independently and observes next-side Pause. Admission checks logical bytes and
retained allocation charge separately against 2 MiB per line, including empty
buffers. The local DNS/backlog hold combines with next-side pressure before
notifying prev. Upstream receive pressure is remembered during DNS and forwarded
to next once Init starts. Failures before next Init finish only prev; internal
failures after it starts finish both initialized sides. Received Finish destroys
local state first and propagates only away from its sender.

### TrojanClient establishment and association ownership

TrojanClient borrows direct TCP and UDP application normal lines. UDP creates one
owned normal TCP carrier on the application's worker; only that carrier receives
next Init. The application keeps its UDP routing context. Signal forwarding maps
the application and carrier explicitly, retaining both exact lines across callbacks
and checking logical life and association afterwards.

A valid first application payload can submit the request after next Init, without
waiting for transport Est. The request and complete first payload share one ordinary
buffer; later TCP forwarding is opaque. Transport Est is forwarded once and starts
an idle first-payload deadline only if the request has not already been sent. The
configurable header-only timeout is an independent producer: while next is paused,
it retains a due flag rather than starting a new send. An admitted application
Payload can still complete its combined-buffer handoff under the batch contract.

Ordinary TCP forwarding and one-datagram upstream wrapping do not gain separate
Pause queues. Downstream UDP retains framing input and completes the current
accepted input batch. Keep only the guard/storage needed for parser reentry,
initialization ordering or a genuine protocol wait. A node-wide pump is not a
contract; use explicit directional handlers and focused helpers for actual work.

Close cancels the deadline, detaches both association links and destroys locally
owned buffers/state before outward Finish. Only the carrier is destroyed here.
Source-owner shutdown drains the dependent carrier while loops, chains and pools
remain alive. No duplicate borrowed-line inventory is needed.

### VlessClient establishment and association ownership

VlessClient borrows direct TCP and UDP application lines and owns only each UDP
application's dependent TCP carrier on the same worker. Both links are attached
before next Init. Its first-payload batching, idle deadline, signal mapping and
opaque TCP paths follow the same ownership/admission rules as TrojanClient.

VLESS protocol readiness remains separate. The request must precede upstream body,
but neither transport Est nor a response is required before submitting a valid
request/body batch after Init. Downstream body waits for complete validated
response metadata. Consuming that metadata cannot lose or reorder a coalesced TCP
body or the first UDP frame. UDP input retains incomplete framing bytes, completes
all ready datagrams in its active accepted batch and preserves an incomplete suffix.

Record request admission before the first outward callback so nested data cannot
send a second request or overtake it. Protocol/reentry storage is bounded; an
otherwise-ready TCP buffer is not retained merely for Pause or Est. Independent
release of an older deferred backlog still respects its consumer's permission.
Close clears timer/parser/ordering state and both links before outward Finish,
never reflects toward its sender, and leaves an owned carrier logically dead.

### TrojanServer associations and fallback replay

TrojanServer borrows the client normal line and owns each UDP backend on that
client's worker. Target, credentials, map membership and callback-ready state must
be published before backend Init. AuthenticationClient is a lookup dependency;
UserController runs only on the protected branch. Authentication, initial parsing
and exact fallback replay remain required independently of transport Est.

After selecting and initializing the TCP/fallback branch, ordinary synchronous
body/reply forwarding needs no queue solely for Pause or Est. Preserve older body
or replay bytes across reentrant branch Init; this is a protocol-ordering barrier,
not permission to maintain permanent TCP transport queues. A local fallback may
send Payload and Finish within Init without ever sending Est.

UDP is an association junction. Upstream callbacks operate on the borrowed client;
backend upstream events use each owned backend, and replies/notifications return
through downstream callbacks. Aggregate backend pressure by exact membership: one
backend's Resume cannot release a carrier still paused by another backend. Client
reply pressure applies to every initialized backend, including new backends.
Publish each contribution before callbacks, clear it on removal, and restart
traversal after callbacks rather than retaining raw sibling pointers or iterators.

Pause stops future carrier admission, not completion of the carrier input already
being decoded. Each complete datagram in that active input is submitted to its
selected backend even if an earlier datagram caused Pause; the backend's receiver
owns bounded in-flight tolerance. Preserve framing/destination checks, initial
input ordering and the incomplete suffix. Stop immediately if the affected line
or association closes. Do not drain unrelated pending input as part of this batch.

Replies received on initialized live backends do not wait for backend Est. They may
forward synchronously with the required datagram framing. If independent backend
producers or reentry require an association FIFO, keep one bounded encoded FIFO,
account entries before callbacks, and stop its independent drain at consumer Pause.
Already-admitted immutable replies belong to the client FIFO and do not need a
borrowed backend pointer kept alive merely as an Est waiter.

Intentional fallback delay owns a real backlog and scheduled drain. That drain
honors Pause and preserves FIFO; Resume permits older ready work before releasing
new producers. Source Finish retains the existing narrow final-batch exception:
at most one synchronous batch, outside branch Init, while unpaused, with the
finished side closed before any callback. Returned callbacks cannot revive parsing
or reopen the finished direction. A zero-delay inline fallback transform follows
the ordinary admitted-batch rule; a deferred release follows the backlog rule.

Retain the client across association callbacks and each exact backend across its
own Init/Payload/permission calls. Close detaches membership and selected-input
links before callbacks, releases only locally owned bytes and returns with owned
backends logically dead. Source shutdown settles dependent lines and delayed work
before reclaiming their reachable resources.

## Worked Example: Tracing a Payload

Consider the chain:

```text
TcpListener -> ObfuscatorClient -> TlsClient -> TcpConnector
   (head)         (middle)          (middle)      (tail)
```

**Upstream (client to remote):**

```text
client bytes arrive at TcpListener's socket
  TcpListener: tunnelNextUpStreamPayload(t, line, buf)
    -> ObfuscatorClient.fnPayloadU: scramble bytes, forward upstream
      -> TlsClient.fnPayloadU: encrypt via BoringSSL, forward upstream
        -> TcpConnector.fnPayloadU: write ciphertext to the remote socket
```

**Downstream (remote to client):**

```text
remote bytes arrive at TcpConnector's socket
  TcpConnector: tunnelPrevDownStreamPayload(t, line, buf)
    -> TlsClient.fnPayloadD: decrypt, forward downstream
      -> ObfuscatorClient.fnPayloadD: unscramble, forward downstream
        -> TcpListener.fnPayloadD: write plaintext to the accepted client
```

Notice that the **same** `TlsClient` instance handles encrypt on `fnPayloadU` and
decrypt on `fnPayloadD`. The direction, not the tunnel, decides the
transformation. If `TlsClient`'s upstream payload write blocks at `TcpConnector`,
backpressure flows back as a `Pause` in the downstream direction — and must not be
reflected past a side that has already finished.

## Checklist for This Part

Before you call a flow change done:

- Does `Init` initialize this tunnel's line state before any callback can use it?
- Are upstream callbacks forwarded only with `tunnelNextUpStream*`, and downstream
  only with `tunnelPrevDownStream*`?
- Does every re-entrant call either return immediately or protect the line with
  `lineCallWithRef()` / manual `lineRef()` + `lineIsAlive()`?
- On a `false` from `lineCallWithRef()`, do you avoid touching `line`, `ls`, and
  `LinestateDestroy()`?
- Does `Finish` destroy local state **before** propagating the real close?
- When closing from the middle, do you finish upstream first, then downstream,
  then return?
- If you send final protocol bytes during `Finish`, do you mark the sender side
  finished before the send and block reflected `Pause`/`Resume`?
- Does Pause stop new source admission and independent drains while allowing only
  the bounded completion of admitted synchronous input? Are receiver tolerance,
  FIFO publication, tiny/empty entries and overflow/close behavior explicit?
- Does retained data have a parser, protocol, ordering or producer obligation,
  rather than an unnecessary output queue copied into a transparent transform?
- Does only the line **owner** ever call `lineDestroy()`?
- Did you classify each line as **owned normal**, **borrowed normal**, or
  **packet** before editing its `Finish` path?
- Does every owner `Finish` path for a normal line return with
  `! lineIsAlive(line)` — including the error, timeout, and terminal-verdict
  branches?
- Are io callbacks, timers, idle items, and map entries detached before the
  owner's state and line are destroyed?
- Does a borrowed-line path avoid `lineDestroy()` entirely?
- Is `requestProgramShutdown()` used *in addition to* closing an owned line, never
  instead of it?
- Did you avoid adding an `initialized` flag the source does not require?
