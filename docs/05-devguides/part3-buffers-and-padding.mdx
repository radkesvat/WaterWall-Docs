# Part 3: Buffers, Padding & Shift Buffers

If your change frames payloads, prepends a header, rewrites bytes in place, or
allocates working memory, you must understand `sbuf_t`, the buffer pools, and the
chain-wide left-padding contract. Getting this wrong produces tunnels that work in
one chain layout and corrupt memory in another.

Source of truth: `ww/bufio/shiftbuffer.h`, `ww/bufio/buffer_pool.h`, and the
`required_padding_left` field in `ww/objects/node.h`.

## The `sbuf_t` Anatomy

WaterWall payloads are carried in `sbuf_t` ("shift buffer"), a padded, shiftable
byte buffer. Its header is exactly 32 bytes and the data area is 32-byte aligned
(so AVX2 copies stay aligned):

```c
struct sbuf_s
{
    uint32_t curpos;       // offset of the current payload start within buf[]
    uint32_t len;          // current payload length, in bytes
    uint32_t capacity;     // total allocation of buf[] (constant for the buffer's life)
    uint16_t l_pad;        // reserved left padding (constant once created)
    uint16_t flags;
    uint8_t  buf[];        // 32-byte aligned data
};
```

For ordinary buffers, the cursor moves inside a fixed allocation. The flag
`kSbufFlagSplice` gives the payload a different representation, described below.
The storage diagram and accessor descriptions here apply to ordinary buffers:

```text
   |<-- left capacity -->|<------- payload (len) ------->|<-- writeable tail -->|
   +---------------------+-------------------------------+----------------------+
buf[0]                curpos                        curpos+len             capacity
   |<------ l_pad ------>|
   (reserved padding)
```

- **`curpos`** moves left when you prepend (shift left) and right when you consume
  from the front.
- **`len`** is how many payload bytes are valid starting at `curpos`.
- **Left capacity** (`sbufGetLeftCapacity` = `curpos`) is how many bytes you can
  still prepend by shifting left.
- **Writeable tail** (`sbufGetMaximumWriteableSize` = `capacity - curpos`) is how
  much you can address forward from the cursor — note this is **not** the spare
  room beyond the current payload; to append `extra` bytes compare against
  `len + extra`.

### Key Accessors

| Call | Returns |
| --- | --- |
| `sbufGetLength(b)` | current payload length (`len`) |
| `sbufGetRawPtr(b)` / `sbufGetMutablePtr(b)` | pointer to the payload start (`buf + curpos`) |
| `sbufGetLeftCapacity(b)` | bytes available to prepend (`curpos`) |
| `sbufGetMaximumWriteableSize(b)` | bytes addressable from the cursor (`capacity - curpos`) |
| `sbufGetTotalCapacity(b)` | full allocation (constant) |
| `sbufGetLeftPadding(b)` | the original `l_pad` value |

### Reading and Writing

Aligned and unaligned integer helpers exist for header fields:

```c
sbufWriteUI16(b, port);            // aligned 16-bit write at the cursor
sbufWriteUnAlignedUI32(b, value);  // unaligned 32-bit write
uint16_t v; sbufReadUI16(b, &v);   // aligned read
sbufWrite(b, src, n);              // raw copy of n bytes at the cursor
sbufConsume(b, n);                 // drop n bytes from the payload tail count
sbufShiftRight(b, n);              // advance cursor: consume n bytes from the front
```

### Splice payloads: `kSbufFlagSplice`

`kSbufFlagSplice` identifies a dedicated `sbuf_t` wrapper for payload held in
the kernel. Its physical control storage is 32 bytes plus reserved left padding.
A `wio_fd_t *` is stored at the original payload start, `buf + l_pad`; the
object itself remains separately allocated. This pointer identifies the source
socket and its lazily initialized pipe. It is control data and does not count
as payload bytes. The preceding `l_pad` bytes are real reserved headroom.

`sbufCreateSplice(pad_left)` and `bufferpoolGetSpliceBuffer(pool)` return empty
wrappers with only `kSbufFlagSplice` set. Before use, the caller initializes the
descriptor pointer, the FD/Piped location flags, and the logical payload size.
These allocations are dedicated to splice metadata; ordinary payload bytes use
the small/large buffer APIs. Ordinary buffer duplication does not select the
splice pool.

Splice buffers must not carry `sbuf_lifetime_t` metadata: their `lifetime` must
remain `NULL`. Both WIO splice helpers check this with ordinary debug `assert()`
calls.

Two additional flags describe the location of the represented body. Both are
meaningful only when `kSbufFlagSplice` is set:

- `kSbufFlagSplicePiped`: the body has been spliced into the descriptor's pipe.
- `kSbufFlagSpliceFD`: the body remains in the source file descriptor.

For this representation, length and capacity describe the logical payload,
whose body may still be in the socket or have been moved into its pipe.
They do not describe the wrapper's physical
allocation or authorize reading or writing that many bytes through a buffer
pointer. A tunnel may trust these sizes for accounting and forwarding while
treating the kernel-backed body as opaque.

When splice I/O is active, Payload callbacks may receive these wrappers. The event loop and adapters that
support splice interpret the descriptor and manage pipe I/O; the initial
adapters are `TcpListener` and `TcpConnector`. Forwarding tunnels that already
pass buffers synchronously and opaquely and use size-based accounting can
usually keep their Payload code unchanged. They need no special
flag branch just to pass the wrapper onward. Code that handles the splice
representation directly must understand the flag.

Each `wio_t` records its selected I/O mode in the one-bit `splice_enabled`
field. `wioEnableSplice(io)` initializes the descriptor's nonblocking,
close-on-exec pipe before setting this field. It returns `0` on success or
`-1` with `errno` set on failure, leaving the mode unchanged on failure.
An existing pipe is reused. `wioDisableSplice(io)` clears the flag without
closing the pipe; `wioIsSpliceEnabled(io)` reads it. Use these helpers on the WIO owner thread.
The flag starts disabled whenever WIO adopts a new descriptor, including
reuse of a cached or pooled WIO. `wioEnableSplice()` asserts that the WIO is
open and has never registered read interest. A sticky `read_started` bit
records successful `WW_READ` registration through `wioAdd()` (including
`wioRead()`); stopping reads does not clear it. The bit resets only when WIO
adopts a new descriptor. This checks WIO read activation, not peer arrival
of bytes in the kernel socket queue or raw OS reads outside WIO.

`TcpListener` enables the flag on an accepted socket when its finalized chain
has `supports_splice` set, before forwarding `Init` or starting reads.
`TcpConnector` applies the same chain check to its destination WIO immediately
after successful socket adoption, before connecting or starting reads. Both
adapters close the affected connection if pipe initialization fails.
Read/send dispatch does not consult the flag yet.

**Splice buffers must not be deferred.** A buffer carrying
`kSbufFlagSplice` may be forwarded synchronously through the current callback
chain, but must not be retained in a queue or saved for later processing. This
includes `PipeTunnel` handoffs to another worker, posting to the main thread,
timers, and deferred callbacks on the same thread.

Before deferring work, use the dedicated splice helpers to consume all bytes
represented by the wrapper through `read()` or `splice()`. Tunnel code must
use the helpers rather than issue raw reads or splices that bypass their
accounting, and must not queue the unconsumed wrapper. A partial transfer
leaves the same restriction on the unconsumed splice payload.

Ordinary payload processing leaves the kernel-backed body and its descriptor pointer
uninspected and unmodified. The normal left
padding path remains available: a tunnel may call `sbufShiftLeft()` and write
its own prefix within physically reserved headroom and its advertised padding
budget. The pointer stays at `buf + l_pad` as `curpos` moves left. Those real
prefix bytes precede the kernel-backed body in the logical payload. The permission
to prepend does not permit overwriting the pointer or accessing body bytes
through `buf`.

#### Consuming the socket body into the pipe

`wioMoveSpliceBuferToPipe(buf)`, declared in `ww/event/wloop.h`, reads the stored
pointer from `buf + l_pad` and moves socket bytes from `handle->fd` into
`handle->pipefd[1]`. The pipe must already be initialized, normally by
`wioEnableSplice()`. This helper never creates it: an uninitialized pipe causes
`LOGF()` followed by `abortProgramNow(1)` in every build. The source socket
must be nonblocking. Callers must serialize access to the descriptor and hold a
reservation covering the requested socket bytes.

The helper checks at runtime, including in release builds, that
`kSbufFlagSplice` and `kSbufFlagSpliceFD` are set and `kSbufFlagSplicePiped`
is clear. A violation calls `LOGF()` and `abortProgramNow(1)`.
The splice representation contract requires a
splice allocation. Logical `capacity` cannot independently prove the physical
allocation size. `curpos` must be at or left of `l_pad`; any prepended bytes
are excluded from the splice request:

```c
prefix_bytes = buf->l_pad - buf->curpos;
socket_bytes = buf->len - prefix_bytes;
```

It makes a nonblocking splice attempt, retrying `EINTR`, and returns the actual
number of bytes moved. Only a positive result reduces `handle->reserved`, by
that exact amount. A zero-length body returns zero without a splice syscall.
Unsupported builds return `-1` with `errno` set to `ENOSYS`.

On full completion, the helper clears `kSbufFlagSpliceFD` and sets
`kSbufFlagSplicePiped`, preserving the other flags. An empty body also completes.
Short transfers, EOF before completion, and splice errors leave the flags
unchanged and currently call `LOGF()` followed by `abortProgramNow(1)`.
The diagnostic includes the requested count, syscall result, and error number.
This is temporary handling: short splices remain valid syscall outcomes.
Reservation accounting always uses the actual transferred count, including
before this abort. Length, capacity, cursor, prefix bytes, and references
remain unchanged.

#### Converting a splice payload into ordinary storage

`wioTransformSpliceBufferToRealBuffer(buf, dest, pool)`, declared in
`ww/event/wloop.h`, consumes the splice wrapper and returns `dest`, an ordinary
buffer supplied by the caller. Pass the owning worker's `buffer_pool_t`; its
splice tier receives the consumed wrapper through `bufferpoolReuseBuffer()`.
The call must run on that pool's owning thread. After success, the caller owns
only `dest` and must not access or recycle `buf` again.

The source must have `kSbufFlagSplice` and exactly one of `kSbufFlagSpliceFD`
or `kSbufFlagSplicePiped`. The helper reads the pointer at `buf + l_pad`, copies
the real prefix (`l_pad - curpos` bytes), and reads the remaining body from
`handle->fd` or `handle->pipefd[0]`, according to the location flag. A selected
pipe must already be initialized. Callers must serialize descriptor access and
hold a reservation covering an FD-backed body. Source-FD reads reduce
`handle->reserved` by the actual count read; pipe reads do not reduce it again.

The destination's previous contents are replaced. Its cursor becomes the source
cursor, preserving the remaining left headroom, and its length becomes the
source's complete length, including the prepended bytes. Its allocation
`capacity` and original `l_pad` remain unchanged. Before copying or reading,
the helper requires enough physical storage for that cursor and the full
payload. It clears all splice flags on the result. The source must have no
lifetime metadata, as checked by a debug assertion. The helper neither transfers
nor releases lifetime metadata; the destination's metadata stays unchanged and
remains the caller's responsibility.

Invalid flags, a splice destination, insufficient destination storage, an
uninitialized selected pipe, short reads, and every read error (including
`EINTR`) call `LOGF()` followed by `abortProgramNow(1)` in every build.
A positive short source-FD read updates `reserved` before aborting. The helper
makes one read attempt for a nonempty body; an empty body requires no syscall.
Unsupported builds also log with `LOGF()` and abort.

Accessors such as `sbufGetMutablePtr()` deliberately add no splice-specific
checks or runtime assertions. Their callers uphold the representation
contract. Corrupting the descriptor pointer can break I/O or crash the process, but
there is no guarantee of an immediate crash that would reliably detect misuse.

This section defines the representation contract. Splice-buffer pooling provides
the wrapper allocations; event-loop emission and splice-specific BufferStream
handling are not implemented yet. Current BufferStream copying, splitting, and coalescing
operate on ordinary buffers with resident payload bytes.

## Prepending a Header: `sbufShiftLeft`

The whole reason `l_pad` exists is so a tunnel can prepend a protocol header
**without reallocating or memmoving** the payload. You move the cursor left and
write into the freed space:

```c
// Reserve room and move the cursor back by header_len bytes.
assert(sbufGetLeftCapacity(buf) >= header_len);
sbufShiftLeft(buf, header_len);     // curpos -= header_len; len += header_len

// Now write the header at the new front.
sbufWriteUI16(buf, htons(payload_len));
// ... fill the rest of the header ...
```

`sbufShiftLeft` asserts that enough left capacity exists:

```c
static inline void sbufShiftLeft(sbuf_t *const b, const uint32_t bytes)
{
    assert(sbufGetLeftCapacity(b) >= bytes);
    b->curpos -= bytes;
    b->len    += bytes;
}
```

If the assertion fires (or, in a release build, if you shift left past the start),
you have prepended more than your padding budget allows — which is the next
section.

## The Padding Contract: `required_padding_left`

A tunnel may only rely on left padding it **advertised** in its `node.c`:

```c
.required_padding_left = kMyProtocolHeaderSize,
```

During chain finalization, the runtime sums `required_padding_left` across every
node in the chain and reserves that much left padding in the buffers it hands out
(`tunnelchainInsert` accumulates `sum_padding_left`; `tunnelchainFinalize` calls
`globalstateUpdateAllocationPadding`). In other words:

> The left capacity available to your tunnel at runtime is the sum of the padding
> budgets of **your tunnel and every tunnel closer to the adapter that produced
> the buffer**. If you prepend bytes you never advertised, you are spending
> someone else's budget, and the buffer may not have it in a different chain.

This is why a framing tunnel that "works on my machine" can corrupt memory once a
user puts a different node in front of it. Advertise what you prepend.

Rules:

- Use `sbufShiftLeft()` only when `sbufGetLeftCapacity()` is at least the header
  size you need.
- Keep every prepend within this tunnel's advertised `required_padding_left`.
- If you must prepend more than your budget, either raise
  `required_padding_left` to match, or build a fresh buffer (see below) instead of
  shifting.

## Buffer Pools

For ordinary runtime buffers, do not `malloc`. Use the worker-local buffer pool so
allocations are recycled and correctly padded. The pool is reachable from any
line:

```c
buffer_pool_t *pool = lineGetBufferPool(line);     // this line's worker pool

sbuf_t *big   = bufferpoolGetLargeBuffer(pool);    // large working buffer
sbuf_t *small = bufferpoolGetSmallBuffer(pool);    // small working buffer
sbuf_t *splice_buf = bufferpoolGetSpliceBuffer(pool); // 32 control-storage bytes plus splice padding

// ... use the buffer ...

bufferpoolReuseBuffer(pool, buf);                  // return it to the pool
lineReuseBuffer(line, buf);                        // convenience: pool of line's worker
```

Pools are **per worker**. A line belongs to exactly one worker (`lineGetWID`), so
always use that line's pool — never a different worker's. Buffers from a pool
already carry the chain's reserved left padding, so a pooled buffer is the correct
place to build a payload you intend to prepend onto.

Each buffer pool has large, small, and splice caches backed by separate shared
master pools. `bufferpoolCreate()` takes all three master pools; physical splice
control storage is fixed at `SPLICE_BUFFER_STORAGE_SIZE` (32 bytes), excluding
left padding. Splice allocation is explicit:
`bufferpoolGetBestFit()` continues to select only the large/small tiers.

Each tier refills at most four buffers at a time, further bounded by half the
local cache capacity and its available slots. Pools whose previous refill batch
was smaller than four retain that smaller batch. Cache capacities and shrink
thresholds are independent of this refill limit.

`bufferpoolGetSpliceBufferStorageSize()` and `bufferpoolGetSpliceBufferPadding()` expose
the splice geometry. `bufferpoolUpdateAllocationPaddings()` accepts separate
large, small, and splice padding arguments. Global chain-padding updates cover
all three tiers, and device pools inherit all three padding values from their
worker pool. Set padding before populating the local caches.

The existing `lineGetBufferPool()`, `getWorkerBufferPool()`, and
`getCurrentEventWorkerBufferPool()` accessors all expose the splice tier through
`bufferpoolGetSpliceBuffer()`. `lineReuseBuffer()` and `reuseBuffer()` use the same
recycling path as `bufferpoolReuseBuffer()`, subject to their existing worker
ownership requirements. Recycling clears flags and length; for a splice wrapper,
it first restores physical capacity from the 32-byte control storage and its
reserved padding. Checkout restores `kSbufFlagSplice` with both location flags
clear. Pooling manages buffer storage, not pipe I/O.

If you need a buffer bigger than the current one for an append, use
`sbufReserveSpace()` (it reallocates and copies only when necessary) rather than
hand-rolling growth.

`sbufCreateSplice(pad_left)` directly allocates an empty buffer with exactly
32 bytes of payload capacity, plus left padding rounded up to a 32-byte
boundary. Its payload capacity stays at 32 bytes regardless of the CPU cache
line size. The buffer starts with zero length, only `kSbufFlagSplice` set, and no lifetime
metadata; `sbufDestroy()` releases the allocation.

### Sizing Destination Buffers for Untrusted or Variable Payloads

When sizing a destination buffer from an untrusted or variable payload length:

- Use `bufferpoolGetBestFit()` (or another checked growth operation) rather than
  assuming a fixed buffer tier fits the input. Supply the left padding required
  by the onward buffer contract as well as the payload capacity: when neither
  pool tier fits, best-fit creates a dedicated buffer with exactly the requested
  padding. Request zero only for a locally consumed buffer or a proven
  zero-padding destination.
- Compare the requested length with actual writable capacity
  (`sbufGetMaximumWriteableSize()`) in ordinary Release control flow before any
  assert-only length mutator (such as `sbufSetLength()`) or write.
- Publish the `sbuf_t` length only after the producer has successfully written or
  validated that many bytes.

## Buffer Ownership

Buffer lifetime bugs are as common as line lifetime bugs. The rules:

- **A callback takes ownership of the buffer you pass it.** After
  `tunnelNextUpStreamPayload(t, line, buf)` (or the downstream form), `buf` is no
  longer yours. Do not read it, reuse it, or free it.
- **If you keep a buffer, you own it.** You are responsible for eventually
  recycling it with `bufferpoolReuseBuffer` / `lineReuseBuffer`, or handing it to
  a callback.
- **On an error path that still owns a buffer**, return it to the pool (or the
  line) before you close. Do not leak it, and do not touch it after the line dies.
- **If a re-entrant callback killed the line** (a `false` from
  `lineCallWithRef()` / `lineCallWithRefWithBuf()`), only recycle buffers you still hold; do not touch the dead
  line's state to do it.

### BufferStream chunk and exact-read contracts

Use `buffer_queue_t` when individual buffer entries or chunk boundaries matter.
Use `buffer_stream_t` for an ordered byte sequence, such as protocol parsing,
byte inspection, or exact-length extraction. Internal stream boundaries are not
message boundaries and need not match input chunks.

`bufferstreamPush()` takes ownership on every path and may copy an input into
the current tail and recycle the input before returning. Callers must not access
the transferred buffer or pointers into it, depend on its allocation identity,
or require one retained chunk per push. Payload contents and FIFO byte order
are preserved; coalescing is permitted, not guaranteed.

`bufferstreamReadExact()` returns exactly the requested positive number of
available bytes, combining or splitting storage as needed. `ReadAtLeast()` may
return more according to internal chunking. `IdealRead()` transfers an internal
storage chunk efficiently, with no correspondence promised to pushes or wire
records; it requires positive buffered length but can return a retained empty
entry. `FullRead()` returns the complete buffered byte sequence, or `NULL` for
zero logical bytes. Byte views and delimiter searches observe the same ordered
bytes regardless of internal partitioning. Consumers needing a protocol boundary
must parse it and request the appropriate length.

The current push policy copies only a complete, positive input of at most 4 KiB
that fits into the current tail's unused writable space. The resulting chunk
can exceed 4 KiB. It never grows the tail, searches older entries, partially
copies an input, or consumes left padding. Buffers with lifetime metadata are
excluded from push coalescing. These are push-policy
constraints, not guarantees that subsequent stream reads preserve identity or
metadata.

Logical emptiness and buffered length measure bytes, not retained entries.
Zero-length input is enqueued, and an eligible empty tail can absorb later bytes;
it is not a message marker. Retained empty entries still require cleanup.
Coalescing can reduce retained allocations and queue entries but does not replace
protocol byte limits, retained-allocation limits where applicable, or
backpressure. Pool recycling does not guarantee an immediate RSS reduction.

Buffer queues preserve entries, but Debug insertion may replace the allocation
to expose stale aliases. Observe the queue API's returned retained pointer and
ownership/failure contract; do not assume the original input address survives.

For a split `bufferstreamReadExact()`, `use_left_padding` is the exact prefix
budget `U` that the stream may temporarily consume and count toward writable
capacity. A small pooled buffer is eligible only when it provides both the
remaining payload capacity, `max(requested_bytes - U, 0)`, and all `U` configured
padding bytes. Allocator-alignment slack and chain padding owned by other tunnels
are never credited. If the large tier must grow for an oversized result, the
existing reserve fallback preserves that tier's complete chain-wide padding.

### MUX parent streams and decoded child queues

MuxClient and MuxServer accumulate encoded parent bytes in `buffer_stream_t`.
They must extract each complete frame with `muxReadCompleteFrame()`, which uses
the eight-byte header and declared payload length. Never replace that extraction
with arbitrary `IdealRead()`/`FullRead()` chunks. Parent coalescing changes storage
boundaries, not MUX wire-frame boundaries.

Decoded `Data` waiting for a paused child belongs in `pending_child_data`, a
`buffer_queue_t`. Preserve one entry and one onward payload callback per decoded
frame, including zero-length `Data`; drain based on entry count, not logical byte
count. An empty Data body still has a wire header and is not an empty carrier
input or a close signal. Keep the existing logical flow-control and actual
allocation-charge accounting separate.

MUX framing is not general UDP boundary preservation. Both encoders split child
payloads larger than 65,527 bytes, and decoding does not recover the original
callback boundary. Child-side transforms can also split or combine payloads.
Use the UdpOverTcp pair around a UDP flow's byte-stream portion rather than
depending on direct UDP/MUX adjacency; observe that pair's own payload limits.

### Payload length versus retained allocation charge

`sbufGetLength()` measures buffer contents. That is the correct unit for ordinary
queue byte counts, protocol thresholds, FIFO delivery statistics, and
backpressure decisions, and `buffer_queue_t.total_len` intentionally keeps those
logical payload semantics.

Do not treat that content length as a memory charge when a security or resource
limit specifically promises to bound allocations retained by a live queue. An
empty or one-byte `sbuf_t` can still retain its full capacity, left padding,
header, and allocator alignment overhead. Memory-sensitive code that needs such
a hard bound—currently the Mux child, parent, and detached queue limits—must keep
a separate actual-allocation charge. This stricter accounting is specialized;
it must not replace logical length in ordinary buffer queues or in Mux's
payload-based pause and resume thresholds.

### Buffers transferred to scheduled line tasks

Calling `lineScheduleTaskWithBuf()` or
`lineScheduleDelayedTaskWithBuf()` transfers the buffer on **every** result,
including synchronous `RejectedSettled`. The caller must never recycle, destroy,
or inspect it after the call. If the task executes, the task callback receives
ownership. Otherwise the scheduler settles the buffer after optional
cancellation notification: it returns the buffer to the line's pool only while
cleanup runs in that owner event-worker context, including owner-bound teardown,
and destroys it on a foreign or unbound cleanup thread.

The cancellation callback does not receive or own the buffer. It runs before
internal buffer release, while the scheduler's physical line reference remains
held, and must not attempt to infer buffer lifetime from the cancellation
reason. A null cancellation callback suppresses only notification; line death,
submission refusal, quiescence, and teardown still release the buffer exactly
once. This makes memory safety independent of task progress.

In debug builds, `BUFFER_WONT_BE_REUSED(x)` swaps a buffer for a fresh duplicate
and destroys the original, so any stale pointer to the old buffer is caught
quickly. If you see it in reference tunnels, it marks "this buffer must not be
touched again after this point."

## A Complete Prepend Example

Putting it together — a framing tunnel that prefixes a 2-byte big-endian length on
the upstream path, having advertised `.required_padding_left = 2` in `node.c`:

```c
void myTunnelUpStreamPayload(tunnel_t *t, line_t *l, sbuf_t *buf)
{
    const uint16_t payload_len = (uint16_t) sbufGetLength(buf);

    // We advertised 2 bytes of left padding, so this is guaranteed to fit.
    assert(sbufGetLeftCapacity(buf) >= sizeof(uint16_t));
    sbufShiftLeft(buf, sizeof(uint16_t));
    sbufWriteUI16(buf, payload_len);      // (use the project's endianness helper as needed)

    // Hand the buffer upstream; we no longer own it.
    tunnelNextUpStreamPayload(t, l, buf);
}
```

On the downstream side the paired tunnel reads and strips the header with
`sbufReadUI16` + `sbufShiftRight`, then forwards with
`tunnelPrevDownStreamPayload`.

## Common Buffer Mistakes

- Prepending without advertising padding, then relying on left capacity that only
  exists in one chain layout.
- Misusing `sbufShiftLeft` when left capacity is insufficient (the assert is your
  friend in debug; release builds corrupt memory).
- Reusing or reading a buffer after passing it to a forwarding callback.
- Leaking a buffer on an error/close path.
- Using a different worker's pool than the line's own.
- Treating `sbufGetMaximumWriteableSize` as "spare room beyond the payload" — it
  is room from the cursor, so subtract the current length first.
