# WaterWall Developer Guide

This guide is for people and coding agents who implement, fix, or review
tunnels under `tunnels/`. WaterWall is a chain-based tunneling runtime, so a
correct tunnel is not just a parser or encoder. It must preserve callback
direction, line lifetime, per-line state, buffer padding, packet-line behavior,
and composability with whatever nodes appear before or after it.

Do not design a new lifecycle model for one tunnel. Start from the runtime
contracts in `ww/net/`, then copy the shape of mature tunnels that already solve
similar problems.

## Read These Files First

Before changing tunnel behavior, read the source that owns the contract:

| Area | Files |
| --- | --- |
| Tunnel callbacks and chaining | `ww/net/tunnel.h`, `ww/net/tunnel.c` |
| Line lifetime and per-line state | `ww/net/line.h`, `ww/net/line.c` |
| Chain finalization and packet lines | `ww/net/chain.h`, `ww/net/chain.c` |
| Packet-tunnel defaults | `ww/net/packet_tunnel.h`, `ww/net/packet_tunnel.c` |
| Shift buffers and padding | `ww/bufio/shiftbuffer.h`, `ww/bufio/shiftbuffer.c` |
| Buffer pools | `ww/bufio/buffer_pool.h`, `ww/bufio/buffer_pool.c` |
| Node metadata | `ww/objects/node.h` |

Good reference tunnels:

- `TcpListener` and `TcpConnector` for adapter behavior.
- `TlsClient` and `EncryptionClient` for stateful protocol wrapping.
- `MuxClient` for internal line ownership and re-entrant safety.
- `PacketsToStream`, `StreamToPackets`, and `PacketsToConnection` for packet to
  stream boundaries.
- `PingClient` and `PingServer` for packet-tunnel direction decisions.

## Runtime Model

WaterWall chains tunnel instances together. A typical stream chain looks like:

```text
TcpListener -> ObfuscatorClient -> TlsClient -> TcpConnector
```

The first and last nodes are usually adapters. They touch sockets, TUN devices,
or other operating-system resources. Middle tunnels must stay composable: they
transform callbacks and payloads without assuming which adapter is on either
side.

The important runtime objects are:

| Object | Meaning |
| --- | --- |
| `node_t` | Parsed configuration plus metadata such as `type`, `next`, flags, layer group, and `required_padding_left`. |
| `tunnel_t` | Runtime instance of a node. It stores callback function pointers, `next` and `prev`, tunnel state, line-state size, and chain offsets. |
| `line_t` | One normal connection line, logical line, or worker packet line. It stores routing context, user markers, buffer pools, refcount, alive flag, and all tunnels' per-line state. |
| `tunnel_chain_t` | Ordered set of tunnels. During finalization it computes total line-state size, total left padding, and worker packet lines. |

Each tunnel can have:

- tunnel state: one `tstate` for the tunnel instance
- line state: one `lstate` slot per `line_t`

Access them with the existing helpers:

```c
my_tstate_t *ts = tunnelGetState(t);
my_lstate_t *ls = lineGetState(line, t);
```

## Callback Directions

Direction ownership is the first rule to get right.

| Flow | Meaning | Forward with |
| --- | --- | --- |
| Upstream | request, outbound, forward path | `tunnelNextUpStream*` |
| Downstream | response, inbound, backward path | `tunnelPrevDownStream*` |

For payloads:

```c
tunnelNextUpStreamPayload(t, line, buf);
tunnelPrevDownStreamPayload(t, line, buf);
```

For lifecycle:

```c
tunnelNextUpStreamInit(t, line);
tunnelNextUpStreamFinish(t, line);

tunnelPrevDownStreamEst(t, line);
tunnelPrevDownStreamFinish(t, line);
```

Do not reverse these because a server-side tunnel "feels opposite." Draw the
actual chain and decide which callback direction owns the transformation.

## Line Startup

A normal connection starts with `Init`.

1. An adapter creates a `line_t`.
2. The adapter calls `tunnelNextUpStreamInit()`.
3. Each tunnel initializes its own line state.
4. The final adapter starts the real network operation.

`Init` is not isolated. A downstream tunnel can synchronously call back into
`Payload`, `Est`, `Pause`, `Resume`, or `Finish` before `Init` returns.

Rules:

- Initialize this tunnel's line state in `Init`.
- Later callbacks should assume that state exists.
- Do not add an `initialized` flag to hide unsafe control flow.
- If you call a re-entrant callback and then still need the line, protect it.

## Line Lifetime

`line_t` has a refcount and an `alive` flag. `lineLock()` prevents immediate
freeing, but it does not mean the line is still logically alive after a callback.
Check `lineIsAlive()` when you need to continue after a re-entrant call.

Only the tunnel that created a line may destroy it with `lineDestroy()`.

Common creators:

- adapters such as `TcpListener`, `UdpListener`, and `TcpConnector`
- selected middle tunnels such as `MuxServer`, `ReverseClient`,
  `PacketsToStream`, and `PacketsToConnection`

Everyone else must propagate `Finish` and let the owner destroy the line.

`lineDestroy()` eventually asserts that tunnel line states are already zeroed
unless something still holds a positive reference. That is why local state must
usually be destroyed before propagating a real line-closing finish.

## Re-entrant Callback Safety

Treat inter-tunnel callbacks as dangerous. These calls can indirectly close the
line before control returns:

- `tunnelNextUpStreamInit`
- `tunnelNextUpStreamPayload`
- `tunnelPrevDownStreamPayload`
- `tunnelNextUpStreamPause`
- `tunnelPrevDownStreamPause`
- `tunnelNextUpStreamResume`
- `tunnelPrevDownStreamResume`
- `tunnelNextUpStreamEst`
- `tunnelPrevDownStreamEst`

Prefer `withLineLocked()` or `withLineLockedWithBuf()` when you need to continue
after a callback:

```c
if (! withLineLocked(line, tunnelNextUpStreamInit, t))
{
    return;
}

/* The line is still alive here. Re-read state if needed. */
my_lstate_t *ls = lineGetState(line, t);
```

For payload forwarding:

```c
if (! withLineLockedWithBuf(line, tunnelNextUpStreamPayload, t, buf))
{
    return;
}
```

If a helper returns `false`, do not touch `line`, do not touch this tunnel's
line state, and do not call the line-state destroy function just to "clean up."
The close path that killed the line is responsible for that cleanup. Only reuse
buffers that you still own.

Use manual locking when the sequence needs explicit control:

```c
lineLock(line);

/* call one or more potentially re-entrant callbacks */

if (! lineIsAlive(line))
{
    lineUnlock(line);
    return;
}

lineUnlock(line);
```

## Finish Semantics

`Finish` is directional. Once a tunnel has received or sent finish for a
direction, it must not send callbacks back toward that finished side for the same
line.

If a tunnel receives upstream finish, it must not reflect downstream callbacks
back to the sender for that line. If a tunnel receives downstream finish, it must
not reflect upstream callbacks back to the sender.

A middle tunnel that decides to close the whole connection should usually:

1. Destroy this tunnel's local line state.
2. Send upstream finish first.
3. Send downstream finish second.
4. Return immediately.

Do not read fields from `ls` after `myLinestateDestroy(ls)`.

### Final Protocol Bytes

Some protocols must send final bytes before closing, such as TLS `close_notify`,
HTTP final chunks, HTTP/2 `END_STREAM`, WebSocket close frames, or custom
trailers.

The safe shape is:

1. `lineLock(line)`.
2. Mark the sender side as finished using existing directional state, such as
   `prev_finished`, `next_finished`, `can_downstream`, or `can_upstream`.
3. Send final protocol bytes toward the other side.
4. Destroy this tunnel's local line state.
5. Propagate the real WaterWall `Finish`.
6. `lineUnlock(line)`.
7. Return immediately.

The directional mark matters because sending final bytes can trigger
backpressure. For example, an adapter can emit `Pause` while writing the final
frame. That `Pause` must not be forwarded back toward the side that already sent
`Finish`.

## Buffer and Padding Contract

WaterWall uses `sbuf_t` buffers. A buffer has:

- `curpos`: current payload start
- `len`: current payload length
- `capacity`: total allocation
- `l_pad`: reserved left padding

Tunnels can prepend headers efficiently with:

```c
assert(sbufGetLeftCapacity(buf) >= header_len);
sbufShiftLeft(buf, header_len);
```

But a tunnel may only rely on padding it advertised in `node.c`:

```c
.required_padding_left = kMyProtocolHeaderSize,
```

During chain finalization, WaterWall sums `required_padding_left` across the
chain and updates global buffer allocation padding. If you prepend bytes without
advertising enough padding, the tunnel may only work in some chain layouts and
break in others.

Rules:

- Use `sbufShiftLeft()` only when enough left capacity is available.
- Keep prepended bytes within this tunnel's advertised padding budget.
- Use buffer pools (`bufferpoolGetSmallBuffer`, `bufferpoolGetLargeBuffer`,
  `lineGetBufferPool`, `lineReuseBuffer`) for ordinary runtime buffers.
- If a callback takes ownership of a buffer, do not reuse it afterward.
- If an error path still owns a buffer, return it to the line or pool before
  closing.

## Packet Lines

Packet lines are real `line_t` objects, but they are not normal connection
lines.

When a chain contains a layer-3 packet node, `tunnelchainFinalize()` allocates
one packet line per worker. These packet lines are persistent worker helper
lines. They are destroyed when the chain is destroyed, not during normal packet
processing.

Do not call `lineDestroy()` on a packet line during normal runtime.

Packet-line state is worker-local shared state. It is reused for unrelated
packets on the same worker. Treat these fields as scratch packet-pipeline
metadata:

- `routing_context.src_ctx`
- `routing_context.dest_ctx`
- `recalculate_checksum`
- any line state stored on the packet line

Do not treat packet-line state as a per-flow or per-peer identity. If a packet
tunnel needs per-connection behavior, create or manage normal lines behind the
packet side instead.

## Pure Packet Tunnels and Packet Bridges

Pure packet tunnels are created with:

```c
packettunnelCreate(node, sizeof(my_tstate_t), 0);
```

`packettunnelCreate()` asserts that `lstate_size == 0`. These tunnels generally
override packet payload callbacks and do not use connection-style line state.
Examples include `IpOverrider`, `IpManipulator`, `PingClient`, `PingServer`, and
`WireGuardDevice`.

Packet-line anchored bridges are normal tunnels that use the worker packet line
as an anchor for bridge state. Examples:

- `PacketsToStream`
- `StreamToPackets`
- `PacketsToConnection`
- `PacketSplitStream`

For these tunnels, remember that packet-line `Init` is a worker/bootstrap event,
not a per-packet open event. If a chain head is a layer-3 packet node, startup
initialization sends one upstream `Init` per worker packet line. Some bridge
topologies must trigger packet-line initialization manually in `onStart()`.

## Packet Tunnel Direction Example

Paired packet tunnels often transform in opposite callback directions. Do not
copy the client's direction into the server unless the chain flow proves it.

Example:

```text
PingClient:
packet -> PingClient -> IPv4(ICMP(payload -> packet))

PingServer:
packet <- PingServer <- IPv4(ICMP(payload -> packet))
```

`PingClient` encapsulates on upstream payload and forwards with
`tunnelNextUpStreamPayload()`. `PingServer` decapsulates on downstream payload
and forwards with `tunnelPrevDownStreamPayload()`.

Tests for packet tunnels should exercise the real intended direction. If the
server side needs data from the opposite side, use `Bridge` or another existing
composition tunnel instead of changing the tunnel contract.

## Typical Tunnel Layout

Most tunnels follow this shape:

```text
tunnels/MyTunnel/
  CMakeLists.txt
  description.md
  include/MyTunnel/
    interface.h
    structure.h
  instance/
    create.c
    node.c
    chain.c
    index.c
    prepair.c
    start.c
    stop.c
    destroy.c
  common/
    helpers.c
    line_state.c
  upstream/
    init.c
    payload.c
    fin.c
    pause.c
    resume.c
    est.c
  downstream/
    init.c
    payload.c
    fin.c
    pause.c
    resume.c
    est.c
```

`node.c` declares node metadata, including layer group and padding. `create.c`
creates the tunnel and assigns callbacks. `line_state.c` initializes and destroys
per-line state. Callback files should stay small and delegate shared protocol
work to `common/helpers.c` when that makes the state machine clearer.

When you destroy line state, zero the correctly aligned line-state region, as
existing tunnels do:

```c
memoryZeroAligned32(ls, tunnelGetCorrectAlignedLineStateSize(sizeof(my_lstate_t)));
```

## Implementation Workflow

Use this workflow for new features and fixes:

1. Draw the chain flow and mark upstream and downstream directions.
2. Identify which side owns line creation and destruction.
3. Read the existing tunnel implementation and adjacent tunnels.
4. Read `ww/net/line.h`, `ww/net/tunnel.h`, and `ww/net/chain.c`.
5. If framing or prepending is involved, read shift-buffer and buffer-pool code.
6. Choose the closest mature tunnel pattern and stay close to it.
7. Implement the smallest change that preserves composition.
8. Add or update a focused test case when behavior can regress.
9. Validate with the preset build and relevant tests.

Avoid speculative abstractions. In this codebase, correctness usually comes from
matching the existing lifecycle pattern, not from inventing a more generic one.

## Build and Validation

Prefer the `linux` CMake preset:

```bash
cmake --preset linux
cmake --build --preset linux -j8
```

For a focused tunnel build:

```bash
cmake --build --preset linux --target TlsClient -j8
```

For registered tests:

```bash
ctest --preset linux --output-on-failure
ctest --preset linux --output-on-failure -R '^waterwall\.tls_roundtrip$'
```

For one integration case while debugging:

```bash
tests/run_waterwall_case.sh \
  build/linux/Release/Waterwall \
  tests/cases/tls_roundtrip \
  60
```

Do not hand-assemble compile commands. If you need a syntax-only compile, use
the exact command from `build/linux/compile_commands.json`. Be especially
careful with tunnel-local headers named `structure.h`; adding multiple tunnel
include directories to one manual command can silently include the wrong file.

If GCC reports an internal compiler error or bus error in unrelated core files
such as `ww/libc/wlibc.c`, treat it as a build-environment or build-tree problem
first. Reconfigure with the `linux` preset before debugging the tunnel code.

## Review Checklist

Before merging a tunnel change, check:

- Does `Init` initialize this tunnel's line state before any callback can use it?
- Are upstream callbacks forwarded only with `tunnelNextUpStream*`?
- Are downstream callbacks forwarded only with `tunnelPrevDownStream*`?
- Does every re-entrant callback either return immediately or protect the line?
- Does `Finish` destroy local state before propagating a real close?
- If final protocol bytes are sent during `Finish`, is the sender side marked
  finished before the send?
- Are `Pause` and `Resume` blocked from reflecting toward a finished side?
- Does only the line owner call `lineDestroy()`?
- Are packet lines kept alive during normal runtime?
- Is packet-line state treated as worker-local shared state?
- Does every prepend fit inside `required_padding_left`?
- Are buffers recycled exactly on paths that still own them?
- Are tests exercising the intended callback direction?
- Did validation use preset build metadata instead of guessed compiler flags?

## Agent Output Expectations

When using an AI coding agent on WaterWall, ask it to report:

1. Its understanding of the relevant tunnel flow.
2. The bug or requested change.
3. How the fix preserves lifecycle ordering, line safety, direction ownership,
   buffer and padding rules, and packet-line semantics.
4. The implementation summary.
5. The validation commands and results.
6. Remaining risks or edge cases.

That report format forces the important contracts into the open. If a proposed
change cannot explain those contracts, it is not ready.
