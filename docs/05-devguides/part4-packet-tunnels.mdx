# Part 4: Packet Lines & Packet Tunnels

WaterWall handles layer-3 packet flows (TUN devices, WireGuard-style paths, raw
packet processing) as well as ordinary streams. The packet model reuses the
`line_t` type but applies a **completely different lifecycle**. Treating a packet
line like a per-connection line is one of the most damaging mistakes you can make
in this codebase.

Read this part before touching anything under a layer-3 node. Source of truth:
`ww/net/chain.c`, `ww/net/packet_tunnel.c`, `ww/net/line.h`, and the packet
tunnels themselves.

## What a Packet Line Is

A packet line is a real `line_t`, but unlike a connection line it is:

- allocated **once per worker** for any chain that contains a layer-3 node,
- **shared** by every packet that worker processes,
- **not** tied to a TCP/UDP connection lifecycle,
- **not** closed during normal runtime,
- destroyed only when the **chain itself** is destroyed.

"Worker-owned" here means persistent, worker-local packet-pipeline state. It
does not make a node on the left or right its connection owner. Normal lines
created inside a packet chain, including WireGuardDevice's companion transport
lines and UdpStatelessSocket's incoming peer lines, still belong to their exact
creators and close normally. Classify the actual `line_t`, not just its worker
ID or whether the chain contains packet nodes.

The source is explicit. In `tunnelchainFinalize()` (`ww/net/chain.c`), when the
chain contains a packet node, one packet line is created per worker (abridged here
without the surrounding pool cleanup):

```c
line_t **packet_lines = memoryAllocate(sizeof(*packet_lines) * tc->workers_count);
if (! packet_lines)
{
    startupFailureRecord(1);
    return;
}

// ... create and validate every worker's line pool ...
tc->packet_lines = packet_lines;

for (wid_t i = 0; i < tc->workers_count; i++)
{
    if (tc->contains_packet_node)
    {
        packet_lines[i] = lineCreateForWorker(0, tc->line_pools, i);
    }
}
```

And they are torn down only in `tunnelchainDestroy()`:

```c
for (uint32_t i = 0; i < tc->workers_count; i++)
{
    if (tc->packet_lines && tc->packet_lines[i])
    {
        lineDestroy(tc->packet_lines[i]);
    }
}
```

Reach a worker's packet line with `tunnelchainGetWorkerPacketLine(chain, wid)`.

:::danger Never destroy a packet line at runtime
Do not call `lineDestroy()` on a packet line during normal operation, and never
design logic that expects packet lines to be recreated on `Finish`. Packet
adapters such as `TunDevice` assert in debug builds that the packet line is still
alive after forwarding a packet. If your change can let a
packet line die at runtime, that is almost certainly a bug.
:::

## Runtime `Finish` on a Packet Line

[Part 2](part2-lines-and-callbacks.mdx) requires an owner's `Finish` handler for a
**normal** line to return with `! lineIsAlive(line)`. **Packet lines are excluded
from that postcondition, without exception.** A packet line is owned by the chain,
not by any tunnel, and `tunnelchainDestroy()` is the only place that may ever
destroy it. That part is absolute: whatever else your handler does, it must never
call `lineDestroy()` on a packet line.

What a `Finish` on a packet line *means*, though, depends entirely on the hop that
receives it, the direction it arrived from, and the role that handler plays.
There are three categories. Chain position is useful context, but it is not
enough by itself to select one.

### Category 1 — packet-lifecycle anchor: reject impossible close

A packet adapter or bridge may anchor the worker's packet-pipeline state on the
packet line and have no notion of that role closing. Here “adapter” means a
packet-pipeline boundary or lifecycle endpoint, **not** a tunnel that owns the
`line_t`. Nothing in a correct chain finishes that exact role, so a `Finish`
arriving in that handler and direction means a neighbour broke the contract:

- **never** call `lineDestroy()`;
- **fail loudly** — `LOGF(...)` then `abortProgramNow(1)`, the project's
  packet-line contract-violation policy;
- never convert it into normal connection teardown;
- leave the real destruction to `tunnelchainDestroy()`.

That is exactly what the anchoring adapters do:

```c
void tundeviceTunnelDownStreamFinish(tunnel_t *t, line_t *l)
{
    discard t;
    LOGF("TunDevice: unexpected downstream Finish on worker packet line %u", (unsigned int) lineGetWID(l));
    abortProgramNow(1);
}
```

Examples include `TunDevice` and `RawSocket`; the upstream packet sides of
`PacketsToConnection` and `PacketsToStream`; the downstream packet side of
`StreamToPackets`; `PacketSplitStream`; the packet modes of `TesterClient` and
`TesterServer`; and the packet-line role of `WireGuardDevice`. These are
per-handler classifications, not labels for the whole tunnel: the same bridge
may own normal lines on its other side and close those normally.

`tests/unittests/packet_adapter_finish_test.c` proves the covered anchoring calls
do not return.

### Category 2 — transparent middle transform: forward lifecycle

A middle tunnel that transforms packet payloads does not thereby own or terminate
the line lifecycle. It must forward `Init`, `Est`, `Pause`, `Resume`, `Finish`,
and any other callback unrelated to its transform in the same direction:

- upstream callbacks continue with `tunnelNextUpStream*`;
- downstream callbacks continue with `tunnelPrevDownStream*`;
- a received callback is never reflected toward its sender.

Layer 3 has no per-connection TCP window, but that does not erase local scheduling
or queue pressure. Packet/stream bridges and active packet producers still follow
[Part 2's flow-control roles](./part2-lines-and-callbacks.mdx#flow-control-roles-and-admission).
Transparent packet transforms relay signals; a documented packet endpoint may
absorb them. Keep packet loss/admission policy explicit and never destroy the
persistent packet line to implement per-flow pressure handling.

`PingClient` and `PingServer` inherit these lifecycle pass-throughs from
`packettunnelCreate()`. Payload support
is a separate contract: both Ping v2 endpoints require the chain's exact worker
packet line for buffer ownership and worker validation. Their supported edge
orders are:

```text
TunDevice -> PingClient -> RawSocket
RawSocket -> PingServer -> TunDevice
```

An ordinary normal-line topology such as
`UdpListener <-> PingServer <-> UdpConnector` is therefore not a supported Ping
v2 composition. `packettunnelCreate()` keeps standard lifecycle pass-throughs,
but an implemented payload handler may still enforce a stricter packet-line role.

### Category 3 — intentional terminal absorber: handle locally and document

A packet line is still a `line_t`, and a chain may legally terminate one at a
packet-capable terminal adapter. That adapter borrows the packet line without
owning it and may close its own side for a documented reason.

One shipped example is an active `BlackHole` behind `PacketSender`:

```text
PacketSender ──(worker packet line)──> BlackHole(mode=active)
```

During upstream `Init`, an active `BlackHole` sends
`tunnelPrevDownStreamFinish()` **down the worker packet line**, and it lands on
`packetsenderTunnelDownStreamFinish()`. That is not a violation and must not
abort. `PacketSender` owns no per-line state and has no prev, so it absorbs the
close without propagating it or destroying the packet line. It must still stop
that worker's timer and send loop because receiving `Finish` permanently closes
the upstream destination.

An adapter that requires normal connection lines is not a packet-line terminal.
`UdpConnector` is layer-4-only: a packet path must use
`PacketSender -> PacketsToStream -> UdpConnector`, with `StreamToPackets` on the
receiving side when the payload returns to layer 3. The bridge owns the normal
line and handles its recreation without closing the persistent packet line.

This classification is directional. `PacketSender` downstream is an absorber,
while its upstream handler remains fatal because the chain head has no `prev`
that could legally send it a callback. `PacketReceiver` is another intentional
absorber: it owns no per-line state, may terminate either end of a chain, and
reports completion through its timer and report path rather than `Finish`.
Its required `protocol-number` selection controls per-source/protocol counters;
`expected-packets-per-ip` applies to each selected protocol, while all matched
arrivals remain counted even when they exceed that expectation. `ALL` selects
protocol numbers 0–254, matching `PacketSender`.

Propagate the close, release what you own, report a violation — or state in the
handler that you own no per-line state and have no onward direction, so absorbing
the close really is the whole job. A body that is nothing but `discard` statements
does not distinguish the last case from a bug.

The legitimate absorbers today are `BlackHole` (a chain-end sink that borrows
every line), `PacketReceiver` (a chain end that reports by timer and file) and
`PacketSender` downstream (Category 3 above).

`tests/line_ownership_policy_test.py` walks every
`tunnels/*/{upstream,downstream}/fin.c` and rejects a handler whose whole body is
`discard` statements unless it appears in `SILENT_FINISH_ALLOWED` with a written
rationale, so a lost propagation or a lost owner close cannot arrive looking like
a deliberate no-op.

So the question to ask is never only “is this a packet line?” or “is this tunnel
at a chain end?” It is **“what role does this exact handler and direction play,
what does the tunnel keep on this line, and who is still waiting on it?”**

### Dual-role handlers must check the exact role first

Some nodes see **both** a persistent packet line and normal lines they own. The
handler must decide which one it was given before doing anything:

- `WireGuardDevice` is a `packettunnelCreate()` tunnel on its packet side, but it
  also creates one **normal transport line per worker** for its encrypted side.
  A `Finish` on a transport line is an ordinary owned-line close (destroy the
  slot, `lineDestroy()`); a `Finish` on the packet line is a violation and aborts.
- `PacketsToStream` and `PacketsToConnection` anchor bridge state on the packet
  line while owning the normal lines they create behind it.

Use the chain to identify the role — never a name or a guess:

```c
if (tunnelchainIsWorkerPacketLine(tunnelGetChain(t), l))
{
    LOGF("MyNode: unexpected Finish on worker packet line %u", (unsigned int) lineGetWID(l));
    abortProgramNow(1);
}
/* from here on this is a normal line: apply the Part 2 owner postcondition */
```

Any intentional classification that differs by line role or direction must be
documented at the handler and covered by a regression test.

## Packet Lines Are Shared Worker State

Because one packet line serves many unrelated packets on a worker, anything stored
on it is **worker-local scratch state**, not per-connection identity. Be
especially careful with:

- `routing_context.src_ctx` and `routing_context.dest_ctx`
- `recalculate_checksum` (a per-packet scratch flag, see `lineSetRecalculateChecksum`)
- any tunnel line state stored on the packet line

These fields are overwritten packet-to-packet. Do **not** treat them as a stable
peer, flow, or session. If you store state on a packet line, that state must make
sense as one of:

- per-worker state,
- packet-pipeline scratch state,
- bridge state anchored to the worker packet side.

If you need real per-flow or per-connection lifecycle behind packet traffic,
**create normal lines behind the packet side** — do not try to make the packet
line behave like a connection.

## Device ingress fragment policy

On Linux, TunDevice requests IPv4 TCP GSO by default. Explicit `"gso": false`
keeps raw-IP TUN framing. Requested GSO uses a 10-byte little-endian virtio
header and `TUN_F_CSUM | TUN_F_TSO4`; negotiation failure is logged and startup
continues with raw-IP framing. The active framing choice applies to both reads
and writes for the lifetime of the device.

The Linux reader completes metadata-requested Internet checksums on ordinary
records and keeps their fragment handling in the reader. Ordinary `GSO_NONE`
records of either IP family remain accepted. For TCPv4 GSO, the reader builds
separate MTU-sized packets, copies IPv4 and TCP option bytes, uses the GSO
payload size, adjusts TCP sequence/FIN/PSH/CWR, and completes IPv4 lengths,
IDs and header checksums. It writes an adjusted TCP pseudoheader seed into each
segment's checksum field. A partial seed must retain the kernel's pseudoheader
contribution while changing its length; the IPv4 header's current destination
can be a source-route hop rather than TCP's final destination. Valid negotiated
TCPv4 GSO traffic is not filtered by a TCP-option allowlist.

The existing reserved flow-affinity worker batch carries a private completion
callback for GSO segments. The destination worker finishes the TCP checksum
before normal TunDevice delivery, logging, or packet publication. No virtio
metadata, checksum request flag, or new line state reaches the chain, and this
path adds no per-packet lock.

The kernel's requested `gso_max_segs` value of 2,048 is best effort: failure
is logged and GSO continues. It limits some producers, but is not an ingress
validity bound: forwarded/injected GSO can exceed it. The reader
uses one device-owned WaterWall buffer. It selects the pool's best-fit geometry,
then allocates that buffer through the nullable direct-buffer API before
publication, so allocation failure can fall back to raw-IP framing. It retains
one aggregate and expands it in bounded batches. GSO-generated output uses a
reservation budget of at most 512 packets and 8 MiB of actual buffer allocation
charge across reader-owned packets and pending worker deliveries;
exhaustion pauses expansion until a delivery or cancellation returns capacity.
Each credit remains charged through worker TCP completion and TunDevice delivery;
refusal or cancellation settles it without normal delivery.
There is no drop-only segment-count limit. Ordinary records continue through
the existing reader-session and fragment-affinity path. Segment output is
independent packet storage, and reassembly can later publish a complete
datagram larger than the TUN MTU without re-entering the GSO converter.

TunDevice and RawSocket accept an optional `fragment-policy`, either
`reassemble` or `preserve-fragments`. Omission selects `reassemble`; an explicit
invalid value, including `null`, rejects startup. The policy is immutable for
the reader session and is passed to all TUN and capture backends. Write-only
RawSocket instances have no ingress to assemble.

Fragment policy does not impose a node-name or topology allowlist. Normal chain
and layer validation remains in force. Reassembled ordinary packets may pass
through transforms, branches, packet/stream bridges, egress devices or sinks;
each component remains responsible for its input and output contracts.

| Boundary | Contract |
| --- | --- |
| Device ingress, `reassemble` | Publish complete IPv4 datagrams after bounded assembly; ordinary unfragmented input follows the existing path. |
| Device ingress, `preserve-fragments` | Preserve fragment bytes/boundaries and fragment-aware worker selection. |
| `PacketsToConnection`, upstream packet input | Must receive a complete IPv4 datagram before fake DNS, routing or lwIP input. |
| `ConnectionToPackets`, downstream packet input | Must receive a complete IPv4 datagram before flow lookup, worker injection or lwIP input. |
| Packet egress | Enforce existing packet-size and device-MTU limits; ingress reassembly does not provide output fragmentation. |

At either packet-to-stack input, MF or a nonzero fragment offset triggers a clear
`LOGF` diagnostic followed by `abortProgramNow(1)` in Debug and Release. DF alone
is allowed. Structural packet validation/drop behavior remains unchanged. This
is an input-contract violation, not proof that a specific topology is wrong:
a producer, peer or transform can supply the fragment. The failure is deliberately
process-wide, including unrelated connections.

Reassemble before these consumers, regardless of whether fragments originate
from a device or another node. `preserve-fragments` is not rejected at startup
merely because a stack is downstream: the actual delivered packet is checked.
A device policy affects only that device's reads. In particular, a direct
`ConnectionToPackets`/`PacketsToConnection` pair cannot exchange fragmented
output without an intervening reassembly boundary. Both nodes may still emit
IPv4 fragments on their packet output sides.

Reassembly accepts the existing 20-byte IPv4-header subset, exact total length,
valid header checksum, nonempty payload, aligned nonfinal fragments, and payload
ends at most 65,515. Ordinary unfragmented/non-IPv4 input bypasses assembly.
One session owns all incomplete bytes; no incomplete datagram is published.
Completion requires fragment zero, consistent final end and gap-free coverage.
Fragment zero supplies the header including TOS, TTL, reserved and DF bits; MF
and offset are cleared, total length and IPv4 checksum are rebuilt. Transport
bytes and checksums are unchanged. Downstream transport validation remains active.
Overlaps are dropped without overwriting accepted bytes; conflicting ends and
range exhaustion poison the identity. Raw overlapping zero with staged tails
also poisons, preserving the former local rejection rule.

Each session has at most 256 entries, 16 disjoint ranges per entry, and 8,192
accepted fragments per datagram (enough for a maximum IPv4 datagram composed of
minimum-size fragments). Normalized storage is bounded to 4 MiB of actual sbuf
allocation charge, including capacity, padding, header and explicit alignment
overhead. This accommodates dozens of full datagrams while bounding sparse-tail
attacks. Growth reserves old plus new allocations simultaneously and copies only
accepted ranges. Raw mode retains at most 16 pre-zero tails per entry and 256
in total, under a separate 32 MiB actual allocation-charge limit, allowing the full
16-tail staging window even with 1 MiB device receive buffers plus overhead. Fixed entry and
range arrays bound metadata separately. These limits exclude pool caches and RSS.

Entries expire after 15 seconds without deadline refresh. Refusal/expiry keeps
one fixed 15-second local poison interval; retries do not extend it. Opportunistic
sweeping can retain bounded expired storage while idle. Retirement releases all
storage after reader join and pool-owner reset; poison survives restart until its
local deadline. No downstream timer epoch or residue receipt controls this owner.
IPv4 identification reuse still has the protocol's inherent delayed-fragment
ambiguity.

Completed packets retain onward padding and select workers using the ordinary
whole-packet flow hash. Queued session messages still reject stale generations.
Once delivered, complete packets follow ordinary buffer ownership, including
delays, duplication and drops; there is no late device-generation receipt. Raw
mode preserves fragment bytes and boundaries and stages tails until fragment
zero supplies port-based worker affinity, but makes no downstream residue or
post-publication generation guarantee.

Assembly may produce complete datagrams up to 65,535 bytes. Global packet/stream
and raw-egress limits and device-MTU checks remain; an oversized packet may be
dropped at those boundaries. Transforms must handle the complete packets they
receive within their own contracts. Fake DNS sees only complete UDP queries;
fragments from any source trigger the packet-to-stack input's fatal check.

## Linux capture conntrack policy

`RawSocket` uses one `bypass-conntrack` setting for capture and raw output,
defaulting to true. When enabled, Linux capture pairs each source-range NFQUEUE
rule in `filter INPUT` with a `CT --notrack` rule in `raw PREROUTING`. NOTRACK
additionally matches `addrtype --dst-type LOCAL`, so ordinary transit traffic, broadcast, and multicast
are not exempted. The INPUT source-only capture match remains unchanged.
Matching occurs before DNAT; selected local-unicast traffic must not depend on
host conntrack-based NAT or connection-state filtering. Setting the option to
false installs neither capture nor output NOTRACK rules; NFQUEUE capture and
its drop-and-dispatch behavior remain active.
Keep normal raw priority: NOTRACK must not move fragment reassembly or change the
capture payload limit. PMTU/ICMP delivery remains a separate responsibility.

`dont-capture-protocols` is a set of literal IPv4 Protocol bytes (integers
0..255); omission and `[]` exclude nothing and duplicates are idempotent.
Apply the same exclusion predicate to NFQUEUE and incoming NOTRACK, so an
excluded protocol from a configured source reaches ordinary host conntrack and
firewall processing. Filtering only after queue delivery is too late to preserve
conntrack. This option never changes the marked raw socket's OUTPUT exemption.

Linux builds a fixed-size classic BPF bitmap lookup once during capture creation
and stores its text on the device. Nonempty exclusions require the iptables
`bpf` match (`xt_bpf`); empty exclusions add no match. Use the identical predicate
for insertion, rollback, deletion, and cleanup retries in both tables. Literal
protocol zero must work despite `iptables -p 0` meaning all protocols. Read only
the IPv4 Protocol byte; exclusions must not interpret or validate opaque
transport headers or change normal fragment reassembly. Windows includes the
same literal exclusions in its WinDivert filter using `ip.Protocol` comparisons.
The constructor consumes the borrowed exclusion set synchronously; neither
backend retains a pointer into the node's settings.

The reader must be ready before rule installation. Install all INPUT rules
before any enabled NOTRACK rules and activate capture only after all selected
rules succeed.
The lifecycle owner removes NOTRACK before NFQUEUE, including startup rollback,
normal stop, and cleanup following reader failure. Attempt queue cleanup even if
NOTRACK cleanup fails. Account for each rule kind independently, including
commands that may have committed before a timeout; reconcile those outcomes
against the corresponding table and chain. Retain failed cleanup ownership for
retry and report residual rules. Do not mutate the rule ledger from the reader
thread or run blocking firewall commands in the nonblocking stop-request phase.

Rule removal affects future packets. Already-marked or queued packets remain
untracked. `--queue-bypass` cannot undo NOTRACK; abrupt process death or final
cleanup failure can leave `WWCAP_NOTRACK_...` rules in `raw PREROUTING` requiring
administrator removal. This implementation does not reclaim another process's
rules. `skip-sysctl` suppresses optional tuning only, never either rule kind.

## Linux raw output conntrack policy

`RawSocket` defaults `bypass-conntrack` to true. A configured `mark` field is
rejected while it is enabled, including zero or null. Disabling the option
preserves explicit output marks and installs neither capture nor output
NOTRACK exemptions. The Windows backend accepts the setting without changing
WinDivert behavior.

The Linux raw device selects a random mark from values at least `0x00010000`,
preferring the high half of the 32-bit space. Selection checks `iptables-save`
mark comparisons/literal assignments and IPv4 `ip rule` fwmark selectors. It
preserves their match results for an unmarked packet, including masked and
inverted comparisons: the socket mark affects routing before `raw OUTPUT`.
These snapshots provide best-effort avoidance, not a global reservation of
marks on other sockets, native nftables/tc/eBPF rules, or future/concurrent
policy changes. Do not claim that a high range is reserved for WaterWall.

Set `SO_MARK` and install the exact-mark `CT --notrack` rule in `raw OUTPUT`
before publishing the writer. Inspection, selection, socket-option, or rule
installation failure must fail startup and roll back. Keep the ordinary raw
hook priority and packet-size policy. No per-packet firewall commands are
needed; normal routing/firewall, MTU, and ICMP-delivery responsibilities remain.
Host conntrack-based NAT cannot be relied upon for the exempted output.

Only the lifecycle owner runs firewall commands. Stop requests remain
nonblocking. Join the writer before removing its exemption; a failed join must
retain both writer resources and the rule. Record a rule as pending before
insertion because a failed or timed-out command may have committed. Remove by
exact mark and per-installation `WWRAW_NOTRACK_...` comment, reconciling failed
deletion against `raw OUTPUT`. Retain pending cleanup for retry during teardown
and report the mark/comment when it remains unresolved. Abrupt process death
can leave a rule that an administrator must remove; never flush foreign rules.

## Linux capture packet validation

Linux NFQUEUE capture must preserve deliberately invalid IPv4/TCP/UDP checksums
and opaque transport bytes, including XORed headers, unusual TCP flags, invalid
TCP data offsets, and inconsistent UDP lengths. Transport interpretation belongs
to the receiving tunnel. The capture boundary requires a complete IPv4 packet:
at least 20 bytes, version 4, a bounded IHL, and an IPv4 total length matching the
captured payload. Netlink envelope/attribute bounds, kernel sender verification,
packet IDs, actual truncation detection, and the 1,500-byte capture limit remain
enforced. Truncation/oversize logging counts only those size failures; malformed
Netlink messages or invalid basic IPv4 structure use a separate diagnostic.

Only explicit `NFQA_SKB_CSUMNOTREADY` metadata authorizes checksum completion.
For an unfragmented packet, capture attempts to finish this pending kernel work
when its headers can be interpreted safely. If completion cannot be performed,
the bytes remain unchanged and capture still admits the packet. Without that
metadata, capture neither validates nor rewrites checksums. Fragments are not
normalized here: the selected shared fragment policy validates them and may stage, reassemble, or
reject them. Windows capture retains its
checksum-provenance validation policy.

## ProtoSwap checksum representation

ProtoSwap normalizes the TCP/UDP checksum's source and destination address
contributions to zero before mapping, then restores the current addresses'
contributions when decoding. The actual IP addresses stay intact. The mapped
checksum still uses the native TCP (`6`) or UDP (`17`) pseudo-header protocol,
not the mapped number. Address rewrites between endpoints therefore preserve
valid checksums after decoding, without payload scans, packet expansion, or
per-flow state. Both endpoints must use this checksum convention.

Without an existing recalculation request, the incremental adjustment preserves
invalid checksum residuals and detection of payload corruption. Disabled IPv4
UDP checksum zero stays zero; enabled UDP arithmetic zero is transmitted as
`0xffff`. TCP zero is an ordinary checksum value.

Every fragment receives the protocol mapping. Only the fragment containing both
transport checksum bytes receives the address adjustment, including a later TCP
fragment after an 8- or 16-byte first fragment. Fragmentation may occur before
encoding or between endpoints; no reassembly or ordering state is needed.
Fragments of one datagram must receive consistent final addresses. Malformed
IPv4/transport lengths, partial checksum fields and invalid local fragment
geometry pass through unchanged, with their pending request preserved. Trailing
buffer bytes are excluded from the transform; final writers still validate the
packet length.

Native shaping and port ghost run before upstream normalization. An existing
checksum request is completed under the native protocol and actual addresses
before encoding, in either callback direction; a failed request prevents mapping.
For fragments, that request repairs only the IPv4 header. Decoding restores the
address contribution and native protocol before downstream port restoration or
TCP/TLS parsing. Existing downstream checksum requests are handed onward;
upstream decoding can complete them immediately. ProtoSwap creates no new
recalculation request. Arbitrary payload edits while mapped require a transform
that understands this checksum convention.

The shared `updateIpv4TransportChecksumAddresses()` helper takes an effective
TCP/UDP protocol separately from the visible IP protocol and explicit old/new
address contributions in network byte order. It must never manage a line's
checksum request. It applies RFC 1624 equation 3 with 16-bit complements and
end-around carry, and changes at most the two transport checksum bytes.
For whole packets, validate TCP minimum header/data offset or UDP declared length
against IPv4 total length using the effective protocol. For fragments, compute
`fragment_start = fragment_offset * 8` and locate TCP offset 16 or UDP offset 6
relative to the original IP payload. Never form a later-fragment TCP-header
pointer or require every fragment to contain a full transport header.

Preflight the complete transition before any mutation or request consumption.
A no-match or rejected transition must leave bytes and the request unchanged.
A successful encoder must not hand a normalized packet with an unsettled request
to a generic writer: mapped protocol `1`, for example, would select ICMP checksum
logic. Preserve the post-transition request per duplicate or delayed packet;
never restore a consumed request from an earlier cached boolean. An already
mapped upstream packet is decoded exactly once at this node and forwarded native.

## Two Kinds of Packet Tunnels

Not every tunnel that touches packet lines is the same kind of tunnel. There are
two distinct categories, and they have different rules.

### 1. Pure Packet Tunnels (`packettunnelCreate`)

Some tunnels are created with `packettunnelCreate()` instead of `tunnelCreate()`.
From `ww/net/packet_tunnel.c`:

```c
tunnel_t *packettunnelCreate(node_t *node, size_t tstate_size, size_t lstate_size)
{
    if (UNLIKELY(lstate_size != 0))
    {
        return NULL; // pure packet tunnels have no per-line state
    }

    tunnel_t *t = tunnelCreate(node, tstate_size, 0);
    if (! t)
    {
        return NULL; // state-size overflow or allocation failure
    }

    // ... explicitly installs upstream Est and downstream Init forwarding ...
    // ... installs mandatory packet-payload defaults ...
    return t;
}
```

Key facts:

- `packettunnelCreate()` **requires `lstate_size == 0`** and returns `NULL` when
  that contract, state-size validation, or allocation fails. Pure packet tunnels
  have no per-line state, and their constructors must check the result before
  assigning callbacks or accessing tunnel state.
- They are expected to **override the packet payload callbacks**.
- The default payload callbacks are intentionally invalid: they call `LOGF(...)`
  and `abortProgramNow(1)`, so they crash loudly if you forget to override them:

```c
static void packettunnelDefaultUpStreamPayload(tunnel_t *self, line_t *line, sbuf_t *payload)
{
    LOGF("Unexpected call to default up stream payload for a packet tunnel, "
         "this function must be overridden");
    abortProgramNow(1);
}
```

- `Init`, `Est`, `Pause`, `Resume`, and `Finish` use same-direction lifecycle
  pass-throughs. `packettunnelCreate()` explicitly installs upstream `Est` and
  downstream `Init` forwarding because `tunnelCreate()` rejects those events.
  An individual tunnel overrides one
  only when its exact handler role requires an anchoring rejection, explicit
  forwarding, or an intentional terminal absorption as classified above.

Examples: `IpOverrider`, `IpManipulator`, `PingClient`, `PingServer`,
`WireGuardDevice`.

For pure packet tunnels:

- Do not add connection-style line lifecycle logic casually.
- `lstate_size == 0` does **not** mean "packet lines only". A
  `kNodeLayerAnything` packet tunnel also carries normal connection lines.
- Some default callbacks deliberately abort; know which ones you must override.

### 2. Packet-Line Anchored Bridges (`tunnelCreate`)

Other tunnels are ordinary `tunnelCreate()` tunnels that **use the worker packet
line as an anchor** for worker-local bridge state. They cross the boundary between
packet-oriented runtime and connection-oriented runtime.

Examples and what they anchor:

| Bridge | Role |
| --- | --- |
| `PacketsToStream` | packet line to a worker-local stream-facing line; stores that line and a read buffer |
| `StreamToPackets` | a stream line to the packet line; stores the active stream line and read buffer per worker |
| `PacketsToConnection` | packet traffic to lwIP to normal WaterWall connection lines behind the packet side |
| `PacketSplitStream` | splits packet traffic across stream paths |

State stored here is worker-local bridge state — still not per-connection state.
If you need closable per-connection behavior behind packet traffic, create or
manage normal lines behind the packet line instead of closing the packet line.

### Obfuscator stream and packet roles

With `tls_record_header` enabled, ObfuscatorClient and ObfuscatorServer reserve
normal-line receive state through `tunnelCreate()`. Both supported Init directions
initialize that state before forwarding; upstream Est remains pass-through.
Exact worker packet lines bypass this state and preserve one-packet/one-record
validation, checksum requests, and oversized-datagram drops. Packet Finish remains
same-direction forwarding and never destroys the packet line.

Ordinary stream deliveries split into records with at most 65,535 body bytes.
XOR and skip operate per record. One encoded aggregate is sent per delivery;
complete received records become one decoded aggregate, with partial tails kept
for later input. Receive retention is bounded by 2 MiB plus one maximum wire record
(65,540 bytes), for a fixed total of 2,162,692 bytes. This is independent of
pool sizes, RAM profile and splice settings.
Retain input for incomplete records and necessary ordering barriers. Synchronous
aggregate transformation follows Part 2's admitted-batch rule; an independent
retained-backlog drain honors Pause. Malformed records and overflow close the
borrowed normal line through its owner. Finish releases all receive state.

## Packet-Line Initialization

Packet lines are initialized differently from connection lines.

For a chain whose **head is a layer-3 packet node**, the node manager sends one
upstream `Init` on each worker's packet line during startup — **once per worker,
not once per packet**. So packet-line `Init` is a worker/bootstrap event, not a
connection-open event.

But if a bridge relies on packet lines while the chain head is **not** itself a
layer-3 packet node, that automatic init does not happen, and the bridge must
trigger it. `StreamToPackets` does exactly this in `onStart()`, queueing the
bootstrap onto every worker so packet-side tunnels see their `Init` after startup
rather than re-entering init paths inline:

```c
static void streamtopacketsQueueWorkerPacketInit(void *worker, void *arg1, void *arg2, void *arg3)
{
    discard worker;
    discard arg2;
    discard arg3;

    tunnel_t *t = arg1;
    line_t   *l = tunnelchainGetWorkerPacketLine(tunnelGetChain(t), getCurrentEventWorkerWID());

    if (UNLIKELY(! lineCallWithRef(l, tunnelNextUpStreamInit, t)))
    {
        LOGF("StreamToPackets: worker packet line died during packet-side init");
        abortProgramNow(1);
    }
}

void streamtopacketsTunnelOnStart(tunnel_t *t)
{
    for (wid_t wi = 0; wi < getWorkersCount(); wi++)
    {
        if (UNLIKELY(
                sendWorkerMessageForceQueueWithCleanup(wi, streamtopacketsQueueWorkerPacketInit, NULL, t, NULL, NULL) !=
                kWorkerMessageSubmitAccepted))
        {
            LOGF("StreamToPackets: failed to admit required packet-side Init on worker %u", (unsigned int) wi);
            startupFailureRecord(1);
            return;
        }
    }
}
```

So if you create or modify a packet bridge: do not assume packet-line init
happened automatically. Verify whether the init comes from the node manager (chain
head is layer-3) or whether your tunnel must trigger it in `onStart()`.

## Paired Tunnel Direction (the PingClient / PingServer Rule)

Transform role and callback forwarding direction are separate decisions. Ping
wire v2 uses two independent Echo sessions:

```text
client data: PingClient -- Echo Request --> PingServer
             PingClient <-- exact Echo Reply -- PingServer

server data: PingClient <-- Echo Request -- PingServer
             PingClient -- exact Echo Reply --> PingServer
```

- PingClient upstream and PingServer downstream originate type-8 requests with
  their local data. Their peer decodes the request in its corresponding
  callback and forwards the inner packet in the same callback direction.
- A received request's type-0 reply travels back to its sender before the
  original request is delivered. It is an acknowledgement only; the sender
  consumes a matching reply instead of delivering its payload.
- Correlation and replay suppression belong to one bounded synchronized tracker
  per Ping node. Device flow affinity chooses the packet line that runs a
  callback; its WID is not request/reply correlation identity.
- A request receiver publishes two distinct buffers. The generated reply clone
  travels back toward the request sender, while the decoded original continues
  in the direction in which the request was received.
- Consequently, PingServer's upstream request handler sends the reply clone with
  `tunnelPrevDownStreamPayload()` and the decoded original with
  `tunnelNextUpStreamPayload()`. PingClient's downstream request handler sends
  the clone with `tunnelNextUpStreamPayload()` and the decoded original with
  `tunnelPrevDownStreamPayload()`.

Sending the **original received request** back toward its sender would be an
invalid reflection. Sending the separately generated exact Echo Reply in that
opposite direction is required by the wire protocol. Likewise, encapsulating
the original in PingServer's upstream callback would transform it twice.

The procedure for any packet tunnel:

1. Draw the packet flow with arrows.
2. Place the encode/decode step in the callback direction that flow requires.
3. Use `tunnelNextUpStreamPayload()` only for upstream forwarding and
   `tunnelPrevDownStreamPayload()` only for downstream forwarding.
4. Do not treat packet lines as per-connection lines.
5. Do not call `lineDestroy()` on packet lines at runtime.
6. Do not add stream-style lifecycle to a pure packet tunnel unless its design
   requires it.

## Testing Packet Tunnels

Packet tunnel tests must exercise the **real intended direction**. The canonical
Ping test is one direct packet chain:

```text
TesterClient(packet-mode=true)
    -> PingClient
    -> PingServer
    -> TesterServer(packet-mode=true)
```

The upstream request must be acknowledged and restored before TesterServer sees
it; reverse data must become a separate Echo Request and be acknowledged before
TesterClient sees it. Add coverage that would fail if PingServer upstream
encapsulated instead of decoding, if a reply were delivered twice, or if server
data were put into the original request's reply.

The packet-line `Finish` contract has its own coverage, and a new packet-side
handler belongs in it:

- `tests/unittests/packet_adapter_finish_test.c` calls the anchoring adapters'
  `Finish` handlers for real in a forked child and requires the child to die
  rather than return.
- `tests/unittests/packetsender_orderly_shutdown_test.c` proves that
  `PacketSender` cancels a pending worker timer and stops a ready multi-packet
  batch when a payload emits downstream `Finish` re-entrantly, without
  destroying the worker packet line.
- `tests/line_ownership_policy_test.py` fails if a `fin.c` becomes an
  unexplained bare return, or if a contract test loses its ctest registration.

## Rules for Packet-Oriented Changes (Summary)

- Do not close packet lines during runtime, and never `lineDestroy()` one.
- The owner Finish postcondition from Part 2 does **not** apply to packet lines.
- Classify each packet-line `Finish` handler and direction as one of three roles:
  an anchor rejects an impossible close with `LOGF` + `abortProgramNow(1)`; a
  transparent middle transform forwards it in the same direction; an intentional
  terminal absorber documents why there is nothing to forward or release.
- `PacketSender` is direction-specific: downstream absorbs a legitimate close
  from a packet-line terminal such as an active `BlackHole`, while upstream
  remains fatal. `PacketReceiver` is also an intentional terminal absorber.
- A handler that can receive both a packet line and a normal line must branch on
  the exact role (`tunnelchainIsWorkerPacketLine()`) before any cleanup.
- `packettunnelCreate()` only means `lstate_size == 0`; several such nodes are
  `kNodeLayerAnything` and carry ordinary connection lines too, which is why its
  lifecycle callbacks stay plain pass-throughs.
- A `Finish` handler that does nothing must say why: propagate, release, report,
  or document that you own no per-line state and have no onward direction.
- Do not run normal per-connection `Finish` logic on packet lines unless the exact
  handler-role contract explicitly requires it.
- Treat packet-line state as worker-local shared state.
- Treat routing context and `recalculate_checksum` as mutable per-packet metadata,
  never as durable session identity.
- For per-flow lifecycle, create normal lines behind the packet side.
- A `packettunnelCreate()` tunnel has no per-line state (`lstate_size == 0`).
- A bridge that anchors state on the packet line keeps that state across many
  packets on the worker.
- If your code depends on packet-line init, verify where that init comes from.

The single most common mistake to avoid:

```text
Using packet lines as if they were normal connection lines with an ordinary
Init -> Payload -> Finish per-connection lifecycle. They are not.
```
