# Part 6: Building, Testing & Reviewing

A tunnel change is not done when it compiles. It is done when it builds through a
known-good preset, passes the relevant integration tests, and survives the review
checklist. This part covers how to validate work and how to present it.

## Building

Prefer the `linux` CMake preset. Configure once, then build:

```bash
cmake --preset linux
cmake --build --preset linux -j8
```

For a focused build of one changed tunnel target (much faster while iterating):

```bash
cmake --build --preset linux --target TlsClient -j8
```

Tunnel targets are named after the tunnel directory, e.g. `TcpConnector`,
`UdpConnector`, `TcpListener`, `TlsClient`, `MuxClient`.

The configured tree lives in `build/linux/`, and the binary is produced per
configuration, e.g. `build/linux/Release/Waterwall` (also `Debug/` and
`RelWithDebInfo/`). Other preset trees exist under `build/` (`linux-gcc-x64`,
`linux-clang-x64`, `linux-tsan-unit`, and more); do not mix them within a single
verification flow.

Linux runtime code uses the `waterwall_runtime_options` interface, exported
publicly by `ww`: C/C++ compilation receives `-fno-pic -fno-pie`, and executable
links receive `-no-pie`. This covers `ww`, the application, tunnels, their reused
PCH, and runtime-linked tests. The lwIP, UUID, freeres, KCP/FEC, and Brotli wrapper helper targets attach
the same interface directly without inheriting ww's headers or PCH. Application
targets also use `POSITION_INDEPENDENT_CODE OFF` with `CheckPIESupported`.
The policy applies to ordinary and packed builds across Linux CPU variants;
Android, Apple, and other non-Windows operating systems retain their existing policy.
ThreadSanitizer builds retain PIE because the sanitizer requires it. The selected
static runtime dependencies also use this policy: mimalloc, MaxMindDB, c-ares,
libsodium, nghttp2, BoringSSL, and Brotli. Komihash is header-only and inherits the
including runtime source's flags. `waterwall_configure_runtime_dependency()`
applies the interface's compile options, disables an upstream PIC property when
non-PIC compilation is active, and exports the matching executable link options.
This avoids changing vendored sources or mixing upstream CMake link signatures.
Preprocessed assembly receives the same non-PIC options as C/C++; NASM keeps its
own instruction/relocation implementation. The packed launcher, host encoder,
and XZ Embedded retain their own relocation settings.
The startup guard and decoder wrapper are compiled separately for the
application and launcher so their object code follows the respective policy. Do not link the non-PIC runtime
archives into a shared library. This removes ASLR for the application's executable
image but does not eliminate dynamic-library PLT/GOT calls; throughput gains must
be measured. Results from changing only the executable link policy do not measure
this runtime-wide code-generation policy.

The in-tree OpenSSL static build receives `no-pic no-pie` through its own
Configure options on Linux (excluding Android and ThreadSanitizer) and Windows
x86/x64. GCC/Clang builds also receive `-fno-pic -fno-pie` to override default-PIE
toolchains; MSVC does not receive those Unix compiler flags. Other platforms and
Windows ARM retain their existing settings. Imported OpenSSL targets supplied
externally retain their provider's build policy. OpenSSL's `no-pic` also disables
building loadable modules: the default provider remains built in, and the enabled
legacy provider is linked into libcrypto instead of built as a separate module.
This is not a FIPS-module build. The wrapper detects changed Configure options and
recreates its generated OpenSSL build directory before rebuilding the archives.

Windows x86/x64 runtime consumers use the same interface for fixed-base executable
linking. MSVC uses `/DYNAMICBASE:NO /FIXED /INCREMENTAL:NO` and, on x64,
`/HIGHENTROPYVA:NO`. MinGW uses `-fno-pic -fno-pie` for C/C++ runtime compilation
and `--disable-dynamicbase --disable-reloc-section` for executable linking, plus
`--disable-high-entropy-va` on x64. These apply in every configuration, including
Debug; MSVC incremental linking is disabled to permit fixed-base output.
Dependency DLLs retain their own relocation policy. Windows ARM targets retain
ASLR because the platform requires it. Removing the executable's base relocations
requires its preferred address to be available; OS policies that require
relocatable images may reject it. This is an executable-image policy, not a
system-wide override of DLL, heap, stack, or OS-enforced randomization.
See Microsoft's [DYNAMICBASE](https://learn.microsoft.com/en-us/cpp/build/reference/dynamicbase)
and [FIXED](https://learn.microsoft.com/en-us/cpp/build/reference/fixed-fixed-base-address)
references, and the [GNU PE linker options](https://sourceware.org/binutils/docs/ld/Options.html).

### Vendored XZ Embedded

`waterwall_cpu_options` carries the selected architecture flags separately from
the runtime's non-PIC/non-PIE policy. `ww` exports this interface to its consumers;
the root build attaches it privately to `xz_embedded` and both decoder wrappers.
The existing AVX/AVX2/AVX512 switches, baseline selection and old-CPU presets
therefore also control decoder compilation. Launcher startup code and its CPU
guard do not inherit these flags. Standalone host-tool and launcher-fixture builds
retain their own compiler defaults. This permits compiler optimization for the
selected CPU; it adds no SIMD implementation or runtime CPU dispatch to XZ and
does not change the payload format or encoder settings.

`ww/vendor/xz-embedded/README.waterwall.md` records the pinned upstream revision
and source mapping. The root build always builds `xz_embedded` as a static
library and links `Waterwall` through `WaterWall::XZDecoder` to `XZEmbedded::XZEmbedded`, on every
platform, without fetching XZ sources or requiring system liblzma. Other targets
link `XZEmbedded::XZEmbedded` directly to obtain `<xz.h>`; `ww` does not re-export
this dependency. Unused code remains subject to normal static linker elimination.
The compiled decoder uses the XZ container layout with Waterwall-specific
identifiers, LZMA2 + x86 BCJ, CRC32 integrity checks, and only `XZ_SINGLE` decoding.
CRC64, SHA-256, other BCJ filters, multi-call
allocation modes, and concatenated-stream support are disabled. Initialize the
CRC32 table once before concurrent use, as documented in the vendored header.
XZ Embedded provides decompression only.

### Build-time XZ payload tools

`core/tools/xz_encoder/README.md` documents the independent native encoder project.
From `core/tools/xz_encoder`, configure with `cmake --preset host`, build with
`cmake --build --preset host-release -j8`, and test with
`ctest --preset host-release`; repeat with `host-debug` for asserted builds.
The encoder uses pinned upstream liblzma through CPM only in this host build.
Never configure it with the production cross-compilation toolchain. Its code and
libraries are not dependencies of the shipped executable.

Packing itself requires CMake and native C tools, with no Python dependency.
`core/build_host_encoder.cmake` serializes the native configure/build with
`file(LOCK)` and disables tests for the automatic host build. The manual `host`
preset enables the Python regression tests. `core/generate_packed_payload.cmake`
owns staging, stripping, tool invocation and atomic publication under a per-output
lock. The CRT-only `waterwall_payload_tool` validates ELF/PE images and emits
compressed bytes and metadata as C source; `waterwall_xz_encoder` owns compression.
Python remains in test runners, including the Windows launcher fixture. Production
builds with tests disabled do not require Python for these packing steps.

The fixed encoder format is one CRC32 stream with the XZ layout and Waterwall
identifiers, using x86 BCJ at offset zero, then LZMA2 (8 MiB dictionary,
lc/lp/pb 3/0/2, normal mode, BT4, nice length 64,
search depth 64). The separate `WaterWall::XZDecoder` target exposes
`<ww_xz_decoder.h>` and uses XZ Embedded single-call decoding into a bounded
caller-owned buffer. Call `wwXzDecoderInit()` once before concurrent use. Success
requires complete input consumption and the trusted expected output length;
output must be discarded on failure. The wrapper accepts only CRC32 checks.
The shared `ww/vendor/xz-embedded/include/ww_xz_format.h` defines a six-byte
`MUFASA` header magic, a two-byte `gg` footer magic (no terminating NULs), and
`FF` as the private CRC32 selector. The encoder replaces those identifiers in
liblzma output. Both copies of the stream flags become `00 FF`: the selector
is at offset 7 and three bytes before the stream end. Their stored CRCs remain
calculated over the original `00 01` flags. The decoder requires the private
CRC32 marker and normalizes only its own copied header/footer buffers before
CRC validation; caller input stays unchanged. Header, footer, index and block
data checksum validation remain enabled. Compression algorithms, sizes, filters,
indexes and checksum values stay intact. Both native launchers use this format.
Ordinary XZ tools cannot decode it until the magic and both selectors are
restored. The internal `.xz` suffix does not denote a standard XZ file.

This boundary has no Linux loading or startup dependencies. Tests round-trip a
compiled module and exercise malformed inputs and capacity/length failures.
Encoder and payload-source output are created exclusively; existing output and an input/output path
collision must leave existing bytes intact. Windows uses `_open` with `_O_EXCL`
and binary mode before `_fdopen`, because the legacy MSVCRT used by MINGW32/MINGW64
does not implement `fopen`'s C11 `x` mode. Other hosts retain `fopen(..., "wbx")`.

### Optional Linux packed executable

`WW_PACK_RUNTIME` defaults to `OFF`. Native Linux x86-64 builds may use a separate
production tree with identical enabled features and Release LTO:

```bash
cmake --preset linux-packed
cmake --build --preset linux-packed -j8
ctest --preset linux-packed --output-on-failure
```

Linux x64 artifact jobs in GitHub CI enable `WW_PACK_RUNTIME` on the configure
command for GCC, Clang, old-CPU, and AVX512 builds. Presets keep their development
defaults. Artifact names stay the same, and each x64 upload contains only the final
`Release/Waterwall`, excluding the private application. The existing GCC x64
integration lanes exercise that packed executable. Native units, sanitizer jobs,
and other platform/architecture artifacts keep their existing build modes.

The public `Waterwall` target builds the final executable in both ordinary and
packed configurations, including explicit `--target Waterwall` builds. Packed
builds use the private `WaterwallApplication` target for the ordinary application.
The final artifact is `build/linux-packed/Release/Waterwall`. Deploy it with user
configuration, existing system libraries, and any intentionally supplied external
node libraries. The private `waterwall_application` comparison executable is a
normal executable built with the ordinary dependency graph and optimization,
allocator, CPU, and linking policies. Packing adds no global PIC or shared-runtime
requirements. Linux packing remains native x86-64 only. Windows packing accepts x86/x64
targets, including MinGW cross-compilation; Windows ARM and other packed targets
fail configuration. Ordinary builds do not invoke the host encoder or payload generator.

Core-file open failures include the program version on stderr before the error.
The ordinary application and packed launcher use the same startup input-error
reporting, so a missing core file still identifies the executable version without
runtime initialization or decompression.

A serialized independent native build checks both payload tools' dependencies in
`build/xz-encoder-host-<compiler/generator identity>` without inheriting target
compiler environment flags. `WW_HOST_C_COMPILER` selects a native host compiler;
`WW_HOST_ENCODER_GENERATOR` selects its generator. Windows host builds retain
the MSVC environment and use the host `.exe` suffix. The independent manual
encoder presets continue using `build/xz-encoder-host`.
On a Windows Visual Studio build, the native encoder generator selects its own
MSVC compiler without searching for GCC or Clang. Explicitly setting
`CMAKE_SYSTEM_NAME` in a native Windows preset still makes CMake report
`CMAKE_CROSSCOMPILING`; that flag alone does not determine host executability.
Generation finalizes a private executable copy, checks its target identity, compresses
it, and atomically publishes one source containing bytes and exact size/target
metadata under `packed/<configuration>`. The executable, native tools, CMake scripts, and
strip tool are declared dependencies. Failure stops the build without changing the
input executable or publishing partial output. The launcher links the existing
`WaterWall::XZDecoder` target, basic JSON and plain-C input support, without `ww`,
full settings, C++ runtime, networking, or crypto dependencies.
The final launcher is also stripped during linking in every configuration,
including Debug: static symbols and debug information are omitted while symbols
needed for dynamic linking remain. The ordinary application and private comparison
executable retain their normal configuration's debugging information.

The Linux backend requires Linux 3.19 or newer with `memfd_create`, sealing,
`execveat`, and permission to execute anonymous files. `/proc/self/exe` must be
readable to capture the effective outer executable location, including PATH and
symlink invocation. The backend restores directly into a shared writable mapping,
unmaps it, seals the executable, and calls `execveat` with `AT_EMPTY_PATH`. The
kernel/interpreter handles ordinary ELF execution. New executable-memfd flags are
retried only on unsupported-flag errors, never on policy denial. All failures are
nonzero; there is no disk extraction, cache, shell, or supervisor fallback. The
conservative CPU guard runs before both launcher and application startup.

The startup-only handoff uses four reserved arguments:
`--ww-internal-fd=`, `--ww-internal-len=`, `--ww-internal-src=`, and
`--ww-internal-exe=`. The outer launcher rejects these from users. The ordinary
application accepts a complete, nonduplicate set as untrusted configuration input,
strips it before normal CLI validation, reads the declared regular-file snapshot
from offset zero, and closes the descriptor on success or failure. Only the input
descriptor deliberately survives exec; launcher descriptors are above the standard
streams even when those streams were closed. Input remains byte-for-byte intact,
including bytes after a NUL. CLI arguments, environment, CWD, PID, and standard
streams retain their normal meanings. The captured executable path supplies the
existing executable-relative external-library search; it does not change the
kernel's `/proc/self/exe` identity. Restricted mode still prohibits external nodes
and user scripts. Set-ID/file-capability deployment is not a supported packing
contract; this backend adds no credential transfer or privilege workaround.

Native no-LTO unit trees own full-settings cleanup coverage and launcher failure
fixtures. The snapshot unit also crosses a real exec and checks exact large-input
receipt, offset, PID, restricted selection, and descriptor closure. Production
tests select the final launcher explicitly and exercise real restoration,
constructors, TLS, workers, networking, and shutdown. Fixture tests alone cannot
establish full runtime equivalence; unavailable platform, namespace, or privileged
checks must be reported as unverified.

The public-target regression check operates on generated artifacts in an idle,
configured packed tree. Run it separately from other builds/tests of that tree:

```bash
python3 tests/packed_build_target_test.py --build-dir build/linux-packed --config Release
python3 tests/packed_build_target_test.py --build-dir build/linux-packed --config Debug
```

It uses `readelf` (override with `--readelf PATH`) to verify the final launcher has
no static symbol table or debug sections, recreates a missing final executable,
checks regeneration after an application update, and verifies that an unchanged
build leaves the payload stable.

### Windows packed executable bootstrap

Windows x86/x64 builds can opt in with `-DWW_PACK_RUNTIME=ON`. GitHub CI enables
packing for MSVC x86/x64 and every MSYS artifact job (MINGW32, MINGW64, UCRT64 and
CLANG64), while development presets retain their defaults. Existing artifact names
contain only the final `Release/Waterwall.exe`; the private application and debug
files are excluded. Public target `Waterwall` builds the launcher and its ordinary
`WaterwallApplication` payload. Windows ARM64 artifacts remain ordinary because
Windows ARM packing is unsupported.

The launcher is a C executable using CRT allocation, shared startup/basic JSON,
XZ Embedded, and Windows system APIs. It does not link runtime libraries. The
inner application keeps the ordinary fixed-base options. The launcher explicitly
retains ASLR, base relocations, and DEP. Both executables retain the existing
`requireAdministrator` manifest. GNU-compatible stripping applies only to staged
payload copies and the final launcher. MSVC preserves the application's separate
PDB policy; launcher links disable incremental linking and debug generation.
The PE debug directory may still contain VC_FEATURE, POGO, ILTCG, REPRO, or
extended DLL-characteristics metadata with `/DEBUG:NONE`. Its presence alone
does not indicate retained debug symbols. The packed-target check reads the
individual record types, allowing this metadata while rejecting CodeView/PDB,
COFF and other debug records, debug sections, and COFF symbol tables. Extended
DLL-characteristics records can carry CET policy and must not be removed merely
to empty the directory. See the [PE debug types](https://learn.microsoft.com/en-us/windows/win32/debug/pe-format#debug-type).
No PE loader sections are removed manually. Payload generation identifies PE32
and PE32+, rejects DLLs, wrong machines, invalid entry points and section ranges,
and validates again after finalization. Both platforms use the same private
compression stream format described above.

After basic validation, the Windows launcher copies the exact input into an
unnamed pagefile mapping, drops writable access, and inherits only a read-only
snapshot handle and duplicated intended standard handles. The startup boundary
uses `--ww-internal-map=` in place of Linux's descriptor argument, validates a
bounded transport header and committed read-only pages across the complete view,
copies the snapshot into owned CRT memory, and closes the handle. A successful
mapping alone does not establish that reserved pages can be read. All internal
arguments are removed before normal CLI parsing.
Restricted validation remains mandatory. Ordinary Windows stdin retains its CRT
text semantics; restricted stdin retains binary semantics, with no second text
conversion at receipt.

The executable is decoded into non-executable storage and written into a new
private temporary directory. Its protected ACL admits the current user and
SYSTEM and carries the token's integrity label. Extraction requires a local
ACL-capable volume; network/FAT-style temporary roots have no weaker fallback.
Reparse-point roots are refused, the resolved root and every canonical ancestor
are pinned against replacement, and the owned directory and executable stay
protected while in use. Directory pins request traverse access and deny write
and delete sharing; attribute-only opens do not enforce these
[sharing restrictions](https://learn.microsoft.com/en-us/openspecs/windows_protocols/ms-fsa/8c0e3f4f-0729-49f4-a14d-7f7add593819).
Only completely decoded and identified PE bytes are started. New filesystem and
process operations use wide APIs; conversion to the existing active-code-page
startup boundary rejects unrepresentable paths.

`CreateProcessW` loads the child normally with the original CWD, environment and
standard streams. Correct CRT quoting preserves argument boundaries. Captured
outer executable location supplies the runtime's existing resource/node path
override. DLL files directly beside the launcher are copied into the private
extraction directory with its restrictive ACL and held read-only until child
exit. This preserves executable-directory precedence for implicit imports and
bare-name DLL loads while keeping the native CWD/system/PATH search policy and
inherited DLL-directory settings intact. No `SetDllDirectoryW`, PATH expansion,
recursive deployment copy, or stream proxy is added. CWD-only companions remain
in CWD and use the ordinary loader fallback. DLL copies are startup snapshots;
their Windows module paths point into the extraction directory. Resources needed
by a companion through its own module-relative paths are not copied. Such
deployments must use an ordinary build unless those resources are located
explicitly. See Microsoft's
[DLL search order](https://learn.microsoft.com/en-us/windows/win32/dlls/dynamic-link-library-search-order).

The child has its own PID and temporary Windows image path; the launcher waits
without handling traffic. A suspended child is admitted into an owned
kill-on-close job before resuming. Admission failure terminates and reaps the
child. No breakaway or resource-limit policy is requested. The existing Vista
API target is retained; enclosing-job combinations that cannot admit the child
fail explicitly (nested jobs require newer Windows). Native deployment testing
must establish supported OS/service-wrapper combinations. This does not claim
crash-proof admission: forced termination between creation and job assignment
can leave a suspended child, and forced termination or machine failure can leave
extraction files.

After child exit, cleanup closes owned handles, retries deletion a bounded number
of times for both the executable and directory, and reports exact owned residue
as UTF-8 on byte-oriented stderr without recursive deletion. `ExitProcess`
relays the full child DWORD status; cleanup warnings do not replace it. The
console behavior is described in [Part 7](./part7-shutdown-and-signals.mdx).
A Windows Firewall rule for the outer path does not identify the temporary child.
Stable-path firewall/service supervision deployments must use an ordinary build
unless their concrete deployment policy supports this process model. Packing
does not add firewall rules, bypass UAC, or guarantee memory-only storage.

The independent `core/tools/windows_launcher` project compiles the actual launcher
and startup sources with a small PE fixture and companion DLL. From that directory:

```bash
cmake --preset mingw-x64
cmake --build --preset mingw-release -j8
ctest --preset mingw-release --output-on-failure
cmake --build --preset mingw-debug -j8
ctest --preset mingw-debug --output-on-failure
```

For a build-only PE32 cross-check, use `mingw-x86`, `mingw-x86-release`, and
`mingw-x86-debug` with an i686 MinGW compiler. It does not assume Wine32 is installed.
On Windows, use `native`, `native-release`, and `native-debug` from a compiler
environment. The fixture covers exact snapshots, large input, text/binary modes,
source deletion after capture, original location, companion imports from an
unrelated CWD, TLS initialization, child status, malformed handoffs, handle
closure, and concurrent cleanup. The Python fixture normalizes paths to Windows backslashes
at its process boundary, including in MSYS2 environments whose Python defaults
to forward slashes; the original-executable handoff check remains exact.
Native platform unit trees register
`waterwall.windows_packed_startup_unit` and
`waterwall.windows_launcher_arguments_unit` outside the Linux-only test subtree.
Native packed application builds register `waterwall.windows_packed_application`,
which compares startup/settings behavior, requires a size reduction against the
finalized payload, and runs the existing four-worker in-process TLS workload on
both ordinary and packed executables. Registration uses the Windows host and
runnable target architecture, so the native x86/x64 presets register it even
when their explicit system settings make `CMAKE_CROSSCOMPILING` true.
The existing Windows x86/x64 artifact jobs run the MSVC bootstrap fixture and
public-target checks in Debug and Release before upload, using the matching
compiler environment. ARM64 skips these packing checks. The MSYS artifact jobs
run the same bootstrap checks with their own toolchains. Packed artifact builds
explicitly enable tests and run `waterwall.windows_packed_application` against
the same Release launcher that will be uploaded. The comparison checks startup,
worker/TLS behavior and size reduction using the private ordinary application
from that build; a second full application build is unnecessary. Test failure
prevents upload, and a missing artifact is an error.
These tests do not replace manual deployment acceptance.

`windows-cross-mingw-x64` is a full application cross-check preset. It requires
the target MinGW compiler/SDK and native dependency build tools; successful
fixture builds do not prove that every full application dependency cross-builds.
Use the same public-target regression on an idle Windows packed tree:

```bash
python tests/packed_build_target_test.py --build-dir build/windows-launcher-native --config Release --windows
```

On Linux/Wine append `--runner wine`. The check verifies PE identity, launcher
ASLR/DEP/relocations and omitted debug data, application non-ASLR flags, recreation,
regeneration, and stable unchanged output. Header checks and Wine cannot establish
native UAC, console control, ACL/locking, antivirus, firewall or service-wrapper
behavior, nor full runtime workers/TCP/TLS equivalence. Native application tests
gate artifact publication; manual testing remains necessary for deployment-specific
behavior.

### Build Rules

- Do **not** run `cmake --build build ...` against an arbitrary `build/` tree
  unless you have confirmed it is a healthy preset-created tree you intend to use.
- Do **not** mix build trees (`build/`, `build/linux`, `build/linux-gcc-x64`)
  inside one verification flow — you can end up testing a stale binary.
- Prefer preset target builds over root-tree builds.

## Formatting C And Headers

Run the portable `clang-format` command with the repository's `.clang-format`
file on every C or header file you modify:

```bash
clang-format -i --style=file path/to/changed_file.c
clang-format --dry-run -Werror --style=file path/to/changed_file.c
```

Each development environment is responsible for making `clang-format` resolve to
its installed project-compatible formatter; repository documentation must not pin
a distribution-specific executable name. New files must be fully conformant. Some
legacy files are not, so do not reformat untouched code wholesale: format and
verify the changed ranges with `--lines=<start>:<end>` when a full-file pass would
rewrite unrelated lines. If the command is unavailable, report what remains
unformatted or unverified rather than silently skipping the check.

### Build-Authority Modes

The repository's Ninja authority model validates symlink-free graph traversal,
the exact include/subninja closure, Ninja variable timing, and declared generated
inputs. Its toolchain identities also include resolved symlink-target bytes.

The current host-toolchain workflow is nevertheless **diagnostic**, not
release-authoritative: the compiler, subordinate programs, headers, libraries,
plugins, CRT objects, and sysroot are not yet executed from one immutable
snapshot. `tests/tools/cmake_ci_step.py --mode integrity` therefore fails closed
with an immutable-toolchain boundary error. Use `--mode diagnostic` for ordinary
CI until a reviewed immutable toolchain image or snapshot is available; do not
describe a diagnostic record as a hermetic or hostile-same-user guarantee.

## Testing

Tests are registered with CTest under names like `waterwall.<case>` and are driven
by the harness in `tests/`. Each integration case lives in `tests/cases/<case>/`.

On Linux, deterministic integration tests execute inside private user and network
namespaces created without root privileges, with loopback-only isolation
(`tests/run_in_network_namespace.sh`),
preventing port collisions and allowing concurrent execution. Tests are organized
into lanes via `tests/run_test_lane.sh`:

Deterministic cases must not use public DNS or depend on host-network port
availability. A case that intentionally needs live internet belongs in the
explicit `external` lane instead.

The privileged lane uses the same network isolation, but because its wrapper is
already invoked through `sudo -E`, it retains the caller's user namespace and
creates only a private network namespace. This preserves access to runner-owned
workspace paths; nesting root inside a mapped user namespace would lose that
host-filesystem permission authority.

- `support`: production policy and test-harness tests (13 tests), run strictly serially.
- `functional`: deterministic integration tests (153 tests) run in parallel (`min(32, max(4, 4 * CPUs))` jobs).
- `external`: integration tests requiring live host internet access (e.g. Reality against Google), run strictly serially.
- `speed`: multi-stream throughput benchmarks (16 tests), run strictly serially (`RUN_SERIAL TRUE`) to avoid contention.
- `privileged`: root/TUN probe tests (6 tests) run under `sudo -E`.
- `all`: runs support, functional, external, and speed lanes in sequence (183 tests total).

The production tree contains integration, smoke, and source-policy tests. Native
unit tests live in the separate no-LTO tree below. `ctest --preset linux` is
therefore production-only.

Warm-build reference measurements on a 4-CPU host are about 55 seconds for the
support lane, 22–24 seconds for the parallel deterministic functional lane (16 jobs),
less than one second for the serial external lane, 46–48 seconds for the serial speed
lane, and 14–15 seconds for the privileged lane. The ordinary non-privileged
production sequence (`all` lane: support + functional + external + speed) takes
about 2 minutes (~127s). A one-CPU constrained functional run uses four jobs and
takes about 71 seconds. These are planning values, not portable performance
guarantees. The `all` total includes the production policy/harness checks; the
native-unit tree remains separate. Complete production plus the Release native-unit
lane takes about 3.5 minutes including the privileged lane. The Release native-unit
portion measured a median ~74 seconds across three warm `linux-unit-release` runs.
This measurement does not include the additional Debug unit lane; cloud CI runs
Release and Debug in parallel so Debug adds runner work without normally adding its
full duration to the critical path. These values vary with hardware and build
warmth.

The shorter runtime makes broad validation practical. Use the full functional
lane readily for shared networking or tunnel behavior and the ordinary integration
sequence for broad tunnel or harness work. Run complete production plus both
native-unit configurations for shared-core contracts, lifecycle/concurrency work,
multi-subsystem changes, or any change whose impact is difficult to bound. Focused
checks remain the right choice for narrow or non-behavioral edits.

```bash
# Ordinary non-privileged production Release sequence across test lanes.
cmake --preset linux
cmake --build --preset linux --config Release --target check_waterwall_tests -j8

# Run the production support lane (policy and test-harness checks).
bash tests/run_test_lane.sh support build/linux Release

# Run the deterministic functional lane directly in parallel.
bash tests/run_test_lane.sh functional build/linux Release

# Run all ordinary non-privileged production lanes in sequence.
bash tests/run_test_lane.sh all build/linux Release

# Complete native-unit suite: optimized Release plus asserted Debug behavior.
cmake --preset linux-unit-tests
cmake --build --preset linux-unit-release -j8
ctest --preset linux-unit-release --output-on-failure
cmake --build --preset linux-unit-debug -j8
ctest --preset linux-unit-debug --output-on-failure
```

### Native Unit Tests

Native unit tests have a dedicated multi-configuration tree with IPO/LTO disabled
before any project target is created. Release preserves optimization and `NDEBUG`
while avoiding mixed-LTO links; Debug activates assertions and other contract
guardrails. Production Release remains IPO/LTO-enabled, so complete behavioral
validation uses the production lane and both native-unit configurations:

Native unit-test executables intentionally disable inherited precompiled headers.
The production library and tunnel targets retain their shared PCH, but applying it
to each independent test target would create a large duplicate artifact per test
and configuration.

```bash
# Production Release: build the shipped binary plus the production-full suite.
cmake --preset linux
cmake --build --preset linux --config Release --target check_waterwall_tests -j8

# Native units: optimized Release/no-LTO behavior.
cmake --preset linux-unit-tests
cmake --build --preset linux-unit-release -j8
ctest --preset linux-unit-release --output-on-failure

# Native units: assertions and Debug guardrails in the same no-LTO tree.
cmake --build --preset linux-unit-debug -j8
ctest --preset linux-unit-debug --output-on-failure
```

For focused behavioral work, prefer the relevant `linux-unit-debug` selection
first: assertions usually identify a violated ownership, lifecycle, or state
contract closer to its cause. Repeat that coverage with `linux-unit-release`
before completion because optimization and `NDEBUG` can expose different behavior.
Broad/shared changes run both complete presets. Debug is not a substitute for
Release, AddressSanitizer, UndefinedBehaviorSanitizer, or ThreadSanitizer. Never
build native unit tests in the production tree: it contains the LTO-enabled
libraries used by `Waterwall`.

Crypto backend validation follows the same two-tree rule. Each production preset
such as `linux-sodium-crypto` has a matching native-unit preset such as
`linux-sodium-crypto-unit`. Build the shipped executable and run integration
checks from the production tree; build and run native crypto tests only from the
matching no-LTO unit tree. Production crypto presets intentionally do not define
native-unit targets.

The focused shutdown concurrency lane is configured separately:

```bash
cmake --preset linux-tsan-unit
cmake --build --preset linux-tsan-unit -j8
ctest --preset linux-tsan-unit --output-on-failure
```

It covers the controller, worker-message/event-loop admission, reader-session,
and real production-sequence shutdown fixtures under ThreadSanitizer. It is a
focused concurrency lane, not a replacement for the Release/no-LTO unit lane.

The registered no-LTO policy directly checks the unit-tree cache, reachable
compile/link commands, and representative WaterWall, lwIP, and TlsClient
artifacts. That is enough to catch the mixed-LTO regression without building a
second attestation system around the compiler, build tool, or verifier.

Linux cloud CI runs the complete `linux-unit-release` and `linux-unit-debug`
presets as independent parallel jobs. On macOS and Windows, CI builds
`waterwall_platform_unit_tests`, runs the same direct no-LTO policy, and executes
the registered platform unit tests in Release.

Run one case by its registered name (use an anchored regex):

```bash
ctest --preset linux --output-on-failure -R '^waterwall\.tls_roundtrip$'
```

To run a single integration case directly while debugging — passing the binary,
the case directory, and a timeout in seconds:

```bash
tests/run_waterwall_case.sh \
  build/linux/Release/Waterwall \
  tests/cases/tls_roundtrip \
  60
```

There are many roundtrip cases to model new tests on, including
`encryption_roundtrip`, `mux_*_roundtrip`, `http1_*` / `http2_*`,
`packets_stream_bridge_roundtrip`, and the `ping_*_roundtrip` family. Pick the one
closest to your tunnel as a structural reference, then verify that its assertions
actually exercise the changed behavior and failure mode.

:::tip Write a test that would fail if direction were reversed
The highest-value test for a flow or packet change is one that breaks if you swap
upstream/downstream handling. For paired tunnels (client/server, encode/decode),
that single assertion catches the most common regression in this codebase. See the
direction rules in [Part 2](./part2-lines-and-callbacks.mdx) and
[Part 4](./part4-packet-tunnels.mdx).
:::

## Choosing Validation And Regression Coverage

Validation should answer the product question directly and remain proportional to
risk:

- Start with the smallest check that exercises the change: inspection, formatting,
  a focused target, an existing focused test, or a direct integration case.
- Expand to the functional lane for shared networking/tunnel behavior or changes
  spanning cases. Use all production lanes plus native units for shared-core,
  lifecycle/concurrency, multi-subsystem, security-sensitive, or difficult-to-bound
  changes.
- Documentation, comments, and clearly non-behavioral mechanical changes may need
  only inspection, link/diff checks, or a relevant policy check. Do not run a broad
  lane merely because code changed or because the lane is available.
- New observable behavior, meaningful edge cases, changed contracts, and
  reproducible bugs likely to regress normally receive focused coverage. When
  practical, a regression test should fail before the fix and pass afterward.
- A new test is unnecessary when existing coverage already demonstrates the exact
  behavior, reproduction is impractical, or the change has no meaningful behavior
  to assert. State that reason instead of manufacturing a test or a new harness.
- One direct check may establish a narrow deterministic invariant. Use repetition,
  sanitizers, stress, fault injection, or broader tests when concurrency, timing,
  security, or nondeterminism makes one observation insufficient.

A validation failure or unavailable environment is evidence about the validation
attempt, not a pass and not automatic proof that the product is wrong. Preserve the
exact failure and distinguish **failed** from **inconclusive** evidence.

## Syntax-Only Checks

Do not hand-assemble compile commands. If you need a single-file or syntax-only
compile, take the **exact** flags for that file from the generated
`build/linux/compile_commands.json`.

:::warning The `structure.h` collision trap
Every tunnel has a tunnel-local header named `include/<Tunnel>/structure.h`. If you
write a manual compile command that adds several tunnels' `include/` directories
at once, the wrong `structure.h` can be picked up silently, producing confusing
errors or — worse — a build that links the wrong layout. Validate one tunnel in
isolation, or preserve the target's original include order from
`compile_commands.json`. This is the single biggest reason to avoid hand-rolled
compiles.
:::

Common manual-compile failure modes: missing generated dependency headers, wrong
build-tree include roots, and the `structure.h` collision above.

## When the Compiler Itself Crashes

There is a known build-environment issue where an ad-hoc or non-preset build tree
can trigger a GCC internal compiler error, for example:

```text
internal compiler error: Bus error
```

This often happens while compiling **core** files such as `ww/libc/wlibc.c` —
before your edited tunnel is even reached.

An ICE or bus error is **inconclusive**. It is often a stale/ad-hoc build-tree or
host-resource failure, but it can also be a compiler defect exposed by the changed
translation unit. It proves neither that the tunnel is wrong nor that it is
correct. Reproduce first with a clean supported preset before deciding what to
debug, and never report that lane as passed.

### Fallback Strategy When Compilation Is Blocked

Work down this list:

1. `cmake --preset linux`
2. `cmake --build --preset linux --target <ChangedTargets> -j8`
3. `cmake --build --preset linux -j8`
4. If the failure remains, try another supported project preset/toolchain when it
   can answer the same question (for example, the corresponding Clang preset).
5. Report the exact compiler failure and mark the affected validation
   **inconclusive**.
6. Continue with the strongest verification that still works:
   - preset-based target builds,
   - syntax-only checks using `build/linux/compile_commands.json`,
   - focused code review against the contracts in this guide.

Syntax-only checks and review are useful diagnostics, but they do not replace the
missing link/runtime evidence for a behavioral change. State exactly what remains
unverified.

Summary of build priorities:

- prefer the `linux` preset,
- prefer preset target builds over the root `build/` tree,
- prefer `build/linux/compile_commands.json` over guessed compile flags,
- treat a GCC ICE / bus error as inconclusive until a clean supported build
  establishes otherwise.

## Optional Optimization And Evidence Review

This section applies when an optional optimization candidate or the benchmark,
parser, manifest, or evidence machinery used to decide it is in scope. It does not
limit ordinary product review, and it does not limit a task that explicitly asks
to repair reusable test or benchmark infrastructure. An explicit maintainer/user
request for that infrastructure is the separate approval described below.

Validation is support work, not a second product. It should catch a realistic
regression or answer a predeclared engineering question without recursively trying
to prove that every tool in the evidence chain is itself perfect.

### Classify findings without suppressing them

For optimization/evidence work, distinguish:

1. **Production correctness** — a concrete contract, ownership, lifetime,
   concurrency, security, portability, or user-visible defect in shipped code.
2. **Direct regression coverage** — realistic missing coverage for changed product
   behavior that is likely to regress.
3. **Performance decision** — evidence that a specific production candidate meets,
   misses, or cannot be measured against a frozen workload and gate.
4. **Support-machinery quality** — a defect or hardening opportunity in a runner,
   parser, manifest, test seam, artifact collector, or other evidence tool.

This classification sets priority; it is never a reason to hide a valid finding.
A support-tool defect blocks the current decision when it can skip relevant
behavior, create a false pass/fail, corrupt the metric, or otherwise change that
decision. Otherwise report it as non-blocking follow-up work instead of expanding
the current candidate review. A production-review request does not authorize an
unrelated benchmark-infrastructure redesign, and benchmark cleanup must not change
production behavior merely to make evidence pass.

### Force a terminal candidate decision

Before collecting data, freeze the workload, metrics, thresholds, sample and order
count, host requirements, and candidate boundaries. Then:

- Give every isolated optional candidate one terminal disposition: **keep**,
  **revert/defer**, or **inconclusive on this host**. Do not leave it indefinitely
  pending while growing the acceptance system around it.
- A measured regression or failure to earn the declared gain selects the simpler
  baseline. An inconclusive result also defaults to the simpler production baseline;
  the candidate may be deferred for a better benchmark host.
- A host that cannot reliably execute the frozen workload is non-decision-capable.
  Record that fact. Do not tune the workload after seeing results, retry until
  favorable, weaken a gate, or create alternate harness identities to force a
  decision.
- By default, allow one bounded incidental harness-repair pass after the first
  end-to-end attempt. Further repair belongs to an explicitly requested,
  separately scoped infrastructure task.
- Once direct correctness checks pass and the terminal disposition is recorded,
  run broad product validation once on the final retained production set. Do not
  repeatedly rerun it after every evidence-tool revision.

When only non-blocking evidence-machinery limitations remain, report them with the
terminal product disposition. Do not create another product implementation plan
unless an independently reproducible production defect appears or reusable
infrastructure was explicitly requested.

### Do not create proofs of proofs

Unless a separately scoped security, supply-chain, or reproducible-build threat
model requires them, do not add or require:

- verifier replay, validator self-validation, test-of-test mutation frameworks, or
  attestations of the acceptance transaction;
- binary/tool/source hashes, copied verifier source in every result directory,
  child-process ancestry proofs, filesystem provenance, or CI-runner identity;
- general shell/CMake command parsers whose purpose is only to prove that recorded
  commands match recorded flags;
- exhaustive fail-closed schemas for diagnostic fields that cannot change the
  scoped correctness or keep/revert decision; or
- a product setting, protocol field, runtime branch, counter, API, or lifecycle hook
  added solely to make optional evidence easier to authenticate.

A direct deterministic check is often enough for a narrow build option, path,
ownership balance, timeout, or emitted metric. Timing, concurrency, security, and
nondeterminism may require repeated or independent evidence; the rule forbids
recursive meta-validation, not risk-appropriate testing.

### Keep support code and artifacts subordinate

- Prefer existing tests and small fixtures. If new evidence code materially exceeds
  the production change or creates a framework, stop unless that infrastructure
  scope was explicitly authorized.
- Test seams and counters added solely for evidence must compile out of ordinary
  production builds. A production API added only for a benchmark needs separate
  product justification and approval.
- Raw benchmark output, copied manifests, temporary state trees, and repeated runner
  snapshots are generated artifacts. Keep one concise results summary in source and
  bulky reproducibility bundles outside normal history unless requested.
- If optional proof machinery becomes harder to trust than the direct check, prefer
  simplifying, replacing, or removing it over adding another validator. Removal is
  still a code change and follows the task's authorization boundary.

## Code Review Rules And Tunnel Checklist

This checklist is a minimum, not the boundary of review. Inspect changed behavior
and affected callers, callees, neighbors, and error paths for undefined behavior,
bounds and integer errors, races, memory/resource leaks, exhaustion or denial of
service, security problems, invalid configuration handling, compatibility,
portability, and build/test defects. Existing patterns, passing tests, policy
checks, and comments are evidence, not proof.

Report a concrete trigger and impact for each finding, distinguish confirmed
defects from questions or optional improvements, and report material out-of-scope
defects without silently editing them. If no actionable finding exists, say so and
name material residual risks or validation gaps rather than inventing stylistic
findings.

For a tunnel change, confirm every applicable item below:

**Lifecycle and direction**

- `Init` initializes this tunnel's line state before any callback can use it.
- Upstream callbacks are forwarded only with `tunnelNextUpStream*`.
- Downstream callbacks are forwarded only with `tunnelPrevDownStream*`.
- No `initialized` flag was added unless an explicitly documented line-role or
  callback contract requires state before ordinary `Init`.

**Line safety**

- Every re-entrant callback either returns immediately or protects the line
  (`lineCallWithRef()` / manual `lineRef()` + `lineIsAlive()`).
- On a `false` from `lineCallWithRef()`, the code does not touch `line`, line state,
  or `LinestateDestroy()`.
- Only the line **owner** calls `lineDestroy()`.
- Every normal-line owner receiving `Finish` detaches producers and inventories,
  destroys its state, and returns with `! lineIsAlive(line)` on every error,
  timeout, and terminal-verdict branch.
- A borrowed-line path destroys only its own state and never calls
  `lineDestroy()`.
- `requestProgramShutdown()` is never used instead of closing an owned line.

**Finish**

- `Finish` destroys local state before propagating a real close.
- Middle-tunnel teardown finishes upstream first, then downstream, then returns.
- No `Payload`, `Est`, `Pause`, `Resume`, or `Finish` reflects toward the side that
  sent `Finish`.
- If final protocol bytes are sent during `Finish`, the sender side is marked
  finished before the re-entrant send while holding a line reference, and the
  handler unrefs and returns without touching destroyed state.

**Backpressure**

- After receiving `Pause`, a producer initiates no new payload toward that consumer
  until `Resume`.
- Any intentional pre-Pause tolerance is bounded, FIFO-preserving, accounted, and
  has a clear resume or overflow/close path. Transparent middle tunnels do not
  invent buffering merely because adapters have bounded queues.

**Buffers and padding**

- Every prepend fits inside the tunnel's advertised `required_padding_left`.
- `sbufShiftLeft()` is only used when enough left capacity exists.
- Buffers are recycled exactly on the paths that still own them; none leak.

**Packet semantics (if applicable)**

- Packet lines are kept alive during normal runtime.
- Packet-line state is treated as worker-local shared state.
- Packet-line init source (node manager vs. manual `onStart`) is verified.
- Every packet-line `Finish` handler is classified for that exact role and
  direction: fatal anchor, same-direction transparent forwarding, or documented
  terminal absorption. No category destroys the packet line.

**Validation**

- Tests exercise the intended callback direction.
- Validation used preset build metadata, not guessed compiler flags.
- Every modified C/header file was formatted with `clang-format` (or the missing
  tool was reported explicitly).
- Regression coverage was added where it materially protects behavior, or the
  reason existing coverage/non-test validation is sufficient is stated.
- Validation scope is proportional: focused for narrow changes and broad/full for
  shared, concurrent, security-sensitive, or difficult-to-bound work.

## Common Pitfalls (Master List)

A consolidated list of the failure modes this guide exists to prevent:

- Accessing tunnel line state after `LinestateDestroy()` (or reading zeroed
  fields).
- Adding `initialized` flags to compensate for unsafe control flow.
- Touching `line_t*` after an inter-tunnel callback without protection.
- Calling `tunnelNext*` vs `tunnelPrev*` in the wrong direction.
- Reflecting `Pause`/`Resume`/`Finish` back toward a finished direction.
- Emitting `Est`, `Pause`, `Resume`, or `Finish` at the wrong time.
- Keeping a line alive across `Finish` without `lineRef()`.
- Forgetting that `lineDestroy()` expects tunnel states to be zeroed unless the
  refcount is still positive.
- Leaking buffers when a callback kills the line.
- Misusing `sbufShiftLeft()` or ignoring `required_padding_left`.
- Behavior that only works in one chain arrangement but breaks general
  composition.
- Treating packet-line state as per-connection state, or destroying packet lines
  at runtime.
- Assigning callbacks or accessing tunnel state before checking a nullable
  `tunnelCreate()` / `adapterCreate()` / `packettunnelCreate()` result.
- Indexing worker-owned arrays with raw `getWID()` instead of using line, worker,
  loop, or checked event-worker context.
- Treating an existing implementation as proof of correctness instead of checking
  its contract and callers.
- Hand-assembling compile commands when preset build metadata exists.
- Reporting a compiler crash or unavailable environment as passed validation.

## Expected Output From a Coding Agent

Adapt the response to the request and lead with the outcome. A completed change or
review should still make these facts easy to verify:

1. **Result** — what changed, or the confirmed findings in severity order.
2. **Correctness evidence** — the concrete behavior, callers, and applicable
   lifecycle, line, direction, buffer, packet, worker, or shutdown contracts.
3. **Validation** — commands actually run, their results, and any failed or
   inconclusive checks. Do not imply that an unrun lane passed.
4. **Residual risk** — material gaps, assumptions, or follow-up work.

Do not force unrelated tunnel analysis into a documentation or tooling result.
Conversely, a tunnel change that cannot identify its callback direction and exact
line role is not ready. When something consequential remains unclear, investigate
source, tests, callers, and documentation and ask a focused maintainer question if
the repository cannot decide it; do not treat an existing pattern as proof or
invent a lifecycle concept as an incidental workaround.
