# Introduction

WaterWall is a modular, chain-based tunneling framework. It lets you build
network paths by connecting small nodes together in JSON configuration files.

A WaterWall chain can be as simple as a TCP port forward:

```text
TcpListener -> TcpConnector
```

Or it can combine multiple transport, protocol, encryption, multiplexing, and
packet-processing layers:

```text
TcpListener -> MuxClient -> VlessClient -> TlsClient -> TcpConnector
```

The same design can also be used for packet-oriented workflows, such as TUN
interfaces, WireGuard-style paths, raw packet processing, connection-to-packet
bridges, and packet-to-stream bridges.

## How WaterWall Works

Each node has a focused job: accept traffic, select a destination, transform the
data, or send it through a socket or interface. For example, `TcpListener`
accepts a connection and `TcpConnector` opens its outbound connection; nodes
between them add the features that path needs.

You connect nodes with `next` fields in a JSON config. A node's `type` selects
its implementation, while its `name` is the label other nodes use to find it.
`next` refers to that name, not to a node type. Traffic moves upstream toward
`next`, and responses move back downstream through the chain.

A chain describes processing inside one WaterWall instance. A socket connection
between machines joins separate chains: the client side wraps the traffic, and
the server side uses the corresponding nodes to unwrap it. Protocol nodes such
as `VlessClient`, `HttpClient`, and `QuicClient` rely on a separate transport
adapter to reach the remote server.

Because nodes are composable, you can start with a small working setup and add
features one layer at a time.

## Available Node Families

The tables below group the public nodes by purpose. Follow a node link for its
settings, supported modes, and placement rules, or use [All Nodes](./02-noderefs/all-nodes.mdx)
for the alphabetical index. A custom build can disable individual node types.

### Packet Paths and Interfaces

| Purpose | Nodes | What they add |
| --- | --- | --- |
| Packet interfaces | [TunDevice](./02-noderefs/TunDevice.mdx), [RawSocket](./02-noderefs/RawSocket.mdx) | Read and write IP packets through an OS TUN interface or raw packet I/O. |

| Packet discovery | [PacketGenerator](./02-noderefs/PacketGenerator.mdx), [PacketCounter](./02-noderefs/PacketCounter.mdx) | Generate and observe packet traffic for source-IP discovery and packet-path checks. |

## Choosing Compatible Layers

Start with the traffic you need to carry: a TCP byte stream, UDP datagrams, or raw
IP packets. These are different interfaces. A UDP datagram contains application
data; a raw IP packet also contains the IP and transport headers. Use the bridge
nodes when crossing these boundaries, and check each node's supported protocols.
For example, the packet/stream and lwIP bridges above currently support IPv4.

For paired WaterWall transforms, configure the corresponding decoder on the
other side in the matching order. Standard proxy clients may instead connect to
a compatible external server within the modes documented by each node.
Encryption, authentication, multiplexing, and framing are separate choices;
adding one does not automatically add the others.

[Part 4: Choosing Nodes](./01-getting-started/tutorial-part4.mdx) expands these
choices into chain examples, including packet bridges and WireGuard.

## Configuration Model

WaterWall uses two levels of configuration:

| File | Purpose |
| --- | --- |
| `core.json` | Starts the runtime, configures logging/workers/DNS, and lists config files to load. |
| Node config files | Define the actual chains and node settings. |

Example `core.json` (the listed path is relative to the directory where you run
WaterWall):

```json
{
  "misc": {
    "workers": 4,
    "ram-profile": "server",
    "mtu": 1500,
    "try-enabling-bbr": true,
    "libs-path": "libs/"
  },
  "dns": {
    "domain-strategy": "prefer-ipv4"
  },
  "configs": [
    "configs/server.json"
  ]
}
```

Save the corresponding chain as `configs/server.json`:

```json
{
  "name": "simple-forward",
  "nodes": [
    {
      "name": "entry",
      "type": "TcpListener",
      "settings": {
        "address": "0.0.0.0",
        "port": 8080
      },
      "next": "exit"
    },
    {
      "name": "exit",
      "type": "TcpConnector",
      "settings": {
        "address": "example.com",
        "port": 80
      }
    }
  ]
}
```

Here, `entry` and `exit` are node names, and `"next": "exit"` links the listener
to the connector. Port `8080` is the local listening port; `example.com:80` is
the outbound destination. This forwards TCP bytes without rewriting HTTP headers.
The [installation guide](./01-getting-started/installation.mdx) walks through
creating the files and running the executable.

## Why WaterWall?

### Modular by Design

WaterWall does not force every deployment into one fixed proxy shape. You can
compose listeners, connectors, protocol nodes, encryption nodes, packet nodes,
and routing nodes into the shape your network actually needs.

### Configuration First

Most usage is driven by JSON files. You can build and adjust chains without
writing C code.

### Stream and Packet Support

WaterWall is not limited to ordinary TCP streams. It can also work with
packet-oriented paths and bridge packets through stream transports when a
topology requires it.

### Runtime-Oriented Implementation

The core is written in C and designed around asynchronous networking, worker
threads, buffer pools, and reusable tunnel components.

## What WaterWall Is Not

WaterWall is not a single prebuilt VPN profile or one-click proxy preset. It is a
toolkit for building network paths. That flexibility is powerful, but it also
means you should understand the chain you are configuring.

For a first deployment, keep the chain small, verify it works, then add nodes one
at a time.
